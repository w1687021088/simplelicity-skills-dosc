# LRU 链表（Old Sublist 与 Young Sublist）

InnoDB 的 Buffer Pool 使用改进版的 LRU（Least Recently Used）算法管理缓存页的替换策略。与标准 LRU 不同，InnoDB 将 LRU 链表分为两个区域：Young Sublist（热区，占 63/8）和 Old Sublist（冷区，占 3/8），通过 Midpoint Insertion 策略防止大批量全表扫描（热扫描）将真正热点数据驱逐出 Buffer Pool。

---

## 标准 LRU 的问题

```
标准 LRU 问题场景：
执行一个大表全表扫描（如 SELECT * FROM big_table）
→ 大量新页被读入，全部插入 LRU 链表头部
→ 驱逐原来的热点页（频繁访问的小表数据、索引页）
→ 全表扫描结束后，热点数据全部消失，Buffer Pool 命中率骤降
→ 接下来大量请求需要重新从磁盘读取，性能急剧下降

这称为"缓存污染（Cache Pollution）"
```

---

## InnoDB LRU 链表结构

```
LRU List（总长度 = Buffer Pool 页数）：

┌──────────────────────┬───────────────────────────────────────┐
│    Young Sublist     │           Old Sublist                 │
│       (5/8)          │              (3/8)                    │
│    （热区/新区）      │          （冷区/老区）                │
├──────────────────────┼───────────────────────────────────────┤
│  头部（最近访问）    │  Midpoint                  尾部（LRU）│
│  Hot pages           │  新页插入位置       驱逐位置           │
└──────────────────────┴───────────────────────────────────────┘

      ← 频繁访问的页向头部移动
                                         → 长期未访问的页被驱逐
```

---

## Midpoint Insertion 策略

```
新页加载时的行为（不是插入链表头部！）：

1. 从磁盘读取新页
2. 将新页插入到 Old Sublist 的头部（即 Midpoint 处，整个链表的 5/8 位置）
3. 新页处于"观察期"：如果在 innodb_old_blocks_time（默认 1000ms）内
   被再次访问，才移动到 Young Sublist 头部（升温）
4. 如果超过 innodb_old_blocks_time 没有再次访问，该页将随时间推移
   向 Old Sublist 尾部移动，最终被驱逐

这样全表扫描的页：
→ 被读入时进入 Old Sublist（而非 Young Sublist）
→ 全表扫描一般不会在 1 秒内二次访问同一页
→ 这些页无法升温到 Young Sublist
→ 不会驱逐 Young Sublist 中的真正热点数据
```

## 相关配置参数

```sql
-- 查看 LRU 相关参数
SHOW VARIABLES LIKE 'innodb_old_blocks%';
-- +-----------------------+-------+
-- | Variable_name         | Value |
-- +-----------------------+-------+
-- | innodb_old_blocks_pct | 37    | -- Old Sublist 占比（默认 37%，约 3/8）
-- | innodb_old_blocks_time| 1000  | -- 在 Old Sublist 中的最短停留时间（ms）
-- +-----------------------+-------+

-- innodb_old_blocks_pct：Old Sublist 占 LRU 的百分比
-- 默认 37（约 3/8），范围 5-95
-- 增大：为"一次性扫描"保留更多空间，减少对热区的影响
-- 减小：热区更大，适合工作集较小的场景

-- innodb_old_blocks_time：新页在 Old Sublist 中的最短停留时间
-- 默认 1000ms（1秒）
-- 在这个时间内被再次访问才能升温到 Young Sublist
-- 设为 0：任何访问都立即升温（退化为标准 LRU）
-- 增大：需要更多次访问才能升温，更严格的升温条件

-- 动态调整（可在线修改）
SET GLOBAL innodb_old_blocks_pct = 37;
SET GLOBAL innodb_old_blocks_time = 1000;
```

## Young 区的优化：减少锁竞争

```sql
-- 问题：如果每次访问都把页移到链表头部，链表头部会有大量锁竞争
-- InnoDB 优化：只有当页在 Young Sublist 的后 1/4 时，才将其移到头部
-- 前 3/4 的热页：访问时不移动（减少链表操作和锁竞争）
-- 这称为 "Young List 优化" 或 "1/4 规则"

-- 相关统计：
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_made_young%';
-- Innodb_buffer_pool_pages_made_young：从 Old 升温到 Young 的次数
-- Innodb_buffer_pool_pages_made_not_young：停留在 Old 中的次数
-- 两者比值反映了缓存污染程度
```

## 监控 LRU 状态

```sql
-- 通过 SHOW ENGINE INNODB STATUS 查看 LRU 详情
SHOW ENGINE INNODB STATUS \G
-- 在 BUFFER POOL AND MEMORY 部分查看：
-- Pages made young XXXX, not young XXXX
-- youngs/s: 每秒从 Old 升温到 Young 的次数
-- non-youngs/s: 每秒停留在 Old 的次数
-- LRU len: LRU 链表总长度
-- unzip_LRU len: 解压缩页的 LRU 长度
-- I/O sum[XX]: 最近 50 秒访问的 LRU 页
-- I/O cur[XX]: 当前正在访问的 LRU 页

-- 查看 Buffer Pool 页详情（包含 LRU 位置信息）
SELECT * FROM information_schema.INNODB_BUFFER_PAGE_LRU
WHERE TABLE_NAME = '`myapp`.`orders`'
LIMIT 20;
-- ACCESS_TIME：最近访问时间
-- IS_OLD：是否在 Old Sublist 中
-- FREE_PAGE_CLOCK：驱逐时钟值
```

## 全表扫描场景的 LRU 行为

```sql
-- 执行全表扫描前后对比
-- 执行前：查看热点数据是否在 Young Sublist
SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE_LRU
WHERE TABLE_NAME = '`myapp`.`hot_table`' AND IS_OLD = 'NO';

-- 执行大表扫描（可能几百万行）
SELECT COUNT(*) FROM big_table;  -- 触发大量页读入

-- 执行后：热点数据是否还在？
SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE_LRU
WHERE TABLE_NAME = '`myapp`.`hot_table`' AND IS_OLD = 'NO';
-- 使用改进 LRU 后，hot_table 的页应该仍在 Young Sublist

-- 如果没有改进 LRU（innodb_old_blocks_time=0），hot_table 的页会被驱逐
```

## 适用场景

- **OLTP + 批处理混合**：白天 OLTP（热点数据在 Young 区），夜间全表扫描（不影响 Young 区），LRU 改进机制保证 OLTP 热点数据不被扫描操作驱逐
- **报表查询优化**：执行大型报表查询前，适当增大 `innodb_old_blocks_time`，防止报表扫描的大量页升温到 Young 区

---

## 常见问题

**为什么 Old Sublist 是 3/8 而不是更大或更小？**

3/8 是经验值的平衡结果。Old 区太小：全表扫描的页很快就溢出 Old 区进入 Young 区（缓存污染）。Old 区太大：Hot 区缩小，真正的热点数据更容易被驱逐。3/8 在大多数工作负载下提供了合理的缓冲空间，通过 `innodb_old_blocks_pct` 可以根据实际负载调整。

---

## 注意事项

- 如果系统中有周期性的全表扫描（如统计查询、备份操作），建议确保 `innodb_old_blocks_time` 不为 0（保持默认 1000ms 或适当增大），以防止这类操作对 OLTP 热点数据的缓存造成干扰。
- 在 InnoDB 内部，Young Sublist 和 Old Sublist 并不是物理上分开的两个链表，而是同一个 LRU 链表上的逻辑分区，通过 `midpoint` 指针标记分界位置。

---

## 总结

InnoDB 的 LRU 链表分为 Young Sublist（热区，5/8）和 Old Sublist（冷区，3/8）。新页加载时插入 Old Sublist 头部（Midpoint Insertion），超过 `innodb_old_blocks_time`（默认 1000ms）后再次被访问才升温到 Young Sublist 头部。全表扫描的页无法升温（扫描期间不会在 1 秒内二次访问同一页），从而保护了 Young Sublist 中的真正热点数据不被驱逐。通过 `innodb_old_blocks_pct` 和 `innodb_old_blocks_time` 调整策略。

# Buffer Pool 大小配置策略（物理内存 50-70%）

Buffer Pool 大小是影响 InnoDB 性能最关键的单一参数。配置过小会导致频繁从磁盘读取数据，命中率低；配置过大则会导致操作系统内存不足、swap 使用，系统整体变慢甚至 OOM（内存溢出）。常见建议是设置为物理内存的 50-70%，但实际最优值取决于服务器角色、并发量和工作集大小。

---

## 配置基准原则

```
Buffer Pool 配置公式（专用数据库服务器）：

物理内存 × 50-70% = 推荐 Buffer Pool 大小

原因：
  剩余内存需要留给：
  → 操作系统内核（约 1-2 GB）
  → MySQL 连接线程（每连接约 1-4 MB × 最大连接数）
  → MySQL 的其他内存区域：
     - Sort Buffer（innodb_sort_buffer_size）
     - Join Buffer（join_buffer_size）
     - Read Buffer（read_buffer_size）
     - Redo Log Buffer（innodb_log_buffer_size，默认 64MB）
     - Tmp Table（tmp_table_size）
  → 文件系统缓存（OS page cache，对 InnoDB 有额外加速效果）
```

## 配置命令

```sql
-- 查看当前 Buffer Pool 配置
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- 默认：128 MB（不足，生产必须调整）

-- 在线动态调整（MySQL 5.7+ 支持）
SET GLOBAL innodb_buffer_pool_size = 12 * 1024 * 1024 * 1024;  -- 12 GB

-- 查看调整进度
SHOW STATUS LIKE 'Innodb_buffer_pool_resize_status';

-- my.cnf 持久化（重启不丢失）
-- [mysqld]
-- innodb_buffer_pool_size = 12G
-- innodb_buffer_pool_instances = 12  -- 每实例 1GB

-- 注意：my.cnf 中的值会在 MySQL 启动时生效
-- 如果 innodb_buffer_pool_size 不是 chunk_size × instances 的整数倍
-- MySQL 会自动向上取整并在错误日志中记录警告
```

## 评估当前 Buffer Pool 是否足够

```sql
-- 方法1：命中率评估
-- 命中率 < 95%：Buffer Pool 严重不足，需要扩大
-- 命中率 95-99%：可以考虑适当扩大
-- 命中率 > 99%：Buffer Pool 基本足够
SELECT
    ROUND(
        (1 - SUM(CASE WHEN VARIABLE_NAME = 'Innodb_buffer_pool_reads'
                      THEN VARIABLE_VALUE END) /
             SUM(CASE WHEN VARIABLE_NAME = 'Innodb_buffer_pool_read_requests'
                      THEN VARIABLE_VALUE END)
        ) * 100, 2
    ) AS hit_rate_pct
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN ('Innodb_buffer_pool_reads', 'Innodb_buffer_pool_read_requests');

-- 方法2：工作集大小估算
-- 查看当前数据库总数据量
SELECT
    TABLE_SCHEMA AS db_name,
    SUM(DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024 / 1024 AS total_size_gb
FROM information_schema.TABLES
GROUP BY TABLE_SCHEMA
ORDER BY total_size_gb DESC;

-- 如果总数据量 >> Buffer Pool 大小，需要评估热点数据的比例
-- 通常活跃的"热点数据"占总数据的 10-30%
-- Buffer Pool 至少应能容纳热点数据

-- 方法3：等待空闲页次数
SHOW STATUS LIKE 'Innodb_buffer_pool_wait_free';
-- 大于 0 说明 Buffer Pool 内存不足，立即扩大
```

## 内存使用计算示例

```
服务器：32GB 物理内存，专用 MySQL，最大连接数 500

内存分配：
  操作系统：           2 GB
  MySQL 连接线程：     500 × 2 MB = 1 GB（估算）
  InnoDB Log Buffer：  64 MB
  Sort/Join/Read Buffer：每连接约 4 MB（按峰值并发 100 计）= 400 MB
  其他 MySQL 管理内存：200 MB
  文件系统 page cache：2 GB（保留）
  ────────────────────────────────
  留给 Buffer Pool：   32 - 2 - 1 - 0.064 - 0.4 - 0.2 - 2 ≈ 26 GB
  
  配置：innodb_buffer_pool_size = 24G（保留少量余量）
        innodb_buffer_pool_instances = 24（每实例 1GB）
```

## NUMA 架构下的 Buffer Pool 配置

```sql
-- NUMA（Non-Uniform Memory Access）架构下，跨 NUMA 节点的内存访问比本地内存慢
-- 建议：每个 NUMA 节点分配独立的 Buffer Pool 实例

-- 查看 NUMA 节点数（Linux 命令）
-- numactl --hardware | grep 'available'
-- available: 2 nodes (0-1)  → 2 个 NUMA 节点

-- 配置建议：
-- 总 Buffer Pool = NUMA节点内存 × 0.7 × 节点数
-- 实例数 = NUMA节点数 × N（N使得每实例 >= 1GB）

-- Linux 启动 MySQL 时绑定 NUMA 节点内存：
-- numactl --interleave=all mysqld_safe &
-- 或 my.cnf：
-- [mysqld_safe]
-- numa-interleave=ON
```

## 适用场景

- **容量规划**：新搭建 MySQL 服务器时，根据物理内存按 50-70% 规则初始配置
- **性能优化**：命中率持续低于 99% 时，逐步增大 Buffer Pool（每次增加 10-20%），观察命中率变化
- **云数据库**：云数据库通常按规格自动配置 Buffer Pool，了解规则有助于选择合适的规格

## 常见问题

**Buffer Pool 设置了 24GB，但 MySQL 实际使用内存超过了 28GB，正常吗？**

正常。Buffer Pool 之外，MySQL 还需要额外内存用于：Redo Log Buffer（默认 64MB）、查询缓存（Sort/Join Buffer 等，按并发连接数积累）、InnoDB 的自适应哈希索引、元数据缓存等。MySQL 进程实际占用内存通常比 `innodb_buffer_pool_size` 多 1-3 GB，规划时需预留这部分空间。

---

## 注意事项

- 将 Buffer Pool 配置为超过物理内存 80% 时，操作系统内存紧张，可能触发 swap。swap 会导致严重的性能问题（磁盘上的交换比 Buffer Pool 磁盘 I/O 更差）。建议禁用 swap（`vm.swappiness=0` 或更激进地关闭 swap），确保 MySQL 内存不会被换出。
- 在线动态扩大 Buffer Pool（`SET GLOBAL innodb_buffer_pool_size`）会在后台异步进行，期间 MySQL 正常服务，但可能有短暂的内存申请开销。缩小 Buffer Pool 会触发脏页刷盘，可能更耗时。

---

## 总结

Buffer Pool 大小建议为物理内存的 50-70%，专用 MySQL 服务器可以到 70%，混合服务器需留出更多余量。评估方法：命中率（目标 99%+）、工作集大小估算、`Innodb_buffer_pool_wait_free > 0`（需立即扩容）。MySQL 5.7+ 支持在线动态调整（`SET GLOBAL innodb_buffer_pool_size`），通过 `Innodb_buffer_pool_resize_status` 查看进度。配置时还需考虑 MySQL 其他内存（连接线程、Sort/Join Buffer 等）约占 2-4GB。

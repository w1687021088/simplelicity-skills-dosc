# LSN（Log Sequence Number）日志序列号

LSN（日志序列号）是 InnoDB 全局单调递增的 8 字节整数，代表 Redo Log 流中的字节偏移量。每向 Redo Log 写入 1 字节内容，LSN 就增加 1。LSN 是 InnoDB 内部各模块协调工作的核心时间轴：Checkpoint 用它标记已安全刷盘的位置，数据页用它记录自己的修改版本，崩溃恢复用它判断哪些 Redo Log 需要重放。

---

## LSN 的基本概念

```
LSN 的本质：
  Redo Log 流从服务器启动开始连续写入
  LSN = 当前 Redo Log 中的字节偏移量（从初始值开始累加）
  初始值不为 0，MySQL 8.0 初始 LSN 约为几百（小的固定起始值）

LSN 的特性：
  → 全局唯一（整个 InnoDB 实例只有一个 LSN 序列）
  → 单调递增（永不减小，永不重置）
  → 高并发下原子递增（Lock-Free 机制）
  → 每个事务提交时都会消耗一段 LSN 范围（该事务 Redo Log 的字节数）
```

---

## LSN 的多个类型

```sql
-- 在 SHOW ENGINE INNODB STATUS 中可以看到多个 LSN：

SHOW ENGINE INNODB STATUS \G
-- LOG 部分：
-- Log sequence number  17321684936
--   ↑ 当前内存中最新的 LSN（最后一个写入 Redo Log Buffer 的记录位置）
--   = write_lsn
--
-- Log flushed up to   17321684900
--   ↑ 已刷写到磁盘 Redo Log 文件的最新 LSN
--   = flushed_lsn
--   write_lsn - flushed_lsn = 未刷盘的 Redo Log 大小（通常很小）
--
-- Pages flushed up to 17321678432
--   ↑ 数据页已刷盘所覆盖到的最大 LSN
--   所有 LSN <= 此值的数据页修改已经刷盘
--   = dirty_pages_flushed_lsn
--
-- Last checkpoint at  17321678432
--   ↑ 上次 Checkpoint 的 LSN（等于 Pages flushed up to 或略小）
--   = checkpoint_lsn
--   Redo Log 中 LSN <= checkpoint_lsn 的部分可以被循环覆盖
```

## LSN 与数据页的关系

```sql
-- 每个数据页的 Page Header 中存储 LSN：

-- FIL_PAGE_LSN（8字节）：该页最后一次被修改时对应的 LSN
-- 这个 LSN 告诉 InnoDB："我的内容反映了 Redo Log 在此 LSN 时的状态"

-- 崩溃恢复时的 LSN 比较逻辑：
-- 对于每条 Redo Log 记录（对应某个页的修改，记录中有 LSN）：
--   if（页的 FIL_PAGE_LSN < Redo Log 记录的 LSN）：
--     → 该页还没包含这次修改 → 应用这条 Redo Log（重放）
--   else：
--     → 该页已经包含了这次修改（或更新的修改）→ 跳过（避免重复应用）

-- 查看数据页的 LSN（通过 innochecksum 工具）
-- innochecksum -p 456 --page-type-dump myapp/orders.ibd
-- 输出每页的 FIL_PAGE_LSN 等信息
```

## LSN 在各模块中的应用

```sql
-- 1. Redo Log 写入
--    每次写 Redo Log 记录前：原子递增 LSN，分配 LSN 范围
--    写入后：Redo Log 记录的尾部标记该条记录对应的 LSN

-- 2. Buffer Pool 脏页管理
--    脏页控制块记录该页首次被修改时的 oldest_modification_lsn
--    Flush List 按 oldest_modification_lsn 排序（小在尾部）

-- 3. Checkpoint 推进
--    Checkpoint = 推进 checkpoint_lsn 到当前 Flush List 尾部页的 oldest_modification_lsn
--    推进 Checkpoint 后，Redo Log 中 LSN <= new_checkpoint_lsn 的部分可以被覆盖

-- 4. 主从复制（Binary Log）
--    Binlog 和 Redo Log 通过 XID（事务 ID）对应，不直接使用 LSN
--    但 LSN 在从库追赶主库的进度中有间接关系

-- 5. 备份工具（XtraBackup 等）
--    备份时记录当前 checkpoint_lsn
--    增量备份：复制 checkpoint_lsn 到 current_lsn 之间的 Redo Log
```

## LSN 的实际观察

```sql
-- 观察 LSN 变化速度（写入量的直观指标）
-- 间隔 1 秒查询两次，差值就是每秒写入的 Redo Log 字节数

-- 查询1：
SELECT VARIABLE_VALUE AS lsn_now
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Innodb_lsn_current';

-- 等待 1 秒后查询2
SELECT VARIABLE_VALUE AS lsn_1s_later
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Innodb_lsn_current';

-- 差值 = 每秒 Redo Log 写入量（字节）
-- 这是评估 Redo Log 大小是否合理的直接依据

-- performance_schema 中的 LSN 相关指标
SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
    'Innodb_lsn_current',
    'Innodb_lsn_flushed',
    'Innodb_lsn_last_checkpoint',
    'Innodb_redo_log_capacity_resized',
    'Innodb_redo_log_enabled'
);
```

## 适用场景

- **性能基准测试**：通过采集 LSN 的增长速度，精确量化写入负载（每秒产生多少字节 Redo Log）
- **Redo Log 容量规划**：`(current_lsn - checkpoint_lsn)` 反映了当前 Redo Log 的"压力"，接近总容量时需要扩容或优化刷盘速度
- **崩溃恢复分析**：崩溃恢复的时间与 `(current_lsn - checkpoint_lsn)` 成正比，减少这个差值可以缩短崩溃恢复时间

## 常见问题

**为什么数据库启动后 LSN 不是从 0 开始？**

LSN 的起始值是固定的非零值（MySQL 8.0 约为几百到几千），并在数据库运行过程中持续累加。重启 MySQL 后，LSN 从上次关闭时的值继续增长（记录在系统表空间），而不是重置为 0。这确保了 LSN 在整个数据库生命周期内的全局唯一性。如果 LSN 在重启后归零，会导致新 Redo Log 记录和旧数据页的 FIL_PAGE_LSN 比较混乱。

---

## 注意事项

- LSN 是 8 字节无符号整数，最大值约为 1.8 × 10^19。即使每秒写入 1 GB 的 Redo Log（极端高写入场景），耗尽 LSN 空间也需要约 58 万年，实际上无需担心 LSN 溢出。
- 通过监控 `current_lsn - checkpoint_lsn`（未被 Checkpoint 的 Redo Log 大小）可以直观判断 Redo Log 的使用压力。这个值接近 `innodb_redo_log_capacity` 时就需要警惕。

---

## 总结

LSN 是 InnoDB 的全局单调递增计数器，代表 Redo Log 流中的字节偏移量。有四个关键 LSN：write_lsn（内存最新）、flushed_lsn（已刷盘）、dirty_pages_flushed_lsn（数据页刷盘进度）、checkpoint_lsn（可覆盖边界）。每个数据页存储 `FIL_PAGE_LSN`，崩溃恢复时通过比较页的 LSN 和 Redo Log 记录的 LSN 判断是否重放。`current_lsn - checkpoint_lsn` 反映 Redo Log 使用压力，是容量规划和性能监控的核心指标。

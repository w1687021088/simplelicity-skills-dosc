# Redo Log 物理日志结构

Redo Log（重做日志）是 InnoDB 实现持久性（Durability）的核心机制。它记录的是对数据页的**物理变更**（修改了哪个表空间、哪个页、哪个偏移量、改了什么值），而不是 SQL 语句本身。MySQL 崩溃重启后，InnoDB 通过重放 Redo Log 将所有已提交但尚未刷盘的事务变更恢复到数据文件中，保证已提交的数据不会丢失。

---

## Redo Log 的本质

```
Redo Log 记录的是什么：

一个典型的 Redo Log 记录（Redo Log Record）：
┌──────────┬───────────┬────────┬──────────┬───────────────────────────┐
│ Log Type │ Space ID  │ Page No│ Offset   │ Data（修改后的内容）        │
│  (1字节) │ (4字节)   │(4字节) │(2字节)   │ (变长)                    │
└──────────┴───────────┴────────┴──────────┴───────────────────────────┘

含义：
→ 将表空间 Space ID 的第 Page No 页，从偏移量 Offset 开始，写入 Data

举例（插入一行数据）：
→ Log Type = MLOG_WRITE_STRING
→ Space ID = 23（orders 表的 .ibd 文件）
→ Page No = 456
→ Offset = 1024
→ Data = [新行的字节数据]
```

## Redo Log 的层次结构

```
Redo Log 存储层次（从小到大）：

Log Block（日志块）：
  大小：512 字节（对应磁盘扇区大小，保证原子写入）
  结构：
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Block Header (12字节) │  Log Record Data (496字节) │ Trailer (4字节)│
  │  - LOG_BLOCK_HDR_NO   │  多个 Redo Log Record      │  校验和         │
  │  - LOG_BLOCK_DATA_LEN │                            │                │
  │  - LOG_BLOCK_FIRST_REC│                            │                │
  └──────────────────────────────────────────────────────────────────────┘

Log Group（日志组）：
  包含一组 Redo Log 文件
  循环写入：文件1 → 文件2 → ... → 文件N → 文件1（覆盖写）

Redo Log File：
  MySQL 8.0.30 之前：ib_logfile0, ib_logfile1
  MySQL 8.0.30+：#ib_redo0, #ib_redo1, #ib_redo2, ... （动态管理）
```

## MySQL 8.0.30+ 的 Redo Log 架构变更

```sql
-- MySQL 8.0.30 之前的固定文件结构：
-- datadir/ib_logfile0
-- datadir/ib_logfile1
-- 固定 innodb_log_files_in_group 个文件（默认 2 个）
-- 固定 innodb_log_file_size 大小（默认 50MB）

-- MySQL 8.0.30+ 的动态 Redo Log 管理：
-- 文件名格式：#ib_redo{N}（N 从 0 开始递增）
-- InnoDB 自动管理文件数量，文件可以动态增减
-- 总容量受 innodb_redo_log_capacity 控制

-- 查看当前 Redo Log 配置
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
-- MySQL 8.0.30+：默认 100 MB（= 2 × 50MB，向后兼容旧默认值）
-- 推荐生产环境设置为 4-8 GB

SHOW VARIABLES LIKE 'innodb_log_file%';
-- MySQL 8.0.30 之前的参数（旧版本兼容）

-- 查看 Redo Log 文件
-- ls -la /var/lib/mysql/#ib_redo*
-- 或 Windows：dir datadir\#ib_redo*
```

## Redo Log 记录类型

```sql
-- InnoDB 定义了约 50 种 Redo Log 记录类型（log type）
-- 常见类型：

-- MLOG_1BYTE (1)：修改页中 1 个字节
-- MLOG_2BYTES (2)：修改页中 2 个字节
-- MLOG_4BYTES (4)：修改页中 4 个字节
-- MLOG_8BYTES (8)：修改页中 8 个字节
-- MLOG_WRITE_STRING (30)：修改页中一段连续字节
-- MLOG_REC_INSERT (9)：插入一条索引记录（B-Tree）
-- MLOG_REC_DELETE (10)：删除一条索引记录
-- MLOG_REC_UPDATE_IN_PLACE (13)：原地更新索引记录
-- MLOG_INIT_FILE_PAGE2 (56)：初始化一个新数据页
-- MLOG_MULTI_REC_END (31)：复合 Redo Log 组的结束标记

-- 通过 information_schema 查看 Redo Log 状态
SELECT * FROM performance_schema.global_status
WHERE VARIABLE_NAME LIKE 'Innodb_redo%';
```

## LSN（Log Sequence Number）与 Redo Log 的关系

```sql
-- LSN 是 Redo Log 中每个字节的全局顺序编号
-- 每写入一字节 Redo Log，LSN 递增 1
-- LSN 在整个 InnoDB 生命周期内单调递增，永不重置

-- 查看当前 LSN
SHOW ENGINE INNODB STATUS \G
-- 在 LOG 部分：
-- Log sequence number  XXXXXXXX   （当前最新 LSN，内存中）
-- Log flushed up to    XXXXXXXX   （已刷到磁盘的 LSN）
-- Pages flushed up to  XXXXXXXX   （已刷盘数据页的最大 LSN，Checkpoint LSN）
-- Last checkpoint at   XXXXXXXX   （上次 Checkpoint 的 LSN）

-- LSN 的多个含义：
-- current_lsn：当前最新 LSN（Redo Log Buffer 中最新记录的位置）
-- flushed_lsn：已写入 Redo Log 文件的 LSN
-- checkpoint_lsn：上次 Checkpoint 的 LSN（.ibd 中数据页已经包含此 LSN 前的所有修改）

-- crash recovery 时：
-- 从 checkpoint_lsn 开始重放 Redo Log 到 current_lsn
-- 不需要重放全部 Redo Log，只需重放 checkpoint 之后的部分
```

## Redo Log 的物理页结构

```
数据页（16KB）中的 LSN 信息：
每个数据页的 Page Header 中存储：
  - FIL_PAGE_LSN (8字节)：该页最后一次被修改时的 LSN
  - FIL_PAGE_FILE_FLUSH_LSN：仅系统表空间第一页使用

Crash Recovery 使用 LSN 的逻辑：
  1. 读取 Checkpoint LSN（Last checkpoint at）
  2. 从 Redo Log 中 checkpoint_lsn 位置开始读取
  3. 对于每条 Redo Log 记录：
     a. 定位到目标页（space_id + page_no）
     b. 读取该页的 FIL_PAGE_LSN
     c. 如果 FIL_PAGE_LSN < Redo Log 记录的 LSN：应用该 Redo Log 记录（需要重放）
     d. 如果 FIL_PAGE_LSN >= Redo Log 记录的 LSN：跳过（页已包含该修改）
  4. 重放完成，数据库恢复到崩溃前的已提交状态
```

## 适用场景

- **崩溃恢复**：任何 InnoDB 数据库都依赖 Redo Log 进行崩溃恢复，理解其结构有助于分析恢复失败的根本原因
- **性能调优**：Redo Log 是写密集型系统的关键 I/O 路径，合理配置 `innodb_redo_log_capacity` 和 `innodb_log_buffer_size` 对写入性能至关重要

## 常见问题

**Redo Log 和 Binlog 都记录了数据变更，为什么需要两个日志？**

两者目的不同：Redo Log 是 InnoDB 的物理日志，记录对数据页的物理变更，用于崩溃恢复（保证持久性）；Binlog 是 MySQL Server 层的逻辑日志，记录 SQL 语句或行变更，用于主从复制和时间点恢复。两者配合工作：事务提交时先写 Redo Log（prepare 阶段），再写 Binlog，再提交 Redo Log（commit 阶段），形成两阶段提交（2PC）确保两个日志的一致性。

## 注意事项

- MySQL 8.0.30+ 使用动态 Redo Log 管理（`#ib_redo*` 文件），`innodb_redo_log_capacity` 替代了旧的 `innodb_log_file_size × innodb_log_files_in_group`。从 8.0.30 之前的版本升级时，InnoDB 会自动将旧的 `ib_logfile0/1` 迁移到新格式，无需手动操作。
- Redo Log 文件不能被直接删除（MySQL 运行时），它们受 InnoDB 管理。如果需要扩大 Redo Log 容量，通过修改 `innodb_redo_log_capacity` 然后重启 MySQL 即可，InnoDB 会自动重新创建 Redo Log 文件。

---

## 总结

Redo Log 是 InnoDB 的物理日志，记录对数据页（表空间 ID + 页号 + 偏移量 + 新值）的变更，以 512 字节的 Log Block 为单位存储，通过 LSN 全局排序。MySQL 8.0.30+ 将固定的 `ib_logfile0/1` 改为动态管理的 `#ib_redo*` 文件，总容量由 `innodb_redo_log_capacity` 控制（推荐 4-8GB）。崩溃恢复时，从最后一个 Checkpoint LSN 开始重放 Redo Log，通过比较页的 FIL_PAGE_LSN 决定是否重放，确保已提交事务的持久性。

# Redo Log 刷盘策略 innodb_flush_log_at_trx_commit

`innodb_flush_log_at_trx_commit` 是控制 Redo Log 刷盘时机的关键参数，直接决定了 MySQL 在事务提交时 Redo Log 写入磁盘的方式。不同的设置值在数据安全性和写入性能之间做出不同的权衡：值为 1 时最安全但每次提交都有 fsync 开销，值为 0 或 2 时性能更好但存在不同程度的数据丢失风险。

---

## 三个取值的行为差异

| 参数值 | 事务 COMMIT 时的动作 | 后台每秒 | 数据安全性 | 性能 |
|--------|---------------------|---------|-----------|------|
| 0 | 不做任何 I/O 操作 | 写入 OS 缓冲 + fsync | 最低（崩溃丢失最多 1 秒写入）| 最高 |
| 1 | 写入 OS 缓冲 + fsync | - | 最高（ACID 完全满足）| 最低 |
| 2 | 写入 OS 缓冲（不 fsync）| fsync | 中等（MySQL 崩溃不丢失，OS 崩溃丢失最多 1 秒）| 中等 |

---

## 每个值的详细行为

```sql
-- 查看当前设置
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
-- 默认：1（最安全模式，满足 ACID D）

-- 值 = 1（默认，推荐生产主库）：
-- COMMIT → write(Redo Log Buffer → OS 缓冲) → fsync(OS 缓冲 → 磁盘)
-- 每次提交都调用 fsync，确保日志持久化到物理磁盘
-- 即使操作系统崩溃，数据也不会丢失
-- 缺点：每次提交有 1 次 fsync 调用（机械硬盘约 200-500 IOPS）

-- 值 = 2（折中方案，适合从库或对少量丢失容忍的场景）：
-- COMMIT → write(Redo Log Buffer → OS 缓冲)
-- 每秒后台线程 → fsync(OS 缓冲 → 磁盘)
-- MySQL 进程崩溃不丢数据（OS 缓冲在内核，进程崩溃不清空）
-- 操作系统/电源故障丢失最多 1 秒的已提交事务
-- 优点：去掉了每次提交的 fsync，性能大幅提升

-- 值 = 0（高风险，一般不用于生产）：
-- COMMIT → 不做任何 I/O
-- 每秒后台线程 → write + fsync
-- MySQL 进程崩溃可能丢失最多 1 秒的事务（Buffer 中未刷出的 Redo Log）
-- 操作系统崩溃同样丢失最多 1 秒的事务
-- 优点：最高写入性能，但安全性最差

-- 修改参数（支持动态修改）
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
-- 或 my.cnf：innodb_flush_log_at_trx_commit = 1
```

## 性能影响量化

```sql
-- sysbench OLTP 写入测试（参考值，实际取决于硬件）
-- 配置：8 核 CPU，机械硬盘，Buffer Pool 8GB，并发 32 线程

-- innodb_flush_log_at_trx_commit = 1：
--   TPS ≈ 500-2000（受机械硬盘 fsync IOPS 限制）

-- innodb_flush_log_at_trx_commit = 2：
--   TPS ≈ 5000-20000（去掉 fsync 后大幅提升）

-- innodb_flush_log_at_trx_commit = 0：
--   TPS ≈ 6000-25000（略高于 2，因为连 write 也省了）

-- SSD 环境下，值为 1 和 2 的差距缩小：
-- SSD fsync 延迟约 0.1-0.5ms（机械硬盘约 5-10ms）
-- SSD 上值 = 1 的性能比机械硬盘高很多

-- 监控每次提交的 Redo Log 写入情况
SHOW STATUS LIKE 'Innodb_os_log_fsyncs';
-- 这个值每秒的增量 = 每秒 fsync 次数
-- 值 = 1 时：等于每秒提交次数
-- 值 = 2 时：约等于 1（每秒一次后台 fsync）
```

## 与 sync_binlog 的配合

```sql
-- MySQL 的持久性需要 Redo Log 和 Binlog 共同保证
-- 两个参数配合使用：

-- 最高安全配置（金融/核心业务）：
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;
-- 每次 COMMIT：Redo Log fsync + Binlog fsync
-- 两次 fsync，性能开销最大，数据最安全

-- 折中配置（一般互联网业务）：
SET GLOBAL innodb_flush_log_at_trx_commit = 2;
SET GLOBAL sync_binlog = 1000;
-- Redo Log 每秒 fsync，Binlog 每 1000 次提交 fsync
-- 性能大幅提升，可能丢失最多 1 秒事务（OS 崩溃时）

-- 最高性能配置（从库/测试环境，允许数据丢失）：
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
SET GLOBAL sync_binlog = 0;
-- 不做额外 fsync，性能最高，安全性最低
```

## 组提交（Group Commit）对值=1 的优化

```sql
-- Group Commit（组提交）：
-- MySQL 5.7+ 的 Binlog Group Commit 和 InnoDB Redo Log Group Commit
-- 多个并发事务同时到达 COMMIT 时：
-- → 不是每个事务单独 fsync
-- → 而是将一批事务的 Redo Log 批量 fsync（一次 fsync 完成多个事务）
-- → 大幅减少 fsync 次数，在 innodb_flush_log_at_trx_commit = 1 时也能有较好的吞吐

-- 控制组提交延迟（等待更多事务加入组）
SHOW VARIABLES LIKE 'binlog_group_commit%';
-- binlog_group_commit_sync_delay：等待更多事务加入的延迟（微秒，默认 0）
-- binlog_group_commit_sync_no_delay_count：不等待的最小组大小（默认 0）

-- 设置延迟（增加组大小，减少 fsync 次数，但增加单事务延迟）
SET GLOBAL binlog_group_commit_sync_delay = 1000;  -- 1 毫秒
-- 适用于：写入量大的场景，1ms 内通常有多个事务等待提交
```

## 不同场景的推荐配置

| 场景 | innodb_flush_log_at_trx_commit | sync_binlog | 说明 |
|------|-------------------------------|-------------|------|
| 金融/支付（最高安全）| 1 | 1 | ACID 完全满足，性能最低 |
| 互联网主库 | 1 | 1 | 标准生产配置，SSD 影响较小 |
| 从库（延迟容忍）| 2 | 1000 | 从库有主库保证，可适当降低 |
| 测试/开发环境 | 0 | 0 | 最高性能，数据丢失可接受 |
| 数据仓库（大批量 ETL）| 2 | 0 | 写入量大，每秒刷盘足够 |

---

## 适用场景

- **生产主库**：保持默认值 1，确保不丢失任何已提交事务
- **读写分离从库**：可设置为 2，主库保障数据安全，从库追求更高回放速度
- **写密集型系统**：通过 Group Commit（调整 `binlog_group_commit_sync_delay`）在保持值=1的同时提升吞吐量

---

## 常见问题

**设置为 2 时，MySQL 进程崩溃不丢数据，如何理解？**

当 `innodb_flush_log_at_trx_commit = 2` 时，COMMIT 时 Redo Log 写入 OS 的 Page Cache（内核缓冲区），未调用 fsync。OS Page Cache 是由操作系统内核管理的，不属于 MySQL 进程的内存。当 MySQL 进程崩溃（如 OOM Kill、段错误）时，OS Page Cache 中的数据不会丢失（内核仍在运行）。操作系统后台会定期将 Page Cache 刷到磁盘，每秒还有 InnoDB 后台线程调用 fsync 刷盘。只有操作系统本身崩溃（内核 panic）或断电，Page Cache 才会丢失。

---

## 注意事项

- `innodb_flush_log_at_trx_commit` 的修改对已有连接立即生效（动态参数），但要记得同步修改 `my.cnf` 确保重启后不回退到旧值。
- 在使用了半同步复制（semi-sync replication）的集群中，从库的 Redo Log 刷盘设置对整体持久性的影响有限，因为事务提交需要至少一个从库确认接收 Binlog 后才返回。这种情况下从库可以使用值 = 2 以提高回放速度。

---

## 总结

`innodb_flush_log_at_trx_commit` 控制 Redo Log 的刷盘时机：值为 1（默认）每次 COMMIT 都 fsync，最安全满足完整 ACID；值为 2 COMMIT 只写 OS 缓冲，每秒后台 fsync，MySQL 崩溃不丢数据但 OS 崩溃可能丢 1 秒；值为 0 COMMIT 不做任何 I/O，每秒后台写入+fsync，最快但最不安全。生产主库使用值 = 1，配合 SSD 和 Group Commit 可以获得高性能；从库可以使用值 = 2。

# Checkpoint 检查点机制

Checkpoint（检查点）是 InnoDB 将 checkpoint_lsn 推进到更新位置的操作，本质上是告知系统："LSN <= checkpoint_lsn 的所有脏页已经刷盘，对应的 Redo Log 可以被循环覆盖。"Checkpoint 机制平衡了 Redo Log 的循环使用、数据页刷盘速度和崩溃恢复时间三者之间的关系，是 InnoDB 持续运行的重要保障。

---

## Checkpoint 的作用

```
Checkpoint 解决的两个核心问题：

问题1：Redo Log 是循环写的，空间有限
  → Checkpoint 推进后，旧的 Redo Log 空间可以复用
  → 没有 Checkpoint，Redo Log 写满后数据库停止写入

问题2：崩溃恢复时间
  → 崩溃恢复需要从上次 Checkpoint 重放到最新 LSN
  → Checkpoint 越新，需要重放的 Redo Log 越少，恢复越快
  → 不做 Checkpoint，每次恢复都要重放全部历史 Redo Log
```

---

## Checkpoint 的触发机制

```sql
-- InnoDB 有两种 Checkpoint：

-- Sharp Checkpoint（完全检查点）：
--   MySQL 正常关闭时触发（innodb_fast_shutdown = 0 或 1）
--   将 Buffer Pool 中所有脏页全部刷盘
--   然后设置 checkpoint_lsn = current_lsn
--   重启时无需重放任何 Redo Log（干净关闭）

-- Fuzzy Checkpoint（模糊检查点）：
--   MySQL 运行时持续进行的后台 Checkpoint（不停止服务）
--   只将部分脏页刷盘，checkpoint_lsn 推进到安全位置
--   有多种触发方式（见下）

-- Fuzzy Checkpoint 的触发场景：
-- 1. Master Thread Checkpoint：InnoDB 主线程每秒/每 10 秒触发
-- 2. Flush LRU List Checkpoint：LRU 尾部脏页需要腾出空间时
-- 3. Async Flush Checkpoint：Redo Log 使用率超过阈值时（75% 触发异步刷盘）
-- 4. Dirty Page too much Checkpoint：脏页比例超过 innodb_max_dirty_pages_pct 时
```

---

## Checkpoint 的推进过程

```
Fuzzy Checkpoint 推进步骤：

1. InnoDB 确定安全的刷盘范围
   → 取 Flush List 尾部的最小 oldest_modification_lsn = target_lsn
   
2. 触发 Page Cleaner 将 Flush List 中 LSN <= target_lsn 的脏页刷盘

3. 等待刷盘完成后，更新 checkpoint_lsn = target_lsn

4. 将新的 checkpoint_lsn 写入 Redo Log 文件的特定位置（checkpoint 记录）

5. Redo Log 中 LSN <= checkpoint_lsn 的部分可以被新数据覆盖

Checkpoint 写入位置：
  MySQL 8.0.30 之前：写入 ib_logfile0 的文件头（固定位置）
  MySQL 8.0.30+：写入动态 Redo Log 文件的特定区域
```

## 监控 Checkpoint 状态

```sql
-- 查看 Checkpoint 相关信息
SHOW ENGINE INNODB STATUS \G
-- LOG 部分：
-- Log sequence number  17321684936    (write_lsn)
-- Log flushed up to   17321684936    (flushed_lsn)
-- Pages flushed up to 17321678432    (刷盘数据页的 LSN 进度)
-- Last checkpoint at  17321678432    (checkpoint_lsn)

-- 关键指标：
-- Redo Log 使用率 = (write_lsn - checkpoint_lsn) / redo_log_capacity * 100%
-- = (17321684936 - 17321678432) / (100 * 1024 * 1024) * 100%
-- 使用率过高说明 Checkpoint 推进速度跟不上写入速度

-- 通过 performance_schema 监控
SELECT
    VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
    'Innodb_lsn_current',
    'Innodb_lsn_last_checkpoint',
    'Innodb_checkpoint_age',        -- write_lsn - checkpoint_lsn
    'Innodb_checkpoint_max_age'     -- Redo Log 容量（触发强制 Checkpoint 的阈值）
);

-- 计算 Checkpoint 压力比例
-- Innodb_checkpoint_age / Innodb_checkpoint_max_age * 100%
-- > 75%：触发异步强制刷盘
-- > 90%：数据库写入开始停滞
```

## Checkpoint 与崩溃恢复时间

```
崩溃恢复时间 ∝ (write_lsn - checkpoint_lsn) / 重放速度

影响因素：
1. write_lsn - checkpoint_lsn：未 Checkpoint 的 Redo Log 大小
   → 这取决于：Redo Log 总大小、脏页刷盘速度、写入量
   → 通常是 Redo Log 总容量的 0-80%

2. 重放速度：
   → 单线程 Redo Log 重放（传统方式）：受磁盘读取速度限制
   → MySQL 8.0+ 并行 Redo Log 重放：多线程并行重放，速度更快

实践数据（参考）：
  Redo Log 4GB + 脏页 20GB：崩溃恢复约 2-5 分钟（SSD）
  Redo Log 4GB + 脏页 20GB：崩溃恢复约 10-30 分钟（HDD）

控制崩溃恢复时间：
  → 减小 innodb_redo_log_capacity（缩小恢复范围，但写入频率增加）
  → 增大 innodb_io_capacity 和 innodb_io_capacity_max（加快刷盘速度）
  → 使用 SSD（提升 Redo Log 重放速度）
```

## 参数调优

```sql
-- 与 Checkpoint 相关的关键参数：

-- 1. innodb_max_dirty_pages_pct（默认 90%）
--    脏页比例超过此值触发强制 Checkpoint + 加速刷盘
SET GLOBAL innodb_max_dirty_pages_pct = 75;  -- 更积极地触发 Checkpoint

-- 2. innodb_max_dirty_pages_pct_lwm（默认 10%）
--    低水位：脏页比例低于此值时降低刷盘速率
SET GLOBAL innodb_max_dirty_pages_pct_lwm = 10;

-- 3. innodb_io_capacity（默认 200）
--    InnoDB 后台 I/O 操作速率上限
--    影响 Checkpoint 的推进速度
SET GLOBAL innodb_io_capacity = 2000;  -- SSD 建议设置更高

-- 4. innodb_io_capacity_max（默认 2000）
--    紧急情况下的最大 I/O 速率（Redo Log 压力大时使用）
SET GLOBAL innodb_io_capacity_max = 4000;

-- 5. innodb_adaptive_flushing（默认 ON）
--    根据 Redo Log 使用率动态调整刷盘速率（影响 Checkpoint 推进速度）
```

## 适用场景

- **容量规划**：Checkpoint 推进速度必须跟上写入速度，否则 Redo Log 写满。通过监控 `Innodb_checkpoint_age / Innodb_checkpoint_max_age` 评估 Checkpoint 压力
- **性能问题排查**：数据库出现周期性写入停顿时，通常是 Checkpoint 压力引起的大批量强制刷盘，需要增大 Redo Log 容量或提升磁盘 I/O 能力

---

## 常见问题

**调大 Redo Log 容量后，Checkpoint 压力降低了，但崩溃恢复时间会增加吗？**

理论上会，但实际影响取决于脏页刷盘速度。更大的 Redo Log 允许更多脏页积压（checkpoint 推进更慢），但 Page Cleaner 的刷盘速率是相对稳定的。崩溃时 `write_lsn - checkpoint_lsn` 代表需要重放的量，这个值不一定因为 Redo Log 变大而增大（因为 Page Cleaner 还在持续刷盘）。通常调大 Redo Log 后崩溃恢复时间的增加是可接受的。

---

## 注意事项

- 如果 MySQL 使用 `innodb_fast_shutdown = 2`（非常快速关闭，不刷脏页不写 Checkpoint）关闭，则下次启动时需要完整的崩溃恢复（从最后一个 Sharp Checkpoint 重放所有 Redo Log），启动时间会很长。正常关闭建议使用 `innodb_fast_shutdown = 1`（默认，刷 Buffer Pool 脏页）。
- 手动执行 `SET GLOBAL innodb_buffer_pool_dump_now = ON` 之后，紧接着做计划停机时，可以先执行完整刷盘：`SET GLOBAL innodb_max_dirty_pages_pct = 0`，等待脏页降为 0，再正常关闭，这样重启后的 Checkpoint 位置更新，恢复更快。

---

## 总结

Checkpoint 通过推进 checkpoint_lsn 使旧 Redo Log 空间可以被循环复用，同时控制崩溃恢复时需要重放的 Redo Log 范围。运行中使用 Fuzzy Checkpoint（不停服务，持续小批量刷盘），关闭时使用 Sharp Checkpoint（全部刷盘）。监控指标：`Innodb_checkpoint_age / Innodb_checkpoint_max_age`，接近 75% 时触发异步强制刷盘，接近 100% 时写入停滞。通过增大 Redo Log 容量（`innodb_redo_log_capacity`）和提升刷盘速率（`innodb_io_capacity`）降低 Checkpoint 压力。

# Redo Log 文件组与循环写入

Redo Log 由一组文件构成（文件组），InnoDB 以循环方式写入这些文件：写满最后一个文件后，回到第一个文件重新开始覆盖写入。循环写入意味着旧的 Redo Log 记录会被覆盖，因此必须确保被覆盖的 Redo Log 对应的脏数据页已经刷盘（Checkpoint 机制保证这一点），否则那些 Redo Log 永远不能被覆盖，Redo Log 空间耗尽会导致数据库无法写入。

---

## Redo Log 文件组的历史演变

```
MySQL 8.0.30 之前：固定文件方式

[mysqld]
innodb_log_files_in_group = 2   # 文件数量（默认 2）
innodb_log_file_size = 50M      # 每个文件大小（默认 50MB）
# 总容量 = 2 × 50MB = 100MB

文件：
  datadir/ib_logfile0  （50MB）
  datadir/ib_logfile1  （50MB）

写入顺序：
  ib_logfile0 → ib_logfile1 → ib_logfile0（循环）

MySQL 8.0.30+：动态文件方式

innodb_redo_log_capacity = 100M  # 总容量（向后兼容旧默认值）
# 文件数量由 InnoDB 自动管理（默认 32 个小文件）

文件：
  datadir/#ib_redo0
  datadir/#ib_redo1
  ...
  datadir/#ib_redo31

优点：
  文件大小更小（便于管理和垃圾回收）
  总容量可在线动态调整
  更好地利用并行 I/O
```

## 循环写入的工作机制

```
Redo Log 文件组循环写入示意：

┌────────────────────────────────────────────────────────────────────┐
│  Redo Log 文件组（总容量 N GB）                                      │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────────┐ │
│  │  可以被覆盖区域  │  不可覆盖区域（已提交但脏页未刷盘）        │ │
│  │  (checkpoint 前) │  (checkpoint 后的未处理 Redo Log)          │ │
│  └─────────────────────┬──────────────────────────┬─────────────┘ │
│                         ↑                          ↑              │
│                   checkpoint_lsn              write_lsn           │
│                   （已完成刷盘）            （当前写入位置）       │
└────────────────────────────────────────────────────────────────────┘

可用空间 = 总容量 - (write_lsn - checkpoint_lsn)
```

## 查看 Redo Log 使用情况

```sql
-- 查看 Redo Log 容量配置
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
-- MySQL 8.0.30+，默认 100MB

-- 查看 Redo Log 当前状态（LSN 信息）
SHOW ENGINE INNODB STATUS \G
-- 在 LOG 部分寻找：
-- Log sequence number  17321684936    ← 当前最新 LSN（write_lsn）
-- Log flushed up to   17321684936    ← 已刷到磁盘的 LSN
-- Pages flushed up to 17321678432    ← 数据页已刷盘的 LSN
-- Last checkpoint at  17321678432    ← 上次 Checkpoint 的 LSN

-- 计算已使用的 Redo Log 空间：
-- used_redo_log = write_lsn - checkpoint_lsn
-- = 17321684936 - 17321678432 = 6504 字节（非常少）

-- 通过 performance_schema 查看 Redo Log 使用率
SELECT * FROM performance_schema.innodb_redo_log_files;
-- MySQL 8.0.30+：查看各个 Redo Log 文件的状态
-- 或通过 information_schema 查看
SELECT * FROM information_schema.INNODB_METRICS
WHERE SUBSYSTEM = 'recovery'
ORDER BY NAME;
```

## Redo Log 写满的后果

```sql
-- 当 write_lsn 追上 checkpoint_lsn + 总容量 时，Redo Log 空间耗尽
-- 此时 InnoDB 无法写入新的 Redo Log
-- → 所有写操作（INSERT/UPDATE/DELETE）被阻塞
-- → 等待 Checkpoint 推进（即等待脏页刷盘）
-- → 严重时整个数据库的写入被 hang 住

-- 触发 Redo Log 写满的原因：
-- 1. innodb_redo_log_capacity 配置太小
-- 2. 写入速度 > 脏页刷盘速度（Page Cleaner 速度不够）
-- 3. 大量大事务积压了大量 Redo Log 而未提交

-- 发现 Redo Log 写满告警：
-- MySQL 错误日志中会出现：
-- [Warning] InnoDB: Over 90% of the redo log has been consumed.
-- [Warning] InnoDB: Over 95% of the redo log has been consumed.
-- 这是严重警告，需要立即关注

-- 快速临时解决：增大 innodb_redo_log_capacity（MySQL 8.0.30+，可动态调整）
SET GLOBAL innodb_redo_log_capacity = 2 * 1024 * 1024 * 1024;  -- 2GB
-- 或修改 my.cnf 后重启（更推荐，确保持久化）
```

## 推荐的 Redo Log 大小配置

```ini
# my.cnf 配置示例

# MySQL 8.0.30+（推荐方式）
[mysqld]
innodb_redo_log_capacity = 4G   # 推荐生产环境

# MySQL 8.0.30 之前（旧方式）
[mysqld]
innodb_log_file_size = 1G       # 每个文件 1GB
innodb_log_files_in_group = 4   # 4 个文件，总 4GB
# 注意：修改后需要正常关闭 MySQL，删除旧 ib_logfile0/1，再启动

# Redo Log 大小选择原则：
# 场景1：写入量大（如电商高峰期每秒几万次写入）
#   → 4-8 GB
# 场景2：中等写入量
#   → 2-4 GB  
# 场景3：读多写少
#   → 1-2 GB（默认 100MB 严重不足！）
# 原则：Redo Log 应能容纳 1-2 小时的写入量
#       通过 Innodb_os_log_written 估算每小时写入量
```

## Redo Log 大小变更操作

```sql
-- MySQL 8.0.30+：动态调整（无需停机）
SET GLOBAL innodb_redo_log_capacity = 4 * 1024 * 1024 * 1024;
-- InnoDB 在后台创建新的 Redo Log 文件并平滑切换
-- 查看调整进度：
SELECT * FROM performance_schema.innodb_redo_log_files;

-- MySQL 8.0.30 之前：需要停机操作
-- 1. 正常关闭 MySQL（不能强制 kill）
--    SET GLOBAL innodb_fast_shutdown = 0;  -- 确保完整关闭
--    mysqladmin -u root -p shutdown
-- 2. 修改 my.cnf
--    innodb_log_file_size = 1G
--    innodb_log_files_in_group = 4
-- 3. 删除旧文件（或 InnoDB 重新创建后自动处理）
-- 4. 启动 MySQL，InnoDB 自动创建新大小的 Redo Log 文件
```

## 适用场景

- **性能调优**：Redo Log 太小是常见的性能问题，写密集型应用 `innodb_redo_log_capacity` 应至少设置 2GB，推荐 4-8GB
- **容量规划**：通过 `Innodb_os_log_written` 采样 1 小时，计算每小时 Redo Log 写入量，据此配置合理的 Redo Log 总容量

---

## 常见问题

**如何估算合适的 Redo Log 大小？**

在当前配置下运行 1 小时，查询 `Innodb_os_log_written` 的增量，这就是 1 小时的 Redo Log 写入量。Redo Log 总容量应设置为这个值的 1-2 倍，以确保有足够的空间缓冲脏页刷盘的延迟，同时避免过大导致崩溃恢复时间过长（因为需要重放更多 Redo Log）。

---

## 注意事项

- 增大 Redo Log 大小会增加崩溃恢复时间，因为 InnoDB 需要重放的 Redo Log 更多。通常这是可以接受的权衡（崩溃恢复是小概率事件，生产性能才是日常关注点）。实测中，8GB Redo Log 的崩溃恢复时间通常在 1-5 分钟以内（取决于机器性能）。
- 在 MySQL 8.0.30 之前修改 Redo Log 大小，务必使用 `SET GLOBAL innodb_fast_shutdown = 0` 确保完整关闭（缓慢关闭），让 InnoDB 将所有脏页刷盘后再退出，避免残留脏页在重启时因旧的 Redo Log 文件已被删除而无法恢复。

---

## 总结

Redo Log 文件组采用循环写入机制，write_lsn 追赶 checkpoint_lsn，可用空间 = 总容量 - (write_lsn - checkpoint_lsn)。MySQL 8.0.30+ 使用动态文件（`#ib_redo*`）通过 `innodb_redo_log_capacity` 控制总容量，支持在线调整。生产环境推荐 4-8GB（默认 100MB 严重不足）。Redo Log 写满时所有写操作被阻塞，需立即扩容或检查脏页刷盘是否正常。

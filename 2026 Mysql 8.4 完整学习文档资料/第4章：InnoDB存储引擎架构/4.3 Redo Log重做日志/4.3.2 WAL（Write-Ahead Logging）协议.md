# WAL（Write-Ahead Logging）协议

WAL（预写式日志）是数据库领域保证持久性和原子性的通用协议，其核心规则是：**在数据页写入磁盘之前，必须先将对应的 Redo Log 写入磁盘**。InnoDB 的 Redo Log 机制严格遵循 WAL 协议，这使得数据库在崩溃后能够通过重放日志恢复到一致状态，而不需要在每次写操作后都立即刷写数据页（这会产生大量随机 I/O）。

---

## WAL 的核心规则

```
WAL 规则（Write-Ahead Logging Principle）：

规则1：数据页刷盘之前，必须先将对应的 Redo Log 刷盘
        → 确保崩溃时能用 Redo Log 重放丢失的数据页修改

规则2：事务提交之前，必须将该事务的所有 Redo Log 刷盘
        → 确保提交的事务不会因崩溃而丢失（持久性 D）

违反 WAL 规则的后果：
→ 如果数据页刷盘了但对应的 Redo Log 还没刷盘，然后崩溃
→ 重启后：Redo Log 中没有记录，认为该页未被修改
→ 但磁盘上的数据页实际上已经被修改了
→ 数据不一致（实际上 InnoDB 不会出现此情况，因为严格遵循 WAL）
```

---

## InnoDB 中的 WAL 实现

```
事务提交时的完整流程（遵循 WAL）：

应用层发起 COMMIT
     ↓
步骤1：将 Redo Log Buffer 中该事务的所有 Redo Log 记录刷写到 Redo Log 文件
       （顺序写，非常快）
     ↓
步骤2：调用 fsync() 确保 Redo Log 已持久化到磁盘
     ↓
步骤3：返回给客户端"提交成功"
     ↓
步骤4（异步）：后台 Page Cleaner 将脏数据页刷写到 .ibd 数据文件
       （随机写，延迟执行，不阻塞提交）

关键：步骤1+2 必须在步骤3之前完成（WAL 规则2）
      步骤4 在步骤1+2 之后即可（WAL 规则1）
```

## WAL 带来的性能优势

```
对比两种极端策略：

策略A（每次修改立即刷盘数据页）：
  每次 INSERT/UPDATE/DELETE → 随机写磁盘
  16KB 数据页随机写：机械硬盘约 100 IOPS → 100 次写/秒
  SSD 约 10,000-100,000 IOPS → 10,000-100,000 次写/秒

策略B（WAL + 延迟数据页刷盘）：
  每次提交 → 顺序追加写 Redo Log（几十到几百字节）
  顺序写：机械硬盘约 100 MB/s → 远多于随机写
  数据页延迟批量刷盘（减少随机 I/O，增大 I/O 合并机会）

结论：
  WAL 将大量随机写（数据页）转换为顺序写（Redo Log）
  写性能提升可达 10-100 倍（取决于工作负载）
```

## WAL 与事务两阶段提交（2PC）

```
MySQL 的两阶段提交（确保 Redo Log 和 Binlog 的一致性）：

Prepare 阶段：
  1. InnoDB 将事务的 Redo Log 写入文件（prepare 状态）
  2. Redo Log 中标记该事务为 PREPARE

Commit 阶段：
  3. MySQL Server 将事务的 Binlog 写入 Binlog 文件
  4. Binlog fsync 刷盘
  5. InnoDB 将 Redo Log 中该事务标记为 COMMIT
  6. Redo Log fsync 刷盘（如果 innodb_flush_log_at_trx_commit=1）
  7. 返回客户端"提交成功"

崩溃场景分析：
  崩溃在步骤3之前：Redo Log 为 PREPARE，没有 Binlog → 回滚该事务
  崩溃在步骤4之后：Redo Log 为 PREPARE，有 Binlog → 提交该事务
  这样保证了 Redo Log 和 Binlog 的最终一致性
```

## WAL 的顺序写特性

```sql
-- 验证 Redo Log 是顺序写的
-- Redo Log Buffer 是内存中的环形缓冲区
-- 所有事务的 Redo Log 记录按时间顺序追加到 Buffer 末尾
-- 刷盘时，将 Buffer 中的内容追加写到当前 Redo Log 文件末尾
-- 不会寻址，不会随机写

-- 监控 Redo Log 写入情况
SHOW STATUS LIKE 'Innodb_os_log%';
-- Innodb_os_log_written：写入 Redo Log 的字节数（累计）
-- Innodb_os_log_fsyncs：Redo Log fsync 次数（累计）
-- Innodb_os_log_pending_fsyncs：等待 fsync 的数量
-- Innodb_os_log_pending_writes：等待写入的数量

-- 计算 Redo Log 写入速率（每秒）
-- 需要间隔采样两次 Innodb_os_log_written
SELECT VARIABLE_VALUE / 1024 / 1024 AS redo_log_written_MB
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Innodb_os_log_written';
```

## WAL 与故障恢复的保证

```
WAL 提供的故障恢复保证：

已提交事务（COMMIT 已返回给客户端）：
  → Redo Log 已刷盘（WAL 规则2）
  → 崩溃后重放 Redo Log，数据页恢复到提交状态
  → 保证持久性（D in ACID）

未提交事务（崩溃时事务还在进行中）：
  → Redo Log 可能部分写入
  → InnoDB 重播 Redo Log 到最后一个完整的 COMMIT 记录
  → 没有完整 COMMIT 记录的事务通过 Undo Log 回滚
  → 保证原子性（A in ACID）

数据页部分写（Torn Page）：
  → Doublewrite Buffer 处理（不是 WAL 负责的范围）
```

## 适用场景

- **理解 InnoDB 写路径**：所有写操作的性能分析都离不开 WAL，理解 WAL 有助于分析 `innodb_flush_log_at_trx_commit` 对性能和安全性的影响
- **高并发写入优化**：WAL 是 InnoDB 支持高并发写入的基础，优化 Redo Log 的 I/O 路径（如使用 SSD、独立磁盘）能显著提升写入吞吐量

## 常见问题

**WAL 中 Redo Log 刷盘是随机写还是顺序写？**

顺序写。Redo Log 文件是循环使用的，所有写入都是追加到当前位置，下一次写接着上次的末尾。这是 WAL 相比直接刷数据页的核心性能优势。顺序写的 IOPS 开销远小于随机写，机械硬盘上顺序写吞吐可达 100-200 MB/s，而随机写通常只有 1-5 MB/s（100-200 IOPS × 16KB/页）。

---

## 注意事项

- WAL 的顺序写优势在机械硬盘（HDD）上最为明显，因为 HDD 的随机 I/O 和顺序 I/O 性能差距巨大。在 NVMe SSD 上，随机 I/O 和顺序 I/O 的差距较小，但顺序写仍然优于随机写（特别是在高并发时减少 I/O 冲突）。
- `innodb_flush_log_at_trx_commit` 参数控制 Redo Log 的刷盘时机，是 WAL 协议实现中的关键配置点，值为 1 时严格遵守 WAL（最高安全性），值为 0 或 2 时有不同程度的松弛（更高性能但存在丢数据风险）。详见 4.3.7。

---

## 总结

WAL（预写式日志）是 InnoDB 持久性的基础协议：提交前必须先将 Redo Log 刷盘，数据页可以延迟刷盘。这将大量随机写（数据页）转换为顺序写（Redo Log），大幅提升写入吞吐量。两阶段提交（2PC）扩展了 WAL 确保 Redo Log 和 Binlog 的一致性。崩溃恢复时，通过重放 Redo Log（已提交事务）+ 回滚 Undo Log（未提交事务）恢复到崩溃前的一致状态。

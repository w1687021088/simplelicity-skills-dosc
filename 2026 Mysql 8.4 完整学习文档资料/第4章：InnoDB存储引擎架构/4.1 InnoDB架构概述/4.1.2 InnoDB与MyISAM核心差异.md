# InnoDB 与 MyISAM 核心差异

InnoDB 和 MyISAM 是 MySQL 历史上使用最广泛的两种存储引擎。MySQL 5.5 起将默认引擎从 MyISAM 切换为 InnoDB。两者在事务支持、锁粒度、崩溃恢复、并发性能等方面存在本质差异，理解这些差异有助于在混合场景下做出合理的引擎选择。

---

## 核心差异对比

| 对比维度 | InnoDB | MyISAM |
|---------|--------|--------|
| 事务支持 | 完整 ACID 事务 | 不支持事务 |
| 锁粒度 | 行级锁（Record Lock / Gap Lock）| 表级锁（全表加锁）|
| 外键约束 | 支持（FOREIGN KEY）| 不支持（解析后忽略）|
| MVCC | 支持（Read View + Undo Log）| 不支持 |
| 崩溃恢复 | Redo Log 自动恢复 | 需手动 `REPAIR TABLE` |
| 全文索引 | 支持（MySQL 5.6+）| 支持 |
| 数据存储 | 聚簇索引，数据与主键索引合并 | 堆表，数据文件与索引文件分离 |
| 磁盘文件 | `.ibd`（表空间文件）| `.MYD`（数据）+ `.MYI`（索引）|
| COUNT(*) | 全表扫描（无精确计数缓存）| 直接从元数据读取（有精确计数）|
| 索引结构 | B+ Tree（聚簇 + 二级索引）| B+ Tree（索引存储行指针）|
| 并发写入 | 行锁支持高并发写 | 表锁，写操作串行 |
| 内存占用 | 需要 Buffer Pool 内存 | 占用内存相对较少 |

## 数据文件结构差异

```sql
-- InnoDB 文件（innodb_file_per_table=ON，8.0+ 默认）
-- datadir/myapp/orders.ibd   → 表数据 + 索引（一个文件包含所有）

-- MyISAM 文件（每张表 3 个文件）
-- datadir/myapp/orders.MYD   → 实际数据行
-- datadir/myapp/orders.MYI   → 索引文件
-- datadir/myapp/orders.sdi   → 表结构（8.0+）

-- 查看表的数据文件大小
SELECT TABLE_NAME, ENGINE,
    DATA_LENGTH / 1024 / 1024     AS data_MB,
    INDEX_LENGTH / 1024 / 1024    AS index_MB,
    DATA_FREE / 1024 / 1024       AS free_MB
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp';
```

## 聚簇索引 vs 堆表

```sql
-- InnoDB：聚簇索引（Clustered Index）
-- 表数据按主键顺序存储在 B+ Tree 的叶子节点
-- 主键查询不需要"回表"，因为数据就在索引叶子节点
CREATE TABLE t_innodb (
    id   INT PRIMARY KEY,
    name VARCHAR(50),
    age  INT
) ENGINE = InnoDB;
-- 数据存储：叶子节点 = [id | name | age]（按主键排列）

-- MyISAM：堆表（Heap Table）
-- 数据行按插入顺序存储在 .MYD 文件
-- 索引的叶子节点存储的是数据行的文件偏移量（行指针）
CREATE TABLE t_myisam (
    id   INT PRIMARY KEY,
    name VARCHAR(50),
    age  INT
) ENGINE = MyISAM;
-- 索引叶子节点 = [id | file_offset]
-- 查找数据需要 2 步：①读索引获取偏移量 ②根据偏移量读数据文件

-- InnoDB 二级索引的查找过程（回表）：
-- SELECT * FROM t_innodb WHERE name = 'alice';
-- ① 在 name 索引 B+ Tree 中找到叶子节点，获得主键 id=5
-- ② 用 id=5 在主键索引中查找完整行数据（这就是"回表"）
```

## 事务与崩溃恢复差异

```sql
-- InnoDB：完整事务支持
START TRANSACTION;
INSERT INTO orders VALUES (1, 100.00, NOW());
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 1;
COMMIT;  -- 两个操作原子提交

-- MyISAM：不支持事务
INSERT INTO myisam_table VALUES (1, 'data');  -- 每条语句自动提交
-- 无法 ROLLBACK，也没有 Undo Log

-- 崩溃恢复演示：
-- InnoDB：MySQL 重启后自动检查 Redo Log
--   未提交事务 → 自动回滚（应用 Undo Log）
--   已提交但未刷盘 → 自动重放（应用 Redo Log）
-- MyISAM：崩溃后数据可能损坏，需手动修复
-- REPAIR TABLE myisam_table;
-- CHECK TABLE myisam_table;
```

## COUNT(*) 性能差异

```sql
-- MyISAM：COUNT(*) 无 WHERE 条件时直接从 .MYI 文件头读取行数，O(1)
SELECT COUNT(*) FROM myisam_large_table;  -- 瞬间返回

-- InnoDB：COUNT(*) 没有精确缓存，需要扫描（但 8.0 有优化）
-- 原因：MVCC 机制下不同事务看到的行数不同，无法缓存全局精确值
SELECT COUNT(*) FROM innodb_large_table;  -- 需要扫描索引

-- InnoDB COUNT(*) 优化建议：
-- 1. MySQL 优化器会选择最小的二级索引扫描（而非聚簇索引）
-- 2. 如果业务需要频繁统计总行数，可以维护一个计数器表
CREATE TABLE stats (
    table_name VARCHAR(64) PRIMARY KEY,
    row_count  BIGINT DEFAULT 0
);
-- 触发器维护 or 应用层维护 row_count
```

## 锁机制差异的影响

```sql
-- MyISAM：写操作加表锁，所有读操作在写期间等待
-- 场景：多个 SELECT 正在执行时，一个 UPDATE 需要等全部读完才能执行
-- 或：UPDATE 执行时，所有 SELECT 都要等待

-- InnoDB：行锁，读写不互斥（MVCC 实现）
-- 场景：UPDATE 只锁定修改的行，其他行的 SELECT 和 INSERT 可以并发执行

-- 测试：两个会话并发执行
-- 会话 1：UPDATE myisam_table SET val = 1;  → 加表锁
-- 会话 2：SELECT * FROM myisam_table;       → 被阻塞（等表锁释放）

-- 会话 1：UPDATE innodb_table SET val = 1 WHERE id = 5;  → 锁 id=5 行
-- 会话 2：SELECT * FROM innodb_table WHERE id = 6;        → 不阻塞（不同行）
```

## 适用场景

- **InnoDB**：所有需要数据安全的业务场景（电商、金融、用户系统等），崩溃后自动恢复，并发写入性能优秀
- **MyISAM**：存量旧系统的历史遗留表，或纯只读的统计表（利用 COUNT(*) 优化），生产新系统不建议使用

## 常见问题

**已有 MyISAM 表，需要迁移到 InnoDB，有什么注意事项？**

执行 `ALTER TABLE tbl ENGINE=InnoDB` 会重建整张表，并在原表上持有 MDL 锁（期间读操作不阻塞，写操作阻塞）。迁移前需注意：迁移后 `COUNT(*)` 性能会有所下降（原先 O(1)，迁移后需扫描），需要评估影响并考虑应用层的计数缓存；如果表中有全文索引，需要确认 InnoDB 全文索引的语法和 MyISAM 一致；磁盘空间约需要原表的 2 倍（重建过程中新旧两份数据同时存在）。

---

## 注意事项

- 从 MySQL 8.0 起，`mysql` 系统数据库中的系统表（如 `mysql.user`）已全部迁移到 InnoDB，不再使用 MyISAM。这意味着系统表也享有事务保护和崩溃自动恢复。
- MyISAM 在 MySQL 8.0+ 版本中仍然可用，但官方已不再积极开发新特性，长期来看可能被进一步边缘化。新项目不要使用 MyISAM。

---

## 总结

InnoDB 与 MyISAM 的本质差异在于：InnoDB 支持事务（ACID）、行级锁（高并发）、MVCC（读写不阻塞）和自动崩溃恢复（Redo Log）；MyISAM 使用表级锁（并发差）、无事务支持、崩溃后需手动修复。InnoDB 使用聚簇索引（数据与主键索引合并存储），MyISAM 使用堆表（数据和索引分离）。MySQL 5.5 起默认 InnoDB，生产环境新表应全部使用 InnoDB。

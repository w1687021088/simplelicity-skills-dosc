# 记录锁 Record Lock 结构

Record Lock（记录锁）是 InnoDB 行级锁的基础形式，锁定索引记录上的单个键值。在内存中，每个 Record Lock 以一个 `lock_t` 结构体表示，结合一个位图（Bitmap）来标识同一页（Page）中哪些记录被锁定。理解 Record Lock 的内存结构有助于分析锁的粒度、锁内存消耗和锁冲突检测的实现原理。

---

## Record Lock 的内存结构

```
lock_t 结构体（记录锁部分）：

通用字段（lock_t 基础部分）：
  trx：指向所属事务（trx_t *）
  type_mode：锁类型和模式的位字段组合
    bit 0-7：锁模式（LOCK_IS / LOCK_IX / LOCK_S / LOCK_X 等）
    bit 8-11：锁类型标志
    LOCK_TABLE (32)：表级锁
    LOCK_REC   (32) = LOCK_REC 位：行级锁
    LOCK_WAIT  (256)：等待锁（未获得）
    LOCK_GAP   (512)：间隙锁（不锁记录本身，锁间隙）
    LOCK_REC_NOT_GAP (1024)：纯记录锁（不含间隙）
    LOCK_INSERT_INTENTION (2048)：插入意向锁
  hash：在哈希表中的链表指针
  trx_locks：在事务锁链表中的链表指针

记录锁专用字段（un_member.rec_lock）：
  space：锁所在的表空间 ID（space_id）
  page_no：锁所在的页号（page_no）
  n_bits：位图的 bit 数量（= 页内堆序号上限 + 64，留有余量）
  位图：跟在 lock_t 结构体之后的字节数组
    每个 bit 对应页内一个 heap_no（堆序号）
    bit = 1：对应 heap_no 的记录被此锁锁定
    bit = 0：对应记录未被此锁锁定
```

---

## 位图的使用方式

```
一个页内最多有几百条记录，每条记录有唯一的 heap_no（0=Infimum, 1=Supremum, 2-N=用户记录）

举例：
  一个事务 UPDATE orders WHERE dept_id = 5
  假设 dept_id=5 的记录分布在两个页中：
    Page 100：heap_no 5, 12, 23（3条记录）
    Page 101：heap_no 7, 15（2条记录）

  InnoDB 创建的锁对象：
    lock1：space=X, page=100, 位图中 bit5=1, bit12=1, bit23=1
    lock2：space=X, page=101, 位图中 bit7=1, bit15=1

  共 2 个 lock_t 对象（不是 5 个！）
  → 同一页内的多条锁记录合并到一个 lock_t 的位图中
  → lock_t 数量 = 事务跨越的页数，而非锁定的行数

位图的内存大小：
  n_bits = ((max_heap_no >> 3) + 1) 字节 ≈ 几十字节（一页几百条记录）
  整个 lock_t 大小 ≈ 结构体（~80字节）+ 位图（~50字节）= 约 130 字节
```

## 不同类型的记录锁模式

```sql
-- 记录锁的几种模式（type_mode 中的标志位组合）：

-- 1. 纯记录锁（Record Lock，不含间隙）
--    LOCK_X | LOCK_REC_NOT_GAP
--    锁定具体的索引键值，不锁键值前的间隙
--    在 RC（READ COMMITTED）隔离级别下的 DML 产生此类锁
--    SELECT * FROM orders WHERE id = 100 FOR UPDATE;
--    → 在 RC 级别：只锁 id=100 的记录，不锁间隙

-- 2. 间隙锁（Gap Lock）
--    LOCK_X | LOCK_GAP
--    只锁键值前的间隙，不锁记录本身
--    防止其他事务在此间隙插入新记录（防止幻读）
--    在 RR 级别下，DELETE/UPDATE 删除不存在的键时产生

-- 3. 临键锁（Next-Key Lock）
--    LOCK_X（无 LOCK_GAP 也无 LOCK_REC_NOT_GAP）
--    = 记录锁 + 间隙锁（锁记录本身 + 记录前的间隙）
--    RR 级别下 DML 的默认行锁类型

-- 查看锁模式（performance_schema）
SELECT
    ENGINE_TRANSACTION_ID,
    LOCK_MODE,  -- X, X,REC_NOT_GAP, X,GAP, S, S,REC_NOT_GAP 等
    LOCK_DATA   -- 锁定的记录主键值（或 supremum）
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = 'myapp' AND OBJECT_NAME = 'orders';
-- LOCK_MODE 示例：
-- X,REC_NOT_GAP → 纯记录 X 锁
-- X,GAP         → 间隙 X 锁
-- X             → 临键锁（记录 + 间隙）
-- S             → 临键共享锁
```

## 记录锁的冲突检测

```
锁兼容性检查（lock_rec_has_to_wait）：

当事务 B 请求对 heap_no=5 的记录加 X 锁时：
1. 在 rec_hash 中找到该页的所有锁（lock_t 链表）
2. 遍历每个 lock_t，检查其位图的 bit5 是否为 1（该 heap_no 是否被锁）
3. 如果找到 bit5=1 的 lock_t：
   → 检查锁模式兼容性：
   → S 与 S：兼容（多个事务可同时持有 S 锁）
   → S 与 X：不兼容（需要等待）
   → X 与 任何锁：不兼容（需要等待）
4. 如果不兼容：事务 B 的 lock_t 加上 LOCK_WAIT 标志，加入等待队列
5. 当持有锁的事务释放时：唤醒等待队列中的下一个事务

Supremum 记录（heap_no=1）的特殊处理：
  LOCK_GAP | LOCK_X on Supremum = 锁定"最大记录之后的间隙"
  任何试图在此间隙插入的事务都会等待
```

## 适用场景

- **行锁内存估算**：理解 lock_t 对象与页的关系，可以估算大批量更新时的锁内存消耗（跨越的页数 × ~130 字节），防止内存溢出
- **锁模式分析**：通过 `LOCK_MODE` 字段（X、X,REC_NOT_GAP、X,GAP）判断具体的锁类型，从而分析锁冲突的根本原因

## 常见问题

**同一事务对同一行多次加锁会产生多个 lock_t 对象吗？**

不会。InnoDB 会进行锁升级（Lock Upgrading）：如果事务 A 已对 heap_no=5 的记录持有 S 锁，再请求 X 锁时，会升级为 X 锁（修改位图中的锁模式），不会创建第二个 lock_t 对象。锁合并的原则是"同一事务对同一页的锁合并到一个 lock_t"（通过位图）。只有来自不同事务的锁，或跨越不同页的锁，才会产生不同的 lock_t 对象。

---

## 注意事项

- 行锁（lock_t）在事务提交或回滚时统一释放，不是逐条 DML 语句后释放（除非显式使用 SAVEPOINT）。这意味着长事务会长期持有大量行锁，阻塞其他事务。设计应尽量缩短事务范围，减少持有时间。
- `LOCK_DATA` 字段显示的是锁定记录的主键值（或二级索引值）。如果显示 `supremum pseudo-record`，表示锁定的是 Supremum 虚拟记录（即该页最大记录之后的间隙）。

## 总结

Record Lock（记录锁）在内存中以 `lock_t` 结构体存储，包含锁模式（`type_mode`：X、S、LOCK_GAP、LOCK_REC_NOT_GAP 等）和一个位图（标记同页内哪些 heap_no 被锁定）。同一事务对同一页的多行锁合并到一个 `lock_t`（节省内存），不同页或不同事务的锁是独立的 `lock_t` 对象。锁冲突检测通过遍历 rec_hash 中同页的所有 `lock_t` 对象并检查位图实现。行锁粒度的三种类型（纯记录锁/间隙锁/临键锁）通过 `type_mode` 中的标志位组合区分，可通过 `performance_schema.data_locks.LOCK_MODE` 直接观察。

# 锁表 Lock Table

Lock Table（锁表）是 InnoDB 在内存中维护的全局锁管理结构，所有事务持有的锁信息都注册在这个结构中。与关系数据库中的"表"无关，这里的"锁表"是指一个内存中的哈希表（Hash Table），以"表 + 页 + 堆号"或"表 ID"为键，快速定位和查找特定行或表上的锁。InnoDB 通过锁表实现行锁的冲突检测、等待队列管理和死锁检测。

---

## 锁表的内存组织结构

```
InnoDB 锁系统（lock_sys）的内存结构：

全局锁系统（lock_sys_t）：
  ├── 行锁哈希表（hash_table_t *rec_hash）
  │    键：(space_id, page_no) 即"哪个表空间的哪一页"
  │    值：该页上的所有行锁（lock_t 链表）
  │    → 快速找到同一页上的所有行锁
  │
  ├── 谓词锁哈希表（hash_table_t *prdt_hash）
  │    用于 R-Tree（空间索引）的谓词锁
  │
  ├── 表锁链表（各表的 table_lock 链表）
  │    通过 dict_table_t（表对象）直接引用
  │
  └── 等待事务链表（wait_thrs）
       正在等待锁的事务队列

每个锁对象（lock_t）：
  ├── 所属事务指针（trx_t *trx）
  ├── 前后链表指针（用于同一页上锁的链表）
  ├── 锁类型（LOCK_TABLE / LOCK_REC）
  ├── 锁模式（S / X / IS / IX / AUTO_INC 等）
  ├── 等待标志（LOCK_WAIT：是否在等待中）
  └── 位图（用于行锁，标记该页中哪些行被锁定）
```

## 锁表的工作原理

```sql
-- 场景：事务 A 更新某行
-- UPDATE orders SET status = 'done' WHERE id = 1001;

-- InnoDB 加锁步骤：
-- 1. 找到 id=1001 的行所在页（假设 space=5, page=123）
-- 2. 在 rec_hash 中查找键 (5, 123) 对应的锁链表
-- 3. 遍历该链表，检查是否有与当前请求冲突的锁：
--    → 如果有 S 锁（共享锁），X 锁（排他锁）请求冲突 → 等待
--    → 如果有 X 锁，任何新锁请求都冲突 → 等待
--    → 如果没有冲突锁 → 创建新的 lock_t 加入链表
-- 4. 在事务对象（trx_t.lock_list）中记录新锁

-- 通过 performance_schema 查看当前持有的锁
SELECT
    ENGINE_TRANSACTION_ID,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    LOCK_TYPE,       -- RECORD（行锁）或 TABLE（表锁）
    LOCK_MODE,       -- X, S, X,REC_NOT_GAP, X,GAP 等
    LOCK_STATUS,     -- GRANTED（已获得）或 WAITING（等待中）
    LOCK_DATA        -- 锁定的记录值（主键值）
FROM performance_schema.data_locks
ORDER BY ENGINE_TRANSACTION_ID;

-- 查看锁等待情况
SELECT
    r.LOCK_ID AS waiting_lock,
    r.ENGINE_TRANSACTION_ID AS waiting_trx,
    b.ENGINE_TRANSACTION_ID AS blocking_trx,
    r.OBJECT_NAME AS table_name
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks r ON w.REQUESTING_ENGINE_LOCK_ID = r.ENGINE_LOCK_ID
JOIN performance_schema.data_locks b ON w.BLOCKING_ENGINE_LOCK_ID = b.ENGINE_LOCK_ID;
```

## 锁对象的内存占用

```sql
-- 每个行锁对象（lock_t）的内存大小：
-- 固定部分：约 64-96 字节（结构体本身）
-- 位图部分：ceil(heap_no / 8) 字节（记录页内哪些行被锁定）
-- 一个页最多几百条记录，位图最多几十字节

-- 一个事务持有 1000 个行锁（1000 个 lock_t 对象）：
-- 内存占用：1000 × 约 80 字节 = 约 80 KB

-- 注意：InnoDB 行锁是基于页的粒度组织的
-- 如果事务锁了同一页的多行，仍然只有一个 lock_t 对象（位图中标记多行）
-- 所以实际内存开销 = lock_t 数量 × 约 80 字节
--                  （lock_t 数量 = 事务跨越的不同页数，而非行数）

-- 查看锁系统内存使用（通过 INNODB_METRICS）
SELECT NAME, COUNT, STATUS
FROM information_schema.INNODB_METRICS
WHERE SUBSYSTEM = 'lock'
ORDER BY NAME;
-- lock_row_lock_current_waits：当前等待行锁的数量
-- lock_deadlocks：死锁发生次数（累计）
-- lock_row_lock_time：行锁等待总时间
```

## 锁的哈希表分片（MySQL 8.0 优化）

```sql
-- MySQL 8.0 之前：
-- 整个锁系统共用一把全局互斥锁（lock_sys->mutex）
-- 高并发时，锁系统本身成为瓶颈

-- MySQL 8.0.19+ 引入锁系统分片（Lock System Sharding）：
-- rec_hash 被分成多个分片（shard）
-- 每个分片有独立的互斥锁
-- 不同页上的锁操作可以并发进行（不同分片不争用）
-- 分片数量 = 系统 CPU 核数（动态调整）

-- 在 MySQL 8.4 中此优化已成熟：
-- 大幅减少高并发场景下锁系统的互斥锁争用
-- 特别有利于多个事务锁定不同表/不同行的场景

-- 查看锁系统互斥锁竞争情况
SELECT NAME, COUNT_STAR, SUM_TIMER_WAIT / 1e12 AS total_wait_sec
FROM performance_schema.mutex_instances
WHERE NAME LIKE '%lock_sys%'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

## 适用场景

- **高并发锁冲突分析**：当系统出现大量锁等待时，通过 `performance_schema.data_locks` 和 `data_lock_waits` 分析锁表中的冲突情况，找到热点行（被大量事务争用的记录）
- **锁内存压力评估**：当事务持有大量行锁（如批量 UPDATE 锁了几十万行）时，通过 `INNODB_METRICS` 中的锁相关指标评估锁内存使用，防止内存溢出

## 常见问题

**什么情况下一个事务会产生大量 lock_t 对象（而不是位图合并）？**

当事务锁定的行分散在多个不同的页上时，每个页对应一个 `lock_t` 对象。例如，一个事务 UPDATE 了 10000 行，这些行分布在 500 个不同的数据页上，则会创建 500 个 `lock_t` 对象（每个页一个）。每个 `lock_t` 的位图标记该页内哪些行被锁。如果这 10000 行都在同一个页上（不可能，因为一页存不下），则只有 1 个 `lock_t` 对象。因此，行锁内存开销与跨越的页数相关，而非行数。

## 注意事项

- `information_schema.INNODB_LOCKS` 和 `INNODB_LOCK_WAITS` 在 MySQL 8.0 中已被废弃，改用 `performance_schema.data_locks` 和 `data_lock_waits`。新代码应使用 performance_schema 视图，功能更完整且性能更好。
- 锁表（rec_hash）在内存中，不持久化到磁盘。MySQL 重启后所有锁清除（未提交的事务回滚，锁随之释放）。因此查看锁表信息只对当前运行实例有意义。

## 总结

Lock Table（锁表）是 InnoDB 锁系统（`lock_sys_t`）中的核心内存哈希结构，以 `(space_id, page_no)` 为键，存储该页上所有行锁（`lock_t`）对象的链表，支持快速锁冲突检测。每个 `lock_t` 包含锁类型、模式、等待标志和行位图（标记同页内哪些行被锁）。MySQL 8.0.19+ 引入锁系统分片，大幅减少高并发时的互斥锁争用。通过 `performance_schema.data_locks` 和 `data_lock_waits` 查看当前锁状态，替代已废弃的 `information_schema.INNODB_LOCKS`。

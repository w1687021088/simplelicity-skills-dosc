# 事务对象 Transaction Object

Transaction Object（事务对象）是 InnoDB 在内存中为每个活跃事务维护的核心数据结构，用 C++ 的 `trx_t` 结构体表示。当一个客户端连接执行 `BEGIN`、`START TRANSACTION` 或第一条 DML 语句时，InnoDB 创建一个事务对象，分配唯一的事务 ID（`trx_id`），并维护该事务的所有状态信息，直到事务提交或回滚后被清理。理解事务对象的内容有助于掌握 InnoDB 如何跟踪事务状态、管理锁和生成 Undo Log。

---

## 事务对象的主要字段

```
trx_t 结构体（内存中，活跃事务期间存在）的关键字段：

事务标识：
  trx_id：事务 ID，全局唯一递增整数，是 MVCC 的核心标识
           只读事务（纯 SELECT）在 MySQL 8.0+ 中不立即分配 trx_id
           只有执行 DML 时才分配（延迟分配优化）

  trx_state：事务当前状态
    TRX_STATE_NOT_STARTED：未开始
    TRX_STATE_ACTIVE：活跃（已执行 DML，未提交/回滚）
    TRX_STATE_PREPARED：2PC 第一阶段完成（等待 COMMIT）
    TRX_STATE_COMMITTED_IN_MEMORY：已提交（清理中）

日志信息：
  undo_no：该事务已生成的 Undo Log 记录序号（递增）
  rsegs：分配给该事务的回滚段（Rollback Segment）引用
  undo_state：Undo 段状态（ACTIVE / CACHED / TO_FREE 等）

锁信息：
  lock_list：该事务持有的所有锁（行锁 + 表锁）的链表
  wait_lock：该事务当前等待的锁（如果在等待则非空）
  wait_started：等待锁的开始时间（用于超时检测）
  lock_heap：锁内存分配堆（该事务的锁对象从此堆分配）

并发控制：
  read_view：该事务的 Read View（快照，用于 MVCC 可见性判断）
             RC 级别：每次 SELECT 创建新的 read_view
             RR 级别：事务开始时创建，整个事务期间不变

执行状态：
  n_mysql_tables_in_use：正在使用的 MySQL 表数
  n_lock_table_updates：表级锁等待计数
  op_info：当前操作描述字符串
```

## 查看活跃事务对象信息

```sql
-- 通过 information_schema 查看活跃事务
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS trx_age_sec,
    trx_requested_lock_id,     -- 正在等待的锁 ID
    trx_wait_started,          -- 锁等待开始时间
    trx_weight,                -- 事务权重（用于死锁检测时选择牺牲者）
    trx_rows_locked,           -- 持有的行锁数量
    trx_rows_modified,         -- 修改的行数
    trx_mysql_thread_id,       -- 对应的 MySQL 连接线程 ID
    trx_query                  -- 当前执行的 SQL
FROM information_schema.INNODB_TRX
ORDER BY trx_started;

-- trx_weight（事务权重）的计算：
-- weight = undo_records（已修改的行数）+ lock_count（持有的锁数）
-- 死锁时，weight 最小的事务被选为"牺牲者"（ROLLBACK）
-- weight 越大 = 已做的工作越多 = 越不应该被回滚

-- 查看事务持有的锁
SELECT *
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = 'myapp'
  AND ENGINE_TRANSACTION_ID = '12345';  -- trx_id
```

## 事务 ID 的分配机制

```sql
-- 事务 ID 是 InnoDB 中的全局递增计数器
-- MySQL 8.0 的只读事务优化：
-- 只有修改了数据（DML）的事务才分配持久化的 trx_id
-- 纯 SELECT 事务使用临时的只读 ID（不持久化，不占用全局计数器）

-- 查看当前事务 ID
SELECT trx_id FROM information_schema.INNODB_TRX
WHERE trx_mysql_thread_id = CONNECTION_ID();

-- 查看全局事务 ID 计数器
SHOW ENGINE INNODB STATUS \G
-- TRANSACTIONS 部分：
-- Trx id counter 12345678（下一个分配的 trx_id）

-- 事务 ID 溢出的处理：
-- trx_id 是 6 字节无符号整数（最大 2^48 - 1 ≈ 281 万亿）
-- 在实际系统中几乎不会溢出（即使每秒 100 万个事务，也需要 8900 年）
```

## 事务对象的生命周期

```
1. 事务创建：
   执行 BEGIN / START TRANSACTION（或第一条 DML）
   → InnoDB 在内存中分配 trx_t 结构体
   → 分配 trx_id（DML 时分配，纯 SELECT 延迟）
   → 从 Rollback Segment 分配 Undo Slot（DML 时）
   → 创建 Read View（SELECT 时，取决于隔离级别）
   
2. 事务执行：
   每次 DML → 生成 Undo Log，trx_t.undo_no 递增
   每次加锁 → 在 trx_t.lock_list 中记录
   每次 SELECT（RC 级别）→ 创建新的 read_view
   
3. 事务提交：
   将 Undo Log 写入 History List（等待 Purge 清理）
   释放所有锁（lock_list）
   释放 Read View
   写 Redo Log（含提交标记）
   trx_state → TRX_STATE_COMMITTED_IN_MEMORY
   trx_t 结构体归还到内存池（复用）
   
4. 事务回滚：
   按 Undo Log 逆序执行逆操作（恢复旧值）
   释放所有锁
   释放 Read View
   标记 Undo Log 可回收
```

## 适用场景

- **死锁分析**：通过 `information_schema.INNODB_TRX` 查看 `trx_weight` 最小的事务，理解为什么 InnoDB 选择它作为死锁牺牲者
- **长事务监控**：监控 `trx_age_sec`（事务年龄）和 `trx_rows_modified`，发现运行时间过长的事务，这类事务持有大量锁，阻止 MVCC Purge 推进

## 常见问题

**为什么同一个 MySQL 连接，多次 SELECT 看到的 trx_id 不同？**

在 MySQL 8.0 中，纯只读事务（只有 SELECT，没有 DML）不会分配正式的持久化 trx_id，而是使用一个虚拟的只读 ID。`information_schema.INNODB_TRX` 不会显示纯只读事务（它没有正式 trx_id）。只有执行了 DML 或者显式 `BEGIN` + `SELECT FOR UPDATE` 等加锁操作的事务，才会分配和显示真正的 trx_id。

## 注意事项

- `trx_t` 结构体在内存中只存在于事务活跃期间，提交或回滚后被归还到内存池（待复用），不会无限增长。内存池的大小受 `innodb_lock_heap_initial_size` 等参数影响，但在正常情况下不需要调整。
- 高并发系统中，大量并发事务会在内存中同时存在大量 `trx_t` 对象，每个对象本身较小（几百字节），但积累的锁对象（lock_t，通常每把行锁 64 字节左右）可能占用大量内存。监控 `innodb_buffer_pool_stats` 和系统内存使用，防止锁内存耗尽。

## 总结

Transaction Object（`trx_t`）是 InnoDB 在内存中为每个活跃事务维护的核心结构，包含事务 ID（`trx_id`）、状态（`trx_state`）、Undo Log 引用、锁链表（`lock_list`）和 Read View。只有 DML 事务才分配持久化的 `trx_id`（MySQL 8.0 只读事务延迟分配优化）。通过 `information_schema.INNODB_TRX` 查看所有活跃事务的状态。事务提交/回滚后，`trx_t` 释放所有锁和 Read View，结构体本身归还到内存池复用。`trx_weight`（修改行数 + 锁数量）决定死锁检测时的牺牲者选择。

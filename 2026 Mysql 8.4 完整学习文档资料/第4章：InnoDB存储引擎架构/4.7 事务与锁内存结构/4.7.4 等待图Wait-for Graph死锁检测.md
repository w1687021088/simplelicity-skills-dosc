# 等待图 Wait-for Graph 死锁检测

Wait-for Graph（等待图，简称 WFG）是 InnoDB 用于死锁检测的有向图数据结构，在内存中动态维护。图中每个节点代表一个事务，每条有向边代表"事务 A 正在等待事务 B 释放某个锁"（A → B）。当图中出现环路（Cycle）时，说明存在死锁——一组事务相互等待，形成循环依赖，无法自动推进。InnoDB 使用深度优先搜索（DFS）检测环路，并选择代价最小的事务作为牺牲者（Victim）回滚，打破死锁。

---

## 等待图的结构

```
Wait-for Graph 示意：

正常情况（无死锁）：
  事务A → 等待 → 事务B（A 等待 B 持有的锁）
  事务C → 等待 → 事务D
  无环路，不是死锁

死锁情况（有环路）：
  事务A → 事务B（A 等待 B 的锁）
  事务B → 事务A（B 等待 A 的锁）
  A → B → A，形成环路 = 死锁

三方死锁：
  事务A → 事务B → 事务C → 事务A
  环路长度为 3，同样是死锁

图的数据结构：
  节点（Node）：活跃事务（trx_t *）
  边（Edge）：等待关系（wait_lock + trx_locks + undo_no 确定因果关系）
  图在内存中动态构建（不持久化），随锁的申请/释放实时更新
```

## 死锁的发生场景

```sql
-- 经典两事务死锁：

-- 连接1（事务A）：
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 锁定 id=1
-- 等待 id=2 的锁...

-- 连接2（事务B）：
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 2;  -- 锁定 id=2
UPDATE accounts SET balance = balance + 100 WHERE id = 1;  -- 等待 id=1 的锁!
-- 死锁！事务B等待事务A(id=1)，事务A等待事务B(id=2)

-- 连接1（事务A 继续）：
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- 等待 id=2 的锁！
-- → InnoDB 检测到死锁，选择一个事务回滚

-- 死锁报错信息：
-- ERROR 1213 (40001): Deadlock found when trying to get lock;
-- try restarting transaction
```

## InnoDB 死锁检测算法

```
死锁检测触发时机：
  每当一个事务进入锁等待时，InnoDB 立即运行死锁检测（DFS）
  而不是定期轮询（避免死锁长时间阻塞）

深度优先搜索（DFS）过程：
  从新加入等待的事务（trx_A）开始
  → 查找 trx_A 正在等待的锁（wait_lock）
  → 找到持有该锁的事务（trx_B）
  → 如果 trx_B 也在等待锁 → 继续 DFS（trx_B 等待谁？）
  → 如果最终找到 trx_A 自身 → 发现环路 = 死锁
  → 选择牺牲者并回滚

牺牲者选择规则：
  选择 trx_weight 最小的事务作为牺牲者（回滚代价最小）
  trx_weight = undo_no（已修改行数）+ lock_count（持有锁数）
  weight 最小 = 已做工作最少 = 回滚代价最小

牺牲者处理：
  → 回滚牺牲事务（undo 逆操作，释放所有锁）
  → 其他等待事务获得锁，继续执行
  → 牺牲事务的客户端收到错误 1213（DeadLock）
  → 应用层应捕获此错误并重试事务
```

## 死锁检测的性能开销

```sql
-- 每次锁等待都触发 DFS，时间复杂度 O(N)（N=活跃事务数）
-- 高并发下（几千并发事务），死锁检测本身可能成为性能瓶颈

-- 禁用死锁检测（不推荐，慎用）：
SHOW VARIABLES LIKE 'innodb_deadlock_detect';
-- 默认：ON

SET GLOBAL innodb_deadlock_detect = OFF;
-- 关闭后，死锁由 innodb_lock_wait_timeout 超时处理
-- 超时后事务回滚（较慢，默认 50 秒才超时）
-- 适合确定没有死锁风险的极高并发场景（如同一行的高频更新）

-- 调整锁等待超时（作为死锁的补充保护）
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
-- 默认：50 秒
-- 即使没有死锁，等待超过此时间也回滚

SET SESSION innodb_lock_wait_timeout = 10;  -- 缩短为 10 秒（减少等待时间）
```

## 查看死锁信息

```sql
-- 查看最近一次死锁详情（最重要的死锁诊断方法）
SHOW ENGINE INNODB STATUS \G
-- 在 LATEST DETECTED DEADLOCK 部分：
-- 包含：
-- *** (1) TRANSACTION：事务1的详情（SQL、持有的锁）
-- *** (1) HOLDS THE LOCK(S)：事务1持有的锁
-- *** (1) WAITING FOR THIS LOCK TO BE GRANTED：事务1等待的锁
-- *** (2) TRANSACTION：事务2的详情
-- *** WE ROLL BACK TRANSACTION (1/2)：谁被回滚了

-- 查看死锁统计（累计次数）
SELECT NAME, COUNT, STATUS
FROM information_schema.INNODB_METRICS
WHERE NAME = 'lock_deadlocks';

-- 记录所有死锁到错误日志（MySQL 5.6.15+）
SHOW VARIABLES LIKE 'innodb_print_all_deadlocks';
-- 默认：OFF（只保留最近一次）
SET GLOBAL innodb_print_all_deadlocks = ON;
-- 开启后，所有死锁写入 MySQL 错误日志（error log）
-- 便于事后分析生产环境死锁历史
```

## 避免死锁的设计原则

```sql
-- 原则1：事务内以固定顺序访问资源（防止循环依赖）
-- 错误：事务A先锁 accounts(1)，再锁 accounts(2)
--       事务B先锁 accounts(2)，再锁 accounts(1) → 死锁

-- 正确：所有事务都按 id 从小到大顺序访问
-- 事务A：先锁 accounts(1)，再锁 accounts(2)
-- 事务B：先锁 accounts(1)，再锁 accounts(2) → 不会死锁（B 会等 A 释放(1)）

-- 原则2：缩小事务范围，减少锁持有时间
-- 将长事务拆分为多个短事务（减少锁冲突概率）

-- 原则3：使用索引避免全表扫描（全表扫描会锁定大量记录）
-- 确保 WHERE 条件使用到索引，避免 RR 级别下不必要的间隙锁

-- 原则4：应用层捕获死锁错误并重试
-- try {
--   executeTransaction();
-- } catch (DeadlockException) {
--   retryTransaction();  // 自动重试，通常 1-3 次后成功
-- }
```

## 适用场景

- **高并发事务系统**：当系统死锁频率高时（每分钟超过几次），通过 `innodb_print_all_deadlocks=ON` 记录所有死锁，分析死锁 SQL 模式，通过调整访问顺序或缩短事务来消除
- **计数器型高频更新**：对同一行频繁更新的场景（如库存扣减），可以考虑关闭死锁检测（`innodb_deadlock_detect=OFF`）并缩短锁等待超时，以减少死锁检测的 CPU 开销

## 常见问题

**死锁检测的 DFS 算法在几千个并发事务下会很慢吗？**

在极高并发（几千事务同时等待锁）的场景下，DFS 确实可能成为 CPU 热点。MySQL 8.0.18+ 优化了死锁检测的并发，引入了锁系统分片（sharding），使不同分片的锁等待可以并发检测，减少了串行 DFS 的瓶颈。但对于真正极端的高并发（秒级几万个锁等待），可以考虑关闭死锁检测（`innodb_deadlock_detect=OFF`）并依靠超时机制，同时在应用层消除死锁的根源（固定资源访问顺序）。

## 注意事项

- `SHOW ENGINE INNODB STATUS` 只显示最近一次死锁的详情，之前的死锁会被覆盖。如果需要保留所有死锁记录，必须设置 `innodb_print_all_deadlocks = ON`（写入 MySQL 错误日志）或通过监控工具定期采集。
- 死锁后被回滚的是牺牲事务（weight 最小的），不一定是"先发生死锁"的那个事务。应用层不能假设哪个事务会被回滚，必须对死锁错误（ERROR 1213）做通用的重试处理。

## 总结

Wait-for Graph（等待图）是 InnoDB 内存中的有向图，节点为活跃事务，边为"等待锁"关系（A → B 表示 A 等待 B 持有的锁）。每次事务进入锁等待时，InnoDB 立即运行 DFS 检测环路（死锁）。检测到死锁后，选择 `trx_weight`（修改行数+锁数）最小的事务回滚（牺牲），打破死锁，其他事务恢复执行。通过 `SHOW ENGINE INNODB STATUS` 查看最近死锁详情，`innodb_print_all_deadlocks=ON` 记录所有死锁。避免死锁的关键是固定资源访问顺序和缩短事务范围。

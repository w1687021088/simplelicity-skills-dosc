# COMPRESSED 压缩行格式

COMPRESSED 是 InnoDB 的压缩行格式，在 DYNAMIC 格式的基础上增加了对整个数据页的 zlib 压缩。每个 16KB 的数据页被压缩后存储到更小的物理页（通过 `KEY_BLOCK_SIZE` 指定，可以是 1/2/4/8 KB），减少磁盘 I/O 和存储空间。代价是每次读取需要解压（CPU 开销），写入需要压缩再解压（修改页内容后需要重压缩）。COMPRESSED 适合读多写少、磁盘空间有限、CPU 资源充足的归档场景。

---

## COMPRESSED 格式的工作原理

```
正常流程（无压缩）：
  磁盘：16KB 数据页 ←→ Buffer Pool：16KB 页

COMPRESSED 格式的流程：
  磁盘：KEY_BLOCK_SIZE KB 压缩页（如 8KB）
  Buffer Pool：
    ├── 压缩页（8KB，直接来自磁盘）
    └── 未压缩页（16KB，解压后的内容，用于实际读写）

Buffer Pool 中的双份存储：
  压缩页：用于与磁盘交互（减少 I/O）
  非压缩页：用于 CPU 读写（避免每次操作都解/压缩）
  当内存紧张时，InnoDB 可以丢弃非压缩页（保留压缩页）
  下次访问时再解压（以 CPU 换内存）
```

## 创建和配置 COMPRESSED 格式

```sql
-- 创建使用压缩格式的表
CREATE TABLE orders_archive (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_data  TEXT,
    created_at  DATETIME
) ENGINE = InnoDB
  ROW_FORMAT = COMPRESSED
  KEY_BLOCK_SIZE = 8;   -- 压缩页大小（KB）：1、2、4、8（默认 8）
-- KEY_BLOCK_SIZE 必须是 innodb_page_size 的约数
-- innodb_page_size=16K → KEY_BLOCK_SIZE 可以是 1/2/4/8（不能是 16，那等于不压缩）

-- 查看 COMPRESSED 表的压缩效果
SELECT
    TABLE_NAME,
    ROW_FORMAT,
    DATA_LENGTH / 1024 / 1024 AS data_mb,
    INDEX_LENGTH / 1024 / 1024 AS index_mb,
    CREATE_OPTIONS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'orders_archive';
-- CREATE_OPTIONS 中会显示 row_format=COMPRESSED

-- 通过通用表空间使用压缩（需要 FILE_BLOCK_SIZE）
CREATE TABLESPACE ts_compressed
    ADD DATAFILE 'ts_compressed.ibd'
    FILE_BLOCK_SIZE = 8192  -- 8KB，等于 KEY_BLOCK_SIZE × 1024
    ENGINE = InnoDB;

CREATE TABLE archive_data (
    id   BIGINT PRIMARY KEY,
    data TEXT
) TABLESPACE = ts_compressed
  ROW_FORMAT = COMPRESSED
  KEY_BLOCK_SIZE = 8;
```

## 压缩率与 KEY_BLOCK_SIZE 的选择

```sql
-- 不同 KEY_BLOCK_SIZE 的压缩效果（参考值）：
-- KEY_BLOCK_SIZE = 8（压缩到 50%）：空间节省 50%，I/O 减少 50%
-- KEY_BLOCK_SIZE = 4（压缩到 25%）：空间节省 75%，I/O 减少 75%，CPU 开销更大
-- KEY_BLOCK_SIZE = 2（压缩到 12.5%）：极高压缩比，CPU 开销极大

-- 实际选择依据：
-- 1. 先用 KEY_BLOCK_SIZE = 8 测试，观察压缩效果（INFORMATION_SCHEMA 查询）
-- 2. 如果压缩率不理想（压缩后 > 7.5KB），说明数据压缩性差，考虑不使用压缩
-- 3. 文本类数据（JSON/XML/TEXT）压缩比通常好（可达 60-80% 压缩率）
-- 4. 已压缩的二进制数据（图片/视频）压缩比极差，不建议使用 COMPRESSED

-- 查看压缩统计
SELECT
    database_name,
    table_name,
    compress_ops,           -- 压缩操作次数
    compress_ops_ok,        -- 成功压缩次数
    compress_time,          -- 压缩消耗时间
    uncompress_ops,         -- 解压操作次数
    uncompress_time         -- 解压消耗时间
FROM information_schema.INNODB_CMP_PER_INDEX;

-- 总体压缩统计（不按表/索引分组）
SELECT * FROM information_schema.INNODB_CMP;
-- compress_ops_ok / compress_ops 越接近 1，说明压缩质量越好
-- 如果大量压缩失败（压缩后超出 KEY_BLOCK_SIZE），说明数据不适合此压缩级别
```

## COMPRESSED 格式的 Buffer Pool 行为

```sql
-- COMPRESSED 表在 Buffer Pool 中的双份存储可能导致内存紧张
-- 特别是当压缩后大小与 16KB 差不多时，Buffer Pool 利用率反而下降

-- 监控 COMPRESSED 表的 Buffer Pool 使用情况
SELECT
    COMPRESS_OPS,
    COMPRESS_OPS_OK,
    UNCOMPRESS_OPS,
    COMPRESS_TIME,
    UNCOMPRESS_TIME
FROM information_schema.INNODB_CMP;

-- 控制是否在 Buffer Pool 中保留未压缩页（权衡内存 vs CPU）
SHOW VARIABLES LIKE 'innodb_use_native_aio';
-- 相关：innodb_compression_level（默认 6，zlib 压缩级别 0-9）
SHOW VARIABLES LIKE 'innodb_compression_level';
-- 值越高：压缩比越好，但 CPU 开销更大
-- 生产环境通常使用默认 6，归档场景可以提高到 9（更高压缩比）

SET GLOBAL innodb_compression_level = 9;  -- 最高压缩比（更多 CPU）
```

## COMPRESSED 格式的限制

```sql
-- 1. 不支持在系统表空间中使用（只能用于 file-per-table 或通用表空间）
-- 2. innodb_page_size != 16KB 时，不支持 COMPRESSED 格式
-- 3. COMPRESSED 格式不支持在线 DDL（某些 ALTER TABLE 操作需要 COPY 算法）
-- 4. 主从复制中，从库同样需要解压能力（CPU 开销在从库也存在）

-- 检查页面压缩是否启用（非 COMPRESSED 行格式，是另一种压缩机制）
SHOW VARIABLES LIKE 'innodb_compression_failure_threshold_pct';
-- 压缩失败阈值（默认 5%）：如果 5% 的压缩操作失败，InnoDB 将增加"填充"以减少失败
```

## 适用场景

- **归档表**：历史订单、日志等只读或极少更新的数据，使用 COMPRESSED 格式节省 50-80% 磁盘空间
- **磁盘空间紧张但 CPU 充足**：对于纯文本类数据（JSON 格式的记录、XML 文档、长文本描述），压缩比通常较高，性价比好

## 常见问题

**COMPRESSED 格式和 MySQL 8.0 的页压缩（Page Compression）有什么区别？**

COMPRESSED 行格式（通过 `ROW_FORMAT=COMPRESSED` 指定）是在 InnoDB 层面对整个数据页进行 zlib 压缩，在 Buffer Pool 中保留双份（压缩页 + 非压缩页），适合任何操作系统。MySQL 8.0 的页压缩（通过 `COMPRESSION='zlib'` 或 `COMPRESSION='lz4'` 指定）是在文件系统层面（利用支持稀疏文件的文件系统 + hole punching 技术）压缩，只需要在 Buffer Pool 中保留非压缩页，对内存压力更小，但需要支持 hole punching 的文件系统（ext4、XFS 等）和操作系统支持。

---

## 注意事项

- COMPRESSED 格式的写入性能比 DYNAMIC 低，因为每次修改页内容后，需要重新压缩该页（如果修改后压缩结果仍适合 KEY_BLOCK_SIZE，直接写入；否则需要页分裂）。对于写密集型表，不建议使用 COMPRESSED 格式。
- `innodb_cmp_per_index_enabled = ON`（默认 OFF）才能启用按索引统计的压缩数据，默认情况下只能查看 `INNODB_CMP`（全局统计），无法按表/索引分析压缩效果。

---

## 总结

COMPRESSED 格式在 DYNAMIC 基础上增加了 zlib 页压缩，通过 `KEY_BLOCK_SIZE`（1/2/4/8 KB）控制压缩后的物理页大小。Buffer Pool 中同时保存压缩页（用于 I/O）和非压缩页（用于读写），内存占用是正常页的 2 倍。适合文本类、读多写少的归档数据（压缩比 50-80%）。不适合随机写密集或已压缩的二进制数据。通过 `information_schema.INNODB_CMP` 监控压缩效率，`innodb_compression_level`（默认 6）控制压缩强度。

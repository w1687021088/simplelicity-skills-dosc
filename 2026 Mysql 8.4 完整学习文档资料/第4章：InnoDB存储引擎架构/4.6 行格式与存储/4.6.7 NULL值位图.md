# NULL 值位图

NULL 值位图（NULL Flags Bitmap）是 COMPACT/DYNAMIC 格式行记录中变长字段长度列表之后、Record Header 之前的一段字节，用于标记该行中哪些列的值为 NULL。每个可以存储 NULL 的列（即列定义中没有 NOT NULL 约束的列）在位图中占 1 个 bit 位。NULL 位图的设计使得 NULL 列在行记录中完全不占用存储空间（既不占变长字段长度列表，也不占列值区域），仅通过 1 bit 来传递"此列为 NULL"的信息。

---

## NULL 位图的结构规则

```
NULL 位图的计算规则：

步骤1：确定参与位图的列
  只有可为 NULL 的列（没有 NOT NULL 约束的列）参与
  有 NOT NULL 约束的列不占位图中的 bit 位
  （因为 NOT NULL 列不可能为 NULL，不需要位图记录）

步骤2：计算位图字节数
  参与列数 ÷ 8 = 字节数（向上取整）
  0 个可 NULL 列 → 0 字节（无 NULL 位图）
  1-8 个可 NULL 列 → 1 字节
  9-16 个可 NULL 列 → 2 字节
  ...

步骤3：位的分配顺序
  按列定义的逆序分配 bit（与变长字段长度列表的逆序一致）
  第一列对应最高 bit？不完全准确：
  → 实际上，位图字节按列顺序排列，第一个 bit 对应第一个可 NULL 列
  → 逆序指的是位图整体（字节）在行记录中的顺序（从高地址到低地址读取）

直觉理解：
  对于 6 个可 NULL 的列（col1 到 col6）：
  NULL 位图占 1 字节：[bit7=col6_null, ..., bit2=col1_null, bit1 bit0 = 0 0]
  → 从最低有效位开始，每位对应一个可 NULL 列（col1 在 bit0，col6 在 bit5）
```

## 举例说明 NULL 位图

```sql
-- 表结构
CREATE TABLE t (
    id      INT       NOT NULL,   -- NOT NULL，不参与 NULL 位图
    name    VARCHAR(50),          -- 可 NULL，位图 bit0
    score   INT,                  -- 可 NULL，位图 bit1
    grade   CHAR(1),              -- 可 NULL，位图 bit2
    note    VARCHAR(200),         -- 可 NULL，位图 bit3
    PRIMARY KEY (id)
) ROW_FORMAT = COMPACT;

-- 插入 4 个可 NULL 列（bit0 到 bit3）
-- 总共 4 个 bit，用 1 字节存储

-- 情形1：INSERT INTO t VALUES (1, 'Alice', NULL, 'A', NULL);
-- name = 'Alice'（非 NULL，bit0 = 0）
-- score = NULL（bit1 = 1）
-- grade = 'A'（非 NULL，bit2 = 0）
-- note = NULL（bit3 = 1）
-- NULL 位图：0000_1010（二进制，bit3=1, bit1=1）= 0x0A

-- 情形2：INSERT INTO t VALUES (2, NULL, NULL, NULL, NULL);
-- 全部可 NULL 列为 NULL
-- NULL 位图：0000_1111 = 0x0F

-- 情形3：INSERT INTO t VALUES (3, 'Bob', 90, 'B', 'good');
-- 全部非 NULL
-- NULL 位图：0000_0000 = 0x00

-- 验证：通过 hexdump 或 innochecksum 工具可以查看原始字节
```

## NULL 位图与存储效率

```
NULL 位图的存储效率分析：

场景1：100 列表，其中 80 列可为 NULL，每行有 20 列为 NULL
  NULL 位图大小：80 / 8 = 10 字节
  NULL 列节省的空间（以 INT 为例，每列 4 字节）：
    20 列 × 4 字节 = 80 字节节省
  净增加：10 字节（位图）- 80 字节（节省）= -70 字节
  → 行记录比全部非 NULL 时小 70 字节！
  
  结论：NULL 列越多，通过 NULL 位图节省的空间越大
  NULL 对于稀疏数据（很多 NULL 值）的表存储效率非常高

场景2：100 列表，每行只有 1-2 列为 NULL
  NULL 位图大小：10 字节（固定，不管有几列是 NULL）
  NULL 列节省：1-2 列 × 4 字节 = 4-8 字节
  净增加：10 - 8 = 2 字节（略微增加）
  
  结论：NULL 列很少时，NULL 位图可能略微增加存储开销
  但在实践中，允许 NULL 的设计通常是因为业务上确实有很多 NULL 值
```

## NOT NULL 列与 NULL 列的存储差异

```sql
-- 比较：NOT NULL 整型 vs 可为 NULL 的整型

-- 场景：1000 万行，age 列，约 30% 的行 age 为 NULL

-- 方案A：age INT NULL（允许 NULL）
-- NULL 行（300万行）：
--   age 不在列值区域（节省 4 字节/行）
--   NULL 位图中 1 bit（已有其他 NULL 列时，不额外增加字节数）
-- 非 NULL 行（700万行）：
--   age 在列值区域（4 字节/行）
-- 整体存储：700万 × 4字节 = 约 28 MB
-- 
-- 方案B：age INT NOT NULL DEFAULT -1（用 -1 表示未知）
-- 所有行（1000万行）：age 在列值区域（4 字节/行）
-- 整体存储：1000万 × 4字节 = 约 40 MB
--
-- 结论：允许 NULL 时（若确实有大量 NULL 值），比用默认值存储节省空间

-- 查看单行的大小（近似）
SELECT AVG_ROW_LENGTH, TABLE_ROWS, DATA_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'users';
```

## 索引中的 NULL 处理

```sql
-- NULL 值可以被索引（InnoDB 支持 NULL 值进入 B+ Tree 索引）
-- NULL 值在 B+ Tree 中排在最小值之前（NULL < 任何非 NULL 值）
-- 对于唯一索引：允许多个 NULL 值（NULL ≠ NULL，SQL 标准）

-- 验证：
CREATE TABLE t_null (
    id   INT PRIMARY KEY,
    val  INT,
    UNIQUE INDEX idx_val (val)
);
INSERT INTO t_null VALUES (1, NULL);
INSERT INTO t_null VALUES (2, NULL);  -- 唯一索引允许多个 NULL
INSERT INTO t_null VALUES (3, 1);
-- INSERT INTO t_null VALUES (4, 1);  -- ERROR：唯一约束冲突

-- 在索引中 NULL 值对范围查询的影响：
SELECT * FROM t_null WHERE val IS NULL;  -- 使用 idx_val 索引
SELECT * FROM t_null WHERE val IS NOT NULL;  -- 使用 idx_val 索引
SELECT * FROM t_null WHERE val > 0;  -- 使用 idx_val 索引，不扫描 NULL 行
```

## 适用场景

- **稀疏数据建模**：对于"可选字段"（如用户资料中不是必填的手机号、生日等），允许 NULL 比使用默认空字符串或 0 更节省空间（尤其是大量行确实没有该字段值时）
- **存储优化分析**：理解 NULL 位图有助于判断是否值得将稀疏字段设置为 NOT NULL（以消除 NULL 位图开销）或保持 NULL（利用位图节省 NULL 行的列存储）

## 常见问题

**NULL 位图和变长字段长度列表都是逆序的，为什么这样设计？**

两者都在 Record Header 之前（低地址方向），列值区域在 Record Header 之后（高地址方向）。读取行记录时，InnoDB 从 Record Header 的起始地址出发，向前（低地址）读取 NULL 位图和变长字段长度列表。逆序存储使得"第一列"的信息最靠近 Record Header，从 Record Header 向前依次读取就是按列顺序（第一列、第二列…）解析，对顺序读取更友好。

## 注意事项

- NULL 位图的字节数只取决于表中可为 NULL 的列的数量（不管这些列实际是否为 NULL），不会随着 NULL 值的多少而变化。即使所有可 NULL 列都非 NULL，NULL 位图仍然占用固定字节（所有位为 0）。
- 在进行 `ALTER TABLE` 添加或删除 NOT NULL 约束时，如果这改变了可为 NULL 的列数量，InnoDB 需要重建整张表（因为 NULL 位图的大小改变了，所有行的字节布局都变了）。这类 DDL 操作在生产环境需要借助 pt-online-schema-change 等工具避免长时间表锁。

## 总结

NULL 值位图是 COMPACT/DYNAMIC 行记录中紧接变长字段长度列表的字节区域，为每个可为 NULL 的列分配 1 个 bit（每 8 列占 1 字节）。bit = 1 表示该列为 NULL，NULL 列在列值区域和变长字段长度列表中均不占用任何空间，极大地节省稀疏数据的存储开销。只有定义了 NOT NULL 约束的列才不参与位图。NULL 位图的大小固定取决于表中可 NULL 列的数量，与实际 NULL 值数量无关。理解 NULL 位图是精确计算行记录大小和评估 NULL vs 默认值存储效率的必要知识。

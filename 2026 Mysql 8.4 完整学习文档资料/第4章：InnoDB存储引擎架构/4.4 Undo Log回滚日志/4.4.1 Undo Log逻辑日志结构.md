# Undo Log 逻辑日志结构

Undo Log（回滚日志）是 InnoDB 实现事务原子性（Atomicity）和 MVCC（多版本并发控制）的基础。与 Redo Log 的物理日志不同，Undo Log 是逻辑日志，记录的是将数据恢复到修改前状态所需的逆操作（如 INSERT 对应的 DELETE、UPDATE 对应的反向 UPDATE）。每次 DML 操作都会生成相应的 Undo Log 记录，存储在 Undo 表空间中。

---

## Undo Log 的两大用途

```
用途1：事务回滚（原子性）
  事务执行过程中，任何时刻 ROLLBACK：
  → 按逆序读取该事务的 Undo Log 记录
  → 将每个修改还原到修改前的状态
  → 实现"这个事务好像没发生过"的效果

用途2：MVCC 一致性读（隔离性）
  事务读取数据时，某行数据可能已被其他事务修改
  → 通过行记录中的 DB_ROLL_PTR（回滚指针）找到旧版本 Undo Log
  → 构建出该行在特定时间点的历史版本
  → 实现不同事务看到不同时间点的数据（一致性读）
```

---

## Undo Log 的逻辑结构

```
Undo Log Record 的逻辑内容：

INSERT 操作的 Undo Log：
  → 记录：被插入行的主键值
  → 回滚操作：DELETE 该主键对应的行

DELETE 操作的 Undo Log：
  → 记录：被删除行的全部列值（或主键 + 所有列值）
  → 回滚操作：重新 INSERT 该行

UPDATE 操作的 Undo Log：
  → 记录：被修改列的修改前值（不记录未修改的列）
  → 回滚操作：将修改列还原为记录的旧值

注意：这是逻辑操作的记录，不是像 Redo Log 那样记录
     具体的字节偏移量和字节值（物理记录）
```

## Undo Log 的存储位置

```sql
-- MySQL 8.0 之前：Undo Log 存储在系统表空间（ibdata1）中
-- MySQL 8.0+：Undo Log 存储在独立的 Undo 表空间文件中

-- 查看 Undo 表空间相关配置
SHOW VARIABLES LIKE 'innodb_undo%';
-- +----------------------------+-------+
-- | Variable_name              | Value |
-- +----------------------------+-------+
-- | innodb_undo_directory      | ./    | -- Undo 文件目录（默认与 datadir 相同）
-- | innodb_undo_log_encrypt    | OFF   | -- Undo Log 加密（MySQL 8.0.16+）
-- | innodb_undo_log_truncate   | ON    | -- 是否自动收缩 Undo 表空间（默认 ON）
-- | innodb_undo_tablespaces    | 2     | -- Undo 表空间数量（MySQL 8.0 默认 2）
-- +----------------------------+-------+

-- 查看 Undo 表空间文件
SELECT SPACE_ID, NAME, STATE, SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'innodb_undo%';
-- 文件：undo_001, undo_002（MySQL 8.0 默认）

-- 默认 Undo 表空间文件位于 datadir
-- undo_001 和 undo_002（或早期版本的 undo001、undo002）
```

## Undo Log Record 的物理组织

```
Undo Log 在 Undo 表空间中的物理存储：

Undo Tablespace（.ibu 文件或 ibdata1 中的区域）
  └── Rollback Segment（回滚段）× 128
       每个回滚段对应 1 个 rollback segment header 页
       └── Undo Log Segment（Undo 段）× 1024
            每个 Undo 段包含多个 Undo 页
            └── Undo Page（16KB）
                 └── Undo Log Record（变长）× N
                      多条 Undo 记录顺序存储在页中

回滚段和事务的关系：
  每个事务分配一个回滚段
  事务的所有 Undo Log 记录存储在该回滚段的 Undo 段中
  事务提交后：INSERT Undo Log 立即删除；UPDATE/DELETE Undo Log 保留供 MVCC 使用
```

## Undo Log 与 Redo Log 的对比

| 对比维度 | Undo Log | Redo Log |
|---------|---------|---------|
| 日志类型 | 逻辑日志（逆操作）| 物理日志（字节变更）|
| 主要用途 | 事务回滚 + MVCC | 崩溃恢复（前滚）|
| 存储位置 | Undo 表空间（.ibu 文件）| Redo Log 文件（#ib_redo*）|
| 生命周期 | 有效事务结束后 + MVCC 不再需要时删除 | 写满后循环覆盖 |
| 写入时机 | 数据修改时同步写入 | 数据修改时同步写入 |
| 持久化 | 通过 Redo Log 保证（Undo Log 的修改也写 Redo Log）| 自身即为持久化目标 |

## 适用场景

- **事务回滚**：所有支持 ROLLBACK 的场景都依赖 Undo Log，理解其结构有助于分析大回滚操作的性能瓶颈
- **长事务问题**：长时间运行的事务会持续积累 Undo Log，且旧版本无法被 Purge，理解 Undo Log 结构有助于分析 History List 增长问题

---

## 常见问题

**Undo Log 本身是否也需要 Redo Log 保护？**

是的。Undo Log 存储在 Undo 表空间的数据页中，这些页和普通数据页一样受 Buffer Pool 管理，对 Undo 页的修改同样会产生 Redo Log。这意味着 Undo Log 的变更在崩溃后可以通过 Redo Log 恢复，从而确保 Undo Log 在崩溃恢复阶段可以被正确使用（用来回滚未完成的事务）。

---

## 注意事项

- Undo Log 的空间会随着长事务的运行而持续增长（无法被 Purge 的旧版本）。如果系统中存在长时间运行的事务（如未提交的大批量操作），需要监控 Undo Log 的空间使用情况（`information_schema.INNODB_METRICS` 中的 `trx_rseg_history_len`）。
- MySQL 8.0 将 Undo Log 迁移到独立表空间（`undo_001`, `undo_002`）后，`innodb_undo_log_truncate=ON` 允许 InnoDB 自动收缩过大的 Undo 表空间，解决了旧版本中 `ibdata1` 无法收缩的痛点。

---

## 总结

Undo Log 是逻辑日志，记录 DML 操作的逆操作（INSERT → DELETE、UPDATE → 反向 UPDATE），用于事务回滚和 MVCC 历史版本构建。存储在 Undo 表空间（MySQL 8.0+ 独立的 `undo_001/undo_002` 文件），物理组织为：Undo Tablespace → Rollback Segment（128个）→ Undo Segment（1024个）→ Undo Page（16KB）→ Undo Record。INSERT 产生的 Undo Log 在提交后可立即删除，UPDATE/DELETE 产生的 Undo Log 需保留至无事务需要其旧版本为止。

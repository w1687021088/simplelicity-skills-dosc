# Purge 清理过期 Undo 记录

Purge 是 InnoDB 的后台清理线程，负责清理不再需要的旧版本 Undo Log 记录和已被 DELETE 标记的行数据。当一条 Undo Log 记录不再被任何活跃事务的 Read View 需要时，Purge 线程会将其从 Undo 表空间中物理删除，并将 DELETE 标记的行从数据页中彻底移除，同时释放对应的 Undo Slot 空间。Purge 的及时性直接决定了 Undo 表空间的大小和 History List 的长度。

---

## Purge 的两项工作

```
工作1：清理 Undo Log 记录
  当 UPDATE/DELETE Undo Log 不再被任何 Read View 需要时
  → Purge 线程将该 Undo Log 记录从 Undo 段中物理删除
  → 释放 Undo 页空间（最终可以被新的 Undo Log 复用）

工作2：物理删除 DELETE MARK 的行
  DELETE 操作不会立即从数据页删除行，只会在行头打上 delete-mark 标志
  → 等到没有事务需要看到该行的旧版本时
  → Purge 线程将 delete-mark 的行从 B+ Tree 数据页中彻底移除
  → 同时清理相关的 UPDATE Undo Log（DELETE 操作使用 UPDATE Undo）

什么时候"不再需要"？
  当 Undo Log 的事务 ID < 所有活跃事务的最小事务 ID（min_active_trx_id）时
  → 任何当前事务都不需要再通过这条 Undo Log 访问历史版本
  → 该 Undo Log 可以安全删除
```

## Purge 线程的配置

```sql
-- 查看 Purge 相关参数
SHOW VARIABLES LIKE 'innodb_purge%';
-- +-------------------------------+-------+
-- | Variable_name                 | Value |
-- +-------------------------------+-------+
-- | innodb_purge_batch_size       | 300   | -- 每批次处理的 Undo 页数（默认 300）
-- | innodb_purge_rseg_truncate_frequency | 128 | -- Undo Segment 收缩频率
-- | innodb_purge_threads          | 4     | -- Purge 线程数（默认 4）
-- +-------------------------------+-------+

-- 增大 Purge 线程数（高写入压力时）
SET GLOBAL innodb_purge_threads = 8;
-- 允许多个 Purge 线程并行清理不同 Undo Segment

-- 增大每批次处理量（加速清理积压）
SET GLOBAL innodb_purge_batch_size = 1000;
-- 默认 300，增大可以加速 Purge，但会增加 Purge 对 I/O 的占用

-- 查看 Purge 线程状态
SELECT NAME, TYPE, STATE
FROM performance_schema.threads
WHERE NAME LIKE '%purge%';
```

## 监控 Purge 进度

```sql
-- 监控 History List 长度（Purge 积压指标）
-- History List = 已提交但 Undo Log 尚未被 Purge 的事务数量

SHOW ENGINE INNODB STATUS \G
-- 在 TRANSACTIONS 部分：
-- History list length 1234
-- 正常：< 1000
-- 偏高：1000-10000（Purge 轻微积压）
-- 告警：> 10000（Purge 严重积压，长事务可能存在）

-- 通过 information_schema 查看
SELECT NAME, COUNT
FROM information_schema.INNODB_METRICS
WHERE NAME = 'trx_rseg_history_len';

-- 查看当前活跃事务（阻止 Purge 的元凶通常是长事务）
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS trx_age_seconds,
    trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_age_seconds DESC;
-- 长时间运行的事务会阻止 Purge 推进
```

## 长事务阻止 Purge 的影响

```
长事务阻止 Purge 的场景：

事务A（时间戳 T=100，大量 SELECT，长时间未提交）
事务B（T=200，已提交，产生了大量 UPDATE Undo）
事务C（T=300，已提交，产生了大量 UPDATE Undo）

Purge 无法清理 B 和 C 的 Undo Log
原因：事务A的 Read View 最小事务ID = 100
      B(200) 和 C(300) 都 > 100
      → 事务A可能需要通过这些 Undo Log 读取历史版本
      → Purge 必须等待事务A提交

后果：
  → History List 持续增长（大量 Undo Log 积压）
  → Undo 表空间持续膨胀（无法 Truncate）
  → MVCC 版本链变长，查询需要遍历更长的链（性能下降）

解决方案：
  → 定期监控长事务（超过 60 秒的事务）
  → 设置 long_trx_kill_threshold（第三方工具）或应用层超时
  → 在 MySQL 中配置 innodb_lock_wait_timeout 避免长时间等待锁
```

## Purge 与删除性能

```sql
-- DELETE 操作的两阶段过程：

-- 阶段1：事务执行时（立即发生）
-- DELETE FROM orders WHERE id = 1001;
-- → 在数据页中，将该行标记为 delete-marked（不立即移除）
-- → 写入 UPDATE Undo Log（记录行的旧值，用于回滚和 MVCC）
-- → 事务提交后，delete-marked 行对新事务不可见

-- 阶段2：Purge 时（延迟发生）
-- → Purge 线程确认没有事务需要该行的旧版本
-- → 物理移除 delete-marked 行（从 B+ Tree 中删除记录，释放页空间）
-- → 删除对应的 UPDATE Undo Log 记录

-- 大批量 DELETE 的影响：
-- 如果快速 DELETE 了 100 万行：
--   100 万个 delete-marked 标记立即产生
--   Purge 需要逐步清理这些行（I/O 密集型操作）
--   期间这些 delete-marked 行仍然占用数据页空间
--   表的实际空间不会立即减少（需要等 Purge + 碎片回收）

-- 检查数据碎片（DELETE 后空间未回收）
SHOW TABLE STATUS LIKE 'orders';
-- Data_free：已删除但未被复用的空间
-- 可以通过 OPTIMIZE TABLE orders; 回收（会锁表/重建）
```

## Purge 的 I/O 影响

```sql
-- 控制 Purge 对 I/O 的影响
-- Purge 使用 innodb_io_capacity 分配的 I/O 配额的一部分
-- 不会独占全部 I/O，与 Flush List 的页刷盘共享 I/O 配额

-- 如果 History List 积压严重，可以临时增大 I/O 容量加速 Purge
SET GLOBAL innodb_io_capacity = 4000;    -- 提高 I/O 上限
SET GLOBAL innodb_io_capacity_max = 8000;

-- 监控 Purge 完成的 Undo 记录数
SHOW STATUS LIKE 'Innodb_purge%';
-- （MySQL 8.0 中这些指标在 performance_schema.global_status 中）
SELECT NAME, COUNT
FROM information_schema.INNODB_METRICS
WHERE SUBSYSTEM = 'purge'
ORDER BY NAME;
-- purge_del_mark_records：被 Purge 清理的 DELETE 标记行数
-- purge_undo_log_pages：Purge 处理的 Undo 页数
```

## 适用场景

- **定期维护**：设置长事务超时或监控脚本，发现超过 60-120 秒未提交的事务时发出告警，避免 Purge 积压
- **大批量删除后优化**：DELETE 大量数据后，等待 Purge 清理完成，再执行 `ANALYZE TABLE` 更新统计信息（或 `OPTIMIZE TABLE` 重建表回收空间）

## 常见问题

**History List 积压到 50000 了，如何快速处理？**

首先找到并终止阻止 Purge 的长事务：`SELECT trx_id, trx_started, trx_query FROM information_schema.INNODB_TRX ORDER BY trx_started`，找出最老的事务并评估是否可以 `KILL` 对应的连接。其次临时增大 `innodb_purge_threads`（如从 4 改为 8）和 `innodb_io_capacity`，让 Purge 更快地处理积压。一旦最老的活跃事务提交，History List 通常会快速下降。

---

## 注意事项

- Purge 是后台异步操作，不阻塞正常的 DML 操作，但 Purge 的 I/O 会与正常业务 I/O 竞争。在 I/O 密集型系统中，Purge 的积压（History List 过长）会间接影响查询性能（MVCC 版本链变长，SELECT 需要遍历更多 Undo 版本）。
- 使用 `TRUNCATE TABLE` 而不是 `DELETE FROM table` 清空大表，因为 TRUNCATE 不产生 Undo Log，不需要 Purge，也不会产生 delete-marked 行。但 TRUNCATE 不可回滚，使用前需确认。

---

## 总结

Purge 线程负责两项工作：物理清理 DELETE 标记的行和清理不再需要的 UPDATE Undo Log。触发条件是 Undo Log 的事务 ID 小于所有活跃事务的最小 ID。通过 `innodb_purge_threads`（默认 4）控制并发度，通过 History List 长度（`SHOW ENGINE INNODB STATUS`）监控积压情况。长事务是 Purge 积压的主要原因，必须定期监控和处理超时未提交的事务。History List 正常应小于 1000，超过 10000 需要立即排查。

# Undo Tablespace 表空间管理

Undo Tablespace（Undo 表空间）是 InnoDB 存储 Undo Log 的专用表空间。MySQL 8.0 将 Undo Log 从系统表空间（ibdata1）迁移到了独立的 Undo 表空间文件，支持自动收缩（Truncate），解决了旧版本中 ibdata1 无法缩小的历史问题。每个 Undo 表空间最多可包含 128 个回滚段（Rollback Segment），每个回滚段最多 1024 个 Undo Slot，理论上支持数万个并发事务同时运行。

---

## Undo Tablespace 的演变

```
MySQL 5.7 及之前：
  Undo Log 存储在系统表空间（ibdata1）中
  问题：ibdata1 只增不减（即使 Purge 清理了旧版本，空间不会归还 OS）
  解决方案：只能通过 mysqldump + 重建来收缩 ibdata1

MySQL 8.0：
  默认创建 2 个独立 Undo 表空间（undo_001, undo_002）
  支持 innodb_undo_log_truncate = ON（自动收缩）
  支持 ALTER UNDO TABLESPACE 管理
  支持运行时新增/停用 Undo 表空间
```

## 查看和管理 Undo 表空间

```sql
-- 查看 Undo 表空间列表
SELECT SPACE_ID, NAME, FILE_SIZE, STATE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'innodb_undo%'
   OR NAME LIKE 'undo_%';
-- NAME 示例：innodb_undo_001、innodb_undo_002
-- STATE：online（正常使用）、empty（已清空，可以被删除）

-- 通过另一个视图查看
SELECT TABLESPACE_NAME, FILE_NAME, TOTAL_EXTENTS, EXTENT_SIZE
FROM information_schema.FILES
WHERE TABLESPACE_NAME LIKE '%undo%';

-- 查看 Undo 表空间的文件路径
SHOW VARIABLES LIKE 'innodb_undo_directory';
-- 默认：与 datadir 相同
-- 可以配置到独立的 SSD 上以提升 Undo I/O 性能

-- 查看 Undo 表空间数量配置
SHOW VARIABLES LIKE 'innodb_undo_tablespaces';
-- MySQL 8.0 默认值：2（最少 2 个，才能支持 Truncate）
-- 范围：2-127
```

## 创建新的 Undo 表空间

```sql
-- 运行时创建新的 Undo 表空间（MySQL 8.0.14+）
CREATE UNDO TABLESPACE undo_003
    ADD DATAFILE 'undo_003.ibu';
-- 文件扩展名 .ibu（undo 专用）

-- 验证创建成功
SELECT SPACE_ID, NAME, STATE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME = 'innodb_undo_003';
-- STATE = 'online'（已激活并可使用）

-- 将 Undo 表空间文件放到不同磁盘（性能优化）
CREATE UNDO TABLESPACE undo_fast
    ADD DATAFILE '/fast_nvme/mysql/undo_fast.ibu';
```

## 停用和删除 Undo 表空间

```sql
-- 步骤1：将 Undo 表空间设为 inactive（停止分配新事务到该表空间）
ALTER UNDO TABLESPACE undo_003 SET INACTIVE;
-- 已有事务继续使用，新事务不再分配到该表空间

-- 步骤2：等待该表空间变为 empty（所有事务完成，Purge 清空该表空间）
-- 监控状态变化：
SELECT NAME, STATE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME = 'innodb_undo_003';
-- STATE: active → inactive → empty

-- 步骤3：STATE 变为 empty 后，删除 Undo 表空间
DROP UNDO TABLESPACE undo_003;

-- 注意：必须至少保留 2 个 active Undo 表空间
-- 尝试删除最后一个 active Undo 表空间会报错
```

## 自动收缩 Undo 表空间（Truncate）

```sql
-- 查看自动收缩配置
SHOW VARIABLES LIKE 'innodb_undo_log_truncate';
-- 默认：ON（MySQL 8.0 默认开启自动收缩）

-- 控制触发收缩的阈值
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';
-- 默认：1073741824（1 GB）
-- 当 Undo 表空间超过此阈值时，触发自动收缩

-- 自动收缩的流程：
-- 1. 当某个 Undo 表空间大小 > innodb_max_undo_log_size（1GB）时
-- 2. InnoDB 将该表空间标记为 inactive
-- 3. 等待该表空间的所有活跃事务提交，Purge 线程清空所有 Undo Log
-- 4. 将文件截断（Truncate）到初始大小
-- 5. 重新标记为 active

-- 监控收缩操作
SELECT NAME, STATE, TABLESPACE_TYPE
FROM information_schema.INNODB_TABLESPACES
WHERE TABLESPACE_TYPE = 'UNDO';
-- 收缩中：STATE 会短暂变为 inactive

-- 查看 Purge 状态
SHOW ENGINE INNODB STATUS \G
-- 查找 TRANSACTIONS 部分：
-- Purge done for trx's n:o < XXXXX undo n:o < 0 state: running
```

## Undo 表空间的大小估算

```sql
-- 影响 Undo 表空间大小的因素：
-- 1. 活跃事务的数量和 Undo 量
-- 2. 长事务（阻止旧版本被 Purge）
-- 3. 写入频率（修改操作越多，Undo 越多）

-- 查看当前 Undo 表空间实际大小
SELECT
    NAME,
    FILE_SIZE / 1024 / 1024 AS size_mb
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE '%undo%';

-- 查看 History List 长度（Purge 积压）
-- History List 越长，说明有越多 UPDATE Undo 等待被 Purge
SHOW ENGINE INNODB STATUS \G
-- 在 TRANSACTIONS 部分：
-- History list length XXXX
-- 正常应小于 1000，超过 10000 说明积压严重
```

## 适用场景

- **Undo 表空间膨胀**：通过 `innodb_undo_log_truncate=ON` 和 `innodb_max_undo_log_size` 配置自动收缩，无需人工干预
- **独立磁盘优化**：将 Undo 表空间放在高速 SSD 上（`innodb_undo_directory` 或创建时指定路径），与数据文件和 Redo Log 分离
- **大并发系统**：增加 Undo 表空间数量（`CREATE UNDO TABLESPACE`）分散回滚段竞争

---

## 常见问题

**Undo 表空间的自动 Truncate 会影响正在运行的事务吗？**

不会阻断正在运行的事务。Truncate 是先将表空间标记为 inactive（新事务不分配到该表空间，但已有事务继续），等所有已有事务完成并经过 Purge 清空后，才执行文件 Truncate。整个过程对业务透明，只是短暂的收缩操作。但如果有长事务一直不提交，该 Undo 表空间将无法完成 Truncate（因为 Purge 被长事务阻止）。

---

## 注意事项

- MySQL 8.0 默认的 2 个 Undo 表空间（`innodb_undo_tablespaces=2`）在大多数场景下已经足够。如果系统并发极高（几千个并发写事务），可以增加到 4-8 个，以减少多个事务竞争同一个回滚段的情况。
- Undo 表空间的自动收缩（Truncate）需要至少 2 个 active 的 Undo 表空间，因为收缩时会临时将一个表空间设为 inactive，另一个继续提供服务。这也是最少需要 2 个 Undo 表空间的原因。

---

## 总结

Undo Tablespace 是 MySQL 8.0 独立出来的 Undo Log 存储区域（`.ibu` 文件，默认 `undo_001/undo_002`）。通过 `innodb_undo_log_truncate=ON`（默认）和 `innodb_max_undo_log_size`（默认 1GB）配置自动收缩，解决旧版本 ibdata1 膨胀无法收缩的问题。可以通过 `CREATE UNDO TABLESPACE` 添加新表空间，通过 `ALTER UNDO TABLESPACE ... SET INACTIVE` + `DROP UNDO TABLESPACE` 删除不需要的表空间。至少需要保留 2 个 active Undo 表空间。

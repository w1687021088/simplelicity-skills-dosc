# History List 长度监控

History List Length（历史列表长度）是 InnoDB 中衡量 Undo Log 积压情况的核心指标，表示已提交事务但其 Undo Log 尚未被 Purge 线程清理的事务数量。这个值越大，说明 Purge 越滞后，Undo 表空间占用越多，同时 MVCC 版本链越长，影响读操作性能。正常生产环境中应将 History List Length 控制在数百以内，超过 10000 需要立即排查。

---

## History List 的含义

```
History List 记录的内容：
  每个已提交事务（产生了 UPDATE/DELETE Undo Log）在提交时
  会将自己的 Undo Log 添加到 History List 中
  Purge 线程从 History List 中取出最老的条目逐步清理

History List Length = 
  "已提交、产生了 UPDATE/DELETE Undo 的事务数量，且 Undo 尚未被 Purge 清理"

History List Length 增长原因：
  1. 写入速度 > Purge 处理速度（正常，Purge 通常能追上）
  2. 长事务阻止 Purge 推进（Purge 无法越过最老活跃事务的事务ID）
  3. innodb_purge_threads 太少（Purge 能力不足）
  4. I/O 性能瓶颈（Purge 需要读写 Undo 页）
```

---

## 查看 History List 长度

```sql
-- 方法1：SHOW ENGINE INNODB STATUS（最常用）
SHOW ENGINE INNODB STATUS \G
-- 在 TRANSACTIONS 部分：
-- Trx id counter 12345678
-- Purge done for trx's n:o < 12345100 undo n:o < 0 state: running but idle
-- History list length 578
--   ↑ 这就是 History List Length
-- 578 < 1000，属于正常水平

-- 方法2：information_schema.INNODB_METRICS
SELECT NAME, COUNT, STATUS
FROM information_schema.INNODB_METRICS
WHERE NAME = 'trx_rseg_history_len';
-- COUNT 列即为 History List Length

-- 方法3：performance_schema（MySQL 8.0+）
SELECT VARIABLE_VALUE AS history_list_length
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Innodb_history_list_length';
-- MySQL 8.4 新增此状态变量，无需解析 SHOW ENGINE INNODB STATUS
```

## History List 的监控告警阈值

| History List Length | 状态 | 建议操作 |
|--------------------|------|---------|
| < 1000 | 正常 | 无需干预 |
| 1000 - 10000 | 偏高 | 检查是否有长事务，确认 Purge 正在工作 |
| 10000 - 100000 | 告警 | 排查长事务，增大 purge_threads |
| > 100000 | 严重 | 立即排查，可能存在长时间未提交的事务 |
| > 1000000 | 紧急 | Undo 表空间可能耗尽，必须立即处理 |

## 排查 History List 增长的原因

```sql
-- 步骤1：找出最老的活跃事务（Purge 被阻止的元凶）
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS trx_age_seconds,
    trx_rows_modified,
    trx_rows_locked,
    LEFT(trx_query, 200) AS trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC
LIMIT 10;
-- trx_age_seconds 越大，说明事务运行时间越长
-- 这些长事务是阻止 Purge 的主要原因

-- 步骤2：确认 Purge 的推进位置
SHOW ENGINE INNODB STATUS \G
-- Purge done for trx's n:o < 12345100
-- 当前事务计数器：12345678
-- Purge 已处理到事务 12345100，还剩 578 个未处理
-- 如果 Purge 的推进速度很慢（多次查询差值小），说明 Purge 能力不足

-- 步骤3：检查 Purge 线程数
SHOW VARIABLES LIKE 'innodb_purge_threads';
-- 如果是 1-2，可以增大到 4-8

-- 步骤4：确认 I/O 是否瓶颈
SHOW STATUS LIKE 'Innodb_os_log_fsyncs';
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';
-- 如果磁盘读写接近上限，Purge I/O 可能被压缩
```

## 自动化监控脚本思路

```sql
-- 创建监控存储过程（定期检查 History List）
DELIMITER $$
CREATE PROCEDURE check_history_list_alert()
BEGIN
    DECLARE hist_len BIGINT DEFAULT 0;
    DECLARE long_trx_count INT DEFAULT 0;

    -- 获取 History List 长度
    SELECT VARIABLE_VALUE INTO hist_len
    FROM performance_schema.global_status
    WHERE VARIABLE_NAME = 'Innodb_history_list_length';

    -- 获取超过 60 秒的活跃事务数
    SELECT COUNT(*) INTO long_trx_count
    FROM information_schema.INNODB_TRX
    WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;

    -- 输出监控结果
    SELECT
        hist_len AS history_list_length,
        long_trx_count AS long_transactions_over_60s,
        CASE
            WHEN hist_len > 100000 THEN 'CRITICAL'
            WHEN hist_len > 10000  THEN 'WARNING'
            WHEN hist_len > 1000   THEN 'NOTICE'
            ELSE 'OK'
        END AS status;
END$$
DELIMITER ;

-- 调用
CALL check_history_list_alert();
```

## History List 与 MVCC 查询性能

```sql
-- History List 增长对查询的影响：
-- 每次 SELECT 读取某行时，需要沿着版本链（Undo Log 链）查找可见版本
-- 版本链越长（更多 UPDATE/DELETE 未被 Purge），遍历时间越长

-- 举例：
-- 一行被修改了 10000 次（10000 条版本链），最老事务的 Read View 需要读最旧版本
-- → SELECT 需要遍历 10000 条 Undo Log 才能找到可见版本
-- → 查询时间大幅增加（可能从毫秒级变为秒级）

-- 监控单行版本链长度（间接方法）
-- 通过 information_schema.INNODB_BUFFER_PAGE 查看具体页
-- 或通过分析频繁更新的表的查询性能变化来判断
```

## 处理 History List 积压

```sql
-- 方案1：终止长事务（最直接）
-- 找到阻止 Purge 的最老事务
SELECT trx_id, trx_mysql_thread_id, trx_started
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC LIMIT 1;

-- 终止对应的连接
KILL QUERY <trx_mysql_thread_id>;  -- 终止 SQL，不断开连接
-- 或
KILL CONNECTION <trx_mysql_thread_id>;  -- 断开连接（事务自动回滚）

-- 方案2：加速 Purge
SET GLOBAL innodb_purge_threads = 8;     -- 增加 Purge 并发度
SET GLOBAL innodb_purge_batch_size = 1000;  -- 增加每批处理量
SET GLOBAL innodb_io_capacity = 4000;    -- 提升 I/O 上限

-- 方案3：应用层预防
-- 设置短事务超时：在应用代码中设置事务超时（如 SET innodb_lock_wait_timeout）
-- 避免在事务中执行耗时操作（如调用外部 API）
-- 使用短事务而非长事务（批量操作分小批次提交）
```

## 适用场景

- **日常运维监控**：将 History List Length 加入数据库监控大盘（Prometheus + Grafana），设置阈值告警（1000 通知，10000 告警，100000 紧急）
- **慢查询排查**：当某个 SELECT 慢得不寻常时，检查 History List 长度，如果很高则可能是版本链遍历导致的，而不是索引问题

## 常见问题

**History List 已经降到 0 了，但 Undo 表空间文件还是很大，如何收缩？**

History List 为 0 说明 Purge 已将所有积压清理完毕，Undo Log 数据已删除。但 Undo 表空间文件（`.ibu`）不会自动缩小（已分配的文件页被释放但文件大小保持）。需要依靠 `innodb_undo_log_truncate=ON` 的自动 Truncate 机制：当 Undo 表空间大小超过 `innodb_max_undo_log_size`（默认 1GB）时，InnoDB 会自动截断文件。也可以手动触发：`ALTER UNDO TABLESPACE innodb_undo_001 SET INACTIVE` → 等待 STATE=empty → InnoDB 自动 Truncate。

## 注意事项

- 在 MySQL 8.4 中，`Innodb_history_list_length` 已作为独立的 `global_status` 变量暴露，可以通过 `performance_schema.global_status` 直接查询，不再需要解析 `SHOW ENGINE INNODB STATUS` 的文本输出，更适合自动化监控。
- 设置 `innodb_max_purge_lag`（默认 0，表示不限制）可以在 History List 过长时自动降低 DML 操作速度（增加延迟），给 Purge 追上的机会。但这会降低业务吞吐量，一般不在生产环境使用，用于测试场景验证系统行为。

---

## 总结

History List Length 是衡量 InnoDB Undo Log Purge 积压的核心监控指标。通过 `SHOW ENGINE INNODB STATUS`（History list length）或 `performance_schema.global_status`（Innodb_history_list_length，MySQL 8.4+）查看。正常值 < 1000，超过 10000 需排查长事务，超过 100000 需立即处理。长事务是积压的主要原因，解决方法是终止长事务 + 增大 `innodb_purge_threads`。History List 过高会导致 MVCC 版本链变长，SELECT 查询需要遍历更多 Undo 版本，性能下降。

# INSERT Undo 与 UPDATE Undo 差异

InnoDB 根据 DML 操作类型生成不同类型的 Undo Log 记录，主要分为 INSERT Undo 和 UPDATE Undo（UPDATE 和 DELETE 都使用 UPDATE Undo）。两种类型的 Undo Log 在内容、生命周期和使用方式上存在本质差异：INSERT Undo 只用于回滚，不用于 MVCC，因此事务提交后可以立即删除；UPDATE Undo 除了用于回滚，还需要为其他事务的 MVCC 读提供历史版本，必须保留到没有任何事务需要该版本为止。

---

## 两种 Undo Log 的对比

| 对比维度 | INSERT Undo | UPDATE Undo |
|---------|------------|------------|
| 对应操作 | INSERT | UPDATE、DELETE |
| 记录内容 | 被插入行的主键值 | 被修改列的修改前值（含所有列，或差异列）|
| 是否用于 MVCC | 否（新插入的行对旧事务不可见）| 是（旧事务需要读取修改前的历史版本）|
| 事务提交后 | 立即可以删除 | 保留至没有事务需要该版本为止 |
| 回滚操作 | DELETE 该主键行 | 将修改列还原为旧值 |
| 存储结构 | INSERT Undo Segment | UPDATE Undo Segment |

---

## INSERT Undo 的详细行为

```sql
-- INSERT 操作的 Undo Log 内容：
-- 记录被插入行的主键（Primary Key）
-- 回滚时：执行 DELETE WHERE pk = 记录的主键值

-- 举例：
INSERT INTO orders (id, amount, user_id) VALUES (1001, 99.99, 5);
-- 生成的 INSERT Undo Log：
-- type: TRX_UNDO_INSERT_REC
-- 主键：id = 1001

-- 如果事务回滚：
-- DELETE FROM orders WHERE id = 1001;（逻辑上的逆操作）

-- MVCC 视角：INSERT Undo 不需要用于 MVCC
-- 原因：INSERT 生成的新行对事务开始前的 Read View 不可见
--      （新行的 DB_TRX_ID > Read View 中的任何活跃事务 ID）
--      所以其他事务根本不需要通过 Undo Log 访问 INSERT 前的"版本"
--      （因为 INSERT 前该行根本不存在）

-- 事务提交后，INSERT Undo Log 立即加入 purge 队列，可以很快被清理
```

---

## UPDATE Undo 的详细行为

```sql
-- UPDATE 操作的 Undo Log 内容：
-- 记录被修改列的修改前值（旧值）
-- 回滚时：将这些列还原为旧值

-- 举例：
UPDATE orders SET amount = 199.99, status = 'paid' WHERE id = 1001;
-- 假设修改前：amount = 99.99, status = 'pending'
-- 生成的 UPDATE Undo Log：
-- type: TRX_UNDO_UPD_EXIST_REC
-- 主键：id = 1001
-- 修改列：amount_old = 99.99, status_old = 'pending'

-- 如果事务回滚：
-- UPDATE orders SET amount = 99.99, status = 'pending' WHERE id = 1001;

-- DELETE 操作同样使用 UPDATE Undo（两阶段删除）：
DELETE FROM orders WHERE id = 1001;
-- 第一步（DELETE MARK）：将行标记为"删除"（delete-marked flag = 1）
--   生成 UPDATE Undo Log：记录行的完整内容（用于 MVCC 读取旧版本）
-- 第二步（PURGE）：事务提交且无事务需要该版本后，物理删除行
--   Undo Log 也在此时被物理清理

-- UPDATE Undo 必须保留供 MVCC 使用：
-- 场景：事务 A 修改了一行（生成 UPDATE Undo），事务 A 提交
--      事务 B（开始于 A 提交之前）仍在运行，需要读取该行的旧版本
--      → UPDATE Undo 必须保留，直到事务 B 结束（或所有早于 A 提交的事务结束）
```

---

## Undo Log 版本链

```
UPDATE Undo 构成了行数据的版本链（Version Chain）：

行记录（当前最新版本）：
  DB_TRX_ID = 事务C的ID（最近修改的事务）
  DB_ROLL_PTR → 指向事务C产生的 UPDATE Undo Log

  事务C的 UPDATE Undo Log（中间版本）：
    old_value: {amount: 199.99, status: 'paid'}
    DB_ROLL_PTR → 指向事务A产生的 UPDATE Undo Log

    事务A的 UPDATE Undo Log（最旧版本）：
      old_value: {amount: 99.99, status: 'pending'}
      DB_ROLL_PTR → NULL（没有更旧的版本）

版本链遍历：
  事务B读取此行时：
  → 检查当前版本的 DB_TRX_ID：事务C，比B的 Read View 新，不可见
  → 通过 DB_ROLL_PTR 找到事务C的 Undo Log：中间版本，DB_TRX_ID仍为C
  → 继续通过 DB_ROLL_PTR 找到事务A的 Undo Log：旧版本，DB_TRX_ID为A
  → A 在 B 的 Read View 中可见 → 返回这个旧版本（99.99, 'pending'）
```

## 两种 Undo 的 Segment 分配

```sql
-- InnoDB 将 INSERT Undo 和 UPDATE Undo 分配到不同的 Undo Segment
-- 同一个回滚段（Rollback Segment）中包含两类 Undo Segment：
-- type = TRX_UNDO_INSERT：用于存储 INSERT Undo
-- type = TRX_UNDO_UPDATE：用于存储 UPDATE Undo

-- 分开管理的优势：
-- INSERT Undo 在提交后可以快速释放（不需要等待 MVCC）
-- UPDATE Undo 需要等待 Purge，生命周期更长
-- 分开管理避免两种 Undo 混合导致空间碎片化

-- 查看当前 Undo 使用情况
SELECT * FROM information_schema.INNODB_TRX
WHERE trx_id IN (
    SELECT trx_id FROM information_schema.INNODB_TRX
);
-- 正在运行的事务的 Undo Log 无法被 Purge
```

## 适用场景

- **大批量 DELETE 优化**：DELETE 操作使用 UPDATE Undo，DELETE 大量行时会产生大量 UPDATE Undo，Purge 需要时间清理。建议大批量删除分批进行（每次几千行），避免单次操作产生过多 Undo Log
- **长事务问题排查**：长时间运行的事务导致 UPDATE Undo 无法 Purge（History List 增长），进而导致 Undo 表空间膨胀

## 常见问题

**UPDATE 只修改了 2 列，Undo Log 记录的是全部列还是只有 2 列？**

InnoDB 只记录被修改的列的旧值（不记录未修改的列）。但如果表有主键索引或包含 BLOB/TEXT 大列，处理方式略有不同。对于 MVCC 读取，InnoDB 在访问 Undo Log 记录时，会将 Undo 中的旧列值与当前行（的未修改列）合并，构建出完整的历史版本行记录。

---

## 注意事项

- `TRUNCATE TABLE` 不产生 Undo Log（它是 DDL 操作，直接删除表数据文件），因此 TRUNCATE 不能回滚。相比之下，`DELETE FROM table`（不带 WHERE）会产生大量 UPDATE Undo，虽然可以回滚，但会产生大量 Undo Log 记录，性能较差。
- 对于主键 UPDATE（修改主键值），InnoDB 内部会分解为一次 DELETE + 一次 INSERT，因此会同时产生 UPDATE Undo（对应 DELETE 部分）和 INSERT Undo（对应 INSERT 部分）。

---

## 总结

INSERT Undo 只记录主键，用于回滚时的 DELETE 操作，事务提交后可立即清理，不用于 MVCC。UPDATE Undo（包含 DELETE 操作）记录修改列的旧值，除回滚外还构成行的版本链（通过 DB_ROLL_PTR 链接），供 MVCC 读取历史版本，必须保留到所有需要该版本的事务结束后才能被 Purge。这一差异是 Undo Log 管理和 Purge 机制设计的核心依据。

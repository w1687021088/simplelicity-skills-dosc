# User Records 用户记录

User Records（用户记录区）是 InnoDB 数据页中存储实际行数据的区域，位于 Infimum/Supremum 之后、Free Space 之前。每条用户记录由记录头信息（Record Header）和实际数据列组成，页内所有记录通过单向链表按主键顺序相连，从最小虚拟记录（Infimum）到最大虚拟记录（Supremum）构成一个有序链表。理解 User Records 的结构是掌握 InnoDB 行记录存储和查询执行的基础。

---

## 记录在页内的物理布局

```
数据页内 User Records 区域（以 COMPACT 格式为例）：

页内地址（从低到高）：
  ...
  [Infimum 记录（虚拟最小记录）]
  ↕ 链表指针（next record offset）
  [行记录1：Record Header + 实际列值]
  ↕
  [行记录2：Record Header + 实际列值]
  ↕
  [行记录3：Record Header + 实际列值]
  ↕
  [Supremum 记录（虚拟最大记录）]
  ...

注意：物理地址顺序不代表逻辑顺序
  → 行记录按插入顺序物理存储
  → 通过 Record Header 中的 next record offset（下一条记录的相对偏移）
    构成按主键顺序的逻辑链表
  → 物理上可以是乱序的，逻辑上是有序的
```

## Record Header（记录头信息）

```
COMPACT 格式的 Record Header（5字节）：

位字段布局（从高到低）：
┌────────────┬─────┬────────┬─────────────────┬──────────────┐
│ reserved   │ del │ min_rec│ n_owned         │ heap_no      │
│ (2 bit)    │ (1) │ (1)    │ (4 bit)         │ (13 bit)     │
├────────────┴─────┴────────┴─────────────────┴──────────────┤
│              record type (3 bit)                            │
├─────────────────────────────────────────────────────────────┤
│              next record offset (16 bit)                    │
└─────────────────────────────────────────────────────────────┘

字段含义：
  del（delete_mask，1bit）：
    是否被标记为删除（DELETE 操作设置此位，Purge 后才物理删除）

  min_rec（min_rec_flag，1bit）：
    是否是 B+ Tree 非叶子层中的最小记录（路由用）

  n_owned（4bit）：
    该记录负责的 Page Directory 槽内记录数量（4-8条）
    仅 Slot 的最后一条记录的 n_owned > 0

  heap_no（13bit）：
    该记录在页内堆（Heap）中的序号
    0 = Infimum，1 = Supremum，2 开始 = 用户记录

  record_type（3bit）：
    000 = 普通用户记录（B+ Tree 叶子节点）
    001 = B+ Tree 非叶子节点记录（中间节点）
    010 = Infimum 虚拟记录
    011 = Supremum 虚拟记录

  next_record（16bit）：
    下一条记录相对当前记录的偏移量（有符号整数）
    通过此字段构成按主键顺序的单向链表
```

## 行记录的数据部分

```sql
-- COMPACT 格式行记录（列值之前）的信息：
-- 变长字段长度列表（逆序存储各变长列的长度）
-- NULL 值位图（每个可为 NULL 的列占 1 bit）
-- Record Header（5字节）
-- 实际列值（按列定义顺序存储）
-- 隐藏列（DB_TRX_ID 6字节 + DB_ROLL_PTR 7字节，仅聚簇索引）
-- （如果没有显式主键，还有 DB_ROW_ID 6字节）

-- 举例：表 orders（id INT, user_id INT, amount DECIMAL(10,2), note VARCHAR(255)）
-- 行数据组成（COMPACT 格式）：
-- [变长列长度列表：note 的实际长度] [NULL 位图] [Record Header]
-- [id（4字节）] [user_id（4字节）] [amount（4字节）]
-- [note（实际字节数）] [DB_TRX_ID（6字节）] [DB_ROLL_PTR（7字节）]

-- 查看行数据的实际大小
SELECT
    TABLE_NAME,
    AVG_ROW_LENGTH,
    DATA_LENGTH,
    (DATA_LENGTH / TABLE_ROWS) AS actual_avg_row
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'orders'
  AND TABLE_ROWS > 0;
```

## Infimum 与 Supremum

```
Infimum（虚拟最小记录）：
  heap_no = 0
  record_type = 010（Infimum 类型）
  next_record → 指向页内第一条用户记录
  "内容"：字符串 "infimum\0"
  作用：链表头部边界，遍历从 Infimum 的 next 开始

Supremum（虚拟最大记录）：
  heap_no = 1
  record_type = 011（Supremum 类型）
  next_record = 0（链表终止）
  "内容"：字符串 "supremum"
  作用：链表尾部边界，最大锁范围（临键锁会锁定 Supremum）

链表遍历示例：
  SELECT * FROM orders WHERE id BETWEEN 100 AND 200;
  → 从 B+ Tree 找到第一个 id >= 100 的叶子页和记录
  → 沿 next_record 链表遍历，直到 id > 200 或到达 Supremum
  → 如果当前页遍历完（到 Supremum），通过 FIL_PAGE_NEXT 跳到下一页
```

## 删除记录的处理

```sql
-- DELETE 操作在 User Records 中的处理：
-- 1. 将记录的 delete_mask 设置为 1（标记为删除）
-- 2. 不立即物理删除（该记录仍占用空间）
-- 3. 将该记录从 next_record 链表中断开（其他记录绕过它）
-- 4. 将该记录的空间加入 PAGE_FREE 链表（可复用）
-- 5. PAGE_GARBAGE 增加（垃圾字节数）
-- 6. 后台 Purge 线程：在确认没有事务需要此记录的 MVCC 版本后
--    物理清除（将其从 PAGE_FREE 链表移除，内存标记为可覆盖）

-- 查看页内删除标记记录的比例（间接方式）
-- PAGE_N_HEAP 包含删除标记记录，PAGE_N_RECS 不包含
SELECT PAGE_NUMBER,
       NUMBER_RECORDS,
       INDEX_ID
FROM information_schema.INNODB_BUFFER_PAGE
WHERE TABLE_NAME = '`myapp`.`orders`'
  AND PAGE_TYPE = 'INDEX'
ORDER BY PAGE_NUMBER;
```

## 适用场景

- **存储优化**：了解行记录的 Record Header 和实际数据布局，有助于计算实际行大小（含 Header、NULL 位图、隐藏列），从而更准确地预估表的存储空间
- **锁分析**：理解 User Records 的单向链表结构和 Supremum 的特殊角色，有助于理解临键锁（Next-Key Lock）和间隙锁（Gap Lock）的锁定范围

## 常见问题

**为什么 SELECT COUNT(*) FROM 一张表比预想的慢？**

`COUNT(*)` 需要全表扫描（除非有更合适的索引统计）。在扫描时，InnoDB 需要加载每个数据页，沿 User Records 链表遍历所有有效记录（delete_mask = 0 的记录）并计数。如果表数据量大且 Buffer Pool 命中率低，大量页从磁盘读取，是 COUNT(*) 慢的根本原因。InnoDB 不像 MyISAM 那样有精确的行数计数器，这是设计上的权衡（支持 MVCC 的代价）。

---

## 注意事项

- User Records 区域并不是紧密排列的连续存储，删除后会产生"空洞"（delete-marked 记录占用的空间）。虽然新插入会优先复用这些空间，但当空洞较多时，页的利用率会下降。`OPTIMIZE TABLE` 重建表可以消除页内空洞，但代价是锁表。
- 行记录中 Record Header 里的 `next_record` 是相对偏移量，不是绝对地址。这使得 InnoDB 在页内移动记录时只需要修改 `next_record` 指针，而不需要更新所有指向该记录的引用。

---

## 总结

User Records 是数据页中存储实际行数据的区域，每条记录由 Record Header（5字节，含 delete_mask、heap_no、record_type、next_record 等字段）和实际列值组成。所有记录通过 `next_record` 字段构成按主键顺序的单向逻辑链表，从 Infimum 开始，到 Supremum 结束。DELETE 操作设置 `delete_mask=1` 并断开链表，不立即物理删除（等 Purge 清理）。COMPACT 行格式在数据前存储变长列长度列表和 NULL 位图，聚簇索引行包含 DB_TRX_ID 和 DB_ROLL_PTR 隐藏列用于 MVCC。

# System Tablespace 系统表空间（ibdata1）

System Tablespace（系统表空间）是 InnoDB 最古老的存储区域，对应数据目录下的 `ibdata1` 文件（或多个 `ibdata*` 文件）。它最初承担了 InnoDB 所有内部数据结构的存储职责，随着 MySQL 版本的演进，其中的很多内容已被迁移到独立文件，但仍保留了若干核心功能。理解系统表空间的历史和现状，是理解 InnoDB 存储架构演变的基础。

---

## 系统表空间的历史内容变化

| 内容 | MySQL 5.7 及之前 | MySQL 8.0+ |
|------|----------------|-----------|
| InnoDB 数据字典 | 存储在系统表空间 | 迁移到 MySQL 数据字典（.sdi 文件）|
| Doublewrite Buffer | 存储在系统表空间 | MySQL 8.0.20+ 迁移到独立 .dblwr 文件 |
| Insert Buffer / Change Buffer | 存储在系统表空间 | 仍在系统表空间（未迁移）|
| Undo Log | 存储在系统表空间 | 迁移到独立 Undo Tablespace（undo_001/002）|
| Rollback Segments | 存储在系统表空间 | 系统表空间保留少量，主要在 Undo Tablespace |
| 用户表数据/索引 | 可以存储（早期默认）| 建议使用 file-per-table（默认 ON）|

## 系统表空间的当前内容（MySQL 8.0+）

```sql
-- MySQL 8.0 中系统表空间（ibdata1）仍然存储：
-- 1. Change Buffer（插入缓冲）
-- 2. 事务系统相关的元数据页（如回滚段头页）
-- 3. 某些全局 InnoDB 内部结构

-- 查看 ibdata1 文件大小
-- （Linux）ls -lh /var/lib/mysql/ibdata1
-- （Windows）dir C:\ProgramData\MySQL\MySQL Server 8.4\Data\ibdata1

-- 查看系统表空间配置
SHOW VARIABLES LIKE 'innodb_data_file_path';
-- 默认：ibdata1:12M:autoextend
-- 含义：ibdata1 文件，初始 12MB，自动扩展（无上限）

-- 查看系统表空间信息
SELECT SPACE_ID, NAME, STATE, SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME = 'innodb_system';
```

## 系统表空间的配置

```sql
-- 查看数据目录
SHOW VARIABLES LIKE 'datadir';

-- 配置多个系统表空间文件（适合将大文件分散到多个磁盘）
-- my.cnf 配置：
-- [mysqld]
-- innodb_data_file_path = ibdata1:512M:autoextend
-- 或拆分到多个文件：
-- innodb_data_file_path = ibdata1:1G;ibdata2:1G:autoextend
-- 注意：分号分隔，只有最后一个文件可以 autoextend

-- 限制自动扩展的上限（避免 ibdata1 无限增长）
-- innodb_data_file_path = ibdata1:512M:autoextend:max:2G
-- 超过 2G 后停止自动扩展（写入会报错）

-- 注意：innodb_data_file_path 只能在初始化时配置
-- 修改需要停机 + 导出数据 + 重新初始化（破坏性操作）
```

## ibdata1 膨胀与处理

```sql
-- ibdata1 膨胀的主要原因（现代 MySQL 8.0 相对较少）：
-- 1. Undo Log 积压（MySQL 5.7 之前）→ MySQL 8.0 已迁移到独立 Undo 表空间
-- 2. Change Buffer 数据量大
-- 3. 内部管理页面积累

-- MySQL 8.0 的 ibdata1 通常维持在较小的大小（几十 MB 到几百 MB）
-- 因为大部分内容已迁移到其他独立文件

-- 如果 ibdata1 异常增大（超过 1GB）：
-- 检查 Change Buffer 大小
SHOW ENGINE INNODB STATUS \G
-- 在 INSERT BUFFER AND ADAPTIVE HASH INDEX 部分
-- 看 Ibuf: size X, free list len X, seg size X

-- 检查是否有大量 UPDATE Undo 残留（MySQL 5.7 及之前）
-- 在 8.0+ 中 Undo 已独立，ibdata1 应该不会因 Undo 膨胀

-- 收缩 ibdata1（破坏性操作，需要完整迁移）：
-- 1. mysqldump 导出全部数据
-- 2. 停止 MySQL
-- 3. 删除 ibdata1（和 ib_logfile0/1）
-- 4. 修改 innodb_data_file_path 配置
-- 5. 重新初始化 MySQL
-- 6. 导入数据
```

## 系统表空间与 file-per-table 的关系

```sql
-- 历史遗留：早期版本默认将用户表存在系统表空间
-- innodb_file_per_table = OFF（已废弃的旧默认）

-- 现代做法（MySQL 8.0 默认 ON）：
SHOW VARIABLES LIKE 'innodb_file_per_table';
-- ON：每个表独立 .ibd 文件（推荐）
-- OFF：表数据存入系统表空间（不推荐）

-- 使用 file-per-table 的优势：
-- → 每个表独立文件，DROP TABLE 后立即释放磁盘空间（ibdata1 无此能力）
-- → 可以将不同表放到不同表空间/磁盘
-- → 表级备份恢复更方便

-- 查看哪些表存储在系统表空间（space_id = 0）
SELECT TABLE_SCHEMA, TABLE_NAME
FROM information_schema.INNODB_TABLES
WHERE SPACE = 0 AND TABLE_SCHEMA NOT IN ('mysql', 'sys', 'information_schema', 'performance_schema');
-- 这些表在系统表空间中，DROP TABLE 后空间不会释放
-- 建议迁移到独立表空间：ALTER TABLE t ENGINE=InnoDB;（重建到 file-per-table）
```

## 适用场景

- **运维监控**：监控 `ibdata1` 大小变化，异常增长时检查 Change Buffer 积压或 Undo 问题（MySQL 5.7）
- **容量规划**：在 MySQL 8.0 环境下，`ibdata1` 通常保持较小，不是磁盘容量规划的主要关注点，重点是各表的独立 `.ibd` 文件

---

## 常见问题

**MySQL 8.0 中 ibdata1 应该有多大？**

在 MySQL 8.0 中，大多数数据已迁移到独立文件，`ibdata1` 主要存储 Change Buffer 和少量内部元数据，正常情况下大小在 12MB 到几百 MB 之间。如果 `ibdata1` 增长到几个 GB，可能是以下原因：Change Buffer 异常积压（检查非唯一索引的写入量）、有表仍然存储在系统表空间（`innodb_file_per_table = OFF` 时创建的表）。

---

## 注意事项

- `innodb_data_file_path` 是初始化时配置的参数，一旦数据库初始化后不能随意更改（更改会导致 InnoDB 无法识别现有数据文件）。如果需要扩展系统表空间（如最后一个文件不是 autoextend 且满了），只能在配置末尾追加新文件，不能修改已有文件条目。
- MySQL 8.4 LTS 中，`ibdata1` 的角色进一步淡化，核心用途仅剩 Change Buffer 的持久化存储。对于新部署的 MySQL 8.4 系统，保持默认的 `ibdata1:12M:autoextend` 配置即可，不需要特别设置。

---

## 总结

系统表空间（`ibdata1`）是 InnoDB 最古老的存储区域，随 MySQL 版本演进，大部分内容已迁移到独立文件（Undo 表空间、Doublewrite 文件、MySQL 数据字典）。MySQL 8.0+ 中 `ibdata1` 主要存储 Change Buffer 和少量内部元数据，正常大小在几十 MB 到几百 MB 之间。通过 `innodb_data_file_path = ibdata1:12M:autoextend` 配置，支持多文件拆分。`ibdata1` 无法收缩（需要完整重建），但 MySQL 8.0 中其膨胀问题已基本消除，主要风险来自 `innodb_file_per_table=OFF` 时创建的表。

# Page Directory 页目录

Page Directory（页目录）是 InnoDB 数据页尾部（File Trailer 之前）的一个槽数组，每个槽（Slot）是 2 字节的偏移量，指向页内某条记录的地址。InnoDB 通过页目录实现页内记录的二分查找：先用二分在槽数组中定位范围（O(log n)），再在该范围内顺序遍历链表（O(k)，k 很小），从而将页内查找的时间复杂度从纯链表遍历的 O(n) 降低到接近 O(log n)。

---

## Page Directory 的结构与规则

```
Page Directory 在数据页中的位置（从页尾向上增长）：

页结构（尾部放大）：
...
[User Records 区域]
[Free Space]
┌─────────────────────────────────────────────────────────┐ ← Free Space 结束
│ Slot N（2字节）→ 指向 Supremum 记录                     │
│ Slot N-1（2字节）→ 指向某条用户记录                     │
│ Slot N-2（2字节）→ 指向某条用户记录                     │
│ ...                                                     │
│ Slot 1（2字节）→ 指向某条用户记录                       │
│ Slot 0（2字节）→ 指向 Infimum 记录                      │
└─────────────────────────────────────────────────────────┘ ← 页尾 - File Trailer
[File Trailer（8字节）]

槽分配规则：
  Slot 0（最小槽，页尾最低地址）→ 永远指向 Infimum（n_owned = 1）
  Slot 最大（页尾最高地址）     → 永远指向 Supremum（n_owned = 1-8）
  中间槽                        → 每个槽管理 4-8 条用户记录
  每个槽指向该槽"负责"的最后一条记录（最大 key 的那条）
```

---

## 槽（Slot）的分配规则

```
槽的分组规则（以 COMPACT 格式为例）：

初始（仅 Infimum + Supremum）：
  Page Directory：[Slot0→Infimum, Slot1→Supremum]
  PAGE_N_DIR_SLOTS = 2

插入第 1 条记录（user_rec_1）：
  Supremum 的 n_owned 从 1 变为 2（Supremum 负责 user_rec_1）
  Page Directory：[Slot0→Infimum, Slot1→Supremum]
  PAGE_N_DIR_SLOTS = 2（未增加新槽）

插入第 2-8 条记录（user_rec_2 到 8）：
  Supremum 的 n_owned 增加到最大 8
  Page Directory：[Slot0→Infimum, Slot1→Supremum]（仍然 2 个槽）

插入第 9 条记录时（超出 8 条/槽上限）：
  将 Supremum 负责的 8 条记录分成两组（各 4 条）
  新建 Slot2 指向前 4 条的最后一条，Slot1（Supremum）负责后 4 条
  PAGE_N_DIR_SLOTS = 3

规律：
  每个槽负责 4-8 条记录
  一个页最多约 16256 字节 / 单行大小 = 最多几百到几千条记录
  Page Directory 最多几十到几百个槽
  二分查找槽需要 log2(槽数) 次比较 → 远小于遍历所有记录
```

## 基于 Page Directory 的查找过程

```sql
-- 查找 id = 5000 的记录（假设主键为 id）：

-- 步骤1：从 B+ Tree 根节点向下找到包含 id=5000 的叶子页
--        （B+ Tree 查找，跨页操作）

-- 步骤2：在叶子页内通过 Page Directory 二分查找：
--   a. 取中间槽 Slot_mid，读取其指向记录的 key
--   b. 如果 key < 5000 → 在右半部分继续二分
--      如果 key > 5000 → 在左半部分继续二分
--      如果 key = 5000 → 在此槽负责的范围内顺序查找
--   c. 找到对应槽后，从该槽指向的记录开始顺序遍历链表（最多 8 条）
--   d. 在 4-8 条记录中找到 id = 5000

-- 总比较次数：log2(槽数) + 4-8 次顺序查找
-- 例如 200 条记录 ≈ 25 个槽：log2(25) ≈ 5 次二分 + 4-8 次顺序 = 约 10 次比较
-- 对比纯链表遍历：平均 100 次比较
-- 二分查找带来约 10x 加速

-- 注意：Page Directory 的查找只在单个页内，
-- 跨页查找（B+ Tree 非叶节点路由）是单独的机制
```

## 查看 Page Directory 相关信息

```sql
-- 通过 Page Header 了解槽数量
-- PAGE_N_DIR_SLOTS 字段（Page Header 第一个 2 字节字段）

-- 通过 information_schema 查看页级信息
SELECT
    PAGE_NUMBER,
    NUMBER_RECORDS,
    INDEX_ID,
    IS_LEAF
FROM information_schema.INNODB_BUFFER_PAGE
WHERE TABLE_NAME = '`myapp`.`orders`'
  AND PAGE_TYPE = 'INDEX'
ORDER BY PAGE_NUMBER;
-- NUMBER_RECORDS：该页的记录数
-- 槽数量 ≈ NUMBER_RECORDS / 6（大约每槽 6 条记录）

-- 估算 Page Directory 大小：
-- 槽数量 × 2 字节
-- 例如：100 条记录 → 约 17 个槽 → 34 字节（占 16KB 页的 0.2%，开销极小）
```

## 适用场景

- **查询优化理解**：二分查找页目录是单页内等值查找的加速机制，理解它有助于解释为什么 InnoDB 的索引查找在到达叶子页后还有一个"页内查找"步骤，以及这个步骤的时间复杂度
- **行数统计**：`PAGE_N_DIR_SLOTS × ~6` 可以快速估算一个页中的记录数（不精确但有参考价值）

## 常见问题

**Page Directory 的槽与 B+ Tree 索引是同一个东西吗？**

不是。Page Directory 是页内（单个数据页）的二分查找加速结构，仅在一个 16KB 页内有效，槽指向的是页内记录的偏移量。B+ Tree 索引是跨页的树形结构，非叶子节点包含键值和子页指针，用于在整个表的数据文件中定位到包含目标记录的叶子页。两者是不同层次的查找机制：先通过 B+ Tree 找到目标页，再通过 Page Directory 在页内快速定位。

---

## 注意事项

- Page Directory 的槽值是从页首开始的字节偏移量（2字节，最大 65535，对于 16KB 页已足够）。槽数组在物理上从页尾向前增长（Slot 0 在最后面，最大槽号在最前面），这与直觉相反但与 InnoDB 的内部实现一致。
- 当页内发生记录删除和碎片整理（Page Reorganization）时，Page Directory 中的槽值（偏移量）会随之更新（记录物理位置改变），但槽的数量和逻辑结构保持不变。

---

## 总结

Page Directory 是数据页尾部的 2 字节槽数组，每个槽指向页内一组记录中最后一条的偏移量，每组 4-8 条记录。初始 2 个槽（指向 Infimum 和 Supremum），随记录插入动态增加。页内查找时，先在 Page Directory 中二分查找（O(log n)）定位到对应槽，再顺序遍历该槽的 4-8 条记录（O(1)），总体接近 O(log n)，远优于纯链表遍历的 O(n)。`PAGE_N_DIR_SLOTS`（Page Header 中）记录当前槽数量。

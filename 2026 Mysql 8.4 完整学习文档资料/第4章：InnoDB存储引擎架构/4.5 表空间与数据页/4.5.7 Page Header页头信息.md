# Page Header 页头信息

Page Header（页头）是 InnoDB 数据页的第二个组成部分，紧跟在 File Header（38字节）之后，占用 56 字节，记录了该页的各种状态信息，包括页内记录数量、空闲空间位置、Page Directory 的槽数量、B+ Tree 层级、上次插入位置等。页头信息是 InnoDB 管理页内记录的"控制中心"，每次插入、删除、更新行记录时都会同步修改相关的页头字段。

---

## Page Header 的字段结构

```
Page Header（56 字节）的字段详解：

PAGE_N_DIR_SLOTS（2字节）：
  Page Directory 中的槽（Slot）数量
  初始：2（Infimum 和 Supremum 各一个槽）
  每 4-8 条记录新增一个槽
  用于二分查找，快速定位记录

PAGE_HEAP_TOP（2字节）：
  堆（Heap）中第一个空闲字节的偏移量
  新记录优先从此位置开始分配（追加写）
  删除记录不会立即释放此处，而是加入删除链表

PAGE_N_HEAP（2字节）：
  页内堆中的记录数量（含 Infimum/Supremum 和已删除记录）
  最高位（bit 15）：1=COMPACT格式，0=REDUNDANT格式

PAGE_FREE（2字节）：
  已删除记录链表的头部偏移量（可复用空间链表）
  新插入记录优先从删除链表中复用空间，再从 Free Space 分配

PAGE_GARBAGE（2字节）：
  已删除记录占用的总字节数（碎片空间大小）
  PAGE_GARBAGE 达到一定程度时，可能触发页内碎片整理（OPTIMIZE）

PAGE_LAST_INSERT（2字节）：
  最后一次插入记录的偏移量
  用于判断是否顺序插入（连续插入同一方向可优化插入位置搜索）

PAGE_DIRECTION（2字节）：
  最后一次插入的方向：
  PAGE_LEFT（1）：向左插入（小于上次）
  PAGE_RIGHT（2）：向右插入（大于上次，顺序插入场景）
  PAGE_NO_DIRECTION（5）：无方向（随机插入）

PAGE_N_DIRECTION（2字节）：
  连续朝同一方向插入的次数

PAGE_N_RECS（2字节）：
  页内实际用户记录数量（不含 Infimum/Supremum，不含已删除记录）

PAGE_MAX_TRX_ID（8字节）：
  修改过此页的最大事务 ID（仅在二级索引页中使用）
  MVCC 快速过滤：如果 PAGE_MAX_TRX_ID < 当前事务 Read View 的低水位，
  则此页的所有行对当前事务可见，无需逐行检查 DB_TRX_ID

PAGE_LEVEL（2字节）：
  该页在 B+ Tree 中的层级
  0 = 叶子节点（存储实际行数据）
  ≥1 = 非叶子节点（存储索引键值 + 子页指针）

PAGE_INDEX_ID（8字节）：
  该页属于哪个索引（索引 ID）
  与 information_schema.INNODB_INDEXES 中的 INDEX_ID 对应

PAGE_BTR_SEG_LEAF（10字节）：
  叶子节点段的 Segment Header（仅在 B+ Tree 根页中有效）

PAGE_BTR_SEG_TOP（10字节）：
  非叶子节点段的 Segment Header（仅在 B+ Tree 根页中有效）
```

## 关键字段的使用场景

```sql
-- 1. PAGE_N_RECS：快速获取页内记录数（不需要遍历所有记录）
-- 当 InnoDB 需要知道一个页有多少记录时，直接读取此字段
-- 比遍历所有行记录快得多

-- 2. PAGE_MAX_TRX_ID：MVCC 快速可见性过滤
-- 在二级索引扫描时，如果 PAGE_MAX_TRX_ID < Read View 低水位，
-- 整页的记录都对当前事务可见，无需每行都通过 Undo Log 检查可见性
-- 这是 InnoDB 优化 MVCC 读性能的重要机制

-- 3. PAGE_LEVEL：判断页类型
-- 读取任意页时可以通过 PAGE_LEVEL 判断是叶子节点还是中间节点
-- 层级 0 的页存储行数据，层级 >= 1 的页存储键值 + 子页号

-- 4. PAGE_DIRECTION 和 PAGE_N_DIRECTION：判断插入模式
-- 如果连续向右插入（PAGE_DIRECTION = PAGE_RIGHT）
-- InnoDB 可以直接从 PAGE_LAST_INSERT 之后插入，无需搜索
-- 顺序插入的性能优于随机插入，正是利用了这个优化

-- 查看页级信息（通过 innochecksum 工具）
-- innochecksum -p <page_no> --dump-file=/tmp/page_dump.txt myapp/orders.ibd
```

## PAGE_FREE 与碎片管理

```sql
-- 删除记录时的处理：
-- 不立即将空间返回给 Free Space
-- 而是将该记录加入 PAGE_FREE 指向的删除链表（头插法）
-- PAGE_GARBAGE 增加（记录碎片字节数）

-- 再次插入时的空间分配顺序：
-- 1. 优先查找 PAGE_FREE 链表中是否有足够大的可用槽（碎片复用）
--    如果找到：使用该槽（避免扩展 Free Space）
-- 2. 否则：从 PAGE_HEAP_TOP 处分配新空间（扩展 Free Space 底部）

-- 页内碎片整理：
-- 当 PAGE_GARBAGE 较大（碎片化严重），且 Free Space 不足以插入新记录时
-- InnoDB 会对页进行碎片整理（重排列所有记录）
-- 这是一个页内的局部操作，不影响其他页

-- 监控表的碎片情况
SELECT DATA_FREE, DATA_LENGTH, INDEX_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'orders';
-- DATA_FREE 很大说明有已分配但可复用的空间（跨页的碎片）
```

## PAGE_INDEX_ID 与索引对应关系

```sql
-- PAGE_INDEX_ID 记录该页属于哪个索引
-- 每个索引有唯一的 INDEX_ID（在整个 InnoDB 实例中唯一）

-- 查看表的所有索引 ID
SELECT INDEX_ID, NAME, TABLE_ID, TYPE, N_FIELDS
FROM information_schema.INNODB_INDEXES
WHERE TABLE_ID = (
    SELECT TABLE_ID FROM information_schema.INNODB_TABLES
    WHERE NAME = 'myapp/orders'
);

-- 通过 INDEX_ID 定位该索引占用的所有页
SELECT PAGE_NUMBER, PAGE_TYPE, IS_LEAF
FROM information_schema.INNODB_BUFFER_PAGE
WHERE INDEX_ID = 1234  -- 替换为实际 INDEX_ID
ORDER BY PAGE_NUMBER;
```

## 适用场景

- **性能分析**：理解 `PAGE_DIRECTION` 和 `PAGE_N_DIRECTION` 有助于理解为什么顺序插入（自增主键）比随机插入快，以及如何通过插入模式影响 B+ Tree 的效率
- **存储分析**：通过 `PAGE_N_RECS` 和 `PAGE_GARBAGE` 可以估算页的填充率和碎片程度，决定是否需要 `OPTIMIZE TABLE`

## 常见问题

**Page Header 中 PAGE_N_RECS 和 PAGE_N_HEAP 有什么区别？**

`PAGE_N_RECS` 是有效用户记录数（不含 Infimum/Supremum 虚拟记录，不含已删除记录），是业务层面看到的记录数。`PAGE_N_HEAP` 是堆中所有记录数（含 Infimum/Supremum 的 2 条、还有已 DELETE 标记的记录）。如果大量记录被删除，`PAGE_N_HEAP - PAGE_N_RECS - 2` 就是该页中被删除但尚未物理清除的记录数（等待 Purge）。

## 注意事项

- Page Header 的字段在每次行记录插入、删除、更新时都会被修改，这些修改同样会产生对应的 Redo Log，以确保崩溃后可以通过 Redo Log 恢复 Page Header 的正确状态。
- `PAGE_MAX_TRX_ID` 字段只在二级索引页中维护（不在聚簇索引页中），这是因为二级索引的 MVCC 优化依赖此字段做快速过滤，而聚簇索引每行都有 `DB_TRX_ID`，不需要页级过滤。

## 总结

Page Header（56字节）是数据页的控制信息区，关键字段包括：`PAGE_N_DIR_SLOTS`（Page Directory 槽数，二分查找基础）、`PAGE_N_RECS`（有效记录数）、`PAGE_MAX_TRX_ID`（MVCC 快速过滤）、`PAGE_LEVEL`（B+ Tree 层级，0=叶子）、`PAGE_FREE`（删除记录复用链表）、`PAGE_DIRECTION/N_DIRECTION`（插入方向优化）。这些字段共同支撑了 InnoDB 的记录查找、插入优化、MVCC 过滤和空间管理机制。

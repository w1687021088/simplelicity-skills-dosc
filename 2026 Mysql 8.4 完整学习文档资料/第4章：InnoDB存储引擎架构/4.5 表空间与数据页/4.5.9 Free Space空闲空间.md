# Free Space 空闲空间

Free Space（空闲空间）是 InnoDB 数据页中位于 User Records 和 Page Directory 之间的未使用区域。随着新记录的插入，User Records 区域从上向下增长，Page Directory 从下向上增长，两者之间的 Free Space 逐渐减小。当 Free Space 不足以容纳新记录时，页面被认为"已满"，触发页分裂（Page Split）。理解 Free Space 的管理机制有助于优化存储空间利用率和减少不必要的页分裂。

---

## Free Space 的位置与增长方向

```
数据页空间分配示意（随时间变化）：

初始状态（仅含 Infimum/Supremum）：
┌──────────────────────────────────────────────────────────┐
│ File Header + Page Header + Infimum + Supremum           │ ↑
├──────────────────────────────────────────────────────────┤
│                                                          │
│             Free Space（大约 16 KB - 128 B）              │
│                                                          │
├──────────────────────────────────────────────────────────┤
│ Page Directory（初始 2 个槽 × 2字节 = 4字节）             │ ↓
├──────────────────────────────────────────────────────────┤
│ File Trailer（8字节）                                     │
└──────────────────────────────────────────────────────────┘

插入若干记录后：
┌──────────────────────────────────────────────────────────┐
│ File Header + Page Header + Infimum + Supremum           │ ↑
├──────────────────────────────────────────────────────────┤
│ User Records（已插入的行记录）   → 向下增长               │
├──────────────────────────────────────────────────────────┤
│        Free Space（剩余可用）                             │ ← PAGE_HEAP_TOP
├──────────────────────────────────────────────────────────┤
│ Page Directory（槽数组）        ← 向上增长               │
├──────────────────────────────────────────────────────────┤
│ File Trailer（8字节）                                     │
└──────────────────────────────────────────────────────────┘

页满（Free Space = 0）：
  User Records 的底部 = Page Directory 的顶部
  → 无法再插入新记录（触发页分裂）
```

## PAGE_HEAP_TOP 与 Free Space 的关系

```sql
-- PAGE_HEAP_TOP（在 Page Header 中）：
-- 记录 User Records 区域的下一个可用位置（从页首计算的偏移量）
-- 新记录插入时从 PAGE_HEAP_TOP 开始分配空间
-- 插入后 PAGE_HEAP_TOP += 新记录大小

-- Free Space 大小计算（近似）：
-- Free Space ≈ Page Size - (Fixed Headers) - User_Records_Size - Page_Directory_Size

-- 更精确的计算（通过 Page Header 字段）：
-- Free Space 起始位置：PAGE_HEAP_TOP（当前已分配的末尾）
-- Free Space 结束位置：Page Directory 的起始位置（从页尾算起）
-- Free Space 大小 = Page Directory 起始 - PAGE_HEAP_TOP

-- 查看数据页的填充率（间接方式）
SELECT
    TABLE_NAME,
    DATA_LENGTH / 1024 AS data_kb,
    TABLE_ROWS,
    AVG_ROW_LENGTH,
    DATA_LENGTH / (TABLE_ROWS * AVG_ROW_LENGTH) AS page_fill_ratio
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'orders'
  AND TABLE_ROWS > 0;
-- page_fill_ratio < 1 说明有空闲空间（正常）
-- 接近 1 说明填充率高
```

## 删除记录后的 Free Space 变化

```sql
-- 重要：DELETE 操作不会增加 Free Space！
-- DELETE 只将记录标记为删除（delete_mask = 1）并加入 PAGE_FREE 链表
-- Free Space（PAGE_HEAP_TOP 到 Page Directory 之间）并不增加
-- 被删除的空间是"碎片"（PAGE_GARBAGE 统计），不是 Free Space

-- 碎片空间的复用：
-- 下次插入时，InnoDB 先检查 PAGE_FREE 链表
-- 如果链表中有足够大的空槽 → 复用该槽（不消耗 Free Space）
-- 如果没有合适的槽 → 从 Free Space 中分配（消耗 Free Space）

-- 当 PAGE_GARBAGE 很大且 Free Space 为 0 时：
-- 页内实际有很多碎片空间，但无法直接用
-- InnoDB 会重整页（Page Reorganization）：
--   将所有有效记录紧凑排列，Free Space 恢复为连续可用空间
--   PAGE_GARBAGE 重置为 0

-- 触发页重整的条件：
-- 页满（Free Space = 0）+ 新记录无法从 PAGE_FREE 链表中找到合适槽
-- 且重整后空间足够 → 重整而非分裂
```

## Fill Factor（填充率）

```sql
-- InnoDB 的 MERGE_THRESHOLD（页合并阈值）影响页的利用率：
SHOW VARIABLES LIKE 'innodb_merge_threshold_set_all_indexes';
-- 默认：不设置（各索引使用默认值 50%）

-- 每个索引可以单独设置合并阈值（MySQL 5.7+）
-- 创建索引时指定：
CREATE INDEX idx_user_id ON orders(user_id)
    COMMENT 'MERGE_THRESHOLD=40';
-- 当一个页的记录量低于 40% 时，InnoDB 会尝试合并相邻页

-- 页分裂后的 Fill Factor：
-- 顺序插入（自增主键）：页分裂在最后一页，新页初始为 0%，
--                       原页 100% 满（效率高）
-- 随机插入：页分裂时将约一半记录移到新页，
--           两个页都约 50% 满（空间浪费）
-- 中间插入：填充率在 50%-100% 之间，取决于具体情况

-- 查看表的大致空间利用率
SELECT
    TABLE_NAME,
    DATA_LENGTH / 1024 / 1024 AS data_mb,
    DATA_FREE / 1024 / 1024 AS free_mb,
    100 * DATA_FREE / (DATA_LENGTH + DATA_FREE) AS free_pct
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'myapp'
ORDER BY free_pct DESC;
-- free_pct 高说明空间浪费多，考虑 OPTIMIZE TABLE 重建
```

## 适用场景

- **容量规划**：对于写入量大且 DELETE 频繁的表，理解 Free Space 和 PAGE_GARBAGE 的关系，可以更准确地预估实际存储空间（包含碎片）与净数据量的差距
- **性能优化**：随机插入导致页分裂后 Free Space 多（每页约 50% 利用率），如果业务允许，换为顺序主键能将利用率提升到接近 100%，减少存储空间并提高缓存效率

## 常见问题

**OPTIMIZE TABLE 真的能收缩表文件大小吗？**

对于 `innodb_file_per_table=ON` 的表，`OPTIMIZE TABLE` 会重建整张表（创建新表、迁移数据、删除旧表），重建后的 `.ibd` 文件消除了碎片，填充率提高，文件大小减小。对于系统表空间中的表，`OPTIMIZE TABLE` 重建后的空间会被系统表空间回收利用，但 `ibdata1` 文件不缩小（只是内部标记为可用）。

---

## 注意事项

- `OPTIMIZE TABLE` 执行期间会锁住整张表（MDL 锁），生产环境应在业务低峰期执行，或使用 `pt-online-schema-change` 等在线工具。对于频繁 DELETE + INSERT 的表，碎片会持续积累，定期执行 OPTIMIZE 是必要的。
- Free Space 在 Page Directory 和 User Records 之间是连续的未分配区域。当 User Records 和 Page Directory 的增长"撞上"时（Free Space = 0），发生页分裂。页分裂时 InnoDB 分配新页，将约一半记录迁移到新页，更新父页的索引记录，整个过程对用户透明但有性能开销。

## 总结

Free Space 是数据页中 User Records（向下增长）和 Page Directory（向上增长）之间的未分配连续区域。通过 `PAGE_HEAP_TOP`（Page Header 字段）追踪空闲起始位置。DELETE 操作不增加 Free Space（只增加 PAGE_GARBAGE 碎片），插入时优先复用 PAGE_FREE 链表中的碎片空间，其次才消耗 Free Space。Free Space 耗尽时触发页分裂（顺序插入效率高于随机插入）。通过 `DATA_FREE` 字段和 `OPTIMIZE TABLE` 管理碎片与空间利用率。

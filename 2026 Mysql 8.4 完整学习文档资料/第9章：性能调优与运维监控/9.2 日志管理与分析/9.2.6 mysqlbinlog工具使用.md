# mysqlbinlog 工具使用

`mysqlbinlog` 是 MySQL 自带的命令行工具，用于解析和查看二进制日志（binlog）文件的内容。它可以将 binlog 中的事件转换为可读的 SQL 语句或文本描述，是数据恢复（PITR）、复制故障排查和审计分析的核心工具。对于 ROW 格式的 binlog，需要配合 `--verbose` 和 `--base64-output=DECODE-ROWS` 参数才能看到具体的行变更内容。

---

## 基本用法

```bash
# 查看 binlog 文件的全部内容：
mysqlbinlog /var/lib/mysql/mysql-bin.000001

# 查看并解码 ROW 格式的行事件（必须加 -v）：
mysqlbinlog -v /var/lib/mysql/mysql-bin.000001
# -v 显示行变更的伪 SQL（@1, @2 表示列号）
# -vv 额外显示列的数据类型

# 隐藏 base64 编码的原始数据，只显示解码后的内容：
mysqlbinlog --base64-output=DECODE-ROWS -v /var/lib/mysql/mysql-bin.000001

# 查看远程服务器的 binlog（不需要本地文件）：
mysqlbinlog --read-from-remote-server --host=192.168.1.100 \
            --user=repl --password mysql-bin.000001
```

## 时间和位置过滤

```bash
# 按时间范围过滤（最常用）：
mysqlbinlog --start-datetime='2024-06-15 10:00:00' \
            --stop-datetime='2024-06-15 12:00:00' \
            /var/lib/mysql/mysql-bin.000001

# 按位置（Position）过滤：
mysqlbinlog --start-position=1234 \
            --stop-position=5678 \
            /var/lib/mysql/mysql-bin.000001

# 只查看特定数据库的事件：
mysqlbinlog --database=mydb /var/lib/mysql/mysql-bin.000001
# 注意：--database 对 ROW 格式的过滤是基于事件头中的数据库名
# 对 STATEMENT 格式是基于 USE 语句
# 跨库操作可能无法被正确过滤

# 跳过指定 server_id 的事件：
mysqlbinlog --server-id=1 /var/lib/mysql/mysql-bin.000001
# 只显示 server_id=1 的事件

# 跨多个 binlog 文件查看：
mysqlbinlog /var/lib/mysql/mysql-bin.000001 \
            /var/lib/mysql/mysql-bin.000002 \
            /var/lib/mysql/mysql-bin.000003
```

## ROW 格式输出解读

```bash
# ROW 格式 binlog 用 -v 解码后的输出示例：

# INSERT 操作：
### INSERT INTO test.orders
### SET
###   @1=1001                    -- 第1列（如 id）= 1001
###   @2='2024-06-15 10:30:00'   -- 第2列（如 create_time）
###   @3='pending'               -- 第3列（如 status）
###   @4=99.50                   -- 第4列（如 amount）

# UPDATE 操作：
### UPDATE test.orders
### WHERE
###   @1=1001                    -- 修改前的值（WHERE 条件）
###   @2='2024-06-15 10:30:00'
###   @3='pending'
###   @4=99.50
### SET
###   @1=1001                    -- 修改后的值
###   @2='2024-06-15 10:30:00'
###   @3='shipped'               -- status 从 pending 变为 shipped
###   @4=99.50

# DELETE 操作：
### DELETE FROM test.orders
### WHERE
###   @1=1001
###   @2='2024-06-15 10:30:00'
###   @3='shipped'
###   @4=99.50

# @N 表示第 N 列，需要对照表结构才能知道具体列名
# 使用 -vv 可以看到列类型信息
```

## 数据恢复（PITR）

```bash
# 基于时间点的数据恢复流程：

# 假设场景：
# 凌晨 2:00 全量备份
# 上午 10:30 有人误删了 orders 表
# 需要恢复到 10:29:59

# 步骤1：恢复全量备份
mysql < /backup/full_backup_0200.sql

# 步骤2：回放 binlog 到误操作之前
# 先找到误操作的位置：
mysqlbinlog --start-datetime='2024-06-15 10:25:00' \
            --stop-datetime='2024-06-15 10:35:00' \
            -v /var/lib/mysql/mysql-bin.000005 | grep -i "DROP TABLE"
# 找到 DROP TABLE 的 Position，假设在 Position 12345

# 步骤3：回放 binlog（从备份时间到误操作之前）
mysqlbinlog --start-datetime='2024-06-15 02:00:00' \
            --stop-position=12345 \
            /var/lib/mysql/mysql-bin.000003 \
            /var/lib/mysql/mysql-bin.000004 \
            /var/lib/mysql/mysql-bin.000005 \
            | mysql -u root -p

# 步骤4：跳过误操作，继续回放后续 binlog
mysqlbinlog --start-position=12400 \
            /var/lib/mysql/mysql-bin.000005 \
            /var/lib/mysql/mysql-bin.000006 \
            | mysql -u root -p
```

## 闪回（Flashback）

```bash
# 闪回是将 binlog 中的操作"反向执行"
# INSERT → DELETE，DELETE → INSERT，UPDATE → 交换 SET 和 WHERE

# 使用 mysqlbinlog 的 --flashback 参数（某些版本支持）
# 或使用第三方工具 binlog2sql 实现闪回

# binlog2sql 工具用法：
# 安装：pip install binlog2sql
# 或：git clone https://github.com/danfengcao/binlog2sql.git

# 生成回滚 SQL：
python binlog2sql.py -h127.0.0.1 -P3306 -uroot -p \
    --start-file='mysql-bin.000005' \
    --start-position=12345 --stop-position=12400 \
    --flashback \
    -dorders_db -torders

# 输出的反向 SQL 示例：
# 原操作：DELETE FROM orders WHERE id=1001
# 闪回SQL：INSERT INTO orders (id, ...) VALUES (1001, ...)

# 原操作：UPDATE orders SET status='shipped' WHERE id=1001
# 闪回SQL：UPDATE orders SET status='pending' WHERE id=1001
```

## 常用参数汇总

| 参数 | 作用 | 示例 |
|-----|:----:|:----:|
| -v / --verbose | 解码 ROW 事件为伪 SQL | mysqlbinlog -v binlog.000001 |
| -vv | 额外显示列类型 | mysqlbinlog -vv binlog.000001 |
| --base64-output=DECODE-ROWS | 隐藏 base64 编码 | 配合 -v 使用 |
| --start-datetime | 起始时间 | '2024-06-15 10:00:00' |
| --stop-datetime | 结束时间 | '2024-06-15 12:00:00' |
| --start-position | 起始位置 | 1234 |
| --stop-position | 结束位置 | 5678 |
| --database | 过滤数据库 | mydb |
| --read-from-remote-server | 从远程读取 | 配合 --host 使用 |
| --require-row-format | 强制 ROW 格式 | 安全校验 |
| --include-gtids | 过滤 GTID | 'uuid:1-100' |
| --exclude-gtids | 排除 GTID | 'uuid:50' |

## 适用场景

- **误操作后的数据恢复**：通过全量备份 + binlog 回放实现 PITR（Point-in-Time Recovery），将数据恢复到误操作之前的时间点
- **复制故障排查**：查看从库复制中断位置的 binlog 内容，确认是什么事件导致了复制错误

## 常见问题

**mysqlbinlog 报错 unknown variable 'default-character-set=utf8mb4' 怎么办？**

这是因为 my.cnf 中 `[client]` 段配置了 `default-character-set=utf8mb4`，而 mysqlbinlog 不支持该参数。解决方法：①在命令行指定 `--no-defaults` 参数跳过配置文件：`mysqlbinlog --no-defaults /var/lib/mysql/mysql-bin.000001`；②或将 my.cnf 中的 `default-character-set` 配置从 `[client]` 段移到 `[mysql]` 段（mysqlbinlog 不读取 `[mysql]` 段）。

---

## 注意事项

- mysqlbinlog 的 `--database` 过滤在 ROW 格式和 STATEMENT 格式下的行为不同。ROW 格式基于事件头中的数据库名过滤，STATEMENT 格式基于当前 USE 的数据库过滤。如果在一个库中执行了跨库操作（如 `USE db1; UPDATE db2.t1 SET ...`），STATEMENT 格式会认为这属于 db1 的事件。使用 `--database` 过滤时需注意这种差异。
- 将 mysqlbinlog 输出管道传入 mysql 客户端执行时（`mysqlbinlog ... | mysql`），如果中途出错，后续的 SQL 不会继续执行。建议先将输出重定向到文件（`mysqlbinlog ... > recovery.sql`），检查 SQL 内容后再执行（`mysql < recovery.sql`），避免恢复过程中的意外中断。

## 总结

`mysqlbinlog` 是解析 binlog 的核心工具。ROW 格式需要 `-v` 或 `-vv` 解码行变更。支持按时间（`--start-datetime`/`--stop-datetime`）和位置（`--start-position`/`--stop-position`）过滤。用于 PITR 数据恢复：全量备份 + binlog 回放到误操作前。支持远程读取（`--read-from-remote-server`）。配合 binlog2sql 实现闪回。`--no-defaults` 解决字符集报错。`--database` 过滤在不同 binlog 格式下行为不同。建议先输出到文件再检查执行。

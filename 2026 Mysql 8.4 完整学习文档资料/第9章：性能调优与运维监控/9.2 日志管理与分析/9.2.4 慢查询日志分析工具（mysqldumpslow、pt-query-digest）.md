# 慢查询日志分析工具（mysqldumpslow、pt-query-digest）

慢查询日志记录了执行时间超过阈值的 SQL 语句，但原始日志文件可能包含成千上万条记录，逐条查看既耗时又低效。使用专业的分析工具可以对慢查询日志进行归类、统计和排序，快速定位需要优先优化的 SQL。MySQL 自带的 `mysqldumpslow` 和 Percona 提供的 `pt-query-digest` 是两个最常用的慢查询日志分析工具。

---

## mysqldumpslow（MySQL 自带）

```bash
# mysqldumpslow 是 MySQL 安装包自带的 Perl 脚本
# 位于 MySQL 的 bin 目录下

# 基本用法：
mysqldumpslow /var/log/mysql/slow.log

# 常用排序选项（-s 参数）：
# -s t  按总查询时间排序（默认）
# -s at 按平均查询时间排序
# -s c  按出现次数排序
# -s l  按总锁等待时间排序
# -s al 按平均锁等待时间排序
# -s r  按总返回行数排序
# -s ar 按平均返回行数排序

# 显示前 10 条最慢的查询：
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 显示出现次数最多的前 20 条慢查询：
mysqldumpslow -s c -t 20 /var/log/mysql/slow.log

# 按平均时间排序，显示前 5 条：
mysqldumpslow -s at -t 5 /var/log/mysql/slow.log

# 不抽象化数字和字符串（显示原始 SQL）：
mysqldumpslow -a /var/log/mysql/slow.log

# 过滤包含特定内容的查询：
mysqldumpslow -s t -t 10 -g "orders" /var/log/mysql/slow.log
# -g 按正则表达式过滤，只显示包含 "orders" 的查询
```

## mysqldumpslow 输出解读

```
mysqldumpslow 输出示例：

Count: 256  Time=3.45s (883s)  Lock=0.00s (0s)  Rows=50.2 (12851)
  root[root] @ localhost
  SELECT * FROM orders WHERE status = 'S' AND create_time > 'S' ORDER BY id DESC LIMIT N

各字段含义：
  Count: 256          → 该类查询出现了 256 次
  Time=3.45s (883s)   → 平均执行时间 3.45 秒，总时间 883 秒
  Lock=0.00s (0s)     → 平均锁等待 0 秒，总锁等待 0 秒
  Rows=50.2 (12851)   → 平均返回 50.2 行，总返回 12851 行
  SQL 模板            → 数字被替换为 N，字符串被替换为 'S'

分析思路：
  优先优化"总时间最长"的查询（Count × 平均时间）
  这类查询对数据库的整体负载影响最大
  Count 很高但平均时间不长的查询也需要关注
  因为优化后可以减少大量 I/O
```

## pt-query-digest（Percona Toolkit）

```bash
# pt-query-digest 是 Percona Toolkit 中的工具
# 功能比 mysqldumpslow 强大得多

# 安装 Percona Toolkit（Linux）：
# CentOS/RHEL：
# yum install percona-toolkit
# Ubuntu/Debian：
# apt-get install percona-toolkit

# 基本用法：
pt-query-digest /var/log/mysql/slow.log

# 分析最近 1 小时的慢查询：
pt-query-digest --since '1h' /var/log/mysql/slow.log

# 分析特定时间范围：
pt-query-digest --since '2024-06-15 10:00:00' --until '2024-06-15 12:00:00' /var/log/mysql/slow.log

# 只分析特定用户的查询：
pt-query-digest --filter '$event->{user} eq "app_user"' /var/log/mysql/slow.log

# 只分析特定数据库的查询：
pt-query-digest --filter '$event->{db} eq "mydb"' /var/log/mysql/slow.log

# 输出到文件：
pt-query-digest /var/log/mysql/slow.log > /tmp/slow_report.txt

# 将结果存入数据库（便于持续追踪）：
pt-query-digest --review h=localhost,D=slow_log_db,t=query_review /var/log/mysql/slow.log

# 只显示前 20 条最慢的查询类型：
pt-query-digest --limit 20 /var/log/mysql/slow.log
```

## 两种工具的对比

| 对比维度 | mysqldumpslow | pt-query-digest |
|---------|:------------:|:---------------:|
| 来源 | MySQL 自带 | Percona Toolkit |
| 安装 | 无需额外安装 | 需要安装 percona-toolkit |
| 输出详细度 | 基础统计 | 详细统计（P95、stddev 等）|
| 时间过滤 | 不支持 | 支持（--since/--until）|
| 用户/库过滤 | 不支持 | 支持（--filter）|
| 查询指纹 | 简单抽象（N/S）| 标准化指纹 + 哈希 |
| 输出到数据库 | 不支持 | 支持（--review）|
| 实时分析 | 不支持 | 支持（分析 tcpdump 和 processlist）|
| 适合场景 | 快速查看 | 深入分析 |

## 实战分析流程

```bash
# 完整的慢查询优化流程：

# 步骤1：确认慢查询日志已开启
mysql -e "SHOW VARIABLES LIKE 'slow_query_log'"
mysql -e "SHOW VARIABLES LIKE 'long_query_time'"

# 步骤2：用 pt-query-digest 生成分析报告
pt-query-digest /var/log/mysql/slow.log > /tmp/slow_report.txt

# 步骤3：查看 TOP 5 慢查询
head -100 /tmp/slow_report.txt

# 步骤4：对 TOP 1 的查询执行 EXPLAIN
mysql -e "EXPLAIN SELECT * FROM orders WHERE status='pending' AND create_time > '2024-01-01' ORDER BY id DESC LIMIT 100"

# 步骤5：根据 EXPLAIN 结果优化索引
# 如果 type=ALL（全表扫描），添加索引：
mysql -e "ALTER TABLE orders ADD INDEX idx_status_time (status, create_time)"

# 步骤6：验证优化效果
# 清空慢查询日志，观察新的慢查询数量
mysql -e "SET GLOBAL slow_query_log = OFF"
# 删除或重命名旧日志
mysql -e "SET GLOBAL slow_query_log = ON"
# 等待一段时间后再次分析
```

## 适用场景

- **日常性能巡检**：DBA 每天或每周用 pt-query-digest 分析慢查询日志，生成报告，找出 TOP 10 慢查询进行优化
- **线上问题快速定位**：收到数据库性能告警时，用 mysqldumpslow 快速查看最近的慢查询，定位可疑 SQL

## 常见问题

**pt-query-digest 分析大文件很慢，如何加速？**

有几种方法：①使用 `--since` 和 `--until` 限制时间范围，只分析需要的时间段；②使用 `--limit` 限制输出条数（如 `--limit 20`）；③先用 `tail` 截取最近的日志再分析（`tail -100000 slow.log > recent_slow.log`）；④将慢查询日志按天切割（配合 logrotate），每次只分析当天的日志文件。对于 GB 级的日志文件，pt-query-digest 的处理时间可能需要几分钟到十几分钟。

## 注意事项

- mysqldumpslow 将参数值抽象为 N（数字）和 S（字符串），这意味着不同参数值的相同模板查询会被归为一类。在大多数情况下这是期望的行为（因为关注的是 SQL 模板而非具体参数），但如果需要看到原始 SQL 参数值，使用 `-a` 参数禁用抽象化。
- pt-query-digest 的 `--review` 功能可以将分析结果存入数据库表，每次分析只处理新增的慢查询。这对于长期追踪慢查询趋势非常有用，可以发现某个查询是从什么时候开始变慢的，或者某次上线后是否引入了新的慢查询。

## 总结

mysqldumpslow 是 MySQL 自带的慢查询分析工具，使用简单，适合快速查看。pt-query-digest 是 Percona Toolkit 提供的专业分析工具，功能强大：支持时间过滤、用户过滤、P95 统计、输出到数据库等。推荐日常使用 pt-query-digest 进行深度分析。分析慢查询的关键指标：总响应时间（占比）、执行次数、平均时间、Rows_examined/Rows_sent 比值。优化流程：分析报告 → EXPLAIN → 添加索引 → 验证效果。

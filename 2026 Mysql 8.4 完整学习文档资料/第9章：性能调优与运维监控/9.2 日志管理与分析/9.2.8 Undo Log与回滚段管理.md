# Undo Log 与回滚段管理

Undo Log（回滚日志）是 InnoDB 存储引擎用于支持事务回滚和 MVCC（多版本并发控制）的核心日志。当事务修改数据时，InnoDB 会将修改前的旧版本数据记录到 Undo Log 中。如果事务回滚，InnoDB 使用 Undo Log 将数据恢复到修改前的状态；如果其他事务需要读取旧版本数据（一致性读），也通过 Undo Log 构建数据的历史版本。Undo Log 存储在 Undo 表空间中，由回滚段（Rollback Segment）组织管理。

---

## Undo Log 的作用

```
Undo Log 有两个核心功能：

1. 事务回滚（Rollback）
   事务执行 INSERT 时，Undo Log 记录"删除该行"的信息
   事务执行 DELETE 时，Undo Log 记录"插入该行"的信息
   事务执行 UPDATE 时，Undo Log 记录"将列恢复为旧值"的信息
   
   ROLLBACK 时：按 Undo Log 的记录反向执行
   将数据恢复到事务开始前的状态

2. MVCC 一致性读
   其他事务需要读取被当前事务修改但尚未提交的数据时
   不直接读当前版本（避免脏读）
   通过 Undo Log 链找到该行的历史版本
   返回对当前事务可见的版本
   
   Undo Log 链：
   最新版本 → Undo Log v3 → Undo Log v2 → Undo Log v1
   每个版本包含修改者的事务 ID
   读取时根据隔离级别判断哪个版本可见

Undo Log 的类型：
  insert undo log：INSERT 操作产生
    事务提交后可以立即释放（INSERT 的旧版本无需被其他事务读取）
  update undo log：UPDATE 和 DELETE 操作产生
    事务提交后不能立即释放（其他事务可能还需要读取旧版本）
    由 Purge 线程在确认没有事务需要后清理
```

## 回滚段（Rollback Segment）

```sql
-- 回滚段是 Undo Log 的容器
-- 每个回滚段包含多个 Undo Slot
-- 每个活跃事务占用一个 Undo Slot

-- 查看回滚段数量：
SHOW VARIABLES LIKE 'innodb_rollback_segments';
-- 默认值：128
-- 取值范围：1 ~ 128

-- 每个回滚段最多 1024 个 Undo Slot
-- 因此最大并发事务数 ≈ 128 × 1024 ≈ 131072
-- 实际受限于 Undo 表空间的大小

-- 回滚段分配：
-- InnoDB 自动管理回滚段的分配
-- 每个 Undo 表空间包含若干回滚段
-- 事务开始时自动分配一个 Undo Slot
```

## Undo 表空间管理

```sql
-- MySQL 8.0+ 使用独立的 Undo 表空间

-- 查看 Undo 表空间：
SELECT TABLESPACE_NAME, FILE_NAME, FILE_TYPE, STATUS, ENGINE
FROM INFORMATION_SCHEMA.FILES
WHERE FILE_TYPE = 'UNDO LOG';

-- 默认情况下 MySQL 8.0 初始化时创建 2 个 Undo 表空间：
-- innodb_undo_001 → undo_001（数据目录下）
-- innodb_undo_002 → undo_002

-- 创建额外的 Undo 表空间：
CREATE UNDO TABLESPACE undo_003 ADD DATAFILE 'undo_003.ibu';
CREATE UNDO TABLESPACE undo_004 ADD DATAFILE 'undo_004.ibu';

-- 查看所有 Undo 表空间的状态：
SELECT NAME, SPACE_TYPE, STATE, FILE_SIZE / 1024 / 1024 AS size_mb
FROM INFORMATION_SCHEMA.INNODB_TABLESPACES
WHERE SPACE_TYPE = 'Undo';

-- 设置活跃 Undo 表空间（将某个标记为不活跃以便截断）：
ALTER UNDO TABLESPACE undo_003 SET INACTIVE;
-- 不活跃后 Purge 线程会清空并截断该表空间
-- 截断完成后文件大小回到初始值（通常 16MB）

-- 重新激活：
ALTER UNDO TABLESPACE undo_003 SET ACTIVE;

-- 删除不再需要的 Undo 表空间：
-- 必须先设为 INACTIVE 并等待截断完成
DROP UNDO TABLESPACE undo_003;
-- 不能删除默认的 2 个 Undo 表空间
-- 必须至少保留 2 个活跃的 Undo 表空间
```

## 自动截断（Truncation）

```sql
-- Undo 表空间会随着事务操作不断增长
-- 自动截断可以回收空间

-- 查看是否启用自动截断：
SHOW VARIABLES LIKE 'innodb_undo_log_truncate';
-- 默认值：ON（MySQL 8.0.2+）

-- 开启/关闭自动截断：
SET GLOBAL innodb_undo_log_truncate = ON;

-- 截断触发的大小阈值：
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';
-- 默认值：1073741824（1GB）
-- 当 Undo 表空间超过此大小时触发截断

-- 设置阈值：
SET GLOBAL innodb_max_undo_log_size = 512 * 1024 * 1024;  -- 512MB

-- Purge 触发截断的频率：
SHOW VARIABLES LIKE 'innodb_purge_rseg_truncate_frequency';
-- 默认值：128
-- Purge 系统每执行 128 次后检查一次是否需要截断

-- 自动截断的过程：
-- 1. Purge 线程检测到 Undo 表空间超过 innodb_max_undo_log_size
-- 2. 选择一个 Undo 表空间标记为截断目标
-- 3. 将该表空间中的回滚段标记为不活跃
-- 4. 等待使用这些回滚段的事务全部完成
-- 5. 清理 Undo Log 数据
-- 6. 截断表空间文件到初始大小（约 16MB）
-- 7. 重新激活回滚段
-- 注意：需要至少 2 个 Undo 表空间才能轮流截断
```

## 长事务对 Undo Log 的影响

```sql
-- 长事务会阻止 Undo Log 的清理，导致 Undo 表空间膨胀

-- 查看最老的活跃事务：
SELECT trx_id, trx_started, trx_state,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec
FROM INFORMATION_SCHEMA.INNODB_TRX
ORDER BY trx_started ASC
LIMIT 5;

-- 查看 Purge 状态：
SHOW ENGINE INNODB STATUS\G
-- TRANSACTIONS 部分：
-- Purge done for trx's n:o < 12345678 undo n:o < 0
-- History list length 1234
-- 
-- History list length：等待 Purge 清理的 Undo Log 记录数
-- 如果该值持续增长，说明有长事务阻止了 Purge

-- 监控 History list length：
SELECT VARIABLE_VALUE AS history_list_length
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Innodb_history_list_length';

-- 参考值：
-- < 1000：正常
-- 1000~100000：需要关注，可能有长事务
-- > 100000：严重，Undo 表空间会快速增长
-- > 1000000：紧急，需要立即排查并终止长事务
```

## 适用场景

- **Undo 表空间磁盘空间管理**：当 Undo 表空间文件不断增长占用大量磁盘时，通过自动截断或手动截断回收空间
- **长事务导致的 Undo Log 膨胀排查**：监控 `Innodb_history_list_length`，当该值持续增长时排查长事务

---

## 常见问题

**Undo 表空间文件很大但数据库中没有大事务，为什么？**

Undo 表空间膨胀不一定是因为单个大事务，也可能是因为长事务。即使事务本身只修改了一行数据，但如果这个事务长时间不提交（如忘记 COMMIT 的交互式会话、应用代码中未关闭的事务），Purge 线程就无法清理在该事务开始之后产生的所有 Undo Log。一个运行了 1 小时的空闲事务就可能阻止这 1 小时内所有其他事务产生的 Undo Log 被清理。排查方法：查看 `INFORMATION_SCHEMA.INNODB_TRX` 中 `trx_started` 最早的事务，检查其是否还在活跃。

---

## 注意事项

- 自动截断虽然方便，但截断过程本身有性能开销。截断时需要将目标 Undo 表空间的回滚段设为不活跃，减少了可用的回滚段数量，可能影响并发事务能力。在高并发写入的生产环境中，如果截断导致了性能抖动，可以设置 `innodb_undo_log_truncate=OFF` 关闭自动截断，在业务低峰期手动截断（`ALTER UNDO TABLESPACE ... SET INACTIVE`）。
- 创建额外的 Undo 表空间可以分散 I/O 负载。将不同的 Undo 表空间文件放在不同的存储设备上，减少单个磁盘的 I/O 压力。MySQL 8.0 支持最多 127 个 Undo 表空间（加上默认的 2 个）。

---

## 总结

Undo Log 支持事务回滚和 MVCC 一致性读。存储在独立的 Undo 表空间中（MySQL 8.0+ 默认 2 个）。回滚段（默认 128 个）管理 Undo Slot，每个活跃事务占一个 Slot。`innodb_undo_log_truncate=ON`（默认）开启自动截断，超过 `innodb_max_undo_log_size`（默认 1GB）时触发。长事务阻止 Undo Log 清理导致空间膨胀，监控 `Innodb_history_list_length`。支持 `CREATE/DROP UNDO TABLESPACE` 管理额外的 Undo 表空间。必须保留至少 2 个活跃 Undo 表空间。

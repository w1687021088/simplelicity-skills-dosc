# Binary Log 格式与管理

Binary Log（二进制日志，简称 binlog）记录了 MySQL 服务器上所有修改数据的操作（INSERT、UPDATE、DELETE、DDL 等），是 MySQL 复制和数据恢复的核心机制。binlog 有三种记录格式：STATEMENT（语句）、ROW（行）和 MIXED（混合）。MySQL 8.0 默认使用 ROW 格式，且从 8.0.34 起 `binlog_format` 参数被标记为废弃，ROW 格式成为唯一推荐方式。MySQL 8.4 中应始终使用 ROW 格式。

---

## 三种 binlog 格式

| 格式 | 记录内容 | 数据安全性 | 日志大小 | 状态 |
|-----|:-------:|:--------:|:-------:|:---:|
| STATEMENT | 原始 SQL 语句 | 可能不一致 | 小 | 将被移除 |
| ROW | 每行数据的变更 | 一致 | 大 | 默认，推荐 |
| MIXED | 自动选择 | 较一致 | 中 | 将被移除 |

---

## 各格式详解

```
STATEMENT 格式：
  记录原始的 SQL 语句
  优点：日志体积小（一条 UPDATE 影响 100 万行只记录一条 SQL）
  缺点：
    非确定性函数可能导致主从不一致
    例如 NOW()、UUID()、RAND()、FOUND_ROWS() 等
    在主库和从库上执行可能产生不同结果
  状态：MySQL 8.0.34+ 废弃，将在未来版本移除

ROW 格式（默认，推荐）：
  记录每一行数据的变更前后的值
  一条 UPDATE 影响 100 万行 → 记录 100 万条行变更
  优点：
    数据一致性最高
    不受 SQL 语句确定性的影响
    支持精确的数据恢复（可以看到具体改了什么）
  缺点：
    日志体积较大（特别是批量操作）
    大量行变更时 binlog 增长很快
  
MIXED 格式：
  MySQL 自动判断：安全的 SQL 用 STATEMENT，不安全的用 ROW
  试图兼顾两者的优点
  但判断逻辑复杂，某些边界情况仍可能不一致
  状态：MySQL 8.0.34+ 废弃
```

## 参数配置

```sql
-- 查看 binlog 是否启用：
SHOW VARIABLES LIKE 'log_bin';
-- MySQL 8.0+ 默认启用（ON）

-- 查看当前格式：
SHOW VARIABLES LIKE 'binlog_format';
-- 默认值：ROW

-- 查看 binlog 文件路径：
SHOW VARIABLES LIKE 'log_bin_basename';

-- 查看当前 binlog 文件列表：
SHOW BINARY LOGS;

-- 查看当前正在写入的 binlog 文件：
SHOW MASTER STATUS;
-- MySQL 8.4 中改为：
SHOW BINARY LOG STATUS;

-- sync_binlog 刷盘策略：
SHOW VARIABLES LIKE 'sync_binlog';
-- 默认值：1
-- 1 = 每次事务提交都 fsync binlog（最安全）
-- 0 = 由操作系统决定何时刷盘
-- N = 每 N 个事务 fsync 一次

-- 在 my.cnf 中配置：
-- [mysqld]
-- log_bin = /var/log/mysql/mysql-bin
-- binlog_format = ROW
-- sync_binlog = 1
-- binlog_expire_logs_seconds = 604800  -- 7 天自动清理
-- max_binlog_size = 1073741824         -- 单文件最大 1GB
```

## binlog 的生命周期管理

```sql
-- 查看 binlog 自动过期时间：
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
-- 默认值：2592000（30 天）
-- MySQL 8.0 中替代了旧的 expire_logs_days

-- 设置保留 7 天：
SET GLOBAL binlog_expire_logs_seconds = 604800;

-- 手动清理旧的 binlog：
-- 清理指定文件之前的所有 binlog：
PURGE BINARY LOGS TO 'mysql-bin.000050';

-- 清理指定时间之前的所有 binlog：
PURGE BINARY LOGS BEFORE '2024-06-01 00:00:00';

-- 手动切换到新的 binlog 文件：
FLUSH BINARY LOGS;
-- 关闭当前 binlog 文件，创建新文件（编号 +1）

-- 查看 binlog 文件大小限制：
SHOW VARIABLES LIKE 'max_binlog_size';
-- 默认值：1073741824（1GB）
-- 当 binlog 文件达到此大小时自动切换到新文件
```

## binlog 内容查看

```bash
# 使用 mysqlbinlog 工具查看 binlog 内容：

# 查看 binlog 文件内容：
mysqlbinlog /var/lib/mysql/mysql-bin.000001

# 查看 ROW 格式的详细行变更（需要 -v 参数）：
mysqlbinlog -v /var/lib/mysql/mysql-bin.000001
# -v 显示每行变更的列值
# -vv 显示列类型信息

# 查看指定时间范围的 binlog：
mysqlbinlog --start-datetime='2024-06-15 10:00:00' \
            --stop-datetime='2024-06-15 12:00:00' \
            /var/lib/mysql/mysql-bin.000001

# 查看指定位置范围的 binlog：
mysqlbinlog --start-position=1234 --stop-position=5678 \
            /var/lib/mysql/mysql-bin.000001

# 只查看特定数据库的 binlog：
mysqlbinlog --database=mydb /var/lib/mysql/mysql-bin.000001

# 将 binlog 转换为 SQL 用于数据恢复：
mysqlbinlog /var/lib/mysql/mysql-bin.000001 > /tmp/recovery.sql
mysql < /tmp/recovery.sql
```

## ROW 格式的优化参数

```sql
-- binlog_row_image 控制 ROW 格式记录的列范围：
SHOW VARIABLES LIKE 'binlog_row_image';
-- full（默认）：记录所有列的前后值
-- minimal：只记录被修改的列 + 主键
-- noblob：记录除 BLOB/TEXT 外的所有列

-- minimal 可以显著减少 binlog 体积
-- 但可能影响某些数据恢复场景（无法看到所有列的旧值）
-- 生产环境推荐 full 或 noblob

-- binlog_rows_query_log_events：在 ROW 格式中附加原始 SQL
SHOW VARIABLES LIKE 'binlog_rows_query_log_events';
-- 默认值：OFF
-- 开启后 binlog 中会包含触发行变更的原始 SQL（作为注释）
-- 便于排查问题，但会略微增大 binlog 体积
SET GLOBAL binlog_rows_query_log_events = ON;
```

## 适用场景

- **主从复制的数据同步**：binlog 是 MySQL 复制的基础，主库产生 binlog，从库的 I/O 线程读取并应用。ROW 格式确保主从数据完全一致
- **基于时间点的数据恢复（PITR）**：通过全量备份 + binlog 回放，可以将数据库恢复到任意时间点。ROW 格式的 binlog 还支持"闪回"——将 binlog 中的操作反向执行

---

## 常见问题

**binlog 占用了大量磁盘空间，如何处理？**

binlog 持续增长是正常的，管理方式：①设置 `binlog_expire_logs_seconds`（推荐 7~30 天），MySQL 自动删除过期 binlog；②手动清理：`PURGE BINARY LOGS BEFORE '日期'`；③减小 `max_binlog_size`（如 256MB）让每个文件更小，便于管理；④使用 `binlog_row_image=minimal` 减少 ROW 格式的体积。注意不要手动删除 binlog 文件（`rm`），必须通过 `PURGE` 命令清理，否则 MySQL 的 binlog 索引文件会不一致。如果有从库，清理前确保从库已经读取了要清理的 binlog。

---

## 注意事项

- `sync_binlog=1` 配合 `innodb_flush_log_at_trx_commit=1`（"双一配置"）是数据安全的最高保障，但也会影响写入性能。在金融等核心业务中必须使用双一配置。在从库或非关键业务中，可以设置 `sync_binlog=0` 或 `sync_binlog=100` 提升性能，代价是 OS 崩溃时可能丢失少量 binlog 数据。
- MySQL 8.4 中 `binlog_format` 参数已废弃，不应再在 my.cnf 中显式设置该参数（使用默认的 ROW 即可）。如果从旧版本升级，需要移除 my.cnf 中的 `binlog_format=STATEMENT` 或 `binlog_format=MIXED` 配置，否则可能收到废弃警告。

## 总结

Binary Log 记录所有数据修改操作，是复制和数据恢复的核心。三种格式：ROW（默认，推荐，最安全）、STATEMENT（将移除）、MIXED（将移除）。MySQL 8.4 只应使用 ROW 格式。`sync_binlog=1` 保证每次提交刷盘。`binlog_expire_logs_seconds` 控制自动清理。`mysqlbinlog` 工具查看内容。`binlog_row_image` 控制记录的列范围。用 `PURGE` 命令而非手动删除文件。双一配置是金融级安全标准。

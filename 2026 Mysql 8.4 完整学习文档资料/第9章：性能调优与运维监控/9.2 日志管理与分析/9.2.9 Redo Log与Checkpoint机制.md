# Redo Log 与 Checkpoint 机制

Redo Log（重做日志）是 InnoDB 实现事务持久性（Durability）和崩溃恢复的核心机制。InnoDB 采用 WAL（Write-Ahead Logging）策略：事务修改数据时，先将修改记录写入 Redo Log 并持久化到磁盘，然后才将数据页的修改写入数据文件。如果 MySQL 崩溃，重启后通过重放 Redo Log 即可恢复未写入数据文件的修改。Checkpoint 机制则负责将 Buffer Pool 中的脏页定期刷新到数据文件，推进 Redo Log 的可回收位置，确保 Redo Log 不会被写满。

---

## Redo Log 的工作原理

```
WAL（Write-Ahead Logging）流程：

事务执行 UPDATE 操作时：
  1. 在 Buffer Pool 中修改数据页（产生脏页）
  2. 生成该修改的 Redo Log 记录
  3. 将 Redo Log 写入 Log Buffer（内存）
  4. 事务提交时将 Log Buffer 刷盘到 Redo Log 文件
     （由 innodb_flush_log_at_trx_commit 控制刷盘策略）
  5. 返回客户端"提交成功"
  6. 脏页后续由后台线程异步刷入数据文件（.ibd）

关键点：
  步骤 4 完成后事务就持久化了（即使脏页还没刷盘）
  Redo Log 是顺序写入（速度快）
  数据文件是随机写入（速度慢）
  WAL 用顺序写代替随机写，提升性能

崩溃恢复：
  MySQL 异常重启后：
  1. 读取 Redo Log 中最近的 Checkpoint 位置
  2. 从 Checkpoint 位置开始扫描 Redo Log
  3. 将 Redo Log 中记录的修改重新应用到数据页
  4. 回滚未提交的事务（使用 Undo Log）
  5. 恢复完成，接受新连接
```

## LSN（Log Sequence Number）

```sql
-- LSN 是 Redo Log 的逻辑时间戳
-- 单调递增的字节计数器
-- 用于标识 Redo Log 中每个位置

-- 查看关键 LSN：
SHOW ENGINE INNODB STATUS\G
-- LOG 部分输出：
-- Log sequence number          12345678900
-- Log flushed up to            12345678800
-- Pages flushed up to          12345678000
-- Last checkpoint at           12345677000

-- 各 LSN 的含义：
-- Log sequence number：当前最新写入 Log Buffer 的 LSN
-- Log flushed up to：已刷盘到 Redo Log 文件的 LSN
-- Pages flushed up to：已将脏页刷盘的最老 LSN
-- Last checkpoint at：最近一次 Checkpoint 的 LSN

-- LSN 之间的关系（从大到小）：
-- Log sequence number >= Log flushed up to >= Pages flushed up to >= Last checkpoint

-- 差距的含义：
-- Log sequence number - Log flushed up to：
--   Log Buffer 中还未刷盘的数据量（通常很小）
-- Log sequence number - Last checkpoint：
--   Redo Log 中"活跃"的数据量
--   崩溃恢复时需要重放的最大数据量
--   如果接近 Redo Log 总容量，需要加速 Checkpoint
```

## Checkpoint 机制

```
Checkpoint 的核心作用：

1. 推进 Redo Log 的可回收位置
   Redo Log 是循环使用的（或者说是有限容量的）
   当所有 LSN < X 的脏页都已刷盘
   那么 Redo Log 中 LSN < X 的部分就可以被覆盖
   X 就是 Checkpoint LSN

2. 缩短崩溃恢复时间
   恢复只需要重放 Checkpoint LSN 之后的 Redo Log
   Checkpoint 越频繁，恢复时需要重放的数据越少

Checkpoint 的两种类型：

Sharp Checkpoint（全量刷新）：
  将 Buffer Pool 中的所有脏页一次性刷盘
  MySQL 正常关闭（innodb_fast_shutdown=0）时使用
  不适合在运行时使用（会导致长时间阻塞）

Fuzzy Checkpoint（模糊刷新，日常使用）：
  每次只刷新一部分脏页
  不阻塞前台查询
  包括以下几种触发方式：

  a) Master Thread Checkpoint
     后台主线程每秒或每 10 秒执行一次
     按一定比例刷新脏页

  b) FLUSH_LRU_LIST Checkpoint
     Buffer Pool 需要空闲页时
     从 LRU 链表尾部淘汰页面
     如果被淘汰的页面是脏页，需要先刷盘

  c) Async/Sync Flush Checkpoint
     当 Redo Log 空间使用率超过阈值时触发
     75% 以下：正常（Adaptive Flushing）
     75%~90%：异步刷新（加速刷脏页）
     > 90%：同步刷新（阻塞前台操作，紧急刷盘）

  d) Dirty Page too much Checkpoint
     当脏页比例超过 innodb_max_dirty_pages_pct 时
     加速刷新脏页
```

## 自适应刷新（Adaptive Flushing）

```sql
-- InnoDB 根据 Redo Log 使用率自动调整脏页刷新速度

SHOW VARIABLES LIKE 'innodb_adaptive_flushing';
-- 默认值：ON
-- 开启后 InnoDB 根据 Redo Log 消耗速度预判
-- 提前加速刷新脏页，避免 Redo Log 写满

SHOW VARIABLES LIKE 'innodb_adaptive_flushing_lwm';
-- 默认值：10（%）
-- 低水位标记：Redo Log 使用率低于 10% 时不触发自适应刷新

-- 自适应刷新的算法：
-- InnoDB 计算当前的 Redo Log 生产速度
-- 预测多久后 Redo Log 会写满
-- 据此动态调整脏页刷新速度
-- 在 innodb_io_capacity 和 innodb_io_capacity_max 范围内调整

-- 关键参数配合：
SHOW VARIABLES LIKE 'innodb_max_dirty_pages_pct';
-- 默认值：90
-- 脏页比例超过此值时强制加速刷新

SHOW VARIABLES LIKE 'innodb_max_dirty_pages_pct_lwm';
-- 默认值：10
-- 脏页比例低于此值时预刷新停止
```

## MySQL 8.4 的 Redo Log 管理

```sql
-- MySQL 8.0.30+ / 8.4 使用 innodb_redo_log_capacity 管理

-- 查看当前 Redo Log 容量：
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
-- 默认值：104857600（100MB）

-- InnoDB 自动维护 32 个 Redo Log 文件
-- 位于 datadir/#innodb_redo/ 目录下
-- 每个文件 = innodb_redo_log_capacity / 32

-- 监控 Redo Log 状态（MySQL 8.0.30+）：
SHOW STATUS LIKE 'Innodb_redo_log%';
-- Innodb_redo_log_capacity_resized：当前生效的容量
-- Innodb_redo_log_checkpoint_lsn：最新 Checkpoint LSN
-- Innodb_redo_log_current_lsn：当前最新 LSN
-- Innodb_redo_log_flushed_to_disk_lsn：已刷盘的 LSN

-- 在线调整 Redo Log 容量：
SET GLOBAL innodb_redo_log_capacity = 2 * 1024 * 1024 * 1024;  -- 2GB

-- 监控调整进度：
SHOW STATUS LIKE 'Innodb_redo_log_resize_status';
```

## 常见问题

**MySQL 崩溃恢复需要多长时间？**

恢复时间取决于 Checkpoint LSN 和最新 LSN 之间的差距（即需要重放的 Redo Log 数据量）。Redo Log 容量越大、Checkpoint 越不频繁，差距可能越大，恢复时间越长。经验值：重放 1GB Redo Log 大约需要 1~3 分钟（取决于 I/O 性能和数据页的复杂度）。如果 Redo Log 容量设为 4GB 且崩溃时恰好积累了大量未 Checkpoint 的数据，恢复可能需要 5~15 分钟。可以通过 `innodb_fast_shutdown=1`（默认）让正常关闭时快速完成，但崩溃恢复仍需完整重放。

---

## 注意事项

- `innodb_fast_shutdown` 参数控制 MySQL 正常关闭时的行为。值=0 时执行 Sharp Checkpoint（刷所有脏页 + purge 所有 Undo），关闭很慢但重启很快；值=1（默认）不做完整的 Checkpoint，关闭快但重启可能需要 Redo Log 恢复；值=2 只写日志不做任何刷新，关闭最快但重启需要完整的崩溃恢复。升级 MySQL 版本前建议设为 0 确保干净关闭。
- 不要手动删除 `#innodb_redo/` 目录下的 Redo Log 文件。这些文件是 InnoDB 正常运行所必需的。如果删除后重启 MySQL，InnoDB 会认为需要崩溃恢复但找不到 Redo Log 文件，可能导致数据丢失或无法启动。

## 总结

Redo Log 通过 WAL 机制保证事务持久性：先写日志再写数据。LSN 是 Redo Log 的逻辑位置标识。Checkpoint 定期将脏页刷盘，推进 Redo Log 的可回收位置，缩短崩溃恢复时间。自适应刷新（Adaptive Flushing）根据 Redo Log 使用率动态调整刷新速度。MySQL 8.4 使用 `innodb_redo_log_capacity` 管理 Redo Log（自动维护 32 个文件）。崩溃恢复从 Checkpoint LSN 开始重放 Redo Log。恢复时间取决于需要重放的数据量。`innodb_fast_shutdown` 控制关闭时的 Checkpoint 行为。

# Slow Query Log 慢查询日志

Slow Query Log（慢查询日志）记录执行时间超过 `long_query_time` 阈值的 SQL 语句。与 General Log 记录所有 SQL 不同，Slow Query Log 只记录"慢"的 SQL，因此对性能的影响较小，适合在生产环境长期启用。慢查询日志是 SQL 性能优化的核心工具——通过分析慢查询日志找出执行时间最长的 SQL，针对性地优化索引和查询写法，是提升数据库整体性能的最有效手段。

---

## 参数配置

```sql
-- 查看是否启用：
SHOW VARIABLES LIKE 'slow_query_log';
-- 默认值：OFF

-- 查看慢查询阈值：
SHOW VARIABLES LIKE 'long_query_time';
-- 默认值：10（秒）
-- 支持微秒精度，如 0.1 表示 100 毫秒

-- 查看日志文件路径：
SHOW VARIABLES LIKE 'slow_query_log_file';
-- 默认值：hostname-slow.log

-- 在线开启慢查询日志：
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的查询记录到慢日志

-- 在 my.cnf 中配置（推荐）：
-- [mysqld]
-- slow_query_log = ON
-- slow_query_log_file = /var/log/mysql/slow.log
-- long_query_time = 1
-- log_output = FILE

-- 查看慢查询计数：
SHOW STATUS LIKE 'Slow_queries';
-- 自启动以来超过阈值的查询总数
```

## 慢查询日志内容

```
慢查询日志文件的内容示例：

# Time: 2024-06-15T10:30:01.123456Z
# User@Host: app_user[app_user] @ 192.168.1.50 [192.168.1.50]  Id: 12345
# Query_time: 3.456789  Lock_time: 0.000123  Rows_sent: 100  Rows_examined: 1500000
SET timestamp=1718444001;
SELECT * FROM orders WHERE create_time > '2024-01-01' ORDER BY amount DESC LIMIT 100;

各字段含义：
  Time：查询完成的时间
  User@Host：执行查询的用户和客户端地址
  Id：连接线程 ID
  Query_time：查询执行时间（秒，含微秒）
  Lock_time：等待表锁的时间
  Rows_sent：返回给客户端的行数
  Rows_examined：扫描的总行数（优化重点指标）
  SQL 语句：实际执行的 SQL

关键指标：
  Query_time 越大 → 查询越慢
  Rows_examined / Rows_sent 比值越大 → 扫描效率越低
  例如 Rows_sent=100, Rows_examined=1500000
  说明扫描了 150 万行只返回 100 行，缺少合适的索引
```

## 慢查询日志分析工具

```bash
# mysqldumpslow（MySQL 自带工具）：
# 按查询时间排序，显示前 10 条最慢的查询：
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按出现次数排序（最频繁的慢查询）：
mysqldumpslow -s c -t 10 /var/log/mysql/slow.log

# 按扫描行数排序：
mysqldumpslow -s r -t 10 /var/log/mysql/slow.log

# 输出示例：
# Count: 156  Time=3.45s (538s)  Lock=0.00s (0s)  Rows=100.0 (15600)
# SELECT * FROM orders WHERE create_time > 'S' ORDER BY amount DESC LIMIT N
# （S 和 N 是参数化后的占位符）

# pt-query-digest（Percona Toolkit，更强大）：
pt-query-digest /var/log/mysql/slow.log

# pt-query-digest 输出更详细：
# 按总执行时间排名
# 显示每种查询的平均时间、最大时间、P95 时间
# 显示查询的执行计划建议
# 可以直接输出到文件或数据库
pt-query-digest /var/log/mysql/slow.log --output=report > slow_report.txt

# 只分析最近 1 小时的慢查询：
pt-query-digest --since '1h' /var/log/mysql/slow.log
```

## 相关参数

```sql
-- 记录没有使用索引的查询（即使没有超过时间阈值）：
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
-- 默认值：OFF
SET GLOBAL log_queries_not_using_indexes = ON;

-- 限制每分钟记录的无索引查询数量（防止日志爆炸）：
SHOW VARIABLES LIKE 'log_throttle_queries_not_using_indexes';
-- 默认值：0（不限制）
SET GLOBAL log_throttle_queries_not_using_indexes = 60;
-- 每分钟最多记录 60 条无索引查询

-- 记录管理语句到慢日志：
SHOW VARIABLES LIKE 'log_slow_admin_statements';
-- 默认值：OFF
-- 开启后 ALTER TABLE、ANALYZE TABLE 等管理语句也会被记录

-- 记录从库复制的慢查询：
SHOW VARIABLES LIKE 'log_slow_replica_statements';
-- 默认值：OFF
-- 开启后从库 SQL 线程执行的慢查询也会被记录

-- 最小扫描行数阈值：
SHOW VARIABLES LIKE 'min_examined_row_limit';
-- 默认值：0
-- 设为非零值时，只有扫描行数超过此值的慢查询才会被记录
-- 可以过滤掉扫描行数很少但执行时间长（等锁）的查询
```

## 适用场景

- **生产环境的常规性能监控**：将 `long_query_time` 设为 1~2 秒，长期启用慢查询日志，定期用 pt-query-digest 分析，找出需要优化的 TOP SQL
- **上线前后的性能对比**：在新版本上线前后分别收集慢查询日志，对比分析是否有新增的慢查询或性能退化

## 常见问题

**long_query_time 设为多少比较合适？**

没有标准答案，取决于业务的延迟要求。常见的设置：①通用 Web 应用：1~2 秒（大多数 Web 页面要求 1~3 秒内响应，超过 1 秒的 SQL 就需要关注）；②对延迟敏感的应用（如支付）：0.1~0.5 秒；③分析型查询（报表）：5~10 秒。建议初始设为 1 秒，如果慢查询日志增长太快（每天 > 100MB），适当增大阈值；如果日志很小（每天 < 1MB），可以降低阈值以发现更多可优化的查询。

## 注意事项

- 慢查询日志记录的 `Query_time` 是实际执行时间，不包含等待获取锁的时间（`Lock_time` 单独记录）。一个查询 `Query_time=0.001` 但 `Lock_time=5.000`，说明查询本身很快但等锁等了 5 秒。优化方向不是优化 SQL 本身，而是排查锁冲突。
- 慢查询日志文件没有自动清理机制，需要配合 logrotate 定期轮转。建议保留最近 7~30 天的慢查询日志。轮转时使用 `FLUSH SLOW LOGS` 命令让 MySQL 关闭旧文件并打开新文件。

## 总结

Slow Query Log 记录执行时间超过 `long_query_time` 的 SQL，是性能优化的核心工具。默认关闭，生产环境建议长期开启。`long_query_time` 默认 10 秒，建议设为 1~2 秒。日志内容包含 Query_time、Lock_time、Rows_sent、Rows_examined 等关键指标。分析工具：mysqldumpslow（自带）和 pt-query-digest（更强大）。Rows_examined/Rows_sent 比值大说明缺少索引。`log_queries_not_using_indexes` 可记录无索引查询。需配合 logrotate 管理日志文件。

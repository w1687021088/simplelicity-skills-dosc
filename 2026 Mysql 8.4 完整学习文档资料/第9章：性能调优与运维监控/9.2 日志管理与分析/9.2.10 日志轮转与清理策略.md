# 日志轮转与清理策略

MySQL 在运行过程中会产生多种日志文件：Error Log、General Log、Slow Query Log、Binary Log 等。这些日志文件如果不加管理会持续增长，占用大量磁盘空间，甚至导致磁盘写满影响数据库正常运行。日志轮转（Log Rotation）是指定期关闭当前日志文件、创建新文件，并按照保留策略清理旧文件的过程。不同类型的日志有不同的轮转和清理方式。

---

## FLUSH LOGS 命令

```sql
-- FLUSH LOGS 可以关闭并重新打开各类日志文件

-- 刷新所有日志：
FLUSH LOGS;
-- 等同于同时执行以下所有命令

-- 按类型分别刷新：
FLUSH BINARY LOGS;    -- 关闭当前 binlog，创建新的 binlog 文件（编号+1）
FLUSH ERROR LOGS;     -- 关闭并重新打开错误日志文件
FLUSH GENERAL LOGS;   -- 关闭并重新打开通用查询日志
FLUSH SLOW LOGS;      -- 关闭并重新打开慢查询日志
FLUSH RELAY LOGS;     -- 关闭并重新打开中继日志
FLUSH ENGINE LOGS;    -- 刷新存储引擎日志

-- 命令行方式：
-- mysqladmin flush-logs
-- mysqladmin flush-logs error       -- 只刷新错误日志
-- mysqladmin flush-logs slow        -- 只刷新慢查询日志

-- FLUSH LOGS 的行为：
-- Binary Log：创建新文件（mysql-bin.000002 → mysql-bin.000003）
-- Error Log / General Log / Slow Log：
--   关闭当前文件句柄
--   重新打开同名文件（如果文件被重命名了，则创建新文件）
--   这就是配合 logrotate 的关键
```

## Error Log 轮转

```bash
# Error Log 没有内置的自动轮转机制
# 需要使用操作系统的 logrotate 工具

# Linux logrotate 配置文件：/etc/logrotate.d/mysql-error

/var/log/mysql/error.log {
    daily                    # 每天轮转
    rotate 30                # 保留 30 个旧文件
    missingok                # 文件不存在不报错
    compress                 # 压缩旧日志
    delaycompress            # 延迟一天再压缩（方便查看最近的日志）
    notifempty               # 空文件不轮转
    create 640 mysql mysql   # 创建新文件的权限和属主
    postrotate
        # 轮转后通知 MySQL 重新打开日志文件
        mysqladmin --defaults-file=/root/.my.cnf flush-logs error
        # 或者使用 kill -HUP 发送信号
    endscript
}

# 手动执行 logrotate 测试：
# logrotate -f /etc/logrotate.d/mysql-error

# 轮转流程：
# 1. logrotate 将 error.log 重命名为 error.log.1
# 2. 执行 postrotate 中的 flush-logs error
# 3. MySQL 关闭旧文件句柄，创建新的 error.log
# 4. 旧文件 error.log.1 在第二天被压缩为 error.log.1.gz
```

## Slow Query Log 轮转

```bash
# Slow Query Log 同样使用 logrotate

# 配置文件：/etc/logrotate.d/mysql-slow

/var/log/mysql/slow.log {
    weekly                   # 每周轮转
    rotate 12                # 保留 12 周（约 3 个月）
    missingok
    compress
    delaycompress
    notifempty
    create 640 mysql mysql
    postrotate
        mysqladmin --defaults-file=/root/.my.cnf flush-logs slow
    endscript
}

# 也可以用 SQL 方式轮转：
# SET GLOBAL slow_query_log = OFF;
# -- 重命名文件：mv slow.log slow.log.bak
# SET GLOBAL slow_query_log = ON;
# -- MySQL 自动创建新的 slow.log
```

## Binary Log 自动清理

```sql
-- Binary Log 有内置的自动清理机制，不需要 logrotate

-- 查看自动清理时间：
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
-- 默认值：2592000（30 天）

-- 设置保留天数：
SET GLOBAL binlog_expire_logs_seconds = 604800;  -- 7 天

-- 手动清理：
-- 清理指定文件之前的 binlog：
PURGE BINARY LOGS TO 'mysql-bin.000050';

-- 清理指定时间之前的 binlog：
PURGE BINARY LOGS BEFORE '2024-06-01 00:00:00';

-- 查看当前 binlog 文件列表和大小：
SHOW BINARY LOGS;

-- 重要提示：
-- 不要用 rm 直接删除 binlog 文件
-- 必须使用 PURGE BINARY LOGS 命令
-- 否则 binlog 索引文件（mysql-bin.index）会不一致
-- 如果有从库，确保从库已经读取了要清理的 binlog

-- binlog 文件大小控制：
SHOW VARIABLES LIKE 'max_binlog_size';
-- 默认值：1073741824（1GB）
-- 单个 binlog 文件达到此大小后自动切换到新文件
```

## General Log 轮转

```bash
# General Log 通常只在排查问题时临时开启
# 如果长期开启，需要配置轮转

# 方式1：logrotate（类似 Error Log）
/var/log/mysql/general.log {
    daily
    rotate 7
    missingok
    compress
    notifempty
    create 640 mysql mysql
    postrotate
        mysqladmin --defaults-file=/root/.my.cnf flush-logs general
    endscript
}

# 方式2：SQL 方式轮转
# SET GLOBAL general_log = OFF;
# -- mv general.log general.log.bak
# SET GLOBAL general_log = ON;

# 方式3：如果输出到表（log_output=TABLE）
# TRUNCATE TABLE mysql.general_log;
# 表模式不需要 logrotate
```

## 各日志的清理策略汇总

| 日志类型 | 轮转方式 | 推荐保留时间 | 清理命令 |
|---------|:-------:|:----------:|:-------:|
| Error Log | logrotate + FLUSH ERROR LOGS | 30~90 天 | logrotate 自动 |
| Slow Query Log | logrotate + FLUSH SLOW LOGS | 7~30 天 | logrotate 自动 |
| General Log | logrotate 或手动 | 1~7 天（临时使用）| 手动关闭/TRUNCATE |
| Binary Log | binlog_expire_logs_seconds | 7~30 天 | PURGE BINARY LOGS |
| Relay Log | relay_log_purge=ON 自动清理 | 自动 | MySQL 自动 |
| Redo Log | InnoDB 自动管理 | 不需清理 | 自动循环使用 |
| Undo Log | innodb_undo_log_truncate 自动截断 | 不需清理 | 自动截断 |

## 磁盘空间监控

```bash
# 监控 MySQL 数据目录的磁盘使用：

# 查看数据目录位置：
mysql -e "SHOW VARIABLES LIKE 'datadir'"

# 查看各类文件的磁盘使用：
du -sh /var/lib/mysql/*.log          # Error Log
du -sh /var/lib/mysql/mysql-bin.*    # Binary Log
du -sh /var/lib/mysql/relay-bin.*    # Relay Log（从库）
du -sh /var/lib/mysql/#innodb_redo/  # Redo Log
du -sh /var/lib/mysql/undo_*        # Undo 表空间

# 查看总磁盘使用：
df -h /var/lib/mysql/

# 建议告警阈值：
# 磁盘使用率 > 80%：警告
# 磁盘使用率 > 90%：严重告警
# 磁盘使用率 > 95%：紧急（可能导致 MySQL 写入失败）
```

## 适用场景

- **生产环境的日常运维**：所有生产环境的 MySQL 都必须配置日志轮转和清理策略，防止日志文件无限增长占满磁盘
- **磁盘空间告警后的紧急处理**：磁盘空间不足时，通过清理 binlog（`PURGE BINARY LOGS`）和 truncate 日志表快速释放空间

## 常见问题

**磁盘空间不足但 PURGE BINARY LOGS 后空间没有释放，为什么？**

可能的原因：①还有进程持有已删除文件的文件描述符（Linux 下删除的文件如果还被进程打开，空间不会释放）。用 `lsof +D /var/lib/mysql/ | grep deleted` 检查。解决方法是重启 MySQL 或执行 `FLUSH BINARY LOGS`。②清理的 binlog 不是占用空间的主要部分。检查 `.ibd` 数据文件（可能是大表）、Undo 表空间文件（可能因长事务膨胀）或 InnoDB 的临时表空间（`ibtmp1`）是否占用了大量空间。

## 注意事项

- logrotate 的 postrotate 脚本中执行 `mysqladmin flush-logs` 需要 MySQL 的用户名和密码。建议使用 `--defaults-file` 指定包含认证信息的配置文件（如 `/root/.my.cnf`），避免在脚本中明文写密码。该配置文件的权限应设为 `600`（仅 root 可读）。
- 在有从库的复制架构中，清理主库的 binlog 前必须确认所有从库都已读取了要清理的 binlog。可以通过 `SHOW REPLICAS`（或 `SHOW SLAVE HOSTS`）查看从库列表，再通过 `SHOW REPLICA STATUS` 查看各从库已读取到的 binlog 位置。如果清理了从库还未读取的 binlog，从库复制会中断。

---

## 总结

MySQL 各日志的轮转方式不同：Error/Slow/General Log 使用 logrotate + `FLUSH LOGS` 轮转；Binary Log 使用 `binlog_expire_logs_seconds` 自动清理或 `PURGE BINARY LOGS` 手动清理；Relay Log 由 MySQL 自动清理（`relay_log_purge=ON`）；Redo Log 和 Undo Log 由 InnoDB 自动管理。不要用 `rm` 直接删除 binlog 文件。logrotate 的 postrotate 脚本需要调用 `flush-logs`。磁盘使用率 80% 以上需告警。清理 binlog 前确认从库已读取。

# events_waits_current 等待事件

`events_waits_current` 表记录每个线程当前正在经历的等待事件。所谓"等待事件"，就是线程在执行过程中被阻塞或暂停的原因，比如等待获取互斥锁（mutex）、等待磁盘 I/O 完成、等待行锁释放等。等待事件是 Performance Schema 中粒度最细的监控数据，可以精确定位查询"慢在哪里"——到底是 CPU 计算慢、磁盘读取慢、还是在等锁。

---

## 等待事件的分类

```
Performance Schema 中的等待事件按前缀分类：

wait/io/file/         文件 I/O 等待
  等待磁盘文件的读写完成
  例如：wait/io/file/innodb/innodb_data_file（数据文件 I/O）
  例如：wait/io/file/innodb/innodb_log_file（Redo Log I/O）
  例如：wait/io/file/sql/binlog（Binlog 写入）

wait/io/table/        表 I/O 等待
  等待表的读写操作
  例如：wait/io/table/sql/handler（表访问）

wait/io/socket/       网络 Socket I/O 等待
  等待网络数据传输
  例如：wait/io/socket/sql/client_connection

wait/synch/mutex/     互斥锁等待
  等待获取互斥锁（排他锁）
  例如：wait/synch/mutex/innodb/buf_pool_mutex（Buffer Pool 锁）
  例如：wait/synch/mutex/innodb/log_sys_mutex（日志系统锁）

wait/synch/rwlock/    读写锁等待
  等待获取读写锁
  例如：wait/synch/rwlock/innodb/btr_search_latch（AHI 锁）

wait/synch/cond/      条件变量等待
  等待条件满足
  例如：wait/synch/cond/innodb/srv_master_thread（主线程休眠）

wait/lock/table/      表级锁等待
  等待表级的元数据锁（MDL）或表锁

wait/lock/metadata/   元数据锁等待
  等待 DDL 操作的元数据锁
  例如：wait/lock/metadata/sql/mdl
```

## 基本查询

```sql
-- 查看当前所有线程的等待事件：
SELECT
    THREAD_ID,
    EVENT_NAME,
    TIMER_WAIT / 1000000000 AS wait_ms,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    OBJECT_TYPE,
    OPERATION
FROM performance_schema.events_waits_current
WHERE EVENT_NAME != 'idle'
ORDER BY TIMER_WAIT DESC;

-- 查看当前被 I/O 阻塞的线程：
SELECT
    t.PROCESSLIST_USER,
    t.PROCESSLIST_DB,
    ewc.EVENT_NAME,
    ewc.TIMER_WAIT / 1000000000 AS wait_ms,
    ewc.OBJECT_NAME AS file_name,
    ewc.OPERATION
FROM performance_schema.events_waits_current ewc
JOIN performance_schema.threads t ON ewc.THREAD_ID = t.THREAD_ID
WHERE ewc.EVENT_NAME LIKE 'wait/io/file/%'
  AND t.TYPE = 'FOREGROUND'
ORDER BY ewc.TIMER_WAIT DESC;

-- 查看当前等待锁的线程：
SELECT
    t.PROCESSLIST_USER,
    t.PROCESSLIST_ID,
    ewc.EVENT_NAME,
    ewc.TIMER_WAIT / 1000000000 AS wait_ms,
    ewc.OBJECT_SCHEMA,
    ewc.OBJECT_NAME
FROM performance_schema.events_waits_current ewc
JOIN performance_schema.threads t ON ewc.THREAD_ID = t.THREAD_ID
WHERE ewc.EVENT_NAME LIKE 'wait/synch/%'
  OR ewc.EVENT_NAME LIKE 'wait/lock/%'
ORDER BY ewc.TIMER_WAIT DESC;
```

## 等待事件的启用

```sql
-- 默认情况下 wait 类探针大部分是关闭的
-- 需要手动启用才能采集等待事件

-- 启用所有等待事件探针：
UPDATE performance_schema.setup_instruments
SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'wait/%';

-- 启用等待事件的消费者：
UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES'
WHERE NAME LIKE 'events_waits%';

-- 只启用特定类型（如文件 I/O）：
UPDATE performance_schema.setup_instruments
SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'wait/io/file/%';

-- 使用 sys schema 便捷方式：
CALL sys.ps_setup_enable_instrument('wait');
CALL sys.ps_setup_enable_consumer('current');
```

## 等待事件统计分析

```sql
-- 等待事件全局统计（按事件类型聚合）：
SELECT
    EVENT_NAME,
    COUNT_STAR AS total_count,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec,
    AVG_TIMER_WAIT / 1000000000 AS avg_wait_ms,
    MAX_TIMER_WAIT / 1000000000 AS max_wait_ms
FROM performance_schema.events_waits_summary_global_by_event_name
WHERE COUNT_STAR > 0
  AND EVENT_NAME != 'idle'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

-- 找出总等待时间最长的事件类型
-- 这就是数据库性能瓶颈所在
-- 如果是 wait/io/file → I/O 瓶颈
-- 如果是 wait/synch/mutex → 锁竞争瓶颈
-- 如果是 wait/lock → 行锁或元数据锁问题

-- 按线程统计等待（找出等待最多的线程）：
SELECT
    t.PROCESSLIST_USER,
    t.PROCESSLIST_DB,
    ews.EVENT_NAME,
    ews.COUNT_STAR,
    ews.SUM_TIMER_WAIT / 1000000000000 AS total_sec
FROM performance_schema.events_waits_summary_by_thread_by_event_name ews
JOIN performance_schema.threads t ON ews.THREAD_ID = t.THREAD_ID
WHERE ews.COUNT_STAR > 100
  AND ews.EVENT_NAME != 'idle'
ORDER BY ews.SUM_TIMER_WAIT DESC
LIMIT 20;
```

## 适用场景

- **定位查询慢的根因**：当一条查询执行很慢时，通过等待事件可以精确判断慢在哪里——是磁盘 I/O（wait/io/file）、锁等待（wait/synch/mutex 或 wait/lock）、还是网络传输（wait/io/socket）
- **诊断系统级性能瓶颈**：通过全局等待事件统计（`events_waits_summary_global_by_event_name`），找出整个服务器最大的性能瓶颈类型

## 常见问题

**启用所有 wait 探针后性能下降明显，如何处理？**

`wait/synch/mutex` 和 `wait/synch/rwlock` 类探针的开销最大，因为互斥锁的获取和释放在 MySQL 内部非常频繁（每秒可能数百万次）。建议的做法是：①只在排查问题时临时启用全部 wait 探针，排查完成后关闭；②日常只保留 `wait/io/file` 和 `wait/io/table` 探针（I/O 类），这些探针的调用频率低得多，开销很小；③使用 `events_waits_summary_global_by_event_name` 统计表而非 `events_waits_current`，统计表的查询开销更小。

---

## 注意事项

- 等待事件是 Performance Schema 中粒度最细的数据，一条 SQL 语句的执行过程中可能产生数百到数千个等待事件。因此 `events_waits_history` 和 `events_waits_history_long` 表的数据更替非常快，可能在几秒内就被新数据覆盖。如果需要捕捉特定问题时刻的等待事件，需要在问题发生时立即查询，或者增大 `performance_schema_events_waits_history_long_size`。
- 等待事件中出现频率最高的通常是 `idle`（线程空闲等待客户端请求），这是正常的。分析时应排除 `idle` 事件，只关注真正的性能等待（I/O、锁、同步等）。

---

## 总结

`events_waits_current` 记录每个线程当前的等待事件，是定位性能瓶颈根因的核心工具。等待类型包括文件 I/O（wait/io/file）、网络 I/O（wait/io/socket）、互斥锁（wait/synch/mutex）、读写锁（wait/synch/rwlock）、元数据锁（wait/lock/metadata）等。默认大部分 wait 探针关闭，需手动启用。通过 `events_waits_summary_global_by_event_name` 统计全局等待分布，判断瓶颈类型。mutex/rwlock 探针开销大，排查时临时启用。分析时排除 idle 事件。

# events_statements_history 历史语句

`events_statements_history` 和 `events_statements_history_long` 是 Performance Schema 中用于记录 SQL 语句执行历史的两张表。`events_statements_history` 按线程保留最近执行的 N 条语句（默认 10 条/线程），适合查看某个连接最近的操作。`events_statements_history_long` 全局保留最近的 N 条语句（默认 10000 条），适合回顾整个服务器最近的活动。这两张表的列结构与 `events_statements_current` 完全相同。

---

## events_statements_history（线程历史）

```sql
-- 每个线程保留最近 N 条语句
-- N 由 performance_schema_events_statements_history_size 控制

SHOW VARIABLES LIKE 'performance_schema_events_statements_history_size';
-- 默认值：10（每个线程保留最近 10 条）

-- 查看某个线程的最近执行历史：
SELECT
    THREAD_ID,
    EVENT_ID,
    SQL_TEXT,
    TIMER_WAIT / 1000000000000 AS exec_time_sec,
    ROWS_EXAMINED,
    ROWS_SENT,
    ERRORS,
    WARNINGS
FROM performance_schema.events_statements_history
WHERE THREAD_ID = 100
ORDER BY EVENT_ID DESC;

-- 查看当前连接的执行历史：
SELECT
    SQL_TEXT,
    TIMER_WAIT / 1000000000000 AS exec_time_sec,
    ROWS_EXAMINED,
    ROWS_SENT
FROM performance_schema.events_statements_history
WHERE THREAD_ID = (
    SELECT THREAD_ID FROM performance_schema.threads
    WHERE PROCESSLIST_ID = CONNECTION_ID()
)
ORDER BY EVENT_ID DESC;

-- 查看某个用户的最近执行历史：
SELECT
    t.PROCESSLIST_USER,
    t.PROCESSLIST_DB,
    esh.SQL_TEXT,
    esh.TIMER_WAIT / 1000000000000 AS exec_time_sec,
    esh.ROWS_EXAMINED
FROM performance_schema.events_statements_history esh
JOIN performance_schema.threads t ON esh.THREAD_ID = t.THREAD_ID
WHERE t.PROCESSLIST_USER = 'app_user'
ORDER BY esh.TIMER_WAIT DESC
LIMIT 20;
```

## events_statements_history_long（全局长历史）

```sql
-- 全局保留最近 N 条语句（所有线程共享）
-- N 由 performance_schema_events_statements_history_long_size 控制

SHOW VARIABLES LIKE 'performance_schema_events_statements_history_long_size';
-- 默认值：10000

-- 默认该消费者是关闭的，需要手动启用：
SELECT NAME, ENABLED
FROM performance_schema.setup_consumers
WHERE NAME = 'events_statements_history_long';
-- 默认 ENABLED = NO

-- 启用：
UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES'
WHERE NAME = 'events_statements_history_long';

-- 查看全局最近执行的慢查询：
SELECT
    t.PROCESSLIST_USER,
    t.PROCESSLIST_DB,
    eshl.SQL_TEXT,
    eshl.TIMER_WAIT / 1000000000000 AS exec_time_sec,
    eshl.ROWS_EXAMINED,
    eshl.ROWS_SENT,
    eshl.CREATED_TMP_DISK_TABLES,
    eshl.NO_INDEX_USED
FROM performance_schema.events_statements_history_long eshl
JOIN performance_schema.threads t ON eshl.THREAD_ID = t.THREAD_ID
WHERE eshl.TIMER_WAIT > 1000000000000  -- > 1 秒
ORDER BY eshl.TIMER_WAIT DESC
LIMIT 20;
```

## 语句摘要统计表

```sql
-- events_statements_summary_by_digest 是最实用的统计表
-- 按语句指纹（Digest）聚合统计

SELECT
    SCHEMA_NAME,
    DIGEST_TEXT,
    COUNT_STAR AS exec_count,
    SUM_TIMER_WAIT / 1000000000000 AS total_time_sec,
    AVG_TIMER_WAIT / 1000000000000 AS avg_time_sec,
    MAX_TIMER_WAIT / 1000000000000 AS max_time_sec,
    SUM_ROWS_EXAMINED,
    SUM_ROWS_SENT,
    SUM_ROWS_EXAMINED / GREATEST(SUM_ROWS_SENT, 1) AS avg_scan_ratio,
    SUM_CREATED_TMP_DISK_TABLES,
    SUM_NO_INDEX_USED,
    FIRST_SEEN,
    LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 找出执行次数最多的 SQL：
SELECT DIGEST_TEXT, COUNT_STAR, 
    AVG_TIMER_WAIT / 1000000000000 AS avg_sec
FROM performance_schema.events_statements_summary_by_digest
ORDER BY COUNT_STAR DESC
LIMIT 10;

-- 找出平均执行时间最长的 SQL：
SELECT DIGEST_TEXT, COUNT_STAR,
    AVG_TIMER_WAIT / 1000000000000 AS avg_sec,
    MAX_TIMER_WAIT / 1000000000000 AS max_sec
FROM performance_schema.events_statements_summary_by_digest
WHERE COUNT_STAR > 10  -- 至少执行过 10 次
ORDER BY AVG_TIMER_WAIT DESC
LIMIT 10;

-- 找出扫描效率最低的 SQL：
SELECT DIGEST_TEXT, COUNT_STAR,
    SUM_ROWS_EXAMINED / GREATEST(COUNT_STAR, 1) AS avg_rows_examined,
    SUM_ROWS_SENT / GREATEST(COUNT_STAR, 1) AS avg_rows_sent
FROM performance_schema.events_statements_summary_by_digest
WHERE SUM_ROWS_EXAMINED > 100000
ORDER BY SUM_ROWS_EXAMINED DESC
LIMIT 10;

-- 重置统计数据（重新开始计数）：
TRUNCATE performance_schema.events_statements_summary_by_digest;
```

## 三张表的对比

| 对比维度 | events_statements_current | events_statements_history | events_statements_history_long |
|---------|:------------------------:|:------------------------:|:-----------------------------:|
| 记录范围 | 每线程当前/最近 1 条 | 每线程最近 N 条 | 全局最近 N 条 |
| 默认 N 值 | 1 | 10 | 10000 |
| 默认启用 | YES | YES | NO |
| 数据保留 | 被下一条覆盖 | FIFO 循环 | FIFO 循环 |
| 适合场景 | 实时查看 | 排查单线程问题 | 回顾全局活动 |

## 适用场景

- **排查某个连接的异常行为**：通过 `events_statements_history` 查看某个线程最近执行了哪些 SQL，判断是否有异常操作（如意外的 DELETE、重复的全表扫描等）
- **SQL 性能趋势分析**：通过 `events_statements_summary_by_digest` 找出总执行时间最长、执行次数最多、扫描效率最低的 SQL 类型，作为优化的优先级排序依据

## 常见问题

**events_statements_summary_by_digest 中的 DIGEST_TEXT 显示为 NULL 是什么原因？**

当 `performance_schema_digests_size` 设置的容量被耗尽时，新的 SQL 指纹无法被记录到摘要表中，这些"溢出"的语句会被归入一个 `DIGEST = NULL` 的特殊行。可以通过 `SHOW STATUS LIKE 'Performance_schema_digest_lost'` 查看丢失了多少语句的统计。解决方法是增大 `performance_schema_digests_size`（在 my.cnf 中设置并重启），或者用 `TRUNCATE` 清空摘要表释放空间。

---

## 注意事项

- `events_statements_history` 的大小由 `performance_schema_events_statements_history_size` 控制，该参数只能在启动时设置。默认 10 条/线程在排查问题时可能不够用（问题语句可能已被新语句覆盖）。生产环境中可以考虑增大到 20~50，内存增加不大但可用性提升显著。
- `events_statements_summary_by_digest` 表在长时间运行后可能积累大量的语句指纹。`FIRST_SEEN` 和 `LAST_SEEN` 列可以帮助判断某个 SQL 模板是什么时候首次出现和最近一次出现的。定期 TRUNCATE 这张表可以重新开始统计，便于观察最近时间窗口内的 SQL 分布。

---

## 总结

`events_statements_history` 按线程保留最近 N 条语句（默认 10 条），适合排查单连接问题。`events_statements_history_long` 全局保留最近 N 条（默认 10000，默认关闭），适合回顾整体活动。`events_statements_summary_by_digest` 按语句指纹聚合统计，是日常性能分析最实用的表。关键指标：总执行时间、执行次数、平均时间、扫描行数/返回行数比。可通过 TRUNCATE 重置统计。`DIGEST = NULL` 表示指纹容量耗尽。

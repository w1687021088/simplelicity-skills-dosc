# file_io_summary 表 IO 统计

Performance Schema 提供了两张文件 I/O 统计表：`file_summary_by_event_name`（按事件类型聚合）和 `file_summary_by_instance`（按文件实例聚合）。它们记录了 MySQL 服务器所有文件操作的统计数据，包括读写次数、读写字节数和等待时间。通过这些表可以清楚地了解哪些文件的 I/O 最频繁、哪些文件的 I/O 延迟最高，是诊断 I/O 性能瓶颈的关键工具。

---

## file_summary_by_event_name（按事件类型聚合）

```sql
-- 按文件 I/O 事件类型查看统计
-- 了解哪类文件操作最耗时

SELECT
    EVENT_NAME,
    COUNT_STAR AS total_ops,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec,
    COUNT_READ,
    SUM_NUMBER_OF_BYTES_READ / 1024 / 1024 AS read_mb,
    SUM_TIMER_READ / 1000000000000 AS read_wait_sec,
    COUNT_WRITE,
    SUM_NUMBER_OF_BYTES_WRITE / 1024 / 1024 AS write_mb,
    SUM_TIMER_WRITE / 1000000000000 AS write_wait_sec,
    COUNT_MISC,
    SUM_TIMER_MISC / 1000000000000 AS misc_wait_sec
FROM performance_schema.file_summary_by_event_name
WHERE COUNT_STAR > 0
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 15;

-- 常见的事件类型：
-- wait/io/file/innodb/innodb_data_file  InnoDB 数据文件（.ibd）
-- wait/io/file/innodb/innodb_log_file   Redo Log 文件
-- wait/io/file/sql/binlog               Binlog 文件
-- wait/io/file/innodb/innodb_temp_file  InnoDB 临时文件
-- wait/io/file/sql/slow_log             慢查询日志文件
-- wait/io/file/sql/io_cache             排序和临时文件
-- wait/io/file/innodb/innodb_dblwr_file Doublewrite 文件
```

## file_summary_by_instance（按文件实例聚合）

```sql
-- 按具体文件查看 I/O 统计
-- 找出 I/O 最繁忙的具体文件

SELECT
    FILE_NAME,
    EVENT_NAME,
    COUNT_STAR AS total_ops,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec,
    COUNT_READ,
    SUM_NUMBER_OF_BYTES_READ / 1024 / 1024 AS read_mb,
    AVG_TIMER_READ / 1000000000 AS avg_read_ms,
    COUNT_WRITE,
    SUM_NUMBER_OF_BYTES_WRITE / 1024 / 1024 AS write_mb,
    AVG_TIMER_WRITE / 1000000000 AS avg_write_ms
FROM performance_schema.file_summary_by_instance
WHERE COUNT_STAR > 0
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

-- 找出读 I/O 最多的文件：
SELECT
    FILE_NAME,
    COUNT_READ,
    SUM_NUMBER_OF_BYTES_READ / 1024 / 1024 AS read_mb,
    SUM_TIMER_READ / 1000000000000 AS read_wait_sec,
    AVG_TIMER_READ / 1000000000 AS avg_read_ms
FROM performance_schema.file_summary_by_instance
WHERE COUNT_READ > 0
ORDER BY SUM_TIMER_READ DESC
LIMIT 10;

-- 找出写 I/O 最多的文件：
SELECT
    FILE_NAME,
    COUNT_WRITE,
    SUM_NUMBER_OF_BYTES_WRITE / 1024 / 1024 AS write_mb,
    SUM_TIMER_WRITE / 1000000000000 AS write_wait_sec,
    AVG_TIMER_WRITE / 1000000000 AS avg_write_ms
FROM performance_schema.file_summary_by_instance
WHERE COUNT_WRITE > 0
ORDER BY SUM_TIMER_WRITE DESC
LIMIT 10;
```

## 列含义说明

```
file_summary 表的统计列分为三组：

读操作（Read）：
  COUNT_READ：读操作次数
  SUM_TIMER_READ：读操作总等待时间（皮秒）
  MIN_TIMER_READ / AVG_TIMER_READ / MAX_TIMER_READ：最小/平均/最大读延迟
  SUM_NUMBER_OF_BYTES_READ：读取的总字节数

写操作（Write）：
  COUNT_WRITE：写操作次数
  SUM_TIMER_WRITE：写操作总等待时间
  MIN_TIMER_WRITE / AVG_TIMER_WRITE / MAX_TIMER_WRITE
  SUM_NUMBER_OF_BYTES_WRITE：写入的总字节数

杂项操作（Misc）：
  COUNT_MISC：杂项操作次数（如 open、close、seek、stat 等）
  SUM_TIMER_MISC：杂项操作总等待时间
  这些操作不涉及数据读写，但仍有时间开销

汇总列：
  COUNT_STAR：所有操作的总次数 = COUNT_READ + COUNT_WRITE + COUNT_MISC
  SUM_TIMER_WAIT：所有操作的总等待时间
```

## 实战分析场景

```sql
-- 场景1：判断 I/O 瓶颈类型
-- 如果 innodb_data_file 的总等待时间远大于其他文件
-- 说明数据文件的随机读写是瓶颈
-- 优化方向：增大 Buffer Pool、使用更快的存储

-- 场景2：找出 I/O 延迟异常的文件
SELECT
    FILE_NAME,
    AVG_TIMER_READ / 1000000000 AS avg_read_ms,
    MAX_TIMER_READ / 1000000000 AS max_read_ms,
    AVG_TIMER_WRITE / 1000000000 AS avg_write_ms,
    MAX_TIMER_WRITE / 1000000000 AS max_write_ms
FROM performance_schema.file_summary_by_instance
WHERE COUNT_STAR > 100
  AND (AVG_TIMER_READ > 10000000000    -- 平均读 > 10ms
    OR AVG_TIMER_WRITE > 10000000000)  -- 平均写 > 10ms
ORDER BY AVG_TIMER_READ DESC;
-- SSD 的平均 I/O 延迟通常在 0.1~1ms
-- 如果 > 10ms 说明存储性能有问题

-- 场景3：判断 Binlog 写入是否是瓶颈
SELECT
    FILE_NAME,
    COUNT_WRITE,
    SUM_NUMBER_OF_BYTES_WRITE / 1024 / 1024 AS write_mb,
    AVG_TIMER_WRITE / 1000000000 AS avg_write_ms
FROM performance_schema.file_summary_by_instance
WHERE EVENT_NAME = 'wait/io/file/sql/binlog'
ORDER BY SUM_TIMER_WRITE DESC;
-- 如果 binlog 的写延迟很高
-- 考虑将 binlog 放到独立的高速存储上

-- 场景4：重置统计数据（重新开始计数）
TRUNCATE performance_schema.file_summary_by_event_name;
TRUNCATE performance_schema.file_summary_by_instance;
-- 可以在优化前后分别 TRUNCATE，对比优化效果
```

## 使用 sys schema 简化查询

```sql
-- sys schema 提供了更友好的视图：

-- 按文件查看 I/O 统计（自动格式化单位）：
SELECT * FROM sys.io_global_by_file_by_bytes
ORDER BY total DESC
LIMIT 10;

-- 按等待时间查看：
SELECT * FROM sys.io_global_by_file_by_latency
ORDER BY total_latency DESC
LIMIT 10;

-- 按等待类型查看：
SELECT * FROM sys.io_global_by_wait_by_bytes
ORDER BY total DESC
LIMIT 10;

-- sys schema 的视图自动将皮秒转换为可读格式（如 1.23 s、45.6 ms）
-- 将字节转换为 KB/MB/GB
-- 比直接查 performance_schema 表更方便
```

## 适用场景

- **I/O 性能瓶颈诊断**：通过文件 I/O 统计找出 I/O 最密集的文件类型和具体文件，判断是数据文件、Redo Log、Binlog 还是临时文件导致的 I/O 瓶颈
- **存储设备性能评估**：通过平均读写延迟（AVG_TIMER_READ/WRITE）评估底层存储的实际性能，判断是否需要升级存储硬件

## 常见问题

**file_summary_by_instance 中 MISC 操作的等待时间很高，这正常吗？**

MISC 操作包括文件的打开（open）、关闭（close）、定位（seek）、同步（fsync）等操作。其中 fsync（刷盘同步）的延迟通常最高，特别是 `innodb_data_file` 和 `innodb_log_file` 的 fsync。如果 MISC 延迟远高于 READ 和 WRITE，通常是 fsync 导致的。在 HDD 上 fsync 可能需要 5~20ms（等待磁盘旋转），在 SSD 上通常 < 1ms。可以通过调整 `innodb_flush_log_at_trx_commit` 和 `sync_binlog` 减少 fsync 频率来降低 MISC 等待。

---

## 注意事项

- 文件 I/O 统计是从 MySQL 启动开始累积的。长时间运行的服务器上，某些文件的累计读写量可能非常大，不太能反映"当前"的 I/O 状况。建议在分析前先 `TRUNCATE` 两张表重置统计，然后运行一段时间（如 10 分钟到 1 小时）后再查询，得到的是这段时间内的 I/O 分布。
- `file_summary_by_instance` 中的 `FILE_NAME` 是绝对路径。如果数据目录使用了符号链接或者多个表空间分散在不同磁盘上，可以通过文件路径区分不同磁盘的 I/O 负载，评估是否需要调整数据文件的分布。

---

## 总结

`file_summary_by_event_name` 按事件类型聚合文件 I/O 统计，`file_summary_by_instance` 按具体文件聚合。统计包含读/写/杂项三组指标：次数、字节数、等待时间（最小/平均/最大）。用于诊断 I/O 瓶颈类型（数据文件 vs Redo Log vs Binlog）、评估存储性能（平均延迟）、判断 fsync 是否过重。sys schema 提供格式化视图（`io_global_by_file_by_bytes`、`io_global_by_file_by_latency`）。分析前建议 TRUNCATE 重置统计。SSD 正常延迟 < 1ms，HDD 正常 5~20ms。

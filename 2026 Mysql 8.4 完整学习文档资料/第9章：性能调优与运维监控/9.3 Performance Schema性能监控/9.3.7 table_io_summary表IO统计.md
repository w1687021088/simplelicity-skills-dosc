# table_io_summary 表 IO 统计

`table_io_waits_summary_by_table` 是 Performance Schema 中用于监控表级 I/O 操作的统计表。它记录了每张表的读（SELECT）、写（INSERT）、更新（UPDATE）、删除（DELETE）操作的次数和等待时间。通过这张表可以清楚地了解哪些表的 I/O 最繁忙、哪些表的访问延迟最高，是定位热点表和优化表访问模式的核心工具。

---

## table_io_waits_summary_by_table

```sql
-- 查看 I/O 最繁忙的表（按总等待时间排序）：
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    COUNT_STAR AS total_ops,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec,
    COUNT_READ,
    SUM_TIMER_READ / 1000000000000 AS read_wait_sec,
    COUNT_WRITE,
    SUM_TIMER_WRITE / 1000000000000 AS write_wait_sec,
    COUNT_FETCH,
    COUNT_INSERT,
    COUNT_UPDATE,
    COUNT_DELETE
FROM performance_schema.table_io_waits_summary_by_table
WHERE OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

-- 各操作类型的含义：
-- COUNT_FETCH：SELECT 查询读取的行数（包括全表扫描和索引扫描的每一行）
-- COUNT_INSERT：INSERT 操作次数
-- COUNT_UPDATE：UPDATE 操作次数
-- COUNT_DELETE：DELETE 操作次数
-- COUNT_READ = COUNT_FETCH
-- COUNT_WRITE = COUNT_INSERT + COUNT_UPDATE + COUNT_DELETE
-- COUNT_STAR = COUNT_READ + COUNT_WRITE
```

## 按索引统计

```sql
-- table_io_waits_summary_by_index_usage 按索引级别统计
-- 可以看到每个索引的使用频率

SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    INDEX_NAME,
    COUNT_STAR AS total_ops,
    COUNT_FETCH AS fetch_count,
    COUNT_INSERT AS insert_count,
    COUNT_UPDATE AS update_count,
    COUNT_DELETE AS delete_count,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
  AND COUNT_STAR > 0
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;

-- INDEX_NAME = NULL 表示全表扫描（没有使用任何索引）
-- 如果某张表的 INDEX_NAME=NULL 行的 COUNT_FETCH 很大
-- 说明该表有大量全表扫描，需要添加索引

-- 找出没有使用索引的表访问（全表扫描）：
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    COUNT_FETCH AS full_scan_rows,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE INDEX_NAME IS NULL
  AND COUNT_FETCH > 10000
  AND OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY COUNT_FETCH DESC
LIMIT 10;

-- 找出未被使用的索引（COUNT_STAR = 0）：
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    INDEX_NAME
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE INDEX_NAME IS NOT NULL
  AND COUNT_STAR = 0
  AND OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY OBJECT_SCHEMA, OBJECT_NAME;
-- 这些索引可能是冗余的，占用空间且影响写入性能
-- 但要确认统计数据覆盖了足够长的时间（包括定时任务等低频查询）
```

## 表锁等待统计

```sql
-- table_lock_waits_summary_by_table 记录表级锁的等待统计
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    COUNT_STAR AS total_lock_waits,
    SUM_TIMER_WAIT / 1000000000000 AS total_wait_sec,
    COUNT_READ_NORMAL,
    COUNT_READ_WITH_SHARED_LOCKS,
    COUNT_WRITE_ALLOW_WRITE,
    COUNT_WRITE_CONCURRENT_INSERT,
    COUNT_WRITE_LOW_PRIORITY,
    COUNT_WRITE_NORMAL
FROM performance_schema.table_lock_waits_summary_by_table
WHERE COUNT_STAR > 0
  AND OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

## 使用 sys schema 简化查询

```sql
-- sys schema 提供了更友好的表 I/O 视图：

-- 按延迟排序的表 I/O：
SELECT * FROM sys.schema_table_statistics_with_buffer
ORDER BY io_read_latency DESC
LIMIT 10;

-- 按操作量排序：
SELECT
    table_schema,
    table_name,
    rows_fetched,
    rows_inserted,
    rows_updated,
    rows_deleted,
    io_read,
    io_write
FROM sys.schema_table_statistics
WHERE table_schema NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY rows_fetched + rows_inserted + rows_updated + rows_deleted DESC
LIMIT 10;

-- 找出未使用的索引：
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema NOT IN ('performance_schema', 'mysql', 'sys');

-- 找出冗余索引：
SELECT * FROM sys.schema_redundant_indexes
WHERE table_schema NOT IN ('performance_schema', 'mysql', 'sys');
```

## 实战分析

```sql
-- 完整的表 I/O 分析流程：

-- 步骤1：重置统计（开始新的监测窗口）
TRUNCATE performance_schema.table_io_waits_summary_by_table;
TRUNCATE performance_schema.table_io_waits_summary_by_index_usage;

-- 步骤2：等待一段时间（如 1 小时的业务高峰）

-- 步骤3：分析热点表
SELECT OBJECT_SCHEMA, OBJECT_NAME,
    COUNT_STAR AS ops,
    SUM_TIMER_WAIT / 1000000000000 AS wait_sec
FROM performance_schema.table_io_waits_summary_by_table
WHERE OBJECT_SCHEMA NOT IN ('performance_schema', 'mysql', 'sys')
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- 步骤4：分析热点表的索引使用情况
SELECT INDEX_NAME, COUNT_FETCH, COUNT_INSERT, COUNT_UPDATE, COUNT_DELETE
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA = 'mydb' AND OBJECT_NAME = 'hot_table'
ORDER BY COUNT_STAR DESC;

-- 步骤5：如果 INDEX_NAME=NULL 的 FETCH 很多
-- 说明需要为该表添加索引
-- 配合慢查询日志找到具体的全表扫描 SQL
-- 使用 EXPLAIN 分析后创建合适的索引
```

## 适用场景

- **热点表识别**：找出 I/O 最密集的表，评估是否需要分表、增加缓存或优化查询
- **未使用索引清理**：通过 `table_io_waits_summary_by_index_usage` 找出 `COUNT_STAR=0` 的索引，评估是否可以删除以减少写入开销和磁盘占用

## 常见问题

**COUNT_FETCH 的数值远大于实际的 SELECT 查询次数，为什么？**

`COUNT_FETCH` 统计的不是 SELECT 语句的次数，而是从表中读取的行数。一个 SELECT 如果扫描了 10 万行，`COUNT_FETCH` 就增加 10 万。这和 `events_statements_summary_by_digest` 中的 `COUNT_STAR`（统计的是语句执行次数）不同。因此 `COUNT_FETCH` 更能反映表的实际 I/O 负担——即使只有少量的 SELECT 语句，如果每次都全表扫描百万行，`COUNT_FETCH` 也会非常大。

---

## 注意事项

- 通过 `table_io_waits_summary_by_index_usage` 找出的"未使用索引"需要谨慎处理。某些索引可能只在月度报表、年度结算等低频场景中使用，如果监测窗口不够长，可能会将这些索引误判为未使用。建议在决定删除索引之前，统计数据至少覆盖一个完整的业务周期（如一个月），并与开发团队确认后再操作。
- `table_io_waits_summary_by_table` 的统计是从 MySQL 启动或上次 TRUNCATE 以来累积的。在长期运行的服务器上，累积数据可能跨越了多次业务变更，不太能反映当前的访问模式。建议定期 TRUNCATE 并在特定时间窗口内采集数据进行分析。

---

## 总结

`table_io_waits_summary_by_table` 按表聚合 I/O 操作统计（FETCH/INSERT/UPDATE/DELETE 次数和等待时间）。`table_io_waits_summary_by_index_usage` 按索引聚合，INDEX_NAME=NULL 表示全表扫描。COUNT_STAR=0 的索引可能是冗余索引。sys schema 提供 `schema_table_statistics`、`schema_unused_indexes`、`schema_redundant_indexes` 等友好视图。COUNT_FETCH 统计的是行级读取次数而非查询次数。分析前建议 TRUNCATE 重置。未使用索引的判断需覆盖完整业务周期。

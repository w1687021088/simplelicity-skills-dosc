# replication_summary 复制统计

Performance Schema 提供了一组复制相关的监控表，可以从多个维度查看 MySQL 主从复制的状态、延迟、错误等信息。相比传统的 `SHOW REPLICA STATUS`（或旧版的 `SHOW SLAVE STATUS`），Performance Schema 的复制表结构更清晰，支持多通道（Multi-Source）复制的监控，并且可以使用标准 SQL 进行灵活查询和关联。

---

## 复制相关的 Performance Schema 表

```sql
-- MySQL 8.0/8.4 中复制相关的 Performance Schema 表：

-- 连接配置（I/O 线程连接到主库的配置）：
SELECT * FROM performance_schema.replication_connection_configuration\G

-- 连接状态（I/O 线程的运行状态）：
SELECT * FROM performance_schema.replication_connection_status\G

-- 应用配置（SQL 线程/Worker 的配置）：
SELECT * FROM performance_schema.replication_applier_configuration\G

-- 应用状态（SQL 线程的总体状态）：
SELECT * FROM performance_schema.replication_applier_status\G

-- 协调器状态（多线程复制的协调线程）：
SELECT * FROM performance_schema.replication_applier_status_by_coordinator\G

-- Worker 状态（多线程复制的每个 Worker 线程）：
SELECT * FROM performance_schema.replication_applier_status_by_worker\G

-- 组复制成员信息（如果使用 MGR）：
SELECT * FROM performance_schema.replication_group_members\G

-- 组复制统计（MGR）：
SELECT * FROM performance_schema.replication_group_member_stats\G
```

## 连接状态监控

```sql
-- replication_connection_status 关键列：

SELECT
    CHANNEL_NAME,
    SOURCE_UUID,
    SERVICE_STATE,                -- I/O 线程状态：ON / OFF / CONNECTING
    RECEIVED_TRANSACTION_SET,     -- 已接收的 GTID 集合
    LAST_ERROR_NUMBER,
    LAST_ERROR_MESSAGE,
    LAST_ERROR_TIMESTAMP,
    LAST_HEARTBEAT_TIMESTAMP,     -- 最后一次心跳时间
    COUNT_RECEIVED_HEARTBEATS,    -- 收到的心跳总数
    LAST_QUEUED_TRANSACTION,      -- 最后写入 Relay Log 的事务 GTID
    LAST_QUEUED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,    -- 主库提交时间
    LAST_QUEUED_TRANSACTION_IMMEDIATE_COMMIT_TIMESTAMP,   -- 写入 Relay Log 的时间
    LAST_QUEUED_TRANSACTION_START_QUEUE_TIMESTAMP,
    LAST_QUEUED_TRANSACTION_END_QUEUE_TIMESTAMP
FROM performance_schema.replication_connection_status\G

-- 判断 I/O 线程是否正常：
-- SERVICE_STATE = 'ON' 表示正常运行
-- SERVICE_STATE = 'OFF' 表示已停止
-- SERVICE_STATE = 'CONNECTING' 表示正在尝试连接（可能网络问题）
-- LAST_ERROR_NUMBER != 0 表示有错误
```

## 应用状态监控

```sql
-- replication_applier_status 关键列：

SELECT
    CHANNEL_NAME,
    SERVICE_STATE,              -- SQL 线程状态：ON / OFF
    REMAINING_DELAY,            -- 延迟复制的剩余等待秒数
    COUNT_TRANSACTIONS_RETRIES  -- 事务重试次数
FROM performance_schema.replication_applier_status\G

-- 多线程复制：协调器状态
SELECT
    CHANNEL_NAME,
    SERVICE_STATE,
    LAST_ERROR_NUMBER,
    LAST_ERROR_MESSAGE,
    LAST_ERROR_TIMESTAMP,
    LAST_PROCESSED_TRANSACTION,
    LAST_PROCESSED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
    LAST_PROCESSED_TRANSACTION_IMMEDIATE_COMMIT_TIMESTAMP
FROM performance_schema.replication_applier_status_by_coordinator\G

-- 多线程复制：各 Worker 线程状态
SELECT
    CHANNEL_NAME,
    WORKER_ID,
    SERVICE_STATE,
    LAST_ERROR_NUMBER,
    LAST_ERROR_MESSAGE,
    LAST_APPLIED_TRANSACTION,
    LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS source_commit,
    LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP AS apply_end,
    APPLYING_TRANSACTION,
    APPLYING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP
FROM performance_schema.replication_applier_status_by_worker\G
```

## 复制延迟计算

```sql
-- MySQL 8.0+ 可以通过 Performance Schema 精确计算复制延迟

-- 方法1：基于事务时间戳计算
SELECT
    CHANNEL_NAME,
    LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS source_commit_time,
    LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP AS replica_apply_time,
    TIMESTAMPDIFF(SECOND,
        LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
        LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP
    ) AS replication_lag_sec
FROM performance_schema.replication_applier_status_by_worker
WHERE SERVICE_STATE = 'ON'
ORDER BY WORKER_ID;

-- 方法2：基于队列延迟（I/O 线程接收 vs SQL 线程应用）
SELECT
    cs.CHANNEL_NAME,
    cs.LAST_QUEUED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS queued_source_time,
    ws.LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS applied_source_time,
    TIMESTAMPDIFF(SECOND,
        ws.LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
        cs.LAST_QUEUED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP
    ) AS apply_lag_sec
FROM performance_schema.replication_connection_status cs
JOIN performance_schema.replication_applier_status_by_worker ws
    ON cs.CHANNEL_NAME = ws.CHANNEL_NAME
WHERE ws.WORKER_ID = 1;

-- 比 Seconds_Behind_Master 更准确
-- Seconds_Behind_Master 基于时间戳差值，可能受系统时钟影响
-- Performance Schema 的方法基于 GTID 和实际的事务提交/应用时间戳
```

## 与 SHOW REPLICA STATUS 的对比

| 对比维度 | SHOW REPLICA STATUS | Performance Schema 表 |
|---------|:-------------------:|:-------------------:|
| 数据来源 | 单一命令输出 | 多张表可 JOIN |
| 多通道支持 | 需要 FOR CHANNEL | 每行一个通道 |
| 延迟精度 | Seconds_Behind_Master（粗略）| 事务级时间戳（精确）|
| Worker 详情 | 不支持 | replication_applier_status_by_worker |
| SQL 查询 | 不支持 WHERE/JOIN | 标准 SQL 灵活查询 |
| 错误历史 | 只看最新错误 | 可记录最后处理的事务 |
| MGR 支持 | 不支持 | replication_group_members |

## 组复制（MGR）监控

```sql
-- 查看组复制成员状态：
SELECT
    MEMBER_ID,
    MEMBER_HOST,
    MEMBER_PORT,
    MEMBER_STATE,       -- ONLINE / RECOVERING / OFFLINE / ERROR
    MEMBER_ROLE,        -- PRIMARY / SECONDARY
    MEMBER_VERSION
FROM performance_schema.replication_group_members;

-- 查看组复制统计：
SELECT
    MEMBER_ID,
    COUNT_TRANSACTIONS_IN_QUEUE AS queue_size,
    COUNT_TRANSACTIONS_CHECKED AS certified_count,
    COUNT_CONFLICTS_DETECTED AS conflicts,
    LAST_CONFLICT_FREE_TRANSACTION
FROM performance_schema.replication_group_member_stats;

-- queue_size 持续增长说明该成员应用速度跟不上
-- conflicts > 0 说明有写冲突被回滚
```

## 适用场景

- **多源复制环境的统一监控**：当一个从库连接多个主库（Multi-Source Replication）时，通过 Performance Schema 可以在一张表中查看所有通道的状态，比逐个执行 `SHOW REPLICA STATUS FOR CHANNEL` 方便得多
- **精确的复制延迟监控**：通过事务级时间戳计算延迟，比 `Seconds_Behind_Master` 更准确，适合对延迟敏感的业务

## 常见问题

**replication_applier_status_by_worker 中某个 Worker 报错但其他 Worker 正常，怎么处理？**

多线程复制中每个 Worker 独立应用事务。某个 Worker 报错时，该 Worker 停止，协调器也会停止分配新事务给该 Worker，但其他 Worker 可能还在运行（取决于 `replica_preserve_commit_order` 设置）。处理步骤：①查看报错 Worker 的 `LAST_ERROR_MESSAGE` 和 `APPLYING_TRANSACTION`（正在应用的事务 GTID）；②分析错误原因（常见：主键冲突、行不存在、表结构不一致）；③修复数据不一致后，`START REPLICA` 恢复复制；④如果是可跳过的错误，可以设置 `SET GLOBAL sql_replica_skip_counter = 1`（基于位置）或 `SET GTID_NEXT='问题GTID'` + 空事务跳过。

## 注意事项

- Performance Schema 的复制表中，时间戳列（如 `LAST_QUEUED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP`）在 MySQL 8.0.1+ 才可用。如果从低版本升级而来，确认这些列有正确的值。另外，这些时间戳基于 GTID 事务标记，如果未启用 GTID（`gtid_mode=OFF`），部分时间戳列可能为空。建议生产环境始终启用 GTID。
- `replication_group_members` 和 `replication_group_member_stats` 只在使用 Group Replication（MGR）时有数据。普通主从复制不使用这两张表。

---

## 总结

Performance Schema 提供了一组复制监控表，比 `SHOW REPLICA STATUS` 更结构化、更灵活。核心表：`replication_connection_status`（I/O 线程状态）、`replication_applier_status`（SQL 线程状态）、`replication_applier_status_by_worker`（Worker 状态）。支持多通道复制的统一监控。通过事务时间戳精确计算复制延迟。`replication_group_members` 监控 MGR 成员。所有表支持标准 SQL 查询和 JOIN。建议启用 GTID 以获取完整的时间戳数据。

# Performance Schema 架构

Performance Schema 是 MySQL 内置的性能监控框架，从 MySQL 5.5 开始引入，在 MySQL 8.0/8.4 中已经非常成熟。它通过在 MySQL 服务器内部的关键代码路径上插入"探针"（Instrument），实时采集服务器运行时的各种性能数据，包括 SQL 语句执行、等待事件、I/O 操作、锁竞争、内存分配等。这些数据存储在内存中的 `performance_schema` 数据库的各张表里，DBA 可以通过标准的 SQL 查询来分析服务器的性能状况。

---

## 整体架构

```
Performance Schema 的核心组成：

1. Instruments（探针/采集器）
   插入在 MySQL 源码中的监控点
   每当代码执行到该点时，生成一个性能事件
   
   探针分类（按名称前缀）：
   wait/          等待事件（互斥锁、读写锁、条件变量、I/O）
   stage/         执行阶段（如 Sending data、Sorting result）
   statement/     SQL 语句（SELECT、INSERT、UPDATE 等）
   transaction/   事务（BEGIN、COMMIT、ROLLBACK）
   memory/        内存分配和释放
   idle/          空闲等待
   error/         错误事件

   探针总数：MySQL 8.0 中有 1000+ 个探针
   每个探针可以单独启用或禁用
   启用的探针越多，采集的数据越详细，但开销也越大

2. Consumers（消费者/数据存储）
   决定采集到的事件数据存储到哪些表中
   
   消费者层次结构：
   global_instrumentation（全局开关）
     thread_instrumentation（线程级开关）
       events_waits_current（当前等待事件）
         events_waits_history（最近的等待事件）
         events_waits_history_long（更长的等待历史）
       events_stages_current
         events_stages_history
         events_stages_history_long
       events_statements_current
         events_statements_history
         events_statements_history_long
       events_transactions_current
         events_transactions_history
         events_transactions_history_long
     statements_digest（语句摘要/指纹）

   父级消费者关闭 → 子级消费者也不会收集数据

3. Tables（数据表）
   performance_schema 数据库中的表
   存储采集到的性能数据
   只存在于内存中，不持久化到磁盘
   MySQL 重启后数据丢失
```

## 表的分类

```sql
-- performance_schema 中的表可以分为以下几类：

-- 配置表（Setup Tables）：
-- 控制哪些探针启用、哪些消费者启用
SELECT * FROM performance_schema.setup_instruments LIMIT 10;
SELECT * FROM performance_schema.setup_consumers;
SELECT * FROM performance_schema.setup_actors;
SELECT * FROM performance_schema.setup_objects;
SELECT * FROM performance_schema.setup_threads;

-- 当前事件表（Current Events）：
-- 每个线程当前正在进行的事件
SELECT * FROM performance_schema.events_statements_current;
SELECT * FROM performance_schema.events_waits_current;
SELECT * FROM performance_schema.events_stages_current;

-- 历史事件表（History）：
-- 每个线程最近的 N 个事件（默认 10 条/线程）
SELECT * FROM performance_schema.events_statements_history;

-- 长历史表（History Long）：
-- 全局最近的 N 个事件（默认 10000 条）
SELECT * FROM performance_schema.events_statements_history_long;

-- 摘要/统计表（Summary Tables）：
-- 聚合统计数据
SELECT * FROM performance_schema.events_statements_summary_by_digest;
SELECT * FROM performance_schema.file_summary_by_instance;
SELECT * FROM performance_schema.table_io_waits_summary_by_table;
SELECT * FROM performance_schema.memory_summary_global_by_event_name;

-- 实例表（Instance Tables）：
-- 当前存在的对象实例
SELECT * FROM performance_schema.mutex_instances;
SELECT * FROM performance_schema.file_instances;
SELECT * FROM performance_schema.socket_instances;
```

## 性能开销

```
Performance Schema 的性能影响：

默认配置下的开销：
  CPU：约 1%~5%（取决于负载类型）
  内存：约 100~500MB（取决于启用的探针和历史表大小）

开销控制原则：
  只启用需要的探针（不需要的关闭）
  只启用需要的消费者（不需要 history_long 就关闭）
  减小历史表的大小限制

内存分配：
  Performance Schema 在启动时预分配内存
  不使用 MySQL 的通用内存分配器
  内存大小通过以下参数控制：
  performance_schema_events_statements_history_size（每线程语句历史数）
  performance_schema_events_statements_history_long_size（全局语句长历史数）
  performance_schema_events_waits_history_size
  performance_schema_events_waits_history_long_size
  performance_schema_max_table_instances
  performance_schema_max_thread_instances
```

## 适用场景

- **生产环境的性能监控**：Performance Schema 默认启用，开销可控，适合在生产环境中长期运行。通过定期查询统计表，可以了解哪些 SQL 消耗最多资源、哪些表 I/O 最频繁、哪些锁竞争最严重
- **性能问题的深度诊断**：当遇到性能问题时，临时启用更多的探针和消费者，采集详细的等待事件、执行阶段等数据，定位性能瓶颈的根因

## 常见问题

**Performance Schema 和 INFORMATION_SCHEMA 有什么区别？**

两者都是 MySQL 的元数据和监控数据库，但定位不同。`INFORMATION_SCHEMA` 提供的是数据库对象的静态元数据（表结构、索引、权限等），查询时是即时采集的，某些查询可能较慢。`performance_schema` 提供的是运行时的动态性能数据（语句执行、等待事件、I/O 统计等），数据是持续采集并存储在内存中的，查询速度很快。简单说：`INFORMATION_SCHEMA` 回答"数据库里有什么"，`performance_schema` 回答"数据库在做什么"。

## 注意事项

- Performance Schema 的数据存储在内存中，MySQL 重启后所有数据丢失。如果需要持久化监控数据（如做趋势分析），需要定期将关键统计表的数据导出到外部存储（如 Prometheus + Grafana 通过 mysqld_exporter 采集，或自行编写脚本定时 SELECT 插入到历史表）。
- Performance Schema 的表是只读的（除了配置表），不能对数据表执行 INSERT、UPDATE、DELETE。但可以使用 TRUNCATE 清空统计数据，重新开始计数。例如 `TRUNCATE performance_schema.events_statements_summary_by_digest` 可以清零所有语句摘要统计。

## 总结

Performance Schema 是 MySQL 内置的性能监控框架，通过 Instruments（探针）采集事件、Consumers（消费者）控制数据存储。表分为配置表、当前事件表、历史表、统计表和实例表。探针按类型分为 wait/stage/statement/transaction/memory/idle/error。消费者有层次结构，父级关闭则子级不采集。默认开启，性能开销 1%~5%。数据存于内存，重启丢失。可用 TRUNCATE 重置统计。配合 sys schema 提供更友好的查询视图。

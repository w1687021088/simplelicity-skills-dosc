# 锁等待与死锁分析

InnoDB 使用行级锁来实现事务的并发控制。当多个事务同时修改相同的数据时，就会产生锁等待（Lock Wait）——一个事务持有锁，另一个事务等待获取该锁。如果两个事务互相等待对方持有的锁，就会形成死锁（Deadlock）。InnoDB 内置了死锁检测机制，能自动检测并回滚其中一个事务来打破死锁。理解锁等待和死锁的诊断方法，是处理并发问题的核心技能。

## 锁等待诊断

```sql
-- 查看当前正在等待锁的事务：
SELECT
    r.trx_id AS waiting_trx_id,
    r.trx_mysql_thread_id AS waiting_thread,
    r.trx_query AS waiting_query,
    b.trx_id AS blocking_trx_id,
    b.trx_mysql_thread_id AS blocking_thread,
    b.trx_query AS blocking_query
FROM performance_schema.data_lock_waits w
JOIN information_schema.INNODB_TRX r ON r.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
JOIN information_schema.INNODB_TRX b ON b.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID;

-- 查看当前所有 InnoDB 事务：
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec,
    trx_mysql_thread_id,
    trx_query,
    trx_rows_locked,
    trx_rows_modified,
    trx_lock_memory_bytes
FROM information_schema.INNODB_TRX
ORDER BY trx_started ASC;

-- 查看当前持有的所有锁：
SELECT
    ENGINE_TRANSACTION_ID,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    INDEX_NAME,
    LOCK_TYPE,     -- RECORD（行锁）或 TABLE（表锁）
    LOCK_MODE,     -- S（共享锁）、X（排他锁）、IS、IX、GAP 等
    LOCK_STATUS,   -- GRANTED（已获取）或 WAITING（等待中）
    LOCK_DATA      -- 锁定的数据（主键值等）
FROM performance_schema.data_locks
WHERE LOCK_STATUS = 'GRANTED'
ORDER BY ENGINE_TRANSACTION_ID;

-- 查看正在等待的锁：
SELECT
    ENGINE_TRANSACTION_ID,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    LOCK_TYPE,
    LOCK_MODE,
    LOCK_DATA
FROM performance_schema.data_locks
WHERE LOCK_STATUS = 'WAITING';

-- 使用 sys schema 快速查看锁等待：
SELECT * FROM sys.innodb_lock_waits\G
-- 输出包含：
-- waiting_trx_id / waiting_pid / waiting_query
-- blocking_trx_id / blocking_pid / blocking_query
-- locked_table / locked_index / locked_type
-- waiting_trx_age / blocking_trx_age
-- sql_kill_blocking_query / sql_kill_blocking_connection
-- 最后两列直接给出 KILL 命令，复制执行即可
```

## 锁等待超时

```sql
-- innodb_lock_wait_timeout 控制锁等待的最大秒数：
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
-- 默认值：50（秒）

-- 等待超过此时间后，等待的事务会收到错误：
-- ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

-- 注意：超时只回滚当前语句，不回滚整个事务
-- 如果需要超时时回滚整个事务：
-- [mysqld]
-- innodb_rollback_on_timeout = ON（默认 OFF）

-- 调整超时时间：
SET GLOBAL innodb_lock_wait_timeout = 30;  -- 全局
SET SESSION innodb_lock_wait_timeout = 10; -- 当前会话

-- OLTP 系统建议设短一些（10~30 秒）
-- 数据仓库/批量处理可以设长一些（120~300 秒）
```

## 死锁分析

```sql
-- 查看最近一次死锁信息：
SHOW ENGINE INNODB STATUS\G
-- 找到 LATEST DETECTED DEADLOCK 部分

-- 死锁输出解读：
-- *** (1) TRANSACTION:
--   事务1的信息：事务ID、活跃时间、正在执行的SQL
-- *** (1) HOLDS THE LOCK(S):
--   事务1已持有的锁（锁类型、锁定的记录）
-- *** (1) WAITING FOR THIS LOCK TO BE GRANTED:
--   事务1正在等待的锁

-- *** (2) TRANSACTION:
--   事务2的信息
-- *** (2) HOLDS THE LOCK(S):
--   事务2已持有的锁
-- *** (2) WAITING FOR THIS LOCK TO BE GRANTED:
--   事务2正在等待的锁

-- *** WE ROLL BACK TRANSACTION (2)
--   InnoDB 选择回滚事务2（通常选择回滚代价小的事务）

-- 将所有死锁信息记录到错误日志：
SET GLOBAL innodb_print_all_deadlocks = ON;
-- 每次发生死锁都会在 error log 中记录完整信息
-- 生产环境建议开启
```

## 死锁的常见原因

```
原因1：不同顺序访问多张表
  事务A：UPDATE orders → UPDATE inventory
  事务B：UPDATE inventory → UPDATE orders
  
  事务A 锁定 orders 等待 inventory
  事务B 锁定 inventory 等待 orders → 死锁
  
  解决：所有事务按相同顺序访问表

原因2：不同顺序更新同一张表的不同行
  事务A：UPDATE t SET ... WHERE id=1; UPDATE t SET ... WHERE id=2;
  事务B：UPDATE t SET ... WHERE id=2; UPDATE t SET ... WHERE id=1;
  
  解决：按主键顺序更新

原因3：间隙锁（Gap Lock）冲突
  事务A：SELECT ... WHERE id > 100 FOR UPDATE（锁定 id>100 的间隙）
  事务B：INSERT INTO t (id, ...) VALUES (150, ...)（尝试插入到间隙中）
  
  如果同时有反方向的操作，可能死锁
  解决：缩小锁定范围、使用 READ COMMITTED 隔离级别（减少间隙锁）

原因4：唯一索引冲突导致的死锁
  多个事务同时 INSERT 相同唯一键值
  第一个事务持有 X 锁
  后续事务等待 S 锁（重复键检查）
  如果第一个事务回滚，多个等待的事务同时获得 S 锁
  然后都尝试插入 → 死锁
  
  解决：INSERT ... ON DUPLICATE KEY UPDATE 或应用层去重
```

## 死锁预防策略

```sql
-- 策略1：按固定顺序访问表和行
-- 所有事务都按照：表A → 表B → 表C 的顺序操作
-- 同表内按主键升序更新

-- 策略2：保持事务简短
-- 减少事务持有锁的时间
-- 避免在事务中做耗时操作（如调用外部 API）

-- 策略3：使用较低的隔离级别
SET SESSION transaction_isolation = 'READ-COMMITTED';
-- READ COMMITTED 不使用间隙锁（大部分场景）
-- 减少锁冲突的概率

-- 策略4：合理使用索引
-- 没有索引时 UPDATE/DELETE 可能锁定全表（或大量行）
-- 有索引时只锁定匹配的行

-- 策略5：在应用层处理死锁重试
-- 死锁是正常现象，应用代码应该捕获 1213 错误码
-- 自动重试事务（通常 1~3 次即可）

-- 伪代码：
-- for retry in range(3):
--     try:
--         execute_transaction()
--         break
--     except DeadlockError:
--         if retry == 2:
--             raise
--         sleep(random(0.01, 0.1))

-- 策略6：高并发热点行使用乐观锁
-- UPDATE accounts SET balance = balance - 100, version = version + 1
-- WHERE id = 1 AND version = 5;
-- 通过版本号避免悲观锁
```

## 适用场景

- **线上频繁出现锁等待超时（ERROR 1205）**：通过 `sys.innodb_lock_waits` 或 `data_lock_waits` 找到阻塞源头，判断是慢查询、长事务还是应用逻辑问题
- **死锁频繁影响业务**：开启 `innodb_print_all_deadlocks` 记录所有死锁，分析死锁模式后调整事务访问顺序或隔离级别

## 常见问题

**innodb_deadlock_detect 能否关闭来提升性能？**

可以关闭（`innodb_deadlock_detect=OFF`），但要谨慎。死锁检测在高并发场景下本身有一定的 CPU 开销（因为每次等待锁时都要检查是否形成了死锁环）。在极高并发的热点行更新场景中，关闭死锁检测可以减少 CPU 开销。但关闭后，死锁只能通过 `innodb_lock_wait_timeout` 超时来打破（默认等 50 秒），业务体验会很差。如果关闭死锁检测，需要将 `innodb_lock_wait_timeout` 设得很小（如 3~5 秒），并在应用层做好重试逻辑。大多数场景不建议关闭。

---

## 注意事项

- `SHOW ENGINE INNODB STATUS` 只显示最近一次死锁的信息。如果发生了新的死锁，旧的信息会被覆盖。建议开启 `innodb_print_all_deadlocks=ON`，将所有死锁信息持久化到错误日志中，便于事后分析。
- 锁等待超时（ERROR 1205）默认只回滚当前语句，不回滚整个事务。这意味着事务中前面已执行的语句（如已插入的数据）仍然有效。应用代码收到 1205 错误后，如果不显式 ROLLBACK，事务会保持在部分完成的状态，持有之前获取的锁，可能导致更多的锁等待。建议应用代码在收到锁等待超时后立即 ROLLBACK 整个事务。

---

## 总结

锁等待通过 `performance_schema.data_lock_waits` 和 `sys.innodb_lock_waits` 诊断。`innodb_lock_wait_timeout`（默认 50 秒）控制等待超时。死锁通过 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 部分分析。`innodb_print_all_deadlocks=ON` 将所有死锁记录到错误日志。死锁常见原因：不同顺序访问表/行、间隙锁冲突、唯一索引冲突。预防策略：固定访问顺序、保持事务简短、使用 READ COMMITTED、应用层死锁重试。超时只回滚当前语句（非整个事务），应用需显式 ROLLBACK。

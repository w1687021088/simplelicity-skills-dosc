# 表修复 REPAIR TABLE

`REPAIR TABLE` 是 MySQL 内置的表修复语句，用于修复损坏的表。它主要适用于 MyISAM 存储引擎的表，对 InnoDB 表不适用（InnoDB 有自己的崩溃恢复机制）。MyISAM 表由于不支持事务和崩溃安全，在 MySQL 异常退出、磁盘故障等情况下更容易发生损坏。`REPAIR TABLE` 通过重建索引文件或使用表结构定义（FRM）来修复损坏的表。

---

## 基本语法

```sql
-- REPAIR TABLE 语法：
REPAIR [NO_WRITE_TO_BINLOG | LOCAL]
    TABLE tbl_name [, tbl_name] ...
    [QUICK] [EXTENDED] [USE_FRM]

-- 修复单张表：
REPAIR TABLE mydb.legacy_table;

-- 修复多张表：
REPAIR TABLE mydb.t1, mydb.t2, mydb.t3;

-- 输出示例：
-- +-----------------+--------+----------+----------+
-- | Table           | Op     | Msg_type | Msg_text |
-- +-----------------+--------+----------+----------+
-- | mydb.legacy_table | repair | status   | OK       |
-- +-----------------+--------+----------+----------+

-- Msg_text 的可能值：
-- OK：修复成功
-- Table is already up to date：表不需要修复
-- 具体的错误信息：修复失败的原因
```

---

## 修复选项

```sql
-- QUICK 选项：
-- 只修复索引文件（.MYI），不修改数据文件（.MYD）
-- 速度最快，适用于数据文件没有损坏的情况
REPAIR TABLE mydb.legacy_table QUICK;

-- EXTENDED 选项：
-- 逐行重建索引，比默认修复更彻底但更慢
-- 当默认修复失败时使用
REPAIR TABLE mydb.legacy_table EXTENDED;

-- USE_FRM 选项：
-- 当索引文件（.MYI）丢失或严重损坏时使用
-- 根据数据字典中的表定义信息重建索引文件
-- 注意：会丢失 AUTO_INCREMENT 的当前值
-- 注意：压缩表不能使用此选项
REPAIR TABLE mydb.legacy_table USE_FRM;

-- NO_WRITE_TO_BINLOG / LOCAL 选项：
-- 修复操作不写入 Binlog（不会复制到从库）
-- 如果从库的同一张表也损坏了，需要在从库上单独修复
REPAIR NO_WRITE_TO_BINLOG TABLE mydb.legacy_table;
```

## 修复策略（由简到繁）

```
修复 MyISAM 表的推荐顺序：

步骤1：先用 CHECK TABLE 确认损坏
  CHECK TABLE mydb.legacy_table;
  如果返回 OK，不需要修复

步骤2：尝试 QUICK 修复
  REPAIR TABLE mydb.legacy_table QUICK;
  只修复索引，速度快
  如果成功且 CHECK TABLE 返回 OK，修复完成

步骤3：尝试默认修复
  REPAIR TABLE mydb.legacy_table;
  重建索引并验证数据行
  如果成功，修复完成

步骤4：尝试 EXTENDED 修复
  REPAIR TABLE mydb.legacy_table EXTENDED;
  逐行扫描数据重建索引
  速度最慢但最彻底

步骤5：使用 USE_FRM 修复
  REPAIR TABLE mydb.legacy_table USE_FRM;
  当 .MYI 文件完全损坏或丢失时使用
  会丢失 AUTO_INCREMENT 当前值

步骤6：如果以上都失败
  使用备份恢复
  或使用 myisamchk 工具在离线状态下修复
```

## myisamchk 离线修复工具

```bash
# myisamchk 是 MyISAM 表的命令行修复工具
# 必须在 MySQL 未运行时使用（或表未被使用时）

# 检查表：
myisamchk /var/lib/mysql/mydb/legacy_table.MYI

# 快速修复（只修复索引）：
myisamchk -r -q /var/lib/mysql/mydb/legacy_table.MYI
# -r = --recover
# -q = --quick

# 标准修复：
myisamchk -r /var/lib/mysql/mydb/legacy_table.MYI

# 安全修复（最彻底，逐行重建）：
myisamchk --safe-recover /var/lib/mysql/mydb/legacy_table.MYI

# 带内存参数的修复（大表修复更快）：
myisamchk -r \
  --key_buffer_size=512M \
  --myisam_sort_buffer_size=512M \
  --read_buffer_size=4M \
  --write_buffer_size=4M \
  /var/lib/mysql/mydb/legacy_table.MYI

# 批量修复所有 MyISAM 表：
myisamchk -r /var/lib/mysql/*/*.MYI

# 修复后刷新表缓存（MySQL 运行时）：
# mysql -e "FLUSH TABLES"
```

## mysqlcheck 在线修复工具

```bash
# mysqlcheck 是 MySQL 运行时使用的批量维护工具
# 本质上是对 CHECK TABLE / REPAIR TABLE 的封装

# 检查单个数据库：
mysqlcheck -u root -p --check mydb

# 检查所有数据库：
mysqlcheck -u root -p --check --all-databases

# 修复单个数据库：
mysqlcheck -u root -p --repair mydb

# 修复所有数据库：
mysqlcheck -u root -p --repair --all-databases

# 快速修复：
mysqlcheck -u root -p --repair --quick mydb

# 自动修复（先检查再修复有问题的表）：
mysqlcheck -u root -p --auto-repair --all-databases
# --auto-repair：先执行 CHECK，只对有问题的表执行 REPAIR
```

## InnoDB 表的"修复"替代方案

```sql
-- InnoDB 不支持 REPAIR TABLE
-- 但有以下替代修复方案：

-- 方案1：ALTER TABLE 重建表（最常用）
ALTER TABLE mydb.orders ENGINE=InnoDB;
-- 实际过程：读取所有数据 → 创建新表 → 写入数据 → 替换旧表
-- 可以修复索引损坏和碎片
-- 等同于 OPTIMIZE TABLE

-- 方案2：导出再导入
mysqldump -u root -p mydb orders > orders_backup.sql
mysql -u root -p mydb -e "DROP TABLE orders"
mysql -u root -p mydb < orders_backup.sql

-- 方案3：使用 innodb_force_recovery 紧急恢复
-- 当 MySQL 因 InnoDB 损坏无法启动时：
-- [mysqld]
-- innodb_force_recovery = 1
-- 启动后立即 mysqldump 导出所有数据
-- 然后重建实例

-- 方案4：从备份恢复
-- 使用最近的备份 + Binlog 做时间点恢复（PITR）
```

## REPAIR TABLE 与 CHECK TABLE 的对比

| 对比维度 | CHECK TABLE | REPAIR TABLE |
|---------|:-----------:|:------------:|
| 作用 | 检测损坏 | 修复损坏 |
| InnoDB 支持 | 支持（检测） | 不支持 |
| MyISAM 支持 | 支持 | 支持 |
| 锁类型 | 读锁 | 写锁 |
| 对业务影响 | 阻塞写操作 | 阻塞读写操作 |
| 使用时机 | 怀疑损坏时先检查 | 确认损坏后修复 |
| 命令行工具 | mysqlcheck --check | mysqlcheck --repair |
| 离线工具 | myisamchk --check | myisamchk --recover |

## 适用场景

- **MyISAM 表损坏后的修复**：MySQL 崩溃或异常退出后，MyISAM 表出现 `Table is marked as crashed and should be repaired` 错误时使用
- **索引文件丢失或损坏**：使用 `REPAIR TABLE ... USE_FRM` 根据表定义重建索引

---

## 常见问题

**REPAIR TABLE 修复后数据是否完整？**

取决于损坏的程度和类型。如果只是索引损坏（.MYI 文件），`REPAIR TABLE` 通常可以完整恢复，因为数据文件（.MYD）没有问题。如果数据文件也损坏了，`REPAIR TABLE` 会跳过无法读取的行，修复后的表可能会缺少部分数据。修复完成后应检查表的行数是否与预期一致，并与备份对比确认。`REPAIR TABLE` 的输出中如果有 `warning: Number of rows changed from X to Y`，说明有数据丢失。

---

## 注意事项

- `REPAIR TABLE` 会对表加写锁（排他锁），修复期间该表的所有读写操作都被阻塞。大表的修复可能需要较长时间（取决于表大小和损坏程度）。生产环境中应在维护窗口执行，或提前做好业务降级准备。
- 在执行 `REPAIR TABLE` 之前，建议先备份表的数据文件（.MYD）和索引文件（.MYI）。虽然修复操作本身很少导致额外的数据丢失，但在索引严重损坏的极端情况下，某些修复尝试可能使情况更糟。有了备份可以回退。对于 InnoDB 表，不要尝试手动复制 .ibd 文件作为"备份"，使用 mysqldump 或其他逻辑备份工具。

---

## 总结

`REPAIR TABLE` 主要用于修复 MyISAM 表，InnoDB 表不支持。修复选项：QUICK（快速修复索引）、EXTENDED（逐行重建索引）、USE_FRM（根据表定义重建索引文件）。修复顺序：QUICK → 默认 → EXTENDED → USE_FRM → 备份恢复。离线工具 `myisamchk`（MySQL 未运行时使用）和在线工具 `mysqlcheck`（MySQL 运行时使用）。InnoDB 的替代修复方案：`ALTER TABLE ... ENGINE=InnoDB`（重建表）、导出再导入、`innodb_force_recovery`。修复期间加写锁，阻塞所有读写。修复前建议备份。

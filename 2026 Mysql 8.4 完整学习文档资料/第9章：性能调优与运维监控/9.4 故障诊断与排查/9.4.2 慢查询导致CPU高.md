# 慢查询导致 CPU 高

MySQL 的 CPU 使用率飙升通常是因为存在大量消耗 CPU 的 SQL 查询。常见的 CPU 密集型操作包括：全表扫描（没有索引）、大量排序（filesort）、复杂的 JOIN、子查询、正则表达式匹配等。当多个这样的查询同时执行时，CPU 会迅速达到 100%，导致所有查询变慢，连接堆积，最终影响整个服务。

---

## 快速定位高 CPU 查询

```sql
-- 步骤1：确认 CPU 高是 MySQL 造成的
-- 在操作系统层面检查：
-- Linux：top -H -p $(pgrep mysqld)
-- 查看 mysqld 的各个线程的 CPU 使用情况

-- 步骤2：查看当前正在执行的查询
SELECT
    ID,
    USER,
    HOST,
    DB,
    TIME,
    STATE,
    LEFT(INFO, 200) AS sql_text
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Query'
  AND TIME > 1
ORDER BY TIME DESC
LIMIT 20;
-- 关注执行时间长（TIME 大）的查询

-- 步骤3：使用 Performance Schema 找出消耗最多的 SQL
SELECT
    DIGEST_TEXT,
    COUNT_STAR AS exec_count,
    SUM_TIMER_WAIT / 1000000000000 AS total_time_sec,
    AVG_TIMER_WAIT / 1000000000000 AS avg_time_sec,
    SUM_ROWS_EXAMINED AS total_rows_examined,
    SUM_ROWS_EXAMINED / GREATEST(COUNT_STAR, 1) AS avg_rows_examined,
    SUM_NO_INDEX_USED AS no_index_count
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
-- 总时间最长的 SQL 类型就是 CPU 消耗的主要来源

-- 步骤4：使用 sys schema 快速查看
SELECT * FROM sys.statement_analysis
ORDER BY total_latency DESC
LIMIT 10;

-- 查看全表扫描的查询：
SELECT * FROM sys.statements_with_full_table_scans
ORDER BY no_index_used_count DESC
LIMIT 10;
```

## 典型的 CPU 密集型查询

```sql
-- 类型1：全表扫描（EXPLAIN 中 type=ALL）
-- 没有合适的索引，MySQL 扫描整张表
SELECT * FROM orders WHERE status = 'pending';
-- 如果 orders 表有 500 万行且 status 无索引
-- 每次查询都要扫描 500 万行

-- 优化：添加索引
ALTER TABLE orders ADD INDEX idx_status (status);

-- 类型2：大量排序（Using filesort）
SELECT * FROM orders ORDER BY create_time DESC LIMIT 100;
-- 如果 create_time 没有索引，MySQL 需要读取所有行后排序
-- 排序是 CPU 密集型操作

-- 优化：添加索引
ALTER TABLE orders ADD INDEX idx_create_time (create_time);

-- 类型3：不合理的 JOIN
SELECT * FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE o.status = 'pending';
-- 如果 JOIN 条件没有索引，产生笛卡尔积

-- 优化：确保 JOIN 列有索引
ALTER TABLE order_items ADD INDEX idx_order_id (order_id);
ALTER TABLE order_items ADD INDEX idx_product_id (product_id);

-- 类型4：子查询效率低
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);
-- 相关子查询可能对外表每一行都执行一次

-- 优化：改写为 JOIN
SELECT DISTINCT u.* FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.amount > 1000;

-- 类型5：LIKE '%keyword%' 前缀模糊匹配
SELECT * FROM products WHERE name LIKE '%手机%';
-- 前缀通配符无法使用索引，只能全表扫描
-- 优化：使用全文索引（FULLTEXT）或搜索引擎（Elasticsearch）
```

## 使用 EXPLAIN 分析

```sql
-- 对 TOP SQL 执行 EXPLAIN 分析执行计划：
EXPLAIN SELECT * FROM orders WHERE status = 'pending' ORDER BY create_time;

-- 关注以下指标：
-- type 列：
--   ALL = 全表扫描（最差）
--   index = 全索引扫描
--   range = 范围扫描（较好）
--   ref = 非唯一索引查找（好）
--   eq_ref = 唯一索引查找（好）
--   const = 常量查找（最好）

-- rows 列：预估扫描行数
--   如果远大于实际返回行数，说明扫描效率低

-- Extra 列：
--   Using filesort = 需要排序（CPU 开销）
--   Using temporary = 需要临时表（CPU + I/O 开销）
--   Using where = 在服务器层过滤（非索引过滤）
--   Using index = 覆盖索引（好，不需要回表）

-- EXPLAIN ANALYZE（MySQL 8.0.18+）：
-- 实际执行查询并显示每个步骤的实际行数和时间
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending' ORDER BY create_time\G
```

## 紧急处理

```sql
-- 当 CPU 已经 100% 且数据库无响应时：

-- 方式1：KILL 掉最耗时的查询
-- 先找到：
SELECT ID, TIME, LEFT(INFO, 100)
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Query'
ORDER BY TIME DESC
LIMIT 5;

-- 然后 KILL：
KILL <ID>;

-- 方式2：批量 KILL 执行超过 60 秒的查询
SELECT CONCAT('KILL ', ID, ';')
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Query'
  AND TIME > 60;

-- 方式3：如果无法登录 MySQL
-- 在操作系统层面发送信号：
-- kill -SIGTERM $(pgrep mysqld)  -- 正常关闭（会等待事务完成）
-- 不推荐 kill -9（可能导致数据损坏）
```

## 持续优化策略

```sql
-- 开启慢查询日志长期监控：
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;
SET GLOBAL log_throttle_queries_not_using_indexes = 60;

-- 定期用 pt-query-digest 分析慢查询日志：
-- pt-query-digest /var/log/mysql/slow.log > /tmp/report.txt

-- 定期查看 Performance Schema 统计：
-- 关注 SUM_ROWS_EXAMINED / SUM_ROWS_SENT 比值大的查询
-- 比值 > 1000 说明扫描效率极低

-- 使用 ANALYZE TABLE 更新表统计信息：
ANALYZE TABLE orders;
-- 统计信息过旧可能导致优化器选择错误的执行计划
```

## 适用场景

- **收到 CPU 使用率告警后的排查**：按照"确认 MySQL 导致 → 找出 TOP SQL → EXPLAIN 分析 → 优化索引/SQL"的流程处理
- **日常性能巡检**：通过慢查询日志和 Performance Schema 统计，提前发现并优化可能导致 CPU 问题的查询

## 常见问题

**CPU 使用率高但 SHOW PROCESSLIST 没有看到明显的慢查询，可能是什么原因？**

可能有以下情况：①大量快速但频繁的查询（每个查询只要 10ms 但每秒执行上万次），单个查询看起来不慢但总量很大。查看 `events_statements_summary_by_digest` 中 `COUNT_STAR` 最高的查询。②后台线程活动（如 Purge 线程、刷脏页），通过 `SHOW ENGINE INNODB STATUS` 查看。③Performance Schema 统计采集的开销（如果启用了太多探针）。④统计信息维护（ANALYZE TABLE 自动执行）。

## 注意事项

- 添加索引虽然能加速 SELECT，但每个索引都会增加 INSERT/UPDATE/DELETE 的开销（因为需要同时维护索引）。在写入密集的表上添加索引需要权衡读写性能。一般建议每张表的索引数控制在 5~8 个以内。
- `EXPLAIN ANALYZE` 会实际执行查询（不像 `EXPLAIN` 只做计划分析）。对于执行时间很长的查询，`EXPLAIN ANALYZE` 也需要等待很长时间。可以先用 `EXPLAIN` 快速查看执行计划，确认需要深入分析时再使用 `EXPLAIN ANALYZE`。

---

## 总结

CPU 飙高的主要原因是存在 CPU 密集型 SQL：全表扫描、大量排序、复杂 JOIN、相关子查询等。诊断流程：PROCESSLIST 找执行中的慢查询 → Performance Schema 找 TOP SQL → EXPLAIN 分析执行计划 → 优化索引或改写 SQL。紧急处理：KILL 耗时查询。持续优化：开启慢查询日志、定期 pt-query-digest 分析、关注 ROWS_EXAMINED/ROWS_SENT 比值。EXPLAIN 中 type=ALL 和 Extra=Using filesort 是重点关注对象。

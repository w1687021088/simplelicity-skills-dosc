# 内存溢出 OOM 分析

OOM（Out of Memory）是指 MySQL 进程因内存使用超过系统可用内存，被 Linux 内核的 OOM Killer 强制终止的情况。MySQL 被 OOM Kill 后会立即退出（不是正常关闭），重启时需要执行崩溃恢复。OOM 是生产环境中最严重的故障类型之一，因为它会导致服务中断且可能出现数据丢失风险。

---

## 确认是否被 OOM Kill

```bash
# 检查系统日志确认 MySQL 是否被 OOM Killer 终止：

# CentOS / RHEL：
dmesg | grep -i "out of memory"
dmesg | grep -i "killed process"
# 或
grep -i "oom" /var/log/messages

# Ubuntu / Debian：
grep -i "oom" /var/log/syslog
grep -i "killed process" /var/log/kern.log

# 输出示例：
# Out of memory: Killed process 12345 (mysqld) total-vm:12345678kB,
# anon-rss:8765432kB, file-rss:0kB, shmem-rss:0kB,
# oom_score_adj:0

# 关键信息：
# total-vm：MySQL 进程的虚拟内存大小
# anon-rss：MySQL 进程的物理内存（常驻集）大小
# oom_score_adj：OOM 评分调整值

# 检查 MySQL 错误日志：
# 如果是 OOM Kill，错误日志中通常没有正常关闭的记录
# 最后的日志可能就是正常运行时的记录，然后突然中断
# 重启后会有崩溃恢复的日志
```

## MySQL 内存使用构成

```
MySQL 的内存使用主要包含以下部分：

全局内存（固定分配，与连接数无关）：
  innodb_buffer_pool_size          最大的内存消费者
  innodb_log_buffer_size           Redo Log 缓冲区（默认 16MB）
  key_buffer_size                  MyISAM 键缓冲（默认 8MB）
  table_open_cache × 约 4KB       打开表的缓存
  table_definition_cache × 约 4KB 表定义缓存
  Performance Schema               约 100~500MB

会话内存（每连接分配，总量 = 单连接用量 × 连接数）：
  sort_buffer_size                 排序缓冲（默认 256KB）
  join_buffer_size                 JOIN 缓冲（默认 256KB）
  read_buffer_size                 顺序读缓冲（默认 128KB）
  read_rnd_buffer_size             随机读缓冲（默认 256KB）
  tmp_table_size                   内存临时表大小（默认 16MB）
  thread_stack                     线程栈（默认 1MB）
  net_buffer_length                网络缓冲（默认 16KB）
  binlog_cache_size                Binlog 缓存（默认 32KB）

粗略估算公式：
  总内存 ≈ innodb_buffer_pool_size
         + innodb_log_buffer_size
         + key_buffer_size
         + Performance Schema 内存
         + max_connections × (sort_buffer_size + join_buffer_size
           + read_buffer_size + read_rnd_buffer_size + thread_stack
           + binlog_cache_size + net_buffer_length)
         + 临时表内存（动态）
         + 操作系统和其他进程的内存需求

实际计算示例（典型配置）：
  innodb_buffer_pool_size = 8GB
  max_connections = 500
  每连接会话内存约 2MB（最大情况）
  Performance Schema ≈ 300MB
  其他全局 ≈ 200MB

  最大内存 ≈ 8GB + 500 × 2MB + 300MB + 200MB
           ≈ 8GB + 1GB + 0.5GB
           ≈ 9.5GB

  服务器应至少有 12GB 内存（留 20% 给操作系统）
```

## 使用 Performance Schema 分析内存

```sql
-- 查看 MySQL 当前的内存分布：
SELECT * FROM sys.memory_global_by_current_bytes
LIMIT 20;

-- 按大类汇总：
SELECT
    SUBSTRING_INDEX(event_name, '/', 2) AS code_area,
    FORMAT_BYTES(SUM(current_alloc)) AS current_alloc
FROM sys.x$memory_global_by_current_bytes
GROUP BY SUBSTRING_INDEX(event_name, '/', 2)
ORDER BY SUM(current_alloc) DESC;

-- 查看总内存使用：
SELECT * FROM sys.memory_global_total;

-- 查看每个连接的内存使用：
SELECT
    thread_id,
    user,
    current_allocated,
    total_allocated
FROM sys.memory_by_thread_by_current_bytes
ORDER BY current_allocated DESC
LIMIT 20;
-- 如果某个连接的内存使用异常高
-- 可能是执行了复杂查询（大排序、大临时表）

-- 查看内存使用的历史峰值：
SELECT
    EVENT_NAME,
    CURRENT_NUMBER_OF_BYTES_USED / 1024 / 1024 AS current_mb,
    HIGH_NUMBER_OF_BYTES_USED / 1024 / 1024 AS peak_mb
FROM performance_schema.memory_summary_global_by_event_name
WHERE HIGH_NUMBER_OF_BYTES_USED > 100 * 1024 * 1024  -- 峰值 > 100MB
ORDER BY HIGH_NUMBER_OF_BYTES_USED DESC
LIMIT 15;
```

## 常见 OOM 原因与解决方案

```
原因1：innodb_buffer_pool_size 设置过大
  服务器 16GB 内存，Buffer Pool 设了 14GB
  加上连接内存、Performance Schema、操作系统
  总内存需求超过物理内存
  
  解决：
  Buffer Pool 设为物理内存的 50%~70%
  16GB 服务器：Buffer Pool 设为 8~10GB
  留出足够的内存给连接和操作系统

原因2：连接数过多
  max_connections = 2000
  每个连接即使空闲也占用约 1MB 线程栈
  如果大量连接同时执行排序/JOIN，每连接可能消耗 10MB+
  2000 × 10MB = 20GB
  
  解决：
  降低 max_connections 到合理值
  使用连接池减少实际连接数
  降低 sort_buffer_size、join_buffer_size

原因3：大查询消耗大量临时表内存
  复杂的 GROUP BY / ORDER BY 查询
  创建大量内存临时表
  超过 tmp_table_size 后转为磁盘临时表
  但转换前已分配的内存不会立即释放
  
  解决：
  优化查询减少临时表使用
  降低 tmp_table_size 限制单个临时表的内存

原因4：内存碎片（glibc malloc 碎片）
  MySQL 频繁分配和释放不同大小的内存块
  glibc 的内存分配器可能保留已释放的内存不归还操作系统
  RSS 持续增长但 Performance Schema 显示的使用量稳定
  
  解决：
  使用 jemalloc 替代 glibc 的 malloc
  # CentOS：yum install jemalloc
  # 在 mysqld_safe 或 systemd 中配置：
  # LD_PRELOAD=/usr/lib64/libjemalloc.so.2
  
  或者定期调用 malloc_trim（需要 MySQL 支持）

原因5：Performance Schema 内存过大
  启用了大量探针和历史表
  history_long_size 设置过大
  
  解决：
  减小 performance_schema_events_*_history_long_size
  关闭不需要的探针
```

## 预防 OOM

```bash
# 1. 调整 OOM Score（降低 MySQL 被杀的优先级）：
# MySQL 进程的 OOM score 越低，越不容易被杀
echo -1000 > /proc/$(pgrep mysqld)/oom_score_adj
# -1000 = 完全不会被 OOM Killer 杀掉
# 但如果内存真的耗尽，系统可能会 kernel panic

# 推荐设为 -500~-900：
echo -800 > /proc/$(pgrep mysqld)/oom_score_adj

# 在 systemd 中永久配置：
# [Service]
# OOMScoreAdjust=-800

# 2. 禁用 swap 或设置低 swappiness：
echo 1 > /proc/sys/vm/swappiness
# 或永久配置：
# vm.swappiness = 1 写入 /etc/sysctl.conf
# sysctl -p

# 3. 设置内存 cgroup 限制（防止 MySQL 无限占用内存）：
# 如果使用 systemd：
# [Service]
# MemoryLimit=12G
# 超过限制时 MySQL 会收到内存分配失败，而非被 OOM Kill

# 4. 监控内存使用趋势：
# Prometheus + mysqld_exporter 监控：
#   mysql_global_status_innodb_buffer_pool_bytes_data
#   mysql_global_status_threads_connected
#   process_resident_memory_bytes
# 设置告警：RSS > 物理内存的 85% 时告警
```

## 常见问题

**MySQL 重启后怎么知道上次是因为 OOM 被杀的？**

MySQL 错误日志中不会直接记录"OOM"，因为 OOM Kill 是操作系统级别的强制终止（SIGKILL），MySQL 进程没有机会写日志。判断方法：①检查系统日志（`dmesg`、`/var/log/messages`、`/var/log/syslog`）中是否有 OOM Killer 的记录。②MySQL 错误日志中如果看到重启后的崩溃恢复记录（`InnoDB: Starting crash recovery`），但没有之前的正常关闭记录（`mysqld: Shutdown complete`），就可能是被 OOM Kill 或其他异常终止。③检查 MySQL 进程的退出码：如果是被 SIGKILL（信号 9）终止的，在 systemd 日志中可以看到 `Main process exited, code=killed, status=9/KILL`。

## 注意事项

- 会话级的缓冲区（如 `sort_buffer_size`、`join_buffer_size`）不是连接建立时就分配的，而是在需要时才分配。一个空闲的 Sleep 连接不会消耗 sort_buffer 内存。但当大量连接同时执行需要排序的查询时，内存使用会瞬间飙升。因此内存估算要考虑最坏情况（所有连接同时使用最大缓冲）。
- `innodb_buffer_pool_size` 是 MySQL 最大的内存消费者。修改这个参数后需要重新评估服务器的总内存是否足够。在线调整 Buffer Pool 大小（`SET GLOBAL innodb_buffer_pool_size = ...`）时，如果增大的值超过了可用内存，可能直接导致 OOM。建议在调整前计算总内存需求。

---

## 总结

OOM 是 MySQL 因内存不足被 Linux OOM Killer 强制终止。通过 `dmesg` 和系统日志确认。MySQL 内存由全局内存（Buffer Pool、Performance Schema）和会话内存（排序/JOIN 缓冲 × 连接数）构成。常见原因：Buffer Pool 设太大、连接数过多、大查询消耗临时表内存、glibc 内存碎片。预防：Buffer Pool 设为物理内存的 50%~70%、控制 max_connections、使用 jemalloc、调整 OOM Score、监控内存趋势。Performance Schema 的 `memory_summary_global_by_event_name` 和 sys schema 的 `memory_global_by_current_bytes` 用于分析内存分布。

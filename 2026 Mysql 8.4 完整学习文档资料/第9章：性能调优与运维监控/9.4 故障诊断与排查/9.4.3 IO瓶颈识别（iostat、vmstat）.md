# IO 瓶颈识别（iostat/vmstat）

数据库是 I/O 密集型应用，磁盘读写性能直接影响 MySQL 的整体表现。当 MySQL 出现查询变慢、Buffer Pool 命中率下降、Redo Log 写入延迟等问题时，需要判断是否存在 I/O 瓶颈。Linux 系统提供了 `iostat` 和 `vmstat` 等工具用于监控系统级 I/O 状态，结合 MySQL 内部的 Performance Schema 文件 I/O 统计，可以全面诊断 I/O 瓶颈。

---

## iostat 工具

```bash
# iostat 是 sysstat 包提供的工具
# 安装：yum install sysstat 或 apt install sysstat

# 基本用法（每 2 秒刷新一次，共 10 次）：
iostat -xm 2 10

# 输出关键列说明：
# Device    rrqm/s  wrqm/s  r/s    w/s    rMB/s  wMB/s  avgrq-sz  avgqu-sz  await  r_await  w_await  svctm  %util
# sda       0.50    12.30   150    200    5.8    8.2    80.5      2.3       6.6    4.2      8.5      1.8    63.0

# 各列含义：
# r/s：每秒读请求数
# w/s：每秒写请求数
# rMB/s：每秒读取的 MB 数
# wMB/s：每秒写入的 MB 数
# avgrq-sz：平均每个请求的扇区数（请求大小）
# avgqu-sz：平均队列深度（等待处理的 I/O 请求数）
# await：平均 I/O 等待时间（ms），包含排队时间 + 服务时间
# r_await：平均读等待时间（ms）
# w_await：平均写等待时间（ms）
# svctm：平均服务时间（ms）（已废弃，不再准确）
# %util：设备利用率（0~100%）

# 判断 I/O 瓶颈的指标：
# %util > 80%：设备接近饱和（HDD 尤其敏感）
# await > 10ms（SSD）或 await > 20ms（HDD）：延迟偏高
# avgqu-sz > 4：队列积压，I/O 请求排队等待
# r/s + w/s（IOPS）接近设备上限

# 只查看特定磁盘：
iostat -xm -p sda 2 5

# 查看 NVMe 设备：
iostat -xm -p nvme0n1 2 5
```

## vmstat 工具

```bash
# vmstat 提供系统级的 CPU、内存、I/O 概览
# 每 2 秒刷新一次：
vmstat 2 10

# 输出示例：
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  2  1  10240 512000 128000 4096000   0    0   500  2000 5000 8000 30  5 60  5  0

# 关键列：
# r：运行队列中的进程数（等待 CPU）
# b：阻塞状态的进程数（等待 I/O）← 重要
# swpd：已使用的交换空间（KB）
# free：空闲内存（KB）
# si/so：每秒从 swap 读入/写出的 KB 数
# bi：每秒从块设备读入的 KB 数
# bo：每秒写入块设备的 KB 数
# wa：CPU 等待 I/O 的百分比 ← 重要

# 判断 I/O 瓶颈：
# b > 0 且持续：有进程因等待 I/O 被阻塞
# wa > 10%：CPU 花费较多时间等待 I/O
# wa > 30%：严重的 I/O 瓶颈
# si/so > 0：正在使用 swap（内存不足，严重影响性能）
```

## MySQL 内部的 I/O 监控

```sql
-- 结合 Performance Schema 从 MySQL 内部查看 I/O 情况：

-- 文件 I/O 统计（按文件类型）：
SELECT
    EVENT_NAME,
    COUNT_READ AS reads,
    SUM_NUMBER_OF_BYTES_READ / 1024 / 1024 AS read_mb,
    AVG_TIMER_READ / 1000000000 AS avg_read_ms,
    COUNT_WRITE AS writes,
    SUM_NUMBER_OF_BYTES_WRITE / 1024 / 1024 AS write_mb,
    AVG_TIMER_WRITE / 1000000000 AS avg_write_ms
FROM performance_schema.file_summary_by_event_name
WHERE COUNT_STAR > 0
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

-- InnoDB Buffer Pool 命中率：
SELECT
    (1 - (
        (SELECT VARIABLE_VALUE FROM performance_schema.global_status
         WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads')
        /
        GREATEST(
            (SELECT VARIABLE_VALUE FROM performance_schema.global_status
             WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests'),
            1)
    )) * 100 AS buffer_pool_hit_rate;
-- 命中率 < 99% 说明有较多的物理磁盘读
-- 可能是 Buffer Pool 太小或工作集太大

-- InnoDB I/O 状态：
SHOW ENGINE INNODB STATUS\G
-- 关注 FILE I/O 部分：
-- Pending normal aio reads: 0  → 等待的异步读请求
-- Pending normal aio writes: 0 → 等待的异步写请求
-- 如果 Pending 值持续 > 0，说明 I/O 子系统跟不上

-- InnoDB 的数据读写量：
SHOW STATUS LIKE 'Innodb_data_reads';        -- 物理读次数
SHOW STATUS LIKE 'Innodb_data_writes';       -- 物理写次数
SHOW STATUS LIKE 'Innodb_data_read';         -- 物理读字节数
SHOW STATUS LIKE 'Innodb_data_written';      -- 物理写字节数
SHOW STATUS LIKE 'Innodb_buffer_pool_wait_free'; -- 等待空闲页次数
-- wait_free > 0 说明 Buffer Pool 中没有空闲页
-- 需要等待脏页刷盘后才有空间，I/O 压力大
```

## 常见 I/O 瓶颈场景

```
场景1：Buffer Pool 太小
  表现：
    Innodb_buffer_pool_reads 持续增长
    Buffer Pool 命中率 < 95%
    iostat 的 r/s 很高（大量随机读）
  解决：增大 innodb_buffer_pool_size

场景2：Redo Log 写入瓶颈
  表现：
    iostat 中 Redo Log 所在磁盘的 w_await 高
    SHOW ENGINE INNODB STATUS 中 log write requests 很高
    事务提交变慢
  解决：
    将 Redo Log 放到独立的高速存储（NVMe）
    调整 innodb_flush_log_at_trx_commit（从 1 改为 2，牺牲少量安全性）
    增大 innodb_redo_log_capacity 减少 Checkpoint 频率

场景3：Binlog 写入瓶颈
  表现：
    binlog 所在磁盘的 w_await 高
    sync_binlog = 1 时每次事务都 fsync binlog
  解决：
    Binlog 放到独立磁盘
    非关键业务 sync_binlog = 0 或 100

场景4：临时表和排序文件 I/O
  表现：
    tmpdir 所在磁盘的读写量大
    大量查询使用 Using filesort 或 Using temporary
  解决：
    优化查询减少临时表使用
    将 tmpdir 设置到内存文件系统（tmpfs）
    增大 tmp_table_size 和 max_heap_table_size

场景5：磁盘使用 swap
  表现：
    vmstat 中 si/so > 0
    wa 很高
  解决：
    增加物理内存
    减小 innodb_buffer_pool_size 或 max_connections
    设置 vm.swappiness = 1（几乎不使用 swap）
```

## 不同存储类型的参考指标

| 指标 | HDD（7200 RPM）| SSD（SATA）| NVMe SSD |
|-----|:-------------:|:---------:|:--------:|
| 随机 IOPS | 100~200 | 10,000~50,000 | 100,000~500,000 |
| 顺序带宽 | 100~200 MB/s | 400~600 MB/s | 2,000~7,000 MB/s |
| 正常 await | 5~15 ms | 0.1~1 ms | 0.02~0.2 ms |
| 告警 await | > 20 ms | > 5 ms | > 1 ms |
| %util 告警 | > 70% | > 80% | > 90% |

## 适用场景

- **数据库整体性能下降的排查**：当所有查询都变慢时（不是个别慢查询），优先检查 I/O 指标，判断是否存在磁盘瓶颈
- **新服务器上线前的存储性能评估**：用 `fio` 工具测试磁盘的随机读写 IOPS 和延迟，确保满足 MySQL 的 I/O 需求

## 常见问题

**iostat 显示 %util 接近 100% 但 await 很低，这是瓶颈吗？**

不一定。`%util` 统计的是设备"忙碌"的时间百分比，但现代 SSD 和 NVMe 支持并行处理大量 I/O 请求（高队列深度）。即使 `%util` 显示 100%，设备可能仍有余量处理更多请求。判断是否真正瓶颈应看 `await`（延迟）和 `avgqu-sz`（队列深度）。如果 `await` 低（< 1ms for SSD）且 `avgqu-sz` 适中（< 32），说明设备在高效工作，不是瓶颈。如果 `await` 升高且 `avgqu-sz` 很大，才说明设备过载。

## 注意事项

- MySQL 的数据目录、Redo Log、Binlog、临时文件建议分布在不同的磁盘或存储卷上。这样可以将随机读（数据文件）、顺序写（Redo Log、Binlog）和临时 I/O（排序、临时表）的负载隔离，避免互相影响。通过 iostat 可以分别监控每个磁盘的 I/O 状况。
- Linux 内核参数 `vm.swappiness` 控制系统使用 swap 的倾向。MySQL 服务器建议设为 1（而非 0，因为 0 在某些内核版本下可能导致 OOM killer 触发）。使用 swap 对 MySQL 性能影响极大，因为 Buffer Pool 中的内存页被换出到磁盘后再访问时延迟从纳秒级变为毫秒级。

## 总结

I/O 瓶颈诊断使用 `iostat`（设备级 I/O 统计）和 `vmstat`（系统级概览）。iostat 关键指标：`await`（延迟）、`%util`（利用率）、`avgqu-sz`（队列深度）。vmstat 关键指标：`b`（I/O 阻塞进程数）、`wa`（CPU 等 I/O 占比）、`si/so`（swap 使用）。MySQL 内部通过 Performance Schema 文件 I/O 统计和 Buffer Pool 命中率辅助判断。常见瓶颈：Buffer Pool 太小、Redo Log/Binlog 写入慢、使用 swap。数据文件和日志文件建议分磁盘存放。SSD/NVMe 的 %util 不能单独判断瓶颈，需结合 await。

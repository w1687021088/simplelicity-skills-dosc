# 主从延迟排查

主从延迟（Replication Lag）是指从库的数据落后于主库的时间差。在 MySQL 主从复制架构中，主库的数据变更通过 Binlog 传输到从库，由从库的 SQL 线程（或多个 Worker 线程）重放。如果从库重放的速度跟不上主库产生变更的速度，就会产生延迟。主从延迟会导致从库上读取到过期数据，影响读写分离架构的数据一致性。

---

## 延迟监控

```sql
-- 方式1：SHOW REPLICA STATUS（传统方式）
SHOW REPLICA STATUS\G
-- 关键字段：
-- Seconds_Behind_Master：从库落后主库的秒数
--   0 = 无延迟（同步）
--   NULL = I/O 线程或 SQL 线程未运行
--   > 0 = 有延迟
-- Replica_IO_Running：I/O 线程状态（Yes/No/Connecting）
-- Replica_SQL_Running：SQL 线程状态（Yes/No）
-- Relay_Log_Space：Relay Log 占用的磁盘空间

-- Seconds_Behind_Master 的局限性：
-- 1. 只反映 SQL 线程正在处理的事件与主库的时间差
-- 2. 如果 I/O 线程也有延迟，可能被低估
-- 3. 受主从时钟不同步影响
-- 4. 从库暂停复制后恢复时可能瞬间跳变

-- 方式2：Performance Schema（MySQL 8.0+ 推荐）
SELECT
    CHANNEL_NAME,
    LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS source_commit,
    LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP AS replica_apply,
    TIMESTAMPDIFF(SECOND,
        LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
        LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP
    ) AS lag_seconds
FROM performance_schema.replication_applier_status_by_worker
WHERE SERVICE_STATE = 'ON';
-- 基于事务时间戳，比 Seconds_Behind_Master 更准确

-- 方式3：pt-heartbeat（Percona 工具，最准确）
-- 在主库上持续写入心跳记录（带时间戳）
-- 在从库上读取心跳记录与当前时间比较

-- 主库端（持续运行）：
-- pt-heartbeat --update --host=master_host --database=percona

-- 从库端（监控延迟）：
-- pt-heartbeat --monitor --host=replica_host --database=percona
-- 输出示例：0.05s [ 0.00s, 0.00s, 0.00s ]
-- 当前延迟 0.05 秒，最近 1/5/15 分钟平均值
```

## 延迟的常见原因

```
原因1：从库 SQL 线程单线程回放（最常见）
  MySQL 5.6 之前 SQL 线程是单线程的
  主库可以并发写入，从库只能串行回放
  主库的写入速度 > 从库的回放速度 → 延迟
  
  解决：开启多线程复制（MTS）
  SET GLOBAL replica_parallel_workers = 8;
  SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
  -- MySQL 8.0.27+ 默认 LOGICAL_CLOCK
  -- MySQL 8.4 已移除 DATABASE 类型

原因2：主库上的大事务
  一个事务修改了 100 万行
  主库提交只需 1 次（并发写入快）
  从库回放需要逐行重做（串行处理）
  大事务在从库回放期间，延迟持续增长
  
  解决：
  拆分大事务为小批次
  避免一次 DELETE/UPDATE 百万行
  使用分批处理（每次 1000~10000 行）

原因3：从库硬件性能不足
  从库使用了比主库差的硬件（如 HDD vs SSD）
  从库同时承担大量读查询，资源竞争
  
  解决：
  从库使用相同配置的硬件
  减少从库的读负载
  为从库添加索引优化查询

原因4：从库上的大查询阻塞回放
  从库上执行了一个长时间的 SELECT 查询
  如果 SQL 线程需要修改被 SELECT 读取的表
  可能因为元数据锁（MDL）等待而被阻塞
  
  解决：
  从库上避免执行长时间查询
  或使用 pt-kill 自动终止超时查询

原因5：网络延迟
  主从之间网络带宽不足或延迟高
  I/O 线程接收 Binlog 变慢
  
  诊断：
  SHOW REPLICA STATUS 中检查
  Master_Log_File vs Relay_Master_Log_File
  如果差距大 → I/O 线程延迟（网络问题）
  如果相同 → SQL 线程延迟（回放问题）

原因6：主库上执行 DDL
  ALTER TABLE 等 DDL 在从库上也需要执行
  大表的 DDL 可能需要几分钟到几小时
  DDL 执行期间其他事务的回放被阻塞
  
  解决：
  使用 pt-online-schema-change 或 gh-ost
  这些工具不阻塞从库回放
```

## 诊断流程

```sql
-- 步骤1：确认延迟是 I/O 线程还是 SQL 线程导致

SHOW REPLICA STATUS\G
-- 比较以下字段：
-- Master_Log_File / Read_Master_Log_Pos     → I/O 线程读到的位置
-- Relay_Master_Log_File / Exec_Master_Log_Pos → SQL 线程执行到的位置

-- 如果 Master_Log_File 和主库的当前 binlog 文件差距大
-- → I/O 线程延迟（网络问题或主库 dump 线程问题）

-- 如果 Master_Log_File 与主库一致，但 Relay_Master_Log_File 落后
-- → SQL 线程延迟（回放速度不够）

-- 步骤2：如果是 SQL 线程延迟，检查正在回放的事务
SELECT
    WORKER_ID,
    APPLYING_TRANSACTION,
    APPLYING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
    LAST_APPLIED_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker
WHERE SERVICE_STATE = 'ON';

-- 步骤3：检查从库上是否有阻塞 SQL 线程的查询
SELECT ID, USER, HOST, DB, TIME, STATE, INFO
FROM information_schema.PROCESSLIST
WHERE COMMAND != 'Sleep'
  AND TIME > 10
ORDER BY TIME DESC;

-- 步骤4：检查从库的系统资源
-- CPU：top -H -p $(pgrep mysqld)
-- I/O：iostat -xm 2 5
-- 内存：free -h

-- 步骤5：检查多线程复制配置
SHOW VARIABLES LIKE 'replica_parallel_workers';
SHOW VARIABLES LIKE 'replica_parallel_type';
-- 如果 workers = 0 或 1，开启多线程复制
```

## 多线程复制调优

```sql
-- MySQL 8.0/8.4 的多线程复制（MTS）配置：

-- 停止复制：
STOP REPLICA;

-- 设置并行 Worker 数量：
SET GLOBAL replica_parallel_workers = 8;
-- 建议值：CPU 核心数的 50%~100%
-- 不要超过主库的并发写入线程数

-- 设置并行类型（MySQL 8.4 只支持 LOGICAL_CLOCK）：
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
-- LOGICAL_CLOCK：同一组提交的事务可以并行回放
-- 并行度取决于主库的 binlog_transaction_dependency_tracking

-- 保持提交顺序：
SET GLOBAL replica_preserve_commit_order = ON;
-- 确保从库的事务提交顺序与主库一致
-- 虽然回放是并行的，但提交顺序保持一致

-- 启动复制：
START REPLICA;

-- 验证多线程复制是否生效：
SELECT WORKER_ID, SERVICE_STATE, LAST_APPLIED_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker;
-- 应该看到多个 Worker 在运行
```

## 适用场景

- **读写分离架构中读到旧数据**：通过监控主从延迟判断数据过期程度，对强一致性读请求路由到主库
- **从库延迟告警后的排查处理**：按照"确认延迟来源（I/O vs SQL）→ 分析原因 → 针对性优化"的流程处理

## 常见问题

**主从延迟突然增大然后缓慢恢复，可能是什么原因？**

最常见的原因是主库上执行了一个大事务或 DDL。例如一个 DELETE 删除了 50 万行，这个操作在主库上几秒就完成了，但在从库上需要逐行重做，可能需要几分钟。在从库回放这个大事务期间，`Seconds_Behind_Master` 会持续增大。回放完成后，如果主库没有新的大事务，延迟会逐渐追平降为 0。可以通过 `SHOW REPLICA STATUS` 中的 `Exec_Master_Log_Pos` 观察是否在缓慢移动（而非停滞）来判断是否在回放大事务。

---

## 注意事项

- `Seconds_Behind_Master` 在某些情况下会显示 0 但实际有延迟。例如：I/O 线程正常但 SQL 线程已停止（此时显示 NULL），或者主库长时间没有写入（没有新事件供从库比较）。建议使用 `pt-heartbeat` 或 Performance Schema 的事务时间戳来获取更准确的延迟数据。
- 开启多线程复制后，如果出现复制错误，排查会比单线程复制复杂。需要检查 `replication_applier_status_by_worker` 中每个 Worker 的状态。某个 Worker 报错后，协调器会停止分配新事务，但其他 Worker 可能还在运行之前分配的事务。恢复时可能需要处理 Gap（Worker 之间的执行间隔）。

---

## 总结

主从延迟监控：`Seconds_Behind_Master`（传统）、Performance Schema 事务时间戳（推荐）、`pt-heartbeat`（最准确）。延迟分为 I/O 线程延迟（网络问题）和 SQL 线程延迟（回放问题）。常见原因：单线程回放、大事务、从库性能差、大查询阻塞、DDL。核心解决方案：开启多线程复制（`replica_parallel_workers`）、拆分大事务、使用在线 DDL 工具。多线程复制推荐 `LOGICAL_CLOCK` 类型并开启 `replica_preserve_commit_order`。

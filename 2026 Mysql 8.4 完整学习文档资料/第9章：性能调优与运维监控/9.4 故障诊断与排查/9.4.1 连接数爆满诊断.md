# 连接数爆满诊断

当 MySQL 客户端尝试连接时收到 `ERROR 1040 (HY000): Too many connections` 错误，说明当前活跃连接数已达到 `max_connections` 的上限，新连接被拒绝。这是生产环境中最常见的故障之一。连接数爆满通常不是单纯的参数设置问题，而是应用层连接管理不当、慢查询堆积或锁等待等深层问题的表现。

---

## 紧急处理：如何在连接满时登录

```sql
-- MySQL 预留了 max_connections + 1 个连接给拥有 CONNECTION_ADMIN 权限的用户
-- 即使普通连接满了，管理员仍可以登录

-- 方式1：使用拥有 CONNECTION_ADMIN 权限的账号登录
mysql -u root -p
-- root 默认拥有 CONNECTION_ADMIN 权限

-- 方式2：通过管理端口登录（MySQL 8.0.14+）
-- 需要在 my.cnf 中提前配置：
-- [mysqld]
-- admin_address = 127.0.0.1
-- admin_port = 33062
-- create_admin_listener_thread = ON

mysql -u root -p --host=127.0.0.1 --port=33062
-- 管理端口独立于普通端口，不受 max_connections 限制

-- 登录后先查看当前连接情况：
SHOW STATUS LIKE 'Threads_connected';    -- 当前连接数
SHOW STATUS LIKE 'Max_used_connections'; -- 历史最高连接数
SHOW VARIABLES LIKE 'max_connections';   -- 最大连接数限制
```

## 诊断步骤

```sql
-- 步骤1：查看连接分布（按用户）
SELECT USER, COUNT(*) AS conn_count
FROM information_schema.PROCESSLIST
GROUP BY USER
ORDER BY conn_count DESC;

-- 步骤2：查看连接分布（按来源主机）
SELECT SUBSTRING_INDEX(HOST, ':', 1) AS client_host, COUNT(*) AS conn_count
FROM information_schema.PROCESSLIST
GROUP BY client_host
ORDER BY conn_count DESC;

-- 步骤3：查看连接分布（按状态）
SELECT COMMAND, COUNT(*) AS cnt
FROM information_schema.PROCESSLIST
GROUP BY COMMAND
ORDER BY cnt DESC;
-- Sleep 数量多 → 空闲连接未释放
-- Query 数量多 → 查询堆积（可能有慢查询或锁等待）

-- 步骤4：查看具体的空闲连接（Sleep 连接）
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Sleep'
ORDER BY TIME DESC
LIMIT 20;
-- TIME 列表示连接空闲的秒数
-- 如果大量连接空闲了几百甚至几千秒，说明应用未正确关闭连接

-- 步骤5：查看正在执行的查询
SELECT ID, USER, HOST, DB, TIME, STATE, INFO
FROM information_schema.PROCESSLIST
WHERE COMMAND != 'Sleep'
  AND COMMAND != 'Daemon'
ORDER BY TIME DESC
LIMIT 20;
-- 如果有查询执行了很长时间，可能是慢查询导致连接堆积

-- 步骤6：使用 Performance Schema（更准确）
SELECT
    t.PROCESSLIST_USER AS user,
    t.PROCESSLIST_HOST AS host,
    t.PROCESSLIST_COMMAND AS command,
    t.PROCESSLIST_TIME AS idle_time,
    esc.SQL_TEXT
FROM performance_schema.threads t
LEFT JOIN performance_schema.events_statements_current esc
    ON t.THREAD_ID = esc.THREAD_ID
WHERE t.TYPE = 'FOREGROUND'
ORDER BY t.PROCESSLIST_TIME DESC
LIMIT 20;
```

## 常见原因与解决方案

```
原因1：应用未正确关闭连接（最常见）
  表现：大量 Sleep 状态的连接，空闲时间很长
  原因：代码中数据库连接未 close()，连接泄漏
  解决：
    临时：降低 wait_timeout（如 300 秒）自动断开空闲连接
    SET GLOBAL wait_timeout = 300;
    SET GLOBAL interactive_timeout = 300;
    根本：修复应用代码，使用 try-finally 确保连接关闭

原因2：连接池配置不当
  表现：某个客户端主机的连接数特别多
  原因：连接池最大连接数设置过大
  解决：
    应用连接池的 maxPoolSize 不应超过需要
    经验值：单个应用实例 20~50 个连接通常足够
    总连接数 = 应用实例数 × 单实例连接池大小
    确保总数 < max_connections 的 80%

原因3：慢查询导致连接堆积
  表现：大量连接在 Query 状态，执行时间长
  原因：某个慢 SQL 占用连接不释放，新请求排队
  解决：
    临时：KILL 掉执行时间过长的查询
    KILL <processlist_id>;
    根本：优化慢查询（添加索引、重写 SQL）

原因4：锁等待导致连接堆积
  表现：连接状态为 Waiting for table metadata lock 或类似锁等待
  原因：DDL 操作（如 ALTER TABLE）被长事务阻塞
    长事务持有锁 → DDL 等待 → 后续所有查询等待 DDL → 连接堆积
  解决：
    找到并终止阻塞的长事务
    SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started;
    KILL <blocking_thread_id>;

原因5：max_connections 设置确实太小
  表现：业务增长后连接数自然增加
  解决：
    SET GLOBAL max_connections = 500;  -- 在线调整
    同时评估每个连接的内存开销（约 1~10MB/连接）
    确保服务器内存足够
```

## 批量清理空闲连接

```sql
-- 生成批量 KILL 命令（清理空闲超过 600 秒的连接）：
SELECT CONCAT('KILL ', ID, ';') AS kill_cmd
FROM information_schema.PROCESSLIST
WHERE COMMAND = 'Sleep'
  AND TIME > 600
  AND USER != 'system user';
```

## 适用场景

- **线上 Too many connections 报错的紧急处理**：按照诊断步骤快速定位原因（空闲连接泄漏、慢查询堆积、锁等待），采取临时措施恢复服务
- **连接数使用率持续偏高的优化**：通过分析连接分布，优化应用连接池配置和 wait_timeout 设置

## 常见问题

**增大 max_connections 能解决问题吗？**

大多数情况下不能。如果根因是连接泄漏或慢查询堆积，增大 max_connections 只是延缓了问题爆发的时间。而且每个连接都需要消耗内存（排序缓冲、join 缓冲、线程栈等，每个连接约 1~10MB），盲目增大 max_connections 可能导致内存不足甚至 OOM。正确做法是先诊断根因，只有在确认连接数不够是因为业务自然增长时才增大 max_connections，同时确保服务器有足够内存。

## 注意事项

- 使用 `KILL` 命令终止连接时要注意：如果被终止的连接正在执行一个大事务（如大量 INSERT 或 UPDATE），MySQL 需要回滚该事务，回滚过程可能很慢（取决于已修改的数据量）。在回滚完成之前，该连接不会真正释放。可以通过 `SHOW ENGINE INNODB STATUS` 的 TRANSACTIONS 部分查看回滚进度。
- 生产环境建议提前配置好管理端口（`admin_port`），这样在连接数爆满时仍然有独立的管理通道可以登录排查。如果没有配置管理端口，可以尝试在本机使用 socket 方式连接（`mysql -u root -p --socket=/var/lib/mysql/mysql.sock`），socket 连接也使用预留的管理连接名额。

---

## 总结

连接数爆满（Too many connections）的诊断流程：通过管理连接或管理端口登录 → 查看连接分布（按用户、主机、状态）→ 定位根因（空闲泄漏、慢查询堆积、锁等待、配置不足）→ 采取临时措施（KILL 空闲连接、降低 wait_timeout、增大 max_connections）→ 根本修复（修复连接泄漏代码、优化慢查询、调整连接池配置）。预防措施：配置管理端口、设置合理的 wait_timeout、监控连接数并设置告警。

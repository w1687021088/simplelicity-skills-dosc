# innodb_thread_concurrency 并发线程数

`innodb_thread_concurrency` 限制同时在 InnoDB 内核中执行的线程数量。当并发线程数达到此限制时，新的线程会先休眠一段时间（由 `innodb_thread_sleep_delay` 控制），然后排队等待进入。该参数的目的是在高并发场景下减少线程之间的上下文切换和资源竞争，防止过多线程同时执行导致 CPU 效率下降。默认值为 0，表示不限制并发线程数。

---

## 参数说明

```sql
-- 查看当前值：
SHOW VARIABLES LIKE 'innodb_thread_concurrency';
-- 默认值：0（不限制）
-- 取值范围：0 ~ 1000

-- 在线动态修改：
SET GLOBAL innodb_thread_concurrency = 16;

-- 在 my.cnf 中配置：
-- [mysqld]
-- innodb_thread_concurrency = 16

-- 相关参数：
SHOW VARIABLES LIKE 'innodb_thread_sleep_delay';
-- 默认值：10000（微秒 = 10毫秒）
-- 当线程无法进入 InnoDB 内核时的等待时间

SHOW VARIABLES LIKE 'innodb_adaptive_max_sleep_delay';
-- 默认值：150000（微秒 = 150毫秒）
-- 自适应调整的最大睡眠时间

SHOW VARIABLES LIKE 'innodb_concurrency_tickets';
-- 默认值：5000
-- 线程进入 InnoDB 后获得的"票据"数
-- 用完票据后需要重新排队
```

---

## 工作机制

```
innodb_thread_concurrency 的并发控制流程：

当 innodb_thread_concurrency = 0（默认）：
  所有线程自由竞争进入 InnoDB
  不做任何并发限制
  适合大多数现代服务器

当 innodb_thread_concurrency > 0：
  线程请求进入 InnoDB 时：
    1. 检查当前 InnoDB 内活跃线程数
    2. 如果 < innodb_thread_concurrency → 直接进入
    3. 如果 >= innodb_thread_concurrency → 先睡眠 innodb_thread_sleep_delay 微秒
    4. 睡眠后再次尝试，如果仍然不行 → 进入 FIFO 等待队列
  
  票据机制（Ticket）：
    线程成功进入 InnoDB 后获得 innodb_concurrency_tickets 个票据（默认 5000）
    每执行一次行操作消耗一个票据
    票据用完后线程退出 InnoDB，重新排队
    目的：防止单个长查询长期占用并发名额

  自适应睡眠调整：
    InnoDB 根据系统负载自动调整 innodb_thread_sleep_delay
    负载低时缩短睡眠时间，负载高时延长
    上限为 innodb_adaptive_max_sleep_delay
```

## 设置建议

```
值=0（默认，推荐大多数场景）：
  不限制并发
  InnoDB 内部使用自适应机制管理线程调度
  现代 CPU（多核）和操作系统的线程调度器已经很高效
  大多数情况下不需要手动限制

需要设置非零值的场景：
  1. CPU 核数较少（< 8核）但并发连接很高（> 200）
     过多线程在少量 CPU 上竞争会导致上下文切换开销过大
  2. 观察到 CPU sys%（系统调用时间）过高
     大量线程频繁的内核态切换
  3. 查询延迟随并发增加而非线性增长
     说明线程竞争导致效率下降

设置参考值：
  CPU 核数 × 2 是常见的起点
  4核服务器：innodb_thread_concurrency = 8
  8核服务器：innodb_thread_concurrency = 16
  16核服务器：innodb_thread_concurrency = 0 或 32
  32核+：建议保持默认 0

验证效果：
  设置后观察 TPS（每秒事务数）和平均查询延迟
  如果 TPS 提升、延迟降低 → 设置有效
  如果 TPS 降低 → 值设太小了，增大或改回 0
```

## 监控并发线程状态

```sql
-- 查看当前 InnoDB 内部的线程状态：
SHOW ENGINE INNODB STATUS\G

-- ROW OPERATIONS 部分：
-- Number of rows inserted 12345, updated 6789, deleted 123, read 456789
-- 0 queries inside InnoDB, 0 queries in queue
-- 上面的 "queries inside InnoDB" 就是当前在 InnoDB 内执行的线程数
-- "queries in queue" 是等待进入的线程数

-- 如果 queries in queue 持续 > 0
-- 说明 innodb_thread_concurrency 限制了并发
-- 需要增大该值或改为 0

-- 通过 performance_schema 监控：
SELECT * FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
    'Innodb_row_lock_current_waits',
    'Threads_running'
);
-- Threads_running：当前正在运行的线程数
-- 如果远超 CPU 核数，考虑限制并发
```

## 适用场景

- **低核数高并发的服务器**：在 4~8 核但有 200+ 并发连接的环境中，设置合理的 `innodb_thread_concurrency` 可以减少上下文切换，提升整体吞吐量
- **云服务器的小规格实例**：2核4G 或 4核8G 的小规格云服务器，CPU 资源有限，限制并发可以防止过度竞争

## 常见问题

**innodb_thread_concurrency 设置为 0 和设置为一个很大的值（如 1000）有什么区别？**

两者的行为有根本不同。设置为 0 时，InnoDB 完全跳过并发检查逻辑，线程直接进入 InnoDB 执行，没有任何额外开销。设置为 1000 时，虽然几乎不会触发限制（很少有 1000 个线程同时在 InnoDB 中），但每个线程进入 InnoDB 时仍然需要执行并发检查的代码路径（获取计数器、比较、票据管理等），会有少量额外的 CPU 开销。所以推荐使用 0 而不是一个很大的值。

---

## 注意事项

- `innodb_concurrency_tickets` 的默认值 5000 对大多数负载是合适的。但如果有大量全表扫描的长查询（每次扫描数百万行），5000 个票据可能很快用完，导致长查询频繁被中断和重新排队，反而增加总执行时间。对于这种场景，可以增大 `innodb_concurrency_tickets`（如 50000），让长查询有更多连续执行的机会。
- `innodb_thread_concurrency` 的值设置得过小（如设为 2~4）会严重限制并发能力，导致大量请求排队，即使 CPU 和 I/O 资源充足也无法充分利用。如果不确定合适的值，建议保持默认的 0。

---

## 总结

`innodb_thread_concurrency` 限制 InnoDB 内核中的并发线程数，默认 0（不限制）。设为 > 0 时超出限制的线程会睡眠和排队。票据机制（`innodb_concurrency_tickets=5000`）防止单线程长期占用。自适应睡眠延迟动态调整等待时间。大多数现代多核服务器保持默认 0 即可。低核数高并发场景可设为 CPU核数 × 2。通过 `queries inside InnoDB` 和 `queries in queue` 监控。值为 0 比大值更优（跳过检查逻辑）。过小的值会严重限制吞吐量。

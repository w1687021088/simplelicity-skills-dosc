# innodb_flush_log_at_trx_commit 刷盘策略

`innodb_flush_log_at_trx_commit` 是 InnoDB 最重要的持久性（Durability）参数，控制事务提交时 Redo Log 的刷盘行为。该参数有三个取值（0、1、2），分别代表不同的数据安全性和写入性能之间的权衡。理解这三个值的行为差异，是做好 MySQL 性能调优和数据安全决策的基础。

---

## 三种刷盘策略

```
innodb_flush_log_at_trx_commit = 1（默认值，最安全）：
  事务提交时：
    1. 将 Log Buffer 写入 Redo Log 文件（write）
    2. 立即调用 fsync() 将 Redo Log 刷到磁盘
  效果：每次事务提交都保证数据持久化到磁盘
  数据安全：最高，MySQL 崩溃或操作系统崩溃都不丢数据
  性能影响：每次提交都有磁盘 fsync，性能最低

innodb_flush_log_at_trx_commit = 2（折中方案）：
  事务提交时：
    1. 将 Log Buffer 写入操作系统文件缓存（write）
    2. 不立即 fsync，由后台线程每秒 fsync 一次
  效果：事务提交很快（只写到 OS 缓存）
  数据安全：MySQL 进程崩溃不丢数据（OS 缓存中有数据）
           操作系统崩溃或断电可能丢失最近 1 秒的事务
  性能影响：比值 1 快很多

innodb_flush_log_at_trx_commit = 0（最快，风险最大）：
  事务提交时：
    1. 仅将数据写入 Log Buffer（内存）
    2. 后台线程每秒将 Log Buffer 写入文件并 fsync
  效果：事务提交最快（只写内存）
  数据安全：MySQL 进程崩溃可能丢失最近 1 秒的事务
           操作系统崩溃或断电同样丢失数据
  性能影响：最高性能
```

---

## 三种策略的对比

| 对比维度 | 值=1（默认）| 值=2 | 值=0 |
|---------|:---------:|:----:|:----:|
| 提交时写入 | 写文件 + fsync | 写 OS 缓存 | 写 Log Buffer |
| fsync 频率 | 每次提交 | 每秒 | 每秒 |
| MySQL 崩溃丢数据 | 不丢 | 不丢 | 可能丢 1 秒 |
| OS 崩溃/断电丢数据 | 不丢 | 可能丢 1 秒 | 可能丢 1 秒 |
| 写入性能 | 基准 | 约提升 50%~100% | 约提升 100%~200% |
| ACID 合规 | 完全合规 | 部分合规 | 不合规 |

## 配置方法

```sql
-- 查看当前值：
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

-- 在线动态修改（立即生效）：
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
-- 仅影响新的连接（已建立连接的行为不变）

-- 在 my.cnf 中配置（永久生效）：
-- [mysqld]
-- innodb_flush_log_at_trx_commit = 1

-- 配合 sync_binlog 使用（双一配置，最安全）：
-- innodb_flush_log_at_trx_commit = 1
-- sync_binlog = 1
-- "双一配置"是金融等高安全场景的标准配置
```

## 与 sync_binlog 的配合

```sql
-- sync_binlog 控制 binlog 的刷盘策略
-- 与 innodb_flush_log_at_trx_commit 配合使用

-- sync_binlog = 1：每次事务提交都将 binlog 刷盘
-- sync_binlog = 0：由操作系统决定何时刷盘
-- sync_binlog = N：每 N 个事务刷盘一次

-- 常见组合：

-- "双一配置"（最安全）：
-- innodb_flush_log_at_trx_commit = 1
-- sync_binlog = 1
-- 每次提交：Redo Log fsync + binlog fsync
-- 适合：金融、支付、核心业务

-- "双零配置"（最快）：
-- innodb_flush_log_at_trx_commit = 0
-- sync_binlog = 0
-- 每秒批量刷盘
-- 适合：测试环境、可接受数据丢失的场景

-- 折中配置：
-- innodb_flush_log_at_trx_commit = 2
-- sync_binlog = 100
-- MySQL 崩溃不丢数据，OS 崩溃最多丢 1 秒
-- 适合：非核心业务、日志型数据
```

```
不同刷盘策略对写入性能的影响（参考值，实际取决于硬件）：

测试条件：sysbench oltp_write_only，16 线程

SSD 存储：
  值=1（双一配置）：约 3000 TPS
  值=2：约 5500 TPS（提升 ~83%）
  值=0：约 7000 TPS（提升 ~133%）

HDD 存储：
  值=1（双一配置）：约 200 TPS
  值=2：约 800 TPS（提升 ~300%）
  值=0：约 1200 TPS（提升 ~500%）

结论：
  HDD 上差异巨大（fsync 延迟高）
  SSD 上差异缩小但仍然明显
  使用 NVMe SSD 可以缩小值=1 的性能劣势
```

## 临时调整的场景

```sql
-- 某些场景下可以临时调整为非安全值提升性能：

-- 场景1：大批量数据导入
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
-- 执行大量 INSERT/LOAD DATA 操作
-- ...导入完成后恢复：
SET GLOBAL innodb_flush_log_at_trx_commit = 1;

-- 场景2：从库（Replica）
-- 从库的数据可以从主库重新同步
-- 可以使用值=2 提升从库的复制追赶速度
-- [mysqld]（从库配置）
-- innodb_flush_log_at_trx_commit = 2
-- sync_binlog = 0

-- 场景3：备份恢复
-- 恢复 mysqldump 备份时临时设置为 0
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
SET GLOBAL sync_binlog = 0;
-- source /backup/backup.sql;
-- 恢复完成后改回安全值
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;
```

## 适用场景

- **金融/支付等核心业务**：必须使用"双一配置"（`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`），确保每笔交易数据在任何故障下都不丢失
- **大批量数据导入或备份恢复**：临时设置为 0 或 2 提升性能，完成后恢复为安全值

---

## 常见问题

**在从库上设置 innodb_flush_log_at_trx_commit=2 安全吗？**

在从库上使用值 2 是比较常见的优化做法。原因：从库的数据来源于主库的 binlog，即使从库因 OS 崩溃丢失了最近 1 秒的数据，重启后可以从主库重新同步这些数据（通过 binlog 重放）。因此从库的数据安全性由主库的 binlog 保证，不依赖从库自身的 Redo Log 持久性。但如果从库要作为故障转移的候选主库，需要权衡是否接受短暂的数据差异。某些 DBA 会在候选主库上仍然使用值 1 以确保切换后数据完整。

---

## 注意事项

- `innodb_flush_log_at_trx_commit` 的 fsync 频率说明中的"每秒一次"并非绝对精确。InnoDB 的后台线程大致每秒执行一次刷盘操作，但实际间隔可能受系统负载、InnoDB 内部活动（如 checkpoint）的影响而有所波动。在极端情况下，实际丢失的数据可能略多于或略少于 1 秒。
- 修改该参数使用 `SET GLOBAL` 后，已经存在的连接仍使用旧值，只有新建立的连接才使用新值。如果需要所有连接立即生效，可能需要让应用程序重新建立连接。通过连接池的连接回收机制，通常在几分钟内所有连接都会更新为新值。

---

## 总结

`innodb_flush_log_at_trx_commit` 控制事务提交时 Redo Log 的刷盘行为。值=1（默认）：每次提交 fsync，最安全但最慢；值=2：提交写 OS 缓存，每秒 fsync，MySQL 崩溃不丢数据，OS 崩溃可能丢 1 秒；值=0：提交只写内存，每秒刷盘，最快但风险最大。与 `sync_binlog` 配合的"双一配置"是金融场景标准。SSD 上性能差异约 50%~100%，HDD 上差异可达 300%~500%。从库和批量导入可以临时使用非安全值。修改后需新连接才生效。

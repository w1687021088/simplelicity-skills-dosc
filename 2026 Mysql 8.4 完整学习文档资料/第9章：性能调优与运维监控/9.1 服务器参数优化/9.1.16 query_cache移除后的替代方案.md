# query_cache 移除后的替代方案

MySQL 的查询缓存（Query Cache）在 MySQL 5.7 中被标记为废弃，并在 MySQL 8.0 中被完全移除。查询缓存的设计思路是将 SELECT 语句的结果直接缓存在内存中，相同的 SQL 再次执行时直接返回缓存结果。但在实际生产中，查询缓存的命中率很低（表有任何写操作都会让该表的所有缓存失效），而且全局互斥锁（mutex）在高并发下成为严重瓶颈。MySQL 8.0+ 和 8.4 中不再有 query_cache 相关参数，需要使用其他方案实现类似的缓存功能。

---

## 查询缓存被移除的原因

```
MySQL Query Cache 的核心问题：

1. 高失效率
   任何对表的写操作（INSERT/UPDATE/DELETE）
   都会使该表的所有查询缓存失效
   即使写操作修改的数据与缓存的查询完全无关
   在写操作频繁的 OLTP 场景下，缓存命中率极低

2. 全局互斥锁瓶颈
   Query Cache 使用一个全局的 mutex
   所有查询在检查缓存和更新缓存时都需要获取此锁
   高并发下成为严重的性能瓶颈
   甚至比不使用缓存更慢

3. 内存碎片化
   Query Cache 使用自己的内存管理
   长时间运行后内存碎片严重
   分配和释放效率低下

4. 缓存匹配机制过于严格
   SQL 文本必须完全相同才能命中（包括大小写、空格）
   SELECT * FROM t WHERE id=1
   和 SELECT * FROM t WHERE id = 1（多一个空格）不命中

MySQL 官方在 8.0 中彻底移除了 Query Cache
所有相关参数和状态变量被删除
```

## 替代方案一：应用层缓存（Redis/Memcached）

```
最常用的替代方案：在应用层使用 Redis 或 Memcached

工作流程：
  1. 应用发起查询前，先查 Redis
  2. Redis 有缓存 → 直接返回（不查 MySQL）
  3. Redis 无缓存 → 查 MySQL → 将结果存入 Redis → 返回

优势：
  缓存粒度可控（按 key 精确控制失效）
  不受 MySQL 表级失效的限制
  支持复杂的失效策略（TTL、主动失效、延迟删除）
  性能比 MySQL Query Cache 好几个量级
  支持分布式部署，可横向扩展

常见模式：
  Cache-Aside（旁路缓存，最常用）：
    读：查缓存 → 未命中 → 查 DB → 写缓存
    写：更新 DB → 删除缓存
  
  Read-Through（读穿透）：
    缓存自动加载数据
    
  Write-Behind（写后更新）：
    先写缓存，异步写 DB

适用场景：
  读多写少的热点数据（商品详情、用户信息）
  可以容忍短暂数据不一致（TTL 过期后刷新）
```

## 替代方案二：ProxySQL 查询缓存

```sql
-- ProxySQL 内置了查询缓存功能
-- 可以在 SQL 代理层实现类似 MySQL Query Cache 的效果
-- 但设计更合理，支持按规则控制

-- 配置 ProxySQL 查询缓存：
-- 连接到 ProxySQL 管理端（6032）：

-- 为特定查询启用缓存：
INSERT INTO mysql_query_rules
    (rule_id, active, match_digest, cache_ttl, apply)
VALUES
    (100, 1, '^SELECT.*FROM products WHERE id', 60000, 1);
-- cache_ttl = 60000 毫秒（60 秒）
-- 匹配的 SELECT 查询结果会被缓存 60 秒

-- 设置缓存大小限制：
UPDATE global_variables
SET variable_value = '256'
WHERE variable_name = 'mysql-query_cache_size_MB';

-- 应用配置：
LOAD MYSQL QUERY RULES TO RUNTIME;
SAVE MYSQL QUERY RULES TO DISK;
LOAD MYSQL VARIABLES TO RUNTIME;
SAVE MYSQL VARIABLES TO DISK;

-- 查看缓存命中情况：
SELECT digest_text, count_star, sum_time,
    cache_ttl, hostgroup
FROM stats_mysql_query_digest
WHERE cache_ttl > 0
ORDER BY count_star DESC;
```

## 替代方案三：InnoDB Buffer Pool 优化

```
虽然不是直接的查询缓存替代
但优化 Buffer Pool 可以达到类似的效果

原理：
  InnoDB Buffer Pool 缓存数据页和索引页
  热点数据常驻内存
  重复查询相同数据时不需要读磁盘
  虽然仍需执行 SQL 解析和执行
  但磁盘 I/O 是大部分查询的主要瓶颈

优化措施：
  1. 增大 innodb_buffer_pool_size（尽量覆盖热点数据）
  2. 监控 Buffer Pool 命中率（目标 > 99%）
  3. 使用 innodb_buffer_pool_dump_at_shutdown = ON
     innodb_buffer_pool_load_at_startup = ON
     重启后自动恢复 Buffer Pool 内容（预热）
```

## 各替代方案对比

| 方案 | 缓存位置 | 失效控制 | 性能 | 实现复杂度 | 适用场景 |
|-----|:-------:|:-------:|:---:|:--------:|:-------:|
| Redis/Memcached | 独立服务 | 精确控制 | 极高 | 中 | 通用，最推荐 |
| ProxySQL Cache | SQL 代理层 | TTL 控制 | 高 | 低 | 已使用 ProxySQL |
| Buffer Pool 优化 | MySQL 内部 | 自动（LRU）| 中 | 低 | 所有场景 |
| 应用内存缓存 | 应用进程 | 精确控制 | 极高 | 低 | 单实例简单场景 |
| MySQL 物化视图 | MySQL 表 | 手动刷新 | 中 | 中 | 复杂聚合查询 |

## 适用场景

- **从旧版本升级到 MySQL 8.0/8.4 的系统**：原来依赖 Query Cache 的应用需要迁移到 Redis/Memcached 或 ProxySQL 缓存方案
- **需要查询结果缓存的读密集型应用**：使用 Redis 的 Cache-Aside 模式缓存热点查询结果，比 MySQL 原生 Query Cache 效果好得多

## 常见问题

**升级到 MySQL 8.0/8.4 后 my.cnf 中的 query_cache 参数会导致启动失败吗？**

在 MySQL 8.0 中，如果 my.cnf 中包含 `query_cache_type` 或 `query_cache_size` 等已移除的参数，MySQL 会在启动时报错并拒绝启动（unknown variable）。升级前必须从 my.cnf 中删除所有 `query_cache_*` 相关参数。另外，如果应用代码中使用了 `SELECT SQL_CACHE ...` 语法，`SQL_CACHE` 关键字在 8.0 中已被移除，需要从 SQL 语句中删除该修饰符。`SQL_NO_CACHE` 虽然还可以使用但已无效果，也建议删除。

---

## 注意事项

- 从 MySQL Query Cache 迁移到 Redis 缓存时，需要在应用层处理缓存一致性问题。最常见的问题是"缓存与数据库不一致"：数据库更新了但缓存还是旧数据。推荐使用"先更新数据库，再删除缓存"的策略（Cache-Aside 的写入模式），配合 TTL 作为兜底（即使删除缓存失败，TTL 过期后也会刷新）。
- ProxySQL 的查询缓存功能相比 Redis 方案更简单（不需要修改应用代码），但灵活性较低：只能基于 SQL 文本匹配和 TTL 控制缓存，无法根据业务逻辑精确控制失效。适合作为快速替代方案，但长期来看 Redis 方案更灵活。

---

## 总结

MySQL Query Cache 在 8.0 中被完全移除，原因是高失效率、全局锁瓶颈和内存碎片。所有 `query_cache_*` 参数和状态变量已删除。替代方案：①Redis/Memcached 应用层缓存（最推荐，Cache-Aside 模式）；②ProxySQL 查询缓存（不需改代码，TTL 控制）；③优化 Buffer Pool（数据页缓存，减少 I/O）。升级前必须从 my.cnf 中移除旧参数。从 SQL 中移除 `SQL_CACHE` 关键字。Redis 方案需处理缓存一致性（先更新 DB，再删除缓存 + TTL 兜底）。

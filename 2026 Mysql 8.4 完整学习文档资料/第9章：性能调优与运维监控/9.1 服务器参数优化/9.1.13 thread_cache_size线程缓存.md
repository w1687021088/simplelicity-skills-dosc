# thread_cache_size 线程缓存

`thread_cache_size` 控制 MySQL 在线程缓存中保留多少个空闲线程以供复用。当客户端断开连接时，对应的线程不会立即销毁，而是放入线程缓存中。当有新连接到来时，MySQL 优先从缓存中取出一个线程来服务，而不是创建新线程。线程的创建和销毁是有成本的（需要分配和释放内存、线程栈等），通过缓存复用线程可以减少这些开销，特别是在连接建立和断开频繁的场景中效果明显。

---

## 参数说明

```sql
-- 查看当前值：
SHOW VARIABLES LIKE 'thread_cache_size';
-- 默认值：自动计算 = 8 + (max_connections / 100)，上限 100
-- 取值范围：0 ~ 16384

-- 在线动态修改：
SET GLOBAL thread_cache_size = 64;

-- 在 my.cnf 中配置：
-- [mysqld]
-- thread_cache_size = 64

-- 查看线程缓存相关状态：
SHOW STATUS LIKE 'Threads%';
-- Threads_cached：当前线程缓存中的空闲线程数
-- Threads_connected：当前已建立的连接数
-- Threads_created：自启动以来创建的总线程数
-- Threads_running：当前正在执行查询的线程数
```

---

## 线程缓存的工作流程

```
新连接到来时：
  1. 检查线程缓存中是否有空闲线程
  2. 如果有 → 从缓存取出一个线程（快速，无需创建）
  3. 如果没有 → 创建新线程（较慢，需要分配资源）

连接断开时：
  1. 检查线程缓存中的线程数是否 < thread_cache_size
  2. 如果 < → 将线程放入缓存（复用）
  3. 如果 >= → 销毁线程（释放资源）

thread_cache_size = 0 时：
  禁用线程缓存
  每次连接都创建新线程，断开都销毁
  开销最大，不推荐

thread_cache_size 足够大时：
  几乎所有连接都能复用缓存中的线程
  Threads_created 增长缓慢
  连接建立速度更快
```

## 判断是否需要调整

```sql
-- 计算线程缓存的命中率：
SELECT
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Threads_created') AS threads_created,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Connections') AS total_connections;

-- 缓存未命中率 = Threads_created / Connections
-- 例如 Threads_created = 500, Connections = 100000
-- 未命中率 = 500 / 100000 = 0.5%（很好）

-- 参考标准：
-- 未命中率 < 1%：线程缓存足够大，不需要调整
-- 未命中率 1%~5%：可以适当增大 thread_cache_size
-- 未命中率 > 5%：需要增大 thread_cache_size

-- 查看当前缓存利用情况：
SHOW STATUS LIKE 'Threads_cached';
-- 如果 Threads_cached 经常为 0，说明缓存不够用
-- 如果 Threads_cached 接近 thread_cache_size，说明缓存足够
```

## 设置建议

```
根据连接模式设置：

长连接模式（连接池、持久连接）：
  连接建立后长时间保持，很少断开重连
  thread_cache_size 的重要性较低
  默认值通常足够
  设为 16~32 即可

短连接模式（PHP 等每次请求新建连接）：
  连接频繁建立和断开
  thread_cache_size 非常重要
  建议设置 64~128
  甚至可以设为 max_connections / 2

混合模式：
  thread_cache_size = 32~64

计算方法：
  观察运行一段时间后的 Threads_created 增长速度
  如果每秒创建 > 10 个线程，增大 thread_cache_size
  直到 Threads_created 增长速度降至接近 0
```

## 适用场景

- **PHP 等短连接应用**：PHP 的默认 MySQL 连接模式是短连接（每个 HTTP 请求建立连接，请求结束断开），增大 `thread_cache_size` 可以避免频繁创建和销毁线程的开销
- **高连接频率的微服务架构**：多个微服务频繁建立和释放连接，线程缓存可以显著降低连接建立的延迟

## 常见问题

**thread_cache_size 设置得很大会浪费很多内存吗？**

不会造成太大浪费。缓存中的空闲线程只保留线程的基本数据结构和线程栈（`thread_stack`，默认 1MB），不会分配 `sort_buffer_size`、`join_buffer_size` 等会话级缓冲。所以 `thread_cache_size=100` 最多占用 100MB 左右的内存（100 个线程栈），对于几十 GB 内存的服务器来说可以忽略。实际中缓存中的线程数取决于连接的断开频率，不一定会达到 `thread_cache_size` 的上限。

---

## 注意事项

- 如果应用层已经使用了连接池（如 Java 的 HikariCP、Druid，或 ProxySQL 作为连接池代理），连接池会维持固定数量的长连接，很少断开和重建。在这种情况下 `thread_cache_size` 的作用很小，保持默认值即可。连接池本身就是更好的"线程复用"方案。
- `thread_cache_size` 的默认自动计算公式（`8 + max_connections/100`，上限 100）对大多数场景已经足够。只有在监控发现 `Threads_created` 快速增长（每秒 > 10）时才需要手动调整。

---

## 总结

`thread_cache_size` 控制空闲线程的缓存数量，避免频繁创建和销毁线程的开销。默认值 = `8 + max_connections/100`（上限 100）。通过 `Threads_created / Connections` 计算未命中率（< 1% 为佳）。短连接模式建议 64~128，长连接（连接池）模式默认值足够。缓存的内存开销很小（每线程约 1MB 线程栈）。支持在线修改。如果应用使用连接池，线程缓存的重要性大幅降低。

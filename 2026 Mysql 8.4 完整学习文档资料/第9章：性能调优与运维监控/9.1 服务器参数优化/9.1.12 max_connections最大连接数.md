# max_connections 最大连接数

`max_connections` 控制 MySQL 服务器允许的最大客户端连接数。当已建立的连接数达到此限制时，新的连接请求会收到 `Too many connections` 错误（错误码 1040）。MySQL 实际允许 `max_connections + 1` 个连接，额外的一个连接保留给拥有 `CONNECTION_ADMIN` 权限的管理员账号，确保在连接满时管理员仍然可以登录排查问题。

---

## 参数说明

```sql
-- 查看当前最大连接数：
SHOW VARIABLES LIKE 'max_connections';
-- 默认值：151
-- 取值范围：1 ~ 100000

-- 在线动态修改：
SET GLOBAL max_connections = 500;

-- 在 my.cnf 中配置：
-- [mysqld]
-- max_connections = 500

-- 查看历史最大连接数（自启动以来）：
SHOW STATUS LIKE 'Max_used_connections';
-- 如果该值接近或等于 max_connections，说明曾经触及上限

-- 查看当前活跃连接数：
SHOW STATUS LIKE 'Threads_connected';
-- 当前已建立的连接数（包括空闲连接）

SHOW STATUS LIKE 'Threads_running';
-- 当前正在执行查询的线程数（活跃线程）
```

## 连接数的计算

```
max_connections 的合理值取决于多个因素：

因素1：可用内存
  每个连接占用的内存 ≈ 线程栈(thread_stack) + 各种会话缓冲
  thread_stack: 默认 1MB（MySQL 8.4 为 1MB）
  sort_buffer_size: 默认 256KB（按需分配）
  join_buffer_size: 默认 256KB（按需分配）
  read_buffer_size: 默认 128KB
  read_rnd_buffer_size: 默认 256KB
  tmp_table_size: 默认 16MB（按需分配）
  net_buffer_length: 默认 16KB
  
  保守估计：每个连接 4~10MB（大多数连接空闲时占用很少）
  活跃连接：可能 10~50MB（取决于查询复杂度和临时表）

因素2：操作系统文件描述符限制
  每个连接需要一个文件描述符
  Linux 默认 open_files_limit 可能为 1024 或 65535
  MySQL 启动时会自动尝试增大 open_files_limit
  可以用 SHOW VARIABLES LIKE 'open_files_limit' 查看

因素3：实际业务需求
  Web 应用：连接池通常 20~50 个连接/实例
  微服务架构：多个服务各有连接池，总连接数 = 实例数 × 每实例连接池大小
  
粗略计算：
  可用内存 = 总内存 - buffer_pool_size - OS预留(2G) - 其他缓冲
  max_connections ≈ 可用内存 / 每连接内存估计
  
示例：64GB 服务器，buffer_pool_size=48G
  可用 = 64G - 48G - 2G - 2G = 12G
  保守估计每连接 10MB：max_connections ≈ 1200
  实际设置 500~1000（留安全余量）
```

## 连接数监控

```sql
-- 综合监控查询：
SELECT
    @@max_connections AS max_conn,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Threads_connected') AS current_conn,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Max_used_connections') AS peak_conn,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Threads_running') AS active_threads,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Aborted_connects') AS aborted_conn;

-- 查看每个用户/主机的连接数：
SELECT user, host, COUNT(*) AS conn_count
FROM information_schema.processlist
GROUP BY user, host
ORDER BY conn_count DESC;

-- 查看连接状态分布：
SELECT command, COUNT(*) AS count
FROM information_schema.processlist
GROUP BY command
ORDER BY count DESC;
-- 常见状态：
-- Sleep：空闲连接（已连接但没有执行查询）
-- Query：正在执行查询
-- Connect：正在建立连接

-- 告警阈值建议：
-- Threads_connected / max_connections > 80%：警告
-- Threads_connected / max_connections > 90%：严重告警
-- Max_used_connections = max_connections：紧急（已触及上限）
```

## 管理员保留连接

```sql
-- MySQL 允许 max_connections + 1 个连接
-- 第 max_connections + 1 个连接保留给 CONNECTION_ADMIN 权限的用户

-- 授予管理员 CONNECTION_ADMIN 权限：
GRANT CONNECTION_ADMIN ON *.* TO 'admin'@'%';

-- MySQL 8.0.14+ 支持专用管理端口：
-- [mysqld]
-- admin_address = 127.0.0.1
-- admin_port = 33062
-- 管理员可以通过 33062 端口连接，不受 max_connections 限制

-- 连接到管理端口：
-- mysql -u admin -p -h 127.0.0.1 -P 33062
```

## 连接数过多的处理

```sql
-- 当出现 Too many connections 错误时的处理步骤：

-- 步骤1：通过管理端口或保留连接登录
-- mysql -u admin -p -h 127.0.0.1 -P 33062

-- 步骤2：查看连接状态，找出问题
SELECT id, user, host, db, command, time, state
FROM information_schema.processlist
WHERE command != 'Daemon'
ORDER BY time DESC
LIMIT 50;

-- 步骤3：清理长时间空闲的连接
-- 找出空闲超过 300 秒的连接：
SELECT id, user, host, time
FROM information_schema.processlist
WHERE command = 'Sleep' AND time > 300;

-- 杀掉空闲连接（逐个杀）：
KILL 12345;

-- 步骤4：临时增大 max_connections
SET GLOBAL max_connections = 1000;

-- 步骤5：设置空闲连接超时自动断开
SET GLOBAL wait_timeout = 300;          -- 非交互连接 5 分钟超时
SET GLOBAL interactive_timeout = 600;   -- 交互连接 10 分钟超时
```

## 适用场景

- **Web 应用和微服务架构的连接管理**：根据应用服务器的数量和每个服务器的连接池大小，计算所需的总连接数，设置合理的 `max_connections` 值
- **突发高并发场景**：在促销活动或流量高峰时，连接数可能突增，需要提前增大 `max_connections` 并确保服务器内存足够

## 常见问题

**max_connections 设置为 10000 但实际只能建立几百个连接，为什么？**

可能是操作系统的文件描述符限制。每个 MySQL 连接需要一个文件描述符，加上打开的表文件也需要文件描述符。Linux 默认的用户级文件描述符限制可能只有 1024。需要检查 `ulimit -n` 和 MySQL 的 `open_files_limit`（`SHOW VARIABLES LIKE 'open_files_limit'`）。解决方法：在 `/etc/security/limits.conf` 中增大 `nofile` 限制，或在 systemd 的 MySQL 服务配置中设置 `LimitNOFILE=65535`。

---

## 注意事项

- 不要盲目将 `max_connections` 设得过大。每个连接即使空闲也会占用少量内存（线程栈等），大量空闲连接会浪费内存资源。更好的做法是在应用层使用连接池（如 HikariCP、Druid），控制每个应用实例的连接池大小，从源头限制总连接数。
- `wait_timeout` 和 `interactive_timeout` 控制空闲连接的自动断开时间。默认 `wait_timeout=28800`（8小时），在高并发场景中过长。建议缩短为 300~600 秒，及时释放不再使用的连接。但不要设得过短（如 30 秒），否则应用的连接池可能因为连接频繁被断开而不停重建连接。

## 总结

`max_connections` 控制最大客户端连接数，默认 151。MySQL 额外保留 1 个连接给 `CONNECTION_ADMIN` 用户。通过 `Max_used_connections` 监控历史峰值，据此调整。连接数受内存和文件描述符限制。每连接约 4~10MB 内存。使用 `wait_timeout` 控制空闲连接超时。应用层使用连接池控制总连接数。MySQL 8.0.14+ 支持专用管理端口（`admin_port`）。连接满时通过管理端口登录排查。告警阈值：80% 警告、90% 严重。

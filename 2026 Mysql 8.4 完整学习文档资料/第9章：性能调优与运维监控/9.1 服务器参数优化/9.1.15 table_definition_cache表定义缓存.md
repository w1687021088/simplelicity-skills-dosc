# table_definition_cache 表定义缓存

`table_definition_cache` 控制 MySQL 可以缓存多少张表的定义信息（表结构、列信息、索引元数据等）。与 `table_open_cache` 不同，表定义缓存是所有线程共享的，且不消耗文件描述符。每张表只需要一份定义信息，无论有多少线程在访问它。表定义缓存可以加速表的打开过程，特别是在数据库中有大量表的场景下效果显著。

---

## 参数说明

```sql
-- 查看当前值：
SHOW VARIABLES LIKE 'table_definition_cache';
-- 默认值：MIN(400 + table_open_cache / 2, 2000)
-- 最小值：400
-- 上限默认封顶 2000

-- 在线动态修改：
SET GLOBAL table_definition_cache = 4000;

-- 在 my.cnf 中配置：
-- [mysqld]
-- table_definition_cache = 4000

-- 查看与表定义缓存相关的状态：
SHOW STATUS LIKE 'Open_table_definitions';
-- 当前缓存中的表定义数量

SHOW STATUS LIKE 'Opened_table_definitions';
-- 自启动以来打开表定义的总次数
-- 如果增长很快，说明缓存不够
```

---

## 与 table_open_cache 的区别

| 对比维度 | table_open_cache | table_definition_cache |
|---------|:---------------:|:---------------------:|
| 缓存内容 | 表的打开实例（文件句柄等）| 表的定义（结构元数据）|
| 共享方式 | 每线程独立 | 所有线程共享 |
| 文件描述符 | 消耗 | 不消耗 |
| 内存占用 | 较大 | 较小 |
| 同一表多线程 | 每线程各占一个实例 | 只需一份定义 |
| 默认值 | 自动计算（通常 2000~4000）| MIN(400 + table_open_cache/2, 2000) |

## 在 InnoDB 中的作用

```
table_definition_cache 在 InnoDB 中有双重角色：

1. 表定义缓存
   缓存 InnoDB 表的元数据（列定义、索引结构等）
   来源于数据字典（Data Dictionary）
   缓存后不需要每次都从数据字典读取

2. 表空间文件打开数量的软限制
   InnoDB 的 file-per-table 模式下每张表一个 .ibd 文件
   table_definition_cache 限制同时打开的 .ibd 文件数
   与 innodb_open_files 取较大值生效

   如果同时设置了 table_definition_cache 和 innodb_open_files：
     实际限制 = MAX(table_definition_cache, innodb_open_files)
   如果都没设置：
     使用 table_definition_cache 的默认值

3. 数据字典对象缓存（Dictionary Object Cache）
   MySQL 8.0 的数据字典使用独立的对象缓存
   table_definition_cache 是表定义分区的大小限制
   超出限制时使用 LRU 策略淘汰
   有外键关联的表不会被淘汰（始终保留在缓存中）
```

## 设置建议

```
根据数据库中的表数量设置：

表数量 < 500：
  默认值（通常 2000）完全足够
  无需手动调整

表数量 500~2000：
  设为 2000~3000
  确保大部分表定义可以常驻缓存

表数量 2000~10000（多租户 SaaS 等）：
  设为表数量的 1.5 倍
  例如 5000 张表 → table_definition_cache = 7500

表数量 > 10000：
  设为表数量的 1.2 倍
  但需要评估内存消耗（每个表定义约 1~5KB）
  10000 张表 ≈ 10~50MB 内存

监控判断：
  如果 Opened_table_definitions 持续增长
  且增长速度 > 每秒 5 次
  需要增大 table_definition_cache
```

## 适用场景

- **数据库中有大量表的环境**：如电商平台每个店铺独立建表、SaaS 多租户每个租户一组表，总表数可达数千甚至数万，合理设置 `table_definition_cache` 避免频繁从数据字典加载表定义
- **频繁执行 DDL 操作的开发环境**：频繁的 CREATE TABLE、ALTER TABLE 操作会导致表定义缓存频繁刷新，适当增大缓存可以减少元数据重新加载的开销

---

## 常见问题

**table_definition_cache 设置得比实际表数量大很多会有什么问题？**

不会有明显问题。表定义缓存是按需填充的——只有被访问过的表才会被加入缓存。如果数据库有 1000 张表但 `table_definition_cache=10000`，缓存中最多也只有 1000 个表定义，多余的容量不会被使用，也不会预分配内存。每个表定义占用的内存很小（约 1~5KB），即使设为 10000 也只占用几十 MB，对于现代服务器完全可以忽略。所以如果不确定合适的值，设得偏大是安全的。

---

## 注意事项

- 在 MySQL 8.0+ 的数据字典架构中，表定义存储在 InnoDB 系统表空间（`mysql.ibd`）中，不再使用 `.frm` 文件。`table_definition_cache` 缓存的是数据字典中的表定义对象。缓存命中时直接从内存获取，缓存未命中时需要从 InnoDB 系统表空间读取，涉及磁盘 I/O。
- 有外键关联的表在 `table_definition_cache` 中不会被 LRU 淘汰。如果数据库中大量表之间有外键关系，这些表会常驻缓存，挤占其他表的缓存空间。在有大量外键的数据库中，可能需要额外增大 `table_definition_cache`。

---

## 总结

`table_definition_cache` 控制缓存表定义（元数据）的数量，所有线程共享，不消耗文件描述符，内存占用小。默认值 `MIN(400 + table_open_cache/2, 2000)`。与 `table_open_cache` 的区别：前者缓存共享的表定义，后者缓存每线程的打开实例。在 InnoDB 中还作为 `.ibd` 文件打开数的软限制。通过 `Opened_table_definitions` 增长速度判断是否需要增大。设置偏大无害。有外键的表常驻缓存不被淘汰。根据表数量设为 1.2~1.5 倍。

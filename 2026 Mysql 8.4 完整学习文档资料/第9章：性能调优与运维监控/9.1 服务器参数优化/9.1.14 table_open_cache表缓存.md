# table_open_cache 表缓存

`table_open_cache` 控制 MySQL 服务器可以同时打开的表文件句柄数量。每当一个线程访问一张表时，MySQL 需要打开该表的文件句柄（.ibd 文件、.frm 文件等）。如果表已经在缓存中，直接使用缓存中的句柄；如果不在缓存中，需要重新打开文件。频繁打开和关闭表文件会消耗系统资源，合理设置 `table_open_cache` 可以减少文件打开的开销。

---

## 参数说明

```sql
-- 查看当前值：
SHOW VARIABLES LIKE 'table_open_cache';
-- 默认值：自动计算 = MAX((open_files_limit - 10 - max_connections) / 2, 400)
-- 通常在 2000~4000 之间
-- 取值范围：1 ~ 524288

-- 在线动态修改：
SET GLOBAL table_open_cache = 4000;

-- 在 my.cnf 中配置：
-- [mysqld]
-- table_open_cache = 4000

-- 查看当前打开的表数量：
SHOW STATUS LIKE 'Open_tables';
-- 当前打开的表数量

SHOW STATUS LIKE 'Opened_tables';
-- 自启动以来打开表的总次数
-- 如果该值增长很快，说明 table_open_cache 太小
```

## 表缓存的工作机制

```
MySQL 表缓存的原理：

每个线程独立打开表：
  如果 10 个线程同时访问同一张表 t1
  缓存中需要 10 个 t1 的打开实例
  每个实例有自己的文件描述符和缓冲区

缓存满时的行为：
  1. 当需要打开新表但缓存已满
  2. MySQL 使用 FIFO（先进先出）策略
  3. 关闭最早不再使用的表
  4. 打开新表放入缓存

所需的 table_open_cache 估算：
  table_open_cache ≈ max_connections × 平均每连接访问的表数
  
  例如：
    max_connections = 200
    每个查询平均涉及 5 张表
    table_open_cache ≈ 200 × 5 = 1000
    建议设为 2000（留余量）

文件描述符关系：
  每个打开的表需要 1~2 个文件描述符
  open_files_limit 必须大于 table_open_cache + max_connections + 其他
  如果 open_files_limit 不够，table_open_cache 无法生效
```

## 判断是否需要调整

```sql
-- 方法1：检查 Opened_tables 增长速度
SHOW STATUS LIKE 'Opened_tables';
-- 间隔一段时间再查一次
-- 如果 Opened_tables 每秒增长 > 10，说明缓存不够

-- 方法2：计算缓存命中率
SELECT
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Open_tables') AS open_tables,
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Opened_tables') AS opened_tables,
    @@table_open_cache AS cache_size;

-- 方法3：查看当前打开的表
SHOW OPEN TABLES FROM mydb;
-- 显示指定数据库中当前打开的表

-- 方法4：如果 Open_tables 接近 table_open_cache
-- 说明缓存使用率高，需要增大
```

## 与 table_open_cache_instances 配合

```sql
-- MySQL 5.6.6+ 支持 table_open_cache_instances
SHOW VARIABLES LIKE 'table_open_cache_instances';
-- 默认值：16
-- 取值范围：1 ~ 64

-- 作用：将表缓存拆分为多个实例
-- 减少并发访问时的互斥锁竞争
-- 类似于 innodb_buffer_pool_instances 的思路

-- 每个实例的容量 = table_open_cache / table_open_cache_instances
-- 例如 table_open_cache=4000, instances=16
-- 每个实例容量 = 250

-- 在 my.cnf 中配置：
-- [mysqld]
-- table_open_cache = 4000
-- table_open_cache_instances = 16
```

## 适用场景

- **数据库中有大量表的场景**：如 SaaS 多租户架构中每个租户有独立的表集合，总表数可能达到数千到数万张，需要较大的 `table_open_cache` 避免频繁开关表文件
- **高并发短查询场景**：大量连接频繁访问不同的表，如果缓存太小，每次查询都需要重新打开表文件，增加文件系统的 open/close 系统调用开销

---

## 常见问题

**table_open_cache 和 table_definition_cache 有什么区别？**

`table_open_cache` 缓存的是表的"打开实例"（包括文件描述符、缓冲区等），每个线程对每张表都需要一个独立的打开实例。`table_definition_cache` 缓存的是表的"定义信息"（表结构、列信息、索引信息等），是所有线程共享的。一张表只需要一份定义信息，但可能有多个打开实例（多个线程同时访问同一张表）。`table_definition_cache` 占用内存更少且不消耗文件描述符。两者需要同时合理配置。

---

## 注意事项

- `table_open_cache` 的有效值受 `open_files_limit` 限制。如果操作系统的文件描述符限制（`ulimit -n`）太小，MySQL 无法打开足够多的表文件。需要确保 `open_files_limit` >= `table_open_cache × 2 + max_connections + 安全余量`。可以在 systemd 的 MySQL 服务配置文件中设置 `LimitNOFILE=65535`。
- 执行 `FLUSH TABLES` 会关闭所有打开的表并清空表缓存。在繁忙的服务器上执行 `FLUSH TABLES` 会导致短暂的性能下降，因为所有后续的表访问都需要重新打开文件。避免在高峰期执行 `FLUSH TABLES`。

---

## 总结

`table_open_cache` 控制可同时打开的表文件句柄数量。默认自动计算（通常 2000~4000）。每个线程对每张表需要独立的打开实例。通过 `Opened_tables` 增长速度判断是否需要增大（每秒 > 10 需增大）。估算：`max_connections × 平均涉及表数`。受 `open_files_limit` 限制。`table_open_cache_instances`（默认 16）将缓存拆分为多个实例减少锁竞争。与 `table_definition_cache` 区别：前者缓存打开实例（消耗文件描述符），后者缓存表定义（共享、轻量）。

# 增量备份 Incremental Backup

增量备份（Incremental Backup）是指每次备份只包含自上一次备份（全量或增量）以来发生变化的数据。与全量备份相比，增量备份的数据量更小、备份速度更快、占用的存储空间更少。但恢复时需要按顺序依次应用全量备份和所有增量备份，恢复过程相对复杂。增量备份是大型数据库备份策略的重要组成部分。

---

## 增量备份的原理

```
增量备份的工作原理：

全量备份（周日凌晨）：
  备份全部数据 → 备份集 F0（50GB）

增量备份1（周一凌晨）：
  只备份周日→周一之间变化的数据 → 备份集 I1（2GB）

增量备份2（周二凌晨）：
  只备份周一→周二之间变化的数据 → 备份集 I2（3GB）

增量备份3（周三凌晨）：
  只备份周二→周三之间变化的数据 → 备份集 I3（1.5GB）

恢复（周三下午发生故障）：
  步骤1：恢复全量备份 F0
  步骤2：应用增量备份 I1
  步骤3：应用增量备份 I2
  步骤4：应用增量备份 I3
  步骤5：应用 binlog（I3 之后到故障时刻）
  → 数据恢复到故障前的状态

优势：
  备份总大小：50 + 2 + 3 + 1.5 = 56.5GB
  如果每天全量备份：50 × 4 = 200GB
  节省存储空间：约 72%

劣势：
  恢复需要按顺序应用所有增量备份
  任何一个增量备份损坏 → 后续的增量备份都无法使用
  恢复时间比全量备份长（需要多次应用）
```

## 物理增量备份（XtraBackup）

```bash
# 步骤1：首先执行全量备份（作为基础）
xtrabackup --backup --target-dir=/backup/full \
    --user=root --password=xxx

# 步骤2：基于全量备份执行第一次增量备份
xtrabackup --backup --target-dir=/backup/inc1 \
    --incremental-basedir=/backup/full \
    --user=root --password=xxx
# --incremental-basedir 指向上一次备份的目录
# XtraBackup 会比较 LSN（Log Sequence Number）
# 只备份 LSN 大于基础备份的数据页

# 步骤3：基于第一次增量执行第二次增量备份
xtrabackup --backup --target-dir=/backup/inc2 \
    --incremental-basedir=/backup/inc1 \
    --user=root --password=xxx

# 恢复增量备份：
# 1. Prepare 全量备份（不回滚未提交事务）
xtrabackup --prepare --apply-log-only --target-dir=/backup/full

# 2. 应用第一个增量备份
xtrabackup --prepare --apply-log-only --target-dir=/backup/full \
    --incremental-dir=/backup/inc1

# 3. 应用第二个增量备份（最后一个不用 --apply-log-only）
xtrabackup --prepare --target-dir=/backup/full \
    --incremental-dir=/backup/inc2

# 4. 恢复数据
# systemctl stop mysqld
# rm -rf /var/lib/mysql/*
xtrabackup --copy-back --target-dir=/backup/full
# chown -R mysql:mysql /var/lib/mysql
# systemctl start mysqld
```

## 逻辑增量备份（基于 binlog）

```bash
# MySQL 的逻辑备份工具（mysqldump）本身不直接支持增量备份
# 但可以通过 Binary Log 实现逻辑增量备份

# 步骤1：全量逻辑备份（记录 binlog 位置）
mysqldump -u root -p --all-databases --single-transaction \
    --source-data=2 --flush-logs > full_backup.sql
# --source-data=2 记录备份时的 binlog 文件名和位置
# --flush-logs 刷新 binlog，从新的 binlog 文件开始记录

# 步骤2：备份新产生的 binlog 文件（即增量数据）
# 假设全量备份时 binlog 位置是 mysql-bin.000010
# 之后产生了 mysql-bin.000011, mysql-bin.000012

# 复制增量的 binlog 文件到备份目录：
# cp /var/lib/mysql/mysql-bin.000011 /backup/binlog/
# cp /var/lib/mysql/mysql-bin.000012 /backup/binlog/

# 恢复：
# 1. 恢复全量备份
# mysql -u root -p < full_backup.sql
# 2. 应用增量 binlog
# mysqlbinlog /backup/binlog/mysql-bin.000011 \
#     /backup/binlog/mysql-bin.000012 | mysql -u root -p
```

## 增量备份的 LSN 机制（XtraBackup）

```
XtraBackup 增量备份基于 InnoDB 的 LSN（Log Sequence Number）：

LSN 是 InnoDB 内部的递增序列号
每次数据修改都会增加 LSN
XtraBackup 在备份时记录当前的 LSN

全量备份结束时：LSN = 1000000
增量备份1时：
  扫描所有数据页
  只备份 LSN > 1000000 的页（即全量备份后修改过的页）
  增量备份1结束时：LSN = 1200000

增量备份2时：
  只备份 LSN > 1200000 的页
  增量备份2结束时：LSN = 1350000

查看备份的 LSN 信息：
  cat /backup/full/xtrabackup_checkpoints
  # backup_type = full-backuped
  # from_lsn = 0
  # to_lsn = 1000000
  # last_lsn = 1000000

  cat /backup/inc1/xtrabackup_checkpoints
  # backup_type = incremental
  # from_lsn = 1000000
  # to_lsn = 1200000
  # last_lsn = 1200000
```

## 增量备份 vs 差异备份

| 对比维度 | 增量备份 | 差异备份 |
|---------|:------:|:------:|
| 基准 | 上一次备份（全量或增量）| 最近一次全量备份 |
| 备份大小 | 最小 | 中等（随时间增长）|
| 备份速度 | 最快 | 快 |
| 恢复复杂度 | 高（需要所有增量）| 中（只需全量+最新差异）|
| 恢复速度 | 慢（多次应用）| 较快（两次应用）|
| 容错性 | 低（链式依赖）| 高（独立于其他差异）|

## 适用场景

- **大型数据库的日常备份**：数据量在 100GB 以上的数据库，每天执行全量备份耗时过长且占用大量存储空间。使用"每周全量 + 每天增量"的策略可以显著减少备份时间和存储成本
- **频繁变更的数据库**：数据变更量占总数据量比例较小的场景（如每天变更量 < 总量的 5%），增量备份的优势最明显

## 常见问题

**增量备份链中某个增量备份损坏了怎么办？**

如果增量备份链中的某个备份文件损坏或丢失，那么该备份之后的所有增量备份都无法使用——因为增量备份是链式依赖的，每个增量都基于上一个备份的 LSN。例如全量 → inc1 → inc2 → inc3 中，如果 inc2 损坏，inc3 也无法使用，只能恢复到 inc1 的时间点。然后通过 binlog 重放恢复后续的数据变更。为降低这一风险，建议：①每次增量备份后立即验证备份文件的完整性；②将备份文件存储在可靠的存储介质上（如 RAID、分布式存储）；③定期执行全量备份，缩短增量链的长度。

## 注意事项

- XtraBackup 的增量备份是基于数据页级别的（不是行级别），即使某个数据页中只有一行数据发生了变化，整个数据页（通常 16KB）都会被备份。因此增量备份的大小不完全等于实际变更的数据量，可能比预期稍大。
- 增量备份链的长度不宜过长。如果在两次全量备份之间有 30 个增量备份，恢复时需要依次应用 30 个增量，耗时很长且出错概率增加。建议增量链长度控制在 7 个以内（即每周执行一次全量备份）。

---

## 总结

增量备份每次只备份自上一次备份以来的变化数据，备份量小、速度快、节省存储。物理增量备份（XtraBackup）基于 InnoDB LSN 机制，只备份 LSN 变化的数据页。逻辑增量备份通过 binlog 实现。恢复时需按顺序应用全量 + 所有增量备份（链式依赖）。增量链中任一环节损坏会影响后续恢复。推荐策略：每周全量 + 每天增量，增量链不超过 7 个。适合大型数据库和数据变更比例较小的场景。

# 全量备份 Full Backup

全量备份（Full Backup）是指对数据库中所有数据进行完整的备份，每次备份都包含数据库在备份时刻的全部数据。全量备份是最基础、最简单的备份方式，也是增量备份和差异备份的基础——增量备份和差异备份都需要一个全量备份作为起点。无论使用逻辑备份（mysqldump）还是物理备份（XtraBackup），全量备份都是备份策略的核心组成部分。

---

## 逻辑全量备份（mysqldump）

```bash
# 全库全量备份：
mysqldump -u root -p --all-databases --single-transaction \
    --routines --triggers --events \
    --source-data=2 > full_backup_$(date +%Y%m%d).sql

# 参数说明：
# --all-databases：备份所有数据库
# --single-transaction：使用一致性快照（InnoDB），不锁表
# --routines：包含存储过程和函数
# --triggers：包含触发器（默认开启）
# --events：包含事件调度器的事件
# --source-data=2：记录 binlog 位置（注释形式）
#   MySQL 8.4 中 --master-data 已重命名为 --source-data

# 指定数据库的全量备份：
mysqldump -u root -p --databases mydb1 mydb2 \
    --single-transaction --source-data=2 > db_backup.sql

# 压缩备份（减少磁盘占用）：
mysqldump -u root -p --all-databases --single-transaction \
    | gzip > full_backup_$(date +%Y%m%d).sql.gz

# 恢复压缩的备份：
# gunzip < full_backup_20240615.sql.gz | mysql -u root -p
```

## 物理全量备份（XtraBackup）

```bash
# Percona XtraBackup 全量备份：
xtrabackup --backup --target-dir=/backup/full_20240615 \
    --user=root --password=xxx

# 备份完成后需要 prepare（应用 redo log）：
xtrabackup --prepare --target-dir=/backup/full_20240615

# 恢复：
# 1. 停止 MySQL
# systemctl stop mysqld
# 2. 清空数据目录
# rm -rf /var/lib/mysql/*
# 3. 拷贝备份文件
# xtrabackup --copy-back --target-dir=/backup/full_20240615
# 4. 修复权限
# chown -R mysql:mysql /var/lib/mysql
# 5. 启动 MySQL
# systemctl start mysqld

# MySQL Enterprise Backup（商业版）：
# mysqlbackup --user=root --password=xxx \
#     --backup-dir=/backup/full backup-and-apply-log
```

## 全量备份的频率规划

```
全量备份频率取决于以下因素：

1. 数据量大小
   - 小型数据库（< 10GB）：可以每天全量备份
   - 中型数据库（10~100GB）：每天或每周全量备份
   - 大型数据库（> 100GB）：每周全量备份 + 每天增量备份

2. 恢复时间目标（RTO）
   - RTO < 1小时：每天全量备份 + 频繁增量备份
   - RTO < 4小时：每天全量备份
   - RTO < 24小时：每周全量备份

3. 恢复点目标（RPO）
   - RPO = 0（不丢数据）：全量备份 + binlog 持续备份
   - RPO < 1小时：全量备份 + 频繁 binlog 备份
   - RPO < 24小时：每天全量备份

4. 存储空间
   - 全量备份占用空间大
   - 需要保留多份历史备份（如最近 7 天）
   - 总存储 = 数据量 × 保留份数
   - 50GB 数据 × 7 份 = 350GB 存储

常见策略组合：
  策略A：每天全量（简单，适合小库）
  策略B：每周全量 + 每天增量（节省空间和时间）
  策略C：每周全量 + 每天差异（恢复比增量快）
```

## 适用场景

- **小型数据库的日常备份**：数据量在 50GB 以下的数据库，每天执行全量备份是最简单有效的备份策略，不需要管理增量备份的依赖链
- **增量/差异备份的基础**：全量备份是增量备份和差异备份的起点。恢复时首先恢复最近的全量备份，再应用增量或差异备份

## 常见问题

**全量备份期间会影响在线业务吗？**

取决于备份方式和参数。逻辑备份（mysqldump）使用 `--single-transaction` 参数时，对 InnoDB 表不加锁，通过一致性快照读取数据，对在线业务影响很小（但会增加服务器的 CPU 和 I/O 负载）。对 MyISAM 表仍需要锁表。物理备份（XtraBackup）是热备工具，备份过程中不锁表（仅在备份 non-InnoDB 数据时短暂加锁），对在线业务影响最小。但无论哪种方式，大数据量的全量备份都会增加服务器的 I/O 负载，建议在低峰期执行。

---

## 注意事项

- 全量备份的恢复是**覆盖式**的——恢复时会用备份数据替换当前数据。如果需要保留备份时刻之后的数据变更，需要在恢复全量备份后，再通过 binlog 重放将数据恢复到指定时间点（PITR）。
- 全量备份文件应存储在与数据库服务器不同的物理位置（不同的磁盘、不同的服务器、异地存储）。如果备份文件和数据库在同一块磁盘上，磁盘故障时备份也会丢失，失去备份的意义。

## 总结

全量备份（Full Backup）每次备份数据库的全部数据，是最基础的备份方式。逻辑全量备份：`mysqldump --all-databases --single-transaction`。物理全量备份：`xtrabackup --backup`。频率规划：小库每天全量，大库每周全量 + 每天增量。备份后必须验证（检查文件完整性、测试恢复）。备份存储在独立的物理位置。全量备份是增量/差异备份的基础，也是 PITR 恢复的起点。使用 `--single-transaction`（逻辑）或热备工具（物理）减少对在线业务的影响。

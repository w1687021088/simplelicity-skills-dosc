# 温备份与锁表

温备份（Warm Backup）是介于热备份和冷备份之间的一种备份方式。温备份期间数据库保持运行状态，但会对部分或全部表施加锁定，限制写入操作（通常只允许读取）。这种方式在不停止数据库服务的前提下，通过锁表来保证备份数据的一致性。温备份常见于对 MyISAM 表的备份、mysqldump 不使用 `--single-transaction` 的场景、以及 XtraBackup 备份 non-InnoDB 数据时的短暂锁定。

---

## 温备份的典型场景

```sql
-- 场景1：mysqldump 备份 MyISAM 表（自动加锁）
-- mysqldump 在不使用 --single-transaction 时
-- 默认使用 --lock-tables 对每个数据库的所有表加读锁

-- mysqldump 的锁表参数：
-- --lock-tables（默认开启）：
--   逐个数据库加读锁（LOCK TABLES ... READ）
--   同一数据库内的表是一致的
--   不同数据库之间可能不一致

-- --lock-all-tables：
--   对所有数据库的所有表同时加全局读锁
--   所有表的数据在同一时刻一致
--   备份期间所有表都不能写入

-- 场景2：手动锁表备份
FLUSH TABLES WITH READ LOCK;
-- 所有表被刷新并加全局读锁
-- 此时可以安全地复制数据文件或执行备份
-- 备份完成后释放锁：
UNLOCK TABLES;

-- 场景3：XtraBackup 备份 non-InnoDB 数据
-- XtraBackup 在备份 InnoDB 数据时不加锁（热备份）
-- 但在备份 non-InnoDB 数据时会短暂加全局锁：
-- FLUSH TABLES WITH READ LOCK → 复制 non-InnoDB 文件 → UNLOCK TABLES
-- 锁定时间通常很短（秒级到分钟级）
```

---

## FLUSH TABLES WITH READ LOCK 详解

```sql
-- FLUSH TABLES WITH READ LOCK（FTWRL）是温备份的核心操作

-- 执行过程：
-- 1. 等待所有正在执行的写操作完成
-- 2. 关闭所有打开的表
-- 3. 对所有表施加全局读锁
-- 4. 在锁释放之前，不允许任何写操作

-- 影响：
-- 所有 INSERT/UPDATE/DELETE/DDL 操作被阻塞
-- SELECT 查询正常执行
-- 新的写请求在队列中等待

-- 注意事项：
-- 1. 如果有长时间运行的查询，FTWRL 会等待它完成
SHOW PROCESSLIST;
-- 检查是否有长查询可能导致 FTWRL 等待过长

-- 2. FTWRL 锁是会话级别的
-- 执行 FTWRL 的连接断开 → 锁自动释放
-- 不要在脚本中执行完 FTWRL 后关闭连接再复制文件

-- 3. FTWRL 的正确使用模式：
-- 在同一个连接中执行：
FLUSH TABLES WITH READ LOCK;
-- 然后在另一个终端/脚本中复制数据文件
-- 复制完成后回到此连接释放锁：
UNLOCK TABLES;

-- 4. 获取 binlog 位置（配合 FTWRL）：
FLUSH TABLES WITH READ LOCK;
SHOW BINARY LOG STATUS;
-- 记录 File 和 Position
-- 执行备份...
UNLOCK TABLES;
```

## --lock-tables vs --single-transaction vs --lock-all-tables

| 参数 | 锁类型 | 影响范围 | 一致性级别 | 适用引擎 |
|-----|:-----:|:------:|:--------:|:------:|
| --lock-tables | 逐库读锁 | 单库内一致 | 库级一致 | MyISAM |
| --lock-all-tables | 全局读锁 | 所有表 | 全局一致 | 所有引擎 |
| --single-transaction | 无锁（MVCC）| 无阻塞 | 全局一致 | InnoDB |

```bash
# 纯 InnoDB 环境（推荐，不锁表）：
mysqldump --single-transaction --all-databases > backup.sql

# 混合引擎环境（MyISAM + InnoDB）：
mysqldump --lock-all-tables --all-databases > backup.sql
# 备份期间所有写操作被阻塞

# 只有 MyISAM 表（默认行为）：
mysqldump --lock-tables --all-databases > backup.sql
# 逐库加锁，不同库之间可能不一致
```

## 温备份的锁等待问题

```sql
-- 温备份中常见的锁等待问题：

-- 问题1：FTWRL 等待长查询
-- 如果有一个运行了 30 分钟的 SELECT 查询
-- FTWRL 需要等待它完成才能获取全局锁
-- 在等待期间，后续的所有写操作也被阻塞

-- 诊断：
SHOW PROCESSLIST;
-- 查看 State 列是否有 "Waiting for table flush"

-- 解决：
-- 1. 在执行 FTWRL 前检查长查询并终止
SELECT * FROM information_schema.PROCESSLIST
WHERE COMMAND != 'Sleep' AND TIME > 300;
-- KILL process_id;

-- 2. 使用 --single-transaction 避免锁表（仅 InnoDB）

-- 问题2：备份期间写操作堆积
-- FTWRL 期间所有写操作排队等待
-- 如果备份时间长（如复制大量文件），队列可能很长
-- 释放锁后大量写操作同时执行，可能导致瞬间负载飙升

-- 解决：
-- 尽量缩短锁定时间
-- 使用 XtraBackup（只在 non-InnoDB 阶段短暂加锁）
-- 将所有表转换为 InnoDB（避免 FTWRL）
```

## 三种备份方式对比

| 对比维度 | 热备份 | 温备份 | 冷备份 |
|---------|:-----:|:-----:|:-----:|
| 数据库状态 | 运行，可读写 | 运行，只读 | 已停止 |
| 业务影响 | 无（或极小）| 中（写被阻塞）| 大（完全中断）|
| 一致性保证 | MVCC / redo log | 锁表 | 静态文件 |
| 操作复杂度 | 中 | 中 | 低 |
| 备份工具 | XtraBackup, mysqldump(ST) | mysqldump(LT), FTWRL | cp, rsync |
| 适用引擎 | InnoDB | MyISAM, 混合引擎 | 所有引擎 |

## 适用场景

- **包含 MyISAM 表的数据库备份**：MyISAM 不支持事务和 MVCC，无法使用 `--single-transaction` 实现热备份。必须通过锁表（温备份）或停库（冷备份）来保证数据一致性
- **需要获取精确 binlog 位置的备份**：在配置主从复制或进行时间点恢复（PITR）时，需要在锁表状态下获取精确的 binlog 位置（`SHOW BINARY LOG STATUS`），确保 binlog 位置与备份数据完全对应

## 常见问题

**如何减少温备份的锁表时间？**

几个有效的方法：①将所有用户表从 MyISAM 转换为 InnoDB（`ALTER TABLE t ENGINE=InnoDB`），这样就可以使用 `--single-transaction` 实现热备份，完全避免锁表；②使用 XtraBackup 替代 mysqldump，XtraBackup 对 InnoDB 数据不加锁，只在备份 non-InnoDB 数据时短暂加锁（通常几秒到几十秒）；③在执行 FTWRL 前先终止所有长查询，避免 FTWRL 长时间等待；④优化备份流程，在锁定期间只做必要的操作（如记录 binlog 位置），文件复制在锁释放后通过其他机制保证一致性。

---

## 注意事项

- `FLUSH TABLES WITH READ LOCK` 获取的全局锁是会话级别的。如果执行 FTWRL 的连接意外断开（如网络超时），锁会自动释放，可能导致备份数据不一致。在脚本中使用时应确保连接稳定，建议设置足够长的超时时间（`wait_timeout`、`interactive_timeout`）。
- 在高并发的生产环境中执行 FTWRL 需要特别谨慎。如果服务器上有大量并发写操作，FTWRL 获取锁后所有写操作都会排队等待，连接数可能快速增长到 `max_connections` 上限，导致新连接被拒绝。建议在低峰期执行，或提前通知应用层暂停写入。

---

## 总结

温备份在数据库运行状态下通过锁表限制写入来保证一致性。核心操作：`FLUSH TABLES WITH READ LOCK`（全局读锁）。mysqldump 参数：`--lock-tables`（逐库锁）、`--lock-all-tables`（全局锁）。备份期间允许读取但阻塞写入。适用于 MyISAM 表和需要精确 binlog 位置的场景。最佳实践：将表转为 InnoDB 使用 `--single-transaction` 热备，避免锁表。锁是会话级别的，连接断开自动释放。减少锁表时间：用 XtraBackup、终止长查询、优化备份流程。

# 逻辑备份与物理备份区别

MySQL 的备份方式从底层实现上分为两大类：逻辑备份（Logical Backup）和物理备份（Physical Backup）。逻辑备份导出的是 SQL 语句或文本格式的数据，恢复时通过重新执行 SQL 语句重建数据库。物理备份直接复制数据库的底层数据文件（如 InnoDB 的 `.ibd` 文件、redo log、undo log 等），恢复时将文件拷贝回数据目录即可。两种方式各有优缺点，适用于不同的场景。

---

## 逻辑备份

```sql
-- 逻辑备份工具：mysqldump、mysqlpump、MySQL Shell dump utilities

-- mysqldump 导出示例：
-- mysqldump -u root -p --single-transaction mydb > mydb_backup.sql

-- 导出的文件内容是 SQL 语句：
-- CREATE TABLE `users` (
--   `id` int NOT NULL AUTO_INCREMENT,
--   `name` varchar(100) DEFAULT NULL,
--   PRIMARY KEY (`id`)
-- ) ENGINE=InnoDB;
-- INSERT INTO `users` VALUES (1,'张三'),(2,'李四'),(3,'王五');

-- 逻辑备份的特点：
-- 1. 输出为可读的 SQL 文本文件
-- 2. 与存储引擎无关（可以跨引擎恢复）
-- 3. 可以跨平台（Linux 导出 → Windows 恢复）
-- 4. 可以跨版本（MySQL 5.7 导出 → 8.4 恢复，需注意兼容性）
-- 5. 可以选择性备份（指定库、表、条件）
-- 6. 备份速度较慢（需要查询所有数据）
-- 7. 恢复速度较慢（需要重新执行所有 SQL）
-- 8. 备份文件通常比原始数据大（SQL 语法开销）
--    或更小（不包含索引数据，压缩效率高）
```

---

## 物理备份

```
物理备份工具：Percona XtraBackup、MySQL Enterprise Backup、
             文件系统快照（LVM snapshot）、直接复制数据文件

物理备份的内容：
  直接复制数据库的底层文件：
  - InnoDB 表空间文件（*.ibd）
  - 系统表空间（ibdata1）
  - Redo Log（ib_logfile0, ib_logfile1 或 #innodb_redo 目录）
  - Undo Log（undo_001, undo_002）
  - Binary Log（mysql-bin.000001 等）
  - 配置文件（my.cnf）
  - 数据字典（mysql.ibd）

物理备份的特点：
  1. 备份速度快（直接复制文件，接近磁盘 I/O 速度）
  2. 恢复速度快（拷贝文件回数据目录即可）
  3. 备份文件大小等于数据文件大小
  4. 不可跨平台（Linux 备份不能直接在 Windows 恢复）
  5. 不可跨大版本（8.0 备份通常不能在 8.4 直接恢复）
  6. 不能选择性备份单个表（XtraBackup 部分支持）
  7. 需要额外的 prepare 步骤（应用 redo log）
```

## 详细对比

| 对比维度 | 逻辑备份 | 物理备份 |
|---------|:------:|:------:|
| 备份内容 | SQL 语句/文本数据 | 数据库底层文件 |
| 备份速度 | 慢（需查询数据）| 快（直接复制文件）|
| 恢复速度 | 慢（重新执行 SQL）| 快（拷贝文件）|
| 备份大小 | 通常较小（纯数据）| 等于数据文件大小 |
| 跨平台 | 支持 | 不支持 |
| 跨版本 | 支持（注意兼容性）| 不支持跨大版本 |
| 选择性备份 | 支持（库/表/条件）| 有限支持 |
| 对业务影响 | 较小（--single-transaction）| 较小（热备工具）|
| 恢复粒度 | 可恢复单表/单库 | 通常整库恢复 |
| 工具 | mysqldump, mysqlpump | XtraBackup, MEB |
| 适合数据量 | 小到中（< 100GB）| 中到大（> 100GB）|
| 压缩效率 | 高（文本压缩率高）| 中（二进制压缩率一般）|

## 备份速度与恢复速度对比

```
假设数据库大小为 50GB：

逻辑备份（mysqldump）：
  备份时间：30~60 分钟（取决于表结构复杂度和数据量）
  备份文件大小：约 20~40GB（SQL 文本）
  压缩后大小：约 5~10GB
  恢复时间：2~6 小时（重建表结构 + 插入数据 + 重建索引）

物理备份（XtraBackup）：
  备份时间：5~15 分钟（接近磁盘读取速度）
  备份文件大小：约 50GB（等于数据文件大小）
  压缩后大小：约 15~25GB
  恢复时间：10~30 分钟（拷贝文件 + prepare）

结论：
  数据量越大，物理备份的速度优势越明显
  50GB 以下的数据库，逻辑备份通常可以接受
  100GB 以上的数据库，强烈建议使用物理备份
```

## 混合备份策略

```
生产环境推荐的混合备份策略：

1. 定期物理备份（主备份）
   - 每天凌晨执行 XtraBackup 全量备份
   - 每 6 小时执行 XtraBackup 增量备份
   - 保留最近 7 天的备份

2. 定期逻辑备份（辅助备份）
   - 每周执行 mysqldump 全库备份
   - 用于跨版本迁移、部分恢复等场景
   - 保留最近 4 周的备份

3. Binary Log 持续备份
   - 实时备份 binlog 到远程存储
   - 用于时间点恢复（PITR）
   - 保留与全量备份对应的时间范围

恢复优先级：
  快速恢复 → 使用物理备份
  部分恢复（单表）→ 使用逻辑备份
  时间点恢复 → 物理备份 + binlog 重放
```

## 适用场景

- **逻辑备份适用**：小型数据库（< 50GB）、需要跨平台或跨版本迁移、只需备份特定表或满足特定条件的数据、开发和测试环境的数据导入导出
- **物理备份适用**：大型数据库（> 100GB）、需要最快的恢复速度（RTO 要求严格）、需要增量备份以减少备份时间和存储空间、生产环境的主备份方案

## 常见问题

**逻辑备份和物理备份可以同时使用吗？**

不仅可以，而且推荐同时使用。在生产环境中，最佳实践是以物理备份作为主要备份手段（快速备份和恢复），以逻辑备份作为辅助手段（跨版本迁移、部分恢复、备份验证）。物理备份保证了快速的灾难恢复能力（RTO），逻辑备份提供了更高的灵活性。两者配合 binlog 持续备份，形成完整的备份恢复体系。

---

## 注意事项

- 逻辑备份（mysqldump）在备份大型数据库时会消耗大量的服务器 CPU 和内存资源（需要查询所有数据并格式化为 SQL），可能影响在线业务。建议在低峰期执行，并使用 `--single-transaction`（InnoDB 表）避免锁表。
- 物理备份恢复后需要确保 MySQL 版本与备份时的版本一致（至少是相同的大版本）。跨大版本恢复物理备份通常不被支持，需要使用逻辑备份进行版本迁移。

---

## 总结

逻辑备份导出 SQL 语句，速度慢但灵活（跨平台、跨版本、选择性备份），适合小型数据库和迁移场景。物理备份复制数据文件，速度快但灵活性低（不跨平台、不跨版本），适合大型数据库和快速恢复场景。生产环境推荐混合策略：物理备份（主）+ 逻辑备份（辅）+ binlog 持续备份。逻辑备份工具：mysqldump、mysqlpump。物理备份工具：Percona XtraBackup、MySQL Enterprise Backup。数据量 > 100GB 时强烈建议物理备份。

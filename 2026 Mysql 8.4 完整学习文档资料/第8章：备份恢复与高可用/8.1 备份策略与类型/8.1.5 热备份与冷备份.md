# 热备份与冷备份

根据备份时数据库的运行状态，备份可以分为热备份（Hot Backup）和冷备份（Cold Backup）。热备份在数据库正常运行、业务不中断的情况下进行，用户可以继续读写数据。冷备份需要停止数据库服务后再进行，备份期间数据库不可用。两种方式在数据一致性、操作复杂度、业务影响方面有显著差异。

---

## 冷备份（Cold Backup）

```
冷备份的操作流程：

1. 停止 MySQL 服务
   systemctl stop mysqld

2. 复制数据目录下的所有文件
   cp -r /var/lib/mysql /backup/cold_backup_20240615/
   
   需要复制的文件：
   - *.ibd（InnoDB 表空间文件）
   - ibdata1（系统表空间）
   - ib_logfile*（Redo Log，MySQL 8.0.30 之前）
   - #innodb_redo/（Redo Log 目录，MySQL 8.0.30+）
   - undo_*（Undo Log）
   - mysql.ibd（数据字典）
   - mysql-bin.*（Binary Log）
   - my.cnf（配置文件）

3. 启动 MySQL 服务
   systemctl start mysqld

恢复流程：
1. 停止 MySQL 服务
2. 清空数据目录
3. 将备份文件复制到数据目录
4. 修复文件权限（chown -R mysql:mysql /var/lib/mysql）
5. 启动 MySQL 服务

冷备份的特点：
- 操作最简单（直接复制文件）
- 数据一致性最高（停库状态下文件不会变化）
- 不需要任何特殊工具
- 业务中断时间 = 停库 + 复制时间 + 启动时间
- 数据量大时复制耗时长 → 业务中断时间长
```

## 热备份（Hot Backup）

```
热备份在数据库运行状态下进行，不停止服务：

逻辑热备份（mysqldump）：
  mysqldump --single-transaction --all-databases > backup.sql
  - 使用 InnoDB 的一致性快照读取数据
  - 不阻塞 DML 操作（INSERT/UPDATE/DELETE）
  - 备份期间业务正常运行
  - 但会增加服务器的 CPU 和 I/O 负载

物理热备份（XtraBackup）：
  xtrabackup --backup --target-dir=/backup/hot
  - 复制 InnoDB 数据文件的同时记录 redo log 变化
  - 备份完成后通过 prepare 将 redo log 应用到数据文件
  - 实现一致性的热备份
  - 备份期间只在复制 non-InnoDB 数据时短暂加全局锁

热备份的特点：
- 业务不中断，用户无感知
- 需要专业工具（mysqldump 的 --single-transaction 或 XtraBackup）
- 数据一致性通过 MVCC 或 redo log 保证
- 备份过程中数据可能继续变化，需要机制保证一致性
- 是生产环境的首选备份方式
```

## 详细对比

| 对比维度 | 热备份（Hot Backup）| 冷备份（Cold Backup）|
|---------|:-----------------:|:-----------------:|
| 数据库状态 | 运行中 | 已停止 |
| 业务中断 | 不中断 | 中断（停库期间）|
| 数据一致性 | 通过 MVCC/redo log 保证 | 天然一致（静态文件）|
| 操作复杂度 | 中等（需要工具）| 简单（复制文件）|
| 备份工具 | mysqldump, XtraBackup | cp, rsync, tar |
| 对性能影响 | 有（I/O 和 CPU 负载）| 无（已停库）|
| 适用场景 | 生产环境（不能停库）| 维护窗口、测试环境 |
| 恢复复杂度 | 中等 | 简单（拷贝回去）|
| 支持增量 | 是（XtraBackup）| 否（每次全量）|

## 热备份的一致性保证机制

```sql
-- mysqldump 的一致性保证（--single-transaction）：
-- 1. 开始一个长事务（START TRANSACTION WITH CONSISTENT SNAPSHOT）
-- 2. 在该事务的 MVCC 快照下读取所有表的数据
-- 3. 所有读取的数据都是事务开始时刻的一致视图
-- 4. 备份期间其他事务的修改不影响备份数据的一致性
-- 5. 备份完成后提交事务

-- 限制：--single-transaction 只对 InnoDB 表有效
-- MyISAM 表仍然需要锁表来保证一致性

-- XtraBackup 的一致性保证：
-- 1. 开始复制 InnoDB 数据文件（.ibd）
-- 2. 同时持续复制 redo log 的变化
-- 3. 数据文件复制完成后，停止 redo log 复制
-- 4. Prepare 阶段：将 redo log 应用到数据文件
-- 5. 最终结果：数据文件 + 已应用的 redo log = 一致的数据快照

-- XtraBackup 在备份 non-InnoDB 数据时：
-- 执行 FLUSH TABLES WITH READ LOCK（全局读锁）
-- 复制 non-InnoDB 表的文件（如 MyISAM 的 .MYD, .MYI）
-- 记录 binlog 位置
-- 释放读锁
-- 锁定时间通常很短（秒级）
```

## 适用场景

- **热备份适用**：生产环境中不允许停机的业务系统、7×24 小时运行的在线服务、对可用性要求高的金融和电商系统
- **冷备份适用**：有定期维护窗口的系统（如每月凌晨停机维护）、开发和测试环境的数据备份、灾难恢复演练中需要最高一致性保证的场景

## 常见问题

**热备份的数据和冷备份的数据一样可靠吗？**

在使用正确的工具和参数的前提下，热备份的数据与冷备份一样可靠。mysqldump 的 `--single-transaction` 通过 InnoDB 的 MVCC 机制保证数据一致性，XtraBackup 通过 redo log 回放保证数据一致性。这些一致性保证机制经过了大量生产环境的验证，是成熟可靠的。热备份的数据在恢复后，与冷备份恢复的数据在逻辑上完全等价。唯一的风险是如果备份工具本身有 bug 或使用方式不正确（如对 MyISAM 表使用 `--single-transaction` 而不加锁），可能导致数据不一致。

---

## 注意事项

- 冷备份虽然操作简单，但在大型数据库（数百 GB 到 TB 级别）中，停库复制数据的时间可能长达数小时，这对业务的影响是不可接受的。因此大型生产数据库几乎都使用热备份。冷备份主要保留在测试环境和极小型数据库中使用。
- 热备份期间虽然业务不中断，但备份操作会消耗服务器的 I/O 带宽和 CPU 资源。在高负载时段执行热备份可能导致查询响应时间增加。建议在业务低峰期（如凌晨）执行备份，并通过 `ionice` 和 `nice` 命令（Linux）限制备份进程的资源优先级。

---

## 总结

热备份在数据库运行状态下进行，业务不中断，通过 MVCC（mysqldump）或 redo log 回放（XtraBackup）保证一致性，是生产环境的首选。冷备份需要停止数据库，操作简单但业务中断，适合有维护窗口的小型系统。热备份工具：mysqldump（`--single-transaction`）、XtraBackup、MySQL Enterprise Backup。冷备份工具：cp、rsync、tar。大型数据库必须使用热备份。备份应在低峰期执行以减少对业务的影响。

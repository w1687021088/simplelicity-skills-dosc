# 主从切换与故障转移

主从切换（Switchover）是指在计划性维护中将从库提升为新主库的操作；故障转移（Failover）是指在主库意外宕机时将从库紧急提升为新主库的操作。两者的操作步骤类似，但故障转移没有计划准备时间，对 DBA 的响应速度和操作熟练程度要求更高。正确执行主从切换和故障转移是保障 MySQL 高可用的核心运维技能。

---

## 计划性切换（Switchover）

```bash
# 计划性切换：主库正常，有计划地切换角色

# 步骤1：确认从库已追上主库（延迟为 0）
# 在从库执行：
# SHOW REPLICA STATUS\G
# Seconds_Behind_Source: 0  ← 确认延迟为 0

# 步骤2：停止应用程序写入主库
# 通过负载均衡或应用配置将写入流量切换到维护模式
# 或者在主库设置只读（防止切换期间有新写入）
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;

# 步骤3：等待从库完全追上（GTID 一致）
# 在主库：
SHOW BINARY LOG STATUS\G
# Executed_Gtid_Set: server_uuid:1-1000

# 在从库：
SHOW REPLICA STATUS\G
# Executed_Gtid_Set: server_uuid:1-1000  ← 完全追上
# Seconds_Behind_Source: 0

# 步骤4：停止从库复制
STOP REPLICA;

# 步骤5：将从库提升为主库
RESET REPLICA ALL;
# 删除从库的复制配置（不再作为从库）
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;
# 从库现在变为新主库，开放写入

# 步骤6：将旧主库变为新从库（可选，如果旧主库可用）
# 在旧主库：
SET GLOBAL read_only = ON;
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='new_master_host',
    SOURCE_PORT=3306,
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_AUTO_POSITION=1;
START REPLICA;

# 步骤7：更新应用程序的数据库连接配置
# 将写入指向新主库
```

## 紧急故障转移（Failover）

```bash
# 故障转移：主库意外宕机，需要紧急提升从库

# 步骤1：确认主库确实故障（避免误判）
# 检查主库是否可达：ping、telnet 3306、检查服务器状态
# 确认不是网络抖动或临时故障

# 步骤2：选择最佳候选从库
# 选择复制延迟最小的从库（数据最新）
# 在每个从库查看：
# SHOW REPLICA STATUS\G
# Seconds_Behind_Source: ?
# Executed_Gtid_Set: ?（GTID 集合最大的从库数据最新）

# 步骤3：让候选从库追上 binlog（如果主库 binlog 可访问）
# 如果主库宕机但 binlog 文件可以通过其他方式获取
# 通过 mysqlbinlog 将额外的 binlog 应用到候选从库

# 如果主库完全不可访问，跳过此步骤（接受部分数据丢失）

# 步骤4：停止候选从库的复制
STOP REPLICA;
RESET REPLICA ALL;

# 步骤5：将候选从库提升为新主库
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

# 步骤6：将其他从库切换到新主库
# 在其他从库执行：
STOP REPLICA;
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='new_master_host',
    SOURCE_PORT=3306,
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_AUTO_POSITION=1;
START REPLICA;

# 步骤7：更新应用程序连接
# 将写入指向新主库地址

# 步骤8：处理旧主库
# 旧主库恢复后，检查是否有额外的事务需要处理
# 在确认无数据差异后，将其作为新的从库加入复制
```

## GTID 模式下故障转移的优势

```sql
-- GTID 模式简化了故障转移的操作

-- 传统位置模式的问题：
-- 不同从库记录的 binlog 文件名和 Position 不同
-- 切换到新主库后，其他从库需要知道从新主库的哪个位置开始复制
-- 需要手动计算 binlog 位置，容易出错

-- GTID 模式的优势：
-- 每个事务有全局唯一的 GTID
-- 从库知道自己已执行了哪些事务（gtid_executed）
-- 连接到新主库时，自动从尚未执行的事务开始复制
-- 不需要手动计算 binlog 位置

-- GTID 故障转移后其他从库的配置（最简单）：
STOP REPLICA;
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='new_master_host',
    SOURCE_AUTO_POSITION=1;
START REPLICA;
-- SOURCE_AUTO_POSITION=1 会自动处理 GTID 差距

-- 验证其他从库是否正常追上新主库：
SHOW REPLICA STATUS\G
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0
```

## 切换时间目标（RTO）

```
不同方案的 RTO 对比：

手动切换（人工操作）：
  计划切换：10~30 分钟（有充足准备时间）
  紧急故障转移：5~15 分钟（取决于 DBA 响应速度和熟练程度）

MHA（MySQL Master HA）自动故障转移：
  30~90 秒（检测到故障 → 提升从库 → 应用 binlog）

Orchestrator 自动故障转移：
  约 30~60 秒

MGR（组复制）自动故障转移：
  5~10 秒（内置的 Paxos 协议自动选举）

InnoDB Cluster（MySQL Router + MGR）：
  秒级（全自动，应用透明）

RTO 优化建议：
  提前演练切换操作
  使用半同步复制减少数据差异
  使用 GTID 简化操作
  部署 MHA 或 Orchestrator 实现自动化
```

## 适用场景

- **计划性维护（硬件升级/版本升级）**：在计划维护窗口内执行 Switchover，先将流量切换到从库，对主库执行维护后再切回或保持新主库角色
- **主库突发故障的快速恢复**：主库宕机后，通过预先演练过的故障转移步骤，在数分钟内恢复写入服务，最大限度减少业务中断时间

## 常见问题

**故障转移后发现有一批订单数据丢失，如何处理？**

如果使用的是异步复制，主库故障时未传输到从库的 binlog 数据会丢失。如果旧主库的 binlog 文件可以访问（如磁盘未损坏，只是 MySQL 进程崩溃），可以：①用 `mysqlbinlog` 解析旧主库上未传输的 binlog；②将这些事务手动应用到新主库（注意要跳过 GTID 已存在的事务）；③如果无法访问旧主库的 binlog，只能接受数据丢失并通过应用层的补偿机制处理（如重新提交订单）。这就是为什么推荐使用半同步复制（`AFTER_SYNC` 模式）——确保主库提交的事务至少被一个从库收到，避免这种情况。

## 注意事项

- 在紧急故障转移中，必须先确认旧主库完全无法提供服务后才能提升新主库。如果旧主库只是网络临时中断但 MySQL 仍在运行，可能出现"脑裂"（Split-Brain）情况——两个 MySQL 实例都认为自己是主库并接受写入，导致数据冲突。推荐在网络层通过 VIP（虚拟 IP）或 DNS 切换来确保旧主库和新主库不会同时对外服务写请求。
- 故障转移完成后，原来连接到旧主库的应用程序需要重新连接到新主库。通常通过以下方式实现：VIP 漂移（将主库 VIP 绑定到新主库）、DNS 切换（修改主库域名指向的 IP）、负载均衡器配置更新（如 ProxySQL）。其中 VIP 漂移是最常用的方式，可以实现应用程序无感知切换（不需要修改应用程序的数据库连接地址）。

## 总结

主从切换（Switchover）：计划性操作，步骤严谨（停写 → 等待追上 → 停复制 → 提升从库 → 配置其他从库 → 更新应用连接）。故障转移（Failover）：紧急操作，选延迟最小的从库，接受可能的数据丢失。GTID 模式通过 `SOURCE_AUTO_POSITION=1` 大幅简化切换操作。RTO：手动 5~30 分钟，MHA/Orchestrator 30~90 秒，MGR 5~10 秒。避免脑裂：通过 VIP 漂移、DNS 切换确保单一主库。半同步复制降低故障转移时的数据丢失风险。建议使用 MHA 或 Orchestrator 实现自动化切换。

# MHA 高可用方案原理

MHA（Master High Availability Manager）是由日本 DeNA 公司开发的开源 MySQL 高可用管理工具。MHA 的核心功能是在主库故障时自动完成故障转移：识别最新的从库、从主库（如可访问）或其他从库补全 binlog 差距、将最新从库提升为新主库、其他从库切换到新主库。MHA 是 MySQL 传统主从架构中应用最广泛的自动化高可用方案之一。

---

## MHA 的组件架构

```
MHA 由两个核心组件组成：

MHA Manager（管理节点）：
  通常运行在独立的监控服务器上
  负责监控主库健康状态
  检测到主库故障后触发自动故障转移
  协调整个切换流程
  通常只需要一个管理节点

MHA Node（数据节点）：
  安装在每个 MySQL 服务器上（主库和所有从库）
  提供本地操作能力（binlog 解析、日志复制）
  由 MHA Manager 通过 SSH 调用

整体架构：

  [MHA Manager] ─── SSH ───→ [MySQL 主库 + MHA Node]
       │          ─── SSH ───→ [MySQL 从库1 + MHA Node]
       │          ─── SSH ───→ [MySQL 从库2 + MHA Node]
       │
       └─── 监控主库 3306 端口
            检测到主库不可达 → 触发故障转移

前提条件：
  MHA Manager 到所有数据节点必须配置 SSH 免密登录
  所有 MySQL 节点之间也需要 SSH 免密登录
  （用于从其他从库获取差异 binlog）
```

## 故障转移的详细流程

```
MHA 自动故障转移的执行步骤：

阶段1：故障检测
  MHA Manager 默认每 3 秒检测一次主库
  检测方法：连接主库 3306 端口
  默认检测 2 次失败后确认主库故障
  为避免误判，还会尝试从其他从库确认（VIP 检测）

阶段2：从库状态检查
  SSH 连接到所有从库
  获取每个从库的 Relay Log 位置（read_master_log_pos）
  和已应用的位置（exec_master_log_pos）
  确定数据最新的从库（候选主库）

阶段3：补全 binlog 差距
  方式1：如果主库 SSH 可达（磁盘未损坏只是进程崩溃）：
    通过 SSH 从主库复制最新的 binlog
    将未传输的 binlog 应用到候选主库（通过 mysqlbinlog）
  方式2：如果主库完全不可达：
    在从库之间互相比较 Relay Log
    将 Relay Log 最新的部分复制给其他从库
    尽量减少数据差距

阶段4：提升候选主库
  在候选从库上执行：
    STOP REPLICA;
    RESET REPLICA ALL;
    取消只读状态

阶段5：切换其他从库
  其他从库重新配置复制源为新主库
  CHANGE REPLICATION SOURCE TO SOURCE_HOST=new_master...

阶段6：执行 VIP 漂移脚本（如配置）
  将主库的 VIP 绑定到新主库
  应用程序无感知切换
  
整个过程通常在 30~90 秒内完成
```

## MHA 的配置

```ini
# MHA Manager 配置文件（/etc/mha/app.conf）：

[server default]
# MySQL 用户
user=mha_user
password=MhaPass123!
# SSH 用户
ssh_user=root
# 主库 binlog 目录
master_binlog_dir=/var/log/mysql
# 工作目录（存放日志和状态文件）
manager_workdir=/var/log/mha
manager_log=/var/log/mha/manager.log
# 远程工作目录（数据节点上）
remote_workdir=/tmp/mha

[server1]
hostname=192.168.1.100
port=3306
# candidate_master=1  ← 标记为候选主库（优先提升）

[server2]
hostname=192.168.1.101
port=3306
candidate_master=1     # 优先作为候选主库

[server3]
hostname=192.168.1.102
port=3306
no_master=1            # 永远不提升为主库（如备份专用从库）
```

## MHA 的常用命令

```bash
# 检查 SSH 连接和 MySQL 连通性：
masterha_check_ssh --conf=/etc/mha/app.conf

# 检查复制配置是否正确：
masterha_check_repl --conf=/etc/mha/app.conf

# 启动 MHA Manager（后台监控）：
masterha_manager --conf=/etc/mha/app.conf \
    --remove_dead_master_conf \
    --ignore_last_failover &

# 查看 MHA 状态：
masterha_check_status --conf=/etc/mha/app.conf

# 停止 MHA Manager：
masterha_stop --conf=/etc/mha/app.conf

# 手动触发故障转移（测试）：
masterha_master_switch --conf=/etc/mha/app.conf \
    --master_state=dead \
    --new_master_host=192.168.1.101 \
    --ignore_last_failover

# 计划性切换（主库正常时）：
masterha_master_switch --conf=/etc/mha/app.conf \
    --master_state=alive \
    --new_master_host=192.168.1.101
```

## VIP 漂移集成

```bash
# MHA 支持通过自定义脚本实现 VIP 漂移
# 在配置文件中指定：
# master_ip_failover_script=/etc/mha/master_ip_failover.sh
# master_ip_online_change_script=/etc/mha/master_ip_online_change.sh

# VIP 漂移脚本示例（简化）：
#!/bin/bash
# master_ip_failover.sh

VIP="192.168.1.200/24"
IF="eth0"

case "$1" in
  "stopssh")
    # 从旧主库移除 VIP
    ssh $ORIG_MASTER_HOST "ip addr del $VIP dev $IF"
    ;;
  "start")
    # 在新主库添加 VIP
    ip addr add $VIP dev $IF
    arping -c3 -A -I $IF ${VIP%/*}  # ARP 广播更新缓存
    ;;
esac

# VIP 漂移效果：
# 切换前：VIP 192.168.1.200 → 旧主库 192.168.1.100
# 切换后：VIP 192.168.1.200 → 新主库 192.168.1.101
# 应用程序连接的是 VIP，切换后自动连接到新主库
```

## MHA 的局限性

```
MHA 的已知局限：

1. 维护状态
   MHA 的代码库自 2018 年后更新缓慢
   对 MySQL 8.0/8.4 的新特性支持有限
   社区活跃度降低

2. 单点故障（MHA Manager）
   如果 Manager 宕机，无法自动故障转移
   需要部署 Manager 的高可用（如 Keepalived）

3. 对 SSH 的依赖
   需要所有节点之间的 SSH 免密登录
   在安全策略严格的环境中难以配置
   SSH 故障会影响 MHA 的正常工作

4. 不支持多主（MGR）拓扑
   MHA 设计用于传统主从复制
   不支持 MGR 组复制的拓扑

5. 每次切换后需要重新启动 Manager
   故障转移后 Manager 进程退出
   需要运维人员手动重启（或脚本自动重启）

替代选择：
  Orchestrator（更现代，活跃维护，支持复杂拓扑）
  ProxySQL + Orchestrator（配合实现读写分离 + HA）
  MGR + MySQL Router（原生高可用方案）
```

## 适用场景

- **传统主从复制架构的自动化故障转移**：在已有传统主从复制且不打算迁移到 MGR 的环境中，MHA 提供自动化的故障检测和切换，将 RTO 从人工操作的 5~15 分钟降低到 30~90 秒
- **需要快速部署高可用方案的场景**：MHA 的架构相对简单，配置文件直观，比 MGR 更容易理解和部署，适合技术积累较少或希望快速上线高可用能力的团队

## 常见问题

**MHA 故障转移后 Manager 进程退出，怎么让它自动重启？**

MHA Manager 在完成一次故障转移后会退出（设计如此，防止重复切换）。可以通过以下方式处理：①使用 `--ignore_last_failover` 参数允许短时间内再次切换；②将 MHA Manager 作为 systemd 服务运行并设置 `Restart=on-failure`；③使用监控脚本检测 Manager 是否运行，不运行时自动重启；④同时检查切换原因，避免反复切换。在生产环境中，通常会在故障转移后先进行人工确认，再重启 Manager，确保不会因为配置问题导致错误的切换。

## 注意事项

- MHA 的故障转移依赖 SSH 连接的稳定性。如果在故障转移过程中 SSH 连接中断，转移可能不完整（已提升新主库但其他从库未切换）。建议监控 SSH 连接状态，确保网络稳定。在网络条件不稳定的环境中，考虑使用 Orchestrator 替代（Orchestrator 通过 HTTP API 而非 SSH 管理，更可靠）。
- MHA 的候选主库（`candidate_master=1`）必须确保其 binlog 内容的连续性。如果某个从库长期延迟较大，不应将其设为候选主库，否则故障转移后可能丢失较多数据。应将延迟最小、硬件性能较好的从库设为候选主库。

## 总结

MHA 是传统主从复制架构中成熟的自动化高可用工具。组件：MHA Manager（监控节点）+ MHA Node（每台 MySQL 服务器）。故障转移流程：检测故障 → 评估从库 → 补全 binlog → 提升新主库 → 切换其他从库 → VIP 漂移。RTO 约 30~90 秒。依赖 SSH 免密登录。支持 VIP 漂移实现应用透明切换。使用 `candidate_master=1` 指定候选主库，`no_master=1` 排除特定从库。局限：代码更新缓慢、SSH 依赖、Manager 切换后需重启。现代替代方案：Orchestrator、MGR + MySQL Router。

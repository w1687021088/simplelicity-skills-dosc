# 主从复制异步架构

MySQL 主从复制（Master-Replica Replication）是最基础也是最广泛使用的高可用架构。异步复制是默认的复制模式：主库执行事务并提交，然后将 binlog 异步发送给从库，从库接收并重放 binlog 同步数据。主库不等待从库的确认就完成事务提交，因此主从之间存在复制延迟，这是异步复制的核心特征。异步复制架构可以实现读写分离、数据冗余、容灾备份等目标。

---

## 异步复制的工作原理

```
MySQL 异步复制的三线程模型：

主库：
  Binlog Dump 线程（一个连接一个线程）
  ↑ 当从库连接时创建
  负责读取 binlog 并发送给从库

从库：
  I/O 线程（IO_THREAD）
  ↑ 负责连接主库，接收 binlog，写入 Relay Log
  
  SQL 线程（SQL_THREAD）
  ↑ 负责读取 Relay Log，重放 SQL 语句，应用到从库数据

复制流程：
  1. 从库 I/O 线程连接到主库
  2. 主库创建 Binlog Dump 线程
  3. Binlog Dump 线程将 binlog 事件发送给从库 I/O 线程
  4. 从库 I/O 线程接收 binlog 并写入 Relay Log
  5. 从库 SQL 线程读取 Relay Log 并执行，应用到从库数据
  
异步的含义：
  主库提交事务后，立即返回成功给客户端
  不等待 Binlog 是否被从库接收或重放
  如果主库崩溃，还未传输到从库的 binlog 将丢失
  → 可能丢失数据（无损的切换需要额外机制）
```

## 搭建主从复制

```sql
-- 主库配置（my.cnf）：
-- [mysqld]
-- server_id = 1              ← 主库 server_id，全局唯一
-- log_bin = mysql-bin        ← 启用 binlog
-- binlog_format = ROW        ← 推荐 ROW 格式
-- binlog_expire_logs_seconds = 604800  ← binlog 保留 7 天

-- 从库配置（my.cnf）：
-- [mysqld]
-- server_id = 2              ← 从库 server_id，不能与主库相同
-- relay_log = relay-bin      ← Relay Log 文件前缀
-- read_only = ON             ← 从库设为只读（防止误写入）
-- super_read_only = ON       ← 更严格的只读（连 SUPER 用户也受限）

-- 主库：创建复制用户
CREATE USER 'repl'@'%' IDENTIFIED BY 'ReplPass123!';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
FLUSH PRIVILEGES;

-- 主库：查看当前 binlog 位置
SHOW BINARY LOG STATUS\G
-- File: mysql-bin.000015
-- Position: 157

-- 从库：配置复制源并启动
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='192.168.1.100',
    SOURCE_PORT=3306,
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_LOG_FILE='mysql-bin.000015',
    SOURCE_LOG_POS=157;

START REPLICA;

-- 检查从库复制状态：
SHOW REPLICA STATUS\G
-- Replica_IO_Running: Yes     ← I/O 线程正常
-- Replica_SQL_Running: Yes    ← SQL 线程正常
-- Seconds_Behind_Source: 0    ← 复制延迟为 0
```

## GTID 模式的主从复制

```sql
-- GTID（Global Transaction Identifier）模式更简单可靠

-- 主库和从库的 my.cnf：
-- [mysqld]
-- gtid_mode = ON
-- enforce_gtid_consistency = ON
-- log_replica_updates = ON   ← 从库也记录 binlog（级联复制需要）

-- 从库配置（GTID 模式不需要指定 binlog 文件和位置）：
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='192.168.1.100',
    SOURCE_PORT=3306,
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_AUTO_POSITION=1;    ← 自动使用 GTID 确定复制位置

START REPLICA;

-- GTID 模式的优势：
-- 1. 故障转移更简单（不需要记住 binlog 位置）
-- 2. 不会重复执行已执行过的事务
-- 3. 多源复制更容易管理
-- 4. 检测复制循环更可靠
```

## 多从库架构

```
一主多从是最常见的异步复制架构：

                    ┌─ 从库1（处理读请求 Region A）
主库 ─── binlog ───┼─ 从库2（处理读请求 Region B）
                    ├─ 从库3（备份专用，关闭 binlog）
                    └─ 从库4（延迟复制，用于误操作恢复）

各从库的用途：
  读写分离：从库1/2 分担读请求，减轻主库压力
  备份专用：从库3 专门用于 mysqldump 备份，避免在主库备份影响性能
  延迟复制：从库4 使用 CHANGE REPLICATION SOURCE TO ... SOURCE_DELAY=3600
            延迟 1 小时复制，提供 1 小时内的误操作恢复能力
  灾备从库：异地从库，提供异地容灾能力

设置延迟复制（用于误操作保护）：
  CHANGE REPLICATION SOURCE TO SOURCE_DELAY=3600;  -- 延迟 1 小时
  START REPLICA;
```

## 复制状态监控

```sql
-- 关键监控指标：

-- 1. 查看复制线程状态
SHOW REPLICA STATUS\G
-- Replica_IO_Running: Yes/No/Connecting
-- Replica_SQL_Running: Yes/No
-- Seconds_Behind_Source: N    ← 复制延迟（秒）
-- Last_IO_Error: ...           ← I/O 线程错误
-- Last_SQL_Error: ...          ← SQL 线程错误

-- 2. 查看所有从库的复制状态（在主库）
-- 通过 performance_schema 查看从库连接：
SELECT * FROM performance_schema.replication_connection_status\G

-- 3. GTID 模式下查看执行情况
SHOW VARIABLES LIKE 'gtid_executed';     -- 已执行的 GTID 集合
SHOW VARIABLES LIKE 'gtid_purged';       -- 已清除的 GTID 集合

-- 在主库查看：
SHOW BINARY LOG STATUS\G
-- Executed_Gtid_Set: server_uuid:1-1000

-- 在从库查看与主库的差距：
SELECT GTID_SUBTRACT(
    '@@master.Executed_Gtid_Set',  -- 主库的 GTID 集合
    @@global.gtid_executed         -- 从库的 GTID 集合
);  -- 结果为从库还未执行的 GTID
```

## 适用场景

- **读写分离架构**：主库负责所有写入和少量读取，从库负责大量读取请求。在读多写少的业务（如内容平台、电商商品展示）中，可以通过增加从库数量线性扩展读取能力
- **异地容灾**：在异地数据中心搭建从库，通过异步复制保持数据同步。主数据中心故障时，将流量切换到异地从库，实现灾难恢复

## 常见问题

**异步复制的主从延迟通常有多大？会不会导致用户读到旧数据？**

在局域网内、数据写入不是特别频繁的情况下，主从延迟通常在毫秒到秒级。如果写入量大或网络延迟高（如跨机房），延迟可能达到几十秒甚至更高。应对方法：①对于要求强一致的读操作（如用户支付后查询订单），直接路由到主库读取；②使用半同步复制（lossless）确保 binlog 被至少一个从库接收后才返回成功；③应用层在写入后对同一数据的读取在短时间内路由到主库（"读主库"策略）；④监控 `Seconds_Behind_Source`，超过阈值时告警并将读请求临时切换到主库。

## 注意事项

- 异步复制存在数据丢失风险。如果主库发生故障时有部分 binlog 还未传输到从库，这部分数据在故障转移后会丢失。对于不能接受任何数据丢失的业务，应使用半同步复制（`AFTER_SYNC` 模式）或 MGR 组复制来替代异步复制。
- `read_only = ON` 和 `super_read_only = ON` 是保护从库数据一致性的重要配置。如果不设置只读，从库上的误写操作可能导致主从数据不一致，进而导致复制中断（遇到主键冲突等错误）。建议所有从库都设置 `super_read_only = ON`。

## 总结

MySQL 异步复制通过 binlog 实现主库到从库的数据同步。三线程：主库 Binlog Dump、从库 I/O、从库 SQL。异步特性：主库提交后不等从库确认，存在复制延迟和故障时数据丢失风险。推荐使用 GTID 模式（`SOURCE_AUTO_POSITION=1`）简化管理。多从库架构：读写分离、备份专用、延迟复制、异地容灾。监控关键指标：`Seconds_Behind_Source`、`Replica_IO_Running`、`Replica_SQL_Running`。从库必须设置 `read_only=ON` 和 `super_read_only=ON`。适合读多写少和异地容灾场景。

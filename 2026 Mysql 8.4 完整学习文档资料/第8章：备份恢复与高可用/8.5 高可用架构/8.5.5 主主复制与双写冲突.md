# 主主复制与双写冲突

主主复制（Master-Master Replication，也称双主复制）是指两个 MySQL 实例互相作为对方的从库，每个实例都可以接受写入，写入后通过复制同步到对方。表面上看，主主复制可以实现双活写入和高可用，但实际上双写冲突是主主复制的核心难题——两个节点同时对同一数据进行不同的修改，会导致数据不一致。在实际生产环境中，主主复制通常以"一主一备"模式使用，而非真正的双活写入。

## 主主复制的配置

```sql
-- 主主复制的拓扑：
-- 节点 A ←→ 节点 B
-- A 是 B 的主库，B 也是 A 的主库

-- 节点 A 的 my.cnf：
-- [mysqld]
-- server_id = 1
-- log_bin = mysql-bin
-- binlog_format = ROW
-- gtid_mode = ON
-- enforce_gtid_consistency = ON
-- auto_increment_increment = 2     ← 自增步长为 2（双主关键配置）
-- auto_increment_offset = 1        ← A 节点自增起始值为 1，产生 1,3,5,7...

-- 节点 B 的 my.cnf：
-- [mysqld]
-- server_id = 2
-- log_bin = mysql-bin
-- binlog_format = ROW
-- gtid_mode = ON
-- enforce_gtid_consistency = ON
-- auto_increment_increment = 2     ← 自增步长为 2
-- auto_increment_offset = 2        ← B 节点自增起始值为 2，产生 2,4,6,8...

-- 节点 A 上配置复制（从 B 复制）：
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='node_b_host',
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_AUTO_POSITION=1;
START REPLICA;

-- 节点 B 上配置复制（从 A 复制）：
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='node_a_host',
    SOURCE_USER='repl',
    SOURCE_PASSWORD='ReplPass123!',
    SOURCE_AUTO_POSITION=1;
START REPLICA;
```

## 自增 ID 冲突与解决方案

```sql
-- 主主复制中的自增 ID 冲突问题：

-- 场景：A 和 B 同时插入数据，都使用 AUTO_INCREMENT

-- 不配置 auto_increment_increment/offset 的问题：
-- A 插入 id=1，B 同时也插入 id=1
-- A 的 INSERT 复制到 B 时：B 已有 id=1 → 主键冲突 → 复制中断

-- 解决方案：配置不同的自增偏移量
-- A：auto_increment_increment=2, auto_increment_offset=1
--    自增序列：1, 3, 5, 7, 9, ...（奇数）
-- B：auto_increment_increment=2, auto_increment_offset=2
--    自增序列：2, 4, 6, 8, 10, ...（偶数）

-- 这样 A 和 B 永远不会产生相同的自增 ID
-- 消除自增 ID 冲突

-- 查看当前配置：
SHOW VARIABLES LIKE 'auto_increment%';

-- 注意：如果扩展为多主（>2 个节点），需要调整步长
-- 3 节点：increment=3, offset=1/2/3
-- 4 节点：increment=4, offset=1/2/3/4
```

## 双写冲突的类型

```
主主复制的双写冲突有多种类型：

1. 主键冲突
   A 插入 id=5，B 同时也插入 id=5（未配置不同偏移量）
   A 的记录复制到 B → 主键冲突
   
2. 更新冲突
   A 将 status 从 pending 改为 processing
   B 同时将 status 从 pending 改为 failed
   A 的更新复制到 B：此时 B 的 status 是 failed，
   但 A 的 binlog 中记录的 before image 是 pending
   → ROW 格式下：before image 不匹配 → 复制错误
   → STATEMENT 格式下：可能静默覆盖 B 的修改 → 数据不一致

3. 删除-更新冲突
   A 更新了一条记录
   B 同时删除了同一条记录
   A 的更新复制到 B：记录不存在 → 复制错误

双写冲突是主主复制的根本问题
在业务层面无法完全避免（除非保证同一数据只由一个节点写入）
```

## 主主复制的实际应用模式

```
主主复制在生产环境中的实际使用方式：

模式1：一主一备（最常用）
  正常状态：只有 A 节点接受写入，B 节点只读
  A 故障：B 节点接管，开放写入
  A 恢复：A 重新作为备节点，不接受写入
  
  优势：避免双写冲突，同时保留快速故障切换能力
  劣势：B 节点资源利用率低（只读）
  
模式2：按表分区写入（理论上可行但复杂）
  表1/表2 的写入指向 A
  表3/表4 的写入指向 B
  保证同一张表的写入只来自一个节点
  
  问题：跨表事务可能导致一致性问题
       数据分区管理复杂
  → 实际很少使用

模式3：替代方案（更推荐）
  使用 MGR（组复制）替代主主复制
  MGR 的多主模式（multi-primary）内置冲突检测和处理机制
  冲突事务会自动回滚，比主主复制更安全
  → 需要双活写入时，推荐使用 MGR 而非传统主主复制
```

## 冲突处理策略

```sql
-- 当主主复制发生冲突时，复制会中断
-- 复制错误信息示例：
-- Last_SQL_Error: Could not execute Update_rows event on table mydb.orders;
-- Can't find record in 'orders'; Error_code: 1032

-- 处理策略1：跳过错误（临时措施，有风险）
-- GTID 模式下跳过冲突事务：
SET GTID_NEXT='conflicting_server_uuid:N';
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
-- 危险：跳过后两边数据不一致，需要手动核查

-- 处理策略2：设置 replica_skip_errors（不推荐）
-- [mysqld]
-- replica_skip_errors = 1062,1032  ← 自动跳过主键冲突和记录不存在错误
-- 这会静默忽略冲突，导致数据不一致而不报警

-- 处理策略3：根本解决——避免双写
-- 通过应用层、中间件（ProxySQL）将写入路由到单一节点
-- 确保同一张表的写入只来自一个 MySQL 节点

-- 处理策略4：使用 MGR 替代
-- MGR 的 Paxos 协议在提交前检测冲突
-- 冲突事务直接回滚，不会让冲突传播到复制
```

## 与 MGR 的对比

| 对比维度 | 主主复制 | MGR（组复制）|
|---------|:------:|:----------:|
| 冲突检测 | 无（被动发现）| 内置（主动检测）|
| 冲突处理 | 复制中断 | 自动回滚 |
| 双活写入安全性 | 低 | 较高 |
| 配置复杂度 | 中等 | 较高 |
| 成员管理 | 手动 | 自动 |
| 最大节点数 | 通常 2 | 9 |
| 推荐用途 | 一主一备切换 | 多主写入或单主高可用 |

## 适用场景

- **高可用主备切换**：使用主主复制的"一主一备"模式，正常时只有一个节点写入，故障时快速切换到备节点，恢复写入服务，切换时间通常在秒级
- **数据库版本升级的滚动切换**：搭建主主复制，先升级备节点，然后切换到备节点（此时备节点是新版本），再升级旧主节点，实现不停服的版本升级

## 常见问题

**配置了 auto_increment_increment 和 offset 后，自增 ID 会不连续，业务代码会有问题吗？**

自增 ID 不连续是正常的，业务代码不应该依赖自增 ID 的连续性。自增 ID 只是唯一标识符，间隙（如 1,3,5 而不是 1,2,3）不影响数据的正确性。业务代码中用到 `id+1` 这种依赖连续性的逻辑是不规范的。如果业务确实需要连续的序列号（如订单号），应该在应用层或通过独立的序列号生成服务（Redis/ZooKeeper）生成，不要依赖数据库的自增 ID。

---

## 注意事项

- 主主复制中，即使配置了 `auto_increment_increment` 和 `auto_increment_offset` 解决了自增 ID 冲突，仍然无法解决业务逻辑层面的双写冲突（如两个节点同时修改同一行数据）。真正安全的双活写入需要在应用层保证同一条记录的写入只路由到一个节点，或者使用 MGR 的 Paxos 协议进行冲突检测。
- 主主复制配置中，如果其中一个节点的复制中断了，另一个节点继续接受写入，中断期间的数据差异会越来越大。恢复复制时可能需要处理大量冲突或手动同步数据。建议监控两个节点的复制状态，发现复制中断立即处理，避免差异积累过大。

---

## 总结

主主复制让两个 MySQL 实例互相复制，理论上支持双活写入，但双写冲突是核心难题。解决自增 ID 冲突：配置不同的 `auto_increment_increment` 和 `auto_increment_offset`（A 奇数、B 偶数）。双写冲突类型：主键冲突、更新冲突、删除-更新冲突。实际应用：一主一备模式（只有一个节点写入，避免冲突）。冲突后复制中断，GTID 模式下用空事务跳过。推荐替代：MGR 组复制提供内置冲突检测。不依赖自增 ID 连续性。监控两节点复制状态，及时处理中断。

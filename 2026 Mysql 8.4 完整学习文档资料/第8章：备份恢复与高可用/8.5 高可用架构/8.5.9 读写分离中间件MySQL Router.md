# 读写分离中间件 MySQL Router

MySQL Router 是 Oracle 官方提供的轻量级 MySQL 代理中间件，是 MySQL InnoDB Cluster 和 InnoDB ReplicaSet 架构的核心组件之一。MySQL Router 提供透明的读写分离和故障转移功能，应用程序连接 Router 的读写端口（通常是 6446）或只读端口（通常是 6447），Router 自动将请求路由到合适的 MySQL 节点。与 ProxySQL 相比，MySQL Router 更轻量、配置更简单，与 MySQL 官方产品（InnoDB Cluster、InnoDB ReplicaSet）深度集成。

---

## MySQL Router 的架构

```
MySQL Router 在 InnoDB ReplicaSet 中的角色：

应用程序
    │
    ├── 连接端口 6446（读写，路由到主库）
    └── 连接端口 6447（只读，路由到从库）
    
    ↓
    
MySQL Router
    ├── 监听 6446（读写端口）→ Primary（主库）
    ├── 监听 6447（只读端口）→ Secondary（从库，轮询负载均衡）
    └── 持续监控集群健康状态（通过 MySQL X Protocol）

    ↓
    
MySQL InnoDB ReplicaSet / InnoDB Cluster
    ├── Primary（主库）: 192.168.1.100:3306
    ├── Secondary 1: 192.168.1.101:3306
    └── Secondary 2: 192.168.1.102:3306

故障自动切换：
  Primary 宕机 → InnoDB Cluster 自动选举新 Primary
  MySQL Router 自动感知新的 Primary
  将 6446 端口的流量切换到新 Primary
  应用程序无感知（连接地址不变）
```

## 与 InnoDB ReplicaSet 的集成

```sql
-- InnoDB ReplicaSet 是 MySQL 8.0+ 的功能，通过 MySQL Shell 管理

-- 步骤1：使用 MySQL Shell 创建 ReplicaSet（在主库上）
-- mysqlsh root@192.168.1.100:3306

-- MySQL Shell 中：
-- var rs = dba.createReplicaSet('myReplicaSet');
-- rs.status();

-- 步骤2：将从库加入 ReplicaSet
-- rs.addInstance('root@192.168.1.101:3306', {recoveryMethod: 'clone'});
-- rs.addInstance('root@192.168.1.102:3306', {recoveryMethod: 'clone'});
-- rs.status();

-- 步骤3：为 MySQL Router 创建账号
-- var rs = dba.getReplicaSet();
-- rs.setupRouterAccount('router_user', {password: 'RouterPass!'});

-- 步骤4：部署 MySQL Router（在应用服务器上）
-- mysqlrouter --bootstrap root@192.168.1.100:3306 \
--     --directory /etc/mysqlrouter \
--     --user mysqlrouter

-- --bootstrap：自动从 InnoDB ReplicaSet 获取拓扑信息
-- --directory：Router 配置文件目录

-- 步骤5：启动 MySQL Router
-- mysqlrouter --config /etc/mysqlrouter/mysqlrouter.conf &
-- 或：systemctl start mysqlrouter
```

## MySQL Router 的配置文件

```ini
# /etc/mysqlrouter/mysqlrouter.conf（bootstrap 自动生成）

[DEFAULT]
logging_folder=/var/log/mysqlrouter
runtime_folder=/var/run/mysqlrouter
data_folder=/var/lib/mysqlrouter

[logger]
level=INFO

[metadata_cache:myReplicaSet]
cluster_type=rs
router_id=1
user=router_user
metadata_cluster=myReplicaSet
ttl=0.5                    # 拓扑信息缓存时间（秒）
auth_cache_ttl=-1
auth_cache_refresh_interval=2

[routing:myReplicaSet_rw]
bind_address=0.0.0.0
bind_port=6446              # 读写端口
destinations=metadata-cache://myReplicaSet/?role=PRIMARY
routing_strategy=first-available  # 总是路由到 Primary

[routing:myReplicaSet_ro]
bind_address=0.0.0.0
bind_port=6447              # 只读端口
destinations=metadata-cache://myReplicaSet/?role=SECONDARY
routing_strategy=round-robin    # 轮询从库
```

## 路由策略

```
MySQL Router 支持以下路由策略：

routing_strategy=first-available（读写端口默认）：
  始终路由到目标列表中第一个可用的节点
  即使有多个 Primary，也只用第一个
  Primary 不可用时自动切换到下一个

routing_strategy=next-available：
  类似 first-available
  失败后切换到下一个，直到成功

routing_strategy=round-robin（只读端口默认）：
  轮询所有可用的 Secondary
  实现请求的负载均衡

routing_strategy=round-robin-with-fallback：
  优先轮询 Secondary
  如果所有 Secondary 不可用，回退到 Primary
  适合读请求，避免从库全部宕机后读请求失败
  
端口映射：
  6446 → PRIMARY（读写端口）
  6447 → SECONDARY（只读端口，轮询）
  6448 → MySQL X Protocol 读写
  6449 → MySQL X Protocol 只读
```

```python
# Python 应用程序连接 MySQL Router 的示例：

import mysql.connector

# 写操作：连接到读写端口（6446）
write_conn = mysql.connector.connect(
    host='mysql_router_host',
    port=6446,                # 读写端口 → 自动路由到 Primary
    user='app_user',
    password='AppPass!',
    database='mydb'
)

# 读操作：连接到只读端口（6447）
read_conn = mysql.connector.connect(
    host='mysql_router_host',
    port=6447,                # 只读端口 → 自动路由到 Secondary
    user='app_user',
    password='AppPass!',
    database='mydb'
)

# 在 Spring Boot（Java）中配置两个数据源：
# spring.datasource.write.url=jdbc:mysql://router_host:6446/mydb
# spring.datasource.read.url=jdbc:mysql://router_host:6447/mydb
```

## 适用场景

- **MySQL InnoDB Cluster 或 InnoDB ReplicaSet 架构**：MySQL Router 与 InnoDB Cluster/RS 原生集成，通过 MySQL Shell bootstrap 命令自动配置，是这两种架构的标准组件，提供开箱即用的读写分离和自动故障转移
- **希望使用官方工具链的团队**：不想引入第三方组件，使用 MySQL 官方的全套工具（MySQL Shell + MySQL Router + InnoDB Cluster）实现高可用和读写分离

## 常见问题

**MySQL Router 部署在哪里比较合适？独立服务器还是应用服务器本地？**

两种部署模式各有优劣：①独立服务器部署：需要考虑 Router 本身的高可用（部署两个 Router + Keepalived），Router 是所有应用的集中代理，单点风险；②应用服务器本地部署（推荐）：每台应用服务器上运行一个 MySQL Router 实例，应用通过 localhost 连接，没有单点问题，网络延迟极低（本地回环）。MySQL 官方也推荐将 Router 部署在应用服务器本地（Sidecar 模式），这样 Router 的故障只影响本台服务器，整体可用性更高。

## 注意事项

- MySQL Router 不缓存应用程序的连接，它是一个透明代理——每次应用程序建立连接，Router 都会向后端 MySQL 建立实际连接。如果应用程序频繁建立和断开连接（短连接），Router 会向 MySQL 产生大量连接/断连操作。建议应用层使用连接池（如 HikariCP、DBCP），保持长连接，减少 MySQL 端的连接压力。
- MySQL Router 的 `ttl`（元数据缓存时间）参数控制 Router 刷新集群拓扑信息的频率。默认 0.5 秒（500ms）。较小的 ttl 意味着拓扑变化（如主库切换）可以更快被 Router 感知，但同时增加了 Router 查询元数据的频率。建议在 0.5~5 秒之间根据 RTO 要求选择，如果要求自动切换在 1 秒内完成，ttl 应设为 0.5 秒。

## 总结

MySQL Router 是 Oracle 官方轻量级 MySQL 代理，与 InnoDB Cluster/ReplicaSet 原生集成。端口约定：6446（读写→Primary），6447（只读→Secondary）。路由策略：`first-available`（读写）、`round-robin`（只读）。通过 `mysqlrouter --bootstrap` 自动生成配置，简化部署。应用层连接两个端口实现读写分离，无需修改 SQL 逻辑。与 MySQL Shell 配合管理 ReplicaSet（`setPrimaryInstance`、`addInstance`）。推荐 Sidecar 模式部署（应用服务器本地）避免单点。`ttl` 控制拓扑刷新频率。适合 InnoDB Cluster/RS 架构和使用官方工具链的场景。

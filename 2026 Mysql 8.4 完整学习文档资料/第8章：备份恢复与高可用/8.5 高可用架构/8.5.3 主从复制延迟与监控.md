# 主从复制延迟与监控

复制延迟（Replication Lag）是指从库应用 binlog 的进度落后于主库的时间差。复制延迟是主从架构中需要持续监控的核心指标，它直接影响读写分离的数据一致性和故障转移时的数据丢失风险。延迟过大意味着从库读取到的数据可能严重滞后于主库，同时在主库故障时需要从库追赶更多的 binlog 才能成为新主库。

---

## 复制延迟的来源

```
主从复制延迟的主要来源：

1. 网络传输延迟
   binlog 从主库传输到从库的网络时间
   局域网通常 < 1ms，跨机房可能 > 50ms
   
2. 从库 SQL 线程（单线程）的处理速度
   默认情况下，从库 SQL 线程是单线程的
   主库的并发写入在从库变成了串行执行
   如果主库有大量并发写入，从库单线程追不上
   → 主要原因之一
   
3. 大事务
   一个大事务（如 UPDATE 100万行）在主库并发执行可能很快
   但在从库 SQL 线程中需要单线程串行执行
   整个事务期间其他事务都在等待
   → 主要原因之一

4. 从库硬件性能
   从库的 CPU、磁盘 I/O 性能低于主库
   处理同样的 SQL 需要更长时间

5. 从库上的其他负载
   从库同时承担大量读请求（如分析查询）
   I/O 资源被读请求占用，SQL 线程重放变慢

6. DDL 操作
   主库执行 ALTER TABLE 等 DDL 操作
   从库需要执行相同的 DDL，可能耗时很长
```

## 延迟监控指标

```sql
-- 基本延迟监控：
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: N    ← 复制延迟（秒）
-- 注意：该值不是绝对准确，是估算值
-- 为 0 时表示从库已追上主库（或 SQL 线程空闲）
-- 为 NULL 时表示复制线程未运行

-- 更精确的延迟监控（performance_schema）：
SELECT * FROM performance_schema.replication_applier_status_by_worker\G
-- WORKER_ID: 1
-- THREAD_ID: ...
-- SERVICE_STATE: ON
-- LAST_SEEN_TRANSACTION: server_uuid:1234  ← 最近应用的 GTID
-- APPLYING_TRANSACTION: server_uuid:1235   ← 正在应用的 GTID
-- APPLYING_TRANSACTION_START_APPLY_TIMESTAMP: 2024-06-15 15:30:00
-- ← 当前事务开始应用的时间，与当前时间的差即为该事务已执行的时间

-- 查看 I/O 线程延迟（binlog 是否已接收）：
SELECT * FROM performance_schema.replication_connection_status\G
-- SOURCE_UUID: ...
-- SERVICE_STATE: ON
-- RECEIVED_TRANSACTION_SET: server_uuid:1-1235  ← 已接收的 GTID
-- LAST_QUEUED_TRANSACTION: server_uuid:1235      ← 最近接收的 GTID

-- 对比主库和从库的 GTID 差距：
-- 在主库：
SHOW BINARY LOG STATUS\G
-- Executed_Gtid_Set: server_uuid:1-1240

-- 在从库：
SHOW VARIABLES LIKE 'gtid_executed';
-- server_uuid:1-1235

-- 差距 = 主库 GTID 1-1240 - 从库 GTID 1-1235 = 5 个事务未应用
```

## 使用多线程复制降低延迟

```sql
-- MySQL 8.0+ 支持多线程并行应用（MTS：Multi-Threaded Slave/Replica）

-- 查看当前并行配置：
SHOW VARIABLES LIKE 'replica_parallel%';

-- 配置多线程并行复制（推荐配置）：
-- my.cnf 或 SET 命令：
SET GLOBAL replica_parallel_workers = 8;         -- 8 个工作线程
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';  -- 并行类型
SET GLOBAL replica_preserve_commit_order = ON;   -- 保持提交顺序

-- 参数说明：
-- replica_parallel_workers: 工作线程数（推荐与主库 CPU 核数一致）
-- replica_parallel_type:
--   DATABASE（旧）：按数据库并行，不同库之间并行
--   LOGICAL_CLOCK（推荐）：基于 binlog group commit 的逻辑时钟并行
--                         同一组 group commit 的事务可以并行应用
-- replica_preserve_commit_order: ON = 保持与主库相同的提交顺序

-- 重启 SQL 线程使配置生效：
STOP REPLICA SQL_THREAD;
START REPLICA SQL_THREAD;

-- 查看并行工作线程状态：
SELECT WORKER_ID, THREAD_ID, SERVICE_STATE,
    LAST_SEEN_TRANSACTION, APPLYING_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker;
```

## 延迟监控最佳实践

```bash
# 监控脚本示例（简化版）：

# 使用 pt-heartbeat（Percona Toolkit）实现精确延迟监控
# pt-heartbeat 比 Seconds_Behind_Source 更准确

# 主库：启动心跳更新
pt-heartbeat --update --daemonize \
    --user=root --password=xxx \
    --database=percona_heartbeat
# 每秒在 heartbeat 表中写入一条时间戳记录

# 从库：检查延迟
pt-heartbeat --monitor \
    --user=root --password=xxx \
    --database=percona_heartbeat \
    --replication-dsn="h=master_host,u=root,p=xxx"
# 通过对比 heartbeat 表中的时间戳和当前时间计算真实延迟

# 告警阈值建议：
# 延迟 > 10秒：警告
# 延迟 > 60秒：严重告警
# 延迟 > 300秒（5分钟）：紧急告警，读请求切换到主库
```

## 延迟过大的处理方法

```sql
-- 处理复制延迟的策略：

-- 1. 启用多线程并行复制（最有效）
SET GLOBAL replica_parallel_workers = 8;
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';

-- 2. 优化大事务
-- 将大的批量 UPDATE/DELETE 拆分为小事务
-- 每次处理 1000~10000 行，减少单个事务的大小

-- 3. 减少从库上的读负载
-- 避免在从库上执行重量级的分析查询
-- 将分析查询专门路由到备用的分析从库

-- 4. 提升从库硬件
-- 使用 SSD 替代 HDD（主要瓶颈通常在磁盘 I/O）
-- 增加从库的 innodb_buffer_pool_size

-- 5. 跳过问题事务（紧急情况）
-- 不推荐，可能导致数据不一致
-- 只在确认该事务可以安全跳过时使用
-- GTID 模式跳过：
SET GTID_NEXT='server_uuid:N';
BEGIN; COMMIT;                 -- 空事务跳过
SET GTID_NEXT='AUTOMATIC';

-- 传统模式跳过一个事务：
-- SET GLOBAL SQL_SLAVE_SKIP_COUNTER=1;  -- 已废弃，不推荐
```

## 适用场景

- **读写分离架构的延迟监控**：在读写分离场景中，从库延迟直接影响用户读取到旧数据的概率。需要持续监控延迟，当延迟超过阈值时自动将读请求路由到主库
- **故障转移前的延迟评估**：在计划切换主库前，需要确认候选从库的延迟接近 0，避免切换后丢失数据

## 常见问题

**Seconds_Behind_Source 为 0 但从库确实落后怎么解释？**

`Seconds_Behind_Source` 的计算方式是用当前时间减去 SQL 线程正在应用的事务的时间戳。如果从库的 Relay Log 中已经没有待处理的事务，SQL 线程空闲，`Seconds_Behind_Source` 会显示 0。但这并不意味着从库完全追上了主库——可能 I/O 线程还没有从主库接收到最新的 binlog。更准确的监控方法是对比主库和从库的 GTID 集合（GTID 差距），或使用 pt-heartbeat 工具。

---

## 注意事项

- `replica_parallel_workers > 0` 时，`replica_preserve_commit_order = ON` 是必须的配置，否则从库的事务提交顺序可能与主库不同，可能导致从库上读取到中间状态的数据（部分已提交、部分未提交）。即使在追求最大并行吞吐量的场景下，也不建议关闭该配置。
- 多线程并行复制对 `LOGICAL_CLOCK` 模式下的并行效果依赖主库的 binlog group commit。如果主库的 `binlog_group_commit_sync_delay` 和 `binlog_group_commit_sync_no_delay_count` 配置得当，更多事务会被合并到同一个 group commit 组中，从库并行度更高，延迟更低。

## 总结

复制延迟来源：网络传输、从库 SQL 线程处理速度（默认单线程）、大事务、从库硬件性能。监控指标：`Seconds_Behind_Source`（估算）、GTID 差距（更准确）、pt-heartbeat（最准确）。降低延迟：启用多线程并行复制（`replica_parallel_workers=8` + `LOGICAL_CLOCK` + `replica_preserve_commit_order=ON`）、优化大事务、减少从库读负载。告警阈值：>10s 警告、>300s 紧急。跳过事务只在确认安全时使用（GTID 模式用空事务跳过）。`Seconds_Behind_Source=0` 不代表完全追上，需结合 GTID 或 pt-heartbeat 确认。

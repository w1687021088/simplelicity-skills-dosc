# 主从复制半同步架构

半同步复制（Semi-Synchronous Replication）是介于异步复制和全同步复制之间的一种复制模式。在半同步复制中，主库在提交事务后，必须等待至少一个从库确认已收到该事务的 binlog 并写入 Relay Log，才向客户端返回成功。如果在超时时间内没有从库确认，主库会自动降级为异步复制。半同步复制可以有效降低主库故障时的数据丢失风险。

---

## 半同步复制的两种模式

```
MySQL 半同步复制有两种等待点：

AFTER_COMMIT（旧版，有损模式）：
  主库流程：事务写 binlog → 提交到存储引擎（数据可见）
           → 等待从库 ACK → 返回成功给客户端
  
  风险：在等待从库 ACK 期间，事务已提交（其他会话可以读到）
        如果主库此时崩溃，从库没有收到 binlog
        故障转移后，从库没有该事务的数据
        但该客户端已经收到"成功"响应
        → 数据丢失（有损）

AFTER_SYNC（新版，无损模式，MySQL 5.7.2+ 默认）：
  主库流程：事务写 binlog → 等待从库 ACK 
           → 收到 ACK 后再提交到存储引擎 → 返回成功给客户端
  
  保证：只有从库确认收到 binlog 后，事务才对外可见
        如果主库崩溃，从库已有完整的 binlog
        故障转移后，从库有全部已确认的数据
        → 无数据丢失（无损）
  
  MySQL 8.4 中 rpl_semi_sync_source_wait_point 默认为 AFTER_SYNC
```

## 安装和配置半同步复制

```sql
-- 主库安装半同步插件：
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
-- Linux: semisync_source.so
-- Windows: semisync_source.dll

-- 从库安装半同步插件：
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';

-- 验证插件已安装：
SHOW PLUGINS;
-- 查看 rpl_semi_sync_source 和 rpl_semi_sync_replica 的状态为 ACTIVE

-- 主库：启用半同步
SET GLOBAL rpl_semi_sync_source_enabled = ON;
SET GLOBAL rpl_semi_sync_source_timeout = 10000;  -- 超时时间 10 秒
SET GLOBAL rpl_semi_sync_source_wait_for_replica_count = 1;  -- 至少 1 个从库确认

-- 从库：启用半同步
SET GLOBAL rpl_semi_sync_replica_enabled = ON;

-- 重启复制（让从库重新连接，触发半同步协商）：
STOP REPLICA IO_THREAD;
START REPLICA IO_THREAD;

-- 验证半同步是否生效：
SHOW STATUS LIKE 'Rpl_semi_sync%';
-- Rpl_semi_sync_source_clients: 1          ← 已连接的半同步从库数量
-- Rpl_semi_sync_source_status: ON          ← 半同步当前状态
-- Rpl_semi_sync_source_yes_tx: 100         ← 半同步成功的事务数
-- Rpl_semi_sync_source_no_tx: 0            ← 降级为异步的事务数
```

## 持久化配置（my.cnf）

```ini
# 主库 my.cnf：
[mysqld]
# 半同步插件（启动时自动加载）
plugin-load-add = semisync_source.so

# 半同步参数
rpl_semi_sync_source_enabled = ON
rpl_semi_sync_source_timeout = 10000        # 超时时间（毫秒），默认 10000
rpl_semi_sync_source_wait_for_replica_count = 1  # 等待 ACK 的从库数量
rpl_semi_sync_source_wait_no_replica = ON   # 无从库时保持半同步等待

# 从库 my.cnf：
[mysqld]
plugin-load-add = semisync_replica.so
rpl_semi_sync_replica_enabled = ON
```

## 超时降级机制

```
半同步超时降级的行为：

场景：从库网络故障或宕机，主库等待 ACK 超时

超时降级流程：
  1. 主库等待从库 ACK（最多 rpl_semi_sync_source_timeout 毫秒）
  2. 超时 → 主库自动降级为异步复制
  3. Rpl_semi_sync_source_status 变为 OFF
  4. 后续事务以异步方式提交（不等待 ACK）

降级后恢复半同步：
  当从库重新连接且追上主库的 binlog 后
  主库自动升级回半同步模式
  Rpl_semi_sync_source_status 变回 ON

超时时间的权衡：
  过短（如 100ms）：
    网络抖动或短暂延迟就会触发降级
    频繁降级影响数据安全性
  过长（如 10000ms = 10秒）：
    主库写入延迟最多增加 10 秒
    在高写入量场景下可能造成连接排队
  推荐：根据业务可接受的延迟设置，通常 1000~10000ms

监控降级情况：
  SHOW STATUS LIKE 'Rpl_semi_sync_source_no_tx';
  ← 该值增大说明发生了降级，需要检查复制状态
```

## 与异步复制的对比

| 对比维度 | 异步复制 | 半同步复制（AFTER_SYNC）|
|---------|:------:|:---------------------:|
| 数据丢失风险 | 有 | 基本无（ACK 确认后提交）|
| 写入延迟 | 无额外延迟 | 有（等待 ACK）|
| 从库故障影响主库 | 无 | 超时前阻塞写入 |
| 配置复杂度 | 简单 | 中等 |
| 适用场景 | 读扩展/异地容灾 | 金融/对数据一致性要求高 |

## 适用场景

- **金融、支付等对数据一致性要求严格的业务**：使用 `AFTER_SYNC` 模式的半同步复制确保主库提交的事务至少被一个从库收到，主库故障后故障转移不会丢失已提交的事务
- **需要降低故障切换时数据差异的场景**：在需要手动或自动故障转移的架构中，半同步复制确保候选从库有最完整的数据，减少故障切换时的数据不一致风险

## 常见问题

**半同步复制是否会成为性能瓶颈？**

半同步复制会增加写入延迟，延迟大小等于主库到从库的网络往返时间（RTT）。在同一数据中心的服务器之间，RTT 通常小于 1ms，写入延迟几乎可以忽略。但在跨数据中心（RTT 几十到几百毫秒）的场景中，每次写入都需要等待跨机房的 RTT，对写入吞吐量影响显著。建议：局域网内使用半同步，跨机房使用异步复制；或者使用 MGR（组复制）替代，MGR 在协议上做了更多优化。

## 注意事项

- `rpl_semi_sync_source_wait_no_replica` 参数控制当没有从库连接时主库是否等待。默认值 `ON` 表示没有从库时主库仍然等待 ACK 直到超时，这会导致每次写入都增加超时时间的延迟。在维护从库时（如从库重启），应将该参数临时设为 `OFF` 或适当缩短超时时间，以避免影响主库写入性能。
- 半同步插件在 MySQL 8.4 中通过 `rpl_semi_sync_source` 和 `rpl_semi_sync_replica` 命名（替代 8.0 早期版本的 `rpl_semi_sync_master` 和 `rpl_semi_sync_slave`）。如果从旧版本升级，需要注意配置文件和监控脚本中的参数名称更新。

## 总结

半同步复制在异步复制基础上增加了"从库 ACK 确认"机制，降低数据丢失风险。两种模式：`AFTER_COMMIT`（有损）和 `AFTER_SYNC`（无损，推荐）。安装插件：`semisync_source.so`（主库）+ `semisync_replica.so`（从库）。关键参数：`rpl_semi_sync_source_timeout`（超时时间）、`wait_for_replica_count`（等待从库数量）。超时降级为异步复制，从库恢复后自动升回半同步。适合金融等对数据一致性要求高的场景。局域网内延迟影响极小，跨机房延迟较大。监控：`Rpl_semi_sync_source_status`、`Rpl_semi_sync_source_no_tx`。

# Orchestrator 可视化拓扑管理

Orchestrator 是由 GitHub 开源的 MySQL 高可用管理和可视化工具，用 Go 语言编写。它不仅提供了自动化故障转移能力，还提供了直观的 Web 界面展示 MySQL 复制拓扑，以及强大的拓扑操作功能（如重构复制链路、安全地提升从库等）。与 MHA 相比，Orchestrator 更现代、维护更活跃，支持更复杂的复制拓扑，并通过 HTTP API 进行管理（不依赖 SSH）。

---

## Orchestrator 的核心功能

```
1. 拓扑可视化
   Web 界面实时显示 MySQL 主从复制拓扑图
   包括每个节点的状态（正常/延迟/故障）
   binlog 位置、GTID、复制延迟等信息
   支持拖拽操作重构复制链路

2. 自动故障检测与转移
   持续监控所有 MySQL 节点的健康状态
   检测到主库故障后自动触发故障转移
   自动选择最优候选主库（数据最新的从库）
   自动切换其他从库到新主库

3. 拓扑重构
   安全地将从库从一个主库迁移到另一个主库
   支持多级复制链路的调整
   例如：将二级从库直接提升为一级从库连接到主库

4. HTTP API
   提供完整的 REST API 进行自动化操作
   curl 可以直接调用 API
   支持与 CI/CD、监控系统集成

5. Orchestrator 自身的高可用
   支持 Orchestrator 集群模式
   多个 Orchestrator 节点互相协调
   避免 MHA Manager 的单点问题
```

## Orchestrator 架构

```
部署架构：

[Orchestrator Server(s)]
    │
    ├── 持续访问所有 MySQL 节点（每 10 秒一次）
    │   通过 MySQL 连接（不依赖 SSH）
    │   收集拓扑信息、健康状态
    │
    ├── Web UI（端口 3000）
    │   拓扑可视化
    │   人工操作界面
    │
    ├── HTTP API（端口 3000）
    │   /api/instance/host:port      查看实例信息
    │   /api/master-equivalent-of    查找主库
    │   /api/graceful-master-takeover  计划切换
    │   /api/recover                 故障恢复
    │
    └── 内部数据库
        SQLite（单节点部署）
        MySQL（集群部署，共享状态）

对所有 MySQL 节点的要求：
  Orchestrator 必须能通过 MySQL 协议连接到所有节点
  需要一个 Orchestrator 专用的 MySQL 用户
```

## 安装与基本配置

```bash
# 下载 Orchestrator（Go 编译好的二进制）：
# wget https://github.com/openark/orchestrator/releases/download/v3.2.6/orchestrator-3.2.6-linux-amd64.tar.gz
# tar xzf orchestrator-3.2.6-linux-amd64.tar.gz

# 在所有 MySQL 节点上创建 Orchestrator 用户：
# mysql -u root -p
CREATE USER 'orchestrator'@'orchestrator_server_ip'
    IDENTIFIED BY 'OrchestratorPass!';
GRANT SUPER, PROCESS, REPLICATION SLAVE, RELOAD ON *.*
    TO 'orchestrator'@'orchestrator_server_ip';
GRANT SELECT ON mysql.slave_master_info
    TO 'orchestrator'@'orchestrator_server_ip';
GRANT SELECT ON performance_schema.*
    TO 'orchestrator'@'orchestrator_server_ip';
```

```json
// orchestrator.conf.json 配置文件（关键部分）：
{
  "MySQLTopologyUser": "orchestrator",
  "MySQLTopologyPassword": "OrchestratorPass!",
  
  "ListenAddress": ":3000",
  
  "MySQLOrchestratorHost": "localhost",
  "MySQLOrchestratorPort": 3306,
  "MySQLOrchestratorDatabase": "orchestrator",
  "MySQLOrchestratorUser": "orchestrator_backend",
  "MySQLOrchestratorPassword": "BackendPass!",
  
  "RecoverMasterClusterFilters": ["*"],
  "RecoverIntermediateMasterClusterFilters": ["*"],
  
  "FailMasterPromotionIfSQLThreadNotUpToDate": true,
  
  "MasterFailoverLostInstancesDowntimeMinutes": 10
}
```

  http://orchestrator_server:3000
  支持基本的用户认证（可集成 LDAP）

## 自动故障转移配置

```json
// 在 orchestrator.conf.json 中配置自动故障转移：
{
  "RecoveryPeriodBlockSeconds": 3600,
  
  "RecoverMasterClusterFilters": ["*"],
  
  "PromotionIgnoreHostnameFilters": ["backup-slave-*"],
  
  "PostMasterFailoverProcesses": [
    "echo 'FailoverCommand {failureType} {failureDescription} {failedHost} {successorHost}' >> /tmp/failover.log",
    "/etc/orchestrator/vip_failover.sh {successorHost} {failedHost}"
  ],
  
  "PostFailoverProcesses": [
    "/etc/orchestrator/send_alert.sh {failureType} {failedHost} {successorHost}"
  ]
}
```

```bash
# 使用 API 触发手动故障转移：
curl -s http://orchestrator:3000/api/graceful-master-takeover-auto/cluster_name

# 查看集群状态：
curl -s http://orchestrator:3000/api/clusters | python3 -m json.tool

# 查看特定实例状态：
curl -s http://orchestrator:3000/api/instance/192.168.1.100/3306 | python3 -m json.tool

# 在命令行中使用 orchestrator-client：
orchestrator-client -c topology -i 192.168.1.100:3306
orchestrator-client -c which-cluster-master -i 192.168.1.100:3306
orchestrator-client -c graceful-master-takeover-auto -i 192.168.1.100:3306
```

## 适用场景

- **需要可视化拓扑管理的团队**：Orchestrator 的 Web UI 让 DBA 可以直观地看到整个复制拓扑的状态，包括延迟、故障等信息，适合有多套 MySQL 实例的团队进行统一管理
- **复杂复制拓扑的安全重构**：在需要频繁调整复制链路（如从库迁移、多级复制调整）的场景中，Orchestrator 提供安全的拓扑操作，防止误操作导致复制中断

## 常见问题

**Orchestrator 不依赖 SSH，那故障转移时如何执行 VIP 漂移？**

Orchestrator 通过执行配置文件中的 `PostMasterFailoverProcesses` 等钩子脚本来实现 VIP 漂移。这些脚本在 Orchestrator 服务器上本地执行，可以调用 SSH、API 或任何其他工具操作 VIP。例如，脚本可以通过 SSH 连接到新主库执行 `ip addr add VIP`，或者调用负载均衡器（如 HAProxy、AWS ALB）的 API 修改后端节点。相比 MHA，Orchestrator 的 VIP 切换更灵活，可以适配各种基础设施。

---

## 注意事项

- Orchestrator 通过 MySQL 连接而非 SSH 管理节点，因此不需要 SSH 免密登录，但需要确保 Orchestrator 服务器的 MySQL 端口（3306）可以访问所有 MySQL 节点。在有防火墙的环境中，需要开放 MySQL 端口。同时，`orchestrator` 用户需要足够的权限（包括 `REPLICATION SLAVE`）来获取复制信息。
- Orchestrator 默认每 10 秒检测一次所有 MySQL 节点。在大型环境（数百个 MySQL 实例）中，这会产生大量的 MySQL 连接。可以通过 `InstancePollSeconds` 调整检测频率，或部署多个 Orchestrator 节点分担检测负载。同时注意 Orchestrator 的内部数据库（SQLite 或 MySQL）的性能，在大量节点时可能成为瓶颈。

## 总结

Orchestrator 是现代化的 MySQL 拓扑管理和高可用工具，用 Go 编写，通过 MySQL 连接和 HTTP API 管理。核心功能：Web 可视化拓扑、自动故障转移、拖拽拓扑重构、REST API。无需 SSH 依赖，比 MHA 更灵活。支持内置集群模式避免单点问题。通过 `PostMasterFailoverProcesses` 钩子实现 VIP 漂移等自定义操作。活跃维护，支持复杂多级拓扑。与 ProxySQL 集成可以实现完整的读写分离 + 自动故障转移方案。适合有可视化需求和复杂拓扑管理需求的团队。

# --master-data 记录 BINLOG 位置

`--master-data`（MySQL 8.4 中已重命名为 `--source-data`）是 mysqldump 的关键参数，用于在备份文件中记录备份时刻的 Binary Log 文件名和位置。这个信息对于配置主从复制（指定从库从哪个 binlog 位置开始复制）和时间点恢复（PITR，从备份恢复后通过重放 binlog 恢复到指定时间点）至关重要。

---

## 参数说明与用法

```bash
# MySQL 8.0 中的参数名：--master-data
# MySQL 8.4 中的新参数名：--source-data
# 两者功能完全相同，只是名称变更（术语标准化）

# --source-data=1（或 --master-data=1）：
# 在备份文件中写入 CHANGE REPLICATION SOURCE TO 语句（非注释形式）
# 恢复后自动配置复制位置
mysqldump -u root -p --single-transaction --source-data=1 \
    --all-databases > backup.sql

# 备份文件中的内容：
# CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='mysql-bin.000015',
#   SOURCE_LOG_POS=154;
# （非注释，恢复时自动执行）

# --source-data=2（或 --master-data=2）：
# 在备份文件中以注释形式写入位置信息
# 恢复后不会自动配置复制，需要手动使用
mysqldump -u root -p --single-transaction --source-data=2 \
    --all-databases > backup.sql

# 备份文件中的内容：
# -- CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='mysql-bin.000015',
# --   SOURCE_LOG_POS=154;
# （注释形式，仅供参考，不自动执行）
```

## 内部执行机制

```sql
-- --source-data 的内部执行过程：

-- 当与 --single-transaction 一起使用时：
-- 1. FLUSH TABLES WITH READ LOCK（获取全局读锁）
-- 2. SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ
-- 3. START TRANSACTION WITH CONSISTENT SNAPSHOT（创建一致性快照）
-- 4. SHOW BINARY LOG STATUS（获取 binlog 位置）
--    → File: mysql-bin.000015, Position: 154
-- 5. UNLOCK TABLES（释放全局读锁）
--    锁定时间极短（通常毫秒级到秒级）
-- 6. 在快照下逐表导出数据...

-- 当不使用 --single-transaction 时：
-- 1. FLUSH TABLES WITH READ LOCK
-- 2. SHOW BINARY LOG STATUS
-- 3. 导出数据（锁一直持有到备份完成）
-- 4. UNLOCK TABLES
-- 锁定时间 = 整个备份时间（可能很长）

-- 关键点：
-- --source-data 与 --single-transaction 配合使用时
-- 全局读锁的持有时间极短（只在获取 binlog 位置时）
-- 之后通过 MVCC 快照保证数据一致性
```

## 配合主从复制使用

```bash
# 使用 --source-data=1 创建从库的初始数据：

# 步骤1：在主库执行备份
mysqldump -u root -p --single-transaction --source-data=1 \
    --all-databases > master_backup.sql

# 步骤2：将备份文件传输到从库服务器
# scp master_backup.sql slave_server:/tmp/

# 步骤3：在从库恢复数据
# mysql -u root -p < /tmp/master_backup.sql
# 恢复过程中会自动执行：
# CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='mysql-bin.000015',
#   SOURCE_LOG_POS=154;

# 步骤4：在从库配置并启动复制
# mysql -u root -p -e "
# CHANGE REPLICATION SOURCE TO
#   SOURCE_HOST='master_ip',
#   SOURCE_USER='repl_user',
#   SOURCE_PASSWORD='repl_password',
#   SOURCE_PORT=3306;
# START REPLICA;
# "
# 注意：步骤3已经设置了 SOURCE_LOG_FILE 和 SOURCE_LOG_POS
# 步骤4只需补充连接信息即可
```

## 配合 PITR（时间点恢复）使用

```bash
# 使用 --source-data=2 记录 binlog 位置用于 PITR：

# 步骤1：全量备份（记录 binlog 位置）
mysqldump -u root -p --single-transaction --source-data=2 \
    --flush-logs --all-databases > full_backup.sql

# 步骤2：查看备份文件中的 binlog 位置
# head -30 full_backup.sql | grep "CHANGE REPLICATION SOURCE"
# -- CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='mysql-bin.000016',
# --   SOURCE_LOG_POS=157;

# 步骤3：发生故障，需要恢复到故障前某时间点

# 3a. 恢复全量备份
# mysql -u root -p < full_backup.sql

# 3b. 从 binlog 位置开始重放到指定时间点
# mysqlbinlog --start-position=157 \
#     --stop-datetime="2024-06-15 14:30:00" \
#     mysql-bin.000016 mysql-bin.000017 | mysql -u root -p
```

## --source-data vs --set-gtid-purged

```bash
# 在 GTID 复制环境中，还需要配合 --set-gtid-purged 参数：

# --set-gtid-purged=AUTO（默认）：
# 如果服务器启用了 GTID → 自动添加 SET @@GLOBAL.gtid_purged
# 如果未启用 GTID → 不添加
mysqldump --single-transaction --source-data=2 \
    --set-gtid-purged=AUTO --all-databases > backup.sql

# --set-gtid-purged=ON：
# 强制添加 SET @@GLOBAL.gtid_purged
# 用于 GTID 复制环境的备份

# --set-gtid-purged=OFF：
# 不添加 SET @@GLOBAL.gtid_purged
# 用于非复制环境或需要在同一服务器恢复

# GTID 环境的备份文件中会包含：
# SET @@GLOBAL.gtid_purged='server_uuid:1-1000';
# -- CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='...',
# --   SOURCE_LOG_POS=...;
```

## =1 与 =2 的选择

| 场景 | 推荐值 | 原因 |
|-----|:-----:|------|
| 搭建新的从库 | =1 | 恢复时自动配置复制位置 |
| 日常备份/PITR | =2 | 记录位置但不自动执行 |
| 非复制环境备份 | =2 或不使用 | 仅记录参考信息 |
| 在同一服务器恢复 | =2 | 避免自动执行影响当前复制 |

## 适用场景

- **搭建主从复制的初始数据同步**：使用 `--source-data=1` 备份主库数据，在从库恢复后自动获得正确的 binlog 复制起始位置，简化从库搭建流程
- **时间点恢复（PITR）的备份基础**：使用 `--source-data=2` 记录全量备份对应的 binlog 位置，故障恢复时先恢复全量备份，再从该位置开始重放 binlog 到目标时间点

## 常见问题

**--source-data 需要什么权限？**

`--source-data` 参数在内部会执行 `FLUSH TABLES WITH READ LOCK` 和 `SHOW BINARY LOG STATUS`，因此需要 `RELOAD` 权限（用于 FLUSH）和 `REPLICATION CLIENT` 权限（用于 SHOW BINARY LOG STATUS）。如果使用专用备份用户，需要确保授予了这些权限：`GRANT SELECT, RELOAD, REPLICATION CLIENT, SHOW DATABASES, LOCK TABLES, PROCESS, EVENT, TRIGGER ON *.* TO 'backup'@'localhost'`。

## 注意事项

- MySQL 8.4 中 `--master-data` 参数已被重命名为 `--source-data`，与复制术语标准化一致（master → source）。旧的 `--master-data` 在 8.4 中可能仍然可用（作为别名），但建议迁移到新名称。同时备份文件中的 SQL 也从 `CHANGE MASTER TO` 变为 `CHANGE REPLICATION SOURCE TO`。
- 当 `--source-data` 与 `--single-transaction` 一起使用时，全局读锁（FTWRL）的持有时间非常短（仅在获取 binlog 位置时）。但如果服务器上有长时间运行的查询，FTWRL 需要等待这些查询完成后才能获取锁，等待期间所有新的写操作都会被阻塞。建议在备份前检查并终止长查询。

## 总结

`--source-data`（原 `--master-data`）在备份文件中记录 binlog 位置（文件名+偏移量）。`=1` 以可执行 SQL 形式写入（自动配置复制），`=2` 以注释形式写入（仅供参考）。与 `--single-transaction` 配合时全局锁持有时间极短。搭建从库用 `=1`，日常备份/PITR 用 `=2`。需要 `RELOAD` 和 `REPLICATION CLIENT` 权限。GTID 环境配合 `--set-gtid-purged` 使用。MySQL 8.4 中参数名从 `--master-data` 改为 `--source-data`。

# --single-transaction 一致性备份

`--single-transaction` 是 mysqldump 最重要的参数之一，它利用 InnoDB 的 MVCC（多版本并发控制）机制，在备份开始时创建一个一致性快照，然后在该快照下读取所有表的数据。整个备份过程不需要对表加锁（不使用 `LOCK TABLES`），业务可以正常进行读写操作，实现了真正的"热备份"。这是 InnoDB 表备份的推荐方式。

---

## 工作原理

```sql
-- --single-transaction 的内部执行过程：

-- 1. 设置事务隔离级别为 REPEATABLE READ
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 2. 开启一个一致性快照事务
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- 此时 InnoDB 创建一个 Read View（读视图）
-- 该 Read View 记录了事务开始时刻的数据版本
-- 后续所有读操作都基于这个快照

-- 3. 逐表导出数据
-- SELECT * FROM table1;  （在快照下读取）
-- SELECT * FROM table2;  （在快照下读取）
-- ...

-- 4. 提交事务
COMMIT;

-- 关键点：
-- 在步骤2到步骤4之间，其他事务的 INSERT/UPDATE/DELETE 正常执行
-- 但 mysqldump 的读取不会看到这些变更（MVCC 保证）
-- 所有导出的数据都是步骤2时刻的一致状态
```

## 基本用法

```bash
# 使用 --single-transaction 备份单个数据库：
mysqldump -u root -p --single-transaction mydb > backup.sql

# 备份所有数据库：
mysqldump -u root -p --single-transaction --all-databases > backup.sql

# 生产环境推荐的完整参数组合：
mysqldump -u root -p \
    --single-transaction \
    --routines \
    --triggers \
    --events \
    --source-data=2 \
    --flush-logs \
    --hex-blob \
    --all-databases > full_backup_$(date +%Y%m%d_%H%M%S).sql

# 参数说明：
# --single-transaction：一致性快照，不锁表
# --routines：包含存储过程和函数
# --triggers：包含触发器
# --events：包含事件
# --source-data=2：以注释形式记录 binlog 位置
# --flush-logs：刷新 binlog，开始新的 binlog 文件
# --hex-blob：以十六进制格式导出二进制数据
```

## --single-transaction 的限制

```
--single-transaction 只对 InnoDB 表有效：

InnoDB 表：
  使用 MVCC 一致性快照读取 ✓
  不加锁，不阻塞写操作 ✓
  数据一致性完全保证 ✓

MyISAM 表：
  MyISAM 不支持事务和 MVCC ✗
  --single-transaction 对 MyISAM 表无效
  MyISAM 表的数据可能在备份过程中被修改
  导致备份数据不一致

混合引擎环境：
  InnoDB 表通过 MVCC 保证一致性
  MyISAM 表没有一致性保证
  建议：将所有 MyISAM 表转为 InnoDB
  或者使用 --lock-all-tables 替代 --single-transaction

其他限制：
  1. 备份期间不能执行 DDL（ALTER TABLE, DROP TABLE 等）
     DDL 会破坏一致性快照
     如果在备份期间有 DDL 执行，备份可能失败或数据不一致

  2. 长事务问题
     --single-transaction 会创建一个长事务
     该事务持续到备份完成
     期间 InnoDB 不能回收该事务之前的 undo log
     可能导致 undo log 膨胀
```

## 与 --lock-tables 和 --lock-all-tables 的对比

| 参数 | 锁机制 | 写阻塞 | 一致性 | 适用引擎 | 推荐度 |
|-----|:-----:|:-----:|:-----:|:------:|:-----:|
| --single-transaction | MVCC 快照 | 不阻塞 | 全局一致 | InnoDB | 高 |
| --lock-tables | 逐库读锁 | 阻塞写 | 库级一致 | 所有 | 低 |
| --lock-all-tables | 全局读锁 | 阻塞写 | 全局一致 | 所有 | 中 |

```bash
# 纯 InnoDB 环境（推荐）：
mysqldump --single-transaction ...

# 混合引擎环境（需要全局一致性）：
mysqldump --lock-all-tables ...

# 不要同时使用 --single-transaction 和 --lock-all-tables
# 它们是互斥的
```

## 备份期间的 DDL 处理

```sql
-- --single-transaction 备份期间如果有 DDL 操作会怎样？

-- 场景1：备份过程中有 ALTER TABLE
-- mysqldump 可能报错：
-- ERROR 1412 (HY000): Table definition has changed, 
-- please retry transaction

-- 场景2：备份过程中有 DROP TABLE
-- 如果 mysqldump 尚未读取该表 → 跳过
-- 如果 mysqldump 正在读取该表 → 报错

-- 场景3：备份过程中有 CREATE TABLE
-- 新表不在 MVCC 快照中 → 不会被备份
-- 这是正确的行为（一致性快照只包含备份开始时刻的数据）

-- 最佳实践：
-- 备份期间避免执行任何 DDL 操作
-- 如果必须执行 DDL，在备份完成后再执行
-- 可以通过 pt-online-schema-change 等工具在线 DDL
```

## 适用场景

- **纯 InnoDB 环境的在线备份**：所有用户表都使用 InnoDB 引擎时，`--single-transaction` 是最佳选择，备份过程不锁表、不阻塞业务，数据一致性由 MVCC 保证
- **需要备份期间保持业务连续性**：在不能接受任何停机或写入阻塞的生产环境中，`--single-transaction` 是唯一的 mysqldump 热备方案

## 常见问题

**使用 --single-transaction 备份时，备份的数据是哪个时间点的？**

备份的数据是 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 执行时刻的一致性快照。无论备份过程持续多长时间（如 1 小时），所有表的数据都是同一个时间点的状态。如果备份开始时表 A 有 100 万行，备份期间插入了 10 万行，备份文件中表 A 仍然是 100 万行（快照时刻的数据）。配合 `--source-data=2`，备份文件中还会记录快照时刻的 binlog 位置，可以基于此位置进行时间点恢复（PITR）。

---

## 注意事项

- `--single-transaction` 创建的长事务会阻止 InnoDB 回收 undo log。如果备份耗时较长（如大数据库备份需要数小时），undo 表空间可能显著增长。备份完成后 undo 空间会逐步回收（通过 purge 线程），但在磁盘空间紧张的环境中需要注意。
- `--single-transaction` 不能与 `--lock-all-tables` 同时使用。如果同时指定，mysqldump 会报错或忽略其中一个参数。在纯 InnoDB 环境中使用 `--single-transaction`，在混合引擎环境中使用 `--lock-all-tables`。

## 总结

`--single-transaction` 利用 InnoDB 的 MVCC 创建一致性快照，实现不锁表的热备份。备份数据是快照时刻的一致状态。只对 InnoDB 表有效，MyISAM 表无一致性保证。备份期间不应执行 DDL 操作。生产环境推荐与 `--routines`、`--triggers`、`--events`、`--source-data=2` 组合使用。不能与 `--lock-all-tables` 同时使用。长时间备份可能导致 undo log 膨胀。是纯 InnoDB 环境中 mysqldump 备份的首选参数。

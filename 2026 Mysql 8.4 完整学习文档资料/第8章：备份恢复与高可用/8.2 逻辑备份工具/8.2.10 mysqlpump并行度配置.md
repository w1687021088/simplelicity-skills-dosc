# mysqlpump 并行度配置

mysqlpump 的多线程并行备份是通过"队列"（Queue）和"线程"（Thread）机制实现的。每个队列可以包含一个或多个数据库，每个队列分配一定数量的工作线程来并行导出数据。合理配置并行度可以充分利用服务器的 CPU 和 I/O 资源，显著提升大型数据库的备份速度。

---

## 并行架构

```
mysqlpump 的并行模型：

                    ┌─── 线程1 → 导出 table_a
队列1（mydb1）──────┼─── 线程2 → 导出 table_b
                    └─── 线程3 → 导出 table_c

                    ┌─── 线程1 → 导出 table_x
队列2（mydb2）──────┤
                    └─── 线程2 → 导出 table_y

队列3（其他库）───── 线程1 → 导出其他库的表

并行层级：
  1. 队列级别：不同队列之间并行执行
  2. 表级别：同一队列中的不同表由不同线程并行导出
  3. 单表内部：单张表只由一个线程导出（不能拆分）

关键限制：
  单张大表仍然是单线程导出的
  如果数据库中有一张特别大的表，该表的导出时间就是瓶颈
  并行主要加速多表/多库的场景
```

## 并行度配置参数

```bash
# 1. --default-parallelism=N
# 设置默认队列的线程数
# 默认值：2
# 值为 0 时禁用并行（单线程模式）

# 使用 4 个线程并行备份：
mysqlpump -u root -p --default-parallelism=4 \
    --all-databases > backup.sql

# 使用 8 个线程（适合多核服务器）：
mysqlpump -u root -p --default-parallelism=8 \
    --all-databases > backup.sql

# 禁用并行：
mysqlpump -u root -p --default-parallelism=0 \
    --all-databases > backup.sql

# 2. --parallel-schemas=N:db1[,db2,...]
# 为指定数据库创建独立的队列并分配线程数

# 为 mydb1 分配 4 个线程，为 mydb2 分配 2 个线程：
mysqlpump -u root -p \
    --parallel-schemas=4:mydb1 \
    --parallel-schemas=2:mydb2 \
    --default-parallelism=1 \
    --all-databases > backup.sql

# 多个数据库共享一个队列：
mysqlpump -u root -p \
    --parallel-schemas=4:mydb1,mydb2,mydb3 \
    --default-parallelism=1 \
    --all-databases > backup.sql
# mydb1、mydb2、mydb3 共享 4 个线程的队列
# 其他数据库使用 1 个线程的默认队列
```

## 生产环境并行度规划

```bash
# 并行度配置原则：

# 1. 总线程数不应超过 CPU 核心数
# 查看 CPU 核心数（Linux）：nproc
# 建议总线程数 = CPU 核心数的 50%~75%
# 例如 16 核服务器：总线程数 8~12

# 2. 为大库分配更多线程
# 查看各数据库的大小：
# SELECT TABLE_SCHEMA,
#     ROUND(SUM(DATA_LENGTH + INDEX_LENGTH)/1024/1024, 2) AS size_mb
# FROM information_schema.TABLES
# GROUP BY TABLE_SCHEMA
# ORDER BY size_mb DESC;

# 3. I/O 带宽也是瓶颈
# 过多的并行线程可能导致 I/O 争抢
# 如果备份存储在 HDD 上，线程数不宜过多（4~8）
# 如果备份存储在 SSD 上，可以适当增加（8~16）

# 示例配置（16核 CPU、SSD 存储、3 个主要数据库）：
mysqlpump -u root -p \
    --parallel-schemas=4:large_db \
    --parallel-schemas=3:medium_db \
    --parallel-schemas=2:small_db \
    --default-parallelism=1 \
    --single-transaction \
    --all-databases > backup.sql
# large_db：4 个线程（最大的库，分配最多资源）
# medium_db：3 个线程
# small_db：2 个线程
# 其他库：1 个线程
# 总线程数：4+3+2+1 = 10（CPU 核心数的 62.5%）
```

## 并行度对备份速度的影响

```
实际测试参考数据（仅供参考，实际取决于硬件和数据特征）：

测试环境：8 核 CPU、SSD、数据量 50GB、100 张表

线程数 | 备份时间 | 相对速度
  1    | 60 分钟 | 1.0x
  2    | 35 分钟 | 1.7x
  4    | 22 分钟 | 2.7x
  8    | 18 分钟 | 3.3x
  16   | 19 分钟 | 3.2x（I/O 瓶颈，反而略慢）

关键发现：
1. 从 1 到 4 线程，提升最明显
2. 超过 CPU 核心数后，提升不明显甚至下降
3. I/O 成为瓶颈后，增加线程无法再加速
4. 如果有一张 30GB 的大表，该表始终是单线程导出的
   即使设置 16 个线程，这张大表的导出时间不变

优化建议：
- 从 4 个线程开始测试
- 逐步增加到 CPU 核心数的 50%~75%
- 观察备份时间和服务器负载
- 找到最佳平衡点
```

## 监控备份进度

```bash
# 使用 --watch-progress 监控备份进度：
mysqlpump -u root -p \
    --default-parallelism=4 \
    --watch-progress \
    --all-databases > backup.sql

# 输出示例：
# Dump progress: 0/5 tables, 0/100000 rows
# Dump progress: 2/5 tables, 45000/100000 rows
# Dump progress: 4/5 tables, 85000/100000 rows
# Dump progress: 5/5 tables, 100000/100000 rows
# Dump completed in 120 seconds

# 进度信息包括：
# - 已完成的表数 / 总表数
# - 已导出的行数 / 总行数（估算）
# - 已耗时
```

## 适用场景

- **多数据库环境的加速备份**：服务器上有多个数据库，每个库有不同的大小和重要性，通过 `--parallel-schemas` 为每个库分配不同的并行度，充分利用服务器资源
- **大量小表的加速备份**：数据库中有数百张小表（每张表几 MB），单线程逐表导出效率低，多线程并行可以显著提升整体速度

## 常见问题

**mysqlpump 的多线程会不会增加对生产数据库的压力？**

会。每个线程都会独立查询数据库，多个线程同时读取数据会增加服务器的 CPU 使用率、内存消耗和 I/O 负载。如果在业务高峰期执行多线程备份，可能影响在线查询的响应时间。建议在低峰期执行备份，并根据服务器负载调整并行度。可以通过操作系统级别的资源限制（如 `nice`、`ionice`）降低备份进程的优先级，或通过 MySQL 的资源组（Resource Groups）限制备份线程的 CPU 使用。

## 注意事项

- mysqlpump 的并行是表级别的，不是行级别的。一张大表（如 30GB）仍然由单个线程导出，无法通过增加并行度加速。如果数据库中的瓶颈是某张特别大的表，mysqlpump 的多线程优势不明显。对于这种场景，考虑使用 MySQL Shell 的 `util.dumpTables()` 或 `mydumper`（支持表内分片并行）。
- 多线程并行导出时，输出文件中不同表的 SQL 语句可能交错排列。这不影响恢复的正确性（mysql 客户端按顺序执行每条语句），但如果需要从备份文件中手动提取特定表的数据，可能比 mysqldump 的顺序输出更难处理。

## 总结

mysqlpump 通过队列和线程机制实现多线程并行备份。`--default-parallelism=N` 设置默认线程数（默认 2）。`--parallel-schemas=N:db1,db2` 为指定数据库创建独立队列。并行是表级别的，单张大表仍单线程导出。总线程数建议不超过 CPU 核心数的 75%。从 4 线程开始测试，逐步调优。`--watch-progress` 监控进度。多线程增加服务器负载，建议低峰期执行。大量小表场景提升最明显。mysqlpump 在 MySQL 8.0.34 中标记为废弃，推荐迁移到 MySQL Shell dump utilities。

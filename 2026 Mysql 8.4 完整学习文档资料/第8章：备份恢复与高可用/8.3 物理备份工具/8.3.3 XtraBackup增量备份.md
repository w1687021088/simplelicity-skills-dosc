# XtraBackup 增量备份

XtraBackup 的增量备份基于 InnoDB 的 LSN（Log Sequence Number）机制，每次增量备份只复制 LSN 大于上一次备份结束时 LSN 的数据页。这意味着增量备份只包含自上一次备份（全量或增量）以来被修改过的数据页，备份速度快、占用空间小。增量备份必须以一个全量备份作为基础，恢复时需要按顺序将所有增量备份应用到全量备份上。

---

## 增量备份的执行流程

```bash
# 完整的增量备份流程（以一周为例）：

# 周日凌晨：全量备份
xtrabackup --backup \
    --target-dir=/backup/full \
    --user=bkpuser --password=xxx

# 周一凌晨：第一次增量备份（基于全量）
xtrabackup --backup \
    --target-dir=/backup/inc1 \
    --incremental-basedir=/backup/full \
    --user=bkpuser --password=xxx
# --incremental-basedir 指向全量备份目录
# XtraBackup 读取 /backup/full/xtrabackup_checkpoints 中的 to_lsn
# 只复制 LSN > to_lsn 的数据页

# 周二凌晨：第二次增量备份（基于第一次增量）
xtrabackup --backup \
    --target-dir=/backup/inc2 \
    --incremental-basedir=/backup/inc1 \
    --user=bkpuser --password=xxx
# --incremental-basedir 指向上一次增量备份目录

# 周三凌晨：第三次增量备份（基于第二次增量）
xtrabackup --backup \
    --target-dir=/backup/inc3 \
    --incremental-basedir=/backup/inc2 \
    --user=bkpuser --password=xxx

# 查看各备份的 LSN 信息：
cat /backup/full/xtrabackup_checkpoints
# backup_type = full-backuped
# from_lsn = 0
# to_lsn = 1000000

cat /backup/inc1/xtrabackup_checkpoints
# backup_type = incremental
# from_lsn = 1000000
# to_lsn = 1200000

cat /backup/inc2/xtrabackup_checkpoints
# backup_type = incremental
# from_lsn = 1200000
# to_lsn = 1350000
```

## 增量备份的恢复

```bash
# 恢复增量备份需要按严格的顺序进行：

# 步骤1：Prepare 全量备份（只前滚，不回滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full
# --apply-log-only：只应用 redo log（前滚已提交事务）
# 不回滚未提交事务（因为后续增量可能包含这些事务的提交记录）

# 步骤2：应用第一个增量备份
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc1
# 将 inc1 中变化的数据页合并到 full 目录
# 同样使用 --apply-log-only

# 步骤3：应用第二个增量备份
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc2

# 步骤4：应用最后一个增量备份（不使用 --apply-log-only）
xtrabackup --prepare \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc3
# 最后一个增量不用 --apply-log-only
# 完成最终的前滚和回滚，得到一致性数据

# 步骤5：恢复数据
# systemctl stop mysqld
# rm -rf /var/lib/mysql/*
xtrabackup --copy-back --target-dir=/backup/full
# chown -R mysql:mysql /var/lib/mysql
# systemctl start mysqld
```

## --apply-log-only 的重要性

```
为什么中间的增量应用步骤必须使用 --apply-log-only？

正常的 prepare 过程包含两步：
  1. 前滚（Redo）：应用 redo log 中已提交事务的修改
  2. 回滚（Undo）：撤销未提交事务的修改

如果在中间步骤执行了回滚：
  某个事务在全量备份时未提交 → 被回滚
  但该事务在 inc1 中提交了 → inc1 中有该事务的提交记录
  全量备份中已经回滚了 → inc1 无法正确应用
  → 数据不一致

使用 --apply-log-only 的效果：
  只执行前滚，不执行回滚
  保留未提交事务的修改
  后续增量可能包含这些事务的提交或回滚记录
  在最后一个增量应用后再统一回滚

总结：
  全量 prepare：--apply-log-only ✓
  中间增量 prepare：--apply-log-only ✓
  最后增量 prepare：不用 --apply-log-only ✓（完成回滚）
```

## 增量备份的大小估算

```
增量备份的大小取决于数据变更的模式：

因素1：修改的数据页数量
  XtraBackup 以数据页（默认 16KB）为单位
  即使只修改了页中的一行，整个页都会被备份
  实际增量大小 ≥ 修改的行数 × 平均行大小
  实际增量大小 ≤ 修改的页数 × 16KB

因素2：数据变更的分布
  热点数据集中在少量页中 → 增量较小
  修改均匀分布在大量页中 → 增量较大

因素3：时间间隔
  增量间隔越长，变化的数据越多
  每天增量 vs 每小时增量

估算示例：
  数据库总大小：100GB
  每天修改约 5% 的数据页
  每天增量大小 ≈ 100GB × 5% = 5GB
  一周的增量总大小 ≈ 5GB × 6 = 30GB
  如果每天全量：100GB × 6 = 600GB
  增量策略节省存储：约 95%
```

## 增量备份参数详解

```bash
# 核心参数：

# --incremental-basedir=/path
# 指定增量基准目录（上一次备份的目录）
# XtraBackup 读取该目录中 xtrabackup_checkpoints 的 to_lsn
# 只备份 LSN > to_lsn 的数据页

# --incremental-lsn=N
# 直接指定增量基准 LSN（替代 --incremental-basedir）
# 适用于基准备份不在本地的场景
xtrabackup --backup \
    --target-dir=/backup/inc1 \
    --incremental-lsn=1000000 \
    --user=bkpuser --password=xxx

# --parallel=N
# 并行复制线程数（加速增量备份）
xtrabackup --backup \
    --target-dir=/backup/inc1 \
    --incremental-basedir=/backup/full \
    --parallel=4 \
    --user=bkpuser --password=xxx

# --compress
# 压缩增量备份（进一步减少空间）
xtrabackup --backup \
    --target-dir=/backup/inc1 \
    --incremental-basedir=/backup/full \
    --compress --compress-threads=4 \
    --user=bkpuser --password=xxx

# --throttle=N
# 限制 I/O 速率
```

## 适用场景

- **大型数据库的每日备份**：数据量在 100GB 以上的数据库，每天全量备份耗时过长且浪费存储。使用"每周全量 + 每天增量"的策略，每天增量只需备份变化的数据页，通常只有全量的 5%~10%
- **RPO（恢复点目标）要求严格的环境**：如果需要将数据恢复到更精确的时间点，可以增加增量备份的频率（如每小时一次），结合 binlog 实现分钟级的 RPO

## 常见问题

**增量链太长（如 30 个增量）会有什么问题？**

增量链过长会带来两个问题：①恢复时间增加——每个增量都需要依次应用到全量备份上，30 个增量需要 30 次 prepare 操作，恢复时间可能是全量恢复的数倍；②可靠性降低——增量链是链式依赖的，任何一个增量备份损坏都会导致后续增量无法使用。如果 inc15 损坏，inc16~inc30 都不可用，只能恢复到 inc14 的状态。建议增量链长度控制在 6~7 个以内（即每周一次全量备份）。如果业务需要更频繁的备份，可以增加全量备份频率（如每 3 天一次）来缩短增量链。

## 注意事项

- 增量备份的 `--incremental-basedir` 必须指向正确的上一次备份目录。如果指向错误的目录（如 LSN 不连续），恢复时数据可能不一致。在自动化脚本中应严格管理 basedir 的指向关系，建议在每次备份后记录 basedir 信息到日志文件。
- 增量备份的 prepare 顺序必须严格按照备份的时间顺序。跳过或乱序应用增量会导致数据损坏。如果不确定增量的顺序，可以通过 `xtrabackup_checkpoints` 文件中的 `from_lsn` 和 `to_lsn` 确认：每个增量的 `from_lsn` 应等于前一个备份的 `to_lsn`。

## 总结

XtraBackup 增量备份基于 InnoDB LSN 机制，只复制自上一次备份以来变化的数据页。命令：`xtrabackup --backup --incremental-basedir=/path`。恢复步骤：全量 prepare（`--apply-log-only`）→ 依次应用增量（`--apply-log-only`）→ 最后一个增量 prepare（不用 `--apply-log-only`）→ copy-back。中间步骤必须使用 `--apply-log-only` 防止提前回滚未提交事务。增量大小通常为全量的 5%~10%。增量链长度建议不超过 7 个。链式依赖——任一增量损坏影响后续所有增量。推荐策略：每周全量 + 每天增量。

# XtraBackup 准备阶段 prepare

XtraBackup 备份完成后，备份目录中的数据文件处于不一致状态——因为数据文件在复制过程中可能被其他事务修改，且可能包含未提交事务的修改。Prepare 阶段（也称为"准备"或"应用日志"阶段）通过将 redo log 应用到数据文件上，使数据文件达到一致性状态。这个过程类似于 InnoDB 在崩溃后的恢复过程。只有经过 prepare 的备份才能用于恢复。

---

## Prepare 的工作原理

```
Prepare 阶段执行两个核心操作：

1. 前滚（Redo / Roll Forward）
   读取备份中的 redo log（xtrabackup_logfile）
   将已提交事务的修改应用到数据文件
   确保所有已提交的数据都写入到数据文件中
   
   类比：数据库崩溃后启动时的 redo 恢复

2. 回滚（Undo / Roll Back）
   检查 undo log 中未提交的事务
   将未提交事务对数据文件的修改撤销
   恢复到事务开始前的状态
   
   类比：数据库崩溃后启动时的 undo 恢复

Prepare 完成后：
  所有已提交事务的数据 → 已写入数据文件
  所有未提交事务的修改 → 已撤销
  数据文件处于一致性状态
  等同于 MySQL 正常关闭后的数据目录状态
```

## 全量备份的 Prepare

```bash
# 全量备份的 prepare（最简单的场景）：
xtrabackup --prepare --target-dir=/backup/full

# 输出关键信息：
# InnoDB: Starting crash recovery...
# InnoDB: Applying batch of redo log records...
# InnoDB: ... (redo log applied)
# InnoDB: Starting to rollback unfinished transactions...
# InnoDB: Rollback of transactions completed
# ...
# 240615 03:30:00 completed OK!

# Prepare 完成后，备份可以直接用于恢复

# Prepare 是幂等的——可以多次执行
# 第二次执行 prepare 时不会改变数据
xtrabackup --prepare --target-dir=/backup/full
# 再次执行也不会出错
```

## 增量备份的 Prepare

```bash
# 增量备份的 prepare 需要特别注意 --apply-log-only 参数

# 场景：全量备份 + 3 个增量备份
# /backup/full, /backup/inc1, /backup/inc2, /backup/inc3

# 步骤1：Prepare 全量备份（只前滚，不回滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full
# --apply-log-only：只执行前滚（redo），不执行回滚（undo）
# 因为后续增量中可能包含当前未提交事务的提交记录

# 步骤2：应用第一个增量（只前滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc1
# 将 inc1 中变化的数据页合并到 /backup/full
# 仍然只前滚，不回滚

# 步骤3：应用第二个增量（只前滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc2

# 步骤4：应用最后一个增量（前滚 + 回滚）
xtrabackup --prepare \
    --target-dir=/backup/full \
    --incremental-dir=/backup/inc3
# 注意：最后一个增量 不使用 --apply-log-only
# 执行完整的前滚和回滚
# Prepare 完成后 /backup/full 中的数据是一致的

# 此时 /backup/full 目录包含了全量 + 所有增量的合并结果
# 可以用于恢复
```

## --apply-log-only 详解

```
--apply-log-only 参数的作用和使用规则：

使用场景：
  全量备份 prepare（后续有增量要应用）→ 使用
  中间增量 prepare → 使用
  最后一个增量 prepare → 不使用
  全量备份 prepare（无后续增量）→ 不使用

为什么中间步骤要用 --apply-log-only：
  事务 T1 在全量备份期间开始但未提交
  → 全量备份中有 T1 的部分修改

  如果 prepare 全量时执行回滚：
  → T1 的修改被撤销

  但 T1 在 inc1 期间提交了：
  → inc1 中有 T1 的提交记录
  → 应用 inc1 时，T1 的数据已经被回滚了
  → 数据不一致！

  使用 --apply-log-only 后：
  → T1 的修改保留（不回滚）
  → 应用 inc1 时，T1 被正确标记为已提交
  → 最后一步回滚时，只回滚真正未提交的事务
  → 数据一致

错误示范（不要这样做）：
  xtrabackup --prepare --target-dir=/backup/full  ← 回滚了未提交事务
  xtrabackup --prepare --target-dir=/backup/full \
      --incremental-dir=/backup/inc1  ← inc1 中的提交记录无法对应
  → 数据不一致！
```

## Prepare 过程的性能

```
Prepare 耗时取决于以下因素：

1. Redo log 的大小
   redo log 越大（备份期间写入越多），前滚耗时越长
   通常几秒到几分钟

2. 未提交事务的数量和大小
   大事务的回滚可能需要较长时间
   通常几秒到几分钟

3. 数据文件的大小
   Prepare 需要读写数据文件
   数据量越大，I/O 越多

4. 磁盘性能
   SSD 上 prepare 明显快于 HDD

参考数据：
  数据量 50GB，redo log 100MB → prepare 约 1~3 分钟
  数据量 500GB，redo log 1GB → prepare 约 5~15 分钟
  数据量 2TB，redo log 5GB → prepare 约 20~60 分钟

优化方法：
  --use-memory=4G  指定 prepare 时使用的内存
  增加可用内存可以加速 prepare 过程
  默认值通常足够，但大型备份可以增加到 4~8GB
```

```bash
# 使用更多内存加速 prepare：
xtrabackup --prepare \
    --target-dir=/backup/full \
    --use-memory=4G

# --use-memory=4G：分配 4GB 内存给 prepare 过程
# 更多的内存可以减少磁盘 I/O，加速前滚和回滚
```

## Prepare 后的验证

```bash
# 1. 检查 prepare 日志的最后一行
# 必须显示 "completed OK!"

# 2. 检查 xtrabackup_checkpoints
cat /backup/full/xtrabackup_checkpoints
# prepare 后 backup_type 应变为 full-prepared
# backup_type = full-prepared
# from_lsn = 0
# to_lsn = 123456789

# 3. 检查 InnoDB 日志中的信息
# prepare 日志中应显示：
# InnoDB: Shutdown completed; log sequence number 123456789
# 表示正常完成

# 4. 在测试环境验证恢复
# 将 prepare 后的备份恢复到测试实例
# 检查数据完整性和一致性
```

## 适用场景

- **备份后立即 prepare（提前准备恢复）**：在每次全量备份完成后立即执行 prepare，使备份处于"随时可恢复"状态。灾难发生时不需要等待 prepare，直接 copy-back 即可恢复
- **增量备份的合并**：将多个增量备份合并到全量备份上，形成包含所有变更的完整数据集，用于最终恢复

## 常见问题

**Prepare 失败了怎么办？**

Prepare 失败的常见原因：①备份不完整（备份过程中中断）——检查备份日志是否有 "completed OK!"；②磁盘空间不足（prepare 过程中需要额外空间）——清理磁盘空间后重试；③增量备份的顺序错误——检查 xtrabackup_checkpoints 中的 LSN 是否连续；④XtraBackup 版本与 MySQL 版本不匹配——使用兼容的版本。如果全量备份的 prepare 失败，需要重新执行全量备份。如果增量的 prepare 失败，可以尝试从全量备份重新开始 prepare 流程（前提是全量备份未被修改过——如果已经 prepare 过全量，需要使用原始未 prepare 的全量备份副本）。

---

## 注意事项

- Prepare 操作会修改 `--target-dir` 中的文件（将 redo log 应用到数据文件上）。如果 prepare 失败或数据损坏，原始备份文件也会被破坏。建议在 prepare 之前复制一份备份作为安全副本，特别是在处理增量备份链时。或者在存储层使用快照保护原始备份。
- Prepare 是单线程操作，不支持并行。即使设置了 `--parallel` 参数也不会影响 prepare 的速度。加速 prepare 的唯一方法是使用 `--use-memory` 增加内存分配和使用高性能存储（SSD）。

---

## 总结

Prepare 阶段通过应用 redo log（前滚）和撤销未提交事务（回滚）使备份数据达到一致性状态。全量备份 prepare：`xtrabackup --prepare --target-dir=/path`。增量备份 prepare：中间步骤使用 `--apply-log-only`（只前滚），最后一步不使用（完成回滚）。`--use-memory=NG` 增加内存加速 prepare。Prepare 会修改目标目录中的文件——建议保留原始备份副本。Prepare 后检查日志中的 "completed OK!" 和 xtrabackup_checkpoints 中的 `full-prepared` 状态。Prepare 是恢复前的必要步骤。

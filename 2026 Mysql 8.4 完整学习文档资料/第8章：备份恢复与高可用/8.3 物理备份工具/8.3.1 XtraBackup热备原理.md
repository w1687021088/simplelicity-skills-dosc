# XtraBackup 热备原理

Percona XtraBackup 是由 Percona 公司开发的开源 MySQL 物理热备份工具，可以在数据库正常运行、不停止服务的情况下完成 InnoDB 表的完整备份。XtraBackup 通过复制 InnoDB 的数据文件同时捕获 redo log 的变化，在 prepare 阶段将 redo log 应用到数据文件上，最终得到一个一致性的物理备份。它是生产环境中大型 MySQL 数据库备份的首选工具。

---

## 核心工作原理

```
XtraBackup 热备份的完整流程：

阶段1：复制 InnoDB 数据文件
  ┌──────────────────────────────────────────┐
  │ XtraBackup 启动                           │
  │ ↓                                        │
  │ 开启 redo log 复制线程（后台持续运行）      │
  │ ↓                                        │
  │ 逐个复制 InnoDB 表空间文件（*.ibd）        │
  │ 复制系统表空间（ibdata1）                  │
  │ 复制 undo 表空间                          │
  │                                          │
  │ 在此过程中：                               │
  │ - 数据库正常接受读写请求                    │
  │ - 数据文件在复制过程中可能被修改             │
  │ - redo log 复制线程持续捕获所有变化          │
  └──────────────────────────────────────────┘

阶段2：复制 non-InnoDB 数据（短暂加锁）
  ┌──────────────────────────────────────────┐
  │ FLUSH TABLES WITH READ LOCK（全局读锁）    │
  │ ↓                                        │
  │ 复制 MyISAM 表文件（*.MYD, *.MYI）        │
  │ 复制 .frm 文件（MySQL 8.0 前）            │
  │ 记录 binlog 位置                          │
  │ ↓                                        │
  │ UNLOCK TABLES（释放锁）                   │
  │                                          │
  │ 锁定时间通常很短（秒级到分钟级）             │
  └──────────────────────────────────────────┘

阶段3：停止 redo log 复制
  ┌──────────────────────────────────────────┐
  │ 停止 redo log 复制线程                     │
  │ 记录最终的 LSN（Log Sequence Number）      │
  │ 备份完成                                  │
  └──────────────────────────────────────────┘

此时的备份状态：
  数据文件可能包含不一致的页（复制过程中被修改）
  但 redo log 包含了所有修改的记录
  需要通过 prepare 阶段修复一致性
```

## Prepare 阶段（崩溃恢复）

```
Prepare 阶段的原理：

备份完成后的数据文件可能处于不一致状态：
  - 某些数据页在复制时已经被其他事务修改
  - 某些事务在备份期间已提交但数据页未刷盘
  - 某些事务在备份期间未提交

Prepare 过程（类似 InnoDB 的崩溃恢复）：
  1. 读取备份中的 redo log
  2. 将 redo log 中已提交事务的修改应用到数据文件（前滚）
  3. 将未提交事务的修改从数据文件中撤销（回滚）
  4. 最终数据文件处于一致状态

命令：
  xtrabackup --prepare --target-dir=/backup/full

Prepare 完成后：
  数据文件是一致的，可以直接用于恢复
  等同于 MySQL 正常关闭后的数据文件状态
```

## LSN（Log Sequence Number）机制

```sql
-- LSN 是 InnoDB 内部的递增序列号
-- 每次数据修改都会增加 LSN
-- XtraBackup 利用 LSN 实现增量备份

-- 查看当前 LSN：
SHOW ENGINE INNODB STATUS\G
-- Log sequence number: 123456789
-- Log flushed up to:   123456700
-- Last checkpoint at:  123456600

-- XtraBackup 备份时记录的 LSN 信息：
-- cat /backup/full/xtrabackup_checkpoints
-- backup_type = full-backuped
-- from_lsn = 0
-- to_lsn = 123456789       ← 备份结束时的 LSN
-- last_lsn = 123456800     ← 最后复制的 redo log 的 LSN

-- 增量备份时：
-- XtraBackup 只复制 LSN > to_lsn 的数据页
-- 大幅减少需要复制的数据量
```

## Redo Log 复制的细节

```
XtraBackup 如何确保不遗漏 redo log：

1. 在开始复制数据文件之前，先启动 redo log 复制线程
2. redo log 复制线程持续监控 InnoDB 的 redo log 文件
3. 一旦有新的 redo log 写入，立即复制到备份目录
4. 数据文件复制完成后，继续复制 redo log 直到停止

时间线示意：
  T0: 启动 redo log 复制
  T1: 开始复制数据文件
  ...
  T2: 数据文件复制完成
  T3: FTWRL（短暂锁定，复制 non-InnoDB）
  T4: 释放锁，停止 redo log 复制
  
  redo log 覆盖范围：T0 → T4
  数据文件复制范围：T1 → T2
  
  T0~T1 的 redo log：可能包含数据文件开始复制前的修改
  T1~T2 的 redo log：覆盖数据文件复制期间的所有修改
  T2~T4 的 redo log：数据文件复制后到锁定期间的修改
  
  通过 prepare 将所有 redo log 应用到数据文件 → 一致状态
```

## 适用场景

- **大型 InnoDB 数据库的在线热备**：数据量在 100GB 以上的生产数据库，XtraBackup 的物理复制速度远超 mysqldump 的逻辑导出，且不需要停止服务
- **需要增量备份能力的环境**：XtraBackup 支持基于 LSN 的增量备份，每天的增量备份只需复制变化的数据页，大幅减少备份时间和存储空间

## 常见问题

**XtraBackup 备份期间对生产数据库的性能影响有多大？**

XtraBackup 备份的主要性能影响来自两方面：①磁盘 I/O 读取——XtraBackup 需要读取所有数据文件，会增加磁盘读取负载。在 HDD 上影响较大（可能使 I/O 延迟增加 50%~100%），在 SSD 上影响较小（增加 10%~30%）。②全局读锁（FTWRL）——在备份 non-InnoDB 数据时短暂加全局锁，锁定时间通常在秒级。如果所有用户表都是 InnoDB，可以使用 `--no-lock` 选项跳过 FTWRL（但不会记录 binlog 位置）。建议在低峰期执行备份，并通过 `--throttle` 参数限制 I/O 速率（如 `--throttle=40` 限制每秒读取 40MB）。

## 注意事项

- XtraBackup 的版本必须与 MySQL 版本兼容。Percona XtraBackup 8.0 支持 MySQL 8.0，但不一定完全支持 MySQL 8.4 的所有新特性。升级到 MySQL 8.4 后，应使用最新版本的 XtraBackup（如 8.4.x），并在测试环境验证备份和恢复的完整性。
- XtraBackup 备份的是物理文件，恢复时目标 MySQL 的版本必须与备份时的版本一致（至少同一大版本）。不能用 8.0 的 XtraBackup 备份在 8.4 上恢复，反之亦然。跨版本迁移仍需使用逻辑备份（mysqldump）。

## 总结

Percona XtraBackup 通过并行复制 InnoDB 数据文件 + 持续捕获 redo log 实现热备份。备份后通过 prepare 阶段（前滚已提交事务 + 回滚未提交事务）获得一致性数据。基于 LSN 支持增量备份。备份过程中只在复制 non-InnoDB 数据时短暂加全局锁（FTWRL），对 InnoDB 数据的备份完全不锁表。适合大型数据库（>100GB）的生产环境。版本必须与 MySQL 兼容。不能跨大版本恢复。建议使用 `--throttle` 限制 I/O 减少性能影响。

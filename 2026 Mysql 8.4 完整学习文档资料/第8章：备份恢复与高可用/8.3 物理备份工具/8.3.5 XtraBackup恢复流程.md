# XtraBackup 恢复流程

XtraBackup 的恢复是将经过 prepare 的备份数据文件复制回 MySQL 数据目录的过程。恢复步骤包括：停止 MySQL 服务 → 清空数据目录 → 复制备份文件 → 修复文件权限 → 启动 MySQL。整个过程相对简单直接，但每一步都需要严格执行，任何遗漏都可能导致恢复失败。本文详细介绍全量恢复、增量恢复以及恢复后的验证流程。

---

## 全量备份的恢复

```bash
# 前提：备份已经完成 prepare
# xtrabackup --prepare --target-dir=/backup/full

# 步骤1：停止 MySQL 服务
systemctl stop mysqld
# 或
# mysqladmin -u root -p shutdown

# 确认 MySQL 已完全停止：
# ps aux | grep mysqld
# 确保没有 mysqld 进程在运行

# 步骤2：清空 MySQL 数据目录
# 警告：此操作不可逆！确保备份可用后再执行
rm -rf /var/lib/mysql/*
# 或者移动到临时位置（更安全）：
# mv /var/lib/mysql /var/lib/mysql_old
# mkdir /var/lib/mysql

# 步骤3：复制备份文件到数据目录
xtrabackup --copy-back --target-dir=/backup/full
# --copy-back：将备份文件复制到 datadir（由 my.cnf 决定）

# 或使用 --move-back（移动而非复制，更快但备份目录会被清空）：
# xtrabackup --move-back --target-dir=/backup/full
# 注意：--move-back 后备份目录不再可用

# 步骤4：修复文件权限
chown -R mysql:mysql /var/lib/mysql
# 确保 MySQL 进程有权读写所有数据文件

# 步骤5：启动 MySQL
systemctl start mysqld

# 步骤6：验证恢复
mysql -u root -p -e "SHOW DATABASES;"
mysql -u root -p -e "SELECT COUNT(*) FROM mydb.users;"
```

## 增量备份的恢复

```bash
# 假设有全量备份和 3 个增量备份：
# /backup/full, /backup/inc1, /backup/inc2, /backup/inc3

# 阶段1：Prepare（合并增量到全量）
# 详见 "8.3.4 XtraBackup准备阶段prepare"

# 1a. Prepare 全量（只前滚）
xtrabackup --prepare --apply-log-only --target-dir=/backup/full

# 1b. 应用增量1（只前滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full --incremental-dir=/backup/inc1

# 1c. 应用增量2（只前滚）
xtrabackup --prepare --apply-log-only \
    --target-dir=/backup/full --incremental-dir=/backup/inc2

# 1d. 应用增量3（前滚 + 回滚，最后一个不用 --apply-log-only）
xtrabackup --prepare \
    --target-dir=/backup/full --incremental-dir=/backup/inc3

# 阶段2：恢复（与全量恢复相同）
systemctl stop mysqld
rm -rf /var/lib/mysql/*
xtrabackup --copy-back --target-dir=/backup/full
chown -R mysql:mysql /var/lib/mysql
systemctl start mysqld
```

## 恢复后配合 binlog 做 PITR

```bash
# 如果需要恢复到备份之后的某个时间点：

# 步骤1：恢复 XtraBackup 备份（全量或增量）
# （按照上述流程完成恢复并启动 MySQL）

# 步骤2：查看备份中记录的 binlog 位置
cat /backup/full/xtrabackup_binlog_info
# mysql-bin.000015	154
# 或包含 GTID：
# mysql-bin.000015	154	server_uuid:1-1000

# 步骤3：从该位置开始重放 binlog 到目标时间点
mysqlbinlog --start-position=154 \
    --stop-datetime="2024-06-15 14:30:00" \
    /path/to/mysql-bin.000015 \
    /path/to/mysql-bin.000016 \
    | mysql -u root -p

# GTID 模式下：
mysqlbinlog --exclude-gtids="server_uuid:1-1000" \
    --stop-datetime="2024-06-15 14:30:00" \
    /path/to/mysql-bin.000015 \
    /path/to/mysql-bin.000016 \
    | mysql -u root -p

# 注意：binlog 文件必须在备份之外单独保存
# XtraBackup 不备份 binlog 文件
# 需要额外的 binlog 备份策略
```

## --copy-back vs --move-back

| 对比维度 | --copy-back | --move-back |
|---------|:-----------:|:-----------:|
| 操作方式 | 复制文件 | 移动文件 |
| 备份保留 | 保留原始备份 | 备份目录被清空 |
| 速度 | 较慢（复制数据）| 快（重命名/移动）|
| 磁盘空间 | 需要 2 倍空间 | 不需要额外空间 |
| 安全性 | 高（备份仍在）| 低（备份被移走）|
| 适用场景 | 有足够磁盘空间 | 磁盘空间紧张 |

```bash
# --copy-back（推荐，保留备份）：
xtrabackup --copy-back --target-dir=/backup/full
# 恢复后 /backup/full 仍然完整

# --move-back（快速，但备份被消耗）：
xtrabackup --move-back --target-dir=/backup/full
# 恢复后 /backup/full 被清空
# 如果恢复后发现问题，无法重新恢复

# 跨文件系统时 --move-back 可能退化为复制
# 如果备份目录和数据目录在不同的文件系统
# --move-back 实际上是复制 + 删除，速度与 --copy-back 相同
```

## 恢复后的验证清单

```sql
-- 恢复并启动 MySQL 后的验证步骤：

-- 1. 检查 MySQL 是否正常启动
-- 查看 Error Log 中有无错误
-- tail -50 /var/log/mysqld.log

-- 2. 检查所有数据库是否存在
SHOW DATABASES;

-- 3. 检查关键表的行数
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA NOT IN
    ('mysql','information_schema','performance_schema','sys')
ORDER BY TABLE_SCHEMA, TABLE_NAME;

-- 4. 检查用户和权限
SELECT User, Host, plugin FROM mysql.user;

-- 5. 检查 InnoDB 状态
SHOW ENGINE INNODB STATUS\G

-- 6. 执行业务关键查询验证数据正确性
-- SELECT ... 关键业务数据的验证查询

-- 7. 如果是复制环境，检查复制状态
SHOW REPLICA STATUS\G
-- 确认复制是否正常（如果需要重新配置复制）
```

## 适用场景

- **灾难恢复**：MySQL 服务器硬件故障、数据目录损坏、误操作导致数据丢失等紧急情况下，通过 XtraBackup 备份快速恢复数据库服务
- **搭建新的从库**：使用 XtraBackup 备份主库数据，恢复到新的从库服务器，然后配置复制关系，比 mysqldump 速度快得多

## 常见问题

**恢复后 MySQL 启动失败怎么办？**

常见原因和处理方法：①权限问题——`chown -R mysql:mysql /var/lib/mysql` 确保文件属于 mysql 用户；②SELinux 限制——`restorecon -Rv /var/lib/mysql` 恢复 SELinux 上下文，或临时关闭 SELinux 测试（`setenforce 0`）；③my.cnf 配置不匹配——如果备份来自不同的服务器，`datadir`、`innodb_data_home_dir`、`innodb_log_group_home_dir` 等路径可能不同，需要调整 my.cnf；④磁盘空间不足——确保数据目录所在分区有足够空间；⑤备份未正确 prepare——检查 prepare 日志是否有 "completed OK!"。Error Log（`/var/log/mysqld.log`）中通常有详细的错误信息。

## 注意事项

- 在执行 `rm -rf /var/lib/mysql/*` 之前，务必确认 XtraBackup 备份已经成功 prepare 且验证过完整性。一旦删除数据目录，原有数据不可恢复（除非有其他备份）。更安全的做法是将旧数据目录重命名（`mv /var/lib/mysql /var/lib/mysql_old`），恢复验证成功后再删除旧目录。
- 如果备份来自不同的服务器（如从主库备份恢复到从库），需要注意 `server_uuid` 和 `auto.cnf` 文件。恢复后的服务器会继承备份中的 `server_uuid`，如果在同一复制拓扑中使用，需要删除 `auto.cnf` 文件让 MySQL 启动时生成新的 `server_uuid`。

## 总结

XtraBackup 恢复流程：停止 MySQL → 清空数据目录 → `xtrabackup --copy-back`（或 `--move-back`）→ 修复权限（`chown -R mysql:mysql`）→ 启动 MySQL → 验证。恢复前备份必须经过 prepare。`--copy-back` 保留备份（安全），`--move-back` 不保留（快速）。恢复后配合 binlog 可做 PITR。验证步骤：检查 Error Log、数据库列表、表行数、用户权限、InnoDB 状态。从不同服务器恢复时注意 server_uuid 和路径配置。恢复从库时删除 auto.cnf 生成新 UUID。

# mysqldump 恢复 mysql 命令行

使用 mysql 命令行工具通过管道（重定向）方式恢复 mysqldump 备份文件，是生产环境中最常用的自动化恢复方式。与交互式 `source` 命令不同，管道恢复直接在操作系统命令行中执行，无需进入 mysql 交互界面，非常适合在 Shell 脚本、定时任务和自动化恢复流程中使用。

---

## 基本用法

```bash
# 最基本的恢复命令：
mysql -u root -p < /backup/backup.sql
# 输入密码后开始恢复

# 指定数据库恢复（备份不含 CREATE DATABASE 时）：
mysql -u root -p mydb < /backup/mydb_backup.sql

# 指定主机和端口：
mysql -h 192.168.1.100 -P 3306 -u root -p < /backup/backup.sql

# 使用配置文件（避免密码暴露）：
mysql --defaults-file=/etc/mysql/restore.cnf < /backup/backup.sql
# restore.cnf 内容：
# [client]
# user=root
# password=MyPassword123!

# 恢复压缩的备份文件：
# Linux:
gunzip < /backup/backup.sql.gz | mysql -u root -p
# 或
zcat /backup/backup.sql.gz | mysql -u root -p

# Windows PowerShell 恢复（注意编码问题）：
# mysql -u root -p mydb < D:\backup\mydb_backup.sql
# 如果遇到编码问题：
# Get-Content D:\backup\mydb_backup.sql -Raw | mysql -u root -p mydb
```

## 恢复参数优化

```bash
# 在恢复命令中添加优化参数：

# 增大 max_allowed_packet（处理大的 INSERT 语句）：
mysql -u root -p --max-allowed-packet=1G < /backup/backup.sql

# 关闭 binlog 记录（非复制环境）：
mysql -u root -p -e "SET sql_log_bin=0;" && \
mysql -u root -p --init-command="SET sql_log_bin=0" < /backup/backup.sql

# 使用 --init-command 设置会话参数：
mysql -u root -p \
    --init-command="SET foreign_key_checks=0; SET unique_checks=0; SET autocommit=0; SET sql_log_bin=0;" \
    < /backup/backup.sql

# 完整的优化恢复命令（生产环境推荐）：
mysql -u root -p \
    --max-allowed-packet=1073741824 \
    --init-command="SET foreign_key_checks=0; SET unique_checks=0; SET sql_log_bin=0;" \
    < /backup/all_databases_backup.sql
```

## 从全库备份中恢复单个数据库

```bash
# 使用 --one-database 参数只恢复指定的数据库：
mysql -u root -p --one-database mydb < /backup/all_databases.sql

# --one-database 的工作原理：
# 解析 SQL 文件，只执行属于指定数据库的语句
# 遇到 USE mydb 后开始执行，遇到 USE other_db 后停止
# 直到再次遇到 USE mydb

# 注意：--one-database 的限制
# 1. 不会创建数据库（需要先手动创建）
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS mydb"
mysql -u root -p --one-database mydb < /backup/all_databases.sql

# 2. 如果备份文件中 USE 语句后有全局操作（如 SET GLOBAL）
#    这些操作可能不会被执行

# 3. 恢复可能不完整——建议优先使用独立的数据库备份文件
```

## 管道恢复的错误处理

```bash
# 默认情况下，恢复过程中的错误会输出到 stderr
mysql -u root -p mydb < /backup/backup.sql 2> /tmp/restore_errors.log

# 同时记录输出和错误：
mysql -u root -p mydb < /backup/backup.sql > /tmp/restore.log 2>&1

# 使用 --force 参数忽略错误继续执行：
mysql -u root -p --force mydb < /backup/backup.sql 2> /tmp/errors.log
# --force：遇到错误不停止，继续执行后续语句
# 错误被记录到 errors.log 中
# 恢复完成后检查 errors.log 了解哪些语句失败

# 检查恢复是否成功（通过退出码）：
mysql -u root -p mydb < /backup/backup.sql
# echo $?  (Linux)
# echo $LASTEXITCODE  (PowerShell)
# 退出码 0 = 成功，非 0 = 有错误
```

## 自动化恢复脚本

```bash
#!/bin/bash
# 自动化恢复脚本示例（Linux）

BACKUP_FILE="/backup/all_databases_20240615.sql.gz"
MYSQL_USER="root"
MYSQL_PASS="MyPassword123!"
LOG_FILE="/var/log/mysql_restore_$(date +%Y%m%d_%H%M%S).log"

echo "$(date): 开始恢复 $BACKUP_FILE" | tee -a $LOG_FILE

# 预恢复优化
mysql -u $MYSQL_USER -p$MYSQL_PASS -e "
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
SET GLOBAL sync_binlog = 0;
" 2>> $LOG_FILE

# 执行恢复
gunzip < $BACKUP_FILE | mysql -u $MYSQL_USER -p$MYSQL_PASS \
    --max-allowed-packet=1073741824 \
    --init-command="SET foreign_key_checks=0; SET unique_checks=0;" \
    2>> $LOG_FILE

RESULT=$?

# 恢复安全参数
mysql -u $MYSQL_USER -p$MYSQL_PASS -e "
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;
FLUSH PRIVILEGES;
" 2>> $LOG_FILE

if [ $RESULT -eq 0 ]; then
    echo "$(date): 恢复成功" | tee -a $LOG_FILE
else
    echo "$(date): 恢复失败，退出码: $RESULT" | tee -a $LOG_FILE
    # 发送告警
fi
```

## source 命令与管道恢复的详细对比

| 对比维度 | source 命令 | mysql < file 管道恢复 |
|---------|:-----------:|:-------------------:|
| 执行环境 | mysql 交互会话内 | 操作系统命令行 |
| 脚本化 | 不方便 | 方便 |
| 进度显示 | 逐条显示 | 无中间输出 |
| 错误重定向 | 直接显示 | 可重定向到文件 |
| 压缩文件 | 需先解压 | 可管道解压 |
| 远程恢复 | 需先登录 mysql | 命令行直接执行 |
| 密码处理 | 交互输入 | 命令行或配置文件 |
| 中断后续处理 | 手动 | 可通过退出码判断 |

## 适用场景

- **自动化恢复流程**：在 Shell 脚本、定时任务、CI/CD 流水线中使用管道恢复，配合退出码检查和日志记录实现完整的自动化恢复流程
- **恢复压缩备份**：通过管道将 gunzip/zcat 的输出直接传给 mysql 命令，无需先解压再恢复，节省磁盘空间和时间

## 常见问题

**恢复过程中报 "ERROR 2006 (HY000): MySQL server has gone away" 怎么办？**

这个错误通常是因为 `max_allowed_packet` 太小，备份文件中某条 INSERT 语句超过了允许的包大小。解决方法：①在恢复命令中增加 `--max-allowed-packet=1G`；②在 my.cnf 的 `[mysqld]` 和 `[client]` 段都设置 `max_allowed_packet=1G`；③如果备份文件中使用了 `--extended-insert`（多行合并为一条 INSERT），单条 INSERT 可能非常大。也可能是服务器的 `wait_timeout` 太短，在大表导入之间的间隙超时断开。可以临时增大 `wait_timeout`：`SET GLOBAL wait_timeout=28800`。

## 注意事项

- 管道恢复时密码如果写在命令行中（`-pMyPassword`），会被记录在 Shell 历史中（`~/.bash_history`），存在安全风险。推荐使用 `--defaults-file` 指定配置文件，或使用 `-p` 交互输入密码。在自动化脚本中可以使用 `mysql_config_editor` 工具将凭据存储在加密文件中。
- 恢复大型备份文件可能耗时数小时。如果通过 SSH 远程操作，建议使用 `screen`、`tmux` 或 `nohup` 防止 SSH 断开导致恢复中断。命令示例：`nohup mysql -u root -p < backup.sql > restore.log 2>&1 &`。

## 总结

管道恢复（`mysql < file.sql`）是生产环境中最常用的自动化恢复方式。支持压缩文件管道解压恢复（`gunzip < file.sql.gz | mysql`）。优化参数：`--max-allowed-packet=1G`、`--init-command` 设置会话变量。`--one-database` 从全库备份中恢复单个库。`--force` 忽略错误继续执行。通过退出码（`$?`）判断恢复成功/失败。恢复前临时调整 `innodb_flush_log_at_trx_commit=0`、`sync_binlog=0` 提升速度，恢复后恢复为安全值。推荐使用配置文件存储凭据。

# 基于时间点恢复 PITR

PITR（Point-In-Time Recovery，时间点恢复）是将数据库恢复到指定时间点的技术。在 MySQL 中，PITR 通过组合全量备份和 Binary Log 重放来实现：先将数据库恢复到全量备份时刻的状态，再从备份时刻的 binlog 位置开始重放到目标时间点。PITR 是应对误操作、数据损坏等场景的核心恢复技术，也是评估备份恢复方案的重要指标（RPO，Recovery Point Objective）。

---

## PITR 的前提条件

```
执行 PITR 必须满足以下条件：

1. Binary Log 已启用
   log_bin = ON（MySQL 8.0+ 默认启用）
   binlog_format = ROW 或 MIXED（推荐 ROW 格式）

2. 有全量备份（包含备份时刻的 binlog 位置）
   mysqldump 备份：使用 --source-data=2 记录 binlog 位置
   XtraBackup 备份：xtrabackup_binlog_info 文件记录 binlog 位置

3. 从备份时刻到目标时刻之间的所有 binlog 文件可用
   binlog 文件必须连续，不能有缺失
   binlog 的保留期限应大于备份策略的间隔

4. 知道目标时间点
   通常是误操作发生的时间点（前一秒）
   或业务需要恢复到的特定时刻

查看 binlog 状态：
   SHOW VARIABLES LIKE 'log_bin';
   SHOW VARIABLES LIKE 'binlog_format';
   SHOW BINARY LOGS;   ← 列出所有 binlog 文件
```

## PITR 的完整操作流程

```bash
# 场景：2024-06-15 15:30 执行了 DELETE FROM orders WHERE 1=1
# 需要恢复到 15:29:59（误操作前一秒）

# 步骤1：确认全量备份和对应的 binlog 位置
# 假设最近全量备份在 03:00，备份文件：backup_20240615_030000.sql
# 查看备份中记录的 binlog 位置：
head -50 /backup/backup_20240615_030000.sql | grep "CHANGE REPLICATION SOURCE"
# -- CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='mysql-bin.000020',
# --   SOURCE_LOG_POS=157;
# 备份时的 binlog 文件：mysql-bin.000020，位置：157

# 步骤2：确认哪些 binlog 文件包含目标时间点的数据
SHOW BINARY LOGS;
# 检查哪些文件的创建时间覆盖了 03:00 到 15:29:59 这个时间段
mysqlbinlog --no-defaults mysql-bin.000020 | head -20
# 确认文件的起始时间

# 步骤3：停止 MySQL（如果还在运行）
# 或者停止应用写入（最小化数据影响）

# 步骤4：恢复全量备份
mysql -u root -p \
    --init-command="SET foreign_key_checks=0; SET sql_log_bin=0;" \
    < /backup/backup_20240615_030000.sql

# 步骤5：重放 binlog 到目标时间点
mysqlbinlog --no-defaults \
    --start-position=157 \
    --stop-datetime="2024-06-15 15:29:59" \
    /var/log/mysql/mysql-bin.000020 \
    /var/log/mysql/mysql-bin.000021 \
    /var/log/mysql/mysql-bin.000022 \
    | mysql -u root -p

# 步骤6：验证恢复结果
mysql -u root -p -e "SELECT COUNT(*) FROM mydb.orders;"
# 确认 orders 表中的数据已经恢复
```

## mysqlbinlog 在 PITR 中的用法

```bash
# 时间点控制参数：
# --start-datetime：从指定时间开始读取 binlog
# --stop-datetime：在指定时间停止读取 binlog
# 格式：YYYY-MM-DD HH:MM:SS

# 从备份的 binlog 位置开始，到误操作时间前停止：
mysqlbinlog \
    --start-position=157 \
    --stop-datetime="2024-06-15 15:29:59" \
    mysql-bin.000020 mysql-bin.000021 \
    | mysql -u root -p

# 先输出到文件检查内容，再决定是否执行：
mysqlbinlog \
    --start-position=157 \
    --stop-datetime="2024-06-15 15:29:59" \
    --verbose \
    mysql-bin.000020 > /tmp/binlog_to_apply.sql

# 检查输出内容（确认不包含误操作的 DELETE）：
# tail -100 /tmp/binlog_to_apply.sql
# grep -n "DELETE FROM orders" /tmp/binlog_to_apply.txt

# 确认后执行：
mysql -u root -p < /tmp/binlog_to_apply.sql

# 指定只重放特定数据库的 binlog：
mysqlbinlog --database=mydb \
    --start-position=157 \
    --stop-datetime="2024-06-15 15:29:59" \
    mysql-bin.000020 | mysql -u root -p
```

## GTID 模式下的 PITR

```bash
# 在 GTID 复制模式下，PITR 的操作略有不同

# 查看 GTID 模式：
SHOW VARIABLES LIKE 'gtid_mode';

# 全量备份中的 GTID 信息：
head -30 /backup/backup.sql | grep "gtid_purged"
# SET @@GLOBAL.gtid_purged='server_uuid:1-500';
# 表示备份包含了 GTID 1 到 500 的所有事务

# 恢复全量备份后，重放 binlog 到时间点：
mysqlbinlog --no-defaults \
    --stop-datetime="2024-06-15 15:29:59" \
    --skip-gtids \
    mysql-bin.000020 mysql-bin.000021 \
    | mysql -u root -p
# --skip-gtids：跳过 binlog 中的 GTID 信息
# 避免与 gtid_purged 冲突

# 或者排除特定 GTID（跳过误操作的事务）：
mysqlbinlog --no-defaults \
    --exclude-gtids="server_uuid:501" \
    mysql-bin.000020 mysql-bin.000021 \
    | mysql -u root -p
# 跳过 GTID 501（误操作的事务）
```

## 验证恢复结果

```sql
-- PITR 完成后的验证步骤：

-- 1. 检查关键表的数据
SELECT COUNT(*) FROM mydb.orders;
SELECT MAX(created_at) FROM mydb.orders;  -- 最新记录的时间

-- 2. 检查数据是否在目标时间点之前
-- 如果 orders 表最新记录的 created_at 在 15:30 之前，说明恢复正确

-- 3. 查看恢复到的 binlog 位置
SHOW BINARY LOG STATUS\G
-- 查看当前的 binlog 位置

-- 4. 如果恢复不完整（数据不对），分析原因：
-- 时间是否正确？--stop-datetime 的时间是否精确？
-- binlog 文件是否完整？是否有遗漏的文件？
-- binlog 格式是否是 ROW？（STATEMENT 格式下某些操作可能无法正确重放）

-- 5. 恢复后开放写入
-- 将应用程序切换回生产实例
-- 或在确认数据正确后停止原实例，将恢复实例升级为主库
```

## PITR 的 RPO 与 RTO

```
RPO（Recovery Point Objective）：可接受的数据丢失量
RTO（Recovery Time Objective）：可接受的恢复时间

PITR 的 RPO 取决于：
  - 全量备份的频率（越频繁，RPO 越小）
  - binlog 是否实时可用（是否有 binlog 延迟或丢失）
  - binlog 的保留策略（expire_logs_days / binlog_expire_logs_seconds）

理论 RPO：
  如果所有 binlog 都可用：RPO ≈ 最后一次已持久化的 binlog 事务
  即几乎为 0（只丢失最后一个 binlog 事务内的数据）

PITR 的 RTO 取决于：
  - 全量备份的恢复速度
  - 需要重放的 binlog 数量（距离备份的时间越长，binlog 越多）
  - 服务器性能

减小 RTO 的方法：
  - 使用物理备份（XtraBackup）替代逻辑备份（mysqldump）
  - 增加全量备份频率（减少需要重放的 binlog）
  - 备份后立即执行 prepare（物理备份）
  - 保持备份服务器随时处于"热备"状态
```

## 适用场景

- **误操作数据恢复**：DBA 或应用程序误执行了 DROP TABLE、大量 DELETE、错误 UPDATE 等操作，需要恢复到误操作前的最后一个时间点，最大限度减少数据丢失
- **满足合规性的 RPO 要求**：金融、医疗等行业的合规性标准要求将 RPO 控制在特定范围内（如 5 分钟以内），PITR 配合频繁的全量备份和连续的 binlog 可以满足这一要求

## 常见问题

**PITR 执行后如何确认恢复到了正确的时间点？**

可以通过以下方式验证：①查看关键表的最新记录时间戳（`SELECT MAX(updated_at) FROM orders`），确认最新记录在目标时间点之前；②在 binlog 分析阶段（步骤2），用 `mysqlbinlog --verbose --stop-datetime` 先输出 SQL 到文件，检查最后几条语句是否是预期的正常操作（不包含误操作）；③如果有应用层的数据快照或截图，对比恢复后的数据；④在测试环境先完整演练一遍，确认恢复时间点正确。如果发现恢复不到位（丢失了正常数据），可以适当调整 `--stop-datetime` 参数重新恢复（前提是全量备份未被覆盖）。

---

## 注意事项

- `mysqlbinlog --stop-datetime` 的时间是基于 binlog 事件的**服务器时间戳**，而非 mysqlbinlog 执行的时间。如果服务器时区配置与本地时区不同，`--stop-datetime` 的时间可能产生偏差。建议在 mysqlbinlog 命令中明确指定时区（`--set-charset=utf8`），或改用更精确的 `--stop-position` 参数。
- PITR 过程中应避免数据库接受新的业务写入。如果在恢复过程中有应用程序写入数据，会导致恢复结果混乱。建议在维护窗口内执行 PITR，或通过网络防火墙/应用层配置临时阻止写入操作，PITR 完成并验证后再恢复正常服务。

## 总结

PITR 通过"全量备份 + binlog 重放"将数据库恢复到指定时间点。前提：启用 binlog、有带位置信息的全量备份、binlog 文件连续可用。核心命令：`mysqlbinlog --start-position=N --stop-datetime="..." binlog... | mysql`。完整流程：恢复全量备份 → mysqlbinlog 重放 binlog 到目标时间 → 验证数据。GTID 模式下使用 `--skip-gtids` 或 `--exclude-gtids`。先将 binlog 输出到文件检查确认后再执行。适合误操作恢复和满足合规 RPO 要求的场景。PITR 期间应停止业务写入。

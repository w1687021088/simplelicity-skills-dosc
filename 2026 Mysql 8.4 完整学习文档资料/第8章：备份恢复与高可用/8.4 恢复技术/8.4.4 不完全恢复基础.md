# 不完全恢复基础

不完全恢复（Incomplete Recovery / Point-in-Time Recovery）是指不将数据库恢复到备份的最新状态，而是恢复到某个特定的时间点、binlog 位置或 GTID 位置。与完全恢复（恢复备份中的全部数据）不同，不完全恢复允许在恢复过程中"跳过"某些操作——比如跳过误执行的 DROP TABLE、DELETE 等破坏性操作，将数据库恢复到误操作发生之前的状态。

---

## 完全恢复与不完全恢复的区别

| 对比维度 | 完全恢复 | 不完全恢复 |
|---------|:------:|:--------:|
| 恢复目标 | 备份时刻的数据 | 指定时间点的数据 |
| 数据范围 | 备份中的全部数据 | 备份 + 部分 binlog |
| 是否需要 binlog | 不需要 | 需要 |
| 恢复精度 | 备份粒度 | 秒级甚至语句级 |
| 典型场景 | 数据库完全损坏 | 误操作恢复 |
| 复杂度 | 低 | 中到高 |

---

## 不完全恢复的前提条件

```
不完全恢复需要满足以下条件：

1. 有可用的全量备份
   mysqldump 备份（包含 --source-data 记录的 binlog 位置）
   或 XtraBackup 备份（包含 xtrabackup_binlog_info 记录的 binlog 位置）

2. 备份到目标恢复时间点之间的所有 binlog 文件可用
   如果 binlog 文件丢失或损坏，只能恢复到丢失之前的位置
   binlog 必须连续，不能有缺失

3. 知道需要恢复到的目标点
   具体时间（如 "2024-06-15 14:30:00"）
   或具体的 binlog 位置（如 mysql-bin.000015 Position 1234）
   或具体的 GTID（如 server_uuid:1-500）

4. 恢复期间数据库不接受新的写入
   恢复过程中如果有新数据写入会导致数据混乱

关键公式：
  恢复后的数据 = 全量备份数据 + 备份时刻到目标时刻的 binlog
```

---

## 不完全恢复的三种方式

```bash
# 方式1：基于时间点恢复（最常用）
# 恢复到指定的时间点，跳过该时间点之后的所有操作
mysqlbinlog --stop-datetime="2024-06-15 14:30:00" \
    mysql-bin.000015 mysql-bin.000016 | mysql -u root -p

# 方式2：基于位置恢复（最精确）
# 恢复到指定的 binlog 位置，跳过该位置之后的操作
mysqlbinlog --stop-position=1234 \
    mysql-bin.000015 | mysql -u root -p

# 方式3：基于 GTID 恢复
# 排除特定的 GTID（如误操作的事务）
mysqlbinlog --exclude-gtids="server_uuid:501" \
    mysql-bin.000015 | mysql -u root -p
```

## 不完全恢复的完整流程

```bash
# 场景：2024-06-15 14:35 有人误执行了 DROP TABLE users
# 需要恢复到 14:34:59（误操作前一秒）

# 步骤1：确认最近的全量备份
# 假设最近备份在 2024-06-15 03:00:00
# 备份中记录的 binlog 位置：mysql-bin.000015 Position 154

# 步骤2：确认需要的 binlog 文件
# 从 mysql-bin.000015 Position 154 到 14:34:59 之间的所有 binlog
# 可能涉及 mysql-bin.000015, mysql-bin.000016 等

# 步骤3：恢复全量备份
mysql -u root -p < /backup/full_backup_20240615_030000.sql

# 步骤4：重放 binlog 到误操作前
mysqlbinlog --start-position=154 \
    --stop-datetime="2024-06-15 14:34:59" \
    /var/lib/mysql/mysql-bin.000015 \
    /var/lib/mysql/mysql-bin.000016 \
    | mysql -u root -p

# 步骤5：验证恢复结果
mysql -u root -p -e "SELECT COUNT(*) FROM mydb.users;"
# 确认 users 表存在且数据正确

# 步骤6：如果需要继续恢复误操作之后的正常数据
# 跳过 DROP TABLE 语句，继续重放后续 binlog
# 这需要先找到 DROP TABLE 的位置，跳过它
```

## mysqlbinlog 的关键参数

```bash
# 时间范围控制：
--start-datetime="YYYY-MM-DD HH:MM:SS"  # 开始时间
--stop-datetime="YYYY-MM-DD HH:MM:SS"   # 结束时间

# 位置范围控制：
--start-position=N    # 开始位置（偏移量）
--stop-position=N     # 结束位置

# GTID 控制：
--include-gtids="uuid:N-M"   # 只包含指定的 GTID
--exclude-gtids="uuid:N"     # 排除指定的 GTID

# 数据库过滤：
--database=mydb    # 只输出指定数据库的事件

# 输出控制：
--verbose (-v)     # 显示行事件的详细内容
--base64-output=DECODE-ROWS  # 解码行事件

# 组合使用示例：
mysqlbinlog \
    --start-position=154 \
    --stop-datetime="2024-06-15 14:34:59" \
    --database=mydb \
    mysql-bin.000015 | mysql -u root -p
```

## 分析 binlog 定位误操作

```bash
# 在执行不完全恢复前，需要先分析 binlog 定位误操作的位置

# 1. 查看 binlog 事件列表（在 mysql 中）
SHOW BINLOG EVENTS IN 'mysql-bin.000015' LIMIT 100;

# 2. 查看指定位置之后的事件
SHOW BINLOG EVENTS IN 'mysql-bin.000015' FROM 1000 LIMIT 50;

# 3. 使用 mysqlbinlog 解析 binlog 文件
mysqlbinlog --verbose \
    --start-datetime="2024-06-15 14:30:00" \
    --stop-datetime="2024-06-15 14:40:00" \
    mysql-bin.000015 > /tmp/binlog_analysis.txt

# 4. 在解析结果中搜索误操作
# grep -n "DROP TABLE" /tmp/binlog_analysis.txt
# grep -n "DELETE FROM" /tmp/binlog_analysis.txt

# 5. 找到误操作的位置信息
# 典型输出：
# # at 12345          ← 事件开始位置
# #240615 14:35:00 server id 1  end_log_pos 12500 ...
# DROP TABLE `users`
# 误操作位置：12345，结束位置：12500

# 恢复策略：
# 重放 binlog 到位置 12345 之前（--stop-position=12345）
# 如果需要跳过误操作继续重放：
# 再从位置 12500 开始重放（--start-position=12500）
```

## 适用场景

- **误操作恢复**：DBA 或开发人员误执行了 DROP TABLE、DELETE（无 WHERE 条件）、TRUNCATE TABLE 等破坏性操作，需要将数据恢复到误操作发生之前的状态
- **数据损坏的精确恢复**：数据库在某个时间点出现数据异常（如应用 bug 导致错误数据写入），需要恢复到异常发生之前的正确状态

---

## 常见问题

**如果备份到目标时间点之间的某个 binlog 文件丢失了怎么办？**

如果 binlog 文件链有缺失，就无法完整地恢复到目标时间点。只能恢复到缺失文件之前的最后可用位置。例如，备份时 binlog 位置在 mysql-bin.000015，目标时间点在 mysql-bin.000018，但 mysql-bin.000016 丢失了，那么只能恢复到 mysql-bin.000015 的末尾。这就是为什么 binlog 的备份和保护非常重要——建议将 binlog 实时同步到远程存储或专用的 binlog 服务器（`mysqlbinlog --read-from-remote-server --raw --stop-never`），确保 binlog 不会因为磁盘故障而丢失。

---

## 注意事项

- 不完全恢复是一个不可逆的操作。一旦将 binlog 重放到数据库中，无法"撤销"已重放的内容。建议在生产环境执行不完全恢复前，先在测试环境中完整演练一遍，确认恢复结果正确后再在生产环境执行。或者先将全量备份恢复到一个临时实例，在临时实例上重放 binlog 验证结果。
- 基于时间点的恢复可能不够精确——如果在同一秒内有多条 SQL 语句执行，`--stop-datetime` 无法精确到语句级别。需要更精确的控制时，应使用 `--stop-position` 基于 binlog 位置恢复，或使用 `--exclude-gtids` 基于 GTID 恢复。

---

## 总结

不完全恢复将数据库恢复到特定时间点而非备份时刻。前提：全量备份 + 连续的 binlog 文件 + 明确的恢复目标点。三种方式：基于时间（`--stop-datetime`）、基于位置（`--stop-position`）、基于 GTID（`--exclude-gtids`）。流程：恢复全量备份 → 用 mysqlbinlog 重放 binlog 到目标点。恢复前需分析 binlog 定位误操作的精确位置（`SHOW BINLOG EVENTS` 或 `mysqlbinlog --verbose`）。binlog 文件必须连续不可缺失。建议先在测试环境演练。基于位置的恢复比基于时间更精确。

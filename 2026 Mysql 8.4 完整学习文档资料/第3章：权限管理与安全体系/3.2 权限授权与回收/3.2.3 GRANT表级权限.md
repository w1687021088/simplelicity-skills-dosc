# GRANT 表级权限

表级权限（Table-level Privilege）使用 `GRANT privilege ON dbname.tablename TO user` 语法授予，将权限精确限定到某个具体的表。这是比数据库级权限更细粒度的控制，适合需要跨库访问特定表、或在同一数据库内对不同表设置不同访问策略的场景。

---

## 语法

```sql
GRANT privilege_type [, privilege_type] ...
    ON database_name.table_name
    TO 'user'@'host';
```

---

## 支持的表级权限

| 权限名称 | 说明 |
|---------|------|
| SELECT | 查询该表 |
| INSERT | 向该表插入数据 |
| UPDATE | 更新该表中的数据 |
| DELETE | 删除该表中的数据 |
| CREATE | 在该数据库中创建表（表级 CREATE 实际作用于数据库）|
| DROP | 删除该表 |
| ALTER | 修改该表的结构 |
| INDEX | 在该表上创建/删除索引 |
| TRIGGER | 在该表上创建/删除触发器 |
| REFERENCES | 在该表上创建外键约束 |

---

## 基本示例

```sql
-- 只授予对特定表的查询权限
GRANT SELECT ON myapp.orders TO 'report_user'@'%';

-- 授予对敏感表的只读权限，对其他表有更多权限
-- 先授予整库 DML
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'app_user'@'%';
-- 再单独限制敏感表只能查询（不能修改）——表级权限会与库级权限叠加，不会替换

-- 跨库访问特定表
GRANT SELECT ON finance_db.exchange_rates TO 'logistics_user'@'%';
-- logistics_user 只能访问 finance_db 库中的 exchange_rates 表
-- 不能访问 finance_db 中的其他表

-- 对多个特定表授权
GRANT SELECT ON myapp.products TO 'external_api'@'%';
GRANT SELECT ON myapp.categories TO 'external_api'@'%';
GRANT SELECT ON myapp.brands TO 'external_api'@'%';
-- 只能访问这三张表，无法访问 myapp 中的其他表
```

---

## 权限的叠加规则

```sql
-- MySQL 权限是各级别权限的并集
-- 假设：全局有 SELECT，数据库级有 INSERT，表级有 DELETE
-- 则对该表的有效权限 = SELECT + INSERT + DELETE

-- 示例：
GRANT SELECT ON *.* TO 'mixed_user'@'%';                 -- 全局 SELECT
GRANT INSERT ON myapp.* TO 'mixed_user'@'%';             -- 库级 INSERT
GRANT UPDATE, DELETE ON myapp.orders TO 'mixed_user'@'%'; -- 表级 UPDATE+DELETE

-- mixed_user 对 myapp.orders 的实际权限：SELECT + INSERT + UPDATE + DELETE
-- mixed_user 对 myapp.products 的实际权限：SELECT + INSERT（没有 UPDATE/DELETE）
-- mixed_user 对其他数据库的表：只有 SELECT
```

## 查看表级权限

```sql
-- 查看某用户的所有权限
SHOW GRANTS FOR 'external_api'@'%';
-- 输出示例：
-- GRANT USAGE ON *.* TO 'external_api'@'%'
-- GRANT SELECT ON `myapp`.`products` TO 'external_api'@'%'
-- GRANT SELECT ON `myapp`.`categories` TO 'external_api'@'%'

-- 从 information_schema 查询表级权限
SELECT GRANTEE, TABLE_CATALOG, TABLE_SCHEMA, TABLE_NAME, PRIVILEGE_TYPE
FROM information_schema.TABLE_PRIVILEGES
WHERE GRANTEE = "'external_api'@'%'"
ORDER BY TABLE_SCHEMA, TABLE_NAME;
```

## 表级权限与视图

```sql
-- 可以对视图授予表级权限，与表相同
GRANT SELECT ON myapp.v_order_summary TO 'report_user'@'%';

-- 通过视图控制权限是常见的安全模式：
-- 1. 创建只暴露必要列的视图（隐藏敏感列）
CREATE VIEW v_user_public AS
    SELECT id, username, created_at FROM users;  -- 不包含 email、phone 等

-- 2. 只给视图授权，不给底层表授权
GRANT SELECT ON myapp.v_user_public TO 'external_app'@'%';
-- external_app 无法查询 users 表，但可以通过视图查询公开信息
```

## 适用场景

- **跨库最小权限**：某账号需要访问其他业务库的特定表（如汇率表、配置表）
- **敏感表隔离**：同一数据库中，对用户信息、支付信息等敏感表限制为只读或无权限
- **外部 API 账号**：第三方合作方账号只能访问合同约定的特定表
- **审计账号**：只能读取特定的日志表或审计表

---

## 常见问题

**表级权限能阻止有数据库级 DROP 权限的用户删除该表吗？**

不能。权限是叠加的，如果用户有数据库级 DROP 权限，那对该数据库中的所有表都有 DROP 权限，无法通过表级权限覆盖。要限制 DROP 权限，需要在数据库级不授予 DROP，然后通过表级权限单独授予需要的权限（这样就没有 DROP 权限了）。

---

## 注意事项

- 表级权限存储在 `mysql.tables_priv` 系统表中，而不是 `mysql.user` 或 `mysql.db` 表。
- 对大量表逐一设置表级权限（如50张表各自单独授权）会导致权限管理复杂，难以维护。更好的方案是先在数据库级授予较宽泛的权限，再通过角色或专用视图来控制访问。

---

## 总结

表级权限通过 `GRANT privilege ON db.table TO user` 将权限精确到具体表。表级权限与全局权限、数据库级权限**叠加**生效，不会互相覆盖。适用于跨库访问特定表、敏感表隔离等精细权限控制场景。表级权限存储在 `mysql.tables_priv` 中，可通过 `information_schema.TABLE_PRIVILEGES` 查询。结合视图使用可以实现列级别的访问控制。

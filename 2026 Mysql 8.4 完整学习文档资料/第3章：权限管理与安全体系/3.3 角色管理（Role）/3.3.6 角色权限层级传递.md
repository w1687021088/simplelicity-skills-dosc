# 角色权限层级传递

MySQL 的角色支持嵌套（角色可以被授予给另一个角色），形成权限的层级传递。当用户激活一个包含子角色的角色时，会递归获得所有层级角色中的权限，无需逐一激活每个子角色。这种机制使权限的层级设计和批量管理成为可能。

---

## 权限层级传递的原理

```
角色授予关系（mysql.role_edges 表）：
  base_read_role ──┐
                    ├── extended_role ──┐
  base_write_role ─┘                   ├── full_access_role ── user_alice
  reports_role ───────────────────────┘
```

```sql
-- 创建层级角色
CREATE ROLE 'base_read_role', 'base_write_role', 'reports_role';
CREATE ROLE 'extended_role', 'full_access_role';

-- 向基础角色授予权限
GRANT SELECT ON myapp.* TO 'base_read_role';
GRANT INSERT, UPDATE, DELETE ON myapp.* TO 'base_write_role';
GRANT SELECT ON reporting.* TO 'reports_role';

-- 将基础角色嵌套到 extended_role
GRANT 'base_read_role', 'base_write_role' TO 'extended_role';

-- 将 extended_role 和 reports_role 嵌套到 full_access_role
GRANT 'extended_role', 'reports_role' TO 'full_access_role';

-- 将 full_access_role 授予用户
GRANT 'full_access_role' TO 'alice'@'%';
SET DEFAULT ROLE 'full_access_role' TO 'alice'@'%';
-- alice 激活 full_access_role 后，通过层级传递获得：
-- SELECT ON myapp.* (来自 base_read_role)
-- INSERT, UPDATE, DELETE ON myapp.* (来自 base_write_role)
-- SELECT ON reporting.* (来自 reports_role)
```

---

## 查看权限传递关系

```sql
-- 查看 role_edges 表（所有角色授予关系）
SELECT FROM_USER AS parent_role, FROM_HOST,
       TO_USER   AS child_role_or_user, TO_HOST
FROM mysql.role_edges
ORDER BY FROM_USER;

-- 递归查看某角色的所有权限（包含嵌套角色）
SHOW GRANTS FOR 'full_access_role' USING 'extended_role', 'reports_role';
-- 注意：SHOW GRANTS ... USING 只展开一层，不递归

-- 查看用户通过角色获得的完整有效权限
SHOW GRANTS FOR 'alice'@'%' USING 'full_access_role';
-- 输出中会包含 full_access_role 层层继承的所有权限
```

## 角色嵌套示例：RBAC 模式

```sql
-- 构建一个典型的 RBAC（Role-Based Access Control）层级

-- 基础权限角色
CREATE ROLE 'perm_select_orders', 'perm_write_orders', 'perm_manage_products';
GRANT SELECT ON myapp.orders TO 'perm_select_orders';
GRANT INSERT, UPDATE ON myapp.orders TO 'perm_write_orders';
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.products TO 'perm_manage_products';

-- 职能角色（由基础权限角色组合而成）
CREATE ROLE 'role_sales', 'role_inventory_manager', 'role_store_manager';
GRANT 'perm_select_orders', 'perm_write_orders' TO 'role_sales';
GRANT 'perm_manage_products' TO 'role_inventory_manager';
GRANT 'role_sales', 'role_inventory_manager' TO 'role_store_manager';
-- role_store_manager = role_sales + role_inventory_manager 的全部权限

-- 创建用户并分配职能角色
CREATE USER 'emp_zhang'@'%' IDENTIFIED BY 'ZhangP@ss1';
GRANT 'role_sales' TO 'emp_zhang'@'%';
SET DEFAULT ROLE 'role_sales' TO 'emp_zhang'@'%';

CREATE USER 'manager_li'@'%' IDENTIFIED BY 'LiP@ss1';
GRANT 'role_store_manager' TO 'manager_li'@'%';
SET DEFAULT ROLE 'role_store_manager' TO 'manager_li'@'%';
```

## 层级修改的影响

```sql
-- 修改基础角色的权限，所有继承链上的用户自动受益

-- 给 perm_select_orders 添加 SELECT on products
GRANT SELECT ON myapp.products TO 'perm_select_orders';
-- 自动效果：
-- role_sales（包含 perm_select_orders）立即有 SELECT on products
-- emp_zhang 激活 role_sales 后，也自动有 SELECT on products
-- role_store_manager（包含 role_sales）也自动有该权限
-- manager_li 也自动有该权限
-- 只修改了一处，整个继承链自动更新
```

## 适用场景

- **企业 RBAC 模型**：将权限抽象为基础权限角色，再组合为职能角色，按组织层级分配
- **SaaS 多租户**：每个租户有自己的角色层级，基础权限角色可以跨租户共享
- **按模块管理**：每个业务模块有自己的读/写角色，系统管理员角色包含所有模块角色

## 常见问题

**嵌套角色的层数有限制吗？**

MySQL 文档没有明确说明嵌套层数的硬限制，但实际上层数过深（超过 16 层）可能影响性能，因为权限检查需要递归解析角色关系。实际设计中通常 2-3 层已足够（基础权限 → 职能角色 → 管理层角色）。

---

## 注意事项

- 角色嵌套中不能出现循环引用（A 包含 B，B 包含 A），MySQL 会拒绝这样的授权：`ERROR 3723: Circular role grants`。
- 从继承链的某个角色中撤销权限，效果会沿链传递——撤销 `base_read_role` 的 SELECT 权限，所有通过继承链持有该角色的用户都会失去 SELECT 权限（在下次权限检查时）。

---

## 总结

角色支持嵌套（`GRANT role TO another_role`），形成权限层级。用户激活一个角色后，递归获得该角色所有子角色中的权限，无需逐一激活子角色。权限关系存储在 `mysql.role_edges` 表。修改基础角色权限后，整个继承链上的用户自动受影响，是权限集中管理的核心优势。不允许循环引用角色。

# 角色与用户区别

MySQL 中的角色和用户在底层共享相同的存储结构（`mysql.user` 表），但在设计意图、使用方式和行为上有明显差异。理解这些差异有助于在实际权限设计中正确选择角色还是用户账户。

---

## 存储结构的相似性

```sql
-- 角色和用户都存储在 mysql.user 表中
SELECT User, Host, account_locked, password_expired, authentication_string, plugin
FROM mysql.user
WHERE User IN ('alice', 'app_read_role')
ORDER BY account_locked;

-- 用户（alice）的特征：
-- account_locked = N（可以登录）
-- authentication_string 非空（有密码哈希）
-- plugin = caching_sha2_password（有认证插件）

-- 角色（app_read_role）的特征：
-- account_locked = Y（不能直接登录）
-- authentication_string = ''（无密码）
-- plugin = ''（无认证插件）
```

---

## 核心区别对比

| 维度 | 用户（User）| 角色（Role）|
|------|------------|------------|
| 能否登录 | 能（有密码和认证插件）| 不能（被锁定、无密码）|
| 主要用途 | 标识一个连接实体（人或应用程序）| 权限集合的载体 |
| 权限激活 | 登录后自动拥有直接授予的权限 | 需要被 GRANT 给用户后，再由用户激活 |
| 创建方式 | CREATE USER | CREATE ROLE 或 CREATE USER（特殊写法）|
| 删除方式 | DROP USER | DROP ROLE 或 DROP USER |
| 能否授权给其他账号 | 不常见（可以，但不推荐）| 是（被 GRANT 给用户或其他角色）|
| 能否嵌套 | 不能直接嵌套 | 角色可以被授予另一个角色（角色嵌套）|

---

## 角色可以嵌套

```sql
-- 角色可以被授予给另一个角色（创建权限层级）
CREATE ROLE 'base_read';
CREATE ROLE 'base_write';
CREATE ROLE 'full_access';

-- 向基础角色授权
GRANT SELECT ON myapp.* TO 'base_read';
GRANT INSERT, UPDATE, DELETE ON myapp.* TO 'base_write';

-- 将基础角色嵌套进全权角色
GRANT 'base_read', 'base_write' TO 'full_access';
-- full_access 现在包含 SELECT + INSERT + UPDATE + DELETE

-- 将 full_access 授予用户
GRANT 'full_access' TO 'charlie'@'%';
SET DEFAULT ROLE 'full_access' TO 'charlie'@'%';

-- charlie 激活 full_access 后，通过嵌套获得 base_read 和 base_write 中的所有权限
SHOW GRANTS FOR 'charlie'@'%' USING 'full_access';
```

---

## 用户也可以被赋予角色

```sql
-- 同一个用户既可以有直接授予的权限，又可以有通过角色获得的权限
CREATE USER 'hybrid_user'@'%' IDENTIFIED BY 'HybridP@ss1';

-- 直接授予全局查看进程权限
GRANT PROCESS ON *.* TO 'hybrid_user'@'%';

-- 通过角色获得数据库级 DML 权限
GRANT 'app_write_role' TO 'hybrid_user'@'%';
SET DEFAULT ROLE 'app_write_role' TO 'hybrid_user'@'%';

-- hybrid_user 的有效权限 = PROCESS（直接）+ app_write_role 的权限（角色）
```

---

## 角色激活机制（用户没有此概念）

```sql
-- 角色被 GRANT 给用户后，不一定立即生效
-- 用户需要"激活"角色才能使用角色中的权限

-- 查看当前会话激活的角色
SELECT CURRENT_ROLE();

-- 激活所有已授予的角色（当前会话有效）
SET ROLE ALL;

-- 激活指定角色
SET ROLE 'app_read_role';

-- 不激活任何角色
SET ROLE NONE;

-- 设置登录时默认激活的角色（永久设置）
SET DEFAULT ROLE ALL TO 'alice'@'%';
-- alice 以后每次登录都自动激活所有已授予的角色
```

---

## mandatory_roles 全局配置（MySQL 8.0+）

```sql
-- 通过 mandatory_roles 变量，让所有用户自动获得指定角色（无需 GRANT）
SHOW VARIABLES LIKE 'mandatory_roles';
-- 默认为空

-- 设置强制角色（所有用户都自动拥有，不能撤销）
SET GLOBAL mandatory_roles = 'base_read_role';

-- 或在 my.cnf 中配置（持久化）：
-- [mysqld]
-- mandatory_roles='base_read_role'

-- 使用 mandatory_roles 后，base_read_role 的权限自动对所有用户生效
-- 不需要单独 GRANT 和 SET DEFAULT ROLE
```

---

## 适用场景

- **需要具体登录账户时**：使用 User（应用程序账户、DBA 账户等）
- **需要权限集合重复分配时**：使用 Role（为多个用户分配相同权限集合）
- **权限层级设计**：使用角色嵌套（base_read → extended_access → full_access）

---

## 常见问题

**可以用 CREATE USER 创建一个"假装角色"的账户吗？**

技术上可以创建一个特殊的 User（无密码、锁定），模拟角色的行为，但 `CREATE ROLE` 更规范——它创建的账户被明确标记为角色，在 SHOW GRANTS 和系统视图中有专门处理，也不需要手动设置锁定和空密码。

---

## 注意事项

- 角色在 `activate_all_roles_on_login` 变量为 ON 时自动激活（不需要设置默认角色）。默认该变量为 OFF，用户登录后需要手动激活角色或设置 DEFAULT ROLE。
- 可以通过 `SET GLOBAL activate_all_roles_on_login = ON` 全局开启自动激活，这样所有用户登录后所有已授予的角色都自动激活，简化管理，但减少了角色激活的精细控制。

---

## 总结

角色与用户共享底层存储，但角色被锁定（不能登录）、无密码，用于封装权限集合并授予给用户。角色需要"激活"才能在会话中生效，通过 `SET DEFAULT ROLE` 或 `activate_all_roles_on_login` 自动激活。角色支持嵌套（角色授予角色），可以构建权限层级。`mandatory_roles` 变量可以让所有用户自动拥有指定角色。

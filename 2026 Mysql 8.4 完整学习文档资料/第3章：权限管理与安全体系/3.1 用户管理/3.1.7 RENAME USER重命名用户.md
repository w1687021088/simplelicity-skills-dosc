# RENAME USER 重命名用户

`RENAME USER` 语句修改 MySQL 账户的名称（用户名或主机名，或两者同时）。重命名后，原有账户的所有权限、密码和属性都会随之迁移到新名称，不需要重新授权。该语句等效于更改账户的标识，而非重建账户。

---

## 语法

```sql
RENAME USER old_user TO new_user [, old_user TO new_user] ...
-- old_user 和 new_user 格式均为 'username'@'host'
```

---

## 基本示例

```sql
-- 修改用户名（主机名不变）
RENAME USER 'alice'@'%' TO 'alice_zhang'@'%';

-- 修改主机名（用户名不变）
RENAME USER 'alice'@'%' TO 'alice'@'192.168.1.%';

-- 同时修改用户名和主机名
RENAME USER 'alice'@'%' TO 'alice_new'@'192.168.1.%';

-- 同时重命名多个用户
RENAME USER
    'alice'@'%'     TO 'alice_zhang'@'%',
    'bob'@'localhost' TO 'bob_li'@'localhost';
```

---

## 重命名对权限的影响

```sql
-- 重命名前查看 alice 的权限
SHOW GRANTS FOR 'alice'@'%';
-- GRANT SELECT, INSERT ON mydb.* TO 'alice'@'%'

-- 执行重命名
RENAME USER 'alice'@'%' TO 'alice_zhang'@'%';

-- 重命名后，权限自动转移到新名称
SHOW GRANTS FOR 'alice_zhang'@'%';
-- GRANT SELECT, INSERT ON mydb.* TO 'alice_zhang'@'%'  ← 权限已自动更新

-- 原名称不再存在
SHOW GRANTS FOR 'alice'@'%';
-- ERROR 1141 (42000): There is no such grant defined for user 'alice' on host '%'
```

---

## 重命名对存储对象的影响

```sql
-- 与 DROP USER 类似，RENAME USER 不会自动更新存储对象中的 DEFINER
-- 如果 'alice'@'%' 是某些视图/存储过程的 DEFINER

-- 查找受影响的存储过程
SELECT ROUTINE_SCHEMA, ROUTINE_NAME, DEFINER
FROM information_schema.ROUTINES
WHERE DEFINER = 'alice@%';

-- 查找受影响的视图
SELECT TABLE_SCHEMA, TABLE_NAME, DEFINER
FROM information_schema.VIEWS
WHERE DEFINER = 'alice@%';

-- 查找受影响的触发器
SELECT TRIGGER_SCHEMA, TRIGGER_NAME, DEFINER
FROM information_schema.TRIGGERS
WHERE DEFINER = 'alice@%';

-- 这些对象的 DEFINER 仍然是旧名称，在调用时会报错
-- 需要找到这些对象并修改 DEFINER（需要 DROP + CREATE 重建）
```

---

## 验证重命名结果

```sql
-- 验证新用户名存在
SELECT User, Host FROM mysql.user WHERE User = 'alice_zhang';

-- 验证旧用户名不存在
SELECT User, Host FROM mysql.user WHERE User = 'alice';
-- 空结果集

-- 确认权限已迁移
SHOW GRANTS FOR 'alice_zhang'@'%';
```

---

## 所需权限

```sql
-- 执行 RENAME USER 需要 CREATE USER 权限
SHOW GRANTS FOR CURRENT_USER();

-- 没有权限时报错：
-- ERROR 1227 (42000): Access denied; you need (at least one of) the CREATE USER privilege(s)
-- for this operation
```

---

## 与 DROP + CREATE 的对比

| 操作方式 | 权限迁移 | 密码保留 | 属性保留 | 操作复杂度 |
|---------|---------|---------|---------|----------|
| RENAME USER | 自动迁移 | 保留 | 保留 | 简单（一条语句）|
| DROP + CREATE | 需重新 GRANT | 丢失（需重设）| 丢失 | 复杂（多条语句）|

---

## 适用场景

- **用户名规范化**：统一账号命名规范（如 `alice` → `alice@company.com` 或 `svc_alice`）
- **主机限制调整**：将 `'user'@'%'` 改为 `'user'@'10.0.0.%'`（缩小访问来源范围）
- **账号交接**：员工离职后，将其账户重命名为新员工名（但更推荐 DROP + CREATE 新账户）

---

## 常见问题

**RENAME USER 执行后是否需要 FLUSH PRIVILEGES？**

不需要，`RENAME USER` 是标准 SQL 语句，会自动更新权限缓存。只有直接修改 `mysql.user` 表（不推荐）后才需要 `FLUSH PRIVILEGES`。

---

## 注意事项

- 如果重命名后，新账户名与已存在的账户名相同（如已有 `'alice_zhang'@'%'`），RENAME USER 会报错：`ERROR 1396 (HY000): Operation RENAME USER failed for 'alice'@'%'`。
- 存储对象中的 DEFINER（存储过程、视图、触发器）不会随账户重命名而自动更新，重命名后这些对象的 DEFINER 变为无效用户，调用时会报错，需要手动处理。

---

## 总结

`RENAME USER 'old_user'@'old_host' TO 'new_user'@'new_host'` 修改账户标识，原有权限、密码和属性自动迁移到新名称，无需重新授权。比 DROP + CREATE 更高效，不会丢失已授予的权限。注意：存储过程、视图、触发器中的 DEFINER 不会自动更新，重命名后需手动检查并修复。

# COMMIT 提交事务

`COMMIT` 是提交当前事务的 SQL 命令，使事务中所有 DML 操作的修改永久生效并对其他事务可见。执行 `COMMIT` 时，InnoDB 完成 Redo Log 的落盘（fsync）、Binlog 的写入（如已启用）、锁的释放、Read View 的清理等一系列操作，确保事务符合持久性（Durability）要求，修改永久保存。

---

## COMMIT 的执行流程

```
COMMIT 内部执行步骤（innodb_flush_log_at_trx_commit = 1，启用 Binlog）：

1. 写入 Redo Log（Prepare 阶段）
   → 将事务的 Redo Log 标记为 PREPARE 状态
   → 将 Redo Log Buffer 中的记录 fsync 到磁盘

2. 写入 Binlog
   → 将事务的 Binlog Event 写入 Binlog 文件（sync_binlog=1 时 fsync）
   → Binlog 包含事务的所有 DML 语句或行变更事件

3. 写入 Redo Log（Commit 阶段）
   → 将 Redo Log 标记为 COMMIT 状态（追加一条 Commit Log 记录）
   → fsync 到磁盘（如果 step1 和 step3 在同一个 fsync 窗口，可以合并）

4. 释放所有锁
   → 释放事务持有的行锁、间隙锁、表级意向锁

5. 释放 Read View
   → 清理事务的 Read View（快照）

6. 将 Undo Log 加入 History List
   → 已提交的 Undo Log 不立即删除，等待 Purge 线程在没有活跃事务引用时清理

7. 返回 COMMIT 成功到客户端
```

## COMMIT 与 COMMIT WORK

```sql
-- 标准 COMMIT
COMMIT;

-- COMMIT WORK（等效于 COMMIT，SQL 标准中的写法）
COMMIT WORK;

-- COMMIT AND CHAIN（提交后立即开启新事务）
COMMIT AND CHAIN;
-- 等效于：COMMIT; START TRANSACTION;
-- 适用于需要连续执行多个事务的场景（避免 autocommit 的间隔）

-- COMMIT AND RELEASE（提交后断开连接）
COMMIT AND RELEASE;
-- 等效于：COMMIT; DISCONNECT;

-- 最常用的就是简单的 COMMIT（无修饰符）
```

## COMMIT 后的数据可见性

```sql
-- COMMIT 完成后，修改对其他事务的可见性：

-- 场景：事务A修改了 id=100 的行并 COMMIT

-- 对于 READ COMMITTED 隔离级别的其他事务：
-- COMMIT 后，其他事务下次执行 SELECT 立即可以看到修改
-- （RC 级别每次 SELECT 创建新的 Read View）

-- 对于 REPEATABLE READ 隔离级别的其他事务：
-- 如果其他事务在 COMMIT 之前已创建 Read View：
--   → 看不到修改（Read View 在 COMMIT 之前建立的，修改的 trx_id 在 Read View 活跃列表中）
-- 如果其他事务在 COMMIT 之后创建 Read View：
--   → 可以看到修改（修改的 trx_id 小于 Read View 的 low_limit_id）

-- 演示：
-- 会话1（RR 隔离级别）：
BEGIN;
SELECT * FROM orders WHERE id = 1;  -- 创建 Read View，看到 amount=100

-- 会话2：
BEGIN;
UPDATE orders SET amount = 200 WHERE id = 1;
COMMIT;  -- 会话2的修改已提交

-- 会话1（继续）：
SELECT * FROM orders WHERE id = 1;
-- → 还是 amount=100（RR 级别，Read View 已固定）
-- 直到会话1 COMMIT 并开启新事务，才能看到 amount=200
```

## 提交性能优化

```sql
-- 问题：高频提交导致 fsync 成为瓶颈
-- 每次 COMMIT 需要 1 次 fsync Redo Log（约 1-10ms）

-- 优化1：批量提交（应用层合并事务）
-- 不好的写法（每条插入一个事务）：
BEGIN; INSERT INTO t VALUES (1); COMMIT;
BEGIN; INSERT INTO t VALUES (2); COMMIT;
-- 1000 行 = 1000 次 COMMIT = 1000 次 fsync

-- 好的写法（批量插入一个事务）：
BEGIN;
INSERT INTO t VALUES (1), (2), ..., (1000);  -- 一次性插入或多次 INSERT
COMMIT;
-- 1000 行 = 1 次 COMMIT = 1 次 fsync（快 1000 倍！）

-- 优化2：合理设置事务大小（不要太大也不要太小）
-- 太小：频繁 COMMIT，fsync 次数多
-- 太大：单个事务持有大量锁（阻塞其他事务），回滚代价大
-- 建议：每次提交约 1000-10000 行（根据实际场景调整）

-- 优化3：多线程并发提交（利用 Group Commit）
-- 多个线程同时 COMMIT，MySQL 的 Group Commit 机制合并 fsync
-- 并发 COMMIT 的吞吐量远高于串行 COMMIT
```

## 适用场景

- **批量数据处理**：将批量 INSERT/UPDATE 包装在单个大事务中，而非每行一个事务，显著减少 COMMIT 次数和 fsync 开销
- **连续事务**：使用 `COMMIT AND CHAIN` 在事务边界无缝衔接，减少 `START TRANSACTION` 的开销

## 常见问题

**COMMIT 成功后，数据一定持久化了吗（不会因重启丢失）？**

取决于 `innodb_flush_log_at_trx_commit` 的设置：值为 1（默认）时，COMMIT 保证 Redo Log 已 fsync 到物理磁盘，即使 MySQL 进程崩溃或 OS 崩溃重启也不会丢失。值为 2 时，Redo Log 已写入 OS 的 Page Cache，MySQL 进程崩溃不会丢失，但 OS 崩溃（如断电）可能丢失最近 1 秒内提交的事务。值为 0 时，每秒才 fsync 一次，任何崩溃都可能丢失最近 1 秒内的提交。

## 注意事项

- 在启用 Binlog 的情况下（主从复制/备份），COMMIT 的持久性需要两个日志（Redo Log 和 Binlog）都落盘。两阶段提交（2PC）保证两者的一致性：如果只有 Redo Log 落盘而 Binlog 未落盘时崩溃，重启后会回滚该事务（Redo Log 中没有 COMMIT 标记）。
- COMMIT 释放所有锁的时机是一个重要的设计决策：锁在 COMMIT 之后统一释放，而不是语句执行后立即释放（这是 InnoDB 的两阶段锁定协议，保证事务的隔离性）。因此长事务会长期持有锁，阻塞其他事务。

## 总结

`COMMIT` 提交事务，使修改永久持久化并对其他事务可见，内部流程包括：Redo Log fsync（Prepare + Commit 两阶段）、Binlog 写入（有 Binlog 时）、锁释放、Read View 清理、Undo Log 加入 History List。`COMMIT AND CHAIN` 可在提交后立即开启新事务。批量提交（多行合并到一个事务）是优化写入性能的关键手段（减少 fsync 次数）。COMMIT 后数据对其他事务的可见时机取决于隔离级别：RC 级别下立即可见，RR 级别下只有在其他事务创建新的 Read View 后才可见。

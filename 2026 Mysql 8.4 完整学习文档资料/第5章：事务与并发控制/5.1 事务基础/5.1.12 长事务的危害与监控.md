# 长事务的危害与监控

长事务是指长时间运行（几分钟、几小时甚至更长）而未提交的事务。在 InnoDB 中，长事务是性能问题和运维故障的主要根源之一，会导致锁积压（阻塞其他事务）、Undo 表空间膨胀（阻止 MVCC 版本清理）、History List 增长（影响所有事务的查询性能）等多重危害。及时发现和处理长事务是 MySQL 运维的重要工作。

---

## 长事务的四大危害

```
危害1：持有锁阻塞其他事务
  长事务执行 DML 时加了行锁
  这些锁在整个事务提交前不会释放
  其他需要同样行的事务必须等待，导致锁等待堆积
  严重时：锁等待链越来越长，系统响应延迟急剧增加

危害2：阻止 MVCC 版本清理（Undo 膨胀）
  MVCC 的 Purge 线程需要确认"没有任何活跃事务引用旧版本"才清理旧 Undo
  长事务持有的 Read View 可能是系统中最旧的快照
  所有比这个快照更新的 Undo Log 版本链都不能被清理
  → Undo 表空间持续增长（可达 GB 甚至 TB）
  → History List Length 持续增加（影响所有 MVCC 查询的版本链遍历性能）

危害3：回滚代价大
  长事务修改了大量数据
  如果需要回滚，需要处理大量 Undo Log，耗时极长（可达数小时）
  回滚期间所有锁继续持有

危害4：主从复制延迟
  长事务的 Binlog 在事务提交时才写入
  如果长事务占用大量资源，从库应用 Binlog 时也会积累延迟
```

## 监控长事务

```sql
-- 方法1：查找运行时间超过 X 秒的事务
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds,
    trx_mysql_thread_id AS thread_id,
    trx_query AS current_sql,
    trx_rows_locked,
    trx_rows_modified,
    trx_tables_in_use,
    trx_tables_locked
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60  -- 超过 60 秒
ORDER BY trx_started;

-- 方法2：结合 processlist 查看完整信息
SELECT
    p.ID AS connection_id,
    p.USER,
    p.HOST,
    p.DB,
    p.COMMAND,
    p.TIME AS process_time_sec,
    p.STATE,
    p.INFO AS current_sql,
    t.trx_id,
    t.trx_started,
    t.trx_rows_modified,
    t.trx_rows_locked
FROM information_schema.PROCESSLIST p
JOIN information_schema.INNODB_TRX t ON p.ID = t.trx_mysql_thread_id
WHERE TIMESTAMPDIFF(SECOND, t.trx_started, NOW()) > 60
ORDER BY t.trx_started;

-- 方法3：通过 performance_schema 监控（更详细）
SELECT
    t.PROCESSLIST_ID,
    t.PROCESSLIST_USER,
    t.PROCESSLIST_HOST,
    t.PROCESSLIST_DB,
    t.PROCESSLIST_TIME,
    t.PROCESSLIST_STATE,
    trx.trx_started,
    TIMESTAMPDIFF(SECOND, trx.trx_started, NOW()) AS age_sec
FROM performance_schema.threads t
JOIN information_schema.INNODB_TRX trx ON t.PROCESSLIST_ID = trx.trx_mysql_thread_id
WHERE TIMESTAMPDIFF(SECOND, trx.trx_started, NOW()) > 60;
```

## 长事务的处理

```sql
-- 杀掉长事务的连接（强制回滚）
KILL CONNECTION thread_id;
-- 注意：KILL CONNECTION 会导致该连接断开，事务自动回滚
-- 适用于：确认该事务不重要，或者已经阻塞了生产系统

-- 更温和的方式：KILL QUERY（只杀当前执行的 SQL，事务继续）
KILL QUERY thread_id;
-- 注意：KILL QUERY 只中断当前 SQL，不回滚整个事务
-- 事务仍然活跃，锁仍然持有！通常不够用，最终还是需要 KILL CONNECTION

-- 找到阻塞其他事务的长事务：
SELECT
    blocking.trx_id AS blocking_trx_id,
    blocking.trx_mysql_thread_id AS blocking_thread,
    waiting.trx_id AS waiting_trx_id,
    waiting.trx_mysql_thread_id AS waiting_thread
FROM information_schema.INNODB_TRX blocking
JOIN performance_schema.data_lock_waits dlw
    ON blocking.trx_id = dlw.BLOCKING_ENGINE_TRANSACTION_ID
JOIN information_schema.INNODB_TRX waiting
    ON waiting.trx_id = dlw.REQUESTING_ENGINE_TRANSACTION_ID;
```

## 配置参数预防长事务

```sql
-- 1. 设置事务超时（会话级别）
-- innodb_lock_wait_timeout：锁等待超时（超时后回滚当前语句）
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
-- 默认：50 秒
SET SESSION innodb_lock_wait_timeout = 30;  -- 缩短为 30 秒

-- 2. innodb_rollback_on_timeout：锁超时时是否回滚整个事务
SHOW VARIABLES LIKE 'innodb_rollback_on_timeout';
-- 默认：OFF（只回滚超时的语句）
-- ON：超时时回滚整个事务（更激进）

-- 3. wait_timeout / interactive_timeout：连接空闲超时
SHOW VARIABLES LIKE 'wait_timeout';
-- 默认：28800 秒（8 小时），过长会导致空闲连接持有事务
SET GLOBAL wait_timeout = 600;   -- 10 分钟空闲断开

-- 4. MySQL 8.0 Performance Schema 长事务告警
-- 可以通过脚本定期查询 INNODB_TRX 并告警
-- 没有内置的"长事务自动断开"功能，需要外部脚本或监控工具
```

## 适用场景

- **生产监控**：建立定期检查长事务的监控脚本（每分钟查询 `INNODB_TRX`），超过阈值（如 5 分钟）则告警，避免长事务造成 Undo 膨胀和锁积压
- **问题排查**：当出现"表被锁住无法操作"时，首先查找持有锁的长事务，通过 KILL 解除阻塞

## 常见问题

**长事务持有的 Read View 会无限阻止 Undo 清理吗？**

是的。只要事务的 Read View 还在（事务未提交/回滚），Purge 线程不能清理比这个 Read View 更新的任何 Undo Log 版本。如果一个事务开始于 1 小时前，这 1 小时内所有其他事务产生的 Undo Log 都不能被清理（即使那些事务早就提交了）。这就是为什么一个长期不活跃但也不提交的"幽灵事务"（持有很旧的 Read View）可以导致 Undo 表空间无限膨胀，即使它什么 DML 都没做。

## 注意事项

- 应用层框架（如 Spring）的 `@Transactional` 注解有时会导致意外的长事务——如果一个标注了 `@Transactional` 的方法调用了其他耗时操作（如 HTTP 请求、文件 I/O），整个方法的执行时间就是事务持续时间。应将事务边界收窄到只包含数据库操作，外部 I/O 操作放在事务之外。
- 在 MySQL 8.0 中，`performance_schema.events_transactions_current` 可以看到当前活跃事务的详细状态，包括等待的锁和事务年龄，信息比 `INNODB_TRX` 更完整。

---

## 总结

长事务（长期未提交的事务）有四大危害：持有锁阻塞其他事务、持有旧 Read View 阻止 Purge 清理 Undo（导致 Undo 表空间膨胀）、回滚代价大、加剧主从复制延迟。通过 `information_schema.INNODB_TRX` 监控运行时间超过阈值的事务，结合 `KILL CONNECTION` 处理阻塞性长事务。配置 `innodb_lock_wait_timeout`、`wait_timeout` 缩短超时时间可减少长事务风险。应用层应收窄事务边界，避免在事务内执行耗时操作。

# 事务并发问题（脏读、不可重复读、幻读）

在多个事务并发执行时，如果隔离性保障不足，会出现三类经典的并发读取问题：脏读（Dirty Read）、不可重复读（Non-repeatable Read）和幻读（Phantom Read）。这三类问题由弱到强，是 SQL 标准定义四个隔离级别的核心依据——不同隔离级别通过禁止不同类型的并发问题来在"数据一致性"和"并发性能"之间取得平衡。

---

## 脏读（Dirty Read）

```
定义：一个事务读到了另一个事务尚未提交的修改数据。

发生级别：READ UNCOMMITTED（读未提交）

原理：
  事务A修改了 id=1 的 balance（1000 → 900），但未提交
  事务B在 READ UNCOMMITTED 级别下直接读取数据页，读到 balance=900
  事务A随后回滚，balance 恢复为 1000
  事务B基于读到的错误值（900）做了后续操作，产生错误结果

危害：
  读到的数据不代表最终状态（可能是临时状态）
  业务逻辑基于脏数据做决策，结果错误

InnoDB 的防止机制：
  READ COMMITTED 及以上级别使用 MVCC
  MVCC 的 Read View 只允许看到已提交事务的修改
  因此 READ COMMITTED 及以上完全消除脏读
```

---

## 不可重复读（Non-repeatable Read）

```
定义：同一事务内，两次读同一行数据，结果不同（期间有其他事务修改并提交了该行）。

发生级别：READ UNCOMMITTED，READ COMMITTED

原理：
  事务A（RC 级别）第一次读 id=1 的 balance，得到 1000
  事务B修改 id=1 的 balance 为 900，并提交
  事务A第二次读 id=1 的 balance，得到 900（RC 级别每次 SELECT 创建新的 Read View）
  同一事务内两次读同一行，结果不同 = 不可重复读

危害：
  事务内多次读取同一数据不一致，难以保证基于该数据的计算正确性

InnoDB 的防止机制：
  REPEATABLE READ（可重复读）级别：
    事务内第一次 SELECT 时创建 Read View，整个事务内不变
    第二次 SELECT 使用同一个 Read View → 看到同一个版本 → 可重复读
```

## 幻读（Phantom Read）

```
定义：同一事务内，两次执行相同范围查询，第二次结果多出（或少了）一些行。

发生级别：READ UNCOMMITTED，READ COMMITTED，REPEATABLE READ（SQL 标准中）

原理：
  事务A（RR 级别）执行 SELECT * FROM orders WHERE amount > 100，得到 5 行
  事务B插入了一行 amount=200 并提交
  事务A再次执行同样的 SELECT，如果能看到新行，则多了 1 行 = 幻读

InnoDB 的两种防止机制：

  1. 快照读（普通 SELECT）的幻读防止：
     MVCC Read View 在事务开始时固定
     事务B插入的新行 trx_id > Read View 上限 → 对事务A不可见
     → 快照读的幻读由 MVCC 防止

  2. 当前读（FOR UPDATE / DML）的幻读防止：
     Next-Key Lock（临键锁）= 行锁 + 间隙锁
     锁定现有行和它们之间的间隙
     事务B无法在被锁的间隙中插入新行（等待事务A释放间隙锁）
     → 当前读的幻读由 Next-Key Lock 防止
```

## 三类问题对比

| 并发问题 | 描述 | 发生条件 | 防止隔离级别 |
|---------|------|---------|------------|
| 脏读 | 读到未提交的修改 | READ UNCOMMITTED | READ COMMITTED 及以上 |
| 不可重复读 | 同行两次读结果不同（行被修改）| RC 及以下 | REPEATABLE READ 及以上 |
| 幻读 | 两次范围查询行数不同（新增/删除行）| SQL标准中RR也可能 | SERIALIZABLE（串行化） |

## InnoDB 在 RR 级别对幻读的特殊处理

```sql
-- SQL 标准中 REPEATABLE READ 不防止幻读
-- 但 InnoDB 在 RR 级别额外使用 Next-Key Lock，防止当前读的幻读

-- 场景1：快照读（普通 SELECT）→ MVCC 防止幻读
BEGIN;
SELECT * FROM orders WHERE amount > 100;  -- 返回 5 行，建立 Read View

-- 其他事务插入并提交一行 amount=200：
-- INSERT INTO orders VALUES (999, 200.00); COMMIT;

SELECT * FROM orders WHERE amount > 100;  -- 仍然返回 5 行（MVCC 快照）
-- → 快照读不会出现幻读

-- 场景2：当前读（FOR UPDATE）→ Next-Key Lock 防止幻读
BEGIN;
SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
-- → 对所有 amount > 100 的行加 X 锁
-- → 对这些行之间的间隙（以及最大值之后的间隙）加 Gap Lock
-- 其他事务尝试在这些间隙中插入：INSERT INTO orders VALUES (999, 200.00);
-- → 等待（被 Gap Lock 阻塞）
-- → 事务A提交后，事务B才能继续
```

## 适用场景

- **隔离级别选择依据**：理解三类并发问题后，可以根据业务对数据一致性的要求选择合适的隔离级别——读多写少的报表系统可用 RC（允许不可重复读），核心事务系统用 RR（防止不可重复读）
- **锁策略设计**：当需要防止某类并发问题时，选择正确的 SELECT 类型（快照读 vs FOR UPDATE）和相应的锁机制

## 常见问题

**InnoDB RR 级别真的完全防止了幻读吗？**

不完全。InnoDB RR 级别防止了两种幻读场景：快照读中由 MVCC 防止（整个事务看到同一快照），当前读中由 Next-Key Lock 防止（锁住间隙阻止插入）。但有一种混合场景仍然可能出现类似幻读：事务内先做快照读看到 5 行，再做当前读（FOR UPDATE），当前读会读取最新版本——如果其他事务在两次读之间提交了插入，当前读会看到 6 行。这种"快照读和当前读混合使用时的不一致"有时也被称为"幻读"，但严格来说是两种不同读机制的特性，不是 RR 级别的缺陷。

---

## 注意事项

- 不可重复读针对的是"同一行被修改"（UPDATE），幻读针对的是"行数变化"（INSERT/DELETE）。这是两个不同的问题，防止机制也不同：不可重复读通过固定 Read View 防止，幻读通过 Next-Key Lock 或 MVCC 防止。
- `READ UNCOMMITTED` 在实际生产中几乎不使用（脏读危害极大）。`SERIALIZABLE` 使用较少（性能代价太高）。实际系统主要在 `READ COMMITTED`（高并发OLTP）和 `REPEATABLE READ`（MySQL 默认，大多数系统首选）之间选择。

---

## 总结

三类事务并发问题：脏读（读到未提交的修改，RC 及以上消除）、不可重复读（同行两次读结果不同，RR 及以上消除）、幻读（范围查询行数变化，SQL 标准中 SERIALIZABLE 才消除，InnoDB RR 通过 MVCC + Next-Key Lock 在大多数场景消除）。InnoDB 默认 RR 级别通过 MVCC（固定 Read View）防止快照读的脏读/不可重复读/幻读，通过 Next-Key Lock 防止当前读的幻读，提供了比 SQL 标准 RR 级别更强的隔离保证。

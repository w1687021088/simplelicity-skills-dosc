# autocommit 自动提交模式

`autocommit` 是 MySQL 控制事务提交方式的系统变量。当 `autocommit = ON`（默认值）时，每条单独的 DML 语句会在执行后自动提交，相当于每条 SQL 都被隐式包裹在一个事务中。当 `autocommit = OFF` 时，所有 DML 操作都在隐式开启的事务中，必须显式执行 `COMMIT` 才能提交，否则会话断开时自动回滚。

---

## autocommit 的行为差异

```sql
-- 查看当前 autocommit 设置
SHOW VARIABLES LIKE 'autocommit';
SELECT @@autocommit;

-- autocommit = ON（默认）：每条 SQL 自动提交
SET SESSION autocommit = ON;

INSERT INTO t VALUES (1);  -- 自动提交，立即持久化
INSERT INTO t VALUES (2);  -- 自动提交，立即持久化
-- 没有显式 BEGIN，每条语句是独立的事务
-- 如果第二条语句失败，第一条已经提交无法回滚

-- autocommit = OFF：需要显式提交
SET SESSION autocommit = OFF;

INSERT INTO t VALUES (3);  -- 不自动提交，在隐式事务中
INSERT INTO t VALUES (4);  -- 不自动提交，在同一隐式事务中
COMMIT;                     -- 显式提交，id=3 和 id=4 一起持久化
-- 或 ROLLBACK 撤销 id=3 和 id=4 的插入
```

---

## autocommit 与 START TRANSACTION 的交互

```sql
-- 即使 autocommit = ON，START TRANSACTION 也会开启手动事务模式
-- 直到 COMMIT/ROLLBACK 后，才恢复 autocommit 行为

SET SESSION autocommit = ON;
INSERT INTO t VALUES (5);  -- 自动提交

START TRANSACTION;          -- 开启手动事务（覆盖 autocommit 行为）
INSERT INTO t VALUES (6);  -- 不自动提交
INSERT INTO t VALUES (7);  -- 不自动提交
ROLLBACK;                   -- 回滚，id=6 和 id=7 被撤销

INSERT INTO t VALUES (8);  -- START TRANSACTION 范围结束后恢复自动提交
-- id=8 自动提交

-- 总结：START TRANSACTION 是"局部禁用 autocommit"的方式
```

## autocommit = OFF 的注意事项

```sql
-- 常见的"忘记提交"陷阱：
SET SESSION autocommit = OFF;

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- ... 执行了很多操作 ...
-- 忘记 COMMIT！

-- 连接断开后：
-- MySQL 自动回滚未提交的事务（修改全部丢失）

-- 另一个问题：长时间未提交的隐式事务
-- 持有行锁，阻塞其他事务

-- 监控未提交事务
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
       trx_query
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;  -- 超过1分钟未提交
```

## 不同语言驱动的默认 autocommit 行为

| 语言/框架 | 默认 autocommit | 说明 |
|---------|----------------|------|
| MySQL CLI | ON | 与 MySQL 服务器默认一致 |
| Java JDBC | ON | 通过 connection.setAutoCommit(false) 关闭 |
| Python pymysql | ON | 默认同服务器设置 |
| Go database/sql | ON | 通过 db.Begin() 开启手动事务 |
| Spring 框架 | 由 @Transactional 控制 | 事务方法内 autocommit=false |

## 全局与会话级设置

```sql
-- 会话级设置（只影响当前连接）
SET SESSION autocommit = OFF;
SET autocommit = OFF;  -- 等价于 SESSION 级别

-- 全局设置（影响新建连接，不影响已有连接）
SET GLOBAL autocommit = OFF;

-- 永久设置（写入 my.cnf）
-- [mysqld]
-- autocommit = 0  或  autocommit = OFF

-- 查看当前有效值
SELECT @@session.autocommit, @@global.autocommit;
```

## 适用场景

- **OLTP 高并发短事务**：`autocommit = ON`（默认）适合短事务场景，每条 SQL 提交，锁持有时间最短
- **批量数据处理**：临时关闭 autocommit（或使用 `START TRANSACTION`）合并多行为一个事务，减少 fsync 次数，大幅提升批量写入性能

---

## 常见问题

**为什么建议使用 START TRANSACTION 而不是 SET autocommit = OFF？**

`SET autocommit = OFF` 关闭后会话内所有后续 SQL 都在隐式事务中，容易忘记 COMMIT，导致长事务和锁积压。`START TRANSACTION` 明确标记事务开始和结束（`COMMIT`/`ROLLBACK`），边界清晰，代码可读性更好，不容易出错。在团队协作和代码维护中，`START TRANSACTION` 的显式边界比 `autocommit=OFF` 的隐式事务更易理解和维护。

---

## 注意事项

- 某些 MySQL 连接池（如 HikariCP）会在归还连接时自动执行 `ROLLBACK` 来清理未提交的事务，避免事务状态"泄漏"到下一个使用该连接的请求。依赖此行为而不在应用层显式回滚是不健壮的做法，应在应用层保证事务的明确结束。
- `autocommit = OFF` 配合 `innodb_flush_log_at_trx_commit = 1` 时，每次 `COMMIT` 都有 fsync 开销。在频繁单条更新的场景中，`autocommit=OFF` 后手动批量提交比 `autocommit=ON` 的逐条自动提交性能高很多（减少 fsync 次数）。

---

## 总结

`autocommit`（默认 ON）控制每条 DML 是否自动提交。ON 时每条 SQL 独立事务自动提交，OFF 时需显式 `COMMIT`。`START TRANSACTION` 在 autocommit=ON 时也会开启手动事务（覆盖 autocommit 行为）。关闭 autocommit 可减少 fsync 次数提升批量写入性能，但易导致忘记提交（长事务、锁积压）。推荐使用 `START TRANSACTION...COMMIT/ROLLBACK` 的显式边界管理，避免 `SET autocommit=OFF` 的隐式事务。

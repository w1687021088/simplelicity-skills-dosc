# 一致性 Consistency 数据库约束

一致性（Consistency）是事务 ACID 特性中的 C，要求事务执行前后数据库都处于满足所有完整性约束的合法状态。一致性是事务的"目标"，其他三个特性（原子性、隔离性、持久性）是实现一致性的手段。MySQL 通过多层约束机制来保障一致性：数据库层面的完整性约束（主键、外键、唯一约束等）由 InnoDB 自动检查，业务层面的一致性规则（如账户余额不为负）由应用逻辑或 CHECK 约束来保障。

---

## 一致性的两个层次

```
层次1：数据库层一致性（MySQL 自动保障）

  主键约束（PRIMARY KEY）：
    → 主键列不能有重复值，不能为 NULL
    → 违反时 SQL 语句报错并回滚（原子性保障这条语句不部分执行）
    
  唯一约束（UNIQUE INDEX）：
    → 唯一列不能有重复值（NULL 允许多个）
    → 违反时报错并回滚

  外键约束（FOREIGN KEY）：
    → 子表的外键值必须在父表中存在（引用完整性）
    → 父表删除/更新时，根据 ON DELETE/ON UPDATE 规则处理子表
    
  NOT NULL 约束：
    → 标记为 NOT NULL 的列不能插入 NULL 值
    
  CHECK 约束（MySQL 8.0.16+ 真正强制生效）：
    → 自定义检查条件（如 balance >= 0）
    → 违反时报错并回滚

层次2：业务层一致性（应用代码保障）
  → 转账总金额不变（两个账户余额之和）
  → 库存量必须 >= 销售量（不超卖）
  → 状态机转换（订单状态只能从"待付款"→"已付款"）
  这些规则 MySQL 无法自动检查，需要应用代码和事务保障
```

## 完整性约束的使用

```sql
-- 主键约束（自动确保一致性）
CREATE TABLE orders (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 主键约束
    user_id    BIGINT NOT NULL,                    -- NOT NULL 约束
    amount     DECIMAL(10, 2) NOT NULL,
    status     ENUM('pending', 'paid', 'shipped', 'done') DEFAULT 'pending',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)    -- 外键约束
        ON DELETE RESTRICT
        ON UPDATE CASCADE
) ENGINE = InnoDB;

-- CHECK 约束（MySQL 8.0.16+ 真正执行）
CREATE TABLE accounts (
    id      BIGINT PRIMARY KEY,
    balance DECIMAL(10, 2) NOT NULL,
    CONSTRAINT chk_balance_positive CHECK (balance >= 0)  -- 余额不能为负
);

-- 违反 CHECK 约束时：
UPDATE accounts SET balance = -100 WHERE id = 1;
-- ERROR 3819 (HY000): Check constraint 'chk_balance_positive' is violated.

-- 查看表上的约束
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'myapp' AND TABLE_NAME = 'accounts';
```

## 外键约束与一致性

```sql
-- 外键约束是关系型数据库保障一致性的重要机制
-- 防止"孤儿记录"（引用不存在的父记录）

-- 父表
CREATE TABLE departments (
    id   INT PRIMARY KEY,
    name VARCHAR(50)
);

-- 子表（有外键）
CREATE TABLE employees (
    id     INT PRIMARY KEY,
    name   VARCHAR(50),
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES departments(id)
        ON DELETE RESTRICT   -- 父表记录被子表引用时，禁止删除父表记录
        ON UPDATE CASCADE    -- 父表主键更新时，子表外键自动同步更新
);

-- 尝试插入不存在的 dept_id
INSERT INTO employees VALUES (1, 'Alice', 999);
-- ERROR 1452: Cannot add or update a child row: foreign key constraint fails

-- 尝试删除被引用的 departments 记录
DELETE FROM departments WHERE id = 1;  -- departments.id=1 有员工引用
-- ERROR 1451: Cannot delete a parent row: foreign key constraint fails

-- 外键的几种规则（ON DELETE/ON UPDATE）：
-- RESTRICT：禁止操作（默认）
-- CASCADE：级联操作（删父时删子，改父键时改子键）
-- SET NULL：父表记录删除/更新时，子表外键设为 NULL
-- NO ACTION：与 RESTRICT 类似（MySQL 中等效）
```

## 业务层一致性的保障

```sql
-- 转账场景的业务层一致性保障

-- 方法1：应用层事务控制（最常用）
BEGIN;
-- 检查余额是否充足（防止超支）
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- 加锁防止并发超支
-- 应用层检查：if balance < 100: ROLLBACK（余额不足）

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 验证一致性（转账后总金额不变）
-- 应用层可在此处做 assertion
COMMIT;

-- 方法2：CHECK 约束（MySQL 8.0.16+）
-- 在 accounts 表上添加 CHECK (balance >= 0)
-- 则 balance - 100 < 0 时 UPDATE 语句直接报错，事务回滚

-- 方法3：触发器（Trigger）
CREATE TRIGGER before_update_balance
BEFORE UPDATE ON accounts
FOR EACH ROW
BEGIN
    IF NEW.balance < 0 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Balance cannot be negative';
    END IF;
END;
```

## 一致性与约束延迟检查

```sql
-- MySQL 中外键约束默认是"立即检查"（每条语句执行后立即验证）
-- 在某些需要批量插入相互引用数据的场景，可以临时禁用外键检查：

SET FOREIGN_KEY_CHECKS = 0;  -- 临时禁用外键检查（会话级别）
-- 执行批量插入...（父子表顺序无关）
SET FOREIGN_KEY_CHECKS = 1;  -- 恢复外键检查

-- 注意：FOREIGN_KEY_CHECKS = 0 期间插入的数据不验证外键，
-- 可能产生不一致数据，恢复后不会回头检查已有数据！
-- 只在明确知道数据正确时使用（如数据迁移脚本）

-- MySQL 不像某些数据库支持延迟约束检查（DEFERRABLE INITIALLY DEFERRED）
-- 外键约束只能通过 FOREIGN_KEY_CHECKS 完全关闭，没有延迟检查的中间选项
```

## 适用场景

- **金融系统**：在账户表上添加 `CHECK (balance >= 0)` 作为数据库层保障，配合应用层事务检查，双重保证余额不会为负
- **数据完整性强要求的系统**：充分使用外键约束（`FOREIGN KEY`）保证引用完整性，而不是仅依赖应用层控制

## 常见问题

**MySQL 8.0 之前的 CHECK 约束是否生效？**

MySQL 8.0.16 之前，InnoDB 不强制执行 CHECK 约束（语法上接受，但不验证）。8.0.16 之后 CHECK 约束才真正生效（违反时报错）。如果有从 5.7 迁移来的表，原有的 CHECK 约束在 8.0.16+ 会开始强制检查，可能导致原来"能写入的非法值"变成错误。升级时需要验证现有数据是否满足 CHECK 约束条件（否则 ALTER TABLE 添加 CHECK 会失败）。

## 注意事项

- 外键约束在高并发的 OLTP 系统中可能成为性能瓶颈：每次 INSERT/UPDATE/DELETE 都需要额外的查找操作（验证父表记录）。一些大型互联网公司选择不使用数据库外键，改由应用层保证引用完整性（换取更高的写入吞吐量）。这是在性能和一致性保障之间的权衡，没有绝对对错，取决于业务需求。
- 在进行大批量数据导入时，临时禁用外键检查（`SET FOREIGN_KEY_CHECKS = 0`）可以大幅提升导入速度，但必须保证导入数据本身的完整性，导入完成后立即恢复。

---

## 总结

一致性是事务的目标状态，要求数据在任何时刻都满足所有完整性约束。MySQL 通过两个层次保障：数据库层（主键唯一性、外键引用完整性、NOT NULL、CHECK 约束——8.0.16+ 真正生效）和业务层（应用代码中的事务控制、业务规则验证）。外键约束（`FOREIGN KEY ... REFERENCES`）是关系型完整性的核心，支持 RESTRICT/CASCADE/SET NULL 等规则。CHECK 约束（`CHECK(condition)`）是 MySQL 8.0.16+ 的重要改进。保障一致性需要原子性、隔离性、持久性的共同配合。

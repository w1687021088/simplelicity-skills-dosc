# 隔离性 Isolation 锁与 MVCC

隔离性（Isolation）要求并发执行的多个事务互不干扰，每个事务仿佛是在系统中独立执行的。InnoDB 通过两种机制共同实现隔离性：MVCC（Multi-Version Concurrency Control，多版本并发控制）用于处理读写不冲突的场景（快照读），锁机制用于处理写写冲突的场景。两者结合使得 InnoDB 在保证隔离性的同时，读操作和写操作可以并发进行，不会互相阻塞。

---

## 隔离性的实现机制对比

| 读写类型 | 实现机制 | 特点 |
|---------|---------|------|
| 快照读（Snapshot Read）| MVCC 读历史版本 | 读不加锁，不阻塞写 |
| 当前读（Current Read）| 锁机制（行锁 + 间隙锁）| 读加锁，阻塞其他写 |
| 写操作 | 行锁（X Lock）| 阻塞其他读当前读和写 |

---

## MVCC 实现隔离性

```sql
-- MVCC 的核心思想：
-- 不同事务看到的是数据在不同时间点的"快照"
-- 读操作不需要加锁，通过版本链找到对当前事务可见的版本

-- 快照读（普通 SELECT，不加锁）：
SELECT * FROM orders WHERE id = 100;
-- InnoDB 根据事务的 Read View（读视图）判断可见性
-- 如果 id=100 的行有多个版本（被其他事务修改中），
-- 当前事务通过 Undo Log 版本链找到符合自己可见性的版本

-- Read View 的核心内容（在事务开始/每次 SELECT 时创建）：
-- low_limit_id：创建 Read View 时最大的活跃事务 ID + 1
-- up_limit_id：创建 Read View 时最小的活跃事务 ID
-- trx_ids：创建时所有活跃事务 ID 列表
-- creator_trx_id：当前事务的 ID

-- 可见性判断规则：
-- 行记录的 DB_TRX_ID（修改此版本的事务 ID）= X：
-- 如果 X < up_limit_id：X 在 Read View 创建前已提交 → 可见
-- 如果 X >= low_limit_id：X 在 Read View 创建后才开始 → 不可见
-- 如果 up_limit_id <= X < low_limit_id：查 trx_ids 列表
--   → X 在活跃列表中：该版本还未提交 → 不可见（读取旧版本）
--   → X 不在活跃列表中：X 已提交 → 可见
```

## 锁机制实现隔离性

```sql
-- 当前读（Current Read）：读取最新版本，加锁防止并发修改

-- 触发当前读的操作：
SELECT * FROM orders WHERE id = 100 FOR UPDATE;     -- X 锁
SELECT * FROM orders WHERE id = 100 LOCK IN SHARE MODE;  -- S 锁
UPDATE orders SET status = 'done' WHERE id = 100;    -- X 锁
DELETE FROM orders WHERE id = 100;                  -- X 锁
INSERT INTO orders VALUES (...);                     -- X 锁（插入意向锁）

-- 锁的类型与隔离性：
-- 行锁（Record Lock）：锁定具体的行记录，防止其他事务读/写该行（当前读时）
-- 间隙锁（Gap Lock）：锁定行之间的间隙，防止其他事务插入（防止幻读）
-- 临键锁（Next-Key Lock）= 行锁 + 间隙锁：RR 级别的默认加锁类型

-- 锁的隔离性保障：
-- 写事务持有 X 锁 → 其他写事务无法修改同行（等待）
-- 读事务（LOCK IN SHARE MODE）持有 S 锁 → 写事务等待 S 锁释放才能写
-- 快照读（普通 SELECT）不加锁 → 不阻塞写事务（只是看不到未提交修改）
```

## MVCC 与锁的协作

```sql
-- 场景：RR 隔离级别下并发读写

-- 事务A（时间1）：
BEGIN;
SELECT * FROM orders WHERE user_id = 100;  -- 快照读，创建 Read View，不加锁

-- 事务B（时间2）：
BEGIN;
UPDATE orders SET amount = 200 WHERE id = 5;  -- 加 X 锁，修改行
COMMIT;  -- 提交，X 锁释放

-- 事务A（时间3，继续）：
SELECT * FROM orders WHERE user_id = 100;  -- 快照读，使用时间1创建的 Read View
-- → 看不到事务B的修改（事务B在事务A的Read View创建后才开始）
-- → 事务A读取的是事务B修改前的版本（通过Undo Log版本链获取）
-- → 这就是 RR 级别的"可重复读"：同一事务内两次 SELECT 结果相同

-- 事务A（时间4）：
UPDATE orders SET status = 'done' WHERE id = 5;  -- 当前读（修改时加锁）
-- → 读取最新版本（事务B修改后的 amount=200）
-- → 加 X 锁
-- → 基于最新版本执行修改（不是基于快照）
```

## 不同隔离级别下 MVCC 的行为

| 隔离级别 | Read View 创建时机 | 行为 |
|---------|-----------------|------|
| READ COMMITTED | 每次 SELECT 时创建 | 每次查询都读最新提交版本 |
| REPEATABLE READ | 事务第一次读时创建 | 整个事务内看到同一快照 |
| SERIALIZABLE | 每次读加 S 锁 | 读写全部串行化 |
| READ UNCOMMITTED | 不使用 MVCC | 直接读最新版本（含未提交）|

## 隔离性与并发问题

```
不同隔离级别可能出现的并发问题：

脏读（Dirty Read）：读到其他事务未提交的数据
  → READ UNCOMMITTED 级别下可能发生
  → READ COMMITTED 及以上级别不会发生（MVCC 读已提交版本）

不可重复读（Non-repeatable Read）：同一事务内两次读同一行结果不同
  → READ UNCOMMITTED / READ COMMITTED 级别下可能发生
  → REPEATABLE READ 及以上不会发生（Read View 在事务内固定）

幻读（Phantom Read）：同一事务内两次范围查询结果行数不同
  → READ UNCOMMITTED 到 REPEATABLE READ 可能发生（SQL 标准）
  → InnoDB 在 RR 级别通过 Next-Key Lock 防止当前读的幻读
  → 快照读（普通 SELECT）由 MVCC Read View 防止幻读
```

---

## 适用场景

- **高并发读写**：MVCC 使读操作不阻塞写操作（快照读），适合读写混合的 OLTP 场景
- **金融一致性要求**：对同一账户的读写用 `SELECT ... FOR UPDATE`（当前读 + 加锁），保证读到最新值并防止并发修改

## 常见问题

**快照读（普通 SELECT）和当前读（FOR UPDATE）在同一事务中混用会怎样？**

混用时需要注意：快照读看到的是 Read View 创建时的快照，当前读看到的是最新版本。如果在事务中先做了快照读，再做当前读，当前读可能看到快照读看不到的已提交修改，两次读的结果不一致是正常的（不是 Bug）。设计时需要明确哪些地方需要"读最新值并加锁"（当前读），哪些地方只需要"历史快照"（快照读）。

---

## 注意事项

- InnoDB 在 RR 级别下，即使只做普通 SELECT（快照读），也需要在第一次 SELECT 时创建 Read View。如果长事务长时间持有很旧的 Read View，会阻止 Purge 线程清理旧版本，导致 History List 增长和 Undo 表空间膨胀。因此长事务（长时间不提交的事务）在 MVCC 系统中有双重危害：持有行锁（阻塞写）+ 持有旧 Read View（阻止 Purge）。
- `READ UNCOMMITTED` 在实践中几乎不使用，因为脏读会导致读到不一致的中间状态，破坏业务逻辑。

---

## 总结

隔离性通过 MVCC 和锁两种机制共同实现。MVCC 基于 Read View 和 Undo Log 版本链，让快照读（普通 SELECT）看到事务创建时的一致快照，读不加锁不阻塞写。锁机制（行锁 + 间隙锁/临键锁）处理当前读（`FOR UPDATE`/DML）的写写冲突，防止并发写入不一致。RC 级别每次 SELECT 创建新 Read View（读已提交），RR 级别只创建一次（可重复读）。InnoDB 在 RR 级别通过 Next-Key Lock 防止当前读的幻读，通过 Read View 固定防止快照读的幻读。

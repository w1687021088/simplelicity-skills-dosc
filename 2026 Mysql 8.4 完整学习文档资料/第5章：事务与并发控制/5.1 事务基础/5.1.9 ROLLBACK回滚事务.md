# ROLLBACK 回滚事务

`ROLLBACK` 是撤销当前事务中所有未提交修改的 SQL 命令，使数据库恢复到事务开始前的状态。InnoDB 通过 Undo Log 实现 ROLLBACK：按照 Undo Log 的逆序执行逆操作，撤销事务中的每条 DML 语句，然后释放该事务持有的所有锁和 Read View。

---

## 基本用法

```sql
-- 显式回滚（放弃当前事务所有修改）
ROLLBACK;
ROLLBACK WORK;  -- SQL 标准写法，等效于 ROLLBACK

-- 示例：转账失败回滚
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 99999;  -- 账户不存在，报错
-- 应用层捕获错误，执行 ROLLBACK
ROLLBACK;
-- 结果：id=1 的余额恢复为原值，没有任何修改
```

---

## ROLLBACK 的内部执行过程

```
ROLLBACK 的详细步骤：

1. 查找 Undo Log 链
   → 通过 trx_t.rsegs 找到该事务的 Undo Segment
   → 获取 Undo Log 链的末尾（最后写入的记录）

2. 逆序执行 Undo Log
   → INSERT Undo → 按主键删除该行（物理删除）
   → UPDATE Undo → 将行数据恢复为旧值
   → DELETE Undo → 清除 delete-mark，恢复行可见性
   → 每次逆操作也生成 Redo Log（保证崩溃后可重做回滚）

3. 释放所有锁
   → 释放行锁、间隙锁、表级意向锁
   → 被此事务阻塞的其他事务被唤醒

4. 清理 Read View 和 Undo 段引用

5. 返回成功
```

## 大事务回滚的性能影响

```sql
-- 回滚耗时 ≈ 正向执行耗时
-- 修改了 N 行，回滚也需要处理 N 行的 Undo Log

-- 监控回滚进度
SHOW ENGINE INNODB STATUS \G
-- 查找：Rolling back trx with id XXX, XXX operations left

-- 回滚期间的影响：
-- 1. 持续消耗 CPU（执行逆操作）
-- 2. 持续写入 Redo Log（每次逆操作都记日志）
-- 3. 大量行锁持续持有（直到回滚完成才释放）
-- 4. 阻塞依赖这些行锁的其他事务

-- 避免大事务的实践：
-- 批量操作拆分为多个小事务（每批 1000-10000 行，分批 COMMIT）
```

## 隐式回滚的情况

```sql
-- MySQL 在以下情况会自动执行隐式回滚：

-- 1. 客户端连接断开：自动回滚未提交事务
-- 2. 死锁检测：牺牲者事务被自动回滚
-- 3. 锁等待超时（innodb_rollback_on_timeout=ON 时）：超时后回滚整个事务
SHOW VARIABLES LIKE 'innodb_rollback_on_timeout';
-- 默认：OFF（只回滚超时的语句，不是整个事务）
-- ON：超时则回滚整个事务（更安全）

-- 4. 语句错误：默认只回滚该语句，不是整个事务
-- 应用层应在捕获错误后显式执行整个事务的 ROLLBACK
```

---

## 适用场景

- **错误处理**：在应用层的 try-catch 中，捕获任何 SQL 异常后执行 ROLLBACK，确保不残留部分完成的操作
- **业务校验失败**：在事务内完成所有修改后，执行业务层校验，校验失败时 ROLLBACK

---

## 常见问题

**事务中某条 SQL 报错后，还能继续执行其他 SQL 吗？**

取决于错误类型。大多数 DML 错误（如 UNIQUE KEY 冲突）只回滚该条语句，事务仍然活跃，可以继续或 ROLLBACK。但最佳实践是：捕获任何错误后立即执行 ROLLBACK，避免在出错后继续事务产生不一致状态。

---

## 注意事项

- DDL 语句（如 `CREATE TABLE`、`ALTER TABLE`、`TRUNCATE TABLE`）在 MySQL 中会触发隐式提交，不能被 ROLLBACK 撤销。即使在事务中执行了 DDL，之前的 DML 修改也会被隐式提交，ROLLBACK 无法回到 DDL 之前的状态。
- 大事务回滚耗时长（与修改量成正比），期间持续持有锁阻塞其他事务。生产环境应避免大事务（拆分为小批次事务，每批提交）。

---

## 总结

`ROLLBACK` 撤销事务中所有未提交的修改，通过逆序执行 Undo Log 中的逆操作恢复数据，然后释放所有锁和 Read View。大事务回滚耗时长（与修改量成正比），生产环境应避免大事务。连接断开、锁等待超时（`innodb_rollback_on_timeout=ON`）、死锁检测都会触发隐式回滚。DDL 触发隐式提交，不可通过 ROLLBACK 撤销。

# 持久性 Durability 日志刷盘

持久性（Durability）是 ACID 中的 D，要求事务一旦提交，其所做的修改就永久保存，即使之后发生系统崩溃、断电等故障也不会丢失。InnoDB 通过 Redo Log（重做日志）和 WAL（Write-Ahead Logging）协议来保障持久性：事务提交时必须先将 Redo Log 刷写到磁盘（fsync），确保 Redo Log 落盘后 COMMIT 才返回成功。即使 MySQL 进程崩溃，下次启动时会从 Redo Log 恢复已提交但尚未写入数据文件的修改。

---

## 持久性的实现机制

```
WAL（Write-Ahead Logging）协议：

规则1：Redo Log 先行
  任何数据页修改写入磁盘前，对应的 Redo Log 必须先写入磁盘

规则2：提交前刷盘
  事务提交（COMMIT）前，该事务产生的所有 Redo Log 必须刷到磁盘

COMMIT 的执行流程（innodb_flush_log_at_trx_commit = 1）：
  1. 将事务的 Redo Log 从 Redo Log Buffer 写入 OS Cache
  2. 调用 fsync（强制 OS Cache 落盘到磁盘）
  3. 等待 fsync 完成（确认 Redo Log 已物理写入磁盘）
  4. 向客户端返回 COMMIT 成功

保障：
  COMMIT 返回后，即使进程立即崩溃，Redo Log 已在磁盘上
  下次 MySQL 启动时，通过 Redo Log 重放恢复已提交的修改
```

---

## innodb_flush_log_at_trx_commit 的选项

| 值 | 行为 | 数据安全性 | 性能 |
|----|------|-----------|------|
| 0 | 每秒写入 OS Cache 并 fsync（与提交无关）| 崩溃最多丢失 1 秒数据 | 最高 |
| 1 | 每次 COMMIT 写入并 fsync（默认）| 完全持久性，零数据丢失 | 较低 |
| 2 | 每次 COMMIT 写入 OS Cache，每秒 fsync | OS 崩溃或断电最多丢失 1 秒 | 较高 |

## Group Commit（组提交）优化持久性的性能代价

```sql
-- 持久性的代价：每次 COMMIT 都需要 fsync Redo Log
-- fsync 是磁盘操作，延迟约 1-5ms（HDD）或 0.1-1ms（SSD/NVMe）
-- 每秒最多支持 200-10000 次提交（取决于存储设备）

-- Group Commit（组提交）优化：
-- 多个并发事务的 COMMIT 合并为一次 fsync
-- MySQL 8.0 的 Group Commit 流程：
-- FLUSH 阶段：多个事务排队，将各自的 Redo Log 写入文件
-- SYNC 阶段：一次 fsync 写入所有排队的 Redo Log（一次磁盘操作 = 多个事务）
-- COMMIT 阶段：按顺序提交 Binlog + 存储引擎事务

-- Group Commit 的效果：
-- 高并发时：100 个事务 → 可能只需要 1 次 fsync（100x 加速）
-- 低并发时：效果有限（只有 1 个事务时仍然是 1 次 fsync）

-- 查看 Group Commit 效果
SHOW STATUS LIKE 'Innodb_os_log_fsyncs';        -- fsync 次数
SHOW STATUS LIKE 'Innodb_os_log_written';        -- Redo Log 写入量
-- 计算每次 fsync 平均写入量：written / fsyncs，越大说明 Group Commit 效果越好
```

## Binlog 与 Redo Log 的双重持久性

```sql
-- 当开启 Binlog 时，持久性需要两个日志都落盘

-- 两阶段提交（2PC）：
-- Phase 1（Prepare）：
--   Redo Log 写入 PREPARE 状态
--   Redo Log fsync 到磁盘

-- Phase 2（Commit）：
--   Binlog 写入磁盘（sync_binlog = 1 时每次 fsync）
--   Redo Log 写入 COMMIT 状态

-- 关键配置（生产环境双重保障）：
SHOW VARIABLES LIKE 'sync_binlog';
-- sync_binlog = 1：每次 COMMIT 时 Binlog fsync（最安全）
-- sync_binlog = 0：由 OS 决定何时 fsync（性能高，但可能丢失）

-- 最安全配置（零数据丢失）：
-- innodb_flush_log_at_trx_commit = 1 + sync_binlog = 1
-- 性能最高但最不安全：
-- innodb_flush_log_at_trx_commit = 0 + sync_binlog = 0

-- 查看当前配置
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
```

## 适用场景

- **金融/支付系统**：必须使用 `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`，确保每次 COMMIT 后数据永久持久化，不接受任何数据丢失
- **日志/统计类系统**：可以使用 `innodb_flush_log_at_trx_commit=2` 或 `0`，允许最多 1 秒的数据丢失，换取更高的写入吞吐量

---

## 常见问题

**为什么 innodb_flush_log_at_trx_commit = 2 比 1 快，但安全性接近？**

值为 2 时，每次 COMMIT 将 Redo Log 写入 OS 的页缓存（Page Cache），OS 崩溃时才会丢失（OS 崩溃很少见）；但如果只是 MySQL 进程崩溃（更常见的情况），OS 的 Page Cache 中的 Redo Log 仍然存在，MySQL 重启后能完整恢复。值为 1 时，即使 OS 也崩溃（如断电），数据也不会丢失（因为已经 fsync 到物理磁盘）。对于大多数非断电场景，值为 2 与值为 1 的数据安全性相当，但写入性能明显更高（减少了 fsync 调用）。

---

## 注意事项

- 使用 RAID 控制器的写缓存或 SSD 的写缓存可以加速 fsync（缓存写入确认），但必须确保缓存有电池保护（BBU）或掉电保护（NVMe 的 PCIe 持久内存），否则看似落盘实际数据在缓存中，断电仍然会丢失。
- Group Commit 在高并发写入时效果显著（合并多个 fsync 为一次），但在低并发场景（如每秒只有几个提交）效果有限，每次提交仍需一次 fsync。这是高并发系统比单线程串行写入性能更好的一个原因（并发时 Group Commit 摊薄了 fsync 成本）。

---

## 总结

持久性通过 Redo Log + WAL 协议实现：COMMIT 前必须将 Redo Log fsync 到磁盘（`innodb_flush_log_at_trx_commit=1`），确保提交后的数据即使 MySQL 崩溃也可通过 Redo Log 恢复。崩溃恢复分两步：Redo 阶段（重放所有 Redo Log）和 Undo 阶段（回滚未提交事务）。Group Commit 将多个并发事务的 Redo Log fsync 合并为一次，大幅提升高并发下的写入吞吐量。开启 Binlog 时需配合 `sync_binlog=1` 实现 Binlog 持久化，通过两阶段提交（2PC）保证 Redo Log 和 Binlog 的一致性。

# 事务状态机与生命周期

InnoDB 中每个事务都有明确的生命周期，从创建到结束（提交或回滚）经历一系列状态变化。理解事务的状态机有助于掌握事务在不同阶段的行为特点，以及 InnoDB 内部如何管理事务从开始到清理的全过程。

---

## 事务的五个状态

```
NOT_STARTED（未开始）：
  事务对象（trx_t）已分配，但事务尚未真正开始
  第一条 DML 执行后进入 ACTIVE 状态
  纯只读 SELECT 可能不创建正式事务对象（只读优化）

ACTIVE（活跃）：
  事务正在执行中（已有 DML 操作）
  持有行锁、Read View（如果有 SELECT）
  此状态可以持续任意长时间（长事务就处于此状态）
  可以转移到：PREPARED（两阶段提交）或 COMMITTED（直接提交）

PREPARED（已准备，2PC 第一阶段完成）：
  只在 XA 事务（外部 XA 两阶段提交）中出现
  Redo Log 已写 PREPARE 标记，等待外部协调者发出 COMMIT 或 ROLLBACK
  普通事务不经过此状态

COMMITTED_IN_MEMORY（已提交但清理中）：
  事务已提交，Redo Log 已刷盘
  正在进行后清理（释放内存、将 Undo Log 加入 History List 等）
  此状态持续时间极短（毫秒级）

ROLLED_BACK（已回滚）：
  等效于 NOT_STARTED（事务已结束，等待内存清理）
```

---

## 完整的事务生命周期

```
事务创建（CREATE）：
  → 客户端执行 BEGIN 或第一条 DML
  → InnoDB 分配 trx_t 结构体
  → 状态：NOT_STARTED / ACTIVE

ACTIVE 阶段：
  → 执行 DML：写 Undo Log，修改 Buffer Pool 数据页，加行锁
  → 执行 SELECT：创建或复用 Read View（取决于隔离级别）
  → 锁持有：在整个 ACTIVE 阶段持续持有所有行锁

  → 转移到 COMMITTED：
     显式 COMMIT，或 autocommit = ON 的单条 DML 自动提交
  
  → 转移到 ROLLED_BACK：
     显式 ROLLBACK，或死锁牺牲者，或连接断开，或锁超时

COMMIT 阶段：
  → 两阶段提交（Redo Log PREPARE → Binlog → Redo Log COMMIT）
  → Redo Log fsync（innodb_flush_log_at_trx_commit=1）
  → 状态变为 COMMITTED_IN_MEMORY
  → 释放所有行锁（此时其他被阻塞的事务可以继续）
  → 释放 Read View
  → Undo Log 加入 History List（等待 Purge）
  → trx_t 归还内存池

ROLLBACK 阶段：
  → 逆序执行 Undo Log 逆操作
  → 释放所有行锁
  → 释放 Read View
  → 清理 Undo 段引用
  → trx_t 归还内存池
```

## 查看事务状态

```sql
-- 查看所有活跃事务的状态
SELECT
    trx_id,
    trx_state,          -- RUNNING / LOCK WAIT / ROLLING BACK / COMMITTING
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
    trx_requested_lock_id,
    trx_wait_started
FROM information_schema.INNODB_TRX
ORDER BY trx_started;

-- trx_state 的含义：
-- RUNNING：事务活跃（正常执行中）
-- LOCK WAIT：等待锁（被其他事务阻塞）
-- ROLLING BACK：正在回滚（大事务回滚可见此状态）
-- COMMITTING：正在提交（很短暂，通常看不到）

-- 通过 performance_schema 查看更详细的事务状态
SELECT
    t.PROCESSLIST_ID,
    trx.TRX_ID,
    trx.TRX_STATE,
    trx.TRX_STARTED,
    trx.TRX_AUTOCOMMIT_NON_LOCKING
FROM performance_schema.events_transactions_current trx
JOIN performance_schema.threads t ON trx.THREAD_ID = t.THREAD_ID
WHERE trx.STATE = 'ACTIVE';
```

## 特殊事务状态：XA 事务

```sql
-- XA 事务（分布式事务两阶段提交）：
-- 需要经过 PREPARED 状态，由外部协调者决定最终提交/回滚

XA START 'xa_trans_001';         -- 开启 XA 事务
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
XA END 'xa_trans_001';           -- 结束 XA 事务执行阶段
XA PREPARE 'xa_trans_001';       -- 进入 PREPARED 状态（等待外部决策）

-- 查看处于 PREPARED 状态的 XA 事务
XA RECOVER;
-- 如果 MySQL 在 PREPARED 后崩溃，重启后 XA 事务仍处于 PREPARED 状态
-- 需要手动决策：
XA COMMIT 'xa_trans_001';        -- 提交
-- 或：
XA ROLLBACK 'xa_trans_001';      -- 回滚

-- MySQL 8.0.28+ 改进：XA 事务的 Binlog 在 PREPARE 时写入
-- 而不是 COMMIT 时，提高了崩溃恢复的可靠性
```

## 事务生命周期中的内存变化

```
trx_t 结构体的生命周期（内存层面）：

1. 分配：从内存池分配 trx_t（复用之前释放的对象）
2. ACTIVE：持有行锁（lock_list）、Read View、Undo 段引用
3. COMMIT：释放 lock_list、Read View；Undo 链交给 Purge
4. 归还：trx_t 归还内存池（不释放系统内存，复用给下一个事务）

锁的生命周期（lock_t）：
1. 创建：事务第一次加锁时分配（从事务的 lock_heap 分配）
2. 持有：整个事务 ACTIVE 阶段持有
3. 释放：COMMIT 或 ROLLBACK 时统一释放所有锁
4. 内存：lock_t 内存随事务一起释放

Read View 的生命周期：
1. 创建：事务第一次 SELECT（RC 级别）或 START TRANSACTION（RR 级别）
2. 持有：直到 COMMIT 或 ROLLBACK
3. 释放：事务结束时释放 Read View
4. 影响：持有 Read View 期间，Read View 的低水位阻止 Purge 清理旧版本
```

## 适用场景

- **事务监控**：通过观察 `trx_state` 为 "LOCK WAIT" 的事务，找到锁等待链路，确定阻塞源头
- **性能分析**：长时间处于 "ROLLING BACK" 状态的事务表明有大事务正在回滚，需要等待完成

## 常见问题

**"LOCK WAIT" 状态的事务最终会如何？**

LOCK WAIT 状态的事务在等待某个锁，有三种可能的结果：等到锁（其他事务释放后获得，继续执行）、超时（等待时间超过 `innodb_lock_wait_timeout`，该语句回滚，取决于 `innodb_rollback_on_timeout` 决定是否回滚整个事务）、死锁（InnoDB 检测到死锁，选择此事务或另一个事务作为牺牲者回滚）。

---

## 注意事项

- 事务对象（`trx_t`）在提交/回滚后不会立即释放到操作系统内存，而是归还到内存池供下一个事务复用（类似对象池）。这避免了频繁的内存分配/释放开销，对高并发场景的性能很重要。
- 在崩溃恢复时，InnoDB 从 Redo Log 中识别出 PREPARED 状态的 XA 事务，对于有对应 Binlog 记录的 PREPARED 事务执行 COMMIT，对于没有对应 Binlog 的执行 ROLLBACK，保证 Redo Log 和 Binlog 的一致性。

---

## 总结

InnoDB 事务经历五个状态：NOT_STARTED（未开始）→ ACTIVE（执行中，持有锁和 Read View）→ PREPARED（仅 XA 事务）→ COMMITTED_IN_MEMORY（提交清理中）→ 结束（ROLLED_BACK）。COMMIT 流程依次执行两阶段提交、锁释放、Read View 清理、Undo 加入 History List；ROLLBACK 流程逆序执行 Undo Log 后释放锁。事务对象（trx_t）通过内存池复用避免频繁分配开销。通过 `information_schema.INNODB_TRX.trx_state` 监控事务状态（RUNNING/LOCK WAIT/ROLLING BACK）是日常运维的基础技能。

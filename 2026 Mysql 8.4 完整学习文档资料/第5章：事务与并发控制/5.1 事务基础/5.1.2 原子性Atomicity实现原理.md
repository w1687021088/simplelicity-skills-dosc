# 原子性 Atomicity 实现原理

原子性（Atomicity）要求一个事务中的所有操作要么全部成功提交，要么全部失败回滚，不存在"部分执行"的中间状态。InnoDB 通过 Undo Log（回滚日志）来实现原子性：每次执行 DML 操作之前，先将"如何逆转该操作"的信息写入 Undo Log，一旦事务需要回滚（显式 ROLLBACK 或错误发生），InnoDB 按 Undo Log 的逆序执行逆操作，将数据恢复到事务开始前的状态。

---

## 原子性的实现核心：Undo Log

```
Undo Log 与原子性的关系：

DML 操作 → 对应 Undo Log 类型：
  INSERT INTO t VALUES (1, 'A')
  → INSERT Undo：记录 "DELETE FROM t WHERE id=1"（主键值）
  → 回滚时：按主键删除这条记录

  UPDATE t SET name='B' WHERE id=1（原值 name='A'）
  → UPDATE Undo：记录 "UPDATE t SET name='A' WHERE id=1"（旧值）
  → 回滚时：将 name 恢复为 'A'

  DELETE FROM t WHERE id=1（原值 name='A'）
  → UPDATE Undo（内容是删除行的完整旧值）
  → 回滚时：将该行重新插入（因为 DELETE 在事务期间只是 delete-mark）

Undo Log 链：
  一个事务的所有 Undo Log 记录通过指针链在一起
  回滚时按链表逆序执行（最后写入的先回滚）
  保证多步操作的逆序恢复
```

## 逐步演示原子性保障

```sql
-- 示例：转账场景（账户 A 转 100 元给账户 B）

-- 事务开始
BEGIN;

-- 步骤1：生成 Undo Log → "UPDATE accounts SET balance=1000 WHERE id=1"
-- 执行 DML：
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 此时数据页已修改（id=1 的 balance 从 1000 → 900）
-- 但事务未提交，其他事务看不到此修改（隔离性）

-- 步骤2：假设此处发生错误（网络超时、业务逻辑错误等）
-- 触发 ROLLBACK

ROLLBACK;

-- InnoDB 的回滚过程：
-- 1. 从 Undo Segment 中找到该事务的 Undo Log 链
-- 2. 逆序执行：
--    → 执行 "UPDATE accounts SET balance=1000 WHERE id=1"
--    → id=1 的 balance 恢复为 1000
-- 3. 释放所有锁
-- 4. 清理 Undo 段引用
-- 最终结果：accounts 表数据完全恢复，没有任何已修改的痕迹
```

## 回滚的内部执行步骤

```sql
-- ROLLBACK 的详细执行流程：
-- 1. 查找事务的 Undo Log 链（通过 trx_t.rsegs 找到 Rollback Segment）
-- 2. 按 Undo Log 序号从大到小（逆操作顺序）遍历
-- 3. 对每条 Undo Log 记录：
--    → INSERT Undo → 执行 DELETE（按主键删除）
--    → UPDATE Undo → 执行 UPDATE（恢复旧值，包含所有修改列的旧值）
--    → DELETE Undo → 清除 delete-mark，恢复行可见性
-- 4. 撤销 delete-mark 或实际删除
-- 5. 释放该事务持有的所有行锁和表锁

-- 查看回滚进度（对于大事务）
SHOW ENGINE INNODB STATUS \G
-- 在 TRANSACTIONS 部分：
-- Rolling back transaction #XXXXX, undone operations: N
-- 显示已回滚的操作数，可以估算剩余回滚时间

-- 注意：大事务回滚非常耗时！
-- 如果事务修改了 100 万行，回滚需要同等量的逆操作
-- 回滚期间持续产生 Redo Log（逆操作本身也需要记录到 Redo Log 保证持久性）
```

## 保存点（SAVEPOINT）与部分原子性

```sql
-- SAVEPOINT 允许在事务内设置"检查点"
-- 回滚到 SAVEPOINT 只撤销该点之后的操作（不是整个事务）

BEGIN;
INSERT INTO orders VALUES (1, 100.00);  -- 操作1
SAVEPOINT sp1;                           -- 设置保存点
INSERT INTO orders VALUES (2, 200.00);  -- 操作2
INSERT INTO orders VALUES (3, 300.00);  -- 操作3

-- 只回滚操作2和操作3，保留操作1
ROLLBACK TO SAVEPOINT sp1;

-- 此时：id=1 的订单存在，id=2 和 id=3 的订单不存在
-- 继续执行其他操作
INSERT INTO orders VALUES (4, 400.00);  -- 操作4
COMMIT;
-- 最终：id=1 和 id=4 的订单提交成功

-- SAVEPOINT 的原子性保障：
-- ROLLBACK TO SAVEPOINT sp1 会执行操作3和操作2的 Undo Log
-- 只撤销 sp1 之后的操作，sp1 之前的操作不受影响
```

## 语句级原子性 vs 事务级原子性

```sql
-- 即使没有显式 BEGIN，每条 SQL 语句也有原子性保障（语句级原子性）

-- 单条 UPDATE 影响 1000 行：
UPDATE orders SET status = 'processed' WHERE created_at < '2024-01-01';
-- 假设执行到一半（500行已修改）时崩溃
-- 重启后：InnoDB 通过 Undo Log 回滚这条语句的所有修改
-- 最终：1000 行都是原始状态（0 行修改成功），而不是 500 行成功

-- 这就是"语句级原子性"：
-- 即使是单条 SQL，如果没有完成，InnoDB 会回滚该语句的所有部分操作

-- 与事务级原子性的区别：
-- 语句级：一条 SQL 要么完全执行，要么完全不执行
-- 事务级：一组 SQL 要么全部提交，要么全部回滚（显式 BEGIN...COMMIT/ROLLBACK）
```

## 适用场景

- **数据完整性保障**：对于需要修改多张表的复杂业务操作（如订单 + 库存 + 积分同时修改），必须将这些操作包装在一个事务中，利用原子性保证"要么全成功要么全不做"
- **错误恢复**：理解 Undo Log 实现原子性的机制，有助于评估大事务回滚的耗时和对系统的影响，从而在设计时避免单个超大事务（拆分为多个小事务）

## 常见问题

**DDL 语句（CREATE TABLE、ALTER TABLE）也有原子性吗？**

在 MySQL 8.0 之前，DDL 操作没有原子性（DDL 执行到一半崩溃会导致不一致状态，如半创建的表文件）。MySQL 8.0 引入了原子 DDL（Atomic DDL），将 DDL 操作整合到事务中，支持 CREATE TABLE、DROP TABLE、ALTER TABLE 等操作的原子性——要么完全成功，要么完全回滚（通过写入 mysql.ddl_log 系统表并在崩溃后重放或回滚）。这是 MySQL 8.0 的重要改进。

---

## 注意事项

- 大事务的回滚耗时与事务修改的数据量成正比（修改了多少行，就需要回滚多少行的 Undo Log）。在生产环境中，应避免单个事务修改大量数据（如百万行 UPDATE），可以拆分为多个小批量事务，每批提交，减少单次回滚的代价。
- Undo Log 本身的写入也需要 Redo Log 保护（Undo Log 页的修改会产生 Redo Log），因此原子性和持久性是相互配合的，不是独立的。这也是 InnoDB 在崩溃恢复时需要先 Redo 再 Undo 的原因（先应用 Redo Log，再回滚未提交事务的 Undo Log）。

---

## 总结

原子性通过 Undo Log 实现：每次 DML 操作前写入"逆操作"信息（INSERT → 对应删除记录、UPDATE → 对应旧值恢复、DELETE → 对应取消 delete-mark），事务回滚时逆序执行 Undo Log 恢复数据。SAVEPOINT 支持部分回滚（只回滚保存点之后的操作）。单条 SQL 也有语句级原子性（语句中途失败回滚该语句的全部修改）。大事务回滚耗时长（与修改量成正比），生产环境应拆分大事务。MySQL 8.0 的原子 DDL 将 DDL 操作也纳入原子性保障范围。

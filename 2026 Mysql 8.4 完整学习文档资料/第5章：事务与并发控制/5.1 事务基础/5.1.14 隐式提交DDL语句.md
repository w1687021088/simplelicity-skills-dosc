# 隐式提交 DDL 语句

隐式提交（Implicit Commit）是指某些 SQL 语句执行时，自动提交当前活跃事务中所有未提交的 DML 修改，无需（也无法通过）显式 COMMIT 触发。DDL 语句是触发隐式提交的最主要类型，同时权限管理语句、`START TRANSACTION`/`BEGIN` 本身以及某些维护语句也会触发。

---

## 触发隐式提交的 SQL 类型

```
DDL 语句（最常见）：
  CREATE TABLE, CREATE INDEX, CREATE VIEW
  CREATE PROCEDURE, CREATE FUNCTION, CREATE TRIGGER, CREATE EVENT
  ALTER TABLE, ALTER VIEW, ALTER PROCEDURE, ALTER FUNCTION
  DROP TABLE, DROP INDEX, DROP VIEW, DROP PROCEDURE, DROP FUNCTION
  RENAME TABLE
  TRUNCATE TABLE
  CREATE DATABASE, DROP DATABASE, ALTER DATABASE

权限管理语句：
  CREATE USER, DROP USER, ALTER USER
  GRANT, REVOKE
  SET PASSWORD, RENAME USER

事务控制语句（触发对前一个事务的隐式提交）：
  START TRANSACTION（开启新事务，先提交旧事务）
  BEGIN（等效于 START TRANSACTION）
  SET autocommit = 1（从 OFF 改为 ON 时）

锁定语句：
  LOCK TABLES, UNLOCK TABLES

分析与维护语句：
  ANALYZE TABLE, OPTIMIZE TABLE, REPAIR TABLE
```

---

## 隐式提交的陷阱演示

```sql
-- 错误示例：期望在失败时回滚 DDL
BEGIN;
INSERT INTO orders VALUES (1001, 'pending', 100.00);  -- DML（未提交）

-- 下面的 DDL 会隐式提交上面的 INSERT！
ALTER TABLE orders ADD COLUMN remark VARCHAR(200);
-- INSERT 被隐式提交，无法通过 ROLLBACK 撤销！

ROLLBACK;  -- 只回滚 ALTER TABLE 之后的操作（没有），INSERT 已提交
-- 结果：id=1001 的订单已永久写入，与预期不同

-- 正确做法：
-- 在执行 DDL 之前，先 COMMIT 或 ROLLBACK 当前事务
COMMIT;  -- 先提交 DML
ALTER TABLE orders ADD COLUMN remark VARCHAR(200);  -- 再执行 DDL
```

## TRUNCATE TABLE 的特殊性

```sql
-- TRUNCATE TABLE 是 DDL，触发隐式提交，不可回滚
-- 与 DELETE 不同：DELETE 是 DML，可以在事务中回滚

-- 可以回滚的 DELETE：
BEGIN;
DELETE FROM orders;    -- DML，删除所有行
ROLLBACK;              -- 成功回滚，数据恢复

-- 不可回滚的 TRUNCATE：
BEGIN;
INSERT INTO orders VALUES (2001, 'new', 50.00);  -- DML（未提交）
TRUNCATE TABLE orders;  -- 触发隐式提交：INSERT 先被提交，然后表被清空
ROLLBACK;               -- 无效，TRUNCATE 已执行
-- 结果：表为空（TRUNCATE 清除了含 id=2001 在内的所有数据）
```

## MySQL 8.0 原子 DDL 与隐式提交

```sql
-- MySQL 8.0 引入原子 DDL（Atomic DDL）
-- 使 DDL 操作本身具有原子性（DDL 失败时自动完整回滚 DDL）
-- 但原子 DDL 不消除 DDL 对前一个事务的隐式提交行为！

-- 原子 DDL 保证：
--   DDL 本身要么完全成功，要么完全回滚（崩溃安全）

-- 原子 DDL 不保证：
--   DDL 执行前的 DML 修改不会被隐式提交

-- 支持原子 DDL 的语句类型（MySQL 8.0）：
-- CREATE/ALTER/DROP TABLE（InnoDB 表）
-- CREATE/DROP DATABASE
-- CREATE/ALTER/DROP PROCEDURE/FUNCTION/VIEW/TRIGGER/EVENT

-- 查看是否支持原子 DDL（通过 MySQL 版本判断）
SELECT VERSION();  -- 8.0+ 支持原子 DDL
```

## 最佳实践

```sql
-- 原则1：不在业务事务中混用 DDL
-- DDL 应在独立的维护窗口执行，与业务 DML 分开

-- 原则2：执行 DDL 前先确认没有未提交的重要事务
-- 检查活跃事务：
SELECT trx_id, trx_started, trx_query
FROM information_schema.INNODB_TRX;

-- 原则3：在应用框架的事务注解之外执行 DDL
-- Spring 中，@Transactional 方法内的 DDL 会触发事务提交
-- 应将 DDL 移到 @Transactional 注解之外

-- 原则4：使用 pt-online-schema-change 或 gh-ost 执行大表 DDL
-- 避免 ALTER TABLE 长时间锁表（这是 DDL 隐式提交之外的另一个问题）
```

## 适用场景

- **数据库升级脚本**：编写数据库版本升级脚本时，将 DDL（ALTER TABLE、CREATE INDEX）和 DML 数据迁移操作分开处理，确保各自的原子性
- **故障排查**：当发现"明明 ROLLBACK 了但数据还在"时，检查事务中是否有 DDL 触发了隐式提交

---

## 常见问题

**TRUNCATE 是 DDL 还是 DML？能被 ROLLBACK 撤销吗？**

在 MySQL 中，`TRUNCATE TABLE` 的行为是 DDL 语义：触发隐式提交，且清空表操作本身不能被回滚（与 `DELETE` 不同）。SQL 标准将 TRUNCATE 分类为 DDL。在需要可回滚的"删除所有行"操作时，必须使用 `DELETE FROM table_name`（无 WHERE 条件），它是 DML，产生 Undo Log，可以在事务中回滚（但代价是需要记录每行的 Undo）。

---

## 注意事项

- `START TRANSACTION` 和 `BEGIN` 本身也会触发对前一个活跃事务的隐式提交（如果有的话）。因此不能通过"嵌套 BEGIN"来实现嵌套事务，第二个 BEGIN 会先提交第一个事务，再开启新事务。MySQL InnoDB 不支持真正的嵌套事务（只有 SAVEPOINT 实现的部分回滚）。
- 在主从复制环境中，触发隐式提交的 DDL 会以单独的事务形式写入 Binlog，从库会同步执行。DDL 之前被隐式提交的 DML 也会以独立事务形式写入 Binlog。

---

## 总结

DDL 语句（CREATE/ALTER/DROP TABLE、TRUNCATE TABLE 等）、权限管理语句（GRANT/REVOKE）、`START TRANSACTION`/`BEGIN` 本身都会触发隐式提交，自动提交当前活跃事务中所有未提交的 DML 修改。`TRUNCATE TABLE` 是最常见陷阱（不可回滚）。MySQL 8.0 的原子 DDL 保证 DDL 本身的原子性，但不消除 DDL 对前一个事务的隐式提交。最佳实践是不在业务事务中混用 DDL，执行 DDL 前先确认没有重要的未提交事务。

# COMMIT 提交事务

`COMMIT` 是提交当前事务的 SQL 命令，使事务中所有 DML 操作的修改永久生效并对其他事务可见。执行 `COMMIT` 时，InnoDB 完成 Redo Log 的落盘（fsync）、Binlog 的写入（如已启用）、锁的释放、Read View 的清理等一系列操作，确保事务符合持久性（Durability）要求，修改永久保存。

---

## COMMIT 的执行流程

```
COMMIT 内部执行步骤（innodb_flush_log_at_trx_commit = 1，启用 Binlog）：

1. 写入 Redo Log（Prepare 阶段）
   → 将事务的 Redo Log 标记为 PREPARE 状态
   → 将 Redo Log Buffer 中的记录 fsync 到磁盘

2. 写入 Binlog
   → 将事务的 Binlog Event 写入 Binlog 文件（sync_binlog=1 时 fsync）

3. 写入 Redo Log（Commit 阶段）
   → 将 Redo Log 标记为 COMMIT 状态
   → fsync 到磁盘（确认 Commit 记录持久化）

4. 释放所有锁
   → 释放该事务持有的行锁、间隙锁、表级意向锁
   → 被此事务阻塞的其他事务被唤醒

5. 释放 Read View
   → 清理事务的快照（MVCC Read View）

6. 将 Undo Log 加入 History List
   → 已提交的 Undo Log 不立即删除，等待 Purge 线程清理

7. 返回 COMMIT 成功到客户端
```

## COMMIT 语法变体

```sql
-- 标准 COMMIT
COMMIT;

-- COMMIT WORK（等效于 COMMIT，SQL 标准写法）
COMMIT WORK;

-- COMMIT AND CHAIN（提交后立即开启新事务，无间隙）
COMMIT AND CHAIN;
-- 等效于：COMMIT; START TRANSACTION;

-- COMMIT AND RELEASE（提交后断开连接）
COMMIT AND RELEASE;
-- 等效于：COMMIT; DISCONNECT;
```

## COMMIT 后的数据可见性

```sql
-- COMMIT 完成后，修改对其他事务的可见性取决于隔离级别：

-- READ COMMITTED 级别的其他事务：
-- COMMIT 后，其他事务下次执行 SELECT 立即可以看到修改
-- （RC 级别每次 SELECT 创建新的 Read View）

-- REPEATABLE READ 级别的其他事务：
-- 如果其他事务在 COMMIT 之前已创建 Read View：
--   → 看不到修改（Read View 在 COMMIT 之前建立）
-- 如果其他事务在 COMMIT 之后创建 Read View：
--   → 可以看到修改（修改的 trx_id 已在 Read View 创建前提交）

-- 示例：
-- 会话1（RR 隔离级别）：
BEGIN;
SELECT * FROM orders WHERE id = 1;  -- 创建 Read View，看到 amount=100

-- 会话2：
BEGIN;
UPDATE orders SET amount = 200 WHERE id = 1;
COMMIT;  -- 会话2的修改已提交

-- 会话1（继续）：
SELECT * FROM orders WHERE id = 1;
-- → 还是看到 amount=100（RR 级别，Read View 已固定）
```

## 批量提交性能优化

```sql
-- 每次 COMMIT 需要 fsync Redo Log（约 1-10ms）
-- 高频单行提交是性能瓶颈，批量提交可大幅提升吞吐量

-- 不好的写法（每条插入一个事务）：
-- 1000 行 = 1000 次 COMMIT = 1000 次 fsync
BEGIN; INSERT INTO t VALUES (1); COMMIT;
BEGIN; INSERT INTO t VALUES (2); COMMIT;
-- ...

-- 好的写法（批量插入一个事务）：
BEGIN;
INSERT INTO t VALUES (1), (2), ..., (1000);
COMMIT;
-- 1000 行 = 1 次 COMMIT = 1 次 fsync（快约 1000 倍！）

-- innodb_flush_log_at_trx_commit 对性能的影响：
-- 值 1（默认）：每次 COMMIT fsync，最安全，最慢
-- 值 2：每次 COMMIT 写 OS Cache，每秒 fsync，性能较高
-- 值 0：每秒写 OS Cache + fsync，性能最高，最不安全
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

## 适用场景

- **批量数据处理**：将批量 INSERT/UPDATE 包装在单个事务中，减少 COMMIT 次数和 fsync 开销
- **连续事务**：使用 `COMMIT AND CHAIN` 在事务边界无缝衔接，减少重新 START TRANSACTION 的开销

---

## 常见问题

**COMMIT 成功后，数据一定持久化了吗？**

取决于 `innodb_flush_log_at_trx_commit` 的设置：值为 1（默认）时，COMMIT 保证 Redo Log 已 fsync 到物理磁盘，即使 MySQL 进程崩溃或 OS 崩溃重启也不会丢失。值为 2 时，MySQL 进程崩溃不会丢失，OS 崩溃（如断电）可能丢失最近 1 秒内提交的事务。值为 0 时，任何崩溃都可能丢失最近 1 秒内的提交。

---

## 注意事项

- 在启用 Binlog 的情况下，COMMIT 的持久性需要 Redo Log 和 Binlog 都落盘。两阶段提交（2PC）保证两者的一致性。如果只有 Redo Log 落盘而 Binlog 未落盘时崩溃，重启后会回滚该事务。
- COMMIT 释放所有锁的时机是整体性的——所有锁在 COMMIT 之后统一释放（两阶段锁定协议），而不是语句执行后立即释放。长事务会长期持有锁，设计时应缩短事务范围。

---

## 总结

`COMMIT` 提交事务，永久持久化修改并释放所有锁和 Read View，内部依次执行 Redo Log 两阶段提交（Prepare + Commit）和 Binlog 写入（有 Binlog 时）。批量提交（多行合并到一个事务）是提升写入吞吐量的关键手段。`COMMIT AND CHAIN` 可在提交后立即开启新事务。COMMIT 后数据对其他事务的可见时机取决于隔离级别（RC 立即可见，RR 需等对方开启新 Read View 才可见）。

# 隐式事务与自动提交 AUTOCOMMIT

MySQL 中有两种事务执行模式：显式事务（通过 `BEGIN`/`START TRANSACTION` 开启，`COMMIT`/`ROLLBACK` 结束）和隐式事务（由 `autocommit` 系统变量控制的自动提交行为）。当 `autocommit = ON`（默认）时，每条 DML 语句都被隐式包裹在一个独立的事务中，执行完毕后自动提交。理解隐式事务的行为对于正确编写事务性代码至关重要。

---

## autocommit 控制原理

```sql
-- 查看当前 autocommit 设置
SHOW VARIABLES LIKE 'autocommit';
SELECT @@autocommit;
-- 默认值：ON（1）

-- autocommit = ON（默认）：每条 SQL 语句是一个独立事务
-- 执行完毕后自动提交，等效于每条 DML 外面隐式包裹了 BEGIN...COMMIT
INSERT INTO t VALUES (1);  -- 相当于：BEGIN; INSERT...; COMMIT;
INSERT INTO t VALUES (2);  -- 相当于：BEGIN; INSERT...; COMMIT;

-- autocommit = OFF：需要显式 COMMIT 才提交
SET SESSION autocommit = OFF;
INSERT INTO t VALUES (1);  -- 未提交，在隐式事务中
INSERT INTO t VALUES (2);  -- 未提交，在同一隐式事务中
COMMIT;                     -- 显式提交，两条插入一起生效
```

---

## 隐式事务与显式事务的交互

```sql
-- 即使 autocommit = ON，START TRANSACTION 也会暂时禁用 autocommit
-- 直到 COMMIT/ROLLBACK 后恢复 autocommit 行为

SET SESSION autocommit = ON;
INSERT INTO t VALUES (5);  -- 自动提交（单条隐式事务）

START TRANSACTION;          -- 开启显式事务（覆盖 autocommit）
INSERT INTO t VALUES (6);  -- 不自动提交
INSERT INTO t VALUES (7);  -- 不自动提交
ROLLBACK;                   -- id=6,7 被撤销

INSERT INTO t VALUES (8);  -- 显式事务结束后，恢复自动提交，id=8 自动提交

-- 结论：START TRANSACTION 是"会话内临时禁用 autocommit"的方式
-- COMMIT/ROLLBACK 后，autocommit 设置恢复到开启 START TRANSACTION 之前的状态
```

---

## 会话级别与全局级别设置

```sql
-- 会话级设置（只影响当前连接）
SET SESSION autocommit = OFF;
SET autocommit = OFF;  -- 省略 SESSION 默认是会话级别

-- 全局设置（影响新建连接，不影响已有连接）
SET GLOBAL autocommit = OFF;

-- 永久修改（写入配置文件 my.cnf）
-- [mysqld]
-- autocommit = 0

-- 查看全局和会话的当前值
SELECT @@global.autocommit, @@session.autocommit;
```

## 不同语言/框架的 autocommit 默认行为

| 语言/框架 | 默认 autocommit | 说明 |
|---------|----------------|------|
| MySQL CLI | ON | 与服务器默认一致 |
| Java JDBC | ON | `connection.setAutoCommit(false)` 关闭 |
| Python pymysql | ON | 连接时可配置 `autocommit=True/False` |
| Go database/sql | ON | `db.Begin()` 开启手动事务 |
| Spring @Transactional | 方法内 OFF | Spring 管理事务范围，方法内自动关闭 autocommit |
| Django ORM | ON | 默认每个查询自动提交（设置 ATOMIC_REQUESTS 可改） |

## autocommit = OFF 的风险

```sql
-- 风险1：忘记提交（连接断开时自动回滚）
SET SESSION autocommit = OFF;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- ... 其他操作 ...
-- 忘记 COMMIT，连接断开时自动回滚，修改全部丢失！

-- 风险2：长时间未提交的隐式事务
-- 持有行锁，阻塞其他事务
-- 持有 Read View，阻止 Purge 清理旧版本（Undo 表空间膨胀）

-- 监控未提交事务
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;
```

## 适用场景

- **OLTP 短事务**：`autocommit = ON`（默认）适合短事务场景，每条 SQL 提交，锁持有时间最短，适合高并发
- **批量数据处理**：临时使用 `START TRANSACTION` 合并多行为一个事务，减少 fsync 次数，大幅提升批量写入性能

---

## 常见问题

**为什么推荐用 START TRANSACTION 而不是 SET autocommit = OFF？**

`SET autocommit = OFF` 关闭后，会话内所有后续 SQL 都在隐式事务中，边界不清晰，容易忘记 COMMIT，导致长事务和锁积压。`START TRANSACTION` 明确标记事务开始和结束（`COMMIT`/`ROLLBACK`），代码可读性更好，边界清晰，维护时更易理解。

---

## 注意事项

- 某些 MySQL 连接池（如 HikariCP）会在归还连接时自动执行 `ROLLBACK` 来清理未提交的事务，防止事务状态"泄漏"到下一个请求。但仍需在应用层保证事务明确结束，不能依赖连接池的清理行为。
- `autocommit = OFF` 配合批量提交时，效果最佳：多条 DML 共用一个事务，一次 fsync 提交，比每条 SQL 单独 autocommit 的吞吐量高很多倍（减少了 fsync 次数）。

---

## 总结

`autocommit`（默认 ON）控制每条 DML 是否自动提交。ON 时每条 SQL 是独立的隐式事务，自动提交；OFF 时需显式 `COMMIT`。`START TRANSACTION` 在任何 autocommit 设置下都能开启显式手动事务，COMMIT/ROLLBACK 后恢复原 autocommit 设置。关闭 autocommit 可减少 fsync 提升批量写入性能，但易导致忘记提交的长事务。推荐使用 `START TRANSACTION...COMMIT/ROLLBACK` 显式边界管理事务，而非 `SET autocommit=OFF`。

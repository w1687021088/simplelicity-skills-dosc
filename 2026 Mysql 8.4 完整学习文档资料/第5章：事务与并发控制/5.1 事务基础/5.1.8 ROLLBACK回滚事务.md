# ROLLBACK 回滚事务

`ROLLBACK` 是撤销当前事务中所有未提交修改的 SQL 命令，使数据库恢复到事务开始前的状态。执行 `ROLLBACK` 时，InnoDB 按照 Undo Log 的逆序执行逆操作，逐一撤销事务中的每条 DML 语句，然后释放该事务持有的所有锁和 Read View。ROLLBACK 是事务原子性的核心保障机制，确保部分失败的操作不会遗留中间状态。

---

## 基本用法

```sql
-- 显式回滚（放弃当前事务所有修改）
ROLLBACK;

-- ROLLBACK WORK（等效于 ROLLBACK，SQL 标准写法）
ROLLBACK WORK;

-- 回滚到保存点（部分回滚）
ROLLBACK TO SAVEPOINT savepoint_name;
ROLLBACK TO sp1;  -- 只回滚 sp1 之后的操作

-- 示例：转账失败回滚
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 扣款
UPDATE accounts SET balance = balance + 100 WHERE id = 99999;  -- 账户不存在，报错
-- 错误发生时，应用层捕获并执行 ROLLBACK
ROLLBACK;
-- 结果：id=1 的余额恢复为原值，没有任何修改
```

## ROLLBACK 的内部执行过程

```
ROLLBACK 的详细步骤：

1. 查找 Undo Log 链
   → 通过 trx_t.rsegs 找到该事务的 Undo Segment
   → 获取 Undo Log 链的末尾（最后写入的 Undo Log 记录）

2. 逆序执行 Undo Log
   → 对每条 Undo Log 记录执行逆操作：
     INSERT Undo → 按主键删除该行（物理删除）
     UPDATE Undo → 将行数据恢复为旧值（回写原有列值）
     DELETE Undo → 清除 delete-mark，恢复行可见性
   → 每次逆操作本身也生成 Redo Log（保证崩溃后可重做回滚）

3. 释放所有锁
   → 释放该事务持有的所有行锁、间隙锁、表级意向锁
   → 被此事务阻塞的其他事务被唤醒

4. 清理 Read View
   → 释放该事务的快照（Read View）

5. 标记 Undo Log 状态
   → 将 Undo 段标记为可回收（Purge 线程清理）

6. 返回成功
```

## 大事务回滚的性能影响

```sql
-- 回滚耗时 = 正向执行耗时
-- 修改了 N 行，回滚也需要处理 N 行的 Undo Log
-- 大事务（几十万行）的回滚可能需要几分钟甚至更长

-- 监控回滚进度
SHOW ENGINE INNODB STATUS \G
-- 查找：Rolling back trx with id XXX, XXX operations left

-- 回滚期间的影响：
-- 1. 持续消耗 CPU（执行逆操作）
-- 2. 持续写入 Redo Log（每次逆操作都记日志）
-- 3. 大量行锁持续持有（直到回滚完成才释放）
-- 4. 阻塞依赖这些行锁的其他事务

-- 避免大事务回滚的实践：
-- 批量操作拆分为多个小事务（每批 1000-10000 行）
-- 每批 COMMIT 后，如果后续出错，只需回滚最后一小批
-- 前面已提交的部分需要应用层执行补偿操作（而非 DB ROLLBACK）
```

## ROLLBACK 与 SAVEPOINT

```sql
-- SAVEPOINT 设置回滚点
SAVEPOINT sp1;

-- ROLLBACK TO SAVEPOINT 只回滚至该点
ROLLBACK TO SAVEPOINT sp1;
ROLLBACK TO sp1;  -- 简写（MySQL 允许省略 SAVEPOINT 关键字）

-- RELEASE SAVEPOINT 删除保存点（不回滚）
RELEASE SAVEPOINT sp1;

-- 完整示例：
BEGIN;
INSERT INTO orders VALUES (1, 'pending', 100.00);
SAVEPOINT step1;

INSERT INTO orders VALUES (2, 'pending', 200.00);
SAVEPOINT step2;

INSERT INTO orders VALUES (3, 'pending', 300.00);
-- 发现第三步有问题，只回滚第三步
ROLLBACK TO step2;
-- 此时 id=1 和 id=2 的记录存在，id=3 回滚

COMMIT;  -- 提交 id=1 和 id=2
```

## 隐式回滚的情况

```sql
-- MySQL 在以下情况会自动执行隐式回滚：

-- 1. 事务内发生错误（如外键约束冲突）
-- MySQL 默认行为（取决于 sql_mode）：
-- 语句失败后，该语句的修改被回滚，但事务不一定回滚
-- 需要应用层检查错误并显式 ROLLBACK

-- 2. 客户端连接断开
-- 连接断开时，MySQL 自动回滚该连接上未提交的事务
-- 保证不会有"游离的"未提交修改

-- 3. 锁等待超时（innodb_lock_wait_timeout）
-- 事务等待锁超时后，该事务的当前语句被回滚
-- 注意：只回滚超时的那条语句，不是整个事务（除非 innodb_rollback_on_timeout=ON）
SHOW VARIABLES LIKE 'innodb_rollback_on_timeout';
-- 默认：OFF（只回滚超时语句，事务继续）
-- ON 时：超时则回滚整个事务

-- 4. 死锁检测回滚
-- InnoDB 检测到死锁时，选择 weight 最小的事务回滚
-- 该事务的所有未提交修改被全部回滚
```

## 适用场景

- **错误处理**：在应用层的 try-catch 中，捕获到任何 SQL 异常后执行 ROLLBACK，确保不残留部分完成的操作
- **业务校验失败**：在事务内完成所有修改后，执行业务层校验（如检查总金额是否一致），校验失败时 ROLLBACK

## 常见问题

**事务中某条 SQL 报错后，还能继续执行其他 SQL 吗？**

取决于错误类型。对于一般 DML 错误（如 UNIQUE KEY 冲突），MySQL 回滚该条语句（语句级原子性），但事务仍然处于活跃状态，可以继续执行其他 SQL 或 ROLLBACK/COMMIT。但如果是严重错误（如语法错误或某些存储过程错误），可能导致整个事务无效。最佳实践是：捕获任何错误后立即执行 ROLLBACK，不要在出错后继续事务（避免不一致状态）。

---

## 注意事项

- DDL 语句（如 `CREATE TABLE`、`ALTER TABLE`、`TRUNCATE TABLE`）在 MySQL 中会触发隐式提交，不能被 ROLLBACK 撤销。即使在事务中执行了 DDL，之前的 DML 修改也会被隐式提交，DDL 之后执行 ROLLBACK 无法回到 DDL 之前的状态。这是 MySQL 事务模型的重要限制。
- 在应用层框架（如 Java Spring）中，事务的 ROLLBACK 通常由框架自动处理（在抛出异常时自动回滚）。但仍需了解底层机制，以便处理框架不自动回滚的场景（如受检异常 checked exception 默认不触发回滚）。

## 总结

`ROLLBACK` 撤销事务中所有未提交的修改，通过逆序执行 Undo Log 中的逆操作恢复数据，然后释放所有锁和 Read View。大事务回滚耗时长（与修改量成正比），期间持续持有锁阻塞其他事务，生产环境应避免大事务（拆分为小批次事务）。`ROLLBACK TO SAVEPOINT` 支持部分回滚（只撤销保存点之后的操作）。连接断开、锁等待超时（`innodb_rollback_on_timeout=ON`）、死锁检测都会触发隐式回滚。DDL 触发隐式提交，不可通过 ROLLBACK 撤销。

# 事务 ACID 特性定义

ACID 是数据库事务的四个核心属性的缩写：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。这四个特性共同定义了一个数据库事务应该具备的行为保障，确保事务在任何情况下（包括系统崩溃、并发访问）都能以可预期和正确的方式执行。MySQL InnoDB 存储引擎完整实现了 ACID 特性。

---

## 原子性（Atomicity）

```
定义：事务中的所有操作要么全部成功提交，要么全部失败回滚，不存在中间状态。

含义：
  一个事务可以包含多条 SQL 语句（INSERT、UPDATE、DELETE 等）
  这些语句作为一个不可分割的整体执行
  如果任何一条失败，整个事务所做的修改都回滚到原始状态

实现机制：
  InnoDB 通过 Undo Log 实现原子性
  每次修改前记录"如何逆操作"（反向 SQL 语义）
  事务回滚时，按照 Undo Log 的逆序执行逆操作，恢复数据

示例：
  BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 扣款
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- 入账
  COMMIT;

  如果第二条 UPDATE 执行失败（如账户 2 不存在），
  整个事务回滚：账户 1 的扣款也被撤销。
  不会出现"扣了款但没入账"的中间状态。
```

## 一致性（Consistency）

```
定义：事务执行前后，数据库从一个一致状态变为另一个一致状态，
      满足所有完整性约束（主键、外键、唯一约束、Check 约束等）。

含义：
  "一致性"是事务的目标，其他三个特性（AID）是手段
  无论发生什么（崩溃、并发），数据都不会违反完整性约束
  
  例如：转账事务要求"转账前后两个账户的总余额不变"
  这是业务层面的一致性规则，由 AID 三个特性共同保障

一致性的两个层次：
  1. 数据库层一致性：
     → 主键唯一性约束（不能有重复主键）
     → 外键引用完整性（不能引用不存在的父记录）
     → NOT NULL 约束（不能插入 NULL 到 NOT NULL 列）
     → 这些由 MySQL 自动在语句执行时检查

  2. 业务层一致性：
     → 账户余额不能为负数（需要业务代码或 CHECK 约束）
     → 库存不能超卖（需要事务控制并发）
     → 这些需要开发者自行保证
```

## 隔离性（Isolation）

```
定义：并发执行的多个事务，每个事务的中间状态对其他事务不可见，
      各事务仿佛在串行执行一样。

含义：
  多个事务并发运行时，一个事务所做的修改在提交前不应影响其他事务
  "完全隔离"意味着串行化（Serializable），但性能代价大
  实际中通过"隔离级别"在隔离性与并发性之间权衡

SQL 标准定义的四个隔离级别（从弱到强）：
  READ UNCOMMITTED：读未提交（隔离性最弱，并发性最高）
  READ COMMITTED：读已提交（消除脏读）
  REPEATABLE READ：可重复读（消除脏读 + 不可重复读，MySQL 默认）
  SERIALIZABLE：串行化（最强隔离，相当于完全串行执行）

实现机制：
  InnoDB 通过两种机制实现隔离性：
  1. MVCC（多版本并发控制）：读写不互斥（快照读）
  2. 锁机制：写写互斥（行锁、间隙锁）
```

---

## 持久性（Durability）

```
定义：事务提交后，其所做的修改永久保存，即使系统崩溃也不丢失。

含义：
  COMMIT 成功后，数据就一定写入了磁盘（不会因为进程崩溃而丢失）
  这是"可靠性"的基础，用户可以信任提交结果

实现机制：
  InnoDB 通过 Redo Log（重做日志）实现持久性
  事务提交时，必须先将 Redo Log 刷到磁盘（fsync）
  即使此后 MySQL 崩溃，下次启动时从 Redo Log 恢复修改

  关键配置：innodb_flush_log_at_trx_commit = 1（默认，最安全）
  → 每次 COMMIT 都 fsync Redo Log 到磁盘
  → 即使硬件故障（OS 崩溃、掉电），已提交的数据不丢失
```

## ACID 四个特性的实现映射

| ACID 特性 | 中文 | MySQL/InnoDB 实现机制 |
|----------|------|---------------------|
| Atomicity | 原子性 | Undo Log（回滚时逆操作恢复数据）|
| Consistency | 一致性 | 约束检查 + A、I、D 共同保障 |
| Isolation | 隔离性 | MVCC + 锁机制（行锁、间隙锁）|
| Durability | 持久性 | Redo Log（WAL + fsync）|

## ACID 与非 ACID 存储引擎的区别

```sql
-- InnoDB（支持 ACID）：
CREATE TABLE orders (
    id     INT PRIMARY KEY,
    amount DECIMAL(10, 2)
) ENGINE = InnoDB;  -- 完整 ACID 支持

-- MyISAM（不支持 ACID）：
CREATE TABLE logs (
    id      INT PRIMARY KEY AUTO_INCREMENT,
    message TEXT
) ENGINE = MyISAM;  -- 无事务、无行锁（只有表锁）、无崩溃自恢复

-- 区别总结（InnoDB vs MyISAM）：
-- 原子性：InnoDB 有 Undo Log 支持，MyISAM 没有
-- 持久性：InnoDB 有 Redo Log，MyISAM 崩溃可能损坏数据
-- 隔离性：InnoDB 有行锁 + MVCC，MyISAM 只有表锁
-- 一致性：InnoDB 有完整约束支持，MyISAM 也有但无事务保证

-- MySQL 8.0 已完全去除 MyISAM 对系统表的使用（全面转向 InnoDB）
```

## 适用场景

- **金融/支付类业务**：必须保证 ACID 的全部四个特性，特别是持久性（`innodb_flush_log_at_trx_commit=1`）和原子性（转账必须要么全成功要么全失败）
- **高并发读写场景**：在保证隔离性的前提下，选择合适的隔离级别（如 READ COMMITTED 而非默认的 REPEATABLE READ），在隔离性与并发性之间取得平衡

## 常见问题

**一致性（Consistency）是不是等同于原子性（Atomicity）？**

不同。原子性是"事务中的操作要么全做要么全不做"，是一个关于事务执行模式的属性。一致性是"事务执行后数据仍然满足所有完整性约束"，是一个关于数据状态的属性。原子性是保证一致性的手段之一，但一致性还需要隔离性和持久性配合，以及业务逻辑正确性。一个事务可以是原子性的（全提交），但如果违反了外键约束，就破坏了一致性。

## 注意事项

- 在非严格 SQL 模式（`sql_mode` 不包含 `STRICT_TRANS_TABLES`）下，MySQL 可能将不合法的值截断后写入而不是报错，这可能悄悄破坏业务层面的一致性。建议在生产环境启用严格模式：`SET sql_mode = 'STRICT_TRANS_TABLES,...';`
- 隔离性的"完全隔离"（Serializable 级别）在实践中使用较少，因为代价太高（大量锁等待）。MySQL 默认的 REPEATABLE READ 加上 InnoDB 的 Next-Key Lock 在大多数场景下已足够，既防止幻读又有较好的并发性。

---

## 总结

ACID 是事务的四大核心属性：原子性（操作不可分割，通过 Undo Log 实现）、一致性（数据满足完整性约束，是事务的目标）、隔离性（并发事务互不干扰，通过 MVCC 和锁实现）、持久性（提交的修改不丢失，通过 Redo Log 实现）。InnoDB 完整支持 ACID，是 MySQL 8.0 的默认存储引擎。理解 ACID 的实现机制（Undo Log、Redo Log、MVCC、锁）是深入掌握 MySQL 并发和事务的基础。

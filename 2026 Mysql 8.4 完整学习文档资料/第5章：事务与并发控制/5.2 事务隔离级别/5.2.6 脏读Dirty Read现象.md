# 脏读 Dirty Read 现象

脏读（Dirty Read）是事务并发执行时可能发生的数据一致性问题之一。当一个事务读取了另一个事务尚未提交的修改数据，并基于这些"临时"数据做出了业务决策，而那个事务随后回滚，导致读到的数据从未在数据库中真正存在过，这种现象就是脏读。脏读只在 READ UNCOMMITTED 隔离级别下发生，READ COMMITTED 及以上级别的 MVCC 机制完全防止了脏读。

---

## 脏读的完整场景

```sql
-- 环境准备：
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance DECIMAL(10,2)
);
INSERT INTO accounts VALUES (1, 1000.00), (2, 500.00);

-- 会话1：设置 READ UNCOMMITTED（允许脏读）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- 时间轴：
-- T1：会话1开始事务，查询账户余额
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000.00

-- T2：会话2开始事务，修改账户余额（但不提交）
-- （会话2）
BEGIN;
UPDATE accounts SET balance = 500.00 WHERE id = 1;  -- 扣款 500，未提交
-- 注意：这条 UPDATE 尚未 COMMIT！

-- T3：会话1再次查询（READ UNCOMMITTED 级别）
SELECT balance FROM accounts WHERE id = 1;
-- 结果：500.00（读到了会话2未提交的修改！）
-- 会话1基于"账户余额为 500"做出了某种业务决策

-- T4：会话2回滚（出错了，撤销修改）
-- （会话2）
ROLLBACK;
-- 会话2的修改被撤销，id=1 的 balance 恢复为 1000.00

-- T5：会话1再次查询
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000.00（与 T3 时读到的不同！）
-- T3 时读到的 500.00 是一个"脏"数据，从未真正提交过

COMMIT;
```

## 脏读的业务危害

```
典型危害场景：

场景1：重复消费/超发
  库存系统：商品库存为 10
  事务A：扣减库存为 9（未提交）
  事务B（READ UNCOMMITTED）：读到库存=9，判断库存充足，继续下单
  事务A回滚：库存恢复为 10
  但事务B已基于"库存=9"的数据完成了下单处理，数据不一致

场景2：错误的账户余额判断
  转账事务：余额从 1000 扣减为 100（未提交）
  风控系统（READ UNCOMMITTED）：读到余额=100，触发低余额告警
  转账事务回滚：余额恢复为 1000
  风控系统误报，告警基于错误数据

场景3：统计计算错误
  报表查询：基于未提交的数据计算汇总，结果包含了会后回滚的数据
  报表统计结果错误
```

## InnoDB 防止脏读的机制

```sql
-- READ COMMITTED 及以上：MVCC 防止脏读

-- MVCC 的可见性原则：
-- 每个行记录有 DB_TRX_ID（最后修改它的事务 ID）
-- Read View 记录了创建时所有活跃（未提交）的事务 ID 列表
-- 如果行记录的 DB_TRX_ID 在 Read View 的活跃列表中：
--   → 该行版本是活跃事务（未提交）修改的，当前事务不可见
--   → 通过 DB_ROLL_PTR（回滚指针）找到该行的上一个已提交版本
--   → 读取上一个已提交版本的数据（而非未提交的最新版本）

-- 演示：READ COMMITTED 下不会脏读
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- Read View 创建，活跃事务列表包含"会话2修改id=1但未提交的事务ID"
-- → 看不到会话2未提交的修改
-- → 读取到 id=1 的上一个已提交版本：balance=1000.00

-- 即使会话2已修改 balance=500 但未提交，当前事务读到的是 1000.00（已提交版本）
```

## 脏读的识别方式

```sql
-- 确认当前隔离级别
SELECT @@transaction_isolation;

-- 如果是 READ UNCOMMITTED，需评估是否接受脏读风险
-- 检查当前是否有未提交的事务
SELECT trx_id, trx_state, trx_query
FROM information_schema.INNODB_TRX
WHERE trx_state = 'RUNNING';
-- 如果有正在运行的事务，READ UNCOMMITTED 可能读到这些事务的未提交修改
```

## 适用场景

- **了解脏读的场景**：在复现数据库并发问题时，有意设置 READ UNCOMMITTED 并构造未提交事务来验证脏读现象
- **特殊只读场景**：对数据精确性无严格要求的近似统计（如日活用户数的粗略估算），可接受脏读，换取最低锁开销

## 常见问题

**脏读是否只影响 SELECT？UPDATE 会读到脏数据吗？**

在 READ UNCOMMITTED 级别下，`UPDATE ... WHERE` 的条件判断也可能基于未提交的版本（通过当前读读取最新版本，包括未提交的），从而修改了"脏"状态下匹配的行。但由于 InnoDB 的行锁机制（写操作加 X 锁），如果被修改的行正被另一个事务的 X 锁持有（那个事务还未提交），当前事务的 UPDATE 需要等待锁。所以写写之间有锁保护，但读的数据可以是脏的。

---

## 注意事项

- 脏读的危害程度与业务逻辑密切相关：对于纯读的数据展示场景（如显示"当前进行中的订单数量"），脏读的影响只是数字可能稍不准确；对于业务决策（如库存判断、余额检查），脏读可能导致严重的数据错误和业务损失。
- 即使设置为 READ UNCOMMITTED，如果查询的表上没有任何活跃的未提交事务，脏读也不会发生（没有"脏"数据可读）。脏读是并发特定条件下的问题，不是必然发生的。

---

## 总结

脏读是 READ UNCOMMITTED 级别下，一个事务读取另一个事务未提交修改数据的现象。未提交的数据可能因事务回滚而不再存在，导致读到的数据从未"真实"存在过，基于脏数据做的业务决策可能严重错误。READ COMMITTED 及以上级别通过 MVCC（Read View 可见性判断）完全防止脏读——只有已提交事务的修改才对其他事务可见，通过 Undo Log 版本链获取行的已提交版本。

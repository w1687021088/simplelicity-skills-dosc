# SERIALIZABLE 串行化

SERIALIZABLE（串行化）是 SQL 标准定义的最高隔离级别。在此级别下，所有并发事务的执行效果与按某种顺序串行执行的结果完全相同——就像事务是一个接一个地依次执行，没有任何并发。InnoDB 通过对所有读操作加共享锁（S 锁）实现 SERIALIZABLE：读操作不再是无锁的 MVCC 快照读，而是加锁的当前读（类似 `LOCK IN SHARE MODE`），彻底防止所有并发问题（脏读、不可重复读、幻读），代价是并发性最低，事务间相互阻塞最严重。

---

## 核心特征

```
SERIALIZABLE 的行为特征：

读操作：
  所有 SELECT 语句隐式加共享锁（S 锁）
  等效于自动为每条 SELECT 加 LOCK IN SHARE MODE
  → 读操作会阻塞写操作（写需要 X 锁，与 S 锁不兼容）
  → 多个读事务可以并发（S 锁与 S 锁兼容）
  → 防止脏读、不可重复读、幻读所有并发问题

写操作：
  DML 加 X 锁，与其他事务的 S 锁和 X 锁均不兼容
  → 写操作会阻塞其他所有读写操作

结果：
  事务相互阻塞严重，并发性最低
  适合对数据一致性要求极高、并发量极低的场景
```

---

## SERIALIZABLE 的行为演示

```sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 会话1：
BEGIN;
SELECT * FROM accounts WHERE id = 1;
-- 加 S 锁（读锁）on id=1

-- 会话2：尝试修改同一行
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- 等待！id=1 上有 S 锁，X 锁无法获取
-- 会话2被阻塞，直到会话1提交/回滚

-- 会话1：
COMMIT;
-- S 锁释放，会话2的 UPDATE 才能继续执行
```

## SERIALIZABLE 防止幻读

```sql
-- SERIALIZABLE 完全防止幻读：

SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 会话1：
BEGIN;
SELECT * FROM students WHERE score > 60;
-- 对扫描范围内的间隙和记录加 S 锁
-- Gap Lock 防止其他事务在此范围内插入

-- 会话2：尝试插入一条 score > 60 的记录
INSERT INTO students VALUES (5, 'Eve', 75);
-- 等待！Gap Lock 阻止插入

-- 会话1再次查询：
SELECT * FROM students WHERE score > 60;
-- 结果行数不变（没有幻读），会话2的插入被阻塞

-- 会话1：
COMMIT;
-- 释放锁，会话2的插入继续
```

## 与其他隔离级别的并发性对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性 | 读阻塞写 |
|---------|:----:|:---------:|:----:|:-----:|:-------:|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 最高 | 否 |
| READ COMMITTED | 否 | 可能 | 可能 | 高 | 否 |
| REPEATABLE READ | 否 | 否 | 部分否 | 中 | 否 |
| SERIALIZABLE | 否 | 否 | 否 | 最低 | 是 |

## 适用场景

- **强一致性金融核心系统**：证券交易、资金清算等对数据一致性要求严格、不允许任何并发异常，且并发量相对可控的场景
- **对数据绝对一致性有要求的短事务**：单次事务执行时间极短（毫秒级），SERIALIZABLE 对并发性的影响有限，但能提供最强一致性保证

## 常见问题

**SERIALIZABLE 级别下，SELECT 也会阻塞写入，这不会导致系统无法工作吗？**

在高并发系统中，SERIALIZABLE 会导致严重的锁等待和吞吐量下降。如果事务持有 S 锁的时间较长（哪怕是普通查询），所有对相同行的写入都会等待。这就是为什么生产环境很少使用 SERIALIZABLE——对于大多数业务场景，REPEATABLE READ（InnoDB 默认）已经提供了足够强的一致性保证，且通过 MVCC 使读写不互相阻塞，并发性远高于 SERIALIZABLE。

---

## 注意事项

- SERIALIZABLE 级别下，autocommit = OFF 的单条 SELECT 也会加 S 锁。如果应用代码在 SERIALIZABLE 环境中有大量只读 SELECT（如监控查询、报表查询），这些 SELECT 都会占用 S 锁并阻塞写入，可能导致写入事务长时间等待。
- 如果业务确实需要 SERIALIZABLE 级别的一致性但又不想阻塞读写，可以考虑应用层加乐观锁（版本号/时间戳控制），或使用 `SELECT ... FOR UPDATE`（显式加写锁）替代自动的 S 锁策略，在需要的地方精确控制锁。

---

## 总结

SERIALIZABLE 是最高隔离级别，所有 SELECT 隐式加 S 锁（相当于 `LOCK IN SHARE MODE`），彻底防止脏读、不可重复读和幻读，事务执行效果等同于串行顺序执行。代价是读阻塞写（S 锁与 X 锁不兼容），并发性最低，死锁概率最高。适合对数据一致性要求极高、并发量可控的场景（如金融核心系统）。多数生产系统选择 REPEATABLE READ（InnoDB 默认），通过 MVCC 实现读写不互阻的较高并发性，同时提供足够强的隔离保证。

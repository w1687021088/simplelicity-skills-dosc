# 幻读 Phantom Read 现象

幻读（Phantom Read）是指在同一事务内，执行两次相同的范围查询，但第二次的结果集中出现了第一次没有的行（或少了某些行），就像出现了"幻影"一样。幻读与不可重复读的区别在于：不可重复读是同一行的值发生了变化（UPDATE），幻读是结果集的行数发生了变化（INSERT 新行或 DELETE 现有行）。幻读在 SQL 标准中直到 SERIALIZABLE 级别才被完全防止，但 InnoDB 在 REPEATABLE READ 级别通过 MVCC 和 Next-Key Lock 的组合在大多数场景下防止了幻读。

---

## 幻读的完整场景

```sql
-- 环境准备：
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    amount DECIMAL(10,2),
    INDEX(user_id)
);
INSERT INTO orders VALUES (1, 100, 500.00), (2, 100, 300.00);

-- 在 READ COMMITTED 级别演示幻读：
-- 会话1：
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;

-- T1：第一次范围查询
SELECT * FROM orders WHERE user_id = 100;
-- 结果：2行（id=1, id=2）

-- T2：会话2插入一条记录并提交
-- （会话2）
BEGIN;
INSERT INTO orders VALUES (3, 100, 800.00);
COMMIT;

-- T3：会话1再次执行相同的范围查询
SELECT * FROM orders WHERE user_id = 100;
-- 结果：3行（id=1, id=2, id=3）
-- 多了一行！这就是"幻读"

COMMIT;
```

## InnoDB RR 级别防止幻读的两种机制

```sql
-- 机制1：MVCC 固定快照（防止快照读的幻读）
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;

SELECT * FROM orders WHERE user_id = 100;
-- T1：返回 2 行，Read View 创建（快照时 user_id=100 只有 2 行）

-- 另一会话插入并提交：INSERT INTO orders VALUES (3, 100, 800.00);

SELECT * FROM orders WHERE user_id = 100;
-- T3：仍然返回 2 行（MVCC 快照固定，新插入的行 trx_id > 快照的 low_limit_id，不可见）
-- 快照读不会出现幻读

COMMIT;

-- 机制2：Next-Key Lock（防止当前读的幻读）
BEGIN;
SELECT * FROM orders WHERE user_id = 100 FOR UPDATE;  -- 当前读
-- InnoDB 加锁：
-- 1. 对 user_id=100 的所有现有行加 X 锁（行锁）
-- 2. 对 user_id=100 的间隙（如 user_id IN (99,100] 和 (100,101] 等范围）加 Gap Lock

-- 其他会话尝试插入 user_id=100：
-- INSERT INTO orders VALUES (3, 100, 800.00);  -- 等待！Gap Lock 阻止插入

SELECT * FROM orders WHERE user_id = 100 FOR UPDATE;
-- 仍然是 2 行（幻读被 Next-Key Lock 阻止）

COMMIT;
```

## RR 级别的幻读残余场景

```sql
-- 在同一事务中混用快照读和当前读，可能出现类似幻读的情况：

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;

-- 快照读：
SELECT * FROM orders WHERE user_id = 100;  -- 返回 2 行（创建 Read View）

-- 另一会话插入并提交：INSERT INTO orders VALUES (3, 100, 800.00);

-- 当前读（读取最新版本）：
SELECT * FROM orders WHERE user_id = 100 FOR UPDATE;
-- 返回 3 行！（当前读看到了新插入的行）
-- 与之前的快照读（2行）结果不同 → 类似幻读

-- 这不是 InnoDB 的 Bug，而是快照读和当前读使用不同版本的设计行为
-- 避免方式：在需要一致性的范围查询中统一使用当前读（FOR UPDATE）

COMMIT;
```

## 幻读 vs 不可重复读

| 特征 | 幻读 | 不可重复读 |
|------|------|---------|
| 变化类型 | 行数变化（INSERT/DELETE）| 列值变化（UPDATE）|
| 针对操作 | 范围查询 | 单行查询 |
| 发生隔离级别 | RC 及以下（SQL标准，InnoDB RR 大部分防止）| RC 及以下 |
| 防止机制 | Next-Key Lock + MVCC | MVCC 固定 Read View |
| SQL标准防止级别 | SERIALIZABLE | REPEATABLE READ |
| InnoDB 防止级别 | REPEATABLE READ（部分）| REPEATABLE READ |

---

## 适用场景

- **范围查询的一致性需求**：在执行"统计某段时间内订单数量"的报表时，如果需要同一事务内多次统计结果一致，应使用 RR 级别的快照读（普通 SELECT）或 `WITH CONSISTENT SNAPSHOT`
- **防止重复插入**：先查询某条件下是否有记录，再决定是否插入，使用 `SELECT ... FOR UPDATE` 配合间隙锁防止并发情况下的重复插入（如防重令牌验证场景）

## 常见问题

**InnoDB RR 级别真的完全消除了幻读吗？**

对于快照读（普通 SELECT），MVCC 固定 Read View 完全消除了幻读（整个事务看到同一快照，新插入的行不可见）。对于当前读（FOR UPDATE/DML），Next-Key Lock 防止了其他事务在被锁范围内插入新行，消除了当前读的幻读。但在同一事务中混合使用快照读和当前读，当前读会看到比快照读更新的数据，仍可能出现类幻读现象。严格意义上，InnoDB RR 没有完全消除所有场景下的幻读。

---

## 注意事项

- 幻读问题在 SQL 标准中只能通过 SERIALIZABLE 级别完全解决（所有 SELECT 加 S 锁，读阻塞写）。InnoDB 在 RR 级别通过 Next-Key Lock 提供了比 SQL 标准更强的幻读防护，但代价是比 RC 级别更多的间隙锁，可能增加死锁概率和并发阻塞。
- 在 RR 级别下，如果业务要求"同一事务内多次范围查询结果一致"，应统一使用快照读（普通 SELECT），不要在事务中间混用 `FOR UPDATE`，避免触发幻读残余场景。

---

## 总结

幻读是同一事务内范围查询行数发生变化的现象（期间其他事务插入或删除了行）。InnoDB RR 级别通过 MVCC 固定快照（防快照读幻读）和 Next-Key Lock（防当前读幻读）在大多数场景下防止幻读，超出 SQL 标准的 RR 级别定义（SQL 标准 RR 允许幻读）。混用快照读和当前读时，当前读仍可能看到新行（类幻读）。SERIALIZABLE 级别通过对所有 SELECT 加 S 锁完全防止幻读，但并发性最低。

# 不可重复读 Non-repeatable Read 现象

不可重复读（Non-repeatable Read）是指在同一个事务内，对同一行数据执行两次读取，但两次读取的结果不同——期间有其他事务修改并提交了该行数据。与脏读（读到未提交数据）不同，不可重复读读到的都是已提交的数据，但同一事务内的一致性遭到了破坏。READ COMMITTED 级别允许不可重复读，REPEATABLE READ 及以上级别通过固定 Read View 防止不可重复读。

---

## 不可重复读的完整场景

```sql
-- 环境准备：
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance DECIMAL(10,2)
);
INSERT INTO accounts VALUES (1, 1000.00);

-- 在 READ COMMITTED 级别演示不可重复读：
-- 会话1：设置 READ COMMITTED
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;

-- T1：会话1第一次查询余额
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000.00

-- T2：会话2修改余额并提交
-- （会话2）
BEGIN;
UPDATE accounts SET balance = 800.00 WHERE id = 1;
COMMIT;  -- 提交！修改已持久化

-- T3：会话1再次查询余额（同一事务，同一行）
SELECT balance FROM accounts WHERE id = 1;
-- 结果：800.00（不同于第一次的 1000.00！）
-- 这就是"不可重复读"：同一事务内，同一行两次读结果不同

COMMIT;

-- 业务问题：
-- 如果会话1在T1读到1000.00后，判断余额充足，计划进行一个需要500.00的操作
-- 在实际扣减前再次确认余额（T3），读到800.00
-- 两次余额不一致，可能导致错误的决策或重复检查
```

## 不可重复读 vs 脏读

| 特征 | 不可重复读 | 脏读 |
|------|---------|------|
| 读到的数据状态 | 已提交的修改 | 未提交的修改 |
| 发生时机 | 其他事务已提交后再次读 | 其他事务修改但未提交时读 |
| 发生隔离级别 | READ COMMITTED 及以下 | READ UNCOMMITTED |
| 修复方式 | REPEATABLE READ 固定快照 | READ COMMITTED 的 MVCC |
| 严重程度 | 中（读到的数据至少是合法的）| 高（读到的数据可能被回滚）|

## REPEATABLE READ 防止不可重复读

```sql
-- RR 级别：整个事务内 Read View 固定，防止不可重复读

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- 默认
BEGIN;

-- T1：第一次查询，创建 Read View，记录此时已提交的状态
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000.00（Read View 创建时的快照）

-- T2：另一会话修改并提交：balance 改为 800.00

-- T3：当前事务再次查询（同一 Read View）
SELECT balance FROM accounts WHERE id = 1;
-- 结果：仍然是 1000.00（Read View 固定，看不到 T2 的提交）
-- Read View 中活跃事务列表不包含"已提交"的会话2事务ID
-- 但会话2在本事务 BEGIN 后才提交，其 trx_id > Read View 创建时的 up_limit_id
-- 实际上是通过版本链判断可见性，结果是不可见（读到旧版本）

COMMIT;
-- 事务结束，下次查询才能看到 800.00
```

## 不可重复读的业务影响

```
典型场景：

场景1：多次校验逻辑中断
  步骤1：查询账户余额 = 1000（充足）
  其他事务：扣款 600，提交，余额变为 400
  步骤2：基于"账户余额充足"的假设，执行下一步操作
  步骤3：再次校验余额 = 400（不充足！）
  → 两次校验结果矛盾，业务逻辑出错

场景2：报表计算不一致
  开始计算报表（RC 级别）：读到某商品库存 = 100
  另一事务出货：库存改为 80，提交
  报表继续计算：同一商品库存 = 80
  → 同一报表中同一商品数据不一致，报表结果无意义

场景3：对账系统
  读取账户A余额 = 1000
  另一事务转账：A扣100，提交
  读取账户A余额 = 900（同一事务内两次读取不同！）
  → 对账逻辑无法在 RC 级别下保证一致性
```

## 适用场景

- **了解并发问题时**：在 RC 与 RR 隔离级别的对比测试中，演示不可重复读现象，帮助理解 MVCC Read View 固定的意义
- **业务评估**：在系统设计时评估当前业务是否能接受不可重复读——如果业务逻辑在一个事务内需要多次读取同一行并保持一致，应选择 RR 级别

## 常见问题

**不可重复读和幻读有什么区别？**

不可重复读针对的是"同一行数据被修改"（UPDATE）——两次读同一行的列值不同。幻读针对的是"范围查询的行数发生变化"（INSERT/DELETE）——两次范围查询返回的行数不同（多了新插入的行或少了被删除的行）。两者是不同类型的并发问题：不可重复读关注单行数据的一致性，幻读关注结果集的范围一致性。防止机制也不同：不可重复读通过 MVCC 固定 Read View 解决，幻读通过 MVCC + Next-Key Lock 解决。

---

## 注意事项

- 不可重复读虽然读到的都是已提交的合法数据，但在一个事务的多个步骤之间，同一行数据的值发生变化可能破坏业务逻辑的一致性假设。选择隔离级别时，需要评估业务是否依赖"同一事务内读取结果的稳定性"。
- 在 RC 级别下，可以通过显式加锁（`SELECT ... FOR UPDATE` 或 `SELECT ... LOCK IN SHARE MODE`）来避免不可重复读——加锁后，其他事务无法修改该行直到当前事务结束，从而保证了读取的稳定性（但代价是降低并发性）。

---

## 总结

不可重复读是同一事务内对同一行两次读取结果不同的现象（期间其他事务修改并提交了该行）。发生于 READ COMMITTED 级别（每次 SELECT 创建新 Read View，看到最新已提交版本）。REPEATABLE READ 通过固定 Read View（整个事务内使用同一快照）防止不可重复读。不可重复读影响事务内多次读取同行数据的一致性，适合对数据读取一致性有要求的场景（如账户余额、库存校验）应升级到 RR 级别。

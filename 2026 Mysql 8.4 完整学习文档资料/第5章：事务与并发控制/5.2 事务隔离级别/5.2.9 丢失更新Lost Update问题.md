# 丢失更新 Lost Update 问题

丢失更新（Lost Update）是并发事务场景中的一种数据一致性问题：两个事务并发读取同一行数据，然后各自基于读到的值进行修改并提交，其中一个事务的更新会被另一个事务的更新覆盖，导致其中一次更新"消失"了。与脏读、不可重复读、幻读不同，丢失更新不是 SQL 标准定义的问题，任何隔离级别（包括 SERIALIZABLE）的普通 MVCC 读都无法从机制层面完全防止——它需要通过应用层或数据库层的锁机制来解决。

---

## 丢失更新的发生场景

```sql
-- 场景：两个用户同时为同一商品增加库存（并发更新库存）
-- 商品 id=1 当前库存 = 10

-- 事务A（会话1）：
BEGIN;
SELECT stock FROM products WHERE id = 1;
-- 读到 stock = 10

-- 事务B（会话2）：
BEGIN;
SELECT stock FROM products WHERE id = 1;
-- 也读到 stock = 10

-- 事务A：基于读到的值 +5（10+5=15），更新库存
UPDATE products SET stock = 15 WHERE id = 1;
COMMIT;  -- 事务A提交，stock = 15

-- 事务B：基于读到的值 +3（10+3=13），更新库存
UPDATE products SET stock = 13 WHERE id = 1;
COMMIT;  -- 事务B提交，stock = 13

-- 最终结果：stock = 13
-- 期望结果：stock = 10 + 5 + 3 = 18
-- 事务A的更新（+5）被事务B覆盖，"丢失"了！
```

---

## 为什么 SERIALIZABLE 也不能防止丢失更新（MVCC 场景）

```sql
-- 在 SERIALIZABLE 隔离级别下，SELECT 加 S 锁
-- 两个事务都加 S 锁读同一行是允许的（S 锁互相兼容）
-- 然后两个事务都执行 UPDATE（需要 X 锁）

-- 实际在 SERIALIZABLE 下的场景：
-- 事务A：SELECT（加 S 锁）→ 读到 stock=10
-- 事务B：SELECT（加 S 锁，与 A 的 S 锁兼容）→ 也读到 stock=10
-- 事务A：UPDATE（需要 X 锁，S 锁导致 B 的 S 锁阻塞）
--   → 事务A等待事务B释放 S 锁
--   → 事务B等待事务A释放 S 锁
--   → 死锁！InnoDB 检测到死锁，回滚一个事务
-- 结论：SERIALIZABLE 下会死锁，而不是优雅地串行化执行

-- 防止丢失更新需要不同的策略（见下文）
```

---

## 解决方案1：悲观锁（SELECT ... FOR UPDATE）

```sql
-- 使用 FOR UPDATE 将读操作加 X 锁（排他锁）
-- 保证读和写之间没有其他事务插入

-- 事务A：
BEGIN;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;  -- 加 X 锁
-- stock = 10，X 锁持有

-- 事务B（此时）：
BEGIN;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
-- 等待！id=1 上有 X 锁，事务B被阻塞

-- 事务A：基于正确的 stock=10 更新
UPDATE products SET stock = stock + 5 WHERE id = 1;  -- 更安全：直接用表达式更新
COMMIT;  -- 释放 X 锁，stock = 15

-- 事务B（继续）：
-- X 锁释放，获得 FOR UPDATE 的 X 锁
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
-- 读到最新值 stock = 15
UPDATE products SET stock = stock + 3 WHERE id = 1;
COMMIT;  -- stock = 18（正确！）
```

---

## 解决方案2：原子更新（推荐）

```sql
-- 最佳方案：直接在 SQL 中使用表达式更新（原子操作，不需要先读再写）
-- UPDATE 语句在 InnoDB 中是当前读（加 X 锁）+ 立即更新

-- 事务A：
BEGIN;
UPDATE products SET stock = stock + 5 WHERE id = 1;
-- 这条 SQL 在执行时：
-- 1. 加 X 锁（当前读最新值）
-- 2. 计算 stock + 5（基于最新值）
-- 3. 写入结果
-- 无需显式 SELECT，避免了"读-思考-写"的时间窗口
COMMIT;  -- stock = 15

-- 事务B（并发）：
BEGIN;
UPDATE products SET stock = stock + 3 WHERE id = 1;
-- 如果 A 先执行：等待 X 锁，获得后读到 stock=15，写入 15+3=18
-- 最终 stock = 18（正确！）
COMMIT;
```

## 解决方案3：乐观锁（版本号控制）

```sql
-- 在表中增加 version 列，每次更新 version + 1
ALTER TABLE products ADD COLUMN version INT DEFAULT 0;

-- 读取时带上 version：
SELECT stock, version FROM products WHERE id = 1;
-- stock=10, version=5

-- 更新时检查 version：
UPDATE products SET stock = 15, version = version + 1
WHERE id = 1 AND version = 5;  -- 版本号必须匹配
-- 如果返回 affected rows = 0：说明有其他事务在此期间修改了（版本号变了）
-- 应用层重试（重新读取并更新）

-- 如果 affected rows = 1：更新成功

-- 特点：
-- 不阻塞读操作（乐观地认为冲突少）
-- 冲突时应用层重试
-- 适合读多写少、冲突概率低的场景
```

---

## 三种解决方案对比

| 方案 | 机制 | 并发性 | 适用场景 |
|------|------|--------|---------|
| 原子更新（表达式 UPDATE）| 数据库原子操作 | 最高 | 简单增减运算（stock + N）|
| 悲观锁（FOR UPDATE）| 数据库行锁 | 低（读阻塞读）| 读后需要复杂计算再写入 |
| 乐观锁（版本号）| 应用层 CAS 重试 | 高（不阻塞）| 读多写少、冲突概率低 |

---

## 适用场景

- **电商库存扣减**：优先使用原子更新（`UPDATE stock = stock - 1 WHERE id = ? AND stock > 0`），既防丢失更新，又防止库存超卖（WHERE 条件确保库存充足才扣减）
- **票务系统**：`SELECT ... FOR UPDATE` 悲观锁锁住票位，防止同一张票被多人购买

## 常见问题

**原子更新（`UPDATE SET col = col + 1`）能完全替代 FOR UPDATE 吗？**

对于简单的加减运算（如库存增减、计数器），原子更新是最优方案，无需显式加锁。但如果更新逻辑较复杂，需要先读取当前值，在应用层进行计算（如基于当前值计算折扣价格，或基于多个字段进行复杂条件判断），再将计算结果写回，则需要用 `FOR UPDATE` 锁住行，在读和写之间防止其他事务介入。

---

## 注意事项

- "丢失更新"不在 SQL 标准的并发问题定义（脏读、不可重复读、幻读）中，但它在实际系统中是非常常见的业务层并发 Bug，需要通过合适的锁策略或原子操作来解决，单靠提高隔离级别无法解决。
- 在分布式系统（多数据库节点）中，原子更新和 FOR UPDATE 的保护范围只在单个数据库节点内，跨节点的丢失更新需要分布式锁（如 Redis 分布式锁）或分布式事务协议来解决。

## 总结

丢失更新是两个事务并发读取同一行、各自基于读到的旧值修改，其中一次更新覆盖另一次，导致某次修改"消失"。MVCC 和任何隔离级别的普通 SELECT 都无法防止丢失更新（S 锁相互兼容，两个事务都能读到同一行）。解决方案：原子更新（`SET col = col + N`，最优）、悲观锁（`SELECT ... FOR UPDATE`）、乐观锁（版本号控制）。原子更新适合简单增减，FOR UPDATE 适合读后复杂计算再写入，乐观锁适合冲突概率低的场景。

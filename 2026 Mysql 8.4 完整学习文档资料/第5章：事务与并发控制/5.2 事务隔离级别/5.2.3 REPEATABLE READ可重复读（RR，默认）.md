# REPEATABLE READ 可重复读（RR，默认）

REPEATABLE READ（可重复读，简称 RR）是 MySQL InnoDB 的默认事务隔离级别，也是 SQL 标准中第三强的隔离级别。RR 的核心特征是：同一事务内，多次读取同一行数据的结果保持一致（可重复读），即使期间有其他事务修改并提交了该行。InnoDB 在 RR 级别的实现超出了 SQL 标准的要求——通过 MVCC 固定快照和 Next-Key Lock（临键锁）的组合，在大多数场景下同时防止了脏读、不可重复读和幻读。

---

## 核心特征

```
REPEATABLE READ 的行为特征：

快照读（普通 SELECT）：
  事务第一次执行 SELECT 时创建 Read View，整个事务生命周期内不变
  → 消除脏读（只读已提交版本）
  → 消除不可重复读（同一行多次读取结果相同）
  → 消除幻读（范围查询看到同一快照，新插入的行不可见）

当前读（FOR UPDATE / DML）：
  使用 Next-Key Lock（临键锁 = 行锁 + 间隙锁）
  → 防止其他事务在锁定范围内插入新行（防止幻读）
  → 锁定已有行 + 行之间的间隙

可能发生的并发问题：
  脏读：不会
  不可重复读：不会（快照读）
  幻读：大多数场景不会（MVCC + Next-Key Lock）
  混合读场景的特殊幻读：理论上存在（快照读+当前读混用）
```

## Read View 固定与可重复读

```sql
-- RR 级别：整个事务使用同一个 Read View

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- 已是默认

BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- Read View 在此处创建：balance=1000

-- 其他会话：
-- BEGIN;
-- UPDATE accounts SET balance = 900 WHERE id = 1;
-- COMMIT;

SELECT balance FROM accounts WHERE id = 1;
-- 使用同一个 Read View：仍然看到 balance=1000
-- 即使其他会话已经提交了修改，当前事务看不到（可重复读）

-- 第三次读取：
SELECT balance FROM accounts WHERE id = 1;
-- 仍然是 balance=1000（不管有多少其他事务提交）

COMMIT;
-- 事务结束，Read View 释放
-- 下一个事务才能看到最新的 balance=900
```

## Next-Key Lock 防止幻读

```sql
-- RR 级别的当前读使用 Next-Key Lock（行锁 + 间隙锁）防止幻读

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;

-- 当前读：查询 score > 60 的所有记录并加锁
SELECT * FROM students WHERE score > 60 FOR UPDATE;
-- 假设返回 score=70, 80, 90 三条记录

-- InnoDB 加的锁：
-- 1. 对 score=70, 80, 90 的记录加 X 锁（行锁）
-- 2. 对 score 值之间的间隙和 90 之后的间隙加 Gap Lock（间隙锁）
-- → 其他事务无法在 score > 60 的范围内插入新行（被间隙锁阻塞）

-- 其他会话尝试插入：
-- INSERT INTO students VALUES (4, 'Dave', 75);  -- 等待！被 Gap Lock 阻塞

-- 再次查询：不会出现新行（幻读被阻止）
SELECT * FROM students WHERE score > 60 FOR UPDATE;
-- 仍然只有 score=70, 80, 90 三条记录

COMMIT;  -- 释放所有锁，其他会话的插入才可以继续
```

## RR 级别的特殊场景：混合读的幻读

```sql
-- 在同一事务中混用快照读和当前读，可能出现"类幻读"
BEGIN;
SELECT * FROM orders WHERE amount > 100;        -- 快照读：返回 5 行（建立 Read View）

-- 其他会话插入并提交：amount=200 的新行

SELECT * FROM orders WHERE amount > 100 FOR UPDATE;  -- 当前读：返回 6 行！
-- 当前读读取最新版本，看到了新插入的行
-- 两次查询行数不同（5行 vs 6行），这是 RR 级别混合使用时的特殊现象

-- 防止方式：统一使用当前读（配合 Next-Key Lock），或避免混用快照读和当前读
COMMIT;
```

## 与其他隔离级别的对比

| 特性 | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|------|:-------------:|:---------------:|:------------:|
| 脏读防护 | 有 | 有 | 有 |
| 不可重复读防护 | 无 | 有 | 有 |
| 幻读防护 | 无 | 大部分有 | 完全有 |
| 间隙锁 | 通常无 | 有 | 有 |
| 并发性 | 高 | 中 | 低 |
| 死锁风险 | 较低 | 中 | 高 |

## 适用场景

- **金融/银行系统**：账户余额查询需要可重复读保证，同一事务内多次读取余额结果一致，防止因读到中间状态做出错误决策
- **报表生成**：长时间运行的报表查询，需要看到一致的数据快照，不受报表生成期间其他事务修改的影响（配合 `WITH CONSISTENT SNAPSHOT`）

## 常见问题

**MySQL 默认的 RR 级别能防止所有幻读吗？**

在普通快照读（普通 SELECT）下，MVCC 固定 Read View 使得事务内的范围查询始终看到同一快照，因此快照读不会出现幻读。在当前读（FOR UPDATE/DML）下，Next-Key Lock 防止了其他事务在被锁范围内插入新行，因此当前读也不会出现幻读。但在同一事务中混用快照读和当前读时，当前读会看到比快照读更新的数据，可能出现类似幻读的现象。这是 RR 级别理论上存在但需要特殊场景才会触发的问题。

---

## 注意事项

- RR 级别的 Next-Key Lock 会锁定间隙（Gap Lock），当 DELETE/UPDATE 涉及不存在的记录时，InnoDB 仍会对"该记录应在的间隙"加 Gap Lock，阻止其他事务在此间隙插入。这可能导致比 RC 级别更多的锁等待和死锁。高并发写入场景建议评估 RC 与 RR 的锁冲突差异。
- 长事务在 RR 级别下会持有很旧的 Read View，阻止 Purge 线程清理旧 Undo 版本，导致 Undo 表空间持续增长。应避免在 RR 级别下运行长事务。

---

## 总结

REPEATABLE READ 是 MySQL InnoDB 默认隔离级别，通过 MVCC 固定 Read View（事务第一次 SELECT 时创建，整个事务内不变）实现可重复读，防止脏读和不可重复读。通过 Next-Key Lock（行锁 + 间隙锁）防止当前读的幻读，通过固定 Read View 防止快照读的幻读。RR 的隔离效果超出 SQL 标准要求（SQL 标准 RR 允许幻读，InnoDB RR 在大多数场景防止）。代价是间隙锁增加了死锁概率，高并发场景可考虑降级为 RC。

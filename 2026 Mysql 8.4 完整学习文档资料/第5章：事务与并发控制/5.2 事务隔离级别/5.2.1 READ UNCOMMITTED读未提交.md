# READ UNCOMMITTED 读未提交

READ UNCOMMITTED（读未提交）是 SQL 标准定义的四个事务隔离级别中最弱的一级。在此级别下，一个事务可以读取其他事务尚未提交的修改数据，这种现象称为"脏读"（Dirty Read）。由于不对读操作加任何限制，READ UNCOMMITTED 提供了最高的并发性，但数据一致性保证最弱，几乎不用于生产环境的业务事务。

---

## 核心特征

```
READ UNCOMMITTED 的行为特征：

读操作：
  不使用 MVCC（不基于 Read View 进行可见性判断）
  直接读取数据页中最新版本（包括未提交的修改）
  因此可以读到其他事务尚未提交的修改（脏读）

写操作：
  与其他隔离级别相同，写操作需要加 X 锁
  写写之间仍然有锁保护，不会导致写覆盖

可能出现的并发问题：
  脏读（Dirty Read）：可能发生
  不可重复读（Non-repeatable Read）：可能发生
  幻读（Phantom Read）：可能发生
```

---

## 脏读演示

```sql
-- 会话1：设置 READ UNCOMMITTED 隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000（当前值）

-- 会话2（同时进行）：
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
-- 注意：会话2尚未 COMMIT！

-- 会话1（继续读取）：
SELECT balance FROM accounts WHERE id = 1;
-- 结果：500（读到了会话2未提交的修改！）
-- 这就是"脏读"

-- 会话2（回滚）：
ROLLBACK;
-- 会话2的修改被撤销，id=1 的 balance 恢复为 1000

-- 会话1再次读取：
SELECT balance FROM accounts WHERE id = 1;
-- 结果：1000（脏读的数据已不一致！）
-- 之前读到的 500 是一个错误的"脏"数据，可能导致错误的业务决策
```

## 与其他隔离级别的对比

| 并发问题 | READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---------|:---------------:|:--------------:|:---------------:|:------------:|
| 脏读 | 可能 | 不会 | 不会 | 不会 |
| 不可重复读 | 可能 | 可能 | 不会 | 不会 |
| 幻读 | 可能 | 可能 | 部分防止* | 不会 |

*InnoDB RR 通过 MVCC + Next-Key Lock 防止大多数幻读场景

## 设置与查看

```sql
-- 设置当前会话的隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;  -- 仅影响下一个事务

-- 设置全局隔离级别（影响新建连接）
SET GLOBAL TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- 查看当前隔离级别
SELECT @@transaction_isolation;   -- MySQL 8.0
SELECT @@tx_isolation;            -- 兼容旧版本
SHOW VARIABLES LIKE 'transaction_isolation';
```

## 适用场景

- **实时监控读取**：对数据准确性要求不高的监控大屏（如显示"实时在线用户数"），允许少量脏读，换取最低锁开销
- **数据仓库 ETL 的某些阶段**：在能确定数据只增不改的场景（如只 INSERT 的 append-only 日志表），READ UNCOMMITTED 的脏读风险实际上为零，但性能最高

---

## 常见问题

**READ UNCOMMITTED 下写操作还需要加锁吗？**

是的。READ UNCOMMITTED 只是放宽了读操作的限制（读不加锁，直接读最新版本），写操作（INSERT/UPDATE/DELETE）仍然按正常规则加 X 锁，防止两个事务同时修改同一行（写写冲突）。READ UNCOMMITTED 消除的只是"读锁"，不是"写锁"。

---

## 注意事项

- READ UNCOMMITTED 在生产业务系统中几乎不使用，因为脏读会导致基于错误中间状态做出错误业务决策（如读到未提交的转账金额并执行了下一步操作，而该转账事务随后回滚）。
- 即使在允许脏读的场景，通常也建议使用 READ COMMITTED（消除脏读），因为 READ COMMITTED 的性能与 READ UNCOMMITTED 差距不大（MVCC 读视图的创建开销极小），但安全性显著更高。

---

## 总结

READ UNCOMMITTED 是隔离级别最弱的级别，允许读取其他事务未提交的修改（脏读）。读操作不使用 MVCC，直接读数据页最新版本。写操作仍需 X 锁（防止写写冲突）。可能发生脏读、不可重复读和幻读三种并发问题。由于脏读可能导致严重的数据不一致，生产环境几乎不使用。即便对一致性要求低，也建议选择 READ COMMITTED（MVCC 防脏读，性能相当）。

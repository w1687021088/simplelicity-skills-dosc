# RC 级别每次查询新建 Read View

READ COMMITTED（RC）隔离级别与 REPEATABLE READ（RR）级别的本质区别，就在于 Read View 的创建时机不同。RC 级别每次执行快照读（普通 SELECT）时都创建一个全新的 Read View，因此每次查询都能看到截至查询时刻所有已提交事务的最新修改。这种行为正是 RC 级别的名字含义："读已提交"——每次都读到当时已提交的最新数据。

---

## RC 级别 Read View 的创建行为

```sql
-- RC 级别：每次 SELECT 创建新 Read View

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;

-- 第一次 SELECT：创建 Read View-1
-- Read View-1 反映 T1 时刻的活跃事务快照
SELECT balance FROM accounts WHERE id = 1;
-- Read View-1: m_ids=[trx_X（正在修改id=1）], ...
-- 结果：1000（上一个已提交版本）

-- 时刻 T2：其他事务 trx_X 提交，balance 变为 900

-- 第二次 SELECT：创建 Read View-2（新的！）
-- Read View-2 反映 T2 时刻之后的活跃事务快照
SELECT balance FROM accounts WHERE id = 1;
-- Read View-2: m_ids=[] （trx_X 已提交，不在活跃列表中）
-- 结果：900（trx_X 已提交，在新 Read View 下可见）

-- 同一事务内，两次查询结果不同（不可重复读）
-- 这是 RC 级别允许的行为
COMMIT;
```

## 与 RR 级别的行为对比

```sql
-- 相同场景，RR 级别的行为：
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;

-- 第一次 SELECT：创建 Read View（整个事务只创建这一次）
SELECT balance FROM accounts WHERE id = 1;
-- Read View: m_ids=[trx_X], ...
-- 结果：1000

-- 时刻 T2：trx_X 提交，balance 变为 900

-- 第二次 SELECT：复用同一个 Read View
SELECT balance FROM accounts WHERE id = 1;
-- Read View 不变：trx_X 的 ID 仍在判断范围内
-- 实际上：trx_X 的 trx_id 在 Read View 创建时在 m_ids 中，不可见
-- 结果：仍然是 1000（可重复读，看不到 trx_X 的提交）

COMMIT;
```

## RC 级别 Read View 创建的时机细节

```sql
-- 在 RC 级别下，以下情况会创建新 Read View：

-- 1. 每条普通 SELECT 语句执行时
SELECT * FROM t;  -- 创建新 Read View

-- 2. 子查询中的 SELECT 也会创建 Read View
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE active = 1);
-- 外层 SELECT 和内层 SELECT 都会各自判断可见性
-- 但由于通常在同一时刻执行，通常使用相同的 Read View 状态

-- 3. 存储过程中的每条 SELECT
DELIMITER //
CREATE PROCEDURE check_balance()
BEGIN
    SELECT balance FROM accounts WHERE id = 1;  -- Read View-1
    -- 如果有其他事务在这两条语句之间提交...
    SELECT balance FROM accounts WHERE id = 1;  -- Read View-2（新的！）
END //
DELIMITER ;

-- 注意：RC 级别下，FOR UPDATE 不创建 MVCC Read View
-- FOR UPDATE 是当前读，直接读最新版本（加锁）
SELECT * FROM t WHERE id = 1 FOR UPDATE;  -- 不创建 Read View，直接加锁读最新版
```

## RC 级别与 Binlog 格式的关系

```sql
-- 在 RC 级别 + STATEMENT 格式 Binlog 的环境中存在数据不一致风险

-- 场景：
-- 主库：RC 级别执行 DELETE FROM orders WHERE status = 'pending'
-- 在该 DELETE 执行期间，另一个事务插入并提交了一条 status='pending' 的行
-- RC 级别下，DELETE 可以看到这条新行（每条语句都用最新快照）
-- 主库删除了这条新行，但记录在 Binlog 中的 SQL 语句在从库执行时，
-- 可能因为执行顺序不同而删除不同的行（从库没有那条新行）

-- 因此，RC 级别必须使用 ROW 格式或 MIXED 格式 Binlog
SHOW VARIABLES LIKE 'binlog_format';  -- 应该是 ROW 或 MIXED
-- 不能使用 STATEMENT 格式（MySQL 8.0 默认已是 ROW 格式）

-- 设置（MySQL 8.0.35+ 已默认 ROW 格式，RC 下更安全）
SET GLOBAL binlog_format = 'ROW';
```

## RC 级别的并发优势

```sql
-- RC 级别不加间隙锁（Gap Lock），并发插入性能更好

-- 场景：多个事务同时插入不同的数据

-- RR 级别（有间隙锁）：
BEGIN;
DELETE FROM orders WHERE status = 'pending';  -- 删除不存在的记录
-- 加间隙锁，阻止其他事务在 status='pending' 范围内插入
-- → 其他插入 status='pending' 的事务都被阻塞

-- RC 级别（无间隙锁）：
BEGIN;
DELETE FROM orders WHERE status = 'pending';  -- 删除不存在的记录
-- 不加间隙锁
-- → 其他插入 status='pending' 的事务不被阻塞，并发性更高

-- semi-consistent read 优化（RC 级别特有）：
-- UPDATE 时，如果遇到不匹配 WHERE 条件的行，
-- RC 级别读取其已提交版本来判断是否匹配，
-- 不匹配则不加锁并立即释放（减少锁持有）
-- RR 级别不做此优化（扫描过的行都持锁）
```

---

## 适用场景

- **高并发写入场景**：RC 级别没有间隙锁，减少了插入操作被阻塞的情况，适合频繁插入的业务场景（如消息队列写入、日志记录）
- **需要读取最新数据的业务**：每次查询都看到最新已提交数据，适合不需要"同一事务内结果一致"但需要"读到最新状态"的场景

## 常见问题

**RC 级别每次 SELECT 都创建 Read View，性能会比 RR 差吗？**

创建 Read View 本身的开销很小（主要是复制当前活跃事务列表），在常规场景下差异可忽略。但在高并发（大量并发事务）场景下，RC 级别因为每次 SELECT 都创建新 Read View，会比 RR 更频繁地访问全局事务系统（trx_sys），可能在极端并发情况下有轻微额外开销。相比之下，RC 级别减少了间隙锁带来的等待，总体并发性通常优于 RR。

---

## 注意事项

- RC 级别每次 SELECT 创建新 Read View 是指在同一个事务内；不同事务之间本来就各自有独立的 Read View，这与隔离级别无关。
- 在使用 RC 级别时，如果业务逻辑要求"一个事务内多次查询同一数据结果一致"（例如先查再扣减库存），应该使用 `SELECT ... FOR UPDATE`（当前读，加锁）而不是依赖普通 SELECT，因为 RC 级别的快照读不提供可重复读保证。

---

## 总结

RC 级别下，每次执行快照读（普通 SELECT）时都创建全新的 Read View，因此每次查询都能看到截至此刻已提交的最新数据。这导致同一事务内多次读取同一行可能得到不同结果（不可重复读），但保证每次看到的都是最新已提交状态（读已提交）。与 RR 的区别在于 Read View 的创建时机：RC 每次 SELECT 新建，RR 事务内只创建一次复用到结束。RC 不加间隙锁，并发性更高，但需配合 ROW/MIXED 格式 Binlog 使用。

# RR 级别事务开始时创建 Read View

REPEATABLE READ（RR）隔离级别下，InnoDB 在事务内第一次执行快照读时创建 Read View，此后整个事务生命周期内复用这同一个 Read View，直到事务 COMMIT 或 ROLLBACK 时释放。固定的 Read View 是 RR 级别实现"可重复读"的核心机制——因为每次查询都使用同一个快照，所以同一事务内多次读取同一行的结果始终一致，不受其他事务提交的影响。

---

## RR 级别 Read View 的创建行为

```sql
-- RR 级别（默认）：第一次快照读时创建 Read View，整个事务复用

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- 默认，无需设置

BEGIN;
-- 此时尚未创建 Read View

-- T1 时刻：其他事务提交了修改（trx_id=50，balance改为 900）

-- 第一次 SELECT：创建 Read View（快照时间点）
SELECT balance FROM accounts WHERE id = 1;
-- Read View 在此刻创建：
-- m_ids = [当前活跃事务列表（不包含已提交的trx50）]
-- m_up_limit_id = 最小活跃事务ID
-- 结果：900（trx50已提交，在快照前提交，可见）

-- T2 时刻：另一个事务提交了修改（trx_id=80，balance改为 700）

-- 第二次 SELECT：复用同一个 Read View
SELECT balance FROM accounts WHERE id = 1;
-- 使用之前的 Read View：m_low_limit_id > 80（80在创建后才开始）或80在m_ids中
-- 结果：仍然是 900（trx80对这个 Read View 不可见）

-- 第三次 SELECT：仍然复用同一个 Read View
SELECT balance FROM accounts WHERE id = 1;
-- 结果：仍然是 900（可重复读）

COMMIT;
-- Read View 释放
```

## `START TRANSACTION WITH CONSISTENT SNAPSHOT` 立即创建

```sql
-- 普通 BEGIN 不立即创建 Read View，第一次 SELECT 时才创建
BEGIN;
-- [Read View 尚未创建]
-- 这段时间内其他事务的提交，之后的第一次 SELECT 都能看到

-- 立即创建 Read View 的方式：
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- [Read View 在 START TRANSACTION 时立即创建！]
-- 此后所有快照读都看不到此时刻之后提交的任何修改

-- 时间差的影响：
-- 场景：需要对多张表做一致性快照备份
BEGIN;
-- T1：创建 Read View（第一次查 orders 表时）
SELECT * FROM orders;           -- Read View 在此创建
-- T2：其他事务提交，修改了 accounts 表
SELECT * FROM accounts;         -- 复用 Read View（accounts 看到 T2 之前的状态）
-- 问题：orders 表快照点=T1，但如果 BEGIN 和第一次 SELECT 之间有其他提交，
-- 两次查询的快照起点实际上相差很少，通常可忽略

-- 使用 WITH CONSISTENT SNAPSHOT 确保严格一致：
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- Read View 在 START TRANSACTION 时创建，此后两张表的查询使用同一快照点
SELECT * FROM orders;
SELECT * FROM accounts;
-- 两张表都看到同一时刻的快照（严格一致）
```

## RR 级别下的只读事务优化

```sql
-- MySQL 8.0 对只读事务的 RR 级别进行了优化：
-- 如果事务以 START TRANSACTION READ ONLY 开启（显式只读）
-- 或 MySQL 推断该事务只有只读操作（autocommit=ON 的单条 SELECT）
-- InnoDB 不会为其分配正式的事务 ID（减少全局计数器竞争）

-- 只读事务的 Read View：
-- creator_trx_id 为 0（无正式事务 ID）
-- 可见性判断仍然正常工作（自己的修改判断除外，只读事务没有修改）

START TRANSACTION READ ONLY;
SELECT * FROM reports WHERE year = 2024;
-- 使用 Read View，但不分配真实事务 ID
-- 减少了 trx_sys 全局锁的争用

-- 显式声明只读事务还有其他优化：
-- 不维护 Undo Log（无写操作）
-- 减少内存占用
```

## Read View 何时"失效"

```sql
-- RR 级别的 Read View 在以下情况下被释放（不是失效，是正常结束）：

-- 1. COMMIT：事务提交，Read View 释放
BEGIN;
SELECT * FROM t;  -- 创建 Read View
COMMIT;           -- Read View 释放，下次 SELECT 会创建新的

-- 2. ROLLBACK：事务回滚，Read View 释放
BEGIN;
SELECT * FROM t;  -- 创建 Read View
ROLLBACK;         -- Read View 释放

-- 3. 显式 START TRANSACTION：开启新事务时，隐式提交上一个事务（释放其 Read View）
SELECT * FROM t;   -- 上一个事务的 Read View（如果有）
START TRANSACTION; -- 隐式提交，上一个事务 Read View 释放；新事务开始
SELECT * FROM t;   -- 新事务的 Read View（第一次 SELECT 时创建）

-- Read View 的生命周期严格与事务绑定
```

## 适用场景

- **可重复读保证**：财务对账、库存校验等需要在事务内多次查询同一数据保持结果一致的场景，RR 级别通过固定 Read View 提供这种保证
- **一致性报表**：使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 开启报表生成事务，确保整个报表期间看到同一时间点的数据快照（即使报表生成需要数分钟）

## 常见问题

**在 RR 级别下，如果 DML（UPDATE/DELETE）在事务内先执行，之后的 SELECT 也使用第一次 SELECT 时创建的 Read View 吗？**

是的，但有一个重要细节：DML 的执行是"当前读"（读最新版本并加锁），而非快照读。DML 执行时不依赖 Read View（直接读最新版本），所以 DML 的执行不会受到 Read View 的影响。之后的 SELECT（快照读）仍然使用第一次快照读时创建的 Read View。如果是 DML 之后第一次执行 SELECT（之前事务内没有任何 SELECT），则 DML 执行后第一次 SELECT 才创建 Read View，此时的快照包含了自己 DML 的修改。

---

## 注意事项

- 在 RR 级别下，如果事务内先执行了 DML（如 UPDATE），然后执行 SELECT，那么 SELECT 创建的 Read View 对应的时间点是 SELECT 执行时，而不是 BEGIN 时。如果在 DML 和 SELECT 之间，其他事务提交了修改，那么 SELECT 能否看到这些修改取决于 Read View 的创建时间（SELECT 执行时），不是 BEGIN 时。
- 长事务在 RR 级别下持有较旧的 Read View，会阻止 Purge 清理旧版本，需要关注事务执行时长。

---

## 总结

RR 级别下，Read View 在事务内第一次执行快照读（普通 SELECT）时创建，之后整个事务使用同一 Read View（"固定快照"），实现可重复读。`START TRANSACTION WITH CONSISTENT SNAPSHOT` 在 BEGIN 时立即创建 Read View（不等到第一次 SELECT），适合需要严格一致性快照的场景。Read View 与事务绑定，在 COMMIT 或 ROLLBACK 时释放。MySQL 8.0 对只读事务不分配真实事务 ID（优化全局计数器竞争），快照读仍然正常工作。

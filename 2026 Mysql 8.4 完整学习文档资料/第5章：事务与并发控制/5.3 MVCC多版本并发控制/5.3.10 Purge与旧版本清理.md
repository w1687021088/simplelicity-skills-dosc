# Purge 与旧版本清理

Purge 是 InnoDB 后台运行的清理机制，负责删除不再被任何活跃事务 Read View 引用的旧行版本（Undo Log 记录）以及被标记为删除（delete-mark）的行。没有 Purge，Undo 表空间会因不断累积历史版本而无限增长，最终耗尽磁盘空间。Purge 是 MVCC 机制中维持系统长期稳定运行的关键后台工作。

---

## Purge 的工作原理

```
Purge 的清理边界：
  系统保存一个"Purge 可见水位"：
    = 当前所有活跃 Read View 中，最旧的 m_up_limit_id
    = 系统中最古老的活跃事务所看到的最旧可见事务 ID

  Purge 可以安全清理的版本：
    DB_TRX_ID < Purge 可见水位 的 Undo 记录
    即：没有任何活跃 Read View 可能需要这些版本

  Purge 不能清理的版本：
    DB_TRX_ID >= Purge 可见水位 的 Undo 记录
    即：某些活跃事务的 Read View 可能还需要访问这些版本

  关键约束：
    只要系统中存在一个持有旧 Read View 的长事务，
    Purge 就无法清理该 Read View 创建时间点之后的任何版本
    → 长事务是 Undo 膨胀的根本原因
```

---

## Purge 的两类清理工作

```sql
-- 工作1：清理 Delete-Marked 行（物理删除）
-- DELETE 操作只做软删除（设置 delete_flag），物理删除由 Purge 完成

-- 软删除后的状态：
-- 行记录存在于数据页中，但 delete_flag = 1
-- DB_TRX_ID = DELETE 操作的事务 ID

-- Purge 判断条件：
-- 如果该行的 DELETE 事务对所有活跃 Read View 都可见（即 Purge 水位 > DELETE 的事务 ID）
-- → 没有任何事务会再需要看到"删除前的版本"
-- → Purge 安全地从数据页中物理删除该行

-- 工作2：清理 Undo Log 旧版本
-- UPDATE 操作在 Undo Log 中保存旧版本，Purge 删除不再需要的旧版本

-- 可以清理的 Undo 记录：
-- Undo 记录的 DB_TRX_ID < Purge 水位
-- 即：所有活跃 Read View 都不需要访问这个版本

-- 注意：INSERT Undo 在事务提交后立即可以清理（插入行无需历史版本）
-- UPDATE/DELETE Undo 需要等到 Purge 水位超过其 DB_TRX_ID 才能清理
```

## Purge 的配置参数

```sql
-- 1. Purge 线程数量
SHOW VARIABLES LIKE 'innodb_purge_threads';
-- 默认值：4（MySQL 8.0）
-- 适当增加可以提升 Purge 速度（在高写入量场景）
SET GLOBAL innodb_purge_threads = 8;  -- 动态修改

-- 2. Purge 批次大小
SHOW VARIABLES LIKE 'innodb_purge_batch_size';
-- 默认值：300（每次 Purge 处理的 Undo 记录数量）
-- 增大批次可提升 Purge 吞吐量，但每次 Purge 时间变长（可能影响响应时间）

-- 3. Purge 触发频率（MySQL 8.0.22+，基于 innodb_purge_rseg_truncate_frequency）
SHOW VARIABLES LIKE 'innodb_purge_rseg_truncate_frequency';
-- 默认值：128（每 Purge 128 次，触发一次回滚段截断）
-- 较小的值：回滚段释放更及时（磁盘回收更快），但 Purge 开销更大

-- 4. 延迟 Purge（innodb_max_purge_lag 相关）
SHOW VARIABLES LIKE 'innodb_max_purge_lag';
-- 默认值：0（不限制，Purge 尽快跟上）
-- 设置为正值：当 History list length 超过此值时，对 DML 施加延迟（降低写入速度）
-- 目的：防止 Purge 跟不上写入导致 Undo 无限膨胀
```

## 监控 Purge 状态

```sql
-- 1. 查看 History list length（未清理的 Undo 版本数量）
SHOW ENGINE INNODB STATUS \G
-- 在输出中查找：
-- History list length 1023   ← 这个值代表未被 Purge 的 Undo 事务数量
-- 正常：< 1000
-- 警告：1000 ~ 10000
-- 严重：> 10000（通常是长事务阻塞 Purge 或 Purge 线程不足）

-- 2. 查找阻塞 Purge 的长事务
SELECT
    trx_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
    trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_started
LIMIT 10;
-- 最早启动的活跃事务就是阻塞 Purge 的"罪犯"

-- 3. 通过 performance_schema 监控 Purge 线程活动
SELECT NAME, STATUS
FROM performance_schema.threads
WHERE NAME LIKE '%purge%';
```

## 长事务阻塞 Purge 的示意

```
场景：事务A（trx_id=100）运行了很长时间（如24小时）

事务A 的 Read View：
  m_up_limit_id = 100（低水位）

Purge 水位 = min(所有活跃 Read View 的 m_up_limit_id) = 100

影响：
  Purge 只能清理 DB_TRX_ID < 100 的版本
  在这 24 小时内，所有 DB_TRX_ID >= 100 的版本都无法清理
  
  假设系统每秒 1000 次 UPDATE（每次产生一个新版本）：
  24 小时 = 86400 秒 × 1000 = 8640 万个旧版本无法清理！
  
  Undo 表空间膨胀 = 每个版本平均 100 字节 × 8640 万 ≈ 8.2 GB！

解决：
  KILL CONNECTION <connection_id_of_trx_A>;  -- 终止长事务
  -- 或：事务A自己 COMMIT/ROLLBACK
  -- Purge 水位随即大幅提升，开始快速清理积压的旧版本
```

## 适用场景

- **Undo 表空间监控**：生产环境应定期监控 `History list length`（通过 `SHOW ENGINE INNODB STATUS`）和 Undo 文件大小，发现异常增长时立即查找并处理长事务
- **Purge 参数调优**：高写入量系统（每秒数万次 DML）可能需要增加 `innodb_purge_threads`（4→8）来保持 Purge 跟上写入速度，防止 History list 积压

## 常见问题

**Purge 清理旧版本后，磁盘空间会立即释放吗？**

不会立即释放给操作系统。Purge 清理旧版本后，Undo 段中的相应页面被标记为可复用，但不会立即将磁盘空间归还给操作系统。InnoDB 会将这些页面加入"空闲页列表"供后续 Undo 操作重复使用。只有当整个 Undo 表空间（undo tablespace）中所有 Undo 段都为空，且满足截断条件时，InnoDB 才会将 Undo 表空间文件的大小实际缩减（通过 `innodb_undo_log_truncate=ON` 和 `innodb_max_undo_log_size` 控制）。

---

## 注意事项

- 不要将 `innodb_purge_threads` 设置过高（超过 CPU 核心数），过多的 Purge 线程会争用 CPU 和磁盘 I/O，反而降低整体性能。通常 4~8 个 Purge 线程足够应对多数生产工作负载。
- 在 MySQL 8.0 中，Undo 表空间可以动态增加（`CREATE UNDO TABLESPACE`）和截断（`innodb_undo_log_truncate=ON`）。开启 `innodb_undo_log_truncate` 可以在 Undo 表空间超过 `innodb_max_undo_log_size` 时自动截断，防止 Undo 无限增长，但截断操作本身有一定开销。

---

## 总结

Purge 是 InnoDB 的后台清理机制，负责物理删除带有 delete-mark 的行和清理不再被任何 Read View 引用的 Undo Log 旧版本。Purge 的清理边界（水位）由系统中最旧活跃 Read View 的低水位决定——长事务持有旧 Read View，直接阻塞 Purge，导致 Undo 膨胀。通过 `SHOW ENGINE INNODB STATUS` 的 `History list length` 监控 Purge 积压情况；通过 `innodb_purge_threads`/`innodb_purge_batch_size` 控制 Purge 速度；通过查找并终止长事务解除 Purge 阻塞。MySQL 8.0 支持 `innodb_undo_log_truncate` 自动截断过大的 Undo 表空间。

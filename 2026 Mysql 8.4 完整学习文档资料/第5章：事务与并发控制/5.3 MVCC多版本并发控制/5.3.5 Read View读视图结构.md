# Read View 读视图结构

Read View（读视图）是 MVCC 机制中的核心数据结构，在事务执行快照读（普通 SELECT）时创建，记录了创建时刻整个系统的事务状态快照。Read View 定义了"哪些事务的修改对当前事务可见"，是版本可见性判断的依据。

---

## Read View 的内部结构

```
Read View 的核心字段（InnoDB 源码 struct ReadView）：

creator_trx_id（创建者事务 ID）：
  当前事务的 ID
  自己修改的行（DB_TRX_ID == creator_trx_id）永远可见

m_ids（活跃事务 ID 列表）：
  创建 Read View 时，所有活跃（未提交）的读写事务 ID 列表
  按 ID 从小到大排序
  这些事务在 Read View 创建时都还未提交，其修改对当前事务不可见

m_up_limit_id（低水位）：
  m_ids 中最小的事务 ID（或 low_limit_id 如果 m_ids 为空）
  DB_TRX_ID < m_up_limit_id 的行版本，一定在 Read View 创建前已提交，可见

m_low_limit_id（高水位）：
  Read View 创建时下一个将要分配的事务 ID
  DB_TRX_ID >= m_low_limit_id 的行版本，一定是 Read View 创建后才开始的事务，不可见
```

---

## Read View 的可见性判断规则

```
对于行版本的 DB_TRX_ID = X，判断流程：

步骤1：检查是否是自己的修改
  if X == creator_trx_id：可见（当前事务自己修改的行）→ 返回

步骤2：检查低水位
  if X < m_up_limit_id：
    X 在 Read View 创建前就已提交 → 可见 → 返回

步骤3：检查高水位
  if X >= m_low_limit_id：
    X 在 Read View 创建后才开始的事务 → 不可见 → 找旧版本

步骤4：查活跃事务列表
  if m_up_limit_id <= X < m_low_limit_id：
    在 m_ids 中二分查找 X：
      找到（X 在列表中）：X 创建 Read View 时还未提交 → 不可见 → 找旧版本
      未找到（X 不在列表中）：X 在 Read View 创建前已提交 → 可见 → 返回
```

## Read View 的创建与销毁时机

```sql
-- READ COMMITTED 级别：
-- 每次 SELECT 时创建新的 Read View（反映最新提交状态）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN;
SELECT * FROM t;  -- 创建 Read View-1（此时活跃事务列表）
-- 其他事务提交...
SELECT * FROM t;  -- 创建 Read View-2（新的活跃事务列表，看到新提交）
COMMIT;
-- Read View-1 和 Read View-2 在各自 SELECT 后不再使用

-- REPEATABLE READ 级别（默认）：
-- 事务内第一次 SELECT 时创建 Read View，整个事务使用同一个
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT * FROM t;  -- 创建 Read View（整个事务使用这个快照）
-- 其他事务提交...
SELECT * FROM t;  -- 复用同一个 Read View（看不到新提交，可重复读）
COMMIT;           -- Read View 销毁

-- 特殊：START TRANSACTION WITH CONSISTENT SNAPSHOT
-- 在 START TRANSACTION 时立即创建 Read View（不等到第一次 SELECT）
START TRANSACTION WITH CONSISTENT SNAPSHOT;
-- Read View 已创建（此后任何时间新提交的修改对本事务不可见）
```

## 多个 Read View 共存

```
系统中同时可能存在多个活跃 Read View（对应多个活跃事务）：

系统状态（当前活跃事务）：
  事务10（RR级别，Read View-1: m_ids=[10], m_up_limit_id=10, m_low_limit_id=20）
  事务15（RC级别，每次 SELECT 创建新 Read View）
  事务18（RR级别，Read View-2: m_ids=[10,15,18], m_up_limit_id=10, m_low_limit_id=20）

Purge 线程的清理约束：
  必须保留所有 Read View 都可能引用的版本
  最早的 Read View 的 m_up_limit_id 决定了 Purge 的清理下界
  → 事务10的 Read View-1 持有 m_up_limit_id=10
  → Purge 不能清理任何 trx_id >= 10 的版本（可能被事务10引用）
  → 事务10不提交/回滚，系统中就一直保留大量旧版本
```

## Read View 的内存开销

```sql
-- Read View 的内存结构（每个 Read View）：
-- 固定部分：约 60 字节（creator_trx_id, up_limit_id, low_limit_id 等）
-- 变长部分：m_ids 列表，每个事务 ID 8 字节
--   100 个活跃事务 → m_ids 约 800 字节
--   1000 个活跃事务 → m_ids 约 8 KB

-- 在高并发系统（大量并发事务）中：
-- 活跃事务数量多 → m_ids 列表大 → Read View 占用内存多
-- RC 级别每次 SELECT 创建新 Read View（频繁创建和销毁）
-- RR 级别每个事务只创建一次（但持有较长时间）

-- 监控 Read View 相关的系统状态：
SHOW ENGINE INNODB STATUS \G
-- 查找：
-- "History list length"（未清理的 Undo 版本数量，与最旧 Read View 相关）
-- "Trx id counter"（当前最大事务 ID）
```

## 适用场景

- **MVCC 工作原理深度理解**：Read View 是理解"为什么不同事务看到不同的数据版本"的关键——每个 Read View 代表一个事务看世界的"视角"
- **隔离级别行为分析**：RC 和 RR 的本质区别就在于 Read View 的创建时机（每次 SELECT vs. 事务第一次读），理解这一点就理解了两者的所有行为差异

---

## 常见问题

**Read View 是物理结构还是逻辑结构？创建它有性能开销吗？**

Read View 是纯内存结构（`struct ReadView`），在事务执行快照读时在内存中创建，事务结束时释放，不会写磁盘。创建 Read View 的主要开销是：获取全局事务链表锁（trx_sys mutex）来读取当前活跃事务列表。在高并发场景（大量活跃事务），这个锁的争用可能带来轻微的创建延迟。RC 级别每次 SELECT 都创建 Read View，在高频查询场景下，这个开销会累积。MySQL 8.0 对 Read View 的创建进行了优化，减少了锁的持有时间。

---

## 注意事项

- Read View 中的 m_ids 列表是创建时的快照，不会动态更新——即使后来某些活跃事务提交了，m_ids 中的记录不会被移除。可见性判断仍然基于 m_ids 的原始内容（创建时的状态）。这保证了 RR 级别下"同一事务内重复读取结果一致"的特性。
- 在使用连接池的系统中，连接复用可能导致 Read View 的意外残留。应确保每次业务操作后事务都被正确提交或回滚，避免 Read View 长时间持有（变成长事务问题）。

---

## 总结

Read View 是 MVCC 快照读的核心数据结构，包含：`creator_trx_id`（当前事务 ID）、`m_ids`（创建时所有活跃事务 ID 列表）、`m_up_limit_id`（低水位，最小活跃事务 ID）、`m_low_limit_id`（高水位，下一个将分配的事务 ID）。可见性判断规则：`DB_TRX_ID < up_limit_id` 可见；`>= low_limit_id` 不可见；中间范围查 m_ids 列表。RC 级别每次 SELECT 创建新 Read View，RR 级别事务内只创建一次（保证可重复读）。Read View 是纯内存结构，事务结束后释放。

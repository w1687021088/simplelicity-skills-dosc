# 隐藏列 DB_ROLL_PTR 回滚指针

`DB_ROLL_PTR`（回滚指针）是 InnoDB 行记录中 7 字节的隐藏列，指向该行在 Undo Log 中保存的上一个历史版本。每次 UPDATE 或 DELETE 操作修改某行时，InnoDB 会将修改前的旧版本写入 Undo Log，并将当前行的 DB_ROLL_PTR 指向该 Undo Log 记录。通过 DB_ROLL_PTR，同一行的所有历史版本被串联成一条"版本链"，MVCC 的快照读通过遍历版本链找到对当前事务可见的版本。

---

## DB_ROLL_PTR 的基本特征

```
DB_ROLL_PTR 属性：
- 大小：7 字节（包含 rollback segment ID + page number + offset）
- 含义：指向此行在 Undo Log 中的上一个版本
- 更新时机：
    INSERT：DB_ROLL_PTR 为 NULL 或特殊值（无历史版本）
    UPDATE：指向修改前的旧版本（在 Undo Log 中）
    DELETE：指向标记 delete-mark 之前的版本
    SELECT：不修改 DB_ROLL_PTR

- 物理结构：
    1 bit：是否是插入的 Undo（Insert Undo）
    7 bits：Undo Segment ID（指向哪个回滚段）
    4 bytes：Undo Log 页号（在回滚段的哪一页）
    2 bytes：页内偏移量（在页内的哪个位置）
```

## 版本链的形成过程

```
版本链示例（账户 id=1 的修改历史）：

初始状态（事务50 INSERT）：
  数据页：
    DB_TRX_ID = 50（INSERT 的事务）
    DB_ROLL_PTR = NULL（无旧版本）
    balance = 1000

事务80 UPDATE（balance 1000 → 800）：
  Undo Log 中写入旧版本：
    [旧版本1]: DB_TRX_ID=50, balance=1000, DB_ROLL_PTR=NULL
  数据页更新：
    DB_TRX_ID = 80
    DB_ROLL_PTR → [旧版本1]
    balance = 800

事务100 UPDATE（balance 800 → 500）：
  Undo Log 中写入旧版本：
    [旧版本2]: DB_TRX_ID=80, balance=800, DB_ROLL_PTR→[旧版本1]
  数据页更新：
    DB_TRX_ID = 100
    DB_ROLL_PTR → [旧版本2]
    balance = 500

版本链（从新到旧）：
  当前行(TRX=100, balance=500) → [旧版本2(TRX=80, balance=800)] → [旧版本1(TRX=50, balance=1000)] → NULL
```

## MVCC 通过版本链查找可见版本

```sql
-- 示例：Read View 的 up_limit_id=85（trx_ids包含事务100）

-- 当前行版本：DB_TRX_ID=100，在 trx_ids 中（未提交）→ 不可见
-- → 通过 DB_ROLL_PTR 读取旧版本2

-- 旧版本2：DB_TRX_ID=80 < up_limit_id=85 → 在 Read View 创建前已提交 → 可见！
-- → 返回 balance=800（这是当前事务能看到的最新已提交版本）

-- 如果 up_limit_id=75（trx_ids包含事务80和100）：
-- 当前行：DB_TRX_ID=100，在 trx_ids → 不可见，找旧版本2
-- 旧版本2：DB_TRX_ID=80，在 trx_ids → 不可见，找旧版本1
-- 旧版本1：DB_TRX_ID=50 < up_limit_id=75 → 可见！
-- → 返回 balance=1000

-- 版本链遍历的性能影响：
-- 版本链越长，遍历越慢（需要多次读取 Undo Log 页）
-- 长版本链是 MVCC 在高频更新场景下的性能隐患
```

## INSERT 的 DB_ROLL_PTR 特殊处理

```sql
-- INSERT 操作的 Undo Log 类型（INSERT Undo）与 UPDATE Undo 不同：
-- INSERT Undo：在事务提交后可以立即清除（不需要 MVCC 访问旧版本）
--   因为：INSERT 的行在其创建事务提交后才对其他事务可见
--   如果 INSERT 事务回滚，需要 Undo 删除该行
--   INSERT 事务提交后，其他事务直接读当前版本即可，不需要访问 Insert Undo

-- UPDATE Undo：需要保留到没有任何 Read View 引用该版本后才能清除
--   因为：旧版本可能被其他事务的 MVCC 快照读所需要

-- 因此 INSERT 操作后，DB_ROLL_PTR 指向的 Insert Undo 在事务提交后可以较快被 Purge 清理
-- 而 UPDATE Undo 可能需要保留较长时间（取决于最旧的活跃 Read View）
```

## 版本链长度与性能

```sql
-- 高频 UPDATE 同一行会导致长版本链，影响 MVCC 查询性能

-- 监控版本链相关的指标：
SHOW ENGINE INNODB STATUS \G
-- 查找：History list length
-- History list length = 未被 Purge 清理的 Undo Log 版本数量
-- 正常：< 1000
-- 需关注：> 10000
-- 严重：> 100000（通常是长事务阻塞 Purge 导致）

-- 查找长事务（持有旧 Read View，阻止 Purge）：
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec
FROM information_schema.INNODB_TRX
ORDER BY trx_started
LIMIT 5;
-- 最旧的事务决定了 Purge 能清理到哪个版本之前
```

## 适用场景

- **MVCC 深度学习**：理解 DB_ROLL_PTR 的版本链机制，有助于解释"为什么事务能看到某个特定的历史版本"，以及"为什么 Undo 表空间会增长"
- **性能诊断**：当发现读操作变慢（`SELECT` 耗时异常增长），可以检查是否存在长版本链（History list length 过大），并查找阻塞 Purge 的长事务

## 常见问题

**DB_ROLL_PTR 在什么情况下会是 NULL？**

`DB_ROLL_PTR` 为 NULL 或特殊的无效值只发生在 INSERT 时（该行最初插入时无历史版本）。在 InnoDB 内部，Insert Undo 的 `DB_ROLL_PTR` 会设置一个特殊的标志位（is_insert=1），而不是真正的 NULL 指针，表示这是插入的初始版本，没有更旧的版本。当 MVCC 遍历版本链到达 is_insert=1 的版本时，停止遍历。

---

## 注意事项

- DB_ROLL_PTR 指向 Undo Log 中的页位置（rollback segment ID + page number + offset），这意味着读取旧版本需要访问 Undo 段的磁盘页。如果版本链很长（Undo 段有大量旧版本），MVCC 遍历版本链会触发多次磁盘 I/O，严重影响查询性能。这是"Undo 膨胀会降低读取性能"的根本原因。
- 在 DELETE 操作中，InnoDB 先将行标记为 delete-mark（软删除），而不是立即物理删除。DB_ROLL_PTR 此时指向删除前的版本，其他事务的 MVCC 快照读可以看到删除前的版本（如果它们的 Read View 创建于删除之前）。物理删除由 Purge 线程异步完成。

---

## 总结

`DB_ROLL_PTR` 是 7 字节的隐藏列，记录指向 Undo Log 中旧版本的物理位置（rollback segment ID + page + offset）。每次 UPDATE/DELETE 操作在 Undo Log 中写入旧版本，并更新 DB_ROLL_PTR 指向该旧版本，从而将同一行的所有历史版本串联成版本链。MVCC 快照读通过逐版本遍历（检查 DB_TRX_ID 的可见性）找到对当前事务可见的版本。版本链越长，遍历越慢；长事务阻塞 Purge 会导致版本链积累、Undo 膨胀和读性能下降。

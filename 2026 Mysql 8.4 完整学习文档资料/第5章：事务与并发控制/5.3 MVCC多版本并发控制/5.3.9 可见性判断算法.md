# 可见性判断算法

InnoDB MVCC 的可见性判断算法是快照读的核心逻辑，决定了对于版本链上的每一个行版本，当前事务能否读取该版本。该算法基于 Read View 的四个字段（`creator_trx_id`、`m_ids`、`m_up_limit_id`、`m_low_limit_id`）与行版本的 `DB_TRX_ID` 进行比较，是一个确定性的判断流程，不存在歧义。

---

## 算法完整流程

```
输入：
  X = 当前行版本的 DB_TRX_ID（该版本最后修改者的事务 ID）
  RV = 当前事务的 Read View
    RV.creator_trx_id = 当前事务 ID
    RV.m_ids = 创建 Read View 时所有活跃事务 ID 列表（已排序）
    RV.m_up_limit_id = m_ids 中最小值（低水位）
    RV.m_low_limit_id = 下一个将分配的事务 ID（高水位）

判断步骤（按顺序，命中即返回）：

步骤1：自身可见性
  if X == RV.creator_trx_id:
      return VISIBLE    ← 当前事务自己修改的行，当然可见

步骤2：低水位判断（快速路径）
  if X < RV.m_up_limit_id:
      return VISIBLE    ← X 在低水位之前已提交，可见

步骤3：高水位判断（快速路径）
  if X >= RV.m_low_limit_id:
      return NOT_VISIBLE ← X 在 Read View 创建后才分配，不可见

步骤4：活跃列表精确查找
  if X in RV.m_ids (binary search):
      return NOT_VISIBLE ← X 创建 Read View 时还在活跃，未提交，不可见
  else:
      return VISIBLE    ← X 不在活跃列表，在创建 Read View 前已提交，可见

输出：VISIBLE（可见，读取此版本）或 NOT_VISIBLE（不可见，通过 DB_ROLL_PTR 找旧版本）
```

## 版本链遍历的完整算法

```
输入：
  行记录（数据页中最新版本）
  Read View RV

算法：
  current_version = 数据页中的最新行版本

  loop:
      X = current_version.DB_TRX_ID
      
      if is_visible(X, RV):  // 按上述算法判断
          return current_version.data  // 返回此版本的数据
      
      if current_version.DB_ROLL_PTR == NULL (is_insert = true):
          return NULL  // 到达版本链末尾，INSERT 行不可见（行对当前事务不存在）
      
      // 通过 DB_ROLL_PTR 读取旧版本（可能需要读 Undo Log 磁盘页）
      current_version = read_undo_record(current_version.DB_ROLL_PTR)

  // 如果遍历完整个版本链都不可见，返回"行不存在"
  return NULL
```

## 详细案例演算

```
系统状态：
  已提交事务：trx_id = 10, 20, 30, 40, 60
  活跃事务（未提交）：trx_id = 50, 70, 90
  下一个将分配 ID = 100

当前事务 trx_id = 65，Read View：
  creator_trx_id = 65
  m_ids = [50, 70, 90]
  m_up_limit_id = 50
  m_low_limit_id = 100

账户 id=1 的版本链（从新到旧）：
  版本4：DB_TRX_ID=90, balance=400（事务90未提交）
  版本3：DB_TRX_ID=70, balance=600（事务70未提交）
  版本2：DB_TRX_ID=60, balance=800（事务60已提交）
  版本1：DB_TRX_ID=30, balance=1000（事务30已提交）

算法执行：
  检查版本4（X=90）：
    90 != 65 (步骤1 pass)
    90 >= 50 (步骤2 pass，90不小于up_limit_id)
    90 < 100 (步骤3 pass，90小于high)
    90 in [50,70,90] → 在活跃列表中 → NOT_VISIBLE

  检查版本3（X=70）：
    70 != 65 (步骤1 pass)
    70 >= 50 (步骤2 pass)
    70 < 100 (步骤3 pass)
    70 in [50,70,90] → 在活跃列表中 → NOT_VISIBLE

  检查版本2（X=60）：
    60 != 65 (步骤1 pass)
    60 >= 50 (步骤2 pass)
    60 < 100 (步骤3 pass)
    60 not in [50,70,90] → 不在活跃列表 → VISIBLE！

  返回版本2的数据：balance=800
```

## DELETE 标记的可见性处理

```
DELETE 操作在 InnoDB 中是"软删除"：
  - 将行标记为 delete-mark（DB_TRX_ID 更新为 DELETE 事务的 ID）
  - 不立即物理删除
  - 版本链保留

可见性判断对 DELETE 行的处理：
  1. 找到对当前事务可见的版本（正常可见性判断）
  2. 如果该版本有 delete-mark：
     → 判断 DELETE 事务对当前 Read View 是否可见
     → 如果 DELETE 事务可见（已提交且在 Read View 的视角已完成）：
         该行已被删除，对当前事务不存在 → 返回"行不存在"
     → 如果 DELETE 事务不可见（如 DELETE 未提交）：
         该行对当前事务仍然存在（可以看到 DELETE 之前的版本）
```

## 算法优化：步骤2的"快速路径"重要性

```
在生产系统中：
  绝大多数行的 DB_TRX_ID 比 up_limit_id 小（历史行）
  → 通过步骤2（低水位比较）直接确定可见，跳过活跃列表查找
  
  低水位快速路径的命中率非常高（~90% 以上的行版本通过此路径判断）
  → 避免了大量的 m_ids 二分查找操作
  → 这是 InnoDB MVCC 能在高并发下保持高性能的关键优化之一

  对于频繁更新的热点行（版本链长），版本链遍历才是性能瓶颈
```

## 适用场景

- **深度理解 MVCC**：通过手动演算可见性判断算法，验证特定事务场景下的可见性结果，排查"为什么某查询看不到最新数据"等问题
- **性能分析**：在高频更新场景下，如果 MVCC 查询变慢，可以分析版本链长度（History list length）和活跃事务列表大小，评估可见性判断的开销

## 常见问题

**为什么 m_ids 不包含已提交事务的 ID？步骤4中"不在列表则可见"是否可靠？**

m_ids 是创建 Read View 时活跃事务的快照，已提交的事务不在列表中。当 `up_limit_id <= X < low_limit_id` 且 X 不在 m_ids 中时，说明 X 是一个在 Read View 创建前就存在（ID 比 up_limit_id 大，说明是在活跃列表最小值之后才分配的）、但在 Read View 创建时已经完成提交的事务（不在活跃列表中）。因此可以确定它已提交，其修改可见。这个判断是可靠的，基于事务 ID 的单调递增性和 m_ids 快照的一致性。

---

## 注意事项

- 可见性判断算法的正确性依赖于事务 ID 的单调递增性。如果事务 ID 发生回绕（在某些极端情况下，48位事务 ID 计数器耗尽归零），算法将产生错误的可见性判断。InnoDB 的设计保证了这种情况在实际中不会发生（48位足够使用极长时间）。
- 整个可见性判断算法是无锁的（除了 Read View 本身的创建需要短暂持锁），判断过程中不需要任何锁，这是 MVCC 实现读写不互阻塞的基础。

---

## 总结

可见性判断算法依次执行四个步骤：自身可见（creator_trx_id 匹配）、低水位判断（DB_TRX_ID < up_limit_id，快速可见）、高水位判断（>= low_limit_id，快速不可见）、活跃列表二分查找（中间范围精确判断）。对版本链的遍历是：从最新版本开始，对每个版本执行上述算法，找到第一个 VISIBLE 版本即返回；全部不可见则行对当前事务不存在。该算法无锁执行，是 MVCC 高并发读写不互阻塞的基础。低水位快速路径是主要性能优化点，覆盖绝大多数行的可见性判断。

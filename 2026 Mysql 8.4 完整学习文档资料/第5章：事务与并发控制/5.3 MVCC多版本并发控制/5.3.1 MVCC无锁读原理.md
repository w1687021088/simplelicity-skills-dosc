# MVCC 无锁读原理

MVCC（Multi-Version Concurrency Control，多版本并发控制）是 InnoDB 实现事务隔离性的核心机制。其核心思想是：通过维护数据的多个历史版本，使读操作不需要加锁也能看到一个一致的数据快照，从而让读写操作可以并发执行而不互相阻塞。MVCC 是 InnoDB 高并发读写性能的关键基础。

---

## MVCC 的基本工作原理

```
MVCC 的核心三要素：

1. 隐藏列（行版本信息）
   每条行记录包含三个隐藏列：
   DB_TRX_ID：最后修改此行的事务ID
   DB_ROLL_PTR：指向此行旧版本的 Undo Log 指针（版本链指针）
   DB_ROW_ID：行记录唯一标识（无主键时自动生成）

2. Undo Log 版本链
   每次 UPDATE/DELETE 操作都会在 Undo Log 中保存旧版本
   通过 DB_ROLL_PTR 将多个版本串成版本链
   形成数据的"历史时间线"

3. Read View（读视图）
   事务执行 SELECT 时创建的"快照元数据"
   记录创建时活跃（未提交）的事务 ID 列表
   通过与行记录的 DB_TRX_ID 比较，决定读取版本链上的哪个版本
```

---

## MVCC 读的可见性判断流程

```
SELECT 的执行流程（快照读）：

1. 创建或获取 Read View（RC 每次创建，RR 复用）
   Read View 包含：
   - creator_trx_id：当前事务的 ID
   - trx_ids：创建 Read View 时所有活跃（未提交）事务的 ID 列表
   - up_limit_id：trx_ids 中最小的事务 ID（低水位）
   - low_limit_id：创建 Read View 时下一个将分配的事务 ID（高水位）

2. 读取行记录，获取 DB_TRX_ID = X

3. 可见性判断：
   如果 X == creator_trx_id：
     → 当前事务自己的修改，可见
   
   如果 X < up_limit_id：
     → X 在 Read View 创建前就已提交，可见
   
   如果 X >= low_limit_id：
     → X 在 Read View 创建后才开始的事务，不可见
     → 通过 DB_ROLL_PTR 找上一个版本，重复判断
   
   如果 up_limit_id <= X < low_limit_id：
     → 查 trx_ids 列表
     → X 在列表中：该事务创建时还未提交，不可见，找上一个版本
     → X 不在列表中：该事务已提交，可见

4. 如果沿版本链遍历到没有可见版本，则该行对当前事务不可见（行不存在）
```

## MVCC 使读写不互阻塞

```sql
-- 演示：写操作不阻塞读操作

-- 会话1（写）：
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;
-- 加 X 锁，balance 修改为 500（未提交）
-- 旧版本（balance=1000）保留在 Undo Log 中

-- 会话2（读，RC 级别）：
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
-- 不需要等待 X 锁！
-- 创建 Read View，会话1的事务ID在 trx_ids 中（活跃）
-- → 读取行时，DB_TRX_ID = 会话1的ID，在 trx_ids 中 → 不可见
-- → 通过 DB_ROLL_PTR 找到上一个版本（Undo Log 中的 balance=1000）
-- → 返回 1000（上一个已提交版本）
-- 读不阻塞写，写不阻塞读！

-- 会话2的 SELECT 立即返回，不需要等待会话1提交
```

## MVCC 与当前读的区别

```sql
-- 快照读（MVCC 读）：普通 SELECT，不加锁，读历史版本
SELECT * FROM accounts WHERE id = 1;

-- 当前读：读最新版本，加锁
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;      -- X 锁
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;  -- S 锁
UPDATE accounts SET balance = 500 WHERE id = 1;       -- X 锁（隐式）
DELETE FROM accounts WHERE id = 1;                   -- X 锁（隐式）

-- 当前读必须等待 X 锁释放（会被写操作阻塞）
-- 快照读不受 X 锁影响（读历史版本）

-- 总结：MVCC 的无锁读特指"快照读"，不是所有 SELECT 都无锁
```

## 版本链示例

```
账户 id=1 的版本链（时间从新到旧）：

[最新版本]
DB_TRX_ID = 100（事务100的修改，balance=500，未提交）
DB_ROLL_PTR → ↓

[旧版本1] - 在 Undo Log 中
DB_TRX_ID = 80（事务80的修改，balance=800，已提交）
DB_ROLL_PTR → ↓

[旧版本2] - 在 Undo Log 中
DB_TRX_ID = 50（事务50的修改，balance=1000，已提交）
DB_ROLL_PTR → NULL（最初版本）

如果某事务的 up_limit_id = 85（trx_ids 包含事务100）：
→ 最新版本（trx_id=100）在 trx_ids 中 → 不可见，找上一版本
→ 旧版本1（trx_id=80）小于 up_limit_id(85) → 不在 trx_ids 中... 
  实际上 80 < 85 且 80 不在 trx_ids 中（已提交）→ 可见！
→ 返回 balance=800
```

## 适用场景

- **高并发读写混合**：MVCC 使读操作不阻塞写操作（快照读），适合 OLTP 的读写混合场景（如电商、社交系统）
- **一致性快照读**：报表查询使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 配合 MVCC，在整个报表生成过程中看到一个固定时间点的数据

## 常见问题

**MVCC 的多个历史版本保存在哪里？会无限增长吗？**

历史版本保存在 Undo Log Segment 中（即 Undo 表空间）。Purge 线程负责清理不再被任何活跃事务的 Read View 引用的旧版本——当一个版本比系统中所有活跃事务的 Read View 都旧时，Purge 线程将其从 Undo 段中清除。因此，只要没有长事务长期持有旧 Read View，Undo 不会无限增长，Purge 会定期清理过期版本。

---

## 注意事项

- MVCC 只对 InnoDB 存储引擎有效（MyISAM 没有 MVCC，也不支持真正的事务）。
- 长事务会持有旧的 Read View，阻止 Purge 清理旧版本，导致 Undo 表空间膨胀。监控和控制长事务是维护 MVCC 性能的重要工作。可以通过 `SHOW ENGINE INNODB STATUS` 查看 History list length（未被 Purge 的 Undo 版本数量），该值过大（如超过数万）说明有长事务阻塞 Purge。

---

## 总结

MVCC 通过三要素实现无锁读：行记录的隐藏列（DB_TRX_ID/DB_ROLL_PTR）记录版本信息，Undo Log 保存历史版本链，Read View 通过可见性算法（对比 DB_TRX_ID 与 trx_ids/up_limit_id/low_limit_id）决定读取版本链上的哪个版本。普通 SELECT 为快照读，不加锁，读历史版本，使读不阻塞写、写不阻塞读。当前读（FOR UPDATE/DML）仍需加锁，读最新版本。Purge 线程定期清理不再被任何 Read View 引用的旧版本。

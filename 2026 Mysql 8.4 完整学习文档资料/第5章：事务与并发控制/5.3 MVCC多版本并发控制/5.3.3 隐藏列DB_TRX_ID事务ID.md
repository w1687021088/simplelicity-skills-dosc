# 隐藏列 DB_TRX_ID 事务 ID

`DB_TRX_ID` 是 InnoDB 每条行记录中最核心的隐藏列，占 6 字节，记录最后修改（INSERT 或 UPDATE）该行的事务 ID。它是 MVCC 可见性判断的核心依据——Read View 通过比较行记录的 DB_TRX_ID 与自身记录的事务 ID 列表，判断当前事务能否看到该行版本。

---

## DB_TRX_ID 的基本特征

```
DB_TRX_ID 属性：
- 大小：6 字节（48 位）
- 含义：最后修改此行版本的事务 ID
- 更新时机：
    INSERT：设置为执行 INSERT 的事务 ID
    UPDATE：设置为执行 UPDATE 的事务 ID（更新行版本）
    DELETE：设置为执行 DELETE 的事务 ID（标记 delete-mark，不立即删除）
    SELECT（快照读）：不修改 DB_TRX_ID（读不修改行版本信息）

- 事务 ID 分配：
    读写事务（有 DML 操作）：分配真实的事务 ID（全局递增计数器）
    只读事务（只有 SELECT）：MySQL 8.0 优化不分配真实 ID（内部用临时 ID）
    autocommit=ON 的单条 SELECT：不分配事务 ID

- 事务 ID 的全局单调递增性：
    新事务的 ID > 所有之前事务的 ID
    这是 MVCC 可见性判断依赖的核心前提
```

## DB_TRX_ID 与版本链

```
行的修改历史通过 DB_TRX_ID + DB_ROLL_PTR 形成版本链：

当前行记录（数据页中）：
  DB_TRX_ID = 100  ← 事务100最后修改了此行
  DB_ROLL_PTR → [Undo Log 旧版本1]
  实际数据：balance = 500

[Undo Log 旧版本1]：
  DB_TRX_ID = 80   ← 事务80之前修改了此行
  DB_ROLL_PTR → [Undo Log 旧版本2]
  实际数据：balance = 800

[Undo Log 旧版本2]：
  DB_TRX_ID = 50   ← 事务50最初插入了此行
  DB_ROLL_PTR = NULL（最初版本，无旧版本）
  实际数据：balance = 1000

版本链 trx_id 序列：100 → 80 → 50（从新到旧）
```

## DB_TRX_ID 在可见性判断中的作用

```sql
-- MVCC 可见性判断的核心步骤：
-- Read View 包含：
--   creator_trx_id：当前事务 ID
--   up_limit_id：Read View 创建时最小活跃事务 ID（低水位）
--   low_limit_id：Read View 创建时下一个待分配的事务 ID（高水位）
--   trx_ids：创建时所有活跃（未提交）事务 ID 的列表

-- 对于行记录的 DB_TRX_ID = X，可见性判断：
--
-- 1. X == creator_trx_id：当前事务自己的修改 → 可见
--
-- 2. X < up_limit_id：X 在 Read View 创建前就已提交 → 可见
--
-- 3. X >= low_limit_id：X 在 Read View 创建后才开始 → 不可见
--    → 通过 DB_ROLL_PTR 找上一个版本，递归判断
--
-- 4. up_limit_id <= X < low_limit_id：
--    → X 在 trx_ids 列表中：该事务创建 Read View 时还未提交 → 不可见
--    → X 不在 trx_ids 列表中：该事务在 Read View 创建前已提交 → 可见

-- 演示：
-- Read View 的 up_limit_id=60, low_limit_id=110, trx_ids=[80,95]

-- 最新版本 DB_TRX_ID=100:
--   60 <= 100 < 110，查 trx_ids=[80,95]，100 不在列表中 → 可见！
--   （事务100在 Read View 创建前已提交）

-- 最新版本 DB_TRX_ID=80:
--   60 <= 80 < 110，查 trx_ids=[80,95]，80 在列表中 → 不可见
--   （事务80创建 Read View 时还在活跃，还未提交）
```

## 查看事务 ID

```sql
-- 查看当前事务 ID（需要事务已有 DML 操作）
BEGIN;
UPDATE accounts SET balance = 999 WHERE id = 1;  -- 触发事务 ID 分配
SELECT TRX_ID FROM information_schema.INNODB_TRX
WHERE TRX_MYSQL_THREAD_ID = CONNECTION_ID();

-- 查看所有活跃事务 ID
SELECT trx_id, trx_state, trx_started, trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_id;

-- performance_schema 方式
SELECT THREAD_ID, TRX_ID, STATE, STARTED
FROM performance_schema.events_transactions_current
WHERE STATE = 'ACTIVE';

-- 事务 ID 的大小关系可以反映事务启动的先后顺序（大 ID 启动更晚）
-- 这是排查并发问题时的有用信息
```

## 适用场景

- **MVCC 原理学习**：通过理解 DB_TRX_ID 与 Read View 的交互，掌握 InnoDB 可见性判断的完整过程
- **并发问题排查**：在排查"为什么某事务看不到另一个事务的修改"时，分析 DB_TRX_ID 与 Read View 中 up_limit_id/trx_ids 的关系，确认可见性判断结果

## 常见问题

**只读事务（只有 SELECT）会分配 DB_TRX_ID 吗？**

MySQL 8.0 对只读事务有优化：如果事务只执行快照读（普通 SELECT），InnoDB 不分配真实的事务 ID（不增加全局事务 ID 计数器），而是使用内部的临时标识符（不对外可见）。只有当事务第一次执行 DML（INSERT/UPDATE/DELETE）或 `SELECT ... FOR UPDATE`/`LOCK IN SHARE MODE` 时，才从全局计数器分配真实的事务 ID。这个优化减少了全局计数器的争用，提升了只读事务的性能。

---

## 注意事项

- DB_TRX_ID 是 6 字节，最大值约 281 万亿。在极高并发的系统中（每秒数万个事务），理论上存在耗尽的可能性（需要约 900 年才能耗尽，实际上不构成问题）。
- DB_TRX_ID 是单调递增的，这一属性是 MVCC 可见性算法正确性的基础。如果 DB_TRX_ID 出现非单调（如回绕）的情况，MVCC 可见性判断会出错。InnoDB 通过设计保证 trx_id 永远单调递增（不允许回绕）。

---

## 总结

`DB_TRX_ID` 是 InnoDB 行记录中的 6 字节隐藏列，记录最后修改该行版本的事务 ID，是 MVCC 可见性判断的核心依据。INSERT/UPDATE/DELETE 操作会更新行的 DB_TRX_ID，快照读不更新。Read View 通过比较行的 DB_TRX_ID 与 up_limit_id/low_limit_id/trx_ids，确定该行版本对当前事务是否可见——不可见时沿 DB_ROLL_PTR 查找版本链上的旧版本，直到找到可见版本或版本链末尾。MySQL 8.0 对只读事务不分配真实事务 ID（优化全局计数器争用）。

# 低水位与活跃事务列表

在 InnoDB 的 Read View 结构中，低水位（`m_up_limit_id`）和活跃事务列表（`m_ids`）是两个紧密相关的字段，共同承担快速筛选行版本可见性的职责。理解这两个字段的含义和相互关系，是掌握 MVCC 可见性判断算法的关键。

---

## 低水位（m_up_limit_id）的含义

```
m_up_limit_id（低水位）：
  定义：Read View 创建时，m_ids 列表中最小的事务 ID
  含义：在低水位之前开始且已提交的所有事务，其修改对当前事务可见

可见性判断：
  if DB_TRX_ID < m_up_limit_id：
    该行版本的修改事务在 Read View 创建前就已提交（ID 比最小活跃事务还小）
    → 一定已提交，可见，直接返回此版本

特殊情况：
  如果创建 Read View 时没有活跃事务（m_ids 为空）：
    m_up_limit_id = m_low_limit_id（所有 ID 都视为已提交）
    → 所有 DB_TRX_ID < m_low_limit_id 的版本均可见

示例：
  活跃事务列表 m_ids = [50, 75, 90]
  m_up_limit_id = 50（最小值）
  → DB_TRX_ID=30（< 50）：一定已提交，可见
  → DB_TRX_ID=50（= 50）：活跃事务，不可见
  → DB_TRX_ID=60（50 < 60 < m_low_limit_id）：需要查 m_ids 列表
```

---

## 活跃事务列表（m_ids）的含义

```
m_ids（活跃事务 ID 列表，也称 trx_ids）：
  定义：创建 Read View 时，系统中所有活跃（已开始但尚未提交的读写事务）的 ID 集合
  含义：这些事务的修改对当前 Read View 不可见（它们在 Read View 创建时还未提交）
  排序：按 ID 从小到大排序（支持二分查找，提升查找效率）

可见性判断：
  if m_up_limit_id <= DB_TRX_ID < m_low_limit_id：
    使用二分查找在 m_ids 中查找 DB_TRX_ID：
      找到（在列表中）：该事务创建 Read View 时还未提交 → 不可见
      未找到（不在列表中）：该事务在创建 Read View 之前已提交 → 可见

注意：
  m_ids 中可能不包含当前事务自身（creator_trx_id）
  即使包含，creator_trx_id 的行版本也通过第一个判断（self-check）处理
```

## 低水位与活跃事务列表的协作

```
可见性判断完整流程（伪代码）：

bool is_visible(trx_id X, read_view RV):
    // 快速路径1：自己的修改
    if X == RV.creator_trx_id:
        return true  // 自己修改的行，可见

    // 快速路径2：低水位（最常见路径，位于低水位以下的都已提交）
    if X < RV.m_up_limit_id:
        return true  // 创建 Read View 前已提交，可见

    // 快速路径3：高水位
    if X >= RV.m_low_limit_id:
        return false  // 创建 Read View 后才开始，不可见

    // 精确查找：在低高水位之间
    if X in RV.m_ids (binary search):
        return false  // 创建时还在活跃，未提交，不可见
    else:
        return true   // 不在活跃列表，在 Read View 创建前已提交，可见
```

## 实际案例分析

```
系统场景：
  已提交的事务：trx_id = 10, 20, 30, 40（已提交）
  活跃事务（未提交）：trx_id = 50, 70, 90
  下一个将分配的事务 ID = 100

Read View（当前事务 trx_id = 80）：
  creator_trx_id = 80
  m_ids = [50, 70, 90]         ← 活跃事务列表（不包含80，因为80在活跃列表中也不会用）
  m_up_limit_id = 50           ← 最小活跃事务ID
  m_low_limit_id = 100         ← 下一个将分配的ID

对不同 DB_TRX_ID 的可见性判断：
  DB_TRX_ID = 80（自己）：creator_trx_id 匹配 → 可见
  DB_TRX_ID = 30（< 50）：低水位判断 → 可见
  DB_TRX_ID = 50：50 在 m_ids 中 → 不可见
  DB_TRX_ID = 60：60 在 [50,100) 范围，不在 m_ids [50,70,90] 中 → 可见（60已提交）
  DB_TRX_ID = 70：70 在 m_ids 中 → 不可见
  DB_TRX_ID = 90：90 在 m_ids 中 → 不可见
  DB_TRX_ID = 95：95 在 [50,100) 范围，不在 m_ids 中 → 可见（95在ReadView创建前已提交）
  DB_TRX_ID = 100：>= m_low_limit_id → 不可见
```

## 低水位对 Purge 的影响

```sql
-- 系统中最旧的 Read View 的低水位决定了 Purge 的清理下界

-- Purge 的清理规则：
-- 只清理比"系统中所有活跃 Read View 的最小 m_up_limit_id"更旧的版本
-- 即：任何 Read View 可能引用的版本，都不能被 Purge

-- 举例：
-- Read View A：m_up_limit_id = 50（最旧的 Read View）
-- Read View B：m_up_limit_id = 80

-- Purge 能清理的版本：trx_id < 50 的所有版本（不被任何 Read View 引用）
-- trx_id >= 50 的版本不能清理（Read View A 可能需要访问这些版本）

-- 结论：长事务（持有很旧的低水位的 Read View）会阻止 Purge 清理旧版本，
-- 导致 Undo 表空间膨胀
SELECT @@innodb_purge_threads;  -- Purge 线程数量
SHOW ENGINE INNODB STATUS \G   -- 查看 History list length（未清理的版本数）
```

## 适用场景

- **MVCC 原理验证**：在实验环境中构造特定的活跃事务场景，通过观察不同事务看到的数据版本，验证低水位和活跃事务列表的可见性判断规则
- **长事务监控**：监控系统中最旧的 Read View 的低水位，低水位越旧说明该事务持续时间越长，需要关注其对 Purge 和 Undo 膨胀的影响

## 常见问题

**如果两个活跃事务的 ID 分别为 50 和 200，m_up_limit_id 是多少？m_ids 只包含这两个 ID 吗？**

`m_up_limit_id` = 50（活跃列表中的最小值）。`m_ids` 包含创建 Read View 时所有活跃的读写事务，不只是这两个——如果系统中还有其他活跃事务（如 ID=100, 150），它们也会在 m_ids 中。m_ids 是完整的活跃事务快照。

---

## 注意事项

- `m_up_limit_id`（低水位）是通过快速比较实现的（直接数值比较），而 `m_ids` 的查找是二分查找（O(log n)）。在活跃事务很多的高并发系统中，m_ids 可能包含数百个条目，二分查找仍然高效（7层比较即可覆盖128个事务）。
- 在 MySQL 8.0 中，对 Read View 的创建进行了优化（减少了 trx_sys 全局锁的持有时间），但 m_ids 的复制仍然需要遍历活跃事务链表，高并发下大量活跃事务会影响 Read View 的创建速度。

---

## 总结

`m_up_limit_id`（低水位）是 Read View 中活跃事务列表的最小 ID，用于快速判断：`DB_TRX_ID < low_water_mark` 的版本一定已提交，可见。`m_ids` 是创建 Read View 时所有活跃事务 ID 的完整列表（按序排列），用于在低高水位之间精确判断可见性——在 m_ids 中找到则不可见，找不到则可见。低水位同时决定了 Purge 的清理下界，最旧的 Read View 低水位越旧，需要保留的 Undo 版本越多，Undo 膨胀风险越大。

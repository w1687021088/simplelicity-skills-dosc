# 锁等待与超时 innodb_lock_wait_timeout

当一个事务试图获取已被其他事务持有的锁时，它会进入等待状态，这就是锁等待（Lock Wait）。`innodb_lock_wait_timeout` 参数控制锁等待的最大时间（秒），超过此时间后，等待的事务会报错并回滚，而不是无限等待（可能导致系统假死）。合理配置锁等待超时是保证系统可用性的重要手段。

---

## innodb_lock_wait_timeout 参数

```sql
-- 查看当前锁等待超时设置
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
-- 默认值：50（秒）

-- 动态修改（会话级）
SET SESSION innodb_lock_wait_timeout = 10;  -- 当前会话等待超时10秒

-- 动态修改（全局）
SET GLOBAL innodb_lock_wait_timeout = 30;  -- 全局修改，影响新连接

-- 永久修改（my.cnf）
-- [mysqld]
-- innodb_lock_wait_timeout = 30

-- 查看不同场景的推荐值：
-- OLTP 系统：5~30 秒（快速失败，允许上层重试）
-- 批处理任务：60~300 秒（容忍长时间等待）
-- 交互式查询：10~30 秒（用户可接受的等待时间）
```

## 锁等待超时的报错与处理

```sql
-- 锁等待超时时，InnoDB 报错：
-- ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

-- 重要行为区别（MySQL 8.0+）：
-- 锁等待超时只回滚当前等待的语句，不回滚整个事务！
-- 这与死锁回滚不同（死锁会回滚整个事务）

-- 演示：
BEGIN;
INSERT INTO orders VALUES (1001, 'A', 100);  -- 成功

-- 等待另一个锁（超时后）：
UPDATE accounts SET balance = 0 WHERE id = 1;
-- ERROR 1205：锁等待超时

-- 此时事务仍然活跃（INSERT 未回滚）！
-- 应用层必须显式 ROLLBACK 或 COMMIT
ROLLBACK;  -- 回滚整个事务（包括前面成功的 INSERT）

-- 如果不 ROLLBACK 而是继续执行其他语句，事务仍然持有 INSERT 的锁
-- 应用层处理锁超时的正确方式：
-- 1. 捕获 ERROR 1205
-- 2. 决定是否重试（ROLLBACK + 重新执行整个事务）
-- 3. 或者 ROLLBACK 整个事务，放弃本次操作
```

## 锁等待的监控

```sql
-- 1. 查看当前正在等待锁的事务
SELECT
    r.trx_id AS waiting_trx,
    r.trx_mysql_thread_id AS waiting_thread,
    r.trx_query AS waiting_query,
    b.trx_id AS blocking_trx,
    b.trx_mysql_thread_id AS blocking_thread,
    b.trx_query AS blocking_query,
    TIMESTAMPDIFF(SECOND, r.trx_wait_started, NOW()) AS wait_seconds
FROM information_schema.INNODB_TRX r
JOIN information_schema.INNODB_TRX b
    ON r.trx_wait_started IS NOT NULL
    AND b.trx_id != r.trx_id
WHERE r.trx_state = 'LOCK WAIT'
ORDER BY wait_seconds DESC;

-- 2. 使用 sys schema 查看（更直观）
SELECT * FROM sys.innodb_lock_waits;
-- 显示：等待事务、阻塞事务、被锁的对象、等待时间

-- 3. performance_schema 精确查看
SELECT
    waiting_trx_id,
    waiting_query,
    blocking_trx_id,
    blocking_query,
    wait_age_secs
FROM sys.innodb_lock_waits;
```

## 处理长时间锁等待

```sql
-- 找到阻塞事务并终止：
SELECT b.trx_mysql_thread_id AS blocking_thread_id
FROM information_schema.INNODB_TRX r
JOIN information_schema.INNODB_TRX b
    ON r.trx_state = 'LOCK WAIT'
    AND b.trx_id != r.trx_id
LIMIT 1;

-- 终止阻塞线程（需要 SUPER 权限或 SYSTEM_USER 角色）
KILL CONNECTION <blocking_thread_id>;
-- 或只终止当前语句：
KILL QUERY <blocking_thread_id>;

-- 注意：KILL CONNECTION 强制断开连接并回滚该连接的活跃事务
-- 应优先用于持有锁时间过长、明显是异常的事务
```

## 不同场景的超时策略

| 场景 | 推荐超时（秒）| 说明 |
|------|:-----------:|------|
| Web API 请求 | 5~10 | 接口通常有 10~30 秒超时，提前报错给上层 |
| 后台任务 | 30~60 | 容忍适当等待，但避免无限阻塞 |
| 数据库维护脚本 | 120~300 | 可以等待较长时间，减少人工干预 |
| 批量数据迁移 | 300+ | 大事务可能需要更长等待时间 |

---

## 适用场景

- **OLTP 系统的快速失败**：将超时设置为 5~10 秒，确保锁等待不会让业务请求超时，上层可以捕获锁等待错误并重试
- **数据库维护**：执行 DDL 或数据迁移时，如果操作需要等待长时间持有锁的事务，可以临时增大超时时间，或主动终止阻塞事务

## 常见问题

**锁等待超时后，整个事务会自动回滚吗？**

不会自动回滚整个事务（MySQL 8.0 的默认行为）。`innodb_lock_wait_timeout` 超时后，InnoDB 只回滚当前正在等待的这条语句，但整个事务仍然活跃（之前成功执行的语句不被回滚，持有的锁也不被释放）。这与死锁处理不同（死锁会回滚整个事务）。应用层必须在捕获到 ERROR 1205 后显式决定是 ROLLBACK 还是继续执行，不能假设事务已被自动回滚。

---

## 注意事项

- `innodb_lock_wait_timeout` 只控制 InnoDB 行锁的等待时间，不控制 DDL 的元数据锁（MDL）等待。MDL 等待由 `lock_wait_timeout` 参数（全局/会话级）控制（默认 31536000 秒，即一年！建议设置为 30~60 秒）。两个参数需要同时关注。
- 在主从复制环境中，从库 SQL 线程应用 Relay Log 时，如果遇到行锁等待，受 `innodb_lock_wait_timeout` 控制。如果从库上有长时间运行的只读事务（持有旧 Read View），可能阻塞 SQL 线程应用 DML，需要关注从库的锁等待情况。

---

## 总结

`innodb_lock_wait_timeout` 控制 InnoDB 行锁等待的最大时间（默认 50 秒），超时后报 ERROR 1205 并回滚当前等待的语句（不是整个事务）。应用层必须捕获此错误并显式 ROLLBACK 或重试。生产系统推荐值：OLTP 业务 5~30 秒，批处理 60~300 秒。通过 `sys.innodb_lock_waits` 监控当前锁等待情况，发现长时间阻塞事务后可通过 `KILL CONNECTION` 终止。注意 MDL 等待由单独的 `lock_wait_timeout` 参数控制。

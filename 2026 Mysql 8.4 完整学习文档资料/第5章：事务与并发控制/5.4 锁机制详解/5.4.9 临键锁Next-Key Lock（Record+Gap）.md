# 临键锁 Next-Key Lock（Record + Gap）

Next-Key Lock（临键锁）是 InnoDB 在 REPEATABLE READ（RR）隔离级别下默认使用的行级锁类型，由记录锁（Record Lock）和间隙锁（Gap Lock）组合而成。它锁定的范围是"某个索引记录"加上"该记录之前的间隙"，用区间表示为 `(前一个键值, 当前键值]`（左开右闭）。Next-Key Lock 是 InnoDB 实现 RR 级别防幻读的核心机制。

---

## Next-Key Lock 的范围定义

```
Next-Key Lock 锁定范围：(前一个键值, 当前键值]（左开右闭）

假设表中主键值为：1, 5, 10, 20

每个主键值对应的 Next-Key Lock 范围：
  对 id=1 的 Next-Key Lock：(-∞, 1]
  对 id=5 的 Next-Key Lock：(1, 5]
  对 id=10 的 Next-Key Lock：(5, 10]
  对 id=20 的 Next-Key Lock：(10, 20]
  对 supremum（上界虚拟记录）的 Next-Key Lock：(20, +∞)

含义：
  锁定了记录本身（Record Lock）+ 记录前面的间隙（Gap Lock）
  防止：修改当前记录（Record Lock 的作用）
         在间隙中插入新记录（Gap Lock 的作用）
```

## Next-Key Lock 的典型触发场景

```sql
-- 前提：RR 级别
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 场景1：范围查询 FOR UPDATE
BEGIN;
SELECT * FROM products WHERE id BETWEEN 3 AND 15 FOR UPDATE;
-- 假设表中 id=5, id=10 存在，id=3,4,6,...,9,11,...,15 不存在
-- InnoDB 加锁：
--   (-∞, 5]  Next-Key Lock（包含 id=5 的记录锁 + id≤5 的间隙锁）
--   (5, 10]  Next-Key Lock（包含 id=10 的记录锁 + (5,10) 间隙锁）
--   (10, 15] Next-Key Lock → 优化为 Gap Lock (10, supremum)
-- 结果：(3, +∞) 范围内无法插入，所有范围内现有行被 X 锁定

-- 场景2：非唯一索引的精确查找
CREATE TABLE orders (id INT PRIMARY KEY, user_id INT, INDEX idx_user(user_id));
INSERT INTO orders VALUES (1,100),(5,200),(10,100),(20,300);

BEGIN;
SELECT * FROM orders WHERE user_id = 100 FOR UPDATE;
-- idx_user 是非唯一索引，user_id=100 有两行（id=1, id=10）
-- 对 idx_user 上的 user_id=100 加 Next-Key Lock：
--   锁定 (previous_key, user_id=100] 的范围（包含间隙）
--   防止其他事务插入新的 user_id=100 行（幻读防护）

-- 场景3：主键精确查找（已存在）
BEGIN;
SELECT * FROM products WHERE id = 5 FOR UPDATE;
-- id=5 存在，主键唯一索引精确查找
-- InnoDB 优化：降级为 Record Lock（X, REC_NOT_GAP），不加间隙锁
-- 因为主键唯一，不可能有相同值插入，无需间隙锁
```

## Next-Key Lock 的降级规则

```
InnoDB 在某些情况下会将 Next-Key Lock 降级为 Record Lock 或 Gap Lock：

降级为 Record Lock（REC_NOT_GAP）的情况：
  1. 唯一索引（主键/UNIQUE）的精确查找（记录存在）
  2. 行已存在，不需要间隙保护

降级为 Gap Lock 的情况：
  1. 查询范围的右边界（超过最大值的间隙）
  2. 只有间隙，没有锁定记录的情况

保持 Next-Key Lock 的情况：
  1. 非唯一索引的精确或范围查找
  2. 范围查询中的中间记录（既锁记录又锁间隙）
  3. 主键/唯一索引的范围查找（范围内的记录）
```

## Next-Key Lock 与 performance_schema

```sql
-- 在 performance_schema.data_locks 中查看 Next-Key Lock：
SELECT
    OBJECT_NAME,
    INDEX_NAME,
    LOCK_MODE,
    LOCK_DATA
FROM performance_schema.data_locks
WHERE LOCK_TYPE = 'RECORD';

-- LOCK_MODE 说明：
-- 'X'              → Next-Key Lock（X型，含记录+间隙）
-- 'S'              → Next-Key Lock（S型）
-- 'X,REC_NOT_GAP'  → 纯记录锁（无间隙）
-- 'X,GAP'          → 纯间隙锁（无记录）
-- 'S,REC_NOT_GAP'  → 共享记录锁
-- 'X,INSERT_INTENTION' → 插入意向锁

-- 示例输出：
-- INDEX_NAME=PRIMARY, LOCK_MODE=X, LOCK_DATA=10
-- 表示对 id=10 加 Next-Key Lock，范围为 (5, 10]
```

## Next-Key Lock 防幻读的机制

```sql
-- 场景：事务A查询后，防止事务B插入新行导致幻读

-- 事务A（RR 级别）：
BEGIN;
SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
-- 假设 amount > 100 的行有 id=5(amount=150), id=10(amount=200)
-- InnoDB 加锁：
--   对 id=5, id=10 加 Next-Key Lock（记录锁 + 前间隙锁）
--   对 "supremum"（最大值后的间隙）加 Gap Lock
-- 整体覆盖了 amount > 100 的所有可能位置（现有行和间隙）

-- 事务B（同时）：
INSERT INTO orders VALUES (7, 101, 130.00);
-- amount=130 > 100，会插入 amount > 100 的范围内
-- 等待！被事务A的 Next-Key Lock 间隙部分阻塞

-- 事务A再次查询：
SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
-- 仍然只有 id=5, id=10 两行（事务B的插入被阻塞）
-- 幻读被防止
```

## 适用场景

- **RR 级别的写操作锁分析**：分析 RR 级别下 UPDATE/DELETE/FOR UPDATE 加了哪些 Next-Key Lock，判断加锁范围是否合理，是否可以优化缩小锁范围（如通过索引优化使范围查询变成精确查找）
- **死锁分析**：Next-Key Lock 是 RR 级别死锁的主要来源，通过理解 Next-Key Lock 的范围来分析死锁的形成路径

## 常见问题

**Next-Key Lock 的锁范围是固定的（基于已有记录的间隙），还是基于 WHERE 条件动态确定？**

Next-Key Lock 的范围由两个因素共同决定：WHERE 条件（确定需要锁定哪些记录和间隙）和当前表中索引的实际键值（确定间隙的边界）。例如，`WHERE id BETWEEN 3 AND 15` 在表中只有 id=5, 10 的情况下，锁定的间隙边界由实际存在的键值决定（(1,5], (5,10], (10,15]等），而不仅仅是 WHERE 条件的范围。如果之后有新行插入改变了键值分布，锁的边界仍然是事务加锁时的键值状态。

---

## 注意事项

- Next-Key Lock 的范围通常比应用层预期的更大。例如，`WHERE id = 15`（id=15 不存在）在 RR 级别不只是"什么都不锁"，而是锁住 (10, 20] 范围（id=15 所在的间隙及其右端点 id=20 的记录）。理解这一点对于分析为什么某个 INSERT 会被意外阻塞很重要。
- 通过 `innodb_status_output_locks` 参数或 `performance_schema.data_locks` 可以精确查看当前事务持有的所有 Next-Key Lock 范围，这是排查并发问题的首选工具。

---

## 总结

Next-Key Lock = Record Lock + Gap Lock，锁定范围为 `(前一键值, 当前键值]`（左开右闭）。是 InnoDB RR 级别默认的行级锁类型，防止范围查询的幻读（既锁现有行，又锁间隙阻止插入）。在唯一索引精确查找（记录存在）时降级为纯 Record Lock（优化锁范围）。在非唯一索引或范围查询中保持 Next-Key Lock 形式。`performance_schema.data_locks` 中 `LOCK_MODE=X`（无后缀）表示 Next-Key Lock，`X,REC_NOT_GAP` 表示纯记录锁，`X,GAP` 表示纯间隙锁。

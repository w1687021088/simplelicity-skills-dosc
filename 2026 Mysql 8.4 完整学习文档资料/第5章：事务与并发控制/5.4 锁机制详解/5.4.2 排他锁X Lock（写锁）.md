# 排他锁 X Lock（写锁）

排他锁（Exclusive Lock，简称 X Lock，也称写锁）是 InnoDB 行级锁中限制最严格的类型。持有排他锁的事务既可以读取也可以修改被锁定的行，同时阻止其他事务对该行加任何类型的锁（无论是 S 锁还是 X 锁）。排他锁保证了同一时刻只有一个事务能修改某行，是实现写操作原子性和隔离性的基础。

---

## 基本语法与自动加锁

```sql
-- 显式加排他锁（FOR UPDATE）
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- 隐式加排他锁（DML 自动加 X 锁）
UPDATE accounts SET balance = 900 WHERE id = 1;   -- 自动加 X 锁
DELETE FROM accounts WHERE id = 1;                -- 自动加 X 锁
INSERT INTO accounts VALUES (10, 'new', 500);     -- 对新插入行加 X 锁（Insert Intention + Record Lock）

-- FOR UPDATE 支持 NOWAIT 和 SKIP LOCKED（MySQL 8.0+）
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;        -- 无法加锁则立即报错
SELECT * FROM orders WHERE status = 'pending' FOR UPDATE SKIP LOCKED;  -- 跳过已锁定行
```

## X 锁的兼容性

```sql
-- X 锁与所有锁都不兼容（排他性）
-- X 与 S 不兼容（有 S 锁时 X 需等待；有 X 锁时 S 需等待）
-- X 与 X 不兼容（两个写操作串行化）

-- 演示：
-- 会话1：
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- 对 id=1 加 X 锁（未提交）

-- 会话2（同时）：
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- 等待！id=1 上有 X 锁，FOR UPDATE 需要 X 锁，不兼容 → 阻塞

-- 会话3（同时）：
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 等待！id=1 上有 X 锁，LOCK IN SHARE MODE 需要 S 锁，与 X 不兼容 → 阻塞

-- 普通 SELECT（快照读）不受影响：
BEGIN;
SELECT * FROM accounts WHERE id = 1;
-- 不需要锁，通过 MVCC 读历史版本 → 立即返回（不等待）
```

## X 锁的加锁范围

```sql
-- X 锁的范围取决于 WHERE 条件和索引使用情况：

-- 精确索引查找（点查，加单行 X 锁）
UPDATE accounts SET balance = 900 WHERE id = 1;
-- id 是主键，精确匹配 → 只锁 id=1 这一行

-- 范围条件（加多行 X 锁 + Gap Lock）
UPDATE accounts SET balance = 0 WHERE balance > 1000;
-- 加 balance > 1000 范围内所有行的 X 锁 + 间隙锁（RR 级别）

-- 无索引条件（全表扫描，可能锁全表）
UPDATE accounts SET status = 'active';  -- 无 WHERE，全表加 X 锁
-- 或：
UPDATE accounts SET status = 'active' WHERE name = 'Alice';  -- name 无索引
-- 全表扫描，对每行都加 X 锁（锁升级，实际上接近表锁效果）
-- 极大降低并发性，应该在 name 列建立索引！

-- 检查锁的情况：
SELECT * FROM performance_schema.data_locks;  -- MySQL 8.0+
```

## FOR UPDATE 与 DML 的 X 锁差异

```sql
-- FOR UPDATE：加 X 锁后不立即修改数据，等待后续操作决策
BEGIN;
SELECT * FROM inventory WHERE product_id = 101 FOR UPDATE;
-- 读取库存并加 X 锁
-- 基于读到的值进行业务判断
IF stock > 0 THEN
    UPDATE inventory SET stock = stock - 1 WHERE product_id = 101;
END IF;
COMMIT;

-- DML 自动 X 锁：加锁和修改原子执行
BEGIN;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 101 AND stock > 0;
-- 加 X 锁 + 修改，原子操作
COMMIT;

-- 推荐使用 DML 自动 X 锁（原子 UPDATE），避免 SELECT...FOR UPDATE 的两步操作
```

## 适用场景

- **写操作互斥**：任何 DML 操作自动加 X 锁，保证同一行不会被并发修改（两个 UPDATE 串行化）
- **读后修改**：在读取当前值后需要基于该值进行修改（如扣减库存、账户转账），使用 `FOR UPDATE` 加 X 锁防止其他事务在读取和修改之间修改该行

## 常见问题

**全表扫描会导致全表 X 锁吗？**

不是真正的"表锁"，但效果接近。无索引的 WHERE 条件触发全表扫描时，InnoDB 会对扫描过的每一行都加 X 锁（RR 级别还会加间隙锁）。虽然锁类型仍然是行锁，但锁住了所有行，使其他事务几乎无法并发修改或锁定任何行。这是性能极差且极危险的场景。应通过建立索引、改写查询来避免全表扫描时的 X 锁积累。

---

## 注意事项

- X 锁在整个事务内持有（两阶段锁定协议），不会在 DML 语句执行后立即释放，而是等到事务 COMMIT 或 ROLLBACK 才统一释放。持有 X 锁的时间越长，其他事务被阻塞的时间越长，因此应缩短事务执行时间，减少 X 锁的持有时长。
- `FOR UPDATE` 除了加行 X 锁外，在 RR 级别下还会加 Next-Key Lock（行锁 + 间隙锁），防止其他事务在被查询范围内插入新行（防幻读）。这是 RC 和 RR 级别在加锁行为上的重要区别。

---

## 总结

X Lock（排他锁/写锁）通过 `FOR UPDATE` 显式加锁，或由 UPDATE/DELETE/INSERT DML 自动加锁。X 锁与所有锁不兼容（排他性），持有 X 锁时其他事务无法对同一行加 S 锁或 X 锁（普通快照读不受影响）。X 锁在整个事务内持有，COMMIT 或 ROLLBACK 时统一释放。加锁范围由 WHERE 条件和索引决定：精确索引匹配加单行锁，范围条件加多行锁（+间隙锁），无索引触发全表扫描时对所有行加 X 锁（并发性极差）。

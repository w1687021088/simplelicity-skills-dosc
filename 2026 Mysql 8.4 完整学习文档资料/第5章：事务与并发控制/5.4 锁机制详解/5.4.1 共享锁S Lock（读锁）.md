# 共享锁 S Lock（读锁）

共享锁（Shared Lock，简称 S Lock，也称读锁）是 InnoDB 行级锁的基本类型之一。持有共享锁的事务可以读取被锁定的行，同时允许其他事务也对同一行加共享锁（共享锁之间兼容，多个事务可以同时读取同一行），但阻止其他事务对该行加排他锁（X Lock）进行修改。共享锁体现了"多读单写"的并发控制思想。

---

## 基本语法

```sql
-- 显式加共享锁（快照读 → 当前读+S锁）
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;

-- MySQL 8.0+ 的新语法（等效）
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- 区别：FOR SHARE 支持 NOWAIT 和 SKIP LOCKED 选项
SELECT * FROM accounts WHERE id = 1 FOR SHARE NOWAIT;        -- 无法加锁则立即报错
SELECT * FROM accounts WHERE id = 1 FOR SHARE SKIP LOCKED;   -- 跳过已被锁的行
```

---

## 共享锁的行为特征

```sql
-- S 锁的兼容性：
-- S 与 S 兼容（多个事务可以同时读同一行）
-- S 与 X 不兼容（有 S 锁时不能加 X 锁）

-- 示例：
-- 会话1：
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 对 id=1 加 S 锁

-- 会话2（同时）：
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 也对 id=1 加 S 锁 → 成功！（S 与 S 兼容）

-- 会话3（同时）：
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- 需要对 id=1 加 X 锁 → 等待！（S 存在，X 不能加）
-- 等待会话1和会话2都释放 S 锁后才能继续
```

---

## S 锁的使用场景

```sql
-- 场景1：读取后需要保证数据在操作期间不被修改
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- balance = 1000，加 S 锁
-- 此时其他事务可以读取（S 兼容），但不能修改（X 不兼容）
-- 进行基于 1000 的计算...
-- 如果只是读取不写入，COMMIT 即可
COMMIT;  -- S 锁释放

-- 场景2：外键约束检查
-- 插入子表记录时，InnoDB 会对父表中对应的主键行加 S 锁
-- 防止父表行被删除（删除需要 X 锁，与 S 不兼容）
BEGIN;
INSERT INTO order_items VALUES (NULL, 1001, 101, 2);  -- order_id=1001
-- InnoDB 自动对 orders 表的 id=1001 行加 S 锁（外键约束检查）

-- 场景3：SERIALIZABLE 级别的自动 S 锁
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
SELECT * FROM accounts WHERE id = 1;
-- SERIALIZABLE 级别下，普通 SELECT 自动加 S 锁（相当于 LOCK IN SHARE MODE）
```

## S 锁与 MVCC 快照读的区别

| 对比维度 | 普通 SELECT（快照读）| SELECT...LOCK IN SHARE MODE（S锁） |
|---------|:------------------:|:---------------------------------:|
| 锁机制 | 不加锁 | 加 S 锁 |
| 读取版本 | 历史版本（MVCC）| 最新版本（当前读）|
| 阻塞写入 | 否（MVCC无锁读）| 是（S 锁阻塞 X 锁）|
| 防止幻读 | 快照固定（RR 级别）| 配合 Gap Lock（RR 级别）|
| 适合场景 | 通用读取 | 读后需确保数据稳定性 |

---

## 适用场景

- **一致性读写操作**：先读取账户余额，判断是否满足某业务条件（如积分兑换），用 `LOCK IN SHARE MODE` 确保读取后数据不被修改，然后基于读到的值进行下一步操作
- **外键维护**：InnoDB 内部在插入子记录时自动对父记录加 S 锁，这是 InnoDB 外键约束实现的内部机制

---

## 常见问题

**LOCK IN SHARE MODE 加 S 锁后，当前事务本身能修改该行吗？**

可以，但会升级为 X 锁。如果当前事务在 `LOCK IN SHARE MODE` 加了 S 锁后，又执行了对同一行的 UPDATE，InnoDB 会将 S 锁升级为 X 锁。但如果其他事务也持有该行的 S 锁，锁升级会等待其他 S 锁释放（可能导致死锁）。

---

## 注意事项

- S 锁与 S 锁兼容，但持有 S 锁的两个事务如果都想升级为 X 锁（都执行后续 UPDATE），会产生死锁——两个事务互相等待对方释放 S 锁。解决方案：如果读取后确定需要修改，一开始就使用 `FOR UPDATE`（直接加 X 锁），而不是先 `LOCK IN SHARE MODE` 后再修改。
- `FOR SHARE` 是 MySQL 8.0 引入的 `LOCK IN SHARE MODE` 的新语法，两者功能相同，但 `FOR SHARE` 支持 `NOWAIT` 和 `SKIP LOCKED` 选项，`LOCK IN SHARE MODE` 不支持这两个选项。

---

## 总结

S Lock（共享锁/读锁）通过 `LOCK IN SHARE MODE` 或 `FOR SHARE` 显式加锁，对被锁行进行当前读（读最新版本）并防止其他事务修改（X 锁不兼容）。S 与 S 兼容，允许多个事务并发读取。与 MVCC 快照读的区别：快照读不加锁（读历史版本），S 锁读最新版本并防止并发修改。SERIALIZABLE 级别下普通 SELECT 自动加 S 锁。InnoDB 外键约束检查内部使用 S 锁。

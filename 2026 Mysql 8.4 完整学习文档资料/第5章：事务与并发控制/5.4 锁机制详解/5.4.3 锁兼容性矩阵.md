# 锁兼容性矩阵

锁兼容性矩阵描述了 InnoDB 中不同类型的锁之间能否共存于同一资源（行或表）上。当两种锁类型兼容时，两个事务可以同时持有这两种锁；当不兼容时，后来请求锁的事务必须等待已持有锁的事务释放后才能继续。理解锁兼容性是分析死锁、锁等待和并发问题的基础。

---

## 行级锁兼容性矩阵

```
InnoDB 行级锁类型（按限制程度从低到高）：
  S（Shared Lock，共享锁）
  X（Exclusive Lock，排他锁）
  IS（Intent Shared，意向共享锁）—— 见表级锁
  IX（Intent Exclusive，意向排他锁）—— 见表级锁
```

**行级锁兼容性（行上的两种锁能否共存）**

| 请求锁 \ 已持有锁 | S | X |
|:--------------:|:-:|:-:|
| S | 兼容 | 不兼容 |
| X | 不兼容 | 不兼容 |

```
解读：
  S + S：兼容（多个事务可以同时读同一行）
  S + X：不兼容（有 S 锁时不能写；有 X 锁时不能读（加锁读）)
  X + S：不兼容（有 X 锁时不能加 S 锁）
  X + X：不兼容（同一行只能有一个写者）
```

---

## 表级锁兼容性矩阵

InnoDB 使用意向锁（IS/IX）实现表级和行级锁的协调，具体见 5.4.6。

**表级锁兼容性（请求表锁时与已有表级锁的兼容性）**

| 请求锁 \ 已持有锁 | IS | IX | S | X |
|:--------------:|:--:|:--:|:-:|:-:|
| IS | 兼容 | 兼容 | 兼容 | 不兼容 |
| IX | 兼容 | 兼容 | 不兼容 | 不兼容 |
| S | 兼容 | 不兼容 | 兼容 | 不兼容 |
| X | 不兼容 | 不兼容 | 不兼容 | 不兼容 |

```
IS = 意向共享锁（事务要对行加 S 锁时，先对表加 IS 锁）
IX = 意向排他锁（事务要对行加 X 锁时，先对表加 IX 锁）
S = 表级共享锁（LOCK TABLE t READ）
X = 表级排他锁（LOCK TABLE t WRITE）
```

## 行级锁的完整类型兼容性

InnoDB 行级锁实际分为更细粒度的类型：

| 锁类型 | 说明 | 与 S 兼容 | 与 X 兼容 |
|--------|------|:--------:|:--------:|
| Record Lock（S）| 记录共享锁 | 兼容 | 不兼容 |
| Record Lock（X）| 记录排他锁 | 不兼容 | 不兼容 |
| Gap Lock | 间隙锁（阻止插入）| 兼容 | 兼容 |
| Next-Key Lock（S）| 临键锁（S）| 兼容 | 不兼容 |
| Next-Key Lock（X）| 临键锁（X）| 不兼容 | 不兼容 |
| Insert Intention Lock | 插入意向锁 | 与 Gap Lock 不兼容 | 与 Gap Lock 不兼容 |

## Gap Lock 的特殊兼容性

```sql
-- Gap Lock 之间相互兼容（即使是两个 X 型 Gap Lock）！
-- 这是因为 Gap Lock 的目的是防止插入，不是阻止其他事务的间隙锁

-- 会话1（RR 级别）：
BEGIN;
SELECT * FROM students WHERE id BETWEEN 5 AND 10 FOR UPDATE;
-- 加 Next-Key Lock：包含行锁 + (5,10) 间隙的 Gap Lock

-- 会话2（RR 级别）：
BEGIN;
SELECT * FROM students WHERE id BETWEEN 7 AND 12 FOR UPDATE;
-- 可以加 (7,12) 范围内的 Gap Lock！
-- Gap Lock 之间兼容（两个 Gap Lock 可以共存）

-- 但插入意向锁（Insert Intention Lock）与 Gap Lock 不兼容：
INSERT INTO students VALUES (8, 'New', 90);
-- 等待！插入意向锁（8位于间隙内）与 Gap Lock 不兼容 → 阻塞
```

## 死锁的兼容性根因

```sql
-- 死锁通常发生在两个事务以不同顺序加不兼容的锁时：

-- 事务A：
BEGIN;
SELECT * FROM a WHERE id = 1 FOR UPDATE;  -- 加 id=1 的 X 锁
-- 等待 id=2 的 X 锁（被 B 持有）
SELECT * FROM a WHERE id = 2 FOR UPDATE;

-- 事务B（同时）：
BEGIN;
SELECT * FROM a WHERE id = 2 FOR UPDATE;  -- 加 id=2 的 X 锁
-- 等待 id=1 的 X 锁（被 A 持有）
SELECT * FROM a WHERE id = 1 FOR UPDATE;

-- A 等 B 释放 id=2，B 等 A 释放 id=1 → 循环等待 → 死锁
-- InnoDB 检测到死锁，选择一个事务作为牺牲者回滚
```

## 适用场景

- **分析锁等待**：在排查锁等待问题时，通过锁兼容性矩阵快速判断是哪两种锁之间的冲突
- **设计并发策略**：在设计高并发系统时，根据锁兼容性选择合适的加锁策略（如是否需要 FOR UPDATE，用 S 锁还是 X 锁）

## 常见问题

**为什么 Gap Lock 之间兼容，而 Insert Intention Lock 与 Gap Lock 不兼容？**

Gap Lock 的目的是阻止其他事务在间隙中插入记录，保护范围查询的一致性。两个 Gap Lock 都是"防止插入的屏障"，它们之间不会相互影响，因此兼容。Insert Intention Lock 是插入操作在真正获取行锁之前加的意向锁，表示"想在此间隙插入"。如果间隙上已有 Gap Lock（表示"不允许在此间隙插入"），则 Insert Intention Lock 与 Gap Lock 冲突，插入等待——这正是 Gap Lock 阻止幻读插入的机制。

---

## 注意事项

- 锁兼容性矩阵是分析锁等待和死锁的理论基础，实际应用中还需考虑锁的粒度（行锁还是表锁）、锁的范围（单行锁、间隙锁、临键锁）以及事务的执行顺序。
- InnoDB 行锁是存储引擎层面的锁，而 `LOCK TABLE` 是 MySQL Server 层的表锁。两层锁都需要考虑兼容性，意向锁（IS/IX）就是用来协调这两层之间关系的机制。

---

## 总结

锁兼容性矩阵描述不同锁类型共存的规则。行级锁：S+S 兼容（多读），X 与任何锁不兼容（独占写）。表级锁：IS 和 IX 互相兼容，但 S 和 X 表锁有各自的限制。Gap Lock 之间兼容（间隙锁不排斥其他间隙锁），但 Insert Intention Lock 与 Gap Lock 不兼容（阻止插入进间隙）。死锁的根本原因是两个事务以不同顺序请求不兼容的锁，形成循环等待。

# performance_schema.data_locks 锁视图

在 MySQL 8.0 中，`information_schema.INNODB_LOCKS` 视图被废弃，替换为 `performance_schema.data_locks`。`data_locks` 视图实时显示 InnoDB 当前持有或等待的所有锁（包括行锁和表锁），不论是否有锁等待，是排查锁问题的首选工具。相比旧的 `INNODB_LOCKS`（只在有锁等待时显示），`data_locks` 提供了更完整的实时锁快照。

---

## data_locks 视图结构

```sql
-- 查看 data_locks 的列定义
DESC performance_schema.data_locks;

-- 主要列说明：
-- ENGINE：存储引擎（通常是 INNODB）
-- ENGINE_LOCK_ID：锁的唯一标识符
-- ENGINE_TRANSACTION_ID：持有或等待此锁的事务 ID
-- THREAD_ID：MySQL 线程 ID（关联 performance_schema.threads）
-- EVENT_ID：事件 ID
-- OBJECT_SCHEMA：被锁对象所在的数据库名
-- OBJECT_NAME：被锁对象的表名
-- PARTITION_NAME：分区名（如果表是分区表）
-- INDEX_NAME：被锁定的索引名（RECORD 类型锁）
-- OBJECT_INSTANCE_BEGIN：锁对象的内存地址
-- LOCK_TYPE：锁粒度（TABLE = 表锁/意向锁，RECORD = 行锁）
-- LOCK_MODE：锁类型（IS/IX/S/X/AUTO_INC 等，含后缀标识）
-- LOCK_STATUS：GRANTED（已获得）或 WAITING（等待中）
-- LOCK_DATA：锁定的数据（行锁时为主键值或索引值）
```

## 常用查询

```sql
-- 1. 查看所有当前锁（包括行锁和表锁）
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    INDEX_NAME,
    LOCK_TYPE,
    LOCK_MODE,
    LOCK_STATUS,
    LOCK_DATA,
    ENGINE_TRANSACTION_ID
FROM performance_schema.data_locks
ORDER BY ENGINE_TRANSACTION_ID, LOCK_TYPE, LOCK_STATUS;

-- 2. 只查看等待中的锁（正在等待获取的锁）
SELECT *
FROM performance_schema.data_locks
WHERE LOCK_STATUS = 'WAITING';

-- 3. 按事务分组，查看每个事务持有的锁数量
SELECT
    ENGINE_TRANSACTION_ID,
    COUNT(*) AS lock_count,
    SUM(LOCK_TYPE = 'RECORD') AS row_lock_count,
    SUM(LOCK_TYPE = 'TABLE') AS table_lock_count
FROM performance_schema.data_locks
WHERE LOCK_STATUS = 'GRANTED'
GROUP BY ENGINE_TRANSACTION_ID;

-- 4. 查看特定表上的所有锁
SELECT
    LOCK_TYPE,
    LOCK_MODE,
    LOCK_STATUS,
    LOCK_DATA,
    ENGINE_TRANSACTION_ID
FROM performance_schema.data_locks
WHERE OBJECT_NAME = 'accounts'
ORDER BY LOCK_STATUS, LOCK_DATA;
```

## LOCK_MODE 的完整标识

```
LOCK_MODE 标识说明：

表级锁（LOCK_TYPE = TABLE）：
  IS         → 意向共享锁（准备加行 S 锁）
  IX         → 意向排他锁（准备加行 X 锁）
  S          → 表级共享锁（LOCK TABLE READ）
  X          → 表级排他锁（LOCK TABLE WRITE）
  AUTO_INC   → 自增锁（innodb_autoinc_lock_mode=0/1 的批量 INSERT）

行级锁（LOCK_TYPE = RECORD）：
  S              → 共享 Next-Key Lock（含间隙）
  S,REC_NOT_GAP  → 共享记录锁（不含间隙）
  S,GAP          → 共享间隙锁（只锁间隙）
  X              → 排他 Next-Key Lock（含间隙）
  X,REC_NOT_GAP  → 排他记录锁（不含间隙）
  X,GAP          → 排他间隙锁（只锁间隙）
  X,INSERT_INTENTION → 插入意向锁
  P_S            → 共享谓词锁（空间索引）
  P_X            → 排他谓词锁（空间索引）
```

## LOCK_DATA 的解读

```sql
-- LOCK_DATA 显示锁定的键值（仅对 RECORD 类型有意义）

-- 主键索引的锁：LOCK_DATA = 主键值
-- 示例：LOCK_DATA = '5' 表示锁住 id=5 的行

-- 二级索引的锁：LOCK_DATA = '索引列值, 主键值'
-- 示例：LOCK_DATA = '100, 5' 表示锁住 dept_id=100 且 id=5 的行
-- （二级索引锁同时包含索引列值和对应的主键值）

-- supremum pseudo-record：LOCK_DATA = 'supremum pseudo-record'
-- 表示锁住了最大值之后的间隙（即表的末尾间隙）
-- 常见于 FOR UPDATE 的范围查询超过最大主键值时

-- infimum pseudo-record：LOCK_DATA = NULL（部分版本）
-- 表示表的起始间隙

-- 查询示例（分析具体锁定的行）：
SELECT
    dl.LOCK_MODE,
    dl.LOCK_DATA,
    dl.LOCK_STATUS,
    t.trx_state,
    t.trx_started
FROM performance_schema.data_locks dl
JOIN information_schema.INNODB_TRX t
    ON dl.ENGINE_TRANSACTION_ID = t.trx_id
WHERE dl.OBJECT_NAME = 'orders'
    AND dl.LOCK_TYPE = 'RECORD'
ORDER BY dl.LOCK_STATUS, dl.LOCK_DATA;
```

## data_locks 与 INNODB_LOCKS 的对比

| 特征 | information_schema.INNODB_LOCKS（已废弃）| performance_schema.data_locks（推荐）|
|------|:----------------------------------:|:------------------------------------:|
| MySQL 版本 | 5.x ~ 8.0.1 | 8.0+ |
| 显示条件 | 只在有锁等待时才显示相关锁 | 显示所有当前锁（无论有无等待）|
| 锁信息完整性 | 只显示锁等待涉及的锁 | 完整显示所有持有和等待的锁 |
| 权限要求 | SELECT_CATALOG_ROLE 或 SUPER | performance_schema 权限 |
| 状态 | MySQL 8.0.1 废弃，8.0.x 移除 | 当前推荐使用 |

## 适用场景

- **实时锁分析**：在事务执行过程中，通过 `data_locks` 实时查看当前持有的所有锁（不只是等待的锁），了解事务的锁占用情况，分析是否存在锁范围过大的问题
- **并发问题排查**：系统出现锁等待或性能下降时，通过 `LOCK_STATUS=WAITING` 的锁找到阻塞的查询，再通过 `GRANTED` 的锁找到持有锁的事务

---

## 常见问题

**为什么 data_locks 中同一个事务有很多行锁记录？**

一个事务可能对多个行加锁（如 UPDATE 修改了多行，或 FOR UPDATE 范围查询匹配了多行），每个锁定的行（或间隙）在 data_locks 中都有独立的记录。此外，InnoDB 在加行锁时，同时会在表上加意向锁（IS/IX），因此每个有行级锁操作的事务至少会有一条表级意向锁记录。行锁数量多是事务锁范围大的直观体现，是分析事务是否过度加锁的参考依据。

---

## 注意事项

- `performance_schema.data_locks` 查询本身有一定性能开销（需要扫描锁系统内部结构），在锁数量极多（如数千个活跃事务各持有大量锁）的情况下，频繁查询 `data_locks` 可能对性能有轻微影响。生产环境不要在监控脚本中以秒级频率查询此视图。
- 在 MySQL 8.0.1 之前的版本中，`information_schema.INNODB_LOCKS` 只在有锁等待时才显示相关锁，无法看到持有中但没有冲突的锁。升级到 MySQL 8.0+ 后，推荐完全切换到 `performance_schema.data_locks`。

---

## 总结

`performance_schema.data_locks` 是 MySQL 8.0 引入的完整锁信息视图，替代了旧的 `information_schema.INNODB_LOCKS`，实时显示所有当前持有（GRANTED）和等待（WAITING）的锁（包括表级意向锁和行级锁）。通过 `LOCK_TYPE`（TABLE/RECORD）、`LOCK_MODE`（IS/IX/S/X/GAP/REC_NOT_GAP/INSERT_INTENTION 等）、`LOCK_DATA`（锁定的键值）可以精确了解每个锁的类型、范围和目标行。是排查锁等待、锁范围分析、死锁根因分析的核心工具。

# 插入意向锁 Insert Intention Lock

插入意向锁（Insert Intention Lock）是 InnoDB 在执行 INSERT 操作时，在真正插入行之前加在插入位置所在间隙上的一种特殊间隙锁。它表示事务"打算在此间隙中插入一条记录"。插入意向锁不是真正意义上的"意向锁"（意向锁是表级锁），而是一种特殊的行级间隙锁，专门用于提升并发插入性能。

---

## 插入意向锁的设计动机

```
问题：如果 INSERT 操作要等待 Gap Lock 释放，才能检查是否有冲突，
      那么在同一间隙内的多个 INSERT 会互相阻塞（串行化），并发性很低。

解决：插入意向锁允许多个事务同时声明"我要往这个间隙插入"，
      只要它们插入的位置（键值）不冲突（不是同一行），它们之间就互相兼容，
      可以并发执行。

示例：
  间隙 (5, 10)
  事务A：INSERT id=6 → 加 Insert Intention Lock on (5,10)
  事务B：INSERT id=8 → 加 Insert Intention Lock on (5,10)
  → 两个 Insert Intention Lock 在同一间隙，但目标键值不同 → 互相兼容！
  → A 和 B 可以并发插入，不互相阻塞

  但如果间隙上有 Gap Lock（表示"禁止插入此间隙"）：
  事务C：SELECT...FOR UPDATE（RR级别）加 (5,10) Gap Lock
  事务A：INSERT id=6 → 需要 Insert Intention Lock on (5,10)
  → Insert Intention Lock 与 Gap Lock 不兼容 → 等待！
```

---

## 插入意向锁的兼容性

```
Insert Intention Lock（插入意向锁）的兼容性：

与 Gap Lock 不兼容（Gap Lock 阻止在间隙内插入）
与其他 Insert Intention Lock 兼容（只要插入位置不同）
与 Record Lock 不冲突（Record Lock 锁已有行，不阻止插入新行的间隙锁）

兼容性矩阵（针对同一间隙）：
| 请求 \ 已有 | Gap Lock | Insert Intention Lock |
|:---------:|:--------:|:--------------------:|
| Gap Lock | 兼容 | 兼容 |
| Insert Intention Lock | 不兼容 | 兼容 |
```

---

## 插入意向锁的生命周期

```sql
-- INSERT 的加锁过程：

-- 步骤1：检查插入位置是否有 Gap Lock 或 Next-Key Lock（间隙部分）
--   有 → 加 Insert Intention Lock，等待 Gap Lock 释放
--   无 → 直接进入步骤2

-- 步骤2：检查是否有唯一键冲突
--   有冲突（唯一键重复）→ INSERT 失败，报 Duplicate Key Error

-- 步骤3：对新插入的行加 X Record Lock（行排他锁）
--   防止其他事务在同一行上并发修改

-- 步骤4：完成插入
--   Insert Intention Lock 与 X Record Lock 都在事务提交时释放

-- 注意：Insert Intention Lock 是等待状态下的锁（等 Gap Lock 时加）
-- 如果间隙上没有 Gap Lock，INSERT 可能不会显式加 Insert Intention Lock
-- 实际加锁细节在 performance_schema 可能只显示最终的 X Record Lock
```

## 查看插入意向锁

```sql
-- 有锁等待时，performance_schema 显示 INSERT 的等待锁
SELECT
    OBJECT_NAME,
    INDEX_NAME,
    LOCK_MODE,
    LOCK_DATA,
    LOCK_STATUS
FROM performance_schema.data_locks;

-- 插入意向锁的标识：LOCK_MODE = 'X,INSERT_INTENTION'
-- LOCK_STATUS = 'WAITING'（等待 Gap Lock 释放）

-- 示例场景：
-- 事务A：SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE
--   → 加 (5, 10] Next-Key Lock（含 Gap Lock 部分）

-- 事务B：INSERT INTO t VALUES (7, 'new')
--   → 需要在 (5,10) 间隙加 Insert Intention Lock
--   → 等待！

-- data_locks 输出：
-- 事务A：LOCK_MODE=X, LOCK_STATUS=GRANTED, LOCK_DATA=10（Next-Key Lock）
-- 事务B：LOCK_MODE=X,INSERT_INTENTION, LOCK_STATUS=WAITING, LOCK_DATA=10
```

## 典型的死锁场景

```sql
-- 两个 INSERT 因 Gap Lock 导致的死锁：

-- 初始状态：表中有 id=5, id=10

-- 事务A：SELECT * FROM t WHERE id = 7 FOR UPDATE（RR 级别）
-- → 加 (5, 10] Next-Key Lock（含间隙 (5,10)）

-- 事务B：SELECT * FROM t WHERE id = 8 FOR UPDATE（RR 级别）
-- → 也加 (5, 10] Next-Key Lock（Gap Lock 兼容，两个 Gap Lock 共存）

-- 事务A：INSERT INTO t VALUES (6, 'a')
-- → 需要在 (5,10) 加 Insert Intention Lock → 等待 B 的 Gap Lock

-- 事务B：INSERT INTO t VALUES (9, 'b')
-- → 需要在 (5,10) 加 Insert Intention Lock → 等待 A 的 Gap Lock

-- A 等 B，B 等 A → 死锁！InnoDB 检测并回滚其中一个
-- ERROR 1213: Deadlock found when trying to get lock; try restarting transaction
```

## 适用场景

- **高并发批量插入**：在并发 INSERT 场景下，插入意向锁允许多个事务同时向同一表（或同一间隙的不同位置）插入，而不互相阻塞，提升批量写入性能
- **死锁分析**：INSERT 触发的死锁通常涉及插入意向锁与 Gap Lock 的冲突，通过分析 `LOCK_MODE=X,INSERT_INTENTION` 的等待关系可以找到死锁的触发链

---

## 常见问题

**INSERT 操作一定会加 Insert Intention Lock 吗？**

不一定。如果插入位置所在的间隙没有 Gap Lock 或 Next-Key Lock（即没有任何事务在锁定该间隙），INSERT 可以直接执行，不需要（或不需要等待）Insert Intention Lock。Insert Intention Lock 本质上是 INSERT 在遇到间隙锁阻挡时的等待锁，在没有间隙锁冲突时，INSERT 会直接为新行加 X Record Lock，然后插入。

---

## 注意事项

- 插入意向锁虽然名字有"意向"二字，但它不是意向锁（意向锁是表级锁 IS/IX），而是行级的间隙锁的特殊形式（存储在同一个间隙上）。不要与 IS/IX 意向锁混淆。
- 在高并发写入的系统中，如果频繁出现因 Insert Intention Lock 等待 Gap Lock 的锁等待或死锁，应考虑降低隔离级别为 RC（消除 Gap Lock，从根本上消除 Insert Intention Lock 的等待来源），或通过业务层设计减少范围锁定操作。

---

## 总结

Insert Intention Lock（插入意向锁）是 INSERT 操作在遇到间隙锁（Gap Lock）阻挡时加的等待锁，表示"打算在此间隙插入"。多个 Insert Intention Lock 之间互相兼容（并发插入同一间隙的不同位置不阻塞），但与 Gap Lock 不兼容（Gap Lock 阻止所有在该间隙的插入）。是 InnoDB 提升并发 INSERT 性能的机制，也是 RR 级别死锁的常见来源之一（Gap Lock + Insert Intention Lock 的循环等待）。在 `performance_schema.data_locks` 中以 `LOCK_MODE=X,INSERT_INTENTION` 标识。

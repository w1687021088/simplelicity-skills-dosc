# 意向锁作用与表级锁冲突

意向锁（Intention Lock）是 InnoDB 设计的一种"公告牌"机制，解决行级锁与表级锁之间高效兼容性检测的问题。当事务在行上加锁时，先在表上登记意向锁（IS 或 IX），这样需要加表级锁的操作只需检查表上的意向锁，而无需扫描每一行，大幅提高了锁系统的效率。

---

## 意向锁解决的核心问题

```
场景：表 accounts 有 1000 万行，以下两类操作并发：
  操作A：事务对 id=1 加 X 行锁（UPDATE）
  操作B：管理员执行 LOCK TABLE accounts WRITE（需要表级 X 锁）

不使用意向锁时：
  操作B 要加表级 X 锁，必须确认表中没有任何行锁
  → 需要扫描全部 1000 万行，检查每行是否有行锁
  → 每次加表锁时 O(N) 的行扫描代价 → 不可接受

使用意向锁时：
  操作A 加 X 行锁前，先在 accounts 表上加 IX 锁
  操作B 加表级 X 锁时，只检查 accounts 表上有没有 IS/IX 锁
  → 发现有 IX 锁 → 等待 → O(1) 的表级意向锁检查
  → 不需要扫描行
```

---

## 意向锁与表级锁的完整冲突关系

| 请求表锁 \ 已有表意向锁 | IS（行有S锁）| IX（行有X锁）| S表锁 | X表锁 |
|:-------------------:|:-----------:|:-----------:|:----:|:----:|
| IS（行加S锁）| 兼容 | 兼容 | 兼容 | 不兼容 |
| IX（行加X锁）| 兼容 | 兼容 | 不兼容 | 不兼容 |
| S 表锁（READ）| 兼容 | 不兼容 | 兼容 | 不兼容 |
| X 表锁（WRITE）| 不兼容 | 不兼容 | 不兼容 | 不兼容 |

## 意向锁与 LOCK TABLE 的冲突示例

```sql
-- 示例1：DML 事务（IX锁）阻塞 LOCK TABLE WRITE

-- 会话1：普通 UPDATE 事务（IX 锁）
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- accounts 表：IX 锁（意向排他锁）
-- id=1 行：X 锁（行排他锁）

-- 会话2：尝试加表级写锁
LOCK TABLE accounts WRITE;
-- 需要表级 X 锁，与 IX 不兼容 → 等待！

-- 会话1提交：
COMMIT;  -- IX 锁和 X 行锁释放
-- 会话2的 LOCK TABLE WRITE 成功获取

-- 示例2：SELECT...LOCK IN SHARE MODE（IS锁）阻塞 LOCK TABLE WRITE

-- 会话1：
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- accounts 表：IS 锁
-- id=1 行：S 锁

-- 会话2：
LOCK TABLE accounts WRITE;
-- X 表锁与 IS 不兼容 → 等待！

-- 会话2：
LOCK TABLE accounts READ;
-- S 表锁与 IS 兼容 → 可以成功！
-- 但 S 表锁不影响其他事务的 LOCK IN SHARE MODE（两个 IS 兼容）

-- 示例3：IX + S表锁 不兼容
-- 会话1：UPDATE（IX 锁）
-- 会话2：LOCK TABLE accounts READ → 等待（S 表锁与 IX 不兼容）
```

## 意向锁对 DDL 的影响

```sql
-- DDL 操作（ALTER TABLE）通常需要 MDL 写锁（Metadata Lock）
-- MDL 写锁等待所有活跃事务（包括持有 IS/IX 的事务）完成

-- 示例：ALTER TABLE 等待长事务
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;  -- 持有 IX 锁

-- 另一会话：
ALTER TABLE accounts ADD COLUMN remark VARCHAR(200);
-- ALTER 需要 MDL 写锁，等待所有持有 MDL 读锁的事务（DML 自动持有 MDL 读锁）
-- → 等待 UPDATE 事务提交

-- 这就是为什么长事务会阻塞 DDL 操作

-- 检查 MDL 等待：
SELECT * FROM performance_schema.metadata_locks;
SELECT * FROM sys.schema_table_lock_waits;  -- sys 视图，更易读
```

## 意向锁的内存表示

```
InnoDB 中意向锁的实现：
  意向锁是表级锁，存储在锁系统的表锁结构中
  每个表有一个锁对象（table lock object）
  表锁对象上记录：IS 锁计数 和 IX 锁计数
  
  加 IS 锁：IS 锁计数 +1
  释放 IS 锁：IS 锁计数 -1
  
  检查 LOCK TABLE WRITE 是否兼容：
    检查 IS 计数 > 0 或 IX 计数 > 0？
    是 → 等待（不兼容）
    否 → 加表锁成功

内存开销：极小（仅几个计数器）
  这是意向锁方案与"无意向锁逐行扫描"相比性能优势巨大的原因
```

## 适用场景

- **分析 ALTER TABLE 阻塞**：当 `ALTER TABLE` 长时间等待时，查看 `sys.schema_table_lock_waits` 和 `performance_schema.metadata_locks`，找到持有 IX/IS 锁（即有未提交 DML）的事务，这些事务阻塞了 DDL 的 MDL 写锁
- **理解 LOCK TABLE 的等待条件**：在需要使用 `LOCK TABLE` 的场景（如数据导出、维护操作），理解哪类操作会与 `LOCK TABLE WRITE`/`READ` 冲突

## 常见问题

**意向锁和 MDL（元数据锁）是同一个东西吗？**

不是。MDL（Metadata Lock）是 MySQL Server 层的锁，保护表的元数据（结构定义），任何 DML/DDL 操作都会自动获取相应级别的 MDL。意向锁（IS/IX）是 InnoDB 存储引擎层的锁，协调行级锁与 `LOCK TABLE` 操作。两者都会影响 DDL 操作：DDL 需要 MDL 写锁（被未提交 DML 的 MDL 读锁阻塞）；`LOCK TABLE` 需要通过意向锁检查（被 IX/IS 锁阻塞）。它们在不同层面工作，共同保证了操作的一致性。

---

## 注意事项

- 意向锁是 InnoDB 内部自动管理的，应用层代码完全透明，无需（也无法）手动控制意向锁的加减。
- 在生产系统中，应避免长时间持有 IX 锁的长事务，因为它们会阻塞 DDL 操作（通过 MDL 等待），而 DDL 的 MDL 写锁等待反过来会阻塞所有后续的读写操作（MDL 读锁请求在写锁等待队列之后排队），导致雪崩效应。

---

## 总结

意向锁（IS/IX）是 InnoDB 在行级锁与表级锁之间架设的"公告牌"层，实现了 O(1) 的表锁兼容性检查（替代 O(N) 的逐行扫描）。加行 S 锁时表上加 IS 锁，加行 X 锁时表上加 IX 锁。IS+IS、IS+IX、IX+IX 均兼容（允许 DML 并发）；IS/IX 与表级 X 锁不兼容（`LOCK TABLE WRITE` 需等待所有意向锁释放）；IX 与表级 S 锁也不兼容（`LOCK TABLE READ` 需等待 IX 锁释放）。意向锁内存开销极小，自动管理，应用层无感知。

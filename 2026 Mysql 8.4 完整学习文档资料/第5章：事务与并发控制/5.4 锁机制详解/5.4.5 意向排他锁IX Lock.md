# 意向排他锁 IX Lock

意向排他锁（Intent Exclusive Lock，简称 IX Lock）是 InnoDB 表级意向锁的一种，由事务在对某行加排他锁（X Lock）之前，自动在该行所在的表上加 IX 锁。IX 锁与 IS 锁构成意向锁体系，共同解决行级锁与表级锁之间的高效兼容性检测问题。IX 锁是生产系统中最常见的意向锁，因为绝大多数 DML 操作（UPDATE/DELETE/INSERT/FOR UPDATE）都会产生 IX 锁。

---

## IX Lock 的自动加锁

```sql
-- IX 锁由 InnoDB 内部自动管理，以下操作会触发 IX 锁：

-- 1. SELECT ... FOR UPDATE
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- InnoDB 自动：对 accounts 表加 IX 锁，对 id=1 行加 X 锁

-- 2. UPDATE（自动加 X 行锁，同时在表上加 IX 锁）
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- InnoDB 自动：对 accounts 表加 IX 锁，对 id=1 行加 X 锁

-- 3. DELETE
BEGIN;
DELETE FROM accounts WHERE id = 1;
-- InnoDB 自动：对 accounts 表加 IX 锁，对 id=1 行加 X 锁

-- 4. INSERT
BEGIN;
INSERT INTO accounts VALUES (10, 'new', 500);
-- InnoDB 自动：对 accounts 表加 IX 锁，新行加 X 锁（插入后）

-- IX 锁与事务绑定：事务提交/回滚时，IX 锁和所有行锁一起释放
```

---

## IX Lock 的兼容性

```
IX 锁在表级的兼容性：

IX + IS = 兼容（可以同时有行读锁和行写锁，行级别自行解决冲突）
IX + IX = 兼容（两个写事务可以同时操作同一表的不同行）
IX + S 表锁 = 不兼容（表级 S 锁不允许行级写操作）
IX + X 表锁 = 不兼容（X 表锁要求完全独占）

IX + IX 兼容的含义：
  事务A 更新 id=1（IX 锁 + X 行锁）
  事务B 更新 id=2（IX 锁 + X 行锁）
  两个事务在表上都持有 IX 锁 → 兼容
  id=1 和 id=2 是不同行 → 行级 X 锁不冲突
  两个事务可以并发执行（互不阻塞）
```

## IX Lock 与 LOCK TABLE 的冲突

```sql
-- IX 锁阻止 LOCK TABLE WRITE 和 LOCK TABLE READ

-- 会话1（DML 事务，持有 IX 锁）：
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- accounts 表上有 IX 锁，id=1 行有 X 锁

-- 会话2（尝试加表锁）：
LOCK TABLE accounts WRITE;
-- 等待！accounts 上有 IX 锁，X 表锁与 IX 锁不兼容 → 阻塞

LOCK TABLE accounts READ;
-- 也等待！S 表锁与 IX 锁不兼容 → 阻塞

-- 会话1：
COMMIT;
-- IX 锁释放，会话2的 LOCK TABLE 才能成功

-- 注意：日常的 DML 操作（SELECT/INSERT/UPDATE/DELETE）
-- 不需要加表级 S/X 锁，因此不会被 IX 锁阻塞
-- IX 锁仅影响 LOCK TABLE 这类需要表级独占锁的操作
```

## 查看 IX 锁

```sql
-- 查看当前所有锁（包括意向锁）
SELECT
    OBJECT_NAME AS table_name,
    LOCK_TYPE,
    LOCK_MODE,
    LOCK_STATUS,
    ENGINE_TRANSACTION_ID
FROM performance_schema.data_locks
WHERE LOCK_MODE IN ('IS', 'IX')
ORDER BY ENGINE_TRANSACTION_ID;

-- 典型输出示例（一个 UPDATE 事务）：
-- table_name=accounts, LOCK_TYPE=TABLE, LOCK_MODE=IX, STATUS=GRANTED
-- （同时还有）
-- table_name=accounts, LOCK_TYPE=RECORD, LOCK_MODE=X,REC_NOT_GAP, STATUS=GRANTED
```

## 适用场景

- **排查 LOCK TABLE 等待**：当 `LOCK TABLE t WRITE` 长时间等待时，通过查询意向锁找到阻塞它的事务（持有 IX 锁的事务），分析哪些 DML 事务在阻止表级锁操作
- **理解 ALTER TABLE 的锁行为**：部分 `ALTER TABLE` 操作需要表级 MDL（元数据锁），在操作之前会等待所有活跃事务（持有 IX 锁的事务）完成，理解这一点有助于评估 ALTER 的影响

## 常见问题

**IX + IX 兼容，那意向排他锁有什么意义？**

IX + IX 兼容的作用是：允许多个事务同时对同一表的不同行执行写操作（并发 DML）。同一行上的 X 锁之间是不兼容的（行级别），因此两个事务更新同一行时仍然会阻塞。IX + IX 兼容主要体现在：允许多个事务同时持有这个"我在该表上有写操作"的公告，而不是让写操作串行化。意向锁本身不阻止 DML 并发，只阻止与 DML 并发的表级锁（`LOCK TABLE`）。

---

## 注意事项

- 在 MySQL 8.0 中，`ALTER TABLE` 对 InnoDB 表使用 Online DDL（在线 DDL），大多数情况下不需要独占表锁（`LOCK=NONE`）。但某些 ALTER 操作需要等待活跃事务提交（等待 MDL 写锁，不是 IX 锁）。IX 锁与 MDL 是不同的锁系统，MDL 是 MySQL Server 层的元数据锁，IX 是 InnoDB 存储引擎层的意向锁。
- 高并发 DML 系统中，表上会同时存在大量 IX 锁（每个写事务各一个），这是正常现象，不影响 DML 并发性。IX 锁的内存开销很小（每个事务只有一个表级意向锁对象）。

---

## 总结

IX Lock（意向排他锁）在事务执行 DML（UPDATE/DELETE/INSERT）或 `SELECT...FOR UPDATE` 时自动加到表上，表示"该表上有行被加了 X 锁"。IX + IX 兼容（允许并发 DML），但 IX 与 S 表锁和 X 表锁不兼容（阻止 `LOCK TABLE`）。IX 锁是生产系统中最常见的意向锁，几乎所有写操作都会产生。通过 `performance_schema.data_locks` 可以查看当前所有意向锁状态。IX 锁与事务绑定，事务结束时释放。

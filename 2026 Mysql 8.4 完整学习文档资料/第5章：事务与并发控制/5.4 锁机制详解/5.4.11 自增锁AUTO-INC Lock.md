# 自增锁 AUTO-INC Lock

AUTO-INC Lock（自增锁）是 InnoDB 为处理 `AUTO_INCREMENT` 列并发插入而设计的一种特殊表级锁。当多个事务同时向含有 `AUTO_INCREMENT` 列的表插入数据时，需要协调自增值的分配，保证每条记录获得唯一且单调递增的 ID。AUTO-INC Lock 的行为由 `innodb_autoinc_lock_mode` 参数控制，不同模式在性能和 ID 连续性之间有不同的权衡。

---

## innodb_autoinc_lock_mode 三种模式

```
innodb_autoinc_lock_mode = 0（传统模式，traditional）：
  每次 INSERT 语句在整个语句执行期间持有 AUTO-INC 表级锁
  语句结束后才释放（不是事务结束）
  优点：ID 严格按语句执行顺序分配，Binlog STATEMENT 格式安全
  缺点：并发 INSERT 互相阻塞（同一时刻只有一个 INSERT 能执行）

innodb_autoinc_lock_mode = 1（连续模式，consecutive）：
  MySQL 8.0 之前的默认值
  对"简单 INSERT"（预知行数）：用轻量级互斥量（mutex）分配 ID，不加 AUTO-INC 锁
  对"批量 INSERT"（行数不确定）：仍加 AUTO-INC 表级锁
  简单 INSERT 并发性较高，批量 INSERT 串行化

innodb_autoinc_lock_mode = 2（交错模式，interleaved）：
  MySQL 8.0 的默认值
  所有 INSERT 都用轻量级 mutex 分配 ID，完全不加 AUTO-INC 表级锁
  最高并发性，ID 可能不连续（多个并发 INSERT 交错分配）
  不适合 STATEMENT 格式 Binlog（会导致主从数据不一致）
  适合 ROW 格式 Binlog（MySQL 8.0 默认）
```

---

## 三种模式对比

| 模式 | 值 | 简单INSERT | 批量INSERT | ID连续性 | 并发性 | Binlog兼容性 |
|------|----|-----------|-----------|---------|--------|------------|
| 传统 | 0 | 表锁 | 表锁 | 严格连续 | 最低 | STATEMENT 安全 |
| 连续 | 1 | mutex | 表锁 | 批量内连续 | 中 | STATEMENT 安全 |
| 交错 | 2 | mutex | mutex | 可能不连续 | 最高 | 需要 ROW/MIXED |

## 自增值的分配行为

```sql
-- 查看和修改 autoinc_lock_mode
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';
-- MySQL 8.0 默认：2（交错模式）

-- 查看表的当前自增值
SHOW TABLE STATUS LIKE 'orders' \G
-- Auto_increment 列显示下一个将分配的自增值

-- 自增值的跳跃（mode=2 下）：
-- 事务A 和 事务B 并发 INSERT：
-- 系统分配：A 得 id=1，B 得 id=2，A 得 id=3（如果 A INSERT 两行）
-- 但如果 A 插入失败并回滚：id=1 和 id=3 被废弃
-- 最终表中只有 id=2，自增值已经跳到 4
-- → 自增值不会因事务回滚而回退（设计上不回退，避免加锁）

-- 检查 MySQL 8.0 中 AUTO_INCREMENT 持久化（重启后自增值不重置）
-- MySQL 8.0 修复了 5.7 中重启后自增值重置的 Bug
-- 通过将自增值写入 redo log，重启后能恢复正确的自增值
```

## AUTO-INC 表级锁的查看

```sql
-- 在 innodb_autoinc_lock_mode=0 或 1（批量INSERT）时，可以观察到 AUTO-INC 锁

SHOW ENGINE INNODB STATUS \G
-- 在输出中查找 AUTO-INC 锁相关信息

-- performance_schema 查看（有等待时）：
SELECT
    OBJECT_NAME,
    LOCK_TYPE,
    LOCK_MODE   -- 'AUTO_INC' 表示自增锁
FROM performance_schema.data_locks
WHERE LOCK_MODE = 'AUTO_INC';
```

## 批量 INSERT 的自增锁影响

```sql
-- innodb_autoinc_lock_mode=1 时，批量 INSERT 持有 AUTO-INC 表锁

-- 批量 INSERT（行数不确定）：
INSERT INTO logs SELECT * FROM old_logs WHERE date > '2024-01-01';
-- 行数不确定（依赖 SELECT 结果），加 AUTO-INC 表级锁
-- 锁持有到 INSERT 语句完成（不是事务结束）
-- 期间：其他任何向 logs 表的 INSERT 都被阻塞

-- 多值 INSERT（行数确定，属于"简单 INSERT"）：
INSERT INTO logs VALUES (NULL, 'event1'), (NULL, 'event2'), (NULL, 'event3');
-- 行数明确（3行），mode=1 或 2 下使用 mutex 而非 AUTO-INC 锁
-- 其他事务的 INSERT 不被阻塞

-- LOAD DATA INFILE：也属于行数不确定，在 mode=1 时加 AUTO-INC 锁
```

## 适用场景

- **高并发写入优化**：确认 `innodb_autoinc_lock_mode=2`（MySQL 8.0 默认），配合 ROW 格式 Binlog，充分利用并发 INSERT 性能，避免 AUTO-INC 表锁成为写入瓶颈
- **从 5.7 迁移到 8.0**：注意 MySQL 8.0 将默认值从 1 改为 2，如果 Binlog 格式是 STATEMENT，需要将 `innodb_autoinc_lock_mode` 改回 1 或将 Binlog 格式改为 ROW

## 常见问题

**AUTO_INCREMENT 列的值会因事务回滚而"收回"吗？**

不会。InnoDB 的自增值分配是不可回退的——一旦分配了某个自增值（无论事务是否提交），该值就被"消耗"了，不会因事务回滚而重新变为可用。这是设计上的权衡：如果允许回退自增值，在并发场景下需要额外的锁或协调机制。因此，高并发插入或回滚操作会导致自增 ID 不连续（出现"空洞"），这是 InnoDB 的正常行为，业务逻辑不应依赖自增 ID 的严格连续性。

---

## 注意事项

- 如果业务要求自增 ID 严格连续（如票据编号、单据流水号），不能使用 `AUTO_INCREMENT`（并发和回滚会导致空洞）。应使用独立的序列号生成服务（如数据库序列号表+乐观锁，或 Redis INCR，或专门的号段服务）。
- `innodb_autoinc_lock_mode` 参数在 MySQL 8.0 中只能通过配置文件 `my.cnf` 设置（不可动态修改），修改后需重启 MySQL 生效。

---

## 总结

AUTO-INC Lock 是 InnoDB 为协调 `AUTO_INCREMENT` 列并发插入而设计的锁机制，行为由 `innodb_autoinc_lock_mode` 控制（0=传统表锁，1=连续/混合，2=交错/无表锁）。MySQL 8.0 默认 mode=2（最高并发，配合 ROW 格式 Binlog）。自增值一旦分配不因事务回滚回收，因此高并发写入会产生 ID 空洞，业务不应依赖 ID 连续性。MySQL 8.0 修复了自增值在重启后重置的 Bug（通过 Redo Log 持久化自增值）。

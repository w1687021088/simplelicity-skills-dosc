# 8.4 优化：自增锁轻量级实现

MySQL 8.4 LTS 延续了 MySQL 8.0 在自增锁方面的优化路线，以 `innodb_autoinc_lock_mode=2`（交错模式）作为默认设置，将原来的表级 AUTO-INC Lock 替换为轻量级的互斥量（mutex），消除了传统自增锁对并发 INSERT 的阻塞问题。结合 ROW 格式 Binlog（MySQL 8.0 起的默认设置），这一组合在高并发写入场景下显著优于旧版本的表级自增锁方案。

---

## 轻量级实现的核心机制

```
传统 AUTO-INC Lock（mode=0/1 的部分场景）：
  锁粒度：表级锁（AUTO_INC 锁类型）
  锁持有时间：整个 INSERT 语句期间（行数不确定的批量 INSERT）
  并发效果：同一时刻只有一个 INSERT 语句能分配自增值
  → 批量 INSERT 串行化，并发性低

轻量级 mutex 方案（mode=2，MySQL 8.0+ 默认）：
  锁粒度：互斥量（内存中的 mutex，不是 InnoDB 行/表锁系统）
  锁持有时间：只在分配自增值的瞬间持有（微秒级别）
  并发效果：多个 INSERT 几乎可以同时分配自增值
  → 并发 INSERT 吞吐量大幅提升

核心区别：
  AUTO-INC 表锁是 InnoDB 锁系统管理的锁（可见于 data_locks 视图）
  mutex 是 InnoDB 内存中的短暂互斥锁（不进入锁系统，对外不可见）
```

## MySQL 8.4 的自增相关默认配置

```sql
-- MySQL 8.4 的自增相关默认值：
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';
-- 默认值：2（交错模式，轻量级 mutex）

SHOW VARIABLES LIKE 'binlog_format';
-- 默认值：ROW（行格式 Binlog，与 mode=2 兼容）

-- 这两个默认值的组合是推荐的生产配置：
-- mode=2：消除 AUTO-INC 表锁，最大化并发 INSERT 性能
-- ROW Binlog：记录行级别的变更，不依赖 SQL 语句的执行顺序
--   → 即使并发 INSERT 导致 ID 不连续/交错，ROW Binlog 仍然能正确复制

-- MySQL 8.4 额外的自增持久化保证：
-- 自增值持久化到 Redo Log（修复了 MySQL 5.7 的重启后自增值重置 Bug）
-- 重启后自增值从 Redo Log 恢复，不会"回到表中最大值+1"
```

## 轻量级实现的 INSERT 流程

```sql
-- mode=2 下的并发 INSERT 执行流程：

-- 事务A 和 事务B 同时执行 INSERT：

-- 步骤1：各自获取 mutex（持有约 1 微秒）
--   A 获取 mutex → 分配 id=1 → 释放 mutex
--   B 获取 mutex → 分配 id=2 → 释放 mutex
--   （几乎同时，不互相长时间阻塞）

-- 步骤2：各自使用分配到的 ID 插入数据
--   A：INSERT 行（id=1, ...）
--   B：INSERT 行（id=2, ...）
--   （可以真正并发执行，只在行锁上竞争）

-- 对比 mode=0 的流程：
-- A 获取 AUTO-INC 表级锁
-- A INSERT 语句完整执行（可能是数秒）
-- A 释放 AUTO-INC 表级锁
-- B 获取 AUTO-INC 表级锁
-- B INSERT 语句完整执行
-- → 完全串行，吞吐量是 mode=2 的几分之一甚至更低
```

| 配置 | 每秒 INSERT（示意，单表大量并发）|
|------|:--------------------------------:|
| mode=0（传统）| 低（AUTO-INC 表锁串行化）|
| mode=1（连续）| 简单 INSERT 中等，批量 INSERT 低 |
| mode=2（交错，8.4默认）| 高（mutex 微秒级）|

## 模式 2 的 ID 不连续性说明

```sql
-- mode=2 下，ID 分配可能不连续（存在空洞）

-- 场景1：事务回滚
BEGIN;
INSERT INTO orders VALUES (NULL, 'order1');  -- 分配 id=101
ROLLBACK;
-- id=101 被废弃，下次 INSERT 从 102 开始
-- 表中 id 序列：...100, 102, 103...（101 缺失）

-- 场景2：多个并发 INSERT 交错
-- 事务A 分配 id=101, 103（插入2行）
-- 事务B 分配 id=102, 104（插入2行）
-- 最终顺序可能是：102, 101, 104, 103（按提交顺序）
-- 或：101, 102, 103, 104（按 ID 顺序）

-- 批量 INSERT 预分配（mode=2 特有行为）：
-- INSERT INTO t SELECT ... （行数不确定）
-- InnoDB 会预分配一批 ID（每次 2 倍增加：1, 2, 4, 8...）
-- 如果实际插入行数少于预分配数量，多余的 ID 被废弃
-- 这会导致 ID 出现较大跳跃
INSERT INTO t SELECT * FROM source WHERE status='active';
-- 预分配：id=100~115（16个），实际插入 10 行
-- 下一次 INSERT 从 id=116 开始（101~115 有6个空洞）
```

## 适用场景

- **高并发写入系统**：互联网应用、消息队列写入、日志记录系统等高频 INSERT 场景，mode=2 消除了 AUTO-INC 表锁，充分发挥多核 CPU 的并发优势
- **主从复制**：MySQL 8.4 默认 ROW 格式 Binlog + mode=2，主从复制不依赖 INSERT 语句的执行顺序，ID 不连续在从库也可以正确复制

## 常见问题

**从 MySQL 5.7（默认 mode=1）升级到 8.4（默认 mode=2）需要注意什么？**

主要关注两点：1) Binlog 格式：如果仍然使用 STATEMENT 格式 Binlog，mode=2 会导致主从数据不一致（必须改为 ROW 或 MIXED 格式）；2) 业务逻辑：如果业务代码依赖 `AUTO_INCREMENT` ID 的连续性（例如将 ID 差值作为业务逻辑的一部分），mode=2 的预分配和并发分配可能导致更多空洞。MySQL 8.0/8.4 默认 ROW 格式，因此如果配置与默认值一致，升级通常无需调整。

---

## 注意事项

- `innodb_autoinc_lock_mode` 是静态参数，只能在配置文件中设置（`[mysqld]` 段），不能在运行时动态修改，修改后需要重启 MySQL 才能生效。
- MySQL 8.4 的 ROW 格式 Binlog + mode=2 是推荐的生产配置，无需修改这两个默认值。只有在有特殊需求（如严格的 ID 连续性要求或使用 STATEMENT 格式 Binlog）时才需要调整 `innodb_autoinc_lock_mode`。

## 总结

MySQL 8.4 默认 `innodb_autoinc_lock_mode=2`（交错模式），使用轻量级内存 mutex（微秒级持有）替代传统的 AUTO-INC 表级锁，消除了并发 INSERT 时的自增锁阻塞，大幅提升高并发写入性能。配合 MySQL 8.0+ 默认的 ROW 格式 Binlog，mode=2 在主从复制环境下完全安全。代价是 ID 可能不连续（事务回滚、预分配批次、并发交错分配均会产生 ID 空洞），业务层不能假设 ID 严格连续。MySQL 8.4 还通过 Redo Log 持久化自增值，修复了 5.7 中重启后自增值可能重置的问题。

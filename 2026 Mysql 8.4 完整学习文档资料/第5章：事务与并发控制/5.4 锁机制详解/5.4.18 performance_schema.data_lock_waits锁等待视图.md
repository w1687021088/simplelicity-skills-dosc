# performance_schema.data_lock_waits 锁等待视图

`performance_schema.data_lock_waits` 是 MySQL 8.0 引入的锁等待关系视图，替代了旧的 `information_schema.INNODB_LOCK_WAITS`。该视图清晰地展示了哪个事务（等待方）在等待哪个事务（阻塞方）释放哪把锁，是分析锁等待关系、查找阻塞根源的直接工具。与 `data_locks` 配合使用，可以完整还原当前系统的锁等待全貌。

---

## data_lock_waits 视图结构

```sql
-- 查看 data_lock_waits 的列定义
DESC performance_schema.data_lock_waits;

-- 主要列说明：
-- ENGINE：存储引擎（INNODB）
-- REQUESTING_ENGINE_LOCK_ID：正在等待（请求中）的锁 ID
-- REQUESTING_ENGINE_TRANSACTION_ID：等待方的事务 ID
-- REQUESTING_THREAD_ID：等待方的 MySQL 线程 ID
-- REQUESTING_EVENT_ID：等待方的事件 ID
-- REQUESTING_OBJECT_INSTANCE_BEGIN：等待锁对象的内存地址

-- BLOCKING_ENGINE_LOCK_ID：阻塞方（被等待）的锁 ID
-- BLOCKING_ENGINE_TRANSACTION_ID：阻塞方的事务 ID
-- BLOCKING_THREAD_ID：阻塞方的 MySQL 线程 ID
-- BLOCKING_EVENT_ID：阻塞方的事件 ID
-- BLOCKING_OBJECT_INSTANCE_BEGIN：阻塞锁对象的内存地址
```

---

## 常用查询

```sql
-- 1. 查看当前所有锁等待关系（谁在等谁）
SELECT
    REQUESTING_ENGINE_TRANSACTION_ID AS waiting_trx,
    BLOCKING_ENGINE_TRANSACTION_ID   AS blocking_trx
FROM performance_schema.data_lock_waits;

-- 2. 联合 data_locks 获取等待和阻塞锁的完整信息
SELECT
    dlw.REQUESTING_ENGINE_TRANSACTION_ID AS waiting_trx,
    dl_wait.LOCK_MODE AS waiting_lock_mode,
    dl_wait.OBJECT_NAME AS waiting_table,
    dl_wait.LOCK_DATA AS waiting_lock_data,
    dlw.BLOCKING_ENGINE_TRANSACTION_ID  AS blocking_trx,
    dl_block.LOCK_MODE AS blocking_lock_mode
FROM performance_schema.data_lock_waits dlw
JOIN performance_schema.data_locks dl_wait
    ON dlw.REQUESTING_ENGINE_LOCK_ID = dl_wait.ENGINE_LOCK_ID
JOIN performance_schema.data_locks dl_block
    ON dlw.BLOCKING_ENGINE_LOCK_ID   = dl_block.ENGINE_LOCK_ID;

-- 3. 联合 INNODB_TRX 获取事务详细信息（包括 SQL 和等待时间）
SELECT
    r.trx_id         AS waiting_trx_id,
    r.trx_query      AS waiting_query,
    r.trx_wait_started,
    TIMESTAMPDIFF(SECOND, r.trx_wait_started, NOW()) AS wait_sec,
    b.trx_id         AS blocking_trx_id,
    b.trx_query      AS blocking_query,
    b.trx_started    AS blocking_trx_started,
    b.trx_mysql_thread_id AS blocking_thread
FROM performance_schema.data_lock_waits dlw
JOIN information_schema.INNODB_TRX r ON dlw.REQUESTING_ENGINE_TRANSACTION_ID = r.trx_id
JOIN information_schema.INNODB_TRX b ON dlw.BLOCKING_ENGINE_TRANSACTION_ID   = b.trx_id
ORDER BY wait_sec DESC;
```

## sys.innodb_lock_waits（推荐的封装视图）

```sql
-- sys schema 提供了更易读的封装视图，推荐优先使用
SELECT * FROM sys.innodb_lock_waits \G

-- 输出字段更直观：
-- wait_started：等待开始时间
-- wait_age：等待时长（如 00:00:05）
-- wait_age_secs：等待秒数
-- locked_table：被锁定的表（schema.table 格式）
-- locked_index：被锁定的索引
-- locked_type：锁类型（RECORD/TABLE）
-- waiting_trx_id：等待方事务 ID
-- waiting_trx_started：等待方事务开始时间
-- waiting_trx_age：等待方事务持续时长
-- waiting_trx_rows_locked：等待方持有的行锁数
-- waiting_trx_rows_modified：等待方修改的行数
-- waiting_pid：等待方的 processlist ID
-- waiting_query：等待方正在执行的 SQL
-- waiting_lock_id：等待方的锁 ID
-- waiting_lock_mode：等待的锁模式
-- blocking_trx_id：阻塞方事务 ID
-- blocking_pid：阻塞方的 processlist ID
-- blocking_query：阻塞方正在执行的 SQL（可能为 NULL，如果阻塞方不在执行 SQL）
-- blocking_lock_id：阻塞方的锁 ID
-- blocking_lock_mode：阻塞方持有的锁模式
-- blocking_trx_started：阻塞方事务开始时间
-- blocking_trx_age：阻塞方事务持续时长
-- blocking_trx_rows_locked：阻塞方持有的行锁数
-- blocking_trx_rows_modified：阻塞方修改的行数
-- sql_kill_blocking_query：终止阻塞方当前 SQL 的命令（KILL QUERY N）
-- sql_kill_blocking_connection：终止阻塞方连接的命令（KILL N）
```

## 通过视图快速解决锁等待

```sql
-- 步骤1：查看当前锁等待
SELECT
    wait_age_secs,
    locked_table,
    locked_type,
    waiting_query,
    blocking_query,
    sql_kill_blocking_connection
FROM sys.innodb_lock_waits
ORDER BY wait_age_secs DESC;

-- 步骤2：分析阻塞原因
-- 如果 blocking_query 为 NULL，说明阻塞方事务没有在执行 SQL
-- （事务已经执行完某个操作但还未提交，长时间持有锁）

-- 步骤3：根据情况决定处理方式
-- 方案A：等待阻塞方自然完成
-- 方案B：联系阻塞方用户，让其 COMMIT 或 ROLLBACK
-- 方案C：紧急情况下，执行 sys.innodb_lock_waits 中的 sql_kill_blocking_connection
KILL <blocking_pid>;  -- 强制终止阻塞连接，阻塞事务自动回滚
```

## 与旧版视图的对比

| 特征 | information_schema.INNODB_LOCK_WAITS（已废弃）| performance_schema.data_lock_waits（推荐）|
|------|:-----------------------------------------:|:-----------------------------------------:|
| MySQL 版本 | 5.x ~ 8.0.1 | 8.0+ |
| 等待方信息 | waiting_trx_id, waiting_lock_id | REQUESTING_ENGINE_TRANSACTION_ID 等 |
| 阻塞方信息 | blocking_trx_id, blocking_lock_id | BLOCKING_ENGINE_TRANSACTION_ID 等 |
| 包含 SQL 信息 | 否（需联合 INNODB_TRX）| 否（需联合 data_locks 和 INNODB_TRX）|
| 推荐替代 | — | sys.innodb_lock_waits（封装视图）|
| 状态 | 8.0.1 废弃 | 当前推荐 |

## 适用场景

- **生产故障快速定位**：系统接口超时告警时，第一时间执行 `SELECT * FROM sys.innodb_lock_waits` 确认是否有锁等待，找到阻塞源头，并获取 `sql_kill_blocking_connection` 命令以便紧急处理
- **日常监控**：在监控系统中定期检查 `data_lock_waits` 是否有等待中的锁，当等待时间超过阈值时触发告警

## 常见问题

**`sys.innodb_lock_waits` 中 blocking_query 显示 NULL 是什么意思？**

`blocking_query` 为 NULL 表示阻塞方事务当前没有正在执行的 SQL 语句。这通常意味着该事务已经完成了某个写操作（如 UPDATE），但还没有 COMMIT 或 ROLLBACK，处于"空闲但持有锁"的状态。这种情况在以下场景中常见：应用代码在事务中执行了 DML 后，还在进行网络调用或其他非数据库操作；或者连接池中的连接在执行了事务后没有正确提交，导致事务长时间"挂起"持有锁。

## 注意事项

- `data_lock_waits` 是 InnoDB 专用视图（ENGINE 列为 INNODB），不包含 MyISAM 等其他存储引擎的锁信息（尽管 MyISAM 也可能有表级锁等待，但 MyISAM 在 MySQL 8.0 中极少使用）。
- `data_lock_waits` 只显示当前正在发生的等待，历史锁等待不会保留在此视图中。如果需要分析历史锁等待模式，应通过 `performance_schema.events_waits_history` 或外部监控工具（如 PMM、Percona Monitoring）收集历史数据。

---

## 总结

`performance_schema.data_lock_waits` 显示当前所有锁等待关系（谁在等谁），替代了 MySQL 8.0 废弃的 `information_schema.INNODB_LOCK_WAITS`。与 `data_locks` 和 `INNODB_TRX` 联合查询可以获取等待方 SQL、阻塞方 SQL、等待时长等完整信息。实际使用中，`sys.innodb_lock_waits` 是更便捷的封装视图，直接提供等待时长、被锁表、双方 SQL、以及终止阻塞方的 `KILL` 命令，是生产环境锁等待排查的首选工具。

# 意向共享锁 IS Lock

意向共享锁（Intent Shared Lock，简称 IS Lock）是 InnoDB 表级锁的一种，由事务在对某行加共享锁（S Lock）之前，自动在该行所在的表上加 IS 锁。意向锁是 InnoDB 内部自动管理的，应用层无法手动控制。它的存在是为了高效地协调行级锁与表级锁之间的冲突检测，避免在加表锁时逐行扫描以确认是否有行锁存在。

---

## 意向锁存在的原因

```
问题背景：
  InnoDB 支持行级锁（S/X Row Lock）和表级锁（LOCK TABLE READ/WRITE）
  当需要对表加表级共享锁（LOCK TABLE t READ）时：
    必须确认表中没有任何行被其他事务加了 X 行锁
  
  如果没有意向锁：
    加表锁前必须遍历表中每一行，检查是否有行锁
    数百万行的表，遍历代价极高 → 不可接受
  
  有意向锁的解决方案：
    事务加行锁前，先在表上加意向锁（IS 或 IX）
    加表锁时，只需检查表上的意向锁状态，无需遍历行
    → 从 O(N行) 的检查降低为 O(1) 的意向锁检查

IS Lock（意向共享锁）：
  事务想对某行加 S 锁时，先对表加 IS 锁
  表示：该表中有行被加了 S 锁（或即将加 S 锁）
```

---

## IS Lock 的自动加锁

```sql
-- IS 锁由 InnoDB 内部自动管理，以下操作会触发 IS 锁：

-- 1. SELECT ... LOCK IN SHARE MODE / FOR SHARE
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- InnoDB 自动：对 accounts 表加 IS 锁，对 id=1 行加 S 锁

-- 2. SERIALIZABLE 级别的普通 SELECT（自动加 S 锁）
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
SELECT * FROM accounts;
-- 普通 SELECT 自动加 S 锁 → IS 锁自动加在表上

-- 3. 外键约束检查中的父表 S 锁
INSERT INTO order_items VALUES (NULL, 1001, 101, 1);
-- 检查 orders.id=1001 是否存在 → 对 orders 表加 IS 锁，对 id=1001 行加 S 锁

-- 注意：普通的 MVCC 快照读（不加 S/X 锁的 SELECT）不会加 IS 锁
SELECT * FROM accounts;  -- 普通快照读，不加任何锁
```

## IS 锁与其他锁的兼容性

```
IS 锁在表级的兼容性（与其他表级锁的兼容性）：

IS + IS = 兼容（多个事务各自持有行 S 锁）
IS + IX = 兼容（S 行锁和 X 行锁可以在同一表上共存，但具体行上可能冲突）
IS + S 表锁 = 兼容（表级 S 锁允许行级读锁）
IS + X 表锁 = 不兼容（X 表锁要求表上没有任何锁定操作）

意义：
  LOCK TABLE t WRITE（X 表锁）会等待所有 IS 锁释放
  → 所有持有行 S 锁的事务提交/回滚后，X 表锁才能获取
  确保表级锁与行级锁的语义一致性
```

## 查看意向锁

```sql
-- MySQL 8.0+ 通过 performance_schema 查看当前锁
SELECT
    ENGINE_LOCK_ID,
    ENGINE_TRANSACTION_ID,
    OBJECT_SCHEMA,
    OBJECT_NAME,
    LOCK_TYPE,      -- TABLE 或 RECORD
    LOCK_MODE,      -- IS, IX, S, X, GAP, REC_NOT_GAP 等
    LOCK_STATUS,    -- GRANTED 或 WAITING
    LOCK_DATA
FROM performance_schema.data_locks;

-- 示例输出（当事务执行 SELECT...LOCK IN SHARE MODE 时）：
-- LOCK_TYPE=TABLE, LOCK_MODE=IS  → 表上的意向共享锁
-- LOCK_TYPE=RECORD, LOCK_MODE=S  → 行上的共享锁

-- MySQL 8.0.1 之前的查询方式（已废弃）：
SELECT * FROM information_schema.INNODB_LOCKS;  -- 仅在有锁等待时才显示
```

## 适用场景

- **理解 LOCK TABLE 的阻塞原因**：当 `LOCK TABLE t WRITE` 需要等待时，通过查询 `performance_schema.data_locks` 可以看到哪些事务持有 IS 或 IX 锁（行锁），这些锁阻止了表级 X 锁的获取
- **理解外键约束的内部机制**：INSERT 子表时触发对父表的 IS 锁（父主键行 S 锁），理解这一机制有助于排查因外键约束引起的锁等待

---

## 常见问题

**意向锁会阻塞普通的 SELECT（快照读）吗？**

不会。意向锁（IS/IX）是表级锁，用于协调行级锁与表级锁（`LOCK TABLE`）之间的冲突。普通快照读（MVCC 读）不加任何锁，也不需要与意向锁进行兼容性检查。只有显式的 `LOCK TABLE READ`（需要表级 S 锁）或 `LOCK TABLE WRITE`（需要表级 X 锁）才需要等待意向锁。日常的 SELECT/INSERT/UPDATE/DELETE 操作不涉及表级 S/X 锁，因此不受意向锁直接影响（但行锁之间仍然有影响）。

---

## 注意事项

- 意向锁（IS/IX）是 InnoDB 全自动管理的，应用层代码不需要（也无法）手动加减意向锁。了解意向锁的目的是帮助理解锁系统的工作原理，特别是在排查 `LOCK TABLE` 等待问题时。
- 意向锁只存在于表级别，没有行级别的意向锁。行级别直接使用 S/X Lock，表级别使用 IS/IX Lock 作为行锁的"公告牌"，告知其他需要加表锁的操作：该表上有行被锁定。

---

## 总结

IS Lock（意向共享锁）是 InnoDB 自动管理的表级意向锁，在对行加 S 锁之前自动加到表上。其存在目的是高效协调行级锁与表级锁的冲突检测——加表级锁时只需检查表上的意向锁状态（O(1)），而无需逐行扫描（O(N)）。IS 锁与 IS/IX 锁兼容，与表级 X 锁不兼容（`LOCK TABLE WRITE` 会等待所有 IS 锁释放）。应用层无需手动管理意向锁，了解它主要用于理解锁等待原因和 InnoDB 内部锁协调机制。

# 死锁检测 Deadlock Detection

死锁（Deadlock）是指两个或多个事务互相持有对方所需要的锁，形成循环等待，所有相关事务都无法继续推进的状态。InnoDB 内置了自动死锁检测机制：通过维护事务的等待关系图（Wait-for Graph），实时检测循环依赖，一旦发现死锁，立即选择代价较小的事务作为"牺牲者"（victim）回滚，让其他事务继续执行。

---

## 死锁的形成条件

```
死锁的四个必要条件（Coffman 条件）：
1. 互斥（Mutual Exclusion）：资源（锁）不能共享（X 锁排他）
2. 持有并等待（Hold and Wait）：事务持有锁同时等待其他锁
3. 不可剥夺（No Preemption）：锁不能被强制从持有者手中取走
4. 循环等待（Circular Wait）：事务形成环形的等待链

InnoDB 无法消除前三个条件（这是锁的基本特性），
通过等待图检测循环等待（第4条），发现后打破循环。
```

## 典型死锁场景

```sql
-- 场景1：不同顺序加锁（最常见）
-- 事务A：
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 持有 id=1 的 X 锁
-- 等待 id=2 的 X 锁

-- 事务B（同时）：
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;   -- 持有 id=2 的 X 锁
-- 等待 id=1 的 X 锁

-- A 等 B 释放 id=2，B 等 A 释放 id=1 → 死锁

-- 场景2：Gap Lock + Insert Intention Lock
-- 事务A：SELECT ... WHERE id = 7 FOR UPDATE（RR级别，加 (5,10) Gap Lock）
-- 事务B：SELECT ... WHERE id = 8 FOR UPDATE（RR级别，加 (5,10) Gap Lock，兼容）
-- 事务A：INSERT id=9（需要 Insert Intention Lock on (5,10)，被 B 的 Gap Lock 阻塞）
-- 事务B：INSERT id=6（需要 Insert Intention Lock on (5,10)，被 A 的 Gap Lock 阻塞）
-- → 死锁

-- 场景3：S锁升级为X锁
-- 事务A：SELECT ... LOCK IN SHARE MODE（持有 S 锁）
-- 事务B：SELECT ... LOCK IN SHARE MODE（也持有 S 锁，兼容）
-- 事务A：UPDATE（需要将 S 锁升级为 X 锁，等 B 的 S 锁）
-- 事务B：UPDATE（需要将 S 锁升级为 X 锁，等 A 的 S 锁）
-- → 死锁
```

## InnoDB 死锁检测机制

```
Wait-for Graph（等待关系图）：
  有向图，节点是事务，边是等待关系
  A → B 表示事务 A 在等待事务 B 释放某个锁
  
  检测算法：深度优先搜索（DFS），检查是否有环
  检测时机：每当事务进入锁等待时，InnoDB 检查是否形成环
  
  死锁发现后的处理：
    选择"代价最小"的事务作为 victim（牺牲者）
    代价计算依据：trx_weight = 事务修改的行数 + 持有的锁数
    回滚 weight 最小的事务（代价最小）
    报错：ERROR 1213: Deadlock found when trying to get lock;
           try restarting transaction
```

## innodb_deadlock_detect 参数

```sql
-- MySQL 8.0 引入了关闭死锁检测的选项：
SHOW VARIABLES LIKE 'innodb_deadlock_detect';
-- 默认：ON（开启死锁检测）

-- 关闭死锁检测（高并发场景的性能优化）：
SET GLOBAL innodb_deadlock_detect = OFF;

-- 关闭死锁检测的适用条件：
-- 确保应用层加锁顺序一致（业务设计上避免循环等待）
-- 通过 innodb_lock_wait_timeout 依赖超时机制处理死锁
-- 高并发下死锁检测本身有性能开销（每次等待都扫描等待图）

-- 关闭后的风险：
-- 真正出现死锁时，会一直等待直到 innodb_lock_wait_timeout 超时
-- 超时后只回滚当前等待语句（不是整个事务），需要应用层处理
-- 仅在能确保无循环等待的系统中考虑关闭
```

## 查看死锁信息

```sql
-- 方法1：SHOW ENGINE INNODB STATUS（查看最后一次死锁）
SHOW ENGINE INNODB STATUS \G
-- 在输出中查找 "LATEST DETECTED DEADLOCK" 部分
-- 包含：
-- 死锁发生时间
-- 涉及的两个事务
-- 每个事务持有的锁
-- 每个事务等待的锁
-- 被回滚的事务（victim）

-- 方法2：performance_schema 死锁事件
-- MySQL 8.0 可以通过 performance_schema.events_errors_summary_by_thread_by_error
-- 查看 ER_LOCK_DEADLOCK（Error 1213）的频率

-- 方法3：开启死锁日志
SET GLOBAL innodb_print_all_deadlocks = ON;
-- 将每次死锁的详细信息写入错误日志（error log）
-- 适合排查频繁死锁的场景

-- 方法4：监控死锁计数
SELECT * FROM information_schema.INNODB_METRICS
WHERE NAME = 'lock_deadlocks';
-- 需要先开启：SET GLOBAL innodb_monitor_enable = 'lock_deadlocks';
```

## 死锁预防策略

```sql
-- 策略1：固定加锁顺序（最有效）
-- 始终以相同的顺序访问多个表/行（如按 id 从小到大更新）
-- 避免：A 先锁 id=1 再锁 id=2，B 先锁 id=2 再锁 id=1

-- 策略2：使用原子操作代替读-改-写
-- 避免：SELECT...FOR UPDATE + UPDATE（持锁时间长）
-- 优先：直接 UPDATE SET col = col + N（原子操作）

-- 策略3：降低隔离级别（消除 Gap Lock）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- Gap Lock 消失，Insert Intention Lock 相关死锁减少

-- 策略4：缩短事务执行时间
-- 将耗时操作（网络请求、复杂计算）移到事务外
-- 减少持锁时间，降低死锁概率

-- 策略5：批量操作拆分为小批次
-- 大批量 UPDATE 一次锁多行 → 与其他事务的冲突面大
-- 小批次多次 UPDATE → 每次锁的行少，冲突面小

-- 应对死锁的应用层策略：
-- 捕获 ERROR 1213，实现自动重试逻辑（指数退避）
```

## 适用场景

- **并发写入系统的稳定性**：在高并发 OLTP 系统中，合理的死锁检测（`innodb_deadlock_detect=ON`）和死锁日志（`innodb_print_all_deadlocks=ON`）是保证系统稳定性和问题排查的基础
- **超高并发优化**：在已经通过业务设计消除循环等待风险的系统中（如热点行更新序列化处理），可以考虑关闭死锁检测，减少检测开销

## 常见问题

**死锁回滚是回滚整个事务还是只回滚当前语句？**

死锁回滚整个事务（与锁等待超时不同）。InnoDB 检测到死锁后，选择代价最小的事务作为牺牲者，将该事务的所有修改完整回滚（所有锁释放），然后让另一个事务继续执行。应用层需要捕获 ERROR 1213，并对整个业务操作进行重试（不只是重试最后一条语句）。

---

## 注意事项

- 频繁死锁通常是业务设计或索引设计问题的信号。如果系统每分钟出现数十次死锁，需要分析死锁日志（`SHOW ENGINE INNODB STATUS` 或 error log），找到触发死锁的 SQL 和加锁顺序，从根本上修复。
- `SHOW ENGINE INNODB STATUS` 只保留最后一次死锁信息，如果死锁发生频繁，旧死锁信息会被覆盖。开启 `innodb_print_all_deadlocks=ON` 将死锁写入 error log，可以获取完整的死锁历史记录。

---

## 总结

InnoDB 通过等待关系图（Wait-for Graph）的 DFS 算法实时检测死锁（循环等待），发现后选择代价最小的事务回滚整个事务（释放所有锁），让其他事务继续。死锁报 ERROR 1213，应用层需捕获并实现重试。`innodb_deadlock_detect=ON`（默认）；高并发系统可关闭（依赖超时）但需业务层保证无循环等待。通过 `SHOW ENGINE INNODB STATUS` 查看最后一次死锁，通过 `innodb_print_all_deadlocks=ON` 记录所有死锁到 error log。预防死锁：固定加锁顺序、使用原子更新、降低隔离级别、缩短事务时间。

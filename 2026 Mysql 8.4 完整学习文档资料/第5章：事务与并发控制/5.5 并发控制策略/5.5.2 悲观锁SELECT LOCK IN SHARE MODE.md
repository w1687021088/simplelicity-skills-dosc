# 悲观锁 SELECT LOCK IN SHARE MODE

`SELECT ... LOCK IN SHARE MODE`（或 MySQL 8.0+ 的等效语法 `SELECT ... FOR SHARE`）是 InnoDB 悲观锁的共享读锁形式。它读取匹配行的最新版本（当前读），并为这些行加共享锁（S Lock），允许其他事务同时读取（加 S 锁），但阻止其他事务修改（阻止 X 锁）。与 `FOR UPDATE` 相比，`LOCK IN SHARE MODE` 允许并发读，是读保护而不是写独占。

---

## 基本语法

```sql
-- 传统语法（MySQL 5.x ~ 8.x 均支持）
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;

-- MySQL 8.0+ 新语法（等效，支持更多选项）
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

-- FOR SHARE 的扩展选项（LOCK IN SHARE MODE 不支持）
SELECT * FROM accounts WHERE id = 1 FOR SHARE NOWAIT;        -- 无法加锁立即报错
SELECT * FROM accounts WHERE id = 1 FOR SHARE SKIP LOCKED;   -- 跳过已锁行

-- 多表查询
SELECT a.balance, o.total
FROM accounts a
JOIN orders o ON a.id = o.user_id
WHERE a.id = 100
FOR SHARE;
-- 对 accounts 和 orders 的相关行都加 S 锁
```

---

## LOCK IN SHARE MODE 的行为特征

```sql
-- S 锁行为：
-- 多个事务可以同时持有同一行的 S 锁（读读不阻塞）
-- S 锁阻止其他事务加 X 锁（阻止修改）

-- 演示：
-- 会话1：
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- id=1 加 S 锁，读到 balance=1000

-- 会话2（同时）：
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 也加 S 锁 → 成功！S+S 兼容，可以同时读取
-- 读到 balance=1000

-- 会话3（同时）：
BEGIN;
UPDATE accounts SET balance = 900 WHERE id = 1;
-- 需要 X 锁，与 S 锁不兼容 → 等待！

-- 会话1提交后（S 锁释放）：
COMMIT;
-- 会话2的 S 锁仍然持有（两个独立事务）
-- 会话3仍在等待会话2的 S 锁
```

---

## 与 FOR UPDATE 的对比

| 对比维度 | FOR UPDATE（X 锁）| LOCK IN SHARE MODE（S 锁）|
|---------|:----------------:|:------------------------:|
| 锁类型 | 排他锁（X Lock）| 共享锁（S Lock）|
| 允许其他 S 锁 | 否 | 是 |
| 允许其他 X 锁 | 否 | 否 |
| 适合场景 | 读后修改数据 | 读后只读，保证不被改 |
| 是否阻塞读操作 | 阻塞加锁读（S/X），不阻塞快照读 | 不阻塞 S 锁，阻塞 X 锁 |
| 死锁风险 | 较高（X+X 易死锁）| 较高（S升X时易死锁）|

## S 锁升级为 X 锁的死锁风险

```sql
-- 危险场景：两个事务都用 LOCK IN SHARE MODE，再试图修改

-- 事务A：
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 加 S 锁，读到 1000

-- 事务B（同时）：
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 也加 S 锁（兼容，成功），读到 1000

-- 事务A 尝试修改（S 升 X）：
UPDATE accounts SET balance = 900 WHERE id = 1;
-- 需要 X 锁，但 B 持有 S 锁 → 等待 B 释放 S 锁

-- 事务B 也尝试修改（S 升 X）：
UPDATE accounts SET balance = 800 WHERE id = 1;
-- 需要 X 锁，但 A 持有 S 锁 → 等待 A 释放 S 锁

-- A 等 B，B 等 A → 死锁！

-- 解决：如果读后确定要修改，直接使用 FOR UPDATE（X 锁），而不是 LOCK IN SHARE MODE
```

## 典型使用场景

```sql
-- 场景1：读取后只做计算，不需要修改（读保护）
BEGIN;
SELECT balance FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- balance = 1000
-- 此时其他事务无法将 balance 改为其他值
-- 基于 1000 进行计算（如手续费计算），计算结果写入其他表
INSERT INTO fee_records VALUES (1, 1000 * 0.001);
COMMIT;
-- S 锁释放
-- 适用：需要"计算期间余额不变"，但不需要修改账户本身

-- 场景2：外键约束验证（InnoDB 内部使用）
-- 插入子表时，InnoDB 自动对父表主键加 S 锁
INSERT INTO order_items VALUES (NULL, 1001, 101, 2);
-- 自动：对 orders.id=1001 加 S 锁（外键检查）
-- 防止父记录在检查期间被删除

-- 场景3：生成一致性报表（读快照 + S 锁）
-- 如果需要多表联查且保证数据在查询期间不被修改：
START TRANSACTION WITH CONSISTENT SNAPSHOT;  -- RR 级别快照
SELECT a.balance, SUM(o.total) 
FROM accounts a
JOIN orders o ON a.id = o.user_id
WHERE a.id = 100
FOR SHARE;  -- 防止查询期间 accounts 和 orders 被修改
COMMIT;
```

---

## 适用场景

- **读后不写的关键数据读取**：需要读取某行数据并在读取期间保证数据不被其他事务修改，但不需要对该行写入的场景（如账户余额校验、权限检查）
- **外键约束检查**：InnoDB 在 INSERT 子表时自动对父表相关行加 S 锁，这是 LOCK IN SHARE MODE 的内部应用场景

---

## 常见问题

**`LOCK IN SHARE MODE` 和 `FOR SHARE` 功能完全相同吗？**

两者加的锁相同（S Lock，当前读），结果等效。主要区别是语法：`LOCK IN SHARE MODE` 是 MySQL 的传统语法（5.x 起支持），`FOR SHARE` 是 MySQL 8.0 引入的标准 SQL 风格新语法（与 `FOR UPDATE` 对称），并额外支持 `NOWAIT` 和 `SKIP LOCKED` 选项。新代码建议使用 `FOR SHARE`（更简洁，支持更多选项）；旧代码中的 `LOCK IN SHARE MODE` 无需修改。

---

## 注意事项

- `LOCK IN SHARE MODE` / `FOR SHARE` 最大的使用陷阱是"读后修改导致死锁"——两个事务都加 S 锁后都试图升级为 X 锁，导致循环等待。如果确定读后需要修改，应直接使用 `FOR UPDATE`（X 锁），从一开始就独占该行，避免锁升级和潜在死锁。
- 与 `FOR UPDATE` 相同，`LOCK IN SHARE MODE` 读取的是当前最新版本（当前读），不是 MVCC 的历史版本。即使在 RR 级别，`LOCK IN SHARE MODE` 也会读最新数据（不受 Read View 限制）。

---

## 总结

`SELECT ... LOCK IN SHARE MODE`（等效 `FOR SHARE`）为匹配行加 S 共享锁，执行当前读（最新版本）。S 锁允许并发读取（S+S 兼容），阻止并发修改（S+X 不兼容）。适合"读后不修改该行但需保证数据不变"的场景，以及 InnoDB 外键约束检查。最大风险是两事务都 S 锁读后再修改会导致锁升级死锁——如果读后确定修改，应使用 `FOR UPDATE`。MySQL 8.0+ 推荐使用 `FOR SHARE`（支持 NOWAIT/SKIP LOCKED）。

# 冲突解决策略对比

在 MySQL 并发控制中，主要有以下几类冲突解决策略：悲观锁（FOR UPDATE / LOCK IN SHARE MODE）、乐观锁（版本号 / 时间戳）、原子更新（UPDATE SET col = col + N）、NOWAIT 快速失败、SKIP LOCKED 跳过冲突。每种策略都有其适用场景、优势和局限性。选择合适的并发控制策略，需要综合考虑冲突频率、性能要求、业务特点和数据一致性需求。

---

## 各策略核心机制

| 策略 | 实现层 | 冲突时行为 | 数据库锁 |
|------|--------|----------|---------|
| 悲观锁（FOR UPDATE）| 数据库层 | 等待锁释放 | X 行锁（排他）|
| 悲观锁（FOR SHARE）| 数据库层 | 等待锁释放 | S 行锁（共享）|
| 乐观锁（版本号）| 应用层 | 提交时冲突报错/重试 | 无 |
| 乐观锁（时间戳）| 应用层 | 提交时冲突报错/重试 | 无 |
| 原子更新 | 数据库层 | 串行化执行（无感知冲突）| X 行锁（短暂）|
| NOWAIT | 数据库层 | 立即报错（不等待）| X/S 行锁 |
| SKIP LOCKED | 数据库层 | 跳过已锁行 | X/S 行锁 |

|---------|:----------------:|:---------------:|:-----------:|:-----------:|:-------:|:------:|:-----------:|

## 各策略的典型代码示例

```sql
-- 策略1：悲观锁（FOR UPDATE）——库存扣减
BEGIN;
SELECT stock FROM inventory WHERE product_id = 101 FOR UPDATE;
-- 基于读到的 stock 值判断是否足够
UPDATE inventory SET stock = stock - 1 WHERE product_id = 101;
COMMIT;

-- 策略2：乐观锁（版本号）——账户余额更新
-- 读取阶段（不加锁）：
SELECT balance, version FROM accounts WHERE id = 1;  -- balance=1000, version=5
-- 提交阶段（带版本检查）：
UPDATE accounts SET balance = 800, version = 6
WHERE id = 1 AND version = 5;
-- rows=0 表示冲突，需重试

-- 策略3：原子更新——计数器、积分、库存（推荐）
UPDATE inventory SET stock = stock - 1
WHERE product_id = 101 AND stock > 0;
-- rows=1：扣减成功；rows=0：库存不足或被并发扣完
-- 不需要先 SELECT，直接一条 UPDATE，性能最优

-- 策略4：NOWAIT——用户界面的独占编辑
BEGIN;
SELECT * FROM orders WHERE id = 1001 FOR UPDATE NOWAIT;
-- ERROR 3572：立即告知用户"该记录正在被其他人编辑"
ROLLBACK;

-- 策略5：SKIP LOCKED——任务队列消费
BEGIN;
SELECT id FROM tasks WHERE status = 'pending' LIMIT 1 FOR UPDATE SKIP LOCKED;
-- 获取一个未被锁定的待处理任务（自动跳过被其他 Worker 锁定的任务）
UPDATE tasks SET status = 'processing' WHERE id = ?;
COMMIT;
```

## 场景决策指南

```
冲突频率高（多个事务竞争同一行）：
  → 读后修改该行：悲观锁 FOR UPDATE
  → 只读保护（不修改）：悲观锁 FOR SHARE
  → 对响应时间敏感（不能等待）：FOR UPDATE NOWAIT

冲突频率低（并发写同一行很少）：
  → 业务逻辑复杂（读取后需要计算）：乐观锁版本号
  → 表已有 updated_at 列（简单场景）：乐观锁时间戳

操作是"加减"性质（计数器、余额、库存）：
  → 直接原子 UPDATE（UPDATE SET col = col + N WHERE condition）
  → 最简洁，性能最优，无需单独的读取步骤

需要从多行中"任取一行"（任务队列、消息分发）：
  → SKIP LOCKED（跳过已被其他消费者锁定的行）
```

## 实际场景选型案例

```
场景1：电商库存扣减（高并发秒杀）
  适合策略：原子更新
  UPDATE products SET stock = stock - 1 WHERE id = 101 AND stock > 0
  原因：直接在数据库层保证扣减的原子性，不需要先读后写，并发性最高

场景2：账户转账（余额一致性要求高）
  适合策略：悲观锁 FOR UPDATE
  原因：转账涉及两个账户的余额变更，需要锁定两个账户行防止并发错误

场景3：博客文章多人协作编辑（冲突概率低）
  适合策略：乐观锁版本号
  原因：多人同时编辑同一篇文章的概率较低，乐观锁减少数据库锁开销

场景4：后台任务分发系统（多 Worker 并发处理）
  适合策略：SKIP LOCKED
  原因：多个 Worker 并发从同一张表取任务，SKIP LOCKED 实现高效无阻塞分发

场景5：配置管理界面（同一配置的并发修改）
  适合策略：悲观锁 FOR UPDATE NOWAIT + 友好提示
  原因：配置被他人编辑时立即告知，不让用户等待，提升交互体验
```

## 适用场景总结

- **高冲突写操作**：悲观锁（FOR UPDATE）是最直接的选择，确保数据一致性，虽然会有等待，但逻辑简单可靠
- **低冲突读改写操作**：乐观锁（版本号）减少数据库锁压力，适合冲突概率低、响应时间要求不高（允许重试）的场景
- **累积型数据修改**：原子 UPDATE（`col = col + N`）是性能最优的方案，适合库存、积分、计数等只需要数值增减的场景

## 常见问题

**原子更新（UPDATE col = col + N）为什么比乐观锁和悲观锁都好？**

原子更新直接在数据库内部完成"读-改-写"三个步骤（单个 SQL 语句的原子执行），既不需要应用层先 SELECT 再 UPDATE（避免了读写之间的时间窗口），也不需要持有 X 锁等待其他事务（只在 UPDATE 执行时短暂加锁，执行完立即结束）。对于"加减"性质的修改，原子更新是最简洁、性能最优的方案。但它无法应用于"读取值→应用层计算→写入计算结果"这类需要应用层参与计算的场景（这时才需要乐观锁或悲观锁）。

---

## 注意事项

- 策略选择没有绝对最优，需要根据业务的具体特征（冲突频率、一致性要求、响应时间、实现成本）综合判断。在系统早期可以从简单的悲观锁开始，性能不满足时再考虑优化为乐观锁或原子更新。
- 无论选择哪种策略，都要确保数据库索引设计合理（避免全表扫描加锁），以及事务尽量短（减少锁持有时间）。索引和事务时长对所有策略的性能都有直接影响。

---

## 总结

并发冲突解决策略各有适用场景：悲观锁（FOR UPDATE/FOR SHARE）适合高冲突、需要读后修改的场景；乐观锁（版本号/时间戳）适合低冲突、读后修改、不能阻塞的场景；原子更新（UPDATE col=col+N）适合数值增减类操作（最简洁高效）；NOWAIT 适合需要立即失败响应的用户交互场景；SKIP LOCKED 适合任务队列多消费者并发分发。选型核心因素：冲突频率（高→悲观锁，低→乐观锁）、操作类型（数值增减→原子更新，复杂计算→乐观/悲观锁）、用户体验（不能等待→NOWAIT，任取一行→SKIP LOCKED）。

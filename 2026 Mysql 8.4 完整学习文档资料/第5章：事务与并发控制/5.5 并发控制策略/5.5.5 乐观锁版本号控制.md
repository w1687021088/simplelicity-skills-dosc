# 乐观锁版本号控制

乐观锁（Optimistic Locking）是一种"假设并发冲突很少发生"的应用层并发控制策略。与悲观锁（加数据库行锁）不同，乐观锁不在读取时加任何锁，而是在提交修改时检查数据是否在读取后被其他事务修改过。版本号控制是乐观锁最常见的实现方式：在表中增加一个 `version` 整型列，每次更新时版本号加 1，提交时检查版本号是否与读取时一致，不一致则说明发生了并发冲突，拒绝更新。

## 版本号乐观锁的表设计

```sql
-- 在表中添加 version 列
CREATE TABLE accounts (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(100) NOT NULL,
    balance DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    version INT NOT NULL DEFAULT 0,         -- 版本号列（乐观锁标记）
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 初始数据
INSERT INTO accounts (username, balance, version) VALUES ('Alice', 1000.00, 0);
```

## 版本号乐观锁的操作流程

```sql
-- 步骤1：读取数据（不加锁，普通 SELECT）
SELECT id, balance, version FROM accounts WHERE id = 1;
-- 应用层获取：balance=1000, version=0（记录当前版本号）

-- 步骤2：应用层执行业务逻辑（不持有任何数据库锁）
-- 例：计算扣款后余额 = 1000 - 200 = 800

-- 步骤3：提交修改（带版本号检查）
UPDATE accounts
SET balance = 800,
    version = version + 1    -- 版本号加 1（标记为新版本）
WHERE id = 1
  AND version = 0;            -- 检查版本号是否与读取时一致
-- 返回受影响行数：
-- 1 → 更新成功（没有冲突）
-- 0 → 更新失败（version 不匹配，说明数据已被其他事务修改）

-- 步骤4：检查受影响行数
-- rows_affected = 1：乐观锁成功，数据更新完成
-- rows_affected = 0：乐观锁冲突，需要重试或报错给用户
```

## 并发冲突场景演示

```sql
-- 两个事务同时读取同一行：
-- 事务A：SELECT → balance=1000, version=0
-- 事务B：SELECT → balance=1000, version=0（同时读取，看到相同的版本）

-- 事务A 先提交：
UPDATE accounts SET balance = 800, version = 1 WHERE id = 1 AND version = 0;
-- rows_affected = 1，成功！版本从 0 变为 1

-- 事务B 后提交（尝试用旧版本号）：
UPDATE accounts SET balance = 900, version = 1 WHERE id = 1 AND version = 0;
-- WHERE version = 0，但当前 version=1（A 已修改）
-- rows_affected = 0，冲突！B 的更新被拒绝

-- 事务B 处理冲突：
-- 选项1：重新读取最新数据，重新计算，再次尝试更新
SELECT balance, version FROM accounts WHERE id = 1;
-- 读到 balance=800, version=1（A 的结果）
-- 基于新余额重新计算...
UPDATE accounts SET balance = 600, version = 2 WHERE id = 1 AND version = 1;
-- rows_affected = 1，成功！

-- 选项2：放弃操作，返回错误给用户
```

## 乐观锁的重试机制

```sql
-- 完整的乐观锁重试模式（伪代码 SQL 风格）：
-- 设置最大重试次数，避免无限循环

-- max_retries = 3
-- retry_count = 0

-- WHILE retry_count < max_retries:
--   SELECT id, balance, version FROM accounts WHERE id = ?  → {balance, version}
--   new_balance = balance - deduction
--   IF new_balance < 0: RAISE "余额不足"
--   
--   rows = UPDATE accounts SET balance=new_balance, version=version+1
--          WHERE id=? AND version=?  (传入读到的version)
--   
--   IF rows == 1: 成功，退出循环
--   ELSE:
--     retry_count += 1
--     IF retry_count >= max_retries: RAISE "并发冲突，请重试"
--     SLEEP(指数退避：10ms * 2^retry_count)  -- 等待一段时间再重试

-- 注意：重试次数不宜太多，通常 3~5 次足够
-- 高冲突率场景下大量重试会加重数据库负担
```

| 场景 | 说明 |
|------|------|
| 文章/内容编辑 | 多人同时编辑同一文档，最后提交者检查版本冲突 |
| 配置更新 | 系统配置被多个进程并发修改，版本检查防止覆盖 |
| 账户信息更新 | 用户个人信息更新（手机、地址），冲突概率低 |
| 低并发写入场景 | 写冲突频率低、不需要锁定的业务 |

## 乐观锁与悲观锁的对比

| 维度 | 乐观锁（版本号）| 悲观锁（FOR UPDATE）|
|------|:--------------:|:-----------------:|
| 数据库锁 | 不加锁 | 加行 X 锁 |
| 并发冲突处理 | 提交时检测，失败重试 | 等待锁释放后执行 |
| 适合冲突频率 | 低冲突频率 | 高冲突频率 |
| 系统开销 | 无锁等待，但需重试 | 锁等待，无重试 |
| 对其他事务影响 | 无阻塞 | 阻塞写操作 |
| 实现层 | 应用层（业务代码）| 数据库层 |

## 常见问题

**版本号乐观锁中 `version` 列溢出怎么办？**

`INT` 类型的版本号最大值约 21 亿，正常业务场景下几乎不可能溢出（即使每秒更新 100 次，需要 200 多年才能溢出）。如果确实担心，可以使用 `BIGINT`（最大 9.2 × 10^18）或让版本号循环（`version = (version + 1) % 2147483647`）。实际中版本号溢出不是问题，更关键的是确保每次 UPDATE 都正确地使用 `version + 1` 更新版本号，以及 SELECT 时正确读取并传递 version 值。

## 注意事项

- 乐观锁的 WHERE 条件中必须同时包含主键（或唯一标识符）和版本号，缺一不可。只有主键无法防止并发冲突（WHERE id=1 的 UPDATE 不知道是否被其他事务修改过）；只有版本号有理论上的问题（虽然极少发生，但不同行可能有相同版本号）。
- 乐观锁不适合高冲突场景——如果大量事务频繁写同一行，乐观锁的冲突率会很高，导致大量重试，整体性能反而不如悲观锁（悲观锁让事务排队而不是重试）。

## 总结

版本号乐观锁在表中增加 `version` 整型列（默认 0），每次 UPDATE 时 `version + 1` 并在 WHERE 子句中检查 `version = <读取时的版本号>`，通过受影响行数（1=成功，0=冲突）判断更新是否有效。读取时不加任何锁，冲突在提交时被发现。冲突后选择重试（重新读取、重新计算、重新更新）或放弃。适合低冲突频率的场景，高冲突频率下应使用悲观锁。实现层在应用层，不依赖数据库锁机制。

# 乐观锁时间戳控制

时间戳乐观锁是乐观锁的另一种实现方式，使用 `updated_at`（最后更新时间戳）列替代整型 `version` 列作为版本标识。读取数据时记录 `updated_at` 的值，提交修改时在 WHERE 子句中检查 `updated_at` 是否发生变化——如果与读取时不同，说明数据在读取后被其他事务修改过，拒绝当前更新。时间戳方案利用了表通常已有的 `updated_at` 列，无需额外增加 `version` 列，实现更简便。

---

## 时间戳乐观锁的表设计

```sql
-- 使用 DATETIME(3) 提供毫秒级精度（减少时间碰撞概率）
CREATE TABLE documents (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT,
    author_id INT,
    updated_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3)  -- 每次 UPDATE 自动更新时间戳
);

-- 注意：ON UPDATE CURRENT_TIMESTAMP 在 UPDATE 修改数据时自动更新时间戳
-- 如果 UPDATE 没有实际改变数据（SET 的值与原值相同），时间戳不会更新（可能因数据库版本而异）
```

---

## 时间戳乐观锁的操作流程

```sql
-- 步骤1：读取数据（记录时间戳）
SELECT id, title, content, updated_at FROM documents WHERE id = 1001;
-- 应用层获取：content='原始内容', updated_at='2025-03-15 10:00:00.000'

-- 步骤2：用户编辑（不加任何锁）
-- 用户修改内容...（可能耗时10秒以上）

-- 步骤3：提交修改（带时间戳检查）
UPDATE documents
SET content = '修改后的内容',
    updated_at = NOW(3)     -- 更新时间戳（如果不依赖自动更新）
WHERE id = 1001
  AND updated_at = '2025-03-15 10:00:00.000';  -- 检查时间戳是否与读取时一致
-- 如果 rows_affected=1：更新成功
-- 如果 rows_affected=0：时间戳不匹配，说明数据被修改，拒绝更新

-- 注意：如果表有 ON UPDATE CURRENT_TIMESTAMP，不需要显式设置 updated_at
UPDATE documents
SET content = '修改后的内容'  -- ON UPDATE 会自动更新 updated_at
WHERE id = 1001
  AND updated_at = '2025-03-15 10:00:00.000';
```

## 时间戳精度与碰撞风险

```sql
-- 时间戳精度对碰撞概率的影响：

-- DATETIME（秒级精度，默认）：
-- 同一秒内的两次更新，第二次更新的时间戳与第一次相同
-- → 第三个事务读取时看到"相同的时间戳"但内容已变
-- → 时间戳未变，WHERE 条件匹配成功，乐观锁失效！

-- DATETIME(3)（毫秒级精度）：
-- 同一毫秒内的两次更新碰撞概率极低（但不为零）
-- 高并发系统下仍有碰撞风险

-- DATETIME(6)（微秒级精度）：
-- 碰撞概率更低，但不为零

-- 结论：时间戳精度越高，碰撞概率越低，但永远不能降为零
-- 相比之下，版本号（整数递增）是精确的冲突检测，无碰撞风险

-- 推荐：在对冲突检测要求严格的场景，使用版本号而不是时间戳
-- 时间戳适合冲突概率极低、且能容忍极低概率漏检的场景
```

## 时间戳乐观锁与版本号乐观锁的对比

| 对比维度 | 版本号（version INT）| 时间戳（updated_at DATETIME）|
|---------|:-------------------:|:----------------------------:|
| 冲突检测精度 | 精确（整数唯一递增）| 依赖时间精度（可能碰撞）|
| 额外列 | 需要额外 version 列 | 通常表已有 updated_at 列 |
| 实现简便性 | 稍复杂（需手动管理 version）| 简便（利用现有字段）|
| 碰撞概率 | 零（每次 +1，唯一递增）| 极低但非零（同时间戳可能）|
| 适用场景 | 需要严格冲突检测 | 冲突概率极低的业务场景 |
| 业务含义 | 仅作乐观锁标记 | 同时提供"最后修改时间"信息 |

## 时间戳乐观锁的完整应用示例

```sql
-- 博客文章编辑场景（时间戳乐观锁）

-- 用户A 打开文章编辑页面：
SELECT id, title, content, updated_at
FROM documents
WHERE id = 1001;
-- 前端记录：updated_at = '2025-03-15 10:00:00.000'

-- 同时，用户B 也打开了该文章并提交修改：
UPDATE documents SET content = 'B的修改' WHERE id = 1001
    AND updated_at = '2025-03-15 10:00:00.000';
-- rows=1，成功。现在 updated_at = '2025-03-15 10:05:00.000'

-- 用户A 提交修改（慢于 B）：
UPDATE documents SET content = 'A的修改'
WHERE id = 1001 AND updated_at = '2025-03-15 10:00:00.000';
-- updated_at 已变为 '2025-03-15 10:05:00.000'，WHERE 不匹配
-- rows=0，冲突！

-- 应用层处理：
-- 显示提示："文章已被他人修改，请刷新后重试"
-- 将最新版本和 A 的修改都显示给用户，让用户选择合并或覆盖
```

## 适用场景

- **内容管理系统（CMS）**：多用户协作编辑文档、博客文章，利用已有的 `updated_at` 字段实现乐观锁，无需修改表结构
- **配置数据更新**：系统配置表通常有 `updated_at` 字段，可以直接用于乐观锁检测，不需要额外的 `version` 列

## 常见问题

**`updated_at` 使用 `ON UPDATE CURRENT_TIMESTAMP` 时，如果 SET 的值与原值相同，时间戳会更新吗？**

在标准 MySQL 行为下，如果 UPDATE 语句的 SET 子句中所有列的新值都与旧值相同（没有实际变化），MySQL 会优化跳过写操作，`ON UPDATE CURRENT_TIMESTAMP` 也不会触发更新（因为行没有实际被修改）。这意味着如果两个事务都将同一行设置为相同的值，时间戳不会变化，第二个事务的乐观锁检查会误判为"没有冲突"，但实际上数据内容没有变化，因此业务上没有问题。

---

## 注意事项

- 使用时间戳乐观锁时，WHERE 子句中的时间戳比较必须使用精确匹配（`=`），不能使用 `>=` 或范围比较，否则不能正确检测冲突。
- 如果系统中存在直接通过 SQL 脚本批量更新数据（不走应用层乐观锁逻辑）的情况，这些批量更新会更新 `updated_at`，可能导致正在编辑该数据的用户提交时产生冲突。这是时间戳（和版本号）乐观锁共同面临的问题，需要在运维操作中注意。

---

## 总结

时间戳乐观锁使用 `updated_at DATETIME(3)` 列作为版本标识，读取时记录时间戳，提交时 WHERE 子句检查时间戳是否变化（`rows_affected=0` 表示冲突）。相比版本号乐观锁，时间戳方案利用已有字段（无需额外列），实现更简便，但存在极低概率的时间戳碰撞风险（同一时刻内的两次更新可能产生相同时间戳，导致漏检）。推荐使用 `DATETIME(3)`（毫秒精度）降低碰撞概率。对冲突检测有严格要求的场景建议使用版本号方案。

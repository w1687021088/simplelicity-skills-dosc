# SKIP LOCKED 跳过锁定行

`SKIP LOCKED` 是 MySQL 8.0 引入的 `FOR UPDATE` 和 `FOR SHARE` 的扩展选项，使 SELECT 在遇到已被其他事务锁定的行时，直接跳过这些行（而不是等待锁释放），立即返回未被锁定的行。这一特性非常适合实现任务队列（Job Queue）和并发任务分发场景——多个消费者从同一张队列表中并发获取待处理任务，每个消费者只处理未被其他消费者锁定的任务，避免了阻塞等待。

---

## 基本语法

```sql
-- FOR UPDATE SKIP LOCKED（排他锁，跳过已锁行）
SELECT * FROM tasks
WHERE status = 'pending'
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- FOR SHARE SKIP LOCKED（共享锁，跳过已锁行）
SELECT * FROM tasks
WHERE status = 'pending'
LIMIT 1
FOR SHARE SKIP LOCKED;

-- 语法约束：
-- SKIP LOCKED 不能与 NOWAIT 同时使用
-- SKIP LOCKED 不能在锁定读（locking reads）以外的语句中使用
-- SKIP LOCKED 对外部查询与子查询的处理方式可能不同
```

---

## 任务队列的典型用法

```sql
-- 场景：多个工作进程并发从 tasks 表获取待处理任务

-- 建表
CREATE TABLE tasks (
    id INT PRIMARY KEY AUTO_INCREMENT,
    task_type VARCHAR(50),
    payload TEXT,
    status ENUM('pending', 'processing', 'done') DEFAULT 'pending',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 工作进程获取任务（并发安全）：
BEGIN;

-- 获取一个未被其他进程锁定的 pending 任务
SELECT id, task_type, payload
FROM tasks
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- 如果找到了任务（假设 id=100）：
UPDATE tasks SET status = 'processing' WHERE id = 100;
COMMIT;  -- 事务提交后，X 锁释放，但 status 已改为 processing

-- 如果没有找到（返回空集）：
-- 所有 pending 任务都被其他进程锁定（或已无 pending 任务）
COMMIT;  -- 提交（不做任何修改）
-- 工作进程等待一段时间后重试
```

## SKIP LOCKED 与等待锁的行为对比

```sql
-- 假设 tasks 表中 id=1 是 pending，被工作进程A 持有 X 锁

-- 工作进程B（不使用 SKIP LOCKED）：
SELECT id FROM tasks WHERE status = 'pending' LIMIT 1 FOR UPDATE;
-- 等待！id=1 有 X 锁，B 被阻塞

-- 工作进程B（使用 SKIP LOCKED）：
SELECT id FROM tasks WHERE status = 'pending' LIMIT 1 FOR UPDATE SKIP LOCKED;
-- 跳过 id=1（已被锁），继续扫描下一行
-- 如果 id=2 未被锁，返回 id=2
-- 如果所有 pending 行都被锁，返回空结果集（不等待）

-- SKIP LOCKED 使多工作进程可以并发处理不同任务，互不等待
```

## 多消费者并发性能示意

```sql
-- 4个工作进程同时运行，各自获取不同任务：

-- 进程1：SELECT id FROM tasks WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
--   → 获得 id=101，加 X 锁，开始处理

-- 进程2：SELECT id FROM tasks WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
--   → 跳过 id=101（已锁），获得 id=102，加 X 锁

-- 进程3：SELECT id FROM tasks WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
--   → 跳过 id=101, 102，获得 id=103

-- 进程4：SELECT id FROM tasks WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
--   → 跳过 id=101, 102, 103，获得 id=104

-- 4个进程并发处理不同任务，没有任何等待！
-- 这是传统的 SELECT+UPDATE 队列模式无法实现的高并发效果
```

## SKIP LOCKED 与事务的关系

```sql
-- SKIP LOCKED 结果集不一致性说明：
-- 查询返回的行集合可能不是某个时间点的完整快照
-- （跳过了被锁定的行，这些行"临时不可见"）
-- 因此 SKIP LOCKED 不适合用于需要事务一致性读的场景

-- 正确用法：任务队列（只关心"获取一个未被处理的任务"）
-- 错误用法：报表查询（需要完整一致的数据集）

-- 使用 SKIP LOCKED 时，应确保被跳过的行会被其他消费者处理
-- 不能出现"任务永远被跳过"的情况（需要超时重置机制）

-- 超时重置（避免任务永久卡在 processing 状态）：
UPDATE tasks
SET status = 'pending', updated_at = NOW()
WHERE status = 'processing'
  AND updated_at < NOW() - INTERVAL 30 MINUTE;
-- 将超过30分钟仍在 processing 的任务重置为 pending
```

## 适用场景

- **分布式任务队列**：多个 Worker 从数据库中并发拉取任务，每个 Worker 只处理未被其他 Worker 锁定的任务，实现任务的自然负载均衡
- **消息队列替代方案**：在轻量级场景下，使用数据库实现可靠的任务队列（数据持久化，无需引入 MQ 中间件），利用 SKIP LOCKED 实现并发消费

---

## 常见问题

**SKIP LOCKED 返回空集意味着所有任务都被处理完了吗？**

不一定。空集意味着满足 WHERE 条件的所有行当前都被其他事务锁定，不一定是真正处理完了。如果所有 pending 任务都被其他 Worker 锁定处理中，SKIP LOCKED 会返回空。这时应该等待一段时间（如 100ms~1s）后重试，或者通过监控 processing 状态行的数量来判断任务队列的实际状态。

---

## 注意事项

- `SKIP LOCKED` 查询的结果集不符合事务一致性（因为跳过了部分符合条件的行），它违反了关系型数据库查询结果"一致性快照"的假设。因此，MySQL 官方文档建议只在特定的任务队列场景下使用 SKIP LOCKED，不应用于普通业务查询。
- 在 RR 级别下，SKIP LOCKED 也会跳过被间隙锁（Gap Lock）保护的行，而不仅仅是记录锁。这在某些边界情况下可能导致比预期更多的行被跳过。

---

## 总结

`SKIP LOCKED` 是 MySQL 8.0 为 `FOR UPDATE`/`FOR SHARE` 添加的选项，遇到已锁行时直接跳过（而不是等待），立即返回未锁定的行。核心适用场景是任务队列——多个消费者并发从同一张表取任务，各取各的，互不阻塞，实现高并发任务分发。SKIP LOCKED 的查询结果不满足事务一致性（跳过了部分行），不适合普通业务查询，只应用于任务分发等特定场景。需要配合超时重置机制，防止任务永久卡在处理中状态。

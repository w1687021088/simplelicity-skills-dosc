# 悲观锁 SELECT FOR UPDATE

悲观锁（Pessimistic Locking）是一种"假设并发冲突一定会发生"的并发控制策略，通过在读取数据时立即加排他锁（X Lock），阻止其他事务对同一数据进行任何修改，从而保证当前事务在整个操作期间独占该数据。`SELECT ... FOR UPDATE` 是 InnoDB 中实现悲观锁的主要语法，执行当前读（读最新版本）并为匹配的行加 X 锁。

---

## 基本语法

```sql
-- 基本语法
SELECT col1, col2, ... FROM table_name
WHERE condition
FOR UPDATE;

-- MySQL 8.0+ 扩展选项
SELECT * FROM orders WHERE id = 1001 FOR UPDATE;             -- 等待锁
SELECT * FROM orders WHERE id = 1001 FOR UPDATE NOWAIT;      -- 无法加锁则立即报错
SELECT * FROM orders WHERE id = 1001 FOR UPDATE SKIP LOCKED; -- 跳过已锁行

-- 多表联合查询的悲观锁
SELECT a.*, b.*
FROM accounts a
JOIN orders b ON a.id = b.user_id
WHERE a.id = 100
FOR UPDATE;
-- 对查询结果涉及的所有表的相关行都加 X 锁
```

---

## 悲观锁的工作流程

```sql
-- 典型的悲观锁使用模式（库存扣减）：

BEGIN;
-- 步骤1：加锁读取当前库存（X 锁，阻止其他事务修改）
SELECT stock FROM inventory WHERE product_id = 101 FOR UPDATE;
-- 返回：stock = 50（此时其他事务无法修改 product_id=101 的 stock）

-- 步骤2：业务判断
-- 应用层检查 stock > 0

-- 步骤3：执行修改
UPDATE inventory SET stock = stock - 1 WHERE product_id = 101;
-- 直接基于数据库值计算，无需担心并发

-- 步骤4：提交，释放锁
COMMIT;
-- X 锁释放，其他等待的事务可以继续

-- 如果步骤2判断 stock = 0（库存不足），回滚：
ROLLBACK;  -- X 锁也释放
```

---

## FOR UPDATE 与快照读的区别

```sql
-- 普通 SELECT（快照读，MVCC）：
BEGIN;
SELECT stock FROM inventory WHERE product_id = 101;
-- 读取的是历史版本（不加锁），可能看到"过时"的值
-- 在 RR 级别下，第一次 SELECT 创建 Read View，之后的结果固定
-- 不适合用于"先读后改"的场景（读到旧值会导致决策错误）

-- SELECT...FOR UPDATE（当前读）：
BEGIN;
SELECT stock FROM inventory WHERE product_id = 101 FOR UPDATE;
-- 读取最新提交版本（current read）并加 X 锁
-- 无论隔离级别是 RR 还是 RC，都读最新数据
-- 适合"先读后改"场景（基于最新值做决策）
```

---

## FOR UPDATE 的加锁范围

```sql
-- 精确主键查询（最小锁范围）：
SELECT * FROM inventory WHERE id = 101 FOR UPDATE;
-- 只锁 id=101 这一行（Record Lock）
-- 推荐：锁范围最小，并发性最高

-- 范围条件（锁多行 + 间隙，RR 级别）：
SELECT * FROM inventory WHERE stock < 10 FOR UPDATE;
-- 锁所有 stock < 10 的行（X 锁）+ 间隙锁（RR级别防幻读）
-- 注意：如果没有 stock 的索引，触发全表扫描，锁全表！

-- 非索引列条件（危险！）：
SELECT * FROM orders WHERE remark = 'urgent' FOR UPDATE;
-- remark 无索引，全表扫描，所有行都被加 X 锁
-- 极大降低并发性，应建立索引

-- 通过二级索引查询：
SELECT * FROM orders WHERE user_id = 100 FOR UPDATE;
-- user_id 有二级索引：锁 user_id=100 的所有行（二级索引 + 聚簇索引）
```

## 适用场景

| 场景 | 说明 |
|------|------|
| 库存扣减 | 并发下单时，FOR UPDATE 保证库存不超卖 |
| 账户转账 | 转账双方账户余额加锁，防止并发修改导致余额异常 |
| 抢票/抢购 | 高价值资源的争抢，用悲观锁保证独占性 |
| 序列号生成 | 从数据库获取下一个流水号，FOR UPDATE 保证唯一性 |
| 状态机更新 | 确保状态从 A→B 的转换是原子的，不被并发修改干扰 |

## 悲观锁与乐观锁的对比

| 对比维度 | 悲观锁（FOR UPDATE）| 乐观锁（版本号）|
|---------|:-----------------:|:--------------:|
| 实现方式 | 数据库行级锁 | 应用层版本检查 |
| 冲突预期 | 假设冲突常发生 | 假设冲突少发生 |
| 加锁时机 | 读取时立即加锁 | 提交时检查版本 |
| 对其他事务的影响 | 阻塞其他写操作 | 不阻塞，冲突时重试 |
| 适合并发程度 | 中低并发 | 中高并发 |
| 数据库压力 | 锁管理开销 | 重试时额外 UPDATE 开销 |

## 常见问题

**FOR UPDATE 加锁后，如果事务没有提交，锁会一直持有吗？**

是的。InnoDB 遵循两阶段锁定协议（2PL），事务期间加的锁在整个事务提交或回滚之前都不会释放。FOR UPDATE 加的 X 锁会持续到 COMMIT 或 ROLLBACK。如果事务因网络中断等原因没有正常结束，MySQL 的 `wait_timeout` 会在连接超时后自动关闭连接并回滚事务，释放锁。这是应用层连接管理需要确保事务及时结束的原因。

---

## 注意事项

- `FOR UPDATE` 的性能关键是锁的持有时间。应尽量缩短从加锁到提交的时间：不要在 FOR UPDATE 和 COMMIT 之间执行耗时的外部调用（HTTP 请求、文件读写等），这些操作应该放到事务外执行，否则会长时间持有 X 锁，阻塞其他事务。
- 在 RC（READ COMMITTED）隔离级别下，FOR UPDATE 不加间隙锁（Gap Lock），只加记录锁（Record Lock），并发性更高。如果业务不需要防幻读，建议使用 RC 级别配合 FOR UPDATE，减少间隙锁带来的锁冲突。

---

## 总结

`SELECT ... FOR UPDATE` 是 InnoDB 悲观锁的标准实现，执行当前读（读最新版本）并为匹配行加 X 排他锁，阻止其他事务读（加锁读）或修改这些行，直到当前事务结束。适合"先读后改"且冲突频率较高的场景（库存扣减、账户转账等）。关键是控制锁的持有时间（从 FOR UPDATE 到 COMMIT 越短越好），以及通过合适的索引缩小加锁范围（避免全表扫描导致锁全表）。MySQL 8.0+ 支持 `NOWAIT`（无法加锁立即报错）和 `SKIP LOCKED`（跳过已锁行）两个扩展选项。

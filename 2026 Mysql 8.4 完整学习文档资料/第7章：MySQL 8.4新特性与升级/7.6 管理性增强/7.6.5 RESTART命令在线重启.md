# RESTART 命令在线重启

MySQL 8.0.4 引入了 `RESTART` SQL 命令，允许通过 SQL 语句触发 MySQL 服务器重启，而无需登录操作系统执行 `systemctl restart mysqld` 或 `service mysql restart`。这在需要远程管理 MySQL 服务器（如通过 MySQL Shell 或远程客户端），或者在应用 `SET PERSIST_ONLY` 的只读变量修改后需要重启使配置生效时特别有用。

---

## 基本语法

```sql
-- RESTART 命令：
RESTART;
-- 效果：
-- 1. MySQL 服务器关闭
-- 2. 如果 MySQL 是由 mysqld_safe 或 systemd 等进程管理器管理的
--    → 进程管理器检测到 MySQL 退出 → 自动重新启动 MySQL
-- 3. 如果 MySQL 是直接手动启动的（如 mysqld &）
--    → MySQL 关闭后不会自动重启
--    → 需要手动重新启动

-- 执行后客户端连接断开：
-- ERROR 2013 (HY000): Lost connection to MySQL server during query
-- 这是正常行为（服务器正在重启）
```

---

## RESTART 的前提条件

```sql
-- 1. 权限要求：SHUTDOWN 权限
SHOW GRANTS FOR CURRENT_USER();
-- 需要包含 SHUTDOWN 权限

-- 授予 SHUTDOWN 权限：
GRANT SHUTDOWN ON *.* TO 'dba'@'%';

-- 2. MySQL 必须由进程管理器（如 systemd）管理
-- 如果 MySQL 是手动启动的，RESTART 等同于 SHUTDOWN
-- 进程管理器检测到 MySQL 退出后负责重新启动

-- 在 Linux 上检查 MySQL 是否由 systemd 管理：
-- systemctl status mysqld
-- 如果显示 active (running) 且有 Main PID → 由 systemd 管理

-- 3. 在 Windows 上
-- 如果 MySQL 作为 Windows 服务运行 → RESTART 可正常工作
-- 如果是手动启动的 → RESTART 等同于关闭
```

## 配合 SET PERSIST_ONLY 使用

```sql
-- 典型工作流：修改只读变量 → 重启生效

-- 步骤1：持久化只读变量（不立即生效）
SET PERSIST_ONLY innodb_buffer_pool_instances = 8;
SET PERSIST_ONLY innodb_dedicated_server = ON;

-- 步骤2：确认持久化成功
SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.persisted_variables
WHERE VARIABLE_NAME IN ('innodb_buffer_pool_instances', 'innodb_dedicated_server');

-- 步骤3：通过 RESTART 命令重启 MySQL
RESTART;
-- 客户端连接断开

-- 步骤4：重新连接并验证
-- mysql -u root -p
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';
-- innodb_buffer_pool_instances: 8（新值已生效）

SHOW VARIABLES LIKE 'innodb_dedicated_server';
-- innodb_dedicated_server: ON（新值已生效）
```

## RESTART vs 操作系统层面重启

| 对比维度 | RESTART 命令 | systemctl restart mysqld |
|---------|:----------:|:----------------------:|
| 执行方式 | SQL 语句 | 操作系统命令 |
| 所需权限 | MySQL SHUTDOWN 权限 | 操作系统 root/sudo |
| 远程执行 | 可以（通过 MySQL 客户端）| 需要 SSH 访问 |
| 进程管理器 | 依赖（必须有）| 自身就是进程管理器 |
| 优雅关闭 | 是（等待事务完成）| 是（发送 SIGTERM）|
| 适用场景 | 远程管理、自动化 | 本地管理、脚本 |

---

## 适用场景

- **远程管理 MySQL 服务器**：当 DBA 只有 MySQL 连接权限（没有操作系统 SSH 权限）时，可以通过 `RESTART` 命令远程重启 MySQL 服务器，使 `SET PERSIST_ONLY` 的配置修改生效
- **自动化运维流程**：在自动化运维脚本中，通过 SQL 完成配置修改（`SET PERSIST_ONLY`）和重启（`RESTART`），无需在 SQL 和操作系统命令之间切换

## 常见问题

**RESTART 命令执行后如何确认 MySQL 已成功重启？**

由于 `RESTART` 会断开当前连接，无法在同一会话中确认重启状态。确认方法：①等待几秒后尝试重新连接 MySQL（`mysql -u root -p`），如果连接成功说明重启完成；②检查 MySQL 的 uptime：`SHOW GLOBAL STATUS LIKE 'Uptime'`，如果值很小（几秒~几十秒）说明刚刚重启过；③检查 Error Log 中的启动信息：`SELECT * FROM performance_schema.error_log ORDER BY LOGGED DESC LIMIT 20`，应能看到服务器启动的日志。

---

## 注意事项

- `RESTART` 命令会断开**所有**客户端连接，不仅仅是执行命令的连接。在执行 `RESTART` 前应确保没有关键的长事务或批量操作正在运行，否则这些操作会被中断并回滚。建议在维护窗口或低峰期执行。
- 如果 MySQL 不是由进程管理器（systemd、mysqld_safe 等）管理的，`RESTART` 命令会导致 MySQL 关闭但**不会重新启动**，相当于执行了 `SHUTDOWN`。在生产环境中应确保 MySQL 由 systemd 管理（`systemctl enable mysqld`），以确保 `RESTART` 能正常工作。

---

## 总结

`RESTART` 是 MySQL 8.0.4+ 的 SQL 命令，通过 SQL 触发 MySQL 服务器重启。需要 `SHUTDOWN` 权限。前提：MySQL 必须由进程管理器（systemd/mysqld_safe/Windows 服务）管理，否则只关闭不重启。典型用法：`SET PERSIST_ONLY` 修改只读变量后执行 `RESTART` 使配置生效。执行后所有客户端连接断开，重新连接后通过 `SHOW GLOBAL STATUS LIKE 'Uptime'` 确认重启成功。适合远程管理和自动化运维场景。生产环境执行前确认无关键事务运行。

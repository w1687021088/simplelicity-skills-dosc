# 原子 DDL Atomic DDL（8.0+ 增强）

MySQL 8.0 引入了原子 DDL（Atomic Data Definition Language）功能，确保 DDL 操作（如 `CREATE TABLE`、`ALTER TABLE`、`DROP TABLE` 等）要么完全成功，要么完全回滚，不会出现中间状态。在 MySQL 5.7 及之前的版本中，DDL 操作不是原子性的——如果在 DDL 执行过程中服务器崩溃，可能导致数据字典与实际文件不一致（如 `.frm` 文件存在但表空间文件损坏，或者 `DROP TABLE t1, t2, t3` 只删了 t1 和 t2 就崩溃了）。原子 DDL 彻底解决了这类问题。

---

## 原子 DDL 的核心机制

```
MySQL 8.0 原子 DDL 的实现基础：

1. 数据字典（Data Dictionary）统一存储
   MySQL 8.0 将数据字典从分散的文件（.frm、.par、.TRG 等）
   统一存储到 InnoDB 表空间中（mysql.ibd）
   数据字典本身就是 InnoDB 表 → 支持事务

2. DDL 操作的事务化
   DDL 语句的执行过程被包装在一个事务中
   成功 → 提交数据字典修改
   失败/崩溃 → 回滚数据字典修改

3. DDL 日志（DDL Log）
   记录 DDL 操作中需要执行的文件系统操作（如删除数据文件）
   用于崩溃后的恢复（redo 或 undo 未完成的操作）

传统 DDL（MySQL 5.7）的问题：
  DROP TABLE t1, t2, t3;
  → 删除 t1 ✓ → 删除 t2 ✓ → 崩溃 → t3 未删除
  → 重启后：t1 和 t2 已经删了（无法回滚），t3 还在
  → 部分完成状态，可能导致应用逻辑错误

原子 DDL（MySQL 8.0+）：
  DROP TABLE t1, t2, t3;
  → 删除 t1 ✓ → 删除 t2 ✓ → 崩溃
  → 重启后：自动回滚 → t1、t2、t3 都恢复
  → 或者：重启后自动重做 → t1、t2、t3 都删除
  → 最终状态：全部成功或全部失败
```

## 支持原子 DDL 的操作

```sql
-- 以下 DDL 操作在 MySQL 8.0+ 中是原子性的：

-- 数据库操作：
CREATE DATABASE mydb;
ALTER DATABASE mydb CHARACTER SET utf8mb4;
DROP DATABASE mydb;

-- 表操作：
CREATE TABLE t1 (id INT PRIMARY KEY, name VARCHAR(100));
ALTER TABLE t1 ADD COLUMN email VARCHAR(200);
DROP TABLE t1;
DROP TABLE t1, t2, t3;  -- 原子性：要么全部删除，要么全部保留
RENAME TABLE t1 TO t2;
TRUNCATE TABLE t1;

-- 索引操作：
CREATE INDEX idx_name ON t1 (name);
DROP INDEX idx_name ON t1;

-- 视图操作：
CREATE VIEW v1 AS SELECT * FROM t1;
DROP VIEW v1;

-- 存储过程/函数/触发器/事件：
CREATE PROCEDURE ...
DROP PROCEDURE ...
CREATE FUNCTION ...
DROP FUNCTION ...
CREATE TRIGGER ...
DROP TRIGGER ...
CREATE EVENT ...
DROP EVENT ...

-- 用户和权限（部分原子性）：
CREATE USER 'user1'@'%';
DROP USER 'user1'@'%';
GRANT ... TO 'user1'@'%';
REVOKE ... FROM 'user1'@'%';
```

## 原子 DDL 的行为验证

```sql
-- 验证 DROP TABLE 的原子性：
CREATE TABLE t1 (id INT);
CREATE TABLE t2 (id INT);

-- 尝试删除 t1, t2 和一个不存在的 t3：
DROP TABLE t1, t2, t3;
-- ERROR 1051 (42S02): Unknown table 'test.t3'
-- 在 MySQL 8.0+ 中：t1 和 t2 都不会被删除（原子性回滚）

-- 验证：
SHOW TABLES;
-- t1 和 t2 仍然存在

-- 对比 MySQL 5.7 的行为：
-- DROP TABLE t1, t2, t3;
-- ERROR: Unknown table 'test.t3'
-- 但 t1 和 t2 已经被删除了！（非原子性）

-- 使用 IF EXISTS 避免错误：
DROP TABLE IF EXISTS t1, t2, t3;
-- t1 和 t2 被删除，t3 不存在但不报错
-- 这不影响原子性——这里没有错误发生
```

## 原子 DDL 与存储引擎

```sql
-- 原子 DDL 的完整原子性只适用于 InnoDB 引擎的表
-- 对于非 InnoDB 引擎（如 MyISAM），DDL 操作可能不完全原子

-- InnoDB 表的 DDL → 完全原子
CREATE TABLE innodb_t (id INT) ENGINE=InnoDB;
-- 崩溃恢复后保证一致性

-- MyISAM 表的 DDL → 数据字典更新是原子的，但文件操作可能不原子
CREATE TABLE myisam_t (id INT) ENGINE=MyISAM;
-- 数据字典中的元数据更新是原子的
-- 但 .MYD 和 .MYI 文件的操作可能在崩溃后处于中间状态

-- 混合引擎的 DROP TABLE：
DROP TABLE innodb_t1, myisam_t1;
-- 数据字典层面是原子的
-- 但 MyISAM 的物理文件清理可能在崩溃后需要手动处理
```

## 与 MySQL 5.7 的对比

| 对比维度 | MySQL 5.7（非原子 DDL）| MySQL 8.0+（原子 DDL）|
|---------|:-------------------:|:-------------------:|
| 数据字典存储 | .frm 文件（分散）| InnoDB 表（集中）|
| DDL 事务性 | 不支持 | 支持 |
| 崩溃恢复 | 可能不一致 | 保证一致 |
| DROP TABLE 多表 | 部分删除可能 | 全部成功或全部回滚 |
| 元数据锁 | 有 | 有（更完善）|
| DDL 日志 | 无 | 有（mysql.innodb_ddl_log）|

## 适用场景

- **大规模 Schema 变更的安全保障**：在执行涉及多张表的 DDL 操作时（如批量重命名、批量删除），原子 DDL 确保操作的完整性。即使中途发生崩溃，重启后数据库状态仍然是一致的，无需手动修复
- **自动化部署中的 DDL 可靠性**：在 CI/CD 流水线或自动化部署脚本中执行 DDL 变更，原子 DDL 消除了"DDL 执行一半就失败"导致的部署环境损坏问题

## 常见问题

**原子 DDL 意味着 DDL 可以回滚（ROLLBACK）吗？**

不完全是。原子 DDL 的"原子性"主要体现在崩溃恢复场景：如果 DDL 执行过程中服务器崩溃，重启后保证数据字典和数据文件的一致性（要么 DDL 完成，要么 DDL 回滚）。但在正常执行中，DDL 语句仍然是隐式提交的（implicit commit）——DDL 语句执行前会自动提交当前未提交的事务，DDL 自身也会自动提交。不能在一个显式事务中执行 DDL 然后 ROLLBACK。例如 `BEGIN; CREATE TABLE t1 ...; ROLLBACK;` 中的 CREATE TABLE 会立即生效，ROLLBACK 不会撤销它。

## 注意事项

- 原子 DDL 引入了 DDL 日志表（`mysql.innodb_ddl_log`），用于记录 DDL 操作中的文件系统操作（如创建/删除表空间文件）。该表在正常情况下会被自动清理，但在某些异常场景下可能残留记录。不应手动修改或删除该表中的数据。
- 从 MySQL 5.7 升级到 8.0+ 后，DDL 行为会发生变化。最明显的变化是 `DROP TABLE t1, t2, t3` 在遇到不存在的表时，5.7 会删除已找到的表（部分完成），而 8.0 会回滚所有操作（全部保留）。升级后应检查依赖这种"部分完成"行为的脚本或流程。

---

## 总结

原子 DDL 是 MySQL 8.0 的重要改进，确保 DDL 操作（CREATE/ALTER/DROP TABLE、CREATE/DROP INDEX 等）要么完全成功要么完全回滚。基于数据字典统一存储到 InnoDB 表空间（取代 .frm 文件）和 DDL 日志机制实现。核心场景：`DROP TABLE t1, t2, t3` 遇到错误时全部回滚（5.7 是部分完成）。完整原子性仅适用于 InnoDB 表。DDL 仍然是隐式提交的，不能在显式事务中回滚。DDL 日志表 `mysql.innodb_ddl_log` 用于崩溃恢复。

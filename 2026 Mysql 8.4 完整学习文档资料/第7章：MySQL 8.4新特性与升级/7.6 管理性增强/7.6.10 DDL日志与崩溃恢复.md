# DDL 日志与崩溃恢复

DDL 日志（DDL Log）是 MySQL 8.0 原子 DDL 机制的核心组成部分，记录了 DDL 操作中涉及的文件系统操作（如创建/删除表空间文件、重命名文件等）。当 DDL 操作执行过程中服务器崩溃时，MySQL 在重启后通过 DDL 日志进行崩溃恢复——要么重做未完成的操作（redo），要么回滚部分完成的操作（undo），确保数据字典和数据文件始终保持一致。

---

## DDL 日志表

```sql
-- DDL 日志存储在 mysql.innodb_ddl_log 表中
-- 该表是 InnoDB 内部表，属于数据字典的一部分

-- 查看 DDL 日志表结构：
SHOW CREATE TABLE mysql.innodb_ddl_log \G
-- 注意：该表通常不可直接查询（隐藏表）
-- 需要通过 debug 模式或特定配置才能查看内容

-- 启用 DDL 日志的调试输出（仅用于诊断）：
SET GLOBAL innodb_print_ddl_logs = ON;
-- 启用后，DDL 日志的内容会输出到 MySQL Error Log

-- 查看设置：
SHOW VARIABLES LIKE 'innodb_print_ddl_logs';
-- innodb_print_ddl_logs: OFF（默认关闭）

-- 启用后执行 DDL 操作：
CREATE TABLE test_ddl (id INT PRIMARY KEY);
-- Error Log 中会出现类似信息：
-- [InnoDB] DDL log insert: [DDL record: DELETE SPACE, id=100, 
--   thread_id=10, space_id=50, old_file_path=./test/test_ddl.ibd]
-- [InnoDB] DDL log delete: by id 100

DROP TABLE test_ddl;
-- Error Log 中会出现对应的 DDL 日志记录
```

## DDL 日志的工作流程

```
DDL 操作（如 CREATE TABLE）的执行流程：

1. 开始 DDL 事务
   → 在数据字典（InnoDB 表）中开始一个事务

2. 写入 DDL 日志
   → 记录"如果需要回滚，应该执行什么操作"
   → 例如 CREATE TABLE 的回滚操作是"删除表空间文件"
   → 日志写入 mysql.innodb_ddl_log 表

3. 执行文件系统操作
   → 创建 .ibd 表空间文件
   → 初始化表空间

4. 更新数据字典
   → 在 mysql.tables、mysql.columns 等数据字典表中插入元数据

5. 提交 DDL 事务
   → 数据字典修改生效
   → 清理 DDL 日志中的记录（正常完成不需要恢复）

崩溃场景分析：

场景A：在步骤2之后、步骤3之前崩溃
  → 重启时：DDL 事务未提交 → 自动回滚数据字典修改
  → DDL 日志中的回滚操作不需要执行（文件还没创建）
  → 结果：表不存在（DDL 未开始）

场景B：在步骤3之后、步骤5之前崩溃
  → 重启时：DDL 事务未提交 → 自动回滚数据字典修改
  → 根据 DDL 日志执行回滚操作 → 删除已创建的 .ibd 文件
  → 结果：表不存在（DDL 完全回滚）

场景C：在步骤5之后崩溃
  → 重启时：DDL 事务已提交 → 数据字典修改已生效
  → DDL 日志已清理 → 无需恢复操作
  → 结果：表存在（DDL 完全成功）
```

## 崩溃恢复过程

```sql
-- MySQL 重启时的 DDL 崩溃恢复步骤：

-- 1. InnoDB 执行 redo log 恢复（标准崩溃恢复）
-- 2. 检查 mysql.innodb_ddl_log 表中是否有残留记录
-- 3. 如果有残留记录：
--    a. 检查对应的 DDL 事务是否已提交
--    b. 已提交 → 执行 DDL 日志中的"后续清理"操作（redo）
--    c. 未提交 → 执行 DDL 日志中的"回滚"操作（undo）
-- 4. 清理 DDL 日志中的记录
-- 5. 正常启动完成

-- Error Log 中的崩溃恢复信息示例：
-- [InnoDB] Starting crash recovery
-- [InnoDB] DDL log recovery: applying ...
-- [InnoDB] DDL log recovery completed

-- 查看 Error Log（MySQL 8.0.22+）：
SELECT * FROM performance_schema.error_log
WHERE SUBSYSTEM = 'InnoDB' AND DATA LIKE '%DDL%'
ORDER BY LOGGED DESC LIMIT 20;
```

## DDL 日志记录的类型

```
DDL 日志中记录的操作类型：

1. FREE（释放表空间）
   → 对应操作：删除 .ibd 文件
   → 场景：DROP TABLE、DROP INDEX（需要删除文件）

2. DELETE（删除文件）
   → 对应操作：删除指定路径的文件
   → 场景：文件清理操作

3. RENAME（重命名文件）
   → 对应操作：重命名 .ibd 文件
   → 场景：ALTER TABLE RENAME、在线 DDL 的文件交换

4. DROP（删除元数据）
   → 对应操作：从数据字典中删除表/索引的元数据
   → 场景：回滚 CREATE TABLE/INDEX

5. INSERT（插入元数据）
   → 对应操作：恢复被删除的元数据
   → 场景：回滚 DROP TABLE/INDEX

每个 DDL 日志记录包含：
- id：日志记录的唯一标识
- thread_id：执行 DDL 的线程 ID
- type：操作类型（FREE/DELETE/RENAME/DROP）
- space_id：表空间 ID
- old_file_path：原文件路径
- new_file_path：新文件路径（RENAME 操作）
```

## 在线 DDL 与 DDL 日志

```sql
-- 在线 DDL（ALTER TABLE ... ALGORITHM=INPLACE）也使用 DDL 日志

-- 在线 DDL 的典型流程：
-- 1. 创建临时表空间文件（shadow copy）
-- 2. 复制数据到临时文件并应用增量修改
-- 3. 原子交换文件（RENAME）
-- 4. 删除旧文件

-- DDL 日志记录了每个步骤的回滚操作：
-- 如果步骤2崩溃 → 删除临时文件
-- 如果步骤3崩溃 → 根据 RENAME 日志恢复文件名
-- 如果步骤4崩溃 → 继续删除旧文件（redo）

-- 监控长时间运行的 DDL：
SELECT EVENT_NAME, WORK_COMPLETED, WORK_ESTIMATED
FROM performance_schema.events_stages_current
WHERE EVENT_NAME LIKE 'stage/innodb/alter%';
```

## 适用场景

- **理解 MySQL 8.0+ 的 DDL 可靠性保证**：在生产环境执行 DDL 操作（特别是在大表上）时，了解 DDL 日志和崩溃恢复机制，可以对 DDL 操作的安全性有更清晰的认知——即使 DDL 过程中发生崩溃，数据库状态也能自动恢复到一致
- **DDL 执行异常的诊断**：当 DDL 操作后出现异常（如表找不到、文件残留等），可以通过 `innodb_print_ddl_logs=ON` 输出 DDL 日志到 Error Log，辅助诊断问题

## 常见问题

**DDL 日志会占用大量存储空间吗？**

不会。DDL 日志存储在 `mysql.innodb_ddl_log` 表中，该表只在 DDL 操作执行期间存在记录，DDL 完成后记录会被自动清理。即使执行一个复杂的 DDL（如 `ALTER TABLE` 大表），DDL 日志中也只有几条记录（几十到几百字节）。DDL 日志的大小与 DDL 操作的复杂度有关，而不是与表的数据量有关。在正常运行状态下，`mysql.innodb_ddl_log` 表通常是空的。只有在 DDL 执行过程中崩溃时，表中才会残留记录（用于崩溃恢复）。

---

## 注意事项

- `mysql.innodb_ddl_log` 是 MySQL 内部管理的系统表，不应手动查询、修改或删除其中的数据。手动操作可能导致崩溃恢复失败，进而造成数据字典与数据文件不一致。如果怀疑 DDL 日志表有问题，应联系 MySQL 支持或使用 `innodb_force_recovery` 参数进行诊断。
- `innodb_print_ddl_logs` 参数仅用于调试目的，在生产环境中不建议长期开启。开启后每个 DDL 操作都会向 Error Log 写入额外的日志信息，增加 Error Log 的大小。调试完成后应及时关闭：`SET GLOBAL innodb_print_ddl_logs = OFF`。

---

## 总结

DDL 日志是 MySQL 8.0 原子 DDL 的核心机制，存储在 `mysql.innodb_ddl_log` 表中。记录 DDL 操作中的文件系统操作（FREE/DELETE/RENAME/DROP），用于崩溃恢复时 redo（重做已提交的 DDL）或 undo（回滚未提交的 DDL）。正常完成的 DDL 会自动清理日志记录。调试：`SET GLOBAL innodb_print_ddl_logs = ON` 将 DDL 日志输出到 Error Log。在线 DDL（ALTER TABLE INPLACE）也使用 DDL 日志保证原子性。不应手动操作 DDL 日志表。DDL 日志只在 DDL 执行期间存在，不占用额外存储空间。

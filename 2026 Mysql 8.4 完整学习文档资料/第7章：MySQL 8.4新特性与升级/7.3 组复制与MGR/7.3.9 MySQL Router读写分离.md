# MySQL Router 读写分离

MySQL Router 是 InnoDB Cluster 架构中的轻量级中间件，位于应用和 MySQL 集群之间，提供透明的读写分离和自动故障转移。应用只需连接 Router 的读写端口或只读端口，Router 自动将请求路由到正确的 MGR 成员——读写请求路由到 Primary，只读请求路由到 Secondary（支持轮询或其他负载均衡策略）。当集群拓扑变化（如 Primary 切换）时，Router 自动更新路由表，应用无需感知。

---

## Router 的端口与路由策略

```
MySQL Router 默认提供 4 个监听端口：

Classic Protocol（传统协议）：
- 6446：读写端口 → 路由到 Primary
  策略：first-available（只连接 Primary）
  
- 6447：只读端口 → 路由到 Secondary
  策略：round-robin（轮询所有 Secondary）

X Protocol：
- 6448：读写端口（X Protocol）→ Primary
- 6449：只读端口（X Protocol）→ Secondary

应用连接示例：
- 写操作：mysql -h router_host -P 6446 -u app -p
- 读操作：mysql -h router_host -P 6447 -u app -p
```

## 部署与初始化

```bash
# 1. 安装 MySQL Router（通常与 MySQL Server 同版本安装包）

# 2. Bootstrap 初始化（自动发现集群拓扑）
mysqlrouter --bootstrap root@192.168.1.101:3306 \
    --directory /opt/mysqlrouter \
    --conf-use-sockets \
    --account mysqlrouter_user \
    --account-create always

# Bootstrap 过程：
# - 连接到集群的任一成员
# - 读取 InnoDB Cluster 的元数据
# - 自动生成配置文件 mysqlrouter.conf
# - 创建专用的 Router 账户（用于查询集群元数据）

# 3. 启动 Router
mysqlrouter --config /opt/mysqlrouter/mysqlrouter.conf &

# 或使用 systemd 管理
# systemctl start mysqlrouter

# 4. 验证 Router 状态
mysqlrouter --config /opt/mysqlrouter/mysqlrouter.conf --version
```

## 路由策略详解

```ini
# mysqlrouter.conf 中的路由配置

# 读写路由（路由到 Primary）
[routing:myCluster_rw]
bind_address = 0.0.0.0
bind_port = 6446
destinations = metadata-cache://myCluster/?role=PRIMARY
routing_strategy = first-available
protocol = classic

# 只读路由（路由到 Secondary）
[routing:myCluster_ro]
bind_address = 0.0.0.0
bind_port = 6447
destinations = metadata-cache://myCluster/?role=SECONDARY
routing_strategy = round-robin
protocol = classic

# 路由策略可选值：
# first-available：连接第一个可用的目标（读写端口使用）
# round-robin：轮询所有可用目标（只读端口使用）
# round-robin-with-fallback：轮询 Secondary，无可用时回退到 Primary
```

## 故障转移的透明性

```
场景：Primary（Member 1）故障

1. MGR 检测到 Member 1 故障，选举 Member 2 为新 Primary
2. Router 通过 metadata-cache 检测到拓扑变化
   （Router 定期查询集群元数据，默认间隔 0.5 秒）
3. Router 更新内部路由表：
   6446 端口 → Member 2（新 Primary）
   6447 端口 → Member 3（唯一的 Secondary）
4. 应用的新连接自动路由到 Member 2
5. 应用已有的到 Member 1 的连接被断开（需要应用重连）

对应用的影响：
- 已有连接断开，需要重连（连接池通常自动处理）
- 重连后自动连接到新 Primary
- 无需修改连接配置（IP、端口不变）
- 故障转移时间 = MGR 选举时间 + Router 检测间隔
  通常 5~15 秒
```

## Router 部署最佳实践

```
部署位置的选择：

方案1：与应用同机部署（推荐）

│ App Server 1│    │ App Server 2│
│ + Router 1  │    │ + Router 2  │
└──────┬──────┘    └──────┬──────┘
       │                   │
       └─────┬─────────┬───┘
             │         │
        ┌────▼──┐ ┌────▼──┐
        │MySQL 1│ │MySQL 2│
        └───────┘ └───────┘

优点：
- Router 故障只影响本机应用
- 减少网络跳数（应用到 Router 走本地回环）
- 无需对 Router 做高可用

方案2：独立 Router 节点
┌──────────┐  ┌──────────┐
│App Srv 1 │  │App Srv 2 │
└─────┬────┘  └─────┬────┘
      │              │
      └──────┬───────┘
             │
     ┌───────▼───────┐
     │ Router (VIP)  │  ← 需要 Keepalived 做高可用
     └───────┬───────┘
             │
        ┌────▼──┐
        │MySQL  │
        └───────┘

缺点：Router 是单点，需要额外的高可用方案
```

## 适用场景

- **InnoDB Cluster 环境中的标准读写分离方案**：MySQL Router 是 InnoDB Cluster 的官方配套组件，与 MGR 和 MySQL Shell 深度集成，是最自然的读写分离方案
- **需要透明故障转移的微服务架构**：在微服务架构中，每个服务实例部署一个 Router，通过统一的端口访问数据库，不需要在应用代码中硬编码数据库 IP 或实现故障转移逻辑

## 常见问题

**MySQL Router 和 ProxySQL 相比，各有什么优劣？**

MySQL Router 的优势：与 InnoDB Cluster 深度集成（Bootstrap 自动发现拓扑）、Oracle 官方支持、配置简单（几乎零配置）。劣势：功能相对简单，不支持查询级别的读写分离（只能按端口分离）、不支持查询缓存、不支持连接池复用、不支持查询重写。ProxySQL 的优势：功能强大（查询级别读写分离、查询缓存、连接池复用、查询路由规则）、高度可定制。劣势：配置复杂、非 Oracle 官方产品、与 InnoDB Cluster 的集成需要额外配置。简单场景用 Router，复杂路由需求用 ProxySQL。

## 注意事项

- Router 连接到 Primary 的端口（6446）使用 `first-available` 策略，意味着所有读写连接都路由到同一个 Primary。Router 不支持"按 SQL 类型自动分流"（如 SELECT 走只读端口，INSERT 走读写端口）——这种分流需要应用层或更高级的代理（如 ProxySQL）实现。应用需要在代码中明确区分读写连接和只读连接，分别连接不同的端口。
- Router 的 `metadata-cache` 通过定期查询集群元数据（`mysql_innodb_cluster_metadata` 库）来感知拓扑变化。默认刷新间隔为 0.5 秒（`ttl=0.5`）。如果需要更快的故障检测，可以减小 ttl 值，但会增加元数据查询频率。

## 总结

MySQL Router 是 InnoDB Cluster 的透明路由层，提供读写分离和自动故障转移。默认端口：6446（读写→Primary，first-available 策略）、6447（只读→Secondary，round-robin 策略）。部署：`mysqlrouter --bootstrap` 自动发现集群拓扑并生成配置。故障转移：Primary 切换后 Router 自动更新路由（通过 metadata-cache，默认 0.5 秒刷新），应用重连后透明路由到新 Primary。推荐与应用同机部署（避免 Router 单点问题）。读写分离需要应用层按端口区分（6446 写 / 6447 读），Router 不支持查询级别自动分流。

# Paxos 协议与 XCom 通信层

XCom（Extended Communication）是 MySQL Group Replication 底层的组通信系统（Group Communication System，GCS），实现了 Paxos 协议的一个变体——Mencius 协议。XCom 负责组成员管理、消息广播、消息排序和故障检测等核心功能。理解 XCom 和 Paxos 的工作原理，有助于理解 MGR 的一致性保证、性能特征和故障行为。

---

## Paxos 协议基础

```
Paxos 是一种分布式共识协议，解决的核心问题是：
在可能出现网络延迟、消息丢失、节点故障的分布式系统中，
如何让多个节点就某个值达成一致（共识）。

Paxos 的三个角色：
- Proposer（提议者）：提出一个值（提案）
- Acceptor（接受者）：对提案进行投票
- Learner（学习者）：学习已达成共识的值

基本流程（两阶段协议）：
Phase 1（Prepare）：
  Proposer → 所有 Acceptor：发送 Prepare(n)（提案编号 n）
  Acceptor → Proposer：如果 n 大于已见过的最大编号，回复 Promise(n)

Phase 2（Accept）：
  Proposer → 所有 Acceptor：发送 Accept(n, v)（编号 n，值 v）
  Acceptor → Proposer：如果 n 等于已 Promise 的编号，回复 Accepted(n, v)
  当多数派 Acceptor 接受 → 值 v 达成共识

多数派原则：
  N 个成员中，需要 (N/2)+1 个成员同意
  3 个成员：需要 2 个同意（容忍 1 个故障）
  5 个成员：需要 3 个同意（容忍 2 个故障）
  7 个成员：需要 4 个同意（容忍 3 个故障）
```

## XCom 在 MGR 中的角色

```
XCom 提供的服务：

1. Total Order Broadcast（全序广播）
   - 所有成员以相同顺序接收所有消息
   - 保证事务在所有成员上以相同顺序被认证
   - 这是数据一致性的基础

2. View Management（视图管理）
   - 维护当前组的成员列表（视图/View）
   - 新成员加入 → 视图变更（View Change）
   - 成员离开或故障 → 视图变更
   - 所有成员看到相同的视图变更序列

3. Failure Detection（故障检测）
   - 成员间定期心跳（group_replication_member_expel_timeout）
   - 超时未响应的成员被怀疑（Suspect）
   - 多数派同意后，故障成员被驱逐（Expel）

4. Message Delivery（消息传递）
   - 通过 group_replication_local_address 指定的端口通信
   - 使用 TCP 连接，成员间全连接拓扑
   - 支持消息压缩（group_replication_compression_threshold）
```

## XCom 通信配置

```sql
-- XCom 使用独立的端口进行成员间通信（不是 MySQL 的 3306 端口）

-- 本地 XCom 通信地址：
SHOW VARIABLES LIKE 'group_replication_local_address';
-- group_replication_local_address: 192.168.1.101:33061
-- 格式：host:port，端口通常使用 MySQL 端口 + 10000

-- 组种子列表（初始发现其他成员的地址）：
SHOW VARIABLES LIKE 'group_replication_group_seeds';
-- group_replication_group_seeds: 192.168.1.101:33061,192.168.1.102:33061,192.168.1.103:33061

-- 消息压缩（减少网络传输量）：
SHOW VARIABLES LIKE 'group_replication_compression_threshold';
-- group_replication_compression_threshold: 1000000（默认 1MB）
-- 超过此大小的消息会被压缩后传输
-- 设为 0 禁用压缩

-- XCom 通信加密（MySQL 8.0.16+）：
-- group_replication_ssl_mode = REQUIRED
-- 使用 SSL/TLS 加密成员间通信
```

## 故障检测与成员驱逐

```sql
-- 故障检测相关参数：

-- 成员驱逐超时（MySQL 8.0.13+）：
SHOW VARIABLES LIKE 'group_replication_member_expel_timeout';
-- group_replication_member_expel_timeout: 5（默认 5 秒）
-- 成员被怀疑后，等待此时间再决定是否驱逐
-- 设为 0 表示立即驱逐（可能导致网络抖动时误驱逐）

-- 自动重新加入尝试（MySQL 8.0.16+）：
SHOW VARIABLES LIKE 'group_replication_autorejoin_tries';
-- group_replication_autorejoin_tries: 3（默认 3 次）
-- 被驱逐后自动尝试重新加入的次数
-- 每次尝试间隔 5 分钟

-- 不可达多数派超时：
SHOW VARIABLES LIKE 'group_replication_unreachable_majority_timeout';
-- group_replication_unreachable_majority_timeout: 0（默认不超时）
-- 当少数派成员无法联系到多数派时，等待多久后自动离开组
-- 设为 0 表示无限等待（需要手动干预）
```

## 网络分区处理

```
网络分区场景（3 个成员，成员 3 与其他成员网络中断）：

分区前：成员 1、2、3 正常（多数派 = 2）
分区后：
  多数派（成员 1、2）：继续正常工作，可以提交事务
  少数派（成员 3）：无法获得多数派确认，事务提交被阻塞

成员 3 的行为：
- 检测到无法联系到多数派
- 如果 group_replication_unreachable_majority_timeout > 0：
  → 等待超时后自动离开组，进入 ERROR 状态
- 如果 group_replication_unreachable_majority_timeout = 0（默认）：
  → 无限等待，直到网络恢复或手动干预
  → 手动干预：STOP GROUP_REPLICATION; 然后重新加入

脑裂防护：
- Paxos 的多数派原则天然防止脑裂
- 两个分区无法同时获得多数派确认
- 只有包含多数派的分区能继续提交事务
```

## 适用场景

- **理解 MGR 一致性保证的原理基础**：XCom 的全序广播确保所有成员以相同顺序处理事务，是 MGR 数据一致性的根本保证。理解这个原理有助于在故障排查时判断一致性问题的根源
- **MGR 网络架构设计**：XCom 的通信特性（全连接拓扑、多数派确认）决定了 MGR 对网络延迟和带宽的要求，是 MGR 网络架构设计的理论基础

## 常见问题

**XCom 通信的网络要求是什么？跨机房部署 MGR 是否可行？**

XCom 要求成员间的网络延迟尽可能低且稳定。同机房部署（RTT < 1ms）是最理想的环境，事务提交延迟增加约 1~3ms。同城双机房（RTT 1~5ms）可以接受，但事务提交延迟会增加到 5~15ms。跨城部署（RTT 20~50ms）不推荐用于 MGR，因为每个事务都需要多数派确认，延迟会累加到事务提交路径上。如果需要跨地域灾备，建议使用 InnoDB ClusterSet（跨集群异步复制）而不是单个 MGR 组跨地域部署。

## 注意事项

- XCom 的通信端口（`group_replication_local_address`）与 MySQL 服务端口是独立的，防火墙需要同时开放两个端口。例如 MySQL 使用 3306，XCom 使用 33061，两个端口都需要在成员间可达。
- XCom 使用 TCP 长连接进行通信，任何一个连接中断都可能触发故障检测。在网络不稳定的环境中，应适当增大 `group_replication_member_expel_timeout`（如 30 秒），避免短暂网络抖动导致成员被误驱逐。

## 总结

XCom 是 MGR 的底层通信层，实现了 Paxos 协议变体（Mencius），提供四大核心服务：全序广播（保证事务顺序一致）、视图管理（成员加入/离开）、故障检测（心跳超时 + 多数派驱逐）、消息传递（TCP 全连接）。多数派原则：N 个成员需要 (N/2)+1 个成员确认，容忍 (N-1)/2 个故障。网络分区时只有多数派分区能继续工作（天然防脑裂）。配置：`group_replication_local_address`（XCom 端口）、`group_replication_group_seeds`（种子列表）。网络要求：低延迟、稳定，推荐同机房部署。

# 认证与冲突检测 Certification

认证（Certification）是 MySQL Group Replication 保证数据一致性的核心机制。每个事务在本地执行完成后，不是直接提交，而是先将事务的写入集（Write Set）广播到组内所有成员。所有成员独立执行冲突检测——如果该事务与其他已通过认证的并发事务存在行级冲突（修改了相同的行），则该事务被拒绝并回滚；如果无冲突，则在所有成员上提交。这种"先执行后认证"的乐观并发控制策略，保证了所有成员最终数据一致。

---

## 认证的工作流程

```
事务从执行到提交的完整流程：

1. 本地执行（Optimistic Execution）
   - 用户在某个成员上执行 INSERT/UPDATE/DELETE
   - 事务在本地 InnoDB 引擎中正常执行
   - 此时事务尚未提交（处于 prepare 阶段）

2. 写入集生成
   - 事务提交时，MySQL 提取该事务的写入集
   - 写入集 = 被修改行的主键（或唯一键）的哈希值集合
   - 使用 transaction_write_set_extraction = XXHASH64

3. 广播到组
   - 通过 XCom 将事务的写入集和 binlog 事件广播到所有成员
   - XCom 保证所有成员以相同顺序接收

4. 认证（Certification）
   - 每个成员独立执行冲突检测
   - 将事务的写入集与认证数据库（Certification Database）比对
   - 认证数据库记录了最近已通过认证的事务的写入集

5. 结果
   - 无冲突 → 事务通过认证 → 在所有成员上提交
   - 有冲突 → 事务被拒绝 → 在发起成员上回滚
   - 由于所有成员以相同顺序接收和认证，结果一致
```

## 冲突判定规则

```sql
-- 冲突判定的核心：写入集是否有交集

-- 场景1：无冲突（可以并行提交）
-- 事务 TA 修改了 orders 表的 id=1
-- 事务 TB 修改了 orders 表的 id=2
-- 写入集无交集 → 两个事务都通过认证

-- 场景2：有冲突（后到的事务被回滚）
-- 事务 TA 修改了 orders 表的 id=1（先到达认证）
-- 事务 TB 修改了 orders 表的 id=1（后到达认证）
-- 写入集有交集（id=1）→ TB 被拒绝

-- 场景3：插入冲突
-- 事务 TA 插入了 id=100 的行（先到达）
-- 事务 TB 也插入了 id=100 的行（后到达）
-- 主键冲突 → TB 被拒绝

-- 冲突的判定标准：
-- 两个事务的写入集中是否存在相同的行标识（主键/唯一键哈希）
-- 如果存在 → 冲突 → 后到的事务回滚
-- 如果不存在 → 无冲突 → 都通过
```

## 认证数据库（Certification Database）

```sql
-- 认证数据库是每个成员内存中维护的数据结构
-- 记录了最近通过认证的事务的写入集信息

-- 查看认证相关统计：
SELECT * FROM performance_schema.replication_group_member_stats \G

-- 关键指标：
-- COUNT_TRANSACTIONS_IN_QUEUE: 等待认证的事务队列长度
-- COUNT_TRANSACTIONS_CHECKED: 已经过认证检查的事务总数
-- COUNT_CONFLICTS_DETECTED: 检测到的冲突总数
-- COUNT_TRANSACTIONS_ROWS_VALIDATING: 认证数据库中的行数

-- 冲突率计算：
-- 冲突率 = COUNT_CONFLICTS_DETECTED / COUNT_TRANSACTIONS_CHECKED × 100%
-- 健康的冲突率应低于 1%
-- 超过 5% 说明写入热点严重，需要优化

-- 认证数据库清理：
-- group_replication_gtid_assignment_block_size 控制 GTID 分配块大小
-- 认证数据库中过期的条目会被定期清理（基于 GTID 已在所有成员执行）
```

## 认证对表结构的要求

```sql
-- MGR 认证机制要求每个表必须有主键或非 NULL 唯一键

-- 原因：认证通过行的主键/唯一键哈希来标识被修改的行
-- 没有主键的表无法生成有效的写入集 → 无法进行冲突检测

-- 检查缺少主键的表：
SELECT t.TABLE_SCHEMA, t.TABLE_NAME
FROM information_schema.TABLES t
LEFT JOIN information_schema.TABLE_CONSTRAINTS tc
    ON t.TABLE_SCHEMA = tc.TABLE_SCHEMA
    AND t.TABLE_NAME = tc.TABLE_NAME
    AND tc.CONSTRAINT_TYPE = 'PRIMARY KEY'
WHERE t.TABLE_TYPE = 'BASE TABLE'
    AND t.TABLE_SCHEMA NOT IN ('mysql', 'information_schema', 
                                'performance_schema', 'sys')
    AND tc.CONSTRAINT_NAME IS NULL;

-- 强制所有表必须有主键（推荐在 MGR 环境中启用）：
SET GLOBAL sql_require_primary_key = ON;
-- 此后 CREATE TABLE 如果没有主键会报错
```

## 适用场景

- **理解 MGR 事务回滚原因的排查基础**：当应用报告事务被回滚（ERROR 3101）时，理解认证机制可以帮助定位冲突原因——检查 `COUNT_CONFLICTS_DETECTED` 增长趋势、确认哪些表的写入存在热点
- **MGR 性能调优的关键指标来源**：通过 `performance_schema.replication_group_member_stats` 监控认证队列长度（`COUNT_TRANSACTIONS_IN_QUEUE`）和冲突率，判断 MGR 的健康状况

## 常见问题

**认证数据库会无限增长吗？如何控制其大小？**

认证数据库不会无限增长。MySQL 会定期清理认证数据库中过期的条目——当某个事务的 GTID 已经在所有成员上执行完毕，该事务的写入集信息就不再需要，会被清理。如果某个成员长时间处于 RECOVERING 状态（如数据恢复中），它会阻止认证数据库的清理（因为该成员可能还需要这些信息），导致认证数据库增长。此时 `COUNT_TRANSACTIONS_ROWS_VALIDATING` 值会持续上升。解决方法：尽快完成 RECOVERING 成员的数据恢复，或将其从组中移除。

## 注意事项

- 认证是**乐观并发控制**——事务先在本地完整执行（包括所有锁等待和 I/O），然后才进行冲突检测。如果事务被拒绝，前面的所有执行工作都白费了。因此在高冲突场景下，大量计算资源会浪费在"执行后被回滚"的事务上。如果冲突率持续很高，应考虑优化写入路由或切换到单主模式。
- 认证过程在每个成员上独立执行，但由于 XCom 保证了消息的全序广播（所有成员以相同顺序接收事务），所有成员的认证结果是一致的——同一个事务在所有成员上要么都通过，要么都被拒绝。

---

## 总结

认证（Certification）是 MGR 数据一致性的核心机制。流程：事务本地执行 → 生成写入集（被修改行的主键哈希）→ 广播到组 → 所有成员独立检测冲突 → 无冲突则提交，有冲突则回滚后到的事务。冲突判定：两个事务的写入集是否有交集（相同行的主键/唯一键哈希）。要求：所有表必须有主键（`sql_require_primary_key=ON`）。监控：`performance_schema.replication_group_member_stats`（`COUNT_CONFLICTS_DETECTED`、`COUNT_TRANSACTIONS_IN_QUEUE`）。认证数据库在内存中维护，过期条目自动清理。乐观并发控制模式，高冲突场景下资源浪费大。

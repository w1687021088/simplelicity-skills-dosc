# InnoDB Cluster 架构

InnoDB Cluster 是 MySQL 官方提供的完整高可用解决方案，将三个组件有机集成：MySQL Group Replication（MGR，提供数据复制和一致性保证）、MySQL Shell（AdminAPI，提供集群管理接口）、MySQL Router（提供透明的应用层路由）。InnoDB Cluster 不是一个独立的产品，而是将已有的 MGR 技术包装为更易于部署和管理的集群方案，降低了 MGR 的使用门槛。

---

## 架构组件

```
InnoDB Cluster 的三层架构：

┌──────────────────────────────────────────┐
│              应用层（Application）         │
│         连接到 MySQL Router              │
└────────────────┬─────────────────────────┘
                 │
┌────────────────▼─────────────────────────┐
│           MySQL Router                    │
│   读写端口(6446) → Primary               │
│   只读端口(6447) → Secondary (轮询)       │
│   自动感知拓扑变化，透明故障转移           │
└────────────────┬─────────────────────────┘
                 │
┌────────────────▼─────────────────────────┐
│     MySQL Group Replication (MGR)         │
│                                          │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐    │
│  │Member 1 │ │Member 2 │ │Member 3 │    │
│  │(Primary)│ │(Second.)│ │(Second.)│    │
│  └─────────┘ └─────────┘ └─────────┘    │
│                                          │
│     通过 MySQL Shell AdminAPI 管理        │
└──────────────────────────────────────────┘
```

## 使用 MySQL Shell 创建集群

```javascript
// 连接到第一个 MySQL 实例
mysqlsh> \connect root@192.168.1.101:3306

// 检查实例是否满足 InnoDB Cluster 要求
mysqlsh> dba.checkInstanceConfiguration('root@192.168.1.101:3306')
// 如果有问题，自动修复：
mysqlsh> dba.configureInstance('root@192.168.1.101:3306')

// 创建集群（在第一个实例上）
mysqlsh> var cluster = dba.createCluster('myCluster')
// 自动配置 MGR 相关参数并启动 Group Replication

// 添加第二个实例
mysqlsh> cluster.addInstance('root@192.168.1.102:3306')
// 自动选择恢复方式（Clone 或 Incremental）

// 添加第三个实例
mysqlsh> cluster.addInstance('root@192.168.1.103:3306')

// 查看集群状态
mysqlsh> cluster.status()
// 显示所有成员的角色、状态、延迟等信息

// 查看详细状态
mysqlsh> cluster.status({extended: 1})
```

## MySQL Router 配置

```bash
# 初始化 MySQL Router（自动获取集群拓扑信息）
mysqlrouter --bootstrap root@192.168.1.101:3306 --directory /opt/mysqlrouter

# Router 自动生成配置文件，包含以下端口：
# 6446: 读写端口（路由到 Primary）
# 6447: 只读端口（路由到 Secondary，轮询策略）
# 6448: 读写端口（X Protocol）
# 6449: 只读端口（X Protocol）

# 启动 Router
mysqlrouter --config /opt/mysqlrouter/mysqlrouter.conf &
```

```sql
-- 应用连接 Router 而不是直接连接 MySQL 实例
-- 读写操作连接 6446 端口：
mysql -h router_host -P 6446 -u app_user -p
-- 自动路由到 Primary

-- 只读操作连接 6447 端口：
mysql -h router_host -P 6447 -u app_user -p
-- 自动路由到某个 Secondary（轮询）

-- Primary 故障后：
-- Router 自动检测到拓扑变化
-- 将 6446 端口的连接路由到新选举的 Primary
-- 应用无需修改连接配置
```

## 集群管理操作

```javascript
// 获取集群对象
mysqlsh> var cluster = dba.getCluster()

// 查看集群状态
mysqlsh> cluster.status()

// 移除成员
mysqlsh> cluster.removeInstance('root@192.168.1.103:3306')

// 重新加入离开的成员
mysqlsh> cluster.rejoinInstance('root@192.168.1.103:3306')

// 手动切换 Primary
mysqlsh> cluster.setPrimaryInstance('root@192.168.1.102:3306')

// 修改集群选项
mysqlsh> cluster.setOption('memberWeight', 80)

// 集群完全崩溃后的恢复（所有成员都离开了组）
mysqlsh> dba.rebootClusterFromCompleteOutage()

// 解散集群
mysqlsh> cluster.dissolve()
```

## InnoDB Cluster vs 手动配置 MGR

| 对比维度 | 手动配置 MGR | InnoDB Cluster |
|---------|:----------:|:-------------:|
| 部署方式 | 手动编辑 my.cnf + SQL | MySQL Shell AdminAPI |
| 部署时间 | 30~60 分钟 | 5~10 分钟 |
| 应用路由 | 需自行配置（ProxySQL 等）| 内置 MySQL Router |
| 故障转移 | MGR 自动选举 | MGR 选举 + Router 自动路由 |
| 集群监控 | 需自行查询 P_S 表 | cluster.status() 一览 |
| 成员管理 | 手动 SQL 操作 | addInstance/removeInstance |
| 灾难恢复 | 手动重建 | rebootClusterFromCompleteOutage |
| 学习成本 | 需理解 MGR 所有参数 | AdminAPI 封装了复杂性 |

## 适用场景

- **快速部署 MySQL 高可用集群**：对于不熟悉 MGR 底层配置的团队，InnoDB Cluster 通过 AdminAPI 大幅简化了部署和管理过程，几条命令即可完成集群搭建
- **需要透明故障转移的应用系统**：MySQL Router 提供了应用层的透明路由，Primary 切换后应用无需修改连接配置，降低了高可用对应用层的侵入性

## 常见问题

**InnoDB Cluster 和直接使用 MGR 有什么本质区别？底层数据复制机制一样吗？**

底层的数据复制机制完全一样——InnoDB Cluster 使用的就是 MySQL Group Replication。InnoDB Cluster 在 MGR 之上提供了三层增值：①MySQL Shell AdminAPI 简化了集群的创建、管理和监控（不需要手动编辑配置文件和执行复杂的 SQL）；②MySQL Router 提供了应用层的透明路由（应用连接 Router 而不是直接连接 MySQL 实例）；③提供了集群生命周期管理功能（如 `rebootClusterFromCompleteOutage` 灾难恢复）。如果团队对 MGR 底层配置非常熟悉，且已有成熟的路由方案（如 ProxySQL），也可以直接使用 MGR 而不用 InnoDB Cluster。

---

## 注意事项

- MySQL Router 应部署在**应用服务器**上（而不是 MySQL 服务器上），每个应用服务器部署一个 Router 实例。这样 Router 的故障不会影响 MySQL 服务，且减少了网络跳数。如果 Router 部署在独立服务器上，Router 本身也需要高可用（通过 Keepalived 等）。
- InnoDB Cluster 的所有管理操作都通过 MySQL Shell 的 AdminAPI 执行。直接通过 SQL 修改 MGR 相关配置（如 `SET GLOBAL group_replication_...`）可能与 AdminAPI 的元数据不一致，导致管理混乱。在 InnoDB Cluster 环境中，应始终通过 AdminAPI 进行管理操作。

## 总结

InnoDB Cluster 是 MySQL 官方的完整高可用方案，由三部分组成：MGR（数据复制和一致性）+ MySQL Shell AdminAPI（集群管理）+ MySQL Router（应用路由）。部署：`dba.createCluster()` → `cluster.addInstance()` → `mysqlrouter --bootstrap`。Router 端口：6446（读写→Primary）、6447（只读→Secondary 轮询）。管理：`cluster.status()`、`cluster.setPrimaryInstance()`、`cluster.removeInstance()`、`dba.rebootClusterFromCompleteOutage()`。底层数据复制机制与 MGR 完全一致，InnoDB Cluster 在 MGR 之上提供了简化管理和透明路由。Router 建议部署在应用服务器上。

# 主选举策略 Primary Election

在 MGR 单主模式下，当 Primary 节点故障、离开组或被手动切换时，组内需要自动选举新的 Primary。MySQL Group Replication 内置了主选举算法，综合考虑成员权重、MySQL 版本和 server_uuid 等因素来决定哪个成员成为新 Primary。MySQL 8.0.2 引入了 `group_replication_member_weight` 参数，允许运维人员通过权重影响选举结果，使特定成员优先成为 Primary。

---

## 选举算法

```
主选举的评判标准（按优先级从高到低）：

1. MySQL 版本（最高优先级）
   - 版本号最低的成员优先
   - 原因：升级期间，旧版本成员更安全作为 Primary
   - 所有成员版本相同时，此规则不起作用

2. 成员权重（group_replication_member_weight）
   - 权重值越高的成员优先
   - 范围：0 ~ 100
   - 默认值：50
   - 相同权重时，进入下一规则

3. server_uuid（最低优先级 / 决胜规则）
   - UUID 字典序最小的成员优先
   - 用于在版本和权重都相同时做最终决策
   - UUID 是随机生成的，结果不可预测

完整选举流程：
所有 ONLINE 状态的 Secondary → 按版本排序（低版本优先）
→ 版本相同的按权重排序（高权重优先）
→ 权重也相同的按 UUID 排序（字典序小优先）
→ 排在第一位的成员成为新 Primary
```

## 通过权重控制选举结果

```sql
-- 查看当前权重：
SHOW VARIABLES LIKE 'group_replication_member_weight';
-- group_replication_member_weight: 50（默认值）

-- 设置权重（动态变量，无需重启）：
SET GLOBAL group_replication_member_weight = 80;

-- 配置示例（3 个成员的权重策略）：
-- 成员 A（高性能服务器）：权重 80 → 优先成为 Primary
-- 成员 B（中等性能服务器）：权重 50 → 次优先
-- 成员 C（备用服务器）：权重 20 → 最低优先级

-- 在各成员上分别设置：
-- 成员 A：SET GLOBAL group_replication_member_weight = 80;
-- 成员 B：SET GLOBAL group_replication_member_weight = 50;
-- 成员 C：SET GLOBAL group_replication_member_weight = 20;

-- 持久化配置（my.cnf）：
-- [mysqld]
-- group_replication_member_weight = 80
```

## 手动指定 Primary

```sql
-- MySQL 8.0.13+ 支持在线手动切换 Primary：
SELECT group_replication_set_as_primary('target_member_uuid');

-- 获取成员 UUID：
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_ROLE, MEMBER_VERSION
FROM performance_schema.replication_group_members;

-- 手动切主的流程：
-- 1. 旧 Primary 完成所有正在执行的事务
-- 2. 旧 Primary 设为 super_read_only = ON
-- 3. 新 Primary 设为 super_read_only = OFF
-- 4. 所有成员更新 MEMBER_ROLE

-- MySQL 8.0.29+ 支持超时参数：
SELECT group_replication_set_as_primary('uuid', 30);
-- 第二个参数是超时时间（秒）
-- 如果 30 秒内旧 Primary 上的事务未完成，自动 kill 这些事务
-- 防止长事务阻塞切主过程
```

## 监控选举过程

```sql
-- 通过 Performance Schema 监控：
SELECT * FROM performance_schema.replication_group_members;

-- 查看组内事件（包括选举事件）：
-- MySQL Error Log 中会记录选举相关信息：
-- [GCS] Member with ID ... has been elected as primary
-- [GCS] View change: members changed ...

-- 通过状态变量监控：
SHOW GLOBAL STATUS LIKE 'group_replication_primary_member';
-- group_replication_primary_member: 3E11FA47-...（当前 Primary 的 UUID）

-- 确认选举完成（新 Primary 已就绪）：
SELECT MEMBER_ROLE FROM performance_schema.replication_group_members
WHERE MEMBER_ID = @@server_uuid;
-- PRIMARY → 当前成员是 Primary
-- SECONDARY → 当前成员是 Secondary
```

## 选举触发场景

```
选举在以下场景下自动触发：

1. Primary 故障（崩溃、网络断开）
   → 故障检测（group_replication_member_expel_timeout 后）
   → 多数派驱逐故障 Primary
   → 自动选举新 Primary

2. Primary 正常离开组（STOP GROUP_REPLICATION）
   → Primary 通知组自己即将离开
   → 触发选举
   → 新 Primary 被选出后，旧 Primary 完成退出

3. 手动切主（group_replication_set_as_primary）
   → 不是故障触发，而是运维主动操作
   → 过程更平滑（旧 Primary 有序交接）

4. 模式切换（从多主切到单主）
   → group_replication_switch_to_single_primary_mode()
   → 需要选出一个 Primary
   → 如果指定了 UUID 则使用指定成员
   → 否则按选举算法选择
```

## 适用场景

- **硬件配置不均的 MGR 环境**：当组内成员的硬件配置不同时（如一台高性能服务器 + 两台普通服务器），通过设置高权重确保高性能服务器优先成为 Primary，充分利用硬件资源
- **计划内维护的优雅切主**：在对 Primary 进行维护（如操作系统升级、硬件更换）前，先通过 `group_replication_set_as_primary` 手动将 Primary 切到其他成员，然后对旧 Primary 进行维护，避免被动故障转移

## 常见问题

**如何确保特定成员永远不会成为 Primary？**

将该成员的权重设为 0：`SET GLOBAL group_replication_member_weight = 0`。权重为 0 的成员在选举中优先级最低，只有当所有其他成员都不可用时才会被选为 Primary。如果需要更强的保证，可以在应用层配合 MySQL Router 的路由策略，确保即使该成员意外成为 Primary，应用也不会向其发送写请求。典型场景：灾备机房的成员设为权重 0，正常情况下只作为数据副本。

---

## 注意事项

- 权重只影响自动选举的结果，不影响手动切主（`group_replication_set_as_primary` 可以将任何成员指定为 Primary，无视权重）。
- 在混合版本的 MGR 组中（如升级过程中），版本号的优先级高于权重。即使低版本成员的权重最低，它仍然会优先被选为 Primary。这是为了保证升级过程中由旧版本成员处理写入，避免新版本的行为差异影响数据一致性。

---

## 总结

MGR 单主模式的主选举算法按优先级：MySQL 版本（低版本优先）→ 成员权重（`group_replication_member_weight`，0~100，高权重优先）→ server_uuid（字典序小优先）。通过设置权重可以控制选举倾向：高性能成员设高权重（如 80），备用成员设低权重（如 20 或 0）。手动切主：`group_replication_set_as_primary('uuid')`（MySQL 8.0.13+），支持超时参数（8.0.29+）。选举触发场景：Primary 故障、正常离开、手动切主、模式切换。权重不影响手动切主结果，混合版本时版本优先级高于权重。

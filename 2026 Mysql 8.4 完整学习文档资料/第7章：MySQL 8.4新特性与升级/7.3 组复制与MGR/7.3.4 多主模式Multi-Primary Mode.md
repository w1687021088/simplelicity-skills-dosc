# 多主模式 Multi-Primary Mode

多主模式（Multi-Primary Mode）是 MySQL Group Replication 的另一种运行模式，允许组内所有成员同时接受读写操作。每个成员既是 Primary 又可以处理写入请求，不存在 Secondary 只读节点的概念。当多个成员同时修改不同的数据时可以并行执行；如果修改了相同的数据行，MGR 的认证机制会检测冲突并回滚其中一个事务。多主模式提供了更高的写入吞吐量，但对应用层的设计提出了更高的要求。

---

## 多主模式的配置

```ini
# my.cnf 配置（所有成员一致）
[mysqld]
# 关闭单主模式 = 启用多主模式
group_replication_single_primary_mode = OFF

# 启用多主一致性检查（多主模式必须开启）
group_replication_enforce_update_everywhere_checks = ON
```

```sql
-- 在线切换到多主模式（MySQL 8.0.13+）：
SELECT group_replication_switch_to_multi_primary_mode();

-- 切换后所有成员的 MEMBER_ROLE 都变为 PRIMARY：
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_ROLE
FROM performance_schema.replication_group_members;
-- 所有成员: MEMBER_ROLE = PRIMARY

-- 切回单主模式：
SELECT group_replication_switch_to_single_primary_mode();
-- 或指定某个成员为 Primary：
SELECT group_replication_switch_to_single_primary_mode('member_uuid');
```

## 多主模式的冲突检测

```sql
-- 冲突场景：两个成员同时修改同一行数据

-- 成员 A 执行：
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- 事务 TA，修改 id=1 的行

-- 成员 B 几乎同时执行：
UPDATE accounts SET balance = balance + 200 WHERE id = 1;
COMMIT;  -- 事务 TB，也修改 id=1 的行

-- 认证过程：
-- 两个事务被广播到组内所有成员
-- 认证模块检测到 TA 和 TB 的写入集有交集（id=1）
-- 先到达认证的事务通过（如 TA）
-- 后到达的事务被拒绝（TB 回滚）
-- 成员 B 收到回滚通知：
-- ERROR 1180: Got error 149 during COMMIT
-- 或者：
-- ERROR 3101: Plugin instructed the server to rollback the current transaction.

-- 应用层必须处理事务回滚并重试
```

## 多主模式的限制

```sql
-- enforce_update_everywhere_checks = ON 时的额外限制：

-- 1. 不支持串行隔离级别（SERIALIZABLE）
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- 在多主模式下执行时会报错
-- 推荐使用 READ COMMITTED

-- 2. 不推荐使用外键的级联操作
-- CASCADE、SET NULL 等级联操作在多主模式下可能导致
-- 不同成员上的执行顺序不同，产生数据不一致
-- 建议在应用层处理级联逻辑

-- 3. 不支持 SELECT ... FOR UPDATE / FOR SHARE 跨成员
-- 行级锁只在本地成员有效，不会跨成员传播
-- 在多主模式下，不同成员可以同时获取同一行的锁
-- 需要依赖认证机制而不是锁来保证一致性

-- 4. DDL 的特殊处理
-- DDL 语句（ALTER TABLE 等）在多主模式下需要特别注意
-- 同一张表的 DDL 和 DML 并发可能导致问题
-- 建议 DDL 操作在单个成员上执行，或使用 pt-online-schema-change
```

## 单主模式 vs 多主模式

| 对比维度 | 单主模式 | 多主模式 |
|---------|:------:|:------:|
| 写入节点 | 1 个 Primary | 所有成员 |
| 写冲突 | 无 | 可能（需应用处理）|
| 应用复杂度 | 低（传统读写分离）| 高（需处理冲突回滚）|
| 写入吞吐 | 受限于单节点 | 分散到多节点 |
| 外键支持 | 支持 | 不推荐 |
| 隔离级别 | 任意 | 不支持 SERIALIZABLE |
| 故障转移 | 自动选举新 Primary | 无需选举（少一个写节点）|
| 运维复杂度 | 简单 | 较高 |
| 推荐程度 | 推荐 | 特定场景 |

## 多主模式的写入分散策略

```
多主模式的最佳实践是"按业务分散写入"：

方案1：按数据库分散
- 成员 A 负责写入 db_orders 相关的业务
- 成员 B 负责写入 db_users 相关的业务
- 成员 C 负责写入 db_products 相关的业务
- 不同成员写不同数据库 → 几乎无冲突

方案2：按业务模块分散
- 成员 A 处理订单创建
- 成员 B 处理用户注册
- 成员 C 处理商品管理
- 每个模块的写入指向固定成员 → 冲突概率低

方案3：按用户 ID 路由（Hash 分散）
- 用户 ID % 3 = 0 → 成员 A
- 用户 ID % 3 = 1 → 成员 B
- 用户 ID % 3 = 2 → 成员 C
- 同一用户的操作在同一成员上 → 无冲突

要避免的反模式：
- 多个成员同时更新同一张热点表的同一行（如库存扣减）
- 不做路由策略，随机选择写入节点
```

## 适用场景

- **写入量超过单节点承受能力的场景**：当业务写入量极大（如物联网数据采集），单个节点的写入吞吐不足时，多主模式可以将写入分散到多个节点。前提是写入的数据分布足够分散，冲突率低
- **需要就近写入的多机房部署**：在同城双机房部署中，每个机房的应用连接本机房的 MGR 成员进行读写，避免跨机房写入延迟。但需要注意跨机房的认证延迟

## 常见问题

**多主模式下事务冲突率高怎么办？**

高冲突率通常意味着多个成员频繁修改同一行数据。解决思路：①优化写入路由策略，确保同一数据的写操作始终路由到同一个成员（消除冲突）；②在应用层实现事务重试逻辑，捕获 ERROR 3101 后自动重试（通常重试 1~2 次即可成功）；③如果冲突率持续很高且无法通过路由策略解决，说明业务模型不适合多主模式，应切换到单主模式。可以通过 `performance_schema.replication_group_member_stats` 中的 `COUNT_TRANSACTIONS_CHECKED` 和 `COUNT_CONFLICTS_DETECTED` 监控冲突率。

## 注意事项

- 多主模式下所有成员的 `super_read_only` 都为 OFF，任何成员都可以执行写操作。应用层的连接池如果没有做好路由策略，可能出现"所有写操作都打到同一个成员"的情况（失去了多主的意义），或者"随机分散导致高冲突率"的情况。多主模式的价值完全取决于应用层的路由策略质量。
- 从多主模式切换到单主模式时（`group_replication_switch_to_single_primary_mode()`），MGR 会等待所有成员上正在执行的事务完成，然后将非 Primary 成员设为 `super_read_only=ON`。如果某个成员上有长事务，切换可能会阻塞较长时间。

## 总结

多主模式（Multi-Primary Mode）允许组内所有成员同时接受读写操作，通过认证机制检测并回滚冲突事务。配置：`group_replication_single_primary_mode=OFF` + `group_replication_enforce_update_everywhere_checks=ON`。在线切换：`group_replication_switch_to_multi_primary_mode()`。限制：不支持 SERIALIZABLE 隔离级别、不推荐外键级联、应用必须处理事务冲突回滚。最佳实践：按业务/数据库/用户 ID 分散写入到不同成员，降低冲突率。适合写入量大且数据分布分散的场景。大多数生产环境仍推荐单主模式，多主模式仅在明确需要多点写入时使用。

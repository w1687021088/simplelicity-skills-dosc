# MGR 限制与注意事项

MySQL Group Replication（MGR）虽然提供了强大的高可用能力，但由于其基于 Paxos 共识和认证机制的架构特点，存在一系列使用限制和约束。理解这些限制对于正确评估 MGR 是否适合特定业务场景、避免部署后出现意外问题至关重要。这些限制涵盖了存储引擎、表结构、事务大小、网络、DDL、数据类型等多个维度。

---

## 存储引擎与表结构限制

```sql
-- 1. 必须使用 InnoDB 引擎
-- MGR 强制要求所有参与复制的表使用 InnoDB
-- 建议在 my.cnf 中禁用其他引擎：
-- disabled_storage_engines = "MyISAM,BLACKHOLE,FEDERATED,ARCHIVE,MEMORY"

-- 检查非 InnoDB 表：
SELECT TABLE_SCHEMA, TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE ENGINE != 'InnoDB'
    AND TABLE_TYPE = 'BASE TABLE'
    AND TABLE_SCHEMA NOT IN ('mysql', 'information_schema', 
                              'performance_schema', 'sys');

-- 2. 所有表必须有主键（或非 NULL 唯一键）
-- 认证机制通过主键标识被修改的行
-- 没有主键的表无法生成写入集 → 事务可能失败
-- 建议启用强制主键：
SET GLOBAL sql_require_primary_key = ON;

-- 3. binlog_format 必须为 ROW
-- MGR 不支持 STATEMENT 或 MIXED 格式
SHOW VARIABLES LIKE 'binlog_format';
-- binlog_format: ROW
```

## 事务限制

```sql
-- 1. 事务大小限制
SHOW VARIABLES LIKE 'group_replication_transaction_size_limit';
-- group_replication_transaction_size_limit: 150000000（约 143MB）
-- 超过此大小的事务会被拒绝
-- 影响场景：大批量 INSERT、LOAD DATA、大表 DDL
-- 解决方案：分批执行（每批控制在限制之内）

-- 2. 不支持 SERIALIZABLE 隔离级别（多主模式）
-- 多主模式下 SERIALIZABLE 会被拒绝
-- 单主模式下可以使用但不推荐

-- 3. 不支持 SAVEPOINT（有限制）
-- 在某些情况下 SAVEPOINT 和 ROLLBACK TO SAVEPOINT 可能导致问题
-- 建议避免在 MGR 环境中使用 SAVEPOINT

-- 4. 不支持显式的表锁（LOCK TABLES / UNLOCK TABLES）
-- LOCK TABLES 在 MGR 中不能跨成员生效
-- 多主模式下使用 LOCK TABLES 可能导致不可预期的行为

-- 5. 事务依赖检测
-- MGR 使用乐观并发控制（先执行后认证）
-- 长事务在执行期间其他成员可能已提交冲突事务
-- 导致长事务在认证阶段被回滚（浪费执行时间）
-- 建议：控制事务大小和执行时间，避免长事务
```

## 网络与成员限制

```sql
-- 1. 最大成员数：9 个
-- 推荐奇数：3、5、7
-- 容错能力：(N-1)/2 个节点
-- 3 个成员：容忍 1 个故障
-- 5 个成员：容忍 2 个故障
-- 7 个成员：容忍 3 个故障

-- 2. 网络延迟要求
-- MGR 的事务提交需要多数派确认
-- 事务延迟 ≈ 网络 RTT × (确认轮数)
-- 同机房（RTT < 1ms）：最佳性能
-- 同城（RTT 1~5ms）：可接受
-- 跨城（RTT > 20ms）：不推荐
-- 跨国（RTT > 100ms）：不可用

-- 3. 网络分区
-- 少数派分区的成员无法提交事务
-- 如果 group_replication_unreachable_majority_timeout = 0（默认）
-- 少数派成员无限等待，需要手动干预

-- 4. 所有成员必须版本兼容
-- 推荐所有成员使用相同的 MySQL 版本
-- 混合版本时低版本成员优先成为 Primary
```

## DDL 限制

```sql
-- 1. DDL 不经过认证的冲突检测
-- DDL（ALTER TABLE 等）不生成写入集
-- DDL 通过全序广播保证在所有成员上执行
-- 但 DDL 和 DML 并发可能导致问题

-- 2. 多主模式下的 DDL 注意事项
-- 避免在多个成员上同时对同一张表执行 DDL
-- DDL 在执行期间会获取元数据锁（MDL）
-- 跨成员的 DDL 并发可能导致死锁或超时

-- 3. 大表 DDL 的影响
-- ALTER TABLE 可能产生大事务（超过 transaction_size_limit）
-- 建议使用 pt-online-schema-change 或 gh-ost 执行在线 DDL
-- MySQL 8.0 的 Instant DDL（ALTER TABLE ... ALGORITHM=INSTANT）
-- 不产生大事务，适合 MGR 环境

-- 4. CREATE TABLE ... SELECT 不支持
-- enforce_gtid_consistency = ON 禁止此语法
-- 替代方案：CREATE TABLE ... LIKE + INSERT INTO ... SELECT
```

## 数据类型与功能限制

```sql
-- 1. 外键（Foreign Key）
-- 单主模式：支持（但级联操作可能影响性能）
-- 多主模式：不推荐（级联操作在不同成员上执行顺序可能不同）

-- 2. 自增列（AUTO_INCREMENT）
-- MGR 中每个成员分配不同的自增区间
-- group_replication_auto_increment_increment 默认为 7
-- 自增值可能不连续（如 1, 8, 15, 22...）
-- 如果业务依赖连续自增 ID → 需要调整设计

-- 查看自增配置：
SHOW VARIABLES LIKE 'group_replication_auto_increment_increment';
-- 默认 7（即使只有 3 个成员，也预留了 7 个间隔）

-- 3. 大字段（TEXT/BLOB/JSON）
-- 大字段会增加写入集和 binlog 事件的大小
-- 可能触发事务大小限制
-- 建议大字段单独存储或控制大小

-- 4. 临时表
-- 临时表不参与复制（这是 binlog 的行为，非 MGR 特有）
-- 但 enforce_gtid_consistency = ON 限制事务内创建/删除临时表
```

## 性能相关限制

| 限制因素 | 影响 | 缓解措施 |
|---------|------|---------|
| 网络延迟 | 每个事务增加 RTT 延迟 | 同机房部署 |
| 认证开销 | CPU 消耗增加 | 优化写入集大小 |
| 大事务 | 广播耗时长，认证慢 | 分批执行，控制事务大小 |
| 热点行冲突 | 事务回滚率高 | 单主模式或优化写入路由 |
| Flow Control | 整体写入速率受限于最慢成员 | 成员硬件配置均衡 |
| 成员数增加 | 共识延迟增加 | 控制在 3~5 个成员 |

## 适用场景

- **MGR 部署前的可行性评估**：在决定使用 MGR 之前，需要逐一检查业务是否触及 MGR 的限制条件。如果业务大量使用 MyISAM 表、缺少主键、依赖大事务或 SERIALIZABLE 隔离级别，则需要先进行改造
- **MGR 环境下的应用开发规范制定**：基于 MGR 的限制，为开发团队制定数据库使用规范，如"所有表必须有主键"、"禁止 CREATE TABLE ... SELECT"、"事务行数不超过 10 万"等

## 常见问题

**从传统主从复制迁移到 MGR，需要做哪些改造？**

主要改造项：①确保所有表使用 InnoDB 引擎（转换 MyISAM 表）；②确保所有表有主键（为缺少主键的表添加主键）；③确保 `binlog_format=ROW`（通常 MySQL 8.0 默认就是 ROW）；④检查是否有 `CREATE TABLE ... SELECT` 语句（改为 `CREATE TABLE LIKE` + `INSERT SELECT`）；⑤检查事务内是否有混合引擎操作（消除）；⑥评估事务大小是否超过 `group_replication_transaction_size_limit`（大批量操作改为分批）；⑦如果使用多主模式，评估外键和隔离级别的使用情况。

---

## 注意事项

- MGR 的认证机制是**乐观并发控制**，事务先完整执行再认证。如果事务执行了 10 秒然后在认证阶段被回滚，这 10 秒的计算资源就浪费了。因此在高冲突场景下（如秒杀），MGR 的性能可能反而不如传统主从复制。建议在这类场景下使用单主模式，并在应用层做好并发控制。
- MGR 要求 `log_replica_updates=ON`（从库也将回放的事务写入自己的 binlog），这会增加从库的磁盘 I/O 和存储空间。如果从库的磁盘性能较差，可能成为性能瓶颈。

---

## 总结

MGR 的主要限制包括：存储引擎（必须 InnoDB）、表结构（必须有主键）、binlog 格式（必须 ROW）、事务大小（默认 143MB 上限）、成员数（最多 9 个，推荐 3~7）、网络（推荐同机房低延迟）、DDL（不经过写入集认证，并发需谨慎）、自增列（不连续，间隔默认 7）、外键（多主模式不推荐）、隔离级别（多主不支持 SERIALIZABLE）。部署前需进行可行性评估，确认业务不触及关键限制。迁移到 MGR 的主要改造：InnoDB 引擎转换、添加主键、消除不兼容语法。

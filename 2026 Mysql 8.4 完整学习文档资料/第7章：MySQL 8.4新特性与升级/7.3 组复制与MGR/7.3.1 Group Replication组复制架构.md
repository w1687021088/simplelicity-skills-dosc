# Group Replication 组复制架构

MySQL Group Replication（简称 MGR）是 MySQL 5.7.17 引入的原生高可用解决方案，提供基于分布式状态机的多主或单主复制架构。与传统的主从复制不同，MGR 中的所有成员组成一个"组"（Group），通过 Paxos 协议的变体（XCom）进行通信和协调，确保组内所有成员的数据一致性。MGR 支持自动故障检测、自动主选举、在线成员变更等特性，是 MySQL InnoDB Cluster 的核心组件。

---

## 架构概述

```
Group Replication 的整体架构：

┌──────────────────────────────────────────────┐
│                   Group（组）                 │
│                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ Member 1 │  │ Member 2 │  │ Member 3 │   │
│  │ (Primary)│  │(Secondary│  │(Secondary│   │
│  │  R/W     │  │  R/O)    │  │  R/O)    │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
│       │              │              │        │
│  ┌────┴──────────────┴──────────────┴────┐   │
│  │          XCom 通信层（Paxos）          │   │
│  │     组成员管理 / 消息广播 / 排序       │   │
│  └───────────────────────────────────────┘   │
└──────────────────────────────────────────────┘

- 每个 Member 是一个完整的 MySQL 实例
- 通过 XCom（Group Communication System）进行成员间通信
- 所有写操作经过组内认证（Certification）后才能提交
- 组内成员数建议为奇数（3、5、7），容忍 (N-1)/2 个节点故障
```

## 核心组件

```
1. Group Communication System (GCS) / XCom
   - 基于 Paxos 协议的通信层
   - 负责组成员管理（加入/离开/故障检测）
   - 保证消息的全序广播（Total Order Broadcast）
   - 所有成员看到相同顺序的事务

2. Certification（认证/冲突检测）
   - 每个事务在提交前被发送到组内所有成员
   - 所有成员独立执行冲突检测（基于写入集）
   - 如果事务与其他并发事务冲突 → 回滚
   - 如果无冲突 → 在所有成员上提交
   - 确保所有成员数据一致

3. Applier（回放）
   - 通过认证的事务在每个成员上异步回放
   - 使用多线程回放（类似 MTS）
   - 本地执行的事务直接提交（已通过认证）
   - 远程事务通过 relay log 回放

4. Recovery（恢复）
   - 新成员加入组时的数据同步机制
   - 可以使用 binlog 传输（增量恢复）
   - 或使用 Clone Plugin（全量恢复）
```

## 基本配置

```ini
# my.cnf 基本配置（每个成员都需要）
[mysqld]
# 基本复制配置
server_id = 1                          # 每个成员不同
gtid_mode = ON                         # MGR 强制要求
enforce_gtid_consistency = ON          # MGR 强制要求
binlog_checksum = NONE                 # MySQL 8.0.21 之前要求
log_bin = mysql-bin
log_replica_updates = ON               # 必须开启
binlog_format = ROW                    # MGR 强制要求 ROW 格式

# 禁用非事务引擎（MGR 要求）
disabled_storage_engines = "MyISAM,BLACKHOLE,FEDERATED,ARCHIVE,MEMORY"

# Group Replication 配置
plugin_load_add = 'group_replication.so'
group_replication_group_name = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"
group_replication_start_on_boot = OFF  # 首次部署时建议 OFF
group_replication_local_address = "192.168.1.101:33061"
group_replication_group_seeds = "192.168.1.101:33061,192.168.1.102:33061,192.168.1.103:33061"
group_replication_single_primary_mode = ON    # 单主模式（推荐）
```

## 启动 Group Replication

```sql
-- 第一个成员（引导组）：
SET GLOBAL group_replication_bootstrap_group = ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group = OFF;

-- 后续成员（加入已有组）：
START GROUP_REPLICATION;

-- 查看组成员状态：
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT, MEMBER_STATE, MEMBER_ROLE
FROM performance_schema.replication_group_members;
-- MEMBER_STATE: ONLINE（正常）, RECOVERING（恢复中）, ERROR（错误）
-- MEMBER_ROLE: PRIMARY（主节点）, SECONDARY（从节点）

-- 停止 Group Replication：
STOP GROUP_REPLICATION;
```

## MGR 与传统复制对比

| 对比维度 | 传统主从复制 | Group Replication（MGR）|
|---------|:----------:|:---------------------:|
| 故障转移 | 手动或依赖外部工具（MHA）| 自动主选举 |
| 数据一致性 | 异步/半同步（可能丢数据）| 强一致（Paxos 共识）|
| 写入节点 | 单主 | 单主或多主 |
| 冲突检测 | 无 | 内置（基于写入集）|
| 成员管理 | 手动配置 | 自动（加入/离开/故障检测）|
| 拓扑变更 | 复杂 | 自动适应 |
| 网络分区处理 | 无 | 多数派原则 |
| 最大成员数 | 无限制 | 9（推荐 3~7）|

## 适用场景

- **需要自动故障转移的关键业务系统**：传统主从复制的故障转移依赖外部工具（MHA、Orchestrator），MGR 内置自动主选举，Primary 故障后几秒内自动选出新 Primary，业务中断时间极短
- **对数据一致性要求严格的金融/交易系统**：MGR 通过 Paxos 共识和冲突认证保证所有成员数据一致，不存在传统异步复制中从库数据落后的问题（已通过认证的事务保证在所有成员上最终一致）

## 常见问题

**MGR 最多支持多少个成员？性能会随成员数增加而下降吗？**

MGR 最多支持 9 个成员。实际部署中推荐 3、5 或 7 个成员（奇数，便于多数派决策）。性能随成员数增加会有一定下降，主要原因是 Paxos 共识需要多数成员确认（3 个成员需要 2 个确认，5 个需要 3 个），成员越多，网络往返时间越长。在同机房 3 个成员的配置下，事务提交延迟通常增加 1~3ms。跨机房部署时，网络延迟是主要瓶颈（RTT 可能 5~50ms），不建议超过 3 个机房。

## 注意事项

- MGR 要求所有表使用 InnoDB 引擎并且有主键（或非 NULL 唯一键）。没有主键的表在认证阶段无法生成写入集，会导致事务被拒绝。部署前应通过 `SELECT TABLE_SCHEMA, TABLE_NAME FROM information_schema.TABLES WHERE ENGINE != 'InnoDB' AND TABLE_SCHEMA NOT IN (...)` 检查非 InnoDB 表。
- MGR 不支持大事务（默认事务大小限制 `group_replication_transaction_size_limit = 150000000`，约 143MB）。超过此限制的事务（如大批量 INSERT）会被拒绝。大批量数据操作应分批执行。

## 总结

MySQL Group Replication（MGR）是基于 Paxos 共识协议的原生高可用解决方案。架构：多个 MySQL 实例组成一个"组"，通过 XCom 通信层保证消息全序广播和成员管理。核心流程：事务提交 → 广播到组 → 所有成员认证（冲突检测）→ 无冲突则提交。两种模式：单主模式（推荐，一个 Primary 读写，其他 Secondary 只读）和多主模式（所有成员可读写，需处理冲突）。强制要求：`gtid_mode=ON`、`binlog_format=ROW`、InnoDB 引擎、表有主键。最多 9 个成员，推荐 3~7 个（奇数）。自动故障检测和主选举，故障转移时间几秒。

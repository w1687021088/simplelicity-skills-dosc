# 流控机制 Flow Control

Flow Control（流控）是 MySQL Group Replication 中防止快成员和慢成员之间数据差距过大的机制。在 MGR 组中，所有成员通过认证后需要在本地回放事务。如果某个成员的回放速度较慢（如硬件较差或 I/O 瓶颈），它的待回放事务队列会不断增长，与其他成员的数据差距越来越大。Flow Control 通过限制写入速率（让快成员"慢下来"）来缩小这个差距，确保所有成员的数据保持相对同步。

---

## Flow Control 的工作原理

```
Flow Control 的核心思想：

1. 监控阶段
   - 每个成员定期报告自己的待认证队列和待回放队列长度
   - 通过 performance_schema.replication_group_member_stats 可查看

2. 触发条件
   - 当某个成员的待认证队列或待回放队列超过阈值时触发
   - 阈值由 group_replication_flow_control_applier_threshold 控制
   - 默认值：25000（待回放事务数）

3. 限流动作
   - 触发后，Flow Control 限制组内的写入速率
   - 具体方式：在 Primary 的事务提交路径上增加等待时间
   - 等待时间根据慢成员的回放速度动态计算
   - 目标：让写入速率 ≈ 最慢成员的回放速率

4. 解除条件
   - 当所有成员的队列长度降到阈值以下时
   - Flow Control 解除限制，恢复正常写入速率
```

## Flow Control 相关参数

```sql
-- 查看所有 Flow Control 参数：
SHOW VARIABLES LIKE 'group_replication_flow_control%';

-- 1. 是否启用 Flow Control（默认启用）
SHOW VARIABLES LIKE 'group_replication_flow_control_mode';
-- group_replication_flow_control_mode: QUOTA（默认，启用配额限制）
-- 可选值：QUOTA（启用）、DISABLED（禁用）

-- 2. Applier 队列阈值（待回放事务数）
SHOW VARIABLES LIKE 'group_replication_flow_control_applier_threshold';
-- group_replication_flow_control_applier_threshold: 25000
-- 当某成员的 applier 队列超过此值时触发 Flow Control

-- 3. Certifier 队列阈值（待认证事务数）
SHOW VARIABLES LIKE 'group_replication_flow_control_certifier_threshold';
-- group_replication_flow_control_certifier_threshold: 25000
-- 当某成员的 certifier 队列超过此值时触发 Flow Control

-- 4. 最小配额（每秒最少允许的事务数）
SHOW VARIABLES LIKE 'group_replication_flow_control_min_quota';
-- group_replication_flow_control_min_quota: 0
-- 0 表示自动计算，非 0 表示强制最低写入速率

-- 5. 最小恢复配额
SHOW VARIABLES LIKE 'group_replication_flow_control_min_recovery_quota';
-- group_replication_flow_control_min_recovery_quota: 0

-- 6. 最大配额
SHOW VARIABLES LIKE 'group_replication_flow_control_max_quota';
-- group_replication_flow_control_max_quota: 0
-- 0 表示不限制最大写入速率

-- 7. 配额释放比例
SHOW VARIABLES LIKE 'group_replication_flow_control_hold_percent';
-- group_replication_flow_control_hold_percent: 10
-- 配额的百分比保留，避免突发写入

-- 8. 队列消耗比例
SHOW VARIABLES LIKE 'group_replication_flow_control_release_percent';
-- group_replication_flow_control_release_percent: 50
```

## 监控 Flow Control 状态

```sql
-- 查看各成员的队列状态：
SELECT MEMBER_ID,
       COUNT_TRANSACTIONS_IN_QUEUE AS certifier_queue,
       COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE AS applier_queue,
       COUNT_TRANSACTIONS_CHECKED AS total_certified,
       COUNT_CONFLICTS_DETECTED AS conflicts,
       COUNT_TRANSACTIONS_REMOTE_APPLIED AS remote_applied
FROM performance_schema.replication_group_member_stats;

-- 关键指标解读：
-- certifier_queue：待认证事务队列长度
--   正常值：< 100
--   预警值：> 1000
--   触发 Flow Control：> 25000（默认阈值）

-- applier_queue：待回放事务队列长度
--   正常值：< 100
--   预警值：> 1000
--   触发 Flow Control：> 25000（默认阈值）

-- 如果某个成员的 applier_queue 持续增长：
-- 说明该成员的回放速度跟不上组内的写入速度
-- Flow Control 会降低整个组的写入速率
```

## 调优建议

```ini
# 生产环境推荐配置

# 场景1：写入量大、对延迟敏感（降低阈值，早触发 Flow Control）
[mysqld]
group_replication_flow_control_mode = QUOTA
group_replication_flow_control_applier_threshold = 10000
group_replication_flow_control_certifier_threshold = 10000

# 场景2：写入量小、成员间性能差异大（保持默认）
[mysqld]
group_replication_flow_control_mode = QUOTA
group_replication_flow_control_applier_threshold = 25000

# 场景3：测试环境、不关心成员间数据差距（禁用 Flow Control）
[mysqld]
group_replication_flow_control_mode = DISABLED
# 警告：禁用 Flow Control 可能导致慢成员严重落后
```

```sql
-- 动态调整（无需重启）：
SET GLOBAL group_replication_flow_control_applier_threshold = 10000;
SET GLOBAL group_replication_flow_control_certifier_threshold = 10000;

-- 临时禁用 Flow Control（紧急排查时）：
SET GLOBAL group_replication_flow_control_mode = 'DISABLED';
-- 排查完毕后恢复：
SET GLOBAL group_replication_flow_control_mode = 'QUOTA';
```

## 适用场景

- **成员间硬件配置不均的 MGR 环境**：当组内有高性能和低性能成员时，Flow Control 确保低性能成员不会无限落后，代价是整体写入速率受限于最慢成员的回放速率
- **写入量波动大的业务系统**：在业务高峰期写入量激增时，Flow Control 自动降速，防止成员间数据差距过大；低峰期自动恢复正常速率

## 常见问题

**Flow Control 触发后，应用感受到的症状是什么？**

应用最直观的感受是事务提交延迟增加。Flow Control 通过在 Primary 的事务提交路径上增加等待时间来限制写入速率，表现为 `COMMIT` 语句的执行时间变长（从正常的几毫秒可能增加到几十甚至几百毫秒）。如果业务对提交延迟敏感，需要关注 `COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE` 指标，一旦持续增长就应排查慢成员的性能瓶颈（磁盘 I/O、CPU、网络等），从根本上解决回放速度不足的问题，而不是简单地调高 Flow Control 阈值或禁用 Flow Control。

---

## 注意事项

- 禁用 Flow Control（`group_replication_flow_control_mode=DISABLED`）虽然可以消除写入延迟，但会导致慢成员的待回放队列无限增长，数据严重落后。极端情况下，慢成员可能需要从头恢复（使用 Clone Plugin），因为 binlog 可能已被 purge。除非是测试环境或有明确理由，否则不建议禁用。
- Flow Control 的限速作用于整个组，即使只有一个慢成员也会影响所有成员的写入速率。如果某个成员因临时问题（如磁盘 I/O 峰值）导致回放变慢，可能拖累整个组的写入性能。及时发现和处理慢成员是保持 MGR 高性能的关键。

---

## 总结

Flow Control 是 MGR 防止成员间数据差距过大的机制。当某个成员的待回放队列超过阈值（`group_replication_flow_control_applier_threshold`，默认 25000）时，自动限制整个组的写入速率至最慢成员的回放速率。核心参数：`flow_control_mode`（QUOTA 启用/DISABLED 禁用）、`applier_threshold`/`certifier_threshold`（触发阈值）。监控：`performance_schema.replication_group_member_stats`（`COUNT_TRANSACTIONS_REMOTE_IN_APPLIER_QUEUE`）。调优：写入敏感场景降低阈值（早触发，减少差距）；解决根本问题应优化慢成员的性能。不建议在生产环境禁用 Flow Control。

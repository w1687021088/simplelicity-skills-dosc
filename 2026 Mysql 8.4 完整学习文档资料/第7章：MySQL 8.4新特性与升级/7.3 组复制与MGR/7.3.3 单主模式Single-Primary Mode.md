# 单主模式 Single-Primary Mode

单主模式（Single-Primary Mode）是 MySQL Group Replication 的默认运行模式，也是生产环境中最推荐的模式。在单主模式下，组内只有一个成员被选为 Primary（主节点），负责处理所有读写操作；其余成员为 Secondary（从节点），只接受只读查询。当 Primary 发生故障时，MGR 自动从 Secondary 中选举新的 Primary，实现自动故障转移。

---

## 单主模式的配置

```ini
# my.cnf 配置（所有成员一致）
[mysqld]
# 启用单主模式（默认值就是 ON）
group_replication_single_primary_mode = ON

# 强制非 Primary 成员为只读（推荐）
group_replication_enforce_update_everywhere_checks = OFF
```

```sql
-- 查看当前模式：
SHOW VARIABLES LIKE 'group_replication_single_primary_mode';
-- group_replication_single_primary_mode: ON

-- 查看当前 Primary 是哪个成员：
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT, MEMBER_ROLE
FROM performance_schema.replication_group_members;
-- MEMBER_ROLE = PRIMARY 的就是主节点
-- 其余为 SECONDARY

-- 也可以通过函数查看 Primary 的 UUID：
SELECT group_replication_get_primary_member();
```

## Secondary 的只读保护

```sql
-- 单主模式下，Secondary 成员自动设为只读：
-- super_read_only = ON（自动设置）

-- Secondary 上执行写操作会报错：
INSERT INTO mydb.t1 VALUES (1);
-- ERROR 1290 (HY000): The MySQL server is running with the
-- --super-read-only option so it cannot execute this statement

-- 当 Secondary 被选举为新 Primary 时：
-- super_read_only 自动设为 OFF
-- 新 Primary 可以正常处理读写操作

-- 当 Primary 降级为 Secondary 时（如手动切主）：
-- super_read_only 自动设为 ON
-- 旧 Primary 变为只读
```

## 手动切换 Primary

```sql
-- MySQL 8.0.13+ 支持在线切换 Primary

-- 将指定成员设为新 Primary：
SELECT group_replication_set_as_primary('member_uuid');
-- member_uuid 是目标成员的 server_uuid
-- 例如：
SELECT group_replication_set_as_primary('3E11FA47-71CA-11E1-9E33-C80AA9429562');

-- 切换过程：
-- 1. 当前 Primary 完成所有正在执行的事务
-- 2. 当前 Primary 设为只读（super_read_only = ON）
-- 3. 目标成员提升为新 Primary（super_read_only = OFF）
-- 4. 所有成员的 MEMBER_ROLE 更新

-- 获取成员 UUID 列表：
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_ROLE
FROM performance_schema.replication_group_members;

-- 在线切换模式（从单主切换到多主）：
SELECT group_replication_switch_to_multi_primary_mode();

-- 从多主切回单主：
SELECT group_replication_switch_to_single_primary_mode();
-- 或指定谁当 Primary：
SELECT group_replication_switch_to_single_primary_mode('member_uuid');
```

## 单主模式的优势

```
与多主模式对比的优势：

1. 无写冲突
   - 只有一个节点接受写操作，不存在并发写入冲突
   - 多主模式下，两个节点同时修改同一行会导致一个事务回滚

2. 应用兼容性好
   - 应用只需连接 Primary 进行读写
   - 不需要处理写冲突和事务回滚重试
   - 与传统主从架构的应用使用方式一致

3. 支持外键和级联操作
   - 多主模式下不推荐使用外键（可能导致复杂的冲突）
   - 单主模式下可以安全使用外键

4. 事务隔离级别灵活
   - 多主模式建议使用 READ COMMITTED
   - 单主模式可以使用任何隔离级别

5. 运维简单
   - 明确的读写节点，监控和排查问题更直观
   - 不需要处理多写冲突的复杂场景
```

## 适用场景

- **绝大多数生产环境的 MGR 部署**：单主模式是 MGR 的默认推荐模式，适合几乎所有业务场景。只有在明确需要多点写入且应用层已做好冲突处理的场景下才考虑多主模式
- **从传统主从复制迁移到 MGR**：单主模式的读写模型与传统主从复制一致（一个写节点、多个读节点），应用层几乎不需要修改，迁移成本最低

## 常见问题

**单主模式下 Primary 故障后，自动选举新 Primary 的耗时是多少？**

自动选举通常在几秒内完成，具体取决于故障检测时间和选举过程。故障检测时间受 `group_replication_member_expel_timeout`（默认 5 秒）影响——成员失联后等待此时间再发起驱逐和选举。选举本身是瞬时的（毫秒级，基于成员权重和 UUID 排序）。总的故障转移时间通常在 5~15 秒之间。应用层需要配合连接池的故障检测机制（如 HikariCP 的 `connectionTimeout`）或 MySQL Router 的自动路由来实现透明的故障转移。

---

## 注意事项

- 单主模式下切换 Primary 时（自动选举或手动 `group_replication_set_as_primary`），正在执行的长事务可能需要等待完成或被 kill。如果旧 Primary 上有长时间运行的事务，切换过程可能会延迟。建议在切换前检查是否有长事务：`SELECT * FROM information_schema.INNODB_TRX WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60`。
- 应用连接到 Primary 节点时，建议通过 MySQL Router 或 ProxySQL 等中间件进行路由，而不是硬编码 Primary 的 IP。否则 Primary 切换后，应用需要手动修改连接地址。

---

## 总结

单主模式（Single-Primary Mode）是 MGR 的默认推荐模式。特点：一个 Primary（读写）+ 多个 Secondary（只读，`super_read_only=ON`）。Primary 故障时自动选举新 Primary（通常 5~15 秒）。手动切主：`SELECT group_replication_set_as_primary('uuid')`。在线模式切换：`group_replication_switch_to_multi_primary_mode()` / `group_replication_switch_to_single_primary_mode()`。优势：无写冲突、应用兼容性好、支持外键、运维简单。适合绝大多数生产环境，与传统主从架构迁移成本最低。

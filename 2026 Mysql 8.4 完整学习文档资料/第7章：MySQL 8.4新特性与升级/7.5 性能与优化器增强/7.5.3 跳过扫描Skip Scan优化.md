# 跳过扫描 Skip Scan 优化

Skip Scan 是 MySQL 8.0.13 引入的索引扫描优化策略，允许优化器在查询条件不包含复合索引前导列时，仍然利用该复合索引进行查询。在传统的索引使用规则中，如果复合索引的前导列没有出现在 WHERE 条件中，该索引无法被使用（"最左前缀原则"）。Skip Scan 通过在前导列的不同值之间"跳跃"扫描，突破了这一限制，在特定条件下显著提升查询性能。

---

## 传统索引使用的限制

```sql
-- 假设有复合索引：INDEX idx_gender_age (gender, age)

-- 传统规则下：
-- 查询1：WHERE gender = 'M' AND age > 25
-- → 使用 idx_gender_age ✓（前导列 gender 在条件中）

-- 查询2：WHERE age > 25
-- → 无法使用 idx_gender_age ✗（缺少前导列 gender）
-- → 只能全表扫描或使用 age 列上的独立索引（如果有）

-- Skip Scan 优化后：
-- 查询2：WHERE age > 25
-- → 可以使用 idx_gender_age ✓
-- 优化器将查询等效转换为：
-- WHERE gender = 'F' AND age > 25
-- UNION ALL
-- WHERE gender = 'M' AND age > 25
-- 在 gender 的每个不同值上分别进行范围扫描
```

---

## Skip Scan 的工作原理

```
索引 idx_gender_age 的 B-Tree 结构：

gender='F', age=18
gender='F', age=22
gender='F', age=25
gender='F', age=30
gender='F', age=35
gender='M', age=20
gender='M', age=23
gender='M', age=28
gender='M', age=32
gender='M', age=40

查询：WHERE age > 30

传统方式（不用 Skip Scan）：
  全表扫描所有行，逐一检查 age > 30 → 慢

Skip Scan 方式：
  步骤1：扫描 gender='F' 的范围，找到 age > 30 的行
    → gender='F', age=35 ✓
  步骤2：跳过到 gender='M' 的范围，找到 age > 30 的行
    → gender='M', age=32 ✓
    → gender='M', age=40 ✓
  完成！只扫描了索引中的相关部分

关键前提：前导列的不同值数量（NDV）必须很少
  gender 只有 F/M 两个值 → 只需要跳 2 次 → 高效
  如果前导列有 10000 个不同值 → 需要跳 10000 次 → 不如全表扫描
```

## 触发条件

```sql
-- Skip Scan 的触发条件：
-- 1. 复合索引的前导列不在 WHERE 条件中
-- 2. 前导列的不同值数量（NDV）很少（如 gender、status 等低基数列）
-- 3. 查询条件包含非前导列的范围条件或等值条件
-- 4. optimizer_switch 中 skip_scan=on（默认开启）

-- 检查 Skip Scan 是否启用：
SELECT @@optimizer_switch LIKE '%skip_scan=on%';

-- 在 EXPLAIN 中识别 Skip Scan：
EXPLAIN SELECT * FROM employees WHERE age > 30;
-- type: range
-- key: idx_gender_age
-- Extra: Using index for skip scan
-- ↑ 关键标识：Using index for skip scan

-- EXPLAIN FORMAT=TREE 中的显示：
EXPLAIN FORMAT=TREE SELECT * FROM employees WHERE age > 30;
-- -> Index range scan on employees using idx_gender_age 
--    over (gender = 'F' AND 30 < age), (gender = 'M' AND 30 < age)
--    (cost=... rows=...)
```

## 控制 Skip Scan

```sql
-- 通过 optimizer_switch 控制：

-- 全局禁用 Skip Scan：
SET GLOBAL optimizer_switch = 'skip_scan=off';

-- 会话级别禁用：
SET SESSION optimizer_switch = 'skip_scan=off';

-- 恢复：
SET SESSION optimizer_switch = 'skip_scan=on';

-- 通过 Hint 控制单条查询：
-- 强制不使用 Skip Scan：
SELECT /*+ NO_SKIP_SCAN(employees idx_gender_age) */
    * FROM employees WHERE age > 30;

-- 强制使用 Skip Scan：
SELECT /*+ SKIP_SCAN(employees idx_gender_age) */
    * FROM employees WHERE age > 30;
```

## Skip Scan 适用与不适用的场景

| 条件 | 是否适用 Skip Scan | 原因 |
|-----|:-----------------:|------|
| 前导列 NDV=2（如 gender）| 适用 | 只需跳 2 次 |
| 前导列 NDV=5（如 status）| 通常适用 | 跳 5 次开销小 |
| 前导列 NDV=100 | 不适用 | 跳 100 次开销大 |
| 前导列 NDV=10000 | 不适用 | 不如全表扫描 |
| 非前导列是等值条件 | 适用 | 每次跳转后精确匹配 |
| 非前导列是范围条件 | 适用 | 每次跳转后范围扫描 |
| 查询需要回表（非覆盖索引）| 可能适用 | 取决于回表行数 |
| 查询是覆盖索引 | 更适用 | 无需回表，效率更高 |

---

## 适用场景

- **低基数前导列 + 高基数后续列的复合索引**：典型场景是 `INDEX(gender, age)` 或 `INDEX(status, created_at)`，前导列只有少数几个值，后续列的查询条件经常单独出现。Skip Scan 避免了为后续列单独创建索引的需要
- **遗留系统中已有复合索引但缺少合适单列索引的场景**：如果修改索引结构的成本较高（如大表 DDL 耗时长），Skip Scan 可以在不修改索引的情况下提升查询性能

---

## 常见问题

**Skip Scan 是否可以完全替代在非前导列上创建独立索引？**

不能完全替代。Skip Scan 的效率取决于前导列的 NDV——NDV 越大，Skip Scan 的开销越高。当前导列 NDV 超过一定阈值时（通常几十到几百个不同值），Skip Scan 的性能反而不如全表扫描或独立索引。如果非前导列经常被单独查询且前导列 NDV 较高，仍然建议为非前导列创建独立索引。Skip Scan 是一种"在没有更好选择时的优化"，不应该成为索引设计的替代方案。

---

## 注意事项

- Skip Scan 只在 `optimizer_switch` 中 `skip_scan=on` 时生效（MySQL 8.0.13+ 默认开启）。如果升级到 MySQL 8.0.13+ 后发现某些查询的执行计划发生了变化（可能变好也可能变差），可以通过 `skip_scan=off` 或 `NO_SKIP_SCAN` Hint 回退到旧的行为。
- Skip Scan 的性能提升幅度取决于前导列 NDV 和表的大小。对于前导列 NDV=2 的百万行大表，Skip Scan 可能将全表扫描（100 万行）优化为两次范围扫描（总计可能只需扫描几万行）。但对于小表（几千行），Skip Scan 的优化效果不明显。

---

## 总结

Skip Scan 是 MySQL 8.0.13 引入的索引优化策略，允许在查询条件缺少复合索引前导列时仍利用该索引。原理：在前导列的每个不同值上分别执行范围扫描（"跳跃"扫描）。关键前提：前导列 NDV 很少（如 2~10 个不同值）。识别：`EXPLAIN` 中 `Extra: Using index for skip scan`。控制：`optimizer_switch` 的 `skip_scan` 标志或 `SKIP_SCAN`/`NO_SKIP_SCAN` Hint。不适合前导列 NDV 高的场景。不能替代独立索引的设计，是"没有更好索引时的优化补充"。

# 哈希连接内存控制 hash_join_buffer_size

MySQL 8.0.18 引入了哈希连接（Hash Join）算法，替代了传统的 Block Nested Loop（BNL）算法，用于处理没有索引的等值 JOIN 操作。哈希连接的核心是在内存中构建哈希表来加速匹配，其内存使用量由 `join_buffer_size` 参数控制。当哈希表超出内存限制时，MySQL 会将部分数据溢写到磁盘，采用分区处理策略。理解哈希连接的内存控制机制，对于优化大表 JOIN 性能至关重要。

---

## 哈希连接的工作原理

```
Hash Join 的两阶段执行：

阶段1：Build Phase（构建阶段）
  - 选择较小的表（Build Table）
  - 将 Build Table 的 JOIN 列值计算哈希并存入内存哈希表
  - 如果内存不足 → 将部分分区溢写到磁盘（Grace Hash Join）

阶段2：Probe Phase（探测阶段）
  - 扫描较大的表（Probe Table）
  - 对每行计算 JOIN 列的哈希值
  - 在哈希表中查找匹配（O(1) 复杂度）
  - 匹配成功 → 输出 JOIN 结果

与传统 Nested Loop 的对比：
  Nested Loop：对外表每行，扫描内表一次 → O(N × M)
  Hash Join：构建哈希表 O(N) + 探测 O(M) → O(N + M)
  当 N 和 M 都很大时，Hash Join 优势明显
```

## 内存控制参数

```sql
-- Hash Join 使用 join_buffer_size 控制内存
SHOW VARIABLES LIKE 'join_buffer_size';
-- join_buffer_size: 262144（默认 256KB）

-- 设置 join_buffer_size（会话级别）：
SET SESSION join_buffer_size = 4194304;  -- 4MB

-- 全局设置：
SET GLOBAL join_buffer_size = 4194304;

-- 持久化配置（my.cnf）：
-- [mysqld]
-- join_buffer_size = 4M

-- 注意：join_buffer_size 是每个 JOIN 操作分配的内存
-- 如果查询有多个 JOIN，每个 JOIN 都会分配一个 buffer
-- 100 个并发连接 × 3 个 JOIN × 4MB = 1.2GB 内存
-- 设置过大可能导致内存不足

-- 推荐值：
-- OLTP 系统：256KB ~ 4MB
-- 分析型查询：4MB ~ 64MB（会话级别设置）
```

## 内存不足时的溢写机制

```sql
-- 当 Build Table 的哈希表超过 join_buffer_size 时：
-- MySQL 使用 Grace Hash Join 策略

-- Grace Hash Join 流程：
-- 1. 将 Build Table 按哈希值分成多个分区（Partition）
-- 2. 能放入内存的分区保留在内存中
-- 3. 放不下的分区溢写到磁盘临时文件
-- 4. 对 Probe Table 也按相同哈希函数分区
-- 5. 逐个分区进行内存中的哈希匹配
-- 6. 磁盘上的分区需要读回内存处理

-- 溢写到磁盘后的性能影响：
-- 额外的磁盘 I/O（写入 + 读取临时文件）
-- 性能显著下降（从毫秒级可能变为秒级）
-- 临时文件位置由 tmpdir 参数指定

-- 监控是否发生了磁盘溢写：
-- 目前 MySQL 没有直接的状态变量监控 Hash Join 溢写
-- 间接指标：
SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables';
-- 如果 Hash Join 溢写，Created_tmp_disk_tables 会增加
```

## 哈希连接的触发条件

```sql
-- Hash Join 在以下条件下自动触发：
-- 1. 等值 JOIN 条件（ON a.id = b.id）
-- 2. JOIN 列上没有可用的索引
-- 3. optimizer_switch 中 hash_join=on（MySQL 8.0.18 默认 OFF，8.0.20+ 默认 ON）

-- 检查 hash_join 是否启用：
SHOW VARIABLES LIKE 'optimizer_switch';
-- 查找 hash_join=on

-- 在 EXPLAIN 中识别 Hash Join：
EXPLAIN FORMAT=TREE
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id;
-- -> Inner hash join (o.customer_id = c.id)
--     -> Table scan on o
--     -> Hash
--         -> Table scan on c

-- 如果 JOIN 列有索引，优化器通常选择 Nested Loop（更优）
-- Hash Join 主要用于无索引的 JOIN 场景

-- 强制使用 Hash Join（通过 Hint）：
SELECT /*+ HASH_JOIN(o, c) */
    * FROM orders o JOIN customers c ON o.customer_id = c.id;

-- 禁止使用 Hash Join：
SELECT /*+ NO_HASH_JOIN(o, c) */
    * FROM orders o JOIN customers c ON o.customer_id = c.id;
```

## join_buffer_size 调优建议

| 场景 | 推荐值 | 说明 |
|-----|:-----:|------|
| OLTP（高并发短查询）| 256KB ~ 1MB | 避免内存占用过高 |
| OLAP（分析型查询）| 4MB ~ 64MB | 减少磁盘溢写 |
| 特定大查询 | 会话级设置 128MB | 只在该查询连接中设置 |
| Build Table < 1MB | 默认 256KB 足够 | 无需调整 |
| Build Table 10MB~100MB | 16MB ~ 128MB | 尽量容纳在内存中 |
| Build Table > 1GB | 考虑添加索引 | Hash Join 不是最优方案 |

## 适用场景

- **临时性的大表 JOIN 分析查询**：在数据分析或报表场景中，经常需要 JOIN 没有索引的临时表或子查询结果。通过在会话级别增大 `join_buffer_size`，可以让 Hash Join 在内存中完成匹配，避免磁盘溢写带来的性能下降
- **数据仓库或 ETL 场景**：ETL 过程中的大表 JOIN 操作通常没有索引（数据是临时加载的），Hash Join 是主要的 JOIN 策略，合理设置 `join_buffer_size` 对 ETL 性能影响显著

## 常见问题

**Hash Join 和 Nested Loop Join 哪个更快？**

取决于场景。如果 JOIN 列有索引，Nested Loop（通过索引查找）通常更快，因为每次查找只需 O(log N) 的 B-Tree 遍历。如果 JOIN 列没有索引，Hash Join（O(N+M)）远优于 Block Nested Loop（O(N×M)）。优化器会自动选择最优的 JOIN 算法，大多数情况下不需要手动干预。只有在优化器选择错误时，才需要通过 `HASH_JOIN` / `NO_HASH_JOIN` Hint 手动指定。最佳实践：优先为 JOIN 列创建索引（让 Nested Loop 高效工作），只在无法添加索引的场景下依赖 Hash Join。

---

## 注意事项

- `join_buffer_size` 是**每个 JOIN 操作**分配的内存，而不是每个查询或每个连接。如果一个查询有 5 个 JOIN 都使用了 Hash Join，内存消耗是 `5 × join_buffer_size`。在高并发环境中，过大的 `join_buffer_size` 可能导致总内存消耗失控。建议在全局层面保持较小值（如 1MB），在需要大 JOIN 的特定查询中通过会话级别临时增大。
- Hash Join 只支持等值条件（`=`），不支持非等值条件（`>`、`<`、`!=`、`LIKE`）。非等值 JOIN 仍然使用 Nested Loop 算法。

---

## 总结

Hash Join 是 MySQL 8.0.18+ 引入的等值 JOIN 算法，用于无索引的 JOIN 场景，时间复杂度 O(N+M) 优于 Nested Loop 的 O(N×M)。内存由 `join_buffer_size` 控制（默认 256KB），超出时溢写到磁盘（Grace Hash Join，性能下降）。调优：OLTP 保持 256KB~1MB（全局），分析查询临时增大到 4MB~64MB（会话级别）。触发条件：等值 JOIN + 无索引。`EXPLAIN FORMAT=TREE` 中显示 `Inner hash join`。Hint 控制：`HASH_JOIN` / `NO_HASH_JOIN`。注意每个 JOIN 独立分配 buffer，高并发时总内存需评估。

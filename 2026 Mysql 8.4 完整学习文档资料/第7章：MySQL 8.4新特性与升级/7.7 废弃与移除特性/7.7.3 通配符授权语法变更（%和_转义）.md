# 通配符授权语法变更（% 和 _ 转义）

MySQL 8.0 对 `GRANT` 语句中数据库名称的通配符匹配行为进行了调整和规范化。在旧版本中，`GRANT ... ON db_name.* TO user` 语句中的数据库名称支持 `%`（匹配任意多个字符）和 `_`（匹配单个字符）作为通配符，但这种行为经常导致混淆和安全隐患。MySQL 8.0 对这一行为进行了明确规范，并引入了 `partial_revokes` 系统变量来配合更精细的权限控制。

---

## 旧版本的通配符行为

```sql
-- 在 MySQL 5.7 及之前版本中：
-- GRANT 语句的数据库名称中 % 和 _ 被视为通配符

-- 授予对所有以 "test" 开头的数据库的权限：
GRANT ALL ON `test%`.* TO 'user1'@'%';
-- 匹配：test, test1, test_db, testing 等所有以 test 开头的库

-- 授予对 "db" + 任意单字符的数据库的权限：
GRANT ALL ON `db_`.* TO 'user1'@'%';
-- 匹配：db1, db2, dba, dbx 等 db 后面跟一个字符的库
-- 注意：也匹配 db_（下划线本身）

-- 问题：如果数据库名称本身包含 % 或 _
-- 例如数据库名为 "my_app"
GRANT ALL ON `my_app`.* TO 'user1'@'%';
-- 这里的 _ 到底是通配符还是字面字符？
-- 答案：在 GRANT 中 _ 被视为通配符！
-- 所以这条语句会匹配 my_app、myXapp、my1app 等

-- 如果只想匹配字面的 "my_app"，需要转义：
GRANT ALL ON `my\_app`.* TO 'user1'@'%';
-- 使用 \_ 转义下划线为字面字符
```

## MySQL 8.0+ 的行为变更

```sql
-- MySQL 8.0 中的行为：

-- 1. GRANT 语句中数据库名的通配符行为保持不变
-- % 和 _ 在 GRANT 的数据库名中仍然是通配符
-- 但 MySQL 8.0 会在某些场景下发出废弃警告

-- 2. partial_revokes 系统变量（MySQL 8.0.16+）
SHOW VARIABLES LIKE 'partial_revokes';
-- partial_revokes: OFF（默认）

-- 启用 partial_revokes 后：
SET GLOBAL partial_revokes = ON;
-- 或在 my.cnf 中：
-- partial_revokes = ON

-- 启用后可以对通配符授权进行部分撤销：
GRANT ALL ON *.* TO 'dev_user'@'%';
-- 授予所有数据库的权限

REVOKE ALL ON `mysql`.* FROM 'dev_user'@'%';
-- 撤销对 mysql 系统库的权限（部分撤销）
-- 在 partial_revokes=OFF 时，这条 REVOKE 不会生效
-- 在 partial_revokes=ON 时，dev_user 拥有除 mysql 外所有库的权限

-- 3. 数据库名中的字面 % 和 _ 需要转义
-- 如果数据库名确实包含 % 或 _ 字符：
GRANT ALL ON `my\_app`.* TO 'user1'@'%';
-- \_ 表示字面下划线

GRANT ALL ON `test\%db`.* TO 'user1'@'%';
-- \% 表示字面百分号
```

## partial_revokes 的影响

```sql
-- partial_revokes = ON 时的权限模型变化：

-- 旧模型（partial_revokes=OFF）：
-- 权限是纯加法的，REVOKE 只能撤销完全匹配的 GRANT
-- GRANT ALL ON *.* → 拥有所有库权限
-- REVOKE ALL ON mysql.* → 不会真正撤销 mysql 的权限
--   因为 *.* 的权限包含了 mysql

-- 新模型（partial_revokes=ON）：
-- 支持部分撤销，可以在全局权限中"挖洞"
-- GRANT ALL ON *.* → 拥有所有库权限
-- REVOKE ALL ON mysql.* → 成功撤销 mysql 的权限
--   dev_user 现在拥有除 mysql 外所有库的权限

-- 查看用户的部分撤销信息：
SHOW GRANTS FOR 'dev_user'@'%';
-- GRANT ALL PRIVILEGES ON *.* TO 'dev_user'@'%'
-- REVOKE ALL PRIVILEGES ON `mysql`.* FROM 'dev_user'@'%'

-- 注意：partial_revokes 一旦启用（且有部分撤销记录存在），
-- 就不能轻易关闭
-- SET GLOBAL partial_revokes = OFF;
-- 如果存在部分撤销记录，会报错
```

## 安全最佳实践

```sql
-- 1. 避免在数据库名中使用通配符授权
-- 不推荐：
GRANT ALL ON `test%`.* TO 'user1'@'%';
-- 推荐：明确指定每个数据库
GRANT ALL ON `test_db`.* TO 'user1'@'%';
GRANT ALL ON `test_staging`.* TO 'user1'@'%';

-- 2. 数据库名包含 _ 时务必转义
-- 不推荐（_ 被视为通配符）：
GRANT ALL ON `my_app`.* TO 'user1'@'%';
-- 推荐（转义为字面字符）：
GRANT ALL ON `my\_app`.* TO 'user1'@'%';

-- 3. 使用 partial_revokes 实现精细权限控制
SET PERSIST partial_revokes = ON;
-- 授予广泛权限后撤销敏感库的访问：
GRANT SELECT, INSERT, UPDATE, DELETE ON *.* TO 'app_user'@'%';
REVOKE ALL ON `mysql`.* FROM 'app_user'@'%';
REVOKE ALL ON `information_schema`.* FROM 'app_user'@'%';
REVOKE ALL ON `performance_schema`.* FROM 'app_user'@'%';
REVOKE ALL ON `sys`.* FROM 'app_user'@'%';
```

## 适用场景

- **多租户环境的权限管理**：每个租户有独立的数据库（如 `tenant_001`、`tenant_002`），使用通配符 `GRANT ALL ON 'tenant\_%'.* TO ...` 授权时需要注意转义，或改用明确的数据库名授权
- **开发环境的安全隔离**：使用 `partial_revokes` 给开发人员授予广泛的数据库访问权限，同时撤销对生产数据库和系统库的访问

## 常见问题

**从 MySQL 5.7 升级到 8.0 后，现有的通配符 GRANT 会受影响吗？**

现有的通配符 GRANT（如 `GRANT ALL ON 'test%'.* TO user`）在升级后仍然有效，行为不变——`%` 和 `_` 仍然被视为通配符。但 MySQL 8.0 建议逐步迁移到更明确的授权方式，避免依赖通配符的模糊匹配。升级后如果启用了 `partial_revokes=ON`，权限模型的行为会发生变化（支持部分撤销），需要仔细评估对现有权限策略的影响。建议升级后使用 `SHOW GRANTS FOR user` 逐一检查关键用户的权限，确保与预期一致。

---

## 注意事项

- 在 `GRANT` 语句中，数据库名如果不使用反引号包裹，`_` 和 `%` 被视为通配符。使用反引号包裹时也是如此（`GRANT ... ON \`test%\`.* ...` 中的 `%` 仍是通配符）。只有使用 `\_` 和 `\%` 转义后才是字面字符。这与 `LIKE` 子句中的通配符转义规则一致。
- `partial_revokes` 是一个需要谨慎使用的功能。一旦启用并创建了部分撤销记录，在关闭 `partial_revokes` 之前必须先删除所有部分撤销记录（通过重新 GRANT 消除 REVOKE 记录）。建议在启用前充分测试，并确保团队理解新的权限模型。

## 总结

MySQL 8.0 规范了 GRANT 语句中数据库名通配符（`%` 和 `_`）的行为。`%` 匹配任意多个字符，`_` 匹配单个字符，使用 `\%` 和 `\_` 转义为字面字符。MySQL 8.0.16+ 引入 `partial_revokes` 系统变量，启用后支持"部分撤销"——在全局权限中排除特定数据库的权限。最佳实践：避免通配符授权、数据库名含 `_` 时转义、使用 `partial_revokes` 精细控制。升级后现有通配符 GRANT 仍有效但建议迁移到明确授权方式。

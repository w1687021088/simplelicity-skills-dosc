# 非标准外键引用非唯一键废弃

MySQL 8.0 开始废弃外键引用非唯一键（non-unique key）的行为。按照 SQL 标准，外键（FOREIGN KEY）约束的被引用列必须是主键或唯一键（UNIQUE KEY），这样才能保证引用关系的明确性——父表中被引用的每个值最多只有一行记录。然而 MySQL 历史上允许外键引用非唯一索引列，这是一个非标准的扩展行为，在 MySQL 8.0 中被标记为废弃，未来版本可能会完全移除。

---

## 外键引用的标准规则

```sql
-- SQL 标准要求：外键引用的列必须是主键或唯一键

-- 标准用法1：引用主键（推荐）
CREATE TABLE departments (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);

CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES departments(id)
    -- departments.id 是主键 → 标准合规 ✓
);

-- 标准用法2：引用唯一键
CREATE TABLE products (
    id INT PRIMARY KEY,
    sku VARCHAR(20) UNIQUE,
    name VARCHAR(100)
);

CREATE TABLE order_items (
    id INT PRIMARY KEY,
    product_sku VARCHAR(20),
    FOREIGN KEY (product_sku) REFERENCES products(sku)
    -- products.sku 是唯一键 → 标准合规 ✓
);
```

## 非标准行为（已废弃）

```sql
-- MySQL 历史上允许外键引用非唯一索引列（非标准）

CREATE TABLE categories (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    parent_name VARCHAR(100),
    INDEX idx_parent_name (parent_name)
    -- parent_name 只有普通索引，不是唯一键
);

-- 在 MySQL 5.7 及之前：以下语句可以成功执行
CREATE TABLE subcategories (
    id INT PRIMARY KEY,
    category_name VARCHAR(100),
    FOREIGN KEY (category_name) REFERENCES categories(parent_name)
    -- categories.parent_name 是普通索引（非唯一）→ 非标准！
    -- MySQL 5.7 允许
    -- MySQL 8.0 允许但发出废弃警告
    -- 未来版本可能拒绝
);

-- MySQL 8.0 中执行上述语句时的警告：
-- Warning 1215: Cannot add foreign key constraint
-- 或者在某些情况下：
-- Warning: Referencing column and referenced column in a foreign key
-- constraint are incompatible.
```

## 为什么引用非唯一键有问题

```
引用非唯一键导致的歧义和问题：

假设 categories 表数据：
id | name    | parent_name
1  | 电子     | NULL
2  | 手机     | 电子
3  | 平板     | 电子     ← parent_name='电子' 有两行记录

subcategories 表：
id | category_name
10 | 电子            ← 引用了 categories.parent_name = '电子'

问题1：引用的歧义
  category_name='电子' 在父表中匹配了两行（id=2 和 id=3）
  到底引用的是哪一行？SQL 标准认为这是不确定的

问题2：级联操作的不确定性
  如果设置 ON DELETE CASCADE
  删除 categories 中 parent_name='电子' 的某一行时
  subcategories 中 category_name='电子' 的行是否应该被删除？
  因为父表中还有另一行 parent_name='电子'
  → 行为不可预测

问题3：性能问题
  外键约束检查需要在父表中查找匹配的行
  如果引用的列不是唯一的，可能匹配多行
  增加了约束检查的复杂度和开销
```

## 升级时的处理

```sql
-- 检查当前数据库中是否存在引用非唯一键的外键：

-- 方法1：通过 information_schema 查询
SELECT 
    tc.TABLE_SCHEMA,
    tc.TABLE_NAME,
    tc.CONSTRAINT_NAME,
    kcu.COLUMN_NAME,
    kcu.REFERENCED_TABLE_NAME,
    kcu.REFERENCED_COLUMN_NAME
FROM information_schema.TABLE_CONSTRAINTS tc
JOIN information_schema.KEY_COLUMN_USAGE kcu
    ON tc.CONSTRAINT_NAME = kcu.CONSTRAINT_NAME
    AND tc.TABLE_SCHEMA = kcu.TABLE_SCHEMA
WHERE tc.CONSTRAINT_TYPE = 'FOREIGN KEY'
    AND kcu.REFERENCED_TABLE_NAME IS NOT NULL;

-- 然后检查被引用的列是否是主键或唯一键：
SELECT TABLE_NAME, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_NAME = 'referenced_table'
    AND COLUMN_NAME = 'referenced_column';
-- NON_UNIQUE = 0 → 唯一索引（合规）
-- NON_UNIQUE = 1 → 非唯一索引（需要修复）

-- 修复方法1：将被引用的列改为唯一键
ALTER TABLE categories ADD UNIQUE INDEX uniq_parent_name (parent_name);
-- 注意：如果列中已有重复值，此操作会失败

-- 修复方法2：修改外键引用主键或唯一键列
ALTER TABLE subcategories DROP FOREIGN KEY fk_name;
ALTER TABLE subcategories ADD FOREIGN KEY (category_name)
    REFERENCES categories(id);  -- 改为引用主键

-- 修复方法3：删除外键约束（如果不再需要）
ALTER TABLE subcategories DROP FOREIGN KEY fk_name;
```

## 适用场景

- **MySQL 5.7 到 8.0+/8.4 的升级准备**：在升级前检查并修复所有引用非唯一键的外键约束，避免未来版本移除此功能后导致的兼容性问题
- **数据库设计规范化**：在数据库设计中遵循 SQL 标准，确保所有外键引用的目标列是主键或唯一键，避免引用歧义和级联操作的不确定性

---

## 常见问题

**如果被引用的列有重复值，无法添加唯一索引怎么办？**

如果被引用的列中已经存在重复值（如 `parent_name` 列中有多行值为 "电子"），直接添加唯一索引会失败。处理方法：①清理重复数据后再添加唯一索引；②重新设计表结构，使用唯一的 ID 列作为外键引用目标（这是最规范的做法）；③如果业务上确实需要引用非唯一列，考虑在应用层实现引用完整性检查，而不是依赖数据库外键约束。在大多数场景中，推荐使用主键（通常是自增 ID）作为外键引用目标。

## 注意事项

- MySQL 8.0 中引用非唯一键的外键仍然可以创建和使用，但会产生废弃警告。这意味着当前不会破坏现有应用，但应尽早规划修复。建议在升级到 MySQL 8.0 后，使用 `SHOW WARNINGS` 检查 DDL 语句的警告信息，定位需要修复的外键。
- InnoDB 存储引擎要求外键引用的列必须有索引（至少是普通索引），但 SQL 标准要求的是唯一索引或主键。MySQL 的废弃警告是在向 SQL 标准靠拢。未来版本可能会强制要求被引用列是唯一键或主键，届时引用非唯一键的 `CREATE TABLE` 和 `ALTER TABLE` 语句将报错而非警告。

## 总结

MySQL 8.0 废弃了外键引用非唯一键（non-unique key）的非标准行为。SQL 标准要求外键引用的目标列必须是主键或唯一键，以保证引用的明确性。引用非唯一键会导致引用歧义、级联操作不确定性和额外的性能开销。当前 MySQL 8.0 仍允许但发出警告，未来版本可能移除。升级前应检查所有外键约束，确保被引用列是主键或唯一键。修复方法：为被引用列添加唯一索引、改为引用主键列、或删除不必要的外键约束。

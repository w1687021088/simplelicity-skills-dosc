# query_cache_type 与 query_cache_size 移除

MySQL 8.0 完全移除了查询缓存（Query Cache）功能，包括所有相关的系统变量（`query_cache_type`、`query_cache_size`、`query_cache_limit`、`query_cache_min_res_unit`、`query_cache_wlock_invalidate`）和状态变量（`Qcache_*`）。查询缓存在 MySQL 5.7.20 中被标记为废弃（Deprecated），在 MySQL 8.0 中被正式移除。如果在 `my.cnf` 中仍然包含这些参数，MySQL 8.0+ 启动时会报错或警告。

---

## 查询缓存被移除的原因

```
查询缓存的工作原理：
  将 SELECT 查询的结果缓存在内存中
  下次执行完全相同的 SQL 时直接返回缓存结果
  表中任何数据变化（INSERT/UPDATE/DELETE）→ 该表所有缓存失效

查询缓存被移除的主要原因：

1. 高并发下的锁竞争
   查询缓存使用一把全局互斥锁（mutex）
   所有读写操作都需要争抢这把锁
   在高并发场景下，锁竞争成为严重瓶颈
   反而降低了整体性能

2. 缓存失效策略过于粗暴
   任何对表的写操作都会使该表的所有缓存条目失效
   对于写操作频繁的 OLTP 系统，缓存命中率极低
   缓存频繁失效→重新缓存→又失效，浪费 CPU 和内存

3. 只对完全相同的 SQL 有效
   SELECT * FROM t WHERE id=1 和 SELECT * FROM t WHERE id = 1
   （空格不同）被视为不同查询，不能命中缓存
   绑定变量的 PreparedStatement 也无法利用查询缓存

4. 内存碎片问题
   查询缓存使用自己的内存分配器
   长时间运行后会产生内存碎片
   query_cache_min_res_unit 参数调优困难

5. InnoDB Buffer Pool 已经提供了数据缓存
   InnoDB 的 Buffer Pool 缓存数据页
   对于相同的数据访问，Buffer Pool 已经避免了磁盘 I/O
   查询缓存在数据缓存之上的额外收益有限
```

## 升级到 8.0+ 时的处理

```ini
# MySQL 5.7 的 my.cnf 中可能包含以下配置：
[mysqld]
query_cache_type = 1
query_cache_size = 67108864
query_cache_limit = 1048576

# 升级到 MySQL 8.0+ 后：
# 方法1：直接删除这些配置行
# 方法2：注释掉这些配置行
# query_cache_type = 1
# query_cache_size = 67108864

# 如果不处理，MySQL 8.0 启动时会报错：
# [ERROR] unknown variable 'query_cache_type=1'
# MySQL 无法启动
```

```sql
-- MySQL 8.0+ 中这些变量不再存在：
SHOW VARIABLES LIKE 'query_cache%';
-- Empty set（没有结果）

-- 状态变量也被移除：
SHOW STATUS LIKE 'Qcache%';
-- Empty set
```

## 查询缓存的替代方案

| 替代方案 | 实现层面 | 特点 | 适用场景 |
|---------|:------:|------|---------|
| InnoDB Buffer Pool | 数据库（自动）| 缓存数据页，自动管理 | 所有 InnoDB 查询 |
| ProxySQL Query Cache | 代理层 | 支持正则匹配、TTL 控制 | 读多写少的查询 |
| Redis/Memcached | 应用层 | 高性能键值缓存 | 热点数据、API 响应 |
| 应用层缓存 | 应用层 | 本地缓存（如 Guava Cache）| 低延迟要求 |
| 物化视图（替代方案）| 数据库 | 预计算结果存储为表 | 复杂聚合查询 |

```sql
-- InnoDB Buffer Pool 调优（替代查询缓存的数据缓存作用）：
-- 将查询缓存省下的内存分配给 Buffer Pool
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- 建议设置为物理内存的 60%~80%
SET GLOBAL innodb_buffer_pool_size = 4294967296;  -- 4GB
```

## 适用场景

- **MySQL 5.7 到 8.0+ 的升级准备**：在升级前检查 `my.cnf` 中是否包含 `query_cache_*` 相关参数，并在升级前移除，避免 MySQL 8.0 启动失败
- **性能调优策略的调整**：如果之前依赖查询缓存来提升读性能，升级后需要转向 InnoDB Buffer Pool 调优、应用层缓存（Redis/Memcached）等替代方案

## 常见问题

**升级到 MySQL 8.0 后，原来依赖查询缓存的应用性能会下降吗？**

在大多数实际生产环境中不会。查询缓存在 MySQL 5.7 中的实际效果取决于工作负载：对于写操作频繁的 OLTP 系统，查询缓存的命中率通常低于 10%，移除后性能几乎无影响，甚至因为消除了锁竞争反而性能提升。对于读多写少的场景（如内容管理系统），可能需要通过增大 InnoDB Buffer Pool 或引入应用层缓存来弥补。建议在升级前通过 `SHOW STATUS LIKE 'Qcache_hits'` 和 `SHOW STATUS LIKE 'Qcache_inserts'` 评估查询缓存的实际命中率。

## 注意事项

- 升级检查工具（如 `mysqlcheck --check-upgrade`、MySQL Shell 的 `util.checkForServerUpgrade()`）会自动检测 `my.cnf` 中是否包含已移除的 `query_cache_*` 参数，并给出修复建议。建议在升级前运行这些工具。
- 一些旧版本的 MySQL 客户端库或 ORM 框架可能在连接初始化时执行 `SET SESSION query_cache_type = ...`。升级到 MySQL 8.0 后这条 SQL 会报错，需要更新客户端库版本或修改连接初始化配置。

## 总结

MySQL 8.0 完全移除了查询缓存功能，包括 `query_cache_type`、`query_cache_size` 等所有相关参数。移除原因：全局互斥锁导致高并发瓶颈、粗暴的缓存失效策略、低命中率、内存碎片、InnoDB Buffer Pool 已提供数据缓存。升级处理：从 `my.cnf` 中删除所有 `query_cache_*` 参数，否则 MySQL 8.0 启动失败。替代方案：增大 InnoDB Buffer Pool、使用 ProxySQL Query Cache、引入 Redis/Memcached 应用层缓存。升级前使用检查工具评估影响。

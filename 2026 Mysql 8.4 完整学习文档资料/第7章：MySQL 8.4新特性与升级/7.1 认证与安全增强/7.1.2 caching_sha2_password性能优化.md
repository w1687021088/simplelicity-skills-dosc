# caching_sha2_password 性能优化

`caching_sha2_password` 是 MySQL 8.0 起的默认认证插件，也是 MySQL 8.4 LTS 唯一推荐的认证方式。它基于 SHA-256 哈希算法，相比旧的 `mysql_native_password`（SHA-1）提供了更强的密码安全性。同时，相比同样使用 SHA-256 的 `sha256_password` 插件，`caching_sha2_password` 通过**服务端缓存机制**解决了 SHA-256 计算带来的连接延迟问题，在安全性和性能之间取得了平衡。

---

## 认证流程与缓存机制

```
caching_sha2_password 的两阶段认证：

第一阶段：快速认证（缓存命中）
1. 客户端发送用户名和密码哈希
2. 服务端在内存缓存（hash cache）中查找该用户的密码哈希
3. 如果缓存命中 → 直接比对 → 认证通过（无 SHA-256 计算，速度极快）
4. 缓存命中的性能与 mysql_native_password 相当

第二阶段：完整认证（缓存未命中）
1. 如果缓存未命中（首次连接或缓存被清除）
2. 服务端需要执行完整的 SHA-256 多轮哈希计算
3. 要求安全通道：SSL/TLS 加密连接 或 RSA 公钥加密密码传输
4. 完整认证成功后，将密码哈希写入缓存
5. 后续连接走第一阶段快速路径

缓存的作用：
- 首次连接：完整 SHA-256 认证（稍慢，约 2~5ms）
- 后续连接：缓存命中，跳过 SHA-256 计算（极快，< 0.1ms）
- 生产环境中，绝大多数连接都命中缓存，性能与旧插件无差异
```

## 缓存管理

```sql
-- 缓存存储在内存中（服务端进程内），重启后清空
-- 缓存条目：每个用户的密码哈希

-- 清除认证缓存（强制所有用户下次连接执行完整认证）：
FLUSH PRIVILEGES;
-- FLUSH PRIVILEGES 会清除 caching_sha2_password 的认证缓存
-- 常见触发场景：修改用户密码后，旧缓存需要被清除

-- ALTER USER 修改密码会自动清除该用户的缓存条目：
ALTER USER 'app'@'%' IDENTIFIED BY 'new_password';
-- 修改密码后，该用户下次连接将走完整认证（第二阶段）
-- 认证成功后自动重新写入缓存

-- 缓存容量：
-- 缓存大小由用户数量决定（每个用户一条记录）
-- 内存开销极小（每条约几百字节），即使有数千用户也不会产生内存压力
```

## SHA-256 哈希轮次配置

```sql
-- caching_sha2_password_digest_rounds 控制 SHA-256 的哈希轮次
-- 轮次越多，密码哈希越难被暴力破解，但首次认证越慢

SHOW VARIABLES LIKE 'caching_sha2_password_digest_rounds';
-- caching_sha2_password_digest_rounds: 5000（默认值）

-- 范围：5000 到 4095000
-- 默认值 5000 在安全性和性能之间的平衡点
-- 增加轮次的影响：
-- 5000轮（默认）：首次认证约 2~3ms
-- 50000轮：首次认证约 20~30ms
-- 500000轮：首次认证约 200~300ms

-- 修改轮次（需要在 my.cnf 中设置，重启生效）：
-- [mysqld]
-- caching_sha2_password_digest_rounds = 5000

-- 注意：修改轮次后，已有用户的密码哈希不会自动更新
-- 需要重新设置密码（ALTER USER ... IDENTIFIED BY ...）才会使用新轮次
-- 新轮次只影响首次认证（缓存未命中时），缓存命中时无影响
```

## RSA 密钥对配置

```sql
-- caching_sha2_password 在非 SSL 连接上使用 RSA 公钥加密密码
-- 服务端需要配置 RSA 密钥对

-- 查看当前 RSA 密钥配置：
SHOW VARIABLES LIKE 'caching_sha2_password%key%';
-- caching_sha2_password_private_key_path: private_key.pem（数据目录下）
-- caching_sha2_password_public_key_path: public_key.pem（数据目录下）

-- 自动生成 RSA 密钥对：
SHOW VARIABLES LIKE 'caching_sha2_password_auto_generate_rsa_keys';
-- caching_sha2_password_auto_generate_rsa_keys: ON（默认开启）
-- MySQL 启动时自动生成密钥对文件（如果不存在）

-- 查看服务端 RSA 公钥：
SHOW STATUS LIKE 'Caching_sha2_password_rsa_public_key' \G
-- 输出 RSA 公钥的 PEM 内容

-- 客户端获取服务端公钥（首次非 SSL 连接时需要）：
-- mysql --get-server-public-key -u app -p
-- 或在连接参数中指定：
-- mysql --server-public-key-path=/path/to/server_public_key.pem -u app -p
```

## 连接场景与性能对比

| 连接场景 | mysql_native_password | caching_sha2_password |
|---------|:--------------------:|:--------------------:|
| SSL 连接（首次）| ~0.5ms | ~3ms（SHA-256 计算）|
| SSL 连接（缓存命中）| ~0.5ms | ~0.5ms（跳过计算）|
| 非 SSL + RSA（首次）| ~0.5ms | ~5ms（RSA 加密 + SHA-256）|
| 非 SSL + RSA（缓存命中）| ~0.5ms | ~0.5ms |
| 连接池长连接 | ~0.5ms | ~0.5ms（首次后始终缓存命中）|
| 安全强度 | SHA-1（较弱）| SHA-256（强）|

## 连接池环境的最佳实践

```sql
-- 在连接池（HikariCP、Druid、c3p0）环境中：
-- 连接池的连接被复用，不频繁断开重连
-- 首次建立连接时走完整认证（缓存未命中）
-- 连接复用期间无需重新认证
-- 当连接被回收并重建时，缓存通常已有条目 → 快速认证

-- 最佳实践：
-- 1. 启用 SSL 连接（MySQL 8.0+ 默认生成自签名证书）
--    确保首次完整认证时密码安全传输
-- 2. 连接池最小连接数适当（min-idle）
--    减少频繁创建/销毁连接，降低首次认证次数
-- 3. 避免频繁执行 FLUSH PRIVILEGES
--    不要在定时任务中无谓地执行 FLUSH PRIVILEGES，这会清除认证缓存
-- 4. 使用 SET PERSIST 而非直接修改 mysql.user 表
--    直接修改表不会自动刷新缓存，可能导致认证不一致
```

## 适用场景

- **MySQL 8.4 新部署的默认认证方案**：所有新建用户默认使用 `caching_sha2_password`，无需额外配置。确保所有客户端驱动支持该插件即可
- **高并发连接池环境的安全认证**：配合连接池使用，首次连接的 SHA-256 计算开销被缓存机制消除，后续连接性能与旧插件一致，同时获得了更强的密码安全性

## 常见问题

**使用 caching_sha2_password 后，客户端报错 "Authentication plugin 'caching_sha2_password' cannot be loaded"，怎么处理？**

这个错误表示客户端库不支持 `caching_sha2_password` 插件。原因通常是客户端驱动版本过低。解决方法：①升级客户端驱动到支持 `caching_sha2_password` 的版本（Java Connector/J 8.0.9+、PHP 7.2.4+、Python PyMySQL 0.9.0+、Node.js mysql2 1.5.2+）；②如果客户端暂时无法升级，可以在 MySQL 8.4 中临时启用 `mysql_native_password`（`my.cnf` 中 `mysql_native_password=ON`），但这只是过渡措施；③确保客户端连接时使用 SSL 或通过 `--get-server-public-key` 获取 RSA 公钥。

## 注意事项

- `caching_sha2_password` 的认证缓存是**服务端内存缓存**，不是持久化存储。MySQL 服务重启后缓存清空，所有用户的首次连接都需要走完整认证。在高可用故障转移（如 MHA 切换、MGR 主从切换）后，新主库的认证缓存为空，短时间内可能有轻微的连接延迟增加，但在连接池环境中影响可以忽略。
- `sha256_password` 插件（`caching_sha2_password` 的前身）在 MySQL 8.0.16 中已被标记为废弃。虽然在 MySQL 8.4 中仍然可用，但不建议使用。新部署应统一使用 `caching_sha2_password`。

## 总结

`caching_sha2_password` 是 MySQL 8.4 的默认且推荐的认证插件，基于 SHA-256 提供比 `mysql_native_password`（SHA-1）更强的密码安全性。核心优化：**服务端缓存机制**——首次连接执行完整 SHA-256 认证后将结果缓存，后续连接直接命中缓存，跳过 SHA-256 计算，性能与旧插件持平。缓存在 `FLUSH PRIVILEGES` 或 `ALTER USER` 修改密码后清除。首次认证需要安全通道（SSL 或 RSA 公钥加密），通过 `caching_sha2_password_auto_generate_rsa_keys=ON`（默认）自动生成 RSA 密钥对。哈希轮次通过 `caching_sha2_password_digest_rounds`（默认 5000）控制。在连接池环境中，缓存命中率接近 100%，性能影响可忽略。

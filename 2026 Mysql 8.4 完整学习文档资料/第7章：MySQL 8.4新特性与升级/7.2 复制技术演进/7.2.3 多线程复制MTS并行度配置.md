# 多线程复制 MTS 并行度配置

传统的 MySQL 复制在从库端使用单线程（SQL Thread）串行回放 relay log 中的事务，当主库并发写入量大时，从库的单线程回放速度跟不上主库的写入速度，导致**复制延迟**。多线程复制（Multi-Threaded Slave/Replica，MTS）通过在从库端使用多个 Worker 线程并行回放事务来解决这个问题。MySQL 8.0 在 MTS 方面做了重大改进，特别是引入了基于写入集（WRITESET）的并行策略，大幅提升了并行度。

---

## MTS 的基本配置

```sql
-- 查看当前并行 Worker 数量：
SHOW VARIABLES LIKE 'replica_parallel_workers';
-- replica_parallel_workers: 4（默认值，MySQL 8.0.27+ 默认改为 4）
-- MySQL 8.0.26 之前的变量名：slave_parallel_workers

-- 设置 Worker 数量（需要先停止复制）：
STOP REPLICA;
SET GLOBAL replica_parallel_workers = 8;
START REPLICA;

-- 也可以在 my.cnf 中配置：
-- [mysqld]
-- replica_parallel_workers = 8

-- Worker 数量的选择建议：
-- 通常设置为 CPU 核心数的 1~2 倍
-- 4 核 CPU → 4~8 个 Worker
-- 8 核 CPU → 8~16 个 Worker
-- 过多的 Worker 不一定能提升性能（受限于并行度和锁竞争）
```

---

## 并行策略（replica_parallel_type）

```sql
-- replica_parallel_type 决定了 Worker 如何分配事务

SHOW VARIABLES LIKE 'replica_parallel_type';
-- replica_parallel_type: LOGICAL_CLOCK（MySQL 8.0.27+ 默认值）

-- 两种并行策略：

-- 1. DATABASE（按数据库分发）
-- 不同数据库的事务可以并行，同一数据库的事务串行
-- 局限：如果业务集中在单个数据库，并行度为 1（退化为单线程）
SET GLOBAL replica_parallel_type = 'DATABASE';

-- 2. LOGICAL_CLOCK（按逻辑时钟分发，推荐）
-- 在主库上同一组提交（同一个 binlog group commit 窗口内）的事务
-- 被认为没有冲突，可以在从库并行回放
-- 并行度取决于主库的 group commit 窗口大小
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
```

## LOGICAL_CLOCK 与 Group Commit

```
LOGICAL_CLOCK 的并行判断依据：

主库上的 Group Commit：
- MySQL 将同一时间窗口内提交的多个事务打包为一个 "commit group"
- 同一个 commit group 内的事务在主库上没有锁冲突（否则不会同时进入 commit 阶段）
- 因此这些事务可以安全地在从库上并行回放

binlog 中的标记：
- 每个事务的 binlog event 包含两个序列号：
  last_committed：该事务依赖的最后一个已提交事务的序号
  sequence_number：该事务自己的序号
- 如果两个事务的 last_committed 相同 → 可以并行
- 如果事务 B 的 last_committed ≥ 事务 A 的 sequence_number → B 依赖 A，必须串行

主库优化 group commit 窗口：
- binlog_group_commit_sync_delay（微秒）
  人为增加 group commit 的等待时间，让更多事务进入同一个 commit group
  默认值 0，可设置为 100~1000 微秒
- binlog_group_commit_sync_no_delay_count
  等待指定数量的事务后立即提交（不再等待 delay）
```

## 提升主库 Group Commit 并行度

```ini
# my.cnf（主库配置，提升从库 MTS 的并行度）
[mysqld]
# 增加 group commit 等待时间（微秒），让更多事务进入同一组
binlog_group_commit_sync_delay = 500

# 等待至少 10 个事务后立即提交（避免延迟过长）
binlog_group_commit_sync_no_delay_count = 10

# 效果：
# 主库每 500 微秒或每 10 个事务提交一组
# 每组内的事务在从库上可以并行回放
# 代价：主库单个事务的提交延迟增加 0~500 微秒
```

## 事务保序（replica_preserve_commit_order）

```sql
-- 并行回放可能改变事务的提交顺序
-- 如果需要从库的提交顺序与主库一致：

SHOW VARIABLES LIKE 'replica_preserve_commit_order';
-- replica_preserve_commit_order: ON（MySQL 8.0.27+ 默认开启）

-- ON：从库的事务提交顺序与主库一致（有少量性能开销）
-- OFF：从库的事务可以按完成顺序提交（更快，但顺序可能不同）

-- 什么时候需要保序：
-- 1. 从库需要作为新主库（故障转移后 GTID 顺序一致性）
-- 2. 从库上有读查询需要因果一致性
-- 3. MGR 环境（Group Replication 要求保序）

-- 什么时候可以不保序（OFF）：
-- 纯只读从库，对提交顺序无要求
-- 追求最大回放速度（如从库延迟过大，需要快速追赶）
```

## 监控 MTS 的运行状态

```sql
-- 查看 Worker 线程状态：
SHOW REPLICA STATUS \G
-- Replica_SQL_Running_State: Waiting for dependent transaction to commit
-- 如果频繁出现此状态，说明并行度不足（Worker 在等待依赖事务完成）

-- Performance Schema 中的 Worker 详情：
SELECT WORKER_ID, LAST_APPLIED_TRANSACTION,
       APPLYING_TRANSACTION, LAST_ERROR_NUMBER
FROM performance_schema.replication_applier_status_by_worker;

-- 查看各 Worker 的事务应用统计：
SELECT WORKER_ID, 
       COUNT_TRANSACTIONS_RETRIES,
       LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
       LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP
FROM performance_schema.replication_applier_status_by_worker;

-- 复制延迟监控：
SELECT CHANNEL_NAME,
       LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS master_commit,
       LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP AS replica_apply,
       TIMESTAMPDIFF(SECOND, 
           LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
           LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP) AS lag_seconds
FROM performance_schema.replication_applier_status_by_worker
WHERE LAST_APPLIED_TRANSACTION != '';
```

## 适用场景

- **主库写入量大导致从库延迟的环境**：当 `SHOW REPLICA STATUS` 显示 `Seconds_Behind_Source` 持续增长时，说明从库单线程回放跟不上主库写入。增加 `replica_parallel_workers` 并使用 `LOGICAL_CLOCK` 策略可以有效减少延迟
- **主库开启了 group commit 的高并发 OLTP 系统**：在事务并发量高的系统中，主库的 group commit 窗口内通常包含多个事务，从库可以充分利用 `LOGICAL_CLOCK` 策略实现并行回放

## 常见问题

**设置了 replica_parallel_workers=16 但从库延迟没有明显改善，是什么原因？**

Worker 数量多不等于实际并行度高。实际并行度取决于主库的 group commit 窗口内有多少事务。如果主库事务写入是串行的（每秒只有少量事务），每个 commit group 只有 1~2 个事务，从库即使有 16 个 Worker，同一时刻也只有 1~2 个 Worker 在工作。解决方法：①在主库上增大 `binlog_group_commit_sync_delay`（如 500~1000 微秒），让更多事务进入同一个 commit group；②使用 WRITESET 并行策略（见 7.2.4），不依赖 group commit，而是基于事务修改的行集合判断冲突，并行度更高。

## 注意事项

- MTS 在回放过程中如果某个 Worker 线程遇到错误（如主键冲突），默认行为是停止所有 Worker 线程，复制整体中断。可以通过 `replica_transaction_retries`（默认 10）自动重试暂时性错误（如死锁），但永久性错误（如数据不一致）需要人工处理。
- 将 `replica_parallel_workers` 从 0（或 1）改为大于 1 时，需要先 `STOP REPLICA`，修改后 `START REPLICA`。运行中不能动态修改。恢复为单线程也需要相同操作。

---

## 总结

多线程复制（MTS）通过多个 Worker 线程在从库并行回放事务，解决单线程回放导致的复制延迟。核心参数：`replica_parallel_workers`（Worker 数，建议 CPU 核心数的 1~2 倍）、`replica_parallel_type=LOGICAL_CLOCK`（基于主库 group commit 的并行策略，MySQL 8.0.27+ 默认）、`replica_preserve_commit_order=ON`（保持提交顺序一致性）。提升并行度：主库增大 `binlog_group_commit_sync_delay`（增加 group commit 窗口），或使用 WRITESET 并行策略。监控：`performance_schema.replication_applier_status_by_worker` 查看各 Worker 的状态和延迟。

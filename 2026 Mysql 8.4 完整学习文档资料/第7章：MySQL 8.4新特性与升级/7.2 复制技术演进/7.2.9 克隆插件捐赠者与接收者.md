# 克隆插件捐赠者与接收者

Clone Plugin 的远程克隆涉及两个角色：**捐赠者（Donor）**——提供数据的源实例，和**接收者（Recipient）**——接收数据的目标实例。理解两个角色在克隆过程中的职责、配置要求和行为差异，是正确使用 Clone Plugin 的基础。克隆过程中，捐赠者负责读取并传输数据，接收者负责接收、写入数据并在完成后自动重启。

---

## 捐赠者（Donor）的职责与配置

```sql
-- 捐赠者是数据的来源，克隆期间继续正常提供服务

-- 1. 安装 Clone Plugin
INSTALL PLUGIN clone SONAME 'mysql_clone.so';

-- 2. 创建专用克隆用户（需要 BACKUP_ADMIN 权限）
CREATE USER 'clone_donor'@'%' IDENTIFIED BY 'donor_password';
GRANT BACKUP_ADMIN ON *.* TO 'clone_donor'@'%';

-- 3. 捐赠者在克隆期间的行为：
-- - 正常处理客户端请求（不停机）
-- - 额外的磁盘读取（读取 InnoDB 数据文件）
-- - 额外的网络输出（通过网络发送数据给接收者）
-- - 会持有一定的内部锁（backup lock），阻止某些 DDL 操作

-- 4. 控制捐赠者的资源消耗：
SET GLOBAL clone_max_data_bandwidth = 100;  -- 限制数据读取速率为 100 MB/s
SET GLOBAL clone_max_network_bandwidth = 50; -- 限制网络传输速率为 50 MB/s
-- 默认值 0 表示不限制
```

## 接收者（Recipient）的职责与配置

```sql
-- 接收者是数据的目标，发起克隆请求

-- 1. 安装 Clone Plugin
INSTALL PLUGIN clone SONAME 'mysql_clone.so';

-- 2. 设置允许的捐赠者列表（安全措施）
SET GLOBAL clone_valid_donor_list = '192.168.1.100:3306';
-- 只允许从指定的捐赠者克隆数据
-- 防止被恶意节点注入数据

-- 3. 执行克隆命令的用户需要 CLONE_ADMIN 权限
GRANT CLONE_ADMIN ON *.* TO 'admin'@'localhost';

-- 4. 接收者在克隆期间的行为：
-- - 接收者的现有 InnoDB 数据将被删除并替换
-- - 克隆完成后，接收者自动重启 MySQL 服务
-- - 重启后，接收者拥有捐赠者的完整数据副本
-- - 接收者的 server_uuid 会重新生成（auto.cnf）

-- 5. 执行克隆：
CLONE INSTANCE FROM 'clone_donor'@'192.168.1.100':3306
    IDENTIFIED BY 'donor_password';
```

## 克隆过程中的锁与 DDL 限制

```sql
-- 克隆期间，捐赠者会持有 backup lock（备份锁）
-- backup lock 阻止以下 DDL 操作：

-- 被阻止的操作（在克隆完成前会等待）：
-- CREATE TABLE, DROP TABLE, ALTER TABLE
-- TRUNCATE TABLE
-- CREATE TABLESPACE, DROP TABLESPACE
-- INSTALL/UNINSTALL PLUGIN

-- 不受影响的操作（正常执行）：
-- SELECT, INSERT, UPDATE, DELETE（DML 操作）
-- START TRANSACTION, COMMIT, ROLLBACK
-- LOCK TABLES, UNLOCK TABLES

-- 接收者在克隆期间：
-- 不接受任何客户端连接（除了克隆进程本身）
-- 因为数据正在被替换，任何查询都无意义

-- 查看备份锁状态：
SELECT * FROM performance_schema.metadata_locks
WHERE LOCK_TYPE = 'BACKUP_LOCK';
```

## 版本兼容性要求

```sql
-- 捐赠者和接收者的版本兼容规则：

-- 1. MySQL 主版本号必须相同
--    捐赠者 8.4.0 → 接收者 8.4.0 ✓
--    捐赠者 8.4.0 → 接收者 8.4.2 ✓（小版本可以不同）
--    捐赠者 8.0.35 → 接收者 8.4.0 ✗（主版本不同）

-- 2. 操作系统和架构必须兼容
--    Linux x86_64 → Linux x86_64 ✓
--    Linux x86_64 → Linux ARM64 ✗
--    Linux → Windows ✗

-- 3. 字符集和排序规则必须兼容
--    两端的 character_set_server 和 collation_server 应一致

-- 4. InnoDB page size 必须相同
--    默认 16KB，如果自定义过需要两端一致

-- 检查版本信息：
SELECT VERSION();
SHOW VARIABLES LIKE 'innodb_page_size';
SHOW VARIABLES LIKE 'character_set_server';
```

## 克隆后接收者的状态

```sql
-- 克隆完成并重启后，接收者的状态：

-- 1. 数据内容：与捐赠者在克隆时间点一致
-- 2. server_uuid：重新生成（不同于捐赠者）
-- 3. server_id：保持接收者原有设置（不被覆盖）
-- 4. GTID 信息：继承捐赠者的 gtid_executed
SELECT @@global.gtid_executed;

-- 5. 用户账户：继承捐赠者的所有用户（mysql.user 表被替换）
--    注意：接收者原有的用户账户会丢失！
--    克隆前应确认能用捐赠者的用户登录接收者

-- 6. binlog：接收者的 binlog 被重置（从新的位置开始）
-- 7. relay log：被清除

-- 查看克隆后的复制坐标：
SELECT BINLOG_FILE, BINLOG_POSITION, GTID_EXECUTED
FROM performance_schema.clone_status;
```

## 适用场景

- **MGR（Group Replication）的自动分布式恢复**：当新成员加入 MGR 组时，如果落后的事务数超过 `group_replication_clone_threshold`，MGR 会自动使用 Clone Plugin 从现有成员（捐赠者）克隆数据到新成员（接收者），整个过程自动完成
- **灾难恢复中的快速实例重建**：当某个从库数据损坏需要重建时，使用远程克隆从主库或另一个健康的从库快速获取数据，比传统的备份恢复方式快得多

## 常见问题

**克隆完成后，接收者的用户账户和权限会被替换为捐赠者的，如何处理？**

这是 Clone Plugin 的设计行为——整个数据目录（包括 `mysql` 系统数据库）都被替换。解决方法：①克隆前确认捐赠者上有可以在接收者上登录的用户（特别是 root 或管理员账户）；②如果接收者有特殊用户（如监控用户、应用专用用户），在克隆前先在捐赠者上创建这些用户；③克隆完成并重启后，用捐赠者的用户登录接收者，再根据需要调整用户权限。

## 注意事项

- 接收者在克隆过程中会**自动重启** MySQL 服务（不指定 DATA DIRECTORY 的情况下）。如果接收者通过 systemd 管理，需要确保 systemd 配置允许 MySQL 自动重启（`Restart=on-failure` 或 `Restart=always`），否则 MySQL 进程退出后不会自动恢复。
- 克隆过程中如果捐赠者或接收者崩溃，克隆操作失败。接收者上的数据处于不一致状态，需要重新执行克隆。建议在网络稳定的环境中执行克隆，并使用 `REQUIRE SSL` 选项确保传输安全。

## 总结

Clone Plugin 的两个角色：捐赠者（Donor）提供数据（需要 BACKUP_ADMIN 权限），接收者（Recipient）接收数据（需要 CLONE_ADMIN 权限，设置 `clone_valid_donor_list`）。克隆期间：捐赠者正常服务但 DDL 受限（backup lock）；接收者数据被替换、克隆后自动重启。版本要求：主版本号相同、操作系统架构兼容、`innodb_page_size` 一致。克隆后接收者状态：数据与捐赠者一致、`server_uuid` 重新生成、继承捐赠者的 `gtid_executed` 和用户账户。通过 `clone_max_data_bandwidth` 和 `clone_max_network_bandwidth` 控制克隆对捐赠者的性能影响。

# 写入集并行 WRITE_SET 并行策略

WRITESET 是 MySQL 8.0 引入的一种比 `LOGICAL_CLOCK` 更激进的多线程复制并行策略。`LOGICAL_CLOCK` 的并行度受限于主库的 group commit 窗口——只有在同一个 commit group 内的事务才能并行回放。而 WRITESET 策略基于事务实际修改的数据行（写入集）来判断冲突：只要两个事务修改的行集合没有交集，即使它们不在同一个 commit group 内，也可以在从库上并行回放。这使得 WRITESET 的并行度通常远高于 `LOGICAL_CLOCK`。

---

## WRITESET 的工作原理

```
LOGICAL_CLOCK 的并行判断：
- 事务 A 和事务 B 在主库的同一个 commit group 内 → 可并行
- 事务 A 和事务 C 在不同 commit group → 必须串行
- 并行度 = commit group 的平均事务数

WRITESET 的并行判断：
- 事务 A 修改了 orders 表的行 id=1,2,3
- 事务 B 修改了 orders 表的行 id=4,5,6
- 两个写入集无交集 → 可并行（即使在不同 commit group）
- 事务 C 修改了 orders 表的行 id=3,7
- 事务 A 和 C 的写入集有交集（id=3）→ 必须串行

写入集的表示：
- 每个事务的写入集 = 被修改行的主键（或唯一键）的哈希值集合
- 使用 XXHASH64 算法计算哈希（transaction_write_set_extraction）
- 哈希值存储在 binlog 中，供从库判断冲突
```

## 配置 WRITESET 并行策略

```sql
-- 主库配置（生成写入集信息到 binlog）：
-- 必须在主库上设置，从库才能利用写入集信息

-- 1. 启用写入集提取（MySQL 8.0 默认已启用）
SHOW VARIABLES LIKE 'transaction_write_set_extraction';
-- transaction_write_set_extraction: XXHASH64（默认值，8.0+）

-- 2. 设置事务依赖跟踪方式为 WRITESET
SET GLOBAL binlog_transaction_dependency_tracking = 'WRITESET';
-- 可选值：
-- COMMIT_ORDER（等同于 LOGICAL_CLOCK，基于 group commit）
-- WRITESET（基于写入集，并行度更高）
-- WRITESET_SESSION（同一 Session 内保序，不同 Session 按写入集并行）

-- 3. 写入集历史大小（用于冲突检测的历史事务数）
SHOW VARIABLES LIKE 'binlog_transaction_dependency_history_size';
-- binlog_transaction_dependency_history_size: 25000（默认值）
-- 保留最近 25000 个事务的写入集用于冲突比较
-- 增大此值可提高并行度（代价是更多内存）
```

```ini
# my.cnf 主库推荐配置
[mysqld]
transaction_write_set_extraction = XXHASH64
binlog_transaction_dependency_tracking = WRITESET
binlog_transaction_dependency_history_size = 25000
```

## WRITESET vs WRITESET_SESSION

```sql
-- WRITESET：不同事务只要写入集无交集就可并行
-- 不考虑事务来自哪个 Session
-- 并行度最高

-- WRITESET_SESSION：同一个 Session（连接）内的事务保持顺序
-- 不同 Session 的事务按写入集判断并行
-- 适合：应用层依赖同一连接内的事务顺序（如读己之写）

-- 当 replica_preserve_commit_order = ON 时：
-- WRITESET 和 WRITESET_SESSION 的行为相同
-- 因为保序已经保证了同一 Session 的事务顺序
```

| 策略 | 并行度 | 同 Session 保序 | 适用场景 |
|-----|:-----:|:------------:|---------|
| COMMIT_ORDER | 低（依赖 group commit）| 是 | 基础多线程复制 |
| WRITESET | 高（基于行级冲突）| 否 | 追求最大并行度 |
| WRITESET_SESSION | 中高 | 是 | 需要 Session 内因果一致 |

## WRITESET 的使用前提

```sql
-- WRITESET 要求每个表必须有主键或非 NULL 唯一键
-- 原因：写入集通过主键/唯一键的哈希来标识被修改的行
-- 没有主键的表无法生成有效的写入集

-- 如果表没有主键：
-- binlog_transaction_dependency_tracking = WRITESET 时
-- 该表的事务退化为 COMMIT_ORDER 策略（无法利用 WRITESET）

-- 检查哪些表缺少主键：
SELECT TABLE_SCHEMA, TABLE_NAME
FROM information_schema.TABLES t
WHERE TABLE_TYPE = 'BASE TABLE'
  AND TABLE_SCHEMA NOT IN ('mysql', 'information_schema', 'performance_schema', 'sys')
  AND NOT EXISTS (
      SELECT 1 FROM information_schema.TABLE_CONSTRAINTS tc
      WHERE tc.TABLE_SCHEMA = t.TABLE_SCHEMA
        AND tc.TABLE_NAME = t.TABLE_NAME
        AND tc.CONSTRAINT_TYPE = 'PRIMARY KEY'
  );

-- 强制要求所有表有主键（MySQL 8.0.13+）：
SET GLOBAL sql_require_primary_key = ON;
```

## 性能对比

```
场景：主库 TPS = 5000，Worker 线程 = 8

COMMIT_ORDER（LOGICAL_CLOCK）：
- group commit 平均 3 个事务/组
- 从库并行度 ≈ 3（8 个 Worker 中同时工作 3 个）
- 从库吞吐 ≈ 3000 TPS → 延迟持续增大

WRITESET：
- 假设 80% 的事务写入集无交集
- 从库并行度 ≈ 6~7（8 个 Worker 中同时工作 6~7 个）
- 从库吞吐 ≈ 4500~5000 TPS → 延迟可控

实际效果取决于业务特点：
- 业务写入分散（不同用户修改不同行）→ WRITESET 并行度很高
- 业务写入集中（热点行，如库存扣减）→ WRITESET 优势有限
```

---

## 适用场景

- **从库延迟严重且 LOGICAL_CLOCK 不够用的环境**：当主库事务并发高但 group commit 窗口较小（每组只有 1~3 个事务），`LOGICAL_CLOCK` 策略的并行度不足以消除延迟时，切换到 `WRITESET` 策略可以大幅提高并行度
- **多级复制链路（A→B→C）的并行优化**：在多级复制链路中，中间级（B）的 binlog 中的 group commit 信息会退化（B 上只有一个 SQL 线程写 binlog），导致下游（C）的 `LOGICAL_CLOCK` 并行度降低。MySQL 官方建议在中间级也设置 `WRITESET`，使下游仍能获得足够的并行度

## 常见问题

**设置了 WRITESET 策略后，从库的 Seconds_Behind_Source 反而增大了，可能是什么原因？**

可能原因：①表缺少主键——没有主键的表无法利用 WRITESET，退化为 COMMIT_ORDER，实际并行度没有提升；②`binlog_transaction_dependency_history_size` 太小——如果历史窗口太小，MySQL 无法充分判断历史事务之间的冲突关系，部分可并行的事务被保守地认为有冲突；③`replica_preserve_commit_order=ON` 导致 Worker 线程之间的等待——保序要求先完成的事务等待序号更小的事务提交完成，降低了整体吞吐。可以在确认安全的情况下临时设为 OFF 追赶延迟。

---

## 注意事项

- WRITESET 策略会增加主库的 CPU 开销（需要为每个事务计算写入集的哈希值），但通常开销很小（每个事务增加几微秒的哈希计算时间），在高吞吐场景下可以忽略。
- 修改 `binlog_transaction_dependency_tracking` 后，需要在从库上执行 `STOP REPLICA; START REPLICA;` 才能生效。新的依赖信息只影响修改后写入的 binlog 事务，已有的 relay log 中的事务仍使用旧的依赖信息。

---

## 总结

WRITESET 是 MySQL 8.0 引入的高级 MTS 并行策略，基于事务实际修改的行集合判断冲突，而不是 group commit 窗口。配置：主库设置 `binlog_transaction_dependency_tracking=WRITESET`（需要 `transaction_write_set_extraction=XXHASH64`，默认已启用）。前提：所有表需要有主键或非 NULL 唯一键（否则退化为 COMMIT_ORDER）。三种策略对比：`COMMIT_ORDER`（低并行度）< `WRITESET_SESSION`（中高并行度，Session 内保序）< `WRITESET`（最高并行度）。通过 `binlog_transaction_dependency_history_size`（默认 25000）调整冲突检测的历史窗口。适合写入分散、从库延迟严重的场景。

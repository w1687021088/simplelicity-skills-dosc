# GTID 复制默认启用

GTID（Global Transaction Identifier，全局事务标识符）是 MySQL 5.6 引入的复制增强功能，为每个事务分配一个全局唯一的标识符（格式：`server_uuid:transaction_id`），替代传统的 binlog 文件名 + 偏移量定位方式。在 MySQL 8.4 LTS 中，GTID 模式被设为**推荐的默认复制方式**，Group Replication（MGR）更是强制要求开启 GTID。GTID 使得复制拓扑的管理、故障转移、从库重建变得简单可靠，消除了手动计算 binlog 位置的复杂性和容错问题。

---

## GTID 的基本概念

```
GTID 格式：server_uuid:transaction_id

示例：3E11FA47-71CA-11E1-9E33-C80AA9429562:1

- server_uuid：MySQL 实例的全局唯一标识（自动生成，存储在 auto.cnf 文件中）
- transaction_id：在该实例上执行的事务的顺序编号（从 1 开始递增）

GTID 集合（GTID Set）：
3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100
表示该 server_uuid 上编号 1 到 100 的事务

多个来源的 GTID 集合：
3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100,
A1B2C3D4-E5F6-7890-ABCD-EF1234567890:1-50
表示来自两个不同主库的事务集合
```

---

## 启用 GTID 模式

```ini
# my.cnf 配置（主库和从库都需要配置）
[mysqld]
# 启用 GTID 模式（必须）
gtid_mode = ON

# 强制 GTID 一致性检查（必须，与 gtid_mode=ON 配合）
enforce_gtid_consistency = ON

# 启用二进制日志（GTID 依赖 binlog）
log_bin = mysql-bin

# 设置唯一的 server_id（每个实例不同）
server_id = 1
```

```sql
-- 验证 GTID 模式已启用：
SHOW VARIABLES LIKE 'gtid_mode';
-- gtid_mode: ON

SHOW VARIABLES LIKE 'enforce_gtid_consistency';
-- enforce_gtid_consistency: ON

-- 查看当前实例已执行的 GTID 集合：
SHOW VARIABLES LIKE 'gtid_executed';
-- gtid_executed: 3E11FA47-...:1-1500

-- 查看当前实例已清除（purge）的 GTID 集合：
SHOW VARIABLES LIKE 'gtid_purged';
-- gtid_purged: 3E11FA47-...:1-500（已删除的 binlog 中包含的 GTID）
```

## GTID 复制 vs 传统复制

| 对比维度 | 传统复制（File+Position）| GTID 复制 |
|---------|:--------------------:|:---------:|
| 定位方式 | binlog 文件名 + 偏移量 | 全局唯一事务 ID |
| 故障转移 | 需手动计算新主库的 binlog 位置 | 自动定位（AUTO_POSITION=1）|
| 从库重建 | 需指定精确的 binlog 位置 | 自动根据已有 GTID 补齐差异 |
| 多源复制 | 每个通道需独立维护位置 | GTID 全局唯一，自动去重 |
| 拓扑变更 | 复杂（重新计算位置）| 简单（GTID 自动适配）|
| 事务一致性 | 依赖 binlog 顺序 | 每个事务有唯一标识 |
| MGR 兼容 | 不兼容 | 强制要求 |

## enforce_gtid_consistency 限制

```sql
-- enforce_gtid_consistency = ON 会禁止以下不安全的 SQL 操作：

-- 1. CREATE TABLE ... SELECT（原子性问题）
CREATE TABLE new_table SELECT * FROM old_table;
-- ERROR 1786 (HY000): Statement violates GTID consistency
-- 替代方案：
CREATE TABLE new_table LIKE old_table;
INSERT INTO new_table SELECT * FROM old_table;

-- 2. 事务内混合使用事务引擎和非事务引擎
START TRANSACTION;
INSERT INTO innodb_table VALUES (1);    -- InnoDB（事务引擎）
INSERT INTO myisam_table VALUES (1);    -- MyISAM（非事务引擎）
COMMIT;
-- ERROR: 混合引擎事务在 GTID 模式下不允许

-- 3. 事务内的 CREATE TEMPORARY TABLE / DROP TEMPORARY TABLE
-- 在事务内创建或删除临时表可能不安全
-- 建议在事务外操作临时表
```

## 适用场景

- **新部署的 MySQL 复制环境**：所有新部署的 MySQL 8.0+ 复制环境都应使用 GTID 模式，它简化了复制管理、故障转移和从库重建的操作，是现代 MySQL 复制的标准配置
- **从传统复制升级到 GTID**：已有的传统复制环境可以在线升级到 GTID（通过逐步将 `gtid_mode` 从 `OFF` → `OFF_PERMISSIVE` → `ON_PERMISSIVE` → `ON` 切换），无需停机

---

## 常见问题

**已有的传统复制环境如何不停机迁移到 GTID 模式？**

MySQL 支持在线逐步启用 GTID，步骤如下：①在所有实例上设置 `gtid_mode=OFF_PERMISSIVE`（允许接收 GTID 事务但不生成）；②设置 `gtid_mode=ON_PERMISSIVE`（开始生成 GTID 事务，同时接受非 GTID 事务）；③确认所有实例的 `Ongoing_anonymous_transaction_count` 为 0（`SHOW STATUS LIKE 'Ongoing_anonymous%'`），即没有匿名事务在进行中；④设置 `enforce_gtid_consistency=ON`；⑤设置 `gtid_mode=ON`。每一步都通过 `SET GLOBAL` 在线完成，无需重启。

---

## 注意事项

- `gtid_executed` 和 `gtid_purged` 是理解 GTID 复制的关键变量。`gtid_executed` 记录了该实例已执行的所有事务的 GTID 集合（包括本地事务和从主库复制的事务）；`gtid_purged` 记录了已经从 binlog 中清除的 GTID 集合。从库在连接主库时，会发送自己的 `gtid_executed` 集合，主库据此计算需要发送哪些差异事务。
- 启用 GTID 后，`RESET MASTER` 命令会清除所有 binlog 和 GTID 信息（`gtid_executed` 和 `gtid_purged` 都重置为空），这在复制环境中是极其危险的操作。只应在初始化新实例或完全重建复制时使用，不要在正在运行的复制拓扑中执行。

---

## 总结

GTID（全局事务标识符）为每个事务分配全局唯一的 `server_uuid:transaction_id` 标识，替代传统的 binlog 文件名+偏移量定位。启用：`gtid_mode=ON` + `enforce_gtid_consistency=ON`（主库和从库都需要）。核心优势：自动定位（无需手动计算 binlog 位置）、简化故障转移、支持自动补齐差异事务。限制：禁止 `CREATE TABLE ... SELECT`、事务内混合引擎、事务内临时表操作。关键变量：`gtid_executed`（已执行的 GTID 集合）、`gtid_purged`（已清除的 GTID 集合）。MySQL 8.4 推荐所有复制环境使用 GTID，MGR 强制要求。

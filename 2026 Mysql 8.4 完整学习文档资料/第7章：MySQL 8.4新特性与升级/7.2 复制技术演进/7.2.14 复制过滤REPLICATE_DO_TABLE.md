# 复制过滤 REPLICATE_DO_TABLE

`REPLICATE_DO_TABLE` 是 MySQL 复制过滤中粒度最细的"白名单"过滤器，允许在从库端精确指定**只复制哪些表**的变更事件。与 `REPLICATE_DO_DB`（按数据库过滤）不同，`REPLICATE_DO_TABLE` 精确到表级别，适合只需要复制少数几张关键表的场景。需要注意的是，`REPLICATE_DO_TABLE` 不支持通配符，每张表必须以 `database.table` 的完整格式指定。

---

## 配置方式

```ini
# 方式1：my.cnf 启动参数（持久化）
[mysqld]
# 只复制指定的表
replicate-do-table = mydb.orders
replicate-do-table = mydb.users
replicate-do-table = mydb.products
```

```sql
-- 方式2：CHANGE REPLICATION FILTER（在线设置，不持久化）
STOP REPLICA SQL_THREAD;

CHANGE REPLICATION FILTER
    REPLICATE_DO_TABLE = (mydb.orders, mydb.users, mydb.products);

START REPLICA SQL_THREAD;

-- 指定通道（多源复制）：
CHANGE REPLICATION FILTER
    REPLICATE_DO_TABLE = (mydb.orders)
    FOR CHANNEL 'channel_1';

-- 清除规则：
CHANGE REPLICATION FILTER REPLICATE_DO_TABLE = ();

-- 查看当前配置：
SHOW REPLICA STATUS \G
-- Replicate_Do_Table: mydb.orders,mydb.users,mydb.products
```

---

## 过滤规则的评估顺序

```
从库 SQL 线程对每个 binlog 事件的过滤评估顺序：

1. REPLICATE_DO_DB / REPLICATE_IGNORE_DB
   → 先按数据库级别过滤
   → 如果数据库级别已经排除，后续不再评估

2. REPLICATE_DO_TABLE / REPLICATE_IGNORE_TABLE
   → 在数据库级别通过后，再按表级别过滤
   → REPLICATE_DO_TABLE 是白名单：只有列表中的表才通过
   → REPLICATE_IGNORE_TABLE 是黑名单：列表中的表被排除

3. REPLICATE_WILD_DO_TABLE / REPLICATE_WILD_IGNORE_TABLE
   → 最后按通配符规则过滤（支持 % 和 _ 通配符）

结论：表级别过滤是在数据库级别过滤之后执行的
如果 REPLICATE_DO_DB 已经排除了某个数据库
该数据库的表不会进入 REPLICATE_DO_TABLE 的评估
```

## 与数据库级别过滤的配合

```sql
-- 场景：只复制 mydb 数据库中的 orders 和 users 两张表

-- 方案1：只用 REPLICATE_DO_TABLE（推荐）
CHANGE REPLICATION FILTER
    REPLICATE_DO_TABLE = (mydb.orders, mydb.users);
-- 简洁明了，直接指定要复制的表

-- 方案2：REPLICATE_DO_DB + REPLICATE_DO_TABLE（冗余但清晰）
CHANGE REPLICATION FILTER
    REPLICATE_DO_DB = (mydb),
    REPLICATE_DO_TABLE = (mydb.orders, mydb.users);
-- 先通过数据库过滤，再通过表过滤
-- 效果与方案1 相同，但增加了一层数据库级别的过滤

-- 方案3：REPLICATE_DO_DB + REPLICATE_IGNORE_TABLE（排除法）
CHANGE REPLICATION FILTER
    REPLICATE_DO_DB = (mydb),
    REPLICATE_IGNORE_TABLE = (mydb.logs, mydb.tmp_data);
-- 复制 mydb 的所有表，除了 logs 和 tmp_data
-- 适合排除少数不需要的表
```

## REPLICATE_DO_TABLE 的限制

```sql
-- 1. 不支持通配符
-- 以下写法是错误的：
-- replicate-do-table = mydb.order_*   ← 不支持！
-- 需要通配符请使用 REPLICATE_WILD_DO_TABLE

-- 2. 必须使用 database.table 的完整格式
-- replicate-do-table = orders         ← 错误！缺少数据库名
-- replicate-do-table = mydb.orders    ← 正确

-- 3. DDL 语句的过滤行为
-- REPLICATE_DO_TABLE 主要过滤 DML（INSERT/UPDATE/DELETE）事件
-- DDL 语句（CREATE TABLE/ALTER TABLE/DROP TABLE）的过滤行为：
--   ROW 格式：DDL 语句始终基于默认数据库过滤（不受表级别过滤影响）
--   STATEMENT 格式：DDL 基于默认数据库过滤
-- 也就是说，REPLICATE_DO_TABLE = (mydb.orders) 可能不会阻止
-- CREATE TABLE mydb.other_table 的复制（取决于默认数据库）

-- 4. 跨表事务
-- 如果一个事务修改了 mydb.orders 和 mydb.logs
-- 只有 mydb.orders 的行事件被回放，mydb.logs 的行事件被跳过
-- 可能破坏事务的原子性
```

## 适用场景

- **从库只需要少数关键业务表**：例如报表从库只需要 `orders`、`order_items`、`products` 三张表生成报表，不需要其他表的数据。通过 `REPLICATE_DO_TABLE` 精确过滤，显著减少从库的数据量和回放负载
- **数据同步到异构系统的中间从库**：将 MySQL 数据同步到 Elasticsearch 或 ClickHouse 等异构系统时，中间从库只需要被同步的表的数据，通过表级别过滤减少不必要的数据处理

## 常见问题

**REPLICATE_DO_TABLE 设置后，新增的表是否需要手动添加到过滤列表？**

是的。`REPLICATE_DO_TABLE` 是严格的白名单机制，只有列表中明确指定的表才会被复制。主库上新创建的表（`CREATE TABLE`）如果不在列表中，该表的 DML 事件不会被复制到从库（DDL 事件的行为取决于默认数据库的过滤规则）。如果新表也需要复制，必须在从库上更新过滤规则：`STOP REPLICA SQL_THREAD; CHANGE REPLICATION FILTER REPLICATE_DO_TABLE = (..., mydb.new_table); START REPLICA SQL_THREAD;`。如果表名模式固定（如 `order_2024`、`order_2025`），建议使用 `REPLICATE_WILD_DO_TABLE` 通配符过滤。

---

## 注意事项

- `REPLICATE_DO_TABLE` 的表名匹配是**大小写敏感**还是**大小写不敏感**，取决于底层操作系统和 `lower_case_table_names` 配置。Linux 上默认大小写敏感（`lower_case_table_names=0`），Windows 上默认不敏感（`lower_case_table_names=1`）。配置过滤规则时应与实际表名的大小写保持一致。
- 通过 `CHANGE REPLICATION FILTER` 在线设置的规则不持久化，MySQL 重启后丢失。生产环境中务必同步在 `my.cnf` 中配置 `--replicate-do-table`。如果只在线设置而不写入配置文件，重启后过滤规则消失，从库可能突然开始复制所有表，导致数据量激增。

---

## 总结

`REPLICATE_DO_TABLE` 是表级别的白名单复制过滤器，只复制列表中指定的表（格式：`database.table`）。配置：`my.cnf` 中 `replicate-do-table=db.table`（持久化）或 `CHANGE REPLICATION FILTER REPLICATE_DO_TABLE=(db.t1,db.t2)`（在线，不持久化）。不支持通配符（需要通配符请用 `REPLICATE_WILD_DO_TABLE`）。评估顺序：数据库级别过滤 → 表级别过滤 → 通配符过滤。新增表不会自动加入白名单，需手动更新规则。适合从库只需少数表数据的场景。注意跨表事务可能被部分过滤，破坏原子性。

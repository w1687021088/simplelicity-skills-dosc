# 半同步复制 AFTER_COMMIT 模式

`AFTER_COMMIT` 是 MySQL 早期（5.5/5.6）的半同步复制模式，也称为"有损半同步"。与 `AFTER_SYNC`（无损半同步）的区别在于：`AFTER_COMMIT` 在主库完成 engine commit（InnoDB 提交）**之后**才等待从库 ACK，而 `AFTER_SYNC` 在 engine commit **之前**等待。这个时序差异直接影响了故障场景下的数据一致性：`AFTER_COMMIT` 模式下，主库崩溃后可能存在"幻读"——某些事务在主库已提交并被其他会话读到，但从库尚未收到该事务，切换后数据丢失。

---

## AFTER_COMMIT 的工作流程

```
AFTER_COMMIT 的事务提交流程：

1. 主库执行事务（InnoDB 引擎层）
2. 主库将事务写入 binlog（sync binlog）
3. 主库执行 engine commit（InnoDB commit） ← 先提交！
4. 主库将 binlog 事件发送给从库
5. 等待从库 ACK（确认已写入 relay log）    ← 提交后才等待
6. 向客户端返回提交成功

与 AFTER_SYNC 的关键差异（步骤 3 和 4 的顺序）：
AFTER_SYNC:   binlog → 发送从库 → 等 ACK → engine commit → 返回客户端
AFTER_COMMIT: binlog → engine commit → 发送从库 → 等 ACK → 返回客户端

AFTER_COMMIT 的"幻读"问题：
- 步骤 3 执行后，事务已经在主库的 InnoDB 中可见
- 其他会话可以读到这个事务的数据
- 如果主库在步骤 4~5 之间崩溃：
  → 从库没有收到该事务
  → 切换到从库后，该事务"消失"了
  → 之前读到数据的会话发现数据不存在了（幻读）
```

---

## AFTER_COMMIT vs AFTER_SYNC 对比

| 对比维度 | AFTER_COMMIT | AFTER_SYNC |
|---------|:-----------:|:----------:|
| 等待 ACK 的时机 | engine commit 之后 | engine commit 之前 |
| 数据一致性 | 可能丢失已提交事务 | 已确认事务不丢失 |
| 幻读风险 | 有（其他会话可能读到未同步事务）| 无 |
| 引入版本 | MySQL 5.5 | MySQL 5.7 |
| 性能 | 略高（提交后再等待）| 略低（等待后才提交）|
| 推荐程度 | 不推荐（遗留模式）| 推荐（MySQL 8.4 默认）|

## 配置方式

```sql
-- 将半同步切换到 AFTER_COMMIT 模式（不推荐，仅用于了解）：
SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_COMMIT';

-- 查看当前模式：
SHOW VARIABLES LIKE 'rpl_semi_sync_source_wait_point';
-- rpl_semi_sync_source_wait_point: AFTER_COMMIT

-- 切回 AFTER_SYNC（推荐）：
SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_SYNC';
```

## AFTER_COMMIT 的"幻读"故障场景

```
场景：转账事务 T1（从账户 A 转 1000 元到账户 B）

时间线（AFTER_COMMIT 模式）：

t1: 主库执行 T1，binlog 写入
t2: 主库 engine commit（InnoDB 提交）  ← T1 已在主库可见
t3: 会话 S2 读到 T1 的结果（账户 B 余额 +1000）
t4: 主库准备发送 binlog 给从库
t5: 主库崩溃！从库未收到 T1
t6: 从库被提升为新主库
t7: 新主库上账户 B 余额没有 +1000 ← T1 丢失
t8: 会话 S2 重新连接到新主库，发现 T1 的数据不存在了 ← 幻读

AFTER_SYNC 模式下的同一场景：
t1: 主库执行 T1，binlog 写入
t2: 主库发送 binlog 给从库
t3: 等待从库 ACK...
t4: 从库 ACK 收到
t5: 主库 engine commit（InnoDB 提交）  ← T1 现在才可见
t6: 返回客户端成功

如果主库在 t3 崩溃：
- T1 未 engine commit → 主库上 T1 不可见（其他会话未读到）
- 从库可能已有也可能没有 T1 → 但不影响一致性
- 不会出现"读到又消失"的幻读问题
```

## 适用场景

- **遗留系统兼容**：在从 MySQL 5.5/5.6 升级的老系统中，可能仍在使用 `AFTER_COMMIT` 模式。理解其行为有助于评估升级到 `AFTER_SYNC` 的必要性和风险
- **对数据一致性要求不严格的非关键业务**：对于数据丢失可以接受的非关键业务（如日志记录、统计数据），`AFTER_COMMIT` 的性能略优于 `AFTER_SYNC`（少了一个同步点的等待），但在 MySQL 8.4 环境下，两者的性能差异已经非常小，不建议为此选择 `AFTER_COMMIT`

## 常见问题

**从 AFTER_COMMIT 切换到 AFTER_SYNC 是否需要停机？**

不需要停机。`rpl_semi_sync_source_wait_point` 是一个动态变量，可以在运行时通过 `SET GLOBAL` 修改：`SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_SYNC'`。修改立即生效，新的事务将使用 `AFTER_SYNC` 模式。正在提交中的事务仍使用旧模式完成。为了持久化配置，还需要在 `my.cnf` 中同步修改。建议在业务低峰期切换，并监控切换后的 `Rpl_semi_sync_source_tx_avg_wait_time` 确认性能影响。

---

## 注意事项

- MySQL 5.7 开始 `AFTER_SYNC` 成为默认模式（`rpl_semi_sync_source_wait_point` 默认值为 `AFTER_SYNC`）。MySQL 8.4 LTS 延续了这个默认值。除非有明确的兼容性原因，否则所有新部署和升级后的环境都应使用 `AFTER_SYNC`。
- `AFTER_COMMIT` 模式下，即使从库 ACK 超时（退化为异步），主库的事务也已经 commit 成功并返回客户端了。这与 `AFTER_SYNC` 的行为相同——超时后都是退化为异步。区别在于正常（未超时）情况下的幻读风险。

---

## 总结

`AFTER_COMMIT` 是 MySQL 早期的半同步模式，在 engine commit **之后**才等待从库 ACK。核心缺陷：主库 commit 后、从库 ACK 前崩溃 → 其他会话已读到的数据在切换后丢失（幻读）。与 `AFTER_SYNC`（无损半同步）的区别：等待 ACK 的时机不同（AFTER_COMMIT 在 commit 后，AFTER_SYNC 在 commit 前）。MySQL 5.7+ 默认使用 `AFTER_SYNC`，MySQL 8.4 LTS 推荐 `AFTER_SYNC`。`AFTER_COMMIT` 仅作为遗留模式保留，新部署不应使用。切换：`SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_SYNC'`（在线生效，无需停机）。

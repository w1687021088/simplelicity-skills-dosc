# GTID 自动定位 AUTO_POSITION=1

`AUTO_POSITION=1` 是 GTID 复制中最核心的配置之一，它让从库在连接主库时**自动确定复制起始位置**，完全不需要手动指定 `MASTER_LOG_FILE` 和 `MASTER_LOG_POS`。从库将自己已经执行的 GTID 集合（`gtid_executed`）发送给主库，主库根据差集计算出从库缺少哪些事务，然后只发送这些缺失的事务。这个机制使得故障转移、从库重建、拓扑变更变得极其简单——只需要 `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION=1`，剩下的定位工作由 MySQL 自动完成。

---

## AUTO_POSITION 的工作原理

```
传统复制的定位方式（手动指定 binlog 位置）：
从库 → 主库：从 mysql-bin.000005 的 position=12345 开始发送
问题：故障转移到新主库时，新主库的 binlog 文件名和位置与旧主库不同
      需要手动计算对应位置（复杂且容易出错）

GTID AUTO_POSITION 的定位方式：
1. 从库连接主库时，发送自己的 gtid_executed 集合
   例如：从库已执行 uuid_A:1-100, uuid_B:1-50
2. 主库计算差集：
   主库 gtid_executed = uuid_A:1-150, uuid_B:1-80
   差集 = uuid_A:101-150, uuid_B:51-80（从库缺少的事务）
3. 主库在自己的 binlog 中找到这些事务，发送给从库
4. 如果差集中的某些事务已从主库 binlog 中 purge → 报错
   （需要通过备份重建从库）

优势：
- 不依赖 binlog 文件名和位置
- 主库切换后，从库自动适配新主库
- 多源复制中，每个通道自动管理各自的 GTID
```

## 配置 AUTO_POSITION

```sql
-- MySQL 8.0.23+ 推荐语法（使用 CHANGE REPLICATION SOURCE TO）：
STOP REPLICA;

CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.1.100',
    SOURCE_PORT = 3306,
    SOURCE_USER = 'repl_user',
    SOURCE_PASSWORD = 'repl_password',
    SOURCE_AUTO_POSITION = 1;

START REPLICA;

-- MySQL 8.0.22 及之前的语法（CHANGE MASTER TO）：
STOP SLAVE;

CHANGE MASTER TO
    MASTER_HOST = '192.168.1.100',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl_user',
    MASTER_PASSWORD = 'repl_password',
    MASTER_AUTO_POSITION = 1;

START SLAVE;

-- 验证配置：
SHOW REPLICA STATUS \G
-- Auto_Position: 1  ← 确认 AUTO_POSITION 已启用
-- Retrieved_Gtid_Set: uuid_A:101-150  ← 从主库接收的 GTID
-- Executed_Gtid_Set: uuid_A:1-150    ← 当前已执行的 GTID
```

## 故障转移中的自动定位

```sql
-- 场景：主库 A 故障，需要将从库 B 提升为新主库
-- 从库 C 需要从旧主库 A 切换到新主库 B

-- 传统复制：需要计算从库 C 在新主库 B 上的对应 binlog 位置
-- GTID AUTO_POSITION：只需指向新主库 B，自动定位

-- 在从库 C 上执行（切换到新主库 B）：
STOP REPLICA;

CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.1.101',    -- 新主库 B 的 IP
    SOURCE_PORT = 3306,
    SOURCE_AUTO_POSITION = 1;          -- 自动定位

START REPLICA;

-- 从库 C 发送自己的 gtid_executed 给新主库 B
-- 新主库 B 计算差集，发送缺失的事务
-- 无需任何手动 binlog 位置计算
```

## AUTO_POSITION 的前提条件

```sql
-- AUTO_POSITION = 1 需要满足以下条件：

-- 1. 主库和从库都启用了 GTID
SHOW VARIABLES LIKE 'gtid_mode';  -- 必须是 ON

-- 2. 主库的 binlog 中包含从库需要的所有差异事务
-- 如果主库已经 purge 了从库需要的 binlog → 报错：
-- ERROR: Got fatal error 1236 from source: 
-- "Cannot replicate because the source purged required binary logs."
-- 解决方案：通过备份+恢复重建从库

-- 3. 不能同时指定 MASTER_LOG_FILE/MASTER_LOG_POS
-- 以下写法会报错：
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '...',
    SOURCE_LOG_FILE = 'mysql-bin.000001',   -- 不兼容！
    SOURCE_LOG_POS = 4,                      -- 不兼容！
    SOURCE_AUTO_POSITION = 1;
-- ERROR: Parameters SOURCE_LOG_FILE, SOURCE_LOG_POS, RELAY_LOG_FILE 
-- and RELAY_LOG_POS cannot be set when SOURCE_AUTO_POSITION is active.

-- 4. 复制线程必须停止后才能修改
STOP REPLICA;  -- 必须先停止
```

## 关闭 AUTO_POSITION（回退到传统定位）

```sql
-- 在某些特殊场景下需要回退到传统的文件+位置定位：
STOP REPLICA;

CHANGE REPLICATION SOURCE TO
    SOURCE_AUTO_POSITION = 0,
    SOURCE_LOG_FILE = 'mysql-bin.000010',
    SOURCE_LOG_POS = 154;

START REPLICA;

-- 回退场景（非常少见）：
-- 1. 调试特定 binlog 事件
-- 2. 跳过某个有问题的事务（GTID 模式下有更优的跳过方式）
-- 3. 兼容不支持 GTID 的特殊工具
```

## 适用场景

- **所有 GTID 复制环境的标准配置**：一旦启用了 GTID 模式，`SOURCE_AUTO_POSITION=1` 应当作为标准配置使用。手动指定 binlog 位置在 GTID 模式下不仅没有必要，还增加了出错风险
- **自动化故障转移工具的基础**：MHA、Orchestrator、MySQL Shell 等自动化故障转移工具都依赖 `AUTO_POSITION` 来实现无缝切换——工具只需将从库指向新主库并设置 `AUTO_POSITION=1`，定位完全自动

## 常见问题

**AUTO_POSITION=1 时报错"source purged required binary logs"，如何处理？**

这说明从库需要的某些事务对应的 binlog 已经从主库删除（被 `PURGE BINARY LOGS` 或 `expire_logs_days` 自动清理）。主库无法提供这些事务，复制中断。解决步骤：①通过 `mysqldump --single-transaction --set-gtid-purged=ON` 或 XtraBackup 从主库做一份全量备份；②在从库上恢复备份（备份中包含 `gtid_purged` 信息）；③重新配置 `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION=1`；④从库将从备份的 GTID 点之后开始追赶主库。预防措施：增大 `binlog_expire_logs_seconds`（保留更多 binlog），确保从库的延迟不超过 binlog 保留时间。

---

## 注意事项

- `AUTO_POSITION=1` 依赖主库 binlog 中保留了从库所需的事务。如果主库的 `binlog_expire_logs_seconds`（默认 2592000 秒，即 30 天）设置过短，而从库长时间断开（如超过 binlog 保留时间），则从库重新连接时会因缺少事务而报错。生产环境建议 binlog 保留时间不少于 7 天，高可用场景建议 14~30 天。
- 在多源复制（Multi-Source Replication）中，每个复制通道（channel）独立使用 `AUTO_POSITION`。每个通道有自己的 `Retrieved_Gtid_Set` 和 `Executed_Gtid_Set`，MySQL 会自动为每个通道计算正确的差集，不会出现事务重复或遗漏。

## 总结

`SOURCE_AUTO_POSITION=1`（或旧语法 `MASTER_AUTO_POSITION=1`）是 GTID 复制的核心配置，让从库自动确定复制起始位置。工作原理：从库发送 `gtid_executed` 集合 → 主库计算差集 → 只发送缺失的事务。配置：`CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION=1`。前提：主库和从库都启用 `gtid_mode=ON`，主库 binlog 保留了从库所需的事务。核心优势：故障转移时只需指向新主库，无需计算 binlog 位置。注意：主库 binlog 被 purge 后，从库需通过备份恢复重建。

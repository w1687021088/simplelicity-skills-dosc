# 复制过滤 REPLICATE_DO_DB

`REPLICATE_DO_DB` 是 MySQL 复制过滤机制中的一种，用于在从库端**只复制指定数据库**的变更，忽略其他数据库的事件。它可以通过启动参数 `--replicate-do-db` 或在线命令 `CHANGE REPLICATION FILTER REPLICATE_DO_DB` 设置。复制过滤在从库的 SQL 线程（Applier）层面执行，IO 线程仍然接收所有 binlog 事件，只是 SQL 线程在回放时跳过不匹配的事件。

---

## 配置方式

```ini
# 方式1：my.cnf 启动参数（持久化，重启后生效）
[mysqld]
# 只复制 mydb 数据库的变更
replicate-do-db = mydb

# 多个数据库需要写多行
replicate-do-db = mydb
replicate-do-db = mydb2
replicate-do-db = mydb3
```

```sql
-- 方式2：CHANGE REPLICATION FILTER（在线设置，不持久化）
STOP REPLICA SQL_THREAD;

CHANGE REPLICATION FILTER REPLICATE_DO_DB = (mydb, mydb2, mydb3);

START REPLICA SQL_THREAD;

-- 指定复制通道（多源复制时）：
CHANGE REPLICATION FILTER REPLICATE_DO_DB = (mydb)
    FOR CHANNEL 'channel_1';

-- 清除过滤规则：
CHANGE REPLICATION FILTER REPLICATE_DO_DB = ();

-- 查看当前过滤规则：
SHOW REPLICA STATUS \G
-- Replicate_Do_DB: mydb,mydb2,mydb3
```

## 基于语句复制（SBR）与基于行复制（RBR）的行为差异

```sql
-- REPLICATE_DO_DB 的过滤行为取决于复制格式（binlog_format）

-- 基于语句复制（STATEMENT）：
-- 过滤依据：当前默认数据库（USE 语句指定的数据库）
-- 不看 SQL 语句实际操作的表属于哪个数据库

USE mydb;          -- 默认数据库 = mydb
INSERT INTO other_db.t1 VALUES (1);
-- REPLICATE_DO_DB = (mydb) → 会被复制！
-- 因为默认数据库是 mydb（即使操作的是 other_db 的表）

USE other_db;      -- 默认数据库 = other_db
INSERT INTO mydb.t1 VALUES (1);
-- REPLICATE_DO_DB = (mydb) → 不会被复制！
-- 因为默认数据库是 other_db（即使操作的是 mydb 的表）

-- 基于行复制（ROW）：
-- 过滤依据：被修改表实际所属的数据库
-- 与默认数据库无关

USE other_db;      -- 默认数据库 = other_db
INSERT INTO mydb.t1 VALUES (1);
-- REPLICATE_DO_DB = (mydb) → 会被复制
-- 因为 mydb.t1 属于 mydb 数据库
```

| 复制格式 | 过滤依据 | 跨库操作行为 |
|---------|---------|------------|
| STATEMENT | 当前默认数据库（USE）| 可能产生意外过滤/遗漏 |
| ROW | 被修改表的实际数据库 | 过滤行为准确 |
| MIXED | 取决于具体语句的格式 | 行为不确定 |

## 与 binlog-do-db 的区别

```sql
-- binlog-do-db：在主库端过滤（不写入 binlog）
-- replicate-do-db：在从库端过滤（写入 binlog 但从库不回放）

-- binlog-do-db（主库配置）：
-- [mysqld]
-- binlog-do-db = mydb
-- 只有 mydb 的变更写入 binlog，其他数据库的变更不记录
-- 问题：如果有从库需要其他数据库的数据 → 无法获取

-- replicate-do-db（从库配置）：
-- [mysqld]
-- replicate-do-db = mydb
-- 主库的 binlog 包含所有数据库的变更
-- 从库的 IO 线程接收所有事件，SQL 线程只回放 mydb 的事件
-- 优点：不同从库可以设置不同的过滤规则
```

## 适用场景

- **从库只需要部分数据库**：在多数据库的 MySQL 实例中，某个从库只需要某几个数据库的数据（如报表从库只需要 `analytics` 数据库），通过 `REPLICATE_DO_DB` 过滤不需要的数据库，减少从库的存储空间和回放负载
- **多源复制中隔离不同来源的数据**：在多源复制（Multi-Source Replication）中，不同通道复制不同主库的数据。通过为每个通道设置 `REPLICATE_DO_DB`，确保每个通道只复制指定的数据库，避免数据库名冲突

## 常见问题

**设置了 REPLICATE_DO_DB 后，为什么有些跨库的 SQL 语句没有被正确过滤？**

这通常发生在使用 STATEMENT 格式复制时。`REPLICATE_DO_DB` 在 STATEMENT 模式下根据**当前默认数据库**（`USE` 语句设置的数据库）判断是否过滤，而不是根据 SQL 语句实际操作的表所属的数据库。例如 `USE db_a; UPDATE db_b.t1 SET col=1`——如果 `REPLICATE_DO_DB=(db_b)`，这条语句**不会被复制**，因为默认数据库是 `db_a`。解决方法：将 `binlog_format` 设置为 `ROW`（MySQL 8.0 默认），行格式复制基于表的实际数据库判断，行为准确。

## 注意事项

- `CHANGE REPLICATION FILTER` 设置的过滤规则**不持久化**，MySQL 重启后丢失。如果需要持久化，必须在 `my.cnf` 中使用 `--replicate-do-db` 参数。MySQL 8.0.27+ 支持 `SET PERSIST` 持久化部分复制变量，但 `CHANGE REPLICATION FILTER` 本身不支持持久化。
- `REPLICATE_DO_DB` 过滤的是整个数据库级别的事件。如果一个事务跨多个数据库（如 `BEGIN; INSERT INTO db1.t1 ...; INSERT INTO db2.t2 ...; COMMIT;`），在 ROW 格式下，只有属于过滤列表中数据库的行事件被回放，其他行事件被跳过。这可能导致事务的部分回放，破坏跨库事务的原子性。

---

## 总结

`REPLICATE_DO_DB` 在从库端过滤复制事件，只复制指定数据库的变更。配置：`my.cnf` 中 `replicate-do-db=dbname`（持久化）或 `CHANGE REPLICATION FILTER REPLICATE_DO_DB=(db1,db2)`（在线设置，不持久化）。SBR 模式基于当前默认数据库（`USE`）过滤，RBR 模式基于表实际所属数据库过滤（更准确，推荐使用 ROW 格式）。与 `binlog-do-db`（主库端过滤）不同，`REPLICATE_DO_DB` 在从库端过滤，不影响其他从库。注意跨库事务可能被部分过滤，破坏原子性。

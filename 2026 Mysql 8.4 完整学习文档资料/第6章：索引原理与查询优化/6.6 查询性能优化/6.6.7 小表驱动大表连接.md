# 小表驱动大表连接

在 MySQL 的嵌套循环连接（Nested Loop Join，NLJ）中，**驱动表**（Outer Table）决定了循环次数——驱动表的每一行都会触发对**被驱动表**（Inner Table）的一次索引查找。因此，驱动表的行数直接决定了被驱动表的查找次数：驱动表越小，循环次数越少，JOIN 的总代价越低。"小表驱动大表"是 JOIN 优化的基本原则，即让**过滤后行数更少的表**作为驱动表，减少对被驱动表的访问次数。

---

## 小表驱动大表的原理

```
Nested Loop Join 的执行模型：

for each row R1 in 驱动表 (where 条件过滤后的行):
    for each row R2 in 被驱动表 (where R2.join_key = R1.join_key):
        output (R1, R2)

总代价 ≈ 驱动表过滤行数 × 被驱动表每次查找代价

被驱动表有索引时：
  每次查找代价 ≈ B+树高度（通常 2~3 次 I/O）
  总代价 = 驱动行数 × 2~3 次 I/O

驱动表和被驱动表互换的代价差：
  小表(100行)驱动大表(100万行)：100 × 3 = 300 次 I/O
  大表(100万行)驱动小表(100行)：100万 × 3 = 300万 次 I/O
  差距：10000 倍！
```

## MySQL 优化器的自动选择

```sql
-- MySQL 优化器（CBO）会自动尝试选择代价更低的 JOIN 顺序
-- 通常会优先让"过滤后行数少的表"作为驱动表

CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(50), status VARCHAR(20));
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT NOT NULL,
    status TINYINT,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id)
);

-- 情况1：WHERE 条件大幅过滤了 users
EXPLAIN SELECT o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.status = 'active' AND u.id BETWEEN 1 AND 100 \G
-- 优化器分析：
-- users 过滤后：约 50 行（id 在 1~100 且 status='active'）
-- orders 无过滤：100 万行
-- 优化器选择 users 为驱动表（行数少）
-- EXPLAIN 输出：table: u 在前，table: o 在后

-- 情况2：WHERE 条件大幅过滤了 orders
EXPLAIN SELECT o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = 1 AND o.amount > 10000 \G
-- orders 过滤后：约 100 行（高金额订单）
-- users 无过滤：10 万行
-- 优化器选择 orders 为驱动表（过滤后更小）
```

## 强制指定驱动顺序

```sql
-- 方法1：STRAIGHT_JOIN（强制按 FROM 中的顺序，左表驱动右表）
SELECT STRAIGHT_JOIN o.id, u.name
FROM users u JOIN orders o ON u.id = o.user_id
WHERE u.status = 'active';
-- 强制 users（左表）为驱动表

-- 方法2：Optimizer Hint JOIN_ORDER（MySQL 8.0+）
SELECT /*+ JOIN_ORDER(u, o) */ o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.status = 'active';
-- 强制 u(users) 为驱动表，o(orders) 为被驱动表

-- 方法3：JOIN_FIXED_ORDER（按 FROM 子句顺序固定，不允许优化器调整）
SELECT /*+ JOIN_FIXED_ORDER() */ o.id, u.name
FROM users u JOIN orders o ON u.id = o.user_id;

-- 什么时候需要手动指定？
-- 统计信息不准（EXPLAIN 显示的驱动顺序与预期不符）
-- 优化器成本估算有误（通过 EXPLAIN FORMAT=JSON 的 query_cost 验证）
-- 特殊业务场景（如某张表的数据量在特定时间段会激增）
```

## IN 子查询中的小表驱动大表

```sql
-- IN 子查询同样遵循"小表驱动大表"原则
-- 通常写成：大表.col IN (小表子查询)
-- 让小表结果集作为内层，大表作为外层驱动

-- 推荐（大表 orders 作为外层，小表 active_users 的结果作为内层）：
SELECT * FROM orders
WHERE user_id IN (
    SELECT id FROM users WHERE status = 'active' AND country = 'CN'
);
-- 内层子查询结果小（活跃的中国用户，假设 1000 个）
-- 优化器物化内层 → 对 orders 扫描，用哈希表查 user_id

-- 不推荐（语义反转，外层是小集合）：
-- 通常情况下，WHERE 条件就能自然确定方向
-- 强行颠倒通常没有意义

-- EXISTS 子查询的驱动方向：
-- EXISTS 的外层是驱动，内层对每行外层行执行一次
-- 所以 EXISTS 适合"外层小、内层大"的场景
SELECT * FROM users u   -- 外层（驱动，通常是小表）
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 10000
);
-- 每个 user，检查是否有高金额订单
-- 如果 users 行数 < orders 行数，EXISTS 方向正确
```

## 验证 JOIN 驱动顺序

```sql
-- 通过 EXPLAIN 验证驱动顺序（EXPLAIN 输出从上到下是驱动到被驱动）
EXPLAIN SELECT o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.status = 'active' \G

-- 输出行顺序：
-- id:1, table: u → 第一行：u 是驱动表（先扫描 users）
-- id:1, table: o → 第二行：o 是被驱动表（根据每个 user_id 查 orders）

-- 通过 EXPLAIN FORMAT=JSON 查看 nested_loop 结构：
EXPLAIN FORMAT=JSON SELECT o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.status = 'active' \G
-- nested_loop 数组的第一个元素是驱动表
-- 第二个元素是被驱动表
```

## "小表"的真正含义

```sql
-- "小表"指的不是表的总行数，而是经过 WHERE 条件过滤后的行数！

-- 错误理解：users(10万行) < orders(100万行) → 总是让 users 驱动
-- 正确理解：
--   如果 WHERE orders.status = 1 只有 100 行 → orders 过滤后更小 → orders 应该驱动
--   如果 WHERE users.status = 'vip' 只有 50 行 → users 过滤后更小 → users 应该驱动

-- 优化器的估算方式：
-- 驱动表的"实际驱动行数" = 驱动表 rows × filtered / 100
-- 被驱动表的"每次查找代价" = 索引访问代价（通常 2~3 次 I/O）

-- 总代价 = 驱动行数 × 被驱动表每次查找代价
-- 两种方向分别计算总代价 → 选择更低代价的方向

-- 例：
-- 方向A：users(50行) 驱动 orders → 50 × 3 = 150 次 I/O
-- 方向B：orders(100行) 驱动 users → 100 × 3 = 300 次 I/O
-- 优化器选方向A（users 为驱动）
```

## 适用场景

- **多表 JOIN 的执行计划审查**：对 EXPLAIN 中 JOIN 顺序与预期不符的查询（如明明小表在 WHERE 中过滤了很多行，却被作为被驱动表），检查统计信息是否准确（`ANALYZE TABLE`），必要时用 Optimizer Hint 手动修正驱动顺序
- **IN 子查询改写方向确认**：在改写相关子查询或将子查询改为 JOIN 时，确认改写后的驱动方向与"小表驱动大表"原则一致；如果因 ORM 框架自动生成了反向的 JOIN 顺序，通过添加 Hint 纠正

## 常见问题

**多表 JOIN（3 张以上）时，优化器如何决定驱动顺序？**

MySQL 优化器对多表 JOIN 采用动态规划或贪心算法枚举可能的 JOIN 顺序，寻找总代价最低的方案。对于 N 个表的 JOIN，完全枚举所有排列需要 O(N!) 的复杂度，MySQL 通过 `optimizer_search_depth` 参数（默认 62，接近完全枚举但有限制）控制枚举深度。超过 7~8 张表的 JOIN 时，优化器会使用贪心启发式（从代价最低的表开始，逐步扩展），可能不是全局最优，此时通过 `/*+ JOIN_ORDER(t1, t2, t3, ...) */` 手动指定 JOIN 顺序可以帮助优化器找到更优方案。

## 注意事项

- "小表驱动大表"在 Hash Join 场景下有所不同。Hash Join 的构建阶段通常选择**估算行数更少的表**作为构建表（Build Table），将其哈希到内存；行数多的表作为探测表（Probe Table）。与 NLJ 不同的是，Hash Join 的总代价是 O(m+n)，不是乘积，所以两种方向的代价差异没有 NLJ 那么大，但仍然是小表构建哈希表（内存使用更少，可以避免磁盘溢出）更优。
- 在 LEFT JOIN 中，驱动顺序受语义约束——左表必须是驱动表（LEFT JOIN 要求左表的所有行都出现在结果中，右表不匹配时用 NULL 填充），优化器不能任意调换顺序。如果 WHERE 条件能将 LEFT JOIN 等价转换为 INNER JOIN（如 `WHERE 右表.col IS NOT NULL`），优化器会将其转为 INNER JOIN 后才自由选择驱动顺序。

## 总结

"小表驱动大表"是 JOIN 优化的基本原则：驱动表（外层）的每一行触发一次被驱动表的索引查找，驱动行数越少，总查找次数越少，代价越低。"小表"指过滤后行数少的表，不是总行数少的表。MySQL 优化器（CBO）通常能自动选择正确的驱动顺序（基于统计信息的成本估算），统计信息准确时不需要手动干预。当优化器选择了次优顺序时，通过 `EXPLAIN FORMAT=JSON` 查看 `query_cost` 验证，用 `/*+ JOIN_ORDER(small_table, large_table) */` 或 `STRAIGHT_JOIN` 手动修正。被驱动表必须有索引（`type: ref` 或 `eq_ref`），否则退化为全表扫描（`Using join buffer`），驱动方向的优化效果大打折扣。

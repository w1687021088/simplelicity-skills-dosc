# long_query_time 阈值设置

`long_query_time` 是控制慢查询日志的核心参数，定义了"多慢算慢"——执行时间超过该阈值（秒）的查询会被记录到慢查询日志中。它支持微秒精度，默认值为 10 秒（对于生产环境几乎没有实际诊断价值）。合理设置 `long_query_time` 是慢查询监控有效性的关键：阈值太高会漏掉很多实际影响用户体验的慢查询，阈值太低则会记录大量正常查询，日志文件快速膨胀，分析成本上升。

---

## long_query_time 的精度与范围

```sql
-- long_query_time 支持微秒精度（6 位小数）
-- 范围：0 到 31536000（1 年），单位：秒

-- 查看当前值：
SHOW VARIABLES LIKE 'long_query_time';
-- long_query_time: 10.000000（默认 10 秒）

-- 动态修改（全局级别，对新连接生效）：
SET GLOBAL long_query_time = 1;        -- 1 秒
SET GLOBAL long_query_time = 0.5;      -- 500 毫秒
SET GLOBAL long_query_time = 0.1;      -- 100 毫秒（高要求场景）
SET GLOBAL long_query_time = 0.001;    -- 1 毫秒（调试用，日志量极大）

-- 修改当前 Session 的阈值（不影响其他连接）：
SET SESSION long_query_time = 0.01;    -- 当前连接 10 毫秒阈值

-- 注意：GLOBAL 修改后，已有的连接仍使用旧值
-- 需要断开重连，或 SET SESSION 明确指定当前连接的值

-- 特殊值 0：记录所有查询（慢查询日志变成全量查询日志）
SET GLOBAL long_query_time = 0;
-- 慎用！在生产环境中设为 0 会记录所有查询，I/O 开销极大
```

## 不同场景的阈值建议

| 场景 | 建议阈值 | 说明 |
|------|:-------:|------|
| 默认值 | 10 秒 | 只能发现严重慢查询，通常需要调低 |
| OLTP 生产环境 | 0.5 ~ 1 秒 | 平衡日志量和发现率，覆盖大多数性能问题 |
| 高性能 OLTP | 0.1 ~ 0.3 秒 | 用户响应时间要求 < 1 秒时适用 |
| 分析/报表查询 | 3 ~ 5 秒 | 分析型查询天然较慢，避免日志噪音 |
| 性能调优期间 | 0.01 ~ 0.1 秒 | 临时降低，发现所有潜在问题 |
| 调试单连接 | 0（Session级）| 只对当前调试连接记录全量查询 |

## 与 min_examined_row_limit 配合使用

```sql
-- min_examined_row_limit：只记录扫描行数超过该值的查询
-- 与 long_query_time 是"AND"关系：两个条件都满足才记录

SHOW VARIABLES LIKE 'min_examined_row_limit';
-- min_examined_row_limit: 0（默认，无最小扫描行限制）

-- 设置：只记录扫描超过 1000 行且执行时间超过 1 秒的查询
SET GLOBAL min_examined_row_limit = 1000;
SET GLOBAL long_query_time = 1;

-- 实践应用：过滤掉小表的慢查询
-- 某些表只有几十行数据，全表扫描也快不了多少
-- 通过 min_examined_row_limit 过滤这类"无意义的慢查询"
-- 聚焦在大表的低效扫描（真正有优化价值的问题）
```

## 记录未使用索引的查询

```sql
-- log_queries_not_using_indexes：记录没有使用索引的查询
-- 独立于 long_query_time（即使查询很快也记录）

SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
-- log_queries_not_using_indexes: OFF（默认）

SET GLOBAL log_queries_not_using_indexes = ON;
-- 开启后，全表扫描的查询即使很快也会被记录

-- 配合 log_throttle_queries_not_using_indexes 限频：
SHOW VARIABLES LIKE 'log_throttle_queries_not_using_indexes';
-- log_throttle_queries_not_using_indexes: 0（无限制，默认）

SET GLOBAL log_throttle_queries_not_using_indexes = 10;
-- 每分钟最多记录 10 条"未使用索引"的警告
-- 防止小表的全表扫描（如 SELECT * FROM config WHERE key='x'）淹没日志

-- 实践：在 long_query_time = 1 的基础上开启此选项
-- 可以发现一些"暂时很快但有风险"的全表扫描
-- 等数据量增长后可能变成慢查询的隐患
```

## 修改阈值的操作时序

```sql
-- 修改 long_query_time 的操作时序（重要！）

-- 1. 修改全局变量（对新连接生效）
SET GLOBAL long_query_time = 1;

-- 2. 修改当前连接（对当前 Session 立即生效）
SET SESSION long_query_time = 1;
-- 不修改 Session 则当前连接仍用旧值

-- 3. 在 my.cnf 中持久化（服务器重启后保持）
-- [mysqld]
-- long_query_time = 1
-- 如果只在运行时修改而不持久化，重启后恢复为文件中的值（或默认值 10）

-- 4. MySQL 8.0+ 的持久化方式（无需修改文件）
SET PERSIST long_query_time = 1;
-- 同时修改运行时值和持久化（写入 mysqld-auto.cnf），重启后保持

-- 验证配置（对比 Global 和 Session 的值）：
SELECT @@GLOBAL.long_query_time AS global_val,
       @@SESSION.long_query_time AS session_val;
```

## 监控慢查询数量的变化

```sql
-- Slow_queries 状态变量记录自 MySQL 启动以来的慢查询总数
SHOW GLOBAL STATUS LIKE 'Slow_queries';
-- Slow_queries: 1234

-- 计算慢查询速率（每分钟新增数量）：
-- 取两次 Slow_queries 的差值 ÷ 时间间隔
-- 例如：5分钟内 Slow_queries 从 1234 增加到 1334
-- 慢查询速率：(1334 - 1234) / 5 = 20 条/分钟

-- 通过 Performance Schema 查看 long_query_time 的实时效果：
SELECT EVENT_NAME, COUNT_STAR, SUM_TIMER_WAIT/1e12 AS total_seconds
FROM performance_schema.events_statements_summary_global_by_event_name
WHERE EVENT_NAME = 'statement/sql/select'
ORDER BY SUM_TIMER_WAIT DESC LIMIT 1 \G

-- 结合 information_schema.PROCESSLIST 查看当前执行时间超阈值的查询：
SELECT ID, USER, HOST, DB, COMMAND, TIME, STATE, INFO
FROM information_schema.PROCESSLIST
WHERE COMMAND != 'Sleep' AND TIME > 1  -- 执行超过 1 秒的查询
ORDER BY TIME DESC \G
```

## 适用场景

- **初次部署后的慢查询基线建立**：在系统上线初期，将 `long_query_time` 设为较低值（如 0.5 秒），结合 `log_queries_not_using_indexes=ON`，运行 3~7 天后分析日志，建立业务的查询性能基线，发现所有潜在的慢查询模式
- **生产故障的快速定位**：当系统响应突然变慢时，临时将 `long_query_time` 降低（如从 1 秒降到 0.1 秒），立即分析最近几分钟的慢查询日志，通常能在几分钟内找到根因

## 常见问题

**SET GLOBAL 修改了 long_query_time，为什么新的慢查询没有按新阈值记录？**

`SET GLOBAL` 只对新建连接生效，对已有连接（包括当前连接）不生效。如果通过连接池（如 Druid、HikariCP）连接数据库，连接池中的现有连接不会自动更新为新的 Session 变量值。解决方法：在修改 `GLOBAL` 后，也执行 `SET SESSION long_query_time = 新值`（仅影响当前连接），或者刷新连接池（关闭所有现有连接，让连接池重新建立），使所有连接使用新的阈值。

## 注意事项

- `long_query_time` 计算的是**查询总时间**（包括锁等待时间），不只是实际执行时间。如果一个查询本身执行只需 0.1 秒，但等待锁花了 2 秒，总时间 2.1 秒超过了阈值，也会被记录。日志中的 `Lock_time` 字段记录了锁等待时间，可以通过 `Query_time - Lock_time` 计算出纯执行时间，区分"慢查询"和"锁等待"两种不同的性能问题。
- 在分析慢查询日志时，不应只关注执行时间（`Query_time`），还应关注 `Rows_examined`（扫描行数）。一些执行时间不超过阈值的查询，如果 `Rows_examined` 很高（如扫描了 100 万行），虽然当前因数据小或 Buffer Pool 热而速度快，随着数据增长会成为隐患。

## 总结

`long_query_time` 控制慢查询日志的记录阈值，默认 10 秒（通常需调低）。支持微秒精度（如 `0.5`=500ms、`0.1`=100ms）。生产 OLTP 环境建议 0.5~1 秒；高性能场景 0.1~0.3 秒；调优期间临时降低到 0.01~0.1 秒。配合参数：`log_queries_not_using_indexes=ON`（发现无索引查询）；`log_throttle_queries_not_using_indexes`（限频避免日志暴涨）；`min_examined_row_limit`（过滤小表扫描噪音）。持久化：`SET PERSIST long_query_time=1`（MySQL 8.0+，重启保持）。通过 `SHOW GLOBAL STATUS LIKE 'Slow_queries'` 监控慢查询数量变化趋势。

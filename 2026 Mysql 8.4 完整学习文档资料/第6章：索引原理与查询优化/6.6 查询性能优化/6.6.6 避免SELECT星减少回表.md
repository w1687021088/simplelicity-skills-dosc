# 避免 SELECT * 减少回表

`SELECT *` 是 SQL 中最常见的写法之一，但也是导致性能问题的常见根源。使用 `SELECT *` 时，MySQL 需要取出所有列的值，这意味着即使查询走了二级索引，也必须回表（通过主键到聚簇索引取完整行）来获取索引中未包含的列。如果改为只 `SELECT` 业务实际需要的列，而这些列恰好都包含在二级索引中，则可以实现**覆盖索引**（Using index），完全避免回表，大幅减少随机 I/O。

---

## SELECT 全列的性能代价

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    note TEXT,           -- 大字段（TEXT），只在少数场景需要
    created_at DATETIME,
    INDEX idx_user_status (user_id, status)
);

-- 使用 SELECT *（必须回表）：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- key: idx_user_status
-- Extra: NULL（无 Using index）← 因为 * 包含了 amount、note、created_at 等不在索引中的列
-- 每行都需要回表（通过主键 id 查聚簇索引）

-- 只 SELECT 索引中包含的列（覆盖索引）：
EXPLAIN SELECT id, user_id, status FROM orders WHERE user_id = 100 AND status = 1 \G
-- key: idx_user_status
-- Extra: Using index  ← 覆盖索引，无回表！
-- id（主键）在二级索引叶子节点中天然包含
-- user_id、status 在 idx_user_status 中
```

## 回表的代价

```
回表的性能代价分析（orders 表，user_id=100 有 1000 行）：

SELECT 全列（有回表）：
1. 通过 idx_user_status 扫描 1000 个索引节点
2. 对每个节点的主键 id，回到聚簇索引取完整行
3. 1000 次随机 I/O（每次读取可能不在同一个数据页）

SELECT id, user_id, status（无回表，覆盖索引）：
1. 通过 idx_user_status 扫描 1000 个索引节点
2. 索引节点中已包含 id、user_id、status，无需回表
3. 0 次额外随机 I/O，顺序扫描索引节点即可

性能差异：
- 数据集较小（1000 行）且在 Buffer Pool 中：差异不明显（内存中随机 I/O 很快）
- 数据集较大（100 万行）且不完全在内存中：差异可能 10x 以上
- 特别是包含 TEXT/BLOB 大字段时，SELECT 全列会读取大字段页面（额外 I/O），代价更高
```

## 覆盖索引设计与 SELECT 列的配合

```sql
-- 根据业务最高频的 SELECT 列设计覆盖索引

-- 场景：订单列表页，只需要 id、user_id、status、amount、created_at
-- 当前索引 idx_user_status (user_id, status) 无法覆盖 amount 和 created_at

-- 方案1：扩展索引（将常用 SELECT 列加入索引）
ALTER TABLE orders ADD INDEX idx_user_status_amount_created
    (user_id, status, amount, created_at);

EXPLAIN SELECT id, user_id, status, amount, created_at
FROM orders WHERE user_id = 100 AND status = 1 \G
-- Extra: Using index（覆盖索引，无回表）

-- 注意：索引过宽会增加写入（INSERT/UPDATE）的维护成本
-- 权衡点：覆盖索引的 SELECT 收益 vs 写入时额外的索引维护成本
-- 高读低写的场景（读多写少）更适合宽覆盖索引

-- 方案2：业务改造，明确 SELECT 必要的列
-- 不建议为了覆盖索引把所有列都加入索引
-- 而是明确业务需要哪些列，删除不必要的列

-- 方案3：保持现有索引，接受少量回表（不一定都需要覆盖索引）
-- 如果回表行数不多（几十行），回表的额外开销很小，可以不扩展索引
```

## SELECT 全列的其他问题

```sql
-- 1. 大字段（TEXT/BLOB）带来额外 I/O
-- TEXT 和 BLOB 列通常不与其他列存储在同一行页（overflow 存储）
-- SELECT 全列包含 TEXT 列 → 需要额外读取 overflow 页面
-- SELECT 不包含 TEXT → 不需要读取 overflow 页面（节省 I/O）

-- 示例（orders 表有 note TEXT 列）：
EXPLAIN SELECT * FROM orders WHERE id = 100 \G
-- MySQL 会读取聚簇索引的行，如果 note 有数据且在溢出页，还需额外读取

-- 只 SELECT 需要的列（不包含 note）：
EXPLAIN SELECT id, user_id, status, amount FROM orders WHERE id = 100 \G
-- 只需读取聚簇索引的主行，不需要读取 note 的溢出页（节省 I/O）

-- 2. 网络传输多余数据
-- SELECT 全列会把所有列通过网络发送到客户端
-- 如果有宽 VARCHAR 列（如 description VARCHAR(2000)），即使业务不需要
-- 也会占用网络带宽，增加客户端解析时间

-- 3. 与 ORDER BY 的交互
-- 大字段进入排序缓冲区（sort_buffer_size），可能导致磁盘排序
-- 如果 ORDER BY 列在索引中但 SELECT 全列还需要其他列，可能影响 index scan
```

## 实际改造步骤

```sql
-- 步骤1：找出使用 SELECT 全列的慢查询
-- 通过慢查询日志 grep 或 Performance Schema 查找
SELECT DIGEST_TEXT, COUNT_STAR, SUM_TIMER_WAIT/1e12 AS total_sec
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%SELECT `%`*%'
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;

-- 步骤2：确认该查询使用了哪个索引（EXPLAIN）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G

-- 步骤3：识别业务实际需要的列（与开发确认）
-- 假设业务只需要 id, user_id, status, created_at

-- 步骤4：改写查询
-- 将 SELECT * 改为 SELECT id, user_id, status, created_at

-- 步骤5：验证是否实现覆盖索引
EXPLAIN SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 100 AND status = 1 \G
-- Extra: Using index  → 覆盖索引，无回表（如果 created_at 在索引中）
-- 如果未能覆盖，考虑是否值得扩展索引

-- 步骤6：在测试环境验证性能改善
-- 使用 EXPLAIN ANALYZE 对比改写前后的实际执行时间和 actual rows
```

## 适用场景

- **高频 API 接口的查询优化**：对于 QPS 很高（每秒数百次）的接口查询（如订单列表、用户信息），将查询全列改为只查必要的列，并配合覆盖索引，可以显著减少每次查询的 I/O 和网络传输，降低数据库负载
- **包含大字段表的查询**：对于含有 `TEXT`、`BLOB`、大 `VARCHAR` 的表，即使回表代价可以接受，避免查询全列也能减少不必要的大字段页面读取，降低 I/O 放大

## 常见问题

**如果表结构将来新增列，SELECT 指定列名的代码就需要修改，维护成本高怎么办？**

这确实是 `SELECT *` 流行的原因之一，但可以通过以下方式平衡维护成本：①在数据访问层（DAO/Repository）使用 ORM 框架（如 MyBatis、Hibernate），通过 ResultMap 映射指定需要的列，新增列时只需更新 ResultMap 而不需要修改所有 SQL；②对于核心业务表，使用接口 DTO 显式定义需要的字段，天然约束了查询全列的使用；③对于真正需要所有列的场景（如数据全量导出），`SELECT *` 是合理的；④对于高频接口，明确指定列的性能收益远超维护成本，值得维护成本的投入。

---

## 注意事项

- 不是所有查询都需要避免查询全列。对于通过主键（或唯一键）直接取一行数据（`WHERE id = ?`）的场景，无论是否写 `SELECT *`，都只有一次聚簇索引查找，回表是不可避免的（主键查询本来就是在聚簇索引上操作），此时查全列和指定列的性能差异主要在于网络传输和大字段读取，而不是回表次数。
- 覆盖索引的收益最大的场景是**二级索引范围扫描**（`type: range` 或 `type: ref`，有大量行需要回表的情况）。如果 `type: const`（主键等值查找），改写查询全列对减少回表没有帮助（因为主键查找本来就直接在聚簇索引，没有"回表"的概念）。

---

## 总结

避免 `SELECT *`（查询全列）的核心价值在于**使覆盖索引成为可能**。当 `SELECT` 的所有列都包含在二级索引中时（包括主键 id，天然在二级索引叶子节点），查询可以只扫描索引而不需要回表（EXPLAIN Extra: Using index），消除随机 I/O。改造步骤：通过慢查询日志找到查询全列的慢 SQL → EXPLAIN 分析当前执行计划 → 明确业务需要的列 → 改写查询 → 检查是否能用覆盖索引 → 必要时扩展索引。注意：主键等值查找中查全列无回表问题；大字段（TEXT/BLOB）的 overflow 页读取是查全列的隐性代价。对于高读低写的高频查询，覆盖索引的优化价值远超索引维护的额外成本。

# 大分页优化书签记录

书签记录（Bookmark / Seek Method / Cursor-based Pagination）是解决大分页问题的另一种思路，原理与延迟关联完全不同。延迟关联减少了回表次数，但仍然需要扫描大量索引节点（offset 越大扫描越多）；书签记录通过记录上一页最后一行的排序列值，下一页查询时直接从这个值之后开始，**完全避免了扫描前 offset 行**，每次翻页的查询代价都是恒定的（始终只扫描 count 行），不随页码增大而恶化。

---

## 书签记录的核心原理

```sql
-- 传统 LIMIT offset 的问题：
-- LIMIT 100000, 20 → 扫描前 100000 行再取 20 行（线性增长）

-- 书签记录的原理：
-- 记住上一页最后一行的排序列值（如 created_at 和 id）
-- 下一页查询：WHERE created_at > ? OR (created_at = ? AND id > ?)
-- 直接从该值之后开始，每次只扫描 20 行（恒定代价！）

-- 适用前提：
-- 1. 排序列有索引
-- 2. 排序顺序固定（只能向后翻页，不能跳页）
-- 3. 应用层能保存"书签"（上一页末行的排序值）
```

---

## 单列书签（按主键分页）

```sql
-- 最简单的书签：按主键（自增 ID）排序分页
-- 这是书签记录最常见的应用场景

-- 第一页（无书签）：
SELECT id, user_id, amount, created_at
FROM orders
ORDER BY id
LIMIT 20;
-- 返回 20 行，记住最后一行的 id（假设 last_id = 20）

-- 第二页（书签 = 20）：
SELECT id, user_id, amount, created_at
FROM orders
WHERE id > 20
ORDER BY id
LIMIT 20;
-- 直接从 id=20 之后扫描，只扫描 20 行！

-- 第 N 页（书签 = 上一页最后的 id）：
SELECT id, user_id, amount, created_at
FROM orders
WHERE id > :last_id
ORDER BY id
LIMIT 20;

-- EXPLAIN 对比：
-- 传统 LIMIT：EXPLAIN SELECT * FROM orders ORDER BY id LIMIT 100000, 20
-- rows: 100020, Extra: Using index（需要扫描 10 万行）

-- 书签记录：EXPLAIN SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20
-- type: range, key: PRIMARY, rows: 20（只扫描 20 行！）
-- Extra: Using where; Using index（覆盖索引 + 范围条件，极高效）
```

## 多列书签（按非唯一列分页）

```sql
-- 当排序列不是唯一键时（如按 created_at 排序），需要多列书签
-- 目的：确保分页结果的唯一性和一致性

-- 问题：如果多行 created_at 相同（同一秒内的多个订单），
-- 仅用 created_at 做书签会漏行或重复行

-- 多列书签方案（created_at + id 组合唯一）：
-- 上一页最后一行：created_at = '2025-01-15 10:00:00', id = 5000

-- 下一页查询（正确处理 created_at 相同的情况）：
SELECT id, user_id, amount, created_at
FROM orders
WHERE created_at > '2025-01-15 10:00:00'
   OR (created_at = '2025-01-15 10:00:00' AND id > 5000)
ORDER BY created_at, id
LIMIT 20;

-- 此写法的问题：OR 条件可能导致索引失效（参见 6.3.3 Index Merge）
-- 更高效的等价写法（使用行比较）：
SELECT id, user_id, amount, created_at
FROM orders
WHERE (created_at, id) > ('2025-01-15 10:00:00', 5000)
ORDER BY created_at, id
LIMIT 20;
-- MySQL 支持行比较（Row Constructor Comparison）
-- 等价于：(created_at > 'x') OR (created_at = 'x' AND id > 5000)
-- 但 MySQL 优化器对行比较的索引利用有限，建议 EXPLAIN 验证

-- 最可靠的多列书签写法（两步法，完全利用索引）：
-- 第一步：用 created_at 索引定位
SELECT id, user_id, amount, created_at
FROM orders
WHERE created_at >= '2025-01-15 10:00:00'   -- >= 包含边界
  AND (created_at > '2025-01-15 10:00:00'   -- 超过边界的行
       OR id > 5000)                          -- 或同时间但 id 更大的行
ORDER BY created_at, id
LIMIT 20;
```

## 书签记录的应用层实现

```python
# 伪代码：应用层如何实现书签翻页

# 初始化（第一页）
last_created_at = None
last_id = None

def get_next_page(conn, page_size=20):
    if last_created_at is None:
        # 第一页，无书签
        sql = """
            SELECT id, user_id, amount, created_at 
            FROM orders 
            ORDER BY created_at, id 
            LIMIT %s
        """
        rows = conn.execute(sql, (page_size,))
    else:
        # 后续页，使用书签
        sql = """
            SELECT id, user_id, amount, created_at 
            FROM orders 
            WHERE (created_at, id) > (%s, %s)
            ORDER BY created_at, id 
            LIMIT %s
        """
        rows = conn.execute(sql, (last_created_at, last_id, page_size))
    
    if rows:
        # 更新书签为当前页最后一行
        last_created_at = rows[-1]['created_at']
        last_id = rows[-1]['id']
    
    return rows
```

## 书签记录 vs 延迟关联 vs 传统 LIMIT 对比

| 对比维度 | 传统 LIMIT | 延迟关联 | 书签记录 |
|---------|:--------:|:------:|:------:|
| 查询代价随页码变化 | 线性增长 | 线性增长（索引层）| 恒定（始终 count 行）|
| 是否支持跳页 | 支持 | 支持 | 不支持 |
| 代码复杂度 | 最低 | 中等 | 较高（需记录书签）|
| 需要的索引 | 排序列索引 | 覆盖索引（排序+SELECT）| 排序列索引（即可）|
| 适用场景 | 小 offset | 中等 offset | 大 offset、流式遍历 |
| 前后翻页 | 支持 | 支持 | 仅向后翻页（扩展可支持双向）|

## 适用场景

- **无限滚动/瀑布流加载**：移动端或 Web 的无限滚动页面，用户持续下拉加载更多内容，本质上是按书签依次取下一批数据，不需要跳页，完全匹配书签记录的特性，且每次加载代价恒定
- **大表全量遍历（ETL/数据导出）**：需要遍历数百万行数据的 ETL 作业或批量数据导出，使用书签记录代替 `LIMIT offset, batch_size`，每批次性能恒定，不会因 offset 增大而越来越慢，整体遍历时间可预期

## 常见问题

**书签记录方案如何支持"向前翻页"（回到上一页）？**

标准的书签记录只能向后翻页，要支持向前翻页需要额外处理：①应用层缓存已访问页的书签列表（如 `bookmarks = [null, id_20, id_40, id_60, ...]`，`bookmarks[n]` 是第 n 页的起始书签），向前翻页时使用 `bookmarks[当前页-1]` 作为书签；②或者改为"双向书签"：向前翻页时使用 `WHERE (created_at, id) < (:bookmark) ORDER BY created_at DESC, id DESC LIMIT 20`（反向排序），取到结果后在应用层再反转顺序显示。这些方案增加了应用层复杂度，需要根据业务需求权衡。

---

## 注意事项

- 书签记录要求**排序列组合必须唯一**，否则可能出现漏行或重复行。如果主排序列（如 `created_at`）不唯一，必须加上主键（`id`）作为第二排序列，确保每行有唯一的"坐标"，书签才能精确定位。
- 书签记录对**索引的要求**：`ORDER BY` 的列需要有索引，且最好是这些列的联合索引（如 `idx_created_id(created_at, id)`），使范围查询 `WHERE (created_at, id) > (?, ?)` 能走索引扫描。如果索引不覆盖 SELECT 的所有列，仍然需要回表，但只有 `count` 行（不是 `offset + count` 行），与传统 LIMIT 相比仍然高效。

## 总结

书签记录（Cursor-based Pagination）通过记录上一页末行的排序列值作为书签，下一页直接从该值之后开始查询（`WHERE sort_col > last_val`），完全避免扫描前 offset 行，每次翻页代价恒定（只扫描 count 行）。单列书签（按主键）最简单，直接用 `WHERE id > :last_id`；多列书签（按非唯一列）需要组合列保证唯一性（如 `WHERE (created_at, id) > (:last_created_at, :last_id)`）。核心优势：代价恒定，不随页码增大而恶化。核心局限：不支持跳页（只能顺序翻页）。适合：无限滚动加载、大表全量遍历/ETL。需与延迟关联结合理解：延迟关联减少回表次数，书签记录消除索引节点扫描，两者解决的侧重点不同。

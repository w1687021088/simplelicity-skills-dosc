# 慢查询日志分析工具 mysqldumpslow

`mysqldumpslow` 是 MySQL 自带的慢查询日志分析工具，通过对慢查询日志文件进行聚合分析，将执行模式相同的 SQL（只有参数值不同）合并统计，输出按指定指标排序的慢查询摘要。这大大降低了分析大型慢查询日志的工作量——一个运行几天的日志文件中可能有数十万条记录，但实际的 SQL 模式通常只有几十到几百种，`mysqldumpslow` 能将这些模式快速归类并按危害程度排序。

---

## 基本语法与常用选项

```bash
# 基本语法
mysqldumpslow [选项] [日志文件路径]

# 常用选项：
# -s order  排序方式（最重要的选项）
#   t  按总执行时间排序（time）
#   at 按平均执行时间排序（average time）
#   c  按执行次数排序（count）
#   l  按总锁定时间排序（lock time）
#   al 按平均锁定时间排序（average lock time）
#   r  按总返回行数排序（rows）
#   ar 按平均返回行数排序（average rows）

# -t N  只输出前 N 条（Top N）
# -g pattern  按正则表达式过滤 SQL
# -a  不对数字和字符串进行抽象（默认数字抽象为 N，字符串抽象为 'S'）
# -n N  SQL 中数字超过 N 个才抽象（避免过度抽象）

# 示例：按总执行时间排序，输出前 10 条
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按执行次数排序，输出前 20 条
mysqldumpslow -s c -t 20 /var/log/mysql/slow.log

# 按平均执行时间排序，只看 SELECT 语句
mysqldumpslow -s at -t 10 -g "SELECT" /var/log/mysql/slow.log
```

## 输出结果解读

```
# mysqldumpslow -s t -t 5 /var/log/mysql/slow.log 的输出示例：

Reading mysql slow query log from /var/log/mysql/slow.log
Count: 234  Time=2.85s (667s)  Lock=0.00s (0s)  Rows=100.0 (23400), app[app]@10.0.0.1
SELECT o.id, o.amount, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = N ORDER BY o.created_at LIMIT N, N

Count: 1892  Time=0.53s (1003s)  Lock=0.00s (0s)  Rows=1.0 (1892), app[app]@10.0.0.1
SELECT * FROM orders WHERE id = N

-- 字段含义：
-- Count: 234         → 该 SQL 模式共执行了 234 次
-- Time=2.85s (667s)  → 平均执行 2.85 秒，总计执行 667 秒
-- Lock=0.00s (0s)    → 平均锁等待 0 秒，总计 0 秒
-- Rows=100.0 (23400) → 平均返回 100 行，总计返回 23400 行
-- app[app]@10.0.0.1  → 执行用户和来源 IP

-- SQL 中的抽象：
-- N    → 数字（WHERE id = N 表示 WHERE id = 具体数字）
-- 'S'  → 字符串（WHERE name = 'S' 表示 WHERE name = 具体字符串）

-- 排序后第一条（最慢的 SQL）：234 次执行，总耗时 667 秒
-- 这是优化的首要目标：虽然平均 2.85 秒，但执行次数多，总耗时最大
```

## 输出优先级分析

```bash
# 不同排序维度关注不同问题：

# 1. 按总执行时间（-s t）：影响最大的 SQL
# → 高频 + 稍慢 = 对数据库总体负担最大
# → 优先优化这类查询

# 2. 按平均执行时间（-s at）：单次最慢的 SQL
# → 通常是大结果集查询或没有索引的全表扫描
# → 可能是偶发性的、用户等待时间最长的查询

# 3. 按执行次数（-s c）：最高频的 SQL
# → 即使单次不慢，高频执行会产生大量 I/O 和 CPU 消耗
# → 适合找"接口热点"（哪些查询被调用最多）

# 4. 按总锁时间（-s l）：锁等待严重的 SQL
# → 查找锁竞争严重的表或业务场景
# → 锁等待高通常需要优化事务或业务逻辑，而不只是索引

# 多维度分析建议：
# 先用 -s t 找最大资源消耗者
# 再用 -s at 找单次最差的查询（可能是低频但严重的问题）
# 然后用 -s c 验证高频查询是否有性能隐患
```

## 实战：完整分析流程

```bash
# 步骤1：确认慢查询日志路径
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query_log_file'"
# Value: /var/log/mysql/mysql-slow.log

# 步骤2：先看下日志基本信息（行数、时间范围）
wc -l /var/log/mysql/mysql-slow.log
head -5 /var/log/mysql/mysql-slow.log  # 查看最早记录时间
tail -5 /var/log/mysql/mysql-slow.log  # 查看最新记录时间

# 步骤3：按总时间找 Top 10
mysqldumpslow -s t -t 10 /var/log/mysql/mysql-slow.log > /tmp/slow_top10_time.txt
cat /tmp/slow_top10_time.txt

# 步骤4：按次数找 Top 10（找高频慢查询）
mysqldumpslow -s c -t 10 /var/log/mysql/mysql-slow.log > /tmp/slow_top10_count.txt
cat /tmp/slow_top10_count.txt

# 步骤5：过滤特定数据库的慢查询
mysqldumpslow -s t -t 10 -g "mydb" /var/log/mysql/mysql-slow.log

# 步骤6：对找到的 SQL 执行 EXPLAIN 分析
# 用实际参数值替换 N/'S'，执行 EXPLAIN
EXPLAIN SELECT o.id, o.amount, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = 1 ORDER BY o.created_at LIMIT 0, 100 \G

# 步骤7：建立优化方案并验证
```

## pt-query-digest（更强大的替代工具）

```bash
# pt-query-digest 是 Percona Toolkit 中的高级慢查询分析工具
# 功能比 mysqldumpslow 更强大：
# - 指纹识别更智能（更好的 SQL 抽象）
# - 支持更多统计维度（响应时间分布、Rows_examined 统计等）
# - 支持实时分析 processlist（不需要日志文件）
# - 支持将分析结果写入数据库表

# 安装 Percona Toolkit（Debian/Ubuntu）
apt-get install percona-toolkit

# 基本使用
pt-query-digest /var/log/mysql/mysql-slow.log > /tmp/slow_report.txt

# 只分析最近 24 小时的记录
pt-query-digest --since 24h /var/log/mysql/mysql-slow.log

# 分析结果写入 MySQL 表（便于历史对比）
pt-query-digest \
    --review h=127.0.0.1,D=percona,t=query_review \
    --history h=127.0.0.1,D=percona,t=query_history \
    /var/log/mysql/mysql-slow.log

# pt-query-digest 的输出包含：
# - 各查询的 P95/P99 响应时间（百分位数）
# - 每种查询的 Rows_examined 分布
# - QPS（每秒查询数）趋势
# 比 mysqldumpslow 更适合生产级别的慢查询分析
```

## 适用场景

- **日常慢查询报告生成**：将 `mysqldumpslow -s t -t 20 慢查询日志` 加入每日定时任务，自动生成 Top 20 慢查询报告，发送给开发团队，形成持续的性能监控闭环
- **新版本上线后的快速验证**：应用新版本部署后，立即运行 `mysqldumpslow` 分析上线后几分钟内的慢查询日志（降低 `long_query_time` 至 0.5 秒），快速发现新代码引入的查询性能问题

## 常见问题

**mysqldumpslow 输出的 SQL 中 N 和 'S' 有时没有按预期抽象，导致相同模式的 SQL 被分开统计了，怎么办？**

这通常发生在 SQL 中含有复杂的 IN 列表（如 `WHERE id IN (1,2,3,4,5)`）或特殊格式的常量时，`mysqldumpslow` 的抽象规则未能完全识别。解决方法：①使用 `-a` 选项关闭抽象（查看原始 SQL），手动分析哪些是同一模式；②使用 `pt-query-digest`，其指纹识别算法更完善，能正确处理 IN 列表和其他复杂常量形式；③对于核心业务查询，直接在慢查询日志中用 `grep` 搜索特定 SQL 模式进行精确分析。

---

## 注意事项

- `mysqldumpslow` 的输出中，SQL 里的 `N` 代表所有数字（包括 0、负数、浮点数），`'S'` 代表所有字符串。相同结构但不同参数值的 SQL 会被合并到同一条统计。但如果 SQL 有语法差异（如大小写不同、空格数量不同），`mysqldumpslow` 可能无法合并，导致相同逻辑的 SQL 被统计为不同条目，`pt-query-digest` 在这方面表现更好。
- `mysqldumpslow` 对于非常大的日志文件（GB 级别）分析速度较慢（单线程处理）。对于大文件，可以先用 `tail -n 100000` 截取最近的记录，或按时间段分割文件后再分析，减少单次处理量。

## 总结

`mysqldumpslow` 是 MySQL 自带的慢查询日志聚合分析工具，核心功能是将相同 SQL 模式（数字→N，字符串→'S'）合并统计。主要选项：`-s t`（按总时间排序）、`-s at`（按平均时间）、`-s c`（按次数）、`-t N`（Top N）、`-g pattern`（过滤）。分析策略：`-s t` 找总资源消耗最大的 SQL（优先优化）→ `EXPLAIN` 分析执行计划 → 建索引/改写 SQL → 验证。高级替代：`pt-query-digest`（Percona Toolkit）功能更强，支持 P95/P99 时间分布、实时 processlist 分析、结果写入 DB，适合生产级深度分析。

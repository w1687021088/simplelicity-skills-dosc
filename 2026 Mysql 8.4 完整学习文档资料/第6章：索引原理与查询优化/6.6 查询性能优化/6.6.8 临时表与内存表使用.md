# 临时表与内存表使用

在 MySQL 查询优化中，"临时表"和"内存表"是两个相关但含义不同的概念。**内部临时表**（Internal Temporary Table）是 MySQL 在执行 GROUP BY、ORDER BY、UNION 等操作时自动创建的中间结果存储，对用户透明；**内存表**（MEMORY Table）是用 `ENGINE=MEMORY` 显式创建的持久化表，数据存储在内存中。理解两者的工作机制、触发条件和性能影响，有助于优化涉及排序、聚合、大结果集的复杂查询。

---

## 内部临时表（Internal Temporary Table）

```sql
-- 内部临时表由 MySQL 自动创建，用于以下场景：
-- 1. GROUP BY 列没有索引（无法用索引排序完成聚合）
-- 2. DISTINCT 需要去重
-- 3. ORDER BY 和 GROUP BY 使用不同的列
-- 4. UNION（合并两个结果集）
-- 5. 子查询物化（select_type: DERIVED 或 MATERIALIZED）
-- 6. 窗口函数（Window Functions）
-- 7. 派生表无法被合并（Derived Merge 不适用的情况）

-- 识别内部临时表（EXPLAIN Extra 字段）：
EXPLAIN SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id \G
-- Extra: Using temporary; Using filesort
--        ↑ 创建了临时表   ↑ 临时表中数据需要排序

-- 没有临时表的等效操作（索引覆盖 GROUP BY）：
-- 如果 user_id 有索引：
ALTER TABLE orders ADD INDEX idx_user (user_id);
EXPLAIN SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id \G
-- Extra: Using index（利用索引的有序性完成 GROUP BY，无临时表）
```

## 内部临时表的存储引擎演进

```sql
-- MySQL 5.7 及之前：
-- 内存临时表：MEMORY 引擎（不支持 TEXT/BLOB 列）
-- 磁盘临时表：MyISAM 引擎

-- MySQL 8.0：
-- 内存临时表：TempTable 引擎（支持 TEXT/BLOB、VARCHAR 列）
-- 磁盘临时表：InnoDB 引擎（更安全，崩溃恢复更好）
-- 可通过参数控制：
SHOW VARIABLES LIKE 'internal_tmp_mem_storage_engine';
-- internal_tmp_mem_storage_engine: TempTable（MySQL 8.0 默认）

-- TempTable 的内存限制：
SHOW VARIABLES LIKE 'temptable_max_ram';
-- temptable_max_ram: 1073741824（默认 1GB）
-- 超过此限制时，转为磁盘临时表（InnoDB 格式）

-- 磁盘临时表的存储位置：
SHOW VARIABLES LIKE 'tmpdir';
-- tmpdir: /tmp（临时文件目录）
```

## 内部临时表的性能影响与优化

```sql
-- 内存临时表 vs 磁盘临时表的代价差异（cost model）：
-- memory_temptable_create_cost: 1.0
-- disk_temptable_create_cost: 20.0（20 倍！）

-- 监控临时表的使用情况：
SHOW GLOBAL STATUS LIKE 'Created_tmp_tables';        -- 内存临时表总数
SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables';   -- 磁盘临时表总数
-- 如果 Created_tmp_disk_tables / Created_tmp_tables > 10%，说明内存不足
-- 考虑增大 tmp_table_size / max_heap_table_size

-- 临时表内存相关参数：
SHOW VARIABLES LIKE 'tmp_table_size';        -- 默认 16MB
SHOW VARIABLES LIKE 'max_heap_table_size';   -- 默认 16MB
-- 内存临时表超过 min(tmp_table_size, max_heap_table_size) → 转为磁盘临时表

-- 增大内存临时表限制（Session 级别，避免磁盘临时表）：
SET SESSION tmp_table_size = 67108864;        -- 64MB
SET SESSION max_heap_table_size = 67108864;   -- 64MB

-- 注意：每个连接独享这段内存，高并发时总内存消耗 = 并发数 × 设置值

-- 优化临时表的根本方法：
-- 1. 添加索引（让 GROUP BY 走索引，不需要临时表）
-- 2. 减少参与聚合的行数（WHERE 条件提前过滤）
-- 3. 避免 SELECT 大字段列进入临时表（TEXT/BLOB 强制使用磁盘临时表）
```

## MEMORY 内存表（显式创建）

```sql
-- MEMORY 表（ENGINE=MEMORY）：数据完全在内存中，速度极快
-- 重启后数据丢失（结构保留，数据清空）

-- 创建内存表：
CREATE TABLE cache_session (
    session_id VARCHAR(64) PRIMARY KEY,
    user_id INT NOT NULL,
    data TEXT,
    expire_at DATETIME,
    INDEX idx_user (user_id)
) ENGINE=MEMORY;

-- MEMORY 表的特点：
-- 默认使用哈希索引（HASH INDEX）→ 等值查询极快，不支持范围查询
-- 可以显式指定 BTREE 索引（支持范围查询）：
CREATE TABLE cache_session (
    session_id VARCHAR(64),
    expire_at DATETIME,
    PRIMARY KEY USING BTREE (session_id),     -- 明确指定 BTREE
    INDEX USING BTREE (expire_at)             -- 范围查询需要 BTREE
) ENGINE=MEMORY;

-- MEMORY 表的限制：
-- 不支持 TEXT / BLOB 类型（存在长度限制）
-- 不支持 AUTO_INCREMENT
-- 固定行格式（VARCHAR 按最大长度分配空间）
-- 不支持事务和外键
-- 并发写入性能受表级锁影响（不是行级锁）
```

## MEMORY 表的使用场景与注意事项

```sql
-- 典型使用场景1：高频读取的小数据集（查找表/字典表）
-- 如：城市编码表、汇率表、配置参数表
CREATE TABLE city_code (
    code CHAR(6) PRIMARY KEY,
    name VARCHAR(50) NOT NULL
) ENGINE=MEMORY;
-- 每次查询都是等值查找，哈希索引极快

-- 典型使用场景2：临时计算中间结果（ETL 中间层）
-- 在存储过程或复杂 ETL 中，将中间计算结果存入 MEMORY 表，
-- 多步骤处理后汇总，最后写入 InnoDB 表

-- 典型使用场景3：会话缓存（轻量级，注意崩溃丢失风险）
-- 小型应用的会话数据（重启后数据丢失是可接受的）

-- 重启后数据丢失的处理：
-- 在 MySQL 启动后（或服务器重启后），需要从持久化来源重新填充 MEMORY 表数据
-- 可以在 MySQL 启动脚本或应用层初始化时执行 INSERT ... SELECT ... FROM innodb_table

-- MEMORY 表的并发写入问题：
-- MEMORY 表使用表级锁（不是 InnoDB 的行级锁）
-- 高并发写入时性能较差（写操作锁全表）
-- 如果有并发写入需求，优先使用 InnoDB 表 + 提高 Buffer Pool 命中率，而不是 MEMORY 表
```

## MEMORY 表 vs 内部临时表 vs InnoDB 表对比

| 对比维度 | MEMORY 表 | 内部临时表（TempTable）| InnoDB 表 |
|---------|:--------:|:-------------------:|:--------:|
| 持久性 | 结构持久，数据重启丢失 | 完全临时（查询结束销毁）| 持久 |
| 事务支持 | 无 | 无 | 有（ACID）|
| 行级锁 | 无（表级锁）| 无 | 有 |
| 最大大小 | max_heap_table_size | temptable_max_ram | 磁盘限制 |
| TEXT/BLOB | 不支持 | 支持（TempTable）| 支持 |
| 索引类型 | HASH（默认）/ BTREE | 内部（无用户控制）| BTREE（B+树）|
| 典型用途 | 字典缓存、会话 | 聚合/排序中间结果 | 业务数据 |

## 适用场景

- **优化含临时表的慢查询**：当 EXPLAIN 显示 `Using temporary` 时，首先检查能否通过添加索引消除临时表（如为 GROUP BY 列添加索引）。如果无法消除，通过 `SET SESSION tmp_table_size = 64M` 临时增大内存限制，避免因临时表溢出到磁盘导致额外 I/O
- **高频访问的小型字典表**：对于系统中被频繁查询的小型参考表（如几千行的城市码表、配置表），使用 MEMORY 引擎可以将所有查找变为纯内存操作，但需要处理重启后的数据填充问题，并评估并发写入是否可以接受表级锁的限制

## 常见问题

**为什么有时候明明数据量不大，仍然出现磁盘临时表（Created_tmp_disk_tables 增加）？**

最常见的原因是查询中包含了 `TEXT` 或 `BLOB` 类型的列。即使在 MySQL 8.0 的 TempTable 引擎下，如果临时表中需要存储 TEXT/BLOB 列（因为 SELECT 包含了这些列，或者 GROUP BY / ORDER BY 操作需要处理这些列），在 MySQL 5.7 的 MEMORY 引擎中会直接转为磁盘临时表；MySQL 8.0 的 TempTable 引擎支持 TEXT/BLOB，但如果数据量超过 `temptable_max_ram` 仍会转磁盘。解决方法：检查查询中是否必须包含大字段列；如果不需要 TEXT 列参与排序/聚合，将其从 SELECT 中移除；或者将 TEXT 列分离到单独的附属表（垂直拆分）。

## 注意事项

- `MEMORY` 表使用 `max_heap_table_size` 控制单个表的最大大小，而不是 `tmp_table_size`（`tmp_table_size` 控制**内部临时表**的最大大小）。两个参数名称相似但控制不同的对象，容易混淆。如果 MEMORY 表数据量超过 `max_heap_table_size`，MySQL 会返回错误（`ERROR 1114: The table 'xxx' is full`），而不是自动转为磁盘。
- 在 MySQL 8.4 中，`temptable_max_mmap`（默认 1GB）控制 TempTable 引擎在内存不足时将部分数据映射到内存映射文件（而不是直接写入磁盘的 InnoDB 临时表），这是介于纯内存和磁盘之间的一种混合模式，可以通过 `SHOW VARIABLES LIKE 'temptable_max_mmap'` 查看和调整。

## 总结

内部临时表（Internal Temporary Table）是 MySQL 自动创建的中间结果存储（不对用户可见），由 GROUP BY 无索引、ORDER BY+GROUP BY 不同列、UNION、子查询物化等触发，EXPLAIN Extra 显示 `Using temporary`。MySQL 8.0 使用 TempTable 引擎（内存，支持 TEXT/BLOB）+ InnoDB（磁盘回退），通过 `tmp_table_size`/`max_heap_table_size` 控制内存上限。MEMORY 显式表（`ENGINE=MEMORY`）：数据完全在内存，重启后数据丢失，使用哈希索引（等值查询快，范围查询需 BTREE），表级锁（并发写入受限），适合字典缓存、ETL 中间结果。优化方向：尽量通过索引消除内部临时表（`Using temporary` 是性能警告）；监控 `Created_tmp_disk_tables/Created_tmp_tables` 比率，过高时增大内存临时表限制。

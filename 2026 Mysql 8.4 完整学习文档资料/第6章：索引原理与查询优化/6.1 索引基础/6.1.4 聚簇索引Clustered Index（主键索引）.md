# 聚簇索引 Clustered Index（主键索引）

聚簇索引（Clustered Index）是 InnoDB 存储表数据的核心方式。InnoDB 的表本质上是一棵 B+树，这棵树的叶子节点存储了完整的行数据，树的键值就是主键。这意味着 InnoDB 中"表数据"和"主键索引"是同一个物理结构——数据按主键顺序物理排列，不存在独立于数据的"主键索引文件"。理解聚簇索引是掌握 InnoDB 所有索引原理的前提。

---

## 聚簇索引的物理结构

```
聚簇索引 B+树结构（以主键 id 为例）：

内部节点（只存键值）：
  [id=100 | id=500 | id=1000]
  /           |            \
子树1       子树2          子树3

叶子节点（存储完整行数据）：
  [id=1, name='Alice', age=25, email='a@a.com']
  [id=2, name='Bob',   age=30, email='b@b.com']
  ...
  [id=100, name='Carol', ...]
  ↔ 双向链表 ↔
  [id=101, name='David', ...]
  ...

特点：
  叶子节点直接存储行的所有列（即表数据）
  叶子节点按主键值有序排列
  叶子节点通过双向链表连接
```

---

## 聚簇索引的确定规则

```sql
-- InnoDB 按以下优先级确定聚簇索引键：

-- 规则1：存在主键（PRIMARY KEY）→ 使用主键作为聚簇索引
CREATE TABLE orders (
    id INT PRIMARY KEY,       -- 聚簇索引键 = id
    user_id INT,
    amount DECIMAL(10,2)
);

-- 规则2：没有主键，但有非 NULL 唯一索引 → 使用第一个非 NULL 唯一索引
CREATE TABLE logs (
    log_uuid CHAR(36) NOT NULL UNIQUE,  -- 聚簇索引键 = log_uuid
    message TEXT,
    created_at DATETIME
);

-- 规则3：既没有主键也没有非 NULL 唯一索引 → InnoDB 自动生成隐藏的 6 字节 DB_ROW_ID 作为聚簇索引
-- （推荐避免此情况，影响性能且无法对外引用）
CREATE TABLE temp_data (
    data TEXT               -- 无主键，InnoDB 自动生成 DB_ROW_ID
);

-- 查看聚簇索引（PRIMARY KEY）
SHOW INDEX FROM orders WHERE Key_name = 'PRIMARY';
```

## 聚簇索引与数据访问

```sql
-- 通过主键查询（直接走聚簇索引，一步到位）：
SELECT * FROM orders WHERE id = 1001;
-- 过程：
-- 1. 从 B+树根节点向下查找 id=1001
-- 2. 到达叶子节点，叶子节点直接包含所有列数据
-- 3. 返回结果（无需回表）
-- I/O：2~3 次（树高），通常根节点已在 Buffer Pool 中

-- 范围查询（利用叶子节点链表）：
SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000;
-- 过程：
-- 1. 定位 id=1000 的叶子节点
-- 2. 沿链表顺序扫描直到 id=2000
-- 顺序 I/O，效率高

-- 主键排序（利用聚簇索引有序性）：
SELECT * FROM orders ORDER BY id LIMIT 100;
-- 直接顺序读取叶子节点，无需 filesort
```

## 聚簇索引与数据物理排列

```
聚簇索引的"聚簇"含义：
  数据行与索引键值"聚集"在一起存储
  → 数据行按主键值的顺序物理排列在磁盘上

主键选择对物理排列的影响：
  自增主键（1, 2, 3, ...）：
    新行总是插入到 B+树末尾（append only）
    不会引起中间节点的分裂
    → 顺序写入，性能最优

  随机主键（UUID、随机 INT）：
    新行插入到 B+树的随机位置
    频繁引起节点分裂（随机 I/O，页碎片）
    → 随机写入，性能相对较低

  建议：OLTP 系统优先使用 AUTO_INCREMENT 整型主键
```

## 聚簇索引的特点汇总

| 特性 | 说明 |
|------|------|
| 每表只有一个 | InnoDB 表只能有一个聚簇索引 |
| 叶子节点存完整行 | 不需要"回表"（主键查询直接获取所有列）|
| 数据按主键有序 | 支持高效范围查询和 ORDER BY 主键 |
| 主键即索引 | 没有独立的主键索引文件，表即索引 |
| 主键短则二级索引小 | 所有二级索引叶子节点都存储主键值 |

---

## 适用场景

- **主键设计指导**：聚簇索引的特性决定了 OLTP 系统应优先选择短整型自增主键（`INT AUTO_INCREMENT` 或 `BIGINT AUTO_INCREMENT`），既可以减少二级索引的空间开销，又能避免随机插入导致的页分裂和碎片
- **主键范围查询的优化**：在分页查询、数据迁移、批量处理等场景中，基于主键的范围查询（`WHERE id > N LIMIT 1000`）利用聚簇索引的顺序性，是最高效的大批量数据遍历方式

## 常见问题

**InnoDB 表可以没有主键吗？有什么影响？**

可以，但不推荐。没有显式主键且没有非 NULL 唯一索引时，InnoDB 会自动创建一个隐藏的 6 字节 `DB_ROW_ID` 作为聚簇索引键。这个隐藏列无法被业务层引用（无法用于 JOIN、WHERE 等），也无法被 MySQL 主从复制的 STATEMENT 格式正确识别，可能导致复制不一致。此外，所有二级索引都会用 `DB_ROW_ID` 作为行指针，6 字节比通常的 4 字节 INT 更大，索引更占空间。强烈建议所有 InnoDB 表都显式定义主键。

---

## 注意事项

- InnoDB 的聚簇索引与 MyISAM 的索引结构有本质区别：MyISAM 的索引（包括主键索引）叶子节点存储的是数据行的物理地址（文件偏移），数据与索引分离存储；InnoDB 的聚簇索引叶子节点直接存储完整行数据，数据与索引合一。
- 修改主键值（`UPDATE orders SET id = 9999 WHERE id = 1`）会触发聚簇索引的 B+树重组（物理位置变动），代价远高于修改普通列，应避免对主键列进行 UPDATE 操作。

---

## 总结

InnoDB 聚簇索引是一棵以主键为键值、叶子节点存储完整行数据的 B+树，表数据与主键索引合为一体，按主键顺序物理排列。确定规则：优先主键 → 第一个非 NULL 唯一索引 → 自动生成 DB_ROW_ID。主键查询无需回表（叶子节点直接返回所有列），范围查询和 ORDER BY 主键利用叶子节点链表顺序扫描。主键选择建议使用短整型自增值（减少二级索引空间，避免随机插入分裂）。每张 InnoDB 表只有一个聚簇索引，所有二级索引都引用聚簇索引键（主键值）。

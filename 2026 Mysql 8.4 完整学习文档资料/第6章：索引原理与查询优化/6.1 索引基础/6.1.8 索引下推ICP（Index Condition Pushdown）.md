# 索引下推 ICP（Index Condition Pushdown）

索引条件下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的查询优化机制，在 MySQL 8.0/8.4 中默认开启。其核心思想是：当 WHERE 子句中的过滤条件涉及索引中的列，但这些条件无法用于索引范围扫描的起点定位时（如联合索引的非最左列），ICP 允许 MySQL 存储引擎（InnoDB）在扫描索引时就对这些条件进行过滤，从而减少需要回表的记录数，降低回表次数。

---

## ICP 的触发场景

```sql
-- 示例：联合索引 idx_zipcode_lastname_firstname
CREATE TABLE people (
    id INT PRIMARY KEY,
    zipcode CHAR(6),
    lastname VARCHAR(50),
    firstname VARCHAR(50),
    address TEXT,
    INDEX idx_zip_last_first (zipcode, lastname, firstname)
);

-- 查询：WHERE zipcode 精确匹配 + lastname 模糊匹配 + address 过滤
SELECT * FROM people
WHERE zipcode = '530000'
  AND lastname LIKE '%中%'          -- 非精确，无法用于范围定位
  AND address LIKE '%建设路%';      -- address 不在索引中

-- idx_zip_last_first 可以用 zipcode='530000' 定位范围
-- 但 lastname LIKE '%中%' 是中间通配，无法继续缩窄索引范围
-- address 不在索引中，无论如何都要回表获取

-- 没有 ICP 时（MySQL 5.5 及更早）：
  步骤1：用 zipcode='530000' 定位索引范围，扫描所有 zipcode=530000 的叶子节点
  步骤2：对每条记录回表（取完整行）
  步骤3：在回表结果上检查 lastname LIKE '%中%' 和 address LIKE '%建设路%'
  → 所有 zipcode=530000 的行都要回表，再过滤

-- 有 ICP 时（MySQL 5.6+）：
  步骤1：用 zipcode='530000' 定位索引范围
  步骤2：在索引叶子节点上就检查 lastname LIKE '%中%'（因为 lastname 在索引中！）
  步骤3：只有通过 lastname 检查的记录才回表
  步骤4：在回表结果上检查 address LIKE '%建设路%'
  → 减少了回表次数！
```

---

## ICP 的工作原理

```
没有 ICP 的执行流程：
  Storage Engine → 根据索引条件找到行 → 将行（主键）返回 Server 层
  Server 层 → 回表获取完整行 → 在 Server 层检查 WHERE 条件

有 ICP 的执行流程：
  Storage Engine → 根据索引条件找到行
                → 在 Storage Engine 层使用索引中的列检查 WHERE 条件
                → 只有满足条件的行才传给 Server 层
  Server 层 → 回表获取通过 ICP 过滤后的行 → 检查剩余 WHERE 条件

ICP 的关键：过滤下推到 Storage Engine 层（InnoDB 内部），
           而不是在 Server 层执行，减少了向 Server 层传递的记录数，
           从而减少了回表次数。

ICP 只能使用：
  - 在索引中存在的列（不在索引中的列无法 ICP）
  - 只对 range、ref、eq_ref、ref_or_null 访问类型有效
  - 不适用于聚簇索引（聚簇索引叶子节点已有完整行，无需"下推"）
  - 不适用于覆盖索引（已经不回表了，ICP 无意义）
```

## ICP 的配置与验证

```sql
-- 查看 ICP 是否开启（默认 ON）
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- 其中：index_condition_pushdown=on

-- 临时关闭 ICP（测试对比用）
SET optimizer_switch = 'index_condition_pushdown=off';

-- 重新开启
SET optimizer_switch = 'index_condition_pushdown=on';

-- 通过 EXPLAIN 确认 ICP 是否生效
EXPLAIN SELECT * FROM people
WHERE zipcode = '530000'
  AND lastname LIKE '%中%' \G
-- Extra: Using index condition   ← 使用了 ICP（注意不是 Using index）
-- Using index condition 表示条件被"下推"到存储引擎层在索引中评估

-- 对比：
-- Using index         → 覆盖索引（完全不回表）
-- Using index condition → ICP（减少回表次数，但仍有回表）
-- (空)                → 普通索引访问，无 ICP
-- Using where         → Server 层过滤（在回表后过滤）
```

## ICP 生效的条件

```
ICP 生效的必要条件：
  1. 访问类型为 range、ref、eq_ref 或 ref_or_null
  2. WHERE 条件中有索引列参与的过滤（不能用于定位起点的那些条件）
  3. 索引是二级索引（主键的聚簇索引不需要 ICP）
  4. 不是覆盖索引（覆盖索引已经不回表，ICP 无额外意义）

ICP 不生效的情况：
  - 访问类型为 ALL（全表扫描）或 index（全索引扫描）
  - 查询只用到了聚簇索引
  - WHERE 条件列不在任何二级索引中
  - 已经是覆盖索引（不需要减少回表）

联合索引中 ICP 的典型场景：
  索引：(a, b, c)
  WHERE a = 1 AND b LIKE '%x%' AND c > 10
  → a=1 可用于定位索引范围起点
  → b LIKE '%x%' 无法用于缩窄范围，但 b 在索引中 → ICP 可检查 b
  → c > 10 可能也在 ICP 范围内（c 在索引中）
  → 只有通过 b 和 c 过滤的行才回表
```

## ICP 与相关优化的对比

| 优化机制 | 过滤位置 | 是否回表 | 适用条件 |
|---------|:-------:|:-------:|---------|
| 覆盖索引 | 索引层 | 不回表 | 查询列全在索引中 |
| ICP | 索引层（存储引擎）| 减少回表次数 | 索引中有 WHERE 条件列且无法用于范围定位 |
| MRR | 排序后回表 | 顺序回表 | 多行回表场景 |
| 普通索引查询 | Server 层 | 全量回表后过滤 | 无以上优化 |

---

## 适用场景

- **联合索引的非范围定位列过滤**：当 WHERE 子句包含联合索引的第一列用于范围定位，后续列有过滤条件但无法精确定位时（如 LIKE、范围比较），ICP 可以在索引层提前过滤，减少回表次数
- **大表中等选择性列的过滤**：对于数据量大、WHERE 中有多个条件（部分在索引中，部分不在）的查询，ICP 可以减少传递到 Server 层的行数，降低整体 I/O

## 常见问题

**EXPLAIN 显示 `Using index condition` 和 `Using where` 同时出现是什么意思？**

`Using index condition` 表示 ICP 生效，部分 WHERE 条件在存储引擎层用索引列评估。`Using where` 表示 Server 层还有额外的 WHERE 条件需要评估（即有些条件不在索引中，需要在回表后在 Server 层过滤）。两者同时出现是正常的，意味着：ICP 先在索引层过滤了可以利用索引列的条件（减少回表），回表后 Server 层再过滤剩余条件（如 `address LIKE '%建设路%'`）。

---

## 注意事项

- ICP 默认开启（`index_condition_pushdown=on`），通常不需要手动配置。如果在某些特定场景下怀疑 ICP 影响了性能（极少见），可以通过 `optimizer_switch` 临时关闭以做对比测试，而不是全局关闭。
- ICP 减少的是回表次数，但不能消除回表。如果查询需要不在索引中的列（如 `address`），回表是不可避免的。只有覆盖索引才能完全消除回表。在进行索引优化时，优先考虑覆盖索引，其次才是依赖 ICP。

---

## 总结

ICP（Index Condition Pushdown）索引条件下推将 WHERE 过滤条件中涉及索引列的判断下推到存储引擎（InnoDB）层，在扫描索引时就过滤不满足条件的记录，只有通过过滤的记录才进行回表，从而减少回表次数。EXPLAIN 中 `Extra: Using index condition` 表示 ICP 生效。ICP 默认开启，适用于二级索引+range/ref 访问类型+有额外索引列过滤条件的场景。ICP 优化的程度取决于索引中可下推的条件过滤掉的行比例——过滤比例越高，ICP 减少的回表越多，性能提升越显著。

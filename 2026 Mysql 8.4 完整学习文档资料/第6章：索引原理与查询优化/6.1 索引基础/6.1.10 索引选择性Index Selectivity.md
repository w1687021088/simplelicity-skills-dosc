# 索引选择性 Index Selectivity

索引选择性（Index Selectivity）是衡量某列（或多列组合）作为索引时过滤能力的指标，定义为：不重复值的数量（基数）除以表的总行数。选择性越高（越接近 1），索引过滤效果越好，查询时能排除越多不必要的行。选择性过低（大量重复值，接近 0）的列建立索引，MySQL 优化器往往会放弃使用，因为通过索引过滤后仍需回表大量数据，不如直接全表扫描。

---

## 选择性的计算公式

```sql
-- 索引选择性 = 不重复值数量 / 总行数
-- 取值范围：(0, 1]
-- 唯一索引：选择性 = 1（每行值都不同）
-- 例如性别列（M/F/未知）：选择性 ≈ 3 / 1000000 ≈ 0.000003

-- 手动计算某列的选择性
SELECT
    COUNT(DISTINCT age) / COUNT(*) AS age_selectivity,         -- age 列选择性
    COUNT(DISTINCT dept_id) / COUNT(*) AS dept_selectivity,    -- dept_id 列选择性
    COUNT(DISTINCT email) / COUNT(*) AS email_selectivity      -- email 列选择性
FROM users;

-- 示例输出：
-- age_selectivity   = 0.0050  （50 个不同年龄 / 10000 行）
-- dept_selectivity  = 0.0010  （10 个部门 / 10000 行）
-- email_selectivity = 1.0000  （每个 email 唯一）

-- 通过 SHOW INDEX 查看 Cardinality（基数估算值）
SHOW INDEX FROM users \G
-- Cardinality: 估算的不重复值数量（InnoDB 通过采样统计，非精确）
-- 选择性 ≈ Cardinality / TABLE_ROWS

-- 更新统计信息（使 Cardinality 更准确）
ANALYZE TABLE users;
```

## 选择性对优化器的影响

```sql
-- 场景：users 表 100 万行
-- 列 gender 的选择性 = 2/1000000 ≈ 0.000002（极低）
-- 列 user_id 的选择性 = 1000000/1000000 = 1（极高）

-- 低选择性列的索引（gender），优化器可能不使用：
EXPLAIN SELECT * FROM users WHERE gender = 'M' \G
-- 结果可能：type: ALL（全表扫描！）
-- 原因：gender='M' 约有 50 万行，回表 50 万次 >> 全表顺序扫描代价

-- 高选择性列的索引（email），优化器总是使用：
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com' \G
-- 结果：type: const 或 ref（走唯一索引）
-- 原因：email 唯一，只有 1 行需要回表

-- 中等选择性列（dept_id，10个部门）：
EXPLAIN SELECT * FROM users WHERE dept_id = 3 \G
-- 约 10 万行匹配，结果取决于优化器的成本评估
-- 有时走索引，有时全表扫描（取决于查询是否有其他条件、是否覆盖索引）
```

## 选择性阈值的经验参考

```
一般经验（并非绝对，优化器会综合多因素）：

高选择性（建索引有效）：
  选择性 > 0.1（10%以上的不重复比例）
  如：user_id、email、手机号、订单号
  → 索引过滤效果好，查询后剩余行数少

中等选择性（视具体查询而定）：
  选择性 0.01 ~ 0.1
  如：城市（100 个城市 / 100 万行 = 0.0001，偏低）
  → 单独建索引效果有限，考虑联合索引（结合高选择性列）

低选择性（单独建索引价值低）：
  选择性 < 0.01
  如：性别（M/F）、状态（pending/done/failed）、是否删除（0/1）
  → 通常不单独建索引
  → 可考虑与高选择性列组合成联合索引

唯一索引（选择性 = 1）：
  如：主键、邮箱、手机号（唯一约束）
  → 等值查询效率最高（const 或 eq_ref）
```

## 利用选择性设计联合索引

```sql
-- 低选择性列 + 高选择性列 = 有效的联合索引
-- 例：status（3种值，选择性 0.000003）+ user_id（唯一，选择性 1）

-- 联合索引选择性：
SELECT COUNT(DISTINCT status, user_id) / COUNT(*) AS combined_selectivity
FROM orders;
-- combined_selectivity ≈ 1.0（status + user_id 组合几乎唯一）
-- 联合索引有效！

-- 设计示例：
CREATE INDEX idx_status_userid ON orders (status, user_id);
-- 查询：WHERE status = 1 AND user_id = 100
-- 先用 status 过滤（粗过滤），再用 user_id 精确定位（精过滤）
-- 整体有效

-- 注意列顺序：
-- idx(status, user_id)：适合 WHERE status=1 AND user_id=100
-- idx(user_id, status)：适合 WHERE user_id=100 AND status=1（通常更好，user_id 高选择性在前）

-- 规则：高选择性列放在联合索引的更左边，索引效率更高
-- （但要兼顾最左前缀原则和具体查询模式）
```

## 前缀索引的选择性

```sql
-- 对于长字符串列（如 email、URL），可以只对前 N 个字符建索引
-- 前缀长度越长，选择性越高，但索引越大

-- 计算不同前缀长度的选择性：
SELECT
    COUNT(DISTINCT LEFT(email, 5)) / COUNT(*) AS sel_5,
    COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS sel_10,
    COUNT(DISTINCT LEFT(email, 20)) / COUNT(*) AS sel_20,
    COUNT(DISTINCT email) / COUNT(*) AS sel_full
FROM users;
-- 选择一个选择性接近全列选择性的最短前缀长度作为前缀索引长度

-- 示例输出：
-- sel_5  = 0.0312（前5字符选择性低）
-- sel_10 = 0.8965（前10字符已接近全列）
-- sel_20 = 0.9998（前20字符几乎全列选择性）
-- sel_full = 1.0000

-- 建前缀索引（前10字符）：
ALTER TABLE users ADD INDEX idx_email_prefix (email(10));
-- 选择性接近全列，但索引大小减少

-- 注意：前缀索引无法做覆盖索引（因为索引中只存前缀，无法完整返回 email 值）
```

## 适用场景

- **索引决策依据**：在评估是否需要为某列建立索引时，计算其选择性作为决策依据。选择性低于 0.01 的列通常不值得单独建索引，除非与高选择性列组合成联合索引
- **联合索引列顺序设计**：在不违背最左前缀使用模式的前提下，将选择性更高的列放在联合索引的左边，可以使索引在各种查询组合下都有更好的过滤效果

## 常见问题

**SHOW INDEX 的 Cardinality 值不准确怎么办？**

InnoDB 的 `Cardinality`（基数）是通过随机页面采样（默认 8 页）估算的，不是精确值。如果表数据变化较大（大量 INSERT/DELETE 后），统计信息可能过时，优化器可能因此做出错误的执行计划选择。解决方法：执行 `ANALYZE TABLE 表名` 强制重新收集统计信息（会短暂加 MDL 读锁）；或调整 `innodb_stats_sample_pages`（默认 8）为更大值以提高统计精度（如 20~50）。在 MySQL 8.0+ 中，还可以使用直方图（HISTOGRAM）提供更精确的列值分布信息（详见 6.5.3）。

---

## 注意事项

- 优化器对索引的选择不仅仅基于单列选择性，还会考虑查询条件的组合、表的总行数、Buffer Pool 命中率估算、索引覆盖情况等综合成本。某列的选择性低并不意味着一定不走索引（比如结合覆盖索引时，即使选择性低，不回表的索引扫描也可能优于全表扫描）。
- 在分析选择性时，要针对实际查询的过滤条件计算选择性，而不是单纯看列的全表选择性。例如 `WHERE status = 'active'` 中，如果 `status='active'` 只占表的 0.5%（而不是 50%），那么即使 status 整体选择性低，针对这个特定值的过滤效果也很好。

---

## 总结

索引选择性 = 不重复值数量 / 总行数，取值 (0, 1]，越接近 1 过滤效果越好。唯一索引选择性为 1，是最优情况。低选择性列（性别、状态等）单独建索引价值有限，优化器可能放弃使用，改走全表扫描。设计联合索引时：①高选择性列放在左边（过滤效果更强）；②低选择性列可以与高选择性列组合形成有效联合索引；③对长字符串建前缀索引时，选择选择性接近全列的最短前缀长度。通过 `COUNT(DISTINCT col) / COUNT(*)` 手动计算选择性；通过 `ANALYZE TABLE` 更新 InnoDB 的 Cardinality 统计信息。

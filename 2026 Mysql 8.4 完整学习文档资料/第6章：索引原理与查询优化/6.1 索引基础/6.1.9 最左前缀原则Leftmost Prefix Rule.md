# 最左前缀原则 Leftmost Prefix Rule

最左前缀原则（Leftmost Prefix Rule）是联合索引（多列索引）的核心使用规则：对于索引 `(a, b, c)`，只有查询条件从索引最左列开始连续使用时，索引才能被有效利用。如果跳过了某一列（如只用 `b` 和 `c` 而没有 `a`），后面的列无法走索引范围定位。这一规则源于联合索引的 B+树有序性：索引先按 `a` 排序，`a` 相同时按 `b` 排序，`b` 相同时按 `c` 排序——没有 `a` 的约束，`b` 的顺序是乱的，无法定位范围。

---

## 联合索引的有序性

```sql
-- 创建联合索引示例
CREATE TABLE employees (
    id INT PRIMARY KEY AUTO_INCREMENT,
    dept_id INT NOT NULL,
    age TINYINT NOT NULL,
    salary DECIMAL(10,2),
    name VARCHAR(50),
    INDEX idx_dept_age_salary (dept_id, age, salary)
);

-- idx_dept_age_salary 叶子节点数据排列示例：
-- [dept_id=1, age=25, salary=5000, id=101]
-- [dept_id=1, age=25, salary=8000, id=203]
-- [dept_id=1, age=30, salary=6000, id=105]
-- [dept_id=2, age=22, salary=4500, id=301]
-- [dept_id=2, age=28, salary=7000, id=402]
-- ...
-- 先按 dept_id 排序 → 再按 age → 再按 salary

-- 如果只看 age 列，它的顺序是：25、25、30、22、28...（乱序！）
-- 这就是为什么跳过 dept_id 直接用 age 无法走索引范围定位
```

## 最左前缀的使用规则

```sql
-- 索引：idx_dept_age_salary (dept_id, age, salary)

-- 完全使用最左前缀（最优）：
EXPLAIN SELECT * FROM employees WHERE dept_id = 1 AND age = 25 AND salary > 5000 \G
-- key: idx_dept_age_salary
-- type: range   → 3列全部使用

-- 使用前两列（dept_id + age）：
EXPLAIN SELECT * FROM employees WHERE dept_id = 1 AND age = 25 \G
-- key: idx_dept_age_salary
-- type: ref     → 使用 dept_id 和 age

-- 只使用第一列（dept_id）：
EXPLAIN SELECT * FROM employees WHERE dept_id = 1 \G
-- key: idx_dept_age_salary
-- type: ref     → 只使用 dept_id

-- 跳过第一列（只用 age）：
EXPLAIN SELECT * FROM employees WHERE age = 25 \G
-- key: NULL
-- type: ALL     → 无法使用索引！age 无法在 idx_dept_age_salary 中定位

-- 跳过中间列（dept_id + salary，跳过 age）：
EXPLAIN SELECT * FROM employees WHERE dept_id = 1 AND salary > 5000 \G
-- key: idx_dept_age_salary
-- type: ref     → 只能用 dept_id 部分，salary 无法用于范围（因为 age 被跳过）
-- key_len 只包含 dept_id 的长度（确认）
```

## 范围条件中断规则

```sql
-- 重要：遇到范围条件（>, <, BETWEEN, LIKE 'prefix%'）后，
-- 后续的列无法用于索引定位（但仍可能用于 ICP）

-- 范围条件在中间：
EXPLAIN SELECT * FROM employees
WHERE dept_id = 1 AND age > 25 AND salary = 6000 \G
-- dept_id 用于等值定位 ✓
-- age > 25 是范围条件 ✓
-- salary = 6000 在范围条件之后 → 无法用于索引定位（仍可 ICP）
-- key_len：只包含 dept_id + age 的长度（salary 无法用于索引范围）

-- 推论：联合索引中，等值条件列应尽量放在前面，范围条件列放在后面
-- idx(dept_id, salary, age) 比 idx(dept_id, age, salary) 更适合：
-- WHERE dept_id = 1 AND salary > 5000（dept_id 等值 + salary 范围）
-- 但不适合：WHERE dept_id = 1 AND age = 25（需要 age 等值，但 salary 在中间）
-- → 索引列顺序设计要考虑具体查询模式
```

## ORDER BY 的最左前缀

```sql
-- ORDER BY 也遵循最左前缀原则
-- 如果 ORDER BY 列不是索引的最左前缀，需要 filesort（文件排序）

-- 利用索引排序（无 filesort）：
EXPLAIN SELECT id, dept_id, age FROM employees
WHERE dept_id = 1 ORDER BY age \G
-- Extra: Using index condition  或  Using where
-- 无 Using filesort → 利用了 (dept_id, age) 的索引顺序

-- 无法利用索引排序（需要 filesort）：
EXPLAIN SELECT id, dept_id, age FROM employees ORDER BY age \G
-- Extra: Using filesort → 没有 dept_id 约束，age 顺序在索引中不连续

-- ORDER BY 多列时也要遵循最左前缀：
EXPLAIN SELECT * FROM employees
WHERE dept_id = 1 ORDER BY age, salary \G
-- Extra: 无 filesort → (dept_id=1 等值) + ORDER BY age, salary 遵循索引顺序

EXPLAIN SELECT * FROM employees
WHERE dept_id = 1 ORDER BY salary, age \G
-- Extra: Using filesort → ORDER BY 列顺序与索引不符（索引是 age, salary 顺序）
```

## MySQL 8.0+ 的跳跃扫描优化（Skip Scan）

```sql
-- MySQL 8.0 引入 Skip Scan（跳跃扫描）优化：
-- 即使没有最左列的等值条件，在某些情况下也能利用联合索引
-- 适用条件：第一列的不同值数量少（低基数）

-- 索引 idx_dept_age_salary (dept_id, age, salary)
-- dept_id 只有 5 个不同值（部门 1~5）

EXPLAIN SELECT * FROM employees WHERE age = 25 \G
-- 可能结果：type: range, Extra: Using index for skip-scan
-- MySQL 自动将此查询转换为：
-- WHERE dept_id = 1 AND age = 25
-- UNION
-- WHERE dept_id = 2 AND age = 25
-- ...
-- WHERE dept_id = 5 AND age = 25
-- 利用联合索引，避免全表扫描

-- 查看 skip scan 配置
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- skip_scan=on（默认）
```

## 最左前缀与索引设计建议

```
1. 将等值查询列放在联合索引的左边，范围查询列放在右边
   好：idx(dept_id, status, created_at)
   查询：WHERE dept_id=1 AND status=1 AND created_at > '2025-01-01'

2. 将高选择性（不重复值多）的列放在左边
   好：idx(user_id, status)  ← user_id 高选择性
   差：idx(status, user_id)  ← status 低选择性（只有几个值）

3. 将 ORDER BY 的列加入索引（按排序顺序）
   查询：WHERE dept_id=1 ORDER BY age
   索引：idx(dept_id, age) → 利用索引有序性，避免 filesort

4. 考虑查询的最左前缀覆盖度
   多个查询共用一个索引时，确保每个查询都能命中最左前缀
```

## 适用场景

- **联合索引设计**：根据最左前缀原则，将查询中最常作为等值条件的列放在联合索引的最左边，确保各个查询能充分利用索引的前缀部分，避免因为列顺序设计不当导致索引失效
- **索引覆盖分析**：通过 EXPLAIN 查看 `key_len` 值（索引实际使用的字节数），可以推算出联合索引中实际参与查询的列数，判断是否有列因违反最左前缀而被"截断"

## 常见问题

**WHERE 条件的书写顺序会影响最左前缀的使用吗？**

不影响。MySQL 查询优化器会自动调整 WHERE 条件的顺序，与索引列顺序匹配。例如 `WHERE age = 25 AND dept_id = 1` 和 `WHERE dept_id = 1 AND age = 25` 对优化器来说是等价的，都能正确使用 `idx(dept_id, age)` 索引。最左前缀原则约束的是索引列的物理顺序，与 SQL 中 WHERE 子句的书写顺序无关。

---

## 注意事项

- `EXPLAIN` 的 `key_len` 列是确认最左前缀使用情况的重要依据。通过计算每列的字节长度（如 `INT NOT NULL` = 4 字节，`INT NULL` = 5 字节，`VARCHAR(50) NOT NULL utf8mb4` = 50×4+2=202 字节），可以从 `key_len` 值推算出联合索引实际使用了几列。
- MySQL 8.0 的 Skip Scan 优化放宽了最左前缀的限制，但其适用条件较严格（第一列低基数），不能依赖它来弥补索引设计的不足。合理的联合索引列顺序设计仍然是最可靠的优化手段。

---

## 总结

最左前缀原则：联合索引 `(a, b, c)` 必须从最左列 `a` 开始连续使用，跳过中间列则跳过列及之后的列无法用于索引范围定位。原因：B+树按最左列优先排序，没有最左列约束时后续列顺序不连续。遇到范围条件（`>`、`<`、`BETWEEN`、`LIKE 'x%'`）后，后续列无法用于索引范围定位（但可能用 ICP）。ORDER BY 也遵循最左前缀，违反则触发 filesort。通过 `EXPLAIN` 的 `key_len` 判断实际使用的前缀长度。MySQL 8.0+ 的 Skip Scan 在第一列低基数时可突破最左前缀限制。

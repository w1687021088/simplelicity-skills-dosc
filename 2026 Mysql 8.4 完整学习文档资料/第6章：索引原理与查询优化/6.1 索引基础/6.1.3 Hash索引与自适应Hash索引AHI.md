# Hash 索引与自适应 Hash 索引 AHI

MySQL 中存在两种与哈希相关的索引机制：显式 Hash 索引（Memory 引擎支持，InnoDB 不支持作为持久化索引）和 InnoDB 的自适应哈希索引（Adaptive Hash Index，AHI）。AHI 是 InnoDB 在 Buffer Pool 中自动维护的纯内存哈希索引，对频繁等值查询的热点数据提供接近 O(1) 的访问速度，是 InnoDB 内部的查询加速机制，无需手动干预。

---

## 显式 Hash 索引（Memory 引擎）

```sql
-- Memory 引擎支持显式 Hash 索引
CREATE TABLE cache_data (
    id INT PRIMARY KEY,
    data VARCHAR(200),
    INDEX USING HASH (id)         -- 显式指定 Hash 索引
) ENGINE=MEMORY;

-- InnoDB 引擎不支持显式 Hash 索引（会自动转换为 B+树）
CREATE TABLE t (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    INDEX USING HASH (name)       -- InnoDB 中此选项被忽略，仍建 B+树索引
) ENGINE=InnoDB;

-- 查看索引类型
SHOW INDEX FROM cache_data \G
-- Index_type: HASH（Memory 引擎）

SHOW INDEX FROM t \G
-- Index_type: BTREE（InnoDB 忽略 USING HASH，建 B+树）
```

---

## Hash 索引的特点

```
Hash 索引工作原理：
  对索引列的值计算 hash(value) → 得到桶位置 → 直接定位记录
  等值查询：O(1) 时间复杂度

Hash 索引的局限性：
  1. 不支持范围查询（hash 后的值无序，无法比较大小）
  2. 不支持排序（ORDER BY 无法利用）
  3. 不支持前缀匹配（LIKE 'abc%'）
  4. 不支持联合索引的最左前缀（hash 整个组合值）
  5. 存在哈希冲突（不同值可能 hash 到同一桶，需要二次比较）
  6. Memory 引擎数据不持久化（服务器重启丢失）

适合场景：
  纯等值查找、数据全在内存中、不需要排序和范围查询
  如：会话数据缓存、临时计算结果
```

---

## 自适应哈希索引 AHI（核心）

```
AHI 的设计思想：
  InnoDB 监控 B+树索引的查询模式
  当某个索引的特定查询（如 WHERE id = N）被频繁重复执行时
  InnoDB 自动在 Buffer Pool 中为该查询路径建立哈希索引
  后续相同查询：直接通过 AHI 在内存中找到对应数据页
  跳过 B+树的逐层遍历（通常 2~3 次页面访问）
  → 将 B+树查询的 O(log N) 变为 O(1)

AHI 的关键特性：
  - 完全自动（InnoDB 自动建立/维护，无需手动配置）
  - 纯内存结构（Buffer Pool 中，不写入磁盘，重启消失）
  - 只覆盖热点数据（频繁被等值查询的 B+树页面）
  - 只支持等值查找（范围查询不走 AHI）
  - 建立条件：某查询模式被执行足够多次（内部阈值）
```

## AHI 的配置与监控

```sql
-- 查看 AHI 是否开启（默认 ON）
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';

-- 关闭 AHI（某些场景下 AHI 维护锁开销比收益大）
SET GLOBAL innodb_adaptive_hash_index = OFF;

-- AHI 分区数（MySQL 8.0+ 默认 8，减少 AHI 维护锁竞争）
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index_parts';
-- 默认：8（将 AHI 分为 8 个分区，减少并发写入时的锁冲突）

-- 通过 SHOW ENGINE INNODB STATUS 查看 AHI 使用情况
SHOW ENGINE INNODB STATUS \G
-- 在输出中找到 INSERT BUFFER AND ADAPTIVE HASH INDEX 部分：
-- Hash table size 1105031, node heap has 1 buffer(s)
-- Hash table size 1105031, node heap has 0 buffer(s)
-- ...（8个分区各自的大小）
-- 0.00 hash searches/s, 0.36 non-hash searches/s
-- hash searches/s：AHI 命中的查询每秒次数
-- non-hash searches/s：未命中 AHI（走 B+树）的查询每秒次数

-- 通过 information_schema.INNODB_METRICS 监控
SELECT NAME, COUNT, STATUS
FROM information_schema.INNODB_METRICS
WHERE NAME LIKE 'adaptive_hash%';
```

## AHI 与 B+树索引的关系

```
不是替代关系，是加速关系：

查询路径（有 AHI 时）：
  SQL → 检查 AHI → 命中 → 直接返回 Buffer Pool 中的页（1次内存访问）
      ↓未命中
      → 走 B+树（2~3 次 Buffer Pool 页访问 或 磁盘 I/O）
      → 如果该查询足够热点 → InnoDB 将此路径加入 AHI

AHI 的 hash key 包含：
  - 索引 ID
  - 查询条件的键值
  - 索引列值的组合
  
AHI 只对等值查询有效：
  WHERE id = 100          → 可走 AHI
  WHERE id BETWEEN 100 AND 200  → 不走 AHI，走 B+树范围扫描
  WHERE name = 'Alice'    → 可走 AHI（如果足够热点）
```

## AHI 的性能影响

```
AHI 带来性能提升的场景：
  - 高并发的等值点查询（如 WHERE primary_key = N）
  - 某几千条热点数据被反复频繁访问
  - OLTP 系统的热点用户/订单查询

AHI 可能带来负面效应的场景：
  - 写密集型负载（每次数据修改都需要同时维护 AHI，有额外开销）
  - 查询模式随机（AHI 难以累积"热点"，但 InnoDB 不断尝试建立，浪费内存和 CPU）
  - 高并发写入时 AHI 锁竞争（即使 8 个分区也可能成为瓶颈）

判断是否关闭 AHI：
  观察 SHOW ENGINE INNODB STATUS 中：
  hash searches/s << non-hash searches/s → AHI 命中率低
  同时 CPU 使用率高 → AHI 维护开销大于收益 → 考虑关闭
```

---

## 适用场景

- **等值查询的极致优化**：对于高并发 OLTP 系统中反复查询相同主键或唯一索引的场景，AHI 可以将等值查询从 2~3 次页面访问降为 1 次内存哈希查找，显著减少 CPU 指令数
- **判断关闭 AHI 的时机**：在以写入为主的负载（INSERT/UPDATE 密集），或查询模式极度随机的系统中，AHI 的维护开销可能超过其带来的收益，此时可以考虑关闭

---

## 常见问题

**AHI 会消耗多少内存？**

AHI 存储在 Buffer Pool 中（不是独立的内存区域），它使用 Buffer Pool 中的一部分空间。通过 `SHOW ENGINE INNODB STATUS` 可以看到 AHI 的 hash table size（哈希桶数量）和 node heap（存储哈希节点的内存页数量）。AHI 的内存占用取决于热点数据的数量，通常不会超过 Buffer Pool 的 5%~10%。如果担心 AHI 占用过多 Buffer Pool 空间，可以通过关闭 AHI 释放这部分内存用于缓存更多数据页。

---

## 注意事项

- AHI 是 InnoDB 内部实现细节，应用层无法直接控制"哪些查询走 AHI"，只能通过调整 `innodb_adaptive_hash_index` 和 `innodb_adaptive_hash_index_parts` 来开关和调整 AHI 分区数。
- MySQL 8.0 将 AHI 分为 `innodb_adaptive_hash_index_parts`（默认 8）个分区，大幅减少了高并发场景下 AHI 维护的锁竞争问题（MySQL 5.7 只有 1 个分区，高并发写入时 AHI 锁经常成为热点）。

---

## 总结

InnoDB 不支持持久化的 Hash 索引（显式 `USING HASH` 会被忽略，建 B+树），但内置了自适应哈希索引（AHI）——一个纯内存的自动维护哈希加速结构。AHI 监控 B+树查询热点，自动为频繁等值查询建立哈希路径，将 O(log N) 降为 O(1)。AHI 默认开启（`innodb_adaptive_hash_index=ON`），8 个分区减少锁竞争。通过 `SHOW ENGINE INNODB STATUS` 监控命中率，在写密集或随机查询为主的负载下可考虑关闭。Memory 引擎支持显式 Hash 索引，但数据不持久化，适合纯内存临时表场景。

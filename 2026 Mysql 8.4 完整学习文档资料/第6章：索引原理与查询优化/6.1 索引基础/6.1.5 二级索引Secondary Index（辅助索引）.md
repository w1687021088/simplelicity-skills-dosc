# 二级索引 Secondary Index（辅助索引）

在 InnoDB 中，除聚簇索引（主键索引）之外的所有索引都称为二级索引（Secondary Index），也叫辅助索引或非聚簇索引。二级索引的叶子节点不存储完整的行数据，而是存储索引列值与对应行的主键值。查询时先通过二级索引找到主键，再通过主键到聚簇索引获取完整行数据（这个过程称为回表）。理解二级索引的结构，是理解回表、覆盖索引、索引失效等现象的基础。

---

## 二级索引的物理结构

```
以 users 表为例（id 为主键，age 有二级索引）：

聚簇索引（主键 B+树）：
  叶子节点：[id=1, name='Alice', age=25, email='a@a.com']
             [id=2, name='Bob',   age=30, email='b@b.com']
             [id=3, name='Carol', age=25, email='c@c.com']

二级索引（age 的 B+树）：
  叶子节点：[age=25, id=1]
             [age=25, id=3]   ← 相同 age，按主键排序
             [age=30, id=2]

特点：
  1. 按 age 值排序
  2. 相同 age 时，按主键 id 排序
  3. 叶子节点只存 age + id，不存其他列
  4. 通过 id 再查聚簇索引获取其他列（回表）
```

## 创建和查看二级索引

```sql
-- 建表时创建二级索引
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    age TINYINT,
    dept_id INT,
    INDEX idx_age (age),                    -- 单列二级索引
    INDEX idx_dept_age (dept_id, age),      -- 联合二级索引
    UNIQUE INDEX idx_email (email)          -- 唯一二级索引
);

-- 建表后添加二级索引
ALTER TABLE users ADD INDEX idx_username (username);

-- 查看所有索引（含二级索引）
SHOW INDEX FROM users \G
-- Key_name: idx_age        → 索引名
-- Column_name: age          → 索引列
-- Index_type: BTREE         → B+树结构
-- Non_unique: 1             → 1=普通索引，0=唯一索引
-- Cardinality: 估算不重复值数量（索引选择性参考值）

-- 使用二级索引查询（EXPLAIN 确认）
EXPLAIN SELECT id, age FROM users WHERE age = 25 \G
-- key: idx_age              → 走二级索引
-- Extra: Using index        → 覆盖索引（不回表）

EXPLAIN SELECT * FROM users WHERE age = 25 \G
-- key: idx_age              → 走二级索引
-- Extra: (空)               → 需要回表获取 *（name, email 等）
```

## 二级索引的查找过程

```
查询：SELECT name FROM users WHERE age = 25

步骤1：查找二级索引 idx_age
  B+树根节点 → 内部节点 → 叶子节点
  找到 [age=25, id=1] 和 [age=25, id=3]

步骤2：回表（用主键到聚簇索引查找）
  取 id=1 → 查聚簇索引 → 得到完整行（name='Alice', ...）
  取 id=3 → 查聚簇索引 → 得到完整行（name='Carol', ...）

总 I/O：
  二级索引 B+树遍历（2~3 次页访问）
  + 每条记录的回表（各 2~3 次页访问）
  回表的代价随结果集行数线性增加
```

## 二级索引与联合索引

```sql
-- 联合索引（多列）的叶子节点存储所有索引列 + 主键
-- 索引 idx_dept_age 叶子节点：[dept_id=1, age=25, id=101]

-- 联合索引的有序性：
-- 先按 dept_id 排序，dept_id 相同时按 age 排序，age 相同时按 id 排序

-- 正确使用联合索引（利用最左前缀）：
SELECT * FROM users WHERE dept_id = 1 AND age = 25;  -- 走 idx_dept_age
SELECT * FROM users WHERE dept_id = 1;               -- 走 idx_dept_age（只用 dept_id 部分）

-- 无法使用联合索引（跳过了最左列）：
SELECT * FROM users WHERE age = 25;  -- 不走 idx_dept_age，走 idx_age 或全表扫描

-- 二级索引叶子节点中的 id 使得联合索引可以支持排序
SELECT * FROM users WHERE dept_id = 1 ORDER BY age;  -- 利用 idx_dept_age 的顺序
```

## 二级索引的维护代价

```
每次 INSERT/UPDATE/DELETE 都需要维护所有相关二级索引：

INSERT 一行：
  更新聚簇索引（1次 B+树插入）
  + 更新每个二级索引（N 次 B+树插入，N 为二级索引数量）

DELETE 一行：
  聚簇索引标记删除
  + 所有二级索引删除对应叶子节点

UPDATE（修改索引列）：
  相当于旧值的"删除" + 新值的"插入"（B+树删除+插入）
  修改非索引列：只更新聚簇索引，二级索引不受影响

二级索引越多 → INSERT/UPDATE/DELETE 越慢
一般建议：单表二级索引不超过 5~6 个
索引不是越多越好，每个索引都有维护成本
```

## 适用场景

- **查询优化的核心工具**：针对频繁作为 WHERE 条件、JOIN 条件、ORDER BY 依据的非主键列创建二级索引，是 MySQL 查询优化最直接、最有效的手段
- **索引数量控制**：在写密集型系统（INSERT/UPDATE 频繁）中，过多的二级索引会使写操作变慢，应根据实际查询需求创建必要的索引，而不是无目的地为所有列创建索引

## 常见问题

**为什么 InnoDB 的二级索引不直接存储行的物理地址（像 MyISAM 那样），而是存主键值？**

如果二级索引存物理地址，当行数据移动（如页分裂导致物理位置变化）时，需要更新所有指向该行的二级索引（代价极高）。InnoDB 存储主键值作为行指针，行的物理位置变化时只需更新聚簇索引，二级索引不受影响（因为主键值不变）。代价是查询时需要额外的一次回表（通过主键到聚簇索引），但换取了写入时的维护简单性。这是 InnoDB 设计上有意为之的权衡。

---

## 注意事项

- 二级索引的叶子节点中，相同索引键值的多条记录按主键值排序。这意味着对于唯一性很低（重复值多）的列（如性别只有 M/F），二级索引的叶子节点密度很低，扫描效率差，查询优化器可能放弃该二级索引转而选择全表扫描。
- `ALTER TABLE` 添加或删除索引在 MySQL 8.0+ 通常支持在线操作（Online DDL），但仍有短暂的元数据锁，对大表执行时需要选择低峰期，并建议使用 `gh-ost` 或 `pt-online-schema-change` 等工具降低影响。

---

## 总结

InnoDB 二级索引是以非主键列为键的 B+树，叶子节点存储索引列值与主键值（不存完整行数据）。查询时先通过二级索引找到主键，再通过主键到聚簇索引获取完整行（回表）。联合索引按多列组合排序，遵循最左前缀原则。每增加一个二级索引都会增加 INSERT/UPDATE/DELETE 的维护开销。实践中应根据实际查询模式建立必要索引，通过覆盖索引（索引列覆盖查询所需所有列）可以消除回表开销，是二级索引性能优化的重要手段。

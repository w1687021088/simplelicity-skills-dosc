# 联合索引与排序优化

联合索引不仅可以加速 WHERE 过滤，还可以消除 ORDER BY 排序的额外代价（避免 filesort）。当查询的 ORDER BY 列与索引列的顺序和方向一致时，MySQL 可以直接利用 B+树叶子节点的有序性返回已排好序的数据，无需在内存或磁盘上进行额外排序。EXPLAIN 的 `Extra` 列中出现 `Using filesort` 是排序优化未生效的标志，消除 filesort 是索引排序优化的目标。

---

## filesort 产生的原因与成本

```sql
-- filesort 并不一定真的写文件（如果 sort_buffer_size 足够，排序在内存中完成）
-- 但无论内存还是磁盘排序，都有额外的 CPU 和 I/O 代价

-- 查看 sort_buffer_size（每个连接分配的排序缓冲区）
SHOW VARIABLES LIKE 'sort_buffer_size';
-- 默认：256KB（不同版本可能不同）
-- 如果排序数据超过此大小 → 写临时文件（磁盘 I/O）

-- filesort 的两种排序模式：
-- 模式1（旧方式）：回表后排序
--   取出所有匹配行 → 按排序列排序 → 返回结果
-- 模式2（优化方式，MySQL 4.1+）：单次扫描排序
--   取出所有匹配行+排序列+输出列 → 排序 → 返回（无需回表）
--   需要 max_length_for_sort_data 配置的空间（默认 4096）

-- 通过 EXPLAIN 确认 filesort：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY amount \G
-- Extra: Using filesort  ← 需要额外排序代价
```

## 索引消除 filesort 的条件

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user_status_created (user_id, status, created_at)
);

-- 条件1：ORDER BY 列必须在索引中，且从索引的某个等值前缀开始
-- 等值过滤 + 索引顺序排序（最优）：
EXPLAIN SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 100 AND status = 1
ORDER BY created_at \G
-- Extra: Using index  ← 覆盖索引 + 无 filesort
-- 解析：user_id=100 等值，status=1 等值，created_at 在索引中有序

-- 条件2：ORDER BY 的列顺序必须与索引定义一致
EXPLAIN SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 100
ORDER BY status, created_at \G
-- Extra: Using index  ← status 和 created_at 顺序与索引一致，无 filesort

-- 条件3：所有 ORDER BY 列的排序方向必须与索引方向一致（或全部相反）
-- 索引：idx_user_status_created (user_id ASC, status ASC, created_at ASC)

-- 全升序（与索引方向一致）：
EXPLAIN SELECT id FROM orders WHERE user_id = 100 ORDER BY status ASC, created_at ASC \G
-- Extra: Using index  ← 无 filesort

-- 全降序（与索引全部相反 → Backward Index Scan）：
EXPLAIN SELECT id FROM orders WHERE user_id = 100 ORDER BY status DESC, created_at DESC \G
-- Extra: Backward index scan; Using index  ← 反向扫描，无 filesort

-- 混合方向（部分 ASC 部分 DESC）→ 需要 filesort：
EXPLAIN SELECT id FROM orders WHERE user_id = 100 ORDER BY status ASC, created_at DESC \G
-- Extra: Using index; Using filesort  ← 混合方向，需要 filesort
-- 解决：使用降序索引（参见 6.2.9）
```

## 失效场景：索引排序被破坏

```sql
-- 场景1：ORDER BY 列跳过了等值过滤之后的索引列
-- 索引：(user_id, status, created_at)
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY created_at \G
-- user_id=100 等值 ✓，但 status 被跳过！
-- created_at 在索引中的顺序不连续（不同 status 的 created_at 混合）
-- Extra: Using index condition; Using filesort  ← 有 filesort！

-- 修复：补充 status 条件，或建新索引 (user_id, created_at)
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at);
EXPLAIN SELECT id, user_id, created_at FROM orders WHERE user_id = 100 ORDER BY created_at \G
-- Extra: Using index  ← 无 filesort

-- 场景2：ORDER BY 列包含了非索引列
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY amount \G
-- amount 不在 idx_user_status_created 索引中
-- Extra: Using filesort

-- 场景3：WHERE 中有范围条件，范围条件之后的索引列不能用于排序
EXPLAIN SELECT id FROM orders WHERE user_id = 100 AND status > 0 ORDER BY created_at \G
-- status > 0 是范围条件，之后的 created_at 无法利用索引顺序
-- Extra: Using index condition; Using filesort  ← filesort！

-- 场景4：ORDER BY 混用索引列和非索引列
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY status, amount \G
-- status 在索引中，amount 不在 → 无法全用索引排序
-- Extra: Using filesort
```

## WHERE + ORDER BY 的联合索引设计原则

```
设计索引时，同时考虑 WHERE 和 ORDER BY 的需求：

原则1：WHERE 等值条件列放左边，ORDER BY 列放右边
  查询：WHERE user_id = 100 ORDER BY created_at
  索引：(user_id, created_at)  ← 正确
        (created_at, user_id)  ← 错误（created_at 在左无法利用排序）

原则2：WHERE 中的范围条件和 ORDER BY 不能共存于同一索引中（通常需要取舍）
  查询：WHERE user_id = 100 AND status > 0 ORDER BY created_at
  如果 status 有过滤需求：
    索引 (user_id, status, created_at) → status 等值时 created_at 可排序，
    但 status > 0 时 created_at 无法排序
  取舍方案：
    a. 如果排序更重要 → 索引 (user_id, created_at)，status 作为 WHERE 回表过滤
    b. 如果过滤更重要 → 索引 (user_id, status)，不排序（接受 filesort）

原则3：覆盖索引 + 排序（Extra: Using index，最优）
  将 SELECT 的输出列也加入索引，实现覆盖索引
  查询：SELECT id, user_id, status, created_at FROM orders
        WHERE user_id = 100 ORDER BY status, created_at
  索引：(user_id, status, created_at) 已覆盖 id（主键）、user_id、status、created_at
  → Extra: Using index（覆盖索引，无 filesort，最优）
```

## GROUP BY 与索引排序

```sql
-- GROUP BY 同样依赖有序性（对 GROUP BY 列进行排序才能分组）
-- 利用索引消除 GROUP BY 的排序：

CREATE TABLE sales (
    id INT PRIMARY KEY,
    region_id INT,
    category_id INT,
    amount DECIMAL(10,2),
    INDEX idx_region_cat (region_id, category_id)
);

-- 走索引的 GROUP BY：
EXPLAIN SELECT region_id, category_id, SUM(amount)
FROM sales
WHERE region_id = 5
GROUP BY region_id, category_id \G
-- Extra: Using index  ← 覆盖索引，利用索引有序性分组

-- 无法走索引的 GROUP BY（跳过前导列）：
EXPLAIN SELECT category_id, SUM(amount)
FROM sales
GROUP BY category_id \G  -- 跳过 region_id
-- Extra: Using temporary; Using filesort  ← 需要临时表+排序
```

## 适用场景

- **分页查询优化**：深分页场景（`ORDER BY id LIMIT 10000, 20`）利用主键聚簇索引的有序性，无需 filesort；对于非主键排序分页，设计联合索引 `(过滤列, 排序列)` 避免 filesort，提高分页效率
- **列表页排序**：内容管理、订单列表、数据报表等需要按时间、状态等列排序的场景，在 `WHERE 过滤列 + ORDER BY 排序列` 上建联合索引，是消除 filesort 的标准做法

## 常见问题

**EXPLAIN 中 `Using filesort` 一定是性能问题吗？**

不一定。对于小结果集（如 LIMIT 10 的查询，匹配的行只有几十条），filesort 在内存中完成（不写磁盘），速度很快，实际对性能的影响可以忽略不计。filesort 值得优化的情况：①结果集很大（几万行以上）且排序频繁；②`sort_buffer_size` 不足导致写临时磁盘文件（`Sort_merge_passes` 指标上升）；③这是高并发高频的核心查询。对于偶发的管理查询或小结果集，无需刻意优化 filesort。

---

## 注意事项

- 消除 filesort 的索引设计有时会与其他查询需求冲突（如某个索引对 WHERE 过滤最优，但对 ORDER BY 排序不适合）。需要根据查询的执行频率和对性能的实际影响做权衡，不必追求所有查询都无 filesort。
- MySQL 8.0+ 支持降序索引（参见 6.2.9），对于 ORDER BY 中列方向混合（部分 ASC、部分 DESC）的场景，通过在索引定义中精确指定各列的排序方向，可以消除原本需要 filesort 的混合排序查询。

---

## 总结

联合索引消除 filesort 的条件：①ORDER BY 的列在索引中；②ORDER BY 之前的索引列全部是等值条件（不能跳过或有范围条件）；③所有 ORDER BY 列方向一致（全 ASC 或全 DESC，全 DESC 用反向扫描）；④ORDER BY 列顺序与索引列顺序一致。设计原则：等值过滤列放左，ORDER BY 列放右；WHERE 范围条件与 ORDER BY 通常需要在"过滤效率"和"排序无 filesort"之间取舍。通过 EXPLAIN 的 `Extra: Using filesort` 识别需要排序优化的查询，通过 `Extra: Using index`（覆盖索引+无 filesort）确认优化成功。

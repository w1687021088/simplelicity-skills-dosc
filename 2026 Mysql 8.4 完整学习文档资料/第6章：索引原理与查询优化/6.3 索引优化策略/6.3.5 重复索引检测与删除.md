# 重复索引检测与删除

重复索引（Duplicate Index）是指在同一张表上，对完全相同的列或相同列的前缀建立了多个索引，使得多个索引的内容完全一样或高度重叠。重复索引不会提升查询性能（优化器只会使用其中一个），但会增加存储空间、降低写入性能（每次 INSERT/UPDATE/DELETE 都要维护所有重复索引），以及干扰优化器做出正确的索引选择。定期检测并删除重复索引是数据库维护的基本工作。

---

## 重复索引的典型场景

```sql
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,        -- 主键（聚簇索引）
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(11),
    age INT,
    dept_id INT
);

-- 场景1：主键上又建了单独的索引（最常见的重复）
ALTER TABLE users ADD INDEX idx_id (id);
-- PRIMARY KEY(id) 和 INDEX idx_id(id) 完全重复！
-- PRIMARY KEY 已经是聚簇索引，额外的 idx_id 完全没有意义

-- 场景2：UNIQUE INDEX 与普通 INDEX 重复
ALTER TABLE users ADD UNIQUE INDEX idx_email_unique (email);
ALTER TABLE users ADD INDEX idx_email (email);
-- idx_email_unique 和 idx_email 存储内容完全相同（UNIQUE 只是多了约束）
-- 删除 idx_email（保留 idx_email_unique，它既有约束又有查询加速）

-- 场景3：长索引包含了短索引（前缀重复）
ALTER TABLE users ADD INDEX idx_dept_age (dept_id, age);
ALTER TABLE users ADD INDEX idx_dept (dept_id);
-- idx_dept(dept_id) 是 idx_dept_age(dept_id, age) 的前缀
-- 对于 WHERE dept_id = N 的查询，两个索引都可以使用
-- idx_dept 是 idx_dept_age 的冗余（idx_dept 存储的内容是 idx_dept_age 的子集）
-- 但这属于"冗余索引"（6.3.6 详细讨论），不是严格意义的"完全重复"

-- 场景4：多次执行 ALTER TABLE ADD INDEX 导致重复
ALTER TABLE users ADD INDEX idx_phone (phone);   -- 第一次执行
ALTER TABLE users ADD INDEX idx_phone (phone);   -- 手误再次执行（MySQL 允许同名不同索引名）
-- 实际上 MySQL 不允许同名索引，第二次会报错
-- 但开发者可能用不同名字创建相同列的索引：
ALTER TABLE users ADD INDEX idx_phone_v2 (phone);
-- 与 idx_phone 完全重复，只是名字不同
```

## 使用 sys 库检测重复索引

```sql
-- MySQL 8.0+ sys 库提供了 schema_redundant_indexes 视图
-- 检测重复和冗余索引

SELECT *
FROM sys.schema_redundant_indexes
WHERE table_schema = 'mydb'
ORDER BY table_name \G

-- 输出字段说明：
-- table_schema：数据库名
-- table_name：表名
-- redundant_index_name：被认为冗余的索引名
-- redundant_index_columns：冗余索引的列
-- dominant_index_name：主导（保留）的索引名
-- dominant_index_columns：主导索引的列
-- subpart_exists：是否有前缀索引
-- sql_drop_index：建议的删除 SQL（直接复制执行）
```

## 使用 performance_schema 手动检测

```sql
-- 通过 information_schema.STATISTICS 手动分析
-- 找出同一表中列完全相同的索引（不含主键）

SELECT
    t1.TABLE_SCHEMA,
    t1.TABLE_NAME,
    t1.INDEX_NAME AS index1,
    t2.INDEX_NAME AS index2,
    GROUP_CONCAT(t1.COLUMN_NAME ORDER BY t1.SEQ_IN_INDEX) AS columns
FROM information_schema.STATISTICS t1
JOIN information_schema.STATISTICS t2
    ON t1.TABLE_SCHEMA = t2.TABLE_SCHEMA
    AND t1.TABLE_NAME = t2.TABLE_NAME
    AND t1.INDEX_NAME < t2.INDEX_NAME
    AND t1.SEQ_IN_INDEX = t2.SEQ_IN_INDEX
    AND t1.COLUMN_NAME = t2.COLUMN_NAME
WHERE t1.TABLE_SCHEMA = 'mydb'
    AND t1.INDEX_NAME != 'PRIMARY'
    AND t2.INDEX_NAME != 'PRIMARY'
GROUP BY t1.TABLE_SCHEMA, t1.TABLE_NAME, t1.INDEX_NAME, t2.INDEX_NAME
HAVING COUNT(*) = (
    SELECT MAX(SEQ_IN_INDEX) FROM information_schema.STATISTICS
    WHERE TABLE_SCHEMA = t1.TABLE_SCHEMA
    AND TABLE_NAME = t1.TABLE_NAME
    AND INDEX_NAME = t1.INDEX_NAME
);
```

## 安全删除重复索引的步骤

```sql
-- 步骤1：确认索引是真正重复的（不只是名字类似）
SHOW INDEX FROM users \G
-- 仔细对比 Column_name 和 Seq_in_index 确认完全重复

-- 步骤2：先将要删除的索引设为 INVISIBLE（安全验证）
ALTER TABLE users ALTER INDEX idx_email INVISIBLE;

-- 步骤3：观察 1~2 天（监控慢查询、执行计划变化）
-- 如果没有问题，执行删除
ALTER TABLE users DROP INDEX idx_email;

-- 步骤4：如果有问题，立即恢复
ALTER TABLE users ALTER INDEX idx_email VISIBLE;

-- 直接删除（确认无风险时）：
ALTER TABLE users DROP INDEX idx_id;      -- 删除主键上的重复索引
ALTER TABLE users DROP INDEX idx_email;   -- 删除被 UNIQUE 覆盖的普通索引

-- 删除后验证：
SHOW INDEX FROM users \G
-- 确认重复索引已删除
```

## 重复索引的性能影响量化

```sql
-- 重复索引对写入性能的影响（每个索引都需要维护）
-- 假设表有 1000 万行，有 3 个重复索引（包含 1 个正常 + 2 个重复）：

-- 插入 1 行：
-- 聚簇索引 1 次 B+树插入（必须）
-- 正常索引 1 次 B+树插入（必须）
-- 重复索引1 1 次 B+树插入（多余！）
-- 重复索引2 1 次 B+树插入（多余！）
-- 共 4 次 B+树操作，而实际只需要 2 次

-- 删除重复索引后：写入减少 50% 的索引维护开销

-- 磁盘空间：
-- 每个索引在 information_schema.INNODB_SYS_INDEXES 中有大小记录
SELECT INDEX_NAME, SUM(DATA_LENGTH) AS index_size
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mydb' AND TABLE_NAME = 'users';
-- 更精确的方式：
SELECT index_name, stat_value * @@innodb_page_size AS size_bytes
FROM mysql.innodb_index_stats
WHERE database_name = 'mydb' AND table_name = 'users'
  AND stat_name = 'size';
```

## 适用场景

- **数据库日常维护**：建议每季度运行一次 `sys.schema_redundant_indexes` 扫描，找出积累的重复/冗余索引并清理，是数据库定期维护的标准操作
- **数据库迁移和重构后**：在完成数据库 Schema 重构、合并代码分支后，多人协作可能在同一张表上独立添加了功能相似的索引，需要检查并去除重复

## 常见问题

**主键已经是索引了，为什么还会有人在主键列上再建一个索引？**

通常原因有两个：①历史遗留问题，在没有主键时先建了单列索引，后来添加主键时忘记删除旧索引；②自动化脚本或 ORM 工具在建表时，同时执行了 `PRIMARY KEY` 定义和单独的 `CREATE INDEX` 命令。MySQL 不会自动检测到"新建的索引与主键重复"并拒绝，因此这种重复完全可能在不知不觉中产生。通过 `SHOW INDEX` 发现 `Column_name` 与主键相同的非 PRIMARY 索引，就是主键列的重复索引。

---

## 注意事项

- 删除重复索引时，一定要确认"主导索引"（保留的那个）能否完全替代"冗余索引"（删除的那个）的所有功能。例如，如果 `idx_email` 是普通索引而 `idx_email_unique` 是唯一索引，删除普通索引保留唯一索引时，需要确认业务逻辑不依赖普通索引允许重复值的特性（通常不会，因为 UNIQUE 约束更严格）。
- `sys.schema_redundant_indexes` 的结果是基于索引定义的静态分析，它只判断列的重叠情况，不考虑查询实际使用模式。即使某个索引在静态分析中被标为"冗余"，如果它经常被某些特定查询使用（通过 `performance_schema` 确认），也不能轻易删除。

---

## 总结

重复索引是指同一张表上对完全相同的列建立了多个索引（或一个索引是另一个的完全前缀）。重复索引不提升性能，但增加写入维护开销和磁盘空间。检测工具：`sys.schema_redundant_indexes`（推荐，提供建议删除 SQL）；`information_schema.STATISTICS` 手动查询。安全删除流程：先设为 `INVISIBLE` → 观察一段时间 → 确认无影响 → 执行 `DROP INDEX`。常见场景：主键列上的额外索引、UNIQUE 和普通索引重复建设、多人协作独立建了相同内容的索引。

# 未使用索引识别

未使用索引（Unused Index）是指自服务器启动（或最后一次统计重置）以来，没有被任何查询读取使用的索引。未使用索引的危害与重复/冗余索引类似：每次 INSERT/UPDATE/DELETE 都需要维护这些索引（B+树节点的分裂/合并），消耗不必要的写入性能和磁盘空间，但却从未为任何查询提供加速。定期识别并删除未使用索引是数据库维护中容易被忽视却很有价值的优化工作。

## 通过 performance_schema 识别未使用索引

```sql
-- performance_schema.table_io_waits_summary_by_index_usage
-- 记录了自服务器上次启动（或统计重置）以来，每个索引被读取的次数

-- 查找从未被读取过的索引（COUNT_READ = 0）
SELECT
    OBJECT_SCHEMA   AS db,
    OBJECT_NAME     AS table_name,
    INDEX_NAME      AS index_name,
    COUNT_READ      AS read_count,       -- 索引扫描次数（0=从未使用）
    COUNT_WRITE     AS write_count       -- 索引维护次数（每次写入都有值）
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA NOT IN ('mysql', 'information_schema', 'performance_schema', 'sys')
  AND INDEX_NAME IS NOT NULL
  AND INDEX_NAME != 'PRIMARY'           -- 排除主键（主键必然被使用）
  AND COUNT_READ = 0                    -- 从未被读取
ORDER BY OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME;

-- 输出示例：
-- db: mydb
-- table_name: orders
-- index_name: idx_old_status           ← 从未被读取的索引
-- read_count: 0
-- write_count: 150000                  ← 但维护了 15 万次！

-- 查找低频使用的索引（可疑但不一定删除）
SELECT
    OBJECT_SCHEMA,
    OBJECT_NAME,
    INDEX_NAME,
    COUNT_READ,
    COUNT_WRITE,
    ROUND(COUNT_READ / (COUNT_READ + COUNT_WRITE) * 100, 2) AS read_ratio_pct
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA = 'mydb'
  AND INDEX_NAME IS NOT NULL
  AND INDEX_NAME != 'PRIMARY'
  AND COUNT_WRITE > 1000               -- 有维护开销
  AND COUNT_READ < 10                  -- 但极少被读
ORDER BY read_ratio_pct ASC;
```

## 通过 sys 库查询未使用索引

```sql
-- sys.schema_unused_indexes：专门列出未使用的索引（更简洁）
SELECT *
FROM sys.schema_unused_indexes
WHERE object_schema = 'mydb'
ORDER BY object_name;

-- 输出字段：
-- object_schema：数据库名
-- object_name：表名
-- index_name：未使用的索引名

-- 生成批量删除 SQL：
SELECT CONCAT('ALTER TABLE `', object_schema, '`.`', object_name,
              '` DROP INDEX `', index_name, '`;') AS drop_sql
FROM sys.schema_unused_indexes
WHERE object_schema = 'mydb'
ORDER BY object_name;

-- 执行前先仔细确认每一条（不要批量盲删！）
```

## 重置统计信息

```sql
-- performance_schema 的统计信息从服务器启动时开始累积
-- 如果服务器最近才重启，统计数据不足以代表真实使用情况

-- 查看服务器运行时间
SHOW GLOBAL STATUS LIKE 'Uptime';
-- Uptime: 604800（秒）= 7天
-- 只有 7 天的统计数据，对于按月/季度执行的定期查询，可能误判为"未使用"

-- 手动重置统计信息（之后重新开始统计）
TRUNCATE TABLE performance_schema.table_io_waits_summary_by_index_usage;

-- 建议：在服务器稳定运行至少 2~4 周后再做未使用索引分析
-- 确保所有业务场景（包括周期性任务）都执行过

-- 查看 performance_schema 是否启用（确保统计功能开启）
SHOW VARIABLES LIKE 'performance_schema';
-- performance_schema: ON（默认开启，MySQL 8.0+）
```

## 识别的局限性与注意事项

```sql
-- 局限1：统计信息在服务器重启后重置
-- 如果索引对应的查询每 3 个月才执行一次（季度报表），
-- 而服务器 2 个月前刚重启，则该索引会被误判为"未使用"

-- 局限2：主从复制中，从库的统计信息可能与主库不同
-- 某些查询只在从库执行（读写分离），主库的统计会显示该索引"未使用"
-- 需要同时检查主库和从库的统计信息

-- 局限3：performance_schema 的表 I/O 监控需要开启
SHOW VARIABLES LIKE 'performance_schema_instrument%';
-- 确保 wait/io/table/sql/handler 相关 instrument 已开启
SELECT ENABLED, TIMED FROM performance_schema.setup_instruments
WHERE NAME LIKE 'wait/io/table%';
-- ENABLED: YES（必须开启才能统计）

-- 局限4：查询缓存（Query Cache）命中时不走索引（MySQL 5.7，已在 8.0 删除）
-- MySQL 8.0+ 已删除查询缓存，此问题不存在

-- 最佳实践：
-- 1. 运行至少 4 周后进行分析
-- 2. 确认统计覆盖了所有业务场景（包括定时任务、月度/季度报表）
-- 3. 结合代码审查（搜索全部 SQL，确认哪些地方用了此索引）
-- 4. 通过 INVISIBLE 安全验证后再删除
```

## 未使用索引删除后的收益估算

```sql
-- 估算删除未使用索引能节省多少写入开销
-- 以 orders 表为例：

-- 表的写入量（每天的 INSERT/UPDATE/DELETE 次数）
SELECT
    SUM(COUNT_INSERT + COUNT_UPDATE + COUNT_DELETE) AS daily_writes
FROM performance_schema.table_io_waits_summary_by_table
WHERE OBJECT_SCHEMA = 'mydb'
  AND OBJECT_NAME = 'orders';

-- 有 3 个未使用索引，每次写入需要维护这 3 个索引
-- 每天写入 100 万次 × 3 个多余索引 = 300 万次多余的 B+树操作
-- 删除后：节省 300 万次/天的 B+树维护开销

-- 磁盘空间节省：
SELECT stat_value * @@innodb_page_size AS size_bytes, index_name
FROM mysql.innodb_index_stats
WHERE database_name = 'mydb'
  AND table_name = 'orders'
  AND stat_name = 'size'
  AND index_name IN ('idx_old_status', 'idx_old_created', 'idx_old_amount');
-- 相加得到这 3 个索引占用的总空间
```

## 适用场景

- **定期数据库维护**：建议每 3~6 个月运行一次未使用索引分析（在统计数据积累足够后），识别并删除自上次维护以来新增的未使用索引，保持数据库索引集合的精简
- **上线后的索引评估**：在新功能上线 1~2 个月后，分析新增索引的实际使用情况，确认索引设计是否符合实际查询模式，及时删除没有发挥作用的索引

## 常见问题

**performance_schema 统计的 `COUNT_READ = 0` 是否确保索引没有被使用？**

在以下前提下可以相信：①服务器运行时间足够长（覆盖了所有业务场景）；②performance_schema 的表 I/O 监控已开启（`setup_instruments` 中 table I/O 相关 instrument 为 ENABLED）；③没有直接连接到数据库执行 SQL 的工具绕过了 performance_schema 统计（通常不存在）。但仍需结合代码搜索做二次确认，特别是对于低频的定时任务、季度报表等场景，`COUNT_READ = 0` 不等于"绝对未使用"，只是"在统计窗口内未使用"。

---

## 注意事项

- `sys.schema_unused_indexes` 和 `performance_schema` 的统计数据只存储在内存中，服务器重启后自动清零。因此，识别未使用索引时，服务器的运行时间是判断可信度的重要参考指标。运行时间越长（覆盖的业务场景越完整），统计数据越有参考价值。
- 删除索引是 DDL 操作，对大表（千万行以上）会有一定的执行时间，但在 MySQL 5.6+ 以后，`DROP INDEX` 支持在线 DDL（`ALGORITHM=INPLACE`），不阻塞 DML 操作，对业务影响较小。在极端情况下仍需在低峰期执行。

## 总结

未使用索引通过 `performance_schema.table_io_waits_summary_by_index_usage`（`COUNT_READ = 0`）或 `sys.schema_unused_indexes` 视图识别。核心局限：统计数据随服务器重启清零，需要足够长的统计窗口（建议 4 周以上）；主从读写分离场景需同时检查主库和从库统计数据。识别流程：sys 视图自动识别 → 结合代码搜索双重确认 → INVISIBLE 安全验证 → DROP INDEX 删除。删除未使用索引的收益：降低每次写入的 B+树维护开销（每个索引各维护一次）；释放磁盘空间；减少 Buffer Pool 中索引页的占用。

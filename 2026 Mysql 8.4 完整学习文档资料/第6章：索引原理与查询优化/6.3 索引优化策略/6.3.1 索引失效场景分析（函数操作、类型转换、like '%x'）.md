# 索引失效场景分析（函数操作、类型转换、like '%x'）

索引失效是指 MySQL 查询优化器无法利用已有的索引来加速查询，退而使用全表扫描（`type: ALL`）或全索引扫描（`type: index`）的情况。索引失效的根本原因是：B+树依赖索引列的有序性进行范围定位，任何破坏这种有序性或改变索引列值的操作，都会使优化器无法在 B+树中精确定位目标范围。本文系统梳理常见的索引失效场景及对应的修复方法。

---

## 场景1：对索引列使用函数操作

```sql
-- 准备数据
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME NOT NULL,
    INDEX idx_created (created_at),
    INDEX idx_user (user_id)
);

-- 失效：对索引列使用函数，破坏 B+树的有序性
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2025 \G
-- type: ALL  ← 全表扫描！YEAR() 函数作用于索引列，无法利用索引定位范围

EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2025-01-15' \G
-- type: ALL  ← DATE() 函数，同样失效

EXPLAIN SELECT * FROM orders WHERE DATE_FORMAT(created_at, '%Y-%m') = '2025-01' \G
-- type: ALL  ← DATE_FORMAT() 函数，失效

-- 修复：将函数转移到常量侧，保持索引列不被操作
EXPLAIN SELECT * FROM orders WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01' \G
-- type: range  ← 使用范围查询，走索引！

EXPLAIN SELECT * FROM orders WHERE created_at >= '2025-01-15 00:00:00'
  AND created_at < '2025-01-16 00:00:00' \G
-- type: range  ← 等效 DATE(created_at) = '2025-01-15' 但走了索引

-- 另一种修复：使用函数索引（MySQL 8.0+）
ALTER TABLE orders ADD INDEX idx_year_created ((YEAR(created_at)));
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2025 \G
-- type: ref  ← 函数索引使 YEAR() 操作可以走索引
```

## 场景2：对索引列进行数学运算

```sql
-- 失效：对索引列进行算术运算
EXPLAIN SELECT * FROM orders WHERE user_id + 1 = 101 \G
-- type: ALL  ← user_id + 1 = 101 等价于 user_id = 100，但 MySQL 优化器
--               不会自动化简（5.7 及更早版本不化简，8.0+ 部分可以）
--               改写为 user_id = 100 可以走索引

EXPLAIN SELECT * FROM orders WHERE user_id * 2 = 200 \G
-- type: ALL  ← 乘法运算破坏索引

-- 修复：将运算移到值侧
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- type: ref  ← 正常走索引

-- 修复2：id 列运算失效的常见案例（主键也不例外）
EXPLAIN SELECT * FROM orders WHERE id + 0 = 1001 \G
-- type: ALL  ← id + 0 破坏聚簇索引定位！
EXPLAIN SELECT * FROM orders WHERE id = 1001 \G
-- type: const  ← 直接等值，最优
```

## 场景3：LIKE 以通配符开头

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(100),
    INDEX idx_username (username),
    INDEX idx_email (email)
);

-- 失效：LIKE 以 % 开头（无法确定 B+树中的起点位置）
EXPLAIN SELECT * FROM users WHERE username LIKE '%张三' \G
-- type: ALL  ← %张三，无法利用 B+树有序性

EXPLAIN SELECT * FROM users WHERE email LIKE '%@gmail.com' \G
-- type: ALL  ← 后缀匹配，索引失效

-- 有效：LIKE 以固定前缀开头（% 在末尾）
EXPLAIN SELECT * FROM users WHERE username LIKE '张%' \G
-- type: range  ← 前缀匹配，可以利用 B+树定位到 '张' 的起始位置

EXPLAIN SELECT * FROM users WHERE email LIKE 'alice%' \G
-- type: range  ← 前缀匹配，可以走索引

-- 修复后缀搜索：全文索引（如果是关键词搜索）
-- 或应用层处理（存储逆序字符串 + 前缀索引）
```

## 场景4：OR 条件（部分列无索引时）

```sql
-- 失效：OR 连接的条件中有列没有索引
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR amount = 99.99 \G
-- amount 没有索引
-- type: ALL  ← 因为 amount 无索引，整个 OR 条件只能全表扫描

-- 修复1：为 OR 的每个列都建索引（启用 Index Merge）
ALTER TABLE orders ADD INDEX idx_amount (amount);
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR amount = 99.99 \G
-- type: index_merge, Extra: Using union(idx_user, idx_amount)
-- MySQL 对两个索引分别扫描，取并集

-- 修复2：改用 UNION 替代 OR（通常比 Index Merge 更稳定）
SELECT * FROM orders WHERE user_id = 100
UNION
SELECT * FROM orders WHERE amount = 99.99;
```

## 场景5：索引列参与类型转换

```sql
-- 详见 6.3.2，这里只做概要
-- 失效：索引列类型与条件值类型不匹配时发生隐式转换

-- phone 列是 VARCHAR(11)，但查询值是数字
CREATE TABLE users2 (
    phone VARCHAR(11) NOT NULL,
    INDEX idx_phone (phone)
);
EXPLAIN SELECT * FROM users2 WHERE phone = 13812345678 \G
-- type: ALL  ← 字符串列与数字比较，发生隐式转换，索引失效

-- 修复：保持类型一致
EXPLAIN SELECT * FROM users2 WHERE phone = '13812345678' \G
-- type: ref  ← 字符串与字符串比较，索引有效
```

## 场景6：NOT IN、NOT EXISTS 和 != 的特殊情况

```sql
-- != 和 <> 在某些情况下无法走索引（取决于选择性）
EXPLAIN SELECT * FROM orders WHERE user_id != 100 \G
-- 可能结果：type: ALL（如果 user_id 数量少，不等于匹配大量行）
-- 或 type: range（如果优化器认为过滤后行数少，走索引）

-- NOT IN（可能走索引，取决于选择性）：
EXPLAIN SELECT * FROM orders WHERE user_id NOT IN (1, 2, 3) \G
-- 通常走索引（range 扫描非 1,2,3 的范围）

-- IS NULL 和 IS NOT NULL（可以走索引）：
ALTER TABLE orders ADD INDEX idx_nullable_col (amount);
EXPLAIN SELECT * FROM orders WHERE amount IS NULL \G
-- type: ref  ← IS NULL 可以走索引（B+树存储 NULL 值）

-- 注意：这些场景的实际行为依赖于统计信息和选择性
-- 优化器可能因行数估算选择全表扫描
```

## 场景7：联合索引违反最左前缀

```sql
-- 已在 6.1.9 详细讲解，这里简要复习
CREATE TABLE t (
    a INT, b INT, c INT,
    INDEX idx_abc (a, b, c)
);

-- 失效（跳过 a）：
EXPLAIN SELECT * FROM t WHERE b = 1 AND c = 2 \G
-- type: ALL  ← a 被跳过，无法走 idx_abc

-- 有效（从最左列开始）：
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3 \G
-- type: ref  ← 完整使用 idx_abc
```

## 场景8：MySQL 8.0+ 函数索引作为修复方案

```sql
-- 对于必须使用函数的查询，MySQL 8.0+ 支持函数索引（表达式索引）
CREATE TABLE orders2 (
    id BIGINT PRIMARY KEY,
    email VARCHAR(100),
    created_at DATETIME,
    INDEX idx_email_lower ((LOWER(email))),       -- 小写函数索引
    INDEX idx_year_created ((YEAR(created_at)))   -- YEAR 函数索引
);

-- 现在这些查询可以走索引：
EXPLAIN SELECT * FROM orders2 WHERE LOWER(email) = 'alice@example.com' \G
-- type: ref  ← 走函数索引

EXPLAIN SELECT * FROM orders2 WHERE YEAR(created_at) = 2025 \G
-- type: ref  ← 走函数索引
-- 注意：查询中的函数写法必须与索引定义完全一致
```

## 索引失效场景汇总

| 场景 | 示例 | 修复方法 |
|------|------|---------|
| 函数操作 | `WHERE YEAR(col) = 2025` | 改为范围查询或建函数索引 |
| 算术运算 | `WHERE col + 1 = 10` | 移运算到值侧：`col = 9` |
| LIKE 前通配 | `WHERE col LIKE '%abc'` | 改前缀匹配或全文索引 |
| OR 有列无索引 | `WHERE a=1 OR b=2`（b 无索引）| 为 b 建索引或改 UNION |
| 隐式类型转换 | `WHERE varchar_col = 123` | 保持类型一致 |
| 违反最左前缀 | `WHERE b=1`（联合索引跳 a）| 补充 a 条件或建单独索引 |

## 适用场景

- **慢查询优化排查**：通过慢查询日志找到慢 SQL，用 EXPLAIN 查看 `type: ALL` 的查询，逐条检查 WHERE 条件是否命中了上述失效场景，针对性修复
- **Code Review 时的索引失效检查**：在代码评审中，对 WHERE 子句使用函数（`DATE()`、`LOWER()`、`YEAR()` 等）的 SQL，标记为潜在的索引失效风险，要求开发者改写或建函数索引

## 常见问题

**EXPLAIN 显示 type: index 是走了索引还是全表扫描？**

`type: index` 是"全索引扫描"——扫描了整个二级索引的所有叶子节点（按索引顺序），并非精确的范围定位。虽然比 `type: ALL`（全表扫描）好一些（因为索引通常比表小），但仍然是低效的扫描方式。真正高效的索引使用是 `type: const`（唯一等值）、`ref`（等值多行）、`range`（范围）。遇到 `type: index` 时，检查查询是否有合适的 WHERE 条件可以添加索引，或者是否可以改写查询让优化器做更精确的范围定位。

---

## 注意事项

- 即使查询避免了上述所有失效场景，优化器仍可能选择不走索引。这通常是因为：统计信息不准确（运行 `ANALYZE TABLE` 更新）、索引选择性过低（匹配行数太多）、或优化器估算回表代价高于全表扫描。这种情况是优化器的正常行为，不一定是"失效"，可以通过 `FORCE INDEX` 强制验证。
- MySQL 8.0+ 的 `EXPLAIN ANALYZE` 可以显示实际执行的行数和时间，帮助区分"索引失效"和"优化器选择不走索引"两种情况。

## 总结

索引失效的核心原因：操作破坏了 B+树的有序性（函数/运算），使优化器无法在索引中做范围定位。主要失效场景：①函数操作索引列（`YEAR()`、`DATE()`）→ 改为范围查询或建函数索引；②算术运算索引列（`col+1=10`）→ 运算移到值侧；③LIKE 前缀通配（`'%abc'`）→ 改前缀匹配；④OR 有列无索引 → 为所有 OR 列建索引；⑤隐式类型转换（字符串列 vs 数字值）→ 保持类型一致；⑥违反最左前缀 → 补充最左列条件。通过 EXPLAIN 的 `type` 字段（ALL=全表，range=范围索引）快速识别失效。

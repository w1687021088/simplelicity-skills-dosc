# 冗余索引识别

冗余索引（Redundant Index）与重复索引（Duplicate Index）有所不同：重复索引是完全一样的索引；冗余索引是一个索引的功能可以被另一个索引完全覆盖，但两者并不完全一样。最典型的冗余关系：`INDEX idx_a (a)` 和 `INDEX idx_ab (a, b)` 同时存在时，`idx_a` 是冗余的——任何能用 `idx_a` 的查询，`idx_ab` 也能处理（利用最左前缀）。冗余索引同样带来写入开销和空间浪费，需要识别并删除。

---

## 冗余索引的典型模式

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    created_at DATETIME NOT NULL,
    amount DECIMAL(10,2)
);

-- 模式1：短索引被长索引的前缀覆盖（最常见）
ALTER TABLE orders ADD INDEX idx_user (user_id);            -- 单列
ALTER TABLE orders ADD INDEX idx_user_status (user_id, status);  -- 联合

-- idx_user(user_id) 是冗余的！
-- 原因：任何 WHERE user_id = N 的查询，idx_user_status 的最左前缀同样适用
-- idx_user 的存在只增加了写入维护开销，没有额外的查询加速

-- 保留 idx_user_status，删除 idx_user

-- 但注意例外：
-- 如果 idx_user_status 非常宽（如包含 10 个列），对于只用 user_id 的查询，
-- 优化器可能更倾向于使用轻量的 idx_user（索引更小，扫描更快）
-- 这种情况下需要评估实际查询性能再决定是否删除

-- 模式2：同一列的多个前缀索引长度不同
ALTER TABLE orders ADD INDEX idx_created_10 (created_at(10));  -- 前10字符（假设是字符串）
ALTER TABLE orders ADD INDEX idx_created_20 (created_at(20));  -- 前20字符
-- idx_created_10 通常是冗余的（idx_created_20 更精确，且相同列的前缀）

-- 模式3：主键索引被单列索引覆盖
-- PRIMARY KEY (id) 已存在
ALTER TABLE orders ADD INDEX idx_id (id);  -- 完全冗余！主键已经是聚簇索引
```

## 通过 sys 库检测冗余索引

```sql
-- sys.schema_redundant_indexes 同时检测重复和冗余索引
SELECT
    table_schema,
    table_name,
    redundant_index_name,
    redundant_index_columns,
    dominant_index_name,
    dominant_index_columns,
    sql_drop_index           -- 建议的删除语句
FROM sys.schema_redundant_indexes
WHERE table_schema = 'mydb'
ORDER BY table_name, redundant_index_name;

-- 典型输出：
-- table_name: orders
-- redundant_index_name: idx_user              ← 冗余索引
-- redundant_index_columns: user_id
-- dominant_index_name: idx_user_status        ← 主导索引（保留）
-- dominant_index_columns: user_id, status
-- sql_drop_index: ALTER TABLE `mydb`.`orders` DROP INDEX `idx_user`

-- 验证确认后执行：
ALTER TABLE orders DROP INDEX idx_user;
```

## 冗余索引的特殊情况

```sql
-- 情况1：短索引提供了覆盖索引能力，长索引不能完全替代
-- 查询：SELECT user_id FROM orders WHERE user_id = 100
-- 使用 idx_user(user_id)：覆盖索引，无回表（user_id 完全在索引中）
-- 使用 idx_user_status(user_id, status)：也是覆盖索引（user_id + status + id 都在）

-- 在此场景下 idx_user 确实是冗余的，idx_user_status 完全覆盖

-- 情况2：短索引比长索引小（IO 更少）
-- 索引 idx_user(user_id)：每条记录 = user_id(4字节) + id(8字节) = 12 字节
-- 索引 idx_user_status(user_id, status)：每条 = 4+1+8 = 13 字节（稍大）
-- 差异很小，但对于亿级表，idx_user 扫描的总 IO 会稍少

-- 结论：对于这类"几乎冗余"的索引，
-- 如果查询只用 user_id（不用 status），且查询量极大，
-- 保留 idx_user 可能有微小的性能优势
-- 否则删除，减少写入维护开销

-- 情况3：排序方向不同的索引不互为冗余（8.0+ 降序索引）
ALTER TABLE orders ADD INDEX idx_user_asc (user_id ASC);     -- 升序
ALTER TABLE orders ADD INDEX idx_user_desc (user_id DESC);   -- 降序
-- 这两个不互为冗余（排序方向不同，用于不同的 ORDER BY 场景）
```

## 冗余索引与联合索引的关系分析

```sql
-- 分析示例：以下索引哪些是冗余的？
-- A: idx_a (col_a)
-- B: idx_ab (col_a, col_b)
-- C: idx_abc (col_a, col_b, col_c)
-- D: idx_b (col_b)
-- E: idx_bc (col_b, col_c)

-- 分析：
-- A(col_a) 被 B(col_a, col_b) 覆盖 → A 冗余（B 的最左前缀包含 A）
-- B(col_a, col_b) 被 C(col_a, col_b, col_c) 覆盖 → B 也冗余（C 的前两列包含 B）
-- 结论：如果保留 C(col_a, col_b, col_c)，则 A 和 B 都可以删除
-- D(col_b) 和 E(col_b, col_c) 不被 C 覆盖（C 的最左是 col_a，D/E 最左是 col_b）
-- D(col_b) 被 E(col_b, col_c) 覆盖 → D 冗余

-- 最终保留：C(col_a, col_b, col_c) 和 E(col_b, col_c)
-- 删除：A, B, D

-- 注意：删除 A 和 B 之前，确认没有查询只需要 col_a 或 (col_a, col_b) 的覆盖索引，
-- 而 C 的额外 col_c 是否会造成不必要的索引扫描开销
```

## 安全删除冗余索引的流程

```sql
-- 步骤1：通过 sys.schema_redundant_indexes 找到候选冗余索引

-- 步骤2：检查 performance_schema 确认该索引的实际使用情况
SELECT INDEX_NAME, COUNT_READ, COUNT_WRITE
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA = 'mydb'
  AND OBJECT_NAME = 'orders'
  AND INDEX_NAME = 'idx_user';
-- COUNT_READ > 0：说明该索引被实际使用（谨慎删除）
-- COUNT_READ = 0：该索引从未被读取过

-- 步骤3：EXPLAIN 验证主导索引能否替代冗余索引
-- 把候选要删除的索引设为 INVISIBLE，运行业务查询，观察执行计划
ALTER TABLE orders ALTER INDEX idx_user INVISIBLE;
-- 如果相关查询仍能正常走 idx_user_status，则 idx_user 确实冗余

-- 步骤4：真正删除
ALTER TABLE orders DROP INDEX idx_user;

-- 步骤5：观察一段时间（慢查询日志、监控）
-- 无异常 → 完成
-- 有问题 → 无法回滚已删除的索引，需要重新创建（代价较高）
-- 因此步骤3的 INVISIBLE 验证非常重要！
```

## 适用场景

- **系统上线多年后的索引清理**：随着业务演进，早期建立的单列索引可能被后续添加的联合索引覆盖，成为冗余。定期（半年或一年）进行冗余索引扫描和清理是数据库维护的必要工作
- **数据库审计与优化**：在接手遗留系统时，对所有表的索引进行冗余分析，清理冗余索引，可以直接改善写入性能并释放磁盘空间

## 常见问题

**删除冗余索引后，主导索引的性能会和原来的单列索引一样吗？**

通常是的，在大多数查询场景下性能相当甚至相同。例如 `WHERE user_id = N` 用 `idx_user_status(user_id, status)` 和用 `idx_user(user_id)` 的查询性能几乎一样（都是等值定位到 user_id 的 B+树范围）。细微差别：联合索引的叶子节点每条记录比单列索引多存储了 status 列（多几个字节），使得联合索引稍大，相同数量的行占用更多 B+树页面。但这个差异对实际查询性能的影响通常可以忽略不计（不超过几个百分点）。

---

## 注意事项

- 删除冗余索引是不可快速撤销的操作（与设为 INVISIBLE 不同，DROP INDEX 后必须重新 CREATE INDEX 才能恢复）。对于大表（千万行以上），重新创建索引可能需要数分钟到数十分钟，期间对写入性能有影响。因此删除前一定要通过 INVISIBLE 做充分验证。
- 在主从复制环境中，DROP INDEX 操作会通过 Binlog 同步到从库，从库也会执行相同的 DDL。如果主从库之间有版本差异，需要确认 DROP INDEX 语法在所有库版本中都兼容。

---

## 总结

冗余索引是指一个索引的功能被另一个更宽的联合索引完全覆盖（如 `idx_a` 被 `idx_ab` 覆盖）。与重复索引不同，冗余索引的列集合是另一个索引的真子集。通过 `sys.schema_redundant_indexes` 自动识别冗余索引（提供建议删除 SQL）。识别后需结合 `performance_schema` 确认实际使用情况，通过 `INVISIBLE` 验证主导索引可以替代后再执行 `DROP INDEX`。冗余索引的危害：增加写入维护开销（与重复索引相同）；浪费磁盘空间；可能干扰优化器做正确的索引选择。

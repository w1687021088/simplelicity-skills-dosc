# OR 条件索引合并 Index Merge

Index Merge（索引合并）是 MySQL 优化器在单表查询中使用多个索引，将各自的结果集进行合并（Union/Intersection）的执行方式。在 WHERE 子句中有 OR 或 AND 连接的多个条件，且每个条件都有对应的索引时，优化器可能选择 Index Merge 代替单一索引扫描或全表扫描。EXPLAIN 输出中 `type: index_merge` 和 `Extra` 中的 `Using union` / `Using intersect` / `Using sort_union` 表示使用了 Index Merge。

---

## Index Merge 的三种类型

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id),
    INDEX idx_status (status),
    INDEX idx_amount (amount)
);

-- 类型1：Union（OR 条件，取并集）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 1 \G
-- type: index_merge
-- key: idx_user, idx_status
-- Extra: Using union(idx_user, idx_status); Using where
-- 执行过程：
--   用 idx_user 扫描 user_id=100 的所有主键
--   用 idx_status 扫描 status=1 的所有主键
--   对两组主键取并集（去重）
--   按并集主键回表获取完整行

-- 类型2：Intersect（AND 条件，取交集）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- 如果没有联合索引，优化器可能使用 Index Merge Intersect
-- type: index_merge
-- key: idx_user, idx_status
-- Extra: Using intersect(idx_user, idx_status); Using where
-- 执行过程：
--   用 idx_user 扫描 user_id=100 的主键集合
--   用 idx_status 扫描 status=1 的主键集合
--   取交集，只回表交集中的行

-- 类型3：Sort Union（OR 条件，需要先排序再合并）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR amount > 500 \G
-- type: index_merge
-- Extra: Using sort_union(idx_user, idx_amount); Using where
-- 当 OR 的一侧是范围查询（非等值）时，使用 Sort Union
-- 需要先对范围扫描结果的主键排序，再合并（避免重复回表）
```

## Index Merge 的性能分析

```sql
-- Index Merge 不一定比全表扫描快，需要综合评估

-- Index Merge Union 的代价：
-- 1. 两次索引扫描（分别扫描两个索引）
-- 2. 主键集合的合并/去重操作（内存排序）
-- 3. 最终按合并结果逐条回表

-- 当以下情况时，Index Merge 比全表扫描更差：
-- 两个条件合并后匹配的行数仍然很多（如 user_id=100 OR status=1 匹配 60% 的行）
-- 两个索引各自扫描的主键集合都很大（内存排序开销高）

-- 通过 EXPLAIN 对比方案：
-- Index Merge Union（两个索引合并）：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 1 \G
-- type: index_merge, rows: 估算行数

-- 强制全表扫描（关闭 Index Merge）：
SET SESSION optimizer_switch = 'index_merge_union=off';
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 1 \G
-- type: ALL, rows: 全表行数

-- 比较两者的 rows × 代价，判断 Index Merge 是否真的更好
```

## Index Merge 与联合索引的选择

```sql
-- 结论：对于 AND 条件，联合索引通常优于 Index Merge Intersect

-- 场景：WHERE user_id = 100 AND status = 1

-- 方案1：两个单列索引 + Index Merge Intersect
-- 两次索引扫描 + 主键取交集 + 回表
-- EXPLAIN: type: index_merge, Extra: Using intersect(idx_user, idx_status)

-- 方案2：联合索引 idx_user_status(user_id, status)
ALTER TABLE orders ADD INDEX idx_user_status (user_id, status);
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- type: ref  ← 直接在 B+树中用组合键定位，一次索引扫描
-- Extra: 无 Using intersect（比 Index Merge 更高效）

-- 联合索引的优势：
-- 一次 B+树遍历 vs 两次索引扫描 + 合并
-- 可以实现覆盖索引（如果查询列在联合索引中）
-- Index Merge Intersect 无法实现覆盖索引

-- 结论：优先建联合索引，不要依赖 Index Merge Intersect 优化 AND 条件
```

## OR 条件的 UNION 改写

```sql
-- 在某些情况下，将 OR 查询改写为 UNION 比 Index Merge Union 更高效

-- 原始 OR 查询（Index Merge Union）：
SELECT * FROM orders WHERE user_id = 100 OR status = 1;

-- 改写为 UNION（更可预期的执行计划）：
SELECT * FROM orders WHERE user_id = 100
UNION
SELECT * FROM orders WHERE status = 1;
-- 每个子查询各自走索引，UNION 去重后返回结果

-- UNION ALL（不去重，如果确保不重叠）：
SELECT * FROM orders WHERE user_id = 100
UNION ALL
SELECT * FROM orders WHERE status = 1 AND user_id != 100;
-- 手动去重逻辑，避免 UNION 的排序去重开销

-- UNION 改写的优势：
-- 每个子查询独立优化，执行计划更可控
-- 避免 Index Merge 的内存合并排序
-- 可以为每个子查询分别使用覆盖索引
```

## Index Merge 的开关控制

```sql
-- 查看 Index Merge 相关开关
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- 相关开关（均默认 on）：
-- index_merge=on               → 总开关，关闭则禁用所有 Index Merge
-- index_merge_union=on         → Union 合并（OR 条件）
-- index_merge_sort_union=on    → Sort Union 合并（OR + 范围）
-- index_merge_intersection=on  → Intersect 合并（AND 条件）

-- 关闭特定类型的 Index Merge（Session 级别）：
SET SESSION optimizer_switch = 'index_merge_intersection=off';
-- 禁止 AND 条件的 Index Merge，强制选择单一索引或全表扫描

-- 全部关闭 Index Merge：
SET SESSION optimizer_switch = 'index_merge=off';

-- 恢复：
SET SESSION optimizer_switch = 'index_merge=on,index_merge_union=on,
index_merge_sort_union=on,index_merge_intersection=on';

-- 使用 Optimizer Hint 控制（单个查询级别）：
SELECT /*+ NO_INDEX_MERGE(orders idx_user, idx_status) */ *
FROM orders WHERE user_id = 100 OR status = 1;
```

## 适用场景

- **OR 条件多个列都有索引，且各自选择性高**：当 OR 两侧的条件各自能过滤大量数据（选择性高），且两者结果集重叠不多时，Index Merge Union 是合理的方案，比全表扫描快
- **排查慢查询中的 Index Merge**：EXPLAIN 发现 `type: index_merge` 时，要验证 Index Merge 是否真的比全表扫描快（通过比较 rows 估算值），必要时通过建立联合索引或改写为 UNION 来优化

---

## 常见问题

**EXPLAIN 显示 Index Merge 是否一定比全表扫描好？**

不一定。Index Merge 比全表扫描好的前提是：参与合并的每个索引各自能过滤大量数据（选择性高），且合并后的结果集总行数不多。如果 `user_id = 100` 匹配 50 万行，`status = 1` 也匹配 50 万行，Union 后总计 80 万行，回表 80 万次的代价可能远超全表顺序扫描 100 万行的代价。判断标准：查看 EXPLAIN 的 `rows` 估算，如果 Index Merge 的 rows 接近全表行数，性能可能不如预期，建议通过 EXPLAIN ANALYZE 验证实际执行时间。

---

## 注意事项

- Index Merge 的主键合并（排序去重）操作在内存中进行（使用 `sort_buffer_size` 配置的内存），如果合并的主键数量非常大，可能导致内存排序溢出到磁盘，使 Index Merge 实际性能更差。
- 对于 AND 条件，如果已经有覆盖相关列的联合索引，优化器通常会优先使用联合索引而不是 Index Merge Intersect。如果 EXPLAIN 显示使用了 Index Merge Intersect 而不是联合索引，可能是联合索引的统计信息不准确，运行 `ANALYZE TABLE` 更新后再检查。

---

## 总结

Index Merge 允许单查询使用多个索引，分三种类型：Union（OR 条件取并集）、Intersect（AND 条件取交集）、Sort Union（OR+范围取有序并集）。EXPLAIN 中 `type: index_merge` 标识，`Extra` 显示具体合并类型。性能评估：Index Merge 不一定优于全表扫描，需要对比 rows 估算值；AND 条件的 Intersect 通常不如联合索引（联合索引一次 B+树遍历 vs 两次索引扫描+合并）。优化建议：AND 条件优先建联合索引；OR 条件两个选择性高的索引可以使用 Index Merge Union，也可以改写为 UNION 获取更可控的执行计划。通过 `optimizer_switch` 可以精细控制 Index Merge 的开关。

# 单列索引 Single-Column Index

单列索引（Single-Column Index）是建立在表的某一个列上的 B+树索引，是 MySQL 中最基本的索引形式。单列索引包括普通索引（INDEX）、唯一索引（UNIQUE INDEX）和主键索引（PRIMARY KEY）。它是处理单列等值查找、范围查找和排序的有效工具，但无法同时利用多列的组合过滤能力。理解单列索引的创建、使用和局限，是索引优化的入门基础。

---

## 创建和管理单列索引

```sql
-- 建表时创建单列索引
CREATE TABLE products (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    category_id INT,
    price DECIMAL(10,2),
    stock INT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_category (category_id),          -- 普通单列索引
    UNIQUE INDEX idx_name (name),              -- 唯一单列索引
    INDEX idx_price (price),                   -- 价格索引
    INDEX idx_created (created_at)             -- 时间索引
);

-- 建表后添加单列索引
ALTER TABLE products ADD INDEX idx_stock (stock);

-- 创建时指定索引算法（默认 BTREE）
ALTER TABLE products ADD INDEX idx_category2 (category_id) USING BTREE;

-- 删除单列索引
ALTER TABLE products DROP INDEX idx_stock;
-- 或
DROP INDEX idx_price ON products;

-- 查看所有索引
SHOW INDEX FROM products \G
```

## 单列索引的查询使用

```sql
-- 等值查询（最优，使用 ref 或 const 类型）
EXPLAIN SELECT * FROM products WHERE category_id = 5 \G
-- type: ref, key: idx_category

-- 范围查询（使用 range 类型）
EXPLAIN SELECT * FROM products WHERE price BETWEEN 100 AND 500 \G
-- type: range, key: idx_price

-- 前缀匹配（LIKE 'xxx%' 可以使用索引）
EXPLAIN SELECT * FROM products WHERE name LIKE '手机%' \G
-- type: range, key: idx_name（唯一索引）

-- 后缀和中间通配符无法使用索引
EXPLAIN SELECT * FROM products WHERE name LIKE '%手机' \G
-- type: ALL（全表扫描，% 在前面无法利用 B+树有序性）

-- 排序（ORDER BY 索引列可以避免 filesort）
EXPLAIN SELECT id, price FROM products ORDER BY price LIMIT 10 \G
-- type: index, Extra: Using index（走 idx_price 扫描，如果是覆盖索引）

-- 范围+排序（只有前面的范围条件走索引，ORDER BY 可能 filesort）
EXPLAIN SELECT * FROM products WHERE price > 100 ORDER BY created_at \G
-- price 走 idx_price，但 ORDER BY created_at 需要 filesort（两个不同的索引）
```

## 单列索引的局限性

```sql
-- 多列过滤时，单列索引只能使用其中一个
EXPLAIN SELECT * FROM products WHERE category_id = 5 AND price < 200 \G
-- MySQL 选择其中一个索引（通常选择 Cardinality 更高的）
-- 另一个条件作为 Server 层过滤

-- 如果两个单列索引都有价值，MySQL 8.0 可能使用 Index Merge
-- （将两个索引的结果取交集，详见 6.3.3）

-- 与联合索引的对比：
-- 两个单列索引：idx_category + idx_price
-- 一个联合索引：idx_category_price (category_id, price)
-- 联合索引对 WHERE category_id=5 AND price<200 更高效
-- 联合索引直接在 B+树中同时利用两列过滤，无需 Index Merge

-- 单列索引无法支持多列组合的覆盖索引
EXPLAIN SELECT category_id, price FROM products WHERE category_id = 5 AND price < 200 \G
-- 如果只有单列索引：无法同时覆盖 category_id + price
-- 如果有联合索引 idx_category_price(category_id, price)：
-- Extra: Using where; Using index（覆盖索引）
```

## 单列索引的适用判断

```
单列索引适合的场景：
  1. 只需要过滤单个列（WHERE 条件只有一列）
  2. 该列经常单独出现在查询条件中
  3. 列的选择性较高（不重复值多）
  4. 列用于 ORDER BY 或 GROUP BY（且 SELECT 的列在索引中）

不适合单独建单列索引的场景：
  1. 列的选择性极低（如性别、状态标志）
  2. 多列总是一起出现在查询条件中（应建联合索引）
  3. 列几乎不用于查询过滤（只用于 SELECT 输出）

判断方法：
  分析高频 SQL 中 WHERE、ORDER BY、JOIN ON 的列
  → 只有单列条件：建单列索引
  → 多列同时出现：建联合索引（通常比多个单列索引更优）
```

## 适用场景

- **外键列索引**：外键列（如 `user_id`、`order_id`、`category_id`）通常需要单列索引支持外键约束检查和关联查询，是单列索引最常见的应用场景
- **唯一性约束**：对需要全局唯一的列（如邮箱、手机号、订单号）建立唯一单列索引，同时满足约束检查和查询加速两个需求

---

## 常见问题

**同一张表建多个单列索引和建一个联合索引哪个更好？**

通常建一个联合索引优于多个单列索引。联合索引可以在 B+树中同时利用多列的过滤能力（一次索引扫描就能完成多列过滤），而多个单列索引只能选一个使用（或通过 Index Merge 组合，但 Index Merge 有额外的排序和合并开销）。此外，联合索引更容易实现覆盖索引（多列都在同一索引中）。多个单列索引的优势是灵活——每个索引都可以单独被不同查询使用；但如果查询模式固定，联合索引几乎总是更优选择。

---

## 注意事项

- 建立索引后，执行 `ANALYZE TABLE` 更新统计信息，帮助优化器做出更准确的执行计划选择。新建的索引在数据量较大时，优化器需要准确的 Cardinality 统计才能决定是否使用该索引。
- 对同一列不要建重复的索引（如既有 `INDEX idx_a(a)` 又有 `UNIQUE INDEX idx_a_unique(a)`）。这两个索引的数据结构几乎相同，浪费存储空间和维护开销。应只保留更严格的约束（UNIQUE）。

---

## 总结

单列索引是建立在单个列上的 B+树索引，包括普通索引（INDEX）、唯一索引（UNIQUE INDEX）和主键索引（PRIMARY KEY）。适合单列等值、范围查询和排序优化；对多列组合过滤的支持有限（需要 Index Merge 或优化器选择）。高频查询中多列同时出现时应优先考虑联合索引。适合的单列索引场景：外键列、唯一性约束列、高选择性列单独出现在查询条件中的列。通过 `EXPLAIN` 的 `type`（ref/range）和 `Extra`（Using index）确认单列索引是否被有效使用。

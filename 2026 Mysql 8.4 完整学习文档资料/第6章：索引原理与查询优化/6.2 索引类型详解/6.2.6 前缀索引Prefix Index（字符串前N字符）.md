# 前缀索引 Prefix Index（字符串前 N 字符）

前缀索引（Prefix Index）是只对字符串列的前 N 个字符建立索引，而不是对整个字符串建立索引。对于长字符串列（如 URL、长文本、邮箱等），全列索引占用空间大、B+树高度增加，而实际上前面几十个字符往往已经能提供足够的区分度。前缀索引以适当降低选择性为代价，换取索引大小的明显缩减和写入性能的提升。但前缀索引有一个重要限制：不能用于覆盖索引。

---

## 前缀索引的创建语法

```sql
-- 基本语法：列名(N) 表示取前 N 个字符
CREATE TABLE articles (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(500) NOT NULL,
    url VARCHAR(2000) NOT NULL,
    content TEXT,
    author_email VARCHAR(200),
    INDEX idx_title_prefix (title(50)),          -- title 的前 50 字符
    INDEX idx_url_prefix (url(100)),             -- url 的前 100 字符
    INDEX idx_email_prefix (author_email(20))    -- email 的前 20 字符
);

-- 建表后添加前缀索引
ALTER TABLE articles ADD INDEX idx_title (title(50));

-- 对 TEXT/BLOB 类型（必须使用前缀索引，不能全列索引）
CREATE TABLE docs (
    id INT PRIMARY KEY AUTO_INCREMENT,
    body TEXT,
    INDEX idx_body (body(200))    -- TEXT 列必须指定前缀长度
);

-- 对 CHAR/VARCHAR 列的前缀索引是可选优化（不是必须）
-- 在字段较短（50字符以内）时，一般直接全列索引，不必使用前缀
```

---

## 确定合适的前缀长度

```sql
-- 目标：找到选择性接近全列的最短前缀长度
-- 计算不同前缀长度的选择性：

SELECT
    COUNT(DISTINCT LEFT(url, 10)) / COUNT(*) AS sel_10,
    COUNT(DISTINCT LEFT(url, 20)) / COUNT(*) AS sel_20,
    COUNT(DISTINCT LEFT(url, 50)) / COUNT(*) AS sel_50,
    COUNT(DISTINCT LEFT(url, 100)) / COUNT(*) AS sel_100,
    COUNT(DISTINCT url) / COUNT(*) AS sel_full
FROM articles;

-- 示例输出：
-- sel_10  = 0.0230   （前10字符区分度低）
-- sel_20  = 0.5674   （前20字符有一定区分度）
-- sel_50  = 0.9512   （前50字符接近全列）
-- sel_100 = 0.9988   （前100字符几乎全列选择性）
-- sel_full= 1.0000

-- 结论：选择前缀长度 50（sel_50 已达 95%，比 sel_full 只少 5%）
-- 但索引大小从全列的平均 150字符 降低到 50字符 = 节省 2/3 空间

-- 经验：选择选择性达到全列 90%~95% 以上的最短前缀长度
ALTER TABLE articles ADD INDEX idx_url (url(50));
```

## 前缀索引的查询行为

```sql
-- 等值查询（MySQL 会先用前缀定位，再在回表后验证完整值）
EXPLAIN SELECT * FROM articles WHERE url = 'https://example.com/article/123' \G
-- key: idx_url_prefix
-- type: ref

-- 内部执行过程：
-- 1. 取查询值的前 50 字符：'https://example.com/article/1'
-- 2. 在 B+树中查找该前缀的叶子节点（可能匹配多行前缀相同的 URL）
-- 3. 回表获取完整行
-- 4. 在 Server 层验证完整的 url 值是否匹配

-- 范围查询
EXPLAIN SELECT * FROM articles WHERE url LIKE 'https://example.com/%' \G
-- 前缀匹配（% 在后面）可以走前缀索引
-- 取前缀 'https://example.com/' 作为索引范围起点

-- 不支持覆盖索引（重要限制！）
EXPLAIN SELECT url FROM articles WHERE url = 'https://example.com/abc' \G
-- 即使只 SELECT url 列，前缀索引也无法做覆盖索引
-- 因为索引中只存储了前 50 个字符，无法完整返回 url 值
-- Extra: NULL（需要回表获取完整 url）
```

## 前缀索引 vs 全列索引

| 对比维度 | 全列索引 | 前缀索引 |
|---------|:-------:|:-------:|
| 索引大小 | 完整字符串长度 | 只有 N 字符长度（更小）|
| 选择性 | 最高（100%）| 略低（取决于 N）|
| 覆盖索引 | 支持 | 不支持 |
| ORDER BY 使用 | 可以（全字符串有序）| 有限制（只按前缀排序）|
| TEXT/BLOB | 不支持全列索引 | 必须使用前缀索引 |
| 查询精度 | 精确（无额外验证）| 需回表验证完整值 |

---

## 前缀索引的局限性

```sql
-- 1. 不支持覆盖索引：
-- 无论查询需要 url 列还是不需要，前缀索引总是需要回表（无法 Extra: Using index）

-- 2. 不支持完整 ORDER BY：
-- ORDER BY url 用前缀索引只能按前 N 字符排序
-- 如果多行前缀相同但完整 URL 不同，排序结果可能不正确
-- 通常 MySQL 会放弃使用前缀索引做 ORDER BY，改用 filesort

-- 3. GROUP BY 类似 ORDER BY 的限制：
-- GROUP BY url 无法使用前缀索引的排序特性

-- 4. 对于高度重复的前缀（如 URL 都以 'https://www.' 开头），
-- 需要设置更长的前缀长度才能达到足够的选择性
```

## 替代方案：哈希列

```sql
-- 对于超长字符串（如完整 URL），可以用哈希列替代前缀索引
-- 哈希列：存储原始值的哈希（如 MD5 或 CRC32）

ALTER TABLE articles ADD COLUMN url_hash INT UNSIGNED
    GENERATED ALWAYS AS (CRC32(url)) STORED;
    
ALTER TABLE articles ADD INDEX idx_url_hash (url_hash);

-- 查询时使用哈希列（等值查找）：
SELECT * FROM articles
WHERE url_hash = CRC32('https://example.com/article/123')
  AND url = 'https://example.com/article/123';  -- 额外验证完整值（防哈希碰撞）

-- 优点：INT(4字节) << 字符串前缀，索引极小
-- 缺点：不支持范围查询（LIKE 'xxx%'），只支持等值
-- 适合：URL 等超长字符串的精确等值查找
```

## 适用场景

- **TEXT/BLOB 类型必须使用前缀索引**：MySQL 不允许对 TEXT/BLOB 类型建全列索引，必须通过 `column(N)` 指定前缀长度。对于需要通过文本列快速查找的场景（如文章标题、描述前缀搜索），前缀索引是必要选择
- **长 VARCHAR 列的空间优化**：对于平均长度超过 100 字符但前缀区分度足够的 VARCHAR 列（如 URL、文件路径），使用前缀索引可以大幅减少索引占用空间，降低 Buffer Pool 压力

## 常见问题

**前缀长度设置为多少合适？**

没有固定答案，取决于列数据的分布特征。通用方法是：通过 `COUNT(DISTINCT LEFT(col, N)) / COUNT(*)` 计算不同 N 值的选择性，选择选择性达到全列 90% 以上的最短 N 值。过短的前缀（选择性太低）会导致索引扫描后大量回表验证；过长的前缀浪费索引空间。对于字符集为 `utf8mb4` 的列，注意 N 是字符数（不是字节数），每个字符最多占 4 字节，`VARCHAR(100)` + `utf8mb4` 的索引条目最多 400 字节。

---

## 注意事项

- 前缀索引对字符集敏感。使用 `utf8mb4` 字符集时，一个字符最多占 4 字节；前缀长度 N 指的是字符数，不是字节数。InnoDB 页中每条索引记录的键值字节数超过页大小的一半时，会使用溢出页存储，建议前缀长度不要太大（一般不超过 200 字符）。
- `LIKE 'prefix%'`（前缀匹配）可以使用前缀索引，但 `LIKE '%suffix'`（后缀匹配）无法使用任何 B+树索引（需要全文索引或应用层处理）。如果业务需要后缀搜索，可以考虑存储逆序字符串并建前缀索引（`LIKE 'xiffus%'`）。

---

## 总结

前缀索引通过只索引字符串列的前 N 个字符，以小幅降低选择性为代价换取索引大小的显著缩减。确定 N 的方法：计算 `COUNT(DISTINCT LEFT(col, N)) / COUNT(*)` 选择接近全列选择性的最短 N 值。TEXT/BLOB 类型必须使用前缀索引（不能全列索引）。前缀索引的核心限制：不支持覆盖索引（总是需要回表）、ORDER BY 中效果受限。对超长字符串的精确等值查找，哈希列（CRC32 + 完整值验证）是更高效的替代方案。前缀长度设置需要权衡选择性（越长越好）与索引空间（越短越好）。

# 唯一索引 UNIQUE INDEX

唯一索引（UNIQUE INDEX）是在普通二级索引的基础上附加了唯一性约束的 B+树索引，保证索引列（或列组合）的值在整张表中不重复。唯一索引既是数据完整性约束，也是查询加速工具。与普通索引相比，唯一索引在查询时能进行更优的"点查"优化（找到匹配行后立即停止扫描），并且在 InnoDB 内部的 Change Buffer 处理上有所不同。

---

## 创建与管理唯一索引

```sql
-- 建表时创建唯一索引
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    phone CHAR(11),
    UNIQUE INDEX idx_email (email),              -- email 唯一
    UNIQUE INDEX idx_phone (phone),              -- phone 唯一（允许 NULL）
    UNIQUE INDEX idx_username (username)         -- username 唯一
);

-- 建表后添加唯一索引
ALTER TABLE users ADD UNIQUE INDEX idx_email (email);

-- 唯一复合索引（组合唯一）
CREATE TABLE user_roles (
    user_id INT NOT NULL,
    role_id INT NOT NULL,
    assigned_at DATETIME,
    UNIQUE INDEX idx_user_role (user_id, role_id)  -- user_id+role_id 组合唯一
);

-- 删除唯一索引
ALTER TABLE users DROP INDEX idx_email;
-- 或
DROP INDEX idx_email ON users;

-- 查看唯一索引（Non_unique = 0）
SHOW INDEX FROM users \G
-- Non_unique: 0 → 唯一索引
-- Non_unique: 1 → 普通索引
```

## 唯一索引与 NULL 值

```sql
-- 唯一索引允许多个 NULL 值（NULL != NULL）
INSERT INTO users (username, email, phone) VALUES ('Alice', 'a@a.com', NULL);
INSERT INTO users (username, email, phone) VALUES ('Bob', 'b@b.com', NULL);
-- 两个 NULL phone 值，不违反唯一约束（NULL 被视为"未知"，不相等）

-- 但如果是 NOT NULL + UNIQUE，则不允许多个相同的非 NULL 值
INSERT INTO users (username, email) VALUES ('Charlie', 'a@a.com');
-- ERROR 1062: Duplicate entry 'a@a.com' for key 'idx_email'
-- email 已存在 a@a.com，违反唯一约束

-- 验证 NULL 允许重复：
SELECT COUNT(*) FROM users WHERE phone IS NULL;  -- 可以有多行 phone=NULL
```

## 唯一索引 vs 普通索引的查询差异

```sql
-- 唯一索引的点查优化（找到匹配行后立即停止）：
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com' \G
-- type: const   → 最优访问类型（唯一索引等值查找）
-- rows: 1       → 只扫描 1 行

-- 普通索引的等值查找（可能有多行匹配，继续扫描）：
EXPLAIN SELECT * FROM users WHERE username = 'Alice' \G
-- 如果 username 是普通索引（允许重复值）：
-- type: ref     → 需要扫描所有匹配 username='Alice' 的叶子节点
-- rows: 可能 > 1

-- 唯一索引：找到第一个匹配行后，InnoDB 知道不可能再有相同值
-- → 停止扫描，返回（或报 0 行）
-- 普通索引：找到匹配行后，必须继续扫描直到下一个不同值
```

## 唯一索引与 Change Buffer

```sql
-- Change Buffer（插入缓冲区）是 InnoDB 对二级索引写入的优化：
-- 当目标索引页不在 Buffer Pool 中时，先将修改记入 Change Buffer
-- 延迟到页面被读取时再合并（减少随机 I/O）

-- 唯一索引不能使用 Change Buffer！
-- 原因：插入到唯一索引时，InnoDB 必须立即读入目标页
--       验证唯一性（是否有重复值）
--       → 无法延迟，必须立即 I/O

-- 普通索引可以使用 Change Buffer：
-- 插入时，如果目标页不在内存中 → 先记入 Change Buffer → 异步合并
-- 减少随机 I/O，提升写入性能

-- 实际影响：
-- 在写密集型场景（大量 INSERT），普通索引的写入性能优于唯一索引
-- 如果业务只需要数据质量保证（不需要唯一约束），用普通索引更好
-- 如果需要唯一性（如邮箱、手机号），只能用唯一索引（接受 Change Buffer 不可用）
```

## 唯一索引与主键的区别

| 对比维度 | 主键（PRIMARY KEY）| 唯一索引（UNIQUE INDEX）|
|---------|:-----------------:|:----------------------:|
| 数量限制 | 每表只能有 1 个 | 可以有多个 |
| NULL 值 | 不允许 NULL | 允许 NULL（可多个）|
| 聚簇索引 | 是聚簇索引（存储行数据）| 是二级索引（存主键值）|
| 自动创建 | 定义 PRIMARY KEY 时自动 | 需要显式定义 |
| Change Buffer | N/A（聚簇索引无 CB）| 不可使用（需即时唯一性检查）|
| 约束级别 | 主键约束 + 唯一约束 | 仅唯一约束 |

## 唯一索引的应用场景

```sql
-- 场景1：业务唯一键（自然键）
-- 邮箱、手机号、身份证号作为唯一索引（而不是主键）
-- 因为这些字段可能为空（NULL）或长度较大，不适合作为主键

-- 场景2：防重复提交
-- 订单表的幂等键（idempotency_key），唯一索引防止重复提交
CREATE TABLE payments (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    idempotency_key VARCHAR(64) NOT NULL,
    amount DECIMAL(10,2),
    UNIQUE INDEX idx_idempotency (idempotency_key)
);
-- 重复提交时，INSERT 会触发唯一约束错误（ERROR 1062）
-- 可以通过 INSERT IGNORE 或 ON DUPLICATE KEY UPDATE 处理

-- 场景3：多对多关系的联合唯一
CREATE TABLE user_permissions (
    user_id INT NOT NULL,
    permission_id INT NOT NULL,
    UNIQUE INDEX idx_user_perm (user_id, permission_id)
);
-- 确保每个用户对每个权限只有一条记录

-- INSERT IGNORE（重复时静默忽略）：
INSERT IGNORE INTO user_permissions VALUES (1, 5);

-- ON DUPLICATE KEY UPDATE（重复时更新）：
INSERT INTO user_permissions (user_id, permission_id, granted_at)
VALUES (1, 5, NOW())
ON DUPLICATE KEY UPDATE granted_at = NOW();
```

## 适用场景

- **业务唯一性保证**：对需要全局唯一的业务标识列（邮箱、手机号、证件号、订单号）建立唯一索引，同时保证数据完整性和查询加速（等值查询类型为 `const`）
- **防重幂等设计**：通过唯一索引实现幂等写入，利用数据库的唯一约束作为分布式场景的"最后一道防线"，防止重复数据入库

## 常见问题

**已经有唯一索引了，还需要主键吗？**

需要。唯一索引是二级索引，叶子节点存储的是主键值；如果没有主键，InnoDB 会生成隐藏的 `DB_ROW_ID` 作为聚簇索引，但这个字段无法被业务层引用（JOIN、WHERE 都无法使用）。此外，唯一索引允许 NULL 值，而主键不允许——唯一索引不能完全替代主键的作用。实践中，应同时定义一个合适的整型自增主键和若干业务唯一索引，两者各司其职。

---

## 注意事项

- 唯一索引会在每次 INSERT 和 UPDATE（修改索引列）时触发唯一性检查，InnoDB 必须读入目标索引页（不能延迟）。在大批量数据导入时，如果表有多个唯一索引，每条记录的插入都会触发多次唯一性检查 I/O，性能显著下降。批量导入时可以考虑先禁用唯一性检查（`SET unique_checks = 0`）导入后再开启，但需要确保数据来源本身无重复。
- 在主从复制中，如果使用 STATEMENT 格式 Binlog，涉及 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE` 的语句在主从上执行结果可能不一致（因为主键自增值不一样）。推荐使用 ROW 格式 Binlog 避免此问题。

---

## 总结

唯一索引（UNIQUE INDEX）是带唯一约束的 B+树二级索引，保证索引列值在表中不重复（NULL 除外，允许多个 NULL）。与主键的区别：唯一索引是二级索引，允许 NULL，每表可有多个；主键是聚簇索引，不允许 NULL，每表只有一个。查询性能：唯一索引等值查找类型为 `const`，找到匹配行立即停止；普通索引为 `ref`，继续扫描到下一个不同值。唯一索引不能使用 Change Buffer（写入时需即时唯一性检查），写入性能略低于普通索引。适用于业务唯一键、幂等写入防重的场景。

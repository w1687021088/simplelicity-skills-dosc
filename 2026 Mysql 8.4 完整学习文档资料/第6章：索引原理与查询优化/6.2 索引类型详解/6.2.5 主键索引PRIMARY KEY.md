# 主键索引 PRIMARY KEY

主键索引（PRIMARY KEY）是 InnoDB 中最特殊的索引——它不是一个独立于表数据的索引结构，而是表数据本身的存储方式（聚簇索引）。InnoDB 表的数据按主键值有序组织在一棵 B+树中，这棵树的叶子节点直接存储完整的行数据。主键的设计直接影响表的物理存储结构、二级索引的空间占用、写入性能和查询效率，是 MySQL 数据库设计中最重要的决策之一。

---

## 主键的定义与规则

```sql
-- 方式1：建表时定义 PRIMARY KEY
CREATE TABLE users (
    id INT NOT NULL AUTO_INCREMENT,
    email VARCHAR(100) NOT NULL,
    username VARCHAR(50) NOT NULL,
    PRIMARY KEY (id)                 -- 单列主键
);

-- 方式2：列定义中直接声明 PRIMARY KEY
CREATE TABLE products (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100)
);

-- 方式3：复合主键（多列组合作为主键）
CREATE TABLE order_items (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT,
    PRIMARY KEY (order_id, product_id)   -- 复合主键
);

-- 主键约束规则：
-- 1. 每表只能有一个 PRIMARY KEY
-- 2. 主键列（或组合）的值必须唯一（与 UNIQUE NOT NULL 等效）
-- 3. 主键列不能为 NULL（隐式 NOT NULL）
-- 4. 主键是聚簇索引（InnoDB 表数据按主键排序）
-- 5. 所有二级索引的叶子节点都引用主键值作为行指针
```

---

## AUTO_INCREMENT 主键的特性

```sql
-- AUTO_INCREMENT 整型主键是 InnoDB 的最佳实践
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,  -- 推荐 BIGINT 应对大数据量
    user_id INT,
    amount DECIMAL(10,2)
);

-- 插入时不需要指定 id（自动递增）
INSERT INTO orders (user_id, amount) VALUES (100, 99.99);

-- 查看最后一次插入的 AUTO_INCREMENT 值
SELECT LAST_INSERT_ID();

-- 查看表的当前 AUTO_INCREMENT 值
SHOW TABLE STATUS LIKE 'orders' \G
-- Auto_increment: 当前下一个将要使用的值

-- MySQL 8.0+ AUTO_INCREMENT 持久化（重启后不会重置）：
-- 旧版本（5.7）：服务器重启后，AUTO_INCREMENT 会回退到 MAX(id)+1
-- MySQL 8.0+：AUTO_INCREMENT 值写入 Redo Log，重启后恢复正确值
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';
-- 默认：2（轻量级，高并发 INSERT 无竞争）
```

## 主键类型选择及影响

```sql
-- 自增整型主键（推荐）
-- 优点：顺序插入（无页分裂），主键短（4/8字节），二级索引紧凑
-- CREATE TABLE t (id INT AUTO_INCREMENT PRIMARY KEY);

-- UUID 字符串主键（不推荐）
-- CREATE TABLE t (id CHAR(36) PRIMARY KEY DEFAULT (UUID()));
-- 缺点：
-- 1. UUID 随机性 → 插入位置随机 → 页分裂频繁 → 碎片多
-- 2. CHAR(36) = 36字节 >> INT = 4字节
--    每个二级索引的叶子节点都要存储 36 字节主键 → 索引膨胀

-- MySQL 8.0+ UUID_TO_BIN（有序 UUID，缓解随机性问题）
CREATE TABLE t_uuid (
    id BINARY(16) PRIMARY KEY DEFAULT (UUID_TO_BIN(UUID(), TRUE)),  -- TRUE=时间有序
    name VARCHAR(100)
);
-- UUID_TO_BIN(uuid, TRUE) 将时间戳部分移到最前 → 减少随机插入

-- 业务自然键（如手机号、身份证号）作主键
-- 缺点：字符串比较慢，长度大，业务键可能变化（更新主键代价高）
-- 建议：作唯一索引（UNIQUE INDEX），另设 INT AUTO_INCREMENT 主键

-- 总结：OLTP 系统优先使用 INT/BIGINT AUTO_INCREMENT 主键
```

## 复合主键的使用

```sql
-- 复合主键适合无自然单一主键的关联表
CREATE TABLE course_enrollments (
    student_id INT NOT NULL,
    course_id INT NOT NULL,
    enrolled_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    grade DECIMAL(5,2),
    PRIMARY KEY (student_id, course_id)
);

-- 复合主键的查询（按最左前缀）：
SELECT * FROM course_enrollments WHERE student_id = 1001;
-- 走主键（聚簇索引），只用 student_id 部分

SELECT * FROM course_enrollments WHERE student_id = 1001 AND course_id = 205;
-- 走主键，完整利用两列

-- 如果需要反向查询：
SELECT * FROM course_enrollments WHERE course_id = 205;
-- 无法走复合主键（course_id 不是最左列）
-- 需要为 course_id 单独建二级索引：
ALTER TABLE course_enrollments ADD INDEX idx_course (course_id);

-- 复合主键与二级索引的关系：
-- 二级索引的叶子节点存储的行指针 = 完整的复合主键值（student_id + course_id）
-- 复合主键越长，二级索引越大
```

## 主键的物理含义与 InnoDB 特性

```
主键 = 聚簇索引键 = 数据物理排列依据

1. 插入性能：
   自增主键 → 永远追加到 B+树末尾 → 顺序 I/O → 高效
   随机主键 → 插入到 B+树中间 → 触发页分裂 → 随机 I/O → 性能下降

2. 范围查询：
   SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000
   → 顺序读取连续的叶子节点 → 高效

3. 二级索引大小：
   所有二级索引叶子节点都存储主键值
   主键 INT(4字节) vs CHAR(36)(36字节)
   有 5 个二级索引的表，1亿行数据：
   INT主键：5 × 1亿 × 4字节 = 200MB 额外二级索引空间
   CHAR(36)主键：5 × 1亿 × 36字节 = 1.8GB 额外二级索引空间

4. 行数据大小：
   主键列的值存储在每行中（聚簇索引叶子节点）
   主键越小，每行越紧凑，每个数据页能存的行数越多
```

## 适用场景

- **OLTP 系统标准设计**：所有 InnoDB 表都应定义显式主键，优先使用 `BIGINT AUTO_INCREMENT`（未来数据量可能超过 INT 上限 21 亿时）；小表（确定不超过 21 亿行）可以使用 `INT AUTO_INCREMENT`
- **关联表的复合主键**：多对多关联表（如用户-权限、订单-商品）使用业务相关列的组合作为复合主键，简化设计，但要注意为非最左列单独建二级索引支持反向查询

## 常见问题

**主键能修改吗？有什么影响？**

技术上可以修改（`UPDATE table SET id = new_id WHERE id = old_id`），但代价极高。修改主键值意味着：①聚簇索引中该行的物理位置可能改变（B+树的重新插入/删除）；②所有指向该行的二级索引叶子节点也要更新（新主键值）。对于大量行的主键修改，代价类似于删除旧行并插入新行。实践中应将主键设计为业务无关的代理键（`AUTO_INCREMENT`），永远不会需要修改主键值。

---

## 注意事项

- 在 MySQL 8.0+ 中，`AUTO_INCREMENT` 值通过 Redo Log 持久化，解决了 MySQL 5.7 及更早版本重启后 `AUTO_INCREMENT` 回退的问题（旧版本在服务器重启后，`AUTO_INCREMENT` 会回退到 `MAX(id)+1`，可能与之前已删除的 ID 冲突）。升级到 MySQL 8.0+ 后不必再担心这个问题。
- 不要对 `AUTO_INCREMENT` 主键列做 `INSERT` 时指定具体值（除非特殊的数据迁移场景）。手动指定会打乱自增序列，可能导致序列跳跃或与已有值冲突。如果必须指定，确保指定的值大于当前 `AUTO_INCREMENT` 值。

---

## 总结

主键索引（PRIMARY KEY）是 InnoDB 的聚簇索引，表数据本身按主键值有序存储在 B+树叶子节点中。每表只有一个主键，不允许 NULL，是所有二级索引的行指针来源（二级索引叶子节点存主键值）。推荐设计：`BIGINT/INT AUTO_INCREMENT`——顺序插入（避免页分裂）、主键短（二级索引空间小）、数值比较快。避免使用 UUID（随机性导致页分裂）或长字符串（二级索引膨胀）作主键。MySQL 8.0+ AUTO_INCREMENT 持久化，解决了重启回退问题。复合主键适合关联表，但要为非最左列建额外二级索引支持反向查询。

# 降序索引 Descending Index（8.4 支持）

降序索引（Descending Index）是 MySQL 8.0 正式引入的索引功能，允许在创建索引时为每列指定升序（ASC）或降序（DESC）的存储方向。在此之前（MySQL 5.x/8.0 之前），虽然 `CREATE INDEX` 语法允许写 `DESC`，但 InnoDB 实际上忽略了这个关键字，所有列总是按升序存储。真正的降序索引从 MySQL 8.0 开始支持，在 MySQL 8.4 LTS 中可以正常使用。

---

## 降序索引解决的问题

```sql
-- 在 MySQL 5.7 及更早版本，以下查询存在一个优化问题：
-- 查询：WHERE dept_id = 1 ORDER BY salary DESC, age ASC

-- 假设索引 idx(dept_id, salary ASC, age ASC)：
-- dept_id=1 等值过滤 ✓
-- salary DESC：需要反向扫描 salary 索引（倒序读叶子节点链表）
-- age ASC：和 salary 方向相反 → 两列排序方向不一致
-- → MySQL 5.7 无法利用索引的有序性，被迫 Using filesort（文件排序）

-- MySQL 8.0+ 可以精确指定每列的存储方向：
-- 索引 idx(dept_id ASC, salary DESC, age ASC)
-- → 与查询的排序方向完全匹配 → 无需 filesort
```

---

## 降序索引的语法

```sql
CREATE TABLE employees (
    id INT PRIMARY KEY AUTO_INCREMENT,
    dept_id INT NOT NULL,
    salary DECIMAL(10,2) NOT NULL,
    age TINYINT NOT NULL,
    name VARCHAR(50),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 创建降序索引（指定每列的排序方向）
ALTER TABLE employees ADD INDEX idx_dept_salary_age (
    dept_id ASC,      -- dept_id 升序（默认，也可以省略 ASC）
    salary DESC,      -- salary 降序（关键：真正的降序存储）
    age ASC           -- age 升序
);

-- 纯降序索引（整个索引按最后更新时间降序）
ALTER TABLE employees ADD INDEX idx_created_desc (created_at DESC);

-- 查看索引（Collation 列：A=升序，D=降序）
SHOW INDEX FROM employees \G
-- Collation: A → ASC（升序）
-- Collation: D → DESC（降序）
```

## 降序索引的使用效果

```sql
-- 查询1：与索引排序方向完全匹配（无 filesort）
EXPLAIN SELECT id, dept_id, salary, age FROM employees
WHERE dept_id = 1
ORDER BY salary DESC, age ASC \G
-- key: idx_dept_salary_age
-- Extra: Using index     ← 覆盖索引，无 filesort
-- （dept_id=1 等值定位，salary DESC + age ASC 与索引方向完全一致）

-- 查询2：与索引排序方向完全相反（反向扫描，也无 filesort）
EXPLAIN SELECT id, dept_id, salary, age FROM employees
WHERE dept_id = 1
ORDER BY salary ASC, age DESC \G
-- key: idx_dept_salary_age
-- Extra: Backward index scan; Using index   ← 反向扫描，无 filesort
-- 索引方向相反可以通过反向读叶子节点链表实现，比 filesort 快

-- 查询3：排序方向混用（既不是正向也不是全反向），需要 filesort
EXPLAIN SELECT * FROM employees
WHERE dept_id = 1
ORDER BY salary DESC, age DESC \G
-- 索引中 age 是 ASC，但查询要 age DESC
-- 同时 salary DESC 和 age DESC 混合方向（无法反向扫描解决）
-- Extra: Using filesort  ← 必须 filesort
```

## 降序索引 vs 反向扫描（Backward Index Scan）

```sql
-- MySQL 8.0 还引入了 Backward Index Scan（反向扫描普通 ASC 索引）
-- 对于全升序或全降序的 ORDER BY，反向扫描已经可以避免 filesort

-- 普通 ASC 索引：
ALTER TABLE employees ADD INDEX idx_salary_asc (salary ASC);

-- ORDER BY salary DESC：使用 Backward Index Scan（反向读 ASC 索引）
EXPLAIN SELECT id, salary FROM employees ORDER BY salary DESC LIMIT 10 \G
-- Extra: Backward index scan; Using index

-- 降序索引的价值在于"混合排序方向"场景：
-- ORDER BY salary DESC, age ASC 这类混合方向查询
-- 普通单向索引（全 ASC 或全 DESC）无法通过反向扫描解决
-- 只有在索引中精确指定各列方向（如 salary DESC, age ASC）才能避免 filesort

-- 验证降序索引的优势：
-- 不使用降序索引（全 ASC）：
EXPLAIN SELECT id, dept_id, salary, age FROM employees
WHERE dept_id = 1 ORDER BY salary DESC, age ASC \G
-- Extra: Using filesort  ← 混合方向，需要 filesort

-- 使用降序索引（salary DESC, age ASC）：
EXPLAIN SELECT id, dept_id, salary, age FROM employees
WHERE dept_id = 1 ORDER BY salary DESC, age ASC \G
-- Extra: Using index     ← 覆盖索引，无 filesort
```

## 降序索引的典型应用

```sql
-- 场景1：新闻/博客列表（按时间倒序 + 分类过滤）
CREATE TABLE posts (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    category_id INT NOT NULL,
    published_at DATETIME NOT NULL,
    views INT DEFAULT 0,
    title VARCHAR(200),
    INDEX idx_cat_time (category_id ASC, published_at DESC)
);

-- 查询某分类的最新文章（使用降序索引，无 filesort）
EXPLAIN SELECT id, category_id, published_at, title
FROM posts
WHERE category_id = 5
ORDER BY published_at DESC
LIMIT 20 \G
-- Extra: Using index  ← 覆盖索引，无 filesort

-- 场景2：排行榜（按分数降序 + 时间升序）
CREATE TABLE scores (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    game_id INT NOT NULL,
    player_id INT NOT NULL,
    score INT NOT NULL,
    played_at DATETIME NOT NULL,
    INDEX idx_game_score (game_id ASC, score DESC, played_at ASC)
);

-- 某游戏的排行榜（分数高的在前，同分时早玩的在前）
SELECT player_id, score, played_at
FROM scores
WHERE game_id = 100
ORDER BY score DESC, played_at ASC
LIMIT 100;
-- 利用降序索引，无 filesort，高效
```

---

## 适用场景

- **混合排序方向的查询**：当 ORDER BY 子句中同时包含升序和降序的列（如 `ORDER BY score DESC, created_at ASC`），降序索引可以直接匹配查询需求，消除 filesort，是降序索引最核心的使用场景
- **倒序时间轴查询**：内容列表、消息流、操作日志等按时间倒序展示的场景，在 `(category_id ASC, created_at DESC)` 联合索引上，查询可以利用索引顺序直接返回结果

## 常见问题

**MySQL 5.7 中 `CREATE INDEX ... DESC` 不是就已经支持降序索引了吗？**

不是。MySQL 5.7 及更早版本的语法虽然允许写 `CREATE INDEX idx (col DESC)`，但 InnoDB 完全忽略了 `DESC` 关键字——实际创建的索引仍然是升序（ASC）索引。这个语法只是为了兼容 SQL 标准，但没有实际效果。真正的降序索引（`Collation: D`）从 MySQL 8.0.1 开始才被 InnoDB 实现，可以通过 `SHOW INDEX` 的 `Collation` 列（`D` 表示降序）确认。

---

## 注意事项

- 降序索引仍然是 B+树结构，只是叶子节点的排列方向相反（键值从大到小存储）。降序索引占用的存储空间与同等升序索引相同，维护开销也相同。选择使用降序索引的依据是查询的 ORDER BY 方向，而不是其他因素。
- 降序索引的 Backward Index Scan（反向扫描）性能略低于正向扫描（因为页面链表是双向的，但反向遍历的 CPU 缓存利用率稍低）。对于全降序或全升序的排序需求，普通索引 + Backward Scan 与降序索引性能相近；只有在混合排序方向时，降序索引才有明显优势。

---

## 总结

降序索引（Descending Index）从 MySQL 8.0 正式支持，MySQL 8.4 LTS 可正常使用。语法：`INDEX idx (col1 ASC, col2 DESC)`，`SHOW INDEX` 的 `Collation` 列显示 `D` 表示降序存储。核心价值：解决混合排序方向（如 `ORDER BY col1 DESC, col2 ASC`）导致的 filesort 问题——普通单向索引无法通过反向扫描解决混合排序，只有精确匹配各列排序方向的降序索引才能消除 filesort。适用场景：新闻/帖子按时间倒序 + 分类过滤；排行榜按分数降序 + 时间升序；任何混合排序方向的高频查询。

# 联合索引 Composite Index

联合索引（Composite Index，也称复合索引或多列索引）是建立在表的多个列上的 B+树索引。联合索引的叶子节点按照索引定义中各列从左到右的顺序组合排序，因此它能同时支持多列的等值、范围过滤和排序。合理设计的联合索引往往比多个单列索引的组合具有更高的查询效率，是 MySQL 索引优化的核心工具。

---

## 创建联合索引

```sql
-- 建表时创建联合索引
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    amount DECIMAL(10,2) NOT NULL,
    created_at DATETIME NOT NULL,
    INDEX idx_user_status (user_id, status),                    -- 2列联合索引
    INDEX idx_user_status_created (user_id, status, created_at) -- 3列联合索引
);

-- 建表后添加联合索引
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);

-- 查看联合索引（Seq_in_index 列显示列顺序）
SHOW INDEX FROM orders WHERE Key_name = 'idx_user_status' \G
-- Key_name: idx_user_status
-- Seq_in_index: 1, Column_name: user_id
-- Seq_in_index: 2, Column_name: status
```

---

## 联合索引的 B+树结构

```
联合索引 idx_user_status(user_id, status) 的叶子节点排列：

[user_id=1, status=0, id=101]
[user_id=1, status=1, id=203]
[user_id=1, status=2, id=305]
[user_id=2, status=0, id=102]
[user_id=2, status=1, id=204]
[user_id=3, status=1, id=405]
...

先按 user_id 排序 → user_id 相同时按 status 排序 → status 相同时按 id 排序

等值查找 user_id=2 AND status=1：
  在 B+树中定位 (user_id=2, status=1) → 找到 id=204 → 回表
  只扫描匹配的叶子节点（高效）

范围查找 user_id=2：
  在 B+树中定位 user_id=2 的起始位置 → 顺序扫描直到 user_id=3
  返回 user_id=2 的所有记录（利用叶子链表）

不使用 user_id 直接查 status=1：
  status=1 在索引中无序（散布在 user_id=1,2,3... 的各条记录中）
  无法定位范围 → 不走索引（违反最左前缀）
```

## 联合索引的有效使用场景

```sql
-- 索引：idx_user_status_created (user_id, status, created_at)

-- 使用所有列（最优）：
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 AND status = 1 AND created_at > '2025-01-01' \G
-- type: range, key_len: 全部3列长度

-- 使用前两列：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- type: ref, key_len: user_id+status 的长度

-- 只使用第一列：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- type: ref, key_len: user_id 的长度

-- 跳过 status，只用 user_id + created_at：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND created_at > '2025-01-01' \G
-- type: ref（只用 user_id），created_at 作为 Server 层过滤
-- key_len 只包含 user_id（status 被跳过，后续列不用于索引）

-- 覆盖索引查询：
EXPLAIN SELECT id, user_id, status FROM orders WHERE user_id = 100 \G
-- Extra: Using index（id、user_id、status 都在 idx_user_status_created 中）
```

## 联合索引 vs 多个单列索引

| 对比维度 | 多个单列索引 | 联合索引 |
|---------|:-----------:|:-------:|
| 多列同时过滤 | Index Merge（有额外开销）| B+树内直接多列过滤（高效）|
| 覆盖索引支持 | 每个索引只包含一列 | 多列都在同一索引，更易实现覆盖索引 |
| 存储空间 | 每个索引独立存储 | 一个索引存所有列，通常总空间更小 |
| 维护开销 | 每个索引独立维护（N个索引=N倍维护）| 单个索引维护（1倍）|
| 灵活性 | 各索引可单独使用不同查询 | 必须遵循最左前缀 |
| 适合场景 | 列经常单独出现在不同查询中 | 多列总是组合出现在查询中 |

## 联合索引对 ORDER BY 的支持

```sql
-- 联合索引可以避免 filesort（需要满足排序方向一致）
-- 索引：idx_user_status_created (user_id, status, created_at)

-- 利用索引排序（无 filesort）：
EXPLAIN SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 100 ORDER BY status \G
-- Extra: Using index（覆盖索引 + 索引有序，无 filesort）

EXPLAIN SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 100 AND status = 1 ORDER BY created_at \G
-- Extra: Using index（覆盖索引，依次按 user_id、status、created_at 排序）

-- 触发 filesort 的情况：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY created_at \G
-- status 被跳过，created_at 排序方向在索引中不连续 → Using filesort

-- 升序/降序混用（MySQL 8.0+ 支持降序索引，可以避免）：
EXPLAIN SELECT * FROM orders WHERE user_id = 100
ORDER BY status ASC, created_at DESC \G
-- 如果索引是全 ASC，此混合排序需要 filesort
```

## 适用场景

- **多列组合查询**：当 WHERE 子句中多个列总是一起出现（如 `user_id + status`、`dept_id + age`），建立联合索引是最高效的方案
- **查询 + 排序优化**：将 WHERE 的过滤列和 ORDER BY 的排序列放入同一联合索引，可以同时避免索引扫描和 filesort

---

## 常见问题

**联合索引的列数越多越好吗？**

不是。过多列的联合索引会：①增加每条索引记录的大小（每次插入/更新都需要维护）；②在大量不同查询模式中可能只有少数能充分利用所有列；③使 B+树每页能存的键值减少，树可能变高。一般建议联合索引不超过 3~4 列，重点是覆盖最高频的查询模式。如果有多种查询组合，建多个针对性联合索引比一个超宽索引更合理。

---

## 注意事项

- 建立联合索引时，MySQL 内部会对索引列的值进行组合比较，因此列的数据类型对比较性能有影响。避免在联合索引中混用字符集或排序规则不同的列，可能导致隐式转换使索引失效。
- 联合索引中如果某列为 `NULL`，在 B+树中 `NULL` 排在最前面（`NULL` 值的行会出现在索引叶子节点的开头）。`IS NULL` 条件可以走联合索引（如果 `NULL` 列是最左前缀）；`IS NOT NULL` 通常也能走索引（作为范围条件）。

---

## 总结

联合索引（多列索引）是建立在多个列上的 B+树，按最左列优先组合排序，遵循最左前缀原则。相比多个单列索引：能在 B+树内同时利用多列过滤（更高效）；更容易实现覆盖索引；总存储和维护开销更低。适合多列组合查询、结合排序优化（WHERE + ORDER BY 放入同一索引）的场景。设计要点：等值列在左，范围列在右；高选择性列在左；兼顾 ORDER BY 列顺序；列数不超过 3~4 列。通过 `EXPLAIN` 的 `key_len` 判断实际使用了联合索引的哪些列。

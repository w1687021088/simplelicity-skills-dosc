# 联合索引列顺序设计

联合索引的列顺序决定了它在各种查询场景下的适用性和效率。同样的列，不同的顺序可能导致截然不同的查询性能。列顺序设计需要综合考虑多个因素：查询的等值/范围条件分布、列的选择性高低、ORDER BY 排序需求、以及是否能实现覆盖索引。没有万能的顺序公式，需要根据实际查询模式进行权衡。

---

## 等值条件优先于范围条件

```sql
-- 核心规则：等值条件列放在联合索引的左边，范围条件列放在右边
-- 原因：范围条件之后的列无法用于索引范围定位（最左前缀规则）

-- 示例表和查询
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT,
    status TINYINT,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_wrong (user_id, amount, status),   -- 错误顺序示例
    INDEX idx_right (user_id, status, amount)    -- 正确顺序示例
);

-- 查询：WHERE user_id = 100 AND status = 1 AND amount > 100

-- 错误顺序 idx_wrong (user_id, amount, status)：
-- user_id=100 等值定位 ✓
-- amount > 100 范围条件 ✓（但）
-- status = 1 在范围条件之后 → 无法用于索引范围定位！只能 ICP 或回表后过滤
-- 实际只用了前两列

-- 正确顺序 idx_right (user_id, status, amount)：
-- user_id=100 等值定位 ✓
-- status=1 等值定位 ✓
-- amount > 100 范围条件 ✓
-- 三列全部有效用于索引！
```

## 高选择性列优先（在查询模式允许的情况下）

```sql
-- 选择性越高（不重复值越多），放在左边的过滤效果越好
-- 但此原则要让步于"等值 > 范围"规则和实际查询模式

-- 示例：user_id 高选择性，status 低选择性（只有 0/1/2）
-- 查询1：WHERE user_id = 100 AND status = 1
-- 查询2：WHERE status = 1（没有 user_id 条件）

-- 如果查询1 是主要查询：
INDEX idx1 (user_id, status)      -- user_id 在左，高选择性先过滤，好
-- user_id=100 过滤出少量行，status=1 进一步精确，最优

-- 如果查询2 也很重要且 status 在前：
INDEX idx2 (status, user_id)      -- 查询2 能走最左前缀
-- 查询1：WHERE status=1 AND user_id=100 也能走完整索引
-- 权衡：查询1在 idx1 下可能更高效（user_id 先定位范围更小）
-- 但 idx2 兼顾了查询2

-- 实际设计时：分析两个查询的频率，选择对更高频查询更优的顺序
-- 或者建两个索引（idx_user_status 和 idx_status_user）
```

## ORDER BY 排序列的加入

```sql
-- 将 ORDER BY 的列加入联合索引（放在等值条件列之后）
-- 可以避免 filesort，利用索引有序性直接返回排序结果

-- 查询：WHERE user_id = 100 AND status = 1 ORDER BY created_at DESC

-- 不含 created_at 的索引：
INDEX idx_user_status (user_id, status)
-- 过滤后，created_at 需要 filesort
-- Extra: Using filesort

-- 含 created_at 的索引：
INDEX idx_user_status_created (user_id, status, created_at)
-- 过滤 user_id=100、status=1 后，created_at 已经有序
-- ORDER BY created_at DESC 利用索引倒序扫描（MySQL 8.0+ 支持）
-- Extra: Backward index scan; Using index（如果覆盖索引）

-- 注意：ORDER BY 列要放在所有等值条件列之后
-- 如果 ORDER BY 列与索引顺序不一致，仍然 filesort
INDEX idx_wrong_order (user_id, created_at, status)
-- WHERE user_id = 100 AND status = 1 ORDER BY created_at
-- user_id 等值 ✓，created_at 范围扫描（没有 status 约束），status=1 无法利用
-- 效果差
```

## 区分度与前缀的关系

```sql
-- 如果第一列区分度很低，索引的初始过滤效率就差
-- 示例：status 只有 3 个值，每个值约 33% 的数据
INDEX idx_status_first (status, user_id, created_at)
-- WHERE status = 1：过滤掉约 33% 的数据，还剩 67% 行
-- 后续 user_id 和 created_at 再过滤
-- 第一列过滤效果差，整体索引效率一般

-- 如果 user_id 在前：
INDEX idx_user_first (user_id, status, created_at)
-- WHERE user_id = 100：假设 100 万用户，每个用户约 100 条订单
-- 第一列就过滤到约 100 行（如果总记录 1000 万）
-- 效率大幅提升

-- 经验原则：
-- 高频等值查询的列 → 放在左边
-- 低选择性的列（作为范围条件的）→ 放在右边
-- ORDER BY 的列 → 放在最右边（等值列之后）
```

## 多查询场景的索引顺序权衡

```sql
-- 实际中往往有多个查询需要使用同一张表，需要权衡
-- 查询A：WHERE user_id = 100 AND status = 1 ORDER BY created_at（高频）
-- 查询B：WHERE status = 1 ORDER BY created_at（中频）
-- 查询C：WHERE user_id = 100 ORDER BY created_at（中频）

-- 理想索引：
INDEX idx_user_status_created (user_id, status, created_at)
-- 查询A：完整利用（user_id 等值 + status 等值 + created_at 顺序）★★★
-- 查询B：跳过 user_id，无法走最左前缀，需要额外索引
-- 查询C：user_id 等值 + created_at 顺序（status 被跳过，但 ICP 可用）★★

-- 补充索引：
INDEX idx_status_created (status, created_at)
-- 查询B：status 等值 + created_at 顺序 ★★★

-- 两个索引组合覆盖了所有查询场景
-- 而不是试图用一个索引解决所有问题
```

## 索引顺序设计检查清单

```
设计联合索引列顺序的步骤：

1. 列出所有使用此表的高频查询（WHERE、ORDER BY 条件）
2. 识别哪些列经常同时出现（组合出现频率高 → 联合索引候选）
3. 在组合列中，按照以下优先级排序：
   a. 等值条件列放左边（因为范围条件会截断后续列的使用）
   b. 高选择性列尽量在前（在不违反 a 的前提下）
   c. ORDER BY 的列放在等值列之后（利用索引有序性避免 filesort）
   d. 覆盖索引需要的额外列放在最右边
4. 用 EXPLAIN 验证各个查询的执行计划
5. 检查 key_len 确认索引使用的列数是否符合预期
```

## 适用场景

- **新业务上线前的索引规划**：在开发阶段分析所有涉及表的 SQL 查询模式，按照等值优先、高选择性优先、ORDER BY 列在后的原则设计联合索引，减少上线后因索引不合理导致的性能问题
- **慢查询优化**：通过慢查询日志和 EXPLAIN 发现索引使用效率不高（key_len 过短、filesort 等），分析现有索引列顺序是否合理，调整顺序或添加新的联合索引

## 常见问题

**如何验证联合索引的列顺序是否合理？**

通过 `EXPLAIN` 查看执行计划：①`type` 应为 `ref` 或 `range`（不应为 `index`/`ALL`）；②`key_len` 应等于预期使用列的字节总长度（如果 key_len 比预期短，说明有列没被用到，可能顺序有问题）；③`Extra` 中不应有 `Using filesort`（如果 ORDER BY 列在索引中，应该无 filesort）；④`Extra: Using index` 代表实现了覆盖索引（额外验证）。通过这四个指标，基本可以判断联合索引的列顺序是否符合查询需求。

---

## 注意事项

- 联合索引的列顺序不是一成不变的，随着业务发展和查询模式的变化，原来合理的顺序可能不再最优。建议定期（季度或半年）回顾高频 SQL 和索引使用情况（通过 `performance_schema` 的索引使用统计），必要时调整索引顺序。
- 调整联合索引顺序需要删除旧索引并创建新索引（DDL 操作），在生产环境对大表操作时，应在低峰期执行，或使用在线 DDL 工具（`pt-online-schema-change`、`gh-ost`）减少对业务的影响。

---

## 总结

联合索引列顺序设计的核心原则：①等值条件列在左，范围条件列在右（范围条件之后的列无法用于索引范围定位）；②高选择性列尽量在前（在不违反等值优先的前提下）；③ORDER BY 的列放在等值条件列之后（利用索引有序性避免 filesort）；④考虑覆盖索引需求，将 SELECT 的列加入索引。通过 `EXPLAIN` 的 `type`、`key_len`、`Extra` 三个字段验证索引顺序是否有效。对于多种查询模式，允许建多个针对性索引，而不是试图用一个超宽索引覆盖所有情况。

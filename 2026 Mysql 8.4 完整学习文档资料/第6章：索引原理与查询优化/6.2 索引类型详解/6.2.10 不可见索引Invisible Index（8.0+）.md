# 不可见索引 Invisible Index（8.0+）

不可见索引（Invisible Index）是 MySQL 8.0 引入的索引管理功能，允许将索引设置为对查询优化器不可见（优化器不会使用该索引），但该索引仍然存在并持续维护（INSERT/UPDATE/DELETE 时正常更新）。这一功能主要用于"软删除"索引——在真正删除一个索引之前，先将其设为不可见，验证业务是否受到影响，如果没问题再彻底删除；如有问题则立即恢复可见性（比重新创建索引快得多）。

---

## 不可见索引的基本操作

```sql
-- 创建表时建不可见索引
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user (user_id) INVISIBLE,               -- 创建时即设为不可见
    INDEX idx_status (status),                         -- 普通可见索引
    INDEX idx_created (created_at)
);

-- 将现有索引设为不可见（优化器无法使用，但索引继续维护）
ALTER TABLE orders ALTER INDEX idx_user INVISIBLE;

-- 将不可见索引恢复为可见
ALTER TABLE orders ALTER INDEX idx_user VISIBLE;

-- 查看索引可见性（Visible 列）
SHOW INDEX FROM orders \G
-- Visible: YES → 可见（优化器可以使用）
-- Visible: NO  → 不可见（优化器忽略）

-- 通过 information_schema 查看
SELECT INDEX_NAME, IS_VISIBLE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'mydb' AND TABLE_NAME = 'orders';
-- IS_VISIBLE: YES / NO
```

## 不可见索引的典型使用流程

```
场景：评估是否可以删除某个"可能没用"的索引

步骤1：识别候选索引（通过 performance_schema 查找长期未使用的索引）
  SELECT OBJECT_NAME, INDEX_NAME
  FROM performance_schema.table_io_waits_summary_by_index_usage
  WHERE OBJECT_SCHEMA = 'mydb'
    AND OBJECT_NAME = 'orders'
    AND INDEX_NAME IS NOT NULL
    AND COUNT_STAR = 0        -- 自服务器启动从未被使用
  ORDER BY OBJECT_NAME;

步骤2：将候选索引设为不可见
  ALTER TABLE orders ALTER INDEX idx_user INVISIBLE;

步骤3：观察一段时间（如 1~2 天高峰期）
  - 监控慢查询日志是否出现新的慢查询
  - 监控查询响应时间是否异常
  - 观察 EXPLAIN 输出中是否有查询因缺少索引而退化

步骤4a：没有问题 → 真正删除索引
  ALTER TABLE orders DROP INDEX idx_user;

步骤4b：出现问题 → 立即恢复
  ALTER TABLE orders ALTER INDEX idx_user VISIBLE;
  （立即生效，比重新建索引快得多，对业务影响小）
```

## 不可见索引的索引维护特性

```sql
-- 不可见索引仍然被 InnoDB 维护！
-- INSERT/UPDATE/DELETE 时，不可见索引照常更新

-- 验证：
INSERT INTO orders (user_id, status, amount) VALUES (100, 1, 99.99);
-- idx_user（INVISIBLE）仍然被更新（内部 B+树正常维护）
-- 写操作的代价与可见索引相同

-- 因此，不可见索引不是为了"减少写入开销"设计的
-- 而是为了"安全评估是否可以删除索引"设计的

-- 验证优化器不使用不可见索引：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- 如果 idx_user 是 INVISIBLE：
-- key: NULL（优化器不使用）→ 全表扫描或用其他索引

-- 强制使用不可见索引（特殊调试场景，Session 级别）：
SET SESSION optimizer_switch = 'use_invisible_indexes=on';
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- 此时即使 idx_user 是 INVISIBLE，优化器也会使用
-- 用于验证"如果这个索引可见，查询计划会是什么"
-- 调试完记得恢复：
SET SESSION optimizer_switch = 'use_invisible_indexes=off';
```

## 不可见索引 vs 删除索引

| 对比维度 | 不可见索引 | 直接删除索引 |
|---------|:---------:|:----------:|
| 优化器使用 | 不使用 | 不使用 |
| 索引维护 | 继续维护（写入开销不变）| 不再维护（写入开销降低）|
| 恢复速度 | 立即（ALTER ... VISIBLE，毫秒级）| 慢（需要重建索引，大表需很长时间）|
| 使用目的 | 安全评估（临时不可见，随时可恢复）| 最终删除（确认不需要）|
| 存储空间 | 不释放（索引仍占用磁盘）| 释放 |

## 不可见索引与主键

```sql
-- 主键（PRIMARY KEY）不能设为不可见
-- 主键是聚簇索引，是表数据的存储结构，必须始终可见

ALTER TABLE orders ALTER INDEX PRIMARY INVISIBLE;
-- ERROR 3522: A primary key index cannot be invisible.

-- 非主键索引（包括唯一索引）都可以设为不可见
ALTER TABLE orders ALTER INDEX idx_status INVISIBLE;  -- 普通索引 ✓
-- 唯一索引也可以设为不可见，但要注意：
-- 不可见的唯一索引仍然执行唯一性约束（INSERT 仍然检查唯一性！）
```

## 适用场景

- **索引清理前的安全评估**：数据库长期运行后可能积累了一些不再被使用的索引（如历史版本代码的查询索引），在删除前先设为不可见，观察业务影响，是删除冗余索引的最安全做法
- **新索引的影子测试（逆向使用）**：也可以先建一个不可见索引，然后通过 `SET SESSION optimizer_switch = 'use_invisible_indexes=on'` 在不影响线上业务的情况下，测试新索引对特定查询的优化效果，确认有效后再将其设为可见

## 常见问题

**不可见索引设置后多久生效？**

立即生效。`ALTER TABLE ... ALTER INDEX ... INVISIBLE` 是元数据操作（修改索引的可见性标志），不需要重建索引，执行时间非常短（毫秒级，持有短暂的 MDL 写锁）。执行后，下一条查询就会发现该索引不可见，优化器不再考虑该索引。恢复可见（`VISIBLE`）同样立即生效。这与删除索引（需要 DDL 操作重组 B+树）和重建索引（大表可能需要数十分钟）相比，可见性切换的代价可以忽略不计。

## 注意事项

- 不可见索引的维护开销与可见索引相同（写入时仍然维护 B+树）。如果确认某个索引是冗余的（通过不可见状态验证后业务完全正常），应尽快执行 `ALTER TABLE ... DROP INDEX` 真正删除，释放存储空间并降低写入开销，而不是长期保持不可见状态。
- 不可见索引在 MySQL 8.0.0 及以上版本支持，如果系统中有 MySQL 5.x 版本的复制从库，`ALTER INDEX ... INVISIBLE` 语句同步到从库时可能出现兼容性问题（MySQL 5.x 不支持此语法）。主从复制升级时需要注意版本兼容性。

## 总结

不可见索引（Invisible Index）是 MySQL 8.0 引入的索引管理功能，通过 `ALTER TABLE t ALTER INDEX idx INVISIBLE/VISIBLE` 控制索引对优化器的可见性。不可见索引：优化器不使用（查询计划中忽略）、InnoDB 继续维护（写入代价不变）、可立即恢复（毫秒级切换，无需重建）。核心用途：删除冗余索引前的安全验证——先设为不可见，观察业务影响，确认安全后再真正删除；出现问题则立即恢复可见性。主键不能设为不可见。通过 `optimizer_switch = 'use_invisible_indexes=on'` 可在 Session 级别临时使用不可见索引（调试用途）。

# id 列与执行顺序

EXPLAIN 输出中的 `id` 列标识了查询中每个 SELECT 操作的序号，是理解多步骤查询（子查询、JOIN、UNION 等）执行顺序的关键。`id` 值的大小决定了执行的先后关系：相同 id 的行从上往下执行；不同 id 中，id 值越大的行越先执行（内层子查询先于外层）；`NULL` 的 id 表示该行是两个查询结果的合并结果集（UNION 结果的临时表）。

---

## id 值的含义规则

```
规则1：id 相同 → 从上往下顺序执行（同一级查询中的多表 JOIN）
规则2：id 不同 → id 值越大越先执行（子查询先于外层查询）
规则3：id 为 NULL → UNION 的结果集合并行（UNION RESULT）

实际执行顺序判断：
  先执行 id 最大的行
  id 相同时，从上到下
  id 为 NULL 的行（UNION RESULT）最后处理
```

---

## 情形1：简单查询（id 全部为 1）

```sql
-- 单表查询
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- id: 1, select_type: SIMPLE, table: orders

-- 多表 JOIN（同一级，id 相同）
EXPLAIN SELECT o.id, o.amount, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 \G

-- 输出：
-- id: 1, select_type: SIMPLE, table: u (驱动表，先执行)
-- id: 1, select_type: SIMPLE, table: o (被驱动表，后执行)
-- id 都是 1，从上到下：先扫描 u，再用 u 的结果驱动 o 的扫描

-- 三表 JOIN
EXPLAIN SELECT o.id, u.name, p.name AS product
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
WHERE o.status = 1 \G
-- id: 1 (三行都是 1)，从上到下：优化器选择的 JOIN 顺序
```

## 情形2：子查询（id 不同，大 id 先执行）

```sql
-- IN 子查询
EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active') \G

-- 可能输出（取决于优化器是否做子查询展开/半连接优化）：
-- id: 1, select_type: PRIMARY, table: orders
-- id: 2, select_type: SUBQUERY, table: users
-- 执行顺序：id=2（users 子查询）先执行，id=1（外层 orders）后执行

-- 相关子查询（DEPENDENT SUBQUERY）
EXPLAIN SELECT *
FROM orders o
WHERE o.amount > (SELECT AVG(amount) FROM orders WHERE user_id = o.user_id) \G
-- id: 1, select_type: PRIMARY, table: o
-- id: 2, select_type: DEPENDENT SUBQUERY, table: orders
-- 相关子查询对外层每行都要重新执行，性能较差
-- 通常应改写为 JOIN 或 WITH 子句
```

## 情形3：UNION 查询（id 混合 + NULL）

```sql
EXPLAIN
SELECT id, user_id FROM orders WHERE status = 1
UNION
SELECT id, user_id FROM orders WHERE status = 2 \G

-- 输出：
-- id: 1, select_type: PRIMARY, table: orders          ← 第一个 SELECT
-- id: 2, select_type: UNION,   table: orders          ← 第二个 SELECT
-- id: NULL, select_type: UNION RESULT, table: <union1,2>  ← 合并去重

-- 执行顺序：
-- id=1：执行第一个 SELECT（status=1）
-- id=2：执行第二个 SELECT（status=2）
-- id=NULL：将 id=1 和 id=2 的结果合并并去重（使用临时表）

-- UNION ALL（不去重，无 UNION RESULT 行）
EXPLAIN
SELECT id FROM orders WHERE status = 1
UNION ALL
SELECT id FROM orders WHERE status = 2 \G
-- 只有 id=1 和 id=2，无 id=NULL 的 UNION RESULT 行
-- 因为 UNION ALL 不需要去重，不需要临时表合并
```

## 情形4：派生表（DERIVED）

```sql
EXPLAIN SELECT t.user_id, t.cnt
FROM (
    SELECT user_id, COUNT(*) AS cnt
    FROM orders WHERE status = 1
    GROUP BY user_id
) AS t
WHERE t.cnt > 5 \G

-- 输出：
-- id: 1, select_type: PRIMARY, table: t      ← 外层查询访问派生表 t
-- id: 2, select_type: DERIVED, table: orders ← 派生表（子查询）

-- 执行顺序：id=2（派生表 orders 聚合）先执行，id=1（外层过滤）后执行

-- MySQL 8.0+ 派生表合并优化（Derived Merge）：
-- 如果优化器能合并派生表，EXPLAIN 中可能不出现 DERIVED 行
-- 而是直接将派生表的查询合并到外层（只有一行）
```

## 情形5：CTE（WITH 子句，MySQL 8.0+）

```sql
EXPLAIN WITH recent_orders AS (
    SELECT user_id, SUM(amount) AS total
    FROM orders
    WHERE created_at >= '2025-01-01'
    GROUP BY user_id
)
SELECT u.name, r.total
FROM users u
JOIN recent_orders r ON u.id = r.user_id
WHERE r.total > 1000 \G

-- 输出：
-- id: 1, select_type: PRIMARY, table: u
-- id: 1, select_type: PRIMARY, table: r (<derived2>)
-- id: 2, select_type: DERIVED, table: orders  ← CTE recent_orders 的物化
-- 或（如果 CTE 被合并）：
-- id: 1, select_type: PRIMARY（所有行合并，无 DERIVED 行）
```

## 通过 id 分析复杂查询执行顺序

```sql
-- 复杂示例：嵌套子查询 + JOIN
EXPLAIN
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.id IN (
    SELECT order_id FROM order_items
    WHERE product_id IN (
        SELECT id FROM products WHERE category_id = 5
    )
) \G

-- 可能输出（未优化）：
-- id: 1, PRIMARY, table: u
-- id: 1, PRIMARY, table: o
-- id: 2, DEPENDENT SUBQUERY, table: order_items
-- id: 3, DEPENDENT SUBQUERY, table: products

-- 执行顺序：
-- id=3（最大，先执行）：扫描 products WHERE category_id=5
-- id=2：扫描 order_items WHERE product_id IN (products 结果)
-- id=1：JOIN users 和 orders，过滤 o.id IN (order_items 结果)

-- 优化建议：将嵌套子查询改写为 JOIN 链式查询：
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE p.category_id = 5;
-- 全部 id=1，JOIN 方式通常优于嵌套子查询
```

## 适用场景

- **复杂查询性能诊断**：当 EXPLAIN 输出有多行时，通过 id 值判断执行顺序，识别哪个步骤的 rows 最大、type 最差（ALL），优先优化影响最大的步骤
- **子查询改写验证**：将子查询改写为 JOIN 后，通过 EXPLAIN 确认 id 列的变化（从多个不同 id 变为全部 id=1），验证优化是否生效

## 常见问题

**同一个查询，EXPLAIN 有时出现 id 不同（子查询），有时又变成 id 相同（被优化器合并），这是怎么回事？**

MySQL 查询优化器会对子查询进行改写（如将 IN 子查询转换为半连接 Semi-join，将 EXISTS 转换为 Anti-join），这些改写可能将原本的子查询合并入主查询的 JOIN 处理流程，使得原本 id 不同的步骤变为 id 相同。这是优化器的正常行为，通常表示优化后的执行计划更高效（避免了重复执行子查询的开销）。如果优化器没有合并，可以通过调整 `optimizer_switch` 中的 `semijoin=on` 等开关，或者手动将子查询改写为 JOIN 来触发合并。

---

## 注意事项

- `id` 相同的行的执行顺序（从上到下）反映了优化器的 JOIN 顺序决策，而不是 SQL 语句中表的书写顺序。MySQL 优化器会根据成本评估自动调整 JOIN 顺序。如果实际 JOIN 顺序与期望不符，可以通过 `STRAIGHT_JOIN` 或 Optimizer Hint（`LEADING`）指定 JOIN 顺序。
- 对于含有 `UNION` 的查询，id=NULL 的 `UNION RESULT` 行表示需要将多个子结果集合并并去重，这里使用了临时表（`Extra: Using temporary`）。如果不需要去重，改用 `UNION ALL` 可以消除这个临时表，提升性能。

---

## 总结

EXPLAIN 的 `id` 列标识查询步骤的执行顺序：同 id 从上到下；不同 id 中大值先执行（子查询先于外层）；id=NULL 是 UNION 结果集合并行（最后处理）。通过 id 分析多步骤查询：识别子查询的嵌套深度、JOIN 的驱动顺序、派生表的物化位置、CTE 的使用方式。实践意义：id 越多、嵌套越深，查询复杂度越高；尽量将子查询改写为 JOIN（id 全部为 1），减少执行步骤；UNION 改 UNION ALL 消除 id=NULL 的临时表合并步骤。

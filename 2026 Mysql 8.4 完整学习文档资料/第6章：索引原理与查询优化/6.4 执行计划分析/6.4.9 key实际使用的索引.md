# key 实际使用的索引

EXPLAIN 输出的 `key` 列显示 MySQL 查询优化器最终选择使用的索引名称。与 `possible_keys`（候选集）不同，`key` 是优化器从候选索引中通过成本比较后的最终决策。`key` 为 `NULL` 表示不使用任何索引（全表扫描）；`key` 为 `PRIMARY` 表示使用了聚簇索引（主键）；`key` 显示索引名称时，结合 `key_len` 可以判断联合索引实际用了几列。

---

## key 的基本读法

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id),
    INDEX idx_user_status (user_id, status),
    INDEX idx_amount (amount)
);

-- 使用主键：
EXPLAIN SELECT * FROM orders WHERE id = 1001 \G
-- key: PRIMARY  ← 聚簇索引

-- 使用二级索引：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- key: idx_user_status  ← 联合索引

-- 无索引（全表扫描）：
EXPLAIN SELECT * FROM orders WHERE amount > 500 \G
-- (假设 amount 无索引)
-- key: NULL  ← 不使用任何索引

-- key 与 possible_keys 的关系：
-- key 必然是 possible_keys 的子集（或 NULL）
-- key 是从 possible_keys 中通过成本模型选出的最优索引
```

---

## key 与 possible_keys 不一致的情况

```sql
-- 情况1：possible_keys 有多个，key 只选了一个
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- possible_keys: idx_user, idx_user_status
-- key: idx_user_status  ← 优化器选了联合索引（更高效）

-- 情况2：possible_keys 有值，key 为 NULL
EXPLAIN SELECT * FROM orders WHERE status = 1 \G
-- (假设 status 只有 3 个值，匹配 80% 的行)
-- possible_keys: idx_user_status（或 idx_status）
-- key: NULL  ← 优化器认为全表扫描比索引+回表更快

-- 情况3：key 中的索引不在 possible_keys 中
-- 这种情况比较少见，通常出现在 ORDER BY 触发的索引覆盖扫描时
-- ORDER BY 利用索引排序的索引可能不在 WHERE 的 possible_keys 中出现
EXPLAIN SELECT user_id FROM orders ORDER BY user_id LIMIT 10 \G
-- possible_keys: NULL（无 WHERE 条件）
-- key: idx_user  ← 用于 ORDER BY 的覆盖索引扫描
```

---

## 强制指定索引（干预 key 的选择）

```sql
-- USE INDEX：建议优化器优先考虑指定索引（不强制）
EXPLAIN SELECT * FROM orders USE INDEX (idx_user) WHERE user_id = 100 \G
-- key: idx_user（通常会遵从建议）

-- FORCE INDEX：强制使用指定索引（优化器必须使用）
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_user_status) WHERE user_id = 100 \G
-- key: idx_user_status  ← 强制使用，即使优化器认为不是最优

-- IGNORE INDEX：排除指定索引（优化器不考虑它）
EXPLAIN SELECT * FROM orders IGNORE INDEX (idx_user) WHERE user_id = 100 \G
-- possible_keys: idx_user_status（idx_user 被排除）
-- key: idx_user_status

-- 使用场景：
-- USE INDEX：引导优化器，适合统计信息不准时
-- FORCE INDEX：强制，适合确认某索引更优但优化器误判时
-- IGNORE INDEX：排除问题索引（如 Index Merge 不需要的索引）

-- Optimizer Hint（MySQL 8.0+ 推荐方式，比 USE/FORCE INDEX 更灵活）：
EXPLAIN SELECT /*+ INDEX(orders idx_user_status) */ *
FROM orders WHERE user_id = 100 \G
```

## key 为 NULL 时的处理策略

```sql
-- key = NULL + possible_keys = NULL → 没有候选索引
-- 解决：为 WHERE 条件列建索引

-- key = NULL + possible_keys 有值 → 优化器放弃了所有候选索引
-- 可能原因：
--   1. 索引选择性低（匹配行数 > 总行数 30% 左右）
--   2. 统计信息过时（运行 ANALYZE TABLE 更新）
--   3. 优化器 Bug 或特殊情况

-- 验证步骤：
-- 1. 检查 Cardinality（选择性）
SHOW INDEX FROM orders \G
-- Cardinality 很小 → 选择性低，优化器正确放弃索引

-- 2. 强制使用索引对比性能
-- a. 不使用索引（优化器选 ALL）：
EXPLAIN SELECT * FROM orders WHERE status = 1 \G

-- b. 强制使用索引：
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_status) WHERE status = 1 \G

-- 3. 实际执行两个查询，对比时间
-- 如果强制索引反而更慢 → 优化器判断正确，key=NULL 是合理的
-- 如果强制索引更快 → 统计信息有问题，ANALYZE TABLE 后重试
```

## key 在 Index Merge 场景下的显示

```sql
-- Index Merge 时，key 列显示多个索引（逗号分隔）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 1 \G
-- key: idx_user,idx_status  ← 两个索引合并
-- type: index_merge
-- Extra: Using union(idx_user,idx_status); Using where
```

## 适用场景

- **确认索引优化效果**：添加新索引后通过 EXPLAIN 查看 `key` 是否变为新索引（从 NULL 变为有值，或从 ALL 型索引变为更高效的索引），验证优化是否达到预期
- **排查索引选择错误**：当 `key` 不是预期的索引时（如优化器选了一个选择性较低的索引而不是联合索引），通过 `FORCE INDEX` 测试正确索引的效果，必要时用 Optimizer Hint 固定索引选择

---

## 常见问题

**key 显示的索引和 SQL 中 `USE INDEX` 指定的不同，是为什么？**

`USE INDEX` 是建议性质，不是强制。优化器会优先考虑 `USE INDEX` 列出的索引，但如果成本模型判断这些索引都比全表扫描差（如匹配行数太多），仍然可能选择不使用指定索引（key=NULL）。如果需要强制使用某个索引，应使用 `FORCE INDEX`。在 MySQL 8.0+ 中，推荐使用 Optimizer Hint（`/*+ INDEX(t idx_name) */`）替代 `FORCE INDEX`，语义更清晰且支持子查询、CTE 等复杂场景。

---

## 注意事项

- `key` 显示的索引名是创建索引时指定的名称。主键索引的名称固定为 `PRIMARY`（无论建表时如何指定主键）。如果在创建索引时没有显式命名，MySQL 自动使用第一个索引列的名称作为索引名。
- 在 MySQL 8.0+ 中，通过 `SHOW INDEX FROM table` 查看的 `Index_name` 与 `key` 列的值完全对应。如果发现 `key` 列显示的索引名与预期不符，通过 `SHOW INDEX` 确认实际的索引名称，避免因索引名变化（如 ALTER TABLE 重命名索引）导致的混淆。

---

## 总结

`key` 列显示优化器最终选择的索引（从 `possible_keys` 候选集中择优）。`key = NULL`：无索引可用（全表扫描）或优化器主动放弃候选索引（选择性低时）。`key = PRIMARY`：使用聚簇索引（主键）。Index Merge 时显示多个索引名（逗号分隔）。当 `key` 不符合预期时：用 `FORCE INDEX` 测试预期索引的效果，对比实际执行时间；确认是优化器误判还是正确决策；通过 `ANALYZE TABLE` 更新统计信息后重新验证。MySQL 8.0+ 推荐用 Optimizer Hint 替代 `FORCE INDEX` 干预索引选择。

# rows 估算扫描行数

EXPLAIN 输出的 `rows` 列是 MySQL 查询优化器对当前步骤需要扫描的行数的估算值，不是精确的实际行数。优化器基于表的统计信息（InnoDB 通过随机采样生成，存储在 `mysql.innodb_index_stats` 和 `mysql.innodb_table_stats` 中）来估算这个值。`rows` 是优化器成本模型的输入之一——`rows` 越大，优化器认为该操作代价越高。多行 EXPLAIN 输出中，每行的 `rows` 值相乘可以粗略估算整个查询需要处理的总行数。

---

## rows 的基本读法

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id),
    INDEX idx_status (status)
);

-- 单表查询的 rows：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- rows: 25  ← 估算 user_id=100 的约有 25 行

EXPLAIN SELECT * FROM orders WHERE status = 1 \G
-- rows: 500000  ← status=1 约有 50 万行（选择性低）

EXPLAIN SELECT * FROM orders \G
-- type: ALL, rows: 1000000  ← 全表估算 100 万行

-- rows 是估算值，有时偏差较大：
-- 实际 user_id=100 有 20 行，估算 25 → 可以接受
-- 实际 user_id=100 有 1 行，估算 25 → 偏差较大（InnoDB 统计采样不精确）
```

---

## 多表 JOIN 的 rows 含义

```sql
-- JOIN 查询中，每行的 rows 是该步骤估算扫描的行数
-- 总代价 ≈ 各行 rows 的乘积（Nested Loop Join 的递推代价）

EXPLAIN SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 \G

-- 可能输出：
-- table: o, type: ref, rows: 500000  ← 扫描 status=1 的约 50 万行
-- table: u, type: eq_ref, rows: 1    ← 每行 orders 对应最多 1 行 users

-- 总处理行数估算：500000 × 1 = 500000 行
-- rows 乘积越小，JOIN 代价越低
```

---

## rows 与 filtered 结合估算实际处理行数

```sql
-- 单独的 rows 是"扫描行数"，不是"最终结果行数"
-- 结合 filtered（过滤比例）可以估算传递给下一步的实际行数：
-- 实际处理行数 ≈ rows × filtered / 100

EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- type: ref, key: idx_user, rows: 25, filtered: 40.00
-- 估算：idx_user 先找到 25 行，其中 40% (10 行) 满足 amount > 500 条件
-- 实际传递给 Server 层的行数约 10 行
```

## rows 不准确的原因与修复

```sql
-- InnoDB 的统计信息基于随机采样，采样页数由 innodb_stats_sample_pages 控制
SHOW VARIABLES LIKE 'innodb_stats_sample_pages';
-- 默认: 8（采样 8 个数据页来估算统计信息）
-- 采样页数越少，估算越不精确

-- 导致 rows 不准确的情况：
-- 1. 大量 INSERT/DELETE/UPDATE 后统计信息未更新
-- 2. innodb_stats_sample_pages 过小（大表估算偏差大）
-- 3. 数据分布极不均匀（某些值集中，采样未覆盖到）

-- 手动更新统计信息：
ANALYZE TABLE orders;
-- 触发重新采样，更新 innodb_table_stats 和 innodb_index_stats

-- 提高采样精度（影响 ANALYZE TABLE 的耗时和精度）：
SET SESSION innodb_stats_transient_sample_pages = 40;  -- 临时调高采样页数
ANALYZE TABLE orders;
SET SESSION innodb_stats_transient_sample_pages = 8;   -- 恢复默认

-- 对于统计信息持久化配置（全局）：
SET GLOBAL innodb_stats_persistent_sample_pages = 20;
-- innodb_stats_persistent=ON（默认）时生效，统计信息持久化到 mysql 表中
```

## rows 与执行计划的成本决策

```sql
-- rows 直接影响优化器的成本估算和索引选择

-- 场景：有两个可用索引，rows 估算影响选择哪个
-- idx_user(user_id)：估算 rows=25
-- idx_amount(amount)：估算 rows=300

-- 其他条件相同时，优化器选 idx_user（rows 更小，代价更低）
-- 如果 idx_user 的 rows 统计不准（实际 1000 行，估算只有 25），
-- 优化器可能错误选择 idx_user → 需要 ANALYZE TABLE 修复

-- 验证统计信息准确性：
-- 通过 EXPLAIN ANALYZE（MySQL 8.0.18+）对比估算 rows 和实际 rows
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100 \G
-- 输出包含：rows=25 (actual rows=1000)
-- 偏差很大 → 需要 ANALYZE TABLE 更新统计

-- 也可以直接查询准确行数（精确但有代价）：
SELECT COUNT(*) FROM orders WHERE user_id = 100;
-- 与 EXPLAIN rows 对比，评估估算准确度
```

## rows 为 1 的特殊情况

```sql
-- type: const 或 eq_ref 时，rows 通常为 1
-- 这是最优的情况（精确定位单行）

EXPLAIN SELECT * FROM orders WHERE id = 1001 \G
-- type: const, rows: 1  ← 主键等值，唯一一行

-- type: ref_or_null 时，rows 会稍大（考虑了 NULL 值行）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR user_id IS NULL \G
-- type: ref_or_null, rows: 26  ← 25(等值) + 1(NULL检查)
```

## 适用场景

- **JOIN 优化**：在多表 JOIN 的 EXPLAIN 中，通过各行 rows 的乘积估算 Nested Loop 的总循环次数，识别哪个 JOIN 步骤代价最高（rows 最大），优先为该步骤建立更好的索引以降低行数
- **统计信息健康检查**：定期对比 EXPLAIN 的 rows 估算值与 `SELECT COUNT(*)` 的精确值，偏差超过 2~3 倍时执行 `ANALYZE TABLE` 更新统计信息

## 常见问题

**EXPLAIN 的 rows 显示 1，但实际执行扫描了几千行，这是怎么回事？**

这是统计信息严重不准确的表现。常见于：表刚删除了大量数据（统计信息未更新）、表数据增长很快但统计信息更新不及时（`innodb_stats_auto_recalc=ON` 默认会在 10% 数据变更后自动更新，但有延迟）、或采样时碰巧采到了稀疏区域。解决方法：执行 `ANALYZE TABLE` 强制更新统计信息，然后重新 EXPLAIN 检查 rows 值。对于极重要的核心表，可以定期在业务低峰期执行 `ANALYZE TABLE`。

---

## 注意事项

- `rows` 是统计估算值，在数据分布极不均匀时（如某个 user_id 有百万行，其他 user_id 只有几行），估算偏差可能非常大。InnoDB 默认的采样页数（8 页）对于小表已经足够，但对于大表（亿级行）可能偏差较大。适当增大 `innodb_stats_persistent_sample_pages`（如调为 20~50）可以提高精度，但会增加 `ANALYZE TABLE` 的执行时间。
- `rows` 的估算值对 `SELECT COUNT(*)` 不适用——`COUNT(*)` 不走 rows 估算，InnoDB 会扫描二级索引（或直接用元数据）计算精确结果。`EXPLAIN SELECT COUNT(*)` 的 rows 值是查询优化的成本估算输入，不是 COUNT 的最终结果。

---

## 总结

`rows` 是优化器估算当前步骤需要扫描的行数，基于 InnoDB 的统计信息（随机采样）生成，是估算值而非精确值。`rows` 直接影响优化器的成本决策（选哪个索引、用什么 JOIN 顺序）。多表 JOIN 中总代价 ≈ 各步骤 rows 的乘积。结合 `filtered` 列（`rows × filtered/100`）估算传递到下一步的实际行数。统计信息过时时 rows 偏差大，通过 `ANALYZE TABLE` 更新；通过 `EXPLAIN ANALYZE` 对比估算 rows 与实际 rows 的偏差量。

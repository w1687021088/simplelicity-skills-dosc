# table 列与表名

EXPLAIN 输出的 `table` 列显示当前行对应的是哪张表的访问操作。在简单查询中，`table` 就是 SQL 中出现的表名或别名；在含有子查询、派生表、UNION 的复杂查询中，`table` 会出现特殊的格式，如 `<derivedN>`（派生表）、`<subqueryN>`（物化子查询）、`<unionM,N>`（UNION 结果集），这些特殊格式直接反映了查询执行结构中的中间结果集。

---

## table 列的基本情况

```sql
-- 简单查询：table = 表名
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- table: orders

-- 使用别名：table = 别名
EXPLAIN SELECT o.id FROM orders o WHERE o.user_id = 100 \G
-- table: o（别名，不是 orders）

-- 多表 JOIN：每个表一行
EXPLAIN SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 \G
-- table: u
-- table: o
```

---

## 特殊格式：`<derivedN>`

```sql
-- 派生表（FROM 子句中的子查询）显示为 <derivedN>
-- N 是对应子查询的 id

EXPLAIN SELECT t.user_id, t.total
FROM (
    SELECT user_id, SUM(amount) AS total
    FROM orders GROUP BY user_id
) AS t
WHERE t.total > 500 \G

-- 输出：
-- id: 1, table: t (<derived2>)   ← 外层查询访问派生表，<derived2> 表示 id=2 的子查询
-- id: 2, table: orders            ← id=2 的子查询是对 orders 表的聚合

-- <derivedN> 意味着 N 号查询的结果被物化为一个临时表
-- 如果 optimizer_switch 中 derived_merge=on（MySQL 8.0 默认），
-- 简单的派生表会被合并，不会出现 <derivedN>
```

---

## 特殊格式：`<subqueryN>`

```sql
-- 物化子查询（MATERIALIZED）显示为 <subqueryN>
-- MySQL 对某些 IN 子查询做物化优化：先执行子查询并生成临时哈希表

EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'CN') \G

-- 可能输出（优化器做物化时）：
-- id: 1, table: orders,   select_type: PRIMARY
-- id: 1, table: <subquery2>, select_type: PRIMARY  ← 与 orders 做 JOIN
-- id: 2, table: users,    select_type: MATERIALIZED  ← 子查询物化

-- <subquery2> 表示 id=2 的子查询的物化结果（哈希表），直接与外层 JOIN
-- 比逐行执行子查询更高效（子查询只执行一次）
```

---

## 特殊格式：`<unionM,N>` 和 UNION RESULT

```sql
EXPLAIN
SELECT id, amount FROM orders WHERE status = 1
UNION
SELECT id, amount FROM orders WHERE status = 2 \G

-- 输出：
-- id: 1, select_type: PRIMARY, table: orders      ← 第一个 SELECT
-- id: 2, select_type: UNION,   table: orders      ← 第二个 SELECT
-- id: NULL, select_type: UNION RESULT, table: <union1,2>  ← 合并 id=1 和 id=2 的结果

-- <union1,2> 表示合并了 id=1 和 id=2 的两个结果集
-- 如果有三个 UNION：<union1,2,3>
-- UNION RESULT 行的 table 列始终是 <unionM,N,...> 格式
```

---

## table 列与分析思路

```
通过 table 列识别查询结构：

1. 所有行都是普通表名/别名 → 简单 JOIN 查询（SIMPLE）

2. 出现 <derivedN> → 有物化的派生表（FROM 子句子查询）
   → 检查是否可以通过 Derived Merge 优化消除派生表

3. 出现 <subqueryN> → 有物化的 IN 子查询（MATERIALIZED）
   → 通常是好的优化，子查询只执行一次

4. 出现 <unionM,N> → 有 UNION 合并操作
   → 评估是否可以改为 UNION ALL 消除去重开销

5. 出现 NULL 的 id 行 → UNION RESULT 合并行
   → 消耗内存/临时表空间做去重排序
```

## 适用场景

- **解读复杂查询的执行层次**：在含有多层子查询、CTE、UNION 的 EXPLAIN 输出中，通过 `table` 列的 `<derivedN>`、`<subqueryN>` 等特殊格式，对应到具体的子查询 id，理解整个执行计划的层次结构
- **派生表优化验证**：关注 `<derivedN>` 是否出现——如果 MySQL 8.0 的 Derived Merge 生效，派生表会被合并，EXPLAIN 中不再出现 `<derivedN>`，可以通过这个现象确认优化是否生效

## 常见问题

**EXPLAIN 中 `table: <derived2>` 和 `table: t` 同时出现于 id=1 的两行，是什么意思？**

这通常出现在外层查询访问一个别名为 `t` 的派生表时，MySQL 的 EXPLAIN 会同时显示别名（`t`）和内部标识（`<derived2>`）。有时只显示别名，有时显示 `<derived2>`，取决于 MySQL 版本和查询的物化方式。本质上都是指"id=2 的子查询的物化结果集"被外层查询以 `t` 的名称访问。查看 `id=2` 对应的行，就能找到派生表实际的查询内容（操作哪张物理表、使用哪些条件）。

---

## 注意事项

- 当 `table` 列显示为表别名时，说明 SQL 中对该表使用了别名（如 `FROM orders o`），EXPLAIN 使用别名而不是原表名。这在有多个同名表（自连接）时特别重要，可以通过别名区分两次访问同一张表的不同逻辑角色（如 `t1` 和 `t2`）。
- `<derivedN>` 格式中的 N 对应的是 EXPLAIN 输出中 `id=N` 的那一行，通过 id 可以追溯到派生表的具体查询内容。当有多层嵌套派生表时（`<derived2>` 里又包含 `<derived3>`），需要层层追溯才能完整理解查询结构。

---

## 总结

EXPLAIN 的 `table` 列显示当前操作的表：普通查询显示表名或别名；`<derivedN>` 表示 id=N 的子查询物化的派生表；`<subqueryN>` 表示 id=N 的 IN 子查询的物化结果（哈希临时表）；`<unionM,N>` 表示 UNION RESULT 中合并了 id=M 和 id=N 的结果集。通过 `table` 列的特殊格式，可以快速理解查询中有哪些中间结果集，以及它们对应的是哪个子查询（通过 id 关联）。派生表（`<derivedN>`）的存在意味着物化开销，MySQL 8.0 的 Derived Merge 会在可能时消除这些物化。

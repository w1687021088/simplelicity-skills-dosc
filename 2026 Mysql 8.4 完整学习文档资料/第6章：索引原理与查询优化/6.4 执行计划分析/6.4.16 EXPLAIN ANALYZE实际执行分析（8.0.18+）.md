# EXPLAIN ANALYZE 实际执行分析（8.0.18+）

`EXPLAIN ANALYZE` 是 MySQL 8.0.18 引入的执行分析工具，它不只是预测执行计划（像普通 EXPLAIN 那样），而是**真正执行 SQL 并在执行过程中收集真实统计数据**，最后以 TREE 格式输出，同时包含优化器的估算值（cost、rows）和实际执行值（actual time、actual rows、loops）。通过对比估算值和实际值，可以准确发现统计信息偏差、识别执行计划中最耗时的步骤，是 MySQL 8.0+ 环境下最强大的查询分析工具。

---

## 基本语法与输出格式

```sql
-- 基本用法
EXPLAIN ANALYZE SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.created_at LIMIT 20 \G

-- 输出格式（TREE 格式，带真实统计）：
-- -> Limit: 20 row(s)  (cost=62345.67 rows=20) (actual time=45.123..45.456 rows=20 loops=1)
--    -> Sort: o.created_at  (cost=62345.67 rows=500000) (actual time=45.100..45.200 rows=20 loops=1)
--       -> Nested loop inner join  (cost=12345.67 rows=500000) (actual time=0.015..40.123 rows=500000 loops=1)
--          -> Index lookup on o using idx_status (status=1)  (cost=2345.67 rows=500000)
--             (actual time=0.012..20.456 rows=500000 loops=1)
--          -> Single-row index lookup on u using PRIMARY (id=o.user_id)  (cost=0.1 rows=1)
--             (actual time=0.000..0.001 rows=1 loops=500000)

-- 输出字段解读：
-- cost=X rows=Y    → 优化器估算值
-- actual time=A..B → 实际执行时间（毫秒）：A=第一行的时间，B=最后一行的时间
-- actual rows=Z    → 实际返回的行数
-- loops=N          → 该步骤被执行了 N 次（JOIN 循环次数）
```

## 对比估算值与实际值

```sql
-- 通过对比 rows 估算 vs actual rows，判断统计信息准确性
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100 \G

-- 输出示例：
-- -> Index lookup on orders using idx_user (user_id=100)  
--    (cost=2.51 rows=25) (actual time=0.018..0.045 rows=1 loops=1)

-- 分析：
-- rows=25（估算）vs actual rows=1（实际）→ 估算偏差 25 倍！
-- 说明统计信息不准确（user_id=100 只有 1 行，但统计估算 25 行）
-- 解决：ANALYZE TABLE orders; 更新统计信息

-- 理想情况（估算准确）：
-- (cost=2.51 rows=25) (actual time=0.018..0.045 rows=22 loops=1)
-- rows=25 vs actual rows=22 → 偏差不大，统计信息基本准确
```

## actual time 字段的两个值含义

```sql
-- actual time=A..B 表示两个时间点（从查询开始到当前步骤的累计时间）：
-- A：该步骤返回第一行的时间（毫秒）
-- B：该步骤返回最后一行的时间（毫秒，即步骤完成时间）

-- 示例解读：
-- -> Index lookup on orders using idx_user  
--    (actual time=0.018..20.456 rows=500000 loops=1)
-- time=0.018：找到第一行只需 0.018ms（索引快速定位）
-- time=20.456：扫描完所有 50 万行需要 20.456ms（总扫描时间）

-- -> Sort: orders.created_at  
--    (actual time=25.100..45.200 rows=20 loops=1)
-- time=25.100：排序开始（依赖前一步的完成，从 20ms 变到 25ms）
-- time=45.200：排序完成，返回 20 行（排序额外耗时约 20ms）
-- → 排序是主要的时间开销！

-- 通过各步骤的 actual time 差值，快速定位最耗时的操作
```

## loops 字段的含义

```sql
-- loops 表示该步骤被执行的次数（通常对应 Nested Loop JOIN 的循环）

EXPLAIN ANALYZE SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.user_id = 100 \G

-- 输出：
-- -> Nested loop inner join (actual time=0.01..5.23 rows=20 loops=1)
--    -> Index lookup on o using idx_user (user_id=100)
--       (actual time=0.01..0.05 rows=20 loops=1)   ← 执行 1 次
--    -> Single-row index lookup on u using PRIMARY (id=o.user_id)
--       (actual time=0.01..0.01 rows=1 loops=20)   ← 执行 20 次（每行 orders 一次）

-- u 的 loops=20，表示对 users 做了 20 次主键查找（每次 orders 的行对应一次）
-- loops × rows = total rows processed
-- 20 次 × 1 行 = 20 行（总处理行数）

-- actual time=0.01..0.01 loops=20 → 每次查找只需 0.01ms（主键等值，非常快）
-- actual time=0.01..5.00 loops=10000 → 每次平均 0.5ms（需要关注的慢循环）
```

## 识别执行计划中最耗时的步骤

```sql
-- 方法：看每步的 actual time B（最后一行时间），相邻步骤差值最大的是瓶颈

EXPLAIN ANALYZE
SELECT o.id, o.amount, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.created_at
LIMIT 20 \G

-- 假设输出时间线：
-- Limit: 20 rows              actual time=..150ms  ← 总耗时 150ms
--   Sort: created_at          actual time=..148ms  ← 排序占了大部分时间（100ms+）
--     Nested loop join        actual time=..40ms   ← JOIN 耗时 40ms
--       Index lookup o        actual time=..38ms   ← 扫描 orders 耗时 38ms（50万行！）
--       Single-row lookup u   actual time=..0.01ms ← users 主键查找极快

-- 时间分布：
-- Index lookup orders: 0 → 38ms（主要耗时1：扫描50万行）
-- Sort: 40ms → 148ms（主要耗时2：对50万行排序）
-- 优化方向：在 (status, created_at) 上建联合索引，消除 filesort
```

## EXPLAIN ANALYZE 的使用注意事项

```sql
-- 注意1：EXPLAIN ANALYZE 会真正执行 SQL！
-- 对于 SELECT → 无副作用（读操作）
-- 对于 UPDATE/DELETE → 数据会被真正修改！（生产环境谨慎）
-- MySQL 8.0.18+ 的 EXPLAIN ANALYZE 支持 INSERT/UPDATE/DELETE，
-- 但会触发真实数据修改，使用时务必在测试环境或用事务包裹

-- 安全的做法（用事务保护，分析后回滚）：
START TRANSACTION;
EXPLAIN ANALYZE DELETE FROM orders WHERE status = 0 AND created_at < '2023-01-01';
ROLLBACK;  -- 回滚，防止实际删除数据

-- 注意2：对于有 LIMIT 的查询，actual rows 是返回的行数，不是扫描的行数
-- 实际扫描行数需要看内层步骤的 actual rows

-- 注意3：EXPLAIN ANALYZE 的时间会因服务器负载、Buffer Pool 状态而变化
-- 同一查询多次执行的 actual time 可能有差异
-- 建议在低负载时执行，或多次执行取平均值
```

## EXPLAIN ANALYZE vs EXPLAIN 的选择

| 场景 | 推荐工具 |
|------|:-------:|
| 快速查看执行计划（不执行 SQL）| `EXPLAIN` |
| 需要成本估算详情 | `EXPLAIN FORMAT=JSON` |
| 验证估算与实际的偏差 | `EXPLAIN ANALYZE` |
| 找出查询中最耗时的步骤 | `EXPLAIN ANALYZE` |
| 生产环境分析正在运行的查询 | `EXPLAIN FOR CONNECTION` |
| 大表的 DML 分析（避免真实执行）| `EXPLAIN`（不用 ANALYZE）|

## 适用场景

- **统计信息准确性验证**：通过对比 `rows`（估算）和 `actual rows`（实际），识别统计信息严重偏差的表，决定是否需要 `ANALYZE TABLE` 更新统计信息
- **复杂查询的时间瓶颈定位**：对于多步骤的复杂查询（多表 JOIN、子查询、排序），通过各步骤的 `actual time` 差值，精确定位最耗时的操作，优先优化瓶颈步骤

## 常见问题

**`EXPLAIN ANALYZE` 的 actual time 为 0 是怎么回事？**

通常出现在以下情况：①查询结果来自 Buffer Pool（完全缓存），磁盘 I/O 为零，时间极短（< 0.001ms，显示为 0）；②使用了 `const` 类型的访问（主键等值），只需一次 B+树查找，速度极快；③`loops=0`，表示该步骤从未执行（如 OUTER JOIN 中被驱动表完全不匹配时）。如果在生产环境中看到高频 SELECT 的 actual time 接近 0，说明 Buffer Pool 命中率很高，查询效率很好。

---

## 注意事项

- `EXPLAIN ANALYZE` 在 MySQL 8.0.18 引入，仅支持 `FORMAT=TREE` 格式输出（不支持 TRADITIONAL 或 JSON）。如果在 8.0.17 及更早版本执行 `EXPLAIN ANALYZE`，会报语法错误。使用前需确认 MySQL 版本。
- 对于有复杂子查询或 CTE 的查询，`EXPLAIN ANALYZE` 的输出可能很长且难以阅读。可以使用 MySQL Workbench 8.0 的 Visual Explain 功能，以图形化方式展示 EXPLAIN ANALYZE 的结果，更直观地看到各步骤的耗时比例。

## 总结

`EXPLAIN ANALYZE`（MySQL 8.0.18+）真正执行 SQL 并输出 TREE 格式的执行统计，包含：估算值（cost、rows）+ 实际值（actual time、actual rows、loops）。核心用途：①对比估算 rows 和 actual rows，发现统计信息偏差；②通过 actual time 的各步骤差值，定位最耗时的操作（排序、JOIN 循环、全表扫描等）；③loops 字段显示 JOIN 循环次数，帮助量化被驱动表的访问代价。注意：会真实执行 SQL（DML 操作有副作用），生产环境中应使用事务包裹 DML 的 EXPLAIN ANALYZE，分析完立即回滚。

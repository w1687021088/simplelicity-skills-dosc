# EXPLAIN FORMAT=JSON 详细输出

`EXPLAIN FORMAT=JSON` 是 MySQL 5.6.5 引入的 EXPLAIN 扩展格式，以 JSON 结构输出执行计划，包含了传统表格格式（`FORMAT=TRADITIONAL`）中没有的额外信息，最重要的是每个步骤的**成本估算（cost_info）**。通过成本信息，可以直接看到优化器为每个操作分配的成本值，理解为什么优化器选择了某个索引而不是另一个，是深入理解查询优化器决策的有力工具。

---

## 基本语法与输出结构

```sql
EXPLAIN FORMAT=JSON SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.created_at
LIMIT 20 \G

-- 输出是一个 JSON 对象，基本结构：
{
  "query_block": {
    "select_id": 1,
    "cost_info": {
      "query_cost": "1250.30"     -- 整个查询的总估算成本
    },
    "ordering_operation": {       -- ORDER BY 操作
      "using_filesort": true,     -- 是否需要 filesort
      "cost_info": {...},
      "nested_loop": [            -- JOIN 操作（嵌套循环）
        {
          "table": {
            "table_name": "o",
            "access_type": "ref",
            "possible_keys": ["idx_status"],
            "key": "idx_status",
            "key_length": "1",
            "ref": ["const"],
            "rows_examined_per_scan": 500000,
            "rows_produced_per_join": 500000,
            "filtered": "100.00",
            "cost_info": {
              "read_cost": "12345.67",    -- 读取索引的成本
              "eval_cost": "50000.00",    -- 处理每行的 CPU 成本
              "prefix_cost": "62345.67", -- 到这一步的累计成本
              "data_read_per_join": "..."
            },
            "used_columns": ["id", "user_id", "status", "created_at"]
          }
        },
        {
          "table": {
            "table_name": "u",
            "access_type": "eq_ref",
            "key": "PRIMARY",
            "rows_examined_per_scan": 1,
            "filtered": "100.00",
            "cost_info": {
              "read_cost": "...",
              "eval_cost": "...",
              "prefix_cost": "..."  -- 比 o 的 prefix_cost 高（累计）
            }
          }
        }
      ]
    }
  }
}
```

---

## cost_info 字段解读

```sql
-- cost_info 在每个表节点和整体 query_block 中都存在
-- 主要字段：

-- query_cost：整个查询的总估算成本（所有步骤累计）
-- read_cost：读取行的 I/O 成本（受 io_block_read_cost 参数影响）
-- eval_cost：CPU 处理每行的成本（受 row_evaluate_cost 参数影响）
-- prefix_cost：到当前步骤为止的累计成本（包含之前所有步骤）
-- data_read_per_join：每次 JOIN 操作估算读取的字节数

-- 通过 prefix_cost 可以识别最昂贵的步骤：
-- 每步的增量成本 = 当前 prefix_cost - 前一步 prefix_cost
-- 增量最大的步骤是优化重点

-- 查看 MySQL 的成本参数配置：
SELECT * FROM mysql.server_cost \G
-- row_evaluate_cost: 0.1（处理每行的 CPU 成本）
-- memory_temptable_create_cost: 1.0（创建内存临时表的成本）
-- memory_temptable_row_cost: 0.1（内存临时表每行写入成本）
-- disk_temptable_create_cost: 20.0（创建磁盘临时表的成本）
-- disk_temptable_row_cost: 0.5
-- key_compare_cost: 0.05（比较索引键的成本）

SELECT * FROM mysql.engine_cost \G
-- io_block_read_cost: 1.0（读取数据页的 I/O 成本）
-- memory_block_read_cost: 0.25（从 Buffer Pool 读取的成本，内存比磁盘低 4 倍）
```

## FORMAT=JSON 特有的字段

```sql
-- 1. using_filesort（明确布尔值）
-- 传统格式：Extra: Using filesort（字符串中查找）
-- JSON 格式：ordering_operation.using_filesort: true/false（直接判断）

-- 2. using_temporary_table（明确布尔值）
-- JSON 格式中明确显示 true/false

-- 3. attached_condition（完整的 WHERE 条件）
-- 显示该步骤实际应用的过滤条件（完整表达式）
"attached_condition": "(orders.`status` = 1)"

-- 4. used_columns（实际用到的列）
-- 显示该步骤访问了哪些列（包括 SELECT、WHERE、JOIN 等用到的）
"used_columns": ["id", "user_id", "status", "amount"]

-- 5. rows_examined_per_scan vs rows_produced_per_join
-- rows_examined_per_scan：每次循环扫描的行数（对应传统格式的 rows）
-- rows_produced_per_join：经过过滤后传给下一步的行数（= rows × filtered/100）
```

## 比较两种 EXPLAIN 格式

| 信息 | FORMAT=TRADITIONAL | FORMAT=JSON |
|------|:-----------------:|:-----------:|
| 成本估算（query_cost）| 无 | 有 |
| 每步的 read_cost/eval_cost | 无 | 有 |
| filesort/temporary 布尔值 | 字符串中识别 | 明确布尔字段 |
| 完整的 WHERE 条件（attached_condition）| 无 | 有 |
| 用到的列列表（used_columns）| 无 | 有 |
| 易读性 | 表格，直观 | JSON，需要解析 |

## 实用技巧：通过 JSON 格式比较两个执行计划

```sql
-- 对比两种索引方案的成本
-- 方案A：只用 idx_status
EXPLAIN FORMAT=JSON
SELECT * FROM orders WHERE status = 1 ORDER BY created_at LIMIT 20 \G
-- 记录 query_cost 值

-- 方案B：用 idx_status_created (status, created_at)
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
EXPLAIN FORMAT=JSON
SELECT * FROM orders WHERE status = 1 ORDER BY created_at LIMIT 20 \G
-- 记录新的 query_cost 值

-- 对比两个 query_cost：
-- 方案A: query_cost: "125000.00"（filesort + 回表）
-- 方案B: query_cost: "5000.00"  ← 联合索引，无 filesort，成本降低 25 倍

-- FORMAT=JSON 的 query_cost 是优化器决策的直接依据
-- 成本越低，优化器越倾向于选择该方案
```

## 使用 FORMAT=TREE（MySQL 8.0.16+）

```sql
-- FORMAT=TREE 用树形文本格式显示执行计划（比 JSON 更紧凑易读）
EXPLAIN FORMAT=TREE SELECT o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = 1 \G

-- 输出示例：
-- -> Nested loop inner join  (cost=62345.67 rows=500000)
--    -> Index lookup on o using idx_status (status=1)  (cost=12345.67 rows=500000)
--    -> Single-row index lookup on u using PRIMARY (id=o.user_id)  (cost=0.1 rows=1)

-- TREE 格式的特点：
-- 直接显示 cost 值（比 JSON 更紧凑）
-- 结构更直观（缩进反映嵌套关系）
-- 是 EXPLAIN ANALYZE 的基础格式（加上实际执行统计）
```

## 适用场景

- **分析优化器索引选择逻辑**：当优化器选择的索引与预期不同时，通过 `FORMAT=JSON` 查看每个候选方案的 `query_cost`，理解为什么优化器选择了某个看似不优的索引（因为它的 query_cost 实际更低）
- **量化优化效果**：在添加索引或修改查询后，通过对比 `FORMAT=JSON` 中的 `query_cost` 变化，以成本数字量化优化效果，比单纯看 type 变化更有说服力

---

## 常见问题

**FORMAT=JSON 的 query_cost 单位是什么？**

`query_cost` 是一个无量纲的抽象成本值，单位不是毫秒或任何实际时间单位，而是 MySQL 内部成本模型计算出的估算值（基于 `mysql.server_cost` 和 `mysql.engine_cost` 表中的成本参数）。它不能直接转换为执行时间，但可以用于同一服务器上两个执行计划的相对比较（cost A > cost B → 方案 B 更优）。实际执行时间受网络、磁盘 I/O、Buffer Pool 命中率等因素影响，不能完全与 query_cost 对应。

---

## 注意事项

- `FORMAT=JSON` 的输出内容比 `FORMAT=TRADITIONAL` 更长，在分析复杂的多表 JOIN 或子查询时，JSON 可能很难阅读。建议使用专业工具（如 MySQL Workbench 的 Visual EXPLAIN）解析 JSON 格式的执行计划，以可视化方式展示各步骤的成本和连接关系。
- `FORMAT=TREE` 是 MySQL 8.0.16 引入的，与 `EXPLAIN ANALYZE` 结合使用效果最好（既有估算成本，又有实际执行时间）。对于 MySQL 8.0.18+ 的环境，`EXPLAIN ANALYZE` 直接输出 TREE 格式加上真实统计，比单独使用 `FORMAT=JSON` 更实用。

---

## 总结

`EXPLAIN FORMAT=JSON` 提供了比传统表格格式更丰富的执行计划信息，最重要的是 `cost_info` 成本字段（`query_cost`、`read_cost`、`eval_cost`、`prefix_cost`），可以直接查看优化器的成本估算，理解其决策逻辑。`FORMAT=TREE`（MySQL 8.0.16+）是更紧凑的树形格式，同样包含成本信息，且是 `EXPLAIN ANALYZE` 的基础格式。通过对比不同执行计划的 `query_cost`，可以量化索引优化的效果。常用于：诊断优化器索引选择异常、量化优化效果、通过成本参数调整优化器行为。

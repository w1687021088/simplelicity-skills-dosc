# filtered 列与条件过滤比例

EXPLAIN 输出的 `filtered` 列显示经过 WHERE 条件（包括索引条件和 Server 层条件）过滤后，估算剩余的行数占 `rows` 的百分比（0.00~100.00）。`filtered` 与 `rows` 结合，可以估算最终传递给下一步（或最终返回）的实际行数：`rows × filtered / 100 = 实际处理行数`。`filtered` 越高，说明索引越精确地过滤了数据（几乎所有索引扫描的行都满足条件）；`filtered` 越低，说明有大量行经过索引扫描后在 Server 层被过滤掉（回表代价高但命中率低）。

---

## filtered 的计算含义

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id)
);

-- 只用了 user_id 索引，但 WHERE 还有 amount 条件（需要回表过滤）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- key: idx_user
-- rows: 25        ← 索引估算扫描 25 行（user_id=100 的行）
-- filtered: 40.00 ← 估算其中 40% 的行满足 amount > 500
-- 实际传递行数：25 × 0.40 = 10 行

-- 联合索引完全覆盖所有 WHERE 条件：
-- ALTER TABLE orders ADD INDEX idx_user_amount (user_id, amount);
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- key: idx_user_amount
-- rows: 10        ← 索引直接过滤到 10 行
-- filtered: 100.00 ← 100% 的索引扫描行都满足条件（无需额外过滤）
-- filtered=100 表示索引精确覆盖了所有 WHERE 条件
```

## filtered 在 JOIN 中的意义

```sql
-- JOIN 中，被驱动表的 filtered 影响 JOIN 的总代价
-- 驱动表的 rows × filtered / 100 = 传递给被驱动表的行数
-- 传递行数越少，被驱动表的 JOIN 循环次数越少

EXPLAIN SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 AND o.amount > 500 \G

-- 输出（假设）：
-- table: o, rows: 500000, filtered: 10.00, key: idx_status
-- table: u, rows: 1,      filtered: 100.00, key: PRIMARY

-- orders 扫描 50 万行（status=1），过滤 10% 后传递 5 万行到 users 的 JOIN
-- 最终：users 做 5 万次主键查找
-- 优化目标：提高 o 的 filtered，减少传递给被驱动表的行数
-- 方法：为 orders 建联合索引 (status, amount)，使 amount > 500 也在索引中过滤

-- ALTER TABLE orders ADD INDEX idx_status_amount (status, amount);
-- 新的估算：orders rows: 50000, filtered: 100.00
-- → 传递给 users 的行数从 5 万减为精确的 5 万（filtered=100 意味着无多余行）
```

## filtered=100 与 filtered<100 的区别

```sql
-- filtered = 100.00：索引过滤完全精确
-- 含义：通过索引扫描的行，全部满足所有 WHERE 条件
-- Extra 通常显示 "Using index"（覆盖索引）或无附加条件过滤

-- filtered < 100.00：索引过滤不完全精确
-- 含义：通过索引扫描的行中，有一部分不满足非索引列的 WHERE 条件
-- Extra 通常显示 "Using index condition"（ICP）或 "Using where"（回表过滤）

-- 示例对比：
-- 情况A：只有 user_id 索引，但 WHERE 还有 amount > 500
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- filtered: 40.00  ← 60% 的回表行被 Server 层过滤掉（浪费了 60% 的回表 I/O）

-- 情况B：有 (user_id, amount) 联合索引
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- filtered: 100.00  ← 无多余回表，索引精确过滤

-- 提升 filtered 的方法：扩展索引列，使更多 WHERE 条件在索引层过滤
```

## filtered 的诊断应用

```sql
-- 当 filtered 很低（如 5% 以下）时，需要评估：
-- 1. 是否可以建更覆盖条件的联合索引（提升 filtered）
-- 2. 当前的回表代价是否过高（rows × (1 - filtered/100) = 浪费的回表次数）

-- 案例：
-- rows: 100000, filtered: 5.00
-- 扫描 10 万行，只有 5% (5000 行) 满足条件
-- 浪费了 95000 次回表！

-- 建联合索引后：
-- rows: 5000, filtered: 100.00
-- 只扫描 5000 行，全部满足，无浪费

-- 计算浪费的回表次数：
-- 优化前浪费 = rows × (100 - filtered) / 100 = 100000 × 0.95 = 95000 次
-- 优化后浪费 = 5000 × 0 = 0 次
-- 节省了 95000 次随机 I/O！

-- 通过 filtered 量化优化收益，说服团队投入索引优化资源
```

## filtered 值的准确性

```sql
-- filtered 同样是估算值（基于统计信息），可能与实际有偏差

-- 通过 EXPLAIN ANALYZE 获取真实的 filtered 值（MySQL 8.0.18+）
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100 AND amount > 500 \G
-- 输出格式（TREE）：
-- -> Filter: (orders.amount > 500)  (cost=2.51 rows=10) (actual time=0.018..0.045 rows=8 loops=1)
--    -> Index lookup on orders using idx_user (user_id=100)  (cost=2.51 rows=25)
--       (actual time=0.015..0.035 rows=25 loops=1)
-- 
-- 估算 filtered: 40%（25行 → 10行）
-- 实际 filtered: 32%（25行实际扫描 → 8行满足条件）
-- 估算偏差不大，统计信息基本准确
```

## 适用场景

- **量化回表浪费**：通过 `rows × (1 - filtered/100)` 计算索引扫描中被 Server 层丢弃的浪费行数，当这个数字很大时，说明需要扩展联合索引以提高过滤精度，减少无效回表
- **JOIN 优化评估**：在多表 JOIN 中，通过驱动表的 `rows × filtered/100` 估算传递到被驱动表的行数，这个值越小 JOIN 代价越低，是决定是否需要优化驱动表索引的量化依据

---

## 常见问题

**filtered=100 是不是意味着查询一定很高效？**

不一定。`filtered=100` 只表示索引扫描的行都满足 WHERE 条件（没有额外的 Server 层过滤），但不代表 `rows` 值合理。如果 `rows=1000000` 且 `filtered=100`，仍然是扫描了 100 万行——虽然每行都满足条件（没有浪费），但扫描量本身就很大。`filtered=100` + `rows` 很大 → 需要考虑能否进一步限制扫描范围（添加更精确的条件或改变索引设计）。真正高效的查询应该同时满足：`rows` 小 + `filtered` 接近 100。

## 注意事项

- `filtered` 是 MySQL 5.7+ 默认显示的列（在 5.6 及更早版本中，需要 `EXPLAIN EXTENDED` 才能看到）。在 MySQL 8.0 中，`filtered` 列始终显示，无需额外语法。
- `filtered` 的估算精度受统计信息质量影响。对于低基数列（如 status 只有几个值），优化器的 `filtered` 估算通常比高基数列（如 user_id）更不准确。MySQL 8.0 引入的直方图（Histograms）可以显著提高低基数列的 `filtered` 估算精度，值得在关键过滤列上建立直方图。

## 总结

`filtered` 列表示经过所有 WHERE 条件过滤后，保留的行占 `rows` 的百分比。`rows × filtered / 100` = 实际传递行数（评估查询代价的关键指标）。`filtered = 100`：索引精确覆盖了所有 WHERE 条件，无多余回表；`filtered < 100`：有部分行通过索引扫描但被 Server 层条件过滤（回表有浪费）。优化方向：通过扩展联合索引（将更多 WHERE 列加入索引），把 Server 层过滤条件下推到索引层，提升 `filtered` 值，减少无效回表。在 JOIN 中，驱动表的 `filtered` 低意味着传递给被驱动表的行多，是优化 JOIN 性能的重要目标。

# select_type 查询类型（SIMPLE, PRIMARY, SUBQUERY）

EXPLAIN 输出的 `select_type` 列描述了当前行所代表的 SELECT 语句的类型，帮助理解整个查询的结构——是简单查询、复合查询的主体、子查询、派生表，还是 UNION 的组成部分。掌握各种 `select_type` 的含义，可以快速判断查询的复杂程度和潜在的性能问题点（如 `DEPENDENT SUBQUERY` 往往意味着循环执行的相关子查询）。

---

## 全部 select_type 值说明

| select_type | 含义 |
|-------------|------|
| SIMPLE | 简单查询，不包含子查询或 UNION |
| PRIMARY | 最外层（主）查询，当查询中有子查询或 UNION 时外层为 PRIMARY |
| SUBQUERY | 在 SELECT 或 WHERE 中的不相关子查询 |
| DEPENDENT SUBQUERY | 相关子查询（引用了外层查询的列，每行外层行都重新执行）|
| DERIVED | FROM 子句中的派生表（子查询用作表）|
| DEPENDENT DERIVED | 依赖外层查询的派生表（较少见）|
| MATERIALIZED | 物化子查询（子查询结果被物化为临时表，MySQL 5.6+）|
| UNCACHEABLE SUBQUERY | 结果不可缓存的子查询（如含 RAND()、NOW() 等不确定函数）|
| UNION | UNION 中除第一个 SELECT 外的后续 SELECT |
| UNION RESULT | UNION 的结果集（对多个 SELECT 结果合并去重的临时表）|

---

## SIMPLE：最简单的形式

```sql
-- 无子查询、无 UNION 的查询，select_type 均为 SIMPLE
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- select_type: SIMPLE

EXPLAIN SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 \G
-- select_type: SIMPLE（两行都是）
-- JOIN 不是子查询，不影响 SIMPLE 判断
```

## PRIMARY 与 SUBQUERY

```sql
-- 当查询含有子查询时，外层查询为 PRIMARY，子查询为 SUBQUERY
EXPLAIN SELECT *
FROM orders
WHERE user_id IN (
    SELECT id FROM users WHERE status = 'active'  -- 不相关子查询
) \G

-- 输出：
-- select_type: PRIMARY, table: orders  ← 外层查询
-- select_type: SUBQUERY, table: users  ← 不相关子查询（可以独立执行一次）

-- SUBQUERY 特点：
-- 不依赖外层查询的列
-- MySQL 可以执行一次后缓存结果
-- 性能通常比 DEPENDENT SUBQUERY 好

-- SELECT 列表中的子查询也是 SUBQUERY
EXPLAIN SELECT id,
    (SELECT COUNT(*) FROM order_items WHERE order_id = orders.id) AS item_count
FROM orders
WHERE user_id = 100 \G
-- 注意：这里是相关子查询（引用了 orders.id）→ DEPENDENT SUBQUERY
```

## DEPENDENT SUBQUERY：性能风险点

```sql
-- 相关子查询：子查询引用了外层查询的列
EXPLAIN SELECT *
FROM orders o
WHERE o.amount > (
    SELECT AVG(amount) FROM orders WHERE user_id = o.user_id  -- 引用了 o.user_id
) \G

-- 输出：
-- select_type: PRIMARY, table: o
-- select_type: DEPENDENT SUBQUERY, table: orders

-- 性能问题：外层 o 扫描每一行，子查询就重新执行一次
-- 如果 orders 表有 10 万行，子查询执行 10 万次！

-- 改写为 JOIN（通常更高效）：
EXPLAIN SELECT o.*
FROM orders o
JOIN (
    SELECT user_id, AVG(amount) AS avg_amount
    FROM orders
    GROUP BY user_id
) AS avg_t ON o.user_id = avg_t.user_id
WHERE o.amount > avg_t.avg_amount \G
-- select_type: PRIMARY（JOIN 方式，无 DEPENDENT SUBQUERY）
-- 聚合子查询只执行一次（GROUP BY + AVG），比重复执行相关子查询高效

-- 也可以用 Window Function 改写（MySQL 8.0+）：
SELECT * FROM (
    SELECT *, AVG(amount) OVER (PARTITION BY user_id) AS avg_amount
    FROM orders
) t
WHERE amount > avg_amount;
```

## DERIVED：派生表

```sql
-- FROM 子句中的子查询形成派生表
EXPLAIN SELECT t.user_id, t.total
FROM (
    SELECT user_id, SUM(amount) AS total
    FROM orders WHERE status = 1
    GROUP BY user_id
) AS t
WHERE t.total > 500 \G

-- 输出：
-- select_type: PRIMARY, table: t (<derived2>)  ← 外层访问派生表
-- select_type: DERIVED, table: orders           ← 派生表的查询

-- MySQL 8.0 派生表合并（Derived Merge）优化：
-- 如果派生表简单（无聚合、DISTINCT、LIMIT 等），优化器可能合并
-- 合并后 EXPLAIN 只有一行（无 DERIVED 行）
-- 通过 optimizer_switch 控制：
-- derived_merge=on（默认）→ 尽可能合并
-- derived_merge=off → 总是物化派生表
```

---

## MATERIALIZED：物化子查询

```sql
-- MySQL 5.6+ 对某些 IN 子查询做物化优化：
-- 将子查询结果物化为临时表（带哈希或索引），加速与外层的连接

EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'CN') \G

-- 可能输出（取决于优化器的选择）：
-- select_type: PRIMARY, table: orders
-- select_type: MATERIALIZED, table: users  ← 子查询物化为临时表

-- 物化 vs 不物化（每次执行子查询）：
-- 物化适合：子查询结果集较小，外层表较大
-- 不物化适合：子查询结果集很大，且外层表较小（避免大临时表）

-- 控制物化：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- materialization=on  → 允许子查询物化（默认）
```

## UNION 与 UNION RESULT

```sql
EXPLAIN
SELECT id, user_id, amount FROM orders WHERE status = 1
UNION
SELECT id, user_id, amount FROM orders WHERE status = 2
UNION
SELECT id, user_id, amount FROM orders WHERE status = 3 \G

-- 输出（4 行）：
-- select_type: PRIMARY,      table: orders  ← 第一个 SELECT
-- select_type: UNION,        table: orders  ← 第二个 SELECT
-- select_type: UNION,        table: orders  ← 第三个 SELECT
-- select_type: UNION RESULT, table: <union1,2,3>  ← 三个结果合并去重

-- UNION RESULT 的 Extra 通常是 Using temporary（用临时表去重）
-- 改为 UNION ALL（不去重）可以消除 UNION RESULT 行

EXPLAIN
SELECT id, user_id FROM orders WHERE status = 1
UNION ALL
SELECT id, user_id FROM orders WHERE status = 2 \G
-- 只有两行（PRIMARY 和 UNION），无 UNION RESULT
```

## UNCACHEABLE SUBQUERY

```sql
-- 子查询含有不确定函数时，结果不可缓存
EXPLAIN SELECT *
FROM orders
WHERE user_id = (SELECT FLOOR(RAND() * 1000)) \G
-- select_type: UNCACHEABLE SUBQUERY
-- 外层每行都需要重新执行子查询（因为 RAND() 每次结果不同）

-- 含 NOW()、CURDATE() 的子查询也是不可缓存的
-- 通常这类查询应该在应用层计算好固定值，而不是在 SQL 中使用 RAND()/NOW()
```

## 适用场景

- **识别相关子查询（DEPENDENT SUBQUERY）并改写**：当 EXPLAIN 出现 `DEPENDENT SUBQUERY` 时，这是高优先级的优化信号——该子查询会对外层每一行重复执行，在大表情况下性能极差，应立即改写为 JOIN 或窗口函数
- **验证子查询优化器的行为**：通过 `select_type` 判断 MySQL 是否对 IN 子查询做了物化（`MATERIALIZED`）或半连接优化，确认优化器的实际执行策略与期望一致

---

## 常见问题

**`PRIMARY` 和 `SIMPLE` 的区别是什么？**

`SIMPLE` 表示整个查询没有子查询或 UNION，是最简单的形式；`PRIMARY` 是有子查询/UNION 时最外层查询的标识。两者都代表"外层/主查询"的逻辑，区别只在于整个 SQL 是否含有子查询或 UNION 结构。单纯的 JOIN 查询（无子查询）是 `SIMPLE`，不是 `PRIMARY`。

---

## 注意事项

- `DEPENDENT SUBQUERY` 是性能问题最大的 select_type，一旦出现在 EXPLAIN 中，几乎总是需要优化。改写方向：用 `JOIN` 替代相关子查询（将子查询提取为独立的聚合查询或派生表，再与外层 JOIN）；或用 MySQL 8.0+ 的窗口函数处理同一分组内的聚合计算。
- MySQL 8.0 的 `Derived Merge` 优化会将简单派生表合并入主查询，使 EXPLAIN 中不再出现 `DERIVED` 行。如果发现 EXPLAIN 只有 `PRIMARY` 而没有预期的 `DERIVED`，可能是优化器合并了派生表（通常是好事），可以通过 `optimizer_switch='derived_merge=off'` 关闭合并来验证。

---

## 总结

`select_type` 描述了 EXPLAIN 中每行的查询角色：`SIMPLE`（无子查询 JOIN）、`PRIMARY`（含子查询时的外层主查询）、`SUBQUERY`（不相关子查询，执行一次可缓存）、`DEPENDENT SUBQUERY`（相关子查询，每行外层行都重新执行，性能危险）、`DERIVED`（FROM 子句派生表）、`MATERIALIZED`（物化的 IN 子查询）、`UNION`（UNION 的后续 SELECT）、`UNION RESULT`（UNION 去重临时表）。优化重点：`DEPENDENT SUBQUERY` → 改写为 JOIN；`UNION RESULT` → 改 UNION ALL；`DERIVED` → 检查是否可以合并（MySQL 8.0 Derived Merge）。

# EXPLAIN 语法与输出列

`EXPLAIN` 是 MySQL 提供的查询执行计划分析工具，用于显示 MySQL 查询优化器对 SQL 语句的执行方案：如何访问表、使用哪个索引、每步估算的行数等。理解 EXPLAIN 的输出是 SQL 调优的基础技能。在 MySQL 8.0+ 中，`EXPLAIN` 还支持 `FORMAT=JSON`、`FORMAT=TREE` 和 `ANALYZE` 等增强选项，提供更丰富的执行计划细节。

---

## EXPLAIN 的基本语法

```sql
-- 基本用法
EXPLAIN SELECT * FROM orders WHERE user_id = 100;

-- 等价写法（DESCRIBE 是 EXPLAIN 的别名）
DESCRIBE SELECT * FROM orders WHERE user_id = 100;

-- 对 DML 语句使用 EXPLAIN
EXPLAIN UPDATE orders SET status = 2 WHERE user_id = 100 AND status = 1;
EXPLAIN DELETE FROM orders WHERE created_at < '2024-01-01';
EXPLAIN INSERT INTO orders_archive SELECT * FROM orders WHERE created_at < '2024-01-01';

-- 对存储过程中的单条 SQL 使用 EXPLAIN（需要单独提取 SQL）

-- 显式指定输出格式（MySQL 8.0+）
EXPLAIN FORMAT=TRADITIONAL SELECT ...;   -- 默认表格格式
EXPLAIN FORMAT=JSON SELECT ...;          -- JSON 格式（更详细，包含成本信息）
EXPLAIN FORMAT=TREE SELECT ...;          -- 树形格式（MySQL 8.0.16+）

-- EXPLAIN ANALYZE（实际执行并显示真实统计，MySQL 8.0.18+）
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100;

-- 加 \G 竖向显示（更易读）
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
```

## EXPLAIN 的全部输出列

```
EXPLAIN 输出的完整列（传统格式）：
+----+-------------+-------+------------+------+---------------+------+---------+------+------+----------+-------+
| id | select_type | table | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra |
+----+-------------+-------+------------+------+---------------+------+---------+------+------+----------+-------+

列说明：
1. id           → 查询标识符（执行顺序）
2. select_type  → 查询类型（SIMPLE/PRIMARY/SUBQUERY/DERIVED 等）
3. table        → 当前步骤访问的表名
4. partitions   → 匹配的分区（非分区表为 NULL）
5. type         → 访问类型（system > const > eq_ref > ref > range > index > ALL）
6. possible_keys→ 优化器认为可能使用的索引
7. key          → 优化器实际选择使用的索引
8. key_len      → 索引使用的字节长度（可推算用了几列）
9. ref          → 与索引列进行比较的值或列
10. rows        → 估算需要扫描的行数
11. filtered    → 经过条件过滤后剩余行的百分比
12. Extra       → 附加信息（Using index/Using where/Using filesort/Using temporary 等）
```

## 各列的快速解读指引

```sql
-- 示例查询及完整输出解读：
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user_status (user_id, status),
    INDEX idx_created (created_at)
);

EXPLAIN SELECT id, user_id, status FROM orders
WHERE user_id = 100 AND status = 1
ORDER BY user_id LIMIT 10 \G

-- 可能输出：
-- id: 1
-- select_type: SIMPLE
-- table: orders
-- partitions: NULL
-- type: ref
-- possible_keys: idx_user_status
-- key: idx_user_status
-- key_len: 5
-- ref: const, const
-- rows: 25
-- filtered: 100.00
-- Extra: Using index

-- 解读：
-- type: ref → 走二级索引等值查询，效率良好
-- key: idx_user_status → 使用了联合索引
-- key_len: 5 → INT(4字节) + TINYINT(1字节) = 5，两列都用到了
-- filtered: 100 → 索引过滤后不需要额外过滤（所有行都符合条件）
-- Extra: Using index → 覆盖索引！无回表（id、user_id、status 都在索引中）
```

## EXPLAIN 的性能评估维度

```
快速评估执行计划质量的关键指标：

优先看 type（访问类型）：
  const/eq_ref → 最优，O(1) 或近 O(1) 查询
  ref/range    → 良好，索引有效过滤
  index        → 警惕，全索引扫描（可能低效）
  ALL          → 危险，全表扫描（需要索引优化）

再看 Extra（附加信息）：
  Using index              → 覆盖索引，最优状态
  Using where              → Server 层额外过滤，通常正常
  Using filesort           → 需要排序，可以优化（建合适索引）
  Using temporary          → 使用临时表，通常需要优化
  Using index condition    → ICP，减少了回表（良好）

看 rows × filtered 估算实际处理行数：
  rows = 1000, filtered = 10.00 → 实际处理约 100 行
  rows * filtered / 100 = 实际处理行数估算

最后看 possible_keys 和 key：
  possible_keys 不为 NULL 但 key 为 NULL → 优化器放弃了索引（需要分析原因）
  key 与预期不同 → 优化器选择了不同的索引（可能需要 FORCE INDEX）
```

## EXPLAIN 对不同 SQL 的支持

```sql
-- SELECT（所有形式）
EXPLAIN SELECT * FROM t1 JOIN t2 ON t1.id = t2.t1_id WHERE t1.status = 1;

-- 子查询
EXPLAIN SELECT * FROM t1 WHERE id IN (SELECT t1_id FROM t2 WHERE status = 1);

-- UNION
EXPLAIN SELECT id FROM t1 WHERE status = 1
UNION
SELECT id FROM t1 WHERE status = 2;

-- DML（INSERT/UPDATE/DELETE）
EXPLAIN UPDATE t1 SET status = 2 WHERE id IN (SELECT id FROM t2);
-- DML 的 EXPLAIN 对于优化批量更新/删除时的索引使用很有用

-- 查看已存在的连接的执行计划（MySQL 8.0+）
EXPLAIN FOR CONNECTION 42;
-- 42 是目标连接的 id（通过 SHOW PROCESSLIST 获取）
-- 可以在另一个连接中分析正在运行的慢查询
```

## EXPLAIN ANALYZE 与 EXPLAIN 的对比

| 对比维度 | EXPLAIN | EXPLAIN ANALYZE |
|---------|:-------:|:---------------:|
| 是否真正执行 | 否（只做预测）| 是（真实执行）|
| rows 准确性 | 估算值（可能不准）| 真实值 |
| 输出格式 | 表格/JSON/TREE | 仅 TREE（带实际时间）|
| 副作用 | 无（只读）| 会执行 DML（写表）|
| 适用场景 | 快速查看预期计划 | 验证计划是否按预期执行 |
| MySQL 版本 | 所有版本 | 8.0.18+ |

## 适用场景

- **SQL 上线前的性能验证**：在新 SQL 上线前，通过 EXPLAIN 确认其执行计划是否符合预期（type 非 ALL、使用了正确的索引、无 Using filesort 等），是防止上线后出现性能问题的基本手段
- **慢查询排查**：通过慢查询日志找到慢 SQL 后，立即用 EXPLAIN 分析执行计划，定位是否存在全表扫描、错误的索引选择、filesort 等问题

---

## 常见问题

**EXPLAIN 的 rows 估算值与实际执行行数偏差很大怎么办？**

`rows` 是 MySQL 基于统计信息（InnoDB 的采样估算）给出的预测值，不是精确值。当统计信息过时（大量 INSERT/DELETE 后未更新）时，偏差会特别大。解决方法：执行 `ANALYZE TABLE 表名` 强制更新统计信息；如果仍然偏差大，调大 `innodb_stats_sample_pages`（默认 8）提高采样精度。对于需要精确执行统计的场景，使用 `EXPLAIN ANALYZE`（MySQL 8.0.18+）获取实际执行时的真实行数。

---

## 注意事项

- `EXPLAIN` 不是真正执行 SQL，因此对于依赖实际数据量的优化决策（如小表的全表扫描 vs 索引），预测结果可能不准确。在复杂查询中，`EXPLAIN` 的结果是优化器基于统计信息的决策，不等于执行时的真实行为。
- `EXPLAIN FOR CONNECTION connection_id` 可以在不中断目标连接的情况下查看其正在执行的 SQL 的执行计划，是生产环境中分析正在运行的慢查询的有效手段，不会影响目标连接的正常执行。

---

## 总结

`EXPLAIN` 是分析 MySQL 查询执行计划的核心工具，输出 12 列：id（执行顺序）、select_type（查询类型）、table（表名）、partitions（分区）、type（访问类型）、possible_keys（候选索引）、key（实际索引）、key_len（索引长度）、ref（比较值）、rows（估算行数）、filtered（过滤比例）、Extra（附加信息）。性能评估优先看 `type`（ALL 最差）和 `Extra`（Using filesort/Using temporary 需关注）。支持 FORMAT=JSON（带成本信息）、FORMAT=TREE（树形）、ANALYZE（真实执行统计）三种增强模式。

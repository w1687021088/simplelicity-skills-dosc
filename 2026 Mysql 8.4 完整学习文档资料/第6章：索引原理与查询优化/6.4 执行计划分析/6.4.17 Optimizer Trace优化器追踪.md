# Optimizer Trace 优化器追踪

Optimizer Trace 是 MySQL 5.6 引入的功能，通过 `information_schema.OPTIMIZER_TRACE` 表记录查询优化器的完整决策过程——包括每个候选索引的成本估算、JOIN 顺序的尝试、子查询的改写、统计信息的使用等所有中间步骤。当 EXPLAIN 的输出无法解释优化器为什么做出某个决定时（如放弃了一个看起来更好的索引，或选择了非直觉的 JOIN 顺序），Optimizer Trace 提供了最详细的内部分析信息。

---

## 开启 Optimizer Trace

```sql
-- 默认关闭（对性能有一定影响，仅调试时开启）
SHOW VARIABLES LIKE 'optimizer_trace';
-- optimizer_trace: enabled=off,one_line=off

-- 开启（Session 级别，不影响其他连接）
SET SESSION optimizer_trace = 'enabled=on';
-- 开启后，执行的每个 SQL 都会生成一条 trace 记录

-- 控制 trace 内容的大小上限
SET SESSION optimizer_trace_max_mem_size = 1048576;  -- 1MB（默认）
-- 如果 trace 很大（复杂查询），增大此值避免被截断

-- 关闭（分析完后立即关闭）
SET SESSION optimizer_trace = 'enabled=off';
```

---

## 执行查询并读取 Trace

```sql
-- 步骤1：开启 trace
SET SESSION optimizer_trace = 'enabled=on';

-- 步骤2：执行要分析的查询
SELECT * FROM orders WHERE user_id = 100 AND status = 1;

-- 步骤3：读取 trace
SELECT * FROM information_schema.OPTIMIZER_TRACE \G

-- 步骤4：关闭 trace
SET SESSION optimizer_trace = 'enabled=off';

-- OPTIMIZER_TRACE 表结构：
-- QUERY：执行的 SQL 文本
-- TRACE：JSON 格式的优化过程（核心内容）
-- MISSING_BYTES_BEYOND_MAX_MEM_SIZE：是否被截断（0 = 完整）
-- INSUFFICIENT_PRIVILEGES：是否有权限查看（通常为 0）
```

## Trace JSON 结构解读

```json
{
  "steps": [
    {
      "join_preparation": {
        "select#": 1,
        "steps": [
          "expanded_query": "SELECT * FROM `orders` WHERE (`orders`.`user_id` = 100) AND (`orders`.`status` = 1)"
        ]
      }
    },
    {
      "join_optimization": {
        "select#": 1,
        "steps": [
          {
            "condition_processing": {...},     // WHERE 条件处理
            "table_dependencies": [...],       // 表依赖关系
            "rows_estimation": [               // 各索引的行数估算（核心！）
              {
                "table": "orders",
                "range_analysis": {
                  "table_scan": {
                    "rows": 1000000,           // 全表扫描估算行数
                    "cost": 100001.1           // 全表扫描成本
                  },
                  "analyzing_range_alternatives": {
                    "range_scan_alternatives": [
                      {
                        "index": "idx_user",
                        "ranges": ["100 <= user_id <= 100"],
                        "rows": 25,            // 该索引扫描估算行数
                        "cost": 27.51,         // 该索引的使用成本
                        "chosen": false,       // 是否被选择
                        "cause": "..."         // 未选择的原因
                      },
                      {
                        "index": "idx_user_status",
                        "ranges": ["100 <= user_id <= 100 AND 1 <= status <= 1"],
                        "rows": 10,
                        "cost": 12.01,
                        "chosen": true         // 被选择！
                      }
                    ],
                    "chosen_range_access_summary": {
                      "chosen_access_method": "range",
                      "best_range_key": "idx_user_status",
                      "best_range_cost": 12.01
                    }
                  }
                }
              }
            ]
          },
          {
            "considered_execution_plans": [    // 考虑的执行计划
              {
                "plan_prefix": [],
                "table": "orders",
                "best_access_path": {
                  "considered_access_paths": [
                    {"access_type": "ref", "index": "idx_user_status", "cost": 12.01}
                  ]
                },
                "chosen": true
              }
            ]
          }
        ]
      }
    },
    {
      "join_execution": {...}  // 实际执行阶段（通常不需要关注）
    }
  ]
}
```

## 通过 Trace 诊断索引未被选择的原因

```sql
-- 场景：EXPLAIN 显示用了 idx_user，但预期应该用 idx_user_status（联合索引更高效）

-- 开启 trace 后执行查询
SET SESSION optimizer_trace = 'enabled=on';
SELECT * FROM orders WHERE user_id = 100 AND status = 1;

-- 读取 trace，找 analyzing_range_alternatives 部分
SELECT JSON_EXTRACT(TRACE, '$**.analyzing_range_alternatives')
FROM information_schema.OPTIMIZER_TRACE \G

-- 可能发现：
-- idx_user_status: rows=10, cost=12.01, chosen=false, cause="cost"
-- 表示选择了更低成本的其他方案

-- 或：
-- idx_user_status: rows=500, cost=550, chosen=false
-- idx_user: rows=25, cost=27.5, chosen=true
-- 说明联合索引的 rows 估算不准（统计信息过时），导致优化器错误选择
-- 解决：ANALYZE TABLE orders; 更新统计信息

SET SESSION optimizer_trace = 'enabled=off';
```

## 诊断 JOIN 顺序决策

```sql
-- Trace 中的 considered_execution_plans 记录了优化器尝试的各种 JOIN 顺序

SET SESSION optimizer_trace = 'enabled=on';
SELECT o.id, u.name FROM orders o JOIN users u ON o.user_id = u.id WHERE o.status = 1;

-- 在 considered_execution_plans 中可以看到：
-- 顺序1：先扫描 orders，再 JOIN users
--   cost: 50000
-- 顺序2：先扫描 users，再 JOIN orders
--   cost: 1000000
-- chosen: 顺序1 → 因为成本更低

-- 通过 trace 可以验证 JOIN 顺序是否合理
-- 如果发现优化器选择了更高成本的 JOIN 顺序，可能是统计信息问题

SET SESSION optimizer_trace = 'enabled=off';
```

## 提取 trace 中的关键信息

```sql
-- 利用 JSON 函数提取 trace 中的关键字段

-- 查看每个索引的成本估算：
SELECT
    JSON_UNQUOTE(JSON_EXTRACT(TRACE, '$**.analyzing_range_alternatives')) AS range_analysis
FROM information_schema.OPTIMIZER_TRACE \G

-- 查看最终选择的索引和成本：
SELECT
    JSON_UNQUOTE(JSON_EXTRACT(TRACE, '$**.best_range_key')) AS best_key,
    JSON_UNQUOTE(JSON_EXTRACT(TRACE, '$**.best_range_cost')) AS best_cost
FROM information_schema.OPTIMIZER_TRACE \G

-- 查看是否发生了子查询改写：
SELECT
    JSON_UNQUOTE(JSON_EXTRACT(TRACE, '$**.transformation_to_semi_join')) AS semi_join_rewrite
FROM information_schema.OPTIMIZER_TRACE \G
```

## Optimizer Trace 与 EXPLAIN FORMAT=JSON 的对比

| 对比维度 | EXPLAIN FORMAT=JSON | Optimizer Trace |
|---------|:------------------:|:--------------:|
| 是否执行 SQL | 否 | 否（只分析）|
| 成本估算 | 最终选择的计划成本 | 所有候选计划的成本 |
| 未选择的候选方案 | 不显示 | 显示（含原因）|
| 索引选择原因 | 不直接说明 | 详细说明（cost/statistics）|
| 输出量 | 中等 | 极大（可达几百 KB）|
| 使用场景 | 日常分析 | 深度调试（优化器决策异常）|

## 适用场景

- **优化器索引选择异常诊断**：当 EXPLAIN 显示的索引与预期不符时（选了一个看起来更差的索引），通过 Trace 找到 `range_scan_alternatives` 中各索引的成本估算，确认是统计信息不准还是索引设计问题
- **复杂查询的 JOIN 顺序验证**：多表 JOIN 时，通过 `considered_execution_plans` 查看优化器尝试了哪些 JOIN 顺序及其成本，验证最终选择是否是全局最优

---

## 常见问题

**Optimizer Trace 输出的 JSON 很大，难以直接阅读，有什么技巧？**

可以结合 MySQL 的 JSON 函数精准提取需要的字段（如上面的 `JSON_EXTRACT` 示例），避免阅读整个 trace。另外，MySQL Workbench 和部分第三方工具（如 Percona Toolkit 的 `pt-query-advisor`）可以解析 Optimizer Trace 并以更直观的方式呈现。对于复杂查询，也可以通过 `SET SESSION optimizer_trace_features = 'greedy_search=on'` 等参数控制 trace 记录哪些优化步骤，减少输出量。

---

## 注意事项

- Optimizer Trace 对性能有一定影响（生成 trace 需要额外 CPU 和内存），应仅在调试时开启，分析完立即关闭（`SET SESSION optimizer_trace = 'enabled=off'`）。不要在高并发生产环境的全局级别开启，只在 Session 级别临时使用。
- 每次执行 SQL 后，`information_schema.OPTIMIZER_TRACE` 表只保留最近一次查询的 trace（默认 `optimizer_trace_limit=1`）。如果需要分析多个查询，可以设置 `optimizer_trace_limit=10` 保留最近 10 条，但会增加内存消耗。

---

## 总结

Optimizer Trace 通过 `SET SESSION optimizer_trace='enabled=on'` 开启，执行 SQL 后从 `information_schema.OPTIMIZER_TRACE` 读取 JSON 格式的优化器完整决策记录。核心价值：显示所有候选索引的成本估算和未被选择的原因（chosen=false + cause），是 EXPLAIN 无法提供的信息。主要用途：诊断索引选择异常（为什么没用预期索引）；分析 JOIN 顺序决策；确认子查询改写是否生效；验证统计信息是否影响了成本估算。注意：应仅在 Session 级别临时开启，分析完立即关闭；输出很大，用 JSON 函数精准提取关键字段。

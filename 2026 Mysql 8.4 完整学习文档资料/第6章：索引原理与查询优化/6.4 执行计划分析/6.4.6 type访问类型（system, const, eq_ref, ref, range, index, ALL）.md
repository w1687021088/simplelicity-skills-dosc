# type 访问类型（system, const, eq_ref, ref, range, index, ALL）

EXPLAIN 输出的 `type` 列是评估查询性能最重要的指标之一，表示 MySQL 如何访问表中的行。从性能最优到最差，依次为：`system` > `const` > `eq_ref` > `ref` > `fulltext` > `ref_or_null` > `index_merge` > `unique_subquery` > `index_subquery` > `range` > `index` > `ALL`。实际工作中最常见的是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL` 这六种，掌握它们的含义是读懂 EXPLAIN 的基础。

---

## system：系统表或单行表

```sql
-- type: system 是最优的访问类型（MyISAM 或 Memory 引擎的单行表）
-- InnoDB 表在满足特定条件时也可能出现 system

-- 典型场景：查询只有一行的系统表
EXPLAIN SELECT * FROM mysql.global_variables WHERE VARIABLE_NAME = 'max_connections' \G
-- 可能 type: system（如果表只有一行）

-- 在 MySQL 8.0 中，InnoDB 的 const 访问是最常见的最优状态
-- system 通常只在特殊情况下出现，一般可以视 const 为最优
```

---

## const：常量查询（唯一索引/主键等值）

```sql
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(100),
    UNIQUE INDEX idx_email (email)
);

-- 使用主键等值查询：
EXPLAIN SELECT * FROM users WHERE id = 100 \G
-- type: const  ← 最优，MySQL 把这行的所有列当作常量处理
-- rows: 1（精确定位，只有 1 行）

-- 使用唯一索引等值查询：
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com' \G
-- type: const  ← 唯一索引等值查询也是 const
-- MySQL 确信最多只有 1 行匹配（唯一约束保证）

-- const 的含义：查询结果是一个"常量"（确定的单行），
-- 在连接查询中，这行的值可以直接作为常量替换
```

---

## eq_ref：多表 JOIN 中被驱动表的唯一索引等值

```sql
-- eq_ref 出现在多表 JOIN 中，被驱动表通过唯一索引（或主键）与驱动表的列等值连接
EXPLAIN SELECT u.name, o.amount
FROM orders o
JOIN users u ON o.user_id = u.id      -- u.id 是主键，被驱动表用主键 eq_ref
WHERE o.status = 1 \G

-- id: 1, table: o, type: ref（驱动表，走 idx_status 或全表扫描）
-- id: 1, table: u, type: eq_ref  ← 被驱动表 users，用主键 id 精确连接
-- eq_ref：每次 JOIN 条件匹配驱动表的一行，被驱动表最多只有 1 行匹配

-- eq_ref 和 const 的区别：
-- const：外层（主查询）的等值查询，结果是单行常量
-- eq_ref：JOIN 中被驱动表的唯一索引等值，每次驱动行对应一行被驱动行
```

---

## ref：非唯一索引等值或最左前缀等值

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT NOT NULL,
    status TINYINT,
    INDEX idx_user (user_id),
    INDEX idx_user_status (user_id, status)
);

-- 普通（非唯一）索引的等值查询：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- type: ref  ← user_id 不是唯一索引，可能有多行匹配
-- 比 const 低一级（不能确定只有一行）

-- 联合索引的部分前缀等值：
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- type: ref  ← 联合索引等值（两列都是等值条件）

-- 使用 ref 的两个条件：
-- 1. 索引不是唯一索引（可能有多行匹配）
-- 2. 或虽然是联合唯一索引但只用了部分列（不能确保唯一）
```

---

## range：索引范围扫描

```sql
-- 使用 BETWEEN、>、<、IN、LIKE prefix% 等范围条件时
EXPLAIN SELECT * FROM orders WHERE user_id BETWEEN 100 AND 200 \G
-- type: range  ← B+树范围扫描，只扫描 [100, 200] 区间的叶子节点

EXPLAIN SELECT * FROM orders WHERE user_id IN (100, 200, 300) \G
-- type: range  ← IN 多值被优化为范围扫描

EXPLAIN SELECT * FROM orders WHERE user_id > 1000 \G
-- type: range

EXPLAIN SELECT * FROM users WHERE email LIKE 'alice%' \G
-- type: range  ← 前缀 LIKE 是范围扫描

-- range 的特点：
-- 只扫描索引中的一个连续区间（或多个独立区间）
-- 不需要扫描整个索引
-- 比 index（全索引扫描）高效得多
```

---

## index：全索引扫描

```sql
-- 扫描整个索引（从第一个叶子节点到最后一个），但不访问数据行
-- 通常出现在覆盖索引扫描中（Extra: Using index）或强制全索引排序

EXPLAIN SELECT user_id FROM orders ORDER BY user_id \G
-- type: index  ← 扫描整个 idx_user 索引（无 WHERE，全索引扫描）
-- Extra: Using index  ← 覆盖索引（只需要 user_id，在索引中）

-- type: index 但没有 Extra: Using index → 非覆盖的全索引扫描（效率低）
EXPLAIN SELECT * FROM orders ORDER BY user_id LIMIT 100 \G
-- type: index（扫描整个索引）+ 每行还需要回表（SELECT *）
-- 这种情况通常需要优化

-- type: index vs type: ALL：
-- type: index：扫描索引树（通常比数据行小，顺序 I/O）
-- type: ALL：扫描数据文件（聚簇索引，全表扫描）
-- 当索引比数据行小时，index 比 ALL 好；否则差别不大
```

---

## ALL：全表扫描（最差）

```sql
-- 扫描聚簇索引的所有叶子节点（即扫描所有行）
EXPLAIN SELECT * FROM orders WHERE amount > 500 \G
-- type: ALL  ← amount 没有索引，必须全表扫描

-- 全表扫描不一定是问题（对于小表）
-- 但对于大表（100 万行以上），ALL 通常是需要优化的信号

-- 修复：为 amount 建索引
ALTER TABLE orders ADD INDEX idx_amount (amount);
EXPLAIN SELECT * FROM orders WHERE amount > 500 \G
-- type: range  ← 现在走索引
```

---

## 其他常见 type 值

```sql
-- ref_or_null：类似 ref，但额外检查 NULL 值行
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR user_id IS NULL \G
-- type: ref_or_null（某些情况下）

-- index_merge：使用多个索引合并（OR 条件）
-- 详见 6.3.3

-- fulltext：使用全文索引
EXPLAIN SELECT * FROM articles WHERE MATCH(content) AGAINST ('MySQL') \G
-- type: fulltext  ← 使用 FULLTEXT 索引
```

## type 值从优到劣完整排序

| type | 含义 | 典型场景 |
|------|------|---------|
| system | 表只有一行（特殊）| 系统表 |
| const | 主键/唯一索引等值 | WHERE id = 1 |
| eq_ref | JOIN 中被驱动表主键/唯一索引等值 | JOIN ON t2.id = t1.fk |
| ref | 非唯一索引等值或联合索引前缀等值 | WHERE idx_col = val |
| range | 索引范围扫描 | WHERE col BETWEEN / IN / > |
| index | 全索引扫描 | 覆盖索引无 WHERE 或 ORDER BY 索引 |
| ALL | 全表扫描 | 无索引或优化器放弃索引 |

---

## 适用场景

- **性能快速评估**：看到 EXPLAIN 后第一眼先看 `type`，ALL 和 index 需要重点关注，const/ref/range 是合格状态，eq_ref/const 是最优状态
- **优化目标确认**：在做索引优化时，以将 `type: ALL` 变为 `type: range` 或更好为目标，验证索引添加后 type 的变化

---

## 常见问题

**`type: index` 和 `type: ALL` 哪个更好？**

大多数情况下 `type: index` 比 `type: ALL` 好，因为扫描索引通常比扫描数据文件（聚簇索引包含完整行）更小（索引文件 << 数据文件），且索引是顺序 I/O。但如果查询是 `SELECT *`（需要完整行），`type: index` 仍然需要对每行回表，最终效果与 ALL 类似。`type: index + Extra: Using index`（覆盖索引）才是真正高效的情况。

---

## 注意事项

- `type: ALL` 不一定都是问题。对于行数很少的表（几十到几百行），全表扫描的代价可以忽略，优化器可能比索引扫描更快（避免了索引 I/O + 回表）。只有在大表（通常 10 万行以上）的高频查询中，ALL 才是需要解决的性能问题。
- 在 MySQL 8.0+ 中，即使表上有合适的索引，优化器也可能因为统计信息不准确（如 Cardinality 估算偏差大）而选择 ALL。运行 `ANALYZE TABLE` 更新统计信息后再查看 EXPLAIN，可以确认是否是统计信息问题导致的 ALL。

---

## 总结

`type` 列是 EXPLAIN 中最核心的性能指标，从最优到最差：`system`（单行表）→ `const`（唯一索引等值）→ `eq_ref`（JOIN 中被驱动表唯一等值）→ `ref`（非唯一索引等值）→ `range`（索引范围）→ `index`（全索引扫描）→ `ALL`（全表扫描）。优化目标：在大表高频查询中，尽量将 ALL 和 index 优化为 ref 或 range；覆盖索引实现的 index（Extra: Using index）是特殊的高效情形。通过添加合适的索引、调整 WHERE 条件写法（避免函数操作、隐式转换）来改善 type。

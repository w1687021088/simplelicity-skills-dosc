# possible_keys 可能使用的索引

EXPLAIN 输出的 `possible_keys` 列显示了 MySQL 查询优化器在分析 WHERE 条件和 JOIN 条件时，认为理论上可以被使用的索引列表。注意这是"可能"使用的候选集，不代表最终一定会使用。优化器会对每个候选索引估算使用它的代价，最终从中选择代价最低的一个（记录在 `key` 列），或者判断全表扫描代价更低时放弃所有候选（`key` 为 NULL）。

---

## possible_keys 的基本含义

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user (user_id),
    INDEX idx_status (status),
    INDEX idx_user_status (user_id, status),
    INDEX idx_amount (amount)
);

-- 示例1：单列等值查询
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- possible_keys: idx_user, idx_user_status  ← 两个索引都可以用（user_id 都在）
-- key: idx_user_status（或 idx_user，取决于 Cardinality 估算）

-- 示例2：多列 WHERE 条件
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1 \G
-- possible_keys: idx_user, idx_status, idx_user_status
-- key: idx_user_status  ← 优化器选择联合索引（最高效）

-- 示例3：主键自动在 possible_keys 中（如果 WHERE 包含主键）
EXPLAIN SELECT * FROM orders WHERE id = 1001 \G
-- possible_keys: PRIMARY
-- key: PRIMARY
```

---

## possible_keys 为 NULL 的情况

```sql
-- possible_keys: NULL → 没有任何索引适用于 WHERE 条件
-- 这通常意味着：
-- 1. WHERE 条件中的列没有索引
-- 2. WHERE 条件中的列有索引，但索引失效（函数操作/类型不匹配等）

-- 无索引的列：
EXPLAIN SELECT * FROM orders WHERE amount > 500 \G
-- 如果 amount 没有索引：
-- possible_keys: NULL, key: NULL, type: ALL

-- 建索引后：
ALTER TABLE orders ADD INDEX idx_amount (amount);
EXPLAIN SELECT * FROM orders WHERE amount > 500 \G
-- possible_keys: idx_amount, key: idx_amount, type: range

-- 索引失效导致 possible_keys 为 NULL：
EXPLAIN SELECT * FROM orders WHERE YEAR(created_at) = 2025 \G
-- 如果 created_at 有索引 idx_created：
-- possible_keys: NULL  ← 函数操作使优化器认为无法使用索引
-- （实际上 idx_created 存在，但被函数操作破坏了使用条件）
```

---

## possible_keys 有值但 key 为 NULL 的情况

```sql
-- 这是一个重要的诊断场景：
-- 优化器知道有索引可以用，但选择了不用（全表扫描）

-- 场景1：索引选择性太低，优化器认为全表扫描更快
EXPLAIN SELECT * FROM orders WHERE status = 1 \G
-- 假设 status=1 占 80% 的行
-- possible_keys: idx_status（有候选索引）
-- key: NULL            ← 但优化器放弃了，选择全表扫描
-- type: ALL

-- 诊断：强制使用索引验证
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_status) WHERE status = 1 \G
-- key: idx_status, rows: 800000  ← 扫描 80% 的行 + 每行回表
-- 对比 ALL 的代价，全表扫描确实更快，优化器的判断是正确的

-- 场景2：统计信息过时，优化器估算错误
-- 解决：ANALYZE TABLE orders; 更新统计信息后重新 EXPLAIN
```

---

## possible_keys 的诊断价值

```sql
-- 分析 possible_keys 时需要关注的几种情况：

-- 情况1：possible_keys 为 NULL（无候选索引）
-- → 需要为 WHERE 条件列建索引

-- 情况2：possible_keys 有值，key = possible_keys 中的某个
-- → 索引被正常使用，关注 type 和 rows

-- 情况3：possible_keys 有值，key = NULL（放弃所有索引）
-- → 优化器判断全表扫描更优（通常因为选择性低）
-- → 考虑：是否需要改写查询、是否统计信息过时

-- 情况4：possible_keys 有多个，key 只用了一个
-- → 优化器在多个候选中选了最优的一个（正常行为）
-- → 如果选择的不是预期的索引，考虑用 FORCE INDEX/USE INDEX 干预

-- 情况5：possible_keys 没有预期的索引
-- → 检查该索引是否真实存在（SHOW INDEX FROM t）
-- → 检查 WHERE 条件是否触发了该索引的失效场景
```

## possible_keys 在多索引场景下的诊断

```sql
-- 查看所有候选索引，辅助判断为何优化器选了某个索引

-- 索引：idx_user(user_id), idx_user_status(user_id, status)
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- possible_keys: idx_user,idx_user_status
-- key: idx_user_status（优化器选择了联合索引）

-- 为什么选 idx_user_status 而不是 idx_user？
-- 两者都可以处理 WHERE user_id=100（最左前缀）
-- idx_user_status 的 Cardinality 可能更高（多列组合更唯一）
-- 但对于只需要 user_id 的查询，idx_user（更小）可能更合适

-- 手动测试两种索引的效果：
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_user) WHERE user_id = 100 \G
EXPLAIN SELECT * FROM orders FORCE INDEX (idx_user_status) WHERE user_id = 100 \G
-- 对比 rows 和 Extra 判断哪个更优
```

## 适用场景

- **索引建立效果验证**：建立新索引后，通过 EXPLAIN 检查 `possible_keys` 是否包含新索引，确认索引已被优化器纳入候选，且 `key` 中是否选择了新索引
- **索引失效诊断**：当 `possible_keys` 中没有预期的索引时（尽管该索引存在），说明该索引因某种原因被排除（WHERE 条件写法导致索引失效），需要检查函数操作、类型转换等失效场景

---

## 常见问题

**`possible_keys` 中出现了很多索引，是否说明索引太多了？**

不一定，但这是一个有意义的信号。`possible_keys` 中的每个索引代表一个优化器需要评估成本的候选，候选越多，优化器的选择计算开销越大（通常可以忽略不计）。更重要的是：如果 `possible_keys` 中有很多索引，但实际查询只用到其中一个（`key` 只有一个），那些从未出现在 `key` 中的索引可能是冗余或未使用的，可以通过 `performance_schema` 进一步确认，考虑删除。

---

## 注意事项

- `possible_keys` 是在查询分析阶段（不是执行阶段）生成的。对于含有子查询或派生表的复杂查询，内层子查询的 `possible_keys` 是相对于子查询自身的 WHERE 条件，与外层查询的 `possible_keys` 相互独立。
- 当 `possible_keys` 包含的索引与 `key` 不同时（优化器选择了一个"不那么明显"的索引），可以通过 `optimizer_trace` 查看优化器对每个候选索引的成本估算，理解选择逻辑。

---

## 总结

`possible_keys` 列出优化器认为可以用于当前 WHERE/JOIN 条件的候选索引，是"待评估"的集合。`key` 是从 `possible_keys` 中选出的最终索引。关键诊断点：`possible_keys = NULL` → 无候选，需要建索引；`possible_keys` 有值但 `key = NULL` → 优化器放弃所有候选（通常因为选择性低或统计信息问题）；`possible_keys` 包含多个但 `key` 只用一个 → 正常，优化器选择了成本最低的。`possible_keys` 不包含预期的索引 → 检查索引失效场景。

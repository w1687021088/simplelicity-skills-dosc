# 优化器提示 Hints（USE INDEX, FORCE INDEX, IGNORE INDEX）

当 MySQL 优化器因统计信息不准、成本估算偏差或特殊业务场景等原因做出了次优的索引选择时，可以通过优化器提示（Optimizer Hint）干预其决策。MySQL 提供了两类干预手段：一是传统的索引提示（Index Hint）—— `USE INDEX`、`FORCE INDEX`、`IGNORE INDEX`，通过 SQL 语句结构指定；二是 MySQL 8.0 引入的新式 Optimizer Hint（注释形式 `/*+ ... */`），功能更强大且支持更多场景。

---

## 传统索引提示

```sql
-- 语法位置：在表名之后、WHERE 子句之前
-- SELECT ... FROM table [[AS] alias] [index_hint_list] WHERE ...

-- USE INDEX：建议优化器只从指定索引中选择（不强制）
-- 如果指定的索引成本更高，优化器仍可能选择全表扫描
SELECT * FROM orders USE INDEX (idx_user_status)
WHERE user_id = 100 AND status = 1;

-- FORCE INDEX：强制使用指定索引（即使全表扫描更低代价也不用）
-- 优化器必须使用指定索引（除非该索引无法满足查询语义）
SELECT * FROM orders FORCE INDEX (idx_user_status)
WHERE user_id = 100 AND status = 1;

-- IGNORE INDEX：排除指定索引，优化器不考虑它
SELECT * FROM orders IGNORE INDEX (idx_old_status)
WHERE user_id = 100 AND status = 1;
-- 用于排除一个不应该被使用的低效索引

-- 可以指定多个索引：
SELECT * FROM orders USE INDEX (idx_user_status, idx_amount)
WHERE user_id = 100 AND amount > 500;

-- 针对特定操作指定索引：
-- FOR ORDER BY：只对 ORDER BY 操作生效
SELECT * FROM orders USE INDEX FOR ORDER BY (idx_created)
WHERE user_id = 100 ORDER BY created_at;

-- FOR GROUP BY：只对 GROUP BY 操作生效
SELECT user_id, COUNT(*) FROM orders USE INDEX FOR GROUP BY (idx_user)
WHERE status = 1 GROUP BY user_id;

-- FOR JOIN：只对 JOIN 操作生效
SELECT o.id FROM orders o USE INDEX FOR JOIN (idx_user_status)
JOIN users u ON o.user_id = u.id;
```

## MySQL 8.0+ 新式 Optimizer Hint

```sql
-- 新式 Optimizer Hint 使用注释格式：/*+ hint_name(...) */
-- 位置：SELECT 关键字之后
-- 优点：语义更清晰，支持子查询、派生表、CTE，不影响 SQL 语法解析

-- INDEX Hint：指定使用的索引
SELECT /*+ INDEX(o idx_user_status) */ o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1;

-- NO_INDEX Hint：排除指定索引
SELECT /*+ NO_INDEX(o idx_old_status) */ *
FROM orders o WHERE user_id = 100;

-- JOIN_ORDER Hint：指定 JOIN 的驱动顺序
SELECT /*+ JOIN_ORDER(u, o) */ o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = 1;
-- 强制 users 先（驱动表），orders 后（被驱动表）

-- JOIN_FIXED_ORDER Hint：完全固定 JOIN 顺序（按 FROM 子句顺序）
SELECT /*+ JOIN_FIXED_ORDER() */ o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id;

-- BNL/NO_BNL Hint（Block Nested Loop 控制）
SELECT /*+ NO_BNL(o) */ * FROM orders o JOIN order_items i ON o.id = i.order_id;

-- HASH_JOIN/NO_HASH_JOIN（MySQL 8.0.18+）
SELECT /*+ HASH_JOIN(o, u) */ o.id FROM orders o JOIN users u ON o.user_id = u.id;
```

## USE INDEX vs FORCE INDEX 的区别

| 对比维度 | USE INDEX | FORCE INDEX |
|---------|:---------:|:-----------:|
| 强制性 | 建议，优化器可以不从（选全表扫描）| 强制，优化器必须用 |
| 备选策略 | 可退回全表扫描 | 只能全表扫描或报错 |
| 适用场景 | 限定候选索引集 | 确信某索引最优时 |
| 风险 | 低 | 高（指定索引可能因数据变化失效）|

```sql
-- 验证区别：
-- 当 idx_user_status 选择性很低时（如 status=1 占 80%）：
EXPLAIN SELECT * FROM orders USE INDEX (idx_user_status) WHERE status = 1 \G
-- key: NULL（USE INDEX 无法强制，优化器仍选 ALL）

EXPLAIN SELECT * FROM orders FORCE INDEX (idx_user_status) WHERE status = 1 \G
-- key: idx_user_status（FORCE INDEX 强制使用，即使代价更高）
-- type: ref, rows: 800000（实际可能比全表扫描更慢）
```

## 传统 Index Hint vs 新式 Optimizer Hint 对比

| 对比维度 | 传统 Index Hint | 新式 Optimizer Hint |
|---------|:--------------:|:------------------:|
| 语法形式 | SQL 结构（FROM 后）| 注释（SELECT 后）|
| 支持子查询/CTE | 否 | 是 |
| 支持 JOIN 顺序 | 否 | 是（JOIN_ORDER）|
| 与工具兼容性 | 可能被 ORM 过滤 | 注释形式，工具兼容性好 |
| 推荐程度（8.0+）| 仍支持但不推荐新写 | 推荐 |

## 适用场景

- **统计信息不准时的临时干预**：当 EXPLAIN 发现优化器选错了索引（因为统计信息过时），在修复统计信息（ANALYZE TABLE）之前，使用 `FORCE INDEX` 作为临时措施保证查询性能稳定，等统计信息修复后再移除 Hint
- **关键查询的执行计划固化**：对于核心业务的高频查询（如主页 Feed、订单列表），不希望因为数据分布变化或版本升级导致执行计划变化，使用 Optimizer Hint 固定执行计划，保证性能的长期稳定性

## 常见问题

**使用 `FORCE INDEX` 后，如果该索引被删除了，查询会怎样？**

如果 `FORCE INDEX` 指定的索引被删除（`DROP INDEX`），该查询会报错（`ERROR 1176: Key 'idx_name' doesn't exist in table`）。这是 `FORCE INDEX` 的一个风险点——索引依赖性变为硬依赖。在删除索引前，需要先检查所有使用了 `FORCE INDEX` 或 `USE INDEX` 引用该索引的 SQL，及时移除 Hint 或替换为新索引名。相比之下，新式 Optimizer Hint（`/*+ INDEX(t idx_name) */`）的表现相同，也会报错。唯一的区别是：如果用 `IGNORE INDEX` 排除了一个已删除的索引，不会报错（因为忽略不存在的索引是合法的）。

---

## 注意事项

- `FORCE INDEX` 是一种绕过优化器的硬编码手段，在大多数情况下，应优先通过修复统计信息（`ANALYZE TABLE`）、添加或优化索引、建立直方图等方式让优化器自己做出正确决策，而不是依赖 `FORCE INDEX`。`FORCE INDEX` 会让执行计划不再随数据分布变化而自适应调整，长期使用可能在数据变化后产生负面影响。
- 在分库分表（如 ShardingSphere）或 ORM 框架（如 MyBatis、Hibernate）的环境中，SQL 中的传统 Index Hint（`USE INDEX`/`FORCE INDEX`）有时会被中间件或 ORM 过滤掉，导致 Hint 无效。新式 Optimizer Hint（注释形式）通常能更好地穿透这些层次（注释不会被过滤），在这类场景下更可靠。

---

## 总结

传统索引提示：`USE INDEX`（建议，可退回全表扫描）、`FORCE INDEX`（强制，不管代价）、`IGNORE INDEX`（排除指定索引），写在表名之后、WHERE 之前，还支持 `FOR ORDER BY`/`FOR JOIN`/`FOR GROUP BY` 针对特定操作。MySQL 8.0+ 新式 Optimizer Hint（`/*+ ... */`）功能更强：`INDEX`/`NO_INDEX`（索引控制）、`JOIN_ORDER`（JOIN 顺序）、`HASH_JOIN`（哈希连接控制）等，支持子查询和 CTE。原则：优先通过修复统计信息和索引设计解决问题，Hint 只作为最后手段。新写 SQL 时推荐使用新式 Optimizer Hint，不推荐继续使用传统 Index Hint。

# 批量键访问 BKA（Batched Key Access）

批量键访问（Batched Key Access，BKA）是 MySQL 5.6 引入的 JOIN 优化技术，用于改进被驱动表有索引的嵌套循环连接（Index NLJ）中的 I/O 效率。传统 Index NLJ 对驱动表的每一行，分别用连接键查被驱动表的索引，每次都是独立的随机 I/O；BKA 通过将驱动表的多个连接键值批量收集到 Join Buffer，然后利用 Multi-Range Read（MRR）一次性按主键顺序批量读取被驱动表的数据行，将多次随机 I/O 转换为顺序 I/O，提高磁盘访问效率。

---

## BKA 的工作原理

```
传统 Index NLJ 的执行过程（一次处理一行）：
1. 从驱动表取一行（row1），得到 join_key = 100
2. 用 join_key=100 查被驱动表的二级索引，得到主键 PK = (5, 12, 20)
3. 回表：分别用 PK=5、PK=12、PK=20 读取被驱动表完整行（3次随机 I/O）
4. 从驱动表取下一行（row2），重复步骤2~3...

每行驱动行 → 独立随机 I/O

BKA 的执行过程（批量处理）：
1. 从驱动表取一批行，将其连接键值收集到 Join Buffer：
   [row1: join_key=100, row2: join_key=200, row3: join_key=150, ...]
2. 用批量键值查被驱动表二级索引，收集所有匹配的主键列表：
   [(5,12,20), (8,30), (15,25)]
3. 将主键列表排序（按主键顺序）：[5, 8, 12, 15, 20, 25, 30]
4. 按顺序批量读取被驱动表的完整行（顺序 I/O，MRR）
5. 与 Join Buffer 中的驱动行匹配后输出结果

多行驱动行 → 批量主键 → 排序后顺序 I/O → 大幅减少随机 I/O
```

## BKA 的触发条件

```sql
-- BKA 的触发条件：
-- 1. 被驱动表使用索引（Index NLJ，有二级索引）
-- 2. 需要回表（不是覆盖索引）
-- 3. BKA 和 MRR 同时开启

-- 查看 BKA 和 MRR 的控制开关：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- batched_key_access=off（默认关闭！需要手动开启）
-- mrr=on（MRR 默认开启）
-- mrr_cost_based=on（基于成本决定是否使用 MRR，默认开启）

-- 开启 BKA（需要同时确保 MRR 已开启）：
SET SESSION optimizer_switch = 'batched_key_access=on,mrr=on,mrr_cost_based=off';
-- mrr_cost_based=off 表示总是使用 MRR（不基于成本决策，更稳定）
-- 生产环境建议：先测试再上线
```

## EXPLAIN 中识别 BKA

```sql
-- 开启 BKA 后，EXPLAIN 的 Extra 列会显示相关信息

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT NOT NULL,
    status TINYINT,
    amount DECIMAL(10,2),
    INDEX idx_user (user_id)
);

-- 场景：orders 有 user_id 索引，需要取完整行（回表）
SET SESSION optimizer_switch = 'batched_key_access=on,mrr=on,mrr_cost_based=off';

EXPLAIN SELECT o.id, o.amount, u.name
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.status = 'active' \G

-- 开启 BKA 后的输出：
-- table: u, type: ref, Extra: NULL（驱动表）
-- table: o, type: ref, key: idx_user
--   Extra: Using join buffer (Batched Key Access)
--          ↑ 明确标识使用了 BKA

-- 未开启 BKA 时的输出（传统 Index NLJ）：
-- table: o, type: ref, key: idx_user
--   Extra: NULL（无任何 join buffer 标记）
```

## join_buffer_size 对 BKA 的影响

```sql
-- BKA 使用 join_buffer_size 缓存驱动表的批量键值
-- join_buffer_size 越大，每批处理的行数越多，顺序 I/O 的效率越高

SHOW VARIABLES LIKE 'join_buffer_size';
-- 默认: 262144（256KB）

-- 估算每批处理行数：
-- 驱动表每行在 Join Buffer 中占用：连接键宽度 + 少量元数据
-- INT 键：约 4 字节
-- 256KB / 4字节 = 约 65536 行/批（足够大多数场景）

-- 如果驱动表连接键较宽（如 BIGINT + VARCHAR）：
-- 可以适当增大 join_buffer_size
SET SESSION join_buffer_size = 4 * 1024 * 1024;  -- 4MB

-- BKA 与 Hash Join 的 join_buffer_size 使用相同参数
-- 注意高并发时的内存总量：并发数 × join_buffer_size
```

## BKA 的性能收益场景

```sql
-- BKA 适合的场景：
-- 1. 被驱动表的二级索引选择性适中（有回表操作）
-- 2. 磁盘 I/O 是瓶颈（HDD 或 SSD 的随机 I/O 成本高）
-- 3. 驱动表传递的连接键值是分散的（随机分布，回表是随机 I/O）

-- 典型场景：用户订单查询
-- drivers: users（活跃用户）→ orders（用 user_id 索引，需要回表取 amount）
-- 传统 NLJ：每个 user_id → 随机读几行 orders 的数据页
-- BKA：批量收集 user_id → 排序主键 → 顺序读取 orders 数据页

-- BKA 不适合的场景：
-- 1. 被驱动表是覆盖索引（无回表，不需要 MRR 优化）
-- 2. Buffer Pool 命中率很高（内存读已经是顺序的，BKA 收益低）
-- 3. 驱动表结果集很小（如只有几行，批量化无意义）
```

## BKA 与 MRR 的关系

```sql
-- BKA 依赖 MRR（Multi-Range Read）实现批量顺序读取

-- MRR 独立于 BKA 工作时：
-- 用于单表的 range 查询（不是 JOIN），批量读取范围内的行
-- EXPLAIN Extra: Using MRR

-- BKA 使用 MRR 时：
-- 将 Join Buffer 中的多个连接键映射为多个主键范围
-- MRR 负责将这些主键排序并顺序读取
-- EXPLAIN Extra: Using join buffer (Batched Key Access)

-- MRR 的参数控制：
SHOW VARIABLES LIKE 'read_rnd_buffer_size';
-- 默认: 262144（256KB）
-- MRR 使用 read_rnd_buffer_size 缓存主键列表，在排序后顺序读取
-- 与 join_buffer_size（BKA 的 Join Buffer）是两个不同的缓冲区

-- 完整开启 BKA + MRR 的最优配置：
SET SESSION optimizer_switch = 'batched_key_access=on,mrr=on,mrr_cost_based=off';
SET SESSION join_buffer_size = 4 * 1024 * 1024;       -- 4MB
SET SESSION read_rnd_buffer_size = 4 * 1024 * 1024;   -- 4MB
```

## BKA vs 普通 Index NLJ vs Hash Join 的对比

| 对比维度 | Index NLJ（无 BKA）| BKA（Index NLJ + 批量）| Hash Join |
|---------|:-----------------:|:---------------------:|:---------:|
| 适用场景 | 被驱动表有索引 | 被驱动表有索引+需回表 | 被驱动表无索引 |
| I/O 模式 | 随机 I/O | 排序后顺序 I/O | 全表顺序扫描 |
| 内存使用 | 无额外缓冲 | join_buffer_size | join_buffer_size |
| 磁盘 I/O 效率 | 一般（随机）| 高（顺序）| 中（全表扫描）|
| 默认状态 | 开启 | 关闭（需手动开启）| 开启（8.0.18+）|

## 适用场景

- **HDD 磁盘上的大表 JOIN 优化**：在传统机械硬盘（HDD）环境中，随机 I/O 的代价远高于顺序 I/O，BKA 将多次随机回表转换为排序后的顺序读取，在磁盘 I/O 密集的环境中可以显著降低查询时间
- **批量订单/用户数据关联查询**：例如查询某批活跃用户（几千个）的所有订单详情，orders 表有 user_id 索引但没有覆盖索引（需要回表取 amount 等字段），BKA 能高效批量读取这批用户的订单

## 常见问题

**BKA 默认是关闭的，为什么不默认开启？**

BKA 默认关闭的原因：①BKA 需要额外的 Join Buffer 内存（高并发时总内存消耗增加）；②在 Buffer Pool 命中率很高的场景（纯内存查询），BKA 的顺序化 I/O 优化几乎无收益；③BKA 依赖 MRR，而 MRR 本身是有成本的（主键排序、缓冲管理）；④对于小结果集的驱动表，批量化的开销反而高于收益。MySQL 保守地将其设为默认关闭，让 DBA 根据实际场景（磁盘密集型、大表关联）决定是否开启，避免对所有场景都造成负担。

## 注意事项

- BKA 只对二级索引回表有效（被驱动表使用了二级索引但还需要回聚簇索引取完整行）。如果被驱动表使用的是覆盖索引（`Extra: Using index`），则不需要回表，BKA 无法进一步优化（已经是最高效的了）。
- 开启 BKA 时，`mrr_cost_based=off` 表示强制使用 MRR 而不基于成本判断，适合明确知道需要顺序 I/O 优化的场景。如果设为 `mrr_cost_based=on`（默认），MySQL 会根据估算的随机 I/O 代价决定是否启用 MRR，可能在某些情况下放弃 MRR/BKA。生产环境建议先关闭成本模型评估，测试效果后再决定最终配置。

## 总结

BKA（批量键访问）通过将多行驱动行的连接键批量收集到 Join Buffer，利用 MRR（Multi-Range Read）将分散的回表主键排序为顺序读取，把随机 I/O 转换为顺序 I/O。默认关闭，需手动启用：`SET optimizer_switch='batched_key_access=on,mrr=on,mrr_cost_based=off'`。触发条件：被驱动表有二级索引 + 需要回表（非覆盖索引）。EXPLAIN 标识：`Using join buffer (Batched Key Access)`。性能收益：磁盘 I/O 密集场景（HDD）收益最大；Buffer Pool 命中率高的场景收益有限。通过 `join_buffer_size` 和 `read_rnd_buffer_size` 调整批量大小。适合大表无覆盖索引的关联查询，不适合覆盖索引查询和小结果集关联。

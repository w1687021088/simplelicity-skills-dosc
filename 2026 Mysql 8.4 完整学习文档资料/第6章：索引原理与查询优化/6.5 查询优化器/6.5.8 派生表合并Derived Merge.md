# 派生表合并 Derived Merge

派生表（Derived Table）是 SQL 中 FROM 子句里的子查询（内联视图）。在 MySQL 5.7 及之前，每个派生表都需要被物化为一个临时表，然后外层查询再对该临时表操作——这会引入额外的临时表写入和读取开销。MySQL 8.0 引入了**派生表合并优化（Derived Merge）**，在满足条件时，将派生表的查询逻辑合并到外层查询中，消除中间临时表，可以显著减少查询代价，特别是对大结果集的派生表效果明显。

---

## 派生表合并的工作原理

```sql
-- 派生表示例（未合并时）：
EXPLAIN SELECT t.user_id, t.total
FROM (
    SELECT user_id, SUM(amount) AS total
    FROM orders WHERE status = 1
    GROUP BY user_id
) AS t
WHERE t.total > 500 \G

-- MySQL 5.7（无合并）：
-- id: 1, select_type: PRIMARY, table: <derived2>   ← 外层扫描临时表
-- id: 2, select_type: DERIVED, table: orders        ← 派生表物化为临时表
-- 执行过程：
-- 1. 扫描 orders（WHERE status=1），聚合结果放入临时表
-- 2. 扫描临时表，过滤 total > 500

-- MySQL 8.0（有合并，如果简单派生表满足条件）：
-- 某些情况下 EXPLAIN 只显示 1 行（无 DERIVED），说明合并成功
-- 派生表的过滤条件 WHERE t.total > 500 被下推到外层处理
```

---

## 派生表合并的触发条件

```sql
-- Derived Merge 不是对所有派生表都生效，有以下限制：

-- 可以合并的派生表：
-- 1. 简单的 SELECT（无聚合、无 DISTINCT、无 GROUP BY、无 ORDER BY）
-- 2. 无 LIMIT/OFFSET 子句
-- 3. 无窗口函数（Window Functions）
-- 4. 不含 UNION
-- 5. 外层查询可以利用内层的索引（合并后仍能走索引）

-- 无法合并的派生表（会物化）：
-- 1. 含 GROUP BY（聚合运算）
SELECT t.user_id, t.cnt
FROM (SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id) AS t
WHERE t.cnt > 5;
-- → 含 GROUP BY，无法合并，必须物化临时表

-- 2. 含 DISTINCT
SELECT t.user_id
FROM (SELECT DISTINCT user_id FROM orders WHERE status = 1) AS t;
-- → 含 DISTINCT，无法合并

-- 3. 含 ORDER BY + LIMIT
SELECT t.id
FROM (SELECT id FROM orders ORDER BY created_at LIMIT 100) AS t
WHERE t.id > 1000;
-- → ORDER BY + LIMIT，无法合并

-- 4. 含 UNION
SELECT t.id
FROM (SELECT id FROM orders WHERE status=1 UNION SELECT id FROM orders WHERE status=2) AS t;
-- → UNION，无法合并

-- 可以合并的示例（简单过滤）：
SELECT t.id, t.user_id
FROM (SELECT id, user_id FROM orders WHERE status = 1) AS t
WHERE t.user_id > 100;
-- → 只有简单 WHERE 过滤，合并为：
-- SELECT id, user_id FROM orders WHERE status=1 AND user_id>100
```

## 通过 EXPLAIN 验证是否发生了合并

```sql
-- 判断方法：EXPLAIN 输出中是否出现 <derived2> 或 select_type=DERIVED

-- 未合并（物化临时表）：
EXPLAIN SELECT t.user_id, t.total
FROM (SELECT user_id, SUM(amount) AS total FROM orders WHERE status=1 GROUP BY user_id) AS t
WHERE t.total > 500 \G
-- id: 1, table: <derived2>  ← 存在 <derived2>，说明派生表被物化
-- id: 2, select_type: DERIVED, table: orders

-- 已合并（无临时表）：
EXPLAIN SELECT t.id, t.user_id
FROM (SELECT id, user_id FROM orders WHERE status = 1 AND amount > 100) AS t
WHERE t.user_id > 100 \G
-- id: 1, select_type: SIMPLE, table: orders  ← 只有一行，派生表被合并！
-- Extra: Using where（合并后的 WHERE 条件）
-- 合并后等价于：SELECT id, user_id FROM orders WHERE status=1 AND amount>100 AND user_id>100
```

## 控制 Derived Merge 的开关

```sql
-- 通过 optimizer_switch 控制是否启用 Derived Merge
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- derived_merge=on  ← 默认开启

-- 关闭（诊断使用，不建议生产环境关闭）
SET SESSION optimizer_switch = 'derived_merge=off';
-- 关闭后，所有满足条件的派生表都会被物化
-- 用于对比合并 vs 物化的性能差异

-- 恢复
SET SESSION optimizer_switch = 'derived_merge=on';

-- 针对单个查询关闭（使用 Optimizer Hint）
SELECT /*+ NO_MERGE(t) */ t.id, t.user_id
FROM (SELECT id, user_id FROM orders WHERE status = 1) AS t
WHERE t.user_id > 100;
-- 强制不合并派生表 t，即使满足合并条件
```

## 派生表合并 vs 物化的性能对比

```sql
-- 对于大结果集的派生表（内层查询返回大量行）：
-- 物化：创建临时表（内存或磁盘）+ 写入全部行 + 外层扫描临时表
-- 合并：不创建临时表，直接在原始表上应用合并后的条件

-- 性能差异估算：
-- 物化内层结果：orders 中 status=1 有 50 万行
-- → 写入 50 万行到临时表：50万次写入
-- → 外层过滤 user_id>100：50万次读取
-- 总计：100 万次操作

-- 合并后直接在 orders 上过滤（status=1 AND user_id>100）：
-- 假设联合索引(status, user_id)：只扫描 user_id>100 且 status=1 的行
-- 可能只有 10 万行
-- 总计：10 万次操作 → 省去了 90 万次操作！

-- 结论：能合并时，合并通常优于物化（特别是外层有额外过滤条件时）
-- 但对于必须物化的情况（GROUP BY 等），MySQL 会自动选择物化
```

## 适用场景

- **重构旧版 SQL 中的派生表**：对于从 MySQL 5.7 迁移的业务，原本为了规避 5.7 限制而使用的派生表写法，在 MySQL 8.0 上可以验证是否发生了合并（通过 EXPLAIN），如果发生了合并，说明 8.0 自动做了优化；如果未合并，考虑改写 SQL 使其满足合并条件
- **诊断含派生表的慢查询**：当发现含有派生表的查询很慢时，首先通过 EXPLAIN 检查是否发生了合并。若存在 `<derived2>` 说明在做临时表物化，可以尝试改写派生表（去掉 GROUP BY/DISTINCT/LIMIT 等阻碍合并的语句），或者用 CTE 替代派生表（MySQL 8.0 CTE 也可能发生合并）

## 常见问题

**为什么 MySQL 8.0 中有的简单派生表仍然物化（出现 `<derived2>`）？**

即使派生表语法上满足合并条件，某些情况下优化器仍会选择物化：①合并后的查询比物化后的查询成本更高（优化器成本估算决定）；②派生表被引用多次（如同一个 CTE 被引用多次）；③含有 LATERAL 关键字的侧向派生表；④一些复杂的内联视图结构让优化器无法确保合并的安全性。可以通过 `/*+ MERGE(alias) */` Hint 强制合并，或通过 `optimizer_switch='derived_merge=off'` 关闭合并后对比性能，确定合并是否真的有益。

---

## 注意事项

- 派生表合并虽然通常能提高性能，但不是在所有情况下都有益。对于极复杂的派生表（如多层嵌套）或特殊的数据分布，物化反而可能更快（物化后可以对临时表建内部索引）。MySQL 优化器通过成本估算自动决策，开发者无需手动干预大多数情况。
- 在 MySQL 8.0 中，CTE（`WITH` 子句）的处理方式类似派生表：简单 CTE 可以被内联（合并），引用多次的 CTE 会被物化（避免重复执行）。`WITH RECURSIVE` 的递归 CTE 始终物化，无法合并。

---

## 总结

派生表合并（Derived Merge）是 MySQL 8.0 的优化特性（`optimizer_switch='derived_merge=on'`，默认开启），将满足条件的派生表逻辑内联到外层查询，消除中间临时表。合并条件：派生表无 GROUP BY、DISTINCT、ORDER BY+LIMIT、UNION、窗口函数。验证方式：EXPLAIN 无 `<derived2>` 和 `DERIVED` 行表示合并成功。控制：`optimizer_switch='derived_merge=off'` 关闭；`/*+ NO_MERGE(alias) */` 针对单个查询关闭；`/*+ MERGE(alias) */` 强制合并。合并效果：消除临时表写入/读取开销，允许外层过滤条件被下推到索引层处理，通常显著提升大结果集派生表查询的性能。

# Cost Model 成本模型配置

MySQL 的 Cost Model（成本模型）是 CBO（基于成本的优化器）进行成本估算的底层参数框架，定义了各种操作（读取磁盘页、处理内存页、CPU 处理每行、创建临时表等）的成本单位。通过调整这些参数，可以改变优化器的成本估算结果，进而影响索引选择、JOIN 策略、是否使用临时表等决策。MySQL 8.0 中成本参数存储在 `mysql.server_cost` 和 `mysql.engine_cost` 两张表中，支持运行时修改。

---

## 成本参数存储表

```sql
-- mysql.server_cost：服务器层操作的成本参数
SELECT * FROM mysql.server_cost \G

-- 字段含义：
-- cost_name：操作名称
-- cost_value：当前配置值（NULL 表示使用 default_value）
-- last_update：最后更新时间
-- comment：说明
-- default_value：默认值

-- mysql.engine_cost：存储引擎层操作的成本参数
SELECT * FROM mysql.engine_cost \G
-- 额外字段：
-- engine_name：存储引擎名（DEFAULT 表示对所有引擎生效）
-- device_type：设备类型（0=旋转硬盘，1=SSD，通常为 0）
```

## server_cost 参数详解

```sql
SELECT cost_name, default_value, cost_value
FROM mysql.server_cost;

-- 关键参数：

-- disk_temptable_create_cost: 20.0
-- 创建磁盘临时表的成本（相比内存临时表高很多）
-- 值越大，优化器越倾向于避免磁盘临时表

-- disk_temptable_row_cost: 0.5
-- 向磁盘临时表写入每行的成本

-- key_compare_cost: 0.05
-- 比较两个索引键值的 CPU 成本（影响排序和 GROUP BY）

-- memory_temptable_create_cost: 1.0
-- 创建内存临时表的成本

-- memory_temptable_row_cost: 0.1
-- 向内存临时表写入每行的成本

-- row_evaluate_cost: 0.1
-- 处理每行数据（条件评估）的 CPU 成本
-- 这是最基础的成本单位，影响几乎所有估算
```

---

## engine_cost 参数详解

```sql
SELECT cost_name, engine_name, device_type, default_value, cost_value
FROM mysql.engine_cost;

-- io_block_read_cost: 1.0
-- 从磁盘读取一个数据页（block）的 I/O 成本
-- 这是 I/O 成本的基准单位
-- 对于全表扫描、索引范围扫描等涉及磁盘 I/O 的操作影响最大

-- memory_block_read_cost: 0.25
-- 从 Buffer Pool（内存）读取一个数据页的成本
-- 是 io_block_read_cost 的 1/4（内存访问比磁盘快约 4 倍）
-- 如果 Buffer Pool 命中率高，优化器会倾向于全扫描而非索引扫描

-- 两者的比值（io_block_read_cost / memory_block_read_cost）反映了
-- 磁盘 I/O 与内存读取的相对代价
-- 对于纯 SSD 存储，可以考虑降低这个比值（磁盘 I/O 更快）
```

## 修改成本参数

```sql
-- 修改 server_cost 参数：
-- 将 row_evaluate_cost 从默认 0.1 改为 0.2（告诉优化器 CPU 更贵）
UPDATE mysql.server_cost
SET cost_value = 0.2
WHERE cost_name = 'row_evaluate_cost';

-- 刷新使修改立即生效：
FLUSH OPTIMIZER_COSTS;

-- 验证修改：
SELECT cost_name, cost_value, default_value
FROM mysql.server_cost
WHERE cost_name = 'row_evaluate_cost';

-- 恢复为默认值（将 cost_value 设为 NULL）：
UPDATE mysql.server_cost
SET cost_value = NULL
WHERE cost_name = 'row_evaluate_cost';
FLUSH OPTIMIZER_COSTS;

-- 修改 engine_cost 参数（以 io_block_read_cost 为例）：
UPDATE mysql.engine_cost
SET cost_value = 2.0
WHERE cost_name = 'io_block_read_cost' AND engine_name = 'DEFAULT';
FLUSH OPTIMIZER_COSTS;
-- 将磁盘 I/O 成本翻倍 → 优化器更倾向于用索引减少磁盘 I/O
```

## 典型调整场景

```sql
-- 场景1：服务器搭载 SSD（磁盘 I/O 更快），调低 I/O 成本比
-- 目的：SSD 上磁盘 I/O 不比内存慢那么多，减小比值避免全表扫描被高估

UPDATE mysql.engine_cost SET cost_value = 0.5
WHERE cost_name = 'io_block_read_cost' AND engine_name = 'DEFAULT';
-- io_block_read_cost 从 1.0 降到 0.5
-- 磁盘 I/O 成本降低 → 全表扫描成本相对降低
-- 可能让优化器在某些情况下更倾向于全表扫描

FLUSH OPTIMIZER_COSTS;

-- 场景2：减少磁盘临时表的创建（内存充足，不想让磁盘临时表影响性能）
UPDATE mysql.server_cost SET cost_value = 40.0
WHERE cost_name = 'disk_temptable_create_cost';
-- 磁盘临时表创建成本翻倍 → 优化器更极力避免磁盘临时表
-- 可能导致更多的 memory_temptable 使用（但内存临时表超限仍会升级到磁盘）

FLUSH OPTIMIZER_COSTS;

-- 场景3：高 CPU 负载的服务器，提高 CPU 相关成本
UPDATE mysql.server_cost SET cost_value = 0.2
WHERE cost_name = 'row_evaluate_cost';
-- CPU 处理每行的成本翻倍 → 优化器更倾向于减少处理行数
-- 可能更积极地利用索引过滤，减少传入 Server 层的行数

FLUSH OPTIMIZER_COSTS;
```

## 成本参数与 EXPLAIN FORMAT=JSON 的关系

```sql
-- 通过 EXPLAIN FORMAT=JSON 查看成本参数对执行计划的影响
-- cost_info.query_cost 是基于当前成本参数估算的总成本

-- 修改 io_block_read_cost 前后对比：
EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 100 \G
-- query_cost: 100.5（默认参数）

UPDATE mysql.engine_cost SET cost_value = 0.5
WHERE cost_name = 'io_block_read_cost' AND engine_name = 'DEFAULT';
FLUSH OPTIMIZER_COSTS;

EXPLAIN FORMAT=JSON SELECT * FROM orders WHERE user_id = 100 \G
-- query_cost: 55.3（io 成本降低后，总成本降低）

-- 注意：成本降低不意味着实际执行更快，只是优化器的估算值变化
-- 如果修改后优化器选择了不同的执行计划，才会影响实际性能
```

## 适用场景

- **SSD 服务器的优化器参数调整**：在 SSD 或 NVMe 存储的服务器上，磁盘 I/O 速度远高于传统 HDD，默认的 `io_block_read_cost` 可能高估了磁盘读取的代价。适当降低 `io_block_read_cost`（如从 1.0 调到 0.5~0.75），让优化器的估算更符合实际硬件性能
- **执行计划稳定性调整**：当优化器在某些情况下频繁在全表扫描和索引扫描之间切换（导致性能不稳定）时，通过微调成本参数（而不是使用 FORCE INDEX）让优化器稳定选择一种方案，比直接使用 Hint 更灵活（影响所有类似查询，无需逐条修改 SQL）

## 常见问题

**修改成本参数是否会永久生效，重启后还有效吗？**

`FLUSH OPTIMIZER_COSTS` 使修改立即对新连接生效（已有连接需要断开重连）。由于成本参数存储在 `mysql.server_cost` 和 `mysql.engine_cost` 这两张系统表中（持久化到磁盘），重启 MySQL 后修改仍然有效（不会恢复为默认值）。要恢复默认值，需要将 `cost_value` 更新为 `NULL`（表示使用 `default_value`）并 `FLUSH OPTIMIZER_COSTS`。建议修改成本参数前备份原始配置，或记录修改内容，便于将来恢复。

---

## 注意事项

- 修改成本参数是一个全局操作，会影响该 MySQL 实例上所有数据库的所有查询的优化器决策，不能针对单个查询或会话设置。在生产环境中调整成本参数需要非常谨慎，应在测试环境充分验证后再应用到生产，并监控修改后的执行计划变化。
- 成本参数调整只影响优化器的成本估算，不改变实际的执行逻辑（不能让磁盘真的变快）。如果优化器因成本参数调整选择了一个实际上更差的执行计划，会导致真实性能下降。调整后应通过监控慢查询日志（slow query log）持续观察，确认调整方向正确。

---

## 总结

MySQL 的 Cost Model 成本参数存储在 `mysql.server_cost`（服务器层：CPU 代价、临时表代价）和 `mysql.engine_cost`（引擎层：磁盘/内存 I/O 代价）中。关键参数：`io_block_read_cost`（磁盘 I/O 成本，默认 1.0）、`memory_block_read_cost`（内存读取成本，默认 0.25）、`row_evaluate_cost`（CPU 处理每行成本，默认 0.1）。通过 `UPDATE mysql.server_cost SET cost_value=x`  + `FLUSH OPTIMIZER_COSTS` 修改。典型调整：SSD 降低 `io_block_read_cost`；高 CPU 负载增大 `row_evaluate_cost`；避免磁盘临时表增大 `disk_temptable_create_cost`。修改影响全局，需谨慎，建议测试环境验证后再上生产。

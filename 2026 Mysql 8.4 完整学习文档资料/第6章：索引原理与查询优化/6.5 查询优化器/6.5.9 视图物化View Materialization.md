# 视图物化 View Materialization

在 MySQL 中，"物化"（Materialization）是指将子查询或视图的结果集执行一次并存储为临时表，供后续查询步骤使用，而不是在每次需要时重复执行。与派生表合并（将子查询内联到外层查询）相对，物化是另一种处理子查询和视图的策略。MySQL 在以下情况使用物化：当子查询结果需要被多次引用（如 CTE 被引用多次）、当子查询无法被合并（含 GROUP BY/DISTINCT 等）、或当优化器判断物化后再查询的总代价低于其他方案时。

---

## MySQL 中的物化类型

```sql
-- 物化（Materialization）出现在以下场景：

-- 1. 不可合并的派生表（DERIVED）
EXPLAIN SELECT t.user_id, t.total
FROM (SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id) AS t
WHERE t.total > 500 \G
-- select_type: DERIVED → 内层聚合查询物化为临时表
-- Extra: Using temporary（创建了内存/磁盘临时表）

-- 2. IN 子查询物化（MATERIALIZED）
EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'CN') \G
-- select_type: MATERIALIZED → 子查询结果物化为哈希临时表
-- 物化后与 orders 做哈希连接

-- 3. CTE 多次引用（自动物化避免重复执行）
WITH active_users AS (
    SELECT id, name FROM users WHERE status = 'active'
)
SELECT o.id, a.name
FROM orders o
JOIN active_users a ON o.user_id = a.id
UNION
SELECT o2.id, a2.name
FROM orders o2
JOIN active_users a2 ON o2.user_id = a2.id AND o2.status = 1;
-- active_users 被引用 2 次 → 物化为临时表，执行一次后两处复用
```

---

## 物化的执行过程

```
IN 子查询物化的执行步骤：
1. 执行内层子查询（SELECT id FROM users WHERE country = 'CN'）
2. 将结果集物化为哈希临时表（每个 id 作为 key）
3. 扫描外层表 orders，每行用 user_id 在哈希临时表中查找匹配
4. 匹配成功的行包含在最终结果中

对比非物化（相关子查询方式）：
1. 扫描外层表 orders 的每一行
2. 对每一行执行内层子查询（SELECT id FROM users WHERE country='CN'）
3. 1000000 行 orders → 执行 1000000 次子查询！

物化的优势：内层子查询只执行一次，建立哈希表后复用
适合场景：外层表很大，内层子查询结果集中等（可以放入内存临时表）
```

## 控制物化的 optimizer_switch

```sql
-- 查看物化相关的优化器开关：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- materialization=on     → IN 子查询物化（默认开启）
-- subquery_materialization_cost_based=on  → 基于成本决定是否物化（默认开启）

-- 关闭物化（测试对比用）：
SET SESSION optimizer_switch = 'materialization=off';
EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE country = 'CN') \G
-- 关闭后可能显示：select_type: DEPENDENT SUBQUERY（退化为相关子查询，性能差）

-- 恢复：
SET SESSION optimizer_switch = 'materialization=on';

-- subquery_materialization_cost_based=on 的含义：
-- 优化器根据成本决定是物化还是直接执行（基于内层子查询预期结果集大小）
-- 如果预期结果集太大（超过某个阈值），可能放弃物化
```

## 物化与 MySQL 视图（VIEW）的关系

```sql
-- MySQL 中普通视图（VIEW）默认是"可合并视图"（Mergeable View）
-- 不是物化视图（MySQL 不支持物化视图，如 PostgreSQL 的 MATERIALIZED VIEW）

-- 可合并视图：视图定义被展开到查询中（内联处理，类似派生表合并）
CREATE VIEW active_orders AS
SELECT id, user_id, amount FROM orders WHERE status = 1;

-- 查询视图时，会被展开为对基础表的查询
EXPLAIN SELECT * FROM active_orders WHERE user_id = 100 \G
-- table: orders（视图被展开，直接显示基础表）
-- 等价于：SELECT id, user_id, amount FROM orders WHERE status=1 AND user_id=100

-- 视图何时会被物化（成为临时表）？
-- 视图含有无法合并的结构（GROUP BY、DISTINCT 等）：
CREATE VIEW user_order_totals AS
SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id;

EXPLAIN SELECT * FROM user_order_totals WHERE total > 500 \G
-- select_type: DERIVED, table: orders → 视图物化为临时表
-- 无法合并（含 GROUP BY）→ 视图被物化处理

-- 查看视图是可合并还是需要物化（通过 INFORMATION_SCHEMA）
SELECT TABLE_NAME, IS_UPDATABLE, DEFINER
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'mydb' AND TABLE_NAME = 'active_orders';
```

## 物化临时表的内存与磁盘

```sql
-- 物化临时表的存储限制：
SHOW VARIABLES LIKE 'tmp_table_size';          -- 内存临时表最大 16MB（默认）
SHOW VARIABLES LIKE 'max_heap_table_size';     -- MEMORY 表最大 16MB（默认）
-- 内存临时表超过 min(tmp_table_size, max_heap_table_size) 时，
-- 自动转为磁盘临时表（InnoDB 格式，MySQL 8.0+）

-- 内存临时表 vs 磁盘临时表的代价差异（cost model 中体现）：
-- memory_temptable_create_cost: 1.0
-- disk_temptable_create_cost: 20.0（20倍差距！）
-- 大型物化结果集（>16MB）必然使用磁盘临时表，代价较高

-- 适当增大 tmp_table_size 可以减少磁盘临时表的产生：
SET SESSION tmp_table_size = 67108864;  -- 64MB（仅当前连接有效）
SET SESSION max_heap_table_size = 67108864;

-- 注意：物化临时表的大小与子查询返回的行数和列宽有关
-- 对于大结果集（百万行），即使增大内存限制也可能溢出到磁盘
```

## 适用场景

- **IN 子查询的性能分析**：当 EXPLAIN 显示 `select_type: MATERIALIZED` 时，说明 IN 子查询被物化，这通常是高效的（比 `DEPENDENT SUBQUERY` 好得多）。但如果内层子查询结果集很大（超过内存临时表限制），物化会写入磁盘，代价急剧上升，此时考虑改写为显式 JOIN
- **CTE 的多次引用优化**：在需要多次引用同一个复杂查询结果的场景（如多个 JOIN 或 UNION 中用到同一聚合），使用 CTE（`WITH` 子句）可以使结果被物化一次后复用，避免同一复杂查询被执行多次

## 常见问题

**MySQL 有没有像 PostgreSQL 那样的物化视图（MATERIALIZED VIEW）？**

MySQL 没有原生的物化视图（存储查询结果并支持刷新的持久化视图）。要实现类似功能，通常的做法是：创建一张汇总表（CREATE TABLE ... AS SELECT ...），通过定时任务（Event Scheduler 或外部 Cron Job）定期更新汇总表的数据，查询时直接查汇总表而不是原始表。这种方式需要手动维护数据的一致性和更新频率，是 MySQL 中替代物化视图的常见架构方案。

---

## 注意事项

- 物化（Materialization）产生的临时表在 MySQL 8.0+ 默认使用 TempTable 存储引擎（内存中），超过限制时转为 InnoDB 格式的磁盘临时表。相比 MySQL 5.7 使用 MEMORY 引擎的内存临时表，TempTable 支持 BLOB/TEXT 类型的列，能处理更多类型的物化结果。
- 物化子查询（`select_type: MATERIALIZED`）和物化派生表（`select_type: DERIVED`）在执行机制上相同（都是创建临时表），但它们在 EXPLAIN 中的 `select_type` 不同，需要区分。前者是 IN/EXISTS 子查询的优化结果，后者是 FROM 子句中子查询的物化。

---

## 总结

物化（Materialization）是将子查询或视图结果存储为临时表以供复用的优化策略，对应 EXPLAIN 中的 `select_type: MATERIALIZED`（IN 子查询物化）或 `select_type: DERIVED`（派生表物化）。MySQL 普通视图本质上是可合并视图（不是物化视图）；含 GROUP BY/DISTINCT 的视图会被物化。物化的代价：创建临时表 + 写入/读取数据；内存临时表（< `tmp_table_size`）代价低；磁盘临时表代价高（cost model 中 20 倍差距）。控制：`optimizer_switch='materialization=on/off'`。适用：IN 子查询内层只执行一次（比相关子查询高效）；CTE 多次引用时物化复用（避免重复执行）。

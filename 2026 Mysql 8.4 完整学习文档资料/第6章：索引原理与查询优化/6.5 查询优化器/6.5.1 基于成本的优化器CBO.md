# 基于成本的优化器 CBO

MySQL 使用的是**基于成本的优化器**（Cost-Based Optimizer，CBO），其核心职责是：对于一条 SQL 语句，在所有可行的执行计划中，通过成本模型估算每种方案的代价，选择总成本最低的方案执行。CBO 的决策质量直接决定了 SQL 的执行效率。与之对应的是基于规则的优化器（Rule-Based Optimizer，RBO），RBO 按固定规则选择执行计划而不考虑数据量——MySQL 不使用 RBO。

---

## CBO 的工作流程

```
SQL 语句解析流程：

1. Parser（解析器）：将 SQL 文本解析为语法树（AST）
   → 验证 SQL 语法是否正确

2. Preprocessor（预处理器）：
   → 检查表和列是否存在
   → 展开通配符（SELECT * → SELECT col1, col2, ...）
   → 视图展开、权限检查

3. Query Optimizer（查询优化器，CBO）：
   → 逻辑优化（查询改写）：
      - 常量折叠：WHERE id = 1+1 → WHERE id = 2
      - 条件下推：将 WHERE 条件尽早过滤
      - 子查询展开：IN 子查询转 Semi-join
      - 派生表合并（Derived Merge）
   → 物理优化（成本估算）：
      - 枚举候选索引，估算每种访问路径的成本
      - 枚举 JOIN 顺序，选择总成本最低的方案
      - 决定是否使用排序/临时表
   → 输出：最优执行计划

4. Execution Engine（执行引擎）：按执行计划调用存储引擎 API 执行
```

## CBO 的成本估算模型

```sql
-- CBO 的成本由两部分组成：I/O 代价和 CPU 代价

-- I/O 代价：读取数据页的代价
--   io_block_read_cost: 1.0（默认，读取一个磁盘页的成本）
--   memory_block_read_cost: 0.25（Buffer Pool 命中时，读取内存页的成本）

-- CPU 代价：处理每行数据的代价
--   row_evaluate_cost: 0.1（处理每行数据的 CPU 成本）

-- 全表扫描成本估算：
-- total_cost = page_count × io_block_read_cost + row_count × row_evaluate_cost
-- 假设 orders 表：100万行，100000个数据页
-- 全表扫描成本 ≈ 100000 × 1.0 + 1000000 × 0.1 = 200000

-- 索引范围扫描成本估算：
-- total_cost = 索引页I/O + 匹配行数 × 回表成本 + 匹配行数 × row_evaluate_cost
-- 假设 idx_user(user_id=100)：25行，索引叶子2页，回表25次
-- 索引扫描成本 ≈ 2 × 1.0 + 25 × 1.0 + 25 × 0.1 = 29.5

-- CBO 对比：全表扫描(200000) vs 索引扫描(29.5) → 选索引

-- 查看成本参数配置：
SELECT cost_name, default_value, current_value
FROM mysql.server_cost;

SELECT cost_name, engine_name, default_value, current_value
FROM mysql.engine_cost;
```

## CBO 的统计信息依赖

```sql
-- CBO 的成本估算依赖表的统计信息：

-- 1. 表级统计：行数（n_rows）和数据页数（clustered_index_size）
SELECT * FROM mysql.innodb_table_stats WHERE database_name = 'mydb' AND table_name = 'orders' \G
-- n_rows: 1000000（估算行数）
-- clustered_index_size: 6250（聚簇索引页数）

-- 2. 索引级统计：索引的选择性（Cardinality）
SELECT * FROM mysql.innodb_index_stats
WHERE database_name = 'mydb' AND table_name = 'orders' \G
-- stat_name=n_diff_pfx01：idx_user 的第一列基数（不同值的估算数量）

-- 3. 直方图（MySQL 8.0+ 新增）：精确的数据分布直方图
SELECT * FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME = 'mydb' AND TABLE_NAME = 'orders';

-- 统计信息不准确 → CBO 估算错误 → 选择错误的执行计划
-- 解决：ANALYZE TABLE orders; 更新统计信息
```

## CBO 的局限性

```
CBO 不是万能的，在以下情况可能做出次优决策：

1. 统计信息过时或不准确
   → 数据量变化大后，CBO 基于旧统计信息估算错误
   → 解决：定期 ANALYZE TABLE

2. 枚举空间受限（join_order_limit）
   → 对于 N 个表的 JOIN，完全枚举所有排列需要 O(N!) 的复杂度
   → MySQL 默认最多枚举 7~8 个表（optimizer_search_depth=62 意味着贪心搜索）
   → 超过 7~8 个表的 JOIN，CBO 可能无法找到全局最优方案

3. 不均匀数据分布（低基数列）
   → status 只有几个值（0,1,2），但各值的行数分布差异很大
   → 没有直方图时，CBO 按均匀分布估算，偏差大
   → 解决：为 status 建直方图（ANALYZE TABLE ... UPDATE HISTOGRAM ON status）

4. 函数计算的成本无法准确估算
   → WHERE SUBSTR(name,1,3) = 'abc' 的成本无法精确计算
   → CBO 可能高估或低估
```

## CBO 的主要优化变换

```sql
-- 1. 常量传播与折叠
-- 原始：WHERE a = 1 AND b = a
-- 优化：WHERE a = 1 AND b = 1（b=a 被替换为 b=1）

-- 2. 冗余条件消除
-- 原始：WHERE a > 5 AND a > 3
-- 优化：WHERE a > 5（a>3 是冗余的）

-- 3. 子查询改写为 Semi-join
-- 原始：WHERE id IN (SELECT id FROM t2 WHERE status=1)
-- 优化：内部转为 Semi-join（更高效的 JOIN 形式）

-- 4. 外连接转内连接（如果 WHERE 条件排除了 NULL）
-- 原始：t1 LEFT JOIN t2 ON... WHERE t2.col IS NOT NULL
-- 优化：t1 INNER JOIN t2（因为 WHERE 已经排除了 t2 不匹配的情况）

-- 通过 EXPLAIN 可以观察优化效果（select_type/type 的变化）
-- 通过 Optimizer Trace 可以看到完整的优化变换过程
```

## 影响 CBO 的主要参数

```sql
-- 查看优化器相关参数
SHOW VARIABLES LIKE 'optimizer%' \G

-- optimizer_switch：控制各种优化特性的开关
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- 常见开关：
-- index_merge=on               → 索引合并
-- use_index_extensions=on      → 利用联合索引的扩展列
-- condition_fanout_filter=on   → 条件扇出过滤（估算 filtered）
-- derived_merge=on             → 派生表合并
-- semijoin=on                  → Semi-join 优化
-- materialization=on           → 子查询物化
-- hash_join=on                 → 哈希连接（MySQL 8.0+）

-- optimizer_search_depth：贪心搜索的最大深度（JOIN 顺序枚举）
SHOW VARIABLES LIKE 'optimizer_search_depth';
-- 默认: 62（接近完全枚举，小值时使用贪心启发式）

-- join_buffer_size：Block Nested Loop 和 Hash Join 使用的缓冲区大小
SHOW VARIABLES LIKE 'join_buffer_size';
-- 默认: 262144（256KB）
```

## 适用场景

- **慢查询根因分析**：当慢查询 EXPLAIN 显示了不合理的执行计划（如全表扫描），了解 CBO 的成本估算机制，才能找到根本原因（统计信息过时、索引选择性低、数据分布不均等）并针对性修复
- **关键查询的执行计划固化**：对于 CBO 偶尔误判（统计信息变化后选择不同执行计划）的核心查询，通过 Optimizer Hint 固定执行计划，防止因 CBO 决策变化导致性能波动

## 常见问题

**CBO 和 RBO 最大的区别是什么？**

RBO 按照预定义的规则选择执行计划（如"有索引就用索引"、"总是选数据量小的表作为驱动表"），不考虑实际的数据量和选择性；CBO 通过统计信息估算成本，选择总代价最低的方案，会根据实际数据分布动态决策（如当索引选择性很低时宁愿全表扫描）。CBO 更智能，但依赖统计信息的准确性；统计信息不准时，CBO 反而可能比 RBO 做出更差的决策。这就是为什么统计信息管理（`ANALYZE TABLE`、直方图）在 MySQL 调优中如此重要。

---

## 注意事项

- CBO 做决策的时间（查询解析和优化的耗时）通常在毫秒级以内，对于简单查询几乎可以忽略不计。但对于超复杂的多表 JOIN（10+ 个表），枚举所有 JOIN 顺序的时间可能超过实际执行时间，这时 MySQL 会使用贪心搜索（不完全枚举）限制优化时间。
- MySQL 8.0 CBO 的能力有显著提升，特别是直方图的引入（8.0+）和哈希连接（8.0.18+）。升级到 MySQL 8.4 后，部分在 5.7 上需要手动 FORCE INDEX 的查询，优化器可以自动做出更好的决策。

---

## 总结

MySQL CBO（基于成本的优化器）通过估算各执行方案的 I/O 代价 + CPU 代价，选择总成本最低的方案。成本估算依赖统计信息（`mysql.innodb_table_stats`、`mysql.innodb_index_stats`、直方图）。CBO 执行逻辑优化（子查询展开、常量折叠）和物理优化（索引选择、JOIN 顺序）。局限性：统计信息不准确、数据分布不均（无直方图）、超多表 JOIN（枚举空间限制）时可能做出次优决策。通过 `ANALYZE TABLE`、直方图、Optimizer Hint 等手段辅助 CBO 做出更正确的决策。

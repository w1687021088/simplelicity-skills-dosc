# 统计信息收集与更新

MySQL 的查询优化器（CBO）依赖统计信息来估算各种执行方案的成本，从而选择最优执行计划。InnoDB 的统计信息包括：表的行数估算（`n_rows`）、数据页数（`clustered_index_size`）、索引的基数（`Cardinality`，即索引列不同值的数量）等。统计信息的准确性直接影响优化器的决策质量——统计信息过时可能导致优化器选错索引或使用次优的 JOIN 顺序。

---

## 统计信息的存储位置

```sql
-- InnoDB 统计信息持久化存储（innodb_stats_persistent=ON，默认）
-- 存储在 mysql 系统库中：

-- 表级统计信息：
SELECT * FROM mysql.innodb_table_stats
WHERE database_name = 'mydb' AND table_name = 'orders' \G
-- n_rows: 1000000          ← 估算行数
-- clustered_index_size: 6250 ← 聚簇索引页数
-- sum_of_other_index_sizes: 1250 ← 其他索引的总页数
-- last_update: 2025-01-15 10:00:00 ← 上次更新时间

-- 索引级统计信息：
SELECT * FROM mysql.innodb_index_stats
WHERE database_name = 'mydb' AND table_name = 'orders' \G
-- index_name: idx_user          ← 索引名
-- stat_name: n_diff_pfx01       ← 第一列的基数（不同值数量）
-- stat_value: 50000             ← user_id 约有 50000 个不同值
-- stat_name: size               ← 索引大小（页数）
-- stat_value: 250
```

## ANALYZE TABLE：手动更新统计信息

```sql
-- 触发统计信息重新采样
ANALYZE TABLE orders;
-- 对 orders 表重新随机采样，更新 innodb_table_stats 和 innodb_index_stats
-- 执行结果：
-- Table: mydb.orders
-- Op: analyze
-- Msg_type: status
-- Msg_text: OK

-- 批量分析多张表
ANALYZE TABLE orders, users, products;

-- 分析整个数据库的所有表（通过 information_schema 生成 SQL）
SELECT CONCAT('ANALYZE TABLE `', TABLE_SCHEMA, '`.`', TABLE_NAME, '`;') AS sql_text
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mydb' AND TABLE_TYPE = 'BASE TABLE';
-- 执行生成的 SQL 列表即可批量更新

-- ANALYZE TABLE 需要哪些权限？
-- SELECT + INSERT 权限（因为要读取和更新 mysql 系统表）
-- 或 SUPER 权限
```

## 自动统计信息更新机制

```sql
-- InnoDB 自动统计更新（innodb_stats_auto_recalc=ON，默认）
-- 当表中数据变化量超过总行数的 10% 时，InnoDB 自动触发后台统计更新
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
-- Value: ON（默认）

-- 自动更新是异步的（后台线程），有延迟
-- 在大量写入后，可能需要几秒到几分钟才能更新统计信息
-- 如果需要立即更新，手动执行 ANALYZE TABLE

-- 禁用自动更新（极少数情况，如统计信息振荡导致执行计划不稳定）
ALTER TABLE orders STATS_AUTO_RECALC=0;
-- 或全局禁用：SET GLOBAL innodb_stats_auto_recalc = OFF;

-- 统计信息的持久化控制
SHOW VARIABLES LIKE 'innodb_stats_persistent';
-- ON（默认）：统计信息持久化到 mysql.innodb_table_stats（重启后保留）
-- OFF：统计信息存于内存，重启后重新采样
```

## 统计信息的采样精度控制

```sql
-- 采样页数控制统计精度（采样越多，精度越高，但 ANALYZE TABLE 越慢）

-- 持久化统计（innodb_stats_persistent=ON）的采样页数
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';
-- 默认: 20（MySQL 8.0），比 5.7 的默认值 8 更高

-- 临时统计（innodb_stats_persistent=OFF）的采样页数
SHOW VARIABLES LIKE 'innodb_stats_transient_sample_pages';
-- 默认: 8

-- 为特定表提高采样精度（不影响全局）：
ALTER TABLE orders STATS_SAMPLE_PAGES=100;
ANALYZE TABLE orders;
-- 这张表的统计采样使用 100 页（更精确但更慢）

-- 或临时全局提高采样精度：
SET GLOBAL innodb_stats_persistent_sample_pages = 50;
ANALYZE TABLE orders;
SET GLOBAL innodb_stats_persistent_sample_pages = 20;  -- 恢复默认
```

## 查看统计信息的准确性

```sql
-- 方法1：对比 EXPLAIN 的 rows 与实际 COUNT(*)
EXPLAIN SELECT * FROM orders WHERE user_id = 100 \G
-- rows: 25（估算）

SELECT COUNT(*) FROM orders WHERE user_id = 100;
-- 结果：1（实际只有 1 行）
-- 偏差 25 倍 → 统计信息不准，需要 ANALYZE TABLE

-- 方法2：通过 EXPLAIN ANALYZE 对比估算和实际
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 100 \G
-- rows=25（估算）vs actual rows=1（实际）→ 偏差大

-- 方法3：通过 SHOW INDEX 查看 Cardinality
SHOW INDEX FROM orders \G
-- Cardinality: 50000（user_id 的基数估算）
-- 实际 user_id 有 100000 个不同值 → Cardinality 偏低 50%
-- → 需要 ANALYZE TABLE 更新

-- 统计信息可接受的偏差范围：
-- 通常 rows 估算偏差在实际值的 2~3 倍以内是正常的
-- 超过 5 倍的偏差可能影响执行计划选择，需要更新统计信息
```

## 统计信息更新的时机建议

```
建议在以下时机主动更新统计信息：

1. 大批量数据导入/删除后
   → INSERT INTO ... SELECT ... 大量行
   → DELETE FROM orders WHERE ... 删除大量行
   → TRUNCATE TABLE（自动重置统计）

2. 执行计划突然变差（出现新的慢查询）
   → 通过 EXPLAIN 发现 type 变为 ALL，而以前是 ref
   → 可能是数据分布变化导致统计信息失效

3. 定期维护（建议每周或每月一次）
   → 在业务低峰期执行 ANALYZE TABLE
   → 对于高频写入的表，增加 ANALYZE TABLE 的频率

4. 建立新索引后
   → ALTER TABLE ADD INDEX 之后，立即 ANALYZE TABLE
   → 确保新索引的统计信息是最新的

5. 升级 MySQL 版本后
   → 重建统计信息确保与新版本的优化器兼容
   → mysql_upgrade 通常会触发重建，但建议手动确认
```

## 适用场景

- **执行计划突然变差的应急处理**：生产环境中某查询突然变慢（从几毫秒变为几秒），通过 EXPLAIN 发现 type 变为 ALL，立即执行 `ANALYZE TABLE` 更新统计信息，很多情况下可以快速恢复正常执行计划
- **大批量数据操作后的维护**：历史数据归档（大量 DELETE）、数据迁移（大量 INSERT）后，受影响表的统计信息需要立即更新，否则优化器会基于过时的行数估算做出错误决策

## 常见问题

**`ANALYZE TABLE` 会锁表吗，影响业务吗？**

InnoDB 的 `ANALYZE TABLE` 在 MySQL 5.6+ 是在线操作（Online DDL），使用较轻量的 MDL 读锁，不会阻塞 SELECT/INSERT/UPDATE/DELETE 操作。执行期间，表的 DML 操作正常进行，只有极短暂的 MDL 写锁（完成更新统计信息的瞬间）。对于普通大小的表（千万行级别），`ANALYZE TABLE` 通常在几秒内完成（取决于 `innodb_stats_persistent_sample_pages` 的值）。对业务的影响通常可以忽略不计，可以在任何时间执行，无需等待业务低峰。

---

## 注意事项

- InnoDB 统计信息是基于随机采样的估算值，天然存在误差。对于数据分布极不均匀（如某些列的值高度集中）的表，即使频繁 `ANALYZE TABLE`，估算偏差也可能较大。这种情况下，使用直方图（MySQL 8.0+）可以显著提高统计精度，见 6.5.3。
- `innodb_stats_persistent=ON` 时，统计信息存储在 `mysql.innodb_table_stats` 和 `mysql.innodb_index_stats` 表中，重启服务器后不会丢失。`innodb_stats_persistent=OFF` 时，统计信息存于内存，每次重启都会重新采样（每次重启可能得到不同的执行计划）。生产环境应保持 `innodb_stats_persistent=ON`（默认值），确保执行计划的稳定性。

---

## 总结

InnoDB 统计信息（行数、索引基数）存储在 `mysql.innodb_table_stats` 和 `mysql.innodb_index_stats` 中。通过 `ANALYZE TABLE` 手动更新（重新采样），`innodb_stats_auto_recalc=ON` 控制 10% 数据变化后自动触发后台更新。统计精度由 `innodb_stats_persistent_sample_pages`（默认 20）控制，增大可提高精度但增加分析时间。统计信息不准确是执行计划异常的最常见原因，通过 EXPLAIN 的 rows 估算与 `SELECT COUNT(*)` 实际值对比，量化统计偏差；偏差过大时立即 `ANALYZE TABLE`。对于数据分布不均匀的列，考虑使用直方图（MySQL 8.0+）补充统计精度。

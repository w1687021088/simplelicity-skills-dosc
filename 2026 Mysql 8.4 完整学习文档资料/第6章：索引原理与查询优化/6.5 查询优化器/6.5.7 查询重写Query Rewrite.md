# 查询重写 Query Rewrite

查询重写（Query Rewrite）是 MySQL 优化器在执行 SQL 之前，对 SQL 逻辑进行等价变换的过程，目的是将查询转换为更高效的形式，而不改变查询的语义（最终结果相同）。查询重写属于"逻辑优化"阶段，发生在"物理优化"（成本估算、索引选择）之前。典型的重写包括：常量折叠与传播、子查询转 Semi-join/Anti-join、外连接转内连接、冗余条件消除、派生表合并等。

---

## 自动重写：常量折叠与传播

```sql
-- 1. 常量折叠（编译期计算常量表达式）
-- 原始：WHERE created_at > NOW() - INTERVAL 7 DAY
-- 内部重写：WHERE created_at > '2025-01-08 10:00:00'（计算出具体值）

-- 2. 常量传播（通过等值条件传播常量）
-- 原始：WHERE a = b AND a = 5
-- 重写：WHERE a = 5 AND b = 5（b=a 被 a=5 传播替换为 b=5）
-- 效果：如果 b 有索引，可以利用 b=5 走索引

-- 验证：通过 SHOW WARNINGS 查看常量传播的结果
EXPLAIN SELECT * FROM orders WHERE user_id = created_by AND user_id = 100;
SHOW WARNINGS \G
-- Message: SELECT * FROM orders WHERE (orders.user_id = 100) AND (orders.created_by = 100)
-- 优化器自动将 created_by 替换为 100（常量传播）
-- 如果 created_by 有索引，就可以利用索引快速过滤

-- 3. 算术表达式预计算
-- 原始：WHERE id = 3 * 7 + 1
-- 重写：WHERE id = 22
```

## 自动重写：冗余条件消除

```sql
-- 冗余或矛盾条件的消除（优化器自动完成）

-- 1. 冗余范围合并
-- 原始：WHERE age > 18 AND age > 21
-- 重写：WHERE age > 21（更严格的条件覆盖了宽松的条件）

-- 2. 恒真条件消除
-- 原始：WHERE 1 = 1 AND user_id = 100
-- 重写：WHERE user_id = 100

-- 3. 恒假条件短路
-- 原始：WHERE user_id = 100 AND 1 = 2
-- 重写：直接返回空结果（短路，不执行表扫描）

-- 4. 外连接转内连接（NULL 被 WHERE 过滤时）
-- 原始：SELECT * FROM t1 LEFT JOIN t2 ON t1.id = t2.t1_id WHERE t2.col IS NOT NULL
-- 重写：等价于 INNER JOIN（因为 WHERE t2.col IS NOT NULL 已排除了 t2 不匹配的行）
-- 效果：内连接通常比外连接有更多优化空间（如 JOIN 顺序可以任意调换）

EXPLAIN SELECT * FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE u.status = 1 \G
-- select_type: SIMPLE（外连接被自动转为内连接）
-- 因为 WHERE u.status=1 要求 u 必须存在（隐式排除了 u 不匹配的行）
```

## 自动重写：IN 子查询转 Semi-join

```sql
-- MySQL 优化器会尝试将 IN 子查询改写为 Semi-join（更高效的 JOIN 形式）

-- 原始（IN 子查询）：
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active');

-- 内部重写为 Semi-join（优化器隐式完成）：
-- Semi-join 语义：对 orders 的每行，检查是否存在至少一个匹配的 users 行
-- 不需要重复处理 users 中多行匹配的情况（IN 的语义是"存在即可"）

-- 验证重写效果（通过 EXPLAIN 的 select_type）：
EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active') \G
-- 如果 select_type: SIMPLE（无 SUBQUERY）→ 子查询被成功转为 Semi-join 合并了

-- 如果看到 select_type: PRIMARY + SUBQUERY → 子查询未被转换（可能原因：
-- 子查询引用了外层列（相关子查询）/ 含 GROUP BY / 含 DISTINCT 等）

-- 控制 Semi-join 优化开关：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- semijoin=on（默认）→ 允许 IN 子查询转 Semi-join
-- SET optimizer_switch = 'semijoin=off';（关闭，不推荐）
```

## 自动重写：IN 列表展开

```sql
-- IN 列表被优化器重写为多个范围条件
-- 原始：WHERE id IN (1, 5, 9, 13)
-- 重写：WHERE id = 1 OR id = 5 OR id = 9 OR id = 13
-- 进一步优化：多个等值 → range 类型的多区间扫描

-- 对于 IN 列表非常长时：
-- WHERE id IN (1, 2, 3, ..., 10000)
-- 优化器会分析 IN 列表的覆盖范围
-- 如果覆盖了表行数的大比例 → 可能转为全表扫描（跳过索引）

-- IN 列表太长（超过 in_predicate_conversion_threshold 时）会影响解析速度
SHOW VARIABLES LIKE 'in_predicate_conversion_threshold';
-- MySQL 8.0+：当 IN 列表元素数 > 该值时，转为 range 扫描方式处理
```

## Query Rewrite 插件（手动重写 SQL）

```sql
-- MySQL 5.7.6 引入了 Query Rewrite Plugin（查询重写插件）
-- 允许 DBA 配置规则，在服务器端自动重写特定 SQL（无需修改应用代码）

-- 安装（通常 MySQL 安装时已包含）
INSTALL PLUGIN rewriter SONAME 'rewriter.so';

-- 配置重写规则（存储在 query_rewrite.rewrite_rules 表）
INSERT INTO query_rewrite.rewrite_rules (pattern, replacement, pattern_database)
VALUES (
    'SELECT * FROM orders WHERE status = ?',          -- 匹配模式
    'SELECT id, user_id, amount FROM orders WHERE status = ? LIMIT 100',  -- 替换为
    'mydb'
);

-- 刷新规则（使新规则生效）
CALL query_rewrite.flush_rewrite_rules();

-- 规则生效后，所有匹配 `SELECT * FROM orders WHERE status = ?` 的 SQL
-- 会被自动重写为 `SELECT id, user_id, amount FROM orders WHERE status = ? LIMIT 100`
-- 应用代码无感知（Server 层完成替换）

-- 查看规则状态：
SELECT * FROM query_rewrite.rewrite_rules \G
-- enabled: YES  ← 规则已启用
-- message: NULL ← NULL 表示规则正常（非 NULL 表示规则有问题）

-- 停用/删除规则：
UPDATE query_rewrite.rewrite_rules SET enabled = 'NO' WHERE id = 1;
CALL query_rewrite.flush_rewrite_rules();

DELETE FROM query_rewrite.rewrite_rules WHERE id = 1;
CALL query_rewrite.flush_rewrite_rules();
```

## 适用场景

- **应用代码不可修改时的 SQL 优化**：当发现某个查询性能差（如 `SELECT *` 或没有 LIMIT），但应用代码无法立即修改（审批周期长、代码已冻结），可以通过 Query Rewrite 插件在数据库层面临时重写，在应用修复前保证系统稳定性
- **验证优化器自动重写的效果**：通过 `SHOW WARNINGS`（在 `EXPLAIN` 后执行）查看优化器对 SQL 做了哪些自动重写（如常量传播、外连接转内连接），理解实际执行的 SQL 与书写的 SQL 之间的差异

## 常见问题

**Query Rewrite 插件的重写规则中的 `?` 是参数占位符吗？**

是的。`?` 是 Query Rewrite 规则中的占位符，匹配任何常量值（字符串、数字、日期等）。规则 `SELECT * FROM orders WHERE status = ?` 会匹配 `SELECT * FROM orders WHERE status = 1`、`SELECT * FROM orders WHERE status = 2` 等所有 status 为不同常量的查询。但不会匹配 `SELECT * FROM orders WHERE status > 1`（操作符不同）或 `SELECT id FROM orders WHERE status = 1`（选择列不同）——规则匹配要求整个 SQL 结构完全相同，只有常量值部分用 `?` 匹配。

---

## 注意事项

- MySQL 的自动查询重写（常量折叠、子查询转换等）是无感知的，不需要 DBA 干预，也不能关闭（这些是基础的逻辑优化）。Query Rewrite 插件则是主动配置的手动重写规则，两者不是同一个概念。
- Query Rewrite 插件的规则匹配基于 SQL 的规范化形式（不区分大小写，忽略多余空格），一条规则可以匹配来自不同客户端、不同用户的相同 SQL。但规则有数据库（`pattern_database`）的概念，不同数据库的同名表需要分别配置规则。

---

## 总结

查询重写分两类：优化器自动重写（无感知）——常量折叠与传播、冗余条件消除、外连接转内连接、IN 子查询转 Semi-join；手动重写——Query Rewrite 插件（`query_rewrite.rewrite_rules`），允许在 Server 层自动替换匹配的 SQL，对应用无感知。自动重写通过 `SHOW WARNINGS`（EXPLAIN 后执行）可以看到重写后的 SQL；手动重写通过安装插件、配置规则、`flush_rewrite_rules()` 生效。手动重写插件适合应用代码不可修改时的临时优化手段。

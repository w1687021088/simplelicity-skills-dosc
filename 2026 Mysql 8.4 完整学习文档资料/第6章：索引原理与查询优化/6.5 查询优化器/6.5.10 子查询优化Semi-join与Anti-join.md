# 子查询优化 Semi-join 与 Anti-join

Semi-join（半连接）和 Anti-join（反连接）是 MySQL 优化器对特定子查询形式的内部改写优化，将原本可能低效的 IN/EXISTS/NOT IN/NOT EXISTS 子查询转换为更高效的 JOIN 执行形式。MySQL 5.6 引入 Semi-join 优化，MySQL 8.0 引入 Anti-join 优化。理解这两种优化的触发条件和执行机制，有助于正确编写可以被优化器高效执行的子查询 SQL。

---

## Semi-join（半连接）的概念

```
Semi-join 的语义：
对于外层表的每一行，检查内层子查询是否"存在"至少一个匹配行
一旦找到第一个匹配，立即停止搜索（不关心有多少个匹配）

原始写法（IN 子查询）：
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active');

语义：对于每个 order，如果对应的 user 的 status 是 active，则包含在结果中
Semi-join 的关键：不关心 users 中有多少个 status='active' 的行，
只关心"是否存在"

Semi-join 等价改写（手动方式）：
SELECT DISTINCT o.*
FROM orders o
INNER JOIN users u ON o.user_id = u.id
WHERE u.status = 'active';
-- 需要 DISTINCT 防止 orders 行因 users 多行匹配而重复
-- 但优化器的 Semi-join 内部不需要显式 DISTINCT（语义上保证了不重复）
```

## Semi-join 的触发条件与 EXPLAIN 识别

```sql
-- Semi-join 对以下形式的子查询生效：
-- WHERE ... IN (SELECT ... FROM t WHERE ...)
-- WHERE EXISTS (SELECT 1 FROM t WHERE t.col = outer.col)

-- 可以触发 Semi-join 的条件：
-- 1. 子查询是不相关的（或简单相关的）不相关子查询
-- 2. 子查询不含 GROUP BY、DISTINCT、聚合函数（SUM/COUNT 等）
-- 3. 子查询不含 UNION
-- 4. IN 或 EXISTS 形式（NOT IN 和 NOT EXISTS 不能用 Semi-join，而是 Anti-join）
-- 5. optimizer_switch 中 semijoin=on（默认）

-- 验证 Semi-join 是否生效（EXPLAIN 中 select_type 变化）：
EXPLAIN SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE status = 'active') \G

-- Semi-join 生效时（select_type 合并为 SIMPLE）：
-- id: 1, select_type: SIMPLE, table: users
-- id: 1, select_type: SIMPLE, table: orders
-- 两个步骤同属 id=1，select_type=SIMPLE → 子查询被合并入主查询

-- Semi-join 未生效时（保持独立子查询）：
-- id: 1, select_type: PRIMARY, table: orders
-- id: 2, select_type: SUBQUERY, table: users
```

## Semi-join 的五种执行策略

```sql
-- MySQL 优化器根据成本选择五种 Semi-join 执行策略之一：

-- 策略1：Duplicate Weedout（重复消除）
-- 先做普通 JOIN，然后通过临时表消除重复行
-- Extra 可能显示：Start temporary; End temporary

-- 策略2：FirstMatch（首次匹配）
-- 对每行外层行，一旦找到第一个内层匹配就停止（最像 Semi-join 语义）
-- Extra: FirstMatch(users)

-- 策略3：LooseScan（松散扫描）
-- 只扫描内层索引的第一个不同值（利用索引有序性减少扫描）
-- Extra: LooseScan

-- 策略4：Materialization（物化）
-- 将内层子查询物化为哈希临时表，与外层做哈希连接
-- select_type: MATERIALIZED

-- 策略5：Table Pullout（表提取）
-- 当内层子查询的列是唯一键时，直接将子查询提取为等值 JOIN
-- 最高效，子查询完全消失，变成 INNER JOIN

-- 查看当前 Semi-join 策略的控制：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- semijoin=on               → 允许 Semi-join
-- loosescan=on              → 允许 LooseScan 策略
-- firstmatch=on             → 允许 FirstMatch 策略
-- duplicateweedout=on       → 允许 Duplicate Weedout 策略
-- materialization=on        → 允许 Materialization 策略
```

## Anti-join（反连接，MySQL 8.0+）

```sql
-- Anti-join 的语义：
-- 对于外层表的每一行，检查内层子查询是否"不存在"任何匹配行
-- 不存在匹配的行才包含在结果中

-- NOT IN 和 NOT EXISTS 在 MySQL 8.0+ 中可以被转换为 Anti-join

-- NOT IN 子查询（NULL 注意事项！）：
EXPLAIN SELECT * FROM orders
WHERE user_id NOT IN (SELECT id FROM users WHERE status = 'banned') \G

-- MySQL 8.0+ Anti-join 生效：
-- EXPLAIN 可能显示：select_type: SIMPLE（两表合并）
-- Extra: Not exists（Anti-join 语义）

-- NOT EXISTS 子查询：
EXPLAIN SELECT o.*
FROM orders o
WHERE NOT EXISTS (
    SELECT 1 FROM blacklist b WHERE b.user_id = o.user_id
) \G
-- MySQL 8.0+ 将此转为 Anti-join（等价于 LEFT JOIN ... WHERE b.user_id IS NULL）

-- Anti-join 在 MySQL 8.0 之前的处理：
-- MySQL 5.7 及更早版本：NOT IN/NOT EXISTS 子查询通常作为相关子查询执行（DEPENDENT SUBQUERY）
-- 效率很低（外层每行执行一次子查询）
-- MySQL 8.0+ Anti-join 优化后，等价于 LEFT JOIN WHERE NULL，高效很多
```

## NOT IN 中的 NULL 陷阱

```sql
-- NOT IN 子查询有一个著名的 NULL 问题：
-- 如果内层子查询的结果集中包含 NULL，NOT IN 整个返回空结果！

-- 示例：
SELECT * FROM orders WHERE user_id NOT IN (1, 2, NULL);
-- 结果：空集！（因为任何值 NOT IN (..., NULL) 都是 UNKNOWN，不是 TRUE）

-- 内层子查询含 NULL 时的危险：
SELECT * FROM orders
WHERE user_id NOT IN (SELECT id FROM users WHERE status = 'banned');
-- 如果 users.id 有任何 NULL 行（通常主键不会，但外键字段可能）→ 返回空集！

-- 安全写法1：用 NOT EXISTS 代替 NOT IN（不受 NULL 影响）
SELECT o.* FROM orders o
WHERE NOT EXISTS (
    SELECT 1 FROM users u WHERE u.id = o.user_id AND u.status = 'banned'
);

-- 安全写法2：在 NOT IN 子查询中加 WHERE col IS NOT NULL
SELECT * FROM orders
WHERE user_id NOT IN (
    SELECT id FROM users WHERE status = 'banned' AND id IS NOT NULL
);

-- Anti-join 的 NOT EXISTS 写法在 MySQL 8.0+ 被优化为等价的高效执行计划
-- 推荐使用 NOT EXISTS 替代 NOT IN，既避免 NULL 问题，又能享受 Anti-join 优化
```

## Semi-join vs Anti-join vs 手动 JOIN 的对比

| 场景 | 子查询写法 | 优化器转换 | 等价手动写法 |
|------|----------|-----------|------------|
| 存在检查 | `WHERE id IN (SELECT ...)` | Semi-join | `INNER JOIN ... GROUP BY/DISTINCT` |
| 存在检查 | `WHERE EXISTS (SELECT 1 ...)` | Semi-join | `INNER JOIN` |
| 不存在检查 | `WHERE id NOT IN (SELECT ...)` | Anti-join（8.0+）| `LEFT JOIN ... WHERE t2.col IS NULL` |
| 不存在检查 | `WHERE NOT EXISTS (SELECT ...)` | Anti-join（8.0+）| `LEFT JOIN ... WHERE t2.col IS NULL` |

## 适用场景

- **替换低效的相关子查询**：当 EXPLAIN 显示 `DEPENDENT SUBQUERY` 时，说明子查询在逐行执行，是性能瓶颈。改写为 IN/EXISTS 形式，触发 Semi-join 优化（合并为一次性操作），或直接改写为显式 INNER JOIN，通常都能大幅提升性能
- **NOT IN/NOT EXISTS 查询（MySQL 8.0+）**：在 MySQL 8.0+ 环境中，对于"找不满足条件的行"的查询（如找没有订单的用户、找没有评论的文章），使用 `NOT EXISTS` 子查询，MySQL 8.0 的 Anti-join 优化会将其转为高效的 LEFT JOIN 执行形式

## 常见问题

**IN 子查询和 EXISTS 子查询在性能上有什么区别？**

在 MySQL 8.0+ 中，两者对于不相关子查询都可以被优化器转换为 Semi-join，执行计划基本相同，性能差异可以忽略。主要选择依据是语义清晰度：`IN` 适合子查询返回一列的情况（语义直观）；`EXISTS` 适合子查询条件较复杂（如多列关联）或需要控制子查询内部逻辑的情况。在 MySQL 5.7 及更早版本中，`EXISTS` 在某些场景下可能比 `IN` 更高效（因为 EXISTS 的相关子查询可以短路），但在 8.0+ 中两者差异已基本消失。

---

## 注意事项

- Semi-join 优化不能用于子查询含有 `GROUP BY`、`HAVING`、`DISTINCT`、`LIMIT` 的情况，也不能用于子查询结果包含多列的情况（`WHERE (a, b) IN (SELECT c, d FROM ...)`——实际上多列 IN 在 MySQL 中支持 Semi-join，但有约束）。遇到这些情况时，优化器退回到物化（Materialization）或相关子查询（DEPENDENT SUBQUERY）执行方式。
- Anti-join 优化（MySQL 8.0+）的一个重要副作用是让 `NOT IN` 和 `NOT EXISTS` 的性能变得相近。在 MySQL 5.7 及更早版本中，`NOT IN` 子查询通常比 `NOT EXISTS` 慢得多（前者无法优化，后者可能利用索引短路）。升级到 MySQL 8.0 后，这个历史优化建议已不再适用，两者可以基于语义清晰度自由选择。

---

## 总结

Semi-join 将 `WHERE col IN (subquery)` 或 `WHERE EXISTS (subquery)` 转换为高效的 JOIN 内部执行形式，对应 EXPLAIN 中 select_type 变为 SIMPLE（子查询合并入主查询）。有五种策略：Table Pullout（最高效，唯一键）、Materialization（物化哈希表）、FirstMatch（首次匹配停止）、LooseScan（索引松散扫描）、Duplicate Weedout（临时表去重）。Anti-join（MySQL 8.0+）将 `NOT IN` / `NOT EXISTS` 子查询转换为高效的 LEFT JOIN 形式。注意：`NOT IN` 遇到子查询结果含 NULL 时返回空集，推荐用 `NOT EXISTS` 代替既避免 NULL 陷阱又能享受 Anti-join 优化。控制：`optimizer_switch='semijoin=on/off'`。

# 哈希连接 Hash Join（8.0.18+）

哈希连接（Hash Join）是 MySQL 8.0.18 正式支持的新 JOIN 算法（在 8.0.20+ 得到进一步完善），用于在连接列上**没有索引**的 JOIN 操作。在 Hash Join 之前，MySQL 只支持嵌套循环连接（Nested Loop Join，NLJ）和块嵌套循环（Block Nested Loop，BNL）。BNL 在被驱动表没有索引时，需要将驱动表数据加载到 Join Buffer 后逐块扫描被驱动表，效率较低；Hash Join 通过构建哈希表替代了这个过程，对大表的非索引等值连接性能有显著提升。

---

## Hash Join 的工作原理

```
Hash Join 的执行步骤（两阶段）：

阶段1 - Build Phase（构建阶段）：
  1. 扫描"构建表"（通常是小表或估算行数少的表）
  2. 将构建表的每一行的连接键值哈希后存入内存哈希表
     哈希表结构：{hash(join_key): [row1, row2, ...]}
  3. 如果哈希表超过 join_buffer_size，则分区溢写到磁盘

阶段2 - Probe Phase（探测阶段）：
  1. 扫描"探测表"（通常是大表）
  2. 对探测表的每一行计算连接键的哈希值
  3. 在内存哈希表中查找匹配的行（O(1) 时间复杂度）
  4. 找到匹配则输出到结果集

对比 Block Nested Loop（BNL）：
  BNL：驱动表行 × 被驱动表行 → O(m×n) 比较次数
  Hash Join：O(m+n) 扫描次数 + O(1) 哈希查找 → 适合大表 JOIN
```

## Hash Join 的触发条件与 EXPLAIN 识别

```sql
-- Hash Join 触发条件：
-- 1. JOIN 的连接列没有索引（有索引时优先用 Index NLJ）
-- 2. 连接条件是等值连接（= 操作符）
-- 3. MySQL 8.0.18+
-- 4. optimizer_switch 中 hash_join=on（默认）

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id INT NOT NULL,    -- 假设没有 user_id 索引
    amount DECIMAL(10,2)
);

CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    status VARCHAR(20)
);

-- 没有 orders.user_id 索引时的 JOIN：
EXPLAIN SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id \G

-- MySQL 8.0.18+ 输出：
-- id: 1, table: u, type: ALL, Extra: NULL
-- id: 1, table: o, type: ALL, Extra: Using join buffer (hash join)
--                                    ↑ 明确标识使用了 Hash Join

-- MySQL 5.7 / 8.0.17 输出（BNL）：
-- Extra: Using join buffer (Block Nested Loop)
```

## Hash Join 与 BNL 的对比

| 对比维度 | Hash Join（8.0.18+）| Block Nested Loop（BNL）|
|---------|:------------------:|:---------------------:|
| 适用条件 | 等值连接（=）| 任意连接条件 |
| 构建数据结构 | 哈希表（O(1) 查找）| 块缓冲区（线性扫描）|
| 内存使用 | join_buffer_size（哈希表）| join_buffer_size（缓冲块）|
| 时间复杂度 | O(m + n) | O(m × n / buffer_size）|
| 溢出到磁盘 | 支持（分区溢写）| 不支持（BNL 不能溢出）|
| 非等值连接 | 不支持 | 支持 |

## join_buffer_size 对 Hash Join 的影响

```sql
-- Hash Join 使用 join_buffer_size 作为哈希表的内存上限
SHOW VARIABLES LIKE 'join_buffer_size';
-- 默认: 262144（256KB）— 对于大表 JOIN 通常太小

-- Hash Join 的内存用完后行为：
-- 将构建表数据分区（partition），每个分区适合放入内存
-- 分区数据写入磁盘临时文件，然后分批处理
-- 整个过程称为 Grace Hash Join（磁盘辅助哈希连接）

-- 查看 Hash Join 溢出情况（性能计数器）：
SHOW STATUS LIKE 'Created_tmp_disk_tables';
-- 如果 Hash Join 发生磁盘溢出，此值会增加（磁盘临时文件）

-- 增大 join_buffer_size 可以减少磁盘溢出：
SET SESSION join_buffer_size = 67108864;  -- 64MB
-- 注意：每个连接独占 join_buffer_size 的内存
-- 大量并发连接时，join_buffer_size 过大会导致内存压力

-- 估算合适的 join_buffer_size：
-- 构建表的行数 × 连接键列宽（字节）= 哈希表近似大小
-- 1000行 × 4字节(INT) = 4KB → 默认 256KB 足够
-- 100000行 × 4字节 = 400KB → 需要 1MB 以上避免溢出
```

## 控制 Hash Join

```sql
-- 全局/会话级控制：
SET SESSION optimizer_switch = 'hash_join=on';   -- 开启（默认）
SET SESSION optimizer_switch = 'hash_join=off';  -- 关闭，退回 BNL

-- 查看当前配置：
SHOW VARIABLES LIKE 'optimizer_switch' \G
-- 找到 hash_join=on 确认已启用

-- 针对单个查询使用 Optimizer Hint：
SELECT /*+ HASH_JOIN(o, u) */ o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id;

SELECT /*+ NO_HASH_JOIN(o, u) */ o.id, u.name
FROM orders o JOIN users u ON o.user_id = u.id;
-- 强制不使用 Hash Join（使用 NLJ 或 BNL）
```

## Hash Join 不适用的情况

```sql
-- 1. 非等值连接（> < >= <= BETWEEN）：Hash Join 只支持等值（=）
SELECT * FROM orders o
JOIN discounts d ON o.amount BETWEEN d.min_amount AND d.max_amount;
-- 无法用 Hash Join（范围条件）→ 使用 BNL 或扫描

-- 2. JOIN 连接列有索引：优先 Index NLJ（更高效）
-- 如果 orders.user_id 有索引：
ALTER TABLE orders ADD INDEX idx_user (user_id);
EXPLAIN SELECT o.id, u.name FROM orders o JOIN users u ON o.user_id = u.id \G
-- Extra: NULL（使用 Index NLJ，不再用 Hash Join）

-- 3. 多表 JOIN 中部分连接有索引：
-- 有索引的 JOIN 对用 Index NLJ，无索引的 JOIN 对用 Hash Join
-- MySQL 8.0+ 可以在同一查询中混用两种 JOIN 算法

-- 4. STRAIGHT_JOIN 指定了固定驱动顺序：
-- STRAIGHT_JOIN 强制 Hash Join 的构建/探测方向也固定
```

## Hash Join 的性能收益场景

```sql
-- 场景1：大表与中等表的无索引等值 JOIN
-- orders（1000万行）JOIN order_items（5000万行），连接键无索引
-- BNL：O(1000万 × 5000万 / buffer_size) 次比较
-- Hash Join：O(1000万 + 5000万) 次操作 → 性能提升可达数十倍

-- 场景2：ETL/数据仓库场景的多表关联
-- 数仓场景中大量表没有业务索引，Hash Join 是主要 JOIN 算法
-- 对于 MySQL 的数仓查询场景，Hash Join 支持后大幅改善了性能

-- 场景3：临时添加 JOIN 的 ad-hoc 查询
-- 分析人员写的即席查询，通常不会预先建索引
-- Hash Join 让这类查询在无索引情况下也有合理的性能

-- 验证 Hash Join 的性能收益（对比实验）：
-- 关闭 Hash Join，使用 BNL：
SET SESSION optimizer_switch = 'hash_join=off';
-- 执行 JOIN 查询并记录执行时间

-- 开启 Hash Join：
SET SESSION optimizer_switch = 'hash_join=on';
-- 执行相同查询，对比执行时间
```

## 适用场景

- **数据分析型查询的优化**：分析类查询（OLAP 型）通常对多张大表做关联，且往往没有为所有连接键建立索引。MySQL 8.0.18+ 的 Hash Join 使这类查询在没有索引的情况下也能以 O(m+n) 的代价完成，比 BNL 的 O(m×n) 高效得多
- **临时关联查询**：在不希望为临时性的分析需求专门建索引时，Hash Join 提供了一个合理的无索引 JOIN 执行方案，避免了为了一次性分析需求而修改表结构的开销

## 常见问题

**为什么有些 JOIN 有索引也会用 Hash Join？**

在 MySQL 8.0.20 及更早版本中，优化器在某些情况下可能选择 Hash Join 而不是 Index NLJ，即使连接键有索引。这通常是成本估算的问题（统计信息不准或成本参数设置问题），可以通过 `/*+ NO_HASH_JOIN(t) */` Hint 强制走 Index NLJ，或通过 `ANALYZE TABLE` 更新统计信息。在 MySQL 8.0.20+ 中，优化器的 Hash Join 触发逻辑得到改善，有索引时通常会优先 Index NLJ。

---

## 注意事项

- Hash Join 在 MySQL 8.0.18 引入，但在 8.0.18~8.0.19 版本中只支持部分情况（不支持外连接 OUTER JOIN 和 Semi-join 中的 Hash Join）。从 MySQL 8.0.20 开始，Hash Join 支持了 LEFT JOIN、RIGHT JOIN 等外连接，适用范围大幅扩展。在 MySQL 8.4 中，Hash Join 的稳定性和适用范围已经非常完善。
- `join_buffer_size` 是连接级别（每个连接）的内存分配，Hash Join 使用这个参数作为哈希表内存上限。在高并发系统中，不应将 `join_buffer_size` 设置得过大（如超过 128MB），否则在并发高峰时内存消耗会非常可观（1000 个连接 × 128MB = 128GB）。建议保持较小的全局默认值，只在需要的 Session 中临时增大。

## 总结

Hash Join（MySQL 8.0.18+）是专为无索引等值连接优化的 JOIN 算法：构建阶段将小表（构建表）的连接键哈希到内存，探测阶段用大表（探测表）的连接键在哈希表中 O(1) 查找，总时间复杂度 O(m+n)，远优于 BNL 的 O(m×n)。触发条件：等值连接（=）+ 连接列无索引。识别：EXPLAIN 的 Extra 显示 `Using join buffer (hash join)`。内存由 `join_buffer_size` 控制；超出则分区溢写到磁盘（Grace Hash Join）。MySQL 8.0.20+ 支持 OUTER JOIN 的 Hash Join。控制：`optimizer_switch='hash_join=on/off'` 或 `/*+ HASH_JOIN/NO_HASH_JOIN */` Hint。

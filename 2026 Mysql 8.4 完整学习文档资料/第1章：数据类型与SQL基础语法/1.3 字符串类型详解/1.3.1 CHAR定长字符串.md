## CHAR 定长字符串

CHAR 是 MySQL 中的定长字符串类型。定长的含义是：无论实际存入的字符串有多短，存储时都会占用声明长度的固定空间。这个特性让 CHAR 在某些场景下比 VARCHAR 更快，但在存储较长且长度变化较大的字符串时，会浪费空间。

---

### 基本特性

| 属性 | 值 |
|------|---|
| 语法 | `CHAR(M)`，M 为字符数，范围 0~255 |
| 存储空间 | 固定 M 个字符，不足时右侧填充空格 |
| 字符计量单位 | 字符数（不是字节数），取决于字符集 |
| 检索时 | 自动去除末尾填充的空格 |
| 最大长度 | 255 个字符 |

---

### 语法

```sql
column_name CHAR(M)
column_name CHAR(M) NOT NULL DEFAULT ''
column_name CHAR(M) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
```

`CHAR` 不带 M 时，等价于 `CHAR(1)`。

---

### 存储行为

```sql
CREATE TABLE char_demo (
    fixed_code CHAR(10)
);

INSERT INTO char_demo VALUES ('ABC');     -- 存储为 'ABC       '（7个空格填充到10个字符）
INSERT INTO char_demo VALUES ('ABCDEFGHIJ'); -- 正好10个字符，不需要填充
INSERT INTO char_demo VALUES ('');        -- 存储为 '          '（10个空格）

-- 检索时自动去除末尾空格
SELECT fixed_code, LENGTH(fixed_code), CHAR_LENGTH(fixed_code) FROM char_demo;
-- 'ABC' -> LENGTH=3, CHAR_LENGTH=3（空格被去除了）
```

注意：空格的去除是 MySQL 的默认行为（PAD_CHAR_TO_FULL_LENGTH SQL 模式未启用时）。如果需要保留尾部空格，可以启用 `PAD_CHAR_TO_FULL_LENGTH`，但这个模式在 MySQL 8.0.13 后已废弃。

---

### 创建示例

```sql
-- 身份证号（固定18位）
CREATE TABLE id_cards (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    id_number   CHAR(18) NOT NULL COMMENT '身份证号，固定18位',
    name        VARCHAR(50) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_id_number (id_number)
);

-- 国家代码（ISO 3166-1 alpha-2，固定2位）
CREATE TABLE countries (
    code    CHAR(2) NOT NULL PRIMARY KEY COMMENT 'ISO 3166-1 alpha-2代码，如CN、US',
    name    VARCHAR(100) NOT NULL
);

-- MD5 哈希（固定32位十六进制字符）
CREATE TABLE file_checksums (
    file_id  INT UNSIGNED NOT NULL AUTO_INCREMENT,
    filename VARCHAR(255) NOT NULL,
    md5_hash CHAR(32) NOT NULL COMMENT 'MD5哈希，固定32个十六进制字符',
    PRIMARY KEY (file_id)
);

-- SHA-256 哈希（固定64位十六进制字符）
CREATE TABLE tokens (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT,
    token   CHAR(64) NOT NULL COMMENT 'SHA-256 hex，固定64位',
    user_id INT UNSIGNED NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_token (token)
);

INSERT INTO countries VALUES ('CN', '中国'), ('US', '美国'), ('JP', '日本');
INSERT INTO id_cards (id_number, name) VALUES ('110101199001011234', '张三');
```

### CHAR 的存储空间计算

CHAR(M) 在不同字符集下的实际字节占用：

| 字符集 | CHAR(10) 存储字节 | 说明 |
|--------|-----------------|------|
| latin1 | 10 字节 | 单字节字符集，1字符=1字节 |
| utf8mb4 | 最多 40 字节 | 每个字符最多 4 字节 |
| utf8mb3 | 最多 30 字节 | 每个字符最多 3 字节 |

在 utf8mb4 字符集下，`CHAR(10)` 实际会在行格式中保留 40 字节的空间（10 × 4字节/字符）。但 InnoDB 的 COMPACT 和 DYNAMIC 行格式做了优化：对于变长字符集，CHAR 列使用可变长度存储，实际占用字节取决于内容。

---

### 适用场景

- **固定长度的编码字段**：MD5 哈希（32位）、SHA-256 哈希（64位）、UUID（32或36位）、身份证号（18位）
- **短码标识**：国家代码（2位）、货币代码（3位）、语言代码（2位）
- **枚举状态的字符形式**：当状态用固定长度的字母代码表示时（如 `'Y'`/`'N'`，`'M'`/`'F'`）
- **联合索引中的短标识列**：CHAR 列在 B+Tree 索引中长度固定，访问速度稳定

### 常见问题

**为什么从 CHAR 列查出来的字符串后面没有空格，但 LENGTH 函数结果对不上？**

MySQL 默认在检索 CHAR 时去除尾部空格。如果需要保留（某些特殊场景），可以在建表时指定 `PAD_CHAR_TO_FULL_LENGTH` 模式，但这个模式已废弃，不推荐依赖它。

**CHAR(10) 存中文会有问题吗？**

不会，CHAR 的 M 是字符数，不是字节数。在 utf8mb4 字符集下，`CHAR(10)` 可以存 10 个汉字（每个汉字 3 字节），或 10 个英文字母（每个 1 字节），或混合内容最多 10 个字符。

**CHAR(0) 有意义吗？**

`CHAR(0)` 是合法的，只能存储空字符串 `''` 或 `NULL`，几乎没有实际使用场景，主要用于节省行的存储（标记某个特性是否存在）。

---

### 注意事项

- 在 utf8mb4 字符集下，`CHAR(M)` 在 InnoDB 中使用可变长度存储（不会浪费空间），但对于 MyISAM，仍然是严格的固定长度存储。这是 InnoDB 的存储优化。
- CHAR 列的值在比较时，尾部空格在大多数排序规则下被忽略。这意味着 `'ABC'` 和 `'ABC   '` 在 CHAR 列中被视为相等，但在 VARCHAR 列中可能不同。
- 超出 CHAR(M) 长度的字符串在严格 SQL 模式下会报错，在非严格模式下会被截断为 M 个字符。

---

### 总结

CHAR 是定长字符串类型，最大 255 个字符。它在存储固定长度的字符串（哈希值、编码、标识符）时语义清晰，且在某些情况下比 VARCHAR 有更好的存储局部性。在 InnoDB 引擎和 utf8mb4 字符集下，CHAR 使用了变长存储优化，不会因为字符串短而浪费空间。适合存储长度固定或几乎固定的短字符串，不适合存储长度差异大的普通文本。

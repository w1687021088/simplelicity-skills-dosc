## VARCHAR 变长字符串

VARCHAR 是 MySQL 中使用最广泛的字符串类型，也是 SQL 标准的核心数据类型之一。"变长"的含义是实际存储空间随字符串内容的长度变化，短字符串少占空间，长字符串多占空间，避免了 CHAR 固定占用的浪费。

---

### 基本特性

| 属性 | 值 |
|------|---|
| 语法 | `VARCHAR(M)`，M 为最大字符数 |
| 存储空间 | 实际字符长度 + 1或2字节的长度前缀 |
| 长度前缀 | M ≤ 255 时 1 字节，M > 255 时 2 字节 |
| 最大长度 | 65535 字节（受行最大字节数限制） |
| 尾部空格 | 保留（不像 CHAR 会去除） |

---

### 语法

```sql
column_name VARCHAR(M)
column_name VARCHAR(M) NOT NULL DEFAULT ''
column_name VARCHAR(M) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
```

---

### 最大长度的实际限制

理论上 VARCHAR 的最大 M 受行最大字节数（65535字节）约束：

- 使用 `utf8mb4` 字符集时，每个字符最多 4 字节，所以 `VARCHAR(M)` 最多允许约 16383 个字符（16383 × 4 = 65532 字节 + 2字节长度前缀 + 1字节NULL标志 ≈ 65535）
- 实际上一行中所有列的字节数加起来不能超过 65535，如果行中有多个 VARCHAR 列，每列的最大长度相互制约

```sql
-- 在 utf8mb4 下，VARCHAR 的实际最大字符数约 16383
CREATE TABLE t1 (col VARCHAR(16383)) CHARSET=utf8mb4;   -- 成功
CREATE TABLE t1 (col VARCHAR(16384)) CHARSET=utf8mb4;   -- 可能报错

-- 查看列的字节限制
SHOW WARNINGS;  -- 在接近限制时 MySQL 会给出警告
```

### 存储行为

```sql
CREATE TABLE varchar_demo (
    name VARCHAR(50),
    description VARCHAR(200)
);

-- 存储实际字符长度 + 1/2字节长度前缀
INSERT INTO varchar_demo VALUES ('Hi', 'Hello World');
-- 'Hi' 存储：2字节内容 + 1字节长度 = 3字节
-- 'Hello World' 存储：11字节内容 + 1字节长度 = 12字节

-- VARCHAR 保留尾部空格
INSERT INTO varchar_demo (name) VALUES ('Bob   ');  -- 保留了3个空格
SELECT name, LENGTH(name), CHAR_LENGTH(name) FROM varchar_demo WHERE name LIKE 'Bob%';
-- name: 'Bob   ', LENGTH=6, CHAR_LENGTH=6
```

CREATE TABLE users (

    nickname    VARCHAR(100) COMMENT '昵称',

    bio         VARCHAR(500) COMMENT '个人简介',

### VARCHAR 的索引限制

InnoDB 默认的索引键长度限制（Barracuda 格式 + Dynamic 行格式 + utf8mb4）：

| 配置 | 最大索引键长度 |
|------|-------------|
| innodb_large_prefix = OFF（旧默认）| 767 字节 |
| innodb_large_prefix = ON（现代默认）| 3072 字节 |
| utf8mb4 单字符最大 4 字节 | → 最多 768 个字符（3072÷4）|

```sql
-- 对 VARCHAR 创建全列索引时的限制
CREATE TABLE t1 (
    email VARCHAR(255),
    INDEX idx_email (email)    -- utf8mb4下：255×4=1020字节，在3072限制内，可以
);

-- 超长 VARCHAR 只能用前缀索引
CREATE TABLE t2 (
    content VARCHAR(2000),
    INDEX idx_content (content(100))  -- 只索引前100个字符
);

-- 查看 VARCHAR 字段能否直接创建完整索引
-- 规则：列字节数 = VARCHAR(M) × 字符集最大字节数
-- utf8mb4: M × 4 ≤ 3072 → M ≤ 768
```

### 适用场景

- **用户名、邮箱**：长度有限制但不固定，VARCHAR 最合适
- **商品名称、标题**：通常在 200 字符以内，内容长度变化大
- **URL 地址**：长度差异大，用 VARCHAR(2048) 或更大
- **短描述、标签**：内容不超过几百字符的文本
- **所有非固定长度的普通文本字段**：这是 VARCHAR 最广泛的使用场景

---

### 常见问题

**VARCHAR 设得大一点（如 VARCHAR(255)）会浪费空间吗？**

不会浪费磁盘存储空间（因为 VARCHAR 按实际长度存储），但会影响内存使用。在创建临时表（排序、GROUP BY 时）时，MySQL 按声明的最大长度分配内存，声明越大，临时表内存占用越多。所以 VARCHAR 的 M 应当设置为合理的实际上限，而不是随手写 255 或 1000。

**VARCHAR(50) 存入 51 个字符会怎样？**

在严格 SQL 模式（`STRICT_TRANS_TABLES`，MySQL 8.4 默认启用）下会报错。在非严格模式下会截断为 50 个字符。

**VARCHAR 和 TEXT 哪个更快？**

对于短文本（几百字符以内），VARCHAR 通常更快，因为它存储在行内，不需要额外的页外存储。TEXT 列在超过一定大小后会离行存储，读取时需要额外 I/O。

---

### 注意事项

- VARCHAR 保留尾部空格，CHAR 不保留。在从 CHAR 迁移到 VARCHAR 时，要检查业务逻辑是否依赖了尾部空格的比较行为。
- VARCHAR(M) 的 M 应当根据实际业务的最大值设置，而不是随意猜测一个大数字。太大的声明会影响内存中临时表的大小。
- 同一列既有长字符串又有短字符串（差异很大）的场景，VARCHAR 相比 CHAR 有明显的存储节省；如果所有值长度接近，CHAR 的固定长度可能反而有轻微的性能优势（免去长度前缀解析）。

---

### 总结

VARCHAR 是变长字符串类型，按实际内容长度加 1~2 字节的长度前缀存储，不浪费空间。在 utf8mb4 字符集下，最大字符数约 16383。VARCHAR 是存储用户名、邮箱、名称、标题等普通文本字段的标准选择，比 CHAR 更灵活，比 TEXT 更高效（对于短文本）。设置 M 时应当根据业务实际最大值，而非随手设置过大的数字。

## TEXT 类型

TEXT 是 MySQL 中存储长文本的标准类型，最大支持 65535 字节（约 64KB）。它是 TEXT 家族中使用最广泛的成员，常用于存储文章正文、商品描述、评论内容等中等长度的文本数据。

---

### 基本特性

| 属性 | 值 |
|------|---|
| 最大存储 | 65535 字节（64KB - 1字节） |
| 最大字符数 | utf8mb4 下约 16383 个字符 |
| 存储方式 | 变长，2 字节长度前缀 |
| 行外存储 | 超过一定大小时存储在行外，行内保留指针 |
| DEFAULT 值 | 不支持 |
| 完整索引 | 不支持，只能用前缀索引 |

---

### 语法

```sql
column_name TEXT
column_name TEXT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
column_name TEXT NOT NULL
```

---

### InnoDB 中 TEXT 的行外存储

InnoDB 的行有大小限制（约 8KB 的行内数据上限，具体取决于页大小和行格式）。当 TEXT 列的内容较大时，InnoDB 会将数据存储在单独的溢出页（Overflow Page）中，行内只保留一个 20 字节的指针。

```sql
-- 查看行格式
SHOW CREATE TABLE posts;
-- ROW_FORMAT=DYNAMIC（InnoDB 8.0+ 默认）

-- 在 DYNAMIC 行格式下：
-- 超过一定大小（通常是 768 字节）的 TEXT/BLOB 列会离行存储
-- 行内只保留 20 字节的指针
-- 读取 TEXT 内容需要额外一次页 I/O
```

### 创建示例

```sql
-- 博客文章表
CREATE TABLE articles (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    title       VARCHAR(200) NOT NULL,
    summary     VARCHAR(500) COMMENT '摘要',
    content     TEXT NOT NULL COMMENT '文章正文，最大64KB',
    author_id   INT UNSIGNED NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    INDEX idx_author (author_id),
    INDEX idx_title (title)   -- 只对 VARCHAR 列建索引
);

-- 商品描述表
CREATE TABLE product_descriptions (
    product_id  INT UNSIGNED NOT NULL PRIMARY KEY,
    description TEXT COMMENT '商品描述'
);

-- 用户评论表
CREATE TABLE reviews (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     INT UNSIGNED NOT NULL,
    product_id  INT UNSIGNED NOT NULL,
    content     TEXT NOT NULL,
    rating      TINYINT UNSIGNED NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

INSERT INTO articles (title, content, author_id) 
VALUES ('MySQL 8.4 新特性', '详细介绍了 MySQL 8.4 的各项改进...', 1);
```

### TEXT 的前缀索引

TEXT 列不能创建完整列索引，只能创建前缀索引：

```sql
-- 对 TEXT 列创建前缀索引（索引前 100 个字节）
ALTER TABLE articles ADD INDEX idx_content_prefix (content(100));

-- 前缀索引的局限：不能用于 ORDER BY、GROUP BY、覆盖索引
-- 只能用于 WHERE content LIKE '关键词%' 这种前缀匹配
SELECT * FROM articles WHERE content LIKE 'MySQL%';  -- 能用到前缀索引

-- 全文搜索用 FULLTEXT 索引（比前缀索引更强大）
ALTER TABLE articles ADD FULLTEXT INDEX ft_content (content);
SELECT * FROM articles WHERE MATCH(content) AGAINST('MySQL 8.4' IN BOOLEAN MODE);
```

### TEXT 与 VARCHAR 的选择

| 场景 | 建议类型 | 原因 |
|------|---------|------|
| 用户名、邮箱（< 255字符）| VARCHAR | 支持 DEFAULT，可直接建索引 |
| 文章正文（> 500字符）| TEXT | 不受行宽度限制 |
| 短描述（< 500字符）| VARCHAR(500) | 行内存储，读取更快 |
| 超长文章（> 64KB）| MEDIUMTEXT/LONGTEXT | TEXT 不够大 |

---

### 适用场景

- **博客/CMS 文章正文**：通常在几千字以内，TEXT 的 64KB 上限足够
- **商品详情描述**：中等长度的产品说明
- **用户评论**：评论内容通常不超过几千字
- **配置内容**：存储较长的 JSON 配置字符串（如果不用 JSON 类型）
- **日志消息**：单条日志记录（如果日志内容不超过 64KB）

### 常见问题

**TEXT 存储中文时，64KB 能存多少字？**

TEXT 的 65535 字节在 utf8mb4 字符集下（中文字符一般是 3 字节），理论上能存约 21845 个汉字（65535 ÷ 3），实际由于 2 字节长度前缀，约 21844 个汉字。如果文章超过这个长度，需要用 MEDIUMTEXT。

**在 TEXT 列上用 LIKE 查询性能如何？**

TEXT 列的 `LIKE '%关键词%'` 是全表扫描，没有索引可用（前缀索引只支持前缀匹配，不支持中缀）。对于全文搜索需求，应建立 FULLTEXT 索引，或者将文本同步到专业的搜索引擎（Elasticsearch 等）。

**能把 VARCHAR(10000) 改为 TEXT 吗？**

可以，但注意 TEXT 不支持 DEFAULT 值，如果原 VARCHAR 列有 DEFAULT，修改时需要先处理这个问题。从 VARCHAR 到 TEXT 的变更是安全的数据转换，反方向（TEXT 到 VARCHAR）需要确认 VARCHAR 的 M 足够大。

---

### 注意事项

- TEXT 列在 GROUP BY、ORDER BY 中使用时，MySQL 需要在临时表中处理，内存效率低于 VARCHAR。如果文章标题等需要排序/分组的字段，应该存在 VARCHAR 列而不是 TEXT。
- 不要在 TEXT 列上做 `WHERE content = '完整字符串'` 的等值查询，TEXT 的等值比较不会用到索引，且全表扫描极慢。
- 在设计时如果不确定内容会有多长，宁可先用 MEDIUMTEXT，给自己留一些余量，之后从大类型改为小类型比从小改为大的风险要低。

---

### 总结

TEXT 类型最大存储 65535 字节（utf8mb4 下约 16383 个字符），适合存储博客正文、商品描述、用户评论等中等长度文本。它不支持 DEFAULT 值和完整列索引，排序和分组效率不如 VARCHAR。内容长度确定在 500 字符以内的字段，优先选 VARCHAR；内容可能超过几百字的长文本，选 TEXT 或更大的类型。

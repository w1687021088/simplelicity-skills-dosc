# CHAR 与 VARCHAR 存储差异对比

CHAR 和 VARCHAR 都是存储字符串的基本类型，两者最本质的区别是存储策略：一个定长，一个变长。在实际开发中，选错类型不会导致功能错误，但会影响存储效率、查询性能以及某些边界行为（如尾部空格的处理）。

---

## 核心差异对比

| 对比维度 | CHAR(M) | VARCHAR(M) |
|---------|---------|-----------|
| 存储方式 | 定长，不足 M 时右侧填充空格 | 变长，按实际字符数 + 长度前缀存储 |
| 长度前缀 | 无 | 1 字节（M≤255）或 2 字节（M>255）|
| 最大 M | 255 个字符 | 约 16383 个字符（utf8mb4下）|
| 检索时空格 | 去除末尾填充空格 | 保留末尾空格 |
| 存储一致性 | 每行该列占用空间固定 | 每行该列占用空间随内容变化 |
| 适合内容 | 长度固定或接近固定的短字符串 | 长度变化较大的字符串 |

---

## 存储空间详细对比

以 utf8mb4 字符集为例，在 InnoDB 引擎中：

| 字符串内容 | CHAR(10) 占用 | VARCHAR(10) 占用 |
|-----------|-------------|----------------|
| `'Hi'`（2字符）| 最多 40 字节（InnoDB 优化）| 2字节内容 + 1字节长度 = 3字节 |
| `'Hello'`（5字符）| 最多 40 字节 | 5字节 + 1字节 = 6字节 |
| `'ABCDEFGHIJ'`（10字符）| 最多 40 字节 | 10字节 + 1字节 = 11字节 |

注意：InnoDB 的 COMPACT/DYNAMIC 行格式对 utf8mb4 字符集的 CHAR 列使用可变长存储，实际字节数取决于字符内容。但对于单字节字符集（如 latin1），CHAR(10) 严格占用 10 字节。

## 尾部空格行为差异

```sql
CREATE TABLE space_test (
    c CHAR(5),
    v VARCHAR(5)
);

INSERT INTO space_test VALUES ('AB   ', 'AB   ');  -- 各有3个尾部空格

SELECT c, v, LENGTH(c), LENGTH(v) FROM space_test;
-- c: 'AB'  LENGTH=2（尾部空格被自动去除）
-- v: 'AB   ' LENGTH=5（尾部空格保留）

-- CHAR 中，'AB' 和 'AB   ' 是等价的
SELECT * FROM space_test WHERE c = 'AB';    -- 返回行（'AB   ' 等于 'AB'）
SELECT * FROM space_test WHERE v = 'AB';    -- 不返回行（'AB   ' 不等于 'AB'）
SELECT * FROM space_test WHERE v = 'AB   '; -- 返回行（精确匹配含空格的值）
```

这个差异在做数据验证或比较时需要特别注意。

## 何时选 CHAR，何时选 VARCHAR

**选 CHAR 的情况：**
- 所有值长度固定，如 MD5 哈希（32位）、UUID（36位）、身份证号（18位）、手机号（11位）
- 列的值长度非常接近，如 ISO 国家代码（2位）、货币代码（3位）
- 列很短（1~4 字符），此时 VARCHAR 的长度前缀开销相对较大

**选 VARCHAR 的情况：**
- 字符串长度差异明显，如用户名（2~50字符）、邮箱（5~254字符）
- 内容较长的文本，但又不需要 TEXT 的无限长
- 大多数普通业务字符串字段的默认选择

---

## 性能方面的考量

**CHAR 的优势：**
- 固定行宽的 MyISAM 表能快速计算行偏移，顺序扫描更快（但 InnoDB 不受益，因为它用行 ID 定位）
- 在某些排序操作中，CHAR 的固定宽度让内存分配更简单

**VARCHAR 的优势：**
- 存储短字符串时占用空间少
- 在列宽度差异大的情况下，VARCHAR 能节省大量空间

实际上，在现代 MySQL（InnoDB 引擎 + DYNAMIC 行格式）的生产负载中，CHAR 和 VARCHAR 在读取性能上的差异微乎其微，存储节省是做选择时更现实的考量因素。

## 实际建表对比示例

```sql
-- 用 CHAR 的场景
CREATE TABLE auth_tokens (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    token_hash  CHAR(64) NOT NULL COMMENT 'SHA-256 hex，固定64位',
    user_id     INT UNSIGNED NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_token (token_hash)
);

-- 用 VARCHAR 的场景
CREATE TABLE users (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    username    VARCHAR(50) NOT NULL COMMENT '用户名，2~50字符',
    email       VARCHAR(255) NOT NULL COMMENT '邮箱',
    city        VARCHAR(100) COMMENT '城市',
    PRIMARY KEY (id)
);

-- 有时会混用（同一表里 CHAR 和 VARCHAR 共存）
CREATE TABLE orders (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_no    CHAR(20) NOT NULL COMMENT '订单号，固定20位',
    remark      VARCHAR(500) COMMENT '备注',
    PRIMARY KEY (id)
);
```

## 常见问题

**能把 CHAR 列改为 VARCHAR 吗？**

可以，且通常是安全的。`ALTER TABLE t MODIFY column VARCHAR(M)` 会把 CHAR 转为 VARCHAR。转换后原来尾部填充的空格会被保留在数据中，如果有业务逻辑依赖 CHAR 的空格自动去除行为，需要提前检查并处理数据。

**用 CHAR(255) 而不用 VARCHAR(255) 有什么问题？**

在 utf8mb4 字符集下，CHAR(255) 在 MyISAM 引擎中每列固定占用 255×3=765 字节。在 InnoDB 中虽然使用变长存储，但内存中的临时表仍按最大宽度分配，会浪费大量内存。总结：不要用大长度的 CHAR，CHAR 的优势只在短固定长度场景下才体现。

---

## 注意事项

- 在多列混合的宽表设计中，如果有几十个短固定编码列，使用 CHAR 既语义清晰（声明了"此列总是固定长度"）又不浪费空间。
- VARCHAR(1) 和 CHAR(1) 对单字符列来说，存储差异只是 1 个长度前缀字节，通常选 CHAR(1) 语义更清晰。
- 不要把 CHAR 当成"更快的 VARCHAR"来随意使用，真正的选择依据是"这个字段的值长度是否固定"。

---

## 总结

CHAR 和 VARCHAR 的核心差异是定长与变长：CHAR 固定占用声明长度的空间，检索时去除尾部空格；VARCHAR 按实际内容存储，保留尾部空格。选型规则简单明了：值长度固定或极接近固定的短字符串用 CHAR，其他所有情况用 VARCHAR。在 InnoDB + utf8mb4 的现代 MySQL 环境下，两者性能差异极小，存储效率是选型的主要考量。

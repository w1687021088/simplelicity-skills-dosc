# INDEX 普通索引创建

普通索引（INDEX 或 KEY）是 MySQL 中最基础的索引类型，不要求索引列的值唯一，主要目的是加速查询。理解索引的创建语法、索引类型选择和最左前缀原则，是编写高性能 SQL 的基础。

---

## 语法

```sql
-- 建表时创建索引
INDEX [index_name] (col_name [(length)] [ASC | DESC] [, ...])
KEY [index_name] (col_name [(length)] [ASC | DESC] [, ...])  -- KEY 是 INDEX 的别名

-- 创建后单独添加
ALTER TABLE tbl_name ADD INDEX index_name (col_name [, ...]);
CREATE INDEX index_name ON tbl_name (col_name [, ...]);

-- 前缀索引（对长字符串的前 N 个字符建索引）
ALTER TABLE tbl_name ADD INDEX idx_prefix (col_name(N));
```

---

## 创建示例

```sql
-- 建表时创建索引
CREATE TABLE orders (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     INT UNSIGNED NOT NULL,
    status      TINYINT UNSIGNED NOT NULL DEFAULT 0,
    amount      DECIMAL(10, 2) NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    INDEX idx_user_id (user_id),                        -- 单列索引
    INDEX idx_status_created (status, created_at),      -- 复合索引
    INDEX idx_created (created_at)                      -- 时间索引
) ENGINE=InnoDB;

-- 建表后添加索引
ALTER TABLE orders ADD INDEX idx_amount (amount);

-- CREATE INDEX 方式
CREATE INDEX idx_user_status ON orders (user_id, status);
```

---

## 复合索引与最左前缀原则

```sql
-- 假设有复合索引：INDEX idx_user_status_created (user_id, status, created_at)
-- 以下查询可以使用该索引：
SELECT * FROM orders WHERE user_id = 100;                          -- 使用 user_id 前缀
SELECT * FROM orders WHERE user_id = 100 AND status = 1;           -- 使用 user_id + status 前缀
SELECT * FROM orders WHERE user_id = 100 AND status = 1 AND created_at > '2026-01-01';  -- 全部使用

-- 以下查询不能使用该索引（跳过了 user_id）：
SELECT * FROM orders WHERE status = 1;                             -- 无法使用（跳过 user_id）
SELECT * FROM orders WHERE status = 1 AND created_at > '2026-01-01'; -- 无法使用

-- 以下查询部分使用（中间列是范围查询，后面的列无法用索引）：
SELECT * FROM orders WHERE user_id = 100 AND created_at > '2026-01-01';
-- 只能用 user_id 部分，created_at 不走索引（中间跳过了 status）
```

## 前缀索引

```sql
-- 对长字符串列，可以只索引前 N 个字符节省索引空间
CREATE TABLE articles (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    url     VARCHAR(1000) NOT NULL,
    title   VARCHAR(500) NOT NULL,
    content MEDIUMTEXT
);

-- 对 url 的前 200 个字符建前缀索引
ALTER TABLE articles ADD INDEX idx_url_prefix (url(200));

-- 对 title 的前 100 个字符建前缀索引
ALTER TABLE articles ADD INDEX idx_title (title(100));

-- 注意：前缀索引不能用于 ORDER BY 和 GROUP BY，也不能作为覆盖索引
```

## 查看索引

```sql
-- 查看表的所有索引
SHOW INDEX FROM orders;

-- 关键字段说明：
-- Key_name: 索引名称
-- Non_unique: 0=唯一索引, 1=普通索引
-- Seq_in_index: 复合索引中列的位置
-- Cardinality: 索引列的基数（唯一值估计数，越高选择性越好）
-- Sub_part: 前缀索引的字符数

-- 通过 information_schema 查看
SELECT index_name, seq_in_index, column_name, non_unique, cardinality
FROM information_schema.STATISTICS
WHERE table_schema = DATABASE() AND table_name = 'orders'
ORDER BY index_name, seq_in_index;
```

## EXPLAIN 验证索引使用

```sql
-- 使用 EXPLAIN 检查查询是否用到了索引
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1;

-- 关键字段：
-- type: ALL（全表）< index（全索引扫描）< range（范围）< ref（非唯一匹配）< eq_ref（唯一匹配）< const
-- key: 实际使用的索引名称
-- key_len: 使用的索引长度（复合索引中用了几个列）
-- rows: 估计扫描行数
-- Extra: 附加信息（Using index=覆盖索引, Using where=回表, Using filesort=排序无索引）
```

---

## 适用场景

- **WHERE 条件列**：最常用，让查询直接通过索引定位数据
- **JOIN 连接列**：外键列和 JOIN ON 条件列
- **ORDER BY / GROUP BY 列**：减少排序开销
- **覆盖索引**：SELECT 的列都在索引中，不需要回表查数据

---

## 常见问题

**索引越多越好吗？**

不是。索引加速读操作，但增加写操作（INSERT/UPDATE/DELETE）的开销——每次写入都需要维护所有相关索引。对于写多读少的表（如日志表），过多索引会明显降低写入性能。一般建议单表索引不超过 5~6 个。

**什么情况下索引会失效？**

- 在索引列上使用函数：`WHERE YEAR(created_at) = 2026`（失效）→ 改为范围查询
- 类型不匹配：字符串列和数字比较（如 `WHERE phone = 13800000000`，phone 是 VARCHAR）
- LIKE 以通配符开头：`WHERE title LIKE '%mysql%'`（失效）
- 使用 OR 连接不同索引列（部分情况失效）

---

## 注意事项

- 复合索引的列顺序很重要：将选择性高（唯一值多）的列放在前面，查询中常用的等值过滤列放在复合索引的前面，范围过滤列放在后面。
- 不要对低基数列（如只有 0/1 两个值的状态字段）单独建索引，选择性太低（查一半数据），索引效果差，优化器可能选择全表扫描。低基数列应与高选择性列组合成复合索引。

---

## 总结

INDEX（或 KEY）创建普通 B-Tree 索引，是加速查询的核心手段。复合索引遵循最左前缀原则，查询条件必须从索引最左列开始连续使用。前缀索引可以节省索引空间但功能受限。通过 `SHOW INDEX` 和 `EXPLAIN` 可以验证索引的存在和使用情况。索引设计需要权衡读写性能，不应无限制地增加索引数量。

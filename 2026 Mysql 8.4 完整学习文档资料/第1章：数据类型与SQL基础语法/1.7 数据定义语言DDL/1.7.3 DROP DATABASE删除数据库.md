# DROP DATABASE 删除数据库

`DROP DATABASE` 是 MySQL 中删除整个数据库（及其所有表、视图、存储过程等对象）的语句。它是破坏性操作，执行后数据无法从 MySQL 层面恢复，操作前必须确认有完整备份。

---

## 语法

```sql
DROP DATABASE [IF EXISTS] db_name;

-- DROP SCHEMA 与 DROP DATABASE 完全等价
DROP SCHEMA [IF EXISTS] db_name;
```

---

## 示例

```sql
-- 删除指定数据库（如果不存在会报错）
DROP DATABASE my_test_db;

-- 安全删除（如果存在则删除，不存在则不报错）
DROP DATABASE IF EXISTS my_test_db;

-- 使用 DROP SCHEMA（等价）
DROP SCHEMA IF EXISTS my_test_db;
```

---

## DROP DATABASE 删除的内容

执行 `DROP DATABASE db_name` 后，以下内容会被删除：
- 数据库目录下的所有表（`.ibd` 文件、`.frm` 文件）
- 数据库目录本身
- 所有视图
- 所有存储过程和函数
- 所有触发器
- 数据库级别的权限授权（GRANT ... ON db_name.\*）

不会删除的内容：
- Binlog 中已经记录的历史日志
- 其他数据库中对本库中对象的引用（如外键约束指向的表已删除，需要手动清理）

---

## 误删后的恢复思路

```sql
-- 通过 Binlog 恢复的基本思路（需要 Binlog 开启且未超过保留期）
-- 1. 找到 DROP DATABASE 语句前的最后一个 Binlog 位置
-- 2. 用 mysqlbinlog 解析 Binlog，恢复到 DROP DATABASE 前
-- 示例（仅供参考）：
-- mysqlbinlog --stop-position=<position_before_drop> mysql-bin.000001 | mysql -u root -p

-- 如果有 mysqldump 备份，直接恢复：
-- mysql -u root -p < backup.sql
```

## 适用场景

- 清理测试数据库
- 删除已下线业务的数据库（下线前必须确认已备份、已通知相关方）
- 自动化脚本中的环境初始化（先 DROP IF EXISTS，再 CREATE）

---

## 常见问题

**DROP DATABASE 会立即释放磁盘空间吗？**

会，InnoDB 的独立表空间文件（`.ibd`）会被删除，磁盘空间立即释放。

**DROP DATABASE 需要什么权限？**

需要对该数据库的 `DROP` 权限，或者全局的 `DROP` 权限。`root` 用户默认有该权限。

---

## 注意事项

- `DROP DATABASE` 是不可逆的破坏性操作，没有回收站，执行后数据直接消失（除非通过 Binlog 或备份恢复）。**生产环境执行前必须确认有完整备份并通知相关负责人。**
- 在启用了 Binlog 的环境中，DROP DATABASE 会被记录到 Binlog，可以用于主从复制同步，也可以用于灾难恢复时找到误删时间点。
- 执行前可以用 `USE db_name; SHOW TABLES;` 确认要删除的数据库内容，避免删错。

---

## 总结

`DROP DATABASE` 删除整个数据库及其所有对象，操作不可逆。加上 `IF EXISTS` 可以避免数据库不存在时报错。在自动化脚本中常与 `CREATE DATABASE` 配合使用（先删除再创建，保证环境干净）。生产环境执行此命令必须有备份，且应在明确的维护窗口内进行。

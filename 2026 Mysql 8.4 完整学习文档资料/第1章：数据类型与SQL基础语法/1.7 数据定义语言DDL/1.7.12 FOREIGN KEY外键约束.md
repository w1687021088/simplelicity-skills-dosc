# FOREIGN KEY 外键约束

外键约束（FOREIGN KEY）在数据库层面强制引用完整性——子表中的外键列的值，必须存在于父表的主键或唯一键中（或为 NULL，如果允许 NULL）。外键是关系型数据库表达表间关系的标准机制，但在高并发互联网业务中，其使用需要权衡。

---

## 语法

```sql
-- 列定义内（只能引用单列）
col_name data_type REFERENCES parent_tbl (parent_col)
    [ON DELETE ref_action]
    [ON UPDATE ref_action]

-- 表级声明（推荐，可命名，支持复合外键）
[CONSTRAINT fk_name] FOREIGN KEY (child_col [, ...])
    REFERENCES parent_tbl (parent_col [, ...])
    [ON DELETE ref_action]
    [ON UPDATE ref_action]

-- ref_action:
--   RESTRICT  | NO ACTION  -- 父行被删/改时，如果有子行则报错（默认）
--   CASCADE               -- 父行删除/更新时，级联删/改子行
--   SET NULL              -- 父行删除/更新时，子行的外键列设为 NULL
--   SET DEFAULT           -- 父行删除/更新时，子行的外键列设为默认值（InnoDB 不支持）
```

---

## 创建示例

```sql
-- 父表
CREATE TABLE departments (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT,
    name    VARCHAR(100) NOT NULL,
    PRIMARY KEY (id)
);

-- 子表（包含外键）
CREATE TABLE employees (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    name        VARCHAR(100) NOT NULL,
    dept_id     INT UNSIGNED,   -- 允许 NULL（员工可能未分配部门）
    PRIMARY KEY (id),
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id)
        REFERENCES departments(id)
        ON DELETE SET NULL     -- 部门删除时，员工的 dept_id 设为 NULL
        ON UPDATE CASCADE      -- 部门 ID 更新时，员工表级联更新
);

-- 订单与用户的强关联（禁止删除有订单的用户）
CREATE TABLE orders (
    id      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id INT UNSIGNED NOT NULL,
    amount  DECIMAL(10, 2) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_orders_user FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE RESTRICT   -- 有订单的用户不能被删除
        ON UPDATE CASCADE    -- 用户 ID 更新时级联更新（实际上用户 ID 不应该改变）
);
```

---

## 参照动作（ref_action）对比

| 参照动作 | 父行删除时 | 父行更新时 |
|---------|----------|---------|
| RESTRICT / NO ACTION | 报错，不允许操作 | 报错，不允许操作 |
| CASCADE | 子行也被删除 | 子行的外键值也被更新 |
| SET NULL | 子行外键列设为 NULL（列须允许 NULL）| 子行外键列设为 NULL |
| SET DEFAULT | InnoDB 不支持 | InnoDB 不支持 |

## 外键的实际行为演示

```sql
-- 测试 RESTRICT
INSERT INTO departments VALUES (1, '技术部'), (2, '市场部');
INSERT INTO employees (name, dept_id) VALUES ('张三', 1), ('李四', 1);

-- 删除有员工的部门（会报错）
DELETE FROM departments WHERE id = 1;
-- ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails

-- 先清空子表再删
DELETE FROM employees WHERE dept_id = 1;
DELETE FROM departments WHERE id = 1;  -- 现在可以删除

-- 测试 CASCADE（以 orders 表为例）
-- 当 fk 设为 CASCADE DELETE 时，删除用户会自动删除其所有订单
DELETE FROM users WHERE id = 100;
-- 自动删除 orders 表中 user_id = 100 的所有行
```

## 查看外键约束

```sql
-- 查看表的外键约束
SELECT constraint_name, column_name, referenced_table_name, referenced_column_name,
       delete_rule, update_rule
FROM information_schema.KEY_COLUMN_USAGE k
JOIN information_schema.REFERENTIAL_CONSTRAINTS r
    ON k.constraint_name = r.constraint_name AND k.constraint_schema = r.constraint_schema
WHERE k.table_schema = DATABASE() AND k.table_name = 'employees';

-- SHOW CREATE TABLE 也会显示外键
SHOW CREATE TABLE employees;
```

## 添加和删除外键约束

```sql
-- 添加外键（已有数据必须满足约束，否则失败）
ALTER TABLE employees ADD CONSTRAINT fk_emp_dept
    FOREIGN KEY (dept_id) REFERENCES departments(id) ON DELETE SET NULL;

-- 删除外键约束
ALTER TABLE employees DROP FOREIGN KEY fk_emp_dept;

-- 临时禁用外键检查（批量导入数据时常用）
SET FOREIGN_KEY_CHECKS = 0;
-- 执行批量操作...
SET FOREIGN_KEY_CHECKS = 1;
```

## 适用场景

- **数据库层面的引用完整性**：传统企业系统、ERP、金融系统
- **开发和测试环境**：有外键约束可以快速发现关联数据问题
- **数据量小、写入频率低的场景**：外键检查的性能开销在此可以忽略

---

## 常见问题

**高并发互联网业务为什么常见不用外键？**

外键约束在每次写入时都需要检查父表，在高并发场景下会产生额外的行锁竞争，影响写入性能。另外，分库分表后父子表可能在不同的数据库实例上，外键无法跨库使用。因此互联网业务通常将引用完整性的保证移到应用层（代码逻辑）来实现，数据库只做存储。

**外键列必须有索引吗？**

MySQL 要求外键列上必须有索引（如果没有，会自动创建）。父表被引用的列也必须是主键或唯一键。

---

## 注意事项

- 外键列的类型必须与父表被引用列的类型完全一致（包括 UNSIGNED/SIGNED）。
- `ON DELETE CASCADE` 使用时需谨慎，删除父行会级联删除大量子行，在生产环境可能造成意外数据丢失。建议在删除逻辑上使用逻辑删除（软删除）而不是物理删除。
- 使用外键时，表的创建和删除顺序有约束：先创建父表，再创建子表；先删除子表，再删除父表。

---

## 总结

FOREIGN KEY 约束在数据库层面强制引用完整性，支持 RESTRICT、CASCADE、SET NULL 三种参照动作。它适合数据一致性要求高且写入频率低的场景；高并发互联网系统通常在应用层保证引用完整性，不使用数据库外键。外键列必须有索引，类型必须与父表引用列完全一致。

# PRIMARY KEY 主键约束

PRIMARY KEY 是表中唯一标识每一行的约束，结合了唯一性（UNIQUE）和非空性（NOT NULL）两个约束。在 InnoDB 存储引擎中，主键同时是聚簇索引，决定了数据的物理存储顺序，对查询性能影响极大。

---

## 主键的特性

| 特性 | 说明 |
|------|------|
| 唯一性 | 同一表中不能有两行的主键值相同 |
| 非空性 | 主键列不能为 NULL（隐式添加 NOT NULL）|
| 唯一索引 | 主键自动创建唯一的 B-Tree 索引 |
| InnoDB 聚簇 | InnoDB 的主键索引即聚簇索引，数据按主键排序存储 |
| 每表只能一个 | 一张表只能有一个主键 |

---

## 语法

```sql
-- 列级声明（单列主键推荐写法）
col_name data_type PRIMARY KEY

-- 表级声明（单列或复合主键）
PRIMARY KEY (col_name [, col_name ...])

-- 命名主键（实际上主键名始终是 PRIMARY，命名无效）
CONSTRAINT pk_name PRIMARY KEY (col_name [, col_name ...])
```

---

## 创建示例

```sql
-- 单列整数主键（最常见）
CREATE TABLE articles (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    title   VARCHAR(200) NOT NULL
);

-- 等价写法（表级声明）
CREATE TABLE articles (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT,
    title   VARCHAR(200) NOT NULL,
    PRIMARY KEY (id)
);

-- 复合主键（联合多列唯一标识一行）
CREATE TABLE order_items (
    order_id    BIGINT UNSIGNED NOT NULL,
    item_seq    SMALLINT UNSIGNED NOT NULL,
    product_id  INT UNSIGNED NOT NULL,
    quantity    INT UNSIGNED NOT NULL DEFAULT 1,
    price       DECIMAL(10, 2) NOT NULL,
    PRIMARY KEY (order_id, item_seq)   -- 复合主键
);

-- 字符串主键（不推荐，性能差，但业务主键可能需要）
CREATE TABLE countries (
    code    CHAR(2) NOT NULL PRIMARY KEY COMMENT 'ISO 3166-1 alpha-2 国家代码',
    name    VARCHAR(100) NOT NULL
);

-- BIGINT 主键（雪花算法 ID 场景）
CREATE TABLE events (
    id          BIGINT UNSIGNED NOT NULL PRIMARY KEY COMMENT '雪花算法生成的 ID',
    event_type  VARCHAR(50) NOT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## InnoDB 聚簇索引原理

InnoDB 中，主键索引就是聚簇索引（Clustered Index），表数据按主键顺序物理存储：

```sql
-- 主键设计的影响：
-- 1. 单调递增的主键（如 AUTO_INCREMENT）
--    - 每次插入在 B+树最右边追加，不需要移动数据，性能好
--    - 行数据紧凑存储，顺序读效率高

-- 2. 随机主键（如 UUID 字符串）
--    - 每次插入可能在 B+树中间位置，导致页分裂，性能差
--    - 数据碎片化，随机 I/O 多

-- UUID 主键的问题演示
CREATE TABLE uuid_test (
    id   CHAR(36) NOT NULL PRIMARY KEY,  -- UUID 字符串（随机顺序）
    data VARCHAR(100)
);
-- 插入时 UUID 是随机值，InnoDB 需要频繁进行页分裂
-- 相比 AUTO_INCREMENT，在大批量写入场景下性能差很多

-- 改进：使用 UUID_TO_BIN() 将 UUID 存为 BINARY(16)
-- 或使用 UUID v7（时间有序）
CREATE TABLE uuid_v7_test (
    id   BINARY(16) NOT NULL PRIMARY KEY,  -- 有序 UUID 二进制
    data VARCHAR(100)
);
```

## 没有主键的表

```sql
-- 如果不定义主键，InnoDB 会按以下顺序选择聚簇索引：
-- 1. 第一个 NOT NULL 的 UNIQUE 索引
-- 2. 没有合适索引时，InnoDB 自动生成一个隐藏的 6 字节行 ID（不可见）

-- 以下表没有明确主键（不推荐）
CREATE TABLE no_pk_table (
    name    VARCHAR(100) NOT NULL,
    email   VARCHAR(200) NOT NULL UNIQUE  -- 这个 UNIQUE 索引会成为聚簇索引
);
```

没有主键的表在复制（Replication）场景中有风险——行格式的 binlog 无法精确定位某一行，DML 操作在从库上可能需要全表扫描。

---

## 适用场景

- **所有业务表都应该有主键**，这是最基本的表设计原则
- **单列自增整数（BIGINT/INT UNSIGNED AUTO_INCREMENT）**：最常见，适合绝大多数场景
- **复合主键**：关联表（多对多关系的中间表）的典型用法
- **业务主键（字符串/UUID）**：当业务需要使用有业务含义的唯一标识时

## 常见问题

**主键能修改吗？**

可以，通过 `ALTER TABLE ... DROP PRIMARY KEY` 删除后再 `ADD PRIMARY KEY(col)` 添加，但对于有外键引用的主键，需要先删除外键再操作。

**复合主键中列的顺序重要吗？**

很重要。复合主键按声明顺序作为 B+树的排序键，查询时遵循最左前缀原则——WHERE 条件中只有最左边的列时可以利用主键索引；跳过最左列则无法利用。

---

## 注意事项

- 主键值不要随意更新，主键是数据的唯一标识，也可能被外键引用；频繁更新主键会导致大量级联操作或外键错误。
- 自增主键在高并发场景中，`AUTO_INCREMENT` 会成为争抢点（自增锁）。MySQL 8.4 的自增锁已改为轻量级模式（`innodb_autoinc_lock_mode=2`，默认值），大幅减少竞争。
- 不建议用 FLOAT/DOUBLE/DECIMAL 作为主键，浮点数的精度问题会导致意外的唯一性冲突。

---

## 总结

PRIMARY KEY 约束同时包含唯一性和非空性，在 InnoDB 中即聚簇索引，决定数据物理存储顺序。推荐使用单调递增的整数（INT/BIGINT UNSIGNED AUTO_INCREMENT）作为主键，避免随机主键（UUID 字符串）造成的 B+树频繁页分裂。所有业务表都应该有主键，没有主键的表在复制和性能上都有隐患。

## TIMESTAMP 时间戳类型

TIMESTAMP 是 MySQL 中与时区联动的日期时间类型，占用 4 字节。它在存储时将本地时间转换为 UTC 保存，在检索时再转换回当前 `time_zone` 设置的时区。这一特性让 TIMESTAMP 天然适合跨时区的系统，但也引入了一个著名的限制——2038 年问题。

---

### 基本特性

| 属性 | 值 |
|------|---|
| 存储空间 | 4 字节 |
| 存储范围 | 1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC |
| 存储方式 | 以 UTC 时间存储（Unix 时间戳） |
| 检索方式 | 转换为当前 `time_zone` 对应的本地时间 |
| 时区敏感 | 是（随时区设置变化）|
| 小数秒 | 支持 TIMESTAMP(fsp)，fsp=0~6 |

---

### 语法

```sql
column_name TIMESTAMP
column_name TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
column_name TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
column_name TIMESTAMP(3)   -- 毫秒精度
```

---

### 创建示例

```sql
-- 带自动时间管理的表（TIMESTAMP 最常见用法）
CREATE TABLE events (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    name        VARCHAR(200) NOT NULL,
    occurred_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

-- 创建时间和更新时间
CREATE TABLE records (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    content     VARCHAR(500) NOT NULL,
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

INSERT INTO events (name) VALUES ('系统启动');
INSERT INTO records (content) VALUES ('初始内容');
UPDATE records SET content = '修改后内容' WHERE id = 1;  -- updated_at 自动更新
```

### 时区转换演示

```sql
-- 当前时区设置
SHOW VARIABLES LIKE 'time_zone';  -- 假设为 Asia/Shanghai（UTC+8）

-- 插入当前时间
INSERT INTO events (name) VALUES ('时区测试');
-- 假设插入时本地时间为 2026-03-14 18:00:00（北京时间）
-- 内部存储的是 UTC 时间：2026-03-14 10:00:00

-- 在 UTC+8 时区查询
SET SESSION time_zone = 'Asia/Shanghai';
SELECT occurred_at FROM events WHERE name = '时区测试';
-- 显示：2026-03-14 18:00:00（北京时间）

-- 切换到 UTC 时区查询
SET SESSION time_zone = '+00:00';
SELECT occurred_at FROM events WHERE name = '时区测试';
-- 显示：2026-03-14 10:00:00（UTC 时间）

-- 恢复时区
SET SESSION time_zone = 'Asia/Shanghai';
```

### 2038 年问题

TIMESTAMP 内部存储的是 32 位 Unix 时间戳（自 1970-01-01 00:00:00 UTC 起的秒数），32 位有符号整数的上限对应的时间是 2038-01-19 03:14:07 UTC：

```sql
-- 查看 TIMESTAMP 的最大值
SELECT TIMESTAMP('2038-01-19 03:14:07') AS max_timestamp;
-- 超过这个时间的值无法用 TIMESTAMP 存储

-- 在 2038 年之后仍然运行的系统，应该用 DATETIME 代替 TIMESTAMP
-- DATETIME 的上限是 9999-12-31 23:59:59
```

对于需要存储 2038 年之后时间的系统，必须使用 DATETIME 或 BIGINT（Unix 时间戳毫秒数）。

### TIMESTAMP 的 NOT NULL 和 NULL 行为

```sql
-- TIMESTAMP 列的特殊默认行为
-- 在 MySQL 8.0 之前，第一个 TIMESTAMP 列默认有 DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
-- MySQL 8.0 起，必须显式声明，否则列为 NOT NULL 但没有默认值

-- 显式声明（推荐写法）
CREATE TABLE t1 (
    ts TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- TIMESTAMP 列允许 NULL
CREATE TABLE t2 (
    ts TIMESTAMP NULL DEFAULT NULL
);
-- NULL 表示"未知时间"，与 DATETIME 的 NULL 语义相同
```

### 适用场景

- **跨时区系统中的事件时间**：同一时间在全球不同时区的用户看到各自的本地时间
- **数据同步时间戳**：记录数据最后同步的 UTC 时间，跨系统对比更方便
- **审计日志的精确时间**：记录操作发生的 UTC 绝对时间
- **系统启停时间**：服务器或应用的启停时间点

---

### 常见问题

**TIMESTAMP 和 DATETIME 都能做 DEFAULT CURRENT_TIMESTAMP，选哪个？**

如果系统只在单一时区运行且不考虑 2038 年问题，两者功能等价。如果系统是多时区或需要明确存储 UTC 时间，选 TIMESTAMP；如果需要保证 2038 年后仍然正确，选 DATETIME。

**修改服务器时区后，TIMESTAMP 列的值会变吗？**

内部存储的 UTC 值不变，但查询时的显示结果会变。这正是 TIMESTAMP 的特性——存储 UTC，展示本地时间。而 DATETIME 的显示值不受时区修改影响。

---

### 注意事项

- 运行到 2038 年之后的系统，如果仍使用 TIMESTAMP 列，会遇到存储失败（超出范围）。提前将关键表的 TIMESTAMP 列迁移到 DATETIME 或 BIGINT 是必要的。
- TIMESTAMP 的时区转换依赖 MySQL 服务器的 `time_zone` 变量设置，不同会话设置不同时区时，同一行的 TIMESTAMP 值会有不同的显示结果，需要在应用层统一处理。

---

### 总结

TIMESTAMP 占用 4 字节，以 UTC 存储，检索时转换为当前时区时间，最大范围到 2038-01-19 UTC。它天然支持时区转换，适合跨时区场景。其最大限制是 2038 年边界——2038 年之后的业务系统应使用 DATETIME。TIMESTAMP 与 DATETIME 都支持 `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` 自动时间管理。

# TIMESTAMP 与 DATETIME 时区差异

TIMESTAMP 和 DATETIME 是 MySQL 中最常用的两种日期时间类型，功能高度相似，但对时区的处理方式截然不同。选错类型在时区不一致的场景下会导致时间数据混乱，理解这个差异是正确设计数据库 schema 的基础。

---

## 核心差异对比

| 对比维度 | TIMESTAMP | DATETIME |
|---------|----------|---------|
| 存储空间 | 4 字节 | 5 字节 |
| 存储内容 | UTC 时间（自动转换）| 原始输入的时间值 |
| 读取时转换 | 转换为当前 `time_zone` | 直接返回存储值，无转换 |
| 时区敏感 | 是 | 否 |
| 日期范围 | 1970-01-01 UTC ~ 2038-01-19 UTC | 1000-01-01 ~ 9999-12-31 |
| 2038 问题 | 有 | 无 |
| DEFAULT CURRENT_TIMESTAMP | 支持 | 支持 |
| ON UPDATE CURRENT_TIMESTAMP | 支持 | 支持 |

## 时区行为演示

```sql
-- 准备测试表
CREATE TABLE tz_comparison (
    id  INT UNSIGNED NOT NULL AUTO_INCREMENT,
    ts  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    dt  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

-- 在 UTC+8（北京时间）下插入
SET SESSION time_zone = 'Asia/Shanghai';
INSERT INTO tz_comparison () VALUES ();
-- 假设插入时北京时间为：2026-03-14 18:00:00

-- 在 UTC+8 查询
SELECT id, ts, dt FROM tz_comparison;
-- ts: 2026-03-14 18:00:00
-- dt: 2026-03-14 18:00:00

-- 切换到 UTC+0 查询
SET SESSION time_zone = '+00:00';
SELECT id, ts, dt FROM tz_comparison;
-- ts: 2026-03-14 10:00:00（TIMESTAMP 自动转换，显示 UTC 时间）
-- dt: 2026-03-14 18:00:00（DATETIME 不变，仍是原来的值）

-- 切换到 UTC-5（美东时间）查询
SET SESSION time_zone = '-05:00';
SELECT id, ts, dt FROM tz_comparison;
-- ts: 2026-03-14 05:00:00（UTC-5 对应的本地时间）
-- dt: 2026-03-14 18:00:00（DATETIME 仍然不变）
```

## 修改服务器时区的影响

```sql
-- 重要：修改全局时区后，TIMESTAMP 列的显示值会改变
SHOW GLOBAL VARIABLES LIKE 'time_zone';  -- 查看当前全局时区

-- 假设服务器从 Asia/Shanghai 改为 UTC
SET GLOBAL time_zone = '+00:00';

-- 新连接查询同一行数据：
-- TIMESTAMP 列：显示 UTC 时间（比原来少 8 小时）
-- DATETIME 列：显示不变（还是当初写入的时间字符串）
```

这个行为会在 DBA 调整服务器时区后造成混乱——TIMESTAMP 列的数据"看起来"变了（实际存储的 UTC 值没有变），而 DATETIME 列的数据纹丝不动。

## 什么情况下用 TIMESTAMP

TIMESTAMP 适合需要"全球统一时间基准"的场景：
- 同一条记录需要在不同时区的用户面前显示对应的本地时间
- 多个时区的节点写入记录，需要在 UTC 基准下排序和比较
- 系统日志记录，UTC 时间是标准的、无歧义的时间表示

```sql
-- 示例：跨时区电商的订单时间
-- 北京用户（UTC+8）下单，纽约用户（UTC-5）查看时，
-- TIMESTAMP 会自动显示各自的本地时间

CREATE TABLE global_orders (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     INT UNSIGNED NOT NULL,
    placed_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '下单时间（UTC存储）',
    PRIMARY KEY (id)
);
```

---

## 什么情况下用 DATETIME

DATETIME 适合需要"原始时间不变"的场景：
- 时间本身不应随时区转换而改变，如"2026年春节假期从2月17日开始"，无论在哪个时区看都应该是 2月17日
- 历史日期记录（如合同签订日期、出生日期），需要保留原始值
- 系统只在单一时区运行，不需要跨时区转换
- 需要存储 2038 年之后的时间

```sql
-- 示例：国内系统的订单时间
CREATE TABLE cn_orders (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    placed_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '下单时间（北京时间原样存储）',
    PRIMARY KEY (id)
);

-- 示例：合同有效期（不应受时区影响）
CREATE TABLE contracts (
    id              INT UNSIGNED NOT NULL AUTO_INCREMENT,
    effective_date  DATE NOT NULL COMMENT '生效日期（纯日期，不含时间）',
    expire_at       DATETIME NOT NULL COMMENT '到期时间（原始时间，不转换）',
    PRIMARY KEY (id)
);
```

## 实际项目中的决策参考

| 场景 | 建议类型 | 原因 |
|------|---------|------|
| 国内单一时区系统 | DATETIME | 不需要时区转换，简单直观 |
| 全球多时区系统 | TIMESTAMP | 统一 UTC 存储，本地化展示 |
| `created_at`/`updated_at` | 两者均可 | 根据系统是否跨时区决定 |
| 历史归档时间（精确）| DATETIME | 不希望时区变更影响历史记录 |
| 需要 2038 年之后的时间 | DATETIME | TIMESTAMP 无法存储 |
| 小于 1970 年的历史时间 | DATETIME | TIMESTAMP 不支持 1970 年前 |

## 常见问题

**导数据时 TIMESTAMP 列的值会变吗？**

如果 mysqldump 的源和目标服务器时区不同，TIMESTAMP 的存储值（UTC）不变，但还原后在不同时区查询会显示不同时间。DATETIME 则完全不受影响。迁移时区不同的服务器时，这是一个需要特别注意的点。

**能在应用层统一用 UTC 时间写入 DATETIME，然后用 DATETIME 代替 TIMESTAMP 吗？**

可以，这是一种常见实践：在应用层将所有时间转换为 UTC 后写入 DATETIME，查询时由应用层再转换为本地时间。这样 DATETIME 也能实现跨时区的统一基准，同时避免了 TIMESTAMP 的 2038 限制。

---

## 注意事项

- 不要在同一个系统中混用 TIMESTAMP（自动时区转换）和 DATETIME（不转换），会让时间比较和排序产生逻辑混乱。
- 如果系统有计划在 2038 年之后运行，现在就应该使用 DATETIME 而不是 TIMESTAMP。从 TIMESTAMP 到 DATETIME 的迁移虽然可行，但在生产系统中是有风险的 DDL 操作。

---

## 总结

TIMESTAMP 和 DATETIME 最本质的区别是时区处理：TIMESTAMP 以 UTC 存储，查询时转换为当前会话时区；DATETIME 原样存储，不做任何时区转换。选型规则：需要跨时区统一基准用 TIMESTAMP；单时区或需要保持原始时间值不变用 DATETIME；需要存储 2038 年之后的时间必须用 DATETIME。

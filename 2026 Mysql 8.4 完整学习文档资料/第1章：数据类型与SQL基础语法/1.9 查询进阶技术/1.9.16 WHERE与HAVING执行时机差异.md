# WHERE 与 HAVING 执行时机差异

WHERE 和 HAVING 都是条件过滤子句，但它们的执行时机不同，可以使用的条件也不同。正确区分两者的用途，既能写出语义正确的 SQL，又能避免不必要的性能损失。

---

## 执行阶段对比

```
SQL 执行阶段顺序：
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

WHERE：在 GROUP BY 之前执行，过滤原始行
HAVING：在 GROUP BY 之后执行，过滤分组聚合结果
```

| 对比维度 | WHERE | HAVING |
|---------|-------|--------|
| 执行时机 | 分组前（GROUP BY 之前）| 分组后（GROUP BY 之后）|
| 能否引用聚合函数 | 不能（COUNT、SUM 等）| 能 |
| 能否引用 SELECT 别名 | 不能（MySQL 中也不能）| 能（MySQL 扩展）|
| 作用对象 | 原始行（每条记录）| 分组结果（每个分组）|
| 是否必须有 GROUP BY | 不需要 | 通常需要（无 GROUP BY 时整表为一组）|
| 性能影响 | 先过滤减少数据量，影响大 | 对已聚合的少量组过滤，影响小 |

---

## 典型对比示例

```sql
-- 需求：统计 2026 年各月"状态为已完成"的订单数，只显示月订单数 > 100 的月份

-- 错误写法1：把聚合条件放 WHERE（聚合函数不能在 WHERE 中）
SELECT DATE_FORMAT(created_at, '%Y-%m') AS month, COUNT(*) AS cnt
FROM orders
WHERE COUNT(*) > 100        -- 报错：WHERE 中不能用聚合函数
GROUP BY DATE_FORMAT(created_at, '%Y-%m');

-- 错误写法2：把行级条件放 HAVING（语义上可以，但性能差）
SELECT DATE_FORMAT(created_at, '%Y-%m') AS month, COUNT(*) AS cnt
FROM orders
GROUP BY DATE_FORMAT(created_at, '%Y-%m')
HAVING status = 2 AND YEAR(created_at) = 2026;  -- 语法上合法，但性能差
-- 这样会把所有订单先分组，再过滤——多做了不必要的分组工作

-- 正确写法：行级条件放 WHERE，聚合条件放 HAVING
SELECT DATE_FORMAT(created_at, '%Y-%m') AS month, COUNT(*) AS cnt
FROM orders
WHERE status = 2                        -- WHERE：先过滤行（减少分组的数据量）
  AND YEAR(created_at) = 2026
GROUP BY DATE_FORMAT(created_at, '%Y-%m')
HAVING cnt > 100;                        -- HAVING：再过滤分组结果
```

## 关于别名引用的差异

```sql
-- SELECT 别名在 WHERE 中不能用（WHERE 在 SELECT 之前执行）
SELECT YEAR(created_at) AS order_year, COUNT(*) AS cnt
FROM orders
WHERE order_year = 2026   -- 报错：Unknown column 'order_year'
GROUP BY order_year;

-- 正确：WHERE 中用原始表达式
SELECT YEAR(created_at) AS order_year, COUNT(*) AS cnt
FROM orders
WHERE YEAR(created_at) = 2026   -- 使用原始表达式
GROUP BY YEAR(created_at);       -- GROUP BY 也要用原始表达式（标准 SQL）

-- MySQL 扩展：HAVING 中可以用 SELECT 别名（GROUP BY 也可以）
SELECT YEAR(created_at) AS order_year, COUNT(*) AS cnt
FROM orders
GROUP BY order_year    -- MySQL 允许 GROUP BY 用别名
HAVING cnt > 100;      -- MySQL 允许 HAVING 用别名
```

## WHERE 不能使用聚合函数的原因

```sql
-- 当 SQL 执行 WHERE 时，MySQL 处理的是原始的每一行
-- 此时分组还没有发生，聚合函数无法计算（没有分组就没有聚合的范围）
-- 聚合函数是在 GROUP BY 分组之后才有意义的

-- 以下两种写法的错误原因相同：
WHERE COUNT(*) > 5      -- 错误：聚合函数在 WHERE 中
WHERE SUM(amount) > 1000 -- 错误：聚合函数在 WHERE 中

-- 正确：把这些条件移到 HAVING
HAVING COUNT(*) > 5
HAVING SUM(amount) > 1000
```

## 适用场景总结

```
WHERE 适合：
- 过滤原始行的条件（字段值匹配、范围过滤、NULL 检查等）
- 能用索引优化的条件（WHERE 比 HAVING 更早执行，能减少后续处理量）

HAVING 适合：
- 基于聚合函数的条件（COUNT、SUM、AVG、MAX、MIN）
- 过滤分组结果的条件
```

---

## 常见问题

**HAVING 中能写非聚合列的条件吗？**

在 MySQL 中可以，但不建议。非聚合列的过滤条件放在 WHERE 中更高效（先过滤减少数据量），放在 HAVING 中虽然结果相同，但性能更差（数据已经分组完才过滤）。

---

## 注意事项

- 一条 SQL 中可以同时有 WHERE 和 HAVING，这是最常见的组合：WHERE 过滤行，HAVING 过滤组。
- 永远不要把能放 WHERE 的条件放到 HAVING——这会导致把不必要的行都带入分组计算，浪费 CPU 和内存。

---

## 总结

WHERE 在分组前执行，过滤原始行，不能使用聚合函数，不能引用 SELECT 别名。HAVING 在分组后执行，过滤分组结果，可以使用聚合函数，在 MySQL 中可以引用 SELECT 别名。行级过滤放 WHERE，聚合结果过滤放 HAVING，是写高性能聚合查询的基本原则。

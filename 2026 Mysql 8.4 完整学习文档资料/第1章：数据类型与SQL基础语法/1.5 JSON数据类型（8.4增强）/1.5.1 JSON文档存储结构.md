## JSON 文档存储结构

MySQL 从 5.7.8 版本引入原生 JSON 数据类型，8.0 和 8.4 持续增强。与把 JSON 当字符串存入 TEXT 列不同，原生 JSON 类型在写入时验证格式合法性，在内部以二进制格式存储，支持直接通过路径表达式访问嵌套字段，大幅减少了应用层的 JSON 解析工作。

---

### JSON 类型的存储特点

| 属性 | 值 |
|------|---|
| 存储格式 | 内部二进制格式（非原始文本）|
| 最大大小 | 与 LONGBLOB/LONGTEXT 相同（受 max_allowed_packet 限制）|
| 写入验证 | 自动验证 JSON 格式合法性 |
| 路径查询 | 支持 JSON 路径表达式直接访问字段 |
| 索引支持 | 不能直接索引 JSON 列，但可通过虚拟列索引特定字段 |

---

### 内部二进制存储格式

MySQL JSON 类型在内部存储的不是原始 JSON 字符串，而是一种优化的二进制格式（称为 "JSONB"，类似 PostgreSQL）。这种格式的特点：

- 对象中的 key 按照字典序排序，方便快速查找
- 内嵌了偏移量信息，可以直接跳转到指定 key 的值，不需要扫描整个文档
- 数值类型（整数、浮点数）以二进制格式存储，而不是字符串

---

### 语法与示例

```sql
column_name JSON
column_name JSON NOT NULL
-- 注意：JSON 列不能有 DEFAULT 值（除 NULL 外）
column_name JSON DEFAULT NULL
```

```sql
-- 用户扩展信息（结构不固定，适合 JSON）
CREATE TABLE user_profiles (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     INT UNSIGNED NOT NULL UNIQUE,
    attributes  JSON COMMENT '用户扩展属性',
    preferences JSON COMMENT '用户偏好设置',
    PRIMARY KEY (id)
);

-- 商品规格（SKU 属性，不同商品属性名不同）
CREATE TABLE product_specs (
    product_id  INT UNSIGNED NOT NULL PRIMARY KEY,
    specs       JSON NOT NULL COMMENT '商品规格，如颜色、尺寸、材质等'
);

-- 订单附加信息
CREATE TABLE order_extras (
    order_id    BIGINT UNSIGNED NOT NULL PRIMARY KEY,
    extras      JSON COMMENT '配送地址、优惠券使用等附加信息'
);

-- 插入 JSON 数据
INSERT INTO user_profiles (user_id, attributes, preferences) VALUES (
    1001,
    '{"age": 28, "city": "北京", "vip_level": 3, "tags": ["tech", "sports"]}',
    '{"theme": "dark", "language": "zh-CN", "notifications": {"email": true, "sms": false}}'
);

INSERT INTO product_specs (product_id, specs) VALUES (
    101,
    '{"color": "黑色", "size": "XL", "material": "纯棉", "weight_g": 250}'
);

INSERT INTO product_specs (product_id, specs) VALUES (
    102,
    '{"color": "银色", "storage_gb": 256, "ram_gb": 8, "os": "iOS 17"}'
);
```

### JSON 文档的基本查询

```sql
-- 提取 JSON 字段（->  是 JSON_EXTRACT 的简写）
SELECT user_id, attributes->'$.city' AS city FROM user_profiles;
-- 输出：1001 | "北京"（带引号的 JSON 字符串）

-- ->> 是去除引号的 JSON_UNQUOTE(JSON_EXTRACT()) 简写
SELECT user_id, attributes->>'$.city' AS city FROM user_profiles;
-- 输出：1001 | 北京（不带引号的纯字符串）

-- 提取嵌套字段
SELECT user_id, preferences->>'$.notifications.email' AS email_on FROM user_profiles;
-- 输出：1001 | true

-- 过滤 JSON 字段的值
SELECT * FROM user_profiles WHERE attributes->>'$.vip_level' = '3';
SELECT * FROM user_profiles WHERE JSON_EXTRACT(attributes, '$.age') > 25;

-- 查看 JSON 文档大小（字节）
SELECT user_id, JSON_STORAGE_SIZE(attributes) AS json_bytes FROM user_profiles;
```

### JSON 与 TEXT 存储 JSON 的对比

| 对比维度 | JSON 类型 | TEXT 存 JSON |
|---------|----------|------------|
| 格式验证 | 写入时自动验证 | 不验证，任意字符串都能存 |
| 字段访问 | 路径表达式直接访问 | 需要在应用层解析 |
| 存储效率 | 二进制格式，访问更快 | 文本存储，每次查询需解析 |
| 部分更新 | 支持（JSON_SET 等函数）| 需要全列更新 |
| 索引 | 可通过虚拟列索引特定字段 | 无法对字段内容索引 |
| 类型安全 | 数值、布尔等保留类型信息 | 全部是字符串 |

### 适用场景

- **结构不固定的属性**：不同商品有不同的规格参数（手机有内存、屏幕尺寸；衣服有颜色、尺码）
- **用户偏好/配置**：每个用户的个性化设置，字段不统一
- **第三方 API 响应缓存**：原样存储 API 返回的 JSON 数据
- **事件日志的附加上下文**：日志事件的额外字段，每种事件类型不同
- **半结构化数据**：既需要一些固定字段（可以作为常规列），又有一些动态字段（用 JSON）

---

### 常见问题

**JSON 类型和 MEDIUMTEXT 存 JSON，查询性能哪个好？**

JSON 类型在内部使用二进制格式存储，访问特定字段时不需要扫描整个文档，速度更快。而 MEDIUMTEXT 每次都要全量传输和解析 JSON 文本。对于频繁按 JSON 字段过滤的查询，JSON 类型配合虚拟列索引性能远好于 TEXT。

**JSON 列能否设置 DEFAULT 值？**

只能设置 `DEFAULT NULL`，不支持设置具体的 JSON 字符串作为默认值（MySQL 8.0.12 之前版本完全不支持 JSON 列的 DEFAULT，8.0.13+ 可以使用表达式，但实践中 JSON 列通常允许 NULL）。

---

### 注意事项

- JSON 文档的最大大小受 `max_allowed_packet` 参数限制，默认 64MB，超过这个大小无法写入。
- 频繁更新 JSON 文档会导致行大小变化，InnoDB 需要重新写入整行数据。对于需要频繁更新某个字段的场景，考虑将频繁更新的字段提取为独立列。
- 不要在一个 JSON 文档中存储过多字段（如几百个 key），这会导致 JSON 文档过大，每次查询传输和解析的代价很高。

---

### 总结

MySQL 的 JSON 类型使用二进制格式存储 JSON 文档，写入时自动验证格式合法性，支持通过路径表达式直接访问嵌套字段，比 TEXT 存储 JSON 在功能和性能上都更优秀。它适合存储结构不固定的扩展属性、用户配置、API 响应缓存等半结构化数据，配合虚拟列索引可以实现高效的字段级查询。

## JSON 数据类型存储限制

MySQL 的 JSON 类型在存储层面有多个需要了解的限制，包括单文档大小上限、索引支持方式、部分更新优化等。了解这些限制有助于在设计时做出合理的取舍。

---

### 存储大小限制

| 限制项 | 说明 |
|--------|------|
| 单个 JSON 文档最大大小 | 与 LONGBLOB/LONGTEXT 相同，理论 4GB |
| 实际单次写入上限 | 受 `max_allowed_packet` 限制，默认 64MB |
| 内部存储格式 | 二进制格式，通常比原始 JSON 字符串稍大 |

```sql
-- 查看 max_allowed_packet（影响单次 JSON 文档的最大写入大小）
SHOW VARIABLES LIKE 'max_allowed_packet';
-- 默认：67108864（64MB）

-- 查看 JSON 文档的实际存储大小（字节）
SELECT JSON_STORAGE_SIZE('{"name": "Alice", "age": 28}') AS bytes;
-- 可能比原始字符串字节数略大（二进制格式开销）

-- 查看 JSON 列的存储大小
SELECT id, JSON_STORAGE_SIZE(meta) AS storage_bytes FROM products LIMIT 5;
```

### 索引限制

JSON 列本身不能直接创建 B-Tree 索引，必须通过以下两种方式间接建索引：

**方式一：生成列（虚拟列）+ 普通索引**

```sql
-- 为 JSON 字段创建虚拟生成列，然后对该列建索引
CREATE TABLE products (
    id      INT UNSIGNED NOT NULL AUTO_INCREMENT,
    meta    JSON,
    -- 虚拟生成列，提取 JSON 中的 price 字段
    price   DECIMAL(10,2) AS (CAST(meta->>'$.price' AS DECIMAL(10,2))) VIRTUAL,
    -- 虚拟生成列，提取 category 字段
    category VARCHAR(50) AS (meta->>'$.category') VIRTUAL,
    PRIMARY KEY (id),
    INDEX idx_price (price),       -- 对虚拟列建索引
    INDEX idx_category (category)  -- 对虚拟列建索引
);

-- 插入数据
INSERT INTO products (meta) VALUES ('{"price": 199.99, "category": "electronics", "brand": "Sony"}');
INSERT INTO products (meta) VALUES ('{"price": 59.99, "category": "books", "title": "MySQL Guide"}');

-- 查询时优化器会自动使用虚拟列索引
SELECT * FROM products WHERE price < 100;        -- 使用 idx_price
SELECT * FROM products WHERE category = 'books'; -- 使用 idx_category

-- EXPLAIN 验证
EXPLAIN SELECT * FROM products WHERE price < 100;
-- type: range, key: idx_price（走索引）
```

**方式二：多值索引（Multi-Valued Index，MySQL 8.0.17+）**

```sql
-- 适用于 JSON 数组，对数组中的每个元素建索引
CREATE TABLE articles (
    id      INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    tags    JSON
);

-- 创建多值索引
ALTER TABLE articles ADD INDEX idx_tags ((CAST(tags AS CHAR(50) ARRAY)));

-- 使用 MEMBER OF 操作符利用多值索引
SELECT * FROM articles WHERE 'mysql' MEMBER OF (tags);

-- 也支持 JSON_CONTAINS
SELECT * FROM articles WHERE JSON_CONTAINS(tags, '"mysql"');

-- EXPLAIN 验证
EXPLAIN SELECT * FROM articles WHERE 'mysql' MEMBER OF (tags);
-- type: ref, key: idx_tags（多值索引生效）
```

### 部分更新优化

MySQL 8.0 对 JSON 列的 `JSON_SET`、`JSON_REPLACE`、`JSON_REMOVE` 操作做了部分更新（Partial Update）优化——如果新值不比旧值大，只更新受影响的字节，而不需要重写整个 JSON 文档。这个优化对大型 JSON 文档的频繁小字段更新非常有价值。

```sql
-- 使用 JSON_STORAGE_FREE 查看部分更新后的可用空间
UPDATE products SET meta = JSON_SET(meta, '$.price', 99.99) WHERE id = 1;
SELECT JSON_STORAGE_FREE(meta) AS freed_bytes FROM products WHERE id = 1;
-- 如果新值比旧值小，freed_bytes > 0，说明有部分空间被释放（但尚未回收）

-- 触发 OPTIMIZE TABLE 可以真正回收空间
OPTIMIZE TABLE products;
```

###  存储效率对比

```sql
-- 比较同一 JSON 内容在不同类型下的存储大小
CREATE TABLE size_compare (
    json_col  JSON,
    text_col  TEXT
);

INSERT INTO size_compare (json_col, text_col)
VALUES ('{"name": "Alice", "age": 28, "city": "Beijing"}',
        '{"name": "Alice", "age": 28, "city": "Beijing"}');

SELECT 
    JSON_STORAGE_SIZE(json_col) AS json_bytes,
    LENGTH(text_col) AS text_bytes
FROM size_compare;
-- JSON 内部二进制格式通常比原始字符串略大（因为包含偏移量等元数据）
-- 但 JSON 类型的随机访问速度远快于 TEXT，因为不需要解析整个字符串
```

### 常见的存储问题

**频繁更新大型 JSON 文档的性能问题：**

```sql
-- 如果 JSON 文档很大（如 10KB），每次修改一个小字段，
-- MySQL 仍然需要写入整个 JSON 行（除非触发部分更新优化）
-- 频繁修改的字段应提取为独立列

-- 不推荐（JSON 文档很大，修改 status 字段代价高）
UPDATE orders SET meta = JSON_SET(meta, '$.status', 'paid') WHERE id = 1;

-- 推荐（将频繁修改的字段提取为独立列）
ALTER TABLE orders ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'pending';
UPDATE orders SET status = 'paid' WHERE id = 1;
```

### 适用场景

了解 JSON 存储限制的目的是在设计时做出正确决策：
- 需要频繁查询的 JSON 字段：提取为虚拟列并建索引
- 数组类型的 JSON 字段需要成员查询：建多值索引
- 频繁修改的字段：提取为普通列
- 不常访问但结构复杂的数据：直接存 JSON 列

---

### 常见问题

**JSON 列能直接参与 ORDER BY 吗？**

可以，但不走索引（除非对虚拟列排序）：

```sql
SELECT * FROM products ORDER BY meta->>'$.price';  -- 全表扫描后排序
SELECT * FROM products ORDER BY price;              -- 使用 idx_price（虚拟列索引）
```

**一张表能有多个 JSON 列吗？**

可以，没有数量限制，但每个 JSON 列的大小仍受行大小和 `max_allowed_packet` 约束。

---

### 注意事项

- JSON 文档不宜设计过深的嵌套（超过 5~6 层），既影响可读性，也影响路径查询性能。
- 避免在单个 JSON 文档中存储大量字段（如几百个 key），这会使文档过大，每次读取代价高昂。
- 虚拟列是实现 JSON 字段高效索引的推荐方案，在 MySQL 8.4 中虚拟列和普通列的功能对等性进一步改善。

---

### 总结

MySQL JSON 类型的实际存储上限受 `max_allowed_packet` 约束（默认 64MB），内部使用二进制格式存储，支持部分更新优化。JSON 列本身不能直接建索引，通过虚拟生成列+普通索引或多值索引（针对数组）来实现高效查询。设计时应将高频查询和修改的字段提取为独立列，而非全部存入 JSON，保持 JSON 列用于真正需要灵活结构的场景。

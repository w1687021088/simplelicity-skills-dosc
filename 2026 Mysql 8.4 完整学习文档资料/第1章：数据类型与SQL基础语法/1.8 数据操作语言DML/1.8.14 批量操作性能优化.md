# 批量操作性能优化

批量 DML 操作（INSERT、UPDATE、DELETE）的性能直接影响数据库的吞吐能力。理解 MySQL 在事务提交、索引维护、锁竞争等方面的开销，并采用正确的批量策略，可以将写入性能提升数倍甚至数十倍。

---

## 批量 INSERT 优化

```sql
-- 优化1：多行 VALUES 一次提交（而非逐行 INSERT）
-- 低效：逐行插入（每行一次网络往返，一次事务提交）
INSERT INTO logs (msg) VALUES ('a');
INSERT INTO logs (msg) VALUES ('b');
INSERT INTO logs (msg) VALUES ('c');

-- 高效：一次多行插入（一次网络往返，一次事务提交）
INSERT INTO logs (msg) VALUES ('a'), ('b'), ('c');
-- 性能差距：在本地测试中，多行插入比逐行快 5~10 倍

-- 优化2：事务批次提交（autocommit=ON 时，每条 SQL 自动提交有磁盘 I/O）
START TRANSACTION;
INSERT INTO logs (msg) VALUES ('batch1'), ('batch2'), ('batch3');
INSERT INTO logs (msg) VALUES ('batch4'), ('batch5'), ('batch6');
-- ... 更多 INSERT
COMMIT;
-- 一次事务提交 = 一次 redo log 刷盘，性能远好于每条 SQL 单独提交

-- 优化3：批次大小控制（单次 INSERT 不要过大）
-- 推荐每批 500~1000 行，每批 COMMIT 一次
-- 过大的单批：可能导致 undo log 膨胀、锁等待增加
-- 过小的单批：每批 COMMIT 的磁盘 I/O 开销积累
```

## LOAD DATA INFILE（最高效的批量插入）

```sql
-- LOAD DATA INFILE 比 INSERT VALUES 快 5~20 倍
-- 适合一次性导入大量静态数据（CSV 文件）
LOAD DATA LOCAL INFILE '/data/records.csv'
INTO TABLE records
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES;
```

## 批量 UPDATE 优化

```sql
-- 优化1：CASE 批量更新（替代循环单行更新）
-- 低效：循环逐行 UPDATE（N 次查询）
-- UPDATE products SET price = 99 WHERE id = 1;
-- UPDATE products SET price = 88 WHERE id = 2;
-- ...

-- 高效：CASE 表达式一次批量更新
UPDATE products
SET price = CASE id
    WHEN 1 THEN 99.00
    WHEN 2 THEN 88.00
    WHEN 3 THEN 77.00
    ELSE price
END
WHERE id IN (1, 2, 3);

-- 优化2：临时表辅助批量更新
CREATE TEMPORARY TABLE temp_price_update (
    product_id INT UNSIGNED NOT NULL,
    new_price  DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (product_id)
);

INSERT INTO temp_price_update VALUES (1, 99.00), (2, 88.00), (3, 77.00);

UPDATE products p
JOIN temp_price_update t ON p.id = t.product_id
SET p.price = t.new_price;
```

## 批量 DELETE 优化（分批删除大量数据）

```sql
-- 一次性删除大量数据会产生大事务（大量 undo log + 长时间持锁）
-- 解决方案：分批删除，每批 COMMIT

-- 方法1：LIMIT 分批
SET @done = 0;
-- 在应用层循环执行：
-- REPEAT:
DELETE FROM audit_logs WHERE created_at < '2024-01-01' LIMIT 1000;
-- UNTIL ROW_COUNT() = 0

-- 方法2：按主键范围分批
-- 首先确认需要删除的 id 范围
SELECT MIN(id), MAX(id) FROM audit_logs WHERE created_at < '2024-01-01';
-- 假设是 1 ~ 5000000

-- 然后按范围循环删除
DELETE FROM audit_logs WHERE id BETWEEN 1 AND 10000 AND created_at < '2024-01-01';
-- 每次推进 10000，循环直到 id 范围结束
```

## 禁用和重建索引（极大批量导入时）

```sql
-- 对于非常大的批量导入（如导入 1000 万行），
-- 可以先删除非唯一索引，导入后重建，比边插入边维护索引更快

-- 步骤1：记录并删除普通索引
SHOW INDEX FROM target_table;
ALTER TABLE target_table DROP INDEX idx_category_id;
ALTER TABLE target_table DROP INDEX idx_created_at;

-- 步骤2：批量插入数据
LOAD DATA INFILE '/data/large_file.csv' INTO TABLE target_table ...;

-- 步骤3：重建索引（INPLACE 算法，不锁表）
ALTER TABLE target_table
    ADD INDEX idx_category_id (category_id),
    ADD INDEX idx_created_at (created_at),
    ALGORITHM=INPLACE, LOCK=NONE;
```

## 关键性能参数

```sql
-- 查看和调整影响批量写入性能的参数
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';   -- 缓冲池大小
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
-- 1（默认）：每次提交刷 redo log 到磁盘（安全但慢）
-- 2：每秒刷一次（性能更好，断电可能丢失最多 1 秒数据）
-- 0：每秒刷到 OS 缓冲（最快，安全性最差）

SHOW VARIABLES LIKE 'bulk_insert_buffer_size';  -- 批量插入缓冲（MyISAM）
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode'; -- 自增锁模式（8.4 默认 2）
```

## 适用场景

- **系统初始化**：一次性导入基础数据、字典数据
- **数据迁移**：从旧系统迁移数据到新系统
- **定期批量更新**：如每天更新商品价格、用户积分
- **历史数据清理**：定期分批删除过期日志、历史记录

## 常见问题

**批量操作期间其他查询变慢了怎么处理？**

大批量 DML 会占用 buffer pool、产生大量 undo log，影响其他查询。解决方法：在低峰期执行、分批操作（每批间隔几毫秒）、控制单批大小（减少单次持锁时间）。

---

## 注意事项

- 批量操作时，监控 `information_schema.INNODB_TRX`，避免产生长时间运行的大事务。
- `innodb_flush_log_at_trx_commit=2` 可以大幅提升批量写入速度，但在机器断电时可能丢失最多 1 秒的数据，仅适合对数据持久性要求不是极高的场景（如离线数据迁移）。

---

## 总结

批量操作性能优化的核心：多行 VALUES 一次提交替代逐行 INSERT；事务批次提交减少磁盘 I/O；大批量删除用 LIMIT 分批执行；超大数据导入优先用 LOAD DATA INFILE；极端情况下可先删除索引、导入后重建。合理控制每批大小（500~1000 行）是兼顾性能和系统稳定的平衡点。

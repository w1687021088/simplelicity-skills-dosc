# 软删除设计模式

软删除（Soft Delete）是指在删除数据时，不真正执行 `DELETE` 语句从数据库物理删除行，而是通过 UPDATE 将该行标记为"已删除"状态。被标记的行在查询时通过 WHERE 条件过滤掉，但数据仍然保存在表中，可以随时恢复。

---

## 软删除的实现方式

```sql
-- 方式1：is_deleted 标志位（最常见）
CREATE TABLE articles (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    title       VARCHAR(200) NOT NULL,
    content     TEXT,
    author_id   INT UNSIGNED NOT NULL,
    is_deleted  TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0正常 1已删除',
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    INDEX idx_author_deleted (author_id, is_deleted)  -- 复合索引：常用查询模式
);

-- 软删除操作
UPDATE articles SET is_deleted = 1 WHERE id = 42;

-- 软删除恢复
UPDATE articles SET is_deleted = 0 WHERE id = 42;

-- 查询时过滤已删除数据
SELECT * FROM articles WHERE is_deleted = 0 AND author_id = 1;

-- 方式2：deleted_at 时间戳（可同时记录删除时间）
CREATE TABLE orders (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id    INT UNSIGNED NOT NULL,
    amount     DECIMAL(10,2) NOT NULL,
    status     TINYINT UNSIGNED NOT NULL DEFAULT 0,
    deleted_at DATETIME DEFAULT NULL COMMENT 'NULL表示未删除',
    PRIMARY KEY (id),
    INDEX idx_user_deleted (user_id, deleted_at)
);

-- 软删除（记录删除时间）
UPDATE orders SET deleted_at = NOW() WHERE id = 1001;

-- 软删除恢复
UPDATE orders SET deleted_at = NULL WHERE id = 1001;

-- 查询时过滤
SELECT * FROM orders WHERE deleted_at IS NULL AND user_id = 100;
```

---

## is_deleted vs deleted_at 对比

| 对比维度 | is_deleted (TINYINT) | deleted_at (DATETIME) |
|---------|---------------------|----------------------|
| 是否记录删除时间 | 否 | 是 |
| 查询过滤性能 | INDEX 选择性低（0/1）| 较好（NULL vs 非 NULL）|
| 存储空间 | 1 字节 | 8 字节 |
| 复原判断 | is_deleted = 0 | deleted_at IS NULL |
| 审计能力 | 不知道何时删除 | 可以查询删除时间 |

## 软删除配合唯一约束的处理

```sql
-- 问题：如果 username 有唯一约束，软删除后再注册相同 username 会报错
CREATE TABLE users (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    username    VARCHAR(50) NOT NULL,
    email       VARCHAR(200) NOT NULL,
    is_deleted  TINYINT UNSIGNED NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username)   -- 全局唯一，软删除后无法重用
);

-- 方案1：软删除时修改值（在 username 后面加上 id，使其不冲突）
UPDATE users 
SET is_deleted = 1, username = CONCAT(username, '_deleted_', id)
WHERE id = 42;
-- alice → alice_deleted_42（不影响其他 alice 注册）

-- 方案2：使用函数索引（只对未删除的行建唯一约束，MySQL 8.0+ 虚拟列）
-- 方案3：使用部分索引的替代（全局唯一改为业务层保证）
```

## 软删除的查询模式

```sql
-- 模式1：所有查询都加 is_deleted = 0（最直接）
SELECT * FROM articles WHERE is_deleted = 0 ORDER BY created_at DESC;

-- 模式2：视图封装软删除过滤（减少应用层每次写 WHERE）
CREATE VIEW active_articles AS
SELECT * FROM articles WHERE is_deleted = 0;

-- 查询活跃文章（不需要每次写 WHERE is_deleted = 0）
SELECT * FROM active_articles WHERE author_id = 1;

-- 模式3：ORM 层面的全局作用域（Eloquent 的 SoftDeletes trait 等）
-- 框架层面自动注入 WHERE deleted_at IS NULL 条件
```

## 适用场景

- **需要可恢复删除**：用户"删除"文章后可以在回收站找回
- **审计合规**：法规要求保留数据记录，不能物理删除
- **数据分析**：历史数据对统计分析有价值，不能丢弃
- **业务回溯**：订单、交易等重要记录不允许物理删除

## 常见问题

**软删除表的数据量会持续增长，如何处理？**

软删除表会随时间积累大量"已删除"的行，增加存储和查询过滤的开销。解决方案：
1. 定期将长期未恢复的已删除数据归档到归档表（`INSERT INTO ... SELECT ... WHERE is_deleted=1 AND deleted_at < 半年前`），然后从主表物理删除
2. 对非常旧的已删除数据执行真正的 DELETE（例如 2 年以上的已删除记录）

---

## 注意事项

- 软删除的查询**每次都要加 `is_deleted = 0` 或 `deleted_at IS NULL`** 的过滤条件，极容易因疏忽遗漏。在团队开发中，通过 ORM 的全局作用域（Scope）或数据库视图来封装这个过滤条件，可以降低遗漏的概率。
- `is_deleted` 列的索引选择性很低（只有 0 和 1 两个值），单独对它建索引效果差。应该和其他高选择性的列（如 user_id、status）一起建复合索引：`INDEX (user_id, is_deleted)`。

---

## 总结

软删除通过 UPDATE 标记删除状态（`is_deleted=1` 或 `deleted_at=NOW()`），避免物理 DELETE，使数据可恢复、可审计。`deleted_at` 方式额外记录了删除时间，审计能力更强。与唯一约束配合时需要处理冲突。软删除表应定期归档已删除的旧数据，避免表无限增长。在团队项目中建议通过视图或 ORM 全局作用域自动注入删除过滤条件。

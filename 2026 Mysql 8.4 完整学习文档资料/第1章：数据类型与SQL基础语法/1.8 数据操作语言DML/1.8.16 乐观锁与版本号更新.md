# 乐观锁与版本号更新

乐观锁是一种无锁并发控制策略：在读取数据时不加锁，在更新时通过版本号（或时间戳）验证数据是否在读取之后被其他事务修改过。如果版本号一致（数据未被修改），更新成功；如果版本号不一致（数据已被修改），更新失败，应用层需要重试。这种方式适用于读多写少、冲突概率低的场景。

---

## 乐观锁的实现原理

```sql
-- 典型的乐观锁表结构：增加 version 版本号列
CREATE TABLE products (
    id       INT UNSIGNED NOT NULL AUTO_INCREMENT,
    name     VARCHAR(200) NOT NULL,
    stock    INT UNSIGNED NOT NULL DEFAULT 0,
    price    DECIMAL(10,2) NOT NULL,
    version  INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    PRIMARY KEY (id)
);

-- 操作流程：
-- 步骤1：读取数据（同时记录 version）
SELECT id, stock, version FROM products WHERE id = 1;
-- 假设返回：id=1, stock=100, version=5

-- 步骤2：业务计算（应用层计算新库存）
-- new_stock = 100 - 1 = 99

-- 步骤3：带版本号条件的 UPDATE
UPDATE products
SET stock = 99, version = version + 1
WHERE id = 1 AND version = 5;  -- 关键：WHERE 中加上 version = 读到的版本号

-- 步骤4：检查影响行数
SELECT ROW_COUNT();
-- = 1：更新成功（没有其他事务在此期间修改了该行）
-- = 0：更新失败（其他事务已经修改了 version，需要重试）
```

## 完整的乐观锁更新示例

```sql
-- 场景：电商库存扣减（多用户并发购买同一商品）

-- 用户A读取商品
SELECT id, name, stock, version FROM products WHERE id = 1;
-- id=1, name='商品A', stock=10, version=3

-- 用户B也读取了相同数据
-- id=1, name='商品A', stock=10, version=3

-- 用户A先执行购买（扣减1件）
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND stock > 0 AND version = 3;
-- ROW_COUNT() = 1，成功，version 变为 4

-- 用户B也执行购买（版本号仍是3，但已经被A改为4了）
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND stock > 0 AND version = 3;
-- ROW_COUNT() = 0，失败（version 已是4，不等于3）
-- 应用层重试：重新 SELECT，得到 version=4, stock=9
-- 再次 UPDATE 用 version=4 → 成功
```

## 使用时间戳的乐观锁

```sql
-- 用 updated_at 时间戳代替 version（精度为秒，并发时可能冲突）
CREATE TABLE configs (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    cfg_key     VARCHAR(100) NOT NULL,
    cfg_value   TEXT NOT NULL,
    updated_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                ON UPDATE CURRENT_TIMESTAMP(6),  -- 微秒精度
    PRIMARY KEY (id)
);

-- 读取
SELECT id, cfg_value, updated_at FROM configs WHERE id = 1;
-- updated_at = '2026-03-15 10:30:00.123456'

-- 带时间戳验证的更新
UPDATE configs
SET cfg_value = 'new_value'
WHERE id = 1 AND updated_at = '2026-03-15 10:30:00.123456';
-- ROW_COUNT() = 0 表示数据已被修改，需要重试
```

## 乐观锁 vs 悲观锁对比

| 对比维度 | 乐观锁（版本号）| 悲观锁（SELECT FOR UPDATE）|
|---------|--------------|--------------------------|
| 加锁时机 | 不加锁（更新时验证）| 读取时立即加排他锁 |
| 并发性能 | 读操作无锁，并发高 | 读操作持锁，并发受限 |
| 冲突处理 | 应用层重试 | 等待锁释放后执行 |
| 适用场景 | 读多写少，冲突概率低 | 写多，冲突概率高 |
| 数据库开销 | 低（无锁等待）| 高（锁等待、锁超时）|
| 实现复杂度 | 应用层需要重试逻辑 | 数据库自动处理，应用简单 |

## 防止超卖的完整方案

```sql
-- 乐观锁 + stock > 0 双重保证（防止超卖）
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND stock > 0 AND version = 3;
-- stock > 0：防止库存变为负数
-- version = 3：防止并发修改导致的数据不一致

-- 如果 ROW_COUNT() = 0：
-- 可能是 version 冲突（重试）或 stock 不足（提示用户库存不足）
-- 重试时区分两种情况：
SELECT stock, version FROM products WHERE id = 1;
-- stock = 0：告知用户库存不足，停止重试
-- stock > 0, version != 3：库存充足但有并发冲突，重试
```

## 适用场景

- **商品库存扣减**：电商秒杀、抢购场景中的库存管理
- **表单提交**：防止同一表单被并发提交两次
- **文档/内容编辑**：多用户同时编辑同一文档时防止覆盖
- **积分/余额变更**：用户余额、积分的并发更新

## 常见问题

**乐观锁失败后应该重试多少次？**

取决于业务场景。对于库存扣减，重试 3~5 次是常见做法；如果重试次数过多仍然失败，说明并发竞争非常激烈，此时可以考虑切换为悲观锁（`SELECT ... FOR UPDATE`）或通过消息队列串行化处理。

**乐观锁的 version 用 INT 还是 BIGINT？**

INT UNSIGNED（最大约 42 亿）对于几乎所有业务场景都足够，很少有单行数据被更新 42 亿次的情况。如果特别担心，可以用 BIGINT UNSIGNED。

---

## 注意事项

- 乐观锁的重试逻辑必须在应用层实现——MySQL 数据库本身不会自动重试，只会返回影响行数为 0。应用层需要检查 `ROW_COUNT()` 或受影响的行数来决定是否重试。
- 高并发场景下，乐观锁频繁重试本身也会给数据库增加读写压力。如果冲突率很高（如秒杀抢购），乐观锁反而不如 Redis 分布式锁或队列串行化的方案。

---

## 总结

乐观锁通过在 UPDATE 的 WHERE 子句中加入版本号条件（`AND version = 读到的版本`）来检测并发冲突，不需要数据库加锁，并发读性能高。更新时检查 `ROW_COUNT()` 是否为 1 来判断是否成功；为 0 则说明有并发冲突，需要应用层重试。适合读多写少、冲突概率低的场景。冲突频繁时应切换为悲观锁或队列化方案。

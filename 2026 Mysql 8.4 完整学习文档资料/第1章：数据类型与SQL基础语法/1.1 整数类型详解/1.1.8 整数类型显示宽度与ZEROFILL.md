# 整数类型显示宽度与 ZEROFILL

显示宽度和 ZEROFILL 是 MySQL 整数类型的两个历史遗留特性。它们在很多老项目和旧文档中大量出现，但在 MySQL 8.0.17 之后已被废弃，理解它们的含义和废弃原因，有助于正确维护存量代码并避免在新代码中继续使用。

---

## 显示宽度是什么

整数类型后面括号中的数字（如 `INT(11)`、`TINYINT(4)`）是"显示宽度"（Display Width），它不影响任何实际存储行为：

- **不改变存储空间**：`INT(4)` 和 `INT(11)` 都占用 4 字节
- **不改变数值范围**：`INT(4)` 和 `INT(11)` 的范围都是 -2147483648 ~ 2147483647
- **不限制输入值的位数**：`INT(4)` 可以存储 12345，不会截断

显示宽度的历史用途：在配合 `ZEROFILL` 属性时，指定输出时填充零的总宽度。

```sql
-- 以下两个定义在存储和范围上完全等价
col1 INT(4)
col2 INT(11)
col3 INT        -- 不写也等价，括号中的数字没有意义
```

---

## ZEROFILL 属性

`ZEROFILL` 属性与显示宽度配合使用，让输出的整数在位数不足时用零从左边填充到指定的显示宽度。

```sql
-- 创建带 ZEROFILL 的列
CREATE TABLE demo (
    order_no  INT(8) ZEROFILL NOT NULL
);

INSERT INTO demo VALUES (12345);

SELECT order_no FROM demo;
-- 输出：00012345
-- 说明：12345 是 5 位，填充到 8 位需要加 3 个零
```

`ZEROFILL` 还有一个副作用：**自动隐含 UNSIGNED 属性**。即在定义了 `ZEROFILL` 的列中，即使没有写 `UNSIGNED`，也会被隐式设为无符号整数。

---

## MySQL 8.0.17 的废弃声明

从 MySQL 8.0.17 开始，官方明确废弃整数类型的显示宽度和 ZEROFILL：

> "The display width attribute is deprecated for integer data types, as is the ZEROFILL attribute."

废弃的原因：
1. 显示宽度从来不控制存储，它只影响某些旧客户端的格式化显示，语义令人困惑
2. 零填充实际上是表示层的问题，应该在应用层做格式化，而不是数据库层
3. 这些特性是 MySQL 对 SQL 标准的非标准扩展，与其他数据库不兼容

**废弃不等于移除**：MySQL 8.4 中这些语法仍然有效，不会报错，但会在未来某个版本被彻底移除。

## 查看表定义中的显示宽度

```sql
-- 查看建表语句（会显示现有列的显示宽度）
SHOW CREATE TABLE demo;

-- 使用 information_schema 查看列定义
SELECT COLUMN_NAME, DATA_TYPE, COLUMN_TYPE 
FROM information_schema.COLUMNS 
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'demo';
-- COLUMN_TYPE 会显示 int unsigned zerofill 等完整定义
```

## 在新代码中替代 ZEROFILL

如果需要格式化输出整数（如固定位数编号），推荐在应用层或查询层做，而不是用 ZEROFILL：

```sql
-- 推荐：在查询中用 LPAD 实现零填充格式化
SELECT LPAD(order_no, 8, '0') AS formatted_no FROM orders;
-- 输出：00012345（8 位，不足补零）

-- 或在 SELECT 中用 FORMAT 或 PRINTF 风格格式化（应用层更合适）
```

在 Java 中：
```java
String formatted = String.format("%08d", orderId);  // 输出 00012345
```

在 Python 中：
```python
formatted = f"{order_id:08d}"  # 输出 00012345
```

## 存量代码的处理建议

如果维护的旧系统中存在大量 `INT(11)`、`TINYINT(1)`、`INT ZEROFILL` 等写法：

- **`INT(11)` 或 `TINYINT(4)` 之类只有显示宽度，没有 ZEROFILL**：完全不影响功能，低风险。新建表时可以去掉括号，存量表不需要紧急修改。
- **有 `ZEROFILL` 属性的列**：如果业务上真的依赖了零填充的格式化输出，需要在应用层加上相应的格式化逻辑后，再移除数据库层的 ZEROFILL 定义。

## 常见问题

**为什么 ORM 生成的 SQL 里有 `int(11)`？**

很多 ORM 框架（如 Hibernate、MyBatis-Generator）在生成建表语句时会沿用 `int(11)` 这种写法，因为历史上这是 MySQL SHOW CREATE TABLE 的默认输出格式。MySQL 8.0.17 废弃后，部分框架已更新，不再生成这种写法，但存量项目中仍然很常见。

**`TINYINT(1)` 被 ORM 映射为 Boolean，如果去掉 (1) 会怎样？**

部分 ORM（如某些版本的 Hibernate）通过检测 `TINYINT(1)` 来决定是否映射为 boolean。去掉括号改为 `TINYINT` 后，这些 ORM 可能将该列映射为 byte/int 而不是 boolean，导致映射结果不同。修改前需要确认 ORM 框架的行为。

**`ZEROFILL` 生成的零填充值会被存储到数据库吗？**

不会。ZEROFILL 只影响从 MySQL 检索数据时的显示格式，数据库内部存储的仍然是原始整数值。

## 适用场景

- **理解旧代码**：遇到 `INT(11)`、`TINYINT(1)`、`INT ZEROFILL` 等写法时，知道这是历史遗留特性，不会误以为影响了存储或范围
- **新建表**：不再使用显示宽度，直接写 `INT`、`BIGINT UNSIGNED` 等，更简洁清晰
- **旧系统迁移**：将存量的显示宽度写法从建表语句中逐步清除，保持代码与 MySQL 8.4 的规范对齐

---

## 注意事项

- 虽然 MySQL 8.4 中显示宽度和 ZEROFILL 仍然有效，但未来某个大版本可能会移除它们。在新建表或重构数据库时应避免使用，以减少未来的迁移成本。
- 修改生产表的列定义（去掉 ZEROFILL）是 DDL 操作，会对大表产生影响，需要评估操作时机和风险。
- 不同 MySQL 客户端工具对显示宽度的显示方式不同，MySQL Workbench 新版本可能不再显示括号中的宽度，而旧版本 mysql 命令行仍然会显示。

---

## 总结

显示宽度（如 `INT(11)` 中的 11）和 ZEROFILL 属性是 MySQL 的历史遗留特性，在 MySQL 8.0.17 之后已被官方废弃。显示宽度不影响存储空间和数值范围，ZEROFILL 只影响客户端的格式化显示而不改变实际存储值。新代码中应避免使用这两个特性，需要零填充格式化的场景在应用层或 SQL 查询中用 `LPAD()` 实现。

# TINYINT 有符号与无符号区别

MySQL 中所有整数类型都有两种形态：有符号（SIGNED）和无符号（UNSIGNED）。TINYINT 作为最小的整数类型，这种区分尤其关键，因为 1 个字节的空间在有符号和无符号模式下能表达的范围差异很大。理解两者的区别是设计表结构时选择正确类型的基础。

---

## 有符号与无符号的范围对比

TINYINT 占用 1 个字节（8 个二进制位）。有符号模式下，最高位用作符号位（0 表示正数，1 表示负数），剩余 7 位表示数值；无符号模式下，全部 8 位都用来表示非负整数。

| 属性 | TINYINT（有符号） | TINYINT UNSIGNED（无符号） |
|------|------------------|--------------------------|
| 存储空间 | 1 字节 | 1 字节 |
| 最小值 | -128 | 0 |
| 最大值 | 127 | 255 |
| 可表示值的个数 | 256 个（-128 到 127） | 256 个（0 到 255） |
| 默认行为 | 不加 UNSIGNED 时的默认类型 | 需要显式声明 UNSIGNED |

两者存储空间完全一样，区别仅在于值域的"偏移方向"。有符号把 256 个值均匀分配在正负两侧，无符号把全部 256 个值分配给非负方向。

---

## 声明语法

```sql
-- 有符号 TINYINT（默认，不需要显式写 SIGNED）
CREATE TABLE example_signed (
    temperature TINYINT NOT NULL COMMENT '温度，有符号，-128~127'
);

-- 无符号 TINYINT（必须显式声明 UNSIGNED）
CREATE TABLE example_unsigned (
    age TINYINT UNSIGNED NOT NULL COMMENT '年龄，无符号，0~255'
);

-- 也可以显式写 SIGNED，但不常见
CREATE TABLE example_explicit (
    offset_value TINYINT SIGNED NOT NULL COMMENT '偏移量，显式声明有符号'
);
```

## 基本示例

```sql
-- 创建测试表，同时包含有符号和无符号列
CREATE TABLE tinyint_demo (
    id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
    signed_col  TINYINT NOT NULL DEFAULT 0       COMMENT '有符号列，范围 -128~127',
    unsigned_col TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '无符号列，范围 0~255',
    PRIMARY KEY (id)
);

-- 插入有符号范围内的值
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (-128, 0);    -- 各自的最小值
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (127, 255);   -- 各自的最大值
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (-50, 200);   -- 正常值
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (0, 0);       -- 零值

-- 查看插入结果
SELECT * FROM tinyint_demo;
-- +----+------------+--------------+
-- | id | signed_col | unsigned_col |
-- +----+------------+--------------+
-- |  1 |       -128 |            0 |
-- |  2 |        127 |          255 |
-- |  3 |        -50 |          200 |
-- |  4 |          0 |            0 |
-- +----+------------+--------------+
```

## 越界插入行为

MySQL 在严格模式（默认开启）下，插入超出范围的值会直接报错；在非严格模式下，超出范围的值会被静默截断为边界值。

```sql
-- 严格模式下测试越界（默认 sql_mode 包含 STRICT_TRANS_TABLES）
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (128, 0);
-- ERROR 1264 (22003): Out of range value for column 'signed_col' at row 1
-- 有符号上限是 127，128 越界

INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (0, 256);
-- ERROR 1264 (22003): Out of range value for column 'unsigned_col' at row 1
-- 无符号上限是 255，256 越界

INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (0, -1);
-- ERROR 1264 (22003): Out of range value for column 'unsigned_col' at row 1
-- 无符号不允许负数

-- 非严格模式下的截断行为（不推荐在生产环境使用）
SET SESSION sql_mode = '';
INSERT INTO tinyint_demo (signed_col, unsigned_col) VALUES (200, 300);
-- signed_col 存入 127（截断到有符号上限）
-- unsigned_col 存入 255（截断到无符号上限）

-- 恢复严格模式
SET SESSION sql_mode = 'STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
```

## 算术运算中的符号差异

有符号和无符号列在参与算术运算时，结果的符号类型可能发生变化，这是一个容易踩坑的地方。

```sql
-- 两个无符号值相减可能产生负数
-- 在 NO_UNSIGNED_SUBTRACTION 未开启时，无符号减法结果仍为无符号
CREATE TABLE subtract_demo (
    a TINYINT UNSIGNED NOT NULL DEFAULT 0,
    b TINYINT UNSIGNED NOT NULL DEFAULT 0
);

INSERT INTO subtract_demo (a, b) VALUES (5, 10);

-- 无符号列相减，如果结果为负数，行为取决于 sql_mode
SELECT a - b FROM subtract_demo;
-- 默认情况下：结果为无符号 BIGINT，5 - 10 会得到一个很大的正数（整数下溢）
-- 这是因为 MySQL 将两个无符号值的减法结果也视为无符号

-- 解决方案1：显式转换为有符号
SELECT CAST(a AS SIGNED) - CAST(b AS SIGNED) AS diff FROM subtract_demo;
-- 结果：-5

-- 解决方案2：使用会话变量
SET SESSION sql_mode = CONCAT(@@sql_mode, ',NO_UNSIGNED_SUBTRACTION');
SELECT a - b FROM subtract_demo;
-- 结果：-5（此时无符号减法允许产生负数结果）
```

## 有符号与无符号的选型原则

选择有符号还是无符号，核心依据是业务字段的值域特征：

| 选型场景 | 推荐类型 | 理由 |
|---------|---------|------|
| 状态码（0~10） | TINYINT UNSIGNED | 状态码不会为负，无符号够用 |
| 布尔标志（0/1） | TINYINT UNSIGNED | 0 和 1 都是非负值 |
| 评分（1~5 星） | TINYINT UNSIGNED | 评分不存在负数 |
| 用户等级（1~100） | TINYINT UNSIGNED | 等级值非负 |
| 温度（摄氏度） | TINYINT | 温度可以为负值 |
| 相对偏移量 | TINYINT | 偏移量可能为正或负 |
| 坐标增量 | TINYINT | 增量可能为正或负 |
| 年龄 | TINYINT UNSIGNED | 年龄不会为负，0~255 足够 |

一个简单的判断原则：**如果字段永远不可能出现负值，用 UNSIGNED；如果有任何可能出现负值，用默认的有符号类型。**

## 与其他整数类型的对比

| 类型 | 字节 | 有符号范围 | 无符号范围 |
|------|------|-----------|-----------|
| TINYINT | 1 | -128 ~ 127 | 0 ~ 255 |
| SMALLINT | 2 | -32768 ~ 32767 | 0 ~ 65535 |
| MEDIUMINT | 3 | -8388608 ~ 8388607 | 0 ~ 16777215 |
| INT | 4 | -2147483648 ~ 2147483647 | 0 ~ 4294967295 |
| BIGINT | 8 | -2^63 ~ 2^63-1 | 0 ~ 2^64-1 |

每种整数类型都支持 UNSIGNED 修饰符，行为一致：正数范围翻倍，不允许负值。

## UNSIGNED 在 JOIN 和比较中的隐式转换

当有符号列和无符号列参与比较或 JOIN 时，MySQL 会进行隐式类型转换，这可能导致意料之外的结果。

```sql
-- 有符号列与无符号列的比较
CREATE TABLE t1 (val TINYINT NOT NULL);
CREATE TABLE t2 (val TINYINT UNSIGNED NOT NULL);

INSERT INTO t1 VALUES (-1);
INSERT INTO t2 VALUES (1);

-- 比较 -1 和 1：直觉上 -1 < 1
SELECT * FROM t1, t2 WHERE t1.val < t2.val;
-- 结果可能不符合预期：MySQL 将有符号 -1 隐式转换为无符号时变成 255
-- 255 > 1，所以条件不成立，返回空结果集

-- 安全的做法：显式转换
SELECT * FROM t1, t2 WHERE CAST(t1.val AS SIGNED) < CAST(t2.val AS SIGNED);
-- 正确返回结果

-- 清理
DROP TABLE t1, t2;
```

## 适用场景

- **TINYINT UNSIGNED** 适合值域确定在 0~255 之间的非负整数：状态码、标志位、枚举值、评分等级、颜色通道值（0~255）等
- **TINYINT（有符号）** 适合值域在 -128~127 之间且可能出现负值的场景：温度偏移、方向增量、相对位移等
- 在宽表设计中（几十个甚至上百个列），合理使用 TINYINT 代替 INT 可以显著节省每行存储空间。一张千万级表，每行省 3 字节（INT→TINYINT），总计可以节省约 30MB

## 常见问题

**UNSIGNED 属性在 MySQL 8.4 中是否被废弃了？**

FLOAT 和 DOUBLE 的 UNSIGNED 属性在 MySQL 8.0.17 中被废弃，但整数类型（TINYINT、SMALLINT、MEDIUMINT、INT、BIGINT）的 UNSIGNED 属性没有被废弃，在 MySQL 8.4 中仍然完全支持，可以正常使用。

**为什么无符号列之间的减法结果不是负数？**

MySQL 默认将两个无符号整数的运算结果也视为无符号类型。如果实际结果为负数，就会发生整数下溢（wraparound），得到一个非常大的正数。解决方法是在 sql_mode 中添加 `NO_UNSIGNED_SUBTRACTION`，或者在查询中用 `CAST(... AS SIGNED)` 显式转换。

**ORM 框架如何处理 UNSIGNED？**

大多数 ORM 框架会将 TINYINT UNSIGNED 映射为语言中的无符号整数或较大范围的有符号整数。比如 Java 中没有无符号 byte 类型，Hibernate 会将 TINYINT UNSIGNED 映射为 `short` 或 `int`。如果依赖 ORM 的自动映射，要注意验证实际映射类型是否符合预期。

## 注意事项

- 一旦表上线运行且有数据，将 UNSIGNED 列改为 SIGNED（或反过来）需要执行 ALTER TABLE，在大表上这个操作可能需要较长时间（虽然 MySQL 8.0+ 的 Online DDL 已经大幅优化）。设计阶段就应该确定好符号类型。
- 不要仅仅因为"多一倍正数范围"就无脑使用 UNSIGNED。如果业务逻辑中可能出现减法运算或者相对值计算，无符号类型的隐式转换问题会带来难以排查的 Bug。
- 在跨表 JOIN 时，确保关联字段的符号类型一致。一个有符号列和一个无符号列做等值 JOIN，虽然功能上可以工作，但隐式转换可能带来性能和正确性问题。

---

## 总结

TINYINT 的有符号和无符号区别在于值域分配方向：有符号（SIGNED）范围是 -128~127，无符号（UNSIGNED）范围是 0~255，存储空间都是 1 字节。选择的核心原则是业务字段是否可能出现负值——永远不为负就用 UNSIGNED，可能为负就用默认的有符号类型。使用 UNSIGNED 时要注意减法运算的隐式转换陷阱和跨类型比较的问题。整数类型的 UNSIGNED 属性在 MySQL 8.4 中仍然完全支持，没有被废弃。

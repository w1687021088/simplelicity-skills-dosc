## BIGINT 数据类型

BIGINT 是 MySQL 整数类型中范围最大的，占用 8 字节，能够表示极大的正负整数。在分布式系统中，全局唯一 ID 生成、时间戳（毫秒级）、大规模计数等场景都离不开 BIGINT。

---

### 基本特性

| 属性 | 值 |
|------|---|
| 存储空间 | 8 字节（64 bits） |
| 有符号范围 | -9223372036854775808 ~ 9223372036854775807（约 ±922 亿亿） |
| 无符号范围（UNSIGNED）| 0 ~ 18446744073709551615（约 1844 亿亿） |
| SQL 标准 | ISO SQL 标准类型 |
| 特殊别名 | `SERIAL` = `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT UNIQUE` |

---

### 语法

```sql
column_name BIGINT
column_name BIGINT UNSIGNED
column_name BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY

-- SERIAL 是 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT UNIQUE 的别名
column_name SERIAL
```

---

### 创建示例

```sql
-- 分布式系统中的雪花算法 ID（典型 19 位数字）
CREATE TABLE orders (
    id          BIGINT UNSIGNED NOT NULL COMMENT '雪花算法生成的全局 ID',
    user_id     BIGINT UNSIGNED NOT NULL,
    amount_fen  INT NOT NULL COMMENT '订单金额（分）',
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    INDEX idx_user_id (user_id)
);

-- 毫秒级 Unix 时间戳
CREATE TABLE events (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    event_name  VARCHAR(100) NOT NULL,
    occurred_at BIGINT UNSIGNED NOT NULL COMMENT '毫秒级时间戳',
    PRIMARY KEY (id)
);

-- 大规模统计计数
CREATE TABLE video_stats (
    video_id    BIGINT UNSIGNED NOT NULL,
    view_count  BIGINT UNSIGNED NOT NULL DEFAULT 0,
    like_count  BIGINT UNSIGNED NOT NULL DEFAULT 0,
    PRIMARY KEY (video_id)
);

-- 使用 SERIAL 别名
CREATE TABLE logs (
    id      SERIAL,            -- 等价于 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT UNIQUE
    message TEXT NOT NULL,
    PRIMARY KEY (id)
);
```

### 雪花算法 ID 与 BIGINT

雪花算法（Snowflake）是分布式系统中常用的 ID 生成方案，生成的 ID 是 64 位整数，结构如下：

| 位数 | 含义 |
|------|------|
| 1 bit | 符号位，始终为 0 |
| 41 bits | 毫秒级时间戳（可用约 69 年） |
| 10 bits | 机器 ID（支持 1024 台机器） |
| 12 bits | 序列号（每毫秒最多生成 4096 个 ID） |

生成的 ID 最大约为 2^63 = 9.2 × 10^18，在 `BIGINT` 有符号范围内，或 `BIGINT UNSIGNED` 的一半范围内。

```sql
-- 插入雪花 ID 示例
INSERT INTO orders (id, user_id, amount_fen) 
VALUES (1234567890123456789, 9876543210, 9900);

-- 查询时直接使用数值
SELECT * FROM orders WHERE id = 1234567890123456789;
```

### BIGINT 与 JavaScript 的精度问题

JavaScript 的 `Number` 类型是 64 位浮点数（IEEE 754），只能精确表示 -2^53 ~ 2^53 范围内的整数（约 ±900 万亿）。当 BIGINT 字段的值超过 2^53 时，通过 JSON 传输到前端会丢失精度。

```
MySQL BIGINT: 1234567890123456789
JSON Number:  1234567890123456768  ← 最后几位被改变（精度丢失）
```

解决方案：将 BIGINT ID 以字符串形式返回给前端：

```sql
-- 在 SQL 中将 BIGINT 转为字符串
SELECT CAST(id AS CHAR) AS id_str, user_id FROM orders WHERE id = 1234567890123456789;
```

在 Java 后端中，使用 `@JsonSerialize(using = ToStringSerializer.class)` 将 Long 类型 ID 序列化为字符串；在 Node.js 中使用支持 BigInt 的 JSON 库。

| 类型 | 存储 | 有符号范围 | 无符号上限 |
|------|------|----------|----------|
| TINYINT | 1B | -128 ~ 127 | 255 |
| SMALLINT | 2B | -32768 ~ 32767 | 65535 |
| MEDIUMINT | 3B | -8388608 ~ 8388607 | 16777215 |
| INT | 4B | -2147483648 ~ 2147483647 | 4294967295 |
| BIGINT | 8B | -9223372036854775808 ~ 9223372036854775807 | 18446744073709551615 |

### 适用场景

- **分布式全局 ID**：雪花算法等方案生成的 64 位 ID，必须用 BIGINT
- **毫秒/微秒时间戳**：毫秒时间戳（13 位数字）超过了 INT 上限，需要 BIGINT
- **高频写入表的主键**：订单表、日志表等每天写入量达到百万/千万级的表，用 BIGINT 一劳永逸
- **大规模统计数据**：视频平台的播放量（如 B 站百亿播放量）、全平台 DAU 统计等

### 常见问题

**BIGINT 的 AUTO_INCREMENT 会用完吗？**

BIGINT UNSIGNED 无符号上限约 1.8×10^19。即使每秒插入 100 万条记录，用完需要 1.8×10^19 / 10^6 / 3600 / 24 / 365 ≈ 570 亿年。实际业务中 BIGINT 主键几乎不可能溢出。

**为什么有些系统用 VARCHAR 存 ID 而不是 BIGINT？**

主要是为了解决 JavaScript 的 JSON 精度问题（见上文），以及部分框架和前端处理字符串 ID 更方便。但字符串 ID 在存储、索引效率上都不如 BIGINT，如果能在接口层做转换，优先还是用 BIGINT 存储。

**BIGINT 和 INT 性能有差异吗？**

在 64 位操作系统上，BIGINT 和 INT 的计算性能几乎没有差异，因为 64 位 CPU 原生支持 64 位整数运算。存储上 BIGINT 多占 4 字节，在行数极多的大表中会有一定空间差异，但通常不是性能瓶颈。

---

### 注意事项

- 使用 BIGINT 列做 JOIN 或 WHERE 条件时，确保关联的列类型完全一致（都是 BIGINT），类型不匹配会触发隐式类型转换，导致索引失效。
- 在 Java 中，BIGINT 映射为 `long`（基本类型）或 `Long`（包装类），不要用 `int` 接收 BIGINT 字段，否则可能溢出。
- 向前端 API 返回 BIGINT ID 时，要么用字符串格式（避免 JS 精度问题），要么明确告知前端需要使用 BigInt 类型处理。

---

### 总结

BIGINT 占用 8 字节，无符号上限约 1.8×10^19，在实际业务中几乎不可能溢出。它是分布式 ID、毫秒时间戳、超大计数的标准选择。唯一需要注意的是与 JavaScript 交互时的 JSON 精度问题——超过 2^53 的 BIGINT 值通过 JSON 传输到前端时需要转为字符串处理。

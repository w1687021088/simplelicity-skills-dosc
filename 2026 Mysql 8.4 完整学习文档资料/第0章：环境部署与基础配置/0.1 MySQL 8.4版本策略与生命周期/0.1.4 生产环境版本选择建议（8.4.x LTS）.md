# 生产环境版本选择建议（8.4.x LTS）

每隔几年就会出现一个关于"MySQL 用哪个版本"的讨论。2026 年的答案比以往更清晰：MySQL 8.4.x LTS 是生产环境的唯一合理选择。这份文档解释为什么是这个结论，以及在 8.4.x 的具体补丁版本选择上有什么原则。

---

## 为什么 2026 年只有 8.4.x

| 可能的候选版本 | 评估结论 |
|-------------|---------|
| MySQL 5.7 | 已于 2023 年 10 月 EOL，彻底排除 |
| MySQL 8.0 | 2026 年 4 月 30 日 EOL，窗口关闭，不适合新项目 |
| MySQL 8.1~8.3 | Innovation Release，早已停止活跃开发 |
| MySQL 8.4.x LTS | 标准支持至 2029 年，扩展支持至 2032 年，当前唯一 LTS 版本 |
| MySQL 9.x Innovation | 快速迭代，不建议生产环境长期使用 |

排除的逻辑很简单：5.7 和 8.0 已经或即将 EOL；8.1-8.3 是过渡版本，官方已不再维护；9.x 系列目前处于 Innovation 阶段，下一个 LTS 版本尚未发布。唯一在维护状态且有长期保障的生产级版本，就是 8.4.x。

---

## 8.4.x 中选哪个补丁版本

在确定使用 8.4 系列后，需要选择具体的补丁版本（8.4.0、8.4.1、8.4.2……）。

**核心原则：不要长期停留在 .0 版本**

`.0` 版本是 LTS 系列的首个 GA 发布，功能已完整，但可能包含一些刚发现的问题（这是所有软件初始 GA 版本的常见情况）。后续的补丁版本（8.4.1、8.4.2……）会陆续修复这些问题。

**建议做法：**
- 新项目启动时，选择当前可用的最新补丁版本（如今天是 8.4.3，就用 8.4.3）
- 生产系统在稳定运行期间，不需要追逐每个补丁版本，但每隔 1~2 个补丁周期应评估一次升级
- 当补丁版本包含高危安全漏洞修复时，应尽快在测试环境验证后升级

```sql
-- 查看当前使用的版本
SELECT VERSION();
-- 输出示例：8.4.3

-- 查看编译时间和系统信息
SHOW VARIABLES LIKE 'version%';
```

## 社区版 vs 企业版的选择

| 维度 | 社区版（Community Edition） | 企业版（Enterprise Edition） |
|-----|--------------------------|---------------------------|
| 费用 | 免费 | 付费（按节点或 CPU 计费） |
| 核心功能 | 完整，与企业版相同 | 完整 + 额外工具 |
| MySQL Enterprise Monitor | 不包含 | 包含 |
| MySQL Enterprise Backup | 不包含 | 包含（MEB） |
| MySQL Enterprise Audit | 不包含 | 包含 |
| MySQL Enterprise Firewall | 不包含 | 包含 |
| 官方技术支持 | 依靠社区 | 24/7 Oracle 支持 |
| 扩展支持期 | 有限 | 完整覆盖 |

对于中小型企业或预算有限的团队，社区版完全可以满足生产需求，配合 Percona 的开源工具（XtraBackup、PMM 监控）可以弥补备份和监控方面的差距。对于金融、电信等有严格 SLA 要求的大型企业，企业版的官方支持和审计工具是合理投入。

## 确认 8.4.x 已安装和运行

```bash
# Linux 系统确认已安装版本
rpm -qi mysql-community-server   # RHEL/CentOS/Rocky Linux
dpkg -l mysql-server             # Ubuntu/Debian

# 确认服务状态
systemctl status mysqld          # Linux systemd
sc query mysql                   # Windows 服务状态

# 登录后确认
mysql -u root -p -e "SELECT VERSION();"
```

```sql
-- 查看详细版本和编译参数
SHOW VARIABLES LIKE 'version%';
-- version: 8.4.x
-- version_compile_machine: x86_64 或 aarch64
-- version_compile_os: Linux 或 Win64

-- 查看系统运行时间（确认实例正常运行）
SHOW STATUS LIKE 'Uptime';
```

## 8.4 的主要改进（相对 8.0）

了解 8.4 的关键改进，有助于判断迁移的价值和迁移后需要关注的变化点：

| 改进方向 | 具体内容 |
|---------|---------|
| 安全认证 | `caching_sha2_password` 成为默认且唯一推荐的认证插件，`mysql_native_password` 默认禁用 |
| Redo Log | 引入 `innodb_redo_log_capacity` 统一控制 Redo Log 容量，废弃旧参数 |
| 复制语法 | 复制相关命令全面从 SLAVE/MASTER 改为 REPLICA/SOURCE |
| 直方图 | 直方图统计支持自动更新，无需手动维护 |
| GTID 复制 | GTID 作为更推荐的默认复制模式，配置更简单 |
| 废弃功能 | 查询缓存彻底移除，mysql_upgrade 工具移除 |

## 适用场景

- **新系统上线**：2026 年上线的所有新项目，直接以 8.4.x 的当前最新补丁版本为基线
- **现有 8.0 系统迁移**：迁移目标锁定 8.4.x，不要迁到 8.1~8.3 等 Innovation 版本
- **开发测试环境**：开发和测试环境使用与生产相同的 8.4.x 版本，避免版本差异导致的环境不一致问题
- **容器化部署**：使用官方 Docker Hub 上的 `mysql:8.4` 或 `mysql:8.4.x` 镜像，指定具体版本号而不是浮动标签

```bash
# Docker 使用方式（指定具体版本，推荐）
docker pull mysql:8.4.3
docker run -d \
    --name mysql84 \
    -e MYSQL_ROOT_PASSWORD=YourPassword@2026 \
    -p 3306:3306 \
    mysql:8.4.3
```

## 常见问题

**直接从 5.7 升级到 8.4 可以吗？**

官方不支持跨主版本直接升级，需要先升级到 8.0 的最新补丁版，再从 8.0 升级到 8.4。所以 5.7 → 8.0 → 8.4 是两步操作。每一步都要用升级检查工具（`util.checkForServerUpgrade()`）提前扫描兼容性问题。

**8.4.0 和 8.4.3 在功能上有差异吗？**

LTS 系列的补丁版本只包含 bug 修复和安全补丁，不引入新功能，也不做行为变更。8.4.0 和 8.4.3 的 SQL 功能集完全相同，只是稳定性和安全性有所提升。这就是为什么推荐用最新补丁版本而不是固守 .0 版本。

**用 Docker 部署 MySQL 8.4 时，标签用 `mysql:8.4` 还是 `mysql:8.4.3`？**

推荐用具体版本号 `mysql:8.4.3`。`mysql:8.4` 这种浮动标签会随新补丁版发布而更新，在不知情的情况下可能导致容器重建后版本变更。生产环境应当明确固定版本号，升级时有意识地修改。

## 注意事项

- 不要在生产环境使用 `-preview`、`-rc` 等非 GA 版本，这些版本没有正式支持。
- 升级补丁版本（如 8.4.2 → 8.4.3）前，应当在测试环境先运行一段时间，确认核心业务 SQL 行为无变化后再升级生产。
- 关注 MySQL 官方 Release Notes 和 Oracle 的 CPU（Critical Patch Update）公告，高危安全漏洞修复需要及时跟进，不能以"怕升级出问题"为由无限期推迟。
- 8.4 默认启用了很多 8.0 中需要手动配置的安全特性，安装后应检查认证插件配置、密码策略等，确保与业务需求匹配。

---

## 总结

2026 年生产环境的 MySQL 版本选择已经没有太多争议，MySQL 8.4.x LTS 是明确的答案。在 8.4.x 的具体选择上，使用当前最新补丁版本，不长期停留在 .0 版本。在社区版和企业版之间，根据团队对官方支持和额外工具的需求做选择——技术能力强的团队社区版完全够用，有 SLA 合同要求的大型项目企业版更合适。无论哪种选择，核心是：用有长期官方保障的版本，不用 EOL 或即将 EOL 的版本。

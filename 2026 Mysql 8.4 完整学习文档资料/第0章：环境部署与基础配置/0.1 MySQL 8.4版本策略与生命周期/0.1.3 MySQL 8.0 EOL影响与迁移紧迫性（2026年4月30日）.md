# MySQL 8.0 EOL 影响与迁移紧迫性（2026年4月30日）

MySQL 8.0 的 End of Life 日期是 2026 年 4 月 30 日。这不是一个可以忽略的技术细节，对于仍在运行 MySQL 8.0 的生产系统，EOL 意味着一系列实际的风险和变化，需要在截止日期前完成迁移评估和实施。

---

## EOL 意味着什么

EOL（End of Life）不是指 MySQL 8.0 会停止运行，而是指 Oracle 官方停止为 8.0 提供：

- **安全补丁**：新发现的安全漏洞不再有官方修复版本
- **Bug 修复**：已知 bug 不会再有补丁版本发布
- **技术支持**：购买了 Oracle 支持服务的企业无法再获得针对 8.0 的技术支持
- **文档更新**：官方文档不再同步更新 8.0 相关内容

从 2026 年 5 月 1 日起，MySQL 8.0 进入"自生自灭"状态——数据库本身继续能运行，但没有官方的安全保障。

---

## EOL 后的实际风险

### 安全漏洞无修复

数据库软件漏洞是黑客攻击的重要入口。EOL 后，一旦 MySQL 8.0 被发现新的安全漏洞（CVE），官方不会发布补丁，系统只能依赖网络层隔离、防火墙规则等外部手段做被动防御。这种防御是有限的，不能替代软件本身的安全修复。

历史上 MySQL 每年都有若干安全漏洞被披露，在 Oracle 的 CPU（Critical Patch Update）中统一修复。8.0 EOL 后，这些修复只会覆盖仍在支持期内的版本（8.4 LTS 等）。

### 合规风险

很多安全合规标准明确要求使用供应商官方维护的软件版本：

| 合规标准 | 相关要求 |
|---------|---------|
| PCI DSS 6.3.3 | 所有系统组件须受到安全补丁保护 |
| ISO 27001 A.12.6.1 | 及时安装安全更新，管理已知漏洞 |
| SOC 2 CC7.1 | 监控和维护系统组件安全性 |
| 等保三级（中国） | 要求软件及时更新安全补丁 |

在审计时，使用 EOL 版本的数据库往往是发现项，可能导致审计不通过或需要提交整改计划。

### 技术支持断档

购买了 Oracle MySQL Enterprise Edition 的客户，合同中的技术支持服务会在 8.0 EOL 后无法覆盖 8.0 相关问题，遇到复杂故障只能依赖社区资源，响应时效和质量无法保证。

## MySQL 8.0 到 8.4 的主要变化

迁移前需要了解 8.4 相对 8.0 的重要变化，以便评估兼容性风险：

| 变化类型 | 具体内容 |
|---------|---------|
| 认证插件 | `mysql_native_password` 在 8.4 中默认禁用，客户端驱动需要支持 `caching_sha2_password` |
| 命令语法 | `SHOW MASTER STATUS` 改为 `SHOW BINARY LOG STATUS`；`SHOW SLAVE STATUS` 改为 `SHOW REPLICA STATUS` |
| 参数变更 | `innodb_log_file_size` + `innodb_log_files_in_group` 被 `innodb_redo_log_capacity` 取代 |
| 参数变更 | `expire_logs_days` 被 `binlog_expire_logs_seconds` 取代 |
| 功能移除 | `mysql_upgrade` 工具移除，升级逻辑集成到服务启动时自动执行 |
| 功能移除 | 查询缓存相关参数（`query_cache_*`）彻底移除 |
| 废弃特性 | 非标准外键引用非唯一索引的行为废弃 |
| GTID 复制 | 8.4 中 GTID 复制成为更推荐的默认配置 |

## 迁移步骤概览

### 第一步：评估现状

```sql
-- 在现有 8.0 环境上检查版本
SELECT VERSION();

-- 检查是否使用了废弃的认证插件
SELECT user, host, plugin FROM mysql.user WHERE plugin = 'mysql_native_password';

-- 检查是否有使用了废弃语法的存储过程和函数
-- 可通过 information_schema.ROUTINES 查看存储过程内容
SELECT ROUTINE_NAME, ROUTINE_TYPE, ROUTINE_DEFINITION 
FROM information_schema.ROUTINES 
WHERE ROUTINE_SCHEMA = 'your_database';
```

### 第二步：使用官方升级检查工具

```bash
# MySQL Shell 的升级检查工具（推荐方式）
mysqlsh -- util checkForServerUpgrade root@localhost:3306 \
    --outputFormat=JSON \
    --targetVersion=8.4.0

# 或在 MySQL Shell 交互模式中
\connect root@localhost:3306
util.checkForServerUpgrade()
```

这个工具会检测当前配置和数据中与 8.4 不兼容的内容，生成详细报告，是迁移前的必要步骤。

### 第三步：测试环境验证

在测试环境部署 MySQL 8.4，导入生产数据，运行业务 SQL 和应用程序，观察是否有异常。重点关注：
- 使用 `mysql_native_password` 的用户账号登录情况
- 使用废弃参数的配置文件
- 使用旧语法的监控脚本（如 `SHOW MASTER STATUS`）

### 第四步：制定切换方案

常见方案是搭建 8.4 从库，先同步到与主库数据一致，测试验证后在业务低峰期切换写入流量，最终将旧 8.0 主库下线。

```sql
-- 在 8.4 新实例上配置为 8.0 的从库
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '旧8.0主库IP',
    SOURCE_USER = 'repl_user',
    SOURCE_PASSWORD = '复制密码',
    SOURCE_AUTO_POSITION = 1;
START REPLICA;
SHOW REPLICA STATUS\G
```

## 常见问题

**EOL 后能继续用 MySQL 8.0 多久？**

技术上没有硬性限制，数据库软件不会因为 EOL 而停止运行。但实际上，每过一段时间，暴露在公网的旧版本数据库面临的安全风险就会增加，且漏洞得不到修复。对于内网隔离良好、不涉及敏感数据的低风险系统，短期延迟迁移风险相对可控；对于公网可达或存储敏感数据的系统，应尽快迁移。

**从 8.0 直接升级到 8.4 会不会有数据丢失？**

正常升级流程不会导致数据丢失。MySQL 升级是原地升级或使用从库切换的方式，不需要删除数据。但升级前务必做完整备份，以备回滚需要。

**升级后旧的应用程序不兼容怎么办？**

主要兼容性问题来自认证插件变更。如果应用驱动不支持 `caching_sha2_password`，可以在迁移初期临时在 my.cnf 中重新启用 `mysql_native_password`（8.4 中可以手动开启），给应用留出升级窗口，然后再逐步切换。

## 注意事项

- EOL 日期以 Oracle 官方声明为准，历史上有少数版本的 EOL 日期曾调整，关注官方渠道是保险做法。
- 不要把"升级到 8.4"和"升级到最新版"混为一谈。8.4 是 LTS 版本，8.4.x 的补丁版会持续发布；MySQL 9.x 是 Innovation 系列，不是生产升级的目标。
- 在升级前使用 `mysqldump --all-databases` 或 XtraBackup 做完整备份，这是任何数据库变更的基本操作规范。
- 企业级用户应当向 Oracle 确认自己的支持合同条款，了解 EOL 对合同服务的具体影响，避免出现"以为有保障但实际没有"的情况。

## 总结

MySQL 8.0 的 EOL 日期是 2026 年 4 月 30 日，这是一个必须认真对待的节点。EOL 后继续运行 8.0 意味着接受无安全补丁、可能违反合规要求、失去官方技术支持三重风险。从现在到 2026 年 4 月，只有几个月时间，越早开始迁移评估，给测试和回滚留出的缓冲时间就越充裕。MySQL 8.4 LTS 是直接的目标版本，主要兼容性工作集中在认证插件、废弃参数和监控脚本的调整上。

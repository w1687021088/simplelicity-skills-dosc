# 字符集配置 utf8mb4 与排序规则选择

字符集和排序规则的选择是 MySQL 配置中最容易被忽视、出了问题又最难排查的部分。很多乱码问题、emoji 存不进去、排序结果奇怪等问题，根源都在这里。MySQL 8.4 在字符集方面的默认值已经非常合理，但仍然需要理解背后的逻辑，才能在不同业务场景下做出正确决策。

---

## utf8 与 utf8mb4 的区别

MySQL 里有两个容易混淆的字符集：`utf8` 和 `utf8mb4`。

- **`utf8`（实际上是 utf8mb3）**：最多支持 3 字节的 Unicode 字符，覆盖了基本多文种平面（BMP），但无法存储 4 字节字符，例如大多数 emoji（😀 是 U+1F600，需要 4 字节）、部分中文扩展字符（如某些生僻字）。
- **`utf8mb4`**：真正的 UTF-8 实现，支持完整的 Unicode（1~4 字节），能存储所有 emoji 和扩展字符。

MySQL 8.0 开始，内部已将 `utf8` 视为 `utf8mb3` 的别名，并计划在将来移除 `utf8` 别名。MySQL 8.4 中，`utf8mb4` 是默认字符集，**新项目应始终使用 `utf8mb4`，不要用 `utf8`**。

```sql
-- 查看 MySQL 8.4 的默认字符集
SHOW VARIABLES LIKE 'character_set_server';
-- 结果：utf8mb4（8.0+ 的默认值）
```

## 排序规则（Collation）的命名规律

排序规则决定了字符串的比较和排序行为，命名格式为：`字符集_语言/标准_特性`。

常见 utf8mb4 排序规则：

| 排序规则 | 说明 |
|---------|------|
| `utf8mb4_general_ci` | 旧版通用规则，不完全符合 Unicode 标准，大小写不敏感 |
| `utf8mb4_unicode_ci` | Unicode 标准排序，大小写不敏感，但基于旧版 Unicode |
| `utf8mb4_0900_ai_ci` | Unicode 9.0，口音不敏感（ai），大小写不敏感（ci），MySQL 8.0 新增，**推荐** |
| `utf8mb4_0900_as_ci` | Unicode 9.0，口音敏感（as），大小写不敏感（ci） |
| `utf8mb4_0900_as_cs` | Unicode 9.0，口音敏感，大小写敏感（cs） |
| `utf8mb4_bin` | 按二进制值排序，区分大小写和口音，最严格 |
| `utf8mb4_zh_0900_as_cs` | 中文排序规则，按拼音排序 |

**命名后缀解读：**
- `ci`（case insensitive）：大小写不敏感，`A` 和 `a` 视为相同
- `cs`（case sensitive）：大小写敏感
- `ai`（accent insensitive）：口音不敏感，`é` 和 `e` 视为相同
- `as`（accent sensitive）：口音敏感
- `bin`：按字节二进制值比较

## MySQL 8.4 的默认排序规则

MySQL 8.4（和 8.0）的默认字符集和排序规则：

```sql
SHOW VARIABLES LIKE 'character_set_server';   -- utf8mb4
SHOW VARIABLES LIKE 'collation_server';        -- utf8mb4_0900_ai_ci
```

`utf8mb4_0900_ai_ci` 相对 `utf8mb4_general_ci` 有明显改进：遵循 Unicode 9.0 标准，多语言排序更准确，性能也有提升。对于大多数新项目，`utf8mb4_0900_ai_ci` 是推荐的默认排序规则。

## 配置字符集的四个层级

MySQL 字符集可以在四个层级分别配置，低级别会覆盖高级别，但前提是更低级别有明确设置：

| 层级 | 范围 | 配置方式 |
|------|------|---------|
| 服务器级 | 全局默认 | my.cnf `[mysqld]` 段 |
| 数据库级 | 指定数据库的默认 | `CREATE DATABASE ... CHARACTER SET ...` |
| 表级 | 指定表的默认 | `CREATE TABLE ... DEFAULT CHARSET ...` |
| 列级 | 指定列 | 列定义中 `CHARACTER SET ... COLLATE ...` |

**优先级（从低到高）**：服务器 < 数据库 < 表 < 列

```sql
-- 数据库级别设置
CREATE DATABASE myapp
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

-- 表级别设置
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    PRIMARY KEY (id)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

-- 列级别设置（针对特殊需求，如某列需要大小写敏感）
CREATE TABLE articles (
    id INT NOT NULL AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    token VARCHAR(64) NOT NULL COLLATE utf8mb4_bin,  -- token 区分大小写
    PRIMARY KEY (id)
);
```

## my.cnf 字符集配置

```ini
[mysqld]
# 服务端字符集和排序规则
character-set-server = utf8mb4
collation-server = utf8mb4_0900_ai_ci

# 确保连接字符集也是 utf8mb4（8.0+ 通常默认，但明确配置更稳妥）
init_connect = 'SET NAMES utf8mb4'

[client]
# 客户端默认字符集
default-character-set = utf8mb4
```

```sql
-- 查看所有字符集相关变量
SHOW VARIABLES LIKE '%character%';
SHOW VARIABLES LIKE '%collation%';

-- 查看当前连接的字符集设置
SHOW VARIABLES LIKE 'character_set_client';      -- 客户端发送的字符集
SHOW VARIABLES LIKE 'character_set_connection';  -- 连接层转换字符集
SHOW VARIABLES LIKE 'character_set_results';     -- 返回给客户端的字符集

-- 在连接时设置字符集
SET NAMES utf8mb4;
-- 等价于同时设置 character_set_client、character_set_connection、character_set_results 为 utf8mb4
```

## 排序规则对查询结果的影响

```sql
-- 创建测试表
CREATE TABLE collation_test (
    name VARCHAR(50)
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

INSERT INTO collation_test VALUES ('Alice'), ('alice'), ('ALICE'), ('bob');

-- ci（大小写不敏感）：三个 Alice 被视为相同
SELECT name FROM collation_test WHERE name = 'alice';
-- 结果：Alice, alice, ALICE（三行都返回）

-- 使用二进制排序规则进行区分
SELECT name FROM collation_test WHERE name COLLATE utf8mb4_bin = 'alice';
-- 结果：alice（只有完全一致的一行）

-- 对特定查询临时使用不同排序规则
SELECT * FROM collation_test ORDER BY name COLLATE utf8mb4_zh_0900_as_cs;
-- 按中文拼音排序
```

## 修改已有数据库/表的字符集

```sql
-- 修改数据库字符集（只影响之后创建的表，不影响已有表）
ALTER DATABASE myapp CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 修改表的字符集（同时转换现有数据）
ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 只修改表的默认字符集（不转换现有数据，慎用）
ALTER TABLE users DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

注意：`ALTER TABLE ... CONVERT TO CHARACTER SET` 会重建整张表，是一个代价较高的操作，大表需要在低峰期执行，或使用在线 DDL 工具（如 pt-online-schema-change）。

## 常见问题

**存入 emoji 报错 "Incorrect string value"**

说明该列使用的字符集是 `utf8`（utf8mb3），不支持 4 字节字符。解决方法：

```sql
-- 将列字符集改为 utf8mb4
ALTER TABLE posts MODIFY content TEXT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

**查询时大小写应该敏感但实际不敏感**

默认 `utf8mb4_0900_ai_ci` 是大小写不敏感的。如果需要某个字段区分大小写（如 API token、密码哈希），将该列设为 `COLLATE utf8mb4_bin` 或 `utf8mb4_0900_as_cs`。

**旧系统从 utf8 迁移到 utf8mb4 时数据会损坏吗？**

不会。utf8mb4 是 utf8mb3 的超集，所有能在 utf8mb3 中存储的字符，在 utf8mb4 中同样有效。迁移过程是安全的，迁移后只是增加了对 4 字节字符的支持。

**LIKE 查询时排序规则会影响匹配吗？**

会影响。在 `ci` 排序规则下，`LIKE '%Alice%'` 会匹配 `alice`、`ALICE`。在 `bin` 排序规则下，`LIKE '%Alice%'` 只匹配大小写完全一致的字符串。

## 适用场景

- **国际化应用**：存储多语言内容（包括 emoji、各类文字），必须使用 `utf8mb4`
- **中文应用**：中文不涉及 emoji 时 `utf8mb3` 技术上可用，但新项目没有理由不用 `utf8mb4`
- **需要大小写敏感的字段**：用户名、密码哈希、API token 等，建议列级别使用 `utf8mb4_bin` 或 `utf8mb4_0900_as_cs`
- **中文拼音排序**：使用 `utf8mb4_zh_0900_as_cs` 排序规则

---

## 注意事项

- `utf8mb4_0900_ai_ci` 是 MySQL 8.0+ 的默认排序规则，但在较旧的客户端或框架中可能不认识这个排序规则名称，需要确认驱动兼容性。
- 字符集修改在 DML 层面会立即生效，但索引的排序信息也会改变，大表修改后需要重建索引才能正确使用。
- 混合使用不同排序规则的列做 JOIN 操作时，MySQL 需要进行排序规则转换（collation coercion），可能导致索引失效，性能下降。尽量保持同一个系统内使用统一的排序规则。
- 不要随意修改已有生产表的字符集，这是高风险操作，一旦涉及大表需要充分评估和演练。

---

## 总结

utf8mb4 是 MySQL 中唯一正确的生产用 UTF-8 字符集，旧的 utf8（utf8mb3）在 MySQL 8.4 中已明确为废弃方向。排序规则方面，`utf8mb4_0900_ai_ci` 是新项目的推荐默认选择，在需要区分大小写或口音的场景下使用更严格的规则。字符集配置要从服务器、数据库、表、列四个层级统一规划，避免混用导致隐性问题。

# 日志文件配置（Error Log、General Log）

MySQL 有多种日志，各自记录不同类型的信息。这份文档聚焦两种最基础的日志：错误日志（Error Log）和通用查询日志（General Log）。前者是定位启动故障和运行时错误的必备工具，后者用于记录所有 SQL 语句，通常只在调试阶段开启。

---

## 错误日志（Error Log）

### 作用

错误日志记录 MySQL 服务的启动和停止事件、严重错误、警告信息，以及初始化时的信息。当 MySQL 无法启动、崩溃或出现异常时，第一个要看的就是错误日志。

### 配置

```ini
[mysqld]
# 错误日志文件路径
log_error = /var/log/mysql/error.log

# 错误日志输出详细程度：1=仅错误, 2=错误+警告, 3=错误+警告+信息（默认2）
log_error_verbosity = 2

# 错误日志的格式（MySQL 8.0+ 新增组件化架构）
# log_error_services 控制日志处理链
# 默认值：log_filter_internal; log_sink_internal
log_error_services = 'log_filter_internal; log_sink_internal'
```

```sql
-- 查看当前错误日志路径
SHOW VARIABLES LIKE 'log_error';

-- 查看日志详细级别
SHOW VARIABLES LIKE 'log_error_verbosity';
```

### 日志内容示例

```
2026-03-14T02:00:01.123456Z 0 [System] [MY-013577] [InnoDB] InnoDB initialization has started.
2026-03-14T02:00:02.456789Z 0 [System] [MY-013578] [InnoDB] InnoDB initialization has ended.
2026-03-14T02:00:02.789012Z 0 [System] [MY-010931] [Server] /usr/sbin/mysqld: ready for connections.
2026-03-14T02:30:00.000001Z 3 [Warning] [MY-010055] [Server] IP address '192.168.1.100' could not be resolved: Name or service not known
2026-03-14T03:00:00.000001Z 5 [ERROR] [MY-013183] [InnoDB] Assertion failure: ...
```

日志格式说明：
- 时间戳（UTC）
- 线程 ID（0 表示主线程）
- 严重级别：`[System]`、`[Note]`、`[Warning]`、`[ERROR]`
- 组件标识：`[InnoDB]`、`[Server]`、`[Repl]` 等
- 错误代码：`[MY-XXXXXX]`
- 消息内容

### MySQL 8.0+ 的错误日志组件化架构

MySQL 8.0 重构了错误日志系统，引入可插拔的组件架构：

| 组件类型 | 常用组件 | 说明 |
|---------|---------|------|
| 过滤器（Filter）| `log_filter_internal` | 根据优先级过滤日志 |
| 过滤器（Filter）| `log_filter_dragnet` | 更灵活的规则过滤 |
| 接收器（Sink）| `log_sink_internal` | 写入本地文件（默认） |
| 接收器（Sink）| `log_sink_json` | 以 JSON 格式输出 |
| 接收器（Sink）| `log_sink_syseventlog` | 写入系统事件日志（Windows Event Log 或 syslog） |

```sql
-- 配置同时写入文件和 JSON 格式（调试用）
SET GLOBAL log_error_services = 'log_filter_internal; log_sink_internal; log_sink_json';
-- 会生成 error.log（普通格式）和 error.log.00.json（JSON格式）两个文件

-- 恢复默认
SET GLOBAL log_error_services = 'log_filter_internal; log_sink_internal';
```

### 手动轮转错误日志

```sql
-- 刷新错误日志（关闭当前日志文件，重新打开）
FLUSH ERROR LOGS;

-- 或使用系统命令
-- mv /var/log/mysql/error.log /var/log/mysql/error.log.old
-- mysql -u root -p -e "FLUSH ERROR LOGS;"
```

## 通用查询日志（General Log）

### 作用

通用查询日志记录所有客户端连接和断开事件，以及所有执行的 SQL 语句（包括管理命令），不论这些语句是否出错。由于记录量极大，生产环境通常关闭，只在特定场景下临时开启调试。

### 配置

```ini
[mysqld]
# 开启通用查询日志（生产环境通常关闭）
general_log = OFF

# 通用查询日志路径（文件输出时）
general_log_file = /var/log/mysql/general.log

# 日志输出目标：FILE（文件）、TABLE（写入 mysql.general_log 表）、FILE,TABLE（两者都写）
log_output = FILE
```

```sql
-- 动态开关通用查询日志（无需重启）
SET GLOBAL general_log = ON;
SET GLOBAL general_log = OFF;

-- 查看当前状态
SHOW VARIABLES LIKE 'general_log%';
SHOW VARIABLES LIKE 'log_output';

-- 临时将日志写入表（便于 SQL 查询日志内容）
SET GLOBAL log_output = 'TABLE';
SET GLOBAL general_log = ON;

-- 查询日志表内容
SELECT event_time, user_host, command_type, argument 
FROM mysql.general_log 
ORDER BY event_time DESC 
LIMIT 20;

-- 清空日志表
TRUNCATE TABLE mysql.general_log;
```

## 两种日志的对比

| 维度 | 错误日志（Error Log） | 通用查询日志（General Log） |
|------|---------------------|--------------------------|
| 记录内容 | 错误、警告、启停事件 | 所有 SQL 语句和连接事件 |
| 生产环境 | 必须开启 | 通常关闭 |
| 磁盘占用 | 小（只记录异常） | 大（高负载下极大） |
| 性能影响 | 极小 | 有一定影响（写入开销） |
| 主要用途 | 故障排查、健康监控 | 全量 SQL 审计、问题复现 |
| 日志格式 | 时间戳 + 级别 + 组件 + 消息 | 时间戳 + 连接 ID + 命令类型 + SQL |

## 常见问题

**MySQL 无法启动，怎么看错误日志？**

```bash
# 找到错误日志路径
cat /etc/my.cnf | grep log_error

# 查看最近的日志内容
tail -100 /var/log/mysql/error.log

# 或使用 journalctl（systemd 环境）
journalctl -u mysqld --since "1 hour ago" | tail -50
```

**错误日志文件越来越大怎么处理？**

配置 logrotate 定期轮转：

```bash
# /etc/logrotate.d/mysql 示例
/var/log/mysql/error.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    postrotate
        mysql -u root -p'密码' -e "FLUSH ERROR LOGS;" 2>/dev/null
    endscript
}
```

**临时开启 General Log 调试后，怎么安全关闭？**

```sql
-- 关闭通用查询日志
SET GLOBAL general_log = OFF;

-- 如果是写入表模式，关闭后也清理一下表
TRUNCATE TABLE mysql.general_log;

-- 恢复为文件输出模式（如果之前改成了 TABLE）
SET GLOBAL log_output = 'FILE';
```

**通用查询日志能记录到某个特定的数据库或用户吗？**

通用查询日志本身不支持过滤，它记录所有用户的所有操作。如果需要按用户或数据库过滤，使用 MySQL Enterprise Audit（企业版功能）或 MariaDB Audit Plugin，或者通过 General Log TABLE 模式后用 SQL 过滤。

## 适用场景

- **错误日志**：任何环境都必须开启，是所有故障排查的起点
- **通用查询日志（临时开启）**：定位"某个应用到底发了哪些 SQL"的问题，复现难以重现的 bug，验证 ORM 框架生成的实际 SQL
- **通用查询日志（持久开启）**：安全审计需要完整 SQL 记录的场景，但需要解决日志存储和轮转问题，以及 I/O 性能影响

---

## 注意事项

- 错误日志路径变更后，需要重启 MySQL 服务才能生效。如果运行时执行 `FLUSH ERROR LOGS`，MySQL 会重新打开当前配置的日志文件路径，不会切换到新路径。
- 通用查询日志在高并发环境下（数千 QPS）会产生大量 I/O，可能影响数据库性能。开启前要评估磁盘 I/O 能力。
- 通用查询日志会记录所有 SQL，包括包含密码的 `ALTER USER` 语句（密码会显示为明文），这是安全隐患，所以调试完要及时关闭。
- 将通用查询日志写入表（`log_output = TABLE`）方便查询，但 `mysql.general_log` 表是 CSV 引擎，不支持索引，数据量大时查询较慢。
- MySQL 8.0+ 的错误日志组件架构比旧版本更灵活，但配置语法也更复杂，建议不要随意修改 `log_error_services`，默认配置已足够日常使用。

---

## 总结

错误日志是 MySQL 运维的基础工具，任何环境都应当配置合理的路径并保持开启。通用查询日志是调试利器，但因为记录量巨大，在生产环境只做临时使用，调试完立即关闭。MySQL 8.0+ 的错误日志采用组件化架构，支持 JSON 格式输出和多种 sink，为日志集成到集中式日志系统（如 ELK Stack）提供了更多灵活性。

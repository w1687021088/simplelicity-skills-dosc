# 时区配置与 system_time_zone 变量

时区问题在 MySQL 中是一个容易被低估的坑，尤其在跨时区部署的分布式系统、Docker 容器环境以及从库架构中。表面上看，读写 DATETIME 和 TIMESTAMP 数据是再普通不过的操作，但时区配置不一致时，数据的实际含义会发生悄然偏移，排查起来非常困难。

---

## MySQL 中的三个时区概念

| 变量 | 说明 | 默认值 |
|------|------|-------|
| `system_time_zone` | MySQL 进程启动时从操作系统继承的时区，只读，无法动态修改 | 操作系统时区 |
| `global.time_zone` | MySQL 服务端全局时区，影响 `NOW()`、`CURRENT_TIMESTAMP` 等函数和 TIMESTAMP 列的存储解读 | `SYSTEM`（表示使用 system_time_zone） |
| `session.time_zone` | 当前会话的时区，覆盖全局设置 | 继承 global.time_zone |

```sql
-- 查看三个时区变量
SELECT @@system_time_zone;         -- 操作系统时区，如 CST 或 Asia/Shanghai
SELECT @@global.time_zone;         -- MySQL 全局时区，默认 SYSTEM
SELECT @@session.time_zone;        -- 当前会话时区，默认 SYSTEM

-- 等效写法
SHOW VARIABLES LIKE '%time_zone%';
```

---

## SYSTEM 与 Asia/Shanghai 的区别

当 `time_zone` 设置为 `SYSTEM` 时，MySQL 使用 `system_time_zone` 的值，即操作系统时区。这在大多数情况下没问题，但有两个潜在风险：

1. **夏令时（DST）问题**：部分国家有夏令时，如果 `system_time_zone` 是 `CST`，它在不同系统上的含义可能不同（美国中部时间 UTC-6/UTC-5，或中国标准时间 UTC+8）。使用命名时区（如 `Asia/Shanghai`）可以消除歧义。

2. **容器和云环境**：容器的系统时区可能与预期不同（Docker 默认 UTC），如果 MySQL 跟随容器时区为 UTC，而应用期望中国时区，写入的 TIMESTAMP 数据会有 8 小时偏差。

**推荐做法**：明确设置 `time_zone = 'Asia/Shanghai'`，不依赖 `SYSTEM`。

---

## 配置时区的方法

### 方法一：my.cnf 静态配置（推荐）

```ini
[mysqld]
default-time-zone = 'Asia/Shanghai'
# 或者
default-time-zone = '+08:00'  # 使用偏移量，更简单但无法处理夏令时
```

使用命名时区（`Asia/Shanghai`）需要 MySQL 已加载时区数据，使用数值偏移（`+08:00`）则不需要。

### 方法二：动态修改（无需重启）

```sql
-- 修改全局时区（对已有连接无效，只影响新连接）
SET GLOBAL time_zone = 'Asia/Shanghai';
SET GLOBAL time_zone = '+08:00';

-- 修改当前会话时区（立即生效，只影响本连接）
SET SESSION time_zone = 'Asia/Shanghai';
SET time_zone = 'Asia/Shanghai';  -- SESSION 可以省略

-- 持久化修改（8.0+ 支持，重启后也生效）
SET PERSIST time_zone = 'Asia/Shanghai';
```

## 加载命名时区数据

使用 `Asia/Shanghai` 这类命名时区，需要 MySQL 的时区表有数据。检查方法：

```sql
-- 检查时区表是否有数据
SELECT COUNT(*) FROM mysql.time_zone_name;
-- 如果结果为 0，说明时区数据未加载
```

加载时区数据的方法：

```bash
# Linux：使用 mysql_tzinfo_to_sql 工具加载系统时区文件
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root -p mysql

# Windows：MySQL 安装包中有 timezone_posix.sql 或 timezone.sql 文件
# mysql -u root -p mysql < "C:\Program Files\MySQL\MySQL Server 8.4\share\timezones.sql"
```

加载完成后无需重启，直接可以使用命名时区。

## DATETIME 与 TIMESTAMP 的时区行为差异

这是时区配置中最重要的细节：

| 类型 | 时区存储行为 | 时区修改的影响 |
|------|------------|-------------|
| DATETIME | 存储字面值，不做时区转换（2026-03-14 10:00:00 就是存 2026-03-14 10:00:00） | 修改时区后读出的值不变 |
| TIMESTAMP | 存储 UTC 时间戳，读写时按当前 session 时区转换 | 修改时区后读出的时间会变 |

```sql
-- 演示差异
CREATE TABLE tz_test (
    dt DATETIME,
    ts TIMESTAMP
);

SET SESSION time_zone = '+08:00';  -- 北京时间
INSERT INTO tz_test VALUES (NOW(), NOW());
-- 假设当前北京时间是 2026-03-14 10:00:00
-- DATETIME 存储：2026-03-14 10:00:00
-- TIMESTAMP 存储：内部存 UTC 2026-03-14 02:00:00（-8小时）

SELECT * FROM tz_test;
-- 时区 +08:00 读出：
-- dt: 2026-03-14 10:00:00
-- ts: 2026-03-14 10:00:00  （从 UTC 02:00 转换回来）

SET SESSION time_zone = '+00:00';  -- 改为 UTC 时区再读
SELECT * FROM tz_test;
-- dt: 2026-03-14 10:00:00  （DATETIME 不变）
-- ts: 2026-03-14 02:00:00  （TIMESTAMP 显示 UTC 时间）
```

## 实际系统中的时区策略

**策略一：全部统一使用 UTC**

所有 MySQL 实例时区设置为 UTC，应用层负责显示时做时区转换。优点是不同地区的服务器数据互通无歧义，TIMESTAMP 最大有效范围可以用到 2038 年；缺点是 SQL 直接查看数据时不直观。

**策略二：服务器本地时区**

MySQL 时区与服务器操作系统时区一致（北京时间 +08:00）。优点是 SQL 直接查看数据时间直观；缺点是跨时区部署时需要额外注意，且 TIMESTAMP 类型的数据在时区切换时会改变显示值。

对于国内业务，两种策略都可行。选定后，所有实例（主库、从库）必须保持一致，否则 TIMESTAMP 列的复制会出现问题。

## 常见问题

**为什么 NOW() 的值和 Linux 系统时间对不上？**

可能是 MySQL 的 `time_zone` 设置与操作系统不同，或者 MySQL 进程继承的 `system_time_zone` 本身就不对（容器环境常见）。

```sql
-- 对比 MySQL 和系统时间
SELECT NOW(), @@system_time_zone, @@global.time_zone;
-- 如果 time_zone 是 SYSTEM，则 NOW() 应与操作系统时间一致
```

**修改了 global.time_zone，已有连接的时区有变化吗？**

没有。`SET GLOBAL time_zone` 只影响新建立的连接，已有连接保持修改前的时区。如果需要立即生效，需要断开重连，或在当前会话用 `SET SESSION time_zone` 修改。

**TIMESTAMP 的最大值是 2038 年问题怎么处理？**

`TIMESTAMP` 类型内部使用 32 位整数存储 Unix 时间戳，最大值是 2038 年 1 月 19 日 UTC 时间 03:14:07。如果系统需要存储 2038 年以后的时间，应使用 `DATETIME` 类型，它支持到 9999 年。

## 适用场景

- **单机国内业务**：`time_zone = '+08:00'` 或 `Asia/Shanghai`，直观简单
- **分布式跨时区系统**：统一使用 UTC，应用层处理时区显示
- **Docker 容器化部署**：明确设置 `time_zone`，不依赖容器操作系统时区
- **全球化应用**：使用命名时区（如 `America/New_York`、`Europe/Berlin`），加载 tzinfo 数据后按地区灵活配置

---

## 注意事项

- `system_time_zone` 是只读的，无法在 MySQL 内部修改。如果需要改变它，只能修改操作系统时区后重启 MySQL 服务。
- 主从复制环境中，主库和从库的 `time_zone` 必须一致，否则 TIMESTAMP 类型的数据在从库上读取时会出现偏差。
- 应用程序与 MySQL 建立连接后，最好显式执行 `SET time_zone`，不依赖数据库的全局默认值，避免因配置差异导致的时间数据问题。
- 存储历史数据时，TIMESTAMP 类型只能存储 1970-01-01 00:00:01 UTC 至 2038-01-19 03:14:07 UTC 范围内的时间，超出范围会存储为 `0000-00-00 00:00:00`。

---

## 总结

MySQL 时区配置涉及三个层面：操作系统时区（决定 `system_time_zone`）、MySQL 全局时区（`global.time_zone`）、会话时区（`session.time_zone`）。建议显式指定 `time_zone = '+08:00'` 或加载时区数据后使用 `Asia/Shanghai`，不依赖 `SYSTEM` 默认值。DATETIME 和 TIMESTAMP 的时区行为存在本质差异，在技术选型时要根据业务对时区敏感性做出明确选择。

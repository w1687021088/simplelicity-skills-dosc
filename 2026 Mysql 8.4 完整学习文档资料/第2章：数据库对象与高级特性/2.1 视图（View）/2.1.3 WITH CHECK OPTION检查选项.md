# WITH CHECK OPTION 检查选项

`WITH CHECK OPTION` 是视图的约束子句，用于限制通过视图进行的 INSERT 和 UPDATE 操作，确保操作后的数据行仍然满足视图的 WHERE 条件。没有此约束时，可以通过视图插入或更新出"逃逸"视图过滤范围的行。

---

## 语法

```sql
CREATE VIEW view_name AS
    SELECT ... FROM ... WHERE condition
    WITH [CASCADED | LOCAL] CHECK OPTION;
```

- `WITH CHECK OPTION`（等同于 `WITH CASCADED CHECK OPTION`）：级联检查，包含当前视图及所有底层视图的 WHERE 条件
- `WITH LOCAL CHECK OPTION`：只检查当前视图的 WHERE 条件，不检查底层视图的条件

---

## 无 CHECK OPTION 时的问题

```sql
-- 不带 CHECK OPTION 的视图
CREATE VIEW active_users AS
SELECT id, username, is_active FROM users
WHERE is_active = 1;

-- 通过视图将某行的 is_active 改为 0（该行从视图中消失）
UPDATE active_users SET is_active = 0 WHERE id = 5;
-- 成功！is_active=0 的行从视图中不可见，数据在底层表中"逃逸"到视图范围外

-- 插入一个 is_active = 0 的行（不满足视图 WHERE 条件）
INSERT INTO active_users (id, username, is_active) VALUES (100, 'test', 0);
-- 也成功！数据写入底层表，但视图查不到
```

---

## WITH CHECK OPTION 阻止逃逸

```sql
-- 加上 WITH CHECK OPTION
CREATE OR REPLACE VIEW active_users AS
SELECT id, username, is_active FROM users
WHERE is_active = 1
WITH CHECK OPTION;

-- 尝试通过视图将 is_active 改为 0
UPDATE active_users SET is_active = 0 WHERE id = 5;
-- ERROR 1369 (HY000): CHECK OPTION failed 'mydb.active_users'

-- 尝试插入 is_active = 0 的行
INSERT INTO active_users (id, username, is_active) VALUES (100, 'test', 0);
-- ERROR 1369 (HY000): CHECK OPTION failed 'mydb.active_users'

-- 允许的操作（满足 WHERE is_active = 1）
UPDATE active_users SET username = 'new_name' WHERE id = 5;  -- 不改变 is_active，允许
INSERT INTO active_users (id, username, is_active) VALUES (100, 'test', 1);  -- is_active=1，允许
```

## CASCADED 与 LOCAL 的区别

```sql
-- 假设有视图链：base_view -> mid_view -> top_view

-- 底层视图（无 CHECK OPTION）
CREATE VIEW base_view AS
SELECT id, name, score FROM students WHERE score >= 60;

-- 中间视图（LOCAL CHECK OPTION：只检查自己的条件）
CREATE VIEW mid_view AS
SELECT id, name, score FROM base_view WHERE score >= 70
WITH LOCAL CHECK OPTION;

-- 顶层视图（CASCADED CHECK OPTION：检查所有层的条件）
CREATE VIEW top_view AS
SELECT id, name, score FROM mid_view WHERE score >= 80
WITH CASCADED CHECK OPTION;

-- 通过 mid_view 插入 score=65 的行
INSERT INTO mid_view (id, name, score) VALUES (1, 'Alice', 65);
-- LOCAL：只检查 mid_view 的条件（score >= 70），65 < 70，INSERT 失败
-- 即使 base_view 没有 CHECK OPTION，mid_view 的 LOCAL 只管自己

-- 通过 top_view 插入 score=75 的行
INSERT INTO top_view (id, name, score) VALUES (2, 'Bob', 75);
-- CASCADED：检查 top_view（score >= 80，失败），不需要看更多了
-- CASCADED 会级联检查整条视图链上有 CHECK OPTION 的所有视图
```

---

## CASCADED 和 LOCAL 的行为对比

| 场景 | LOCAL | CASCADED |
|------|-------|---------|
| 检查范围 | 只检查当前视图的 WHERE | 级联检查所有底层视图的 WHERE |
| 底层视图无 CHECK OPTION | 不检查底层条件 | 仍然检查底层视图的 WHERE |
| 推荐程度 | 有明确需要时使用 | 默认（更安全，防止视图链逃逸）|

---

## 适用场景

- **数据一致性约束**：确保通过视图的所有写操作不会产生"幽灵数据"（写入底层表但视图查不到）
- **行级访问控制**：用视图限制用户只能操作特定条件的行，加 CHECK OPTION 防止用户绕过条件修改数据
- **多租户隔离**：每个租户通过各自的视图操作数据，CHECK OPTION 确保租户不能修改其他租户的数据

---

## 常见问题

**WITH CHECK OPTION 能替代触发器做数据验证吗？**

在简单的行过滤场景（如只让用户操作自己的数据）中可以替代。但 CHECK OPTION 只检查视图的 WHERE 条件，无法做复杂的业务逻辑验证（如跨列约束、计算字段验证）。复杂验证仍需触发器或应用层。

---

## 注意事项

- `WITH CHECK OPTION` 只对**可更新视图**有意义。如果视图本身不可更新（含 GROUP BY、聚合等），CHECK OPTION 也无法阻止写操作（因为写操作本来就不被允许）。
- 默认（不写 LOCAL 或 CASCADED）行为是 `CASCADED`，即级联检查，这是更安全的选择。如果不确定用哪个，使用默认值。

---

## 总结

`WITH CHECK OPTION` 确保通过视图进行的 INSERT 和 UPDATE 操作后，新的行仍然满足视图的 WHERE 条件。不加时，可以通过视图写入"逃逸"视图范围的数据（写入成功但视图不可见）。`CASCADED`（默认）级联检查整条视图链，`LOCAL` 只检查当前视图条件。在行级访问控制和数据隔离场景中是保证数据安全的重要约束。

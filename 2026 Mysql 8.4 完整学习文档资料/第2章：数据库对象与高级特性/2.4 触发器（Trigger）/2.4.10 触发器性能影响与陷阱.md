# 触发器性能影响与陷阱

触发器是隐式执行的自动化代码，虽然便于维护数据一致性，但使用不当会产生严重的性能问题、难以追踪的 Bug 和不可预期的副作用。在高并发或大数据量场景中，触发器的影响尤为显著。

---

## 触发器的性能代价

```sql
-- 无触发器的 INSERT：仅写入数据
INSERT INTO orders (user_id, amount) VALUES (1, 100);
-- 执行时间：1 单位

-- 有3个触发器（BEFORE INSERT + AFTER INSERT + AFTER UPDATE）时的 INSERT：
-- 1. 执行 BEFORE INSERT 触发器（校验 + 填充字段）
-- 2. 实际插入行
-- 3. 执行 AFTER INSERT 触发器（写审计日志 + 更新统计表）
-- 触发器内的 SQL 在同一个事务内执行，整体延迟显著增加

-- 高频写入时测试对比（简化示意）
-- 无触发器：100,000 INSERT/秒
-- 有2个触发器（每个含1条额外 INSERT）：可能降至 40,000 INSERT/秒
```

---

## 常见性能陷阱

```sql
-- 陷阱1：每行触发一次的触发器在批量操作时累积性能消耗
-- 以下语句影响 50,000 行，触发器执行 50,000 次
UPDATE order_items SET discount = 0.1 WHERE category_id = 5;
-- 触发器中每次都有一条 INSERT（写日志），累计执行 50,000 次 INSERT
-- 性能严重下降，且产生 50,000 条日志记录

-- 陷阱2：触发器中的复杂查询（对每行执行 SELECT）
CREATE TRIGGER trg_bad_perf
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    -- 高开销：每插入一行订单，都执行一次全表扫描
    UPDATE users
    SET total_orders = (SELECT COUNT(*) FROM orders WHERE user_id = NEW.user_id)
    WHERE id = NEW.user_id;
    -- 应该改为增量更新：SET total_orders = total_orders + 1
END;

-- 陷阱3：触发器链（级联触发）
-- orders 表的 AFTER INSERT 触发器中 INSERT inventory_logs
-- inventory_logs 表的 AFTER INSERT 触发器中又 UPDATE orders
-- 可能造成无限循环（MySQL 有递归深度限制，但会抛出错误）
```

## 触发器与事务

```sql
-- 触发器在触发它的 DML 操作所在的事务中执行
-- 触发器失败（SIGNAL 或运行时错误）会回滚整个事务

START TRANSACTION;
INSERT INTO orders (user_id, amount) VALUES (1, 200);
-- AFTER INSERT 触发器执行（在事务内）
-- 如果触发器中的 INSERT audit_log 失败（如 audit_log 表不存在）
-- → 整个 INSERT orders 和触发器的操作都被回滚
COMMIT;
```

## 触发器难以调试的问题

```sql
-- 问题：触发器是隐式的，不知道 INSERT 为什么会触发额外操作
-- 现象：明明只执行了 1 条 INSERT，数据库却写入了 3 条记录

-- 排查方法
-- 1. 首先查看表上的触发器
SHOW TRIGGERS WHERE `Table` = 'orders';

-- 2. 用 EXPLAIN 查看 DML 的执行计划（不会显示触发器，但可以确认查询）
EXPLAIN INSERT INTO orders (user_id, amount) VALUES (1, 100);

-- 3. 使用 Performance Schema 追踪触发器执行
SELECT EVENT_NAME, COUNT_STAR, SUM_TIMER_WAIT/1000000000 AS total_ms
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%trigger%';
```

## 触发器的已知局限

| 局限 | 说明 |
|------|------|
| 不支持 TRUNCATE | TRUNCATE 不触发行级触发器，清空表时不会触发 DELETE 触发器 |
| 不能调用返回结果集的过程 | 触发器内不能调用有 SELECT 结果集的存储过程 |
| 不能显式事务控制 | 触发器内不能 COMMIT/ROLLBACK，共享调用者的事务 |
| 每事件只能有一个触发器 | 同一表的同一事件（BEFORE INSERT）只能有一个触发器 |
| 调试困难 | MySQL 没有原生触发器调试器，只能靠日志表辅助 |
| 不可见性 | 应用层看不到触发器的存在，容易造成"幽灵数据" |

## 最佳实践

```sql
-- 1. 保持触发器简单：只做不得不做的事，复杂逻辑放应用层
-- 2. 增量更新而非全量计算
--    错误：SET count = (SELECT COUNT(*) FROM t WHERE ...)
--    正确：SET count = count + 1

-- 3. 避免在触发器中查询大表
-- 4. 用命名规范标识触发器：trg_[表名]_[timing]_[event]
--    如：trg_users_before_insert, trg_orders_after_update

-- 5. 在高频写入的表上谨慎使用触发器
--    可以考虑用消息队列 + 异步处理代替触发器的副作用逻辑

-- 6. 所有触发器都记录在数据库变更日志中（DDL 变更管控）
```

## 适用场景

- **触发器适用**：严格数据完整性（状态机校验）、简单字段填充（updated_at）、不能改动应用层代码时的补丁逻辑
- **触发器不适用**：高频写入表（>1万 QPS）、复杂业务逻辑（多表联动、HTTP 调用）、需要清晰可调试的业务流程

## 常见问题

**如何临时禁用触发器进行批量数据导入？**

MySQL 没有 `DISABLE TRIGGER` 语法。常见做法是在触发器内用一个用户变量作为开关：
```sql
-- 触发器内加判断
IF @disable_triggers IS NULL OR @disable_triggers = 0 THEN
    -- 正常执行触发器逻辑
END IF;

-- 导入数据前关闭
SET @disable_triggers = 1;
-- 批量 INSERT ...
SET @disable_triggers = 0;
```

---

## 注意事项

- 触发器消耗的 CPU 和 I/O 不在应用层 SQL 的执行计划中体现，容易被忽略。在做性能优化时，应将触发器的执行时间纳入整体评估。
- 多层触发器嵌套（触发器 A 的操作触发触发器 B）会使问题排查极为困难，建议尽量避免触发器间的依赖关系。

---

## 总结

触发器虽然方便，但有显著的性能代价（每行执行一次）、隐式性（应用层不可见）和局限性（不支持 TRUNCATE、不能有事务控制、每事件只能有一个触发器）。应保持触发器逻辑简单（增量更新而非全量重算），高频写入表要谨慎使用触发器，复杂业务逻辑应放在应用层或存储过程中。调试时用 SHOW TRIGGERS 排查隐式操作。

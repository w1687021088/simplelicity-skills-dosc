# AFTER DELETE 触发器

`AFTER DELETE` 触发器在行数据成功删除之后自动执行。通过 `OLD` 可以读取已被删除的行数据，常用于记录删除操作的审计日志、同步更新统计数据、清理关联的非外键约束数据等。`NEW` 在 DELETE 触发器中不可用。

---

## 语法

```sql
CREATE TRIGGER trigger_name
AFTER DELETE ON table_name
FOR EACH ROW
BEGIN
    -- OLD.col_name：已被删除的行数据（只读）
    -- NEW 不可用
END;
```

- 数据已被删除，`OLD` 只读，无法恢复数据
- AFTER DELETE 中抛出异常会回滚整个 DELETE 操作

---

## 基本示例：审计日志

```sql
DELIMITER //

-- 记录用户删除操作的审计日志
CREATE TRIGGER trg_users_after_delete
AFTER DELETE ON users
FOR EACH ROW
BEGIN
    INSERT INTO audit_log (
        table_name,
        record_id,
        action,
        old_data,
        operated_at,
        operated_by
    ) VALUES (
        'users',
        OLD.id,
        'DELETE',
        JSON_OBJECT(
            'username', OLD.username,
            'email',    OLD.email,
            'status',   OLD.is_active,
            'created',  DATE_FORMAT(OLD.created_at, '%Y-%m-%d %H:%i:%s')
        ),
        NOW(),
        USER()
    );
END //

DELIMITER ;

-- 删除用户后，自动在审计日志中留下记录
DELETE FROM users WHERE id = 100;
```

## 同步统计数据

```sql
DELIMITER //

-- 删除订单后，更新用户的订单统计
CREATE TRIGGER trg_orders_after_delete
AFTER DELETE ON orders
FOR EACH ROW
BEGIN
    -- 减少用户的订单计数
    UPDATE user_stats
    SET order_count = GREATEST(order_count - 1, 0),
        total_spent = GREATEST(total_spent - OLD.amount, 0)
    WHERE user_id = OLD.user_id;
    
    -- 如果删除的是已完成订单，减少完成数
    IF OLD.status = 3 THEN
        UPDATE user_stats
        SET completed_orders = GREATEST(completed_orders - 1, 0)
        WHERE user_id = OLD.user_id;
    END IF;
END //

DELIMITER ;
```

## 级联清理关联数据（不依赖外键）

```sql
DELIMITER //

-- 文章删除后，清理关联的标签关系和评论
CREATE TRIGGER trg_articles_after_delete
AFTER DELETE ON articles
FOR EACH ROW
BEGIN
    -- 清理文章标签关联
    DELETE FROM article_tags WHERE article_id = OLD.id;
    
    -- 软删除评论（而非真正删除，保留记录）
    UPDATE comments SET deleted_at = NOW()
    WHERE article_id = OLD.id AND deleted_at IS NULL;
    
    -- 减少分类下的文章计数
    UPDATE categories
    SET article_count = GREATEST(article_count - 1, 0)
    WHERE id = OLD.category_id;
END //

DELIMITER ;
```

## BEFORE DELETE vs AFTER DELETE 选择

| 需求 | 推荐时机 |
|------|---------|
| 阻止删除（条件校验）| BEFORE DELETE |
| 删除前归档到历史表 | BEFORE DELETE（确保归档在删除前完成）|
| 删除后写审计日志 | AFTER DELETE |
| 删除后更新统计 | AFTER DELETE |
| 删除后清理关联 | AFTER DELETE 或 BEFORE DELETE（均可）|

---

## 适用场景

- **删除审计**：记录谁删除了哪条记录（JSON 格式存储被删行的完整数据）
- **统计同步**：删除后减少计数器（用 GREATEST 防止减为负数）
- **关联数据清理**：删除主记录后清理外键关系之外的关联数据
- **取消预约占位**：订单删除后释放座位、库存等预占资源

---

## 常见问题

**AFTER DELETE 中可以回滚已删除的数据吗？**

不可以直接"回滚" DELETE，但 AFTER DELETE 触发器中可以重新 INSERT 回去（如果真的需要取消删除），但这样做会导致错误语义，更好的做法是在 BEFORE DELETE 中用 SIGNAL 阻止不应该的删除操作。

---

## 注意事项

- AFTER DELETE 触发器中对 `OLD` 的数据只能读取，不能修改。如果触发器执行失败（抛出异常），整个 DELETE 操作会回滚，被删除的数据会恢复。
- 高频 DELETE 操作的表（如日志表、过期数据清理）应谨慎添加 AFTER DELETE 触发器，每次删除都会额外执行触发器逻辑，可能显著影响清理性能。

---

## 总结

`AFTER DELETE` 触发器在行成功删除后执行，通过 `OLD` 读取已删除的数据（只读）。适合记录删除审计日志、同步更新统计数据、清理不依赖外键的关联数据。与 BEFORE DELETE 的区别：BEFORE 可以阻止删除，AFTER 适合事后响应（日志、统计、清理）。TRUNCATE TABLE 不触发行级触发器。

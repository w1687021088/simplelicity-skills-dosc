# 预处理语句防 SQL 注入

SQL 注入是通过在用户输入中嵌入恶意 SQL 片段来改变原始查询语义的攻击方式。预处理语句通过将 SQL 结构与数据值分离（`?` 占位符），从根本上杜绝了用户输入影响 SQL 语义的可能性，是防止 SQL 注入最可靠的手段。

---

## SQL 注入攻击示例

```sql
-- 危险的字符串拼接方式（存在 SQL 注入风险）
-- 假设应用层代码（PHP/Python/Java）直接拼接用户输入：
-- $user_input = "' OR '1'='1";
-- $sql = "SELECT * FROM users WHERE username = '" + user_input + "'";
-- 实际执行的 SQL：
SELECT * FROM users WHERE username = '' OR '1'='1';
-- 结果：返回所有用户（攻击者绕过了身份验证）

-- 更危险的注入（删表）：
-- $user_input = "'; DROP TABLE users; --"
-- 实际执行：
SELECT * FROM users WHERE username = ''; DROP TABLE users; --';
-- 如果允许多语句，users 表被删除
```

## 预处理语句如何防注入

```sql
-- 安全的预处理语句方式
PREPARE stmt FROM 'SELECT * FROM users WHERE username = ?';

-- 设置用户输入为参数（无论输入什么，都只是值，不会改变 SQL 结构）
SET @user_input = "' OR '1'='1";  -- 注入尝试
EXECUTE stmt USING @user_input;
-- 实际执行：WHERE username = "' OR '1'='1"
-- MySQL 把整个字符串当作 username 的值来比较，没有任何用户会这个用户名
-- 查询结果：空（没有匹配的用户），注入失败

SET @user_input = "'; DROP TABLE users; --";
EXECUTE stmt USING @user_input;
-- 实际执行：WHERE username = "'; DROP TABLE users; --"
-- 同样只是字符串比较，DROP TABLE 不会执行

DEALLOCATE PREPARE stmt;
```

## 各类注入场景下的防护

```sql
-- 场景1：登录验证（最常被注入的场景）
PREPARE stmt_login FROM 
    'SELECT id, username, role FROM users WHERE username = ? AND password_hash = SHA2(?, 256)';

SET @uname = @user_input_username;   -- 来自用户表单
SET @pwd   = @user_input_password;   -- 来自用户表单
EXECUTE stmt_login USING @uname, @pwd;
-- 无论用户输入什么，都只作为值与数据库中的值比较

-- 场景2：搜索查询（LIKE 中的特殊字符）
PREPARE stmt_search FROM 
    'SELECT * FROM products WHERE name LIKE CONCAT(''%'', ?, ''%'')';
SET @keyword = @user_search_keyword;  -- 即使包含 % 或 _ 也只会当成普通字符
EXECUTE stmt_search USING @keyword;

-- 场景3：数字参数（防止整数注入）
PREPARE stmt_page FROM 
    'SELECT * FROM articles ORDER BY id DESC LIMIT ? OFFSET ?';
SET @limit  = 10;
SET @offset = @user_input_page * 10;  -- 应用层确保是整数
EXECUTE stmt_page USING @limit, @offset;
```

## 动态表名的安全处理（无法用 ? 占位）

```sql
DELIMITER //

-- 动态表名不能用 ?，必须白名单校验
CREATE PROCEDURE sp_safe_dynamic_query(IN p_table VARCHAR(64), IN p_id INT)
BEGIN
    -- 白名单校验：只允许访问指定的表
    IF p_table NOT IN ('users', 'orders', 'products') THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '非法的表名，拒绝访问';
    END IF;
    
    -- 通过白名单校验后，安全拼接
    SET @sql = CONCAT('SELECT * FROM `', p_table, '` WHERE id = ?');
    SET @p_id = p_id;
    
    PREPARE stmt FROM @sql;
    EXECUTE stmt USING @p_id;
    DEALLOCATE PREPARE stmt;
END //

DELIMITER ;
```

## 预处理语句安全性的边界

```sql
-- 预处理语句防注入的前提：SQL 结构本身是固定的
-- ? 只防护值注入，无法防护结构注入（表名、列名、排序方向等）

-- 安全：值通过 ? 传入
PREPARE s FROM 'SELECT * FROM orders WHERE status = ?';

-- 不安全：ORDER BY 方向通过字符串拼接（应用层需自行验证只能是 ASC 或 DESC）
SET @order_dir = @user_sort_input;  -- 如果没有校验，用户可以注入任意 SQL
SET @sql = CONCAT('SELECT * FROM orders ORDER BY created_at ', @order_dir);
PREPARE s FROM @sql;   -- 仍然有注入风险！

-- 安全处理 ORDER BY 方向
SET @safe_dir = IF(@user_sort_input = 'DESC', 'DESC', 'ASC');
SET @sql = CONCAT('SELECT * FROM orders ORDER BY created_at ', @safe_dir);
PREPARE s FROM @sql;   -- 只有 ASC 或 DESC 两种可能，安全
```

## 适用场景

- **所有接受用户输入的查询**：搜索、登录、过滤条件，都应使用预处理语句或参数化查询
- **批量插入**：固定结构的批量写入，预处理也能提升性能
- **存储过程中的动态查询**：值参数用 `?`，表名列名用白名单校验

## 常见问题

**应用层已经用了 ORM（如 MyBatis/Hibernate），还需要关注 SQL 注入吗？**

ORM 的参数绑定（如 `#{}` 在 MyBatis 中）内部使用的就是预处理语句，是安全的。但 ORM 也提供了直接拼接 SQL 的方式（如 MyBatis 的 `${}`），使用这些"不安全模式"仍然存在注入风险。应确保所有用户输入通过安全的参数绑定方式传入。

---

## 注意事项

- 预处理语句防注入的核心是**参数与 SQL 结构分离**，服务器在收到 SQL 结构时就完成了解析，之后传入的参数值无法再影响 SQL 的解析树。
- 不要用字符串转义函数（如 `mysql_real_escape_string`）替代预处理语句作为防注入手段，转义函数在特殊编码环境下可能存在漏洞，而预处理语句是协议级别的安全保证。

---

## 总结

预处理语句通过 `?` 占位符将 SQL 结构与数据值彻底分离，是防 SQL 注入最可靠的机制。用户输入的任何内容（包括单引号、注释、分号、DROP TABLE）都只会被当作普通字符串值处理，无法改变 SQL 的解析结构。表名、列名、排序方向等结构性参数无法用 `?` 占位，必须通过白名单校验后再拼接。

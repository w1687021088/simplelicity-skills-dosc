# DEALLOCATE PREPARE 释放语句

`DEALLOCATE PREPARE`（或 `DROP PREPARE`，两者等价）从当前会话中释放一个已由 `PREPARE` 创建的预处理语句，释放其占用的内存和服务器资源。预处理语句使用完毕后应及时释放，是良好的资源管理习惯。

---

## 语法

```sql
{DEALLOCATE | DROP} PREPARE stmt_name;
-- DEALLOCATE PREPARE 和 DROP PREPARE 完全等价，推荐使用前者（更直观）
```

---

## 基本示例

```sql
-- 标准的预处理语句生命周期
PREPARE stmt FROM 'SELECT * FROM users WHERE id = ?';
SET @id = 5;
EXECUTE stmt USING @id;

-- 使用完毕后释放
DEALLOCATE PREPARE stmt;

-- 验证释放后无法再执行
EXECUTE stmt USING @id;
-- ERROR 1243 (HY000): Unknown prepared statement handler (stmt) given to EXECUTE
```

---

## 多次使用后统一释放

```sql
-- 准备一个语句，多次执行，最后统一释放
PREPARE stmt_insert FROM 
    'INSERT INTO logs (user_id, action, created_at) VALUES (?, ?, NOW())';

SET @uid = 1;

-- 多次执行（复用编译结果）
SET @action = 'LOGIN';
EXECUTE stmt_insert USING @uid, @action;

SET @action = 'VIEW_PAGE';
EXECUTE stmt_insert USING @uid, @action;

SET @action = 'LOGOUT';
EXECUTE stmt_insert USING @uid, @action;

-- 所有执行完毕后释放
DEALLOCATE PREPARE stmt_insert;
```

## 在存储过程中的规范用法

```sql
DELIMITER //

CREATE PROCEDURE sp_move_expired_orders()
BEGIN
    DECLARE v_batch_size INT DEFAULT 1000;
    DECLARE v_total      INT DEFAULT 0;
    
    -- 准备批量迁移语句
    PREPARE stmt_move FROM
        'INSERT INTO orders_archive SELECT * FROM orders
         WHERE status = 4 AND created_at < NOW() - INTERVAL 365 DAY
         LIMIT ?';
    
    PREPARE stmt_delete FROM
        'DELETE FROM orders
         WHERE status = 4 AND created_at < NOW() - INTERVAL 365 DAY
         LIMIT ?';
    
    SET @batch = v_batch_size;
    
    batch_loop: LOOP
        EXECUTE stmt_move USING @batch;
        IF ROW_COUNT() = 0 THEN LEAVE batch_loop; END IF;
        
        EXECUTE stmt_delete USING @batch;
        SET v_total = v_total + ROW_COUNT();
    END LOOP batch_loop;
    
    -- 使用完毕后释放两个预处理语句
    DEALLOCATE PREPARE stmt_move;
    DEALLOCATE PREPARE stmt_delete;
    
    SELECT CONCAT('共迁移 ', v_total, ' 条过期订单') AS result;
END //

DELIMITER ;
```

## 什么时候会自动释放

```sql
-- 以下情况预处理语句会自动释放（无需手动 DEALLOCATE）：
-- 1. 当前会话（连接）断开
-- 2. 用相同名称再次 PREPARE（会覆盖旧的预处理语句）

-- 覆盖示例（不报错）
PREPARE stmt FROM 'SELECT 1';
PREPARE stmt FROM 'SELECT 2';   -- 覆盖旧的 stmt（旧的自动释放）
EXECUTE stmt;                   -- 执行的是 SELECT 2

DEALLOCATE PREPARE stmt;
```

## 释放不存在的语句

```sql
-- 释放一个不存在的语句会报错
DEALLOCATE PREPARE non_existent_stmt;
-- ERROR 1243 (HY000): Unknown prepared statement handler (non_existent_stmt) given to DEALLOCATE/RESET

-- 无 IF EXISTS 语法（无法优雅处理，只能在应用层捕获异常）
```

## 适用场景

- **存储过程中的动态 SQL**：过程结束前 DEALLOCATE，防止预处理语句泄漏到其他连接
- **长连接应用**：使用连接池时，每次使用完预处理语句后及时 DEALLOCATE，避免资源积累
- **临时预处理语句**：在脚本中使用后立即释放

---

## 常见问题

**如果连接池重用连接，未释放的预处理语句会影响下一个请求吗？**

会存在风险。如果连接池不在归还连接时重置会话状态，上一个请求遗留的预处理语句在下一个请求中仍然存在（但不会主动执行，只占用内存）。规范做法是在每次使用完预处理语句后立即 DEALLOCATE，或者在应用层使用支持自动管理生命周期的预处理 API（如 JDBC PreparedStatement）。

---

## 注意事项

- 在 MySQL 中，直接使用 SQL 级别的 PREPARE/EXECUTE/DEALLOCATE 是"服务端预处理语句"。大多数客户端驱动（JDBC、Python pymysql 等）有自己的 API 层面预处理语句，它们会自动管理 DEALLOCATE，不需要用户显式调用。
- 一个会话中同时 PREPARE 的语句数量受 `max_prepared_stmt_count` 系统变量限制（默认 16382）。未 DEALLOCATE 的语句超过此上限会报错 `ERROR 1461: Can't create more than max_prepared_stmt_count statements`。

---

## 总结

`DEALLOCATE PREPARE stmt_name` 释放预处理语句，等价于 `DROP PREPARE stmt_name`。预处理语句使用完毕后应显式 DEALLOCATE，特别是在存储过程和长连接中。会话断开或用相同名称再次 PREPARE 时自动释放。释放不存在的语句会报错（无 IF EXISTS 语法）。每个会话的预处理语句数量受 `max_prepared_stmt_count` 限制。

## 主从复制

**MySQL 主从复制的原理是什么？**

MySQL 主从复制基于 Binlog（二进制日志），分为三个步骤：

1. **主库写 Binlog**：主库执行的所有数据变更（INSERT/UPDATE/DELETE/DDL）都记录到 Binlog 中
2. **I/O 线程传输**：从库的 I/O 线程连接到主库，请求 Binlog。主库的 Dump 线程将 Binlog 事件发送给从库，从库将收到的事件写入本地的 Relay Log（中继日志）
3. **SQL 线程重放**：从库的 SQL 线程（或多个 Worker 线程）读取 Relay Log 中的事件并执行，将数据变更应用到从库

复制的三种模式：
- **异步复制**（默认）：主库提交事务后不等从库确认，直接返回客户端。性能最好但可能丢数据（主库故障时从库可能落后）
- **半同步复制**（Semi-Sync）：主库提交事务后等待至少一个从库确认收到 Binlog 后才返回。平衡了性能和数据安全
- **组复制/MGR**（Group Replication）：基于 Paxos 协议的多主复制，所有节点达成共识后才提交。数据一致性最强

面试官关注点：三个线程（Dump/IO/SQL）的作用、Binlog 和 Relay Log 的关系、三种复制模式的区别。

---

**主从复制延迟怎么解决？**

常见原因和解决方案：

1. **从库单线程回放**：主库并发写入，从库串行回放。解决：开启多线程复制（`replica_parallel_workers = 8`，`replica_parallel_type = LOGICAL_CLOCK`）
2. **主库大事务**：一个事务修改大量行，从库回放耗时。解决：拆分大事务为小批次（每次 1000~10000 行）
3. **主库 DDL**：ALTER TABLE 等 DDL 在从库也需要执行。解决：使用 pt-online-schema-change 或 gh-ost
4. **从库硬件差**：从库使用了较差的存储设备。解决：从库使用相同配置的硬件
5. **从库读负载高**：从库承担大量读查询，资源竞争。解决：增加从库数量分散读负载

监控手段：
- `SHOW REPLICA STATUS` 的 `Seconds_Behind_Master`（传统但不够精确）
- Performance Schema 的事务时间戳（`replication_applier_status_by_worker`）
- pt-heartbeat（最准确）

面试官关注点：不是只回答"开多线程"，要能分析不同原因并给出针对性方案。

---

**半同步复制和异步复制的区别？AFTER_SYNC 和 AFTER_COMMIT 有什么区别？**

- **异步复制**：主库提交事务后立即返回，不等从库。如果主库崩溃，从库可能缺少最后几个事务
- **半同步复制**：主库提交事务后等待至少一个从库确认收到 Binlog 事件

AFTER_SYNC vs AFTER_COMMIT：
- **AFTER_SYNC（增强半同步，MySQL 5.7+ 默认）**：主库将 Binlog 写入磁盘后、提交事务到存储引擎之前，等待从库确认。如果等待期间主库崩溃，该事务在主库上未提交，从库上也有 Binlog，不会丢数据且不会出现主从不一致（phantom read on master）
- **AFTER_COMMIT（传统半同步）**：主库先提交事务到存储引擎，然后等待从库确认。如果等待期间主库崩溃，该事务在主库上已提交但从库可能未收到，failover 后可能丢数据

面试官关注点：AFTER_SYNC 比 AFTER_COMMIT 更安全的原因、"phantom read on master"问题。

## 读写分离

**读写分离的实现方式有哪些？各有什么优缺点？**

| 实现方式 | 优点 | 缺点 |
|---------|------|------|
| 应用层代码实现 | 简单直接，无额外组件 | 侵入业务代码，维护成本高 |
| 数据库中间件（ProxySQL/MyCat/ShardingSphere） | 对应用透明，功能丰富 | 增加架构复杂度，中间件本身需要高可用 |
| MySQL Router | 官方组件，与 InnoDB Cluster 集成好 | 功能相对简单 |
| DNS/VIP 方式 | 简单 | 只能做主从切换，不能做读写分离 |

读写分离的核心问题——主从延迟导致读到旧数据：
- **强一致性读**：路由到主库（写后读 / critical read）
- **最终一致性读**：路由到从库（允许短暂延迟）
- **半一致性读**：检查从库延迟，如果延迟 < 阈值走从库，否则走主库
- **会话一致性**：同一个会话中写操作后的读请求路由到主库

面试官关注点：不只是"读走从库写走主库"，要能讨论主从延迟下的一致性问题和解决方案。

## 分库分表

**什么时候需要分库分表？水平拆分和垂直拆分的区别？**

需要分库分表的信号：
- 单表数据量超过 2000 万~5000 万行（InnoDB 建议范围，取决于行大小和查询模式）
- 单库的 TPS/QPS 达到单机性能上限
- 磁盘空间不足

垂直拆分 vs 水平拆分：

| 对比维度 | 垂直拆分 | 水平拆分 |
|---------|:------:|:------:|
| 拆分方式 | 按列拆分（不同列放不同表/库） | 按行拆分（同表的数据分散到多个表/库） |
| 典型场景 | 将大字段（TEXT/BLOB）拆到独立表 | 订单表按用户 ID 取模分到多个库 |
| 优势 | 减少单行大小，提高查询效率 | 突破单表行数和单库性能上限 |
| 复杂度 | 较低，JOIN 可能跨表 | 较高，跨分片查询复杂 |

常见的水平分片策略：
- **哈希取模**：`shard_id = user_id % N`。数据分布均匀，但扩容（改变 N）需要数据迁移
- **范围分片**：按时间或 ID 范围分。查询范围数据方便，但可能出现热点（最新分片压力大）
- **一致性哈希**：扩容时只需迁移部分数据，但实现复杂

面试官关注点：分库分表后的跨分片查询（JOIN、ORDER BY、COUNT）、分布式事务、全局唯一 ID 生成等问题。

---

**分库分表后全局唯一 ID 怎么生成？**

常见方案：

- **数据库自增 + 步长**：多个库的 AUTO_INCREMENT 设置不同的起始值和步长（如库1=1,3,5... 库2=2,4,6...）。简单但扩容困难
- **UUID**：全局唯一但无序（不适合做主键，因为 B+ 树随机插入导致页分裂），且占 36 字节
- **Snowflake 雪花算法**：64 位 ID = 时间戳(41位) + 机器ID(10位) + 序列号(12位)。有序、性能高，但依赖时钟同步
- **号段模式（Leaf/Tinyid）**：从数据库批量获取一段 ID（如 1~1000），用完再取下一段。减少数据库访问，性能好
- **Redis INCR**：使用 Redis 的原子自增。性能好但增加了对 Redis 的依赖

面试官关注点：每种方案的优缺点和适用场景，Snowflake 的时钟回拨问题。

## 高可用架构

**常见的 MySQL 高可用架构有哪些？**

- **主从 + VIP/Keepalived**：一主一从（或多从），通过 VIP 实现主库故障时自动切换。简单但切换时间较长（秒级），可能丢数据
- **MHA（Master High Availability）**：自动检测主库故障，从最新的从库中选择新主库，补齐 Binlog 差异后切换。经典方案但已停止维护
- **InnoDB Cluster（MGR + MySQL Router + MySQL Shell）**：MySQL 官方的高可用方案。基于组复制（Group Replication），支持自动故障检测和 failover。最少 3 节点，基于 Paxos 协议保证数据一致性
- **ProxySQL + 半同步复制**：ProxySQL 做读写分离和故障检测，半同步复制保证数据不丢。灵活但架构复杂
- **InnoDB ClusterSet**：MySQL 8.0.27+ 引入，支持跨数据中心的 InnoDB Cluster 灾备

面试官关注点：各方案的 RPO/RTO、适用规模、是否了解 MGR/InnoDB Cluster。

---

**MySQL Group Replication（MGR）的工作原理？单主模式和多主模式的区别？**

MGR 基于 Paxos（实际是 Mencius 变种）协议实现多节点之间的分布式共识。

工作流程：
1. 任意节点执行写操作后，将事务的写集（Write Set）广播给组内所有节点
2. 所有节点通过 Paxos 协议对事务的全局顺序达成共识（Certification 过程）
3. 如果事务与其他已提交的事务没有冲突，认证通过，所有节点都提交该事务
4. 如果有冲突（修改了相同的行），后到达的事务被回滚

| 对比维度 | 单主模式 | 多主模式 |
|---------|:------:|:------:|
| 写入节点 | 只有 Primary 可写 | 所有节点可写 |
| 故障切换 | 自动选举新 Primary | 无需切换，其他节点继续写 |
| 冲突概率 | 低（只有一个写入点） | 高（多个节点同时写可能冲突） |
| 使用限制 | 较少 | 不支持 SERIALIZABLE、外键级联、大事务更受限 |
| 推荐场景 | 大多数场景 | 多地域低延迟写入 |

面试官关注点：Certification 过程、Write Set 冲突检测、单主 vs 多主的选择依据。

## 备份恢复

**mysqldump、xtrabackup、MySQL Enterprise Backup 的区别？**

| 对比维度 | mysqldump | xtrabackup | MySQL Enterprise Backup |
|---------|:---------:|:----------:|:---------------------:|
| 备份类型 | 逻辑备份（SQL 文本） | 物理备份（数据文件拷贝） | 物理备份 |
| 是否阻塞写 | --single-transaction 不阻塞 InnoDB | 不阻塞（热备） | 不阻塞 |
| 备份速度 | 慢（逐行导出） | 快（直接拷贝文件） | 快 |
| 恢复速度 | 慢（逐行插入） | 快（拷贝文件即可） | 快 |
| 增量备份 | 不支持 | 支持 | 支持 |
| 压缩 | 需要外部工具（gzip） | 内置压缩 | 内置压缩 |
| 适用规模 | 小库（< 50GB） | 中大型库 | 中大型库（商业） |
| 跨版本恢复 | 支持（SQL 兼容） | 不支持（文件格式绑定） | 不支持 |
| 费用 | 免费 | 免费（Percona） | 商业许可 |

面试官关注点：大库为什么不能用 mysqldump（太慢）、xtrabackup 的工作原理（拷贝数据文件 + 应用 Redo Log）。

---

**如何实现 MySQL 的时间点恢复（PITR）？**

PITR（Point-in-Time Recovery）的步骤：

1. 恢复最近的全量备份（mysqldump 或 xtrabackup 的备份）
2. 从 Binlog 中找到全量备份之后的所有事件
3. 使用 mysqlbinlog 工具将 Binlog 事件重放到目标时间点

```bash
# 步骤1：恢复全量备份
mysql -u root -p < full_backup.sql

# 步骤2：应用 Binlog 到指定时间点
mysqlbinlog --start-datetime="2024-06-01 00:00:00" \
            --stop-datetime="2024-06-15 14:30:00" \
            mysql-bin.000100 mysql-bin.000101 mysql-bin.000102 \
            | mysql -u root -p

# 或按位置指定：
mysqlbinlog --start-position=12345 --stop-position=67890 \
            mysql-bin.000100 | mysql -u root -p
```

面试官关注点：PITR 依赖 Binlog 的完整性（不能被清理）、全量备份的频率决定 Binlog 重放的量。

## 常见问题

**面试中被问到"设计一个高可用 MySQL 架构"这种开放题怎么回答？**

建议按以下结构回答：①先了解需求（数据量、QPS、RPO/RTO 要求、预算）；②给出方案选型（小规模用主从+半同步，中规模用 InnoDB Cluster，大规模需要分库分表+中间件）；③画出架构图（主库、从库、中间件、应用层的关系）；④讨论关键问题（failover 流程、数据一致性、监控告警）。避免一上来就说"用 MGR"而不讨论需求和取舍。

## 注意事项

- 架构设计题没有标准答案，面试官考察的是你的思考过程和权衡取舍的能力。要展示你理解每种方案的优缺点，能根据具体需求做出合理选择，而不是死记硬背一种方案。
- 提到分库分表时，要注意先讨论是否真的需要分库分表。很多情况下通过优化查询、增加索引、升级硬件、使用缓存等方式可以解决性能问题，分库分表是最后的手段，因为它会带来巨大的架构复杂度。
